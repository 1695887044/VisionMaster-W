# 正运动 ZMotion 连接与排障

> 分类：运动卡 ｜ 来源：插件 Plugin.Motion.ZMotion

这一页只解决三类现场问题：**连不上**、**连上了但不对**、**跑着跑着自己停了**。
所有的状态、报错原文与恢复动作都来自驱动与运动卡基类的实现，照文案反查最快。

参数含义（卡参数 / 轴参数 / 机型能力）在「卡参数与轴参数」那一页，不在这里重复。

## 先把"现在是什么状态"弄准

运动卡状态机只有五种，命令能不能发**完全由它决定**：

| 状态 | 界面含义 | 门禁放行什么 | 怎么恢复 |
| --- | --- | --- | --- |
| 未连接 | 没连过 / 已断开 | 什么都不放（`运动卡未连接`） | 点「连接」，或勾「随方案启动自动连接」 |
| 正在连接运动卡… | 建链中（网口建链可能几百毫秒到几秒） | 全挡（`运动卡正在连接/断开，请稍候`） | 等它结束；长时间停住见下面"连不上" |
| 在线 | 已连接、可运动 | 全部命令 | —— |
| 报警 | 轮询发现硬信号（伺服报警 / 限位 / 急停输入），驱动已自动急停一次 | **只放行清报警与急停**（其余报 `运动卡处于报警状态，请先清除报警`） | 排除原因 → 清报警（回在线）→ **还要重新使能** |
| 已安全停机 | 命令执行失败/超时，或看门狗判失联；队列已清空、逐启用轴减速停 | 全挡（`运动卡已安全停机，请重新连接后再操作`） | **必须先「断开」再「连接」**（连接是幂等的：状态不是"未连接"时点连接不会真的重连） |

两个容易误读的点：

- 连接成功后状态说明**不是**一句"已连接"，而是驱动写的那行：
  `已连接 ECI3428 @ 192.168.0.11（固件 …）｜4 轴｜IO 24 入 / 16 出`。
  这行是排障第一现场：机型对不对、轴数对不对、IO 点数带不带"未核实"，全在里面。
- 「报警」与「已安全停机」是两件事：前者是卡上真的有硬信号（处理完清报警就能回在线），
  后者多半是**通信**问题（问不到话、命令失败），必须重连。

## 连不上：按报错原文分流

| 状态说明 / 报错原文 | 真正的原因 | 处置 |
| --- | --- | --- |
| `未填写控制器 IP 地址` | 「运动卡设置」的连接地址为空 | 填控制器 IP（如 `192.168.0.11`）。这一步之前不会去碰 SDK |
| `运动卡 SDK 不完整：缺少 zmotion.dll。正运动 SDK 最少需要 zauxdll.dll（辅助层）与 zmotion.dll（核心层）两个文件，请把它们一起放到程序目录（VisionMaster.exe 同级）后重新连接` | native 依赖缺失 | 照后半句点名放文件。**这条是驱动逐个文件查过之后点名给的**，可信 |
| `加载运动卡 SDK 失败：…。文件都在，请确认 SDK 与程序位数一致（本程序为 64 位），以及是否被杀毒软件 / 权限拦截` | 文件在但加载不了（位数、拦截、损坏） | 换 64 位版；把程序目录加入杀软白名单；确认文件不是 0 字节或被"网页版"打包截断 |
| `运动卡 SDK 位数不符：…。请换成 64 位版的 zauxdll.dll / zmotion.dll` | 放了 32 位 DLL | 位数不符时 Windows 报的也可能同样是"找不到模块"，所以这条被单独点明；换 64 位 |
| `连接控制器失败（正运动错误码 N）。检查控制器 IP、网线与供电；确认没有被厂商调试软件或另一个本程序实例占用` | `ZAux_OpenEth` 返回非 0 | 按后半句查；错误码 N 可对照厂商手册或报给厂商（本驱动**不做逐码翻译**，SDK 没有码→文案的接口，凭记忆编表会把人引错方向） |
| 反复"正在连接…"很久才失败 | 地址指向了一台不存在/不通的主机 | 先确认本机与控制器同网段（不同网段永远连不上，与软件无关）；再确认控制器已上电、网线链路亮 |

### native DLL 这件事值得单独讲（现场最容易卡半小时）

- **两个文件缺一不可**：`zauxdll.dll`（辅助层）自己还要导入 `zmotion.dll`（核心层）。
- **报错具有迷惑性**：缺任何一个，Windows/.NET 都只说
  `Unable to load DLL 'zauxdll.dll' or one of its dependencies: 找不到指定的模块 (0x8007007E)` ——
  它**不会**告诉你缺的是 `zmotion.dll`，看上去就像"zauxdll.dll 没放对位置"。
  本驱动的做法是在连接失败时自己去查这两个文件在不在，直接点名缺哪个（上面第二条报错）。
- **放哪**：`VisionMaster.exe` **同级目录**。P/Invoke 默认搜的是 exe 旁，**不搜插件目录 `Modules\`** ——
  把 DLL 放在 `Modules\` 里是加载不到的（诊断信息会把这一层也查一遍，所以它会区分"文件其实只在 Modules 里"这种情况）。
- **位数**：本程序是 64 位，必须用 64 位版 SDK。
- **加载时机**：native 库是在**第一次调用 SDK 函数时**才加载的，所以缺文件的报错出现在**点「连接」的那一刻**，
  而不是软件启动时——插件本身能正常加载、能在驱动列表里选到。

## 连不上：逐项确认清单

1. 「运动卡设置」里驱动类型是不是「正运动 ZMotion 运动卡」（DLL 不在 `Modules\` 里就选不到；选了但列表有、连不上是另一回事）。
2. 连接地址填写、无多余空格、与控制器实际 IP 一致。
3. 本机网卡与控制器**同网段**（不同网段必然连不上；这不是软件能绕的）。
4. 控制器已上电、网线链路正常；厂商调试软件（RTSys 等）能连上同一台。
5. **没有被别人占用**：厂商调试软件、或本程序的**另一个实例**已经连着 —— 正运动的网口连接是独占的，
   后连的会失败。
6. `VisionMaster.exe` 同级有 `zauxdll.dll` **和** `zmotion.dll`，都是 64 位。
7. 杀软/权限没有拦截程序目录里的 DLL 加载。
8. 多张卡：逐个连，先排除 IP 冲突或同一台被配了两遍。
9. 都正常但仍失败：记下状态说明里的**正运动错误码**，连同"哪一步失败（连接控制器）"一起报厂商。

## 连上了但不对

| 现象 | 判据在哪 | 说明与处置 |
| --- | --- | --- |
| 8 轴卡只有前 4 根能用 | 状态说明的轴数、日志"未识别机型…" | 机型没认出来，能力按 4 轴 / 24 入 / 16 出兜底。把「机型」栏填准（`ECI3828` 等）后**重连** |
| 状态说明带"（点数未核实，按显示上限列出）" | 该行本身 | 虚拟 PLC（`VPLC532R`）与未识别机型的 IO 点数是常见上限，不是核实值。以实物接线为准 |
| `轴号 5 超出范围（本卡 4 轴）` | 命令被拒（参数无效） | 轴映射里的物理轴号（**0 基**）超出机型轴数，或机型填小了 |
| 位置/行程按倍数错（看起来能跑） | 日志"设置脉冲当量失败（码 N）——位置与目标将按控制器原单位解释" | `SetUnits` 没下发成功，或 `UnitsPerMm` 配反。核对当量后**重连**（当量只在连接时下发） |
| 轴数对、但有些轴在流程下拉里选不到 | 「运动卡设置」轴映射表 | 轴被置为"不启用"；启用的轴才进候选、才被轮询、才会被"停全部轴/清报警"遍历 |
| 轴名选了却不生效 / 动到别的轴 | 启动体检日志 | 跨卡**轴名重复**：注册表按全局唯一名解析，被影子化的那些不会出现在下拉里（刻意不列"选了必然失败"的项）。改轴名，改名要连同该轴已教的点位与凸轮表标签一起走「重命名」入口 |
| 「轴卡 IO」里选了卡却报找不到 | 该步骤的 `ErrorMessage` | 卡级操作按**卡名称**匹配（区分大小写、逐字比较）。卡名称为空时界面回退显示 IP，但流程里匹配的是卡名称本体；卡名称末尾带空格也会与下拉里 Trim 过的值对不上 |
| 每次重连后第一笔运动方向不对 | 该轴的回零与接线 | 重连后驱动会重发当量并重建能力；零点是否可信由流程决定 —— 见「与步骤算子的配合」里"回零要显式放"的那条 |

## 跑着跑着自己停了

### A. 进「报警」：卡上有硬信号

轮询每拍都会检查轴状态位域（bit3 伺服报警 / bit4 正限位 / bit5 负限位 / bit12 急停输入）。
一旦发现，基类**立刻自动执行一次急停**（清空待执行队列 + 插队"停全部轴 + 立即停"）并把卡打进「报警」，
同时报一条故障。这是刻意的：报警还继续执行队列里的下一条命令等于往故障上再压一次。

- 现场表现：流程里「等待到位」报 `等待轴「X」期间出现异常信号：报警：伺服报警`，或「读轴状态」的 `Alarm=true`。
- 处置：排除原因（过流/过载/断线/机械卡阻）→ 清报警 → **重新使能**（清报警走 `DriveClear`，
  逐启用轴执行，**不会自动使能** —— 使能有机械后果，必须人工明确）→ 建议重新回零。
- 部分轴清不掉会报 `部分轴清除报警失败：X(码 N)、Y(码 M)`，说明报警原因还在。

### B. 进「已安全停机」：通信或执行出问题

三条路都会到这里，判据在状态说明：

| 状态说明 | 触发 | 处置 |
| --- | --- | --- |
| `状态轮询连续失败 3 次：…；已安全停机` | 单次轮询抖动不报警（正运动读状态失败会抛异常），连续 3 次才判失联 | 查网线/供电/控制器是否死机；先「断开」再「连接」 |
| `已 N.Ns 未收到状态响应（看门狗超时 3000ms）；已安全停机` | 问不到话（"在线但不应答"与"正常在线"必须分开） | 同上；通信环境差可把轮询周期与看门狗放宽 |
| `控制器句柄无效（可能已断开）` | 句柄已被清（并发断开 / 控制器重启） | 重连 |
| 命令执行失败 / 超时（如回零超时） | 驱动把失败上抛，基类清队 + 逐启用轴**减速停**（`Single_Cancel(轴,2)`，这是收尾不是急停） | 按报错里的操作与建议处理，再重连 |

恢复动作一律是**先「断开」再「连接」**：连接对非"未连接"状态是幂等的（直接返回"已连上"），
所以在「已安全停机」上点连接不会真的重建链路。

> 「自动重连」这一项目前只是配置：运动卡这一层还没有实现自动重连逻辑，掉了要人工接。
> 界面措辞不要当承诺用。

### C. 命令被拒绝（流程报错但卡没事）

| 拒绝原因 | 含义 | 常见处置 |
| --- | --- | --- |
| `运动卡未连接` | 状态不是「在线」 | 连接 |
| `运动卡正在连接/断开，请稍候` | 建链中（几百毫秒到几秒） | 别把连接放流程中间等 |
| `运动卡处于报警状态，请先清除报警` | 报警态不接受普通命令（急停与清报警除外） | 清报警 → 使能 |
| `运动卡已安全停机，请重新连接后再操作` | 见 B | 断开 → 连接 |
| `轴号 N 超出范围（本卡 M 轴）` | 映射与机型不符 | 改轴号或改机型 |
| `目标 X mm 超出软限位 [min, max] mm` | **只有绝对运动校验软限位**；相对运动、点动不查 | 收紧/放宽软限位，或改目标 |
| `该卡不支持回零方式「…」` | 能力协商：脉冲型只上报 3 种 | 换方式，见回零那页 |
| `输出点 N 超出范围（本卡 M 点）` / `输入点 N 无效` | IO 点号超能力（点号 **0 基**） | 核对机型点数与实物接线 |
| `命令队列已满（上限 256 条）` | 命令堆太快或长命令堵住队列 | 加等待、降循环频率、排查是否有轴在报警 |

## 首次上电的最小验证顺序

新设备第一次接真卡，按这个顺序走，每步都只验一件事，出错能立刻定位：

```
① 连接：状态说明里机型、轴数、IO 点数都对得上，无"未识别机型"/"未核实"
② 读轴状态：位置有读数、Enabled=false、无报警/限位
③ 轴使能：Enable=true → 再读状态，Enabled=true（伺服上电、抱闸打开，先确认机构安全）
④ 轴回零：默认「负限位 + Index」；轴先离开开关再试；确认零点方向与坐标符合预期
⑤ 小行程绝对定位：给一个 1~2 mm 的目标 + 明确速度 → 等待到位 → 读位置
   （这一步专验**当量与方向**：走出的距离对不对、正负号对不对）
⑥ 相对定位：+1 mm、−1 mm 各一次（相对不查软限位，靠硬限位兜）
⑦ 读输入：用「轴卡 IO」逐个读关键传感器，确认点号与实物接线一致（0 基）
⑧ 写输出：逐个写气缸/阀，确认点号与动作对应
⑨ 停止：减速停与立即停各试一次；再试一次急停（勾急停），确认队列被清、轴停下
```

每一步都看两个地方：流程步骤的 `Success` / `ErrorMessage`，以及日志里的中文行（下发原文、拒绝原因、看门狗）。

## 常见问题

**Q：`连接控制器失败（正运动错误码 3）` 这个 3 到底什么意思？**
驱动**没有**码→文案的对照表（zauxdll 不提供这种接口），凭记忆编一张会误导排查。
能确定的是：出错的操作是"连接控制器"、分级是"需检修"（不会自动恢复，要人去看）、
建议是"检查控制器 IP、网线与供电；确认没有被厂商调试软件或另一个本程序实例占用"。
具体码的含义查厂商手册，或把码 + 操作一起报给厂商。

**Q：厂商调试软件能连，本程序连不上。**
驱动给连接失败的建议里专门点了这一项：**确认没有被厂商调试软件或另一个本程序实例占用**。
现场做法是先断开厂商软件、关掉多余的本程序实例，再连一次。
其次是地址：本程序要的是控制器 IP，别填成厂商软件里显示的其他名字或主机名。

**Q：本程序开着，厂商软件就连不上，怎么办？**
两边抢同一个控制器连接时，后连的一方会失败（这正是上面那条建议针对的情形）。
联调期的实用做法：控制流程的一侧用本程序，需要改控制器内部参数（回零高速/低速、到位带宽、SPEED、加减速）时
临时切到厂商软件，改完断开再回本程序。

**Q：断电重启控制器后，软件这边还显示"在线"。**
软件不会自己知道控制器重启了。表现是随后**轮询连续失败**或命令超时，然后进「已安全停机」。
稳妥做法：控制器上电后在本程序里先「断开」再「连接」，并按流程首步重新回零。

**Q：「随方案启动自动连接」勾了，启动后却没连上。**
自动连接只在方案加载时对**勾了这项的卡**发起一次连接，一台失败不影响其它台。
失败的原因就是状态说明里那句（多半是控制器还没上电、或 DLL 缺失）。
处理：确认控制器先于软件上电；然后手工点一次连接即可（配置不用改）。

**Q：报警明明消除了，`读轴状态` 还在报？**
清报警把卡从「报警」带回「在线」，但轴状态位是控制器实时回报的：报警原因未真正排除（过流、机械卡阻）会立刻再报。
另外「已安全停机」**不靠清报警恢复**，那需要重连 —— 从状态说明就能分清这两态。

**Q：怎么让软件在报警时自动把轴放下来 / 自动恢复？**
不要指望软件层"自动恢复"：这类自动动作正是现场事故的来源。
本驱动的设计是**卡住并要求人来处理**（报警 → 自动急停；失联 → 安全停机 + 需重连），
需要工艺上自动处置的部分，请在流程里显式写分支（读到 `Alarm=true` → 走「轴卡 IO」的处置动作），
硬件安全回路该断的电必须自己断。
