# 正运动 ZMotion 与步骤算子的配合

> 分类：运动卡 ｜ 来源：插件 Plugin.Motion.ZMotion

这一页讲**流程里的七个运动步骤在这张真卡上实际发生了什么**：同一条流程在仿真卡与真卡上有哪些行为差别、
参数在流程里给还是控制器里给、以及从仿真切到真卡要逐项核对什么。
步骤本身的端口与参数看「运动控制」工具箱里各步骤的帮助页；卡参数看「卡参数与轴参数」；连不上看「连接与排障」。

## 流程层只给"名字"，不给地址

| 层级 | 寻址用什么 | 由谁解析 |
| --- | --- | --- |
| 轴级步骤（轴使能 / 轴回零 / 轴运动 / 等待到位 / 读轴状态 / 轴停止填了轴名时） | **逻辑轴名**（全局唯一） | 一次解析同时得到"哪张卡 + 卡内物理轴号 + 当量 + 软限位" |
| 卡级步骤（「轴卡 IO」、轴停止留空） | **卡名称**（IO 按名匹配，区分大小写） | 宿主按卡名找设备 |
| 「运动卡设置」 | IP、机型、轴号、当量 | 只有这里出现物理接线信息 |

带来的实际效果：**换卡、改接线、改网段都不动流程**，只动映射表。
反过来说，流程里出现"这张卡动不了那根轴"这类问题时，答案一定在映射表里（轴名重复、轴未启用、机型轴数不够），
而不是在流程里。

## 七个步骤在这张卡上的落点

| 步骤 | 正运动 API | 是否等完成 | 在这张卡上的特别注意 |
| --- | --- | --- | --- |
| 轴使能 | `SetAxisEnable(轴,1/0)`；失能前先 `Single_Cancel(轴,2)` | **等**（步骤超时 + 500 ms） | 输出 `Enabled` 以**下一次轮询**读到的 `GetAxisEnable` 为准，所以可能"步骤成功、`Enabled` 还是 false" |
| 轴回零 | 总线型 `BusCmd_Datum(轴,模式码)` + `GetHomeStatus==1`；脉冲型 `Single_Datum` + 轴空闲 | **等**（步骤超时 + 1000 ms） | 总线型支持 8 种方式、脉冲型只 3 种；回零速度/偏移**沿用控制器内参数**；超时前驱动先停轴 |
| 轴运动 | `SetSpeed`(可选) → `SetAccel/SetDecel`(可选) → `SetSramp` → `Single_MoveAbs` / `Single_Move` | **不等**（下发即完成） | 到位必须靠「等待到位」；速度填 0 = 不覆盖；加速度步骤恒不覆盖；曲线恒梯形（`Sramp=0`） |
| 等待到位 | 读 `GetAxisStatus` 的到位位（bit11）+ `GetIfIdle` | 它就是等待本身 | 判据是"到位且不在运动中"，且**报警/限位优先于到位** |
| 读轴状态 | `GetAxisStatus` / `GetIfIdle` / `GetMpos` / `GetAxisEnable` + `GetInMulti`（轮询里） | 立即返回快照 | 位置是**指令位置**；**速度不回读**，`Velocity` 恒 0；报警文案固定"伺服报警" |
| 轴停止 | `Single_Cancel(轴,模式)`；停全部轴 = 逐启用轴取消 | **不等** | 模式 2=减速停、3=立即停；报警态普通停被拒，勾急停可放行 |
| 轴卡 IO | 写 `SetOp(点号,1/0)`；读走轮询快照 `GetInMulti` | 写不等、读即时 | 点号 **0 基**（`IN0`/`OUT0` 就是点号 0）；写输出在「在线」与「报警」都放行 |

## 参数到底在哪儿给（这张卡最容易配错的一层）

一句话原则：**流程管"去哪、多快、等多久"，控制器管"怎么动、怎么找零、到位怎么判"**。

| 想改的东西 | 在哪儿改 | 说明 |
| --- | --- | --- |
| 目标位置 | 流程「轴运动」的 `Target` 端口 | mm，绝对坐标以回零建立的零点为基准 |
| 速度 | 流程「轴运动」的 `Velocity` 端口 | **填 0 时不覆盖**，沿用控制器内该轴当前 SPEED；要确定性就给非零值 |
| 加减速 | **控制器内**（厂商软件）或点位表 | 流程步骤的加速度恒为"不覆盖"（`Accel ≤ 0` 就不写 `SetAccel/SetDecel`）；驱动只在点位运动给正值时下发 |
| S 曲线 / 平滑 | **点位表 / 调试面板** | 每次定位前驱动都写 `SetSramp`：梯形=0、S 曲线=200 ms（固定值，不可调）。流程步骤恒梯形，会把之前设过的 S 清掉 |
| 回零高速/低速、回零偏移 | **控制器内**（厂商软件） | 驱动刻意不覆盖：现场已调好的机构行为不该被软件改写 |
| 到位判断（跟随误差窗口 / 到位带宽） | **驱动器或控制器内** | 「等待到位」读的是卡给的到位位；判得过严会"看着到了却不报到位" |
| 脉冲当量 | 「运动卡设置」的轴映射 `UnitsPerMm` | 连接时 `SetUnits` 下发（下限 0.0001）；**改完要重连** |
| 软限位 | 「运动卡设置」的轴映射 | **只校验绝对运动**；保持默认 ±1000000 mm 等于这道防线是空的 |
| 轴参数弹窗里的编码器/驱动器/跟随误差字段 | 只是**存档记录** | 当前不下发到卡，也不参与任何判断（真实跟随误差窗口要在伺服参数里设） |

## 仿真（虚拟卡）验不到、必须真机验的清单

| 项目 | 为什么仿真验不到 | 真机怎么验 |
| --- | --- | --- |
| 脉冲当量与方向 | 仿真内部就用 mm，不做 `SetUnits` | 小行程（1~2 mm）绝对定位，量实际位移 |
| 真实节拍 | 仿真匀速逐拍推进，无加减速、无 S 曲线 | 用「等待到位」的 `Elapsed` 统计，再定超时 |
| 回零路径 | 仿真固定几百毫秒后直接把位置写 0 | 验开关极性、撞限位方向、Index 有没有 Z 相 |
| 指令位置 vs 编码器位置 | 仿真没有跟随误差概念 | 看驱动器实际位置/跟随误差；外力推动、丢步都会暴露 |
| 速度回报 | 仿真填 `Velocity`，正运动**不读速度**（恒 0） | 判"动没动"一律用 `Moving` |
| 报警含义 | 仿真靠开关注入"伺服报警" | 真实报警码要在驱动器/控制器侧看 |
| IO 点号与实物对应 | 仿真 8 入 8 出，真卡按机型（且部分机型点数未核实） | 逐个写/读，对着接线表确认（**0 基**） |
| 通信时序、丢包、掉线恢复 | 仿真的异常是"抛异常"注入的 | 拔网线、重启控制器，看是否按预期进「已安全停机」并能重连 |
| 多轴真实并行 | 仿真推进快，掩盖了排队效应 | 同一张卡上两条轴先后下发，观察是否几乎同时起动 |

反过来，**仿真可信的部分**（与真卡共用同一副骨架，直接搬）：命令排队与打断式停止、
超时判失败、软限位与能力门禁、状态机与报警/安全停机、错误文案与分支处置、流程结构（该放使能/回零/等待的位置）。

## 从仿真切到真卡：逐项核对清单

```
① 新增/复制一张卡：驱动类型 = 正运动 ZMotion 运动卡
   卡名称：非空、无首尾空格、全方案唯一   ← 「轴卡 IO」按它逐字匹配
   连接地址（IP）：控制器实际 IP，与本机同网段
   机型：填准确型号（ECI3428 / ECI3828 / ZMC408SCAN / VPLC532R），别让软件兜底
   随方案启动自动连接：控制器先上电再勾
② 轴映射：物理轴号 0 基且 < 机型轴数；轴名全局唯一；不用的轴"停用"而不是删行
③ 每轴填 UnitsPerMm（标定得出）与真实软限位
④ native SDK：VisionMaster.exe 同级放 zauxdll.dll + zmotion.dll（64 位）
⑤ 流程不用改：轴名/卡名不变，连线不动
⑥ 按「连接与排障」页的"首次上电最小验证顺序"走 ①~⑨
⑦ 控制器内参数确认：SPEED、加减速、回零高速/低速/偏移、到位判断窗口
   —— 这些都是仿真里"看不见的默认值"，真机上决定实际行为
⑧ 超时值按真实节拍重定：等待步骤默认 30000 ms、回零默认 120000 ms 只是起点
```

## 口径与失败策略（这张卡上的语义）

- **单位一律 mm / mm/s**：`SetUnits` 之后 API 收发都是用户单位，代码**不再除一次当量**
  （除一次会让位置与目标同步缩小，表现是"能跑但行程全错"，现场极难发现）。
- **下发 ≠ 到位**：`Single_MoveAbs` / `Single_Move` 返回 0 只代表命令进了控制器。
  日志会明确写"已下发…（未等到位；如需等待请在其后加「等待到位」步骤）"。
- **同一张卡上的命令是排队执行的**（单命令线程，FIFO）。所以"轴运动(X) → 轴运动(Y)"两条会先后下发；
  要真并行需要不同卡，或者接受"下发快、执行排队"。急停走的是插队通道，不受排队影响。
- **软限位只拦绝对运动**：相对运动与点动不受它拦，靠卡上的硬限位（能力位 `SupportsHardLimit=true`，
  限位接在控制器上、由控制器直接封锁运动）与驱动器保护。
- **"是否已回零"不是运动门禁**：驱动在连接末尾把已回零标记置 false（本驱动按增量式对待，宁严勿松），
  但基类随后会按能力表里上报的"支持绝对式"把它算成 true —— **这两处口径不一致是已知事实**。
  结论很实际：**不要指望软件替你强制回零**。流程首步显式放「轴回零」；现场确认是绝对值编码器、
  且机构允许免回零时，由你决定省略这一步。
- **命令执行失败或超时的后果**：驱动抛错/报失败 → 基类清空待执行队列、把卡打进「已安全停机」、
  逐启用轴下**减速停**（`Single_Cancel(轴,2)`）。这是收尾而非急停；真正的急停用 `StopMode=3` 走插队通道。
- **硬信号自动急停**：轮询发现报警/限位/急停输入 → 立即 `EmergencyStop()`（清队 + 插队停全部轴）并进「报警」。
  这条在基类做，不交给驱动 —— "报警之后该做什么"必须各家卡一致。
- **被打断不计故障**：急停或流程停止导致的"命令被取消"是预期行为，不记故障、不进安全停机。
- **故障只给三层有把握的东西**：原始错误码（可对厂商手册）、出错的操作上下文、按操作类别的分级与建议。
  SDK 不提供码→文案接口，驱动**不编对照表** —— 凭记忆编的表会把"轴未使能"引到"网线坏了"上去。

## 常见问题

**Q：仿真一切正常，真机上「等待到位」频繁超时。**
八成是速度口径：仿真速度填 0 会用卡级默认 50 mm/s，真卡填 0 是"不覆盖，沿用控制器内 SPEED" ——
控制器里那个 SPEED 可能是 5 mm/s。把 `Velocity` 显式写成非零值再看节拍；节拍仍不对就去控制器内核对加减速。

**Q：仿真里没放「等待到位」也没出事，真机上动作全乱了。**
仿真的回零只有几百毫秒、运动匀速推进，快到你看不出少了等待；真卡上一条定位要跑几百毫秒到几秒，
后面的「轴卡 IO」就在轴还没到位时执行了。这是仿真最有价值的一类"暴露"：结构问题在真机上放大。

**Q：真机上「读轴状态」的 `Velocity` 全是 0，是不是通信有问题？**
不是。这张卡的轮询不读速度寄存器，`Velocity` 恒为 0（缺数据，不是"静止"）。判动没动看 `Moving`。

**Q：想要 S 曲线，流程里怎么设都没有？**
流程步骤的曲线固定梯形，而且驱动每次定位前都会把 `SetSramp` 写成 0（避免上一条命令的残留），
所以之前设过的 S 会被清掉。要 S 曲线：走点位表 / 调试面板的点位运动（那里能选形状，平滑时长固定 200 ms），
或者把速度/加减速在控制器内调好并接受梯形。

**Q：回零每次都撞同一段方向不对。**
回零方式的模式码只能来自手册：`NegativeLimitIndex=1`、`PositiveLimitIndex=2`、`NegativeLimit=17`、`PositiveLimit=18`、
`Origin=19`、`PositiveLimitOrigin=23`、`NegativeLimitOrigin=27`、`PresetZero=37`。
核对三件事：卡上正/负限位实际接在哪一路、电机转向与坐标正方向是否一致、本步骤选的方式。
另外脉冲型卡的寻零参数（方向、速度、偏移）在控制器内设定，仿真与总线型都不覆盖它们。

**Q：清完报警为什么轴还是不动？**
清报警（`BusCmd_DriveClear`，逐启用轴）**不会自动使能** —— 使能会给伺服上电、有机械后果，必须人来明确。
所以恢复顺序固定是：排除原因 → 清报警 → 「轴使能」→（建议）「轴回零」→ 运动。

**Q：两条轴要做同一件事，能不能用插补保证同步？**
本驱动上报的能力是**不支持直线/圆弧插补**，流程层也不提供同步组。
可行做法：两条轴各放一个「轴运动」背靠背下发（几乎同时进控制器），节拍要求高的场合改用卡内联动或硬件同步。

**Q：`轴卡 IO` 在真机上选了卡却报"找不到名为「…」的运动卡"。**
卡名匹配是**逐字、区分大小写**的，且用的是「运动卡设置」里的卡名称本体：
名称为空时界面回退显示 IP（但本体仍是空），名称末尾带空格时下拉里给的是去空格后的值 —— 两种都对不上。
把卡名称改成非空、无首尾空格、全方案唯一的短名，再重选一次。
