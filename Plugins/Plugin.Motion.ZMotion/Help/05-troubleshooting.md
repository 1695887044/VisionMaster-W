# 故障排查：连不上、超时、回零不结束、位置读数不对

> 分类：运动卡 ｜ 来源：插件 Plugin.Motion.ZMotion

本页按"现象 → 机理 → 处置"组织。先按现象找到小节，再照处置逐条核对；
每条里出现的中文提示都是程序里逐字写着的文案，看到的就是它。
参数口径与单位换算的原理在「坐标系与单位口径」页，这里只讲怎么判断与怎么修。

## 0. 三步定位法

1. **看状态行**（运动卡设置窗口左侧列表的每行说明）：它给的是设备当前状态与最近一次状态说明。
2. **看故障提示**：连接失败、报警、命令被拒都会以故障形式上报（含级别、错误码、建议），状态行放不下这么多信息。
3. **看日志**：所有 `Warn` 级别的"不影响继续跑但可能埋雷"的事件（脉冲当量没设上、速度没设上、机型不认识）只在日志里出现，界面不弹。

⚠ 一个重要事实：**连接失败时状态行统一显示「连接失败：设备未给出原因」**。
真正的原因（地址未填、错误码、缺哪个 dll）写在故障信息与日志里，不写在状态行。
排查连接问题时不要只盯状态行。

## 1. 一连接就报"找不到模块"（部署问题）

| 现象 | 机理 | 处置 |
| --- | --- | --- |
| 点连接后提示里有「运动卡 SDK 不完整：缺少 …」 | 正运动 SDK 至少两个 native 文件：`zauxdll.dll`（辅助层）与 `zmotion.dll`（核心层）。少任何一个，Windows 都只报"找不到指定的模块"，且不说是哪个 | 按提示里点名的文件把两个 dll 一起放到 `VisionMaster.exe` 同级目录，重新连接 |
| 提示「文件都在，请确认 SDK 与程序位数一致（本程序为 64 位），以及是否被杀毒软件 / 权限拦截」 | 文件在，但加载器仍拒绝（位数、拦截、损坏） | 换 64 位版 SDK；把程序目录加入杀毒白名单 |
| 提示「运动卡 SDK 位数不符：…。请换成 64 位版的 zauxdll.dll / zmotion.dll」 | 把 32 位 SDK 放进了 64 位进程。它报的同样是"找不到模块"(0x7E)，极易误判为路径问题 | 用官方 64 位版两个 dll 替换 |
| 编译能过、换台机器就报上面这些 | native 库由插件工程在生成后投递到宿主目录；只拷 `Modules\` 里的插件 dll 不带 native 库 | 部署时保证 exe 同级有 SDK 文件（不要只拷 `Modules\`） |

机理要点：这些文件必须落在 **exe 同级**，不是插件所在的 `Modules\`。
`DllImport` 的搜索路径是 exe 目录 → 系统目录 → PATH，**不包含插件目录**。

## 2. 连不上（网络与占用）

故障文案：`连接控制器失败（正运动错误码 {N}）`，建议固定为
`检查控制器 IP、网线与供电；确认没有被厂商调试软件或另一个本程序实例占用`，级别为**需现场处理**。

按顺序核对：

1. 卡的 IP 与本机在同一网段（正运动控制器出厂常为 `192.168.0.x`，本机网卡需同段）。
2. `ping` 得通；网线指示灯亮；控制器已上电。
3. **同一时刻只允许一个上位机连接**：厂商调试软件（RTSys 等）开着时，本程序必然连不上；反之亦然。
4. 本程序自己有没有第二个实例（双击两次、崩溃后残留进程）——同一条 Eth 连接是独占的。
5. 地址栏填的是 IP，不是主机名；且没有多余空格（首尾空格会被去掉，中间的不会）。
6. 状态行为空且日志里是 `未填写控制器 IP 地址` 一类：地址栏根本没填。

连接耗时提醒：网口建链可能要几百毫秒到几秒，界面这段时间显示"正在连接"是正常的，不要反复点。

## 3. 连上一会儿又"安全停机"（通信抖动与看门狗）

| 提示 | 机理 | 处置 |
| --- | --- | --- |
| `状态轮询连续失败 3 次：读取轴 {轴名} 状态失败（码 {N}）；已安全停机` | 轮询线程读轴状态失败会抛异常，基类累计连续失败次数；单次抖动不报警，**连续三次**才判失联 | 查网线/交换机/供电是否被碰松；把轮询间隔从默认 10ms 放宽（见下） |
| `已 {X}s 未收到状态响应（看门狗超时 {N}ms）；已安全停机` | 看门狗：超过设定时长没收到任何成功轮询 | 同上；确认控制器没重启、没被别的上位机抢走 |
| 状态从"在线"变"已安全停机"，且队列里命令都变"已取消" | 失联时轴可能还在按最后一条命令继续走而软件已不知道位置，唯一安全动作是停下来并要求人工确认 | 排除通信问题后**重新连接**，再按需回零；不要指望它自己恢复 |

参数与安全的关系：

- 轮询间隔（`PollIntervalMs`）实际生效范围 1~1000ms；太小会把网口卡问满。
- 看门狗超时下限 200ms（填更小按 200 处理），所以"1s 没响应就判失联"这类配置无法再收紧。
- 命令超时（`CommandTimeoutMs`）同时是回零兜底超时的来源，见下一节。

## 4. 回零相关问题

| 现象 | 机理 | 处置 |
| --- | --- | --- |
| `回零超时（>{N}s）：请检查原点/限位开关、回零方式与回零速度` | 总线型回零以"回零状态=1"为完成判据，其它值（含"正在回零"和"失败"）一律继续等，直到超时。**超时前会先把该轴减速停掉**，不会丢一根还在寻零的轴 | 核对回零方式与机构是否匹配（原点开关、限位开关方向）；回零速度沿用控制器内设置，需去厂商软件调 |
| 步骤「回零」超时时间到点就失败 | 界面没给超时时的兜底为 `max(1000ms, 命令超时)`；「回零」步骤默认 120s（回零慢是正常的） | 长行程轴把步骤超时放宽，别改卡级命令超时（那会影响所有命令） |
| `该卡不支持回零方式「{方式}」` | 能力协商：命令入队前由基类按机型上报的支持集合拦下 | 换成该机型支持的方式（见「卡级与轴级参数」页的回零方式对照表） |
| `正运动驱动不支持回零方式 {枚举名}` | 枚举到模式码的映射里没有这一项（仅出现在扩展了新枚举值却没补映射的情况） | 按手册补映射，不要凭记忆填数字 |
| 回零失败后不敢自动重来 | 回零失败判为**需人工复位**：轴可能正卡在原点开关上，自动重试等于反复撞开关 | 先确认开关与机械位置，再点「清除报警」→重新回零 |
| 「清除报警」点了没用 / 提示 `部分轴清除报警失败：{轴名}(码 {N})、…` | 清报警是**逐根启用轴**执行；某根轴通信失败会让整条命令失败。另外它**不会自动重新使能** | 使能给伺服上电有机械后果，必须由操作员明确点「使能」。逐轴排查报警来源 |
| 清报警提示 `清报警超时` / `清报警命令被拒绝（{结果}）` | 该命令排队执行且等待完成；卡已在报警/安全停机态时被门禁拒绝 | 状态为"报警"或"在线"时才允许清报警；"安全停机"需先重新连接 |

## 5. 位置与读数不对

| 现象 | 机理 | 处置 |
| --- | --- | --- |
| 走 100mm 实际走了 100 个脉冲（或差几个数量级） | 脉冲当量（`UnitsPerMm`）填反，或连接时 `SetUnits` 没设上 | 核对"每 mm 对应多少脉冲"；日志里查 `设置脉冲当量失败（码 {N}）——位置与目标将按控制器原单位解释` |
| 改了 `UnitsPerMm` 没效果 | 单位只在**连接时**下发到卡 | 断开再连接（或重启程序） |
| 位置读数一直不变 | 位置来自轮询缓存；卡在线但轮询失败时缓存停在旧值 | 看状态行与是否有轮询失败告警 |
| 「读轴状态」的速度输出恒为 0 | 驱动不轮询速度（省往返），所以速度字段没有真值 | 需要速度请读伺服侧；不要按这个数做判断 |
| 明明没到位，「等待到位」却过了 | 到位判据来自状态字 bit11；若轴报警停在目标附近，只看到位位会误判 | 「等待到位」步骤本身会优先检查报警/限位信号，因此它比"位置比较"更可靠；自己写判据时别只看到位 |
| 报警中却显示"到位" | 状态位写错（把报警位读成到位位）会造成这种最危险的情形 | 该位定义被闸门断言钉住；若自行改动过解析，运行断言集合确认 |
| 每次连接后都要重新回零／或连上就直接走绝对坐标 | 是否要求回零由"绝对值编码器"能力位决定；本驱动该位的取值与代码注释不一致（详见「坐标系与单位口径」页），因此**不能依赖软件强制回零** | 在流程里显式放「回零」步骤，位置可信与否按工艺自行判定 |

## 6. 命令被拒（不是故障，是拦下来了）

| 提示 | 含义 | 该做什么 |
| --- | --- | --- |
| `运动卡未连接` | 状态为关闭 | 连接 |
| `运动卡正在连接/断开，请稍候` | 连接中/断开中不接受命令 | 稍后重试 |
| `运动卡处于报警状态，请先清除报警` | 报警态只允许清报警 | 清除报警 |
| `运动卡已安全停机，请重新连接后再操作` | 失联或命令失败后的终态 | 排除原因 → 重新连接 |
| `轴号 {N} 超出范围（本卡 {M} 轴）` | 轴映射的物理轴号大于机型轴数 | 改轴映射或填准机型 |
| `轴号 {N} 无法校验（能力未知）` | 机型不认识、能力没报上来 | 在机型栏填准确型号 |
| `输出点 {N} 超出范围（本卡 {M} 点）` | 输出点号超出（点号从 0 计） | 核对接线与点号；注意 IO 点数可能是显示上限 |
| `目标 {V} mm 超出软限位 [{min}, {max}] mm` | 软限位只在**绝对运动**上拦 | 这是正常业务拒绝（提示级），要么改目标要么改软限位 |
| `命令队列已满（上限 {N} 条）` | 队列深度上限（默认 256） | 放慢下发节奏或加大深度（不要靠它做缓冲池） |
| `该命令被打断` / `被急停中断` / `被急停清除` | 停止、失能属打断性命令；急停会清空队列并插队停全部轴 | 预期行为，不是设备故障 |

## 7. 步骤算子侧的对照（配流程时报的错）

| 提示 | 机理 | 处置 |
| --- | --- | --- |
| `运动卡服务尚未就绪：请在主程序内运行流程` | 轴/卡解析入口没拿到宿主注入的服务 | 在主程序里跑，不要用脱离宿主的运行方式验证运动流程 |
| `找不到名为「{轴名}」的轴…` | 轴名解析失败：方案里没有这个逻辑轴名 | 用属性面板的下拉选，别手打；改过轴名要同步改流程 |
| `轴「{轴名}」在卡「{卡名}」上处于停用状态：…` | 轴映射里该行被取消勾选 | 启用该轴或换轴名 |
| `找不到名为「{卡名}」的运动卡：请到「运动卡设置」确认卡名，或换一张卡` | IO 是卡级操作，按卡名找卡 | 检查卡名（改名会让旧流程引用失效） |
| `运动卡「{卡名}」当前不可运动：{状态说明}` | 步骤执行前会看设备状态 | 按状态说明处理（多为报警/安全停机） |
| `等待轴「{轴名}」到位超时（>{N} ms，当前位置 {V} mm）：请检查目标是否超出行程、速度是否过低，或该轴是否被限位/报警阻挡` | 「等待到位」按设备状态轮询，不是等命令完成信号 | 先看这条命令是否真的下发了（定位步骤的输出"命令是否被接受"） |
| `等待轴「{轴名}」到位时被中断（流程已停止）` | 停止流程时优先响应取消 | 正常现象 |
| `定位命令已被接受（不代表已到位）…` | 位置模式**下发即返回** | 多轴联动后必须接「等待到位」步骤 |

## 8. 想改的行为没变（改错了地方）

原则：**流程管"去哪、多快、等多久"，控制器管"怎么动、怎么找零、到位怎么判"**。
下面这张表只解决"我改了没生效，到底该去哪儿改"。

| 想改的东西 | 去哪儿改才生效 | 为什么在这儿 |
| --- | --- | --- |
| 目标位置 | 流程「定位」的 `Target` 端口（mm） | 绝对坐标以回零建立的零点为基准 |
| 速度 | 流程「定位」的 `Velocity` 端口 | **填 0 等于不覆盖**，沿用控制器内该轴当前速度；要确定性就给非零值 |
| 加减速 | 控制器内（厂商软件），或点位表里给正值 | 步骤算子给的加速度恒为"不覆盖"（`≤ 0` 就不下发），别指望流程步骤改它 |
| S 曲线形状 | 点位表 / 调试面板 | 每次定位前都会重写平滑值，**流程步骤里的定位恒梯形**，会把之前设过的 S 清掉 |
| 回零高速/低速、回零偏移 | 控制器内（厂商软件） | 驱动刻意不覆盖：现场已调好的机构行为不该被软件改写 |
| "到位"的判定松紧 | 驱动器/控制器内的跟随误差窗口、到位带宽 | 软件读的是卡给的到位位；判得过严会"看着到了却不报到位" |
| 脉冲当量 | 「运动卡设置」轴映射 | 只在**连接时**下发；改完必须断开重连 |
| 软限位 | 「运动卡设置」轴映射 | 只拦绝对运动；保持默认 ±1000000 mm 等于这道防线是空的 |
| 轴配置弹窗里的编码器/驱动器/跟随误差栏 | 只是**存档记录** | 当前不下发到卡、也不参与任何判断；真实窗口要在伺服参数里设 |
| 机型轴数 / IO 点数 | 「运动卡设置」机型栏 | 由机型表决定能力，填错会直接表现为"轴号超出范围" |

## 9. 从仿真（虚拟卡）切到正运动真卡

切换核对清单（照顺序走，能一次过）：

```
① 新增一张卡：驱动 = 正运动运动控制卡
   卡名称：非空、无首尾空格、全方案唯一   ← 「轴卡 IO」按它逐字匹配
   连接地址：控制器实际 IP，与本机同网段
   机型：填准确型号（ECI3428 / ECI3828 / ZMC408SCAN / VPLC532R），别让软件兜底
   自动连接：控制器先上电再勾
② 轴映射：物理轴号 0 基且小于机型轴数；轴名全局唯一；不用的轴"停用"而不是删行
③ 每轴填脉冲当量（标定得出）与真实软限位
④ native SDK：VisionMaster.exe 同级放 zauxdll.dll + zmotion.dll（64 位）
⑤ 流程不用改：轴名/卡名不变、连线不动
⑥ 按「上手与连接」页的首次上电验证顺序走一遍
⑦ 控制器内参数确认：速度、加减速、回零高速/低速/偏移、到位判断窗口
   —— 这些在仿真里都是"看不见的默认值"，真机上决定实际行为
⑧ 超时按真实节拍重定：等待到位默认 30000ms、回零默认 120000ms 只是起点
```

仿真验不到、必须真机验的项目：

| 项目 | 仿真为什么验不到 | 真机怎么验 |
| --- | --- | --- |
| 脉冲当量与方向 | 仿真内部就用 mm，不下发单位 | 1~2mm 的小行程绝对定位，量实际位移 |
| 真实节拍 | 仿真匀速逐拍推进，没有加减速与平滑 | 用「等待到位」的耗时输出统计，再定超时 |
| 回零路径 | 仿真固定几百毫秒后直接把位置写 0 | 验开关极性、撞限位方向、有没有 Z 相 |
| 指令位置 vs 编码器位置 | 仿真没有跟随误差概念 | 看驱动器实际位置与跟随误差；外力推动、丢步都会在这里暴露 |
| 速度回报 | 仿真会填速度字段，正运动**不回读速度**（恒 0） | 判断"动没动"一律用"是否运动中" |
| 报警含义 | 仿真的报警是开关注入的 | 真实报警原因要在驱动器/控制器侧看 |
| IO 点号与实物对应 | 仿真固定 8 入 8 出，真卡按机型（部分机型点数只是显示上限） | 逐个写/读，对着接线表确认（0 基） |
| 通信时序、丢包、掉线 | 仿真的异常是人为注入的 | 拔网线、重启控制器，看是否按预期进"已安全停机"并能重连 |
| 多轴真实并行 | 仿真推进快，掩盖了排队效应 | 同卡两根轴先后下发，观察是否几乎同时起动 |

仿真可信、可以直接搬的部分（与真卡共用同一副骨架）：命令排队与打断式停止、
超时判失败、软限位与能力门禁、状态机与报警/安全停机、错误文案与分支处置、
以及流程结构本身（该放使能/回零/等待的位置）。

## 10. 名字引用与状态恢复的三个坑

1. **卡名逐字匹配**：卡级操作（IO）按"卡名称"本体比较，区分大小写、不做模糊匹配。
   卡名称留空时界面回退显示 IP，但流程里匹配的仍是卡名称本体；卡名称末尾多一个空格
   就会和下拉里去过首尾空格的值对不上，表现为"选了卡却报找不到"。
2. **轴名跨卡重复会被影子化**：轴按全局唯一名解析，被同名轴压住的那些**不会出现在下拉里**
   （程序刻意不列"选了必然失败"的项）。现象是"轴数对，但有些轴选不到"——改轴名解决；
   改过名的轴要连同它已教的点位与凸轮表标签一起用「重命名」入口处理，别直接改文本。
3. **在"已安全停机"上点「连接」不会真的重连**：连接对非"未连接"状态是幂等的（直接返回"已连上"）。
   恢复动作一律是**先「断开」再「连接」**；「自动重连」目前只是配置项，掉了要人工接。

## 11. 日志里该留什么（报障前）

一次完整报障请带：卡名与地址、状态行全文、故障提示全文（含**正运动错误码**）、出错的操作名（"回零时"还是"读状态时"）、轴名、程序位数、SDK 两个 dll 的所在目录与版本。
错误码是现场对厂商手册的唯一硬依据；本驱动刻意不把错误码翻译成"看起来专业"的猜测文案，
所以看到"正运动错误码 12"这类信息时，正确用法是拿它去查厂商资料，而不是自行推断。
