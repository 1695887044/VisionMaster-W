# 数学计算 · 排障

> 分类：数据处理 ｜ 来源：插件 Plugin.Utility

按"看到什么现象"查。文案原文逐字取自源码与编译器（`FlowCompiler`）与基类（`VisionPluginBase`），
括号里标的是它出现的位置。本插件的算法体只有一次 `switch`：
**正常路径不打日志、不判失败**，所以"日志干干净净但结果不对"是它的常态形态。

## 一、编译/运行前就被拦的

| 现象原文 | 为什么 | 怎么改 |
| --- | --- | --- |
| `[参数缺失] '步骤名' 的必填参数 'A' 未配置！` | `A` 既没连线、`InputValues` 里也没有非空常量（三个输入都是必填，判据来自基类默认） | 在面板里填一个数并确认，或把上游输出连进来 |
| 同上，参数名是 `B` 或 `Operation` | 同一判据换了个端口 | 同上；一元运算的 `B` 填 `0` 占位即可 |
| 节点上亮黄色叹号角标 | 上面那条编译判据的**画布投影**（文案 `必填参数未配置（编译会报参数缺失）：` 后面逐行列端口名） | 悬停看它列了哪几个端口名，逐个补 |
| `[连线类型不匹配] '步骤名' 的输入端口 'A' 期望 Double，但上游 'XXX' 提供的是 Boolean。请在变量绑定处改选类型兼容的输出，或调整上游算子的输出类型。` | `bool` 不属于数值族，"非零即真"在这里不成立 | 上游先接「数值比较」（如 `NotEqual`）或「类型转换」出数值/文本，再连进来 |

（报错里的类型名走 `Type.Name`，所以是 `Double` / `Boolean` / `Int32` 这种 CLR 写法，不是 C# 关键字。）
| 同上，端口是 `Operation`，上游给的是数值 | 编译期连线检查不放行"数值 → 枚举"（运行期转换器认，编译期不认，是刻意的不对称） | 直接在面板下拉里选；确实要上游决定，改连成员名**字符串**输出 |
| `[并行不安全] 分支内步骤 '步骤名'（算子 MathCalculationPlugin）未声明 [ParallelSafe]，…` | 本插件**已标** `[ParallelSafe]`，出现这条说明 DLL 是旧的 | 重建插件工程（`Modules\` 下的 DLL 不由宿主工程带出） |

## 二、跑通了、但结果不是想要的

**现象：节点是绿的，`Result` 却是 `NaN`。**
这是设计口径，不是漏判。除零、负数开方、对负数取对数都只产生 `NaN` 且**不判失败**
（`Divide` 里显式写了 `b == 0 ? double.NaN : a / b`，`Math.Sqrt` / `Math.Log` 自己返回 `NaN`）。
要让它红，在下游接「数值比较」或判定步骤。

**现象：`NaN` 一路传染到上报通道，界面上看不出哪步坏的。**
`NaN` 参与任何算式还得 `NaN`。从最上游往下逐个看 `Result`，
**第一个变成 `NaN` 的那步就是病根**（多半是除零，或负数开方/对数）。
本插件对这类情形不留日志，只能靠逐节点看值。

**现象：`B` 填了值却没生效。**
两种完全不同的原因，先分清：
① 这一行**已经连了上游**——连线值优先于手填值，面板里的数字根本不参与生效（要用手填值就点 ✕ 断线）；
② 选的是**一元运算**（`Sqrt`/`Abs`/三角/对数/`Exp`/取整），这些只看 `A`。

**现象：选了常量、一执行还是报"参数缺失"。**
手填值没落进存盘字典（`InputValues`）。确认一次参数面板让值写回去；
如果这一行连着上游，编译器把连线当作来源，不该再报缺——报了就是连线断了或上游节点被删。

**现象：`Sin` / `Cos` / `Atan` 的结果看着不对。**
参数与返回值都是**弧度**。角度先乘 π/180 再送进去，`Atan` 出来乘 180/π 才是角度。
需要 `atan2(y,x)` 那种象限判别的角度，本节点没有。

**现象：`Round` 把 2.5 变成 2。**
用的是 .NET `Math.Round`，默认**银行家舍入**（四舍六入五成双）。
要传统的"半进位"就 `Add` 0.5 再 `Floor`（两个节点）。

**现象：想要"保留两位小数"，做不到。**
`Round` 不带位数参数，成员表里也没有缩放运算。
常规做法：`Multiply` 100 → `Round` → `Divide` 100（三个节点），或者干脆转 `String` 交给上报格式化。

**现象：大数运算结果变成 `∞`（正无穷）。**
`double` 溢出**不抛异常**，直接得 `±∞`，节点照样绿。
`Exp` / `Power` / `Multiply` 最容易碰到。判 `∞` 要用「数值比较」跟一个足够大的数比，
`NaN` 与 `∞` 在比较里都是全假（见「数值比较」的 `NaN` 一条）。

**现象：日志里出现 `实例名 运算失败: …`，节点是红的。**
走到了 `catch`：`Result` 被置成 `NaN`、`Success=false`、错误信息 = 异常消息原文。
`Math.*` 对 `double` 几乎不抛，所以这条真出现时通常是**取值阶段就坏了**
（上游给的对象强转不成 `double`）。报错信息里没有端口名，先看上游连了什么。

**现象：换了台机器，同一个方案算出来的结果不一样。**
本插件纯 `double`，不读区域设置，也不碰系统时间。
真出现差异请先查上游（相机的像素当量、标定结果）而不是这里；
若是"先转 String 再比"的流程，区域设置的风险在「类型转换」那一节，不在这页。

## 三、改了没反应

**现象：改了源码，界面上的下拉/行为一点没变。**
`Modules\` 下的插件 DLL 不由宿主工程带出，只重建宿主跑的仍是旧 DLL。
必须重建插件工程；还要留意增量构建可能静默漏打包（收尾那次全量重建用 `--no-incremental`）。

**现象：给枚举成员加了中文 `[Display(Name="…")]`，界面上还是英文。**
两处候选生成点（自动参数面板 + 变量绑定窗口）都走 `StepConfigOption.ForEnum`，
显示取成员上的特性、值仍是成员名。界面没变通常是**插件工程没重建**，
不是特性没生效——先核 DLL。

**现象：显示名换了，老方案跑出的运算变了。**
存的是成员名，显示名怎么改都不影响解析；
如果确实串了，说明动过**成员顺序**（枚举落盘是序号），那是不可逆的破坏性改动。

## 四、找谁配合排查

- 值对不对：先接一个「数值比较」把 `Result` 跟期望值比，或直接连到「结果显示」烧进图像。
- 是不是压根没执行：看流程日志有没有该步骤的记录，节点状态是否被上游分支跳过。
- 是不是拿错了靶：确认取的是 `Result`（本节点唯一的输出端口），
  而不是又去连 `A`/`B`——它们是输入端口，下游取不到。
