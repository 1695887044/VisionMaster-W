# 延时

> 分类：常用工具 ｜ 来源：插件 Plugin.Utility（工程 `Plugin.Util.csproj`，C# 类 `DelayPlugin`）

让当前流程暂停指定毫秒数，期间**每 50ms 检查一次急停信号**，可被强制中断。

## 为什么需要它 / 原理

视觉流程不是纯计算：光源要点亮、气缸要动作、相机要曝光完、机械手要到位。
这些"等一等"如果靠反复轮询上游信号实现，会白烧 CPU 也让流程难读；
但如果用一个死的 `Sleep(N)`，急停时程序会卡在这一整段里出不来。

本节点的解法是**分片睡**：

```
elapsed = 0
while elapsed < Delay:
    若 context.CancellationToken 已请求取消 → 记警告并立刻返回（判失败）
    本轮睡 min(50, Delay − elapsed)      ← 最后一片按余量截短
    elapsed += 本片长度，并把 elapsed 写进 ET 输出
```

于是急停最多 50ms 后就能脱出，而 `ET` 一路跟着真实流逝时间走。
它标了 `[ParallelSafe]`（协作取消范式），可以出现在并行分支里。

## 输入端口

| 端口 | 必填 | 说明 |
| --- | --- | --- |
| `Delay` | **是** | 延时时间(ms)，`int`，默认 `500`。`IsRequired = true` |

本插件没有自定义配置视图，走宿主自动生成的参数面板：只有一行"延时时间(ms)"，
填常量或点链接图标连上游（例如把配方里的"稳定时间"接进来）。

## 输出端口

| 端口 | 说明 |
| --- | --- |
| `ET` | 已流逝时间(ms)，`int`。每片睡眠后更新一次，正常完成时≈设定的 `Delay` |
| `State` | 执行状态，`bool`。跑满为 `true`；被急停中断或异常时为 `false` |

## 关键参数

> 完整参数与取值范围以流程中该步骤的「模块参数」界面为准，这里只解释含义。

| 参数（端口名） | 默认 | 说明 |
| --- | --- | --- |
| `Delay` | `500` | 要等待的毫秒数（`int`）。填 `0` 或负数直接完成（不进入循环） |

## 口径与失败策略

- **`Delay` 是必填端口**：`IsRequired = true`，而编译期判据是"必填 **且** 没有连线 **且**
  面板里没填过常量"。三者全空时流程编译直接报
  `[参数缺失] '<步骤名>' 的必填参数 'Delay' 未配置！`
  （注意：**光有默认值 500 不算"已配置"**，必须连上或亲手填一个值。）
- **正常跑满**：`State=true`、`Success=true`、日志 `开始执行延时...` → `延时 {N}ms 完成。`
- **急停中断**：日志 `收到急停信号，已强制中断！`（警告级），`Success=false`、`State=false`、
  `ET` 停在已流逝的毫秒数。**这里不写错误信息文本**，原因只在日志里。
- **异常**：`State=false`、`Success=false`、日志 `{实例名} 发生异常: {消息}`，
  然后**异常继续上抛**（由引擎按执行异常处理）——本节点不吞异常。
- **精度**：`Thread.Sleep` 不保证毫秒级准时，加上 50ms 的分片粒度，
  实际等待时间会比设定值**略长**。它是"等够"用的，不是"精确计时"用的。
- 步骤本身是绿的还是红的全看上面三条，不要拿 `State` 之外的信号推断。

## 典型用法 / 接线

```
IO 输出.气缸动作 ──▶ 延时.Delay（=配方里的动作时间，或直接填 800）
                     延时.ET ──▶ 记录/上报（本轮实际等了多久）
                     延时.Result 无——它只做"等"，不做判定
                     下一算子（等完之后才执行）
```

常见取值：等气缸/真空到位按**实际动作时间 + 20% 余量**（例：实测 600ms → 填 800）；
光源点亮后拍照留 50~100ms 让亮度稳定；相机软触发后按曝光时间留量。

## 常见问题

**Q：填了 500 却还报"必填参数 'Delay' 未配置"？**
A：那是**没连线也没在面板里亲手填过**的情况（默认值不算已配置）。
在参数面板的"延时时间(ms)"里填一个数并确认保存，或者从上游连一个值过来。

**Q：设 1000ms，为什么实际过了 1020ms 左右？**
A：正常现象。`Thread.Sleep` 的粒度加上最后一片的截断，会略多于设定值。
对时序严格的场合，请用触发信号/到位反馈判定，不要用延时兜底。

**Q：按了急停，流程卡在这一秒多才退出来？**
A：本节点最多 50ms 就该脱出。如果确实慢，看是不是**别的步骤**（如通讯超时、
相机取图等待）在挡——延时节点的中断会在日志里留下"收到急停信号，已强制中断！"。

**Q：急停之后这一步算失败还是算成功？**
A：**失败**（`Success=false`）。下游若依赖它，分支会按失败走；
`ET` 还能告诉你实际等了多久。

**Q：`Delay = 0` 会不会报错？**
A：不会，直接完成，`State=true`、`ET=0`、`Success=true`（负数同理，循环一次都不进）。

**Q：能并行吗？多个延时会不会互相抢？**
A：可以。每个步骤实例在自己的执行线程里睡，互不影响；
但同一条串行链上放多个大延时只会线性拉长节拍。

**Q：想在延时期间做点事（比如刷新画面）？**
A：本节点不提供回调。要做"等待 + 轮询"请用条件分支（While）+ 判定算子组合，
或在脚本节点里自己写带取消检查的循环。
