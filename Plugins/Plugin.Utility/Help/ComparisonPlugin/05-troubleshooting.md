# 数值比较 · 排障

> 分类：逻辑判断 ｜ 来源：插件 Plugin.Util（工程 `Plugin.Util.csproj`，C# 类 `ComparisonPlugin`）

按"看到什么现象"来查。本插件只有一个 `switch` 表达式，**运行期不打日志、不抛异常、不判失败**，
所以"日志里什么都没写但结果不对"是它的常态形态，下面按现象逐条给原因和改法。

## 一、编译/运行前就被拦的

| 现象（原文） | 为什么 | 怎么改 |
| --- | --- | --- |
| `[参数缺失] '步骤名' 的必填参数 'A' 未配置！` | `A` 既没连线、手填值又是空的（判据三条同时成立，见「端口与参数」） | 填一个常量，或把上游数值连过来 |
| 同上，参数名是 `B` / `Type` / `Tolerance` | 同上，换了个端口 | 同上 |
| 节点上亮黄色叹号角标 | 同一条判据的画布投影（与编译器逐字对齐） | 悬停看它列出的端口名，逐个补 |
| 连线时报连线类型不匹配（`A` 期望 `double`，上游给的是 `bool` / 文本 / 图像等转不过去的类型） | 宽容转换表覆盖不到这个组合 | 上游先转成数值（用「类型转换」），或改比别的量 |

## 二、跑通了、但结果不是想要的

**现象：六个比较试了个遍，`Result` 全是 `false`，既不等于也不大于。**
原因几乎只有一个：`A` 或 `B` 是 `NaN`。`NaN` 参与的比较按 IEEE 口径一律为假，
而本插件不做任何特殊处理，于是六个分支**集体返回 `false`，并且不报错**。
`NaN` 的典型来源是上游「数学计算」除零（`b == 0` 时它直接给 `NaN`）或负数开方 / 负数取对数。
查法：把上游那个输出端口直接接一个记录或显示看一眼，比在这里猜快。

**现象：明明两个值一样，`Equal` 却是 `false`。**
`Tolerance` 太严。默认 `1E-06`，对像素面积、毫米尺寸这类测量常常不够
（同件重复测量的浮点累加误差能到 1e-5 量级）。按重复性放宽到 `0.001` 这种量级。
它填的是**判定死区**，不是精度指标。

**现象：改一次流程跑一次，`Equal` 时对时错。**
还是容差太严 + 上游值有抖动。放宽容差，或改用 `GreaterThanOrEqual` / `LessThanOrEqual`
做限值判定（带容差时它们对边界的处理更稳）。

**现象：`NotEqual` 一直为真，哪怕两个值看着一样。**
两种可能：① 容差填成了**负数**——`A − B` 的绝对值不可能小于负数，`Equal` 恒假、`NotEqual` 恒真；
② 值确实是 `NaN`（见第一条）。容差必须是**非负数**。

**现象：`GreaterThan` 一直为真，明明 `A` 只比 `B` 大一点点。**
`GreaterThan` 的判据是 `A > B + Tolerance`，反过来填了**负容差**时它变成 `A > B − 绝对值`，
判定被放松了一个死区宽度。检查 `Tolerance` 的符号。

**现象：上下限判定漏放行 / 误拦。**
用了 `GreaterThan` 判下限。带容差以后 `GreaterThan`（阈值 `B + tol`）与
`GreaterThanOrEqual`（阈值 `B − tol`）是**两条不重合的线**，中间那段 `2×tol` 宽的区间里
前者假、后者真。判下限用 `GreaterThanOrEqual`、判上限用 `LessThanOrEqual`，别混。

**现象：只接了 `A`，结果一直在跟 0 比。**
`B` 没连线也没填 → 用声明的默认值 `0.0`。同理 `Type` 留空是 `Equal`、`Tolerance` 留空是 `1E-06`。
"不接也不报错"是这一族工具插件的统一行为，值来自默认值而不是空。

**现象：改了参数、试运行对了，重新打开方案又变回去了。**
两类原因：① 没点「确定」，改动只在当前会话；
② 用的是旧版插件 DLL（枚举静默回退默认值那条历史 bug，见「端口与参数」的转换表）。
先确认 `Modules\Plugin.Util.dll` 是本次构建产物。

**现象：在参数面板改了数字，值就是不跟着变。**
这个端口**已经连了上游**。连线值优先于手填值，手填槽位不参与生效。
要用手填值就把线断开；要两者混用就再加一个本节点分别判定。

**现象：`Result` 看着对，下游判定却反了。**
本节点的 `Result=false` **不等于步骤失败**。步骤恒判成功（绿色），
"超限"只是数据。把 `Result` 接到条件分支 / 判定步骤去产生 NG 语义，
不要指望节点变红。

## 三、想判的东西它判不了

| 想判 | 用什么 |
| --- | --- |
| 文本是否相等（条码、批次号） | 本节点不吃文本（端口是 `double`）。走脚本类节点，或先做数值编码 |
| 日期先后 | 先把日期转成数值（时间戳/序列号）再比；本节点也不直接吃 `DateTime` |
| 值是否落在区间内 | 两个本节点串联（下限 + 上限），结果送「逻辑运算」做 `And` |
| 三个以上值同时判 | 多个本节点 + 「逻辑运算」逐级合并；本节点一次只比两个数 |
| 整数相等要不要设容差 | 计数、序号这类整数值转成 `double` 是精确的，默认 `1E-06` 不会误放行 |
| 空值 / 未定义判定 | 本节点没有"空"的概念：上游没给值时是默认 `0.0`，不是 `null`。要判"有没有测到"请用上游的成功标志位 |

## 四、快速自检（换工位 / 改配方之后）

1. 打开配置界面，四个端口的值逐个看一遍（注意区分"手填值"和"已连线"）。
2. `Type` 与预期逐字对齐——它是英文成员名，看错一个后缀（`GreaterThanOrEqual` vs `GreaterThan`）就是边界差一个 `2×tol`。
3. `Tolerance` 的**符号和量级**：非负，按测量重复性给。
4. 拿一件已知 OK / 已知 NG 各跑一次，看 `Result` 而不是看节点颜色。
5. 若 `Result` 恒假，第一步查上游是不是 `NaN`，第二步才查容差。
