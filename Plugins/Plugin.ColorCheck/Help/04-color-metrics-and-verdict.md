# 颜色序列检查 · 颜色口径与判定

> 分类：图像处理 ｜ 来源：插件 Plugin.ColorCheck

本页回答三件事：**用什么口径把像素变成一个颜色词**、**期望序列从哪来、怎么逐位比**、
**哪些情况失败停流程、哪些只告警继续跑**。最后说清它和「区域颜色检查」的分工。

## 一、颜色口径：固定 HSV 式，界面上没有颜色空间开关

**没有** RGB / HSV / Lab 下拉，**也没有** ΔE、颜色距离、容差半径这类连续量。这不是缺功能，是刻意的：
判定走的是"把像素归成一个**颜色词**"，而线序场景里白线（明度约 240）和浅色背景（约 235）只差几个灰阶，
用连续距离度量会被灰阶漂移牵着走。

三个量都从 R/G/B 现场推（`Core.Halcon.Color.ColorVocabulary`），不调用任何转换算子：

| 量 | 算法 | 管到哪 |
| --- | --- | --- |
| 明度 `v` | `max(R, G, B)` | 判黑、判白、棕的明度上限 |
| 饱和度 `s` | `(max − min) / max`，`max <= 0` 时记 0 | 无彩/有彩分界、白的附加条件 |
| 色相 `h` | 标准 HSV 色相角，0~360 度；`max==min` 时记 0 | 有彩区按角度分色系 |

**先判"有没有颜色"，再按色相分色系**（阈值名就是配置项名，默认值见括号）：

```
s < ColorlessSaturation(0.45)  →  无彩区
    v < BlackValue(80)                                → 黑
    s < WhiteSaturation(0.15) 且 v > WhiteValue(195)   → 白
    (R-G) ≥ BrownWarmth(12) 且 (R-B) ≥ 12 且 v < BrownValue(175) → 棕
    其余                                               → 灰
s ≥ 0.45  →  有彩区，按色相角 h：
    [330,350) → 玫红      ≥350 或 <20 → 红（红跨 0 度）
    [20,45)   → 橙        [45,70)     → 黄
    [70,160)  → 绿        [160,230)   → 蓝
    [230,330) → 紫
```

**颜色词只有 11 个**：`黑 白 灰 棕 红 玫红 橙 黄 绿 蓝 紫`，外加通配符 `*`（这一位不检）。
词表与分类层次是**所有颜色算子共用的一份内核**，各算子只各带一份**阈值数值**副本。

**改色相阈值只影响有彩区**——也就是只有 `s ≥ ColorlessSaturation` 的像素才轮到色相说话。
"黑线读成灰线""白线读成灰线"这类问题动色相阈值一点用都没有，要动的是上面那四项无彩条件。

### 13 项色卡阈值：管到哪、往哪调

每张色卡都是**单边阈值**，比较符号写在源码里（`ColorVocabulary.Classify`）：黑与棕上限是 `v < X`、
白与红的跨零判定是 `v > X` / `h ≥ X`、各色系止点是 `h < X`。所以"调大还是调小"**总能从比较符号现推，不必背口诀**。

| 参数（默认） | 管到哪 | 往哪调 |
| --- | --- | --- |
| `ColorlessSaturation`（0.45） | 无彩/有彩分界，**黑/白/灰/棕全住在这条线以下** | 调低 → 更多像素被判成有彩（灰线容易被读成彩线）；调高 → 彩线容易掉进灰/白 |
| `BlackValue`（80） | 明度低于它才叫黑 | 黑线偏灰（打光强）→ 调高；暗背景被误判成黑线 → 调低 |
| `WhiteSaturation`（0.15） | 白的附加条件：饱和度必须低于它 | 白线偏色（灯光偏黄）→ 略调高，否则白会被读成黄 |
| `WhiteValue`（195） | 明度高于它才叫白 | 白线判不出来 → 调低；反光高光斑被判白 → 调高 |
| `BrownWarmth`（12） | 偏暖判据：R 比 G、B **都**高出这么多才算棕 | 棕色线被读成灰 → 调小；灰色线被读成棕 → 调大 |
| `BrownValue`（175） | 棕的明度上限（比它亮就归灰） | 浅棕/米色该算棕时适当调高（越接近白明度越容易和白抢字） |
| `RoseHueFrom`（330） | 玫红起点 | 玫红被读成紫 → 调小；紫被读成玫红 → 调大 |
| `RedHueFrom`（350） | 红起点（玫红/红分界） | **红与玫红只差十几度**，分不清就只调这一对（330 / 350） |
| `RedHueTo`（20） | 红止点（红跨 0 度：`≥350` 或 `<20` 都是红） | 橙红被读成红 → 调小；红被读成橙 → 调大 |
| `OrangeHueTo`（45） | 橙止点 | 橙黄之间分不清时调它 |
| `YellowHueTo`（70） | 黄止点 | 黄绿之间分不清时调它 |
| `GreenHueTo`（160） | 绿止点 | 青绿被读成蓝 → 调大；青绿被读成绿 → 调小 |
| `BlueHueTo`（230） | 蓝止点（比它高就是紫） | 蓝紫分不清时调它 |

**为什么不做一份"全局统一色卡"**：刻意不做。不同工位、不同产品的打光与材质不一样，
"玫红从哪里算起"本来就可能不同；全局一份要么大家互相迁就，要么再多支持几份、复杂度又上一层。
共用的是**词表（11 个词）与分类层次（先无彩后有彩）**，不是阈值数值。

## 二、取样口径：采样点怎么来、色怎么取

| 口径 | 内容 |
| --- | --- |
| 走向判定 | 矩形**半长大的那条轴**自动判为线束走向，采样方向与之垂直（沿短轴扫）；竖着画也能用 |
| 采样线 | 长轴方向 **5 条**邻近线，偏移 `-4 / -2 / 0 / 2 / 4` 像素。**不沿长轴摊开**（实测线束呈扇形散开，摊开后按行号合并会把只在个别列上明显的边界线洗成背景，丢过线、根数少两根） |
| 取色路径 | 元组版取点：对每条采样线一次调用取回整批灰阶，再按同一短轴位置对 5 个值**逐通道取中位**合成一条中位剖面 |
| 序列起点 | 索引 0 = **坐标较小的那一端**；方向相反勾 `ReverseSequence` |
| 取几根 | 剖面上"可靠像素"的连续段 + 等间距铺出来的线位，逐根取一段的**中位 RGB**（掐掉上下各 1/4 避开暗缝）再归成颜色词 |

**三个自适应阈值**都从**这一幅图**现算，不是写死的经验值——这是换灯换相机不用重调的底气：

| 阈值 | 怎么算 | 界面上 |
| --- | --- | --- |
| 暗线 | 剖面**众数亮度**（最常见的那个亮度就是**线间缝/背景的电平**）− `DarkSpanRatio`% ×（众数亮度 − 2% 分位亮度）。用 2% 分位而不用最小值：一个坏点就能把尺度拉跑 | 可调（`DarkSpanRatio`） |
| 白线 | 亮度的 `BrightPercentile` 分位 | 可调（`BrightPercentile`） |
| 彩度 | 剖面通道极差走**大津法**自动求 | **不给调**：实测极不敏感（20~110 都给出同一个根数），给人调反而多一个会调错的旋钮 |

### 取样旋钮往哪调（含两条方向裁定）

这些旋钮**全是无量纲的比例或百分位，不是绝对灰阶值**——这正是"自适应"的意义：换灯、换工装改的是尺度，比例大体不变。
暗线那条尤其要注意**比较方向**：判定线 = 众数亮度 − 百分比 × 跨度，而可靠判据是 `亮度 < 判定线`，
所以**百分比越小、判定线越高、算"暗"的像素越多**（不是反过来）。

| 旋钮（默认） | 口径 | 往哪调 |
| --- | --- | --- |
| `DarkSpanRatio` 暗线判据幅度（35） | 判定线 = 众数亮度 − 百分比 ×（众数 − 2% 分位亮度），像素**低于**判定线才算可靠的暗 | 线色普遍偏浅、暗缝不明显、暗线漏检（可靠段凑不出 2 段）→ **调小**；浅背景被误当成暗线 → 调大。两张样本图上的**安全阈值窗口是 100~160**，默认 35 给出 154 与 114，都在窗口里。**不许改成写死的绝对灰阶**——脚本版写死 150 只是碰巧落在窗口里，换一盏灯就要重调 |
| `BrightPercentile` 白线百分位（92） | 亮度**高于**这条百分位的行算可靠线像素 | 白线检不到 → **调小**（92 → 85 左右）；浅色背景被收成过长段、日志出现「丢弃了 N 段过长的可靠区间」 → **调高**（阈值抬高，又长又平的背景就落下去了）。⚠ 本控件界面上有两处 ToolTip 写的是"调小"，与算法自己发出的那条告警相反，**以告警与公式为准** |
| `MinRun` 最小段长（4） | 连续这么多行都可靠才算一根线 | 噪点多 → 调大；线很细（一根只有几行）→ 调小 |
| `MaxRunRatio` 最大段长比例（0.33） | 长过剖面长度这个比例的可靠段**按背景丢弃** | 浅色背景被算成线 → 调小或收紧框；真线被当背景丢掉 → 调大；填 `0` = 关掉保护（不推荐） |
| `RuleWindowRatio` 补色窗口比例（0.30） | 给"补出来"的那几根取中位色的窗口半宽（线距的比例） | 相邻两根颜色互相污染 → 调小；补出来的颜色太随机/偏暗 → 调大；线距很密时也调小 |
| `ExtendEnds` 端点外推（开） | 两端各多探一根，判据"那一格有明暗起伏"（局部起伏 ≥ 全局起伏的 20%），不要求认得出颜色 | 端部总少一根就开着；末端把线束外的边缘结构多报一根就关掉 |
| `WireCount` 线数（0 = 自动） | 强制按指定根数，**以检出范围的中点为基准**向两边展开 | 芯数固定、算法偶尔多一根少一根时可以钉死；日志会留一条"按手动指定展开"的说明 |

**线距（pitch）的仲裁**（看懂它才明白日志里那两条告警）：

| 情况 | 听谁的 |
| --- | --- |
| 自相关与分段中位间距相差 25% 以内 | 取平均，互相消噪 |
| 分段线距正好是自相关的整数倍（≥1.6 倍） | **信自相关**——那正是"漏检一半致使中位间距变成两倍"的典型情形，线被补回来 |
| 其余不一致 | **信分段线距**（自相关在边缘信号上容易被线宽变化带偏，实测给过 16 而真值 21.5） |

估完还夹一道硬闸：线距 `< 2` 像素或 `>` 剖面长的一半 → 直接报错，那说明**短边方向根本没和线束走向垂直**，调参数没用，重新画框。

**相位与端点用最小二乘回归定锚**：脚本版拿"第一个可靠段"当起点，端部那根一旦漏检就**整条序列错位一格**；
改成回归定锚后，端部漏检只会少一根，不会整体错位。

**高位深归一**：12/16 位相机图（`uint2`）灰阶远超 255，而明度类阈值与序列分析的直方图（256 桶）全按 8 位标定。
按实测最大灰度**等比压回 0~255**——色相与饱和度是比值，等比缩放不动它们，**颜色词的答案不变**；
压过时留一条告警说明"数值为什么变小了"。

## 三、判定口径：期望序列从哪来、比什么

期望序列的来源**只有两条，端口优先**：

| 优先级 | 来源 | 配方名显示 |
| --- | --- | --- |
| 1 | `ExpectedSequence` 输入端口（非空白） | 「输入端口」 |
| 2 | 配方表 `RecipeText`，**按实测根数匹配**（期望序列的长度就是这条配方要求几根） | 命中那行的产品名 |

逐位比对规则：长度不符直接判不合格且 `BadIndex = 0`；同长度时逐位比，遇到期望位是 `*` 就跳过该位，
否则**按字面比较**，第一个不相等的位号（从 1 起）就是 `BadIndex`。

结论全文只有三种写法（日志、画面标注、`Verdict` 端口、界面摘要共用同一句，避免三处口径不一致）：

```
线序正确，10 芯：黑,白,…（配方「10 芯」）
线序错误：第 3 根应为 灰、实测 白（配方「10 芯」；实测 黑,白,灰,…）
根数不符：实测 9 根（黑,白,…），配方「10 芯」要求 10 根
```

**`BadIndex = 0` 有两种意思**：要么全对，要么**根数本身就不符**。分辨办法只看 `Verdict`。

## 四、失败策略：配置问题按配置问题报，不判 NG

| 类别 | 情形 | 后果 |
| --- | --- | --- |
| **判定不合格** | 线序错、根数不符 | 步骤**照常跑通**，输出齐全，`Result=false`。下游用 `Result` / `BadIndex` / `Verdict` 分流 |
| **跑不动（Fail 停这一步）** | 上游没有图像；尚未框选采样区；图像通道数 < 3；半长/半宽 ≤ 0；采样区短边不足 8 个像素；采样点超出图像范围；剖面几乎没有明暗变化（亮度极差 < 25 级）；可靠段少于 2 段；线距估计异常或回归定锚失败；**配方缺失**；**期望词不在词表** | `Success=false` + `ErrorMessage`，提示语一律写清"怎么补" |
| **只告警、不中断** | 丢弃过长可靠区间；自相关与分段线距打架；线数按手动指定展开；同芯数多条配方（取第一条）；高位深已归一 | 进日志 Warn，判定照常出 |
| **投图失败** | 推图整体包在 `catch` 里 | 静默吞掉：**绝不**把一次成功的检测判成失败（与 `Plugin.PreProcessing` 同一口径）。`DisplayViewIndex=0` 时完全不推 |

**"配方缺失"与"期望词认不出"为什么特意报错而不是判 NG**：
配方没配是工程配置问题——判成 NG 会让一条配错的线永远把良品报成不良，现场只会以为"这批产品有问题"。
词表外的词（"深红"这种）比对按字面做、**永远匹配不上**，若默默判 NG，现场看到的结论是"应为 深红、实测 红"，
根本想不到是配方写错了。这两条与脚本版（走 Else 判 NG）是**有意不同**的。

## 五、和「区域颜色检查」（RegionColorPlugin）的分工

同一个内核（`ColorSampler` 取色、`ColorVocabulary` 分色、`ColorThresholds` 阈值、`ColorMarks` 画面语言），
但**问的问题不同**：

| | 颜色序列检查（本算子） | 区域颜色检查（`Plugin.ColorRegion` 的 `RegionColorPlugin`） |
| --- | --- | --- |
| 采样形状 | 一个矩形，**沿短轴取一条一维剖面** | 矩形/圆/椭圆区域，**区域内逐点** |
| 输出形态 | **一串有序颜色词** + 根数 | **主色 + 占比**这类"这一片是什么颜色、有多纯" |
| 判定 | 与期望**序列逐位**比（顺序有意义） | 与**期望颜色**比（面积/占比有意义） |
| 典型场合 | 线序、排线、色带、色块标签 | 指示灯、色标、颜色纯度、占比 |
| 规整补色 | 有（`Detail` 里标"补"） | 无此概念 |

**选哪个**：关心"顺序对不对"用本算子；关心"这一块现在是不是红/紫"用区域那个。
两个都要就串起来用（先序列检线序，再区域检指示灯），它们的阈值各带各的副本、互不影响。

**想比"两个色差多远"（ΔE）**：两个算子都给不了——它们 output 的是**离散颜色词**，不是连续距离。
要连续量就走别的路线：拿「区域颜色检查」的 `Rgb` 中位色输出端口（`OutputPort<string>`，"区域中位色 R,G,B"）
接「C#脚本」自己算距离，或先用图像处理类插件做通道分离/阈值分割再判。
线序这类"离散颜色词"场景，用本算子就够。
