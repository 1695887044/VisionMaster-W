# 轴运动

> 分类：运动控制 ｜ 来源：插件 Plugin.Motion.Steps

让一根轴走到目标位置。产出是 `Accepted`（命令有没有被收进队列）和 `Axis`（本次用到的轴名，
供下游步骤直接引用），以及每个步骤都有的 `Success` / `ErrorMessage`。

它是运动链路的**第三环**：

`轴使能 ──▶ 轴回零 ──▶ 轴运动 ──▶ 等待到位 ──▶ 读轴状态 / 轴卡 IO / 轴停止`

**本步骤最关键的一条语义：它只下发，不等到位。**
`Accepted=true` 只代表"这条命令被这张卡收下了"，不代表轴已经开始动，更不代表已经到位。
这不是缺陷，而是必然：产线上大量场景要"两轴同时运动"，如果运动内部阻塞等到位，
两条轴就只能串行跑 —— 现场只会发现"节拍莫名慢了一倍"，而且很难看出原因。
要把"下发"和"等待"分开表达，用户才能显式写出自己的意图。

## 为什么需要它 / 原理

- **命令走卡内队列**：入队后由该卡的执行线程按先进先出逐条执行，
  所以"先动轴、再夹紧"这类顺序关系天然是成立的（「轴卡 IO」的写输出走同一条队伍）。
  队列有深度上限（卡级默认 `256`），满了会被拒（返回 `Rejected_QueueFull`，原因原文 `命令队列已满（上限 256 条）`）。
- **目标与速度是输入端口，不是配置项**：因为它常常来自上游 —— 视觉定位给出坐标 →
  这一步接过去 → 轴走过去。做成配置项就绑不了变量，视觉引导无从落地。
  「绝对/相对」同样是端口：这是现场最常切的一个开关，必须能在界面上改、也能被上游动态指定。
- **取值优先级**：一律"上游链接值 > 界面手填值"。手填框被清空时按空值走校验，
  由校验给出"没有启用名为「」的轴"，而不是软件擅自编一个默认坐标 —— 把未知当成一个坐标是最危险的做法。
- **不做点位表绑定**：本步骤只认 `Target` 端口里的数值，不会去读「运动卡设置」里的点位表
  （P0~P15 是给调试面板点位运动用的）。要在流程里用点位，把点位的坐标作为变量喂给 `Target`。
- **加速度与曲线本步骤不下发**：命令里的加速度取 `0`、曲线取梯形。
  落到正运动卡上就是"加速度沿用控制器内既有值（不覆盖）、S 平滑时间每次定位前被写回 0"。
  要按方案指定加减速或走 S 曲线，走「运动卡设置」/调试面板那条路，不要指望这一步。

## 输入端口

| 端口 | 必填 | 说明 |
| --- | --- | --- |
| `Axis` | 否 | 逻辑轴名，默认 `X`。下拉候选来自「运动卡设置」里**已启用**的轴（全局唯一名）；可由上游变量给出 |
| `Mode` | 否 | 运动方式，默认 `绝对（走到坐标点）`。枚举端口，在绑定界面呈现为下拉 |
| `Target` | 否 | 目标位置，默认 `0`，单位 **mm**。绝对=目标点坐标；相对=增量，**可为负**（负号即方向） |
| `Velocity` | 否 | 速度，默认 `0`，单位 **mm/s**。`0` 表示"用卡级默认"（见下方口径，真机与仿真行为不同） |

## 输出端口

| 端口 | 说明 |
| --- | --- |
| `Accepted` | 命令是否被收进队列（本步骤开头先清成 `false`）。**不代表已到位，也不代表已起动** |
| `Axis` | 本次运动的逻辑轴名（原样回填，供下游「等待到位」直接引用，避免手抄轴名抄错） |
| `Success` | 本步骤是否成功（每个步骤都有） |
| `ErrorMessage` | 失败原因原文（每个步骤都有） |

## 关键参数

> 完整参数与取值范围以流程中该步骤的「模块参数」界面为准，这里只解释含义。

本步骤**没有任何配置属性**，四个可调项全部是输入端口（步骤的参数面板只列输入端口，
所以这四项在界面上都能改、也都能被上游链接）：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `Axis` | `X` | 逻辑轴名。一次解析同时得到"哪张卡 + 哪个物理轴号"，流程里没有选卡/填 IP 这件事 |
| `Mode` | `Absolute` | 存档的是成员名 `Absolute` / `Relative`，界面显示中文；改显示名不会断连线 |
| `Target` | `0` | mm；绝对时是目标点，相对时是增量 |
| `Velocity` | `0` | mm/s；0 走默认 |

## 口径与失败策略

- **单位是 mm，不是脉冲**。流程侧一律 mm / mm/s；脉冲当量换算发生在驱动层。
  正运动卡在连接时对每个启用轴下发 `SetUnits`（当量取自轴映射 `UnitsPerMm`，默认 `1000`），
  之后厂商 API 收发的就是 mm，软件**不再二次除当量** —— 所以"改当量"只需改「运动卡设置」里的映射。
- **绝对运动的基准点** = 这根轴的坐标零点，也就是「轴回零」建立出来的那个原点。
  没回零时当前位置是上电瞬间的读数，按绝对坐标运动可能直接撞限位。
- **相对运动的基准点** = 下命令时刻的当前位置（指令位置，不是编码器实际位置）。
  注意：**软限位只校验绝对运动**，相对运动不查 —— 它由卡侧的硬限位与驱动器保护兜底。
  要靠软限位保护某段行程，请把该动作写成绝对运动。
- **速度填 0 的真实行为**（现场最容易踩的差异）：
  正运动卡"命令速度 ≤ 0 就不覆盖"，即沿用**控制器内该轴当前的 SPEED**（可能是厂商调试软件里设的值）；
  虚拟运动卡则回落到卡级默认 `DefaultVelocityMmPerS`（默认 `50`）。
  两者不一致。要确定性的速度，请在流程里显式给非零速度。
- **超时用的是卡级值**：本步骤的命令超时取该卡的 `CommandTimeoutMs`（卡级默认 `30000` ms），
  它只用于"把命令写进卡"这一步；**真正的到位超时由「等待到位」步骤负责**，两者不要混。
- **算不算流程失败**：算，且只覆盖"下发"这一段。
  ① 轴名解析失败、② 卡不在「在线」状态（`运动卡「…」当前不可运动：…`，报警/安全停机/未连接都在这档）、
  ③ 命令被拒绝（软限位越界、轴号无效、队列满、不支持），三种都 `Success=false` 并把原因写进 `ErrorMessage`。
  **下发成功之后的运动失败（撞限位、跟随误差报警、中途掉线）不由本步骤报告**，
  必须由后面的「等待到位」或「读轴状态」去发现。
- **拒绝原因带建议**：被拒绝时文案是 `运动命令被拒绝（<返回成员名>）：<建议原文>`，
  括号里是设备返回的**成员名**（不是中文），后半句才是可直接照做的建议。四种拒绝的含义：
  | 返回成员名 | 含义 | 典型建议原文 |
  | --- | --- | --- |
  | `Rejected_NotConnected` | 卡不在线（未连接 / 连接中 / 报警 / 已安全停机） | `运动卡未连接` / `运动卡正在连接/断开，请稍候` / `运动卡处于报警状态，请先清除报警` / `运动卡已安全停机，请重新连接后再操作` |
  | `Rejected_NotSupported` | 这张卡/这个动作不支持 | 如 `该卡不支持回零方式「…」` |
  | `Rejected_InvalidArgument` | 参数非法：轴号越界或超出软限位 | `目标 12.000 mm 超出软限位 [-1000.0, 1000.0]` |
  | `Rejected_QueueFull` | 下发太快或卡侧卡住 | `命令队列已满（上限 256 条）` |
- **日志一定留痕**：成功时打印 `已下发：X 绝对运动 → 12.000 mm @ 50.0 mm/s（未等到位；如需等待请在其后加「等待到位」步骤）`。
  排查"为什么没等"时先看这行。

## 典型用法 / 接线

```
单轴一次定位：
  轴使能(X) ──▶ 轴回零(X) ──▶ 本步骤(X) ──▶ 等待到位(X) ──▶ 轴卡 IO(OUT0=ON 夹紧)
                                   ▲
                                   └ Target ◀── 视觉定位.X坐标      Velocity ◀── 变量定义.速度

视觉引导（最常见）：
  图像采集 ──▶ 视觉定位 ──▶ 本步骤（Target ◀── 定位结果.X，Mode=绝对）──▶ 等待到位 ──▶ 拍照确认

两轴同时运动（下发/等待拆开的全部意义）：
  本步骤(X) ──┐
              ├──▶ 等待到位(X) ──▶ 下一步
  本步骤(Y) ──┘   等待到位(Y) ──▶ 下一步
  说明：两个运动步骤背靠背放，两条命令进同一队列先后下发，然后各自等待；
        物理上两轴几乎同时起动。若把等待夹在中间，就退化成串行。

收尾：… ──▶ 轴停止（需要中断时）──▶ 读轴状态（确认停下来）
```

`Mode` 用绝对还是相对：定位到"某个位置"用绝对；"再走一段"（退料、微探、补走）用相对。
相对运动的方向靠 `Target` 的正负号表达，`Mode` 里没有方向选项。

## 常见问题

**Q：步骤绿色成功，轴却好像没到位置 / 后面的动作扑空？**
正常现象——本步骤不等到位。在它后面补一个「等待到位」（`Axis` 直接引用本步骤的 `Axis` 输出），
或者在要求不严的场合用「读轴状态」确认 `InPosition` 与 `Moving`。

**Q：`运动卡「…」当前不可运动：…`，但卡明明连着？**
看冒号后面的状态说明。卡可能已经进了「报警」（限位/伺服信号触发）或「已安全停机」（通信看门狗跳闸）。
这两种状态都需要先处理再运动：报警去调试面板清报警，安全停机需要人工重新连接。

**Q：`运动命令被拒绝（Rejected_InvalidArgument）：目标 … mm 超出软限位 […]`？**
九成是**绝对目标超出软限位**（「运动卡设置」里该轴的 `SoftLimitMinMm` / `SoftLimitMaxMm`，默认 ±1000000 mm）。
其次核对：轴名是否指向了另一张卡的同名轴、`Target` 是否被上游给了一个离谱值（视觉像素当量没换算、
坐标系没平移）。相对运动不查软限位，所以这条报错基本只出现在绝对运动上。

**Q：速度填 0 到底跑多快？**
真机上沿用控制器内该轴当前的 SPEED（不是软件里的"卡级默认速度"），仿真卡则用卡级默认 50 mm/s。
节拍敏感的流程请把速度显式写成非零值，或把默认速度配在「运动卡设置」的 `DefaultVelocityMmPerS` 并接受仿真口径。

**Q：想要 S 曲线 / 指定加速度，这一步里没有？**
确实没有。本步骤的加速度恒为"不覆盖"、曲线恒为梯形（正运动侧每次定位前会把 S 平滑时间写 0，
包括上一条命令设过的 S 也会被清掉）。这是刻意的：流程步骤只负责"去哪、多快"，
加减速与平滑形状属于卡的运动参数配置面。

**Q：`运动命令被拒绝（Rejected_QueueFull）：命令队列已满（上限 256 条）` 怎么处理？**
说明这一轮往这张卡堆了太多命令（卡级默认 256 条）。
通常是流程里运动步骤放在循环/并行组里跑得过密，或者长命令卡住了队列：
先检查有没有轴在报警或通信受阻（此时队列不消费），再考虑加等待、降低循环频率或拆分流程。

**Q：换了一张卡、或者重新接了线，流程要改吗？**
不用。改「运动卡设置」里的卡配置与轴映射（`PhysicalIndex` 物理轴号 0 基、`UnitsPerMm` 当量）即可，
流程里引用的还是那个轴名。唯一要重做的是：确认新卡的行程软限位、以及重新回零建立零点。

**Q：为什么 `Axis` 既是输入又是输出？**
输入的 `Axis` 是"我要动哪根轴"；输出的 `Axis` 是"本步骤实际用到的轴名"（把上游给的值定稿下来）。
下游「等待到位」「读轴状态」直接链这个输出，就不存在手抄轴名抄错的问题 ——
尤其当轴名是配方变量给的时候。
