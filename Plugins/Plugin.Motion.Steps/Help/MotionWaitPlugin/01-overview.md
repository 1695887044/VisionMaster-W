# 等待到位

> 分类：运动控制 ｜ 来源：插件 Plugin.Motion.Steps

等一根轴真的走到位置，产出 `Position`（到位位置，mm）和 `Elapsed`（等待耗时，ms）。
它是运动链路的**第四环**，也是「轴运动」的必配搭档：

`轴使能 ──▶ 轴回零 ──▶ 轴运动 ──▶ 本步骤 ──▶ 读轴状态 / 轴卡 IO / 轴停止`

为什么它必须是一个**独立步骤**而不是让「轴运动」自己等：运动是异步的，
产线上大量场景要"两轴同时运动"，如果运动内部阻塞等到位，两条轴就只能串行 ——
现场会发现"节拍莫名慢了一倍"却极难看出原因。把"下发"与"等待"拆开，用户才能显式表达意图。

## 为什么需要它 / 原理

- **等的是设备状态，不是"某条命令的完成信号"**。命令对象不跨步骤传递（那会让流程依赖对象身份，
  无法保存/重放），而"这根轴现在到没到位"是设备上随时可查的事实。
  判据是快照里的 `InPosition` 与 `Moving` 两个位**同时成立**（已到位 且 不在运动中）。
- **读的是轮询快照，不发起通信**。轴状态由这张卡的轮询线程按卡级 `PollIntervalMs`（默认 10 ms）统一刷新，
  本步骤只是"隔一会儿去看一眼最新那份"。所以本步骤的 `PollIntervalMs` 不会增加通信量，
  但它决定了你最快多快能发现变化 —— 设得比卡级轮询还小只是空转。
- **报警/限位优先于"到位"**。轴在报警或撞限位时，位置可能恰好停在目标附近，
  只看 `InPosition` 会把"撞停"当成"走到位"。所以每次循环先查硬信号（急停输入 / 正限位 / 负限位 / 报警），
  有就直接判失败并带上建议。
- **超时也是失败，而且不算"走完了"**：`走不到` 与 `走得慢` 必须能区分开。
- **流程停止能立刻退出**：取消优先于一切判断，不会傻等满超时；等待间隔也是可中断的。
- **同一次判断里字段自洽**：因为读的是同一采样时刻的快照，位置与运动状态不会来自两个时刻。

## 输入端口

| 端口 | 必填 | 说明 |
| --- | --- | --- |
| `Axis` | 否 | 逻辑轴名，默认 `X`。下拉候选来自「运动卡设置」里已启用的轴；**建议直接链上游「轴运动」的 `Axis` 输出**，避免手抄轴名 |

## 输出端口

| 端口 | 说明 |
| --- | --- |
| `Position` | 结束时刻的轴位置（mm，指令位置）。**超时与正常到位都会写**；本步骤开头先清 `0` |
| `Elapsed` | 从进入等待到结束的耗时（ms）。超时时也写实际等了的时长 |
| `Success` | 本步骤是否成功（每个步骤都有） |
| `ErrorMessage` | 失败原因原文（每个步骤都有） |

## 关键参数

> 完整参数与取值范围以流程中该步骤的「模块参数」界面为准，这里只解释含义。

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `Axis` | `X` | 逻辑轴名。这是**输入端口**，界面上可改、可被上游链接 |
| `TimeoutMs` | `30000` | 等待超时 ms（代码里对 ≤0 的值按 `1` 处理，不给 0 或负数）。超过即判失败 |
| `PollIntervalMs` | `20` | 每轮查看快照的间隔 ms，实际取值被夹到 `1~500`（填 1000 也只按 500 跑）。太小的代价是白耗 CPU，通信量不受它影响 |

> 注意：`TimeoutMs` 与 `PollIntervalMs` 是步骤的**配置属性**，而本插件没有自定义配置界面、
> 参数面板只列输入端口 —— 因此这两项在界面上**暂无编辑入口**，实际生效的是默认值/流程存档值。
> 需要改超时，目前只能改流程存档里该步骤的属性值。

## 口径与失败策略

- **单位**：`Position` 是 **mm**（驱动已按脉冲当量换算；正运动卡在连接时对每个启用轴下发 `SetUnits`，
  之后 API 收发都是 mm），不是脉冲数。`TimeoutMs` / `Elapsed` 是毫秒。
- **位置读的是指令位置**（正运动 `GetMpos`），不是编码器实际位置。
  两者在跟随误差、丢步、被外力推动时会有差别：要核对"实际到没到"，请看伺服/编码器等值或直接看机构。
- **坐标基准**：绝对运动的基准是「轴回零」建立的零点；本步骤只是读回来，不做任何坐标系换算。
- **每种结束方式返回值都清楚**（都写 `Position` / `Elapsed`）：
  | 结束情形 | `Success` | `Position` / `Elapsed` | 说明 |
  | --- | --- | --- | --- |
  | 正常到位 | true | 到位位置 / 实际耗时 | `InPosition` 且非 `Moving` |
  | 超时 | false | 超时瞬间的位置 / 已等时长 | 报错含当前位置，便于判断走了多少 |
  | 期间报警/限位/急停 | false | **不写**（保持开头的 0） | 硬信号优先，防"撞停当到位" |
  | 快照读不到 | false | 不写 | 卡可能已断开，附状态说明 |
  | 流程被停止 | false | 不写 | `等待轴「X」到位时被中断（流程已停止）` |
- **算不算流程失败**：算，除"正常到位"外全部失败。超时那句报错本身带排查方向：
  `等待轴「X」到位超时（>30000 ms，当前位置 12.345 mm）：请检查目标是否超出行程、速度是否过低，或该轴是否被限位/报警阻挡`。
- **它不等"别人"**：只等 `Axis` 指定的那一根轴。多轴同时运动时，每个轴各放一个本步骤。

## 典型用法 / 接线

```
标准四步（最常见）：
  轴使能(X) ──▶ 轴回零(X) ──▶ 轴运动(X) ──▶ 本步骤(X) ──▶ 轴卡 IO(OUT0=ON)
                                                  │
                                    Axis ◀────────┘（直接链「轴运动」的 Axis 输出）

两轴同时运动 + 各自等待：
  轴运动(X) ──┐
              ├──▶ 本步骤(X) ──┐
  轴运动(Y) ──┘   本步骤(Y) ──┴──▶ 读轴状态 / 下一步

收尾确认（停止之后）：
  轴停止(X) ──▶ 本步骤(X)（TimeoutMs 给小一点）或 读轴状态(X) 看 Moving=false

报表取数：
  本步骤.Position ──▶ 变量/数据记录（到位位置）
  本步骤.Elapsed  ──▶ 数据记录（单件耗时，用于发现节拍漂移）
```

等待超时怎么给：按"这段行程最长合理耗时 + 余量"。粗略算法：`行程(mm) ÷ 速度(mm/s) × 2 + 1000 ms`。
不要给到几十秒还指望流程自己发现异常 —— 那是看门狗和报警在管的事，超时给太长会让异常件占着工位。

## 常见问题

**Q：本步骤秒过（`Elapsed` 只有几 ms），但轴明明还在路上？**
判据是设备状态，不是"这条命令的结果"。两种可能：① 轴本来就已经停在目标附近（比如这一轮目标位置没变），
`InPosition` 一直为真；② 前面的「轴运动」其实失败了、根本没下发，于是这里读到的是"静止且到位"。
先回看上游运动步骤本轮的 `Success` 与 `Accepted`，再看 `Position` 是不是你以为的目标值。

**Q：真机等到了，仿真里却总是立刻返回？**
虚拟运动卡按"每拍匀速推进"模拟异步运动，理论上也会有耗时；但如果目标与当前位置相同就直接判到位。
仿真的节拍不等于真机节拍 —— 用仿真验**逻辑顺序**，不要用它定超时数值。

**Q：超时了，位置显示差一点点。**
先分清是"没走完"还是"走完了但卡没报到位"：
① 看 `Position` 与目标差多少，差得远就是速度过低/行程过长/被中途停止；
② 差一点点却是到位信号没起来，通常是到位判断条件（跟随误差窗口、到位带宽）在控制器/驱动器侧设得太严，
去厂商软件里看该轴的到位判断参数，而不是把流程超时加大。

**Q：`等待轴「X」期间出现异常信号：报警：…` —— 明明刚才是好的。**
等待过程中卡会持续采样，急停按钮被按下、限位被压到、伺服报警都在这一步暴露。
这**是它该有的表现**：报警优先于到位，宁可报错也不要把撞停当到位传给下一步。按建议处理后再跑。

**Q：`读不到轴「X」的状态快照`？**
说明这张卡连快照都拿不到（还没轮询到、或刚断开）。
去「运动卡设置」/调试面板看卡状态：未连接、已安全停机都会有这句。恢复连接后重试，掉线原因看通信与供电。

**Q：能不能用它代替「读轴状态」做位置判定？**
能拿到位置，但拿不到全貌：本步骤只输出 `Position` 与 `Elapsed`。
要速度、使能、限位、报警、`Status` 一句话描述，请用「读轴状态」。

**Q：`PollIntervalMs` 改大有没有副作用？**
有，但不是通信：它是"多久看一次快照"。给到 500 ms 时，最坏会多等半秒才发现到位，
短行程高精节拍下这半秒就是产能；卡级轮询（默认 10 ms）不受本参数影响。

**Q：多条轴排队等，会不会互相拖累？**
不会互相"等"，但**共享同一条命令队列**：同一张卡上的命令是逐条执行的。
流程里两个轴的动作要真并行，请放到不同卡，或者接受"下发很快、执行排队"这个事实 ——
本步骤只是观察结果，它本身不占用队列。
