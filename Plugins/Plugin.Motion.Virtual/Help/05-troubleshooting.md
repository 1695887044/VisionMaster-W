# 虚拟运动卡（仿真）：排障

> 分类：运动卡 ｜ 来源：插件 Plugin.Motion.Virtual

下面每条都是**界面上/日志里真会出现的原文**（从源码逐字抄），按"现象 → 为什么 → 怎么改"排。
其中"模拟："开头的三句是**故障注入的专属文案**——看到它们，说明有代码把对应开关打开了。

## 一、连接与配置类

**驱动列表里没有「虚拟运动卡（仿真）」**
为什么：宿主扫描的是运行目录 `Modules\` 下实现运动设备接口的类型；`Plugin.Motion.Virtual.dll`
没投递到 `Modules\` 就选不到（插件工程必须放 `Plugins\` 下构建才有投递路径；改源码不重建 = 产物陈旧）。
怎么改：重建插件工程并确认 DLL 进了 `Modules\`，重启应用。

**`已连接虚拟卡（3 轴，增量编码器，需先回零）`**
这不是报错，是连接说明——`SimulatedAbsoluteEncoder` 被设成了 false。
此时"已回零"标记为假，运动类流程要先走「轴回零」；恢复默认（true）重连即回到"位置可信"。

**填了地址/机型却没反应，或者乱填也能连**
预期行为：本驱动的连接过程**完全不读**地址与机型（它们只在正运动那侧有意义）；
仿真轴数/IO 数也不受机型影响（由 `Simulated*Count` 开关定，且**界面上没有入口**、不随方案落盘）。

## 二、命令被拒类（还没执行就被闸门拦下）

**`轴号 5 超出仿真范围（0~2）`**
为什么：轴映射的物理轴号（**0 基**）超出当前仿真轴数。仿真默认 3 根（0~2）。
怎么改：把映射改到 0~2；确实需要更多仿真轴，由测试代码设 `SimulatedAxisCount` 后**重连**。

**`运动卡处于报警状态，请先清除报警`**
为什么：命令闸门对**除清报警外的所有命令**要求卡「在线」，卡此刻在「报警」。
报警来源通常是 `SimulateAlarm` 被打开了（见第四节）。
怎么改：清报警（调试面板或清报警命令）；注意清报警**不会自动使能**，恢复运动前还要补「轴使能」。

**`运动卡已安全停机，请重新连接后再操作`**
为什么：看门狗判失联（常见于 `SimulatePollException` 打开后连续轮询失败）后的状态；
状态机不会自己回在线。怎么改：**先断开再连接**（人工确认那一步不能省——安全停机意味着原因还没排除）。
增量编码器配置下，失联还把"已回零"归了假，重连后要**先回零**。

**`回零被拒绝（Rejected_NotSupported）`一类的"不支持此回零方式"**
为什么：虚拟卡只声明支持 3 种回零方式（负限位+Index / 原点开关 / 零位置预设），
**入队时**就拦（而不是跑到一半才失败）。怎么改：仿真流程改用这 3 种之一；
真机上再按目标卡型换（正运动总线型 8 种、脉冲型 3 种且集合不同——见《相位差》页对照表）。

## 三、执行失败类（命令进了队列，仿真给的失败）

**`轴未使能（请先执行「轴使能」步骤）`**（绝对/相对/点动）
**`轴未使能（回零前需先使能）`**（回零）
为什么：流程里没放使能、或使能失败了、或中途失能/急停过。仿真**不替你省这一步**——
这条与真卡同口径。它的故障级别是"可恢复"，建议原文：`在流程里把「轴使能」步骤放在运动步骤之前`。
怎么改：按链路补 `轴使能 ──▶ …`；急停与清报警都不会自动重新使能。

**`轴处于报警状态，无法运动`**
为什么：驱动层的第二道检查（轴级报警位为真）。正常现场走不到这里——基类门禁会先把整卡拦下；
撞见它说明你在卡还没被轮询转「报警」的那一拍里抢跑了一条运动。
怎么改：等一拍、或直接按"报警态"处理（清报警 → 使能）。

**`输出点 12 超出范围（0~7）`**
为什么：仿真只有 8 个输出口（`SimulatedOutputCount`，点号 0 基）。真卡（如正运动 16~20 出）上同样的点号可能合法。
怎么改：仿真里用 0~7；换真卡时重新核对点号范围（IO 差异是仿真→真机切换清单上的一项）。

**`回零超时（>3000ms）`**（数字取命令超时或卡级 `CommandTimeoutMs`）
为什么：回零期满还没被轮询线程翻完（`SimulatedHomeDurationMs` 被测试代码改得比超时还长，
或轮询线程停了——比如同时开着 `SimulatePollException`）。
怎么改：让回零时长小于超时；两个注入开关不要在没有配套调整的情况下叠着用。

## 四、"模拟："开头的三句 = 故障注入在生效

**`模拟：伺服报警`**（出现在轴状态/`Status` 描述里）
来源：`SimulateAlarm` 被打开（所有轴都报）。它**界面上没有入口**，是冒烟测试/代码设的。
验证完记得关回去，或发一次清报警（清报警会把开关一起复位——否则"清完立刻又报"）。

**`模拟：与运动卡的通信中断`**（轮询异常，随后看门狗 → `已安全停机`）
来源：`SimulatePollException`。人工环境里看到它，说明有测试代码在跑或开关没关。
怎么恢复：关开关后**先断开再连接**。

**`模拟：运动命令执行失败`**（随后该命令判失败，基类按失败处置清队/停机）
来源：`SimulateCommandFailure`。注意它只拦**绝对/相对/回零**三类，点动与停止不受影响。

## 五、"看起来不对但其实正常"类

**Q：仿真一切正常，上真机节拍慢一倍 / 轴串行？**
① 核对"先都下发、再各自等待"的流程排法；② 同一张卡的命令是**排队执行**的，两轴真并行要用不同卡。
仿真推进快（回零 200 ms 级、匀速运动），很容易把"少放等待"掩盖过去——先复核结构。

**Q：仿真里速度填 0 跑出 50 mm/s，真机却是别的值？**
两套口径：仿真 0 → 用卡级默认速度；真卡 0 → 不覆盖控制器内当前速度（可能是厂商调试软件里设的）。
节拍敏感流程显式给速度，别指望两边一致。

**Q：改了脉冲当量，仿真位置纹丝不动？**
正常。仿真不做当量换算，`UnitsPerMm` 对它无效；当量必须真机验（典型现象"走 10 mm 实际走 10000 单位"）。

**Q：`读轴状态` 的 `Velocity` 仿真有数、真机全是 0？**
两边实现不同：仿真填当前推进速度，正运动轮询不读速度寄存器。判"动没动"一律用 `Moving`——
**用仿真验 `Velocity` 会制造"看起来能用"的假象**，这类"字段在仿真里活、在真机里死"的情形见《相位差》页深度表。

**Q：仿真回零只要 200 ms，流程是不是不用等回零？**
不是。「轴回零」步骤**会等待**（卡级超时 + 1000 ms），仿真只是做得快。真机几十秒是常态，超时别照抄仿真观感。

**Q：人工怎么触发异常分支（没有测试代码时）？**
三个注入开关界面上没有入口。可行的两条替代：① 把绝对目标写到软限位之外，让仿真"越界即撞限位"，
观察硬信号 → 急停 → 报警链路；② 把「等待到位」超时给得很小，制造超时分支。

**Q：虚拟卡和真卡混着用可以吗？**
可以同时配多张，每张独立队列与线程。注意「轴停止」留空 = 停**所有卡**的全部轴，混用时仿真卡会被一起停（无副作用，但要知道）。
