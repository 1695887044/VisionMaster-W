# 海康相机 · 取流与触发口径

> 分类：相机驱动 ｜ 来源：插件 Plugin.Camera.Hikvision

本页讲"这台相机怎么出图、图以什么形态进队列、什么时候算没图"。参数怎么填见《端口与参数》，
现象对号入座见《排错》。

## 一、取流节奏：一条线程、四个动作

设备打开成功并「开始采流」后，本驱动拉起**一条自己的取图线程**（每台相机一条，线程名 `HikGrab-序列号`），
每轮固定做四件事：

| 步 | 动作 | 现场含义 |
| --- | --- | --- |
| 1 | 向 SDK 要一帧，**每轮最多等 100 毫秒** | 没来帧就回头再看停止标志，所以"点停止"最多滞后一个 100 ms 周期生效 |
| 2 | 读宽高、像素格式名、缓冲指针与字节数 | 格式不认识 → 丢这一帧并记一条告警，不进队列 |
| 3 | 转成 `Mono8`（灰度）或 `RGB8_Packed`（彩色），再拷成独立字节数组入队 | 入队的永远是 8 bit 的标准布局，下游不必关心相机原生的 Bayer / YUV / 高位深 |
| 4 | 立刻把 SDK 缓冲归还 | SDK 侧收图不被阻塞——这是真机驱动第一条硬约束 |

**单帧失败不带垮线程**：解算异常、转换失败、格式不认识，都只丢那一帧 + 一条告警日志。
真不出图的表现形式是消费端**等图超时**，不是驱动报错。

## 二、触发口径（最容易误解的一项）

本驱动从 2026-10-19 起**真正读取并下发** `CameraSettings.TriggerMode`，四档语义如下：

| 模式 | GenICam 侧 | 谁产生帧 | 采集步骤做什么 |
| --- | --- | --- | --- |
| `Continuous`（连续采图） | `TriggerMode=0` | 相机自由出图 | 只 `WaitNextFrame` |
| `Software`（软触发） | `TriggerMode=1` + `TriggerSource=Software` | 软件每次下发 `TriggerSoftware` 后曝光一次 | 先 `TriggerSoftware()`，再 `WaitNextFrame` |
| `RisingEdge`（上升沿） | `TriggerMode=1` + `TriggerSource=LineN` + `TriggerActivation=RisingEdge` | 相机 IO 线上升沿 | 只 `WaitNextFrame`（外部信号触发） |
| `FallingEdge`（下降沿） | `TriggerMode=1` + `TriggerSource=LineN` + `TriggerActivation=FallingEdge` | 相机 IO 线下降沿 | 只 `WaitNextFrame`（外部信号触发） |

- `TriggerSourceLine`（0~3）对应 `Line0~Line3`，只对上升沿/下降沿有效；`TriggerDelayUs` 是触发延时（微秒）。
- ⚠ **别把两边的 0 当成同一个意思**：GenICam 节点的 0 是"触发关闭 / 连续采图"，
  本仓枚举的 0 是"软触发"。驱动通过 `HikvisionTriggerPlan` 按成员语义映射，**不按数值直接透传**。
- **旧方案迁移**：2026-10-19 之前的配置没有 `TriggerSchemaVersion`，当时驱动固定连续采图；
  升级后这类配置自动迁移成 `Continuous`，保持升级前的真实行为。要改用触发，在相机设置里重新选一次模式并应用即可。
- **失败不静默**：驱动下发后会回读 `TriggerMode`，不一致就抛"触发模式回读不一致"；
  打开设备时触发下发失败会**阻断打开**并关掉句柄，不会再出现"界面说上升沿、相机连续出图"。
- **软触发失败不会退化成等图超时**：采集步骤会明确报"软触发失败"或"驱动不支持软触发"。
- **多相机同步**不在这里解决：每台相机各自按自己的触发设置出图；需要"同一时刻曝光"时，
  仍要由 PLC/同步盒给所有相机同一触发信号（或后续做同步采集步骤）。

## 三、像素格式与通道数

| 相机原生格式名里含 | 判定 | 入队形态 |
| --- | --- | --- |
| `Mono` | 单通道 | 1 字节/像素 |
| `Bayer` / `RGB` / `BGR` / `YUV` / `YCbCr` | 彩色 | 3 字节/像素交错 |
| 其它（含空名） | 不认识 | **丢帧** + 日志"暂不支持的像素格式 X，该帧被丢弃" |

- 判定只看**格式名字符串**（GenICam 命名约定），不看 SDK 枚举的数值。
- 高位深（`Mono10` / `Mono12` / `BayerXX`）入队前已降到 8 bit，下游拿到的是 8 bit 图。
  测量需要 8 bit 之外的灰阶，得在相机侧就用 8 bit 输出并接受降噪——本驱动不提供高位深通道。
- 布局统一：行优先、**无行填充**，单行字节数 = 宽 × 通道。彩色按 R/G/B 顺序交错，
  建图（转成 `HImage`）由消费者「图像采集」按仓库唯一约定完成；**红蓝互换**几乎总是"有人绕过它新写了一份"。
- 宁可丢帧也不给下游一张错位的图——所以换了少见机型/自定义格式后，**先去日志里找那句"暂不支持的像素格式"**。

## 四、队列、计数与"每帧只被取一次"

| 计数 | 涨于 | 用途 |
| --- | --- | --- |
| 累计收帧 | 每帧入队 | 判断"相机到底有没有在出图"——**这是掉线的第一判据** |
| 待消费帧数 | 入队加、取走减 | 长期为 0 且累计在涨 = 帧被别人取走或流程刚好赶上 |
| 溢出丢帧 | 队列超上限、丢最旧 | **每丢一帧 = 一个未被检测的工件**，要当质量事故查 |
| 其它丢弃 | 帧不自洽 / 未连接 / 已停止采流 / 断开或停流时清队列 | 与溢区分开计数，因为原因与处置完全不同 |

- 队列满丢**最旧**：宁可给流程一张较新的图，也不让积压越来越旧。
- 界面"清零计数"只清溢出与丢弃，累计收帧与帧号**不清零**：帧号单调递增是溯源对账的基础。
- 一帧只被消费一次，**帧不广播**：两个采集步骤选同一台相机会互相分抢。

## 五、等图超时怎么读（四个数字定位根因）

采集步骤的超时文案形如：`等待相机「X」出图超时（N ms）；相机状态：…，待消费 N 帧，累计收帧 N，溢出丢帧 N`。

| 计数表现 | 结论 | 下一步 |
| --- | --- | --- |
| 累计收帧不涨 | 相机根本没出图 | 查状态是否 `Streaming`、相机侧是否在等外部触发、网线/供电、是否被别的程序抢走 |
| 累计收帧涨、待消费长期为 0 | 图来了但立刻被取走，本轮没赶上 | 流程节奏问题：看单步耗时，或放宽取图超时 |
| 待消费长期等于队列上限、溢出在涨 | **产能不匹配** | 先解决处理速度或降相机节拍，**不要靠加大队列容量掩盖** |
| 状态显示采流中，但累计不涨 | 掉线未被感知（不启心跳、未订阅 SDK 掉线回调） | 停止采流 → 断开 → 重连 |

**不做"重试等下一帧"**：这一帧没等到就是没等到，继续等只会让流程越来越滞后于生产；
产线上"这一件没检出"必须被明确记录。

## 六、掉线与重连

- 真机这一侧**不启心跳看门狗**（心跳是给"没有任何连接状态可言"的 HTTP 客户端用的）。
- 当前版本**未订阅 SDK 的掉线回调**，因此网线被拔时界面状态不会自己变红。
- 现场判据：累计收帧不再增长 + 采集步骤连续等图超时。处置：停止采流 → 断开 → 重新连接。
- 需要"靠心跳推断掉线"的能力是网络相机那一侧在用，不要把这个现象当缺陷报。

## 七、GigE 与 USB3 的现场差别

- **两类一起枚举**（一次枚举同时覆盖 GigE 与 USB3），配置面上只有一种填法：**序列号**。
- **没有 IP 配置项**：GigE 相机能不能被枚举到，取决于相机与网卡是否同网段、链路是否建立——
  表现是"本次枚举 0 台"，而不是"连不上某个 IP"。
- **不改包长与心跳**：GigE Vision 的 `PacketSize` / `GevHeartbeatTimeout` 沿用相机自身当前的值（MVS 里改过就会带过来）。
  若出现"取图线程一直超时、但 MVS 客户端能出图"，按网络抖动 / 包长超链路能力 / 网卡卸载与校验和设置 /
  交换机端口镜像 / 多个上位机软件抢同一台相机逐条排查。
- **独占访问**：同一台相机同时只能被一个程序打开。MVS 调试客户端、采集卡软件与本软件抢一台时，
  后打开的那个在"打开海康设备失败（错误码 0x…）"上失败。

## 八、多台同时取图

每台相机一条独立取图线程与一条独立队列，互不共享缓冲，因此：

- 算力与带宽是**叠加**的；多相机大节拍时优先确认流程侧的消化能力，而不是加队列。
- **序列号必须逐字互不相同**：重复时按序列号取图只命中先注册的那一台，
  宿主会记一条告警，现场表现是"A 相机的图跑到 B 流程里"，而界面状态看起来一切正常。
- 改名不算——只有序列号参与寻址。
