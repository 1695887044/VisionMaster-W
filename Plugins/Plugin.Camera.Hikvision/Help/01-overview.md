# 海康相机

> 分类：相机驱动 ｜ 来源：插件 Plugin.Camera.Hikvision

海康威视 **GigE / USB3 相机的真机驱动**：自己打开 SDK 设备句柄、启动采流，并在自己的取图线程上把 SDK 帧解成原始像素，
送进这台相机的**帧队列**。它不是流程里的算子——它出现在「系统 → 相机设置」的驱动列表里，
产出的图由流程中的「图像采集 · 相机采集」步骤按节奏消费（每帧只会被取到一次）。

## 为什么需要它 / 原理

**它在驱动族里的位置**：与「网络相机（虚拟）」不同，这里是真机驱动——有 SDK 句柄、有采流命令、有掉线语义。
但两者共用同一副骨架（`CameraDeviceBase`）：环形帧队列 + 溢出计数、连接状态机、心跳看门狗、取图口（消费 / 只读）都在基类里，
本驱动只写"海康与别家不一样的地方"：枚举设备、按序列号对上那一台、开设备、起停采流、下发曝光增益、把 SDK 帧解成像素。

**SDK 是运行时探测的，编译期不引用海康 DLL**。绑定面收敛在一个反射包装器里（`MvsRuntime`），原因是
`MvCameraControl.Net.dll` 的版本必须与相机固件、与本机装的 MVS 客户端对齐，仓库里不代分发。带来的效果：
**没装 MVS 的机器上本驱动照样随插件加载**，直到点「连接」时才给出"去哪装、放哪"的中文指引，其余（状态机 / 队列 / 计数）照常可用。
探测顺序：程序目录 → 程序目录下的 `Modules` → 逐级向上最多六层的 `Modules` → 环境变量 `MVCAM_SDK_PATH` 指向的
`Development\DotNet\`。宿主若已先把它装进进程，就直接复用那一份。

**取图线程**：设备开成功后拉起一条后台线程（每台相机一条，线程名 `HikGrab-{序列号}`），循环做四件事——
`MV_CC_GetImageBuffer_NET`（每轮最多等 100 ms）→ 按像素格式转换成 `Mono8` 或 `RGB8_Packed` → 拷成独立 `byte[]` 入队 →
`MV_CC_FreeImageBuffer_NET` 立刻归还 SDK 缓冲。**SDK 收图侧绝不阻塞**是这里第一条硬约束，
靠"独立取图线程 + 拷贝入队"满足；单帧解算失败只丢那一帧并记一条告警，绝不带垮线程。

**开设备即强制连续采图**（GenICam 节点 `TriggerMode` 写 0），并在打开成功后立刻下发一次方案里存的曝光与增益
（这一步失败只记日志、不阻断连接，可随后在相机设置里重设）。

## 在「系统 → 相机设置」里怎么配

| 项 | 必填 | 说明 |
| --- | --- | --- |
| 驱动类型 | 是 | 选「海康相机」。列表来自宿主扫描 `Modules\` 里实现 `ICameraDevice` 且带 `[Display]` 的类型——DLL 不在 `Modules\` 里就选不到 |
| 序列号 | **是** | **唯一的寻址键**。打开时枚举 GigE + USB3 两类设备，按序列号（忽略首尾空格、忽略大小写）挑中那一台。填 MVS 客户端设备属性里的 `SerialNumber`。没填直接报"尚未配置相机序列号" |
| 显示名 | 否 | 只给人看，**不参与任何寻址**；改它不会断客户端、不会断采集步骤 |
| 备注 | 否 | 界面展示 |
| 自动连接 | 否 | 勾选后宿主在方案加载/启动时对本机执行"连接 + 开始采流"；一台失败不影响其它相机 |
| 采集参数 | 否 | 曝光 / 增益 / 取图超时 / 队列容量 / 心跳超时，见下面「关键参数」 |

**采集步骤那边怎么对上**：在「图像采集」的「相机采集」页下拉里选同一台（下拉候选由宿主按序列号下发快照，
`当前状态：` 那行会当场说清"现在能不能跑"）。方案里存的是**序列号**，不是显示名，也不是内部 Id。

## 产出什么（这台相机的帧队列）

| 项 | 说明 |
| --- | --- |
| 帧（`CameraFrame`） | `PixelData`（行优先、**无行填充**；灰度 1 字节/像素，彩色 3 字节/像素交错）、`Width` / `Height` / `Channels`、`FrameId`（本机从 1 自增）、`Timestamp`（收帧时刻）、`SourceName`（固定为 `hikvision://{序列号}`） |
| 连接状态 | `Closed` / `Connecting` / `Online`（已连接未采流）/ `Streaming`（采流中），外加一句话状态说明 |
| 累计收帧 | 进过队列的帧数（含后来被溢出丢掉的）——采集步骤的 `ReceivedCount` 输出就是它 |
| 待消费帧数 | 队列里当前还有几帧等着被取 |
| 溢出丢帧 | 队列满丢最旧的累计数：**每丢一帧就是一个未被检测的工件**，界面单独红块告警 |
| 其它丢弃 | 掉线/停止采流/帧不自洽被拦下的累计数，与溢出**分开计数**（原因与处置完全不同） |

## 关键参数

> 完整参数与取值范围以流程中该步骤的「模块参数」界面为准，这里只解释含义。
> （相机驱动的这几项在「系统 → 相机设置」里维护，随方案落盘；采集步骤的「取图超时」端口可临时覆盖 `FrameTimeoutMs`。）

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| 曝光 `ExposureTimeUs` | 10000 | **单位是微秒（μs）**，不是毫秒：填 10000 = 10 ms。写进 GenICam 节点 `ExposureTime`（float）；报"设置曝光失败（ExposureTime，错误码 0x…）"就是这台相机拒绝该值（超范围 / 该机型节点名不同） |
| 增益 `Gain` | 0 | 写进节点 `Gain`（float）。**单位由相机自行解释**：多数海康机型是 dB，也有机型是原始码值——与 MVS 客户端里看到的数值对不上时，先确认客户端那一侧显示的物理量 |
| 触发模式 `TriggerMode` | 软触发 | **对本驱动无效**：打开设备时驱动统一写 `TriggerMode = 0`（连续采图、免触发），节拍由流程的消费节奏决定。要硬触发（光电 / 编码器 / PLC 的上升沿、下降沿）见「常见问题」 |
| 取图超时 `FrameTimeoutMs` | 3000 | 消费端"等一帧最多等多久"。**必须是有限值**：无超时的等图会让流程线程永久卡死、现场只能杀进程。填小于 1 的值会被归一到 3000 |
| 队列容量 `BufferCapacity` | 8 | 环形队列容量，超出丢最旧并计入溢出。太小易丢帧；太大会掩盖"产能不匹配"这个真问题、并把延迟越积越大。合法区间 1~1024（越界自动夹取） |
| 心跳超时 `HeartbeatTimeoutMs` | 3000 | **本驱动不启用心跳**（真机不需要靠"多久没消息"推断），这一项对海康只是配置值；网络相机那侧才是真生效 |

## GigE 与 USB3 的现场差别

- **两类一起枚举**：打开时一次枚举 `MV_GIGE_DEVICE | MV_USB_DEVICE`，序列号分别取自 GigE 设备信息与 USB3 设备信息，
  所以同一个驱动既能接网口相机也能接 USB3 相机，**配置面上只有一种填法：序列号**。
- **没有 IP 配置项**：本驱动不按 IP 连设备（这与"填 IP 的第三方 SDK 风格"不同）。GigE 相机能不能被枚举到，
  取决于相机与网卡在不在同一网段、链路是否建立——**表现是"本次枚举 0 台"**，而不是"连不上某个 IP"。
- **不修改包长与心跳**：GigE Vision 的 `PacketSize` / `GevHeartbeatTimeout` 由相机自身当前的值决定（MVS 里改过就会带过来）。
  现场若出现"取图线程一直超时、但 MVS 客户端能出图"，先按下面「常见问题」里的 GigE 老问题清单排查（网络抖动、包长超过链路能力、
  网卡驱动卸载/校验和设置、交换机端口镜像、多个上位机软件抢同一台相机）。
- **独占访问**：同一台相机同时只能被一个程序打开。MVS 调试客户端、采集卡软件、本软件三者抢一台相机时，
  后打开的那个会在"打开海康设备失败（错误码 0x…）"上失败。
- **多台同时取图**：每台一条独立取图线程与一条独立队列，互不共享缓冲；因此多相机的算力/带宽是**叠加**的，
  但帧不广播——一帧只会被消费它的那个采集步骤取走。多台相机务必保证**序列号互不相同**
  （重复时按序列号取图只会命中先注册的那一台，宿主会记一条告警，现场表现是"A 相机的图跑到 B 流程里"）。

## 像素格式与通道数

- 帧只按**目标格式**交给下游：单通道 `Mono8`（1 字节/像素）或三通道彩色（3 字节/像素交错），
  转换由 SDK 的 `MV_CC_ConvertPixelType_NET` 完成，Bayer / YUV / RGB / BGR 系都由它消化。
- 分类只看格式名（GenICam 命名约定）：名字里含 `Mono` → 单通道；含 `Bayer` / `RGB` / `BGR` / `YUV` / `YCbCr` → 三通道；
  **认不出的一律丢帧**并记一条"暂不支持的像素格式 X，该帧被丢弃"——宁可丢帧，也不给下游一张错位的图。
  所以换了新机型、或在相机上开了少见的 10/12bit packed 之外的自定义格式，先去看日志里有没有这句。
- 高位深（`Mono10` / `Mono12` / `BayerXX`）入队前已**降到 8 bit**，因此 HALCON 侧拿到的是 `byte` 图；
  若测量需要 8 bit 之外的灰阶，得在相机侧就用 8 bit 输出并接受降噪，或走带高位深的其它链路（本驱动不提供）。
- 彩色图进来后由消费者（「图像采集」）按仓库统一约定建图：**灰度 1 通道；彩色 3 字节/像素交错，HALCON 通道 1/2/3 = R/G/B**。
  这条约定全仓只有一个转换核心，**红蓝互换**几乎总是"有人绕过它新写了一份"的表现。

## 口径与失败策略

- **打开失败 = 明确失败**，状态干净地回到 `Closed`，一句话原因写进状态说明（形如"打开失败：…"）。
  四类原因分别是：没填序列号 / 没装 MVS 运行时 / 枚举不到那一台（会带上"本次枚举 N 台"） / 创建设备或打开设备返回错误码。
- **启动采流失败**（`MV_CC_StartGrabbing_NET` 返回非 0）：状态退回 `Online` 并写明"启动采流失败（错误码 0x…）"，
  此时相机是在线的但不出图——与"掉线"是两件事，处置也不同。
- **单帧失败不影响流程判定**：解算异常、格式转换失败、格式不认识 → 丢该帧 + 一条告警。真不出图的表现形式是消费端**等图超时**。
- **等图超时怎么读**：采集步骤报"等待相机…出图超时（N ms）；相机状态：…，待消费 N 帧，累计收帧 N，溢出丢帧 N"。
  四个数字就是分诊依据：累计收帧不涨 = 相机没出图（触发/采流/掉线）；累计涨但待消费一直满 = 流程太慢；溢出涨 = 产能不匹配（**要当质量事故查**）。
- **不做"重试等下一帧"**：这一帧没等到就是没等到，继续等只会让流程越来越滞后于生产；产线上"这一件没检出"必须被明确记录。
- **掉线**：真机一侧不启心跳看门狗，且本驱动**未订阅 SDK 的掉线回调**，因此网线被拔时界面状态不会自己变红。
  现场判据是"累计收帧不再增长 + 采集步骤等图超时"；确认后在相机设置里断开再重连（或先停止采流再开始采流）。
- **参数落盘口径**：应用参数成功后基类会把归一化后的值写回相机配置（界面显示与方案里存的是同一份）；
  曝光/增益下发失败会把原因写进状态说明并记日志，不会静默生效一半。

## 典型用法 / 接线

```
① 系统 → 相机设置：驱动=海康相机，序列号=T-0512xxxxxx，勾自动连接 → 连接 → 开始采流
② 流程里的采集步骤：图像采集.Mode = 相机采集，相机下拉选同一台（CameraSerial 落盘为序列号）

海康相机.帧队列 ──▶ 图像采集.相机采集（取图超时端口 0 = 用相机配置）
图像采集.Image ─────▶ 下游算子.SrcImage
图像采集.FrameId / ReceivedCount ──▶ 数据记录 / 结果上报（帧溯源对账）
图像采集.SourceSerial ──▶ 标定 / 坐标变换.SourceSerial（换相机后旧标定自证失效）
```

## 常见问题

**Q：「系统 → 相机设置」的驱动下拉里没有「海康相机」？**
① 看仓库根 `Modules\` 里有没有 `Plugin.Camera.Hikvision.dll`——插件工程必须在 `Plugins\` 下构建，构建约定才会把 DLL 投递到 `Modules\`；
② 有 DLL 但时间戳是旧的 = 改了源码没重建插件工程（只重建宿主跑的仍是旧 DLL）；
③ 看日志里宿主扫描该 DLL 是否失败（缺依赖会整份 DLL 被判"加载失败"）。
**注意不要把 `Core.Interfaces.dll`、`Core.Controls.dll` 一类的公共契约程序集拷进 `Modules\`**——会出现两份静态状态。

**Q：状态说"打开失败：…未找到海康 MVS 运行时（MvCameraControl.Net.dll）…"？**
这是设计好的优雅降级。按那句指引做：装海康 MVS 客户端，把安装目录 `Development\DotNet\MvCameraControl.Net.dll`
复制到本程序的 `Modules\` 目录后重启软件。备选：设置环境变量 `MVCAM_SDK_PATH` 指向 MVS 安装根目录（驱动会去它的
`Development\DotNet\` 找）。括号里的"探测记录"会列出它实际试过哪些路径、各自失败原因，照那条查最快。

**Q：报错里有"MVS SDK 缺少方法 MV_CC_XXX_NET（N 参数）—— MvCameraControl.Net.dll 版本不匹配"？**
放进 `Modules\` 的那份包装器与本驱动绑定的成员对不上（MVS 版本太老或太新）。用与相机固件配套的那个 MVS 版本的 DLL；
不要混拷两份（进程里只认先加载的那一份）。

**Q："未找到序列号为「XXX」的海康相机（本次枚举 0 台）"和"（本次枚举 3 台）"怎么分诊？**
- **0 台** = 根本没枚举到：GigE 网段不通（相机与本机网卡不同网段 / 网线 / 交换机 / 供电）、相机被别的程序独占、
  MVS 运行库不全（只有托管 DLL、缺原生运行库）。这时先在 MVS 客户端里确认能不能看到这台相机——**MVS 看不到，本驱动必然看不到**。
- **N 台（N>0）** = 枚举通了但序列号对不上：多打/少打一位、抄成了用户名而非 `SerialNumber`、方案是从另一台设备拷来的。
  序列号比较会忽略首尾空格与大小写，**其余一位都不能差**。

**Q：打开了设备但一直取不到图（采集步骤等图超时）？**
先分三层：① 相机设置里状态是不是 `Streaming`（`Online` = 已连接但没开始采流，点「开始采流」）；
② 日志里有没有"暂不支持的像素格式…"或"像素格式转换失败…"（有 = 帧到了但被丢，问题在相机输出的格式）；
③ 相机侧是不是设了外部触发（硬触发没来信号就永远没帧）。**注意本驱动开设备时把 `TriggerMode` 写成连续采图**，
所以"我在软件里选了软/硬触发"这一项对海康不生效，触发要按相机的实际情况处理。

**Q：相机不触发时能不能改成硬触发（光电 / 编码器 / PLC）？**
本版本**不通过相机设置下发触发**（`CameraSettings.TriggerMode` 只是配置项，驱动打开时强制连续采图）。
硬触发场合的现场做法是：在相机/MVS 侧把触发配好并接线，让相机只在收到信号时出图；
帧照样进队列，采集步骤按自己的节奏消费——效果上就是"来一件拍一件"，只是触发参数不在本软件里维护。

**Q：改了曝光，图上亮度没变？**
① 单位是**微秒**（填 10 只等于 10 μs，几乎看不见变化；10 ms 要填 10000）；
② 看日志有没有"打开后应用参数失败"或"设置曝光失败（ExposureTime，错误码 0x…）"——有就是相机拒绝了该值；
③ 相机开了自动曝光（AE）时手动值会被它盖掉，先在相机侧关掉自动曝光；
④ 参数是在**连接时/点应用时**下发的，改完要在相机设置里确认生效，而不是等流程跑起来。

**Q：多相机一起跑，出现"A 相机的图被 B 流程检测了"？**
两台相机配了**相同序列号**（重复时按序列号取图只命中先注册的那一台，宿主日志会告警）。
序列号必须逐字唯一；改名不算，只有序列号参与寻址。另外每帧只被消费一次：多个采集步骤选同一台相机会**分抢**帧，
需要同一帧被多处用就把图往下游传，而不是并排接两个采集步骤。

**Q：界面显示"采流中"，但相机其实已经断了？**
本驱动不启心跳看门狗（真机靠 SDK 回调，而当前版本未订阅掉线回调），所以状态不会自动变。
判据看计数：**累计收帧不再增长** + 采集步骤连续等图超时 = 设备已经没了。处置：停止采流 → 断开 → 重新连接。
（需要"靠心跳推断掉线"的能力是网络相机那一侧在用。）
