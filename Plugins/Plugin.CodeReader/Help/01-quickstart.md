# 码读取 · 快速上手

> 分类：图像处理 ｜ 来源：插件 Plugin.CodeReader

## 它是什么、不管什么

把相机拍到的一维条码 / 二维码**翻译成文字**：产线追溯（一物一码、防错比对、MES 上报）的取数节点。
一帧跑完给出三样东西：`Codes`（这一帧里**所有**解出的码文本，数组）、`Count`（码个数）、`Text`（所有码文本的逗号分隔串）。

凡是"要知道码上写的是什么"的场合都用它；但它**只输出文本**：
不输出码的位置、不输出逐码的码制、不输出质量等级或置信度，也**不做定位**（见下）。
读码步骤已标记为**可并行**（纯视觉计算、不碰设备），在多分支流程里可与其它并行步骤同时跑。

多数视觉算子回答"有没有、在哪、多大"，而**追溯系统要的是那串字符**：工件序列号、批次、料号。
和「OCR」的分工也要分清：OCR 认的是**人眼读得懂的文字**（可以人工核图），码读取认的是**编码规则**——
二维码的内容人眼根本读不出来，所以现场唯一能自己验的独立真值是**校验位**（如 EAN 的规则验算），
其余都要靠"拿已知内容的码去对"。

## 原理：建模型 → 查找解码 → 释放

一维和二维走的是**两套引擎**，但骨架都是这三步：

```
① 建模型句柄   create_bar_code_model        / create_data_code_2d_model
② 查找并解码   find_bar_code                / find_data_code_2d
③ 释放句柄     clear_bar_code_model         / clear_data_code_2d_model
```

模型句柄是非托管内存，插件重写了 `Dispose` 把两个引擎的句柄都清掉（反复开关配置窗口才不会稳定泄漏）。
两族必须分开，是因为**结果寻址方式完全不同**：一维只回一个字符串元组（要按整数下标查），
二维回"候选句柄 + 解码字符串"两组（要查细节得把句柄传回去）。

| 维度 | 一维条码 | 二维码 |
| --- | --- | --- |
| 码制在哪给 | 查找时的**入参**，每次现给 | **建模型时定死**（一个模型只能一种码制） |
| 切码制 | 不用重建模型 | 必须清掉再重建（只在切换那一刻发生） |
| 本插件可调参数 | **只有超时** | 极性 + 超时 |
| 极性参数 | **没有这个东西**（实测一维模型不接受，会报 `#3286`） | 有：暗码亮底 / 亮码暗底 / 两种都试 |

三条实现口径直接决定了界面为什么长这样：

- **不做定位**：本节点只吃一张上级裁好的小图，没有"识别区"参数、没有框选，
  配置界面右侧是**只读**显示（刻意不给画图控件，免得让人以为能框选）。
  上级换定位方式（ROI / 模板匹配 / 预处理）都不用改读码节点。
- **参数按码制家族分派**：一维与二维的可调参数不重合，所以「极性」那一块**只在选了二维码时出现**——
  把用不上的参数摆出来，只会让现场以为动它能解决问题。
- **试算与正式运行共用同一条读码路径**：配置界面点「试算一下」看到的结果，就是流程跑起来的结果。
  参数也每次查找前重设一遍，杜绝"参数动了但结果不变"。

## 第一次配读码（五步）

1. **先确定码制**：拿一张实际工件图，对照「码制清单」页对号；分不清就把码制逐一在配置界面点「试算一下」——
   试算与正式运行是同一条读码路径，看到的就是跑起来的。
2. **上游裁图并留余量**：用「ROI（创建ROI）」的 `Crop_ROI名` 输出，**裁剪框 = 码的外接矩形向外扩 5~10 像素**（经验值）。
   传入图带区域域（`reduce_domain` 的产物）时搜索范围缩到该域，**码没完全落在域内就可能找不到**
   ——贴边裁是"图上有码却 `Count = 0`"的第一号原因。
3. **连图**：配置窗口左栏「图像输入」卡片里链接上游（或画布上把上级输出连到 `Image` 端口）。
4. **设超时**：默认 `500` ms。它是"没找到时的止损线"，不是"提高命中率"的旋钮——图里真有好码时，几十毫秒就出来了。
5. **（仅二维码）定极性**：默认「自动（两种都试）」。金属 DPM 常是亮码暗底，两种都试更稳；
   确定极性后明确指定能省一截节拍。

## 典型用法 / 接线

码位置固定（最常见）：

```
图像采集.OutputImage ──▶ 创建ROI.Crop_码区 ──▶ 码读取.Image
码读取.Text ──▶ CSV记录 / 结果上报        （标量，直接进字段）
码读取.Count ──▶ 条件步骤                （判有没有码）
```

码脏、对比度低（先洗图再读）：

```
图像采集.OutputImage ──▶ 图像预处理.Image ──▶ 创建ROI.Crop_码区 ──▶ 码读取.Image
```

一帧要读两种码制（一帧只认一种，所以并联两个步骤）：

```
创建ROI.Crop_标签区 ──▶ 码读取_一维.Image ──▶ 码读取_一维.Text ─┐
创建ROI.Crop_本体区 ──▶ 码读取_二维.Image ──▶ 码读取_二维.Text ─┴─▶ CSV记录
```

**位置原则**：码读取**永远排在"定位 / 裁剪"之后**，它自己不找码在哪。

## 四条口径，先记住再用

- **没读到码 = 正常工况，不算失败**：`Success = true` + `Count = 0` + 一条 Info 留痕
  （日志里带上**当前码制**与超时，并提示先确认"码制是否选对""上级图是否把码完整包住"）。
  理由：工件翻面、未打码、码被遮挡在现场都是正常流，用失败会把良率统计搞脏。**要不要当 NG，请用 `Count` 在下游判**。
- **只有程序级异常才失败**：上游没有图像、码制名不在支持表里、模型建不起来、查找阶段报错。
- **文本原样透传**：不解 GS1 应用标识符、不做编码转换、不修剪内容。乱码与字段拆解都在下游或打码侧解决。
- **多码顺序由引擎决定，不保证稳定**：不要拿"第几个"当业务含义，要稳定归属就一码一路。

界面与端口在「界面与端口」页，码制怎么选在「码制清单」页，读不出来照「排错与调参」页的链往下走。
