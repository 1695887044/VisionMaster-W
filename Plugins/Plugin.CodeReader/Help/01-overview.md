# 码读取

> 分类：图像处理 ｜ 来源：插件 Plugin.CodeReader

把相机拍到的一维条码 / 二维码**翻译成文字**：产线追溯（一物一码、防错比对、MES 上报）的取数节点。
一帧跑完给出三样东西：`Codes`（这一帧里**所有**解出的码文本，数组）、`Count`（码个数）、`Text`（所有码文本的逗号分隔串）。
凡是"要知道码上写的是什么"的场合都用它；但它**只输出文本**，不输出码的位置、逐码的码制、质量等级/置信度。
读码步骤已标记为**可并行**（纯视觉计算，不碰设备），在多分支流程里可与其它并行步骤同时跑。

## 为什么需要它

多数视觉算子回答"有没有、在哪、多大"，而**追溯系统要的是那串字符**：工件序列号、批次、料号。
它和「OCR」的分工也要分清：OCR 认的是**人眼读得懂的文字**（可以人工核图），码读取认的是**编码规则**——
二维码的内容人眼根本读不出来，所以现场唯一能自己验的独立真值是**校验位**（如 EAN 的规则验算），其余都要靠"拿已知内容的码去对"。

## 原理：建模型 → 查找解码 → 释放

一维和二维走的是**两套 HALCON 引擎**，但骨架都是这三步：

```
① 建模型句柄   create_bar_code_model        / create_data_code_2d_model
② 查找并解码   find_bar_code                / find_data_code_2d
③ 释放句柄     clear_bar_code_model         / clear_data_code_2d_model
```

模型句柄是 HALCON 侧的**非托管内存**，本插件重写了 `Dispose` 把两个引擎的句柄都清掉（反复开关配置窗口才不会稳定泄漏）。
两族必须分开，是因为**结果寻址方式完全不同**：一维只回一个字符串元组（要按整数下标查），二维回"候选句柄 + 解码字符串"两组（要查细节得把句柄传回去）。

| 维度 | 一维条码 | 二维码 |
| --- | --- | --- |
| 码制在哪给 | `find_bar_code` 的**入参**，每次查找现给 | **建模型时定死**（一个模型只能一种码制） |
| 切码制 | 不用重建模型 | 必须清掉再重建（只在切换那一刻发生） |
| 本插件可调参数 | **只有超时** | 极性 + 超时 |
| 极性参数 | **没有这个东西**（实测一维模型不接受，会报 `#3286`） | 有：`any` / `dark_on_light` / `light_on_dark` |

三条实现口径，直接决定了界面为什么长这样：

- **不做定位**：本节点只吃一张上级裁好的小图，没有"识别区"参数、没有框选，配置界面右侧是**只读**显示（刻意不给画图控件，免得让人以为能框选）。上级换了定位方式（ROI / 模板匹配 / 预处理）都不用改读码节点。
- **参数按码制家族分派**：一维与二维的可调参数不重合，所以「极性」那一块**只在选了二维码时出现**——把用不上的参数摆出来，只会让现场以为动它能解决问题。
- **试算与正式运行共用同一条读码路径**：配置界面点「试算一下」看到的结果，就是流程跑起来的结果。参数也每次查找前重设一遍，杜绝"参数动了但结果不变"。

## 输入端口

| 端口 | 必填 | 说明 |
| --- | --- | --- |
| `Image` | 编译期不强制，**运行期必须有图** | `HImage`：待读码的图像，应由上级**定位后裁好**并**把码完整包住**；建议是单通道灰度图（彩色请先在上游转灰度）。空图/未初始化 → 本步骤失败，原因写"上游没有图像" |

配置窗口左栏的「图像输入」卡片可以直接链接上游端口或变量，不用回画布拖线；绑定后点「执行」，上游图会自动显示到右侧预览。

## 输出端口

| 端口 | 说明 |
| --- | --- |
| `Codes` | `string[]`：这一帧里所有**成功解出内容**的码文本（一帧可能有多个，实测 Code 39 样张就是两个） |
| `Count` | `int`：码的个数。**下游判"有没有码"用它**（0 = 本帧没有码，属正常工况） |
| `Text` | `string`：所有码文本的逗号分隔形式，给按标量工作的既有下游（比较 / 存变量 / CSV记录 / 结果上报）用 |
| `Success` / `ErrorMessage` | 基类隐式端口：本步骤执行状态与失败原因 |

**明确不输出**：码的位置（行/列）、逐码的码制、质量等级/置信度。别按这些去规划下游。

## 关键参数

> 完整参数与取值范围以流程中该步骤的「模块参数」界面为准，这里只解释含义。

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| 码制 | `Data Matrix ECC 200` | 一帧只按**一种**码制找。界面显示中文/通用名，**流程里存的是 HALCON 原始名**（稳定身份，改中文标签不会让存量图纸失效）。表里没有的名字会报明确错误，**不静默退回默认码制**（静默退回的表现只是"读不到码"，无从排查） |
| 搜索超时(ms) | `500` | `0` = 不限。给默认值是因为**图里没有码时 HALCON 会在候选区域上反复尝试**，没有超时保护会拖住整条流程。调大只影响"找不到时肯花多久试" |
| 极性 | 自动（两种都试） | **仅二维码有效**。默认让 HALCON 暗码亮底、亮码暗底都试——激光 DPM 打码在金属上常是亮码暗底或低对比。已知极性时明确指定可提速。流程里存的是 `any` / `dark_on_light` / `light_on_dark` |

## 口径与失败策略

- **没读到码 = 正常工况，不算失败**：`Success = true` + `Count = 0` + 一条 Info 留痕（日志里带上**当前码制**与超时，并提示先确认"码制是否选对""上级图是否把码完整包住"）。
  理由：工件翻面、未打码、码被遮挡在现场都是正常流，用 Fail 会把良率统计搞脏。**要不要当 NG，请用 `Count` 在下游判**。
- **只有程序级异常才 Fail**：上游没有图像、码制名不在支持表里、模型建不起来、HALCON 查找阶段报错。
- **多码同框**：一帧里所有解出的码都进 `Codes`（只收"解出内容"的，空文本的候选被丢掉）。**多码顺序由 HALCON 决定，不保证稳定**，不要拿"第几个"当业务含义。
- **候选数与解出数不一致时补一条 Warn**：形如"二维候选 N 个（句柄 M 个），其中成功解出 K 个"。它解释了"为什么图上有码却 `Count = 0`"——找到了但没解出内容（码脏 / 对比度低），是排障的关键线索。
- **文本原样透传**：不解 GS1 应用标识符、不做编码转换、不修剪内容。乱码与字段拆解都在下游或打码侧解决（见第二页）。
- **上级裁剪必须留余量**：传入图带 `reduce_domain` 时搜索范围缩到该域，但**码没完全落在域内时可能找不到**（极少数情况下还会在域外找到）。别贴边裁。

## 典型用法 / 接线

码位置固定（最常见）：

```
图像采集.OutputImage ──▶ 创建ROI.Crop_码区 ──▶ 码读取.Image
码读取.Text ──▶ CSV记录 / 结果上报        （标量，直接进字段）
码读取.Count ──▶ 条件步骤                （判有没有码）
```

码脏、对比度低（先洗图再读）：

```
图像采集.OutputImage ──▶ 图像预处理.Image ──▶ 创建ROI.Crop_码区 ──▶ 码读取.Image
```

一帧要读两种码制（一帧只认一种，所以并联两个步骤）：

```
创建ROI.Crop_标签区 ──▶ 码读取_一维.Image ──▶ 码读取_一维.Text ─┐
创建ROI.Crop_本体区 ──▶ 码读取_二维.Image ──▶ 码读取_二维.Text ─┴─▶ CSV记录
```

**位置原则**：码读取**永远排在"定位 / 裁剪"之后**，它自己不找码在哪。

## 常见问题

**Q：为什么配置界面里没有框选、也没有识别区？**
本节点按设计**不做定位**：只吃上级裁好的小图。这样上级换定位方式（ROI / 模板匹配 / 预处理）都不用改读码节点。
要框码的位置就去上游加「ROI（创建ROI）」，把它的 `Crop_ROI名` 连过来。

**Q：图里没有码会报错吗？**
不会。`Success = true`、`Count = 0`，只写一条 Info。判"有没有码"请用 `Count`，别用步骤的执行状态——否则工件翻面都会被记成设备故障。

**Q：一维条码为什么没有"极性"参数？**
实测一维模型不接受极性参数（HALCON 报 `#3286 Wrong generic parameter name`），一维读码本身对极性鲁棒，压根没这个旋钮。
所以界面选了二维码才显示「二维码参数」那一块。亮码暗底的**标签纸条码**要靠上游「图像预处理」的**反色**解决。

**Q：能读出码在哪里、码质量多少分吗？**
不能。只有 `Codes` / `Count` / `Text` 三个输出，没有位置、逐码码制、质量等级。
要定位就得让上游给（ROI / 模板匹配负责"在哪"），要判码质量得靠专用读码器或另做图像判据。

**Q：`Codes` 和 `Text` 该用哪个？**
下游是**标量**口径（比较、存变量、CSV记录、结果上报）就用 `Text`——画布上数组端口只能整体连，`Codes[0]` 这种下标写法未必给得出。
下游要逐个处理多个码才取 `Codes`（配合 `Count` 判空）。

**Q：默认码制为什么是 Data Matrix？**
工业追溯里 Data Matrix 最常见（激光 DPM 打码基本都是它），所以拿它当默认值。
现场读的是标签纸条码时**必须改成对应的一维码制**，否则表现就是"图上明明有条码却 `Count = 0`"。

**Q：选了"一维·自动识别码制"更省心，为什么不推荐？**
`auto` 会让 HALCON 在图里逐个码制试，**节拍明显更慢**，且码制混杂时可能给出意外的匹配。
产线上码制是固定的，选具体码制快得多。

**Q：改了码制/超时好像没生效？**
先确认改的是**运行实例**还是配置界面（改完要保存并重新编译流程），再确认 `Modules\` 下加载的是最新插件 DLL。
参数在每次查找前都会重设一遍、二维码制没变时模型句柄才复用，所以"参数动了结果不变"这条链在本插件里已经堵掉了。
