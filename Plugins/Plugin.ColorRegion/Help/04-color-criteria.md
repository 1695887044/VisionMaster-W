# 颜色区域与判色阈值口径

> 分类：图像处理 ｜ 来源：插件 Plugin.ColorRegion

这一页讲**口径**：颜色区域怎么生成、通道与位深怎么算、判得到底是哪个颜色空间、13 个阈值各管到哪、
`MinShare` 该定多少、以及它和「颜色序列检查」的分工。基础用法见《区域颜色检查》。

## 颜色区域怎么生成（采样区 → 投票点集）

采样区由三件事决定：`RoiShape`（形状）+ `RoiParams`（5 槽几何参数）+ `SamplePoints`（点数上限）。
生成顺序是**先做区域掩膜、再抽点**：

1. `RoiShape` 与 `RoiParams` 还原成 HALCON 区域（矩形走 `rectangle2` 语义，圆/椭圆走对应算子）；
2. 区域与图像**求交**——超出图像的部分被裁掉且不报错（框松一点是常事），但**完全没交集**会报错停下；
3. 区域内的像素点展开成点集，超过 `SamplePoints` 时按**固定步长均匀抽稀**；
4. 一次取回整批点的 R/G/B，逐点分类成颜色词，累计票数；
5. 票数降序取主色；**打平时按词表顺序定序**（黑 白 灰 棕 红 玫红 橙 黄 绿 蓝 紫），
   保证同一块区域每次跑出来的主色都一样。

因为第 1 步用**区域当掩膜**，落在区域外的点不参与投票——这是"方框框圆灯时四个角背景不被采到"的机理。
形状与大小的实际影响：

| 目标 | 画什么 | 为什么 |
| --- | --- | --- |
| 圆形指示灯 | **新建圆形** | 方框的四个角是背景；不作掩膜时背景占比高，会"很有把握地"报出背景色 |
| 按钮/色标方块 | 新建矩形 | 贴合即可，别把相邻颜色圈进来 |
| 椭圆形/斜置色块 | 新建椭圆 | 半径 1/2 与旋转角由拖拽句柄决定 |
| 环形/不规则带 | 矩形 + 收紧 | 采样用区域当掩膜，区域外的点不投票 |

- **框太大**：主色占比被稀释（报"颜色不纯"）。
- **框太小**：采样点太少，容易被一个脏点/高光翻盘。

## 通道与位深口径

- **必须三通道彩色图**：图像通道数小于 3 直接报错停下（灰度图判色没有意义，不做"复制成三通道"这种猜测）。
- **12/16 位高位深自动压回 8 位**：判据的明度阈值（黑 80 / 白 195 / 棕 175）按 8 位标定，
  高位深图不压回去的话"黑"永远判不出、"白"满天飞、灰/棕大面积误判。
  压法是**按实测最大通道值等比缩放**——色相与饱和度是比值量，等比缩放不动它们，所以**颜色词的答案不变**；
  受影响的是 `Rgb`（给的是**归一后**的值）。发生过归一就在日志留一条说明，不是静默改数。
- `Share` 是 `0~1` 的小数，不是百分数；`Rgb` 是 8 位口径（0~255）；坐标全是图像像素系 `(Row, Col)`；
  角度存盘是**弧度**（界面摘要显示成度）。

## 判得到底是哪个颜色空间：固定 HSV 式，没有开关

**界面上没有"RGB / HSV / Lab"下拉，也没有 ΔE / 颜色距离 / 容差半径。**
判定走的是"把每个像素归成一个**颜色词**，然后投票"，这是刻意的：颜色词是离散量，
产线的语义（"红灯亮着"）本来就是离散的；用连续距离度量就得给每个灯配一个容差半径，光照一变半径就失效。

三个量都从 R/G/B 现场推：

| 量 | 算法 | 用途 |
| --- | --- | --- |
| 明度 `v` | `max(R, G, B)` | 判黑（低于 80）、判白（高于 195）、棕的明度上限（低于 175） |
| 饱和度 `s` | `(max − min) / max`（`max` 不大于 0 时记 0） | 无彩/有彩分界（低于 0.45 走黑白灰棕），白的附加条件（低于 0.15） |
| 色相 `h` | 标准 HSV 色相角，0~360 度 | 有彩区按角度分色系 |

```
s 小于 ColorlessSaturation(0.45)  →  无彩区
    v 小于 BlackValue(80)                                 → 黑
    s 小于 WhiteSaturation(0.15) 且 v 大于 WhiteValue(195)  → 白
    (R-G) 不小于 BrownWarmth(12) 且 (R-B) 不小于 12 且 v 小于 BrownValue(175) → 棕
    其余                                                  → 灰
s 不小于 0.45  →  有彩区，按色相角 h：
    [330,350) → 玫红      不小于350 或 小于20 → 红（红跨 0 度）
    [20,45)   → 橙        [45,70)             → 黄
    [70,160)  → 绿        [160,230)           → 蓝
    [230,330) → 紫
```

**颜色词只有 11 个**：`黑 白 灰 棕 红 玫红 橙 黄 绿 蓝 紫`（外加通配符 `*` = 只报不判）。
期望颜色必须**正好**打这些词，"深红""天蓝""熄灭"一律认不出来（现在会直接报错并列出可用词）。

**真要"颜色差多远"的连续量**：本算子给不了 ΔE。可以用 `Rgb`（区域中位色）配合「C#脚本」自行计算，
或改用带阈值分割的预处理算子；但先想清楚：产线上问的通常是"是不是红"，不是"离标准红差几"。

## 13 项阈值：改哪个动到什么

这 13 项是**本步骤自己带的一份副本**（默认值取自内核 `Core.Halcon.Color`），改了随方案落盘，
不影响别的工位、也不影响「颜色序列检查」。

| 配置项 | 默认 | 管到哪 | 现场调向 |
| --- | --- | --- | --- |
| `ColorlessSaturation` | `0.45` | 无彩/有彩分界，**黑/白/灰/棕全住在这条线以下** | 指示灯亮态被读成"灰"（颜色淡）→ 调低；灰机身被读成彩 → 调高 |
| `BlackValue` | `80` | 明度低于它才叫黑 | **灯灭态判不成黑**（灯罩发灰）→ 调高；暗背景被读成黑 → 调低 |
| `WhiteSaturation` | `0.15` | 白的附加条件：饱和度必须低于它 | 白标签在暖光下被读成"黄"→ 调低这条（更严）或调高 `YellowHueTo` |
| `WhiteValue` | `195` | 明度高于它才叫白 | 白块偏暗读成灰 → 调低；高光反光斑被判白 → 调高 |
| `BrownWarmth` | `12` | 偏暖判据：R 比 G、B **都**高出这么多才算棕 | 棕色件读成灰 → 调小；灰件读成棕 → 调大 |
| `BrownValue` | `175` | 棕的明度上限（比它亮就归灰） | 浅棕/米色该算棕时适当调高，但别逼到 `WhiteValue` |
| `RoseHueFrom` | `330` | 玫红起点 | 玫红读成紫 → 调小；紫读成玫红 → 调大 |
| `RedHueFrom` | `350` | 红起点（玫红/红分界） | **红与玫红只差十几度**，分不清只动这一对 |
| `RedHueTo` | `20` | 红止点（不小于 350 或小于 20 都是红） | 橙红读成红 → 调小；红读成橙 → 调大 |
| `OrangeHueTo` | `45` | 橙止点 | 橙黄分不清时调它 |
| `YellowHueTo` | `70` | 黄止点 | 黄绿分不清时调它 |
| `GreenHueTo` | `160` | 绿止点 | **绿灯偏青**（青色 LED 常被读成蓝）→ 调高到 180~190 试试 |
| `BlueHueTo` | `230` | 蓝止点（比它高就是紫） | 蓝紫分不清时调它 |

**关键提醒**：色相阈值只在**有彩区**（`s` 不小于 `ColorlessSaturation`）起作用。
"黑/白/灰/棕之间乱跳"这类问题，动色相阈值一点用都没有，要动的是上面那 6 项无彩条件。

## `MinShare` 怎么定：从明细里量出来，别猜

`MinShare`（默认 `0.60`）是"纯度下限"：主色不仅要**命中期望词表**，占比还要不小于它。

1. 拿一张**已知良品**，点「试算一下」，读「明细」行（如 `红:92%、灰:6%、黑:2%`）；
2. 连测 5~10 件（含边缘位置、含灯罩略有污渍的），记下**最低**的那次主色占比；
3. `MinShare` = 那个最低值再往下留一点余量（例如最低 88% → 填 `0.85`）；
4. 反过来验证：拿一张**混料/贴错色标**的样品，主色占比应落在阈值以下并报"颜色不纯"。

越界值会被**夹回 0~1**（填 1.5 会"永远不纯"、填 -0.2 会"永远合格"），这是有意防止配置错误悄悄改判定。
指示灯边缘的反光、色标与基材的过渡带都会摊薄占比——适当调低是正解。

占比相关：`Share` = 主色票数 / 实际参与投票的采样点数；明细按**票数**算百分比，
只显示投过票的颜色词，取整后相加可能有 ±1~2% 的舍入差。区域里明明只有一种颜色却不到 100%，
是边界过渡带、噪点、反光在投别的词——这是投票机制的**正常表现**，它照实说"有几成把握"。

## 与「颜色序列检查」的分工

两者共用内核 `Core.Halcon.Color` 的**同一套颜色词与判据**，所以"玫红"在哪个算子里答案都一样。
差别在**认顺序**还是**认一块**：

| | 区域颜色检查（本算子） | 颜色序列检查（Plugin.ColorCheck） |
| --- | --- | --- |
| 看的东西 | **一块区域**：ROI 内逐点投票取主色 + 占比 | **一串位置**：沿一条线取一串颜色词，逐位比对 |
| 回答 | 这块是什么颜色、纯不纯、某颜色占比够不够 | 线序/排线/色带的**顺序**对不对 |
| 典型工件 | 指示灯、色标、单块颜色纯度 | 多芯线序、色环电阻、色带 |
| 判定量 | 主色词 + 占比下限 `MinShare` | 每一位的颜色词 |
| 阈值副本 | 各带一份，互不影响 | 各带一份，互不影响 |

选型口径：**只要"这块是不是红"** → 本算子；**要"第 1 红、第 2 黑、第 3 绿"** → 颜色序列检查。
两个都要（既要线序对、又要每根线的颜色够纯）就在流程里串起来——
`FlowCanvasChecks\ColorSyntheticChecks.cs` 的合成场景走的就是"图像采集 → 颜色序列检查 → 区域颜色检查 × 2"
这条完整链（区域红灯 + 区域紫块两个步骤实例并存）。

**阈值与词表的边界**：13 项阈值是每个算子各存一份，所以换工位/换产品要重配属正常，这正是设计意图；
但**颜色词表与分类层次是全仓共用的**（内核），不要指望"在这个算子里把玫红改成别的定义"——
那需要改内核，会影响所有颜色算子。
