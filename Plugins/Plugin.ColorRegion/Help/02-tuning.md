# 区域颜色检查 · 调参与判据

> 分类：图像处理 ｜ 来源：插件 Plugin.ColorRegion

这一页专讲**判色的口径与怎么调**：颜色空间到底用的哪一个、13 个色卡阈值各管什么、
`MinShare` 该定多少、采样区形状怎么选才不被背景带偏、光照漂移之后按什么顺序重调。
基础用法（端口、判定口径、接线）见《区域颜色检查》。

## 判据到底是什么颜色空间：固定 HSV 式，没有开关

**界面上没有"RGB / HSV / Lab"下拉，也没有 ΔE / 颜色距离 / 容差半径**。
判定走的是"把每个像素归成一个**颜色词**，然后投票"，这是刻意的：
颜色词是离散量，产线的语义（"红灯亮着"）本来就是离散的；
用连续距离度量就得给每个灯配一个容差半径，光照一变半径就失效。

三个量都从 R/G/B 现场推：

| 量 | 算法 | 用途 |
| --- | --- | --- |
| 明度 `v` | `max(R, G, B)` | 判黑（< 80）、判白（> 195）、棕的明度上限（< 175） |
| 饱和度 `s` | `(max − min) / max`（`max <= 0` 记 0） | 无彩/有彩分界（< 0.45 走黑/白/灰/棕），白的附加条件（< 0.15） |
| 色相 `h` | 标准 HSV 色相角，0~360 度 | 有彩区按角度分色系 |

```
s < ColorlessSaturation(0.45)  →  无彩区
    v < BlackValue(80)                                → 黑
    s < WhiteSaturation(0.15) 且 v > WhiteValue(195)   → 白
    (R-G) ≥ BrownWarmth(12) 且 (R-B) ≥ 12 且 v < BrownValue(175) → 棕
    其余                                              → 灰
s ≥ 0.45  →  有彩区，按色相角 h：
    [330,350) → 玫红      ≥350 或 <20 → 红（红跨 0 度）
    [20,45)   → 橙        [45,70)     → 黄
    [70,160)  → 绿        [160,230)   → 蓝
    [230,330) → 紫
```

**颜色词只有 11 个**：`黑 白 灰 棕 红 玫红 橙 黄 绿 蓝 紫`（外加通配符 `*` = 只报不判）。
期望颜色必须**正好**打这些词，"深红""天蓝""熄灭"一律认不出来（现在会直接报错并列出可用词）。

**真要"颜色差多远"的连续量**：本算子给不了 ΔE。
可以用 `Rgb`（区域中位色）配合「C#脚本」自行计算，或改用带阈值分割的预处理算子；
但先想清楚：产线上问的通常是"是不是红"，不是"离标准红差几"。

## 13 项色卡阈值：改哪个动到什么

配置路径：节点配置 → 检查参数 → **高级参数** → **颜色判据阈值**。
这 13 项是**本步骤自己带的一份副本**（默认值取自内核），改了随方案落盘，
不影响别的工位、也不影响「颜色序列检查」——但**颜色词表是共用的**，
所以"玫红"在两个算子里始终是同一个意思。

| 参数 | 默认 | 管到哪 | 现场调向 |
| --- | --- | --- | --- |
| `ColorlessSaturation` | `0.45` | 无彩/有彩分界，**黑/白/灰/棕全住在这条线以下** | 指示灯亮态被读成"灰"（颜色淡）→ 调低；灰机身被读成彩 → 调高 |
| `BlackValue` | `80` | 明度低于它才叫黑 | **灯灭态判不成黑**（灯罩发灰）→ 调高；暗背景被读成黑→ 调低 |
| `WhiteSaturation` | `0.15` | 白的附加条件：饱和度必须低于它 | 白标签在暖光下被读成"黄"→ 调低这条（更严）或调高 `YellowHueTo` |
| `WhiteValue` | `195` | 明度高于它才叫白 | 白块偏暗读成灰 → 调低；高光反光斑被判白 → 调高 |
| `BrownWarmth` | `12` | 偏暖判据：R 比 G、B **都**高出这么多才算棕 | 棕色件读成灰 → 调小；灰件读成棕 → 调大 |
| `BrownValue` | `175` | 棕的明度上限（比它亮就归灰） | 浅棕/米色该算棕时适当调高，但别逼到 `WhiteValue` |
| `RoseHueFrom` | `330` | 玫红起点 | 玫红读成紫 → 调小；紫读成玫红 → 调大 |
| `RedHueFrom` | `350` | 红起点（玫红/红分界） | **红与玫红只差十几度**，分不清只动这一对 |
| `RedHueTo` | `20` | 红止点（`≥350` 或 `<20` 都是红） | 橙红读成红 → 调小；红读成橙 → 调大 |
| `OrangeHueTo` | `45` | 橙止点 | 橙黄分不清时调它 |
| `YellowHueTo` | `70` | 黄止点 | 黄绿分不清时调它 |
| `GreenHueTo` | `160` | 绿止点 | **绿灯偏青**（青色 LED 常被读成蓝）→ 调高到 180~190 试试 |
| `BlueHueTo` | `230` | 蓝止点（比它高就是紫） | 蓝紫分不清时调它 |

**关键提醒**：色相阈值只在**有彩区**起作用（`s ≥ ColorlessSaturation`）。
"黑/白/灰/棕之间乱跳"这类问题，动色相阈值一点用都没有，要动的是上面那 6 项无彩条件。

## 采样区：形状、大小与投票质量

投票质量**九成由采样区决定**，先把它弄对再谈阈值。

| 目标 | 画什么 | 为什么 |
| --- | --- | --- |
| 圆形指示灯 | **新建圆形** | 方框的四个角是背景，背景占比高时会"很有把握地"报出背景色 |
| 按钮/色标方块 | 新建矩形 | 贴合即可，别把相邻颜色圈进来 |
| 椭圆形/斜置色块 | 新建椭圆 | 半径 1/2 与旋转角由拖拽句柄决定 |
| 环形/不规则带 | 矩形 + 收紧 | 采样用 HALCON 区域当掩膜，落在区域外的点不参与投票 |

- **框太大**：主色占比被稀释（报"颜色不纯"）。
- **框太小**：采样点太少，容易被一个脏点/高光翻盘。
- **框到图外**：超出部分自动裁掉（不报错）；完全没交集才报错"采样区与图像没有交集"。
- `SamplePoints`（默认 400）是**上限**，超了按固定步长均匀抽稀——均匀抽稀不会让投票偏，
  所以大区域**不需要**调大它；只有"区域很小但想全点都采"时才用得上。

## `MinShare` 怎么定：从明细里量出来，别猜

`MinShare`（默认 `0.60`）是"纯度下限"：主色不仅要**命中期望词表**，占比还要 ≥ 它。

1. 拿一张**已知良品**，点「试算一下」，读「明细」行（如 `红:92%、灰:6%、黑:2%`）；
2. 连测 5~10 件（含边缘位置、含灯罩略有污渍的），记下**最低**的那次主色占比；
3. `MinShare` = 那个最低值再往下留一点余量（例如最低 88% → 填 `0.85`）；
4. 反过来验证：拿一张**混料/贴错色标**的样品，主色占比应落在阈值以下并报"颜色不纯"。

越界值会被**夹回 0~1**（填 1.5 会"永远不纯"、填 -0.2 会"永远合格"），这是有意防止配置错误悄悄改判定。

## 光照漂移与换型：按这个顺序重调

1. **先看主色对不对**：点「试算一下」读「主色」和「明细」。
   主色就对、占比偏低 → 是**采样区/`MinShare`** 的问题，不要动色卡。
2. **主色就不对** → 动 13 项阈值；先分清落在**无彩区**（黑白灰棕）还是**有彩区**（色相），只动对应那一组。
3. **换了灯/加了遮光罩，全批漂移** → 先看 `Rgb` 中位色的绝对值漂了多少：
   明度类阈值（`BlackValue` `WhiteValue` `BrownValue`）跟着打光方向调；
   饱和度分界 `ColorlessSaturation` 是唯一一个"比例型"的稳剂量，通常**不用改**。
4. **位置每帧会变**（工件在传送带上浮动）→ 上游先接「模板匹配」的对齐图或「ROI」的 `Domain_`，
   本算子的采样区坐标始终是**图像像素系**，不会因为上游裁图而自动跟着走。
5. **灯灭态**（要区分"灭"和"绿"）→ 灭态通常读成 `黑` 或 `灰`，把期望写成多候选即可（如 `红,绿` 允许两态；
   灭态另用别的判定链路，或期望填 `*` 只报颜色、由下游用 `Color`/`Share` 自己判）。

| 现象 | 先查这一项 |
| --- | --- |
| 主色判成背景色 | 形状/大小（圆灯用了方框）→ 改「新建圆形」 |
| "颜色不纯：主色只占 N%" | ① 采样区混进背景或第二种颜色；② `MinShare` 定太高 |
| 绿灯读成蓝 | `GreenHueTo`（默认 160）调高；青色 LED 的色相常落在 170~190 |
| 红灯与玫红乱跳 | 只动 `RoseHueFrom` / `RedHueFrom`（330 / 350）这一对 |
| 白标签读成黄/灰 | 白的两条附加条件：`WhiteSaturation`（0.15）与 `WhiteValue`（195）——暖光下先放宽饱和度、再压低明度 |
| 12/16 位相机接手后黑白灰棕大面积错 | 不用改参数：已自动等比压回 8 位，日志有说明；`Rgb` 是归一后的值 |
| 换工位/换产品就要重配 | 正常——阈值是**每个算子各带一份副本**，随各自方案落盘，这正是设计意图 |
| 结果图上找不到标注 | `DisplayViewIndex`（1~9，0=不投射）；轮廓按折线画，圆/椭圆不会画成方框 |

## 常见问题

**Q：试算和正式运行是一样的吗？**
不一样，只差在**判定**那一步：试算不要求先填期望颜色（现场顺序是"先试算出主色 → 一键填成期望"，
若试算就强制填期望，那个入口永远用不上）；填了期望，试算也会把判定一起显示出来。
**运行期必须判定**：期望为空、期望词写错，运行期都会挡下来报错。

**Q：怎么只让它"报颜色"、不参与流程判定？**
在「期望颜色」里写 `*`（期望颜色是配置项，不在输入端口上）。
此时 `Result` 恒为 `true`，`Verdict` 是"只报颜色不判定：X（占 N%，中位色 R,G,B）"，
下游想怎么用 `Color` / `Share` 都行。

**Q：多个颜色都算合格怎么配？**
「期望颜色」用逗号分隔多候选，**命中任一即可**：`红,玫红`。中英文逗号、顿号都认。

**Q：占比和明细里的百分比为什么不加总到 100%？**
明细按**票数**算百分比，只显示投过票的颜色词；取整后相加可能有 ±1~2% 的舍入差。
主色占比 `Share` = 主色票数 / 实际参与投票的采样点数。

**Q：区域里明明只有一种颜色，占比却不是 100%？**
边界过渡带、噪点、反光都会投出别的词。这是投票机制的**正常表现**——它照实说"有几成的把握"。
`MinShare` 就是给这个"不干净"留的余量。

**Q：想让某个颜色占比达到多少才算亮灯？**
用 `Share` 端口：期望填 `*` 让它只报颜色，下游用「数值比较」/「数学计算」判断 `Share ≥ 阈值`，
或直接接「If」（逻辑控制）。这样"颜色对不对"和"亮度够不够"两条判定各管各的。

**Q：这些阈值会不会被别的算子共用掉？**
不会，本步骤各存一份。但**颜色词表与分类层次是全仓共用的**（内核 `Core.Halcon.Color`），
所以不要指望"在这个算子里把玫红改成别的定义"——那需要改内核，会影响所有颜色算子。
