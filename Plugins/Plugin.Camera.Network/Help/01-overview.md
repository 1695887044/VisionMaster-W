# 网络相机（虚拟）

> 分类：相机 ｜ 来源：插件 Plugin.Camera.Network

一台**不存在的相机**：由外部客户端按 HTTP 协议把图持续推给主软件，主软件把它当成一台真相机来管理——
有状态机、有帧队列、有溢出计数、有掉线判定。用途是**没有硬件时把采集链路整条验通**
（能人为注入丢帧、掉线、延迟，这些真机反而做不到），也用于产线上"某工位没有相机、只有上位机丢图"的接入形态。

它自己不产图，产图的是客户端；它的产出是**这台虚拟相机的帧队列**，由流程里的「图像采集 · 相机采集」步骤消费。

## 为什么需要它 / 原理

**骨架不重写一遍**。环形帧队列 + 溢出丢旧计数、连接状态机、心跳看门狗、取图口（消费 / 只读）全部固化在契约层的驱动基类里；
本驱动只写"网络相机与真机不一样的地方"，代码一百来行。加一家真机相机时也照这个形状写，使用层与宿主一行不改。

**"打开"到底打开了什么**：没有物理句柄可开。打开的实质是"宿主收图服务开始接受该序列号的帧"（那一步发生在宿主侧），
所以驱动侧的打开永远成功——这样才能把状态推进到 `Connecting` 并启动心跳看门狗。若这里报失败，
"等待客户端接入"这条链路根本不会开始，明明接得进来却报"打不开"。

**状态机（这是本驱动最要紧的一页）**：

```
Closed ──连接──▶ Connecting ──首次心跳──▶ Online ──首帧到达──▶ Streaming
                    ▲                                             │
                    └────── 心跳超时（默认 3000ms）判掉线，清空队列 ─┘
```

- 打开后**必须停在 `Connecting`**（"等待客户端接入（序列号 X）"），不能直接算 `Online`：
  此刻客户端可能还没接进来。若一打开就标 `Online`，现场看到"没图"时界面就分不清"客户端根本没接进来"和"接进来了但没送帧"
  ——而这两件事的处置完全不同。
- **必须靠心跳判活**：HTTP 是无连接的，客户端进程被杀、网线被拔，主软件收不到任何"掉线通知"，
  只能靠"多久没收到证据"反推。若不启心跳，客户端消失后界面会一直停在"采流中"——现实里相机已经没了，界面却报正常。
- **心跳与推图解耦**：只有心跳能区分"在线但这一刻没出图"（正常：暂停、图片放完、没触发）与"客户端没了"（故障）。
  所以**暂停推图时心跳也必须照发**，否则 3 秒后被判掉线。
- **掉线立刻清空队列**：积压的旧帧在恢复后被取走，会让流程把"几秒前的旧图"当成"当前工件"来检测——
  比明确失败危险得多。丢弃量计入"其它丢弃"，与队列满导致的溢出**分开计数**。
- **停止采流 = 关掉收帧闸门**：停止后送来的帧一律被拒并计入丢弃，队列同时清空，
  所以"下次开始采流"不会立刻取到一张停止前的旧图。

**它是纯托管件**：只引用契约层，不引用 WPF、不引用 HALCON，帧全程以 `byte[]` 流转。
"原始像素 → HImage"这一步留给消费者（图像采集算子），所以换一家相机不会被 HALCON 版本绑死。

## 它能配合谁用（务必分清两条 HTTP 通道）

| 通道 | 端口 | 谁在用 | 语义 |
| --- | --- | --- | --- |
| **相机通道**（本页） | `19100`（`AppConfig.json → NetworkCameraServer`） | 「图像采集」的**相机采集**模式 + 本驱动 | 客户端**持续**推帧 → 入队；流程按自己节奏**消费**，每帧只被取一次；有环形缓冲、溢出计数、心跳判活 |
| **网络推送通道** | `19000`（`AppConfig.json → HttpImageServer`） | 「图像采集」的**网络推送**模式（与相机无关，不需要添加相机） | **推一张图 → 立刻跑一次流程 → 同步回结果**；图像槽只留最新一帧；同一流程同时只允许一次执行（并发推 → 409） |

两条通道语义不同、端口分开，排障时先确认自己走的是哪一条：
"相机设置里有这台网络相机、状态一直 `Connecting`" = 相机通道；
"采集步骤日志停在「槽内暂无图像，开始等待网络推送」" = 网络推送通道。

## 客户端怎么接（协议契约）

| 项 | 值 |
| --- | --- |
| 推一帧 | `POST http://{主机}:{端口}/camera/{序列号}/frame` |
| 心跳 | `POST http://{主机}:{端口}/camera/{序列号}/heartbeat`（无请求体，**每秒一次**） |
| 鉴权 | 请求头 `Authorization: Bearer {Token}`；默认令牌 `visionmaster`（占位值，投用前改 `AppConfig.json → NetworkCameraServer.Token`） |
| 帧内容 | 请求体 = **图片文件的原始字节**（jpg / png / bmp / tif…，不是 raw 像素），可选头 `X-Image-Name: 文件名`（只用于日志与界面回显） |
| 解码 | 宿主统一解码：灰度保持单通道，彩色一律 BGR24 交错；因此客户端不必关心行填充与字节序 |
| 成功回包 | 推帧：`{ success, serial, frameId, received, pending, overflow, bytes }`；心跳：`{ success, serial, state, received, pending, overflow, dropped }` |
| 失败回包 | `{ success:false, message }`（原因在 **message** 字段）；状态码 400 请求体为空 / URL 缺序列号，401 令牌不对，404 序列号不存在（消息里会列出当前已配置的序列号），409 帧被拒绝（相机未打开 / 已停止采流 / 帧数据不自洽 / 设备已释放） |
| 是否等流程 | **不等**。服务端解出像素、入队、立刻回包；客户端不阻塞、拿不到检测结果（这正是"相机"与"网络推送"的本质区别） |
| 现成工具 | `Tools\VirtualCameraClient`（独立 WPF"假相机"：选图片文件夹按间隔连续推 / 手动推单张，心跳独立循环每秒一次；默认 `127.0.0.1:19100`、令牌 `visionmaster`） |
| 监听地址口径 | 配置里 `0.0.0.0` 表示"听所有网卡"，**不能当客户端的目标地址**；相机设置界面会转成"本机IP"提示。跨机推图就填这台工控机的实际 IP |

## 配置项（系统 → 相机设置）

| 项 | 必填 | 说明 |
| --- | --- | --- |
| 驱动类型 | 是 | 选「网络相机（虚拟）」。它的接入方式是**手填序列号**，不是"搜设备"（虚拟相机没有枚举这一步） |
| 序列号 | **是** | 客户端 URL 里 `{序列号}` 那一段，**必须逐字一致**（比较时忽略首尾空格与大小写）。界面上的"等待客户端接入（序列号 X）"就是给你核对这一项用的 |
| 显示名 / 备注 | 否 | 只给人看，不参与寻址；改名不会让客户端失联 |
| 自动连接 | 否 | 勾选后方案加载即开始"等待客户端接入"，配合客户端开机自启 |
| 采集参数 | 否 | 见下面「关键参数」——**其中三项真实生效，三项不生效**，别按真相机的直觉理解 |

## 输出（给「图像采集」消费的东西）

| 项 | 说明 |
| --- | --- |
| 帧 | 宽 / 高 / 通道数（1 灰度、3 彩色 BGR 交错）/ 像素字节（行优先无填充）/ 帧号（本机从 1 自增）/ 采集时刻 / 来源名（客户端声明的 `X-Image-Name`） |
| 状态与一句话说明 | `Closed` / `Connecting`（等待接入或判掉线）/ `Online`（客户端在但没送帧）/ `Streaming`（正在收帧） |
| 累计收帧 / 待消费 | 前者是"这台一共进了多少帧"，后者是"队列里还压着几帧"——采集步骤的 `ReceivedCount` 与超时文案里的计数就是它们 |
| 溢出丢帧 / 其它丢弃 | 两个数分开：**溢出 = 处理不过来**（质量事故，必须查），**丢弃 = 掉线或停止时清掉的陈旧帧** |

## 关键参数

> 完整参数与取值范围以流程中该步骤的「模块参数」界面为准，这里只解释含义。
> （相机驱动的参数在「系统 → 相机设置」里维护，随方案落盘；采集步骤的「取图超时」端口可临时覆盖 `FrameTimeoutMs`。）

| 参数 | 默认 | 对网络相机是否生效 | 说明 |
| --- | --- | --- | --- |
| 取图超时 `FrameTimeoutMs` | 3000 | **生效**（由基类消费） | 消费端"等一帧最多等多久"。填小于 1 的值归一到 3000。**永远不允许无限等**：相机不触发时流程线程会永久卡死、现场只能杀进程 |
| 队列容量 `BufferCapacity` | 8 | **生效** | 环形队列容量，满则丢最旧并计溢出。太小易丢帧，太大会掩盖"产能不匹配"并把延迟越积越大。合法区间 1~1024 |
| 心跳超时 `HeartbeatTimeoutMs` | 3000 | **生效** | 多久没有"还活着"的证据就判掉线。检查频率取该值的 1/3、夹在 200~1000 ms；填小于 200 会被归一到 3000。客户端心跳是每秒一次，所以这个值不要低于 2000 |
| 曝光 `ExposureTimeUs` | 10000 | **不生效** | 曝光由客户端（那台"假相机"）决定，软件侧没有下发通道。改这里只影响配置落盘与回显 |
| 增益 `Gain` | 0 | **不生效** | 同上 |
| 触发模式 `TriggerMode` | 软触发 | **不生效** | 同上；"什么时候出一帧"完全由客户端的推送节拍决定 |

> 曝光/增益/触发这三项"设了不生效"是有意为之：应用参数仍返回成功，因为配置确实被正确保存了——
> 若返回失败，用户在界面每改一次就报一次错，那是纯粹的自欺。但界面上必须按上面这张表理解它们。

## 口径与失败策略

- **"打开"永不失败**（驱动侧无动作）；"开始采流"同理。真正的成败看**状态与计数**，不看按钮返回值。
- **掉线判定 = 心跳超时**，判掉线时：状态回到 `Connecting` + 清空队列 + 计入丢弃，并在日志写
  "已 X.Xs 未收到心跳，等待设备恢复（已清空 N 帧陈旧图像）"。心跳恢复后自动回到在线/采流，不需要人工干预。
- **推帧被拒不刷屏**：同一原因连续出现只在**原因变化时**记一条日志（客户端按 33 帧/秒持续推，逐帧记会把第一条有用的淹掉）。
  看日志时注意"第一条拒绝原因"才是根因。
- **本驱动不关收图服务**：那是全局资源，停一台相机不能影响别的相机与流程。
- **取不到图时看的是采集步骤的文案**：它会把「相机状态 + 待消费 + 累计收帧 + 溢出丢帧」四个数一起给出，
  分诊方法见 `02-troubleshooting.md`。

## 典型用法 / 接线

```
① 无硬件验链路：Tools\VirtualCameraClient（或你自己的客户端）
   主机=127.0.0.1 端口=19100 令牌=visionmaster 序列号=V-CAM-01，每秒心跳 + 按间隔推图
② 系统 → 相机设置：驱动=网络相机（虚拟），序列号=V-CAM-01 → 连接 → 状态从 Connecting 跳到 Streaming
③ 流程里：

V-CAM-01 的帧队列 ──▶ 图像采集.相机采集（CameraSerial=V-CAM-01）
图像采集.Image ─────▶ 下游算子.SrcImage
图像采集.FrameId / ReceivedCount ──▶ 数据记录（帧溯源对账，与客户端日志的 frameId 直接可比）
```

## 常见问题

**Q：状态一直停在"等待客户端接入（序列号 X）"？**
说明打开成功但**没有收到任何心跳或帧**。按顺序查：① 客户端 URL 里的序列号与这里是否逐字一致
（大小写与首尾空格可以不管，**其余一位都不能差**）；② 端口是不是 `19100`（不是 `19000`——那是网络推送通道）；
③ 令牌对不对（401）；④ 客户端有没有在发**心跳**（只推图不发心跳也能进 `Streaming`，但一旦停止推图就会被判掉线，
所以正式接入建议心跳常发）；⑤ 服务是否真在监听——相机设置页面会写"收图服务未启动，网络相机会永远等不到图"。

**Q：客户端报 404，消息里说"当前已配置：A、B"？**
URL 里的序列号不在方案里。照消息里列出的那几台改客户端，或到「系统 → 相机设置」添加这台。
中文或带空格的序列号需要 URL 转义，**现场建议只用字母数字 + 短横线**，这条链路对转义的支持是按"字母数字"惯例设计的。

**Q：客户端报 409，说"相机未打开，请先在「系统 → 相机设置」连接该相机"？**
帧确实到了，但主软件这边没连接这台相机（或已停止采流——"相机已停止采流，帧被拒绝"）。
连接 + 开始采流；若配置里勾了「自动连接」却没生效，看方案是否已保存、以及日志里创建/连接那一步的失败原因。

**Q：界面显示"采流中"，客户端却早被杀了？**
正常情况不可能——HTTP 没有掉线通知，判活全靠心跳：默认 3000 ms 没收到心跳就判掉线并清空队列。
如果真出现了，查三件事：`HeartbeatTimeoutMs` 是不是被填成极大值（小于 200 会归一到 3000）、
客户端是不是还在按每秒一次发心跳（暂停推图时也必须发）、以及这台相机的序列号是否与另一台重复
（重复时按序列号取图只命中先注册那一台，另一台的心跳打不到正在显示的那台）。

**Q：没有图，但相机状态是 `Online`（在线）？**
`Online` 的准确含义是"客户端活着、但此刻没送帧"。这**不是故障**：客户端暂停推图、图片文件夹放完、
或客户端只在触发时推图，都会停在这里。该查触发链路（客户端那边），不要在主软件里找故障。

**Q：「图像采集」报"等待相机…出图超时"，但客户端一直在推？**
看文案里的四个计数：待消费长期为 0 且累计不涨 = 帧没进队（去查客户端的返回码）；
待消费一直满、溢出在涨 = **流程处理不过来**（每帧都对应一个工件，丢帧要当质量事故处理）。
临时放宽只是掩盖：先减处理链或降客户端的推送间隔。

**Q：改了曝光/增益/触发模式，图完全没变化？**
预期行为——这三项对网络相机**不生效**（由客户端决定）。真正影响这台"相机"行为的是：
推送间隔（客户端设）、取图超时、队列容量、心跳超时。

**Q：多台网络相机同时跑要注意什么？**
① 每台一个独立帧队列与一条"传送带"，互不干扰；② **序列号必须唯一**（相机设置会拦重复，宿主日志也会告警）；
③ 同一台相机的帧**不广播**：两个采集步骤选同一台就会互相分抢帧（一帧只被取一次），
需要同一帧多处使用请在一处取图后把 `Image` 传给下游；④ 全部客户端都往同一个 `19100` 端口推，
带宽与磁盘 IO 叠加，多相机大节拍时优先确认流程侧的消化能力。
