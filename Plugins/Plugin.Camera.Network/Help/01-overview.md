# 网络相机（虚拟）

> 分类：相机 ｜ 来源：插件 Plugin.Camera.Network

一台**不存在的相机**：外部客户端按 HTTP 把图持续推给主软件，主软件把它当成一台真相机来管理——
有状态机、有帧队列、有溢出计数、有掉线判定。用途是**没有硬件时把采集链路整条验通**
（能人为注入丢帧、掉线、延迟，这些真机反而做不到），也用于产线上"某工位没有相机、只有上位机丢图"的接入形态。

它自己不产图，产图的是客户端；它的产出是**这台虚拟相机的帧队列**，由流程里的「图像采集 · 相机采集」步骤消费。

本册共三页：本页（定位与上手）·《端口与参数》·《排错》。

## 一、为什么需要它 / 原理

**骨架不重写一遍**。环形帧队列 + 溢出丢旧计数、连接状态机、心跳看门狗、取图口（消费 / 只读）
全部固化在契约层的驱动基类 `CameraDeviceBase`（`Shard\Core.Interfaces\Camera\`）里；本驱动只写
"网络相机与真机不一样的地方"，代码一百来行。加一家真机相机时也照这个形状写，使用层与宿主一行不改。

**"打开"到底打开了什么**：没有物理句柄可开。打开的实质是"宿主收图服务开始接受该序列号的帧"
（那一步发生在宿主侧），所以驱动侧的打开永远成功——这样才能把状态推进到 `Connecting` 并启动心跳看门狗。
若这里报失败，"等待客户端接入"这条链路根本不会开始，明明接得进来却报"打不开"。

**状态机（本驱动最要紧的一段）**：

```
Closed ──连接──▶ Connecting ──首次心跳──▶ Online ──首帧到达──▶ Streaming
                    ▲                                             │
                    └────── 心跳超时（默认 3000ms）判掉线，清空队列 ─┘
```

- 打开后**必须停在 `Connecting`**（说明写"等待客户端接入（序列号 X）"），不能直接算 `Online`：
  此刻客户端可能还没接进来。若一打开就标 `Online`，现场看到"没图"时界面就分不清
  "客户端根本没接进来"和"接进来了但没送帧"——而这两件事的处置完全不同。
- **必须靠心跳判活**：HTTP 是无连接的，客户端进程被杀、网线被拔，主软件收不到任何"掉线通知"，
  只能靠"多久没收到证据"反推。若不启心跳，客户端消失后界面会一直停在"采流中"。
- **心跳与推图解耦**：只有心跳能区分"在线但这一刻没出图"（正常：暂停、图片放完、没触发）
  与"客户端没了"（故障）。所以**暂停推图时心跳也必须照发**，否则默认 3 秒后被判掉线。
- **掉线立刻清空队列**：积压的旧帧在恢复后被取走，会让流程把"几秒前的旧图"当成"当前工件"来检测——
  比明确失败危险得多。丢弃量计入"其它丢弃"，与队列满导致的溢出**分开计数**。
- **停止采流 = 关掉收帧闸门**：停止后送来的帧一律被拒并计入丢弃，队列同时清空，
  所以"下次开始采流"不会立刻取到一张停止前的旧图。

**它是纯托管件**：只引用契约层，不引用 WPF、不引用 HALCON，帧全程以 `byte[]` 流转。
"原始像素 → HImage"这一步留给消费者（图像采集算子），所以换一家相机不会被 HALCON 版本绑死。

## 二、五分钟把链路跑通（无硬件）

1. 启动主软件，确认宿主相机收图服务在监听：「系统 → 相机设置」里网络相机的接入地址能显示出完整 URL。
   若提示"收图服务未启动，网络相机会永远等不到图"，查 `AppConfig.json → NetworkCameraServer.Enabled`
   与端口是否被占用（默认 `19100`）。
2. 「系统 → 相机设置」添加一台：驱动类型选「网络相机（虚拟）」，**序列号手填**（例如 `V-CAM-01`，
   只用字母数字与短横线）。
3. 点「连接」：状态应为 `Connecting`，说明"等待客户端接入（序列号 V-CAM-01）"。
   这一刻还没有客户端，**这是正确状态**，不是失败。
4. 启动 `Tools\VirtualCameraClient`（或你自己的客户端）：主机 `127.0.0.1`、端口 `19100`、
   令牌 `visionmaster`、序列号 `V-CAM-01`，选一个图片文件夹，勾上心跳（默认独立循环，每秒一次），点"开始推图"。
5. 回相机设置：状态先跳 `Online`（收到心跳）或直接 `Streaming`（首帧到达即视为进入采流）。
6. 流程里拖「图像采集」→「相机采集」页选这台，点窗口底部「执行」试运行；
   成功文案形如 `已从相机取图: 宽x高x通道（第 N 帧，来源 文件名）`。

每步不对 → 直接翻《排错》第二节的"现象 → 第一判据 → 处置"。

## 三、务必分清两条 HTTP 通道

| 通道 | 端口 | 谁在用 | 语义 |
| --- | --- | --- | --- |
| **相机通道**（本页） | `19100`（`AppConfig.json → NetworkCameraServer`） | 「图像采集」的**相机采集**模式 + 本驱动 | 客户端**持续**推帧 → 入队；流程按自己节奏**消费**，每帧只被取一次；有环形缓冲、溢出计数、心跳判活 |
| **网络推送通道** | `19000`（`AppConfig.json → HttpImageServer`） | 「图像采集」的**网络推送**模式（与相机无关，不需要添加相机） | **推一张图 → 立刻跑一次流程 → 同步回结果**；图像槽只留最新一帧；同一流程同时只允许一次执行（并发推 → 409） |

两条通道语义不同、端口分开，排障时先确认自己走的是哪一条：
"相机设置里有这台网络相机、状态一直 `Connecting`" = 相机通道；
"采集步骤日志停在「槽内暂无图像，开始等待网络推送」" = 网络推送通道。

**同一份图不会走两条通道**：`/camera/{序列号}/frame` 只进相机通道，`/flow/{流程名}` 只进网络推送通道。
把 URL 写成另一条的路径，就是现场最常见的"推成功了但这边没反应"。

## 四、客户端接入契约（速查）

| 项 | 值 |
| --- | --- |
| 推一帧 | `POST http://{主机}:{端口}/camera/{序列号}/frame` |
| 心跳 | `POST http://{主机}:{端口}/camera/{序列号}/heartbeat`（无请求体，**每秒一次**） |
| 鉴权 | 请求头 `Authorization: Bearer {Token}`；默认令牌 `visionmaster`（占位值，投用前改 `AppConfig.json → NetworkCameraServer.Token`） |
| 帧内容 | 请求体 = **图片文件的原始字节**（jpg / png / bmp / tif…，不是 raw 像素），可选头 `X-Image-Name: 文件名` |
| 解码 | 宿主统一解码：灰度保持单通道，彩色一律 BGR 交错 3 字节/像素；客户端不必关心行填充与字节序 |
| 是否等流程 | **不等**。服务端解出像素、入队、立刻回包；客户端拿不到检测结果（这正是与"网络推送"的本质区别） |
| 现成工具 | `Tools\VirtualCameraClient`（独立 WPF"假相机"：选图片文件夹按间隔连续推 / 手动推单张，心跳独立循环每秒一次） |

回包字段、状态码与逐字错误文案见《端口与参数》《排错》。

## 五、配置与产出（指针）

- 配置项（驱动类型 / 序列号 / 显示名 / 备注 / 自动连接）与六个采集参数中
  **哪三项真实生效、哪三项只是配置值**：见《端口与参数》。
- 帧的字段、四个计数（累计收帧 / 待消费 / 溢出丢帧 / 其它丢弃）的口径：见《端口与参数》。
- 监听地址 `0.0.0.0` 的含义与跨机推图怎么填：见《端口与参数》。

## 六、口径速记

- **"打开"永不失败**（驱动侧无动作）；"开始采流"同理。真正的成败看**状态与计数**，不看按钮返回值。
- **掉线判定 = 心跳超时**，判掉线时状态回到 `Connecting` + 清空队列 + 计入丢弃，日志写
  "已 X.Xs 未收到心跳，等待设备恢复（已清空 N 帧陈旧图像）"。心跳恢复后自动回到在线/采流，不需要人工干预。
- **推帧被拒不刷屏**：同一原因连续出现只在**原因变化时**记一条日志（客户端按 33 帧/秒持续推，
  逐帧记会把第一条有用的淹掉）。看日志时注意"第一条拒绝原因"才是根因。
- **本驱动不关收图服务**：那是全局资源，停一台相机不能影响别的相机与流程。
- **序列号必须逐字唯一**：重复时按序列号取图只命中先注册那一台，另一台的心跳与帧会打错目标。
- **一帧只被消费一次**：两个采集步骤选同一台会互相分抢帧，需要同一帧多处使用请往下游传 `Image`。
