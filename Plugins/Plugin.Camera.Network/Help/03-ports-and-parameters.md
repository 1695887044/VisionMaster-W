# 网络相机（虚拟）· 端口与参数

> 分类：相机 ｜ 来源：插件 Plugin.Camera.Network

本页给实名、真实默认值、状态码与"这一项到底生不生效"。概念与上手见《网络相机（虚拟）》，
现象对号见《排错》。

## 一、它没有流程端口

本插件是**相机驱动**（工具箱分组「相机」），不是算子：没有 `InputPort` / `OutputPort`，
也不出现在流程工具箱里。它对外的三个面是——契约成员（宿主调用）、方案里的配置字段、服务侧的 `AppConfig.json`。

| 契约成员 | 谁调 | 语义 |
| --- | --- | --- |
| `Open()` / `Close()` | 相机设置「连接」/「断开」、自动连接 | 打开**永不失败**（驱动侧无动作）；打开的实质是宿主收图服务开始接受该序列号的帧 |
| `StartStream()` / `StopStream()` | 「开始采流」/「停止采流」 | 停流后收帧闸门关闭：送来的帧一律被拒并计入丢弃，队列同时清空 |
| `PushFrame(frame, out error)` | 宿主收图服务（**不是**本驱动） | 入队前校验帧自洽、回填身份与帧号、把状态推进到 `Streaming` |
| `NotifyAlive()` | 宿主收图服务（收到心跳时） | 把"活着"的证据写进看门狗时钟；`Connecting` 状态据此往前推 |
| `WaitNextFrame(out frame, timeoutMs, ct)` | 「图像采集 · 相机采集」 | **消费**：出队，一帧只被取一次；`timeoutMs` 填 0 或负数 = 用相机配置里的 `FrameTimeoutMs` |
| `TryGetLatest(out frame)` | 预览 | **只读**：`Peek`，不吃生产帧 |
| `ApplySettings(settings)` / `ReadSettings()` | 参数面板 | 见第三节"生效矩阵"：三项真生效、三项只落盘 |
| `State` / `StateDetail` | 界面与采集步骤文案 | `Closed` / `Connecting` / `Online` / `Streaming` + 一句话说明 |
| `ReceivedFrameCount` / `PendingFrameCount` / `OverflowCount` / `DroppedFrameCount` | 计数与超时文案 | 溢出与丢弃**分开计数**；`ResetCounters()` 只清后两项（累计收帧与帧号不重置） |
| `Dispose()` | 方案关闭 / 退出 | 幂等；**不关收图服务**（全局资源） |

## 二、方案里的配置字段

| 字段 | 界面叫什么 | 口径 |
| --- | --- | --- |
| `SerialNo` | 序列号 | **寻址键**：客户端 URL 里 `{序列号}` 那一段。比较忽略首尾空格与大小写，其余一位都不能差 |
| `DisplayName` | 显示名 | 不参与寻址；改名不会让客户端失联 |
| `DriverTypeKey` | 驱动类型 | 选「网络相机（虚拟）」——它的接入方式是**手填序列号**，不是"搜设备"（虚拟相机没有枚举） |
| `Remarks` | 备注 | 纯展示 |
| `AutoConnect` | 自动连接 | 方案加载即开始"等待客户端接入"，配合客户端开机自启 |
| `Settings` | 采集参数 | 见第三节 |

## 三、采集参数生效矩阵（本驱动最容易误解的一张表）

| 参数 | 默认 | 对本驱动 | 说明 |
| --- | --- | --- | --- |
| `FrameTimeoutMs` | 3000 | **生效**（基类消费） | 消费端"等一帧最多等多久"。小于 1 归一到 3000。**永远不允许无限等**：相机不触发时流程线程会永久卡死、现场只能杀进程 |
| `BufferCapacity` | 8 | **生效** | 环形队列容量，满则丢最旧并计溢出。太小易丢帧，太大会掩盖"产能不匹配"并把延迟越积越大 |
| `HeartbeatTimeoutMs` | 3000 | **生效** | 多久没有"还活着"的证据就判掉线。看门狗检查频率取该值的 1/3、夹在 200~1000 ms；小于 200 归一到 3000。客户端心跳每秒一次，所以这个值**不要低于 2000** |
| `ExposureTimeUs` | 10000 | **不生效** | 曝光由客户端（那台"假相机"）决定，软件侧没有下发通道。改这里只影响配置落盘与回显 |
| `Gain` | 0 | **不生效** | 同上 |
| `TriggerMode` | `Software`（本仓 C# 枚举成员） | **不生效** | "什么时候出一帧"完全由客户端的推送节拍决定 |

> 曝光 / 增益 / 触发这三项"设了不生效"是有意为之：`ApplySettingsCore` 仍返回成功，
> 因为配置确实被正确保存了——若返回失败，用户在界面每改一次就报一次错，那是纯粹的自欺。
> 但界面上必须按这张表理解它们。

**归一化规则**（`CameraSettings.Normalized()`，基类在应用前执行）：

| 条件 | 结果 |
| --- | --- |
| `BufferCapacity` 小于 1 | 置 1 |
| `BufferCapacity` 大于 1024 | 置 1024 |
| `FrameTimeoutMs` 小于 1 | 置 3000 |
| `HeartbeatTimeoutMs` 小于 200 | 置 3000 |

## 四、服务侧配置（不在相机里，在全局 `AppConfig.json`）

| 键 | 默认 | 口径 |
| --- | --- | --- |
| `NetworkCameraServer.Enabled` | `true` | 关掉就完全不监听，网络相机这一类相机**整体无法工作**；现场只用真机时可以关，省一个端口 |
| `NetworkCameraServer.Host` | `0.0.0.0` | `0.0.0.0` = 听所有网卡，**不能当客户端的目标地址**；相机设置界面会转成"本机IP"提示。跨机推图就填这台工控机的实际 IP；双网卡只想收视觉网那侧时把 `Host` 改成该网卡的实际 IP |
| `NetworkCameraServer.Port` | `19100` | 只在 1~65535 区间内被采纳，否则回落默认值。刻意与网络推送通道的 `19000` 错开；改了要重启软件让服务重新监听，客户端 URL 也要跟着改 |
| `NetworkCameraServer.Token` | `visionmaster` | 源码里就写着这个占位值，**只防误连、不是安全防线**；投用前改掉（服务启动时会记一条 Warn 提醒） |

## 五、客户端请求契约（逐字）

| 项 | 值 |
| --- | --- |
| 推帧 | `POST /camera/{序列号}/frame` |
| 心跳 | `POST /camera/{序列号}/heartbeat`（**无请求体**，每秒一次） |
| 鉴权头 | `Authorization: Bearer {Token}`（令牌按**逐字**比较，不忽略大小写） |
| 可选头 | `X-Image-Name: 文件名`（只用于日志与界面回显，写进帧的 `SourceName`） |
| 请求体 | 图片文件字节（jpg / png / bmp / tif…）。**不是** base64、**不是** multipart、**不是** raw 像素 |
| 序列号编码 | URL 里的序列号会被做一次反转义（`Uri.UnescapeDataString`）后 `Trim`。中文/空格需要转义，**现场建议只用字母数字与短横线** |

## 六、回包

| 情形 | 状态码 | 正文 |
| --- | --- | --- |
| 推帧成功 | 200 | `success` / `serial` / `frameId` / `received` / `pending` / `overflow` / `bytes` |
| 心跳成功 | 200 | `success` / `serial` / `state` / `received` / `pending` / `overflow` / `dropped` |
| 失败 | 400 / 401 / 404 / 409 | `success:false` + **`message`**（原因就在 message 里） |

| 状态码 | 含义 |
| --- | --- |
| 400 | 请求体为空 / URL 缺序列号 / 图片解码失败 |
| 401 | 令牌不对（或缺 `Authorization` 头） |
| 404 | 序列号不在方案里（message 会列出"当前已配置：…"）；路径写错也落 404 |
| 409 | 帧被拒绝：相机未打开 / 已停止采流 / 帧数据不自洽 / 设备已释放 |

## 七、产出：这台虚拟相机的帧队列

| 项 | 说明 |
| --- | --- |
| 帧 | 宽 / 高 / 通道数（1 = 灰度，3 = 彩色 BGR 交错）/ 像素字节（行优先**无填充**，单行字节数 = 宽 × 通道）/ 帧号（本机从 1 自增）/ 采集时刻 / `SourceName`（客户端声明的 `X-Image-Name`） |
| 状态与一句话说明 | `Closed` / `Connecting`（等待接入或判掉线）/ `Online`（客户端在但没送帧）/ `Streaming`（正在收帧） |
| 累计收帧 / 待消费 | 前者"这台一共进了多少帧"，后者"队列里还压着几帧"——采集步骤的 `ReceivedCount` 与超时文案里的计数就是它们 |
| 溢出丢帧 / 其它丢弃 | 两个数分开：**溢出 = 处理不过来**（质量事故，必须查）；**丢弃 = 掉线或停止时清掉的陈旧帧**，以及入口校验被拦下的帧 |

## 八、与「图像采集」的衔接

- 采集步骤按**序列号**引用这台（`CameraSerial`），方案里存序列号而非显示名。
- 采集步骤的**取图超时**端口（`FrameTimeoutPort`）填 0 或负值即回落到相机配置里的 `FrameTimeoutMs`。
- 与本驱动相关的输出有 `FrameId` / `ReceivedCount` / `SourceSerial`；完整端口表见「图像采集」手册。
- 帧的 `Timestamp` 若客户端没声明时刻，由基类补成"入队那一刻"（`DateTime.Now`），
  所以它表达的是"主软件收到它的时刻"，不是客户端快门时刻。

## 九、常见问题

**Q：为什么三项参数设了不生效，还返回成功？**
见第三节末尾那段说明：配置确实被正确保存了。真要影响这台"相机"行为的是
推送间隔（客户端设）、取图超时、队列容量、心跳超时。

**Q：队列容量该给多大？**
默认 8 适合"节拍均匀、处理时间稳定"的场景。加大只是把"处理不过来"从丢帧变成延迟，
并掩盖真问题；现场应该先减处理链或降推送频率。

**Q：心跳超时可以填 500 ms 让掉线判得更快吗？**
不行——检查频率被夹在 200~1000 ms，而客户端心跳是每秒一次，500 ms 必然误判。
要更快判掉线，得让客户端提高心跳频率，两边一起改。

**Q：多个客户端能往同一序列号推吗？**
协议不拦，但队列只有一份：帧会交错进来，帧号由主软件统一自增。要区分来源就配多个序列号。
