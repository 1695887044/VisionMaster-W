# 坐标变换 · 变换口径与标定消费

> 分类：定位 ｜ 来源：插件 Plugin.PoseTransform

这一页讲**为什么这么算**：两种模式各自的作用对象与方向、坐标到底属于哪个系、
标定数据怎么被消费、以及四类失配为什么这样设计。遇到"值算出来了但不对"的时候，答案基本都在这一页。

## 一、位姿跟随：刚体变换只作用在区域上

一条公式，两个算子：

```
vector_angle_to_rigid(模板参考点, 0°  →  当前位姿, θ)   → HomMat2D      // 模板坐标系 → 当前坐标系
affine_trans_region(基准 ROI, HomMat2D, "nearest_neighbor")            → 当前坐标系下的 ROI
```

- **基准 ROI 的坐标属于模板坐标系**（公式从"模板参考位姿"出发），所以它**必须画在模板/学习图上**。
  这是本插件最重要的一条口径，也是最多的错：画在别的图上 → 基准本身就偏 → 跟随结果**系统性偏移**
  （每次都偏一样的量，看起来像"算法不准"，很容易去找错地方）。
- **模板参考点**是"模板坐标系里，位姿原点落在哪个像素"。默认由**基准 ROI 中心**派生；
  中心不是位姿原点时才关派生、手工指定（例：ROI 偏在工件一角、真正的原点是吸盘中心）。
- `nearest_neighbor` 是最近邻栅化：刚体变换不缩放，所以**跟随前后面积守恒**（正视平面下差异接近 0%）。
  这一条既是不变量也是诊断工具——面积差明显，说明**位姿来源可疑**，而不是变换算错。

### 自检法（一句话判"接线对不对"）

喂一组**模板态**位姿：位姿 = 模板参考点、角度 = 0。此时变换是恒等的，
跟随 ROI 必须与基准 ROI **完全重合**（画面上橙框与绿框重叠、面积差 0）。
不重合就只有两种可能：基准 ROI 画错了图，或模板参考点不是位姿原点。

## 二、对齐图：区域和图的作用方向**互逆**

勾了「输出对齐图」时，公式是**反过来**的：

```
vector_angle_to_rigid(当前位姿, θ  →  模板参考点, 0°)    → HomMat2D      // 当前坐标系 → 模板坐标系
affine_trans_image(当前图, HomMat2D, "bilinear", "false")               → 对齐回参考位姿的图
```

为什么反着来：**区域活在模板坐标系、图活在当前坐标系**，同一个变换对两者的作用方向天然相反。
区域要"从模板走到当前"（正变换），图要"从当前搬回模板"（逆变换），这才叫对齐。

⚠ 如果对图也用正变换，内容会被推离参考位姿**两倍偏差**——现象看着像"跟反了/接错上游"，
实际是方向问题，这是本插件实现过程里真踩过的坑。

出界部分填黑，画幅不变（`"false"` 表示不自动扩幅面，输出与输入同尺寸）。

## 三、和「模板匹配」对齐图的分工（选型表）

| 维度 | 「模板匹配」的 `AlignedImage` | 本插件「位姿跟随」 |
| --- | --- | --- |
| 做什么 | 把目标**重采样**成标准位姿的**新图** | **保留原图坐标**，只变换 ROI / 点 |
| 代价 | 每帧一次图像重采样（插值损失 + 内存拷贝） | 只变换区域（轻） |
| 适合 | 内部 ROI 固定的算子：卡尺 / 颜色 / OCR | `Blob 缺陷检测.MaskRegion`、机器人引导、多特征测量 |
| 不适合 | 引导场景（重采样把原图坐标映射丢了） | 卡尺 / 颜色 / OCR（它们的内部 ROI 目前不能被位姿驱动） |

口诀：**要原图坐标 / 做引导 → 本插件；要喂"内部 ROI 固定"的算子 → AlignedImage。**
已经有 `AlignedImage` 时不必在这里再开对齐图，两者等价，只是多一次重采样。

## 四、像素→机械：矩阵怎么作用、方向谁来管

契约语义（与「标定」插件共用，写在 `CalibrationTransform` 的契约注释里）：

```
Matrix = [a11 a12 a21 a22 a31 a32]            // 六元，映射 (Row, Col) → (X, Y)
X = a11·Row + a12·Col + a31
Y = a21·Row + a22·Col + a32
```

**轴交换、镜像、旋转全部由矩阵吸收，本插件不做任何"方向校正"。**
这不是省事，是纪律：这类系统里最难查的一族错误（负负得正）都出在"再手动校正一次"。
所以界面上**根本没有**方向/符号修正的开关。

### 三种可用标定的差别

| 标定类型 | 数据结构 | 点换算 | 角度换算 | 边界行为 |
| --- | --- | --- | --- | --- |
| **九点**（仿射） | 6 元矩阵 | 直接乘 | 全局线性部分（与位置无关） | 无范围限制（外推性质上是仿射延伸） |
| **透视**（投影） | 9 元矩阵 | 投影除法（除以 `w`） | **该点处的局部雅可比**（与位置有关） | `w≈0` 的像素点**明确失败**（那条线上没有对应机械位置） |
| **网格**（分段仿射） | `N×N` 节点 + 规模 | 三角化定位所在三角形 + 重心插值 | 所在三角形的仿射雅可比 | **只在节点覆盖范围内有效，绝不外推**；节点处精确通过 |

两条要知道的：

- **透视下同一个像素角在不同位置会算出不同机械角**——这是数学事实，不是不稳定。
  九点标定没有这个现象（全局线性）。
- **网格的价值是吸收畸变**：全局一个仿射吃不下镜头/斜面畸变，分段仿射能。
  代价是范围外不能用，以及节点数据必须完整（长度与规模对不上就整份判损坏）。
- 网格的三角化/插值实现放在**契约程序集**里，生产端（标定）与消费端（这里）**用同一份代码**——
  两边各写一份会分叉，结果是同一份标定算出两套坐标，而且节点上看不出差异。

### 反向回显是干什么的

换算出机械坐标后，插件**立刻把它反算回像素**，与输入的像素点比较，偏差超过 `1e-6` px 直接失败：

```
反向回显不一致（偏差 …px）：标定矩阵可能已损坏，请重新标定
```

注意它是**自洽性**检查、不是精度检查：标定本身残差再大也不会让它红（残差大是"标定不准"，
回显红是"矩阵数据坏了/实现错了"）。它的价值是让矩阵在存盘、传输、拷贝途中被改坏这种情况
当场露馅，而不是等机器人抓偏了才发现。`PixelEchoRow` / `PixelEchoCol` 就是这个回显结果，现场可以随时抽查。

### 角度换算的配方（不推三角函数）

1. 取图像 x 轴方向 `(Row=0, Col=1)` 经矩阵**线性部分**映射，得基准方向角 φ0；
2. 对象在图像里转了 θ：方向向量 `(Row=sinθ, Col=cosθ)` 同样映射，得 φ(θ)；
3. 机械角 = `φ(θ) − φ0`，归一化到 `(−180, 180]`。

对象没转时严格为 0（这是基准的定义，任何标定都成立）。
含镜像/轴交换的标定让转角**取反**——由矩阵自然给出，不额外修正。

## 五、四类失配：为什么"必须失败"是设计而不是脾气

本插件的立身纪律：**失配必须明确失败，绝不用旧标定或静默恒等变换糊过去**。
四类失配按"发现成本从低到高"排，所以检查顺序也是这个顺序：

| # | 失配 | 触发条件 | 为什么不能放行 |
| --- | --- | --- | --- |
| ① | **未接标定** | `Transform` 为空 | 放行就只能拿像素当毫米用，换镜头/换工作距离整体错 |
| ② | **标定类型不对** | 只有像素当量（`PixelScale`）；或未知类型 | 像素当量没有机械坐标系；未知类型放行等于"静默按旧逻辑算" |
| ③ | **图像尺寸不符** | 接了 `SrcImage` 且 `当前 ≠ 标定时` | 换分辨率/换相机后旧标定**必须自证失效**，否则会算出一个看着合理的错坐标 |
| ④ | **相机身份不符** | 两端序列号都非空且不相等 | 多相机共线时"拿错相机的标定"是静默错位的经典来源，这里让它当场暴露 |

再加三条同源的数据守卫：

- **位姿/像素点守卫**：`NaN`/`Inf` 与"全零"都判无效。
  理由很实在——匹配失败时下游常拿到 `0` 或 `NaN`，而 `(0,0)` 在图像**左上角**，正常目标不可能在那。
  静默变换的产物是"看起来正常的一个错 ROI / 错坐标"，比直接报错难查十倍。
- **标定数据损坏**：矩阵/投影/网格缺失或退化（行列式近零、三角形退化）→ 明确失败并提示重新运行「标定」步骤。
- **回显不一致即失败**：见上一节。

### "不检查"也是一种设计（三处刻意放行）

| 场景 | 行为 | 为什么 |
| --- | --- | --- |
| 没接 `SrcImage` | 跳过尺寸校验 | 离线调试、纯跟随场景不该被强制要求接图 |
| 标定没记录尺寸（两个 0） | 放行 | 无从比对，交给现场核对；报错会让所有历史标定文件全线失败 |
| 序列号任一端为空 | 跳过身份校验 | 单相机/旧标定文件没填序列号是常态，拦下来只会让人把插件删掉 |

## 六、单位与轴口径（对齐现场最容易吵的地方）

| 口径 | 结论 |
| --- | --- |
| 角度 | 插件侧**一律度**。弧度只在调 HALCON 时出现，界面上永远不会看到弧度值 |
| 上游匹配给的角度 | 「模板匹配」也是度，**直接接**，不要自己换算 |
| 像素轴顺序 | 先 `Row`（垂直）后 `Col`（水平）——端口名就按这个排的 |
| 机械轴对应关系 | 由标定矩阵决定（`X`/`Y` 谁对应哪个方向、是否镜像、是否有旋转），**插件不参与** |
| 机械角与像素角符号 | **可以不同**（含镜像/轴交换的标定属手性翻转，由矩阵自然吸收） |
| 面积单位 | `px²`（栅化后按像素计），跟随前后应当守恒 |

## 七、一期不做什么（避免误期）

- **单目标**：所有点/角度端口都是 `double`，与上游严格同类型。
  多目标请放**多个本步骤**，各自接一对像素点。（硬凑数组类型会在运行期静默拿不到值，比多放几步贵得多。）
- **不驱动算子内部 ROI**：卡尺、颜色、OCR 自己配置的检测区域不受位姿影响——这类需求走 `AlignedImage`。
- **不做标定**：标定是「标定」插件的事，这里只消费它的结果。界面上也没有手填矩阵的入口。
- **不做方向校正**：见第四节。
- **不做多帧平均/滤波**：同一输入同一输出，幂等、无阻塞、无取消分支。
