# 坐标变换 · 开发：不变量与陷阱清单

> 分类：定位 ｜ 来源：插件 Plugin.PoseTransform ｜ 读者：开发

**改这个插件前逐条对照**：每条写成"症状 → 机理 → 守门断言名"。
分两组：**A 组违反会当场编译错误或闸门红**（好查），**B 组违反不报错、只出诡异现象**（难查，历史真踩过）。

守门断言全在 `FlowCanvasChecks\PoseTransformChecks.cs`（`Run()` 一个方法，内部分五节：
**数学层** `:36` / **HALCON 层** `:142` / **插件层** `:193` / **透视标定联动** `:415` / **网格标定联动** `:535`），
共 **62 条 `Check(`**，名字全部以 `[PT]` 开头，可按名反查。

---

## A 组：违反会当场红或抛

**A1 两个模式的所有失败出口都必须走 `Fail(...)` 并 `return`**
本插件的立身纪律是"失配必须明确失败，绝不糊过去"。四类标定失配 + 位姿/像素点守卫 + 回显不一致 + HALCON 异常，
少一个 `return` 就是**继续往下跑并写端口**——下游拿到机械坐标，值还是错的。
症状：现场"抓偏了"，但 `Success` 是 `true`、`ErrorMessage` 只有一行没人看的日志。
守门：`[PT] 插件级失配①未接标定 → 失败且文案含「标定」下一步`、`[PT] 插件级失配②当量标定当九点用 → 失败且指到「九点标定」`、
`[PT] 插件级失配③图像尺寸不符 → 失败且报「重新标定」与两个尺寸`、`[PT] 失配④相机身份不符 → 失败、两台相机都在文案里`、
`[PT] 空 ROI → 失败（不静默输出空区域）`、`[PT] NaN 位姿 → 失败（防匹配失败被静默变换）`、
`[PT] 位姿全零（未接/匹配失败）→ 失败并说明原因`。

**A2 `CheckCalibrationUsable` 的 `switch (t.Kind)` 必须穷尽且 `default` 拒绝**
未知 `Kind` 落 `default` → `不支持的标定类型（{Kind}）：请升级软件或重新标定`。
症状：契约那边新增一种标定模式、消费端忘了补 `case`，C# 不会报错（`switch` 表达式才有穷尽检查，语句没有），
未知标定被**静默按九点走**、拿 `Matrix` 去映射一个根本没有 `Matrix` 的对象。
守门：`[PT] 未知 Kind=(CalibrationKind)7 → 拒绝（防「忘记分支」静默按旧逻辑放行）`。

**A3 只有 `NinePoint` / `Perspective` / `Mesh` 能换算，`PixelScale` 必须拒绝**
像素当量模式没有机械坐标系，`X/Y` 无从谈起。
症状：不拦就是"用像素当量标定当九点用"，输出的"机械坐标"其实是像素号，机器人按它走会撞机架。
守门：`[PT] 失配①未接标定 → 失败并指到「标定」插件`、`[PT] 失配②当量标定当九点用 → 失败并指到「九点标定」`、
`[PT] 矩阵缺失/退化 → 失败并指到「重新运行标定」`（后两条是**数学层**判据，与 A1 那批**插件层**判据成对：
判据若在数学层被改掉，插件层那批会跟着红；两层都留判据是因为"函数单测过、接线后不生效"这类问题只有一层抓不到）。
（`[PT] 失配②当量标定当九点用 → 失败并指到「九点标定」` 与 `[PT] 失配②文案同时含「九点」与「透视」（旧断言依赖「九点」不丢）`
同时是**文案关键词契约**：老断言靠"九点"两个字匹配，改文案时漏掉它就红，另见最后一行的移植清单。）

**A4 跟随分支里绝对不许插标定校验**
`FollowRoi` 与标定**完全解耦**——公式只吃参考点 + 位姿。
症状：有人"顺手"在 `RunFollowRoi` 开头加一句 `CheckCalibrationUsable`，纯跟随链路（不接标定）当场全线失败。
守门：`[PT] FollowRoi 与标定类型解耦：九点/透视输出完全一致、不接标定照常成功`。

**A5 `PoseTransformMath` 必须零 HALCON 依赖**
这一层的存在理由就是"断言可直接构造输入跑，不依赖引擎"（`PoseTransformMath.cs:7`）。
症状：往这层塞一句 `HOperatorSet` → 数学层 16 条断言从"纯托管"变成"要 HALCON 环境"，
环境缺时整节静默跳过，等于把最便宜的一层守门费扔了。
守门：数学层全部 16 条——起于 `[PT] 正变换按契约展开（(100,200) → (110,220)，手算常量）`、
止于 `[PT] 像素点守卫：(0,0)/NaN 必须失败（与位姿守卫同口径）`——都要能在无引擎条件下给出确定数值。

**A6 `Dispose()` 末尾必须 `base.Dispose()`，且标志位先于释放**
基类那一份回收**输出端口**承载的 `HRegion`/`HImage`；本插件那一份回收 `_previewImage` 与 `DisplayImage`。
`Dispose` 顺序固定：`_viewAttached=false` → `_disposed=true` → `_previewLoadId++` → `DisplayImage=null` → `SetPreviewImage(null)` → `base.Dispose()`。
症状：先放对象后置标志 → 还在路上的 `PostToUI` 回程把图**写回已关的窗口**（`ObjectDisposedException`，且是概率性的）；
漏 `base` → 端口值泄漏；漏 `_previewLoadId++` → 在途预览载入落在已释放实例上。

**A7 `RefreshOverlay` 的中间 HALCON 对象必须全部登记进 `temp` 并在 `finally` 释放**
`CopyImage` / `Compose3` / `GenContourRegionXld`×2 / `PaintXld`×3 / `GenCrossContourXld` 全是新对象，`PaintXld` 每画一层出一个新图。
症状：漏一个就是"开一次配置对话框、试运行时几十次 → 几百 MB"。`finally` 里**单个释放失败不许阻断后面的**（`catch { }`）。
守门：叠加预览只在 `_viewAttached` 时刷，所以运行链上没有常驻分配；本条靠代码评审 + A8 的 `DisplayImage` 换图释放兜住量级。

**A8 `DisplayImage` 的 setter 必须 `old?.Dispose()`**
换图即释放前一份叠加副本。
症状：漏了 → 每次刷新漏一幅整图（叠加图是 RGB 三通道，比灰度图还大三倍）。
判据细节：`if (ReferenceEquals(old, value)) return;` 要在 `SetProperty` 之前先抓住旧引用，
`SetProperty` 返回 `true` 才 `old?.Dispose()`（属性已换成新值，旧值只剩 `old` 这一个引用）。

**A9 构造期绝不碰 HALCON 原生库**
`new PoseTransformPlugin()` 之后 `DisplayImage` 必须是 `null`（预览载入只由 `Initialize` / 属性钩子触发）。
症状：构造函数里就生成叠加图 → 断言宿主、工具箱装配、流程反序列化全部被 HALCON 拖住。
守门：`[PT] 构造后 DisplayImage 为 null（构造期不碰 HALCON 原生库）`。

## B 组：违反不报错，只出诡异现象（历史上真踩过）

**B1 double 输出端口没人清零 → 失败轮读到上一轮的好值**
基类 `AutoDisposeRoundOutputs` 只回收 `IDisposable` 型输出，`double` 端口原样留着。
症状：本轮"未接标定"失败了，`MechanicalX` 仍是上一轮的 `405`，机器人照着抓——**而且 `Success=false` 藏在另一层**。
机理：`RunAlgorithm` 第一件事就是 `MechanicalX/Y/Angle` + `PixelEchoRow/Col` 五个归零；
中途失败（含角度换算失败）时端口保持这五个 0。
守门：`[PT] 角度换算失败 → 五个标量端口全部为 0（不留半成品值）`、
`[PT] 角度断开/归零 → MechanicalAngle 复位为 0（不残留上一轮）`（后者还要先跑一条前置断言 `[PT] 角度有值 → MechanicalAngle 已输出（前置条件）`——
没有前置那条，"现在是 0"可能是"从来没给过"，**假通过**）。

**B2 `Success`/`ErrorMessage` 不在 `RunAlgorithm` 里预置 → 假红/假绿**
断言与试运行可以**绕过 `Execute` 直接调 `RunAlgorithm`**，此时基类的预置不会发生。
症状：上一轮失败留下的 `ErrorMessage` 被当成本轮错误（假红），或 `Success` 停在上一轮的 `true`（假绿）。
守门：`[PT] 插件级成功：机械坐标 = 手算 (405,307)，Success=true` 与全部插件级失败断言同时看 `Success`，
任何一侧的预置缺失都会让这一批成对变红。

**B3 `MechanicalAngle` 的"接了才输出"判据必须含 NaN**
`hasAngle = PixelAngle.LinkedSource != null || pixelAngle != 0.0 || !double.IsFinite(pixelAngle)`。
症状：少了第三个条件，上游给 NaN 时 `pixelAngle != 0.0` 虽然为真，但**"未接且值为 0"与"值为 NaN"在日志里长得一样**，
NaN 被静默当成"没接"跳过 → 机械角保持 0、`Success=true`、机器人转了个寂寞。
机理：带 NaN 是为了让"值为 NaN"必须进换算、进而在 `TryPixelAngleToMechanical` 里**明确失败**。
守门：`[PT] 像素角度未接 → MechanicalAngle 不输出（保持 0，不瞎给）`（只判"未接且为 0"那一支）、
`[PT] 像素角度接了 → MechanicalAngle ≈ 30°（保向标定原样映射）`。

**B4 对齐图用正变换而不是逆变换 → 内容被推离参考位姿**
区域活在模板坐标系、图活在当前坐标系，**同一个变换对两者的作用方向互逆**：
区域用正变换 `T`（模板→当前），图必须用逆变换 `T⁻¹`（当前→模板）才叫"对齐"。
`PoseTransformHalcon.FollowImageBack` 里 `VectorAngleToRigid` 的两个三元组是**反着排**的
（`(poseRow, poseCol, θ) → (templateRefRow, templateRefCol, 0)`）。
症状：对图也用 `T` → 目标被推到参考位姿**两倍偏差**之外，看着像"跟反了"，很容易误判成位姿接错。
守门：`[PT] 对齐图方向：内容从位姿搬回参考点（T⁻¹，不是推远两倍）`——这条**只有方向错了才红**，
"整幅黑""尺寸变了"都抓不到，别把它当方向无关的兜底。

**B5 `affine_trans_image` 的三个参数顺序**
实测口径：`(HomMat2D, Interpolate, AdaptImageSize)`；`"false"` = 输出与输入**同幅面**（画幅不变、出界填黑）。
症状：把 `"false"` 写成 `"true"` → HALCON 自动扩幅面，跟随 ROI 与对齐图**不再同一坐标系**，叠上去对不齐；
把插值与自适应标志写反 → 传进去的字符串被当插值方法，HALCON 报参数错或直接原样返回。
（`PoseTransformHalcon.cs` 注释指向 `MatchingPlugin.cs:1577` 的同一条踩坑记录。）

**B6 角度不许"再校正一次"**
镜像 / 轴交换的标定让转角**取反**（手性翻转），这是矩阵的自然结果。
症状：负负得正——"看起来对了，实际差一个符号"，是最难查的一族错误。
机理：`TryPixelAngleToMechanical` 用"方向向量作差"（φ(θ) − φ0），全程不推三角恒等式、不做符号修正。
守门：`[PT] 角度：轴交换（反射）→ 转角取反（−30°，由矩阵吸收、不再校正）`、
`[PT] 角度：保向标定下像素 30° → 机械 30°（±1e-3）`、`[PT] 角度：保向标定下像素 −90° → 机械 −90°（±1e-3）`、
`[PT] 角度：像素 0° → 机械 0°（基准定义，任何标定都成立）`、`[PT] 角度归一化到 (−180, 180]`、
`[PT] 轴交换/符号不错位（(100,200) → (405,307)，手算常量）`（最后一条管**点**的符号不错位，与前面管**角**的几条合起来才是"轴交换"这一族的全覆盖）。
⚠ 归一化区间是**左开右闭** `(−180, 180]`：`−180` 会被表成 `+180`，别按 `[-180, 180)` 比对。

**B7 单位换算只许在 HALCON 层做一次**
插件侧、端口、界面、存盘**一律度**；只有 `PoseTransformHalcon` 里 `× Math.PI / 180.0`。
症状：在插件层先转成弧度再传进去 → HALCON 又乘一次 → 转 30° 变成转 0.5°，跟随 ROI 几乎不动，看着像"没生效"。
守门：`[PT] 跟随姿态敏感：转 90° → 外接框宽高互换（41×21 → 21×41，±1px）`——这条对"角度单位错"极敏感
（弧度 90 会转 5156°，宽高互换的判据直接失配）。

**B8 面积守恒：跟随前后 ROI 面积差 ≈ 0**
`affine_trans_region(..., "nearest_neighbor")` 只有栅化取整的微小差异。
症状：面积差明显 → **位姿来源可疑**（接错上游、或上游匹配到了另一件工件），不是本插件算错。
机理：刚体变换不缩放，面积必须守恒；这条既是不变量也是运行期自诊断（成功日志里那行 `基准面积 …px² → 跟随面积 …px²（±X%）`）。
守门：`[PT] 旋转不丢面积（相对差 < 1e-6）`、`[PT] 模板态自洽：位姿=参考点、角度 0 → 与基准 ROI 完全重合（面积相对差 < 1e-6）`、
`[PT] 插件级跟随成功（模板态）：FollowedRegion 有值且与基准重合（相对差 < 1e-6）`。

**B9 模板态自洽是最强的"接线对不对"探针**
位姿 = 参考点、角度 = 0 时变换恒等，跟随 ROI 必须与基准 ROI **完全重合**。
症状：不重合 = 基准 ROI 画在了非模板图上、或模板参考点不是位姿原点。这两条在界面上**没有任何报错**，
只有工件一动就整体偏。
守门：同 B8 三条。

**B10 两个产物必须"全部算成功才写端口"**
`RunFollowRoi` 先在 `try` 里攒齐跟随 ROI 与对齐图，**再**一次性赋端口；`catch` 里把已算出的都 `Dispose`。
症状：边算边写 → 对齐图失败时 `FollowedRegion` 已经是新值、`FollowedImage` 是上一轮的旧图，
"图是 A 位姿、ROI 是 B 位姿"这种组合下游完全看不出来。
守门：`[PT] 对齐图默认关：FollowedImage 未输出` + `[PT] 勾选对齐图 + 接了 SrcImage → FollowedImage 有值`
（两条对照钉住"只在真的算出来时才写"）。

**B11 相机身份校验"两端都非空才查"，不是"任一端非空就查"**
`imageSerial.Length > 0 && calibSerial.Length > 0` 才比对。
症状：改成"任一端为空就失败" → 所有离线调试、单相机现场、**旧标定文件**（没填序列号）当场全线红，
用户只会得出"这个插件加进去就报错"的结论并把它删掉。
守门：`[PT] 上游序列号为空 → 不查身份（离线/单相机不打扰）`、`[PT] 标定未记录序列号 → 放行（旧标定文件不误拦）`、
`[PT] 身份相符（忽略大小写）→ 正常成功（手算 (405,307)）`（同时钉住比较必须 `OrdinalIgnoreCase`）。

**B12 尺寸失配"标定没记尺寸就放行"**
`SourceImageWidth <= 0 || SourceImageHeight <= 0` → 直接 `true`（无从比对，交现场核对）。
症状：改成报错 → 一切历史标定文件（这条字段是后加的）在 `ToMechanical` 上全红。
守门：`[PT] 尺寸相符→通过；标定未记录尺寸→放行（无从比对，不误报）`、
`[PT] 失配③图像尺寸不符 → 失败、两个尺寸都在文案里`（**文案必须同时含两个尺寸**，现场靠这两个数字判断是哪一侧错了）。

**B13 网格不许外推**
像素点或机械点落在 `N×N` 节点围成的区域外 → 明确失败。
症状：外推出来的坐标在范围外**看着完全合理**（连续性很好），机器人到了远处才发现偏得越来越多。
守门：`[PT] 网格外（正向像素 / 反向机械）→ 明确失败（不外推）`（正、反两个方向各判一次，少一支就是半边失效）、
`[PT] 网格损坏（长度不符 / 缺失）→ 明确失败、文案含「网格」与「重新运行「标定」步骤」`。

**B14 网格换算必须走 `CalibrationMesh`，不许在本插件再写一份**
生产端（「标定」）与消费端（这里）**必须同一份三角化/插值实现**。
症状：分叉 = 同一份标定算出两套坐标，且差异只在三角形内部，采样点恰好落在节点上时**看不出区别**。
守门：`[PT] 网格（节点取自同一仿射）：映射与仿射处处一致（< 1e-9，含节点与格内点）`、
`[PT] 网格反向：机械 → 像素 回到原像素（< 1e-9）`、`[PT] 网格角度：与九点角度换算一致（局部雅可比口径正确）`、
`[PT] 插件级网格：机械坐标 = 手算 (103, 54)，Success=true、回显自校验通过`（这条是**从插件层走一遍**的网格：
数学层三条都对但插件没把 `Mesh` 分支接上，只有它会红）、
`[PT] 畸变网格：格内点误差 ＜ 全局仿射的一半（消费侧确实在吸收畸变）`（最后一条是**反向断言**：
它证明网格路线真的在吃畸变，而不是退化成全局仿射——退化了不报错、只是精度没了）。

**B15 透视分母 ≈ 0 必须失败，透视角度必须随位置变**
`w≈0` 的像素点在物理上不存在对应机械位置；投影映射**不是**全局线性，角度必须用**该点的局部雅可比**。
症状：角度用全局线性部分算透视标定 → 同一个 θ 在画面左右两侧算出同一个机械角，
"中心对、边缘偏"，而且偏量小、单点抽检过得了。
守门：`[PT] 透视分母≈0 的像素点 → 明确失败（w=0 线上拒绝；线外点照常映射）`、
`[PT] 透视角度位置相关：J(p) 手算对比（±1e-6）；同 θ 两位置结果不同`（**"两位置结果不同"是这条的灵魂**，
只比手算常量的话，一个"常量恰好相同"的错误实现也能过）、
`[PT] 透视正/反变换：手算常量（(250,500)→(315,400)、(0,0)→(30,−75)；互逆 < 1e-9）`、
`[PT] 透视矩阵缺失/退化/长度不足 → 拒绝且文案含「损坏/重新运行标定」`、
`[PT] 插件级透视 ToMechanical：坐标=手算 (315,400)、回显 < 1e-6、机械角=手算`、
`[PT] 尺寸失配（透视）：两个尺寸都进文案；相符放行`。

**B16 反向回不自校验不是装饰**
`TryMapMechanicalToPixel` 再算回像素，偏差 `> 1e-6` 直接 `Fail`。
症状：去掉它 → 矩阵在传输/存盘里损坏（部分元素被改写）时正反两套坐标各自"看着都合理"，
现场只有机器人抓偏才知道。`1e-6` 是**自洽性**判据，不是精度判据——标定本身残差再大也不会让它红。
守门：`[PT] 反向回显 = 原始像素点（自校验端口）`、`[PT] 反向互逆（T⁻¹(T(p)) 误差 < 1e-9）`、
`[PT] 旋转+缩放矩阵的正反互逆（< 1e-9）`。

**B17 端口名与类型是"契约面"，改名 = 静默断线**
12 个输入 + 7 个输出，名字同时是 `.vms` 里 `InputValues` 的键与连线表的引用名。
症状：改个名（例如 `PoseRow` → `MatchRow`）编译照过、界面照开，**已配好的方案里那条连线当场落空**，
端口读默认值 0 → 于是触发 B18 的"全零守卫"、报一条看起来像上游问题的错。
守门：`[PT] 输入端口面齐全（绑定用）`、`[PT] 输出端口面齐全`、`[PT] Transform 端口类型 = CalibrationTransform（接标定插件输出）`、
`[PT] 跟随端口类型 = HRegion / HImage（接 BlobDetect.MaskRegion 与图像下游）`——四条合起来把"名字 + 类型"一起钉住。

**B18 位姿/像素点的 `(0,0)` / 全零守卫不许放宽**
`(0,0,0)` 位姿与 `(0,0)` 像素点都判无效。
理由：`(0,0)` 在图像**左上角**，正常目标不可能在那；而它恰好是匹配失败 / 端口未接时的默认值。
症状：为了"允许真的在角上的目标"而放宽 → 匹配失败时算出一个**看起来正常**的跟随 ROI（恒等或微小变换的产物），
下游 Blob 检出一个空结果，谁都不会怀疑到变换上。
守门：`[PT] 位姿守卫：NaN/全零必须失败、正常位姿通过（防匹配失败被静默变换）`、
`[PT] 像素点守卫：(0,0)/NaN 必须失败（与位姿守卫同口径）`——**两条口径必须一致**，只放宽一侧就会出现"跟随能用、换算不能用"这种解释不动的差异。

**B19 界面提示与运行闸门必须同源**
`RefreshStatus` / `RefreshCalibrationInfo` 调的是同一批 `PoseTransformMath` 判定函数，不是复制一份判断。
症状：复制一份 → 信息栏写"就绪"、试运行报"标定与当前图像尺寸不符"，用户从此不看信息栏。
唯一**有意的差异**：残差阈值 `ResidualRmsPx > 1.0` 只把标定信息块染成橙色、**不影响运行**（阈值本身归「标定」插件把关）。

**B20 `_viewAttached` 关掉后运行期不再刷叠加图**
症状：`RunAlgorithm` 末尾无条件 `PostToUI(RefreshOverlay)` → 对话框早关了还在每轮做一次
`GenContourRegionXld` + 三次 `PaintXld` + `new HImage`，产线跑几小时内存一路涨，且界面上没人看见。
机理：`OnViewDetached` 由视图 `Unloaded` 触发；`Dispose` 里也强制置 `false`（视图异常卸载漏事件时的兜底）。

**B21 `Switch (Mode)` 的 `default` 分支不可删**
`Mode` 落盘是字符串成员名，老方案里可能有当前枚举已不存在的值（`ValueConverter.Convert` 失败时保留默认值，
但**手工改过的 `.vms`** 能把整数塞进来）。
症状：删掉 `default` → `switch` 什么都不做、直接走到末尾，`Success=true`、所有输出保持清零值——
"步骤成功但什么都没算"是最难归案的一种现象。
守门：`未知模式：{Mode}（请重新选择模式）` 这条文案目前**只有源码在读**，
新增模式成员时**必须同时加 `case`**，否则老方案的值会从"报错"变成"什么都不做"。

**B22 `[Display]` 的 `GroupName` 决定能不能拖进工具箱**
症状：改了/删了 `GroupName` → 编译全绿、DLL 正常、**工具箱里就是找不到这个算子**（静默消失）。
守门：`[PT] 插件带 [Display]（GroupName=定位，否则工具箱里拖不出来）`。

**B23 模式切换不许清另一种模式的参数**
`OnModeChanged` 只调 `RefreshConfigState()`，**不重置任何端口或配置**。
症状：切模式就清参数 → 用户"位姿跟随"试完想看看"像素→机械"，两边来回切一次，第二边全得重配。
机理：两种模式的输入端口**天然不重叠**（`BaseRegion`/`Pose*` vs `Transform`/`Pixel*`），共存无副作用；
`RefreshCalibrationInfo` 在非 `ToMechanical` 时只是把标定信息块清空，不动数据。

**B24 断言的"跳过"型判据要能被反证**
`FlowCanvasChecks` 里凡是"环境不支持所以跳过"的写法都会给未来的回归留静默放行口（AGENTS.md R38）。
本套断言的对策是把环境依赖压到最低：**数学层 16 条零 HALCON**（A5），只有 HALCON 层与插件层需要引擎；
凡涉及"应该失败"的判据都配一条同族"应该通过"的对照
（`[PT] 失配④相机身份不符 → 失败、两台相机都在文案里` 对 `[PT] 身份相符（忽略大小写）→ 正常成功（手算 (405,307)）`、
`[PT] 失配③图像尺寸不符 → 失败、两个尺寸都在文案里` 对 `[PT] 尺寸相符→通过；标定未记录尺寸→放行（无从比对，不误报）`、
`[PT] 上游序列号为空 → 不查身份（离线/单相机不打扰）` 对 `[PT] 标定未记录序列号 → 放行（旧标定文件不误拦）`），
"闸门本身失效"会让对照那一侧变红。
