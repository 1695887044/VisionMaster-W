# 数据库执行

## 这个步骤做什么

按命名语句执行一条 **UPDATE / DELETE**，返回实际影响行数与耗时。
用于改状态、清队列、批量标记 NG 等"改数据但不需要逐行参数"的场景。

- `AffectedRows`：实际影响行数；
- `ElapsedMs`：本次执行耗时。

## 支持的数据库

SQLite（本地文件）与 MySQL/MariaDB（服务器）。两者步骤配置完全一样；
MySQL 的密码由宿主用 DPAPI 加密保存，`.vms` 不含连接串与密码。

## 前提：语句必须是「执行」类型

在「硬件管理 → 数据库 → 命名语句」里新建语句时，类型选「执行」。
保存时会做三条硬校验：

1. 只允许 `UPDATE` / `DELETE`（`INSERT` 请用「写一行」）；
2. **必须带 `WHERE`**（v1 不做整表操作）；
3. 参数表与 SQL 里的 `@name` 占位符必须一一对应。

`ATTACH` / `DETACH` / 写 `PRAGMA` / DDL 一律拒绝。

## 为什么强制 WHERE

整表更新在生产现场几乎总是误操作：漏了 `WHERE` 一次就把整张结果表刷成同一个值，
而且没有撤销。v1 直接把"无 WHERE"挡在保存期，需要整表操作时请写
`WHERE 1 = 1` 这种显式条件——它至少让"我知道自己在做什么"留下痕迹。

## 影响行数上限

语句上可以设「最大影响行数」（0 = 不限制）。超过上限时：

- 在**事务内回滚**；
- 步骤失败，错误文案写清"影响 N 行 > 上限 M，已回滚"。

宁可不写，也不误删——这是本步骤最重要的一条保护。

## 失败语义

默认 `FailFast = true`：执行失败会抛，步骤变红并中断当轮（停线）。
需要"失败也继续"的现场显式关掉。

只读数据库直接拒绝本步骤：保存语句时就存不进去，配置窗口也会提示。

## 与「写一行」的区别

| | 数据库执行 | 数据库写行 |
| --- | --- | --- |
| SQL | UPDATE / DELETE | INSERT（含 UPSERT） |
| 典型用途 | 改状态、清队列 | 每件结果落一行 |
| 输出 | AffectedRows | Accepted + AffectedRows |
| 失败默认 | 停线 | 停线 |

两者都走"一次调用 = 一个事务"，都不会自动重试。
