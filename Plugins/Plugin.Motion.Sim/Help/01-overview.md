# 产线仿真运动卡（Plugin.Motion.Sim）

## 这个驱动解决什么问题

它把上位机的运动命令送到**另一个进程**里的产线仿真器 `LineSim`（**独立产品、独立仓库**，默认装在 `D:\C#\LineSim`，不在本仓），由仿真世界真正推进轴、工件、IO。
和「虚拟运动卡（仿真）」不是同一件事：

| | 虚拟运动卡 | 产线仿真运动卡（本驱动） |
|---|---|---|
| 世界在哪 | 卡自己肚子里（进程内） | LineSim 进程里（跨进程，TCP 19510） |
| 与视觉的关系 | 无 | 相机拍到的位置 = 轴报的位置 = PLC 读到的位置 |
| 轴数 | 固定 3 轴 / 8 进 / 8 出 | 由仿真器 `hello` 决定（P0 是 3 轴，P2 扩到 44 轴 / 192 IO） |
| 用途 | 验命令队列、门禁、看门狗、故障注入 | 验**整条产线闭环**：定位引导、触发时序、多工位协同 |

一句话：**虚拟卡证明"上位机自己的逻辑对不对"，本驱动证明"上位机与产线对得上"**。两者都要，不能互相替代。

## 三条不可让步的语义

写这个驱动最容易犯的三个错，每一个都会让"仿真通过"变成假绿：

1. **下发 ≠ 到位**。`enqueue` 只回答"收下了吗"，不回答"做完了吗"。轴什么时候到位由仿真器的 1ms tick 决定，
   上位机只能靠 `poll` 看。驱动绝不把 `accepted` 当成 `Done`——那样 Move 会瞬间"完成"，
   而真实产线上"两条轴同时下发、实际串行"的时序问题就永远测不出来。
2. **位置只来自 poll**。驱动不在本地维护位置、不做插值、不猜轨迹。一旦本地补算，
   上位机看到的轨迹就与相机拍到的、PLC 读到的不是同一条，闭环验证失去意义。
3. **轴数与 IO 数由仿真器决定**。驱动不写死 3 轴 8 点：`hello` 回多少就是多少。
   这样 P2 把世界扩到 44 轴 / 192 IO 时，驱动一行都不用改。

## 用之前要准备什么

1. 启动仿真器：`tools\LineSim\bin\Debug\net9.0-windows\LineSim.exe --serve`（默认运控口 19510）。
2. 在「运动卡」里新增一张卡，驱动选**产线仿真运动卡**，地址填 `127.0.0.1:19510`。
3. 流程里先放「轴使能」，再放「轴回零」——仿真器自报**增量式编码器**，
   连上后位置不可信，不回零的运动命令会被拒绝（这与真机一致，不是仿真器的怪癖）。

## 你会看到什么

- 卡状态 `Online`，说明里带 `tick` 与工件数（每秒几十次刷新，说明文字只在变化时更新）。
- 轴状态快照：位置、速度、到位、运动中、使能、正负限位、原点、报警。
  这些值全部来自仿真器，`Timestamp` 由基类在回填时打上位机本地时间。
- 数字输入：由仿真世界按轴位置真推导（例如滑台到位就置位对应传感器），不是随便翻转的假信号。

## 明确不做什么

- **不做多轴插补**：契约层 `MotionTypes.cs` 明说插补"第一期只留枚举位置、不实现"，
  仿真器也没有插补通道。要验插补得先改契约，那是另一个工程。
- **不替代真实驱动**：它没有跟随误差、没有伺服整定、没有编码器噪声。
  它能证明"时序与坐标对得上"，不能证明"真机跑得动"。
- **不改上位机契约**：驱动只实现 `MotionDeviceBase` 的四个抽象成员，
  没有新增接口、没有新增配置类型（端点走 `MotionDescriptor.Address`）。
