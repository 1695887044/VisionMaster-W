# 图像采集 · 四种模式上手与对外接口

配合上一页（端口 / 参数 / 失败口径）使用。本页按模式给出**逐步操作**，并给出两条 HTTP 通道的接口速查表。

## 一、通用操作

1. 流程里拖入「图像采集」→ 双击（或右键「模块参数」）打开配置窗口：左表单、右预览与信息栏、底部状态。
2. 「基本参数 → 采集模式」四张卡片选一：**指定图像 / 文件目录 / 网络推送 / 相机采集**。
   换模式会清空预览并重新校验（旧模式的数据源在新模式下对不上号，留着只会让界面自相矛盾）。
3. 「图像参数 → 显示窗体」选目标窗口（`图像窗口1~9` / `不显示`，默认窗口 1）。
4. 点窗口底部**「执行」试运行**——跑的就是正式运行的同一段代码，信息栏那句话就是最可靠的自检结果。
5. 「确定」写回步骤（只写内存；方案要长期生效仍需保存）。

信息栏的即时校验口径（边改边提示）：空值 = 橙字"请选择…"；路径不存在 = 红字；
端口已被变量链接 = 不校验、给中性说明（路径运行期才产出）。

## 二、指定图像（调试 / 单图复现）

1. 「图像路径」：双击下划线区域浏览选图（扩展名白名单 `.bmp .jpg .jpeg .png .tif .tiff`），或点 🔗 链接上游变量。
2. 右侧预览立刻显示该图；「执行」后信息栏形如 `已加载图像: {路径} ({宽}x{高})`。
3. 输出口关注：`Image`、`CurrentPath`（就是这条路径）、`TotalFiles` 恒为 1、`CurrentIndex` 恒为 0。

常见失败：路径为空 / 文件不存在 / HALCON 读不了该文件（扩展名在名单内但内容损坏）——都会明确失败，不会退回旧图。

## 三、文件目录（离线批处理 / 序列回放）

1. 「文件夹路径」浏览选择；「文件索引」填 0 基索引（或 🔗 链接上游计数变量）。
2. `◀ ▶` 翻页、`刷新预览` 重扫目录；"当前文件：xxx（共 N 张）"随索引更新。
3. 排序是**自然序**（`img2` 在 `img10` 之前，与资源管理器一致）：文件索引直接对应工件顺序，**排序错 = 顺序错**。
   实现刻意不做区域/文化敏感比较——同一台设备上排序必须永远稳定。
4. 运行期**每轮重新枚举**：新增的文件当轮就能读到、删掉的不再占索引。
5. 索引越界会**夹取**并在结果文案里留痕：`已加载图像 [i/N]: {路径}（索引 X 超出 0~N-1，已夹取）`。

常见失败：目录不存在；目录内没有匹配扩展名的文件（`TotalFiles` 报 0）。
子目录**不递归**——需要分目录跑就把索引做成变量、或一个目录配一个采集步骤。

## 四、网络推送（外力推一张、流程跑一次）

**这个模式不需要添加任何相机**，图由外部程序推给宿主收图服务，本步骤从**本流程的图像槽**里取走那张图。

配置页会当场告诉你三件事：
- 服务状态：绿 = "宿主收图服务正在监听 {主机}:{端口}"；橙 = 未监听并给原因
  （`AppConfig.json → HttpImageServer.Enabled=false`，或配置为启用但端口被占用/启动失败）。
- 接口说明四行（URL 形态、鉴权头、配置位置、并发约束）。
- **推送测试**：流程名（预填当前流程，可故意改成不存在的名字验 404）、主机、端口、令牌（可故意填错验 401）
  → 「选择本地图片并推送测试」= **真发一次 HTTP 请求**（走的就是外部相机/PLC 那条路，测通了才算真通）。
  推送前会先把界面上改过的配置写回步骤，所以本次跑的就是你看到的配置。
  结果区给出：`HTTP 状态码 + 客户端耗时`、流程名、图像 `宽x高x通道`、服务端耗时、输出摘要或错误原因。

**接口速查（Hub 通道）**

| 项 | 值 |
| --- | --- |
| 地址 | `POST http://{Host}:{Port}/flow/{流程名}?outputs=步骤名.端口名`（`outputs` 省略 = 回传全部步骤的全部输出端口） |
| 鉴权 | `Authorization: Bearer {Token}`；默认占位令牌 `visionmaster`，投用前必须改 |
| 请求体 | **图片文件原始字节**（非 multipart、非 base64）；可选头 `X-Image-Name: 文件名`（回传为 `CurrentPath`，缺省为 `hub://{流程名}`） |
| 成功回包 | JSON：`success / requestId / flow / elapsedMs / image{width,height,channels} / outputs`；失败 `{success:false, message}`（**原因在 message**） |
| 错误码 | 401 无/错令牌；404 未知流程；400 空 body；409 流程正在运行（同一流程串行）；504 等待结果超时（**不打断流程**，后台继续跑完） |
| 语义约束 | 一次 POST = 推一帧 + 单次执行；图像槽**只留最新一帧**，每槽上限 8 帧、满则丢最旧 |
| 配置位置 | `AppConfig.json → HttpImageServer`：`Enabled` / `Host`（`0.0.0.0` = 所有网卡，客户端要填实际 IP）/ `Port`（默认 19000）/ `Token` / `RequestTimeoutMs`（默认 30000，一般取现场流程最长耗时的 2~3 倍；本期无配置 UI） |
| 客户端超时 | 必须**大于**服务端等待上限（本插件的推送测试按 `RequestTimeoutMs + 5000` 设），否则服务端还在跑、客户端先断，"超时"分不清是流程慢还是网络断 |

流程侧行为：槽里有图 → 直接取（HTTP 链路的正常路径，零等待）；槽空 → **阻塞等待**新图（日志"槽内暂无图像，开始等待网络推送…"），
点「停止流程」可打断（收尾文案"已停止等待网络图像"，属取消、不是故障）。

## 五、相机采集（产线连续采图）

1. **先配相机**：「系统 → 相机设置」→ 选驱动类型（如「海康相机」「网络相机（虚拟）」）→ 填**序列号** → 连接 → 开始采流。
   真机与虚拟相机的接入差别、参数哪些生效，见各自驱动插件的手册（分类「相机驱动」/「相机」）。
2. 回到本页：下拉选这台（同时显示名字与当前状态）；`当前状态：` 那行说清"现在能不能跑"——
   未连接 = 红；已连接但未采流 / 等待客户端接入 = 橙；采流中 = 无提示。
3. 「取图超时(ms)」：默认 0 = 用相机自身配置的超时；可手填或 🔗 链接变量（不同产品节拍不一样）。
4. 「执行」试运行：成功文案 `已从相机取图: {宽}x{高}x{通道}（第 {帧号} 帧，来源 {来源名}）`。
5. 语义要点：**每帧只被消费一次**（同一帧不会被两个采集步骤各取一次——需要同一帧多处使用，取一次再把 `Image` 传给下游）；
   帧队列有上限，处理不过来会丢最旧并计溢出（**丢帧 = 一个未检测的工件**）。

失败文案就是排查指引（照抄搜索）：
`尚未选择相机，请在「相机采集」页选择一个已配置的相机` /
`找不到序列号为「X」的相机。请到「系统 → 相机设置」添加该相机，或回到本步骤的「相机采集」页重新选择` /
`相机「X」未连接（…）。请到「系统 → 相机设置」连接该相机后再运行` /
`等待相机「X」出图超时（N ms）；相机状态：…，待消费 N 帧，累计收帧 N，溢出丢帧 N`。

## 六、两条 HTTP 通道不要混

| | 网络推送（本算子 Hub 模式） | 相机推帧（网络相机驱动） |
| --- | --- | --- |
| 配置节 / 默认端口 | `AppConfig.json → HttpImageServer` / **19000** | `AppConfig.json → NetworkCameraServer` / **19100** |
| URL | `POST /flow/{流程名}` | `POST /camera/{序列号}/frame`，心跳 `POST /camera/{序列号}/heartbeat` |
| 是否等流程结果 | **等**（同步回包，含 outputs） | **不等**（入队即回，流程自己按节奏取） |
| 帧留存语义 | 图像槽只留最新一帧 | 环形队列消费，每帧只取一次，溢出丢最旧并计数 |
| 要不要添加相机 | 不用 | 要在「系统 → 相机设置」添加并连接 |
| 现成客户端 | 配置窗口的「推送测试」按钮 | `Tools\VirtualCameraClient`（独立"假相机"工具） |

## 七、现象 → 查哪一项（速查）

| 现象 | 多半是 | 处置 |
| --- | --- | --- |
| 试运行报"文件不存在"但路径看着没错 | 相对路径 / 网络盘掉线 / 被移动 | 用绝对路径；浏览重选一次 |
| 目录里图在涨，流程却总读前几张 | 上游索引变量没推进 | `CurrentIndex` 打日志对账；确认链接的是推进后的索引而不是常量 |
| 同一张图被反复检测 | 索引越界被夹取（静默吞掉的旧表现已修，现在会留痕） | 看结果文案里"已夹取"那句，修上游计数 |
| 网络推送长期等待 | 流程名不一致 / 令牌错 / 服务未监听 / 客户端根本没推 | 用「推送测试」按钮自测：它拿到的状态码就是服务端视角的真相 |
| HTTP 409 | 上一帧还在跑 | 客户端串行重试（同流程同时只允许一次执行） |
| HTTP 504 | 流程跑不完服务端等待上限 | 加大 `RequestTimeoutMs` 或缩短处理链；注意流程不会被打断，仍在后台跑完 |
| 相机模式取不到图 | 未连接 / 未开始采流 / 客户端没推 / 真机没触发 | 见第五节四条失败文案 |
| 溢出丢帧在涨 | 处理速度跟不上节拍 | 缩短处理链 / 降帧率；不要只靠加大队列容量掩盖 |
| 主界面没图但流程成功 | 显示窗体=0 / 画布采集开关关 / 插件 DLL 未重建 | 见 overview「常见问题」；日志有"已收录 N 帧"=显示侧问题，没有=收录侧问题 |
| 换相机后测量值整体偏 | 旧标定还在用 | 把 `SourceSerial` 接到标定/坐标变换的身份输入，让不匹配**明确失败** |

## 八、产物与部署（改了没生效先查这三条）

1. 插件工程必须留在 `Plugins\Plugin.ImageAcquisition\`：构建约定按目录把 DLL 投递到 `Modules\`，放别处加载不到。
2. 改了插件源码必须**重建插件工程**：`Modules\` 不由宿主工程带出，只重建宿主跑的还是旧 DLL（本仓出过"产物陈旧"事故）。
3. **不要把公共契约程序集（`Core.Interfaces.dll` / `Core.Controls.dll` 等）拷进 `Modules\`**：会出现两份静态状态，
   典型症状是"图投进去取不出来"。
