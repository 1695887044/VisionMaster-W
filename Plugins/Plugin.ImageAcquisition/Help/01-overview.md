# 图像采集

> 分类：常用工具 ｜ 来源：插件 Plugin.ImageAcquisition

流程的**入口算子**：把图从四种来源——单个文件、文件夹、网络推送、相机——取成一张 `HImage` 交给下游视觉步骤，
并把最新图按需投到主界面的视图窗口。除 `Image` 之外它还报出"这张图是从哪来、第几张/第几帧、这台相机是谁"，
供下游做批次追溯与标定身份核对。

## 为什么需要它 / 原理

**一个算子、四条链路**。四种采集模式共用同一个执行核心（`RunAlgorithm` → `ExecuteCore`），
"试运行"与"正式运行"跑的是同一段代码——所以配置窗口底部的「执行」按钮就是最可信的验证手段。

**数据分三层存，各走各的口径**：
- **可被变量链接的数据流参数**做成输入端口（路径、索引、取图超时）：值随流程数据流灌入，可接上游；
- **纯配置项**（采集模式、显示窗体、相机序列号）不落端口、永不连线，随步骤配置持久化；
- **纯界面状态**（预览图、信息栏、文件计数、推送测试表单）只在配置窗口存活，不进流程。

**取图语义按来源分成两种世界**，这是本算子最容易混的地方：
- **文件 / 文件夹**：拉模式——本轮要哪张，按路径或索引读哪张；
- **网络推送（Hub）**：外力驱动——外部程序"推一张 → 触发流程跑一次"，本步骤只是把那张图从本流程的图像槽里取走；
- **相机采集**：推模式——相机持续出图进帧队列，本步骤按自己的节奏**消费**一帧，**每帧只会被取到一次**。

**像素 → HImage 全仓只有一处转换核心**。网络推送与相机采集的像素约定必须逐字节一致
（灰度 = 1 字节/像素；彩色 = 3 字节/像素交错，HALCON 通道 1/2/3 = R/G/B），各写一份早晚出现
"相机采的彩色图颜色是反的、网络推送却是对的"——而灰度图上完全看不出来，只表现为判别类算子莫名不对。
入队/入槽前已有尺寸与字节数自洽校验，≥4 通道（BGRA/RGBA）先抽掉 alpha 压成三通道，2 通道直接拒绝。

**显示是"锦上添花"，不参与成败判定**：采集成功后把图投递到「显示窗体」指定的窗口；投递失败只记一条告警，
绝不把一次成功的采集判成异常。视觉图像页的图像集另有开关（见「常见问题」）。

## 输入端口

| 端口 | 必填 | 说明 |
| --- | --- | --- |
| `FilePath` | 否 | **指定图像**模式：单个图像文件完整路径。可手填、可浏览选择、可 🔗 链接上游变量 |
| `FolderPath` | 否 | **文件目录**模式：图像文件夹路径。同样可链接变量（链接时配置态无法预览，运行期才生效） |
| `FileIndex` | 否 | **文件目录**模式：文件夹内第几张，**0 基**。默认 0；可链接变量（批量回放时由上游计数给） |
| `FrameTimeoutMs` | 否 | **相机采集**模式：等一帧的超时（毫秒）。默认 0 = **使用相机自身配置的超时**；可被上游变量控制（不同产品节拍不一样） |

> 四个口都标为"非必填"：四种模式各用各的，用不到的口留空是合法状态，不会被编译拦下。

## 配置项（随步骤落盘，不可连线）

| 项 | 必填 | 说明 |
| --- | --- | --- |
| `Mode`（界面：采集模式） | 是 | 四选一：`SingleFile`「指定图像」/ `Folder`「文件目录」/ `Hub`「网络推送」/ `Camera`「相机采集」。**换模式会清空预览并重新校验**——旧模式的数据源在新模式下对不上号 |
| `DisplayViewIndex`（界面：显示窗体） | 否 | 采集图发布到主界面几号视图窗口：`图像窗口1~9`；`不显示` = 0（不抢占窗口，图照样给下游）。**写入即夹取到 0~9**（手改方案文件塞进 10/负数不会报错，但表现为"配了显示哪格都不显示"，所以必须夹） |
| `CameraSerial`（界面：相机下拉） | 相机模式必填 | 目标相机的**序列号**（不是显示名、不是内部 Id）。候选列表由宿主在打开配置窗口时下发；序列号对应的相机被删掉时，下拉诚实显示为空、信息栏报红 |

## 输出端口

| 端口 | 说明 |
| --- | --- |
| `Image` | 采集到的图像（`HImage`）。失败轮为空——本轮开轮即清零 |
| `CurrentPath` | 当前来源：文件模式=完整路径；网络推送=客户端声明的图片名（缺省 `hub://{流程名}`）；相机=来源名（缺省 `camera://{序列号}`） |
| `CurrentIndex` | 文件目录模式=当前索引；**相机模式重载为"第几帧"**（兼容既有接线）。要精确帧号请用 `FrameId` |
| `TotalFiles` | 文件夹内符合条件的总数；**相机模式重载为"累计收帧数"**。要精确值用 `ReceivedCount` |
| `FrameId` | **相机帧序号（从 1 开始）**，无任何语义重载；非相机模式为 0。日志对账、结果归档一律用它 |
| `ReceivedCount` | 该相机**累计收到的帧数**（含溢出被丢弃的）；非相机模式为 0 |
| `SourceSerial` | **相机身份**：相机模式 = 本步骤配置的序列号，其余模式为空。接「标定」/「坐标变换」的 `SourceSerial` 输入做自动核对——换相机（换镜头/换工位）后旧标定自证失效，而不是静默用错标定 |
| `Success` / `ErrorMessage` | 基类统一提供：本步是否成功 + 一句话原因（失败原因本身就是排查指引，见「口径与失败策略」） |

## 关键参数

> 完整参数与取值范围以流程中该步骤的「模块参数」界面为准，这里只解释含义。

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `Mode` | `SingleFile`（指定图像） | 枚举落盘为数字；坏档会被踢回默认值 |
| `DisplayViewIndex` | `1` | 写入即夹取 0~9；0 = 不显示（不影响 `Image` 输出与下游） |
| `CameraSerial` | 空串 | 相机模式的寻址键；与「系统 → 相机设置」里那台的序列号逐字对应 |
| `FilePath` / `FolderPath` | 空串 | 空值时信息栏橙字提示"请选择…"；已链接变量时不做校验（路径运行期才产出） |
| `FileIndex` | `0` | 越界**夹取**到有效区间，并在结果文案里注明"索引 X 超出 0~N，已夹取"（静默吞掉会表现为"同一张产品被反复检测"） |
| `FrameTimeoutMs` | `0` | 0 = 用相机配置的超时（默认 3000 ms）。这个口存在的意义就是**绝不能没有超时** |
| 支持的图像扩展名 | `.bmp .jpg .jpeg .png .tif .tiff` | 白名单一处定义：执行核心、目录列表、浏览框都由此派生；不在名单内的文件不进目录列表、不参与索引 |
| 目录排序 | 自然序 | `img2` 排在 `img10` 之前，与资源管理器一致——文件索引直接对应工件顺序，**排序错 = 顺序错** |

## 口径与失败策略

**统一的收尾规则**
- 每一轮**开轮清零**：`Image` / `CurrentPath` / `CurrentIndex` / `TotalFiles` / `FrameId` / `ReceivedCount` / `SourceSerial`
  全部先归零再执行。失败轮不会留上一轮的残留值（下游按"当前索引/总数"判断的步骤尤其依赖这条）。
- 业务失败 → `Success=false` + `ErrorMessage` + 一条 Error 日志；`ErrorMessage` 一律写成"下一步该做什么"。
- 取消（用户点了"停止流程"）→ 本步没产出，`Success=false`、`ErrorMessage` 写"已停止等待图像"，
  但这**不是业务故障**：流程去向由引擎的取消语义决定，本算子绝不试图终止流程。
- 读盘/解码失败时先把已创建的 HALCON 对象释放再上抛，避免连续失败持续吃非托管内存。

**四种模式各自的分界**
- **指定图像**：路径为空 / 文件不存在 / 读图失败都是明确失败；`TotalFiles` 恒为 1。
- **文件目录**：**每轮重新枚举**（不缓存目录）——"拍图落盘"式工作目录里新增的文件当轮就能读到。
  目录不存在 / 目录内没有匹配文件 = 失败（后者 `TotalFiles=0`）。
- **网络推送**：图像槽里没有图是**正常工作状态**，于是**阻塞等待**而不是报失败（旧实现报失败会让本步失败、
  下游每个吃图的步骤再各报一次"输入图像为空"，真正的根因被噪音盖住）。
  正常 HTTP 链路是"先推图再触发流程"，命中快路径、不产生等待；连续运行或手动单跑时槽空等待是常态。
  唯一的退出方式是等到图或用户停止流程；**绝不回退旧图**（回退会产出"长得像成功"的错结果）。
- **相机采集**：四类失败**分开报**——① 没选相机；② 找不到该序列号的相机；③ 相机未连接（状态 `Closed`）；
  ④ 等图超时（文案带"相机状态 + 待消费帧数 + 累计收帧 + 溢出丢帧"四个数）。
  **不做"重试等下一帧"**：这一帧没等到就是没等到，继续等只会让流程越来越滞后于生产；
  产线上"这一件没检出"必须被明确记录，而不是靠等待掩盖过去。

**超时口径**：等图超时 = `FrameTimeoutMs` 端口值，填 0 时取相机配置里的超时；两者都被保证为有限值。
网络推送模式没有"超时"这一说（只有心跳/取消两个退出条件），它的等待上限由流程是否被停止决定。

## 典型用法 / 接线

```
① 离线调试（最常见）
   图像采集.指定图像（浏览选一张良品图）
   图像采集.Image ──▶ 图像预处理.SrcImage ─▶ 下游算子

② 序列回放 / 批处理
   上游计数.变量 ──▶ 图像采集.FileIndex        （0 基，越界自动夹取）
   图像采集.Image ──▶ 下游算子.SrcImage
   图像采集.CurrentPath ──▶ 数据记录（存的记录能反查是目录里哪张图）

③ 外力触发（相机/PLC/上位机推一张跑一次）
   外部程序 ──POST /flow/{流程名}──▶ 本步骤（网络推送，取到刚推进来的那一帧）
   图像采集.Image ──▶ 下游算子；判定结果由同一次 HTTP 请求同步回传

④ 产线连续采图（推模式）
   系统 → 相机设置：添加并连接相机、开始采流
   图像采集.相机采集（CameraSerial = 那台的序列号；取图超时端口 0 = 用相机配置）
   图像采集.Image ─────────▶ 下游算子.SrcImage
   图像采集.FrameId ───────▶ 数据记录.备注 / 结果上报（帧溯源）
   图像采集.SourceSerial ──▶ 标定.SourceSerial ─▶ 坐标变换（换相机后旧标定明确失败）
   （本算子只出原图，不带标注；要往图上烧结果请接「结果显示」算子）
```

## 常见问题

**Q：该选哪种模式？**
调一张静态图 → 指定图像；跑一批已有图（离线复现、批量回归）→ 文件目录；
外力（PLC / 别的软件 / 客户端）"给一张图就跑一次流程并把结果回给对方" → 网络推送；
相机持续出图、流程按自己节奏取帧 → 相机采集。注意**网络推送不需要在「相机设置」里添加任何相机**，
而相机采集必须先在相机设置里添加并连接。

**Q：日志停在「槽内暂无图像，开始等待网络推送（流程「X」）」不动？**
这是等待态、不是故障。按顺序核对：① 客户端 POST 的**流程名**与当前流程是否一致（URL 里那段，
中文/空格需 URL 转义，界面会预填当前流程名）；② **令牌**对不对（401）；③ 服务是否在监听
（配置窗口「网络推送」页会直接写"宿主收图服务正在监听 …"或给出未监听的原因）；④ 是不是同一流程被并发推
（同流程同时只允许一次执行，第二个请求收 409）。要退出等待就点"停止流程"。

**Q：相机模式为什么一直报"等待相机…出图超时"？**
读那一句里的四个数：**累计收帧不涨** = 相机根本没出图（没连接/没开始采流/真机没触发/客户端没推）；
**待消费长期满、溢出丢帧在涨** = 流程处理不过来，帧被丢在队列里（每丢一帧 = 一个未检测的工件，必须查）；
**相机状态写着"已连接但未开始采流"** = 到「系统 → 相机设置」点「开始采流」。
配置窗口的「相机采集」页在编辑时就用颜色提醒过这件事（红=未连接 / 橙=未采流或等待接入 / 空=正常）。

**Q：为什么「图像采集」的配置窗口里没有相机实时预览？**
刻意不提供。预览要拿到设备对象，而设备只存在于宿主的相机仓库里（配置窗口拿到的只是候选快照），
硬要预览就得让插件持有宿主对象，破坏"插件只认契约"。相机图像预览在「系统 → 相机设置」（那里本来就有 Live 预览，
也是更该检查相机的地方）；要验证"这一步能不能取到图"，点配置窗口的「执行」试运行即可——它跑的就是正式运行的同一段代码。

**Q：流程成功了，视觉图像页的格子却一直空？**
① 「显示窗体」是不是选了"不显示"（0）；② 「系统参数设置 → 画布」的两个开关（启用画布采集 / 收录插件注入的图像）
是否打开；③ 日志里有没有"已收录 N 帧"——**有 = 显示侧问题，没有 = 收录侧问题**（先确认插件 DLL 是否重建并投递到 `Modules\`）。

**Q：文件夹里明明有新图，却读不到？**
扩展名必须在白名单内（`.bmp .jpg .jpeg .png .tif .tiff`），且必须在**所选目录本身**（不递归子目录）。
目录排序是自然序，"第几张"按 `img2 → img10` 的直觉排列；运行期没有目录缓存，新增/删除的文件当轮就生效。

**Q：上游给的索引超出范围会怎样？**
自动夹取到有效区间（不会失败），但结果文案会写明"索引 X 超出 0~N，已夹取"。
这条留痕是故意的：批处理场景里上游算错索引若被静默吞掉，表现为"同一张产品被反复检测"，现场极难归因。

**Q：路径 / 索引是从变量链接来的，为什么配置窗口不能预览？**
链接端口的值要运行期才由上游产出，配置态拿不到，预览必然文不对题。此时信息栏给中性说明
（"文件夹路径来自变量链接，运行期生效；配置态无法预览"），而不是报"请先选择…"——
报后者会让人误以为链接失效了。同理：`FileIndex` 被链接时，预览那句会注明"运行期以链接值为准"。

**Q：相机模式下 `CurrentIndex` / `TotalFiles` 是什么意思？能不能改用别的口？**
它们被重载成"第几帧 / 累计收帧数"（历史兼容：改成 0 会悄悄打断已有接线）。
**新接线一律用 `FrameId` 与 `ReceivedCount`**——那两个口不做任何语义重载，非相机模式恒为 0。

**Q：换了相机（换镜头 / 换工位）之后为什么结果莫名不对？**
标定与坐标变换的输入里接上本算子的 `SourceSerial`：它给出"当前图像来自哪台相机"，
与标定所属相机对不上时会**明确失败**，旧标定自证失效，而不是拿另一台相机的像素当量继续算。
失败轮的 `SourceSerial` 会清空，下游不会读到上一轮的残留序列号。

**Q：彩色图红蓝互换 / 灰度图看起来正常但判别不对？**
先确认没有绕过唯一转换核心的新路径：灰度 1 字节/像素、彩色 3 字节/像素交错、HALCON 通道 1/2/3 = R/G/B，
且 4 通道（BGRA）会先抽掉 alpha。这类错在灰度图上看不出来，只表现为颜色类判据莫名不对。
