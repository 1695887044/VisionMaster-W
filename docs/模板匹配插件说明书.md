## 1. 这是什么插件

### 1.1 一句话说明

**模板匹配（Template Matching）= 让计算机"记住"一个物体的样子，然后在一张新图片里把它找出来，并告诉你它在哪里、转了多少度、有多大把握。**

举个生活化的例子：

> 你给机器人看一张螺丝刀的照片（这就是"模板"），然后随便递给它一张桌面照片，
> 它能在照片里把那把螺丝刀圈出来，告诉你：
> "找到了，中心在 (512.3, 340.7)，转了 23.5°，把握有 92%"。
> 就算螺丝刀在照片里被旋转过、甚至稍微缩小放大了一点，它也能找到。

这在工业视觉里叫**定位**，是几乎所有视觉方案的第一步——先找到产品在哪，后续的测量、缺陷检查、机器人抓取才有坐标可用。

### 1.2 它在流程中的位置

这个插件是 VisionMaster 流程编辑器里的一个"步骤"（Step），归在\*\*「定位」分组\*\*下。
典型的流程长这样：

```
[图像采集] → [模板匹配] → [Blob 分析] / [卡尺测量] / [画框裁剪] → …
                    ↓
        输出位置 Row/Column/Angle（位姿）
```

模板匹配输出的**位姿**（位置 + 角度）会被下游步骤直接引用。

### 1.3 核心特性一览

| 特性      | 说明                                          |
| ------- | ------------------------------------------- |
| 多模板库    | 一个插件实例可以装最多 20 个模板（比如"型号 A""型号 B""型号 C"各一个） |
| 配方驱动    | 运行时通过 `RecipeName` 端口按名字自动切换模板，可连上游变量或上位机   |
| 旋转搜索    | 可设定角度范围（默认 -180°\~180°），目标转多少度都能找到          |
| 缩放搜索    | 可选开启（0.5×\~2.0×），目标远近变化导致大小不同也能找到           |
| 涂抹排除    | 模板里反光、会变的区域可以用"画笔"涂掉，不参与匹配                  |
| 三种框选形状  | 矩形 / 圆形 / 椭圆                                |
| 亚像素精度   | 位置输出精确到小数点后（不是整数像素）                         |
| 位姿归一化图像 | 输出一张"把目标摆正"的图，下游插件不用再关心目标转了多少度              |
| 可视化标注   | 运行结果画在图上（绿轮廓 + 文字），可发布到主界面窗口                |

### 1.4 用到的技术：HALCON 的 Shape-Based Matching

本插件底层调用 **HALCON** 机器视觉库的 `create_shape_model` / `find_shape_model` 系列算子。
HALCON 是工业界最主流的商业视觉库之一，其形状匹配算法的特点：

- 基于**边缘梯度**（物体的轮廓形状）而非灰度值本身，所以对光照变化不敏感；
- 支持旋转、缩放、遮挡（只要目标大部分可见就能找到）;
- 速度经过高度优化（图像金字塔 + 由粗到精搜索）。

> 小白提示：你不需要懂 HALCON 也能用这个插件——界面上每个参数都有中文说明。
> 但如果想调得又快又稳，第 2 章的原理值得读一遍。

## 2. 原理篇：模板匹配是怎么工作的

### 2.1 整体思路：两阶段

Shape-based matching 分两个阶段，对应界面上两个按钮：

```JavaScript
阶段一「学习」（create_shape_model）
  给我一张参考图 + 一个框住的区域
  → 我把区域内的"边缘特征"提炼成一个小模型文件
  （可以理解为：把物体的"骨架"记在小本本上）

阶段二「查找」（find_shape_model）
  给我一张待检图 + 之前记的模型
  → 我在图上到处"对骨架"，找到最像的位置
  → 输出：位置 + 角度 + 相似度分数
```

### 2.2 学习阶段做了什么

当你点击「学习模板」时，HALCON 会：

1. **裁出模板区域**：你画的矩形/圆/椭圆框住的像素才算数；
2. **算梯度**：对区域内每个像素，计算"亮度变化的方向和强度"。
   物体的轮廓处亮度变化剧烈（比如黑色的螺丝刀压在白色桌面上），
   平坦区域几乎没变化（白桌面的中间）。
3. **按梯度阈值筛选**：变化太弱的点扔掉（那些多半是噪声或反光），只留下"边"。
   这就是界面上「梯度阈值」参数的作用——阈值越高，留下的边越少、越"硬"。
4. **记录极性**：每条边还记着"从暗到亮"还是"从亮到暗"（这叫**极性**）。
   打开极性校验，黑白方向不一致就不算命中——搜索更快更稳，
   但目标如果可能黑白反转（比如正反面）就要关掉它。
5. **建图像金字塔**：把模板缩小 1/2、1/4、1/8…生成多层"缩略图"。
   这就是「金字塔层数」参数。层数越多，搜索越快（先在模糊小图上粗找，
   再到清晰大图上精修），但太少可能漏掉细节、太多则准备时间长。
6. **预计算旋转变体**：如果你允许 ±180°，HALCON 会按角度步长把模板的骨架
   预先转出几十上百份存着。这就是为什么**改了任何"提取参数"都必须重新学习**——
   这些参数在创建那一刻就"烤"进模型里了（代码注释原话："创建态"参数）。

最终产物是一个 `.shm` 格式的模型文件，本插件把它转成 **base64 字符串**存进方案 JSON——
方案保存/复制到别的电脑，模板跟着走，不需要额外的模型文件。

### 2.3 查找阶段做了什么

每一帧图片进来，`find_shape_model` 会：

1. 对输入图也建同层数的金字塔；
2. **从最顶层（最小的图）开始**，拿着模型骨架在整张图上滑动比对——
   在小图上算一遍代价很低，可以先排除 99% 不可能的位置；
3. 有希望的位置**逐层往下深入**，在大图上精细化，同时精算角度；
4. 每个候选位置给出一个**分数**（0\~1，1 = 完美重合）；
5. 分数 ≥ 「分数下限」的才算命中，再按「最大重叠」去掉重复报告的，
   按「匹配数上限」取前 N 个，输出。

**「激进度」（Greediness）的作用**：滑到一半发现分数已经不可能达标，
要不要提前放弃？0 = 绝不放弃（最准最慢），0.9 = 非常果断（最快、偶有漏检）。
默认 0.8 是工业常用折中。

### 2.4 两个进阶设计（这个插件独有的"商业细节"）

#### ① 模型原点锚定

HALCON 默认把模型原点放在模型内部的"参考点"，**不是你画框的中心**——
实测会差 1\~2 像素（圆域差 +1.5, +1.5）。直接输出的话，"报告的位置"和"你框的中心"对不上。

本插件的解法很聪明：**学习完成后，拿模板在参考图上自己找自己一次**
（自己找自己必然是满分命中），量出"默认原点落点"和"画布中心"的偏差，
然后用 `set_shape_model_origin` 把原点锚回画布中心。
这个补偿量随模型一起序列化保存，运行期自动生效——
从此矩形/圆/椭圆三种形状输出的 Row/Column 一律是"你框的中心"，口径统一。

#### ② 位姿归一化图像（AlignedImage）

目标在画面里可能歪着（转了 23°）。下游很多插件（画框裁剪、卡尺）
的检测区域是**固定的**——总不能每个都动态算旋转。

本插件提供 `AlignedImage` 输出：用刚找到的位姿做一次**刚性变换**
（只平移+旋转，不缩放不变形），把目标从"当前歪着的姿态"搬回"学习时的标准姿态"。
变换后目标永远出现在画面上同一个位置、0° 摆放——
下游插件全部按固定坐标配置，零改动直接用。

```
原始图：目标在 (900, 500) 转 23°      AlignedImage：目标在 (400, 300) 转 0°
┌─────────────────┐                 ┌─────────────────┐
│        ╱╲       │                 │      ┌──┐       │
│       ╱  ╲  →   │   ──变换──▶     │      │▮▮│ ←固定 │
│      ╱ ╱╲ ╲     │                 │      └──┘ 位置  │
│         ↘       │                 │                 │
└─────────────────┘                 └─────────────────┘
```

### 2.5 多模板库 + 配方：一个实例服务多个产品

产线经常"一台设备轮着做几种产品"。这个插件的做法：

- 一个插件实例 = 一座**模板库**（ListBox 列表，每行一个条目）；
- 每个条目 = 一个产品型号的完整档案：区域 + 掩膜 + 提取参数 + 模型载荷 + 参考图路径；
- 运行时看 `RecipeName` 端口送来的名字（可来自上位机切换配方），按名字挑条目匹配；
- 名字没送来 → 用「默认模板」（界面上点"设为默认"的那个）；
- 名字送来了但库里没有 → **直接失败**，错误信息列出库里现有的名字
  （产线口径：不猜、不静默，宁停勿错）。

## 4. 数据模型详解

### 4.1 MatchingEnums.cs —— 只有 20 行，但体现一个重要设计

```csharp
public enum StatusLevel { Info, Warning, Error }
```

配置界面信息栏的三种颜色级别：**绿（正常）/ 橙（提示）/ 红（错误）**。

注意源码注释里写的：`与 BlobDetect 的同名枚举同语义、各插件自带一份（插件间不共享类型，避免跨程序集耦合）`。

> **为什么每个插件都抄一份一样的枚举？**
> 插件 = 独立 DLL，互相之间不引用。如果放在一个"公共库"里，
> 任何一边改枚举都会牵连所有插件重新编译发版。
> 复制 20 行换取**插件之间完全解耦**——这是插件体系的刻意取舍。

### 4.2 MatchingTemplateEntry —— 模板条目（档案卡）

这是"一个产品型号"的完整档案，实现 `INotifyPropertyChanged`（即 INPC）。

> **INPC 是什么？** WPF 的界面绑定机制：属性值变了要"喊一嗓子"
> （触发 `PropertyChanged` 事件），界面才知道要刷新显示。
> 每个 setter 都是同一个三段式套路：
>
> ```csharp
> private string _name = "模板1";
> public string Name
> {
>     get => _name;
>     set { if (!string.Equals(_name, value)) { _name = value; OnChanged(nameof(Name)); } }
> }
> ```
>
> 第一段：先判断"值真的变了吗"（没变就不喊，省性能）；
> 第二段：赋值；
> 第三段：喊一嗓子通知界面。

#### 字段分组一：身份与区域（"你是谁、框在哪"）

| 属性             | 类型         | 说明                                      |
| -------------- | ---------- | --------------------------------------- |
| `Name`         | string     | **配方键**。`RecipeName` 端口按它选条目，如"型号A"     |
| `Shape`        | string     | 区域形状：`Rectangle` / `Circle` / `Ellipse` |
| `Rect`         | double\[5] | 区域参数，**固定 5 个**（见下）                     |
| `Mask`         | string     | 涂抹排除域，PNG 图片的 base64（255 = 挖掉）          |
| `RefImagePath` | string     | 该条目自己的参考图路径（重学时载入）                      |
| `Model`        | string     | **模型载荷**：HALCON 模型文件的 base64。空 = 还没学    |

**Rect 的 5 参数约定**（与区域颜色检查插件同一约定）：

| 形状 | \[0] | \[1] | \[2]   | \[3]  | \[4]  |
| -- | ---- | ---- | ------ | ----- | ----- |
| 矩形 | 中心行  | 中心列  | 角度（弧度） | 半长    | 半宽    |
| 圆  | 中心行  | 中心列  | 半径     | 0（占位） | 0（占位） |
| 椭圆 | 中心行  | 中心列  | 角度     | 半径1   | 半径2   |

> 为什么圆也要凑 5 个？——**存取只有一条路径**。
> 如果矩形 5 个数、圆 3 个数，每处读代码都得写 if-else。
> 统一 5 个，圆的后两位补 0，所有序列化/比较/克隆代码只有一份。

#### 字段分组二：提取参数（"学习时怎么提炼特征"）

这些参数**在 create 时生效**，改任何一个都必须重新学习（原因见 2.2 节第 6 步）：

| 属性                            | 默认         | 含义                          |
| ----------------------------- | ---------- | --------------------------- |
| `NumLevels`                   | 5          | 金字塔层数（1\~10）。越大越快，过大可能漏细节   |
| `MinAngleDeg` / `MaxAngleDeg` | -180 / 180 | 允许的旋转范围（度）                  |
| `AngleStepDeg`                | 0          | 角度步长（度）。0 = HALCON 按模板尺寸自动定 |
| `GradientThreshold`           | 0          | 梯度阈值。0 = 自动对比度              |
| `UsePolarity`                 | true       | 极性校验：黑白方向必须一致才算命中（更快）       |
| `ScaleEnabled`                | false      | 是否启用缩放匹配                    |
| `ScaleMin` / `ScaleMax`       | 0.8 / 1.2  | 缩放范围（倍率）                    |

#### 字段分组三：参数指纹 `LearnedSignature`

一个很巧妙的设计。学习完成时，把"当时用的所有提取参数"拼成一个字符串存下来：

```
"Rectangle|200.5,300.2,0,80,60|5|0|-180|180|0|True|False|0.8|1.2|1234"
   形状      区域5参数        层数 梯度 角度范围  步长 极性 缩放开关 范围   掩膜长度
```

之后只要任何一项被改动（包括掩膜），现算的指纹就和存的不一样 →
界面徽标自动从"已学习"变成橙色的"**参数已改·需重新学习**"。

> 为什么需要它？——提取参数是"烤"进模型的（2.2 节）。
> 用户改了参数却忘了重新学，跑出来的结果用的还是旧参数，现场很难发现。
> 指纹 = 一台"防呆闹钟"。

#### 字段分组四：运行期句柄缓存（不落盘）

```csharp
[JsonIgnore] public HTuple? RuntimeModelId;      // 反序列化后的 HALCON 模型句柄
[JsonIgnore] public string? RuntimeModelSource;  // 记录句柄是从哪份 Model 载荷加载的
[JsonIgnore] public HObject? RuntimeContours;    // 模型特征轮廓（画预览/标注用）
```

- `[JsonIgnore]`：序列化方案时**跳过**——句柄是内存里的东西，存了也没意义；
- **懒加载**：第一次用到该条目时才把 base64 解开成句柄（`EnsureModelLoaded`），
  避免方案一加载就把 20 个模型全解开（占内存又慢）；
- `RuntimeModelSource` 用于**缓存校验**：句柄在，但比对一下"当前 Model 字符串"和
  "当初加载时的字符串"，不一致（用户重学了）就重新加载——防止用旧句柄跑新配置。

### 4.3 条目与序列化：方案怎么存

整库走 `TemplateLibraryJson`（见 5.1），`JsonConvert.SerializeObject(Library)` 一行搞定：

- 所有公开属性自动进入 JSON（含大块的 Model/Mask base64）；
- `[JsonIgnore]` 的运行期句柄不存；
- 加载时反序列化回来，句柄懒加载重建。

## 5. 配置项与输入输出端口详解

### 5.1 配置项（\[StepConfig]：随方案保存的"设置"）

> `[StepConfig]` 是框架的标记：标了这个特性的属性会被**自动保存进方案文件**、
> 打开方案时**自动灌回来**。相当于"持久化的设置项"。

| 配置项                   | 默认     | 说明                                                                               |
| --------------------- | ------ | -------------------------------------------------------------------------------- |
| `TemplateLibraryJson` | `"[]"` | 模板库整体（JSON 数组字符串）。**用 string 存而不是直接存对象数组**，因为 string 经框架的 InputValues 往返最稳（注释原话） |
| `DefaultTemplateName` | 空      | 默认模板名。`RecipeName` 没连/为空时用它                                                      |
| `MinScore`            | 0.5    | 分数下限：低于它的命中不算找到                                                                  |
| `MaxMatches`          | 1      | 最多输出几个实例（1 = 单目标）                                                                |
| `MaxOverlap`          | 0.3    | 两个命中的最大重叠比例（去重）                                                                  |
| `Greediness`          | 0.8    | 搜索激进度 0.1\~0.9，越大越快越容易漏                                                          |
| `DisplayViewIndex`    | 1      | 运行标注图发布到主界面几号窗口（0 = 不发布）                                                         |
| `OutputAlignedImage`  | true   | 是否输出位姿归一化图像                                                                      |

**老方案迁移字段**（`TemplateModel` / `TemplateShape` / `TemplateRect` / `TemplateMask` / `PreviewImagePath`）：
这 5 个是历史版本"单模板时代"的遗留。加载时如果发现新库是空的、但旧字段有值，
`ParseLibraryAndMigrate()` 会把它们打包成库里第一条「模板1」，
然后**清空旧字段**（防止下次又导一遍）。这是升级不破坏用户数据的典型做法。

### 5.2 两个运行时标记

- `_isConfigInstance`（配置态实例标记）：
  宿主为了打开配置界面，会**额外创建一个插件实例**给人用；
  流程真正运行用的是另一个"编译出来的运行实例"。
  两者走同一套灌值代码，但读参考图、反序列化模型、渲染预览这些**只该给"人"做的事**，
  运行实例不该做。所以 `Initialize()`（只有配置界面走）先 `MarkAsConfigInstance()` 盖章，
  之后所有"给人看的"逻辑都检查这个章。
  > 不隔离的后果（注释里记录的真实事故）：流程每次编译都会读图、建模型、开离屏窗口——白白变慢。
- `_seedingCanvas`（播种画布标记）：
  配置界面打开时要把已存条目的区域"回填"到画布上。
  回填动作本身会触发"画布变了"事件，而那个事件的处理逻辑是"用户画了新框 → 写回参数"。
  不加标记就是**自己填的框又触发了写回**，来回震荡。
  播种期间置 true，事件处理器一看"哦是系统回填，不用管"。

> 这两个布尔是"状态机防震荡"的经典手法：**分清"用户做的"和"程序自己做的"**。

### 5.3 输入端口（2 个）

| 端口           | 类型     | 说明                  |
| ------------ | ------ | ------------------- |
| `Image`      | HImage | 待定位的图像，由上游（如图像采集）连入 |
| `RecipeName` | string | 配方名/产品型号，可连上游变量或上位机 |

### 5.4 输出端口（12 个）

**标量端口 = 最高分实例；数组端口 = 全部实例，逐项对齐**（Rows\[i]、Columns\[i]、Angles\[i]、Scores\[i]、Scales\[i] 说的是同一个第 i 个命中）：

| 端口                                                  | 类型     | 说明                                           |
| --------------------------------------------------- | ------ | -------------------------------------------- |
| `Score`                                             | double | 最高分的匹配分数 0\~1                                |
| `Row` / `Column`                                    | double | 最高分实例的中心行/列（**亚像素**，即带小数）                    |
| `Angle`                                             | double | 最高分实例的角度（**度**——平台统一口径，HALCON 原生输出弧度，代码里转换过） |
| `MatchCount`                                        | int    | 命中实例数                                        |
| `MatchedTemplate`                                   | string | 本帧实际用的模板名（追溯用：到底按哪个配方匹配的）                    |
| `Rows` / `Columns` / `Angles` / `Scores` / `Scales` | HTuple | 全部实例的数组版本                                    |
| `MeasureImage`                                      | HImage | 标注图：原图 + 绿色模板轮廓 + 判定文字（没找到也输出 = 原图 + 红字原因）   |
| `AlignedImage`                                      | HImage | 位姿归一化图像（见 2.4②；`OutputAlignedImage` 关掉则不输出）  |

> **角度单位为什么是"度"？** 视觉工程师日常说"转了 23 度"不说"0.4 弧度"。
> 平台约定端口一律给度，HALCON 给弧度，所以在赋值处统一乘了 180/π
> （第 1550、1568 行），渲染前再统一转回弧度喂给算子。
> 代码注释记录了一个历史 bug：某次把弧度当度又乘了一次 π/180（双重转换），
> 端口数值全对，只有标注图上的轮廓不跟着转——极难发现，因为"数字是好的"。

## 6. 学习流程详解（CreateTemplate）

> 对应界面按钮：**「学习模板」**。代码在 `MatchingPlugin.CreateTemplate()`（849 行起）。

### 6.1 学之前：图和区域从哪来

配置界面有两条路把参考图弄上画布（`OnViewLoaded` 里自动尝试）：

1. **试运行带图**：流程里点"试运行"，上游图像会通过 `Image` 端口桥接进配置实例，
   插件订阅了 `Image.PropertyChanged`（`OnImagePortChanged`），图一到就显示到画布——
   **直接用真实相机图学模板，最推荐**；
2. **手填路径载图**：在参考图路径框填本地图片路径，点「载入」（`LoadPreviewImage`）。

区域则是在画布上**右键 → 新建矩形/圆形/椭圆**，框住模板特征。
画布控件（`ImageEdit`）负责画框/拖拽，插件通过 `CanvasRois` 集合与它同步：
控件新建/删除 ROI → 触发 `OnCanvasRoisChanged` → `WriteBackTemplate()` 把框的参数
写进 `CanvasShape`/`CanvasRect`，并同步进当前编辑条目。

> 为什么只认**最后一个** ROI（`CanvasRois.LastOrDefault()`）？
> 模板只需要一个区域。用户重画时以最新的为准，旧的自动作废——
> 比弹窗问"要覆盖吗"少一步打扰。

### 6.2 CreateTemplate 全流程（9 个步骤）

```
① 前置检查（有编辑条目？画了区域？有图？）
② 生成模板区域（GenTemplateRegion：按形状 gen_circle/gen_ellipse/gen_rectangle2）
③ 挖涂抹排除域（region − 涂抹域）
④ 裁域 + 转灰度（reduce_domain → TryToGrayImage）
⑤ 创建模型（create_shape_model 或 create_scaled_shape_model）
⑥ 原点锚定（在参考图上自匹配一次，set_shape_model_origin 补偿）
⑦ 序列化存条目（write_shape_model → base64 → entry.Model）
⑧ 写回区域与指纹（entry.Shape/Rect/LearnedSignature）
⑨ 刷新预览与状态栏
```

下面逐步拆讲关键代码。

#### ① 前置检查（851–874 行）

三连问，每问失败都给**可操作的中文提示**（不是干巴巴的报错）：

- 没有编辑条目 → "请先在模板列表里新增一个条目"
- 没画区域 → "请先在右侧图上右键 → 新建矩形/圆形/椭圆…"
- 没有图 → "请先载入参考图像（或试运行把上游图带进来）"

#### ③ 涂抹排除域（`BuildSmearExclusion`，452 行）

涂抹（Smear）是给"会变 / 会反光 / 没有特征"的区域挖洞的功能：

```
有效排除域 =（绘制涂抹 − 擦除涂抹）∩ 模板区域
```

- 「绘制涂抹」：橙色画笔，涂过的区域从模型里挖掉（反光面不再干扰匹配）；
- 「擦除涂抹」：红色画笔，从排除域里**找回**涂错的区域；
- 最后 ∩ 模板区域：涂到框外的部分不算数。

之后第 ④ 步里 `Difference(region, exclusion)` 把洞真正挖掉。

#### ④ 裁域 + 转灰度（`TryToGrayImage`，2075 行）

- `reduce_domain`：图像很大，先把"有效范围"限制到模板区域（不裁数据，只缩范围）；
- 转灰度的分支逻辑：
  - 1 通道 → 复制一份直接用；
  - 3 通道（RGB）→ `rgb1_to_gray` 标准转灰；
  - 4 通道（RGBA/BGRA，**相机 SDK 常见**）→ 取前 3 通道转灰，alpha 丢弃；
  - 其它 → 中文报错。
- 为什么要转灰？——**模型与运行图通道数必须同口径**
  （注释原话："示意图是彩色、相机图是灰度"这类组合会在匹配时表现异常）。
  学习时统一转灰，运行时也统一转灰，两边永远一致。

#### ⑤ 创建模型（908–971 行）

所有提取参数在此"装箱"：

- 角度：用户填的度数 → 转**弧度**（`Math.Clamp` 先夹在 ±180 内；
  如果用户把最小/最大填反了，自动交换；总范围夹到 ≤ 2π）；
- 角度步长：填 0 → 传 `"auto"`（HALCON 按模板尺寸自动定步长）；
- 梯度阈值：填 0 → 传 `"auto"`（自动对比度）；
- 极性：`UsePolarity` → `"use_polarity"` / `"ignore_polarity"` 字符串；
- 金字塔层数：夹在 1\~10。

然后按是否启用缩放二选一：

- 启用缩放 → `create_scaled_shape_model`（额外传缩放上下限，
  夹在 0.5\~2.0；**上下限相等时会撑开一个最小窗口**——
  退化范围 HALCON 会直接拒绝创建，代码提前把它变成合法输入，
  而不是让用户看到一条看不懂的算子报错）；
- 不启用 → `create_shape_model`。

创建完的句柄存进 `entry.RuntimeModelId`。

#### ⑥ 原点锚定（973–1039 行，本插件最精彩的细节）

原理见 2.4①。代码做法：

```csharp
// 在参考图上自己找自己（必然满分命中）
HOperatorSet.FindShapeModel(gray, entry.RuntimeModelId, …,
    out sr, out sc, …);          // sr/sc = 默认原点的落点
if (sr.Length > 0)
    HOperatorSet.SetShapeModelOrigin(
        entry.RuntimeModelId,
        sr[0].D - CanvasRect[0],  // 补偿量 = 默认落点 − 画布中心
        sc[0].D - CanvasRect[1]);
```

注意注释里的方向提醒（实测踩坑）：
`found_after = found_default − offset`，所以补偿量 = 默认落点 − 画布中心，
**与直觉相反，别"修"成减法**。
补偿失败（catch）只是退回 HALCON 默认原点——位置差 1\~2px，不至于不能跑。

#### ⑦ 序列化存条目（1041–1071 行）

```csharp
HOperatorSet.WriteShapeModel(entry.RuntimeModelId, tempFile);   // 先写临时 .shm 文件
entry.Model = Convert.ToBase64String(File.ReadAllBytes(tempFile)); // 读出字节转 base64
```

- 为什么走临时文件？——HALCON 只提供"写文件"这个出口，没有"导出内存字节"，
  只能 write → 读文件 → 转 base64 → 删临时文件；
- 掩膜同帧写入：`entry.Mask = MaskRegionToBase64(...)`。
  注意这里存的是**原始涂抹域**（绘制 − 擦除，不与模板区域求交）——
  注释记录了早先存"求交后版本"引发的事故：两个版本长度不同，
  而指纹里含 `Mask.Length`，于是"什么都没改"也天天提示需重新学习。
  教训：**同一份数据全系统必须只有一种存储口径**。

#### ⑧⑨ 收尾（1073–1108 行）

- 画布区域写回条目、记录参数指纹；
- `GetShapeModelParams` 读出实际金字塔层数，拼一条信息栏成功消息
  （层数 / 角度范围 / 缩放范围 / 特征尺寸 / 载荷 KB 大小）；
  - 特征尺寸的取法有个小聪明：**圆只有 3 个参数**，直接取 index 3/4 会显示"0×0"；
    注释还记录了更早的事故——取的是迁移字段 `TemplateRect`（新方案下恒为空数组），
    每次学习都数组越界，被外层 catch 吞成"创建模板失败"，而模型其实已经学好了；
- 最后 `UpdateTemplatePreview()` 刷新左下角预览——放在最后是因为
  预览失败会用警告覆盖消息，用户能看到"为什么没预览"。

外层 `try/catch/finally`：catch 给一句带建议的失败消息
（"区域里特征太少？换一块纹理更丰富的区域试试"）；
finally 里逐个 `Dispose()` 所有中间 HALCON 对象（`temp` 列表收集起来的）。

### 6.3 学习过程中界面发生了什么

- 每步都有 `SetStatus(文字, 级别)` 更新信息栏（唯一写入口，文字与颜色**成对**更新，
  避免出现"失败红了之后成功了还是红的"——没有独立改颜色的入口）；
- 编辑条目任何属性变化 → `OnEditingEntryChanged` → `TouchModelStaleness()`
  → 徽标刷新为"参数已改·需重新学习"；
- 换编辑条目（`EditingEntry` setter）时做三件事：
  1. 旧条目收掩膜（`WriteBackSmearToEntry`：当前涂抹写回旧条目保存）；
  2. 新条目播种画布（`SeedCanvasFromEntry`：区域/形状/掩膜回填）；
  3. 刷新新条目的预览（`RefreshPreviewForEntry`：载它的参考图 + 懒加载模型 + 特征轮廓）。

## 7. 运行流程详解（RunAlgorithm）

> 这是流程真正跑起来时每一帧都会执行的代码（1427 行起）。一帧的生命周期：

```
轮首重置端口 → 取输入图 → 选模板条目 → 确保模型已加载
    → 转灰度 → find_shape_model（按条目参数搜索）
    → 端口赋值（标量 + 数组）
    → 没找到？ Fail + 红字标注图，结束
    → 输出 AlignedImage（可选）
    → 渲染标注图 + 发布主界面
```

### 7.1 轮首重置（1430–1440 行）

所有非图像输出端口先归零（Score=0、MatchCount=0、数组清空…）。

> 为什么必须重置？——端口是跨轮次存活的。如果这一帧没找到目标而不重置，
> 下游读到的会是**上一帧的旧结果**——产线上这是"这一件明明不良却放行"的重大事故源。
> （HImage 端口不用手动清，基类 `AutoDisposeRoundOutputs` 轮首自动回收。）

### 7.2 选条目 `ResolveEntry`（1389 行）

三级优先：

```
① RecipeName 端口有名字（非空白，Trim 过）→ 精确按名字找
   找不到 → 返回错误，错误信息里**列出库里现有的全部名字**
            （库空时提示"请先学习模板"）
② 名字没给 → 用 DefaultTemplateName（若存在）
③ 连默认都没有 → 库里第一条
```

产线口径：**不静默、不猜**——配方切换失败宁可停机报错，也不拿错模板继续跑。

### 7.3 模型懒加载 `EnsureModelLoaded`（1317 行）

```csharp
if (entry.RuntimeModelId != null && entry.RuntimeModelSource == entry.Model)
    return true;   // 句柄在、且就是当前这份载荷 → 直接用（缓存命中）
```

否则：base64 解码 → 写临时 .shm → `read_shape_model` 读入句柄 → 记下来源 → 删临时文件。
之后 `RefreshEntryContours` 把模型特征轮廓也取出来（画标注用）。

> 为什么要比对 `RuntimeModelSource`？——用户在运行中途重新学习了模板，
> `entry.Model` 字符串变了，但旧句柄还活着。不比对就会**拿旧模型跑新配置**。

### 7.4 执行查找（1476–1544 行）

- 输入图先 `TryToGrayImage`（与学习同口径，见 6.2④）；
- 搜索参数取法讲究：**角度/层数/缩放来自条目**（学习时烤入的范围，find 不得超出），
  **分数/数量/重叠/激进度来自插件级配置**（运行行为，全局一套）；
- 所有数值全部 `Math.Clamp` 夹进合法区间——用户在界面填了离谱值
  （比如激进度填 5），不至于变成一条 HALCON 算子报错；
- 按是否缩放调用 `find_scaled_shape_model` / `find_shape_model`，
  五个结果元组（行/列/角度/缩放/分数）一次拿回；
- 不缩放时 `scales = 全部填 1.0`（保持数组端口五根对齐，下游不用判断空）。

### 7.5 结果出口（1546–1617 行）

1. **端口赋值**：数组端口直接存元组；角度统一弧度→度；
2. **一个都没找到**（n == 0）：
   - `Fail("未找到目标：…没有满足分数 ≥ 0.50 的匹配（光照/遮挡变化？可降低分数下限重试）")`
     ——错误信息自带**下一步建议**，这是全插件文案的统一风格；
   - 但**仍然输出标注图**（原图 + 红字原因）并发布主界面——
     产线要能**当场看到现场**，不能只是日志里一行字；
3. **找到了**：标量端口取 `scores[0]/rows[0]/cols[0]/angles[0]`（数组按分数降序，\[0] 即最高分）；
4. **AlignedImage**（若开启）：
   - 先校验 `entry.Rect` 是不是 5 个值（被手工改坏时给出"能照着修"的中文提示，
     而不是索引越界的英文异常）；
   - `VectorAngleToRigid(当前行, 当前列, 当前角, 学习行, 学习列, 0)` 生成刚性变换矩阵；
   - `AffineTransImage(..., "constant", "false")`：参数顺序注释特别标注了踩坑
     ——写成 `(hom, "false", "constant")` 会报 #3147 错误；
     `"false"` = 输出与输入同幅面（目标回标准位姿、画幅不变），出界部分填黑；
5. **标注图** + 主界面发布。

### 7.6 失败语义总结

| 情况           | 结果                           |
| ------------ | ---------------------------- |
| 输入图空         | Fail                         |
| 配方名不在库里      | Fail（列出现有名字）                 |
| 模板未学习 / 载荷损坏 | Fail（提示去配置界面学/重学）            |
| 找不到目标        | Fail，**但标注图照常输出**（原图+红字）     |
| 标注渲染失败       | **不影响**端口数据（MatchCount/位姿照常） |
| 任何算子异常       | Fail（带 ex.Message）           |

> 核心原则：**数据和诊断分离**。位姿数据找不到就是失败（下游别猜）；
> 但"看到的现场"永远要给操作员留一张图。

## 8. 图像渲染详解

### 8.1 共用渲染口 `RenderAnnotated`（1888 行）

模板预览（绿轮廓）和运行标注图（命中轮廓+文字）共用一个离屏渲染函数：

```
底图画进窗口 → 叠加轮廓（指定颜色/线宽）→ 左上角白底框文字 → dump 成 HImage
```

三个关键防坑设计：

1. **窗口缓存复用**：HALCON 反复 open/close 窗口会触发 #9302 死锁（仓库既有结论）。
   所以 `_previewWindow` 缓存着，**尺寸不变就复用**，变了才关旧开新，`Dispose` 时统一关；
   渲染全程 `lock (_previewGate)`——多线程同时渲染会把窗口状态搅乱；
2. **显式钉住** **`SetPart`**：不设的话本机实测 part 会被撑到参考图全幅，
   底图缩在左上角一小块，其余全黑；
3. **dump 回读立刻释放**：`new HImage(shot)` 拿到独立句柄后，`shot` 本身**立刻 Dispose**
   ——HALCON 对象是引用计数语义，注释实测：卡尺插件 500 次不释放约漏 160MB。

### 8.2 运行标注图 `RenderResultAnnotation`（1697 行）

- 把模型轮廓按每个命中的位姿摆放（`PlaceContoursAtPoses`，public 静态——
  抽成 public 是为了让冒烟测试能直接断言"度→弧度"换算，防双重转换 bug 复发）；
- 命中：绿轮廓 + 两行文字（实例数/最高分 + 位置/角度）；
- 未找到：原图 + 红字"未找到目标（要求分数 ≥ 0.50）"；
- 文字带**白底框**（`"box_color","white"`）——任何背景上都读得清。

### 8.3 模板预览 `UpdateTemplatePreview`（1801 行）

左下角那个小图的做法：

1. 算模板区域的**轴对齐包围盒**（旋转的矩形取外接正框）：
   `halfH = |sin φ|·半长 + |cos φ|·半宽`（旋转矩形的投影公式），四周各留 6px 边距；
2. `crop_rectangle1` 裁出局部图；
3. 模型特征轮廓**平移**到裁剪坐标系（纯平移，`VectorAngleToRigid(0,0,0, row−r1, col−c1, 0)`）；
4. 离屏窗口上叠画成绿色，dump 回 HImage；
5. 特征叠加失败 → 退回**纯裁剪**（预览仍然有），绝不影响已学的模板。

## 10. 手把手使用指南

### 10.1 第一次学习模板（5 分钟上手）

1. **搭流程**：流程里先放一个「图像采集」，再放「模板匹配」，把前者的图像输出连到后者的 `Image` 端口；
2. **打开配置**：双击模板匹配步骤 → 配置界面打开，若流程刚试运行过，画布会自动显示上游图；
   否则在"参考图路径"填一张本地图片，点「载入」；
3. **画模板区域**：画布上**右键 → 新建矩形**，框住产品的特征部位。
   > 框选诀窍：框**纹理丰富的部分**（边缘多、细节多），别框大平面——
   > 平面没有特征，模型学了个寂寞。也别框进反光面和每次都会变的东西；
4. **（可选）涂抹**：区域内有反光/会变的部分？涂抹模式下拉选"绘制涂抹"，把它涂橙。
   涂错了选"擦除涂抹"找回来。点「清除涂抹」可全部重来；
5. **调提取参数**（一般默认就行）：默认 -180°\~180° 全角度、自动对比度、5 层金字塔；
6. **点「学习模板」**：信息栏变绿，显示"模板「模板1」已学习：金字塔 X 层，角度 …"，
   左下角出现带绿色特征轮廓的预览——绿线就是模型"记住的边"；
7. **保存**：点确定关闭配置（`OnConfirm` 把整个模板库序列化进方案）。

### 10.2 多产品（配方）怎么配

1. 列表区点「新增」→ 自动出现"模板2"（重名自动规避，上限 20 条）；
2. 每条各自：改**名字**（如"型号A"/"型号B"）→ 载各自参考图 → 框区域 → 学习；
3. 把最常用的那条选中，点「设为默认」；
4. 流程里把上位机/变量连到 `RecipeName` 端口，运行时送"型号A"就用 A 的模板。
   `MatchedTemplate` 输出端口可以接回记录系统，追溯每帧实际用了哪个配方。

### 10.3 旋转/缩放怎么配

- **目标会转**：把角度范围设为实际需要的区间（如流水线上只 ±30°，
  就填 -30\~30——**范围越小搜索越快**，不必每次都 ±180）；
- **目标远近/大小会变**：勾选"启用缩放"，按实际波动填倍率（如 0.9\~1.1）。
  不需要就别开——缩放搜索明显更慢。

### 10.4 下游怎么用位姿

- **直接用坐标**：`Row`/`Column`/`Angle` 连到下游（机器人抓取、点胶坐标换算…）；
- **用归一化图（推荐）**：保持"输出位姿归一化图像"开启，把 `AlignedImage`
  连给画框裁剪/Blob/卡尺——这些插件全按**固定坐标**配置，目标永远回到学习位姿，
  一个都不用改。

### 10.5 运行时看结果

「显示窗口」选 1\~9，运行时标注图（绿轮廓+分数+位置文字）自动发布到主界面对应窗口；
填 0 则不发布。没找到目标时窗口显示**原图+红字原因**，现场一眼可判。

## 11. 参数调节速查表

### 匹配参数（运行行为，随时改不用重学）

| 症状            | 调哪个               | 往哪调                    |
| ------------- | ----------------- | ---------------------- |
| 找不到目标（分数不够）   | `MinScore` 分数下限   | ↓ 调低（0.3\~0.5），但太低易误匹配 |
| 同一个目标报了好几个    | `MaxOverlap` 重叠上限 | ↓ 调低（0.1\~0.3）         |
| 图里有很多个目标只报了一个 | `MaxMatches` 匹配数  | ↑ 调大                   |
| 匹配太慢          | `Greediness` 激进度  | ↑ 调高（0.8→0.9）；或收窄角度范围  |
| 匹配偶尔漏掉该找到的    | `Greediness` 激进度  | ↓ 调低（0.8→0.6\~0.7）     |

### 提取参数（改了必须重新学习！）

| 想要            | 调哪个                                        |
| ------------- | ------------------------------------------ |
| 光照变化大、对比度不稳   | `GradientThreshold` 保持 0（自动）；或按实际梯度手填      |
| 目标黑白可能反转（正反面） | `UsePolarity` 关掉（匹配变慢一点）                   |
| 模板小、搜索慢       | `NumLevels` ↑（小模板层数多了快）；模板大且要精度则 ↓         |
| 角度精度不够        | `AngleStepDeg` ↓（步长越小角度越精，但学习越慢）；或交 "auto" |

### 学习质量自查

| 现象              | 原因与对策                      |
| --------------- | -------------------------- |
| 预览里绿轮廓很少/几乎没线   | 区域里特征太少 → 换纹理丰富的部位，或降低梯度阈值 |
| 匹配位置系统性偏 1\~2px | 正常应已被原点锚定消除；仍偏则重学一次        |
| 每次打开都提示"需重新学习"  | 检查是否动过参数；掩膜口径问题已在当前版本修复    |

## 12. 常见问题与排查（FAQ）

**Q1：运行报"未知产品：XXX 没有对应模板（库里有：模板1，模板2）"**
配方名与模板名没对上（大小写/空格）。核对 `RecipeName` 送来的值与列表里的名字**逐字符一致**；或用 `MatchedTemplate` 输出确认当前实际选中项。

**Q2：配置里明明已学习，运行却报"尚未创建模板"**
旧版本 bug（解析只放在 Initialize，运行实例不走它）。当前版本已修——解析放在 `ApplyConfigValues`（编译运行实例也会执行）。若仍出现，确认配置点过「确定」保存。

**Q3：改了参数没重新学习，会怎样？**
界面徽标变橙色"参数已改·需重新学习"；运行仍用**旧模型**。指纹机制在提醒你：改的是"创建态"参数，不重学不生效。

**Q4：匹配分数高但位置不对/轮廓画歪？**
先确认角度单位：端口一律是**度**。历史上有过"弧度当度双重转换"事故——端口数值对、只有标注图轮廓不转。若数值也偏，检查模板区域是否框进了会动的部分。

**Q5：AlignedImage 边缘有黑边？**
正常现象：`"false"` 模式保持画幅不变，目标转回标准位姿后，原画面边缘的部分出界了，出界处填黑（"constant" 填充）。下游检测区域避开画幅边缘即可。

**Q6：换了一台电脑，模板还在吗？**
在。模型以 base64 存在方案 JSON 里，方案拷走模板跟着走。但**参考图路径**是本机路径——只影响"重新打开配置时的画布显示/重学"，不影响运行匹配。

**Q7：能放多少个模板？**
上限 20 条（`.vms` 体积防护，满了会有明确提示）。注释建议：多产品大批量场景考虑**拆流程**。

**Q8：图像是彩色的，模板要用彩色特征吗？**
Shape matching 本质用灰度梯度。插件学习/运行都统一转灰度（含 4 通道 RGBA/BGRA 相机图），黑白特征才稳定。需要颜色信息请用「区域颜色检查」等插件。

**Q9：失败时下游拿不到结果会怎样？**
步骤 Fail，下游按流程的失败策略处理（停止/跳过）。**标注图仍会输出**——`MeasureImage` 在未找到时也有值（原图+红字），方便现场排查。

**Q10：为什么我的流程每次编译都很慢？**
若你改过旧版代码：当时配置态没隔离，编译一次就读图/建模/开离屏窗口。当前版本用 `_isConfigInstance` 隔离了这些"给人看"的动作。

## 14. 预备知识：读懂代码前必须会的 6 个概念

### 14.1 HALCON 的三类对象（HImage / HRegion / HObject / HTuple）

HALCON 是 C/C++ 写的底层库，C# 只是它的"外壳"（封装）。它有三个基本数据类型：

| 类型        | 是什么                                                           | 生活比喻                  |
| --------- | ------------------------------------------------------------- | --------------------- |
| `HImage`  | 一张图片（灰度/彩色像素矩阵）                                               | 一张照片                  |
| `HRegion` | 一片区域（一堆像素坐标的集合，不含像素值）                                         | 一张剪纸：只有形状，只有"哪些位置被选中" |
| `HObject` | HALCON 的"万能口袋"：图像、区域、轮廓（XLD）都能装。`HOperatorSet` 老式 API 的出参多半是它 | 一个不透明袋子，掏出来才知道装的什么    |
| `HTuple`  | 元组：一串数字/字符串/句柄的数组，长度可变                                        | 一排可以放任何东西的格子          |

**调用 HALCON 算子的两种写法**（本插件两种都有）：

```csharp
// 写法一：静态方法 HOperatorSet.XXX（老式，参数全是 out，性能无差）
HOperatorSet.GenCircle(out HObject circle, row, col, radius);
// 意思：调用"生成圆形区域"算子，输入 row/col/radius，输出放进了 circle

// 写法二：对象方法（新式，更接近自然语言）
var smaller = image.ReduceDomain(region);  // "把 image 的有效范围缩到 region 里"
```

> 记住一个通式：**几乎每个算子都是"输入对象 + 参数 → 输出对象"**。
> 看到 `HOperatorSet.Something(input, param, out output)`，
> 就翻译成："对 input 做Something（用 param 这个设置），结果放进 output"。

### 14.2 为什么要疯狂 Dispose（释放内存）

HALCON 的图像/区域是**非托管内存**（不归 C# 的垃圾回收器管）。
你 new 一个 500 万像素的 HImage，GC 根本看不见它——
不手动 `Dispose()`，它就一直在内存里赖着，直到软件崩溃。

所以你会看到本插件到处是这样的代码：

```csharp
finally
{
    foreach (var o in temp)     // temp 是整个过程攒下来的中间对象列表
    {
        try { o?.Dispose(); }   // 一个个释放
        catch { }               // 释放失败也不管——收尾不能抛异常打断主流程
    }
}
```

三种常见释放姿势，全在本插件出现：

```csharp
// 姿势1：using —— 作用域结束自动释放（最推荐）
using var region = GenTemplateRegion();   // 方法一返回，region 自动 Dispose

// 姿势2：try/finally 手动释放（要跨越多段逻辑时）
HObject? placed = null;
try { placed = ...; }
finally { placed?.Dispose(); }            // ?. 意思是"如果 placed 不是 null 才调用"

// 姿势3：属性 setter 里换新弃旧
set {
    var old = _templatePreviewImage;      // 先记住旧的
    if (SetProperty(ref _templatePreviewImage, value))
        old?.Dispose();                   // 换成功后把旧的释放
}
```

> 小白常见疑问：`o?.Dispose()` 前后的 `try { } catch { }` 是不是多余？
> 不是。Dispose 的是**底层 C++ 对象**，句柄可能已经失效（比如窗口刚被关了），
> 再 Dispose 会抛异常——但收尾代码抛异常会把真正的业务异常"顶掉"，
> 所以一律吞掉。这是非托管资源清理的行业标准写法。

### 14.3 INPC：界面怎么"自动"跟着数据变

WPF 的绑定机制：XAML 里写 `Text="{Binding Name}"`，
界面就显示 `Name` 属性的值。但**属性变了界面不会自动知道**——
除非这个类实现了 `INotifyPropertyChanged` 接口（简称 INPC），
并且在 setter 里"喊一嗓子"。

```csharp
public event PropertyChangedEventHandler? PropertyChanged;
// event = 事件：别人可以"订阅"它，喊的时候订阅者都会收到

private void OnChanged(string name) =>
    PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));
// ?.Invoke = "如果有人订阅就通知他们"；参数里带上"变的是哪个属性"的名字
```

界面收到通知后，回头重新读一遍这个属性，刷新显示。整个链条：

```
代码里 Name = "型号A"
  → setter 执行 OnChanged("Name")
  → WPF 绑定引擎收到PropertyChanged事件
  → 引擎重新读取 Name 属性
  → 界面上的文本框变成"型号A"
```

### 14.4 ObservableCollection：集合变化也能"喊"

`List<T>` 只有元素能喊（配合 14.3）。而**列表本身**增删元素时，界面怎么知道？
用 `ObservableCollection<T>`——它在 Add/Remove/Clear 时自动触发
`CollectionChanged` 事件，绑定它的 ListBox/ItemsControl 会自动增删对应的行。

本插件里 `Library`（模板列表）和 `CanvasRois`（画布上的框）都是它。
插件还**订阅**了 CollectionChanged 来做自己的事：

```csharp
CanvasRois.CollectionChanged += OnCanvasRoisChanged;
// += 的意思：把 OnCanvasRoisChanged 方法"挂"到这个事件上，事件发生就调用它
```

### 14.5 端口（InputPort / OutputPort）：步骤之间的水管

流程编辑器里你看到的连线，背后是端口对象：

```csharp
public InputPort<HImage> Image { get; } = new("Image", ...)   // 进水口：等着上游灌水
public OutputPort<double> Score { get; } = new("Score", ...)  // 出水口：算完把水放出来
```

- 连线时：上游的 OutputPort 值自动流进下游的 InputPort；
- 代码里取输入：`Image.GetTypedValue()`（拿到强类型 HImage）；
- 代码里写输出：`Score.Value = 0.95`；
- `InputPort` 还能不连线、直接在属性面板里填**常量**——
  `ActualValue` = "连了线用线上的值，没连用你填的常量"。

### 14.6 序列化：方案文件是怎么保存的

方案（.vms）本质是个 JSON 文件。保存时，框架把每个步骤的
`[StepConfig]` 属性收集成键值对写进去（**序列化**）；
打开时再按名字灌回去（**反序列化**）。
所以：

- 加 `[StepConfig]` 的属性 → 自动随方案保存，不需要你写任何文件读写代码；
- 不加 → 关闭软件就丢（这类叫"会话态"，比如画布上正在拖的框）；
- base64：把**二进制**（模型文件、PNG 图）变成**纯文本字母**的编码方式。
  JSON 里放不了二进制，就先 base64 变成 `AAAAfQ==` 这样的字符串再放。

### 第 3 段：生成模板区域并挖涂抹洞（879\~893 行）

```csharp
using var region = GenTemplateRegion();
// GenTemplateRegion（1207 行）按 CanvasShape 三选一：
//   Circle  → HOperatorSet.GenCircle(out circle, p[0], p[1], p[2]);
//   Ellipse → HOperatorSet.GenEllipse(out ellipse, p[0], p[1], p[2], p[3], p[4]);
//   其他    → HOperatorSet.GenRectangle2(out rect, p[0], p[1], p[2], p[3], p[4]);
// using = 这个 region 在方法结束时自动释放（14.2 的姿势1）

using HRegion? exclusion = BuildSmearExclusion(region);
// BuildSmearExclusion（452 行）：算出"要挖掉的洞"
//   有效排除域 =（绘制涂抹 − 擦除涂抹）∩ 模板区域
//   ① BuildRawSmearRegion()：绘制减擦除 → 用户真正想涂掉的部分
//   ② Intersection(raw, templateRegion)：再和模板区域求交 → 涂到框外的不算
//   ③ AreaCenter 查面积：交完面积是 0（全涂在框外）→ 返回 null = 没有洞
// 返回的是新实例（"归调用方释放"），所以用 using 接。

HObject domainSource = region;            // 默认：模型域 = 整个模板区域
HObject? effective = null;
if (exclusion != null)                    // 有洞才挖
{
    HOperatorSet.Difference(region, exclusion, out HObject effectiveDomain);
    // Difference = 区域减法：region − exclusion → 带洞的区域
    effective = effectiveDomain;
    domainSource = effective;             // 模型域换成"带洞版"
}

HOperatorSet.ReduceDomain(DisplayImage, domainSource, out HObject reduced);
temp.Add(reduced);
// ReduceDomain 不复制像素！只是给 DisplayImage 盖个章：
// "今后涉及你的计算，只有 domainSource 范围内的像素有效"。

```csharp

            HOperatorSet.SetShapeModelOrigin(
                entry.RuntimeModelId,
                sr[0].D - CanvasRect[0],    // 行补偿 = 找到的行 − 你画框中心的行
                sc[0].D - CanvasRect[1]);   // 列补偿同理
    }
    else { /* FindShapeModel 同款，少两个缩放参数 */ }

逻辑拆解：

1. 让模型**在参考图上找它自己**——同一个区域、同一张图，必然以接近 1.0 的分数命中；
2. 命中位置 `sr[0], sc[0]` 就是"HALCON 默认原点认为模板在哪"；
3. 它和你画的框中心 `CanvasRect[0], CanvasRect[1]` 的差 = 原点偏差；
4. `SetShapeModelOrigin` 把这个偏差写进模型——此后每次 find 输出的
   Row/Column 都自动校正为"你框的中心"。

为什么整个 try/catch 只配一句注释？——补偿是**锦上添花**：
失败了输出会偏 1\~2px（精度略降），但功能完好。不值得为它让学习失败。

**方向为什么是减法？**（注释原话："与直觉相反，别修回减法"）
推导：`find 输出 = 真实位置 + 默认原点偏移`。
我们想让它输出"画布中心"，即
`输出' = find输出 − (find输出 − 画布中心) = 画布中心`，
所以补偿量 = `find输出 − 画布中心`（本次实测值），存进模型后永久生效。

## 19. 配置界面交互闭环：从"你点按钮"到"代码执行"的完整路径

前面讲了"代码做什么"，这一章讲**界面和代码怎么连起来**——
小白最困惑的往往是"我点了一下按钮，计算机怎么知道该跑哪个方法？"
我们追一条完整的链。

### 19.1 链条的第一环：DataContext（视图的"大脑"挂载）

配置界面打开时，宿主调用：

```csharp
public object GetConfigView(IStepConfigData stepData)
{
    Initialize(stepData);          // 盖"配置实例"章 + 灌配置值 + 播种画布
    ...
    return new MatchingView { DataContext = this };
    //                     ★ 关键：把插件自己设为界面的 DataContext
}
```

`DataContext = this` 的意思：**"这个窗口里所有** **`{Binding XXX}`** **都到我这找 XXX 属性/命令"**。
从此 XAML 与 C# 建立了联系。

### 19.2 三种交互路径（对应三种控件类型）

**路径 A：按钮 → 事件转发（code-behind 一行）**

以「学习模板」按钮为例，共 3 站：

```xml
<!-- 站1：XAML 里声明按钮（MatchingView.xaml）-->
<Button Content="学习模板" Click="OnCreateTemplateClick" />
<!-- Click="方法名"：点击时调用 code-behind 里叫这个名字的方法 -->
```

```csharp
// 站2：code-behind 转发（MatchingView.xaml.cs，全文 35 行之一）
private void OnCreateTemplateClick(object sender, RoutedEventArgs e)
    => Plugin?.CreateTemplate();
// Plugin = DataContext as MatchingPlugin（把"大脑"从基类强转回具体类型）
// ?.     = 万一 DataContext 不是它（不可能，但保险），就什么都不做
```

```csharp
// 站3：业务方法执行（MatchingPlugin.cs）
public void CreateTemplate() { ... }   // 第 17 章讲过的 9 段
```

**为什么转发层必须存在、却只有一行？**
如果直接在 code-behind 写业务（老式 WinForms 风格），业务就**焊死在界面上**——
自动化测试没法不开窗口就调用它。转发层的存在让"视图零逻辑"成立。

**路径 B：输入框 → 绑定（连转发层都不用）**

以角度下限输入框为例：

```xml
<TextBox>
    <TextBox.Text>
        <Binding Path="EditingEntry.MinAngleDeg" UpdateSourceTrigger="PropertyChanged">
            <!-- Path：绑插件 DataContext 的 EditingEntry 属性的 MinAngleDeg 属性
                 （两跳：先找当前编辑条目，再找它的角度字段）-->
            <!-- UpdateSourceTrigger=PropertyChanged：每敲一个字符就写回源
                 （默认 LostFocus 是"失焦才写"，拖数字框体验差）-->
        </Binding>
    </TextBox.Text>
</TextBox>
```

数据流：**你敲 "-30" → WPF 写回** **`EditingEntry.MinAngleDeg`** **→ setter 执行三段式
（比较/赋值/OnChanged）→ 事件传回界面刷新其它绑定了同属性的控件**
（比如"需重新学习"徽标——插件订阅了 `EditingEntry.PropertyChanged`，
见 `OnEditingEntryChanged` → `TouchModelStaleness`）。

**路径 C：下拉框 → 索引中转**

极性下拉框比较特别——它绑的不是布尔本身，而是一个"翻译属性"：

```csharp
// XAML：SelectedIndex="{Binding PolarityIndex}"   （下拉框只认 0/1/2…索引）
public int PolarityIndex
{
    get => EditingEntry?.UsePolarity == false ? 1 : 0;
    // 读：布尔 → 索引。false→1（忽略极性），其它（true/null）→0（使用极性）
    set
    {
        if (EditingEntry != null)
            EditingEntry.UsePolarity = value == 0;
        // 写：索引 → 布尔。选 0 就是"使用极性"
    }
}
```

为什么多这一层？——XAML 下拉框天生操作**索引**，数据本体是**布尔**，
总要有个地方做翻译。放 C# 里（比放 XAML Converter 里）能用 IDE 跳转和断点，好维护。

### 19.3 画布交互：最复杂的一条链

画布（ImageEdit 控件）同时有 **7 个绑定**在跑：

```xml
<h:ImageEdit
    HImage="{Binding DisplayImage, Mode=OneWay}"
    <!-- 底图：插件 → 控件，单向（用户不直接改图）-->
    DrawObjectList="{Binding CanvasRois}"
    <!-- 框列表：双向。控件新建/拖拽 ROI 会增删这个集合，插件播种也会往里灌 -->
    ActiveRoi="{Binding CanvasActiveRoi, Mode=TwoWay}"
    BrushRadius="{Binding BrushSize, Mode=TwoWay}"
    SmearDraw="{Binding SmearMask, Mode=TwoWay}"
    SmearErase="{Binding SmearEraseRegion, Mode=TwoWay}"
    SmearMode="{Binding CanvasSmearMode, Mode=TwoWay}" />
    <!-- 涂抹四件套：当前笔迹/擦除笔迹/模式/笔刷大小，全部双向 -->
```

**用户画一个框的完整旅程**：

```
① 你在画布上拖出矩形
② ImageEdit 控件内部生成 DrawingObjectInfo（带 5 个坐标 HTuple）
③ 控件把它 Add 进 DrawObjectList（= 插件的 CanvasRois 集合）
④ ObservableCollection 触发 CollectionChanged
   → 插件的 OnCanvasRoisChanged 被调用
   → 先查 _seedingCanvas：是系统回填吗？是 → 直接返回（防震荡）
   → 给新 ROI 挂上 PropertyChanged 监听（拖拽手柄时也要感知）
   → 调 WriteBackTemplate()
⑤ WriteBackTemplate：取最后一个 ROI → PadParams 统一成 5 参数
   → 写进 CanvasShape/CanvasRect（会话态）
   → 写进 EditingEntry.Shape/Rect（档案态！）
   → TouchModelStaleness() → 徽标变橙"参数已改·需重新学习"
```

注意 ④ 里"只认最后一个"的细节（`OnRoiTuplesChanged`）：

```csharp
if (!ReferenceEquals(info, CanvasRois.LastOrDefault()))
    return;   // 不是最新的框？忽略。模板只有一个区域，旧框作废
```

### 20.2 追踪「角度范围」（提取参数类——多一个条目站）

角度和分数不同：它属于**条目**，而且要被"烤"进模型。多两站：

```
界面 EditingEntry.MinAngleDeg
   →【条目 setter】三段式 INPC
   →【指纹联动】OnEditingEntryChanged → TouchModelStaleness
        → 徽标"参数已改·需重新学习" ★ 这是提取参数独有的哨卡
   →【学习时装箱】CreateTemplate：Clamp → 换向 → 度转弧度 → 传给 CreateShapeModel
   →【写进模型】角度范围从此成为模型二进制的一部分（base64 落库）
   →【运行时取用】RunAlgorithm 从 entry（不是从界面属性！）读角度：
        Math.Clamp(entry.MinAngleDeg, ...) —— 再次消毒（防条目被手改坏）
   → find_shape_model(minAngleRad, angleExtent, ...)
```

**为什么运行时从条目读、不从界面属性读？**
运行实例根本没有"界面"——`EditingEntry` 是配置态概念。
条目（`Library`）才是从 `TemplateLibraryJson` 反序列化出来的**唯一事实来源**。
这呼应了 16.2 的界河：配置走 `[StepConfig]`/条目，会话态只服务界面。

### 20.3 追踪「配方名 RecipeName」（跨步骤类——最长的链）

```
【上游】上位机 TCP 写变量 / 上游步骤输出
   → 流程引擎把值灌进本步骤的 RecipeName 端口
   →【端口】InputPort<string>.Value 更新（触发 PropertyChanged）
        │
        ▼

                   │
                   ▼
        结果五元组（弧度）──度──▶ 输出端口 ──▶ 下游步骤
```

### 20.5 从这条链学到的三条工程铁律

1. **用户输入永不信任**：任何进 HALCON 的数值前必有 Clamp/换向/判空——
   界面是给人用的，人一定手滑；
2. **一个数据一个事实来源**：角度范围的事实来源是条目（不是界面控件），
   模型句柄的事实来源校验是 `RuntimeModelSource == Model`——
   出现两个"真相"的地方迟早打架（踩坑 #4 的掩膜口径就是教训）；
3. **错误信息是产品**：`"未知产品：X（库里有：A，B）"`、
   `"分数 ≥ 0.01（可降低分数下限重试）"`——每句话都替下一步动作指路。
   这不是客气，是产线停机时间直接取决于排查速度。

## 21. 相机拍到的到底是什么：像素与灰度

### 21.1 数字图像 = 一张巨大的数字表格

忘掉"照片"这个直观印象。工业相机拍到的，其实是一张**填满数字的表格**：

```
一张 640×480 的灰度图 = 480 行 × 640 列的表格，
每个格子里一个数字，范围 0~255：

列→   0    1    2    3   ...  639
行0 [ 45 | 47 | 52 | 60 | ... | 38 ]
行1 [ 46 | 48 | 55 | 63 | ... | 40 ]
行2 [ 44 | 46 | 51 | 58 | ... | 36 ]
...
行479[ ... ]
```

- 每个格子叫一个**像素**（pixel，picture element）；
- 格子里的数字叫**灰度值**（gray value）：0 = 纯黑，255 = 纯白，中间是深浅不一的灰；
- 表格的行数×列数叫**分辨率**：640×480 = 30.7 万个格子。

所以"计算机看图"的本质是：**读表格里的数字，做数学题**。
模板匹配也不例外——后面你会看到它全程都在做减法和比大小。

### 21.2 彩色图 = 三张灰度图叠在一起

彩色相机的每个像素有**三个**数字：

```
彩色像素 = (R, G, B) = (200, 30, 40)   ← 一个偏红的颜色
```

- R 通道：这个像素有多红（0\~255）
- G 通道：有多绿
- B 通道：有多蓝

三张单色表格叠起来才是一张彩图。这就是第 17 章 `TryToGrayImage` 里
`CountChannels` 数通道数、3 通道要转灰度的原因——
**模板匹配只用灰度那张表**（颜色信息它不看）。
插件的统一口径：不管你喂彩色还是带透明通道的图，都先转成单通道灰度表再匹配。

> 为什么转灰度不丢重要信息？——因为模板匹配认的是**形状边缘**（明暗变化），
> 而明暗变化在灰度表里体现得最纯粹。颜色对它反而是干扰项。

### 21.3 行/列：为什么坐标是 (Row, Column) 而不是 (X, Y)

插件输出 `Row`（行）和 `Column`（列）。注意顺序——**行在前**！

```
         列 Column →
      ┌─────────────────┐
  行  │ (0,0)     (0,639)│
  Row │                  │      一个像素的坐标 = (行, 列)
  ↓   │ (479,0)  (479,639)│      原点在【左上角】！
      └─────────────────┘
```

- **Row 向下增长**（数学课的 Y 轴向上，这里相反，别搞混）；
- 原点在**左上角**，不是中心也不是左下；
- 后面所有"位置 (900, 500)"都读作"第 900 行、第 500 列"= 从顶往下 900、从左往右 500。

这是 HALCON 和整个图像处理界的通用约定（数学书上的坐标系不一样）。
插件端口、日志、标注文字里的位置，全部是这个口径。

### 21.4 一个像素有多大？——分辨率与视野的关系

像素本身没有物理大小！同一个 500 万像素相机：

- 视野（拍到多大范围）= 100mm → 每像素 ≈ 100/2448 ≈ **0.04mm**
- 视野 = 500mm → 每像素 ≈ **0.2mm**

这个值叫**像素当量**（一个像素代表多少毫米），现场最重要的数字之一：

- 你要求定位精度 ±0.05mm → 像素当量必须明显小于它（比如 ≤0.02mm），
  否则"亚像素"再准也没用（地基就歪了）；
- 第 11 章速查表里"调容差/精度"，先确认像素当量够不够，再谈参数。

**现场速算**：像素当量 ≈ 视野宽度(mm) ÷ 相机横向像素数。
拿尺子量一下画面里实际拍到的宽度，除一下就出来。

### 21.5 灰度直方图：一张图体检报告

把整张表里 0\~255 各灰度值的像素数量画成柱状图，就是**直方图**：

```
像素数
  │      ██
  │      ██                    ████
  │     ████                  ██████
  │  ██████████            ████████████
  └──────────────────────────────────── 灰度
  0     暗        中间调         亮    255
  （背景）                    （目标）
```

- 柱子**挤在左边**（全暗）→ 曝光不足；
- 挤在右边（全亮）→ 过曝，边缘信息被"晒没了"；
- **两个分离的峰**（暗背景+亮目标）→ 理想状态，边缘清晰，匹配最稳。

判断光照好不好，不用懂任何算法——看直方图是不是"双峰分得开、不过曝"。
这就是第 24 章打光原则的数学基础。

### 21.6 通道、幅面与三个易混词

| 词         | 意思                             | 插件对应                           |
| --------- | ------------------------------ | ------------------------------ |
| 通道        | 每个像素用几个数字描述（灰度=1，RGB=3，RGBA=4） | `TryToGrayImage` 的分支依据         |
| 幅面        | 图的宽×高（像素数）                     | AlignedImage 保持同幅面（"false" 参数） |
| Domain（域） | 图上的"有效范围印章"：数据都在，但只处理盖章的部分     | `ReduceDomain` 盖章（17 章第 3 段）   |

> Domain 是 HALCON 特色：它**不复制不裁剪像素**，只记"哪些范围参与计算"。
> 所以 reduce\_domain 几乎零耗时，比真的裁图便宜得多。

## 22. 五个核心概念：梯度 / 极性 / 金字塔 / 亚像素 / 位姿

这五个词就是插件界面上全部参数背后的"视觉学"。每个都配小图和参数对照。

### 22.1 梯度（Gradient）：明暗变化的剧烈程度

**梯度 = 相邻像素灰度值变了多少。** 表格视角一目了然：

```
一块均匀灰板的内部（没有梯度）：        物体的边缘（梯度巨大）：
列:   50   50   51   50   52           列:   50   52   200   198   202
                                          ↑
                                     一步从 52 跳到 200，变化 148！
```

- 平坦区域：相邻数字几乎一样 → 梯度 ≈ 0 → **没有信息**；
- 物体边缘：数字猛跳 → 梯度巨大 → **这就是"形状"所在**。

**插件对应参数：「梯度阈值」（GradientThreshold）**

HALCON 提取特征时的规则：梯度 ≥ 阈值的点留下当"特征点"，其余扔掉。

```
阈值调低（如 10）→ 连轻微的纹理变化都留下 → 特征点多、模型"啰嗦"、
                  噪声反光也可能混进来
阈值调高（如 60）→ 只留最硬的轮廓线 → 模型精炼、抗干扰，
                  但特征太少会匹配不稳
阈值 = 0（auto）→ HALCON 扫描全图自动选一个，一般够用
```

> 为什么模板要框"纹理丰富"的区域？——平坦区梯度全是 0，等于框了一片"没有特征的荒地"。
> 绿色预览轮廓（`GetShapeModelContours`）画的就是**留下来的那些特征点**。

### 22.2 极性（Polarity）：边缘的"黑白方向"

边缘不止有"跳了多大"（梯度），还有"从暗到亮还是从亮到暗"——这就是**极性**。

```
从暗到亮的边（+ 极性）：         从亮到暗的边（− 极性）：
  暗 ││ 亮                        亮 ││ 暗
  50 ││ 200                       200 ││ 50
     ↑从左到右：灰度上升               ↑灰度下降
```

**插件对应参数：「使用极性」（UsePolarity，默认开）**

- 开：模板记下每条边的方向，搜索时方向**必须一致**才算命中
  → 候选少一半，**搜索明显变快、更不易误匹配**；
- 关：不管方向，只看变化幅度 → 目标黑白反转也能找到（比如同一零件的正反面），
  代价是慢一点、可能把"反色的相似物"也当命中。

> 现场口诀：目标永远同色 → 开（默认）；目标可能黑白颠倒（翻面来料）→ 关。

### 22.3 金字塔（Pyramid Levels）：先粗后精的找法

**图像金字塔 = 把原图逐级缩小一半叠成一摞**（像金字塔，顶上最小）：

```
第5层  ██          1/32 大小（最模糊）
第4层  ████        1/16
第3层  ████████    1/8
第2层  ████████████ 1/4
第1层  原图         （最清晰）
```

**为什么要缩小？速度。** 在 500 万像素原图上挨个位置试模板要算几百万次；
缩到 1/32 后只有几**千**次——先在顶层（小图）粗扫出"可能在这几个位置"，
再逐层往下、只在候选附近精修。计算量断崖式下降。

**插件对应参数：「金字塔层数」（NumLevels，默认 5）**

| 情况         | 建议                          |
| ---------- | --------------------------- |
| 模板很小（几十像素） | 层数多些（6\~8）：顶层才不会小到没内容       |
| 模板巨大       | 层数少些（3\~4）：顶层太大照样慢          |
| 找不到/定位抖    | 减 1\~2 层试试（层数太多顶层糊成一片，粗找会偏） |

> 学习和运行必须同层数（参数烤进模型了，见 2.2）——
> 这就是为什么 NumLevels 属于"提取参数"，改了必须重新学习。

### 22.4 亚像素（Sub-pixel）：0.4 个像素是怎么算出来的

匹配输出 `Row = 512.347`——行号怎么可能是小数？

因为**边缘的真实位置在两个像素之间**。放大看一条边缘：

```
列:     100    101    102    103
灰度:    55     58    190    195
                ↑
        跳变发生在 101 和 102 之间！
        用两边灰度加权一算（类似求重心）：
        真实边缘位置 ≈ 101.42
```

HALCON 的 `"least_squares"`（最小二乘，find 参数之一）会拿特征点**拟合出连续曲线**
再求交点，把位置精确到像素内的小数——精度能到 1/10 甚至 1/20 像素。

**这就是"亚像素"三个字的全部含义：像素内部的位置细分。**

> 但注意 21.4 的铁律：亚像素精度 ÷ 像素当量 = 物理精度。
> 像素当量 0.2mm 时，1/10 像素也只有 0.02mm；
> 像素当量 0.5mm 时，再亚像素也救不了——先把镜头/视野配对。

### 22.5 位姿（Pose）：位置 + 角度 = 一个"姿态"

**位姿 = "在哪里" + "转了多少度"**，两个数打包：

```
位姿 = (Row=512.3, Column=340.7, Angle=23.5°)

只说"在哪"（位置）────▶ 目标可能是歪的，抓取/测量会翻车
位置+角度（完整位姿）──▶ 下游可以精确补偿旋转
```

**插件对应端口：`Row`** **/** **`Column`** **/** **`Angle`（标量 = 最高分实例）**

`AlignedImage` 就是位姿的图像化应用（2.4②）：用位姿把目标**刚性搬回**学习位姿——
"刚性"= 只平移+旋转，不拉伸不缩放（物体不会因此变形）。

> 关于角度方向的提醒：图像坐标 Row 向下（21.3），
> 所以**屏幕上看顺时针旋转的目标，角度是负的**（数学上顺时针为负）。
> 别用"看起来"判断正负，用输出值实际验证一次最稳。

### 22.6 五概念 × 界面参数对照总表

| 概念  | 一句话     | 界面参数                   | 改了要重学？ |
| --- | ------- | ---------------------- | ------ |
| 梯度  | 明暗变化多剧烈 | 梯度阈值（0=自动）             | ✔      |
| 极性  | 边缘的黑白方向 | 使用极性开关                 | ✔      |
| 金字塔 | 先粗后精提速  | 层数（默认 5）               | ✔      |
| 亚像素 | 像素内位置细分 | 固定 least\_squares（不可调） | —      |
| 位姿  | 位置+角度打包 | 输出端口 Row/Column/Angle  | —      |

## 22A. HALCON 算子手册：本插件用到的每一个算子

> 前面代码里出现的 `HOperatorSet.XXX` 都叫**算子**（operator）——

> 通用读法（14.1 讲过，再强调一次）：
> `HOperatorSet.算子名(输入对象, 参数…, out 输出)` =

### A 组：生成形状与图像（"从零造出一个对象"）

#### `gen_circle` — 生成圆形区域

```csharp
HOperatorSet.GenCircle(out HObject circle, row, col, radius);
//                                    中心行 中心列 半径
```

- **用法**：给中心和半径，产出一个"剪纸圆"；
- **场景**：你明确知道"某处有个圆"（手填坐标、按测量结果画圈）；
- **本插件**：模板区域是圆时（`GenTemplateRegion`）。

#### `gen_ellipse` — 生成椭圆区域

```csharp
HOperatorSet.GenEllipse(out HObject ellipse, row, col, phi, ra, rb);
//                                     中心行 中心列 旋转角 长半轴 短半轴
```

- **场景**：斜着的长圆形区域（比旋转矩形"软"，做 ROI 很常用）；
- **本插件**：模板区域是椭圆时。注意 `phi` 用**弧度**——界面上你填的是度，
  存进条目的是弧度（15 章讲过统一 5 参数约定，第 3 位就是弧度角）。

#### `gen_rectangle2` — 生成任意方向矩形区域

```csharp
HOperatorSet.GenRectangle2(out HObject rect, row, col, phi, length1, length2);
//                                        中心行 中心列 旋转角 半长 半宽
```

- **场景**：**能转方向**的矩形（gen\_rectangle1 只能正着放）——工业 ROI 几乎都用它；
- **本插件**：模板区域是矩形时（默认形状）。

#### `gen_image_const` — 生成一张"素图"

```csharp
HOperatorSet.GenImageConst(out HObject img, "byte", width, height);
//                                      类型   宽     高
```

- **场景**：需要一张"白纸"往上画东西（生成掩膜、画布打底）；
- **本插件**：`MaskRegionToBase64` 里造掩膜底图（"byte" = 每像素 0\~255 一个字节）。

#### `gen_image_proto` — 把图像涂成统一灰度

```csharp
HOperatorSet.GenImageProto(proto, out HObject mask, 0);
//                                     涂成 0（全黑）
```

- **场景**：已有图像，想把它整体刷成某个灰度当底；
- **本插件**：紧接 gen\_image\_const，把素图刷全黑——之后只在涂抹区域画 255，
  一张"255=挖掉"的掩膜图就诞生了。

### B 组：区域运算（"剪纸的加减叠"）

区域（HRegion）就是剪纸（21.6）。三个算子对应三种剪纸动作：

#### `difference` — 减：A − B（从 A 剪掉 B 的部分）

```csharp
HOperatorSet.Difference(region, exclusion, out HObject withHoles);
//  region − exclusion = 带洞的区域
```

- **场景**：**挖洞**——匹配区域里去掉反光块、去掉会动的部件；
- **本插件**：CreateTemplate 里"模板区域 − 涂抹排除域"（17 章第 3 段），
  也用于"绘制涂抹 − 擦除涂抹"（`BuildRawSmearRegion`，你涂错的地方能擦回来就靠它）。

#### `intersection` — 交：A ∩ B（两片剪纸重叠的部分）

```csharp
HOperatorSet.Intersection(raw, templateRegion, out HObject clipped);
```

- **场景**：取**公共部分**——"涂的 + 框的"两条件同时满足才算；
- **本插件**：涂抹域 ∩ 模板区域（`BuildSmearExclusion`）——
  你手一抖涂到框外面，这部分自动不算数。

#### `area_center` — 问剪纸多大、重心在哪

```csharp
HOperatorSet.AreaCenter(region, out HTuple area, out HTuple row, out HTuple col);
//                             面积(像素数)   重心行   重心列
```

- **场景**：算区域大小/质心；**判空利器**——`area == 0` 就是空区域
  （比判 IsInitialized 更彻底，算子运算后可能产出"合法但空"的区域）；
- **本插件**：两处都用它做"运算结果是不是空"的检查（B 组两个算子之后）。

> **三个算子连用 = 涂抹的完整语义**：
> `(绘制 − 擦除) ∩ 模板区域`，再用 area\_center 验空——
> 插件的 `BuildSmearExclusion` 就是这三行。

### C 组：域与裁剪（"圈定工作范围"）

#### `reduce_domain` — 给图盖"有效范围章"（超便宜）

```csharp
HOperatorSet.ReduceDomain(image, domain, out HObject reduced);
// 意思：今后对 reduced 做运算时，只看 domain 圈里的像素
```

- **场景**：**大图上只处理一小块**——不复制像素，几乎零耗时；
- **本插件**：CreateTemplate 用它把图"圈"到模板区域（再喂给 create\_shape\_model）。
  为什么不真裁剪？省内存省时间，且掩膜坐标仍是参考图绝对坐标（好换算）。

#### `crop_rectangle1` — 真裁剪（按正框切一块出来）

```csharp
HOperatorSet.CropRectangle1(image, out HObject crop, r1, c1, r2, c2);
//                                            左上(行,列) 右下(行,列)
```

- **场景**：**真要一块独立小图**（要显示/单独保存，而不是圈范围）；
- **本插件**：`UpdateTemplatePreview` 裁出模板区域做左下角预览。
  注意参数是**两个对角点**（不是中心+半长宽），且只能是正方向矩形——
  所以斜的模板区域要先算**轴对齐包围盒**（22 章之前讲过 halfH/halfW 公式）。

> **reduce vs crop 一句话**：圈范围用 reduce（便宜），要新图用 crop（有拷贝成本）。

### D 组：图像变换与通道

#### `count_channels` — 数通道数

```csharp
HOperatorSet.CountChannels(src, out HTuple channels);   // 1/3/4…
```

- **场景**：不知道来图是什么格式时先问一嘴；
- **本插件**：`TryToGrayImage` 第一行——据此走 1/3/4 通道分支。

#### `copy_image` — 复制一份图

```csharp
HOperatorSet.CopyImage(src, out HObject copy);
```

- **场景**：要一份**独立所有权**的图（上游的句柄归框架，自己留副本）；
- **本插件**：1 通道图"转灰度"时——本来就是灰度，复制一份归自己管。

#### `rgb1_to_gray` — 彩色转灰度（3 通道）

```csharp
HOperatorSet.Rgb1ToGray(rgb, out HObject gray);
```

- **场景**：标准 RGB 图转灰度（人眼权重的加权平均，不是简单平均）；
- **本插件**：3 通道分支。

#### `access_channel` — 掏出第 N 个通道

```csharp
HOperatorSet.AccessChannel(rgba, out HObject c1, 1);   // 1 基编号！
```

- **场景**：只想要某一个通道（比如 RGBA 里的 alpha 丢掉）；
- **本插件**：4 通道分支——掏出前 3 通道给 `rgb3_to_gray`。

#### `rgb3_to_gray` — 三通道分别给定转灰度

```csharp
HOperatorSet.Rgb3ToGray(c1, c2, c3, out HObject gray);
```

- **场景**：通道已经是"散装"的（access\_channel 掏出来的）；
- **本插件**：4 通道分支的第二步。

> 四兄弟合体 = `TryToGrayImage` 全貌：count\_channels 问路 →
> 1 通 copy / 3 通 rgb1\_to\_gray / 4 通 access×3 + rgb3\_to\_gray → 其它报错。

#### `read_image` — 从磁盘读图

```csharp
HOperatorSet.ReadImage(out HObject img, path);   // 支持 bmp/png/jpg/tiff…
```

- **场景**：载入参考图、读掩膜 PNG；
- **本插件**：载参考图（`LoadPreviewImage` / `RefreshPreviewForEntry`）、
  掩膜还原（`Base64ToMaskRegion`）。

### E 组：模板匹配核心（本插件的主角）

#### `create_shape_model` — 学习（不缩放版）

```csharp
HOperatorSet.CreateShapeModel(
    gray,          // 模板图（已转灰度、已圈域）
    numLevels,     // 金字塔层数
    angleStart,    // 角度起点（弧度）
    angleExtent,   // 角度跨度（弧度，不是上限！）
    angleStep,     // 步长（弧度）或 "auto"
    "auto",        // 优化方式（留 auto 即可）
    metric,        // "use_polarity" / "ignore_polarity"
    contrast,      // 梯度阈值 或 "auto"
    "auto",        // 最小对比度（留 auto）
    out HTuple modelId);   // ★ 模型句柄：之后所有操作都认这个编号
```

- **场景**：目标大小不变，只是位置/角度会变——**最常用**；
- **本插件**：`ScaleEnabled = false` 时（默认）。

#### `create_scaled_shape_model` — 学习（带缩放版）

```csharp
HOperatorSet.CreateScaledShapeModel(
    gray, numLevels, angleStart, angleExtent, angleStep,
    scaleMin, scaleMax,   // ★ 多了缩放范围（倍率）
    "auto", "auto", metric, contrast, "auto",
    out HTuple modelId);
```

- **场景**：目标远近会变（镜头/物距不固定），像会变大变小；
- **代价**：每个缩放级别 × 每个角度都预生成变体——**学习慢、模型大、搜索慢**；
- **本插件**：勾了"启用缩放"时。上下限相等会被拒——插件提前撑开 0.005（17 章第 6 段）。

#### `find_shape_model` / `find_scaled_shape_model` — 查找

```csharp
HOperatorSet.FindShapeModel(
    image, modelId, angleStart, angleExtent,   // ← 角度范围必须 ⊆ create 时的范围！
    minScore, numMatches, maxOverlap,
    "least_squares",    // 亚像素精化（22.4）
    numLevels,          // 搜索用几层金字塔（0 = 全部）
    greediness,         // 激进度 0.1~0.9
    out rows, out cols, out angles, out scores);   // 按分数降序！
```

- **用法要点**：
  - 角度/缩放范围**只能比 create 时窄，不能宽**（变体没生成过就找不到）——
    这就是插件从条目（而非界面）读角度的原因（20.2）；
  - 结果**天然按分数降序**，`rows[0]` 永远是最高分；
  - `numMatches` 想多要几个就得 >1，配合 maxOverlap 去重；
- **本插件**：RunAlgorithm 每帧调用（scaled 版多了 scaleMin/Max 两个参数）。

#### `set_shape_model_origin` — 锚定原点（本插件独门）

```csharp
HOperatorSet.SetShapeModelOrigin(modelId, rowOffset, colOffset);
```

- **场景**：想让 find 输出的位置 = **你画的框中心**而不是 HALCON 默认参考点；
- **用法**：偏移量 = 默认落点 − 期望原点（17 章第 7 段的推导，方向别搞反）；
- **本插件**：学习末尾自匹配一次量出偏差后调用。补偿写进模型，**随序列化走**——
  read\_shape\_model 载入后自动生效。

#### `write_shape_model` / `read_shape_model` — 模型存/取盘

```csharp
HOperatorSet.WriteShapeModel(modelId, path);              // 写 .shm 文件
HOperatorSet.ReadShapeModel(path, out HTuple modelId);    // 读回句柄
```

- **场景**：模型持久化。HALCON 没有内存导出接口，**只能经文件**；
- **本插件**：学习后 write→读字节→base64 存 JSON（17 章第 8 段）；
  运行前 base64→临时文件→read（懒加载，18 章 `EnsureModelLoaded`）。
  临时文件用完即删，`Guid` 防并发撞名。

#### `get_shape_model_params` / `get_shape_model_contours` — 问模型信息

```csharp
HOperatorSet.GetShapeModelParams(modelId,
    out levels, out angleStart, out angleExtent, out angleStep,
    out scaleMin, out scaleMax, out _, out _, out _);   // 不关心的用 _ 丢弃
HOperatorSet.GetShapeModelContours(out HObject contours, modelId, level);
//                                                          取第几层的轮廓（1=最细）
```

- **场景**：回读"模型当初按什么参数建的"（对账/显示）；
- **本插件**：params 用来在成功消息里报真实层数；
  contours 取最细层轮廓——**就是预览和标注图上的那些绿线**。

#### `clear_shape_model` — 释放模型句柄

```csharp
HOperatorSet.ClearShapeModel(modelId);
```

- **场景**：模型不要了（重学/删除/退出）。模型占内存不小（几百 KB\~几 MB），
  不 Clear 就是真泄漏；
- **本插件**：`ReleaseEntryModel`（重学前/删条目时/Dispose）。

### F 组：几何变换（"搬运"）

#### `vector_angle_to_rigid` — 一步算出"平移+旋转"矩阵

```csharp
HOperatorSet.VectorAngleToRigid(
    row1, col1, angle1,    // 从：点1 与角度1
    row2, col2, angle2,    // 到：点2 与角度2
    out HTuple hom);       // 输出 2D 仿射（刚性）矩阵
```

- **场景**：**任何"把 A 搬到 B"的需求**——问一次要矩阵，配 affine\_\* 系列使用；
- **本插件**：三处！
  1. AlignedImage：从"当前位姿"变到"学习位姿"（18 章第 7 段）；
  2. 标注轮廓摆放：从模型原点变到命中位姿（`PlaceContoursAtPoses`）；
  3. 预览轮廓平移：从模型原点变到裁剪图内位置。
- 角度**弧度**（界面输出的度要先乘 π/180，踩坑 #3 的教训）。

#### `affine_trans_image` — 用矩阵搬运图像

```csharp
HOperatorSet.AffineTransImage(img, out HObject moved, hom,
    "constant",   // 出界像素填常量（黑）
    "false");     // false=输出与原图同幅面 / true=自动扩到装得下
```

- **场景**：转正目标（AlignedImage）、拼全景、纠偏；
- **本插件**：只在生成 AlignedImage 用。参数顺序踩坑见 18 章第 7 段（#3147）。

#### `affine_trans_contour_xld` — 用矩阵搬运轮廓

```csharp
HOperatorSet.AffineTransContourXld(contours, out HObject moved, hom);
```

- **场景**：轮廓跟目标一起搬（画标注绿线、预览特征线）；
- **本插件**：预览和运行标注都靠它（`UpdateTemplatePreview` / `PlaceContoursAtPoses`）。

> **F 组固定搭配**：`vector_angle_to_rigid`（求矩阵）→
> `affine_trans_image`（搬图）/ `affine_trans_contour_xld`（搬线）。
> 矩阵算一次，能反复用。

### G 组：离屏渲染（"画一张图给我看"）

这组统一服务一个目标：**不开可见窗口，在内存里画出标注图**。

| 算子                  | 一句话                                       | 本插件场景                                           |
| ------------------- | ----------------------------------------- | ----------------------------------------------- |
| `open_window`       | 开一个画板。`"buffer"`=内存画板（看不见），`"local"`=不弹新窗 | `RenderAnnotated` 里按图尺寸开，**缓存复用**（#9302 死锁，8.1） |
| `set_part`          | 定画板显示范围（不设会被撑歪，底图缩一角）                     | 每次绘制前钉 0,0,h-1,w-1                              |
| `disp_obj`          | 把图像/区域/轮廓画上去                              | 画底图、画绿轮廓                                        |
| `set_color`         | 设置后续绘制颜色（"green"/"red"…）                  | 轮廓颜色切换                                          |
| `set_line_width`    | 线宽（像素）                                    | 轮廓 1px 细线                                       |
| `set_font`          | 字体（`-Consolas-16-…` X 格式）                 | `TrySetFont`：失败吞掉不阻断                            |
| `disp_text`         | 写字，可带参数对（"box\_color","white"=白底框）        | 左上角判定文字，任何背景可读                                  |
| `dump_window_image` | 把画板**拍成 HImage**（返回句柄）                    | 渲染结果导出——**立刻拷贝+释放 shot**（#8，500 次漏 160MB）       |
| `close_window`      | 关画板（句柄失效）                                 | 尺寸变了才关旧开新 / Dispose 兜底                          |

> 完整流程：open（缓存）→ set\_part 钉范围 → disp\_obj 底图 →
> set\_color+disp\_obj 轮廓 → disp\_text 文字 → dump 拍图 → （复用，不 close）。
> 全程 `lock(_previewGate)`——HALCON 窗口操作非线程安全。

| # | 参数       | 类型/单位       | 说明       | 本插件填法                   |

## 23. 手工模拟一次匹配（纸上跑一遍 find\_shape\_model）

> 概念都懂了，现在**亲手**跑一遍匹配——用一个 8×8 像素的迷你图，
> 全程手算。算完你就彻底明白"分数"是怎么来的、"找不到"是怎么回事。

### 23.1 出题

**学习阶段**：给你这张 8×8 参考图（灰度值，0 黑 255 白）：

```
     列0  1  2  3  4  5  6  7
行0 [ 50 50 50 50 50 50 50 50 ]
行1 [ 50 50 50 50 50 50 50 50 ]
行2 [ 50 50 200 200 200 200 50 50 ]   ← 中间有个 4×4 的白色方块
行3 [ 50 50 200 200 200 200 50 50 ]      （我们的模板目标）
行4 [ 50 50 200 200 200 200 50 50 ]
行5 [ 50 50 200 200 200 200 50 50 ]
行6 [ 50 50 50 50 50 50 50 50 ]
行7 [ 50 50 50 50 50 50 50 50 ]
```

框住白块（约 2≤行≤5, 2≤列≤5），角度范围 ±45°，梯度阈值 30。

### 23.2 第一步：学习——梯度在哪？

逐个位置看水平方向的灰度变化（垂直方向同理）：

```
行2：[ 50 50 | 200 200 200 200 | 50 50 ]
              ↑跳变 150！           ↑跳变 -150！
          列1→2 处                  列5→6 处
```

- 白块**四条边**各有剧烈跳变（150 > 阈值 30）→ 全部留下当特征点；
- 白块**内部**全是 200→200（变化 0）→ 无特征；
- 背景**内部**全是 50→50 → 无特征。

**学到的模型 = 白块的 4 条边**（以及"每条边是暗→亮还是亮→暗"的极性）。
这解释了 22.1 的话：平坦区域是"荒地"，预览里你看到的绿线就是这些边。

### 23.3 第二步：查找——拿着"边框"在全图比对

现在来一张新图，白块**挪到了右下角、还转了 30°**。
find 的做法（金字塔细节略，就当只有一层）：

```
对每个候选位置 p：
    把模板的 4 条边按角度 θ 摆到 p 处
    → 检查：这些边落下的地方，新图的梯度方向/强度和模型一致吗？
    → 一致的特征点占比 = 该 (p, θ) 的分数
```

- 摆在左上角（旧位置）：边落处全是 50（平坦，无梯度）→ 一致率 0 → 分数≈0；
- 摆在右下角、θ=30°：4 条边全部正好压在新块的边上，梯度 150、
  极性一致 → 一致率 100% → **分数 ≈ 1.0**；
- 摆在右下角、θ=25°：差 5°，每条边错开一点 → 大部分边仍能对上 → 分数 ≈ 0.85；
- **half 全场比完，取分数 ≥ minScore 的前 numMatches 个**，maxOverlap 去重。

输出：`Row=中心行, Column=中心列, Angle≈30°, Score≈1.0`。

### 23.4 从手算过程读出四条实用结论

1. **分数 = 特征点对上的比例**。模板有 100 个特征点、对上 60 个 → 0.6。
   所以目标被**遮挡 40%** 时分数大约就是 0.6 ——
   分数下限（MinScore）其实是在回答"允许挡住多少"；
2. **找不到（n=0）的三种可能**，手算过程全对上了：
   - 分数不够（遮挡/光照变了 → 对上的比例跌破 minScore）；
   - 角度超范围（目标转了 60°，你只允许 ±45° → 摆不出能对上的姿态）；
   - 特征没了（反光把边"洗白"→ 新图里梯度趋 0 → 无边可对，22.4 的过曝）；
3. **角度步长决定角度精度下限**：步长 10° 时 HALCON 先按 10° 一档试
   （least\_squares 再精修，但初始档位太粗、复杂目标可能漏）；
4. **为什么"纹理丰富"重要**：模板特征点越多，个别点失效（反光/脏污）对比例影响越小。
   4 条边的模型，一条边被挡 = 丢 25% 分数；40 条边的模型，同样遮挡只丢 2.5%。

### 23.5 自己动手的作业（可选）

拿任意一张照片试想一遍：
① 哪里梯度大（适合当模板）？② 哪里平坦（框进去是浪费）？
③ 如果这张图整体变暗 50 个灰度级，你框的边还认得出来吗？
（答案：认得——梯度是"变化量"，整体平移灰度不变；
但如果整张图**过曝糊成一片白**，梯度归零，就真找不到了——这正是 24 章要讲的打光。）

## 24. 现场打光与实操建议

> 老师傅说"打光比算法重要"，不是玄学——因为**算法的全部输入就是那张灰度表**，
> 光打不好，表里的数字本身就没信息，任何算法都是无米之炊。

### 24.1 三条打光原则（每条配"为什么"）

**原则一：光要稳，不要亮**

- 匹配依赖梯度（22.1），梯度依赖**边缘清楚**；
- 光源闪烁/工位漏进日光 → 每帧灰度表不一样 → 分数忽高忽低；
- 现场做法：封闭暗箱 + 恒流 LED + 上电预热几分钟（LED 亮度随温度漂移）。

**原则二：方向光会让"同一物体"长两张脸**

- 斜射光下，物体转 90°，反光位置完全不同 → 模型的极性全对不上 → 分数暴跌；
- 现场做法：优先**漫射光**（穹顶光源/背光板/加柔光罩），
  让物体"各个角度都长一个样"——这正是 shape matching 最爱的世界；
- 镜面/金属件：宁可背光拍**轮廓剪影**（背景亮物体黑），
  剪影的边缘永远稳定。

**原则三：双峰直方图是及格线**

21.5 讲过：目标与背景的灰度峰**分得开、不过曝**才及格。
过曝（一片白）会把梯度"晒没"——峰值顶到 255 被削平，边缘变糊。
现场做法：调光圈/曝光/光源亮度，看直方图两峰分离且不顶格。

### 24.2 学习时的四条实操建议

1. **用真实产线图学习，不要用手机拍的"参考样张"**——
   镜头畸变、色温、分辨率都不同，学出来的模型在现场水土不服；
2. **框特征最丰富、且永远存在的部位**：
   - 好：螺丝孔、倒角、丝印边缘、安装孔位；
   - 差：反光面（涂掉！）、会动的盖子、柔软线缆、 O 型圈（挤压变形）；
3. **涂掉一切"会变"的区域**（10.1 的涂抹功能就是为此而生）：
   反光、标签纸（会换版）、液面、气泡、上一工序留下的胶水痕；
4. **学习后立刻做一次"压力测试"**：把目标故意转 ±最大角度、
   平移到视野四角、调暗 20% 光——每次都能找到（分数稳定）才算学好了。

### 24.3 运行期的三条检查习惯

1. **盯** **`Score`** **的趋势而不只是过/不过**：
   分数从 0.95 慢慢滑到 0.75 → 光源在老化/镜头在松，
   这是设备维护的**领先指标**（等跌破 0.5 报警就晚了）；
2. **失败先看标注图**（插件失败也输出红字原图，7.6）：
   目标根本不在视野？姿态超出角度范围？还是糊了？一眼定方向；
3. **改参数按"速查表"（第 11 章）单变量改**：一次只动一个，
   改完重跑 10 帧看分数稳定性——同时改三个参数，好坏都说不清是谁的功劳。

### 24.4 小白现场排障流程图

```
匹配不稳/失败
   │
   ├─ 直方图双峰吗？ ──否──▶ 先修光（24.1）：稳光源→漫射→不过曝
   │
   ├─ 目标超出角度/缩放范围？ ──是──▶ 放宽角度范围 / 启用缩放（重学）
   │
   ├─ 分数临界（0.5~0.6）？ ──是──▶ 换特征更丰富的模板区域（重学）
   │                                  或适度降 MinScore
   │
   ├─ 目标有遮挡/缺料是常态？ ──是──▶ 按最大常态遮挡率设 MinScore
   │
   └─ 都不是 ──▶ 看标注图红字 + 日志 StateDetail，按第 12 章 FAQ 对号入座
```

### 22B.x 一表总收尾：三处"单位/编号"陷阱

| 陷阱             | 涉及算子                                                         | 规则                         |
| -------------- | ------------------------------------------------------------ | -------------------------- |

| 通道/层级是 **1 基** | access\_channel、get\_shape\_model\_contours                  | 第一个 = 1，不是 0               |
