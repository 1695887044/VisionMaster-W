# VisionMaster 视觉检测系统 — 设计思想

> 本文档从源码出发，梳理整套软件的核心设计思想、架构分层、关键设计决策与取舍。配合《软件手册》使用，先读思想、再读操作。

---

## 一、什么是 VisionMaster

**一句话**：一个基于 WPF + Prism + Halcon 的**机器视觉在线检测上位机平台**。用户用**可视化流程画布**把若干**视觉算子插件**（加相机、ROI、脚本、数组统计等）串成一条检测流程，支持**连续/单次运行**，并通过**通信模块**把检测结果实时读写到 PLC / 设备。

**核心要素**：
- **流程（Flow）**：一串步骤的有序组合，是运行的最小执行单元；
- **方案（Solution）**：一个工程 = 多个流程 + 通信连接 + 全局变量 + 布局配置，随 `.vms` 文件落盘；
- **插件（Plugin）**：视觉算子，DLL 动态加载，是流程的积木；
- **变量（Variable）**：本地变量（内存）+ 网络变量（PLC），流程间/设备间交换数据的仓库。

## 二、总体架构分层

```
┌─────────────────────────────────────────────────────────────┐
│            VisionMaster 主程序 (WPF Shell / Prism)            │
│   ShellViewModel / 各种 View + VM / 桥接器 / 持久化服务         │
├────────────┬─────────────┬─────────────┬─────────────────────┤
│  UI / 控件  │   引擎 Engine  │  通信 Comm    │   服务 Services        │
│ (Core.Controls│ FlowCompiler │ Manager工厂     │ 变量/方案/插件服务         │
│   Core.Interfaces│ FlowEngine    │ Modbus/S7连接  │                        │
├────────────┴─────────────┴─────────────┴─────────────────────┤
│             Core 核心层（模型/接口/契约/通用工具）               │
│         不反向依赖任何上层，只被上层引用                          │
└─────────────────────────────────────────────────────────────┘
```

**分层的核心原则**：
1. **Core 最底层**：放变量模型、DTO、接口、通用工具，**原则上不知道具体协议怎么实现**。
2. **Communication / Engine 依赖 Core**：具体协议连接、通信管理器、流程编译与执行引擎。
3. **主程序最顶层**：UI、桥接器、持久化、方案/插件服务——把下层粘起来。
4. **模块化自装配**：`CommunicationModule` / `FlowEngineModule` 通过 `IAppModule` 接口在启动时自注册、自声明退出任务（见后文「模块生命周期」）。

## 三、核心技术选型与设计决策

### 3.1 UI 框架：WPF + Prism (MVVM) + AvalonDock

| 选型 | 用途 | 说明 |
|------|------|------|
| **Prism** | 依赖注入 + 导航 + 弹窗 | `PrismApplication` 作为应用基类，`IContainerRegistry` 注册服务；`RegisterForNavigation`/`RegisterDialog` 管理视图导航与对话框 |
| **AvalonDock** | 停靠面板布局 | 流程列表、工具箱、图像视图等可拖拽停靠；布局随方案保存/恢复 |
| **AvalonEdit** | 脚本编辑器 | ImageScript 插件的代码编辑/高亮 |
| **DynamicExpresso** | 表达式解析 | If/While 条件表达式、数学计算的安全解析执行 |

**MVVM 关键点**：
- `ObservableObject` / `BindableBase` 提供 `SetProperty` + `[CallerMemberName]` 的 INPC，**复刻 Prism 逻辑**并支持数组内容比较、可空类型、枚举比较（见 `Shard/Core.Interfaces/Core/ObservableObject.cs`）。
- 视图绑定 ViewModel，命令走 `DelegateCommand` / `AsyncDelegateCommand`。

### 3.2 依赖注入（DI）与生命周期

`App.xaml.cs` 的 `RegisterTypes` 按顺序注册：
1. **基础服务最先**（日志、性能监控、应用设置、生命周期、通知器）；
2. **模块注册**（通信、引擎）`foreach module.Register()`；
3. **高层服务**（方案、工作空间、变量桥、导航、对话框）。

> **为什么基础服务最先**：Unity 注册工厂解析依赖时可能提前触发可见依赖解析，若基础服务未就位会失败。

**单例注册原则**：接口与具体类型同时注册为单例，保证无论按接口还是按类型解析都拿到同一实例，例如：
```csharp
containerRegistry.RegisterSingleton<AdvancedCommunicationManager>();
containerRegistry.RegisterSingleton<ICommunicationManager, AdvancedCommunicationManager>();
```

### 3.3 插件系统：反射驱动 + 动态端口

`VisionPluginBase` 是所有算子的基类，核心设计：**端口即数据成员**。
- 参与流程数据流的参数一律声明为 `InputPort` / `OutputPort`；
- `EnsurePortsDiscovered()` 用反射扫描属性自动发现端口（省去注册表配置）；
- 插件配置时用 `[StepConfig]` 特性标记配置属性，与端口一起灌值/取快照。

**加载方式**（`PluginService`）：扫描 `Modules/` 目录下 `Plugin*.dll`，用 `Assembly.LoadFrom` 加载，反射找实现 `IVisionPlugin` 的类型，按 `[Display]` 特性的 `GroupName` 分类注册到「模块/相机/激光/轴卡」四个仓库。

**动态输出端口**（`IDynamicOutputProvider`）：ROI 类插件在配置时动态增加端口，编译前按快照 `OutputPortDefinitions` 重建端口集，供布线。

> **设计亮点**：配置值通过 `SnapshotConfigValue` 做 JSON 往返拷贝，确认后界面改动**不污染已确认数据**，避免共享引用陷阱。

### 3.4 流程编译与执行引擎

**流程编译**（`FlowCompiler`）：把可视化的 `StepModel` 树编译成可执行的 `CompiledNode` 树。
- 编译期识别 If / While / For / Break / Continue / Return 六类内置控制节点，其余为普通算子（反射实例化插件）；
- **连线绑定**：`LinkPorts` 解析 `LinkedSources`，支持四类数据源——① 上游算子输出 ② 全局变量 ③ 运行时局部变量（`RuntimeVariableMarkerGuid` 标记） ④ 常量；并用代理端口（`RuntimeVariableProxyPort`/`ArrayIndexProxyPort`/`ConstantOutputPort`）解析。
- **条件表达式**：用 DynamicExpresso 解析，每次新 `Interpreter`（非线程安全），参数里注入局部变量类型做安全校验（`IsSafeExpressionType`）。
- **依赖图**：记录下游→上游依赖，供试运行按序先执行上游链。

**版本检查（脏检查）**：`FlowModel.Version` 随步骤修改而递增（`SetInputValue` 触发通知→版本递增），运行前 `PreRunCheck` 比较 `Flow.Version > session.CompiledVersion` 则提示重编译——**避免改参数不生效**。

**执行引擎**（`FlowEngineService`）：管理会话并发。
- `RunSessionAsync`（连续）：后台 `Task.Run` 循环——`PauseLock.Wait` 实现暂停，`CancellationToken` 实现停止，每循环复位步骤状态；
- `RunSessionOnceAsync`（单次）：跑一次即停；
- 运行状态回写：通过 `Blueprints`（深收集的步骤列表）+ `IsRunningFocus` 高亮当前执行步骤。

### 3.5 通信系统

`AdvancedCommunicationManager` 是通信总管，设计要点：
- **全线程安全集合**：`ConcurrentDictionary` 存连接/配置/定时器/注册变量，`ObservableCollection` 加专用锁；
- **工厂模式**：`ConnectionFactoryManager.CreateConnection(config)` 按协议创建连接，新增协议只需新增配置类+连接类+地址类；
- **三套定时器**：重连定时器、心跳定时器、**变量轮询定时器**（按连接 `ReadCycleMs` 调度）；
- **变量轮询**：轮询线程读设备→`CommunicationVariable.UpdateValue`→`MirrorCallback`→`NetworkVariableModel.UpdateMirrorValue`→INPC→UI 自动刷新；
- **协议配置多态**：`ConnectionConfigBase` 抽象类 + `TypeNameHandling.Auto` + `SerializationBinder` 白名单，反序列化按 `$type` 重建子类，防恶意文件。

### 3.6 变量系统（本地 + 网络）

核心设计：
- **镜像值 vs 直通写**：网络变量 getter 只读内存镜像（不直读设备，防止 UI 高频同步 IO 卡顿），写走 setter 直通设备；
- **桥接器**（`NetworkVariableBridge`）：监听变量集合变化，自动 Bind + 注册轮询 + 接镜像回调，删除自动注销——业务代码只需 `GlobalVariables.Add(...)` 一行；
- **持久化快照**（`VariableDto`）：Core 不能引用 Communication，地址对象靠反射按字符串全名重建（编译时不能引用，就运行时按名字找人）。

### 3.7 序列化与安全

多处用到 **Newtonsoft.Json + TypeNameHandling.Auto + SerializationBinder 白名单**：
- 方案 `.vms`（`SolutionService`）；
- 通信配置 `communications.json`（`AdvancedCommunicationManager`）；
- 白名单只允许本项目 `Models`/`CommunicationContracts` 命名空间类型被反序列化，防止恶意文件借 `$type` 执行任意类型构造。

## 四、启动流程与生命周期

### 4.1 启动链（App.CreateShell）
```
App 构造
 └─ RegisterTypes      注册 DI（基础→模块→高层）
 └─ CreateShell
     ├─ 接线异常分级（RegisterGlobalExceptionHandlers）
     ├─ 注册退出任务(日志落盘收尾) 退出链逆序执行
     ├─ 模块 Initialize（注册自检项/退出任务）
     └─ 启动自检链（单例→配置→插件扫描→通信）
         ├─ Splash 进度窗 + 帧泵保持响应
         ├─ RunWithPump 异步执行自检
         ├─ 失败→显示阻塞原因→退出(exit 2)
         └─ 通过→SetFinished → 返回 Shell
 └─ OnInitialized      主窗口显示后关闭 Splash
 └─ OnExit             执行退出链(逆序)→单例释放
```

**为什么用 `RunWithPump`（帧泵）**：`CreateShell` 必须同步返回窗口，但自检链是异步的。用 `DispatcherFrame` 泵消息帧直到异步工作完成，让 Splash 渲染/响应，**避免启动假死**。

### 4.2 模块自洽——IAppModule
```csharp
public interface IAppModule {
    string Name { get; }
    void Register(IContainerRegistry registry);   // 注册服务
    void Initialize(IContainerProvider container, AppLifetimeService lifetime);
}   // 声明自检项 / 退出任务
```
**设计思想**：每个子系统（通信/引擎）自己声明「我需要注册哪些服务、退出时要做什么」，主程序只负责遍历调用，**开闭原则**——新增模块不改主程序代码。

**退出链逆序执行**：先注册的后释放。日志落盘最先注册→最后运行，保证其他退出任务日志都完整。

### 4.3 自检链
启动时按序注册：单例检查 → 配置检查 → 插件扫描检查 → 通信检查。任一 Error 级失败阻塞启动并给出原因。

## 五、关键设计决策与取舍

| 决策 | 取舍 | 原因 |
|------|------|------|
| 关闭 Aggressive GC 深度清理 | 宁可内存略高，保 UI 流畅 | 定期压缩 LOH+裁剪工作集会**冻结主线程 2~3s**，且 WPF+Halcon 常态内存 >300MB，表现为"空闲双击也卡" |
| 网络变量 getter 不直读设备 | 读内存镜像 | WPF 几十处绑定同一变量，每次刷新调 getter，直读设备必然卡死 |
| 可空类型/数组/枚举统一比较 | 用通用 `ValuesAreEqual` | 装箱值类型引用比较恒不等，数组要比较内容而非引用 |
| Core 用反射重建地址 | 编译期不引用 Communication | Core↔Communication 反向依赖会打结；运行时程序集必然已加载 |
| Expression 每次 new Interpreter | 不用共享实例 | DynamicExpresso Interpreter 非线程安全，流程编译/运行可能多线程 |
| 方案连接配置也存一份进 .vms | 落盘备份 | 通信设置增删改只改内存，保存时同步进方案，重启可恢复 |

## 六、数据流全景（五条链路）

1. **轮询读**（自动）：轮询定时器→连接.Read→`CommunicationVariable.UpdateValue`→`MirrorCallback`→变量镜像→UI。
2. **写设备**（用户）：UI 写值→`netVar.Value = x`→setter→`WriteToDevice`→连接.Write→（稍后）轮询读回刷新。
3. **创建网络变量**：UI 填表→构造地址→`GlobalVariables.Add`→桥接器自动 Bind+注册+接回调→立即上线。
4. **保存方案**：Ctrl+S→布局快照→变量快照→通信配置快照→`.vms` 落盘。
5. **加载方案**：LoadAsync→反序列化→切换方案→`SolutionConfigApplier.Restore`→`VariablePersistenceService.Restore`→`_variableBridge.RebindAll()`→轮询恢复。

> 详细时序见《变量管理系统-设计说明与交接文档.md》第六章。

## 七、可扩展性与演进方向

1. **新增通信协议**：协议分支三件套（配置类 + 连接类 + 地址类），即可被工厂和序列化自动接管，**零维护主程序**。
2. **新增视觉算子**：继承 `VisionPluginBase` → 声明端口 → 加 `[Display]`，编译进 `Modules` DLL 即被扫描加载。
3. **HMI 画布组态**：`IVariableDisplaySource` 已是契约（两类变量都已实现），下一步写"按名解析对象"的注册表即可零成本接入。
4. **动画/监控面板**：`MonitorViewModel`、`PerformanceMonitor` 已预留，可扩展实时曲线/统计。
5. **运动控制**：`PluginProvider` 已预留 `_motions` 仓库与 `RegisterMotion`（目前未实现），是后续接入 EtherCAT/脉冲的挂接点。

## 九、从创建图纸到运行：面向新手的系统讲解

> 本章面向设计新手，用通俗语言把「图纸→编译→运行」这条链路讲透。
> 读完你会明白：为什么这套系统能让你「画流程图就能跑视觉检测」，它背后的三层分离思想、逻辑分支原理、插件协调机制是怎么设计的。

### 9.1 先建立一个整体心智模型

整套系统是**「设计时（画）/ 编译时（造）/ 运行时（跑）」三段分离**的架构，是经典编译器三阶段思想在工业视觉流程引擎上的移植：

```
┌─────────────────┐      ┌──────────────────┐      ┌──────────────────┐
│  设计时 DESIGN    │      │  编译时 COMPILE   │      │  运行时 RUN       │
│  StepModel 蓝图  │ ───► │  CompiledNode 树  │ ───► │  栈式深度遍历执行  │
│  (可编辑/可存盘)  │      │  (只读/已定型)     │      │  (逐节点驱动插件)  │
└─────────────────┘      └──────────────────┘      └──────────────────┘
```

**为什么一定要拆成三层？** 这是全篇的核心设计思想：

| 层 | 代表类型 | 特点 | 心智类比 |
|---|---|---|---|
| 蓝图(设计时) | `StepModel` / `WhileStep` / `ConditionStep` | **可变、可序列化、可编辑**，用户随手拖动 | 你的「施工图纸」，可以反复改 |
| 编译产物(编译时) | `CompiledNode` / `CompiledIfNode` | **只读、封闭、已定型**，一次编译生成 | 「钢筋混凝土结构」固化下来 |
| 执行上下文(运行时) | `ExecutionContext` / `FlowSession` | **可变的运行状态**，每次跑都不一样 | 「现场天气 + 施工队状态」 |

**好处**：图纸（设计时）和现场（运行时）彻底解耦。你不改图纸就能反复跑；改一张图只需重编译一次，不用动其它已跑通的流程。这就是「编译/执行分离」的威力。

---

### 9.2 阶段一：创建图纸（设计时）

**（1）一块方块是怎么诞生的**

你在左侧工具栏拖出一个算子（如「采集图像」），框架做的第一件事是**记录它的类型**，而不是加载它：

```csharp
public StepModel(string icon, string pluginName, string pluginTypeName, string stepName = null)
{
    Icon = icon;
    PluginName = pluginName;
    this.PluginTypeName = pluginTypeName;   // 记住插件全类型名，如 "VisionMaster.Plugins.ImageAcqPlugin"
    StepName = stepName ?? pluginName;
}
```

关键设计：**蓝图不加载插件实例，只记录一个字符串 `PluginTypeName`**。为什么？
- 图纸要能存盘、能反序列化，字符串比活对象好存；
- 图纸要能反复打开，不能让每个方块都拉着一个重量级的相机驱动实例。

**（2）结构型方块（If / While / For）的特殊之处**

它们继承自 `StepModel` 但**额外带容器**（`IContainerStep`）。`ConditionStep` 构造时根据插件名关键字自动决定默认分支：

```csharp
if (pluginTypeName.Contains("If"))
{
    Children.Add(new StepCollection { BranchType = BranchType.If,   StepName = "If",   Expression = "" });
    Children.Add(new StepCollection { BranchType = BranchType.Else, StepName = "Else" });
}
```

`WhileStep` 覆盖基类，只留一个「循环体」容器，让用户在 `Expression` 里填条件（如 `"Score > 80"`）：

```csharp
public WhileStep(...) : base(...)
{
    Children.Clear();
    Children.Add(new StepCollection { BranchType = BranchType.Default, StepName = "循环体", Expression = "" });
}
```

**设计思想**：把「分支结构」本身也建模成一种「步骤 + 子步骤集合」的树。这样**任何结构（顺序/分支/循环）都能递归嵌套**——If 里套 While，While 里套 For，形成任意深度的树状流程。这正是编译器里「AST 抽象语法树」的视觉版。

**（3）连线（端口绑定）是怎么存的**

从一个方块的输出口连到另一个方块的输入口，框架存的是 `LinkedSources` 字典：

```csharp
public Dictionary<string, LinkReference> LinkedSources { get; set; } = new();
// 例如: { "Image": new LinkReference { TargetStepId = 某输出节点Guid, TargetPortName = "Result" } }
```

**设计思想**：蓝图阶段**不真正传数据**，只存「谁连到谁」的**引用信息**。数据流要到运行期才真正发生。这是「惰性求值」——画的时候不关心数据内容，只要关系对就行。

### 9.3 阶段二：编译（编译时）

**（1）编译入口 `FlowCompiler.Compile`**

```csharp
public CompilationResult Compile(...)
{
    var pluginLookup  = new Dictionary<Guid, IVisionPlugin>();   // (1) 步骤ID->插件实例
    var nodeLookup    = new Dictionary<Guid, CompiledNode>();    // (2) 步骤ID->编译节点
    var dependencyMap = new Dictionary<Guid, List<Guid>>();      // (3) 步骤ID->上游依赖集

    CompileSteps(blueprints, flowName, pluginLookup, nodeLookup, result.Errors);   // ① 建节点树
    LinkPorts(blueprints, nodeLookup, pluginLookup, dependencyMap, result.Errors); // ② 绑数据流

    return new CompiledFlow(rootNodes, pluginLookup, nodeLookup, dependencyMap);   // ③ 打包产物
}
```

**三步到底在干嘛？**

| 步骤 | 做的事 | 产出的灵魂结构 |
|---|---|---|
| ① `CompileSteps` | 逐步骤「定型」：把每个蓝图步骤变成对应的执行节点 | `nodeLookup` + 根节点列表 |
| ② `LinkPorts` | 把逻辑连线变成真实的数据端口引用 | `dependencyMap` |
| ③ 打包 | 把节点树 + 插件表 + 依赖表封成一个「可运行物」 | `CompiledFlow` |

**（2）步骤定型：一个 switch 式「分派工厂」**

`CompileSteps` 遍历每个 `StepModel`，按类型检测结果决定造出哪种执行节点：

```csharp
if (step is WhileStep)                    // ← 必须先判断 While！因为它继承自 ConditionStep
{
    node = new CompiledWhileNode { ... };
}
else if (step is ConditionStep)           // If / Switch
{
    node = new CompiledIfNode { Branches = 编译每个子分支 };
}
else if (step is ForStep)                 // 固定次数循环
{
    node = new CompiledForNode { DefaultLoopCount = forModel.DefaultLoopCount };
}
else if (step.PluginTypeName == "BuiltIn_Break")    node = new CompiledBreakNode();
else if (step.PluginTypeName == "BuiltIn_Continue") node = new CompiledContinueNode();
else if (step.PluginTypeName == "BuiltIn_Return")   node = new CompiledReturnNode();
else    // 真正的算子 —— 反射实例化
{
    Type t = Type.GetType(step.PluginTypeName);
    var plugin = (IVisionPlugin)Activator.CreateInstance(t);   // 此刻才真正实例化插件！
    ApplyConfigValues(plugin, step.InputValues);
    if (plugin is IDynamicOutputProvider p) p.RebuildDynamicOutputs();   // 动态端口重建
}
```

**两个必须牢记的设计决定（写对分支的命门）**：
1. **`WhileStep` 必须先于 `ConditionStep` 判断**——因为 `WhileStep : ConditionStep`，`is ConditionStep` 对 While 也是 `true`。顺序反了，While 会被误判成 If，循环就丢了。这是 C# 继承体系里最容易踩的坑。
2. **`BuiltIn_Break/Continue/Return` 是「无插件」的纯控制符**——它们不实例化任何视觉插件，只是执行时改写「流程控制状态」。（见 9.5 节）

**（3）端口连线的四类数据源（`LinkPorts`）**

编译器看到每一条 `LinkReference`，会按目标来源分类：

```
① 连到运行时变量 → 创建 RuntimeVariableProxyPort(varName, expectedType)，塞进 ContextAwareBindings
② 连到常量     → new ConstantOutputPort(常量值, targetType)
③ 连到全局变量 → GlobalVariables.FirstOrDefault(按名匹配)
④ 连到上游算子输出 → 正则解析 "端口名[下标]"；裸名取 upPlugin.Outputs[name]，带下标包 ArrayIndexProxyPort
```

**设计思想**：编译期就把「数据的来源」全部解析、定格成具体的端口对象，运行期只做「取值调用」。这样运行期极快，而且**错误的连线在编译期就报出来**，把 bug 提前到「编译时我就能告诉你哪根线错了」。

**（4）编译期安全校验**

局部变量和运行时变量在编译期都要过一道**安全白名单**：

```csharp
if (!TypeHelper.IsSafeExpressionType(varType))
{
    errors.Add($"[安全拦截] 运行时变量 '{name}' 数据类型不合法！");
    continue;
}
```

**为什么？** 表达式是用户任意字符串（`"Score > 80"`），会被 `DynamicExpresso` 编译成可执行 Lambda。如果允许任意类型，用户输入可能引入危险成员访问。所以编译期**只放行安全的数值/字符串/布尔**类型，从源头掐断表达式注入风险。这是「编译时安全栅栏」。

> **表达式解释器每次 `new`**：`private Interpreter CreateInterpreter() => new Interpreter().Reference(typeof(Math));` —— 因为 `DynamicExpresso.Interpreter` 不是线程安全的，不能在多线程下共享，所以**每次解析都新建一个**。用极小构造开销换线程安全。

### 9.4 阶段三：运行（运行时）

**（1）编译产物长什么样**

`CompiledFlow` 是最终「可运行物」，同时持有三张关键表：

```csharp
public class CompiledFlow
{
    public List<CompiledNode> RootNodes;                    // 顶层顺序执行的起点列表
    public Dictionary<Guid, IVisionPlugin> PluginLookup;   // 步骤ID -> 已实例化插件
    public Dictionary<Guid, CompiledNode> NodeLookup;      // 步骤ID -> 编译节点
    public Dictionary<Guid, List<Guid>> DependencyMap;     // 步骤ID -> 上游依赖（试运行用）
}
```

**设计思想**：把「插件实例」也放进编译产物，且所有插件在 `CompiledFlow.Dispose()` 时统一释放——**编译物是插件的属主/生命周期管理者**。每次编译都 `Activator.CreateInstance` 一整套新插件（持有 `HImage` 等非托管资源），GC 回收不了，必须显式 `Dispose`。

```csharp
foreach (var plugin in ExecutionEngine.PluginLookup.Values)
    plugin?.Dispose();   // 逐个释放，单个失败不阻断其余
```

**（2）执行引擎：一个「栈式深度优先遍历」**

这是运行期最核心、最精妙的方法。它不用递归，而用**显式栈 + 迭代器**实现深度优先：

```csharp
public void Run(IExecutionContext context)
{
    var stack = new Stack<IEnumerator<CompiledNode>>();
    stack.Push(RootNodes.GetEnumerator());          // 压入根节点序列的迭代器

    while (stack.Count > 0)
    {
        if (context.CancellationToken.IsCancellationRequested) return;

        var currentEnumerator = stack.Peek();       // 只看栈顶不弹出

        if (currentEnumerator.MoveNext())           // 取当前序列的下一个节点
        {
            var currentNode = currentEnumerator.Current;
            context.CurrentNodeId = currentNode.Id;

            var nextBranchToRun = currentNode.RunAndGetNext(context);  // 跑当前节点

            if (nextBranchToRun != null && nextBranchToRun.Count > 0)
                stack.Push(nextBranchToRun.GetEnumerator());           // 把子序列压栈（进入分支/循环体）

            if (context.CurrentFlowState == FlowControlState.Return)
                return;                             // 全局 Return：直接终止整个遍历
        }
        else
        {
            stack.Pop();                            // 当前序列耗尽，弹栈回到上一层
        }
    }
}
```

**为什么用栈而不用递归？** 这是整个运行期的灵魂设计：

① **不爆栈**：工业视觉流程可能嵌套几百层 If/While/For。递归调用在超深嵌套时抛 `StackOverflowException`（C# 里**不可捕获**，直接崩），而显式栈在**堆**上，几千层都不崩。

② **可取消（协作式取消）**：每一圈都检查 `CancellationToken`，任何一层都能立刻优雅停下，而不是等深层递归自然返回。支撑了运行时「停止」按钮。

③ **可暂停/恢复**：配合 `PauseLock`（`ManualResetEventSlim`），主循环能停在任意位置。

④ **可插桩观察**：遍历器持有每一步的 `Current`，所以能在顶层拿到「当前正在执行哪个节点」——这就是设计器里**高亮跟随**、日志追踪、断点调试的实现基础。

**（3）一个节点如何「跑」**

每个执行节点都实现同一个抽象方法，返回**下一步要执行的节点列表**（或 `null`）：

```csharp
public abstract class CompiledNode
{
    public abstract List<CompiledNode> RunAndGetNext(IExecutionContext context);
}
```

**返回值的语义非常巧妙**：它是**「控制流转移」的统一接口**——

| 节点 | 返回 | 含义 |
|---|---|---|
| 普通插件执行完 | `null` | 继续顺着当前序列往后走 |
| `If` 命中某分支 | 该分支的 `ExecutionSteps` | 跳到这个分支序列里去执行 |
| `While` / `For` 循环体 | 循环体列表 | 进入循环体序列 |

执行引擎就靠这个返回值决定要不要 `stack.Push`。**「控制流」被抽象成了「返回一个节点列表」**——这是设计模式里 `Command` + `Visitor` 思想的融合。

**（4）典型插件节点执行（`CompiledPluginNode`）**

```csharp
public override List<CompiledNode> RunAndGetNext(IExecutionContext context)
{
    context.CurrentNodeId = Id;
    UpdateStepRuntimeState(context, StepRuntimeState.Running);   // ① 置高亮 = Running

    if (context.CancellationToken.IsCancellationRequested)
    { UpdateStepRuntimeState(context, StepRuntimeState.Skipped); return null; }

    // ② 执行前，把 context 注入所有"运行时变量代理端口"
    if (ContextAwareBindings.Count > 0)
        foreach (var binding in ContextAwareBindings)
            binding.BindContext(context);     // 让引用了运行时变量的 InputPort 拿到最新值

    bool ok = ExternalPlugin.Execute(context);   // ③ 真正调用插件算法
    if (!ok)
    {
        // 业务失败：标 Failed + 落日志，但不抛异常（流程继续，软件不崩）
        UpdateStepRuntimeState(context, StepRuntimeState.Failed);
        context.Logger?.Error(...);
        return null;
    }

    UpdateStepRuntimeState(context, StepRuntimeState.Success);   // ④ 标 Success
    return null;
}
```

**很成熟的工业取舍**：
- 插件**业务失败不抛异常**——相机没拍好、检测没通过，属于「业务状态」而非「系统崩溃」，要记录下来继续跑，不能让整个上位机挂掉。
- **异常和业务失败分开处理**：`Execute` 内部异常被 `catch` 标 Failed 后 `throw`（系统级问题必须抛出），而 `Success=false` 是业务级，不抛。

**（5）状态高亮：一个「执行指针」的巧妙设计**

`UpdateStepRuntimeState` 用了一个「执行指针」语义（不是普通高亮开关）：

```csharp
if (state == StepRuntimeState.Running)
{
    if (session.FocusedStep != null && !ReferenceEquals(session.FocusedStep, step))
        session.FocusedStep.IsRunningFocus = false;   // 指针从上一个步骤移交
    step.IsRunningFocus = true;                       // 恒定只有一行高亮
    session.FocusedStep = step;
}
// 完成不清焦点 —— 高亮短暂停留，避免毫秒级步骤高亮闪变不可见
```

**为什么"完成不立刻清高亮"？** 很多算子执行只要**几毫秒**。若一完成就清高亮，在 UI 渲染的一帧间隙里高亮已消失，肉眼看不到——高亮会「闪变」甚至像没跑。所以执行指针**停留**在最后一步，高亮平滑移动、恒定可见。这是深谙渲染帧调度的 UI 细节。

### 9.5 几个逻辑分支的实现原理（重点）

逻辑分支**贯穿「编译期」和「运行期」两段**。编译期决定「这个分支长什么样」，运行期决定「到底走哪个分支、怎么循环、怎么跳出」。

**（1）一个统一的「控制状态」贯穿全程**

运行期所有控制流都靠 `ExecutionContext` 上的一个枚举：

```csharp
public enum FlowControlState { Normal, Continue, Break, Return }
```

`Break` / `Continue` / `Return` 三个「内置指令节点」**不执行任何算法**，只做一件事——**改写这个状态**：

```csharp
// CompiledBreakNode
context.CurrentFlowState = FlowControlState.Break;    // 告诉外层循环：跳出
// CompiledContinueNode
context.CurrentFlowState = FlowControlState.Continue; // 告诉外层循环：跳过本次迭代
// CompiledReturnNode
context.CurrentFlowState = FlowControlState.Return;   // 告诉整个引擎：终止
```

然后由**循环节点**和**引擎顶层**去「认领」这个状态。这是「子节点喊话 / 父容器响应」的控制流模型。

**（2）`If` 的实现（分支选择）**

`CompiledIfNode` 依次计算每个分支条件，执行第一个为真的分支：

```csharp
foreach (var branch in Branches)
{
    // 组装参数：先局部变量，再运行时变量
    var args = 从 UpstreamLinks / context.LocalVariables 取值填入;

    bool isTrue = (bool)branch.ConditionLambda.Invoke(args);   // 调用编译好的 Lambda
    if (isTrue) return branch.ExecutionSteps;   // ← 关键：返回"命中分支的步骤序列"
}
return null;
```

**设计要点**：
- 条件表达式（`"Score > 80"`）是**编译期**就已被 `DynamicExpresso` 转成可调用 `Lambda`；
- 每个 **`Else` 分支**的条件被编译成恒真值 `"true"`，所以它总是「兜底命中」；
- **If 运行期不做循环**——它只决定「返回哪个分支序列」，然后**外层栈把它压入继续深度遍历**。If 的本质就是**控制流重定向**。

**（3）`While` 的实现（条件循环）**

`CompiledWhileNode` 是真正的循环体，它自己内部 `while`，每一步都判断条件：

```csharp
int iter = 0;
while (iter < MaxIterations)                 // MaxIterations=9999，防死循环
{
    bool isTrue = (bool)LoopBranch.ConditionLambda.Invoke(组装好的args);
    if (!isTrue) break;                       // 条件为假，退出循环

    foreach (var step in LoopBranch.ExecutionSteps)   // 执行循环体
    {
        step.RunAndGetNext(context);
        if (context.CurrentFlowState == FlowControlState.Continue) { 状态复位; break; }  // 跳过本次
        if (context.CurrentFlowState == FlowControlState.Break)   { 状态复位; return null; }  // 跳出循环
        if (context.CurrentFlowState == FlowControlState.Return)  { return null; }          // 终止整个流程
    }
    iter++;
}
return null;
```

**三处硬保护（工业级安全护栏）**：
1. **`MaxIterations = 9999`**：就算用户条件写错永远为真，最多循环 9999 次，**绝不无限死循环**卡死上位机。
2. **每圈检查 `CancellationToken`**：用户一点「停止」，立刻退出。
3. **`try/catch` 包住条件求值，`catch` 直接 `break`**：条件表达式若运行期抛异常（如变量没定义），就当「条件为假」安全退出，不让流程崩溃。

**（4）`For` 的实现（次数循环）**

`CompiledForNode` 是**固定次数**循环，并向外暴露循环索引：

```csharp
int targetCount = DefaultLoopCount;
if (LoopCountLink != null && LoopCountLink.Value != null)
    targetCount = Convert.ToInt32(LoopCountLink.Value);   // 可被上游连线覆盖循环次数

for (int i = 0; i < targetCount; i++)
{
    IndexPort.Value = i;                       // 把当前索引写入输出端口

    foreach (var step in LoopBody)
    {
        step.RunAndGetNext(context);
        if (context.CurrentFlowState == FlowControlState.Continue) { 复位; break; }
        if (context.CurrentFlowState == FlowControlState.Break)   { 复位; return null; }
        if (context.CurrentFlowState == FlowControlState.Return)  { return null; }
    }
}
```

**（与 While 对照，讲清差别）**：
- **For 把索引 `i` 写进 `IndexPort`**——下游算子（如「抓取第 i 个相机」）可连此端口拿到当前循环到了第几次。这是 `IndexPort` 作为**动态输出口**的价值。
- **循环次数可被连线覆盖**：`LoopCountLink` 若连了上游输出，就用上游值；否则用 `DefaultLoopCount`（默认10）。这是「数据流驱动循环次数」。

**（5）三个控制流的动态响应（Break/Continue/Return 核心机制）**

| 指令 | 谁设置状态 | 谁响应（认领） | 紧接的动作 | 作用范围 |
|---|---|---|---|---|
| `Break` | `CompiledBreakNode` | **离它最近的 While/For** | 状态复位为 `Normal`，`return null` | **跳出**当前一层循环 |
| `Continue` | `CompiledContinueNode` | **离它最近的 While/For** | 状态复位为 `Normal`，`break` 内层 foreach | **跳过**本次迭代 |
| `Return` | `CompiledReturnNode` | **引擎顶层 `CompiledFlow.Run`** | 直接 `return` 整个遍历 | **终止**整个流程 |

关键理解：**`Context.CurrentFlowState` 是一个「信号旗」**。只要 `Break` / `Continue` 节点执行一行，就把旗子竖起来。**谁先看到这面旗子，谁就负责把旗子放平并做出反应**。

```
在 While/For 的循环体内部：
  step.RunAndGetNext 执行到某个 "BuiltIn_Break" 节点
    → 它把 CurrentFlowState = Break
    → 返回到循环体的 foreach 里
    → foreach 看到状态 == Break
       → 把状态复位成 Normal       ← 放平旗子
       → return null（退出循环）    ← 响应动作
```

**为什么 Return 要一路传播到引擎顶层？** 因为 Return 的语义是「**终止整个流程**」，不只是当前的循环。所以它不在 While/For 里被「认领复位」，而是**继续往上浮**，直到 `CompiledFlow.Run` 主遍历的那一行 `if (CurrentFlowState == Return) return;`。

**一句话总结三个指令的本质差异**：
- **Break / Continue 是「循环局部」的**——被最近的循环认领并复位、不穿透。
- **Return 是「流程全局」的**——穿透所有循环层，直达引擎主遍历，强制终止。

这就是为什么两个不同的「层」在处理它们——`While/For` 认领 Break/Continue，`CompiledFlow` 认领 Return。**「谁认领」由「语义作用域」决定**，非常符合直觉。

### 9.6 插件与主框架的协调作业机制

**（1）插件是什么、如何被加载**

插件的基类是 `VisionPluginBase`，核心设计叫 **「端口即数据成员」**：

```csharp
public abstract class VisionPluginBase : ObservableObject, IVisionPlugin, IPluginConfigView
{
    public OutputPort<bool> Success { get; } = new("Success", "成功");        // 结果端口
    public OutputPort<string> ErrorMessage { get; } = new("ErrorMessage", "错误信息"); // 错误端口

    private readonly Dictionary<string, IInputPort> _inputs = new();
    private readonly Dictionary<string, IOutputPort> _outputs = new();

    public IReadOnlyDictionary<string, IInputPort> Inputs
    { get { EnsurePortsDiscovered(); return _inputs; } }   // 用反射自动发现端口

    public IReadOnlyDictionary<string, IOutputPort> Outputs
    { get { EnsurePortsDiscovered(); return _outputs; } }
}
```

**设计思想**：参与流程数据流的参数一律声明为 `InputPort` / `OutputPort`。`EnsurePortsDiscovered()` 用反射扫描属性自动发现端口，**省去注册表配置**——写一个算子，只要声明几个 port，就自动出现在画布的输入/输出口上，主框架完全不用改。

**（2）插件如何被主框架找到并分类**

`PluginService.InitPlugins()` 扫描 `Modules/` 目录下 `Plugin*.dll`：

```csharp
var assembly = Assembly.LoadFrom(dllPath);
var types = assembly.GetTypes()
    .Where(t => !t.IsAbstract && typeof(IVisionPlugin).IsAssignableFrom(t));

foreach (var type in types)
{
    var att = type.GetCustomAttribute<DisplayAttribute>();   // 用 Display 特性拿到分类
    var plugin = Activator.CreateInstance(type) as VisionPluginBase;

    var toolItem = new ToolItemModel {
        Category = att.GroupName,   // 按 GroupName 分类
        Name = att.Name,
        ModuleTypeName = type.AssemblyQualifiedName,
        InputDefinitions = plugin.Inputs.Values.Select(...),   // 自动收集输入口
        OutputDefinitions = plugin.Outputs.Values.Select(...), // 自动收集输出口
    };
    _registry.RegisterModule(toolItem);   // 注册到工具箱
}
```

**设计思想**：插件通过 `[Display]` 特性的 `GroupName` 分类（`相机/激光`等），主框架用**反射自动收集它的输入/输出口定义**进工具箱。**你只要写插件 + 打上 `[Display]`，主框架零改动即可识别它**。这是「开闭原则」——对扩展开放、对修改关闭。

**（3）插件如何被编译期实例化（真正「干活」的时刻）**

编译时 `FlowCompiler.CompileSteps` 遇到普通算子，用反射实例化插件并灌配置：

```csharp
Type t = Type.GetType(step.PluginTypeName);
var plugin = (IVisionPlugin)Activator.CreateInstance(t);   // 此刻才真正创建插件实例
ApplyConfigValues(plugin, step.InputValues);               // 把用户填的配置灌进端口/属性
if (plugin is IDynamicOutputProvider p) p.RebuildDynamicOutputs(); // 动态端口重建
```

**关键**：
- 蓝图里只有字符串，**编译时才 `Activator.CreateInstance` 真身实例**——所以改一次流程会重新实例化一整套插件，旧的随 `CompiledFlow.Dispose` 释放。
- `ApplyConfigValues` 把 `InputValues` 灌进端口与 `[StepConfig]` 属性（**已连线的端口跳过**，运行时以连线为准）。
- 若插件实现 `IDynamicOutputProvider`（如 ROI 类），编译前会调 `RebuildDynamicOutputs()` 重建端口集，让动态生成的端口（`Crop_ROI_1` 等）也能被布线。

**（4）插件如何被执行（运行时驱动）**

运行时由 `CompiledPluginNode.RunAndGetNext` 驱动：

```csharp
bool ok = ExternalPlugin.Execute(context);   // 调用插件基类的 Execute
// 基类：public bool Execute(IExecutionContext context)
// { RunAlgorithm(context); return Success.Value is true; }  ← 业务成功与否看 Success 端口
```

**设计要点**：
- 插件基类的 `Execute` 先调业务方法 `RunAlgorithm(context)`，然后**看 `Success.Value` 决定返回 true/false**——业务失败写入 `Success` 端口，**不抛异常**，框架据此标记步骤失败并写日志。
- 发行插件只需重写 `RunAlgorithm`（真正的检测算法），**框架自动接管「调用 + 结果判定 + 状态回写 + 日志」**。

**（5）插件与主框架协调链路总览**

```
【写插件】继承 VisionPluginBase → 声明 InputPort/OutputPort → 重写 RunAlgorithm → 打 [Display]
   │
【加进 Modules】编译成 Plugin*.dll 放进 Modules/ 目录
   │
【启动扫描】PluginService 反射加载 → [Display] 分类 → 收集端口定义 → 注册进工具箱
   │
【拖到画布】生成 StepModel（只记 PluginTypeName 字符串 + LinkedSources 连线引用）
   │
【点编译】FlowCompiler 反射实例化插件 → ApplyConfigValues 灌配置 → (动态端口重建)
   │
【点运行】CompiledPluginNode 调 plugin.Execute(context) → RunAlgorithm 真正干活
   │
【结束】业务失败 Success=false 不抛异常；CompiledFlow.Dispose 统一释放插件(HImage 等)
```

**设计思想**：插件与主框架通过「**反射契约 + 白名单**」松散耦合。主框架不认识任何具体插件，它只认识 `IVisionPlugin` 接口；插件不认识主框架 UI，它只依赖 `IExecutionContext`。**双方只握一个接口，谁都能独立演进**——这是工业软件架构里几乎最优雅的插件化模型。

### 9.7 把全过程串起来（全景动线）

```
【你拖方块】                  StepModel / WhileStep / ConditionStep / ForStep
                                   │  只记录 PluginTypeName(字符串) + LinkedSources(连线引用)
                                   ▼
【点编译】  FlowCompiler.Compile
       CompileSteps  ──► 逐步骤判定类型 → 造 CompiledPluginNode/IfNode/WhileNode/ForNode/Break/Continue/Return
       LinkPorts     ──► 把连线解析成 4 类数据源(运行时变量/常量/全局变量/上游输出) 存入 dependencyMap
       CompileLocalVarParams / CompileRuntimeVarRefs ──► 安全类型校验 + 白名单 + 类型缓存 + Lambda 参数
                                   │
                                   ▼
        CompilationResult + CompiledFlow(RootNodes + PluginLookup + NodeLookup + DependencyMap)
        【编译产物 = 只读的、定型的可运行物】
                                   ▼
【你点运行】  FlowEngineService.RunSessionAsync
       (1) 复位所有步骤状态 ResetState
       (2) 开启 PauseLock / 新建 CancellationTokenSource
       (3) while(!取消) { PauseLock.Wait; 再复位; new ExecutionContext; ExecutionEngine.Run(ctx); }
                                   ▼
       CompiledFlow.Run ──► 栈式深度优先遍历
            ├─ CompiledPluginNode.Execute ──► 真正驱动相机/算法/通信
            ├─ CompiledIfNode ──► 返回命中分支序列 → 压栈
            ├─ CompiledWhileNode ──► 内部 while 循环体, 认领 Break/Continue
            ├─ CompiledForNode ──► 固定次数循环 + IndexPort
            ├─ Break/Continue ──► 竖"控制旗" → 最近循环复位并响应
            └─ Return ──► 旗子穿透到顶层 → 整个遍历 return
                                   ▼
【你点停止/暂停】  CancellationToken.Cancel() / PauseLock.Reset()
【流程结束】      finally 清运行焦点 + Dispose 所有插件实例(HImage等非托管资源) + 复位会话状态
```

### 9.8 这套设计「好」在哪？—— 收益清单

| 设计 | 好处 |
|---|---|
| **三层分离**（设计/编译/运行） | 图纸可反复编辑、可存盘、不拖累重量级插件；改图只需重编译一次；编译产物与蓝图解耦，互不影响 |
| **蓝图只存字符串 + 引用** | 可序列化、可版本管理、可跨机器打开；不保存活对象 |
| **编译期定型**（节点+端口+依赖全部定格） | 运行期极快（只做取值调用）；**错误连线编译期就报**，不留到运行时 |
| **栈式遍历代替递归** | 永不爆栈；天然支持取消/暂停/恢复/高亮插桩 |
| **`CurrentFlowState` 控制旗** | Break/Continue/Return 只用一行改状态，逻辑极简、职责清晰，可任意嵌套 |
| **`MaxIterations` + 每圈取消检查** | 三重防死循环、可紧急停止，视觉流程引擎必备安全护栏 |
| **业务失败不抛异常** | 检测不过/没拍到图属于业务状态，记日志继续跑，上位机绝不崩 |
| **编译物是插件属主** | 统一 Dispose 所有 HImage 等非托管资源，杜绝内存泄漏 |
| **安全类型白名单** | 编译期掐断表达式注入风险 |
| **执行指针高亮** | 几毫秒级步骤高亮仍恒定可见，不闪变 |
| **插件与框架反射契约** | 双方只握接口、松散耦合，各自独立演进（开闭原则） |
| **`DynamicExpresso` 每次 new** | 用极小构造开销换来多线程安全 |
