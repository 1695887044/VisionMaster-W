# 第 0 章 这是什么

**码读取 = 把图里的一维条码 / 二维码"翻译"成文字。**

> 生活比喻：超市收银员拿扫描枪"嘀"一下，条码就变成商品名和价格。视觉里的码读取就是这支扫描枪——只不过它读的是相机拍到的图，而且**一维码和二维码都读**。

它在流程里的位置（归在 **「图像处理」** 分组）：

```
[图像采集] → [创建 ROI] / [模板定位] → [图像预处理] → [码读取] → [CSV记录] / [结果上报]
                                                    ↓
                              Codes(string[]) / Count(int) / Text(string)
```

**一句话**：模板匹配解决"目标在哪"，Blob 解决"有没有缺陷"，而 **码读取解决"码上写的是什么"**——它是产线追溯（一物一码、防错、MES 上报）的关键节点。

## 0.1 一个非常重要的前提：本节点不做定位

**它只吃一张上级已经裁好的小图**，自己不找码在哪。

- 没有"识别区"参数、没有框选、配置界面里也没有图像编辑器（右侧是只读显示 `ImageReadOnly`，刻意不用可拖拽的 `ImageEdit`，免得让人以为能框选）。
- 好处：节点不关心"码在哪里"，上级换了定位方式（预处理 / 模板匹配 / 创建 ROI）也不用改读码节点。

> ⚠️ 上级裁剪时要**把码完整包住、留点余量，别贴边裁**。HALCON 文档写明：若传入图带 `reduce_domain`，搜索范围缩到该域，**但码没完全落在域内时可能找不到**。

# 第 1 章 设计思想

## 1.1 核心原理：建模型 → 查找解码 → 释放模型

一维和二维码走的是**两套不同的 HALCON 引擎**，但骨架都是三步：

```
① 建模型句柄    create_bar_code_model        / create_data_code_2d_model
② 查找 + 解码   find_bar_code                / find_data_code_2d
③ 释放句柄      clear_bar_code_model         / clear_data_code_2d_model
```

**为什么"释放"这一步必须重视**：模型句柄是 HALCON 侧的**非托管内存**。流程反复运行、反复开关配置窗口时若不清，会稳定泄漏。基类的 `Dispose` 只管输出端口承载的值，**管不到引擎内部的句柄**——所以本插件必须重写 `Dispose`。

## 1.2 一维 vs 二维码：最容易搞混的五处差异

| 维度 | 一维 BarCode | 二维 DataCode |
|---|---|---|
| 建模型 | `create_bar_code_model`（只吃通用参数，**不绑码制**） | `create_data_code_2d_model`（**码制在 create 时定死**） |
| 码制在哪给 | `find_bar_code` 的 CodeType **入参** | 建模型时的模型类型 |
| **切码制** | **无需重建模型** | **必须 clear + create** |
| 查找 | `find_bar_code` | `find_data_code_2d` |
| 结果寻址 | 只回一个字符串元组，用**整数下标**查 | 回 `ResultHandles` + `DecodedDataStrings`，查细节要**把句柄传回去** |
| 本插件可调参数 | **仅 `timeout`** | `polarity` + `timeout` |
| 释放 | `clear_bar_code_model` | `clear_data_code_2d_model` |

> 因为两族结果寻址方式完全不同（一个用下标、一个用句柄），硬合成一个引擎会写出一堆 `if (是一维)` 分支——所以本插件拆成 `BarCodeEngine` 和 `DataCodeEngine` 两个类。

## 1.3 三条设计原则

**原则①：没读到码 = 正常工况，不算失败**

`Success = true` + `Count = 0`，只写一条 Info 留痕。

理由：工件翻面、未打码、码被遮挡在现场都是**正常流**，用 `Fail` 会把良率统计搞脏。判定交给下游用 `Count` 做即可。**只有程序级异常**（码制名不认识、模型建不起来、图类型不对）才 `Fail`。

**原则②：同时给数组 `Codes` 和逗号串 `Text`**

`Codes` 是数组（一帧里所有解出的码都返回，实测 Code39 样张就是两个码）。但画布上数组端口只能整体连，而比较/上传/存变量这些既有下游节点**都是按标量写的**——没有 `Text` 它们接不上。所以额外给一个逗号分隔的 `Text`。

**原则③：存 HALCON 原始名，不存中文标签**

`Symbology` 存的是 HALCON 原始名（如 `"Data Matrix ECC 200"`），它是**稳定身份**——改中文标签不会让存量图纸失效。表里查不到时**报明确错误**，不静默退回默认码制。

> 为什么不静默退回：静默退回会让现场以为在用 A 码制、实际按 B 在找，表现只是"读不到码"，无从排查。

## 1.4 参数每次 find 前重设一遍

`set_*_param` 只是往句柄上写几个字段，开销可忽略。而"改了配置却因为句柄被复用而没生效"是极难查的一类问题（现象是"参数动了但结果不变"）。所以宁可每次重设，换掉这个坑。

# 第 2 章 技术特点

## 2.1 元数据

| 特性 | 值 |
|---|---|
| `Name` | 码读取 |
| `GroupName` | 图像处理 |
| `Description` | 读取一维条码与二维码（Data Matrix / QR / Micro QR / PDF417 / Aztec / DotCode 等） |
| `ShortName` | 条码图标（FontAwesome `f02a`） |

## 2.2 端口完整清单（全部固定端口，无动态端口）

| 端口 | 方向 | 类型 | 说明 |
|---|---|---|---|
| `Image` | 入 | HImage | 待读码图像（`IsRequired = false`）。应由上级定位后裁剪好，把码完整包住 |
| `Codes` | 出 | `string[]` | 一帧里所有解出的码文本（可能多个） |
| `Count` | 出 | int | 码的个数。**下游判"有没有码"用它**（0 = 本帧没有码，属正常工况） |
| `Text` | 出 | string | 所有码文本的逗号分隔形式，供按标量工作的既有下游节点使用 |

另有基类隐式端口 `Success`、`ErrorMessage`。

> ⚠️ **本插件不输出**：码的位置（Row/Column）、逐码的码制、质量等级/置信度。这是明确的已知边界，别误以为有。

## 2.3 配置项（只有 3 个）

| 配置 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `Symbology` | string | `Data Matrix ECC 200` | 码制。存 HALCON 原始名，界面显示中文标签 |
| `TimeoutMs` | int | `500` | 搜索超时(ms)，`0` = 不限 |
| `Polarity` | string | `any` | 极性，**仅二维码有效** |

**为什么只有 3 个**：本插件刻意最小化。像"预处理增强、对比度"这类参数**一概没有**——图像增强交给上游 `Plugin.PreProcessing`。多一个旋钮就多一处要现场理解的东西。

**超时为什么默认 500ms**：图里没有码时 HALCON 会在候选区域上反复尝试，没有超时保护会拖住整条流程。

**极性为什么默认 `any`**：激光 DPM 打码在金属上常是亮码暗底或低对比，让 HALCON 两种都试更稳；已知极性时明确指定可提速。

### 极性选项（仅二维码）

| 显示 | 值 |
|---|---|
| 自动（两种都试，推荐） | `any` |
| dark_on_light（暗码亮底） | `dark_on_light` |
| light_on_dark（亮码暗底） | `light_on_dark` |

## 2.5 HALCON 算子清单

### 一维引擎（`BarCodeEngine.cs`）

| 算子 | 作用 |
|---|---|
| `create_bar_code_model` | 建一维模型句柄（不绑码制） |
| `set_bar_code_param`（`timeout`） | 设搜索超时（仅 `>0` 时） |
| `find_bar_code` | 找码并解码（码制作为 CodeType **入参**） |
| `clear_bar_code_model` | 释放模型句柄 |

### 二维引擎（`DataCodeEngine.cs`）

| 算子 | 作用 |
|---|---|
| `create_data_code_2d_model` | 建二维模型（**码制在 create 时定死**） |
| `set_data_code_2d_param`（`polarity` / `timeout`） | 设极性 / 超时 |
| `find_data_code_2d` | 查找 + 解码（回 `ResultHandles` + `DecodedDataStrings`） |
| `clear_data_code_2d_model` | 释放模型句柄（切码制时 + `Dispose` 时） |

> 本插件**没有**用 `decode_bar_code_rectangle2`（"已知位置直接解码"）——那条路要求矩形**角度也准**，现场调参成本高；且本插件按用户要求不做定位，没有"已知位置"这个前提。等真测出节拍不够再加。

## 2.6 性能与独特实现

| 手段 / 设计 | 做法 | 收益 |
|---|---|---|
| **两引擎分离** | 一维/二维各一个引擎类 | ⭐⭐⭐ 结果寻址方式不同，硬合会写一堆分支 |
| **句柄按码制缓存** | 码制没变复用，变了 clear+create | ⭐⭐ 不做"每码制一句柄"字典（防配置界面反复切码制导致句柄堆积） |
| **参数每次 find 前重设** | 防"参数动了结果不变" | ⭐⭐ 消灭极难查的一类问题 |
| **重写 `Dispose`** | 释放两个引擎句柄 | ⭐⭐⭐ 基类管不到引擎内部句柄，不重写必泄漏 |
| **试算与运行共用同一条 `TryRead`** | 若走两套代码，界面上看着对、跑起来不对，那种问题最难查 | ⭐⭐⭐ 所见即所得 |
| **未找到码算正常工况** | `Success=true` + `Count=0` + Info 留痕 | ⭐⭐⭐ 良率统计不被搞脏 |
| **`Codes` 数组 + `Text` 逗号串** | 兼顾数组下游与标量下游 | ⭐⭐ 既有标量节点接得上 |
| **上游图拷贝一份显示** | 上游句柄归框架管，插件只管自己副本 | ⭐⭐ 资源所有权清晰 |

# 第 3 章 使用方式

## 3.1 安装与启用

1. **无需单独安装**：正常编译解决方案即产出 `Modules/Plugin.CodeReader.dll`。
2. 依赖 HALCON 原生库（随软件分发）。
3. **本插件没有需要投递的资源文件**——这是与 `Plugin.Ocr` 的重要差别：一维/二维码的模型是 HALCON **在运行期按码制名现场构造**的，不依赖外部模型文件（OCR 的 `.omc` 是训练产物，必须随插件带）。所以既不需要 Assets 目录，也不需要 PostBuild 投递——**少一条会出错的链路**。
4. 重开软件，工具箱里出现「码读取」（**图像处理** 分组）。

## 3.2 配置界面总览（两列，900×560）

```
┌──────────────────────────┬────────────────────────────┐
│ 左：参数（330px 可滚动）    │ 右：只读图像显示              │
│  ① 图像输入（可🔗链接上游）  │  ImageReadOnly（不能框选）    │
│  ② 码制（下拉）            │                            │
│  ③ 二维码参数（极性）       │  ← 只有选了二维码才出现        │
│  ④ 通用参数（超时）         │                            │
│  ⑤ 试算（按钮 + 结果）      │                            │
└──────────────────────────┴────────────────────────────┘
```

## 3.3 第一次读码（5 步）

**第 1 步｜上级先把码裁好**：用创建 ROI / 模板匹配 / 图像预处理把码找出来并裁好，**把码完整包住、留点余量**（别贴边裁）。

**第 2 步｜接图**：在配置窗口左栏「图像输入」用 `LinkableValueEditor` 直接🔗链接上游（不用回画布拖线）。或在画布上把上级输出连到 `Image` 端口。

**第 3 步｜选码制**：左栏②下拉选码制。选完下方会显示提示：
- 二维码 → "二维码：可调极性。一个模型只能是一种码制，切码制会重建模型。"
- 一维码 → "一维码：无极性参数（一维读码本身对极性鲁棒）。**选具体码制比用「自动」快得多。**"

**第 4 步｜（仅二维码）设极性**：默认 `any`（两种都试）。已知极性就明确指定，可提速。

**第 5 步｜试算**：点「试算一下」，下方显示结果：
```
码制：Data Matrix ECC 200
读到 1 个码
  ABC-123456
```

> 试算与正式运行**共用同一条 `TryRead`**——界面上看着对，跑起来就对。

## 3.4 参数调节速查表

| 现象 | 调哪里 |
|---|---|
| 读不到码 | ① **码制选对了吗**（最常见）② 上级图把码完整包住了吗（别贴边裁）③ 超时太短？调大 `TimeoutMs` |
| 读得慢 | ① 别用 `auto`，选**具体码制** ② 二维已知极性就明确指定（别用 `any`）③ 超时设小一点 |
| 亮码暗底 / 暗码亮底 | （仅二维码）设 `Polarity` 为 `light_on_dark` / `dark_on_light` |
| 一帧有多个码 | 用 `Codes` 数组（或 `Text` 逗号串）。注意多码顺序由 HALCON 定 |
| 想把码内容存变量/比较 | 用 `Text`（标量）。`Codes[0]` 下标写法在画布上未必给得出 |
| 上级图脏、对比度低 | 在上游加 `Plugin.PreProcessing` 洗图（本节点没有增强参数） |

## 3.5 FAQ

**Q1** 为什么没有框选/识别区？
本节点**不做定位**（用户明确要求）。上级用预处理/模板匹配/创建 ROI 把码找出来裁好再连进来。这样节点不关心"码在哪里"，上级换定位方式也不用改读码节点。

**Q2** 图里没码会报错吗？
**不会**。`Success=true` + `Count=0`，只写一条 Info 留痕。工件翻面、未打码、码被遮挡都是正常流——用 `Fail` 会搞脏良率统计。判定交给下游用 `Count` 做。

**Q3** 为什么默认码制是 Data Matrix？
工业追溯里 Data Matrix 最常见（激光 DPM 打码基本都是它）。

**Q4** 一维码为什么没有"极性"参数？
实测 `set_bar_code_param` **拒绝 `polarity`**（HALCON `#3286`）——一维读码本身对极性鲁棒，压根没这个旋钮。把用不上的参数显示出来，只会让现场以为动它能解决问题。

**Q5** 能读出码的位置吗？
**不能**。本插件只输出文本（`Codes`/`Text`/`Count`），不输出位置、逐码码制、质量等级。这是明确的已知边界。

**Q6** 切码制会不会很慢？
一维：不会（模型不绑码制，无需重建）。二维：会重建模型（clear+create），但只在切码制那一刻发生。

**Q7** `auto` 为什么慢？
它会在图里逐个码制试。选具体码制快得多。

## 3.6 现场排障

| 现象 | 排查 |
|---|---|
| 明明图上有码却 `Count=0` | ① 码制选错（日志会带当前码制名）② 上级贴边裁没包住码 ③ 超时太短 |
| 日志出现"二维候选 N 个，其中成功解出 M 个" | 找到了候选但没解出内容（码脏/对比度低）。看上游是否要洗图 |
| 报"不在支持的码制表里" | 码制名拼错。**不静默退回默认**，错误信息会列出所有可选值 |
| 报"上游没有图像" | 上级没连图，或上级输出为空 |
| 读码拖慢整条流程 | 调小 `TimeoutMs`；别用 `auto`；二维明确指定极性 |
| 配置窗口看不到上游图 | 已修（端口订阅 + `ShowUpstreamImage` + `LinkableValueEditor` 两轮修复） |
| 按钮文字被裁 | 已修（删写死 Height，改用 `PluginButton`） |

## 4.1 缺陷修复总览

| 级别 | 问题 | 一句话 |

| P1 | sln GUID 撞车 + 误删配置映射 | CodeReader **静默地不参与构建** |

| P3 | `Codes[0]` 下标在画布未必给得出 | 额外提供 `Text` 逗号串 |

## 4.2 P1 级详解

### ① `set_bar_code_param` 拒绝 `polarity`（`#3286`）

**现象**：给一维模型设极性时报 `#3286 Wrong generic parameter name`。

**原因**：**一维模型的 `set_bar_code_param` 不接受 `polarity`，而二维模型的同名参数是接受的**。一维读码本身对极性鲁棒，压根没有这个旋钮。

**实测被接受的 1D 参数名**（逐个试出来的，不是猜的）：
`element_size_min` / `element_size_max` / `num_scanlines` / `orientation` / `quiet_zone` / `start_stop_tolerance` / `check_char` / `meas_thresh` / `min_identical_scanlines` / `persistence` / `timeout` / `composite_code`

**修法**：一维引擎只用 `timeout`（其余在没实测需求前不暴露）；**配置界面按码制家族显示不同参数项**——1D 面板不该出现极性项。这条差异就是"参数按家族分派"的硬依据。

### ② `DecodedDataStrings` / `ResultHandles` 口径矛盾

**现象**：不确定该按哪个输出判断"解出了几个码"。

**原因**：**HALCON 官方文档对这两个输出的口径自相矛盾**——`ResultHandles` 写"只含成功解码的"，`DecodedDataStrings` 写"含所有检测到的"。既然文档不一致，就不能按任一方写死逻辑。

**修法**：按"**字符串非空**"收码（解不出内容的候选，其字符串为空）；并在数量不一致时把两个数都报出来——宁可多一条诊断，也不要静默丢码。诊断文案：`二维候选 N 个（句柄 M 个），其中成功解出 K 个`。

> 这条诊断解释了"为什么图上有码却 `Count=0`"，是排障的关键线索。

### ③ 配置窗口看不到上游图（两轮修复）

**现象（用户反馈）**："怎么没有上游图像绑定的地方？"

**排查**：流程级绑定是正常的，缺口在配置窗口。

**修法（两轮）**：
- 第一轮：构造函数订阅 `Image.PropertyChanged` → `OnImagePortChanged` → `ShowUpstreamImage()`（**显示的是自己拷的一份**，上游句柄归框架管）→ `OnViewLoaded` 优先显示上游图。
- 第二轮：配置窗口内加「图像输入」**链接卡片**（`LinkableValueEditor`），照 BlobDetect 的做法。

> 两轮的关系：`LinkableValueEditor` 解决"**怎么连**"，`ShowUpstreamImage` 解决"**连上之后怎么看**"。

### ④ sln GUID 撞车 + 误删配置映射（⚠️ 事故）

**现象**：`Plugin.CodeReader` "登记了却不在解决方案里"，构建不报错；误删 sln 配置映射 12 行后，CodeReader 会**静默地不参与构建**。另一次：sln 里声明的 GUID 与 13 处嵌套引用不一致 → 孤儿 GUID → 整解决方案无法加载（`MSB5023`）。

**修法**：改声明侧一行（统一 GUID）；补全被误删的配置映射。

**教训三条**（已写进纪律）：① sln 改动要小心并行任务互相覆盖；② 新增插件工程必须核对 GUID 唯一性；③ 构建"不报错"不等于"参与了构建"，要用产物投递验证。

## 4.3 P2/P3 级详解

### ⑤ 二维模型码制定死 → 切码制必须重建

**现象**：切了二维码制后仍在按旧码制找。

**原因**：`create_data_code_2d_model` 把码制**定死在 create 时**，不像一维那样把码制作为 `find_bar_code` 的入参。

**修法**：句柄按码制缓存——码制没变就复用，变了就 `clear` + `create`。**不做"每个码制一个句柄"的字典**（那会让配置界面试算时反复切换码制、句柄无限堆积）。

### ⑥ 参数改了不生效

**现象**：改了超时/极性，结果没变。

**原因**：句柄被复用，而 `set_*_param` 只在建句柄时设过一次。这是**极难查**的一类问题。

**修法**：参数**每次 find 前重设一遍**。`set_*_param` 只是往句柄上写几个字段，开销可忽略。

### ⑦ 按钮文字被裁

**现象**：配置窗口按钮文字显示不全。

**原因**：按钮写死 `Height=24/26`，而隐式样式 `Padding="18,7"` + `FontSize=13` 需要 34px。

**修法**：删写死 Height，改用公共样式 `PluginButton`。

### ⑧ `Codes[0]` 下标在画布未必给得出

**现象**：想在画布上取"第一个码"但取不到。

**修法**：额外提供 `Text` 逗号串（标量），让按标量工作的既有下游节点（比较/上传/存变量）接得上。

## 4.4 代码级踩坑汇编

| # | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 1 | 一维设极性报 `#3286` | 一维没有 polarity 参数 | 只用 timeout；UI 按家族分派 |
| 2 | 二维切码制不生效 | 码制定死在 create | clear + create |
| 3 | 参数改了不生效 | 句柄复用未重设 | 每次 find 前重设 |
| 4 | 句柄泄漏 | 基类管不到引擎内部句柄 | 重写 `Dispose` 释放两个引擎 |
| 5 | 计数拿不准 | 文档口径自相矛盾 | 按"字符串非空"收码 + 双数诊断 |
| 6 | 上游图所有权混乱 | 直接用了上游句柄 | 显示自己拷的一份 |
| 7 | 内存增长 | 算子输出的区域对象未释放 | `finally` 里 `symbolRegions?.Dispose()` |
| 8 | 试算与运行不一致 | 走两套代码 | 共用同一条 `TryRead` |

## 4.5 HALCON API 踩坑

| # | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 1 | `#3286` Wrong generic parameter name | 一维模型不接受 `polarity` | 一维只用 timeout |
| 2 | 二维切码制不生效 | 码制在 create 时定死 | clear + create |
| 3 | 计数口径拿不准 | 文档自相矛盾 | 按字符串非空收码 |
| 4 | 读不到码（贴边裁） | `reduce_domain` 后码没完全落在域内 | 上级裁剪留余量 |
| 5 | 无码时流程被拖住 | HALCON 在候选区反复尝试 | 设 `timeout`（默认 500ms） |
| 6 | 释放句柄报错 | 用错算子名 | `clear_bar_code_model` / `clear_data_code_2d_model` |

## 4.6 已知边界与待办

- **无独立真值**：二维码/条码的**内容**无法像 OCR 那样人工读图确认（人眼读不出 QR 的比特）。唯一独立真值是 **EAN 校验位**（按编码规则算，不依赖 HALCON）。
- **多码顺序由 HALCON 定**，不保证稳定。
- **未输出**：码位置、逐码码制、质量等级/置信度。
- 上级裁剪必须留余量，别贴边裁。
- `auto` 明显变慢，不推荐。
- `Polarity` 在一维下无意义（良性冗余，界面已隐藏）。
- 未做 `decode_bar_code_rectangle2` 快路径。
- `Codes[0]` 下标写法在画布上未必给得出（用 `Text`）。
- 配置窗口跨线程 `PropertyChanged` 依赖 WPF 封送；订阅不退订（实例生命周期内常驻）。

| 术语 | 含义 |
|---|---|

| 术语 | 含义 |
