## 1. 为什么"又小又拉不动"

`VariableBindingView.xaml` 顶部：

```xml
Width="900" Height="580"
<prism:Dialog.WindowStyle>
    <Style TargetType="Window">
        <Setter Property="ResizeMode" Value="NoResize" />
        <Setter Property="SizeToContent" Value="WidthAndHeight" />
```

三处叠加：

| 写法 | 后果 |
| --- | --- |
| `Width=900` + 三栏布局 | 中间栏固定 280、右侧只有 `*`，900 宽里塞三栏必然挤 |
| `ResizeMode="NoResize"` | 用户**拉不大**（边框不可拖） |
| `SizeToContent="WidthAndHeight"` | 窗口永远贴着内容，就算放开 ResizeMode，拖动也看不到变化（被 SizeToContent 拽回去） |

所以"展示不开"不是美观问题，是**结构上不允许用户自己腾地方**。

### 改法

```xml
<!-- 视图：只给下限，尺寸交宿主 -->
MinWidth="1000" MinHeight="640"

<!-- 宿主窗口：舒适的默认 + 允许缩放 -->
<Setter Property="ResizeMode" Value="CanResize" />
<Setter Property="SizeToContent" Value="Manual" />   <!-- 必须显式设回，否则拖不动 -->
<Setter Property="Width" Value="1180" />
<Setter Property="Height" Value="760" />
<Setter Property="MinWidth" Value="1000" />
<Setter Property="MinHeight" Value="640" />
<Setter Property="WindowStartupLocation" Value="CenterOwner" />
```

三栏也改成等比例自适应（原来 `280 / 280 / *`，拉大窗口只有第三栏变宽）：

```xml
<ColumnDefinition Width="1*"   MinWidth="240" />   <!-- 当前算子输入 -->
<ColumnDefinition Width="10" />                     <!-- GridSplitter -->
<ColumnDefinition Width="1*"   MinWidth="240" />   <!-- 选择上游算子 -->
<ColumnDefinition Width="10" />
<ColumnDefinition Width="1.3*" MinWidth="360" />   <!-- 绑定选项 -->
```

`MinWidth` 是"三栏都得能用"的下限：低于它宁可卡住不缩，也不要挤成一条缝。两个 `GridSplitter` 仍可手动分配（`ResizeBehavior="PreviousAndNext"`）。

## 4. 顺手修的一个真实隐患：类型名解析

上一轮加的"按类型过滤候选"依赖 `Type.GetType(DataTypeName)`。查了仓库里 `DataTypeName` 的实际来源：

- `Engine/PluginService.cs:209/222` → `p.DataType.AssemblyQualifiedName`
- `Engine/FlowQueryHelper.cs:74/122/178` → `AssemblyQualifiedName`
- 各插件 `DynamicPortInfo`（CreateRoi / ImageScript / CSharpScript）→ `AssemblyQualifiedName`

所以绝大多数情况 `Type.GetType` 直接命中。但**插件自己手写的固定端口可能只写短名**（如 `"HalconDotNet.HImage"`），那时 `Type.GetType` 返回 null ⇒ 退回 `object` ⇒ 过滤**静默失效**（界面看起来正常，只是不筛了）。

新增 `TypeHelper.ResolveType`：

```csharp
public static Type ResolveType(string? typeName)
{
    if (string.IsNullOrWhiteSpace(typeName)) return typeof(object);
    var resolved = Type.GetType(typeName, throwOnError: false, ignoreCase: true);
    if (resolved != null) return resolved;
    foreach (var assembly in AppDomain.CurrentDomain.GetAssemblies()) { ...按名查找... }
    return typeof(object);   // 认不出来 = 什么都接得住
}
```

**刻意不用 `GetActualTypeFromLink`**：它对未知类型名返回 `typeof(double)`，于是"HRegion 端口撞上 double 期望"会被判成兼容（数值互转）——把不能绑的放过去。判据方向必须是"认不出来就放行"：最坏结果是"该过滤的没过滤掉"（用户看得见），而不是"能绑的被藏起来"。

`VariableBindingViewModel` 的两处 `Type.GetType`（过滤与双击校验）都换成了它。

## 8. 事后修复：真机打开弹窗抛 XamlParseException

第一版交付后，实际打开弹窗报：

```
System.Windows.Markup.XamlParseException
  Message=设置属性"System.Windows.Setter.Property"时引发了异常。行号为 36，行位置为 14。
内部异常 ArgumentNullException: Value cannot be null. (Parameter 'property')
```

### 根因：`WindowStartupLocation` 不是依赖属性

行 36 是我加的 `<Setter Property="WindowStartupLocation" Value="CenterOwner" />`。

**`Style` 的 Setter 只能设 `DependencyProperty`**，而 `Window.WindowStartupLocation`
是个普通 CLR 属性（没有 `WindowStartupLocationProperty` 静态字段）——
XAML 解析器找不到对应的 DP，于是把 `Setter.Property` 留成 `null`，构造 Setter 时抛 `ArgumentNullException("property")`。

一次性探针逐个 Setter 实测（每种属性都试短名与 `Window.` 全名）：

```
OK    短名 WindowStyle / 全名 Window.WindowStyle
FAIL  短名 ResizeMode                :: ArgumentException: Requested value 'None' was not found.   ← Property 解析成功，只是探针给的值不合法
FAIL  短名 Width / Height / MinWidth / MinHeight  :: FormatException: 无法将"None"字符串转换为 Length   ← 同上，Property 没问题
FAIL  短名 WindowStartupLocation     :: ArgumentNullException: Value cannot be null. (Parameter 'property')   ← 只有它 Property 解析失败
FAIL  全名 Window.WindowStartupLocation :: 同上（加类型前缀也救不了）
```

即：`Width`/`Height`/`MinWidth`/`MinHeight`/`ResizeMode`/`SizeToContent`/`WindowStyle` 都是 DP、可以照常写在 Setter 里；
**只有 `WindowStartupLocation` 不行**。窗口居中交给宿主（Prism DialogService），与仓库里其它弹窗保持一致。

### 顺带查出的第二个潜伏问题

修完上面那条，探针继续往下走，又在第 179 行炸：`无法找到名为"Icon"的资源`（那是 App.xaml 提供的，探针里补上即可）——
补上之后才暴露出**真正潜伏更久的一条**：

```xml
<!-- 视图（DataTemplate 内）原本写的是 -->
Visibility="{Binding Definition.IsFunctionalEnum, Converter={StaticResource BooleanToVisibilityConverter}}"
```

`BooleanToVisibilityConverter` 在 **App.xaml 与 UI 库任何合并字典里都没有定义**（`App.xaml` 只提供 `Icon` / `ExpandToggleButtonTemplate` / `LinkButtonStyle`）。
UI 库里只有一个 `UI/Controls/Converters/BooleanToVisibilityConverter .cs`（类，走 `ui:` 命名空间映射），
正确用法是同文件里已经用着的 `{ui:BooleanToVisibilityConverter}`。

**为什么以前没暴露**：这三处在 `InputPortTemplate`（DataTemplate）内部，`{StaticResource}` 会延迟到**模板实例化**时才解析 ——
左侧端口列表为空时模板从不实例化，所以一直没事；一旦列表渲染出第一行就会抛。
换句话说：**只要打开弹窗时左侧已经能列出端口，这个弹窗就会炸**，只是被更早的 Setter 异常挡住了。
已统一改成 `{ui:BooleanToVisibilityConverter}`（同文件其它位置本来就是这么写的）。

## 9. 探针留档（可复制重建）

这次的关键工具是"**真的构造一遍视图**"。它和冒烟断言互补：断言是静态扫描（不碰 WPF 运行时），
而它跑到 WPF 运行时里，能抓住所有"只在加载 BAML 时才炸"的问题。**只验资源字典是不够的** —— 这点本轮付了学费。

工程 `ViewProbe.csproj`（仓库外临时目录，用完即删）：

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net9.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>
  </PropertyGroup>
  <ItemGroup>
    <ProjectReference Include="..\VisionMaster\VisionMaster.csproj" />
  </ItemGroup>
</Project>
```

要点（踩过的坑都在这儿）：

1. **必须 `new Application()`** —— `pack://` 前缀由 WPF 在 Application 初始化时注册，没有它连相对 URI 都解析不了；
   代价是退出会挂在无消息泵的 STA 线程上，末尾用 `Environment.Exit(...)` 强制收尾。
2. **先把 UI 库字典挂进 `app.Resources`**，否则 `{StaticResource Dialog*}` 会报"找不到资源"（那是环境问题，不是视图问题）。
3. **再补 `Icon`** —— 它是 App.xaml 里的 inline 资源。除它之外**一个键都不要补**：
   凡是视图用到、App 该提供却没有的，都是真机上也会炸的缺陷，必须在视图里改掉，不能在探针里兜住
   （`BooleanToVisibilityConverter` 就是这么被揪出来的）。
4. **`ViewModelLocationProvider.SetDefaultViewModelFactory(_ => null)`** —— 视图挂着 `AutoWireViewModel`，
   Prism 会在设置该附加属性时立刻解析 ViewModel；探针里没有 Prism 容器，不接这一手会先炸在
   `MissingMethodException: No parameterless constructor defined`，根本走不到要验证的地方。
5. **`new VariableBindingView()` 就是 `InitializeComponent()` 的完整路径**（构造函数 → `Application.LoadComponent(this, uri)`），
   不入可视化树即可（Prism 的 VM 解析挂 Loaded，不入树就不触发）。

## 10. 补记：候选行显示数据类型

用户发来截图问："为什么变量弹窗绑定的时候不显示数据类型"。

### 事实：不是改丢的，是一直没有

候选行确实没显示类型 —— 但**改前也没有**（原版是"名称 + 描述"同行横排）。
所以这不是重写时的遗漏，而是原本就缺的一项信息。但用户问得对：**该显示**。

### 为什么该显示

绑定是**类型敏感**的动作。"这一项能不能接住当前端口"本来就靠类型判断，
列表里不显示类型就只能靠名字猜。勾了「显示全部」时更明显 ——
不兼容项被置灰，而"为什么不行"恰恰要看类型（悬停虽有原因，但一眼扫过去才知道该挑哪个）。

### 怎么加

名称行右侧一枚类型胶囊（`DialogChip`），文字走已有的 `TypeNameToFriendlyNameConverter`
（左栏本来就用它，两处口径一致）：`DataTypeName` 存的是程序集限定名
（`System.String, mscorlib, …`），转换器把它变成「文本 (String)」「小数 (Double)」这种可直接读的形式。

不占用名称/描述的位置：描述仍在第二行独占，两者都保留 `TextTrimming`（窄栏时省略号而不是撑破）。
胶囊外层挂 `ToolTip="{Binding DataTypeName}"`，要精确类型名时悬停可见。

### 验证（探针给候选列表喂三种真实形态，强制模板实例化）

```
渲染出的文本：... | 文本 (String) | ... | 小数 (Double) | 图像 (HImage)
∨ 候选行显示类型「文本 (String)」/「小数 (Double)」/「图像 (HImage)」
∨ 名称/描述仍在
```

第三种特意用**插件手写端口**的形态 `"HalconDotNet.HImage, halcondotnet"`（短名 + 程序集后限定），
确认转换器也能转出「图像 (HImage)」—— 不能只测 `typeof(...).AssemblyQualifiedName` 那一种
（仓库里真实端口两种写法都存在：`FlowQueryHelper` / `PluginService` 用全名，插件手写端口可能只写短名）。

### 回归断言

新增 `【绑定】候选行显示数据类型`：整栏重写时最容易漏的就是它，而它又是纯展示项 ——
漏了不会有任何报错，只会让用户面对一列表名字猜类型。
