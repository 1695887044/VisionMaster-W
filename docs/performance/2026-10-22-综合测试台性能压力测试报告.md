## 6. 同一流程并发（运行锁）

同步启动两路 `Test_Comm`，共 5 对：

| 结果 | 次数 |
| --- | --- |
| 200 + 409 | 4 |
| 200 + 200 | 1 |

- 409 证明“同一流程只允许一个运行会话”的锁生效。
- 唯一一对 200/200 是 `Start-Job` 进程启动偏差导致两次请求实际错开（日志显示相隔约 4 s），未形成真正重叠；**不能据此判定锁失效**。
- 建议后续用文件栅栏/同一进程 `HttpClient` 同时发两请求复测。

## 9. 结论

1. **HTTP 服务本身稳定**：单流程 100 次、并发 100 次、混合 22 次、长跑 150 次，除运行锁 409 与测试夹具偏差外，全部成功。
2. **纯处理能力**：`Test_Vision` 约 **0.135 s/次（≈7.4 req/s 顺序）**，`Test_Data` 约 **0.147 s/次（≈6.8 req/s）**；HTTP 开销约 30~50 ms。
3. **固定延时是吞吐主因**：`Test_Comm` 1.28 s、`Test_Logic` 0.79 s、`Test_Motion` 4.08 s，均含流程内 `Delay`/`Wait`，不能当作插件性能。
4. **内存**：150 次视觉长跑峰值约 **997 MB**；混合压力峰值 **1307.8 MB**；2 GB 守卫未触发。500+ 次长跑建议把守卫提到 2.5~3 GB 或调低图像集上限。
5. **CPU**：16 线程下平均 **6.5%**，约 1 核；瓶颈不在 CPU，更多在 HALCON 调用、固定延时与图像集拷贝。

## 10. 建议

| 场景 | 建议 |
| --- | --- |
| 多工位连续生产 | 用单 Main 内联或 `RunInBatch` 架构（见上一轮评审），不要用 HTTP 逐站触发 |
| 高节拍检测 | 去掉测试流程里的 `Delay`/`Wait` 演示段；`Test_Vision` 的 0.135 s 可作为基线 |
| 长跑 | 监控工作集；图像集 `TotalLimit` 300 帧是内存上限的主要来源；必要时关闭实时预览或降低上限 |
| 并发 | 同一流程并发已被 409 拦截；不同流程并发可用，但共享 HALCON/相机/PLC 时需串行或资源锁 |
| 压测 | 建议用固定请求数 + 文件栅栏做并发复测；本次 `Start-Job` 启动偏差使 1 对重复请求未重叠 |
