# 算子试运行耗时归因（变量赋值 10 ms 从哪来，2026-10-23）

> 状态：**已量化，未改产品代码**。本文只回答"配置窗口里那句 `耗时: 10 ms` 是怎么算出来的、
> 10 毫秒花在哪"，不含优化方案。
>
> 被测链路：`PluginConfigShellViewModel.ExecutePlugin` → `PluginTestRunner.Run`
> （真 `FlowCompiler`、真 `FlowSession`、真 `LogService`、真 `VariableAssignmentPlugin`）
> 被测流程：合成流程（1/5/20/50/100 步「变量赋值」串联）+ `解决方案\综合测试台.vms`
> （14 条流程 / 全部嵌套 409 步 / 最大 78 步）
> 探针：`%TEMP%\vm-trial-perf\trialprobe.exe`（仓库外临时工程，未入库；复现见 §7）

## 1. 结论（先看这四条）

1. **10 ms 不是"变量赋值"这个算子的耗时。** 裸调 `VariableAssignmentPlugin.Execute` 的中位数
   **0.2 µs**（p95 0.4 µs）——赋值本身比计时器分辨率还小。
2. **界面上的数字是整个试运行管线的墙钟**：`PluginTestRunner.Run` 的秒表从**全流程重编译**开始，
   依次经过 编译 → 建会话 → 跑上游链 → 灌端口 → 执行目标算子。
   编译耗时按流程总步数走，与"你试的是哪一步"无关。
3. **同一个动作，第一次和第二次不是一个量级**：

   | 场景 | 实测（Release） | 界面显示 |
   | --- | --- | --- |
   | 进程内第一次试运行（该流程此前没编译过） | 22.2 ms | **20 ms** |
   | 进程内第一次试运行（该流程此前编译过一次） | 8.2~8.8 ms | **7~8 ms** |
   | 第二次点同一个按钮 | 0.11~0.34 ms | **0 ms** |
   | 稳态中位数（50 次） | 0.02~0.19 ms | — |

   10 ms 落在"**冷启动残值**"这一档：编译代码/JIT 已经热过一次，但 `Run` 链路本身还是第一次走。
4. **稳态下这个数由流程大小决定**（实测 20~38 µs/步，含真实插件实例化）：

   | 流程 | 步数 | 试运行中位数 |
   | --- | --- | --- |
   | Test_Vision | 78 | 2.27 ms |
   | Test_Logic | 68 | 1.43~1.46 ms |
   | Test_Comm | 45 | 0.66~0.71 ms |
   | Test_Data | 23 | 0.43 ms |
   | Home | 11 | 0.10 ms |
   | Main | 2 | 0.02 ms |

   所以"每点都 10 ms"只可能是：流程很大（约 300 步）/ 上游链里有真在干活的步骤 / 机器当时有负载，
   **不会是赋值算子本身**。

## 2. 这个数字的口径（代码位置）

| 环节 | 位置 | 说明了什么 |
| --- | --- | --- |
| 秒表起表 | `Engine/PluginTestRunner.cs:62` | `Stopwatch.StartNew()` 与"编译整个流程"是同一条语句序列的开头 |
| 计入范围 | `Engine/PluginTestRunner.cs:75` | `compiler.Compile(flow.Steps, flow.FlowName)` —— **整个流程**，不是目标节点的上游 |
| 上游链 | `Engine/PluginTestRunner.cs:121` | `ExecuteUpstreams(...)`：目标节点的所有上游依赖会在编译实例上真跑一遍 |
| 目标执行 | `Engine/PluginTestRunner.cs:131` | `configPlugin.Execute(context)` —— 只有这一段才是"变量赋值" |
| 出数 | `Engine/PluginTestRunner.cs:171` | `Ok(sw.ElapsedMilliseconds, …)` |
| 上屏 | `VisionMaster/ViewModels/DialogViewModels/PluginConfigShellViewModel.cs:443` | `ElapsedText = $"耗时: {result?.ElapsedMs ?? 0} ms"` |

两个由此推出的性质：

- **整数截断**：`ElapsedMs` 是 `long` 且来自 `ElapsedMilliseconds`，界面永远只显示整毫秒。
  赋值本身 0.2 µs，在这个口径下永远显示 0 —— 这个数字**结构上就不可能反映出算子快不快**。
- **不缓存**：`FlowCompiler.Compile`（`Engine/FlowCompiler.cs:244`）没有任何按版本命中的编译缓存，
  且每个步骤在 `Engine/FlowCompiler.cs:847` 走一次 `Activator.CreateInstance(type)`。
  点一次 = 全流程重编译 + 全流程插件重新实例化，**哪怕你只试运行一个 1 步的算子**。

## 3. 冷/热对照（每格一个独立进程）

命令：`trialprobe.exe firstclick <步数> [compileFirst]`

- `compileFirst=False`：进程内第一次动作就是试运行（编译也在里面，全冷）。
- `compileFirst=True`：先单独编译一次该流程（模拟"这个流程此前跑过/编译过"），再量试运行。

| 构建 | 模式 | n=1 | n=5 | n=20 | 第二次点 | 稳态中位数 |
| --- | --- | --- | --- | --- | --- | --- |
| Debug | 全冷 | 25.20 ms（显示 23） | 22.37（20） | 22.56（20） | 0.20~0.51（0） | 0.02~0.19 |
| Debug | 编译已热 | 10.53（9） | 9.39（8） | 10.05（9） | 0.16~0.34（0） | 0.01~0.18 |
| Release | 全冷 | 113.39（111）※ | — | 22.15（20） | 0.27~0.34（0） | 0.02~0.19 |
| Release | 编译已热 | 8.23（7） | 8.81（8） | 8.20（7） | 0.11~0.32（0） | 0.02~0.19 |

※ Release n=1 的那 113 ms 是**进程内第一个动作**：整个 Release 依赖图的程序集装载 + 首次 JIT 全记在这一枪上。
用户实际点试运行时，界面、插件库、流程都已加载过，对应的是第二行 `n=20` 那一格（22 ms）或"编译已热"那三格（8~9 ms）。

**结论**：n=1 与 n=20 在全冷档几乎相同（22.4 vs 22.6 ms），说明这笔钱与流程大小无关，是**首次执行链路的固定成本**。

## 4. 相位归因：这 16~18 ms 里谁占的

命令：`trialprobe.exe phases <步数>`（同一进程连跑两遍，第一遍含首次 JIT，第二遍是稳态）

| 相位 | n=1 第一遍 | n=20 第一遍 | 第二遍（n=20） |
| --- | --- | --- | --- |
| `compiler.Compile`（全流程） | 12.38 ms | 15.19 ms | 0.22 ms |
| `FlowSession.AddBlueprintsDeep` | 0.23 | 0.21 | 0.00 |
| `new ExecutionContext` | 0.70 | 0.33 | 0.00 |
| 端口桥接（`BindContext` + `GetActualValue` + 灌值） | 0.68 | 0.38 | 0.01 |
| `configPlugin.Execute` | **2.54** | **2.35** | **0.017** |
| 合计 | 16.53 ms | 18.46 ms | 0.26 ms |

读法：

- **编译占七成以上**，且是**首次 JIT** 的那一笔（稳态同一条编译只要 0.22 ms）。这就是"第二次点变 0 ms"的来源。
- `Execute` 的 2.35 ms 同样是**首次 JIT**（稳态 17 µs），不是算法。
- 桥接/会话/上下文在冷态各占零点几毫秒，稳态全部归零。**没有任何一项与"变量赋值"的业务逻辑有关。**

## 5. 真实方案上的稳态数据（Debug，50 次试运行取中位数）

同一份 `综合测试台.vms`，每条流程取其中一个「变量赋值」步骤做目标：

| 流程 | 顶层/含嵌套步数 | 编译中位数 | 试运行中位数 | p95 |
| --- | --- | --- | --- | --- |
| Test_Vision | 68 / 78 | 2800~2952 µs | **2.27 ms** | 4.98 ms |
| Test_Logic | 39 / 68 | 1436 µs | 1.43~1.46 ms | 2.58 ms |
| Test_FlowEdge | 25 / 45 | 1014 µs | 0.99 ms | 2.26 ms |
| Test_Comm | 31 / 45 | 908~1007 µs | 0.66~0.71 ms | 1.26~1.82 ms |
| Test_MotionEdge | 19 / 31 | 853 µs | 0.66~0.67 ms | 1.49 ms |
| Test_Motion | 28 / 37 | 532~552 µs | 0.54 ms | 1.19 ms |
| Test_DataEdge | 12 / 18 | 522 µs | 0.52~0.55 ms | 1.30 ms |
| Test_Data | 17 / 23 | 440 µs | 0.43 ms | 0.79 ms |
| Test_VisionEdge | 14 / 20 | 511 µs | 0.55~0.62 ms | 1.48 ms |
| Test_CommEdge | 12 / 18 | 328 µs | 0.33 ms | 0.40 ms |
| Home | 11 / 11 | 98 µs | 0.10 ms | 0.15 ms |
| Test_Report | 7 / 7 | 100 µs | 0.10 ms | 0.20 ms |
| End | 6 / 6 | 91 µs | 0.06 ms | 0.10 ms |
| Main | 2 / 2 | 13 µs | 0.02 ms | 0.02 ms |

两条可下的结论：

1. **试运行中位数 ≈ 编译中位数**（Test_Vision 2.27 vs 2.80；Test_Logic 1.43 vs 1.44）。
   也就是说"点一次试运行"≈"把整个流程重新编译一遍"，业务本身可以忽略。
2. **每步 20~38 µs**（真实插件流程比纯合成的 10 µs/步贵一倍多，因为 `Activator.CreateInstance` 要构造真的插件）。
   按这个斜率外推：**约 300 步的流程，稳态试运行就是 6~11 ms** —— 这才是"每次都是 10 ms"的唯一可能来源。

## 6. 测量边界

| 边界 | 说明 |
| --- | --- |
| **整数截断** | 界面只有整毫秒；0.2 µs 的赋值永远显示 0，本文所有"显示"列都是截断后的值 |
| **无 UI 订阅者** | 探针里的 `WorkspaceContext` 没有挂画布/流程栏 VM。真机上 `MarkStepState` 的 `PropertyChanged` 会多花一点（单步，量级 µs），不影响结论方向 |
| **真实设备 provider 未注入** | 探针用 `Null*` 兜底；真机若上游链里有相机/运动/通讯步骤，`ExecuteUpstreams` 会真等设备（那是另一类"慢"，本表不含） |
| **不存在编译缓存** | 以上数字全部是"每次重编译"的口径。若将来加了缓存，本表整列作废 |
| **Release 的 113 ms** | 是"进程内第一个动作"的极值，不代表用户能看到的值；用 `n=20` 那格做对比 |
| **单机** | 16 核，测量期间有背景负载；跨机对比必须重跑 |

## 8. 怎么判断你看到的那 10 ms 是哪一种

1. **连点两次**：第二次显示 0 ms → 是冷启动（第 3 节），与你的流程无关，重开一次界面就会重现一次。
2. **两次都 10 ms 左右** → 走第 5 节的斜率：要么流程总步数在 300 上下，要么目标步骤的上游链里有真在干活的步骤
   （`ExecuteUpstreams` 会把它们真跑一遍）。此时把目标步骤的上游连线断开再试一次，数字应立刻掉到 1 ms 级。
3. **数值每次抖动很大（0/3/10/20 混着出现）** → 是 GC/调度尾延迟，看 p95 而不是单次。
