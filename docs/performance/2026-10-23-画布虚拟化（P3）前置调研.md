# 画布虚拟化（P3）前置调研（2026-10-23）

> 触发：用户希望"几千点也不卡"，并要求保留虚拟化方向。
> 本文只做**调研与阻塞项清单**，不写代码。结论会直接决定 P3 是"复制 Nodify 模板"还是"自写编辑器"。
> 依据：`Nodify.dll` 7.3.0 反编译（`VisionMaster\bin\Debug\net9.0-windows\Nodify.dll`）+ 本仓库源码 + 2026-10-23 实测。

---

## 1. 一句话结论

**Nodify 7.3 不支持"只换一个面板"就完成虚拟化。** 要么复制并改写 `NodifyEditor` 的控件模板（版本锁定），
要么自写编辑器控件（工作量大 3~5 倍）。在第 3 节的三条守门断言补齐之前动手，会出现"gate 全绿、真机框选崩溃"。

---

## 2. 硬事实（反编译 + 源码）

### 2.1 Nodify 里没有虚拟化面板

| 事实 | 证据 |
| --- | --- |
| `Nodify.dll` 里**不存在**任何 `VirtualizingPanel` 派生类 | `ilspycmd -l c` 全量类型清单；DLL 字符串搜 `VirtualizingPanel` 0 命中 |
| 默认条目宿主是 `NodifyCanvas : Panel` | 类型基类；`MeasureOverride` / `ArrangeOverride` 遍历 `InternalChildren` **全部子元素** |
| `NodifyCanvas.ArrangeOverride` 用 `Location + RenderSize` 求并集得到 `Extent` | 同上；`ItemsExtent` 因此随**全部**已实现容器增长 |
| `NodifyEditor` **没有重写 `ItemsPanel`** | 反编译中 `ItemsPanel` 出现 0 次 |
| `OnApplyTemplate` 强制取模板里的 `PART_ItemsHost`（`Panel` 类型，`IsItemsHost=True`）+ `PART_ConnectionsHost` | 反编译 `OnApplyTemplate`；缺任一即抛 `InvalidOperationException` |
| 小地图也是全量 | `MinimapPanel : Panel`（internal sealed），`Measure/ArrangeOverride` 遍历全部 `MinimapItem` |

**推论**：`ItemsPanel` 设成虚拟化面板不会被使用——WPF 的 `ItemsPresenter` 走模板里那个 `IsItemsHost`。
必须改模板或换编辑器。

### 2.2 Nodify 自带的"大图优化"不是虚拟化

反编译得到的三个字段：
```
EnableRenderingContainersOptimizations = true
OptimizeRenderingMinimumContainers    = 700
OptimizeRenderingZoomOutPercent       = 0.3
```
`ApplyRenderingOptimizations()`：当 `Items.Count >= 700` 且缩小到阈值以下时，给 `ItemsHost.CacheMode`
套一个 `BitmapCache`。这是**位图缓存**，省的是重绘，不省容器生成——首次切换那一刀照付。
注意它按 `Items.Count` 判，本仓 600 节点 + 泳道/容器很可能已过 700，做性能对比时必须考虑它已生效。

### 2.3 现有代码对 Nodify 的依赖面（换面板/换编辑器各自谁接管）

完整表在 `VisionMaster\Views\FlowCanvasView.xaml`（`1444-1548`）。要点：

| 依赖 | 现状 | 只换模板 | 换编辑器 |
| --- | --- | --- | --- |
| `Connections` / `ConnectionTemplate` | `xaml:1448-1449` | 不动（在 `PART_ConnectionsHost`） | 自行实现 |
| `PendingConnection` + 模板内 `AncestorType=nodify:NodifyEditor` | `xaml:1456, 1537, 1542` | 不动 | 命令绑定静默失效，必须改绑定 |
| `ItemsDragStarted/CompletedCommand` 实参形态 | `xaml:1453-1454`；VM 侧 `FlowCanvasViewModel.cs:2654/2697` 依赖 `Execute(editor.DataContext)` | 不动 | 必须复刻，否则**真机拖动不改序、不出浮层**而断言仍绿 |
| `FitToScreen` 依赖 `ItemsExtent` | `FlowCanvasView.xaml.cs:129, 172` | **面板必须提供全量 extent**（由数据算，不按已实现容器算） | 同上 |
| `BringIntoView(container.Bounds)` / 回退 `node.Location` | `xaml.cs:136-146` | 已容忍容器为 null（`FindContainerFor` 返回 null 时走回退） | 同上 |
| `ViewportZoom/Location/Size` + `ViewportTransform` | `xaml.cs:274-282`（`ToGraphPosition`）、`DragGuidesAdorner` | 不动 | **换原点会让粘贴落点与参考线全偏** |
| `Minimap` 的 `ViewportLocation/Size` TwoWay | `xaml:1604-1605` | 不动 | 必须保留同名 DP |
| `Panel.ZIndex`（`ItemContainerStyle` 绑定 `ZOrder`） | `xaml:1502`；`CanvasNodeViewModel.ZOrder` 深度×3+身份 | 面板必须是 `Panel` 才吃 `ZIndex` | 自画叠放 |
| `Connector.Anchor` | 本仓**不依赖**：连线端点由 VM 直接算（`CanvasLinkViewModel.SourceAnchor/TargetAnchor`，`xaml:119` 注释） | 不动 | 只有建线/命中依赖 |

**关键有利条件**：画线几何已经收敛到 VM（`UpdateLinkAnchors`，`FlowCanvasViewModel.cs:1630`）。
虚拟化不需要碰连线几何，只需要保证"可见节点的 `Location`/`LaneWidth` 正确"。

### 2.4 `NodifyEditor` 对"容器必须全部存在"的硬假设（P3 最大风险）

反编译发现的 6 处直接解引用，虚拟化后 `ContainerFromIndex` 返回 null 会 NRE：

| 成员 | 行为 |
| --- | --- |
| `ItemContainers` | `for (Items) ContainerFromIndex(i)`，虚拟化后大量 null |
| `SelectedContainers` / `BeginDragging` / `AlignSelection` | 依赖 `ItemContainers` |
| `BeginSelecting` → `SelectionHelper.Start(ItemContainers, …)` → `.Where(x => x.IsSelectable)` | **框选直接 NRE** |
| `SelectArea` / `InvertSelection` / `UnselectArea` | `((ItemContainer)ContainerFromIndex(i)).IsSelectableInArea` **直接强转** |
| `ApplyPreviewingSelection` | 同样直接解引用（框选结束 NRE） |
| `FindNextFocusTarget` / `TryFindContainerToFocus` | 键盘导航，空集合时 `.First()` 可能抛 |
| `DraggingOptimized.Update/End` | `(TranslateTransform)itemContainer.RenderTransform` 强转 + 写 `Location`；拖动中被回收 → 视觉丢失/提交错位 |
| `NodifyCanvas.ArrangeOverride` | 每个直接子元素强转 `INodifyCanvasItem` → 往 items 宿主里塞非 item 元素会 `InvalidCastException` |
| `GetContainerForItemOverride` | 创建 `ItemContainer` 并挂 `TranslateTransform`，自定义编辑器必须复刻 |

## 4. 必须新增的三条守门断言（现在没有）

P3 落地前先补，否则"gate 全绿、真机框选崩"：

1. **真 editor 框选不抛且选中集正确**：白底拖框覆盖 3 个节点 → 选中 3 个、无异常。
2. **多选含屏外节点拖动不抛且顺序正确**：选中 1 屏内 + 1 屏外 → 拖动 → `ItemsDragCompleted` 提交顺序正确。
3. **首帧 `FitToScreen` 后 `ItemsExtent` 覆盖全量节点**：extent 宽高 ≥ 数据算出的外接框（防"缩在左上角"）。

## 5. 本轮（P1）实测给 P3 的证据

见 `docs\performance\2026-10-23-流程切换卡顿基线.md` 的「P1 复测」一节。要点：

- 3000 节点（10 条流程，每条约 353 步）：`heavy_layout ≈ 1.3~1.4 s`，其中 GC 暂停 ≈ 0.9 s。
- `diag` 归因：摘掉画布 DataContext 后 `layout` 掉到 **190~320 ms**；再摘流程栏掉到 **0**。
- 即"容器生成 + 模板展开"这一段本身约 **200~300 ms**（与 3000 节点无关的部分被 GC 主导）。

**这解释了一件反直觉的事**：P1 的减分配在 3000 节点上收益有限，因为**大头是 GC 停顿**，
而 GC 停顿来自"一次性造出几千个对象"——只有把"造对象"这件事本身变成 O(可见) 才能根治。
这不是优化，是 P3 才能解决的**结构问题**。

## 6. P3 两条路线（待用户拍板）

| | A. 复制并改写 `NodifyEditor` 模板 | B. 自写编辑器控件 |
| --- | --- | --- |
| 做法 | 复制 `themes/styles/nodifyeditor.baml` 对应的 XAML 到本仓，把 `PART_ItemsHost` 换成自研 `VirtualizingNodifyCanvas` | 新写一个 `FlowCanvasEditor`，自管视口/命中/框选/拖拽，Nodify 只用于 `Connector`/`StepConnection` 视觉 |
| 保留 | 拖拽策略、框选、键盘导航、`PendingConnection` 全部仍是 Nodify 的 | 只有视觉资产复用 |
| 要解决的 | 2.4 那 6 处 null 假设（需为虚拟化后的 null 打补丁——**改不了 Nodify 私有代码**，只能在自研面板里保证"编辑器认为在视口内的项都已实现"） | 上述全部自己实现 |
| 版本风险 | Nodify 升级要重新对模板 | 只对 `Connector`/`StepConnection` 的公开 API |
| 工作量（粗估） | 1~2 周 | 3~5 周 |
| 主要风险 | 编辑器内部行为（`SelectionHelper`/`DraggingOptimized`）无法改动，只能"喂饱"它——需要"虚拟化窗口 = 编辑器可见区域 + 缓冲"，等于**伪虚拟化**（省的是屏外远处的项，视口附近的仍然全实现） | 交互全面重写，回归面大 |

> **我的判断**：A 更现实，但它是"伪虚拟化"——真实收益来自"视口外不实现"，
> 3000 节点全展开时视口内可能仍有几百个，收益需要实测确认，不能先承诺。
> 建议 P3 立项时先做一个**只读探针**：临时把 `Nodes` 裁到"视口内 + 缓冲"，
> 用 `--switch-perf` 量一次，看 `heavy_layout` 掉多少。**这是 1 天的活，能决定要不要投 1~2 周。**
