> 状态：**已量化，未优化**。本文只回答"点一下流程到界面落定，UI 线程被谁占住、占多少"，
> 不包含任何产品代码改动。下一步的优化方案单独出。
>

## 1. 结论（先看这五条）

1. **`Workspace.SwitchFlow` 本身是 0 ms**。没有任何订阅者时，切流程的同步调用耗时 0.0 ms
   （`floor`/`diag C` 实测）。钱全部花在**订阅者**身上。
2. **单次切换在 UI 线程上分配 2.5~4.5 MB**（45 步流程 3.0 MB，78 步流程 4.5 MB），
   随之而来的 GC 暂停占了 `layout` 段的 **20~45%**（大流程 105~122 ms）。
3. **`layout` 段的绝对量级与"画布是否可见"几乎无关**：`canvas`（画布可见）与 `none`
   （两栏都收起）的 `layout` 中位数差在 ±5% 内（245.7 vs 235.3 ms）。**收起面板不等于不付钱。**
4. **把画布视图的 DataContext 摘掉，成本掉到 1/4~1/6**；把两个视图的 DataContext 都摘掉，掉到 0。
   说明这笔钱由 "工作区通知 → 两个 VM 各自重建" 这条链驱动，而**不是**渲染或绘制。
5. 因此"改渲染 / 改虚拟化"打不到点上；第一刀应该切在**每次切换的重建量与分配量**上
   （`FlowCanvasViewModel.Render()` 每次 `Nodes.Clear()` + 重建全部节点 VM + 全部连线 VM）。

## 2. 测量方法

### 2.1 三段口径（互不重叠，相加 ≈ 用户感到的那一下）

| 段 | 起点 | 终点 | 装的是什么 |
| --- | --- | --- | --- |
| `vm` | 调用 `Workspace.SwitchFlow(target)` | 同步返回 | `CurrentFlow` 通知 → 画布 `RebuildCore` 的 VM 侧 + 流程栏绑定通知 |
| `layout` | 紧接着 | `host.UpdateLayout()` 返回 | ItemContainer 生成、模板展开、连线出图、一次渲染前测量 |
| `deferred` | 紧接着 | 延迟队列排空（≤8 帧） | 画布 `FitToScreen`（排在 Background）、流程栏选中同步、200ms 计时器 |

`gc` 列是 `GC.GetTotalPauseDuration()` 在这一轮里的增量——**它已包含在 `layout`/`vm` 里**，
不是额外时间；列出来是为了回答"这 250 ms 里有多少是 GC 停顿"。

### 2.2 相位（变体对照，每相位一个干净进程）

| 相位 | 含义 |
| --- | --- |
| `canvas` | 只显示画布（流程栏 Collapsed），顺序链开、数据线关 |
| `tree` | 只显示流程栏 |
| `none` | 两栏都 Collapsed —— **对照组，证明"收起"并不省时间** |
| `floor` | **不切流程**，只 `UpdateLayout` + 排空 —— 归零地板 |
| `noorder` / `minimap` / `collapse` | 只画布，分别关顺序链 / 开小地图 / 全部容器折叠 |
| `diag` | 归因实验：逐个摘掉 DataContext，看成本掉在哪（见 §4） |

每个相位必须在**独立进程**里跑。同一进程连跑五个相位会累积污染：2026-10-23 第一版实测
`canvas` → `tree` 的数字从 238 ms 涨到 1601 ms，而中间只有开关差异。

### 2.3 采样

- 每条流程热切换 **7 轮**，取中位数；同一相位跑 **3 次独立进程**，取三次中位数的中位数。
- 冷切换（该流程首次显示、布局库空、走 `AutoLayout`）只在 `canvas` 相位量，且只量 1 次。
- 每轮测量前：`WaitRender()`（等一帧渲染）+ `Drain()`（排空延迟队列），
  避免上一轮的积压算进本轮。不做这一步时同一相位两次跑能差 5 倍。

## 4. 归因实验（`diag` 相位，单进程单次，方向性证据）

把订阅者逐个摘掉，看 `layout` 掉到哪。靶是大流程（≥30 步），A/B/C 各 1 个样本：

| 组 | 做法 | Test_Comm(45) layout | Test_Vision(78) layout | Test_Logic(68) layout | FlowEdge(45) layout |
| --- | --- | --- | --- | --- | --- |
| A | 两栏可见但收起（= `none`） | 197.1 | 441.6 | 391.6 | 263.1 |
| B | 再摘**画布**的 DataContext（画布 VM 随之 `Deactivate`） | **36.0** | **77.1** | **43.8** | **42.7** |
| C | 再摘**流程栏**的 DataContext | **0.0** | **0.0** | **0.0** | **0.0** |

分配量（`GC.GetAllocatedBytesForCurrentThread`，一次切换、UI 线程）：

| 流程 | 步数 | 分配 | 节点数 | 连线数 |
| --- | --- | --- | --- | --- |
| Test_Comm | 45 | **3.0 MB** | 53 | 36 |
| Test_Logic | 68 | **4.0 MB** | 87 | 50 |
| Test_Vision | 78 | **4.5 MB** | 84 | 71 |
| Test_MotionEdge | 31 | 2.5 MB | 43 | 18 |
| Test_FlowEdge | 45 | 3.0 MB | 60 | 29 |

三条可下的结论：

1. `SwitchFlow` 在无订阅者时 **0.0 ms** —— 工作区本身不是成本来源。
2. 画布 VM 的订阅是大头（B 相对 A 掉了 75~90%）。
3. 剩下的 36~78 ms 在**流程栏**（B 里画布已断，仍有开销；C 摘掉流程栏后归零）——
   即使流程栏是 `Collapsed` 也照付。

## 5. 明确的测量边界（不要拿这些数字当"端到端卡顿"）

| 边界 | 说明 |
| --- | --- |
| **不含渲染线程** | `CompositionTarget.Rendering` 在 UI 线程、于渲染提交**之前**触发；托管侧无法观测 GPU 提交与呈现。本文三个数全部是 **UI 线程忙时**，不是"到画面稳定"。 |
| **Debug 构建** | JIT 不做优化，绝对值偏高。Release 重跑会小一截，但**比例关系**（layout ≫ vm、收起不等于省时间）预计不变——未验证。 |
| **单机 + 有背景负载** | 测量期间 ZCode / Edge WebView / 微信在跑，CPU 负载约 8%。三次进程 `heavy_layout` 已给出波动区间（±5%），跨机对比前必须重跑。 |
| **`render_tier=2`** | 硬件渲染可用（非软件回退），但**未记录显卡型号**，换机重测可能不同档。 |
| **`diag` 是单样本** | A/B/C 各 1 次、单进程。用作**方向性归因**，不能当精确差值。 |
| **`floor` 是 0.0** | 它测的是"没有任何待办时 `UpdateLayout()` 的耗时"，不是"这台机器渲染一帧多贵"。 |
| **冷切换样本量 1** | 见 §3 注。 |

## 7. 已知的坑（写在这里省下一轮重踩）

| 坑 | 现象 | 正解 |
| --- | --- | --- |
| 同一进程连跑多相位 | 越靠后的相位数字越大（238 → 1601 ms） | 每相位一个进程 |
| 计时前不对齐渲染 | `deferred` 段跨进程差 5 倍 | `WaitRender()` + `Drain()` 后再起表 |
| 流程栏计时器 | 只画布的相位里 200ms 计时器仍在遍历全树，随机落进测量窗口 | 流程栏不在相位里时 `processVm.Deactivate()` |
| `CollapseAllCommand` | 只作用于当前挂接流程 | 逐流程 `Layout.SetCollapsed` |
| 无窗口离屏渲染 | 与真窗口差 2~3 倍，差的正是要量的那段 | 屏幕外真窗口 `Left/Top = -4000`（R53 同款理由） |
| 本机执行策略 `Restricted` | 直接 `-File` 报"禁止运行脚本" | 一律带 `-ExecutionPolicy Bypass` |
| 驱动的退出码 | `floor` 相位原本无 `heavy_*` 字段 → 判"无数据"红 | 驱动对 `floor` 单独解析；聚合按 `heavy_layout` 判有无数据 |
| 相位开关没生效 | 第一版五个相位的 `layout` 全在 330~530 ms，看起来"合理" | 每相位打 `phase_state`（`Visibility` + 可视树节点数）自检 |
| `diag` 拿小流程做靶 | Home(11 步) 得 41 ms，与大流程的 210 ms 差 5 倍，结论会全错 | 归因靶一律取 ≥30 步的流程 |
| exe 被上一轮占用 | `MSB3027 … 被 FlowCanvasChecks (pid) 锁定` | 等上一轮跑完再 build（探针会自己退出） |

## 8. 下一步（不在本文范围）

按 §1-5 的证据，优化只能落在**减少每次切换的重建与分配**上。候选方向（待评审，未实施）：

1. `FlowCanvasViewModel.Render()` 现状是 `Nodes.Clear()` + `_nodePool.Clear()` + 重建全部节点/连线 VM；
   换成按 `StepID` 增量同步（保留未变节点的 VM 与连线 VM）。
2. 流程栏 `TreeView` 在 `Collapsed` 时仍生成容器：断掉 `CurrentFlow.Steps` 的绑定或延迟到可见时再挂。
3. 两条一起做之前，先做 1 并复测本基线——目标是把 `heavy_layout` 从 ~210 ms 压到 GC 地板以下。

改完必须用本文同一套命令复测，并在新报告里与本表逐行对照。

### 9.2 归因（`diag`，3000 节点 / 10 流程，单样本）

| 组 | `layout` |
| --- | --- |
| A 两栏可见但收起 | ~1500 ms（GC 600~840 ms） |

### 9.3 结论修订

**§1 的第 5 条（"第一刀切在重建量与分配量上"）在小规模成立、在大规模不成立。**
3000 节点实测证明：`layout` 的 55~65% 是 **GC 暂停**，而 GC 暂停来自"一次性造出几千个对象"。
减分配能减少"白造的部分"（本批砍掉的隐藏数据线 VM），但造对象的**总量级**没变——
节点 VM、`ItemContainer`、模板元素仍按全量创建。**只有虚拟化（O(可见)）能治。**

§1 的其余四条在 3000 节点上再次被验证：
- `SwitchFlow` 无订阅者仍是 0 ms；
- "收起面板 ≠ 不付钱"（A 组比正常态几乎一样）；
- 摘 DataContext 才是真正的开关（B/C 组）。

## 10. 布局耗时 vs 节点数（2026-10-24 窗口实验）

用 `--switch-perf <vms> 1 window<N>` 把 `Nodes` 裁到前 N 个再布局（安静机器，`nop_floor=0.1`）：

| 节点数 | `heavy_layout` |
| ---: | ---: |
| 60 | 343 ms |
| 120 | 455 ms |
| 240 | 679 ms |
| 451 | 1044 ms |

**结论：次线性**，拟合 `layout ≈ 300 ms + 1.65 ms × N`。

两个推论：

1. **有约 300 ms 的固定成本**（与节点数无关：面板/滚动/视口/渲染线程首帧）。
   所以"分页限量"能砍掉增量，但砍不到 0——下限就是这个固定值。
2. **用户机器的单位成本约 43 ms/节点**（19407 ms ÷ 451，见 §9 真机日志），是探针的 26 倍。
   按同一形状折算，把一页压到 40~60 步大约能到 **2~3 s**，仍不是亚秒。

**根治只能靠"不建元素"**：自绘层实测 2268 节点快照 25 ms、一帧 11~32 ms
（`docs/code-changes/2026-10-24-画布自绘（C2-第0-1步）.md`）。

## 11. C2 决策测量：Nodify 画布 vs 自绘层（2026-10-24）

折叠只是跳过 measure，容器对 VM 的绑定仍在响应，实测占 ~1000 ms），自绘层接管。

测量命令：`--switch-perf <vms> 1 canvas|surface`（安静机器，`nop_floor=0.1`）。

### 11.1 353 步 × 13 流程（`压测-3000节点.vms`，451 可见节点）

| 段 | Nodify 画布 | 自绘层 | 倍数 |
| --- | ---: | ---: | ---: |
| `heavy_vm` | 47.8 ms | 6.2 ms | 7.7× |
| `heavy_layout` | 1035.5 ms | 201.9 ms | 5.1× |
| `heavy_deferred` | 115.4 ms | 10.6 ms | 10.9× |
| **`heavy_total`** | **1198.8 ms** | **218.7 ms** | **5.5×** |

### 11.2 单条 3542 步流程（2268 可见节点，`压测-3000节点-单流程.vms`）

| 段 | Nodify 画布 | 自绘层 | 倍数 |
| --- | ---: | ---: | ---: |
| `heavy_vm` | 413.3 ms | 85.5 ms | 4.8× |
| `heavy_layout` | **25 774.7 ms** | **2 774.6 ms** | **9.3×** |
| `heavy_deferred` | 804.7 ms | 140.4 ms | 5.7× |
| **`heavy_total`** | **26 992.7 ms** | **3 000.4 ms** | **9.0×** |

### 11.3 结论与未解项

- **替换方向成立**：规模越大收益越大（9× vs 5.5×），因为 Nodify 的成本随节点数线性增长，自绘是 O(可见)。
- **但 2268 节点仍有 2.77 s 的 `layout` 未归因**：自绘层只有一个 `FrameworkElement`，
  `Measure/Arrange` 都是 O(1)，这 2.77 s 不该存在。**替换前必须先定位它**，
  否则真机上"19 s → 3.5 s"里有一大块是未知开销。
- 用户机器单位成本约为探针的 26×（见 §10），按同比例折算：353 步流程 **19.4 s → 约 3.5 s**，
  仍不是亚秒——**光替换渲染层不够，还要减少每次切换重建的东西**。

### 12.3 900 ms 花在哪（关键结论）

同条件 `[画布] 分段` 显示 VM 重建本身就要 **527~750 ms**（装填 412~631 ms 是大头）。
自绘层 451 节点一帧渲染按 §11.1 的实测约 **150~300 ms**。也就是说：

> **换掉画布只能把 4 s 打到 0.9 s；再往下必须动 `FlowCanvasViewModel.RebuildCore` 和流程树，不是渲染层的事。**

这条把"下一步该优化谁"钉死了：渲染层继续投入的边际收益已经很小。

### 12.4 踩到的坑：勾了自绘一片空白（已修）

第一版适配用 `ComputeFitViewport(size, minZoom: 0.001, maxZoom: 1.0)`。
压测流程是**单列长链**，实测内容 `bounds=40,40,800,29406`，视口只有 `614×349`：

- 按比例适配算出 `zoom = 301/29406 ≈ 0.0102`；
- 451 个 156×58 的节点被压成 **1.6×0.6 px** 的像素点，`_simpleMode` 又只画纯色块；
- 肉眼看就是"一片空白"，但 `SetModel`/`OnRender` 一切正常（日志 `实画=451`）。

**修法**（`FlowCanvasView.SyncSurface`）：

1. 适配缩放下限提到 **0.25**（`FitZoomFloor`）；撞到下限时不再居中，改成**左上角对齐**（`margin=24`），
   因为长链流程居中等于把视口停在链条正中间，看不到开头。
2. 新增 `_surfaceUserAdjusted`：用户滚过轮/拖过画布之后，切流程不再抢回视口；没动过则每次切流程重新适配。

判据留了三行诊断日志（`[自绘] SetModel …` / `[自绘] Sync …` / `[自绘] OnRender …`），
一次性输出（每次 `SetModel` 只落一行），**下一轮定位同类问题直接看这三行**。
