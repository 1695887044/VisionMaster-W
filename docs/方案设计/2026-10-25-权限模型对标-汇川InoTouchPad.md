# 权限模型对标：汇川 InoTouchPad 用户管理

> 日期：2026-10-25
> 输入：`D:\INOVANCE\InoTouchPad\InoTouchPad软件帮助.chm`（V1R7，2026-04）
> 目的：回答「是否要给每个操作一个权重、用户一个数值范围」；对照当前方案级用户管理规格，给出取舍建议。
> 结论：**汇川不是单一权重/范围。它用「用户组 + 32 位权限位掩码」做操作授权，另用「用户等级 1~20」做分级管理。** 我们的 `ScadaRole` 只相当于它的“用户等级”的 3 档粗粒度；`ScadaPermission` 12 个命名权限才相当于它的“权限位”，但目前被映射成角色，不是按组存储的权限集合。

---

## 一、汇川怎么做（原文要点）

### 1.1 权限分配给“用户组”，不分配给用户

§15.1 简介：

> 在用户管理中，权限不会直接分配给用户，而是分配给用户组。例如，用户 A 分配给“调试工程师”用户组并被授予相应权限。不需要为每个用户分别分配权限，只需将权限分配给用户组。

§15.2.1 组管理：

> 用户组中系统默认有“管理员”组和“操作员”组。“管理员”默认拥有所有权限，“操作员”权限可设定。
> 组权限中勾选了的权限表示对应的组就拥有了此种权限。例如“调试工程师_A组”勾选了“操作”、“管理”、“监视”，则该组拥有这三项权限。

→ 用户组是权限的载体；新增一类人只需加组，不用逐用户配。

### 1.2 组权限是 32 位整数位掩码

§17.3.5 用户管理 · 系统函数 `GetAuthorization`：

> 把当前登录的用户所属组的权限写入到指定的变量。权限值根据用户勾选的组权限计算得出，**组权限通过 32 位整数表示，每一位代表 1 个权限**。变量只能为 Int32 类型。

§5.1.4 系统变量：

| 变量 | 含义 | 类型 |
|---|---|---|
| `$CurrentUserName` | 当前用户名 | String |
| `$CurrentUserGroupId` | 当前用户所属组 Id | Int32 |
| `$CurrentUserAuthority` | 当前用户权限值（组权限 32 位掩码） | Int32 |

→ 操作授权是**集合成员判断**：`(userMask & requiredBit) != 0`，不是数值大小比较。

### 1.3 对象级权限 + 未授权弹登录

§15.3.3 应用示例：

> 选中“参数设置”按钮，属性 → 安全 → 运行系统安全 → 权限，选择“管理”权限；数字 IO 域选择“操作”权限。
> 未登录或未经授权而单击组态权限的控件时，会弹出“登录”对话框；以有权限的用户登录后，后续操作不再弹。
> 李四只有“操作”权限，可改温度值；单击“参数设置”按钮时会再次弹出登录对话框。

§15.3.1：

> 拥有“管理”权限的用户可以在“用户管理”视图中管理所有用户，其它受限用户则只能管理自己。

→ 权限挂在**对象**上（按钮/输入框/视图），不是只挂菜单；未授权是“弹登录”而不是只灰显。

### 1.4 用户等级是独立维度：1~20，越小权限越大

§15.2.2 用户管理：

> 用户等级的数值越小，权限越大。User_1 等级 19、User_2 等级 20，则 User_1 登录后能在用户视图中看见 User_2，反之看不见。
> 密码修改配置为否时，只有自己和管理员能改密码；为是时，和自己相同或高于自己级别的用户都可以改。

§14.2.1.2 Web/精益数字化：

> 登录用户级别和参数修改用户级别范围均为整数 0~20，**数值越小，权限越大**；用户等级与阈值比较决定能否登录/改参数。

→ 用户等级管的是“层级/可见性/能管谁”，不是“每个操作能不能点”。操作授权仍由组权限位决定。

### 1.5 管理保护与系统函数

§17.3.5：

| 函数 | 规则 |
|---|---|
| `AddUser` | **仅当前登录用户组为管理员时生效**；无登录/非管理员组执行无效 |
| `RemoveUser` | 管理员组按用户名删除；**admin 用户不可删除** |
| `ChangePassword` | 修改指定用户密码 |
| `ShowLogonDialog` / `Logon` / `Logoff` | 登录/登出 |
| `RestoreDefaultPassword` | 超级密码恢复所有用户默认密码（111111） |

→ 与我们的“最后一个管理员不可删 / 不能删自己”同族；汇川额外有“超级密码重置”。

## 二、和当前规格对照

| 维度 | 汇川 InoTouchPad | 我们当前规格 | 差异判断 |
|---|---|---|---|
| 权限载体 | 用户组 | 用户角色（Operator/Engineer/Administrator） | 我们的角色 = 3 个固定组 |
| 操作权限 | 32 位位掩码，每 bit 一个权限 | 12 个命名 `ScadaPermission`，映射到角色 | 我们有命名权限，但没有按组存集合 |
| 用户等级 | 1~20，越小权限越大；管可见性/改密 | 无独立等级；角色即等级 | 我们只有 3 档，且方向是“越大越强” |
| 对象权限 | 控件/视图的“权限”属性 + 权限控制可见性 | 四类入口统一 `ScadaPermissionGate`；运行态图元 `RequiredRole` | 我们偏全局入口，缺对象级细粒度 |
| 未授权 | 弹登录框，登录后可继续 | `CanExecute` 灰显 + handler 拒绝 + 回执 | 桌面端灰显更清晰；HMI 弹登录更顺手 |
| 管理范围 | 管理员管全部；受限用户管自己 | 管理员专属页；登录弹窗有改密入口 | 我们更严格，少了“我的账号”自助 |
| 账号归属 | 工程级 | **方案级** `<方案根>\Users\ScadaUsers.json` | 我们的方案隔离是更强项，不能丢 |
| 安全例外 | 权限可配置，可能把 Stop 锁掉 | Stop/JogStop 恒放行（SL16/AX9） | 我们的例外更安全，应保留 |
| 管理员保护 | admin 不可删 | 最后一个管理员/自删保护 | 目标一致 |
| 密码 | 复杂度、默认 111111、超级密码重置 | PBKDF2、默认 admin123、Web 拒绝默认密码 | 我们的密码学更强；不要抄默认密码 |

## 三、关键结论：你要的不是“权重”，是“权限集合 + 等级”

把“每个操作一个数值、用户一个范围”拆开看，其实是两个问题：

1. **这个操作需要什么权限？**
   - 汇川答案：一个**权限位**（如“操作”“管理”“监视”）。
   - 用户答案：所属组的**权限掩码**。
   - 判定：`(mask & bit) != 0`。
   - 这是**集合**，不是范围；所以“能操作但不能管理”“能监视但不能操作”可以同时成立。

2. **这个人能管谁、能看谁？**
   - 汇川答案：**用户等级 1~20**，越小权限越大；用于用户列表可见性、改密规则、Web 登录阈值。
   - 这是**序数**，不是操作权限。
   - 我们的 `ScadaRole` 1/2/3 就是这个序数的粗粒度版，但方向相反（我们越大越强）。

**单一数值范围会把这两层压成一层**：给用户一个 max，就同时决定了“能操作什么”和“能管谁”，无法表达“工程师但只读”“操作员但能看报表不能控制”这类组合。

## 四、三种落地方案

### 方案 A：保持三档角色（当前规格，推荐先做）

- 用户侧：Operator / Engineer / Administrator 三档下拉。
- 动作侧：保留 12 个命名 `ScadaPermission` + 穷举 `PermissionFor` + `default` 拒绝。
- 内部可给 `ScadaPermission` 挂一个 `Level` 做排序，但**不把数字暴露给用户**。
- 账号文件仍是 `Role` 1/2/3，G14 不变。
- 代价：无法表达“工程师但只读”“操作员但能看报表不能控制”。

**适用**：现场就是三档人，需求与当前规格一致。B0/B5 不用改。

### 方案 B：用户组 + 32 位权限掩码（汇川式）

- `ScadaPermission` 改 `[Flags]`，12 个命名位（可扩到 32）。
- 新增 `ScadaUserGroup`（方案级）：`Name`、`PermissionMask`、可选 `Level`。
- 用户记录存 `GroupId`（或保留 `Role` 映射内置组，新增 `Group` 兼容旧文件）。
- 内置组：Operator / Engineer / Administrator，掩码按当前 12 权限映射；可新增自定义组。
- `ScadaPermissionGate` 改位判断：`(mask & requiredBit) != 0`；未知位/未知组一律拒绝。
- UI：账号页签加“用户组”编辑（复选框），用户页签选组；管理员组不可删；最后管理员/自删保护。
- 账号文件：新增可选字段；G14 必须改（不是静默加字段）。
- Stop/JogStop 仍恒放行（不放进可配置位，或强制所有组带 `SafetyStop` 位）。
- 代价：B1/B2 契约、账号文件、B5 账号页签、审计都要改；属于规格变更。

**适用**：确实需要“操作但不管理”“监视但不操作”“工程师但只读”等组合。

### 方案 C：只加用户等级（1~20）

- 保留三档权限不变，只给用户加一个 1~20 的等级，用于“能管谁/能看谁”。
- 操作授权仍按角色。
- 代价：多一个维度，但不解决操作细粒度；方向还要统一（建议保持“越大越强”，不要抄汇川的“越小越大”）。
- **不推荐单独做**：它解决的是层级，不是权限集合。

## 六、建议

1. **先确认是否真的需要“操作/管理/监视”分离。**
   - 如果现场只需要“操作员/工程师/管理员”三档，选 A，当前规格不动。
   - 如果需要“同一档里有人能操作、有人只能看”，选 B。
2. **不要用单一数值范围替代权限集合。** 汇川的 32 位掩码已经证明：操作授权是集合成员判断，不是大小比较。
3. **用户等级可以后加，但方向要统一。** 我们现有 `ScadaRole` 是“越大越强”；汇川是“越小越大”。如果加等级，建议沿用“越大越强”，并在 UI 写清“1=操作员、2=工程师、3=管理员”，避免现场误配。
4. **Stop/JogStop 恒放行必须保留。** 汇川的对象权限可以配置到 Stop 上；我们不应把安全动作交给可配置位。
5. **未授权交互可以分层**：运行态 SCADA 画面可考虑“弹登录”（HMI 习惯）；工程菜单/桌面管理页继续“灰显 + 回执”（当前规格）。不要一刀切改成弹窗。
6. **账号归属仍是方案级。** 汇川是工程级；我们的 `<方案根>\Users\ScadaUsers.json` 是方案隔离的关键，不能为了抄组模型退回工程级。
