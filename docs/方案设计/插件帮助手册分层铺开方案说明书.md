## 五、闸门改法（HM13 分档 + HM16 页数台账）

改 [HelpManualCheck.cs](file:///D:/C%23/VM/FlowCanvasChecks/HelpManualCheck.cs)，**四处**：

1. **HM13 从"统一 100 行"改成"按档位取 100/150/300"**。档位表用**插件类名为键**的静态字典，未登记条目**默认按 M 要求**（防"漏登记 = 零要求"）。沿用 HM13 现有的"已交才判"语义：开发页 0 页的条目仍跳过（欠账走 HM15 台账），所以这条改动对当前工作树**不会新增红灯**，并且是**渐进生效**——角色每交一册，那一册立刻受该档下限约束。
2. **新增 HM16 档位表覆盖闸门（判红）**：`Tiers` 字典与"带 `GroupName` 的插件类"必须**一一对应**——表里没有的条目（新增插件类没登记档位）红、表里有但源码已消失的条目（档位过期）红。未登记虽然在行数检查上仍按 **M** 兜底（`DefaultTier`，保证"漏登记只会更严不会零要求"），但兜底不是放行口，不钉这条档位表会和语料悄悄脱节、L 档新条目被按 M 放行。
3. **新增 HM17 骨架完整度台账（不判红）**：逐条目输出"用户页数 / 开发页数 / 开发行数"是否达档，日志里摊开"达标 n / 总数 m + 欠账清单"。铺开是分批的，一次性判红等于"全有或全线红"；**等 42 条全部交完，把这条翻成红线**。
4. 反向自检：故意把一个 L 档开发章节压到 200 行 → HM13 必须红；故意给新插件类不登记档位 → HM16 必须红（R38：判据要能被反证）。
5. **新增 HM6b「同一分册内 `NN-` 前缀不许重复」（判红）**——铺开现场两次撞上"旧页没退场、新页又写一遍"（`Plugin.Matching` 三个前缀撞号、`Plugin.CodeReader` 两个、`Plugin.ColorCheck` 两个、`Plugin.BlobDetect`/`Plugin.ZMotionCard`/`Plugin.Motion.Steps` 各有），HM6 只查 `^\d\d-` **格式**、看不出**重号**。后果是静默的：宿主按资源名 Ordinal 排页序，撞号那两页谁在前随机，界面照常打开、目录树照常有节点。判据按"该插件类真正拿到的那批页"（`PagesFor`）分组，所以多插件程序集各自的分册互不误伤。首跑命中 **15 处重号**，逐条由角色退旧页清掉。

## 六b、实测教训：派工粒度要按"角色的工具调用预算"切（2026-10-16 铺开时踩的）

首批按上表 7 组派出，结果 **5 组在 150 次工具调用上限处被截断**（`error_max_turns`），实测消耗：运动控制 196、数据上报与工具集 186、预处理颜色几何 183、检测区域 177、采集标定相机 162；只有"OCR/深度学习/脚本"组（69 次）跑完并交出完整三段式回报。截断的回报文本一律停在"开始读源码 / 开始写页"，看上去像没干活——**但查盘发现多数条目其实已经写完了**（`ImageAcquisition` 471 行、`Calibration` 675 行、`BeadInspect` 开发章节 529 行、`CSharpScript` 679/249 行都在盘上）。这与上一轮 `failed: Model response interrupted` 是同一条教训的第二次验证：**回报状态不等于产出状态，先查落盘的 md 与 csproj，再决定重派什么。**

真正没动的只有 6 处：`PreProcessing`、`ColorCheck`、`Camera.Hikvision`、`Camera.Network`、`ImageAssign`、`RunFlow`。于是改成**窄粒度重派**：单角色 ≤ 2 个条目，L 档条目一个角色只管 1 个（`PreProcessing` L 档单独一组），`Plugin.Motion.Steps` 七个条目拆成两半，`Plugin.Utility` 六个条目按档位切成两组。12 次角色调用把剩下的补完。

**三条要沿用的派工纪律**（下轮再铺开直接照抄）：

1. **单角色 ≤ 2 个条目**（L 档 1 个）。7 组 × 6 条目的分法是按"知识族"切的，不是按"预算"切的，撞上 150 次上限只是时间问题。
2. **开工预算闸门写进派工指令**：第 15~20 次工具调用内必须开始写盘；取事实只用**批量 grep**（一次 `grep -n` 打多个符号名），不许逐文件 Read 摸底；时间吃紧先交**开发页**（HM13 判红，用户页只有 HM8 的 70 行底线，先厚谁一目了然）。
3. **命名口径要在派工前定死**，否则角色各写各的。本轮出现的分叉：`MotionEnablePlugin` 用英文 slug（`02-ports-and-parameters.md`）、`ComparisonPlugin` 用中文名（`02-端口与参数.md`）。定稿：**页序只由 `NN-` 前缀决定，中文名不影响装载**；因此**旧页保留原名**（不为"好看不改名"，改名要重建工程、还可能撞别的 `NN-`），**新增页一律英文 slug**，与 CreateRoi 样板对齐。

**顺带查出的现场脏法**：`Plugin.BlobDetect` 被两个角色先后写过，新 5 张用户页 + `10-dev-*` 与旧 `01-overview.md`/`02-tuning.md` 并存——**两个 `01-`、两个 `02-`，页序撞车**（宿主按资源名 Ordinal 排，撞号就是随机序）。重派时明确"**先逐条比对旧页事实搬进新页 → 再删旧页 → 再补开发页**"，顺序反过来会丢事实。这不是闸门能拦的（HM6 只查 `NN-` 前缀格式，不查同目录内前缀重复），下轮铺开时该把它列进验收第 6 步的自检项。
