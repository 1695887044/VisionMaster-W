# 第三轮控件联合评审计划：数据表格 / 轴控台 / 报警条

日期：2026-10-25　状态：**评审计划（待组织会审）**；本轮不改任何代码

## 1. 为什么是这三个（选择理由）

选型标准三条：① 现场使用频率；② 出错后果的严重度；③ 已知技术债密度。

| 控件 | TypeKey | 选择理由 |
| --- | --- | --- |
| **数据表格** | `Hmi.DataGrid` | 报警历史、日志、追溯清单全靠它；**已知技术债最密**：R19（GridView 必须挂 `GridListViewStyle`）、R21（行内边距 4）、R159（`RowHeight=Auto` 构造期抛异常）、列宽不支持星号、5000 行分页与实时插入（`NewestFirst`）互相拉扯 |
| **轴控台 / 轴面板** | `Hmi.AxisConsole` / `Hmi.AxisPanel` | **唯一会动设备的图元**：R108（权限在按下前判、点动按住才动、回零长按 0.5s、不许声明名为 `IsEnabled` 的 DP）、R99（下发 ≠ 到位）、R138（点位表每拍重读 + 指纹短路）、AX7/AX10 十余条断言。上一次并发会话的运动安全断言红，也是这条链 |
| **报警条** | `Hmi.AlarmBanner` | 操作员**第一眼看到的报警面**：严重度编码、紧急级不可静音、滚动与确认入口、与"报警汇总表"的分工（条=知道有事，表=处理掉）。颜色/闪烁/声音三处耦合，最容易出现"看得见但看不懂" |

> 没选 `Hmi.Report` / `Hmi.Symbol` / `Hmi.PipeRun`：它们刚出、已有独立设计基线与断言，优先级低于上面三个"每天都在用"的控件。

## 2. 每个控件要重点评审什么

### 2.1 数据表格 `Hmi.DataGrid`

**功能评审点（应用工程师主导）**

1. 数据来源与刷新：实时插入（`NewestFirst`）时正在看历史会不会被拽回顶部；切页/切画面后行是否残留。
2. 容量：5000 行分页 vs 无限滚动的取舍；单页最多多少行不影响交互（目标：翻页 < 200ms）。
3. 列配置：列宽（无星号列宽）、对齐、格式串、空值占位（空 vs `—` vs `0`）。
4. 交互：行选中是否参与"按选中项执行"；能否复制单元格；双击是否进详情。
5. 空态与异常态：无数据 / 未接数据源 / 变量解析不到，三者文案是否区分。
6. 权限：导出/清空是否需要权限（当前表格无导出，需确认是否补）。

**UI 评审点（前端设计师主导）**

1. 表头与行高：R19/R21 的 4px 内边距体系；表头是否吸顶；斑马纹对比度。
2. 信息密度：12~13px 字号下每屏行数；数字列右对齐 + 等宽字体（`Cascadia Mono`）是否统一。
3. 状态编码：选中 / 悬停 / 隔行 / 不可用行（如已确认报警）四态是否互不干扰。
4. 溢出：长文本截断 + ToolTip；列宽不足时的优先级（哪列先让位）。
5. 触控：行高 ≥ 36（触摸），表头点击排序的命中区。
6. 滚动条：内容宽度变化时是否抖动；横向滚动是否与固定列冲突。

### 2.2 轴控台 / 轴面板 `Hmi.AxisConsole` / `Hmi.AxisPanel`

**功能评审点（应用工程师 + 运动安全）**

1. 门禁：`CanOperate` 是否每拍重算；权限不足时按钮是**灰掉**还是"点了才拒绝"（R108 要求按下前判）。
2. 点动：按住才动、抬起/离开/丢捕获即停（要 `CaptureMouse`）；看门狗超时兜底是否在。
3. 回零：长按 0.5s 的判定与提示；误触概率。
4. 位置语义：当前位置 / 目标位置 / 偏差三者是否同屏；`下发 ≠ 到位` 是否在界面上有明确区分（例如"已下发"与"已到位"两个状态）。
5. 点位表：每拍重读 + 指纹短路（R138），编辑中不被重建；离线/未使能/未回零时点位能否编辑。
6. 报警态：报警时只允许"清报警"，其他动作是否真的被挡住。
7. 权限与审计：每次运动命令是否落审计（谁、哪根轴、什么命令、结果）。

**UI 评审点（前端设计师主导）**

1. 危险分级：停止/回零/点动/使能四类动作的视觉权重是否与危险度一致（停止永远可点且最显眼）。
2. 反馈：按住期间的状态（脉冲/高亮）、命令执行中（忙碌）、失败原因（ToolTip 或行内红字）。
3. 数字可读性：位置值用等宽字体、固定小数位；单位与数值分列（同 `IOField` 本轮改法）。
4. 禁用与不可用：未使能/未回零/超软限位三种"不能动"的原因是否各自可辨，而不是统一灰掉。
5. 触控：点动按钮命中区 ≥ 44px；相邻按钮间距避免误触。
6. 颜色：报警红、使能绿、运动中蓝——三者色盲可辨性（不只靠颜色，配文字/图标）。

### 2.3 报警条 `Hmi.AlarmBanner`

**功能评审点（应用工程师主导）**

1. 严重度过滤：条上显示哪些级别；紧急级是否置顶且不可静音。
2. 条数：`MaxRows` 与滚动行为；新报警插入是否打断正在阅读的那一条。
3. 确认入口：条上是否允许确认（当前分工：条=知道，表=处理）；点条是否跳转到报警汇总表/画面。
4. 空态：`EmptyText`（"系统正常"）与"未接报警源"是否区分。
5. 与声音/播报的关系：静音是否同时停播报（已实现），条上是否显示"已静音"。
6. 数据源：是否与报警汇总表共用同一份活动列表（不允许各存一份）。

**UI 评审点（前端设计师主导）**

1. 严重度编码：色条 + 圆点 + 文字（三重编码），色盲可辨。
2. 层级：报警名 / 条件 / 时间 的信息顺序；宽度不足时先截断哪一段。
3. 动效：新报警进入是否闪一下（≤200ms）；紧急级是否允许持续闪烁（防干扰）。
4. 密度：一行能放几条信息；多条时是堆叠还是轮播。
5. 对比度：深色底上红/黄字的对比度（≥ 4.5:1）。
6. 触控与无障碍：整条是否可点；键盘焦点可见。

## 3. 角色分工

| 角色 | 关注 | 必须回答的问题 |
| --- | --- | --- |
| **SCADA 组态应用工程师**（现场视角，2 人：工艺 1 + 电气/运动 1） | 操作顺序、报警语义、权限与审计、异常与恢复路径 | "现场戴手套、赶时间的时候，会不会点错/看不出来？" |
| **前端设计师**（交互 + 视觉，1~2 人） | 信息层级、状态机、密度、触控命中、对比度、令牌化 | "这一屏在同状态下，操作员 3 秒内能不能判断'现在能不能动、出了什么事'？" |
| **运动安全评审**（轴控必到） | 门禁、看门狗、失败兜底、下发与到位 | "任何一个按钮失效或误触，最坏后果是什么？" |
| **实现负责人**（本仓库维护者） | 改动边界、断言成本、回归面 | "这条改动的判据是什么？谁来钉住它？" |

**表决规则**：功能问题由应用工程师 + 运动安全定"必须改/可延后"；UI 问题由前端设计师定；
冲突（如"密度 vs 可读性"）由实现负责人给出成本后，按"现场安全 > 可读性 > 密度"排序裁决。

## 4. 评审流程（建议 5 步，一次会议 + 两轮书面）

1. **材料准备（会前 1 天）**：每个控件出一份"现状包"——① 模板 XAML 关键片段；② 属性表（key / 显示名 / 默认值）；
   ③ 现有断言清单（哪些行为已被钉住）；④ 真机或离屏截图（空态/正常/报警/禁用四态）。
2. **分角色独立书面评审（各 30 分钟，互不参考）**：每人按上面的"评审点"逐条写"问题 + 证据 + 建议"，
   避免会议上一人定调。
3. **合并会审（60~90 分钟）**：按控件逐个过；每条问题先对齐"是不是同一个问题"，再定级别（P1/P2/P3）。
4. **裁定与排期**：输出裁定表（问题 / 级别 / 改不改 / 谁改 / 判据），P1 进本轮，P2 排下一批，P3 只记录。
5. **落盘**：裁定表进 `docs/UI设计基线/<控件>-review/README.md`；实现的改动进 `docs/code-changes/`；
   每条 P1 必须配一条断言（否则"改好了"无法证明）。

## 5. 预期产出

- 3 份设计基线（`docs/UI设计基线/scada-datagrid-review/` 等），每份含：现状复刻、改版对照、裁定表；
- 1 份本轮实施清单（P1 项 + 断言编号）；
- 若涉及轴控：额外一份"安全影响说明"（每个改动的失效模式与兜底）。

## 6. 风险与前置

- **轴控台评审必须带着 `MotionCommandGate` 与 `MotionActionExecutor` 的现状一起看**，只看界面会漏掉门禁；
- 数据表格的 `RowHeight=Auto` 是**构造期抛异常**（R159），评审时不要把它当成"样式问题"；
- 三个控件都有既有断言（`ScadaChecks` 3056 条中相当一部分），任何"改外观"的结论都要先确认不会打红判据，
  否则要同时给出判据更新理由。
