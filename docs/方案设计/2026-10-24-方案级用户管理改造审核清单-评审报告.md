## 0. 一句话结论

**这份清单的方向、风险和边界判断都是对的，工程纪律引用几乎全部准确；不能直接批准的原因是三处"证据/口径错误会导致实现出来就是错的"，以及整套权限矩阵漏掉了整整两族真实存在的入口。**

清单在"该不该做、做成什么样、哪些是已知边界"上表现优秀：22 条现状证据我逐条回磁盘核对，**18 条完全成立，4 条轻微漂移（行号或路径），0 条内容错误**。密码学保不动、账号不进 `.vms`、审计不加列、切方案撤销全部 Web 会话、fail-closed 绑定失败——这些判断都有硬证据支撑，且理由写得比多数设计文档清楚。

问题集中在"实现时才暴露"的地方：**审计文件名的真实格式对不上**、**审计目录归属与方案目录结构自相矛盾**、**权限矩阵漏了 `FlowAction` 与轴面板两族入口**、**`Release` 构建与 `ScadaWebChecks` 基建的可行性没核**。这些不是设计分歧，是照抄就会坏的事实错误。

## 1. 阻断级问题（必须改，否则实现出来就是错的）

### B1 — 审计文件名格式错误，`ScadaAuditReader` 照此实现会读不到任何行

**清单写法**（§3.8）：`按 Audit\yyyyMMdd.csv 读取`

**磁盘事实**（`VisionMaster/Services/ScadaAuditWriter.cs:199`）：

```csharp
private const string FileNameFormat = "Audit-{0:yyyy-MM-dd}.csv";
```

真实文件名是 **`Audit-2026-10-24.csv`**（带 `Audit-` 前缀、日期段用**横线**分隔）。清单写的 `yyyyMMdd.csv` 三重不符：少了前缀、少了横线、少了 `.csv` 前的横线结构。

**后果**：F13 新建的 `ScadaAuditReader` 若按清单实现，`Directory.GetFiles` 模式匹配为空 → 审计页永远空白。而 UM5 的"六种状态各有可断言标志"会把"空"当成合法空态，**断言全绿、功能全废**——正是 AGENTS.md R38 说的"跳过型断言"最坏形态。

**改法**：§3.8 与 F13 改为"复用 `ScadaAuditWriter.FileNameFormat` 的同一常量（`Audit-{0:yyyy-MM-dd}.csv`），**由 writer 公开该格式**，reader 与清理逻辑共用一份，禁止 reader 自带一份字符串"。同时补一条断言：reader 读到的文件数 = writer 写过的日期数。`docs/归档/SCADA/SCADA商业级交付路线图.md:22` 已记着正确格式 `Audit\Audit-yyyy-MM-dd.csv`，说明这是清单笔误而非设计意图。

### B2 — 审计目录是程序目录，与 §3.2 的"方案目录结构"自相矛盾

**清单自相矛盾**：§3.2 定义方案根下有 `Image / Alarms / History / Logs / Users`（**没有 `Audit`**），§3.8 却说审计读 `Audit\yyyyMMdd.csv`；同时 §1.2 明确"方案级审计文件 → 不做，理由是按方案拆文件会碎片化证据"。

**磁盘事实**：

- `ScadaAuditWriter.DefaultDirectory => Path.Combine(AppContext.BaseDirectory, "Audit")`（`:290`）——**程序目录**，不是方案目录
- `App.xaml.cs:425-426` 注册时用的正是这个 `DefaultDirectory`
- 所以审计 CSV 的真实位置是 `<程序目录>\Audit\Audit-yyyy-MM-dd.csv`，**从来不在方案根下**

**后果**：F12 要"注入 `Func<string?>` 方案标签"——这个设计本身是对的（标签进说明列）。但清单把 `Audit\` 写在方案目录语境里（§3.2 的代码块与 §3.8 的路径写法并列），实现者极可能去 `<方案根>\Audit\` 找文件，或者在 readers 里把方案根当审计根 → 读空。SL14/SL20 都建立在"reader 能读到 writer 写的文件"这个前提上。

**改法**：§3.8 首句明确写"审计文件仍在**程序目录** `<程序目录>\Audit\`（机器级，`ScadaAuditWriter.DefaultDirectory`），本方案只给它加方案标签，**不搬迁、不按方案分目录**"，并在 §3.2 的目录表下加一行注："`Audit\` 不在此列表中，它属于程序目录"。F12/F13 的改法随之收窄为"注入标签 + 复用 writer 的目录与文件格式出口"。

### B3 — 权限矩阵漏掉 `FlowAction`（14 个动作）与轴面板整族入口

清单 §3.6 声称"每个菜单/命令/快捷键/命令面板都有唯一判据"，§3.6-E 也列了"命令面板/快捷键走同一 gate"。但实测：

**① `FlowAction` 全族无角色判据。** `VisionMaster/ViewModels/FlowListViewModel.cs:125-260` 的 `FlowCommandExecute` 有 14 个分支（`Create / Delete / Rename / EditComment / ToggleEnabled / Compile / Manager / RunOnce / RunContinuous / Stop / VariableEvents / BrowseList / Edit`），**一处 `CurrentRole`/`CanOperate` 判断都没有**（grep 该文件 `CurrentRole|CanOperate|Satisfies` = 0 命中）。这些是真能改方案内容的动作：建流程、删流程、改名、编译、单条流程运行。

清单 §3.6-C 把 `Compile` 定为 Engineer，但那是 `ExecutionAction.Compile`（`ShellViewModel:1194` → `DoCompileAll`）；**`FlowAction.Compile` 是另一个入口、另一条实现**（`FlowListViewModel:215` 自己调 `_compiler.Compile`），同样把流程推进运行态。不覆盖它，等于"整体编译要工程师、单条编译谁都能按"。

**② 轴面板按钮族。** `Scada.Controls/Elements/AxisPanelElement.cs` 的 `CanOperate`（`:440`）判的是 `AccessPolicy.CanOperate(Element?.RequiredRole)`——**图元上配的 `RequiredRole`**，默认 `null` = **不限制**。也就是说：`SystemAction.MotionBoard` 归 Engineer 只挡住了"打开板卡窗口"，而运行画面上轴面板里的点动/回零/使能按钮，在图元没配 `RequiredRole` 时**任何在场的人都能按**。AGENTS.md R108 要求的"权限在按下前判（`CanOperate` 绑 `IsEnabled`，每拍重算）"—代码里确实有这段（`:544`），但判据来源是图元属性而非角色矩阵。

**后果**：这两族合起来，等于权限矩阵覆盖了"菜单"和"窗口打开"，却漏了"流程栏的编辑族"和"运行画面上的运动按钮族"。现场表现是"设置了工程师权限，操作员照样能点动一台伺服"——这是清单 §8 R1/R2 想承认的桌面信任边界**之外**的新口子，因为点动根本不需要碰文件。

**改法**：§3.6 新增两节：

- **F. 流程操作（`FlowAction` 全量 14 项）**：`Create/Delete/Rename/EditComment/ToggleEnabled/Edit/Manager/VariableEvents/Compile` → `EditStructure`/`Compile`（Engineer）；`RunOnce/RunContinuous/Stop` → `ControlRun`/`Stop`（Operator，Stop 恒放行）；`BrowseList` 无限制。`FlowCommandExecute` 首行加 gate 判，且 `FlowCommand` 的 `CanExecute` 同步接 gate（`AsyncDelegateCommand` 支持 `canExecute`）。
- **G. 运行态图元族（轴面板/按钮/输入框）**：明确"图元 `RequiredRole` 是**方案级配置**，本批不自动套角色矩阵；但要写进已知边界并给一条补救：新用户管理页提供「按角色批量设置图元 `RequiredRole`」的能力，或至少在打开含轴面板的画面时提示"该面板未设权限"。**若不做，必须在 §8 风险表新增一条 R15 明确承认"运行画面上的轴操作不受角色矩阵约束"**，不能让 §3.6 的"每个入口都有唯一判据"继续留着。
