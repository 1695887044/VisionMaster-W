## 1. 这个仓库已经验证过一半

`\.zcode\workflow-drafts\二期真并行执行方案设计与交叉质证.dwf.ts` 是一次真实的多模型交叉评审：
阶段 1 出方案（glm-5.3）→ 阶段 2 第一线评审（deepseek-flash）→ 阶段 3 第二线独立评审（hy4-preview-f，**明确"不给它看第一线结论，保持无锚定"**）→ 阶段 4 作者按两线结论修订。

它产出的不是"看起来更周全"的措辞，是 **8 条高危 + 7 条中低危**的可落地缺陷，其中：

- 【高危 3】FailFast 状态机自相矛盾：方案写"业务失败→记 Faulted(业务)"，但 `BranchOutcome` 没有该成员、业务失败无异常对象（`CompiledPluginNode.cs:44-51` 不抛、`VisionPluginBase` 默认 `RethrowOnException=false`），实现者只能编造异常。**两线独立发现同一处** —— 这是评审有效的强证据。

- 【高危 6】同步 join + 不限流在嵌套并行下线程池饥饿（8×8≈73 线程）。

**结论：多视角独立评审在这个仓库有实证收益，值得做成常设机制。** 但同一份草稿也暴露了三个必须先解决的问题（见 §5）。

## 3. 判据必须换：从"都同意"到"无法再给出带证据的反驳"

"评审到三方都同意为止"作为终止条件有两个反向失效：

1. **谄媚收敛**：第二轮看到别人的结论后说"同意"是最省力的输出。三方独立评审会退化成一份评审的三种措辞，收益归零。
2. **无限发散**：任何模型都能对任何方案再生成一条"我仍然担心"。以"态度一致"为终点，循环不会自然停止。

正确的收敛判据落在**发现集**上，不落在态度上：

> 收敛 = 不存在"未被处置且带可复现证据"的 finding（severity ≥ medium）。

每条 finding 只有两种归宿：**被新版本改掉**，或**被至少两名评审以反证驳回**（反证要给 `file:line`，不是"我认为不重要"）。三方"同意"是这个过程的结果，不是投票投出来的。

**副作用（重要）**：议题必须可判定。并发边界、契约一致性、断言可测性这类有客观判据的议题能收敛；"这个界面好不好看"不能靠证据收敛，那类走 `R124`/`R129` 的基线对照，不要塞进这个闭环。

## 4. 建议形状：驱动器 + 文件协议

### 4.1 目录（产物落 `artifacts\roundtable\`，代码落 `tools\roundtable\`）

`audit_root.ps1` 只校验根目录一级条目，`artifacts` 与 `tools` 均已在 `tools\root-layout.json` 白名单内，**不需要登记新根目录**；不要为这个功能在根目录新建目录（R166）。

```
artifacts\roundtable\<yyyyMMdd>-<topic>\
  topic.json                    议题、冻结产物(路径+sha256)、必读清单、轮次上限
  inbox\<agent>.jsonl           append-only 消息流（复用 .agent-teams 形状）
  rounds\01\brief-<agent>.md    该 agent 本轮的任务书（驱动器生成）
  rounds\01\verdict-<agent>.json 结构化评审结论（agent 产出，驱动器校验）
  rounds\01\diff.patch          本轮相对上一冻结版本的改动
  consensus.json                驱动器计算的处置表与收敛判定
  transcript.md                 人读的时间线（谁在第几轮提了什么、怎么处置的）
```

### 4.2 消息（复用现有 inbox 形状，只加三个字段）

现有 `.agent-teams\archive\vm-takeover\inbox\captain.jsonl` 已是 `{"id","from","to","content"}`。补 `round` / `kind`（`brief|verdict|rebuttal|chair`）/ `artifactSha`，不另造格式。

### 4.3 verdict 契约（agent 必须按此产出，否则判红）

```json
{
  "agent": "zcode|qoder|codebuddy",
  "round": 1,
  "artifactSha": "…",
  "verdict": "pass|pass-with-fixes|fail",
  "findings": [{
    "id": "F-qoder-01",
    "severity": "high|medium|low",
    "claim": "一句话说清是什么问题",
    "evidence": "相对路径:起止行",
    "repro": "怎么证明（读哪几个文件、什么条件下触发）",
    "proposedFix": "一句话"
  }],
  "rejectedFromOthers": [{ "id": "F-zcode-02", "reason": "…", "counterEvidence": "路径:行" }]
}
```

`findings` 为空**不等于通过**——空数组按"无效评审"判红重跑（草稿里"空返回等于没做评审"是同一个坑）。

### 4.4 一轮的流程

1. 驱动器冻结产物（文档或 commit hash），写 `topic.json` + 三份 `brief`。
2. **第一轮盲评**：三份 brief 互不可见，各自只拿议题 + 必读清单 + 冻结产物。
3. 三个 CLI 并行跑（`-p` + 只读/plan 权限），各自把 verdict 写到指定路径。
4. 驱动器做 schema 校验 + 证据行号存在性校验（行号越界/文件不存在 → 该条判废并重跑，不进入裁决）。
5. 合并发现集，按 §3 判据处置：已修 / 被两名评审反证驳回 / 未处置。
6. 未收敛 → 生成下一轮 brief：**只含"未处置 finding + 上一版到本版的 diff"**，不重贴全文（控制上下文与成本）。第二轮起才允许看别人的结论，且任务不是"表态"而是逐条 `accept/reject + 证据`——把"同意"变成有成本的动作，这是反谄媚的机制。
7. 轮次上限 3。到上限仍未收敛 → 输出分歧清单交人裁决，驱动器退出码非 0。

## 5. 三条不可让的纪律

| # | 纪律 | 违反后果 |
|---|---|---|
| 1 | **首轮盲评**，第二轮才交换 | 锚定一旦发生，三方独立评审退化为一份评审的三种措辞（草稿已显式写明"不给它看 deepseek 结论"） |
| 2 | **评审对象冻结**（文档版本或 commit hash），修订是单独一步、由一人做、产出新快照再开轮 | 三个评审与改动赛跑，行号对不上，证据校验全部失效 |
| 3 | **空返回 / schema 不合格 / 证据不可复现 = 判红** | 与 R183② 同源：没人能验证的"通过"比没有结论更坏。实测已确认 CodeBuddy 认证失败时退出码为 0，只看退出码必假绿 |

## 7. 落地路径

### 7.1 现在就能跑：ZCode 单机三线盲评（零登录成本）

用现有 workflow 机制把"两线"扩成"三线"，模型分配走 `subagent_model`。今天可用，真读代码、有行号证据、无需任何额外登录。缺点：三个视角都是同一宿主的模型，**不引入异构工具链**。

### 7.2 目标形态：三进程异构闭环（需两次 `/login`）

驱动器依次/并行拉起三个 CLI，各自在只读模式下评审同一份冻结产物，verdict 落文件，驱动器裁决。这才是"三个软件协同作业"的完整形态，也是唯一能引入异构能力的路径——例如 `.qoder\settings.local.json` 配了 CodeGraph MCP（`codegraph-server.exe --mcp --workspace D:\C#\VM`），而本会话**没有** CodeGraph 工具（R28 明写"本会话无 CodeGraph 工具"），Qoder 能给出索引级影响面，本会话只能给 grep/read 结论。

前置：Qoder 与 CodeBuddy 各做一次 `/login`；给三家各写一份只读评审的提示词模板；确认三家的 `-p` 在只读模式下不会尝试写文件。

### 7.3 不建议：UI 自动化

三个 GUI 抢焦点，版本一升级就坏。既然三家都有 CLI，没有理由走这条路。

---

## 8. 需要用户裁决的三点

1. **是否给 Qoder 与 CodeBuddy 各做一次 `/login`**（不做就只能停在 §7.1）。
2. **收敛阈值**：medium 以上未处置即不收敛（保守，轮次多）／只认 high（快，会漏中危）。
3. **谁做终裁**：轮次用尽的分歧由用户裁决，还是指定某个角色（如 architect）代裁后报备。
