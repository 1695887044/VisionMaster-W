## 0. 一句话

把「变量赋值」名字列（以及后续所有"写到哪个变量"的字段）从**行内浮层 + 可编辑下拉**收敛成**一个弹窗**：
名字列变只读块，点它开窗；弹窗左侧虚拟化候选列表（搜索 + 类型筛选），右侧选中项详情；运行时作用域多一个"直接用列表外的名字"出口。

## 2. 整体思路

### 2.1 三条约束决定了形态

1. **名字不是值**：`AssignmentRow.VariableName` 是普通字符串配置（`Models\AssignmentRow.cs:33`），只有"值"是端口。
   所以不能复用绑定弹窗（`DataBindView` 的产物是 `LinkReference`，四种 Kind 全是"如何解析出一个值"）。R33 / R188 / R190。
2. **运行时名字空间是开集**：静态只能扫到上游「变量定义」节点（`Engine\FlowQueryHelper.cs:244` 只认 `VariableDefinitionPlugin`），
   脚本 `Context.SetVar` 造的名字静态不可见。所以运行时列**必须**保留"手输一个列表外的名字"的能力（R190 唯一例外）。
3. **插件拿不到 `IDialogService`**：插件只引用 `Core.Interfaces` + `Core.Controls`（`Plugins\Plugin.Utility\Plugin.Util.csproj`）。
   所以弹窗必须由宿主开、插件通过事件回调拿结果 —— 照 `LinkPathEvent` 的既有先例（`LinkableValueEditor.xaml.cs:686` → `ProcessViewModel.cs:562`）。
   这条通道已在插件视图里跑通（值列 🔗 就是它）。

### 2.2 为什么 dialog-only（不保留行内浮层）

行内控件一旦删掉，三类缺陷**不是被优化而是被删除**：
`ItemsControl` 不虚拟化、每次按键 `Clear()`+`Add`、每行复制全量候选 —— 宿主代码全部消失。
同时删掉一批已记录在案的坑：可编辑 ComboBox 清 `ItemsSource` 推空串（`AssignmentRowVm.cs:79-100`）、
打开浮层先清搜索词（`:46-54`）、R35 那 6 个输入事件钩子（`VariableAssignmentView.xaml.cs:29-35`）。

代价：改一行名字从 2 次交互变 3 次。缓解：`Enter` 直接确定并关闭（"点开 + 回车"）。

### 2.3 与"统一走绑定弹窗"的关系

- **取值绑定**：已经统一（`LinkableValueEditor` 🔗 → `DataBindView`），本方案不动。
- **写名选择**：本方案把它统一到**一个名字选择弹窗**，但**不**复用 `DataBindView` 的语义（不给名字挂 `LinkReference`）。
- 后续 `DataRecord` / `ResultUpload` / `CSharpScript` / `ImageAssign` 的名字字段用**同一个弹窗**，只是入参不同。

| # | 动作 | 行为 |
| --- | --- | --- |

## 5. 实现要点

### 5.1 事件契约（`Shard\Core.Interfaces\PickVariableNameEvent.cs`，新增）

```csharp
public sealed class PickVariableNameEvent
{
    public Guid TargetStepId { get; init; }        // = StepData.StepId：弹窗据此算"上游运行时变量"
    public string Scope { get; init; }             // "Global" / "Runtime"（与 VariableAssignmentPlugin 同一套字面量）
    public string CurrentName { get; init; }
    public bool AllowFreeText { get; init; }       // Runtime = true（R190 开集）
    public Action<VariablePickResult>? OnPicked { get; init; }   // null = 取消
}

public sealed record VariablePickResult(string Name, Guid VariableId, string Scope, string TypeName, bool IsInvalid);
```

- **`TargetStepId` 不能省**：`PluginVariableOptions.Build(workspace, targetStepId)` 靠它算上游运行时变量；
  漏了就是 2026-10-20 那次"单绑定模式下运行时候选整批为空"的复发。
- 纯加性契约变更（不动既有签名），按 R12 走一次架构评审留痕。

### 5.5 候选来源一致性

弹窗与插件**必须**用同一份口径（`PluginVariableOptions.Build`），否则会出现"弹窗里选得到、插件里提示失效"。
判据：弹窗打开后列表条数 == 插件侧 `_configContext.Variables` 同 `Scope` 的条数（断言里直接比）。

### 5.6 性能硬约束（可判定）

| 约束 | 判据 |
| --- | --- |
| 列表虚拟化 | 5,000 条候选，实际 `ListBoxItem` 容器 ≤ 25（探针 S4 已证目标形态为 6） |
| 高度有界 | 内容超过 3 屏才封顶；十几行不出现内层滚动条（照 2026-10-29 那次修复的门槛） |
| 过滤 | 5,000 条过滤 < 200 ms（实测 26 ms） |
| 行内零候选 | 插件视图里不再有 `ItemsSource="{Binding Candidates}"` / `FilteredCandidates` |

| 3 | 运行期只按名字写，契约里没有 Id 重载 | `VariableAssignmentPlugin.cs:1094-1101` → `Shard\Core.Interfaces\IGlobalVariableWriter.cs:26`（唯一方法 `TryWrite(string name, …)`） |

### 5.7.2 设备身份的口径（复用既有，不另造）

- 设备 = `NetworkVariableModel.ConnectionName`，**序数比较**；本地 / IO / 系统变量没有设备。
- 这不是新口径：批 2 的唯一性判定已经用它（`Core\Binding\VariableNameScope.cs:23-73` 的 `ScopeOf` / `DescribeScope`），轮询注册表的键也是 `(连接名, 变量名)`。
- 没有独立的"设备 Id"可用（`NetworkVariableModel` 只有 `ConnectionName`）。所以分工固定：**分组键 = 连接名，寻址键 = `VariableId`**。

### 5.7.3 数据结构改动（4 处）

| # | 结构 | 改动 | 理由 |
| --- | --- | --- | --- |
| 1 | `VariableOption`（`Shard\Core.Interfaces\IPluginConfigContextProvider.cs:209`） | 加 `string? DeviceName`（= ConnectionName，本地为 null）+ `bool IsNameDuplicated`（该名字在本方案多台设备上存在） | 插件视图要显示"哪台设备"，而插件够不到 `NetworkVariableModel`，只能由宿主算好推进来 |
| 2 | `PluginVariableOptions.Build`（`:46-136`） | 去重键 `(name, scope)` → **`VariableId`**（Id 为空时回退 `name+scope`，运行时变量走这条）；`DeviceName` 取 `VariableNameScope.ScopeOf` 口径；第二遍扫全表算 `IsNameDuplicated` | 一条变量 = 一个 Id；按名字去重正是"第二台消失"的根因 |
| 3 | `AssignmentRow`（`Plugins\Plugin.Utility\Models\AssignmentRow.cs`） | 加 `Guid VariableId`；`DeviceName` 只做显示与旧数据提示（`[JsonIgnore]`） | 落盘后运行期才能精确寻址；变量改名不断链 |
| 4 | `VariableAssignmentPlugin.TryAssign`（`:1092-1110`） | 全局分支改 `context.SharedVariables.TryWrite(row.VariableId, row.VariableName, value, out error)`；`VariableId == Guid.Empty` 时回退现有 `GlobalVariables.TryWrite(name, …)` | 契约已存在（`ISharedVariableAccess.cs:32`），`GlobalVariableWriter` 已同时实现两个接口（`GlobalVariableWriter.cs:27`），类型守门与落值只有一份 |

运行时作用域不动：本地变量没有稳定 Id，`LocalVariables` 本来就是按名字的字典（`CreateIfNotExists` 语义也保持）。

### 5.7.4 旧方案（没有 Id）怎么处理

- 打开旧 `.vms` → `VariableId` 为空 → 走名字路径 → 若重名，运行期报歧义（批 1 已保证**不写错设备**）。
- 界面提示：名字块显示 `需重选` 徽标 + 提示行「该名字在 2 台设备上都有，请重新选择一次以绑定设备」。
- 用户重选一次 → 写回 `VariableId`（自愈，与 `LinkReference.TargetVariableId` 的自愈回填同款，见 `VariableRegistry.ResolveGlobalLink`）。
- **不自动猜**：绝不按"第一个命中"回填 Id —— 那等于把静默错值装回来。

### 5.7.5 取值方向（绑定弹窗）的同类修复

`FlowQueryHelper` 的全局节点把每个变量铺成 `PortDefinition{Name, VariableId, …}`，`Name` 只有变量名 → 两个同名项在绑定弹窗里长得一模一样。两条路（需拍板）：

- (a) 给 `PortDefinition.Name` 加设备段（`L1 · Alarm[90]`）—— 会改到显示串与既有断言；
- (b) 只在 `VariableBindingViewModel:746-749` 拼 `DisplayAddress` 时加设备段 —— 影响面小，但候选行内仍看不出差别。

建议 **(b) + 候选行内加设备 chip**（与选择器同一视觉），不动 `PortDefinition.Name`。
