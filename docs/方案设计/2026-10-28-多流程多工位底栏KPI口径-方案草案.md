## 2. 为什么不能只给一个全局数

| 指标 | 多流程/多工位下的问题 |
| --- | --- |
| 节拍 | 节拍天然是**每流程**的。N 条并行时求和没有物理意义，平均也没有意义（快站被慢站拖住，平均值不代表产出）。 |
| OK / NG | **串联工位**（同一产品依次过站）跨站求和 = 同一件产品被重复计数，良率会算错；只有**并联独立工位**（各自加工不同产品）求和才成立。 |
| 告警 | SCADA 报警定义是**方案级、按变量触发**，没有流程/工位归属。现在只能全局计数；要按工位拆，必须给报警定义补"工位/分组"标签（另一个改动）。 |

结论：底栏不可能用"一套数"同时表达 N 条流程。必须先把**口径**写死，再接数据。

## 3. 承载方式（推荐）：按流程投影只读系统变量

> 这一节是 2026-10-28 用户提议"建流程时建一条系统变量、程序内部维护"的落地形态。
> 结论：**方向正确，但要做成"派生只读系统变量"，不要做成落盘的用户变量。**

### 3.1 为什么不是"在方案里新建一条用户变量"

| 做法 | 后果 |
| --- | --- |
| 流程创建时往 `SolutionModel.Variables` 加一条普通变量 | 改名/删除/复制流程都要同步维护（四处以上，漏一处就静默不一致）；老方案要迁移；用户可改名/删除，KPI 静默失效；值随方案落盘，"上次退出时的节拍"会变成幽灵数据；变量清单被 N×M 条统计量污染。 |

现有系统变量基础设施已经把这些问题解决掉了：

- `SystemVariableModel`：**只读派生量**，不实现 `IWritableVariable`（写路径如实拒绝，误绑静默忽略），
  不落盘，身份是**确定性 Guid**（`Core/Models/Variable/SystemVariableModel.cs:14-31`）。
- `SystemVariableCatalog`：按实体（轴）投影"父变量 + 字段"，同一实体同一字段**复用实例**，
  改名只改模型上的 `Name` 并让注册表重扫（`Core/Binding/SystemVariableCatalog.cs:24-31/215-219`）。
- `RecipeVariableCatalog`：非设备类系统变量的先例（当前配方状态），
  目录在 Core、来源接口 + 宿主实现，变化时 `Publish`（`Core/Binding/RecipeVariableCatalog.cs`）。
- `SystemVariableHost`：多提供方合并、串行写集合、名字/Id 冲突先注册者优先
  （`Core/Binding/SystemVariableHost.cs:26-120`）。
- `System.` 前缀是保留前缀，用户变量不能新建/改名成它（`SystemVariableCatalog.IsReservedName`，
  `Core/Binding/VariableNameRules.cs:33-35`）。

### 3.2 建议形态

每个流程投影一组：

```
System.Flow.<流程名>                    （父变量，可整块监视）
System.Flow.<流程名>.State              （运行 / 暂停 / 停止 / 故障）
System.Flow.<流程名>.CycleTimeMs        （上一轮耗时）
System.Flow.<流程名>.CycleTimeAvgMs     （最近 N 轮均值）
System.Flow.<流程名>.RoundCount         （完成轮次）
System.Flow.<流程名>.OkCount
System.Flow.<流程名>.NgCount
System.Flow.<流程名>.UnknownCount       （未判定/异常轮次，既不算 OK 也不算 NG）
System.Flow.<流程名>.CurrentStep        （当前执行节点名；并行分支见 §4）
System.Flow.<流程名>.CurrentStepIndex   （第几个，可选）
System.Flow.<流程名>.StepCount          （节点总数）
System.Flow.<流程名>.LastRoundAt        （最近一轮完成时间）
```

- **身份**：`SHA1("flow-var|{FlowID}|{字段}")` 前 16 字节 → 改名、重启、换机器都不变；
  SCADA/连线按 Id 寻址，改名后绑定仍命中（与运动轴同一手法）。
- **名字**：由 `FlowName` 派生，改名时目录调 `UpdateName` 并让注册表重扫；
  流程名在方案内唯一（`FlowListViewModel` 已有重名校验），不会撞名。
- **生命周期**：目录在方案加载/流程增删改名时 `Rebuild`；删除流程 → 变量消失；
  复制流程 → 新 `FlowID` → 新变量。**不需要迁移脚本，老方案打开即有。**
- **写入方**：只有宿主发布器（`UpdateMirrorValue` 是 internal，目录在 Core）；
  流程逻辑和用户都写不进去。流程要表达 OK/NG，写自己的普通变量，宿主在轮末读。
- **不落盘**：重启后计数从 0 开始、首轮完成前无节拍（显示"待首轮"）。
  若现场要求跨班次累计，另做持久化计数器（或写 SCADA 历史库），不要靠系统变量持久化。

### 3.3 数据来源（引擎零改动）

| 字段 | 来源 |
| --- | --- |
| State | `SessionStateChanged`（`FlowEngineService.cs:49`） |
| CycleTimeMs / Avg / RoundCount / LastRoundAt | `FlowRunStarted` → `FlowRunCompleted` 之间 Stopwatch（`:462/476`） |
| CurrentStep / CurrentStepIndex | 100ms 轮询 `session.FocusedStep`（`Core/Models/Compileds/CompiledNode.cs:333` 维护），**合并到 10~20Hz 再发布** |
| StepCount | 流程结构变化时递归计数（`session.Blueprints.Count` 或模型层深计数） |
| OkCount / NgCount | 轮末读流程配置的"判定源"（见 §4.1）；未配置时只累计 UnknownCount |
| UnknownCount | 读不到判定值（未配置/本轮未执行/类型不符）或会话 `Faulted`；**不把步骤 Failed 直接当 NG** |

宿主侧新增 `FlowRuntimeVariableSource`（订阅上述事件 + 轮询）与
`FlowRuntimeVariableCatalog`（Core，投影 + 实例复用 + 改名），在 `SystemVariableModule` 注册，
顺序排在配方/通讯/相机之后。**不改 `Engine`、不改 `FlowSession` 契约。**

### 3.4 收益

- 底栏、SCADA 图元、脚本、结果上报/数据记录**共用同一份**按流程统计，不再各算一套。
- 底栏只负责"按什么范围展示"（选中流程 / N 条在跑），不再承担统计口径。
- 每个工位可以直接在 HMI 上绑 `System.Flow.<工位>.CycleTimeMs` 等，不用写插件。

## 4. 仍需拍板的三个口径

| # | 问题 | 建议 |
| --- | --- | --- |
| 1 | 工位之间是**串联**（同一产品过站）还是**并联**（各自独立产品）？ | 决定底栏是否允许跨流程求和；默认按串联处理（不求和）。 |
| 2 | **当前执行节点**在并行分支下怎么显示？ | `FocusedStep` 只有主线程一个指针，并行分支按设计**不碰它**（`CompiledNode.cs:275-306`）；默认显示"主线程焦点"，并行时标注"并行中"，不假装能显示全部。 |
| 3 | **OK/NG 判定源**：流程结果变量，还是"步骤失败即 NG"？ | **每流程显式配置判定源**：变量优先、判定表端口可选；未配置只累计 `UnknownCount`。详见 §4.1。 |

### 4.1 OK/NG 判定源（推荐）

**结论**：`OkCount/NgCount` 只认**业务判定**；判定不到就记 `UnknownCount`。**不要用"步骤 Failed"当 NG，也不要当 Error**。

依据（仓库里两种插件对"NG"的状态语义正好相反）：

- 判定表 NG 时会 `Fail(summary)`，步骤变 Failed（`Plugins/Plugin.JudgeTable/JudgeTablePlugin.cs:773-774`）。
- 卡尺明确"NG 是正常结果（Success 保持 true）"（`Plugins/Plugin.CaliperMeasure/CaliperMeasurePlugin.cs:884-886`）；
  斑点只在空图/标定/异常时 `Fail()`，NG 只写 `IsOk`（`Plugins/Plugin.BlobDetect/BlobDetectPlugin.cs:1349-1382`）。

所以"步骤 Failed"在不同插件里既可能是不良、也可能是技术故障，不能作为统一判定源。

**配置**（`FlowModel` 新增，可选、随 `.vms` 落盘、向后兼容）：

| 字段 | 说明 |
| --- | --- |
| `ResultSource` | `None` / `Variable` / `StepPort`，默认 `None` |
| `ResultVariableId` + `ResultVariableName` | `Variable` 模式：每轮结束写 true/false 的布尔变量（也接受 string/int）；Id 优先、名字兜底，改名不丢 |
| `ResultStepId` + `ResultPortName` | `StepPort` 模式：判定步骤（通常是判定表）的 bool 输出端口，如 `IsOk` |

**读取时机**：`FlowRunCompleted` 里同步读，读完才进入下一轮；`session.DebugEnabled == true` 的调试轮跳过。

**归一化**：

| 值 | 判定 |
| --- | --- |
| bool | true = OK，false = NG |
| string | `OK/PASS/TRUE/合格/良品` → OK；`NG/FAIL/FALSE/不合格/不良` → NG；空/其它 → Unknown |
| int | 1 = OK，0 = NG；其它 → Unknown |
| 读不到 / 类型不符 / 本轮判定步骤未执行 | Unknown（不计入 OK/NG） |

**两种模式怎么选**：

- **新方案、用判定表**：优先 `StepPort`。不增加变量；步骤的 `State` 能证明本轮真的执行过，天然没有"沿用上一轮"的问题。
- **已有方案、用脚本/逻辑运算汇总**：用 `Variable`。兼容现有 `<工位>_Result` 约定（样例主流程就是这样汇总的，
  `tools/vms-generator/Program.SamplePair.cs:482-516`）。要求判定变量**每轮无条件写**；
  若流程里可能跳过判定步骤，建议同时写一个 `*_ResultRound` 自增戳，宿主比对戳变了才认，否则记 Unknown。
- **都没配**：`Ok/Ng` 显示"未配置"，只累计 `RoundCount/UnknownCount`，绝不拿 0 或步骤失败冒充。

**线级 vs 工位级**：

- 每条流程的 OK/NG 是**工位级**。
- 串联线的线级结果 = 主流程汇总变量（样例里的 `CurrentResult`/`allOk`）或末站判定；
  **不能把各工位 OK/NG 相加**（同一件产品会重复计数）。
- 并联独立工位才允许求和；这属于方案级"产线拓扑"声明（§4 第 1 条）。

**断言**：

① NG 且 `Success=true`（卡尺/斑点）→ 计 NG，不计 Unknown；
② 判定表 NG（步骤 Failed）→ 仍按 `IsOk` 计 NG，不因步骤 Failed 改记 Unknown；
③ 技术故障导致判定步骤没跑 → Unknown，不沿用上一轮；
④ 未配置 → Ok/Ng 保持 0 且显示"未配置"；
⑤ 两条流程互不串数；⑥ 调试轮不计；⑦ 流程改名后按变量 Id / 步骤 Id 仍能读到。

### 4.2 内置"结果输出"步骤（推荐形态）

**定位**：流程图上显式的"本轮判定声明"节点。它只声明 OK/NG + 原因，不计算节拍、不统计计数、
不输出当前节点；这三项由宿主统计。**不要叫"流程状态输出"**——它输出不了状态全集。

#### 4.2.1 形态与端口

- 实现：普通插件类 `ResultOutputPlugin : VisionPluginBase, IFlowResultSource`，
  放进现有 `Plugins\Plugin.Utility`（不新建工程），工具箱分组「流程控制」。
- 端口（只有输入，没有输出）：

| 端口 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `IsOk` | bool | 是 | 本轮业务判定，true=OK / false=NG；编译器按 `IsRequired` 检查未接线 |
| `Reason` | string | 否 | NG 原因/摘要，进日志与 `System.Flow.*.LastReason` |

- `[ParallelSafe]`：只读写自己的端口，允许出现在并行分支。
- **关键语义**：NG 时步骤本身仍然 `Success=true`。判定是正常结果，步骤失败只表示"没拿到判定"；
  否则父流程/`FlowInvoker` 会把产品 NG 当成技术故障（`Engine/FlowInvoker.cs:140-147` 现有口径）。

#### 4.2.2 执行语义

- `RunAlgorithm` 只做三件事：读 `IsOk`/`Reason`、记一行日志、`Success.Value = true`。
- `IsOk` 未接线但被填了常量 → 记 Warn（允许测试用，但生产流程应接上游判定）。
- 不在插件里写任何变量：写全局变量会退回用户变量生命周期问题；系统变量只读
  （`Core/Models/Variable/SystemVariableModel.cs:14-31`）。

#### 4.2.3 宿主怎么读

- 新增 `IFlowResultSource`（`Shard\Core.Interfaces`，`bool IsOk` / `string Reason`），
  由"结果输出"步骤实现；宿主按**接口**识别，不按类名字符串。
- `FlowRunCompleted`（`Engine/FlowEngineService.cs:476`）里：
  1. 遍历 `session.Blueprints`（深表，含分支/循环内步骤）；
  2. `session.ExecutionEngine.PluginLookup.TryGetValue(step.StepID, out var plugin)`；
  3. 取 `step.State == Success` 且 `plugin is IFlowResultSource` 的步骤；
  4. 多个命中 → 取 `LastRunStartTimestamp` 最大的（最后执行），并记 Warn；
  5. 没有命中 → 按 `FlowModel.ResultSource` 回退（变量/步骤端口），否则 Unknown。
- 步骤被跳过/未到达（`Skipped`/`Idle`）→ 不读端口值，记 Unknown；这样不会沿用上一轮。
- 宿主读取在流程线程、轮末同步完成；只读一个 bool/string，不阻塞下一轮。

#### 4.2.4 校验与迁移

- 编译/保存校验（只警告，不阻断）：
  - `Role=Main` 且没有任何结果源（无结果输出步骤、无变量/端口配置）→
    "主流程缺少判定源，底栏 OK/NG 将显示未判定"；
  - 结果输出步骤 > 1 → "只有最后执行的一个生效"；
  - `Role=Home/End/None` 不校验（它们不产生产品）。
- 旧方案：没有该步骤 → Unknown；**不自动插入**（静默改用户流程图是红线级行为）。
- 兼容路径：`FlowModel.ResultSource = Auto` 时优先级
  `结果输出步骤 > 配置的结果变量 > 配置的步骤端口 > Unknown`；
  老方案继续用 `<工位>_Result` 变量，新方案用步骤。
- 位置约束：放在主路径末尾、所有 `Return` 之前；放在循环里时"最后一次执行"生效，
  一个轮次多件产品需要另一种计数源（一票/轮 ≠ 一票/件）。

#### 4.2.5 工程与测试

- 落点：`Plugins\Plugin.Utility\ResultOutputPlugin.cs` + `Help\ResultOutputPlugin\`（R41 手册）；
  若独立成 `Plugin.FlowControl` 工程，还要守红线①与 R62 sln 登记，不推荐。
- 契约：`Shard\Core.Interfaces\IFlowResultSource.cs`（新增、纯增量，R12 评审）。
- 构建：重建 `Plugin.Util`（红线③），跑 `tools\run_gates.ps1`。
- 断言：
  ① `IsOk=true/false` → 宿主读 OK/NG；
  ② `IsOk` 未接线 → 编译期 `[参数缺失]`；
  ③ 分支未走到 → Unknown，不沿用上一轮；
  ④ 两个结果输出 → 取最后执行并 Warn；
  ⑤ 调试轮不计；
  ⑥ 子流程的结果不覆盖父流程（按 `CurrentFlowName`/会话归属）；
  ⑦ 帮助资源数 = 磁盘 .md 数（R42）。

补充口径：

- **调试运行不计入生产 KPI**：`session.DebugEnabled == true` 的轮次跳过（引擎在事件前已置位，`:415`）。
- **底栏范围**：默认跟当前选中流程；多于一条在跑时显示 `N 条在跑`，点开浮窗每流程一行。
- **告警**：全局 `UnacknowledgedCount`，沿用"产线告警 ≠ 日志警告"的既有决定。

## 6. 风险与踩过的坑

1. **别用"最后开轮的那条流程"当全局当前流程**：`ImageCollectionService._currentFlowName`
   已经踩过（2026-10-27 诊断：A 的帧记成 B，清错窗口）。统计必须按会话/发布方身份归属。
2. **别把 `PerformanceMonitor` 当每轮统计**：它是会话级，`ExecutionCount` 不是轮次。
3. **别把"步骤 Failed"直接当 NG，也不能当 Error**：判定表 NG 时会 `Fail()`（`JudgeTablePlugin.cs:773-774`），
   而卡尺/斑点明确"NG 是正常结果，Success 保持 true"（`CaliperMeasurePlugin.cs:884-886`、
   `BlobDetectPlugin.cs:1349-1382` 只在技术错误时 `Fail()`）。同一状态在不同插件里含义相反，
   所以 OK/NG 必须有显式判定源；`UnknownCount` 只表示"这轮没拿到判定"。
4. **当前节点必须节流**：快节拍流程每节点一次通知，会把 SCADA 绑定/UI 通知队列刷满
   （仓库已有"每秒上万次跨线程通知"的教训，`Core/Models/ProcessStep/StepModel.cs:240-243`）。
   轮询 + 10~20Hz 合并；`UpdateMirrorValue` 同值自动短路（`SystemVariableModel.cs:156-174`）。
5. **并行分支没有"当前节点"**：`FocusedStep` 是单指针，分支步骤按设计不碰它；
   显示层必须如实标注，不能拿主线程焦点冒充全部。
6. **系统变量只读**：流程逻辑不能写；要表达 OK/NG 就写普通结果变量，宿主轮末读。
7. **不落盘 = 重启清零**：这是刻意取舍（避免"上次退出的幽灵值"）；跨班次累计另做持久化。
8. **多流程并发与单 Main 策略的冲突**：如果多工位并行是长期形态，`FlowBatchSelector`
   的单 Main 约束需要重新评审（7 GB 内存事故的历史约束），否则工具栏"循环运行"永远只能启动一条。

## 7. 更完整的架构（评审结论）：把"一轮"变成引擎一等对象

> 结论：比"结果输出步骤"更彻底的方案，是让引擎为每一轮产出一条不可变的
> `FlowRoundResult`，所有消费者（底栏、SCADA、结果上报、数据记录、报表、子流程调用）
> 读同一条记录。结果输出步骤降级为"判定来源之一"，不再是统计核心。

### 7.1 为什么现在的方案还不完美

同一件事实（"这一轮跑得怎么样"）目前至少有四处各自实现：

- 引擎只有会话级 `PerformanceMonitor`（`Core/Toolkit/PerformanceMonitor.cs:132`），不是每轮；
- `FlowInvoker` 把"有步骤 Failed"当调用失败（`Engine/FlowInvoker.cs:140-147`）；
- 判定表 NG 时 `Fail()`（`Plugins/Plugin.JudgeTable/JudgeTablePlugin.cs:773-774`），
  卡尺/斑点 NG 时 `Success=true`（`CaliperMeasurePlugin.cs:884-886`、`BlobDetectPlugin.cs:1349-1382`）；
- 样例方案自己维护 `OKCount/NGCount/CurrentResult`（`tools/vms-generator/Program.SamplePair.cs:482-516`）。

同一个"轮次结果"有四种口径，必然漂移；底栏无论读哪一份，都无法解释"为什么是 OK/NG"。

### 7.2 目标模型

| 字段 | 说明 |
| --- | --- |
| FlowId / FlowName / SessionId | 身份 |
| RoundIndex / StartedAtUtc / CompletedAtUtc / CycleTimeMs | 轮次与节拍 |
| Outcome | Ok / Ng / Unknown / Aborted / Faulted |
| VerdictSource | ResultStep / Variable / StepPort / None |
| Reason / FailedStepId / FailedStepName | 可追溯 |
| StepCount / CompletedStepCount | 进度 |
| IsDebug / Trigger | 过滤与归因 |

- 引擎在 `FlowRunCompleted` 之后构建记录，发布 `FlowRoundCompleted`；
  `FlowSession.LastRound` 保存最后一条。
- 判定由 `IFlowVerdictResolver` 解析（结果输出步骤 > 变量 > 步骤端口 > Unknown），
  引擎只依赖接口，不依赖工作区。
- `FlowInvoker` 改为读 `LastRound`：`Success` = 轮次完成（Ok/Ng/Unknown），
  另加 `Verdict` 字段；产品 NG 不再被当成调用故障。
- 系统变量 `System.Flow.*` 从 `FlowRoundCompleted` 投影，不再自己计时。
- 底栏/SCADA/上报/报表读同一份聚合；点 OK/NG 可下钻到最近 N 轮（步骤/原因/图/日志）。

### 7.3 工业级扩展（按需）

- `IFlowRunLedger`：内存环形 + 异步落盘（CSV/SQLite），支持班次/工单/追溯/良率/OEE；
  底栏只是查询视图。写入必须异步，不能拖慢流程轮。
- 线级拓扑：`SolutionModel.Line`（工位顺序、串联/并联、LineResultPolicy）。
  **线级良率需要产品身份（SN/工单）**；没有产品身份时只能做工位统计，
  不能把各工位 OK/NG 相加当线良率（同一件产品会重复计数）。
- 若主线流程本身按顺序调用各工位（样例的 Main 就是这样），产品身份隐含在"一轮"里，
  不需要额外 SN；若各工位是独立会话并发跑，必须补产品身份才能汇总。

### 7.4 分期

| 期 | 内容 | 改动面 | 价值 |
| --- | --- | --- | --- |
| L1 | 系统变量 + 结果输出步骤/变量 | 宿主 + 插件 | 底栏有数，工位可绑 SCADA |
| L2 | `FlowRoundResult` + `FlowRoundCompleted` + resolver + 修 FlowInvoker | 引擎契约（R12） | 单一事实源，修 NG 当失败，支持下钻 |
| L3 | Ledger + 线级拓扑 + 班次/工单 | 持久化 + 方案模型 | 追溯、良率、报表 |

**推荐 L2 作为"完美与成本"的平衡点**；L3 只在需要班次/追溯/线级良率时做。
