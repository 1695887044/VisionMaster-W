## 1. 目标与范围

在现有"通用视觉流程软件"中引入运动控制，第一批支持**正运动（ZMotion）**与**雷赛（LeadShine）**运动卡，
并满足：

1. **方案级配置**：在解决方案（.vms）里配置运动卡（卡型 + 地址 + 轴映射 + 参数）；
2. **可扩展**：预留驱动接口，后期新增别的板卡品牌**不动主程序**；
3. **扫描识别**：主程序扫描 `Modules\` 下的驱动 DLL 自动识别，与现有相机/算子插件同一套发现机制；
4. **商业化水准**：安全、断线恢复、故障诊断、可测试性、授权留口。

**范围边界（第一期不做）**：电子齿轮/凸轮、多卡协同插补的复杂场景、实时运动规划（轨迹由板卡自己完成，软件不插值）。

## 2. 仓库现状（必须知道的机制，精确到文件）

> 以下是从仓库实读出的结论。接手时这些是"既有事实"，不要重新发明。

### 2.1 流程步骤插件的加载

- 入口：`Engine\PluginService.cs` → `InitPlugins()`（约 L37）。
- 扫描目录：`Modules\`（DEBUG 下 `..\..\..\..\Modules`）。
- 加载：`LoadPlugin(string dllPath)`（约 L171）用 `Assembly.LoadFrom`，再反射找
  `typeof(IVisionPlugin).IsAssignableFrom(t)` 的类型，`Activator.CreateInstance`。
- 契约：实现 `IVisionPlugin` + 派生 `VisionPluginBase`（`Shard\Core.Interfaces\`），
  **必须带** `[Display(Name, GroupName, Description, ShortName)]`，否则被跳过；文件名须 `Plugin` 开头。
- 产物：注册成 `ToolItemModel`（含 `InputDefinitions/OutputDefinitions`）→ `IPluginProvider.RegisterModule`。
- 无版本校验、无卸载、无程序集隔离（`LoadFrom` 进默认 ALC，进程常驻）。

### 2.2 相机体系 —— 运动要照抄的范式

这是"**非流程步骤的设备驱动插件**"的成熟先例，运动卡几乎 1:1 对照：

| 维度 | 相机 | 运动卡（照做） |
|---|---|---|
| 设备契约 | `Shard\Core.Interfaces\Camera\ICameraDevice.cs` | `Shard\Core.Interfaces\Motion\IMotionCard.cs` |
| 基类 | `CameraDeviceBase.cs`（固化环形队列/状态机/心跳） | `MotionCardBase.cs`（固化指令队列/状态机/看门狗） |
| 纯配置 | `CameraDescriptor.cs`（可序列化） | `MotionCardDescriptor.cs` |
| 驱动扫描 | `PluginService.LoadCameraDrivers(assembly)`（约 L266） | `LoadMotionCards(assembly)` |
| 驱动注册 | `IPluginProvider.RegisterCamera` | `RegisterMotion`（见 2.6 的陷阱） |
| 驱动实例 | `Plugins\Plugin.Camera.Network\NetworkCameraDevice.cs` | `Plugins\Plugin.Motion.ZMotion\` |
| 生命周期服务 | `VisionMaster\Services\Camera\CameraProvider.cs` | `VisionMaster\Services\Motion\MotionProvider.cs` |
| 方案集合 | `SolutionModel.CameraConfigs`（约 L128） | `SolutionModel.MotionCards` |

`CameraProvider` 里照抄的方法：`SyncFromSolution()`（增删/按驱动+标识重建设备）、
`ConnectAutoStart()`、`ReleaseAll()`、`MarkConfigDirty()`、`EnsureSynced()`、`DevicesChanged` 事件、
`AvailableDrivers`（列出可用驱动）、`CreateDevice`（用 `Activator.CreateInstance(driver.DriverType, descriptor)`，
要求驱动提供 `Xxx(CameraDescriptor)` 构造，`ILogService` 注入 `baseDevice.Log`）。

### 2.3 通信体系 —— 线程与工厂的范式

- `Communication\Communications\Manager\ConnectionFactory.cs`：`IConnectionFactory` + `ConnectionFactoryManager`
  是"**驱动接口 + 注册表**"先例（内置注册，非 Modules 动态加载）。
- **一条连接一个专属工作线程**：`ConnectionWorker.cs`。运动卡的"一卡一指令线程"照这个来。
- 扫描组：`ScanGroupConfig`（周期 + 名称），变量侧只存组名引用。

### 2.4 方案模型与持久化

- `Core\Models\SolutionModel.cs`：已有 `CameraConfigs`、`CommunicationConfigs`。新增 `MotionCards` 即可。
- 持久化：`Core\SolutionService.cs`，`TypeNameHandling.Auto` + `SafeSerializationBinder`（`$type` 白名单，防恶意 .vms），
  原子写（先 `.tmp` 再 `File.Replace`），加载时做老方案升级归一化。**新增可序列化类型若要放进 .vms，
  需要确认 `SafeSerializationBinder` 白名单是否要登记**（关键，见 8.1）。

### 2.5 端口与参数元数据

- 端口 = 数据成员：`public InputPort<T> / OutputPort<T>` 属性（`VisionPluginBase.EnsurePortsDiscovered` 反射收集）。
- 参数 = `[StepConfig]` 标注属性（`EnsureConfigPropsDiscovered` 收集；`ApplyConfigValues`/`OnConfirm` 在 `InputValues ⇄ 属性` 间往返）。
- 动态端口：`IDynamicOutputProvider.RebuildDynamicOutputs()`，先例 `CreateRoiPlugin`（ROI 变化时重建端口并把
  名字+类型快照写回 `StepModel.OutputPortDefinitions`）；`FlowCompiler.cs`（约 L513）编译前重放。
- 步骤引用设备的方式：**按名字/序列号，不按 Guid**。先例 `Plugins\Plugin.ImageAcquisition\ImageAcquisitionPlugin.cs`：
  `[StepConfig] public string CameraSerial`，运行时 `context.Cameras.TryGetDeviceBySerial(serial, out device)`。

### 2.6 已存在的 Motion 占位与**陷阱**

- `Core\IPluginProvider.cs`：已有 `MotionPlugins` / `RegisterMotion` / `GetMotion`。
- `Engine\PluginProvider.cs`：`RegisterMotion(plugin) => RegisterModule(plugin)`（约 L120，注释"分类未启用"）。
  **陷阱**：直接用它会把运动驱动当成普通流程算子混进左侧工具列表。必须先改成与 `RegisterCamera` 等价的真注册。
- `Engine\PluginService.cs`：`LoadPlugin` 里有 `case "轴卡"` 分支（约 L227-248），目前只 `ShowWarn`，要接上真实加载。
- `VisionMaster\Lifetime\Checks\PluginScanCheck.cs`：已把 `MotionPlugins.Count` 计入启动统计。

### 2.7 参考工程里已有的正运动代码（直接搬）

不在主程序编译范围，但**正运动的 SDK 对接逻辑已经写好**：
- `WPF-Halcon-流程拖拉\05Motion\Plugin.ZMotion\`：`ZMotionAxis.cs`、`ZMotionControl.cs`、`Zmcaux.cs`。
- `WPF-Halcon-流程拖拉\01Main\VM.Start\Core\MotionBase.cs`、`MotionViewBase.cs`、`Events\MotionConnectEvent.cs`。

M4 落地正运动驱动时，搬这些文件的逻辑、重写外壳以符合新契约，**不要从零啃厂商 SDK**。

## 3. 总体架构（四层）

```
L4 流程步骤插件   Modules\Plugin.Motion.Steps.dll      用户拖进流程的：轴运动/回零/等待/读状态/IO
L3 设备资源层     MotionProvider + SolutionModel.MotionCards   方案级配置与生命周期
L2 能力抽象层     IMotionCard + MotionCapabilities + 命令/状态模型
L1 驱动实现插件   Modules\Plugin.Motion.ZMotion.dll / .LeadShine.dll   一品牌一个
```

数据流（运行时）：
1. 方案加载 → `MotionProvider.SyncFromSolution()` 按 `MotionCards` 重建设备实例；
2. 流程步骤经 `[StepConfig] string CardName` + `context.Motions.TryGetByName(name)` 拿到 `IMotionCard`；
3. 步骤 `Enqueue(...)` 下发命令 → 卡线程顺序执行 → 状态回报（`StateChanged` / 轮询）；
4. 轴位置/状态可作 `OutputPort<double/bool>` 输出，被下游步骤或变量引用。

### M2：核心步骤 + 命令模型

**目标**：补齐用户常用步骤，把命令的"分类/取消/超时/生命周期"做完整。

**任务 2.1** 命令模型落地（`MotionCommand.cs` + `MotionCardBase`）：
- 命令分类：`Motion`（顺序）/ `Query`（立即，不走队）/ `Emergency`（插队 + 清队）。
- 生命周期：`Accepted → Queued → Executing → Done / Failed / Timeout / Canceled`。
- 每条命令带超时；`Home` 标记为"不可盲目重试"。

**任务 2.2** 步骤插件（都放 `Plugin.Motion.Steps`，用 `[Display(GroupName="运动控制")]`）：
- `MotionHomePlugin`（回零，`HomeMode` 枚举随能力协商）
- `MotionWaitPlugin`（等到位/等 IO 条件/延时——运动是异步的，这步必须独立）
- `MotionReadStatusPlugin`（读轴位置/速度/状态/限位/报警，输出 `double`/`bool` 端口）
- `MotionStopPlugin`（参数化：减速停/立即停）

**任务 2.3** 类型对齐：轴位置用 `double`（mm），状态用 `bool`，报警用 `int`/`string`。

**验收**：新增步骤能在流程里拖、参数在弹窗配、端口在变量绑定里可见且类型正确；命令生命周期有断言覆盖。

### M3：安全 + 生命周期 + Abort

**目标**：这是"能卖"的门槛。分三块，可并行。

**任务 3.1 安全**：
- `EmergencyStop` 走专用通道（插队 + 清队），`MotionCardBase` 里固化，驱动不能绕过。
- 双层限位：软限位（软件判）+ 硬限位（卡层，能力位 `SupportsHardLimit` 暴露）。
- 看门狗：卡线程与主线程互心跳，卡死自动安全停机。
- 手动 Jog 安全：按住才动 + 速度上限（M5 的调试面板用，这里先把语义定下）。

**任务 3.2 生命周期与恢复**：
- 状态机细化为：`初始化/连接中/在线/离线(可重连)/报警/安全停机/升级中`。
- 断线重连策略（自动 or 人工，配置项）；重连后按 `Capabilities.SupportsAbsoluteEncoder` 决定是否要求回零。
- 错误分级：可恢复 / 需复位 / 需维修，分别给日志与界面提示。
- `CancelAll()`：流程停止/切方案/关窗的统一安全停止入口。

**任务 3.3 流程 Abort**（按 M0.2 的方案）：
- 给执行上下文加取消/中断令牌；`VisionPluginBase` 加 `OnAbort` 钩子；执行器在急停/停止时传播 Abort。
- 运动步骤在 Abort 时发安全停止，而不是把"被打断"误记为"失败"。

**任务 3.4 故障注入测试**：虚拟卡支持模拟断线/报警/超时/NACK，断言安全停、错误分级、重连/回零要求。

**验收**：故障注入场景下流程正确 Abort、轴安全停、错误分级正确；无 `Failed` 误报。

### M5：商业化外围（可与 M3/M4 并行）

### 6.2 `IMotionCard`

```csharp
public interface IMotionCard : IDisposable
{
    string DriverName { get; }                    // 驱动显示名
    MotionCapabilities Capabilities { get; }      // 能力协商
    MotionCardState State { get; }                // 见状态机
    event EventHandler<MotionCardState>? StateChanged;

    void Connect(MotionCardDescriptor descriptor);
    void Disconnect();

    // —— 查询：立即返回，不走命令队列 ——
    AxisStatus ReadAxis(int axisIndex);
    bool ReadInput(int port);
    void WriteOutput(int port, bool value);

    // —— 命令：走队列 ——
    MotionCommandResult Enqueue(MotionCommand command);   // Move / Home / Stop / SetOutput...
    MotionCommandResult EmergencyStop();                  // 插队 + 清队，驱动必须实现
    void CancelAll();                                     // 统一安全停止
}
```

## 7. 关键设计决策与理由

1. **逻辑轴名寻址**（`AxisMapping.LogicalName`），流程步骤引用名字不引用物理轴号 → 换卡/改接线只改映射表。
2. **能力协商**（`MotionCapabilities`）而不是"大而全接口" → 换品牌时方案能迁移，但"哪里不支持"当场明确报错。
3. **工程单位（mm）在驱动层换算** → 流程步骤不感知"脉冲还是毫米"。
4. **安全逻辑挂在设备资源层（MotionProvider/Base），与流程解耦** → 流程没跑、流程被改坏、异常分支时，安全仍生效。
5. **驱动/步骤两类插件分离**（照相机：驱动实现 `IMotionCard`，步骤实现 `IVisionPlugin`），一个 DLL 不要既当驱动又当算子。

## 8. 风险与注意事项（踩坑预警）

### 8.1 序列化白名单
`.vms` 用 `SafeSerializationBinder` 白名单。新增 `MotionCardDescriptor` 等类型若放进去，**必须先确认白名单登记规则**，否则旧方案/新类型反序列化会失败。M0.3 专门确认。

### 8.2 线程纪律（本仓库极其讲究，前几轮探针都因此踩过坑）
- 运动卡**一卡一条指令线程**（照 `ConnectionWorker`），状态回报**不得直接摸 UI**（走 Dispatcher 投递，仓库已有约定）。
- 卡回调/事件可能来自非 UI 线程，`MotionProvider` 的事件要按仓库既有"线程亲和"约定转投。
- 资源释放：卡、线程、队列、定时器必须成对，`Dispose` 要幂等（本仓库对 `IDisposable` 资源回收有大量既定做法）。

### 8.3 Abort 语义（唯一需要动流程内核的点）
现状：步骤只有 `Success`/`ErrorMessage`（成功/失败两态）。运动引入后需要第三种"**被打断**"：
- 方向（最小侵入）：执行上下文加取消/中断令牌，`VisionPluginBase` 加 `OnAbort` 钩子，执行器在急停/停止/切方案时传播。
- 关键区别：Abort 不是 Failed——日志、重试、恢复、用户提示都要区分。M0.2 先出方案，M3 实现。
- **不要**一开始就大改执行器；先加令牌与钩子，行为上"默认等价于停"即可平滑过渡。

### 8.4 异步语义（最容易写错的业务逻辑）
`MoveAbsolute` 是"启动"，`MotionWait` 是"等到位"。文档和 UI 都要明示，否则用户会写出"两条轴同时动却串行执行"的流程。

### 8.5 实时性边界（写进契约注释）
软件是毫秒级调度，承担不了硬实时。插补/急停必须由**板卡自己**（板载缓冲）完成，软件只下发命令。
契约注释里要明确禁止"每毫秒由软件喂位置"这种写法。

### 8.6 不要做的事
- 不要照抄相机的"推模式"（运动是命令+轮询，不是推帧）。
- 不要把每个驱动 API 做成一个插件（会膨胀成几十个）。
- 不要直接使用现有 `RegisterMotion`（它转发到 `RegisterModule`，会把驱动混进算子列表）——先修。
