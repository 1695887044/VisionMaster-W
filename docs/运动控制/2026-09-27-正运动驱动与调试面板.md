## 2. "一带多"在哪里

用户提出"这种轴卡都是一带多的，我在程序里没看到"——分两层，这次补齐的是第二层：

| 层 | 位置 | 说明 |
| --- | --- | --- |
| **配置层** | 运动卡设置 → **轴映射表** | 一张卡一张配置，卡下列出 **N 行轴**（逻辑名 ↔ 物理轴号 + 脉冲当量 + 软限位），流程按逻辑名引用轴 |
| **操作层** | 运动卡调试 → **左侧轴列表** | 一张卡**并排列出它的每一根轴**（位置 + 到位/运动中/限位/报警状态点），选中哪根就在中间操作哪根 |

调试面板的轴列表是"一带多"最直接体现：4 轴卡就有 4 行，每行位置实时刷新，
一眼能看出哪根在动、哪根报警。**不会出现"只知道卡在动、不知道哪根轴在动"**。

## 3. 驱动实现（与板卡无关的部分一行没写）

`ZMotionCard : MotionDeviceBase` 只实现四个方法（`ConnectCore` / `DisconnectCore` / `PollStatusCore` / `ExecuteCommandCore`）
外加 `SafeStopCore`。命令队列、急停插队、命令门禁、看门狗、故障分级全部继承自基类 ——
**这正是上一轮把契约层与驱动层分开的回报**：接真卡时没有回头改任何架构。

### 三处"写错后果很重"的约定（都取自参考工程已投产的写法）

1. **`SetUnits` 之后位置/速度 API 一律是用户单位（mm）** —— 读 `Mpos` **不要再除脉冲当量**。
   除一次会让所有位置缩到 1/1000，而目标位置也同样缩小，于是"看起来能跑，只是行程全错"。
2. **回零完成判据是 `GetHomeStatus == 1`**；homemode 数字只能来自手册：
   `负限位+Index=1 / 正限位+Index=2 / 负限位=17 / 正限位=18 / 原点=19 / 正限位+原点=23 / 负限位+原点=27 / 零位置预设=37`。
   填错一个数字，轴会按完全不同的寻零路径走（把"负限位+Index"填成"正限位+Index"，轴会朝反方向撞）。
3. **位置模式运动是"下发即返回"**，等到位交给「等待到位」步骤 —— 否则多轴同时起步写不出来。

### 安全相关的取舍（宁严勿松）

- `SupportsAbsoluteEncoder = false`：正运动的轴是不是绝对式取决于所配伺服，SDK 没有统一查询接口，
  所以**保守声明为增量式** —— 连上后必须回零。代价是多回一次零，换来的是"绝不按不可信坐标运动"。
- 只读状态失败即抛异常 → 由基类累计"连续失败"→ 看门狗判失联 → 安全停机（不吞异常变成"轴状态一直不变"）。
- 清报警**不自动重新使能**（使能会给伺服上电，有机械后果，必须人来点）。
- 回零速度/偏移**沿用控制器内既有设置**，不擅自覆盖现场用厂商软件调好的参数。
- 回零超时后**先停轴**再报错，不把还在寻零的轴丢下。

### 错误码字典：不编造，给有把握的三层

SDK 只返回一个 int，且**没有码→文案的接口**（核实过：`zauxdll` 没有 `GetErrMsg` 这类导出）。
凭记忆编一张"12=参数错误、34=通信超时"的对照表看着专业，但现场一旦按错误方向排查，
损失比"没翻译"大得多。所以 `ZMotionFaults.Interpret` 给的是：

1. **原始错误码**（现场可对厂商手册、可报给厂商）；
2. **出错的操作上下文**（"回零时"还是"读状态时"——这本身就定位了大半）；
3. **按操作类别的分级与建议**（连接→需现场处理；回零/运动→需人工复位；读状态→可恢复）。

## 4. 调试面板

### 三项手动操作之外的诉求都覆盖了

- **控制**：使能 / 失能 / 停止 / 急停（急停是独立的实心红按钮，不藏在子菜单）
- **定位**：目标位置 + 速度 → 「走到（不等待）」与「**走到并等待到位**」（后者调试时更常用：
  点一下就能看到它到底走没走到），带 「取当前位置」（对位起点）
- **回零**：方式下拉**只列该卡上报支持的方式**（能力协商）、带 120s 超时
- **IO**：输入点实时灯（200ms 刷新）+ 输出点点击切换

### 三条安全设计（手动操作特有的风险）

1. **点动「按住才动」**：UI 库新增 `HoldCommandBehavior` —— 按下执行、**按住期间每 150ms 重复**、
   松开/移出/失焦/控件禁用都收尾。用 `Mouse.Capture` 保证"按住后移出再松开"也能收到事件。
2. **点动心跳兜底**：VM 看门狗发现超过 **500ms** 没收到界面脉冲就自动停 ——
   即使界面事件全丢（失焦、卡顿、行为失效），设备也不会一直走。
   **安全不能建立在"事件一定送达"的假设上**，这是点动与普通按钮的根本区别。
3. **关窗必停点动**：点动的终点是"松手"，而面板都关了就不会再有松手事件；
   定位类运动有终点，不必停（让它走完）。

## 5. 部署（native 库放对位置）

`zauxdll.dll` 必须落在**宿主 exe 旁边**，不能只在 `Modules\`：

`DllImport("zauxdll.dll")` 的搜索路径是 exe 目录 → 系统目录 → PATH，**不包括插件 dll 所在的 `Modules\`**
（插件托管 dll 由 `PluginService` 用 `Assembly.LoadFrom` 从 `Modules\` 装载，但那与 native 库查找规则是两码事）。
所以 csproj 里用 `Plugins\Directory.Build.targets` 早已备好的 `$(HostBinDir)` 投递一份 ——
与 `Plugin.ImageScript` 投递脚本资源是同一手法。

另外把三个运动插件**登记进了 `VisionMaster.sln`**（原先漏登，`dotnet build VisionMaster.sln` 不会产出它们）。
`pack.ps1` 按 `Plugin.*.dll` 通配统计，无需改。

## 7. 真机联调清单（需要你接一台卡）

自动化能验的到"契约与逻辑"为止，以下必须接真卡：

1. **连通性**：填 IP → 连接 → 看状态栏是否显示机型/固件版本（未识别机型会提示核对）；
2. **脉冲当量**：标定每轴 `UnitsPerMm`，走 100mm 用卡尺量 —— 这一步错，后面全错；
3. **使能**：点「使能」，确认伺服上电、状态点变绿；
4. **点动**：按住"正向点动"→ 轴走、**松手立即停**（重点确认松手那一瞬）；
5. **定位**：填目标 → 「走到并等待到位」→ 位置收敛到目标；
6. **回零**：选对方式 → 回零 → 位置归零、`IsHomed` 变 true；
7. **软/硬限位**：手动走到限位附近，确认触发后进报警态且后续运动被拒；
8. **IO**：逐个点输出，确认对应继电器动作；输入点用手碰一下看灯变绿；
9. **急停**：运行中按急停 → 轴立即停、队列清空。

## 9. 首次真机连接故障：DllNotFoundException（缺 zmotion.dll）

实际点「连接 / 断开」时报：

```
连接失败: DllNotFoundException: Unable to load DLL 'zauxdll.dll' or one of its dependencies:
找不到指定的模块。(0x8007007E)
```

### 排查过程（值得留档：这条消息会把人引向错误方向）

| 假设 | 验证方法 | 结论 |
| --- | --- | --- |
| native 库没投递到 exe 旁 | `VisionMaster\bin\Debug\net9.0-windows\zauxdll.dll` 存在（2320896 字节） | 否 |
| 位数不匹配 | zauxdll.dll = `0x8664` AMD64；VisionMaster.exe = `0x8664` AMD64 | 否 |
| 缺 VC++ 运行库 | `vcruntime140` / `vcruntime140_1` / `msvcp140` 都在 System32 | 否 |
| **dll 的依赖缺失** | 用 `LoadLibraryEx` 带**完整路径**加载 → 同样失败，错误码 126 | **是** |

关键认知：`0x8007007E` = `ERROR_MOD_NOT_FOUND`，语义是"**或其依赖**找不到"，
与"文件不在"（`ERROR_FILE_NOT_FOUND` = 2）是两回事。
而 .NET 把它包装成 `DllNotFoundException: Unable to load DLL 'zauxdll.dll' ...` ——
**消息里只会出现你直接 P/Invoke 的那个名字**，看上去完全像"zauxdll.dll 没放对位置"。
"显式全路径也加载失败"这一条就把"路径问题"彻底排除掉了。

### 真正原因

解析 `zauxdll.dll` 的 PE 导入表（PowerShell：DOS 头 → PE 头 → `DataDirectory[1]` → 逐段做 RVA→文件偏移转换）：

```
=== zauxdll.dll 的静态依赖（共 18 个） ===
zmotion.dll      System32=无   SDK目录=无   输出目录=无     ← 就它
KERNEL32.dll     System32=有
USER32.dll / GDI32.dll / ... （其余 17 个都是系统库，都在）
```

正运动 SDK 是**两层**：

| 文件 | 角色 |
| --- | --- |
| `zauxdll.dll` | 辅助层（我们 P/Invoke 的就是它，`ZAux_*` 系列） |
| `zmotion.dll` | **核心层**，由前者的导入表静态依赖 |

少任何一个都加载失败，而报错只会提到 `zauxdll.dll`。

### 已做的三件事

1. **csproj 改为通配投递** `Sdk\*.dll`（原先是逐个列文件名）：
   SDK 升级时往 `Sdk\` 里丢文件即可，不必记得改 csproj；
   并加了构建期 `<Error>`（`Sdk\` 下没有任何 native 库时直接失败，而不是等到运行期炸）。
2. **驱动自带诊断**：捕获 `DllNotFoundException` 后逐个检查 native 文件，**直接点名缺哪些**：
   > 运动卡 SDK 不完整：缺少 zmotion.dll。正运动 SDK 最少需要 zauxdll.dll（辅助层）与
   > zmotion.dll（核心层）两个文件，请把它们一起放到程序目录（VisionMaster.exe 同级）后重新连接

   另外单独捕获 `BadImageFormatException` 并提示"位数不符"——
   32 位 SDK 装到 64 位进程上，Windows 报的**同样是 0x7E**，极易误判为路径问题。
3. **断言钉住**：新增"SDK 完整性"断言（`zauxdll.dll` 与 `zmotion.dll` 必须同时存在）。
   这条断言**当前是红的**，因为 `zmotion.dll` 尚未拿到 —— 这是有意为之：
   它把"缺文件"从"连接时才发现"提前到"构建后即报"，且直接给出补哪个文件。
   （冒烟总数因此从 828/15 变成 830/16，多出的那 1 条失败就是它。）

### 补文件的两种方式

- **立刻试**：把 `zmotion.dll` 直接拷到 `VisionMaster\bin\Debug\net9.0-windows\`（与 exe 同级），
  不必重新构建；
- **长期正确**：放进 `Plugins\Plugin.Motion.ZMotion\Sdk\`，之后每次构建会自动投递到宿主 bin
  （通配投递 + `$(HostBinDir)`，见 §5）。

### 顺带一条构建注意事项

若程序**正在运行**，`dotnet build VisionMaster.sln` 会因 `Modules\*.dll` 与 `bin\*.dll` 被进程锁定而失败
（`MSB3027 / MSB3021 文件被 VisionMaster (PID) 锁定`）。构建前先退出程序即可。

**几个真正说明问题的数字**：

- **点动速度链正确**：10 mm/s × 0.6 s = 理论 6.0 mm，实测走 **5.8 mm**（含加减速段，吻合）；
- **脉冲当量换算正确**：定位到 25.000 mm，实测稳定在 25.000~25.060 mm
  （0.06 mm = 60 脉冲，在 20ms 轮询采样与减速停的正常范围内）；
- **回零超时处理正确**：仿真器没接原点开关，3 秒短超时后**正常返回**且不卡死
  （验证了"超时先停轴再报错"这条路径，而不是把轴丢在那儿）；
- 使能 / 读输入 / 写输出 / 急停 / 断开 全部按预期返回。

### 联调中发现并修掉的一个真问题

首次联调时状态栏显示 **"4 轴"**，而这台控制器是 **32 轴** ——
因为 `VPLC532R` 不在机型表里，走了"未识别 → 最小配置兜底"的分支。

已修：把 `VPLC532R` 加进机型表（轴数 32 取自控制器状态窗口的 `RealAxes: 32`；
`VirtualAxes: 64` 是控制器内部的**虚轴**，用于电子齿轮/凸轮等计算，不作为运动轴对外，故不取 64）。

顺带引入 `ZMotionModelInfo.IoCountApproximate`：VPLC 的 IO 点数取决于组态，
截图里也没给，所以**不编**——状态栏如实显示
"IO 24 入 / 16 出（**点数未核实，按显示上限列出**）"。
理由：IO 列多了只是"点一下会失败"，列少了会让用户以为某个输出坏了；
与其在两个都可能错的数字里选一个，不如让界面说实话。

### 这一步验证不到什么（仍需实机）

仿真器里的"轴动"是模型在走，所以以下**必须接真伺服/真机构**才算验过：

1. 伺服**报警**（过流/过载/断线）与服务使能的真实时序；
2. **硬限位开关**与急停回路的物理响应（仿真器里这些信号是假的）；
3. **原点/限位开关**的真实回零过程（本次回零只验证了"超时路径"）；
4. 脉冲当量的**机械标定**（走 100mm 用卡尺量）；
5. 多轴联动时的机械干涉与节拍。

### 11.1 回零方式：英文枚举 → 中文

原样：下拉里是 `NegativeLimitIndex` 这种**枚举成员名**。操作员看不懂。

新增 `Shard/Core.Interfaces/Motion/MotionEnumDisplay.cs`（契约层，驱动与界面共用一份中文）：

   我凭记忆写了 `MotionCommandResult.Faulted / Cancelled` 两个**不存在的成员**，
   构建直接报 `CS0117` 把我拦住（该枚举实际只有 `Accepted` + 四个 `Rejected_*`）。
3. 顺带补上 `Text(MotionCardState)` / `Text(MotionCommandResult)`，
   其中四种"被拒绝"各自说明**为什么**（未连接 / 不支持 / 参数非法 / 队列已满）——
   现场看到这四种该做的事完全不同。

视图侧改为 `DisplayMemberPath="DisplayName"`，悬停给出该方式的一句话说明
（如"撞到负限位后找第一个 Index 脉冲，精度最高，机台最常见"）。

另外把**未连接时列出全部 8 种方式**（原先留空）：空白下拉会让人以为功能不可用，

### 11.2 红框：排查过程与结论

截图里回零下拉是**空白 + 红框**。红框是 WPF 默认的校验错误模板，说明 `Validation.HasError = true`。

## 12. StackOverflowException：在「运动卡设置」里改轴参数必崩

现象：**在运动卡设置面板里改轴距/限位等参数时，进程直接消失**，
只留下一行 `System.StackOverflowException`，**没有堆栈**（这是 .NET 里唯一无法捕获的异常）。

### 12.1 排查路径（逐条排除，最后落在同步器上）

| 怀疑 | 检查 | 结论 |
| --- | --- | --- |
| 样式 `BasedOn` 自引用/成环 | 扫全部主题文件，构建 BasedOn 图并查环 | 19 条边、**无环无自引用** |
| 主题字典键重复 | 扫全部主题文件 | **285 个键全部唯一**（这条是上一轮刚修的，会启动即崩） |
| 属性/方法自引用 | 扫我改动过的 8 个文件 | 只有 `ToString() => DisplayName` 这类正常转发 |
| 事件订阅链 | 扫运动模块全部 `PropertyChanged +=` / `CollectionChanged +=` | `OnDevicesChangedHandler` 只刷新运行态 |
| `DataGrid` + 编辑 | 读 `DialogDataGrid` 样式、`AxisMapping` 模型 | 样式正常、模型是纯 POCO |
| **设备表同步器** | 读 `MotionProvider.EnsureSynced` / `SyncFromSolution` | **★ 命中** |

### 12.2 根因：同步器在"广播事件"之后才复位状态

```csharp
// MotionProvider.SyncFromSolution() 尾部（修复前）
   351:  DevicesChanged?.Invoke(this, EventArgs.Empty);      // 先广播
   352:  RememberSynced(...);                                 // 后清脏位/记方案引用
```

递归链（每一步都能在代码里对上）：

```
① 用户在表格里改参数 → VM 调 MarkConfigDirty() → _configDirty = 1
② 界面绑定读 row.Device（如"轴数"来自 Device.Capabilities.AxisCount）
        → MotionProvider.TryGetDevice → EnsureSynced()
③ _configDirty == 1 → 不满足早退 → SyncFromSolution()
④ SyncFromSolution 走到 L351 → 广播 DevicesChanged
⑤ MotionSettingsViewModel.OnDevicesChangedHandler → row.RefreshRuntime()
        → RaisePropertyChanged(nameof(Device))
⑥ WPF 绑定在 PropertyChanged 上是**同步求值**的 → 立刻读 row.Device
        → TryGetDevice → EnsureSynced()
⑦ ★ 此时 _configDirty 仍然是 1（RememberSynced 在 L352，代码还没走到）
        → 再进 SyncFromSolution → 回到 ④
```

栈一路加深，直到 `StackOverflowException`。

**为什么"改参数"是必崩的触发点**：表格用的是
`Binding="{Binding UnitsPerMm, UpdateSourceTrigger=PropertyChanged}"` —— **每次按键都写回源**，
于是每次都 `MarkConfigDirty`，也就每次都具备进入这条链的条件。

### 12.3 修复（两处，缺一不可）

**① 重入闸**（根本修复）：`EnsureSynced` 用 `Interlocked.CompareExchange` 挡住重入：

```csharp
if (Interlocked.CompareExchange(ref _syncing, 1, 0) != 0) return;
try { ...原有判据 + SyncFromSolution()... }
finally { Volatile.Write(ref _syncing, 0); }
```

同步期间再进来的调用**直接返回**：它想要的结果由**正在进行的那次**同步产生，不需要也无法重入。

**② 顺序**（语义修复）：把 `RememberSynced(...)` 提到 `DevicesChanged?.Invoke(...)` **之前**。
这样事件处理里那次 `EnsureSynced` 会因为"三个判据都不变"直接早退 ——
事件处理者看到的也才是"同步已完成"的一致状态。

### 12.4 同类隐患：相机 Provider 一模一样

`CameraProvider` 是同一套设计（`MarkConfigDirty` + 三个廉价判据 + `DevicesChanged`），
`EnsureSynced` 同样没有重入保护、`DevicesChanged` 同样在 `RememberSynced` 之前（L337/338）。
**已一并修掉** —— 它没崩只是运气（界面恰好没绑 `Device` 上的属性）。

### 12.5 为什么只能靠静态断言守住

`StackOverflowException` **无法被捕获**：写一个"复现测试"会把测试进程本身杀掉，
拿不到任何输出（连 `try/catch` 都进不去）。所以新增了 4 条**静态断言**（`MotionZMotionChecks`）：

- 两个 Provider 的 `EnsureSynced` 都含重入闸 `Interlocked.CompareExchange(ref _syncing, 1, 0)`；
- 两个 Provider 的 `SyncFromSolution` **方法体内** `RememberSynced(...)` 出现在 `DevicesChanged` 之前。

第二条刻意**限定在方法体内**比较：早退分支里也有一句 `RememberSynced`，
用全文 `IndexOf` 比会永远成立 —— 那样断言就白写了（这个坑在写的时候当场踩到）。

### 12.6 验证

```

```

新增 4 条断言全绿。**这个修复无法用探针自动验证**（见 12.5），
需要你复测一次：在运动卡设置里连续改几项轴参数（脉冲当量、软限位），确认不再崩。

## 13. 实测反馈的两个面板问题

### 13.1 「轴映射」表格是空的

现象：设置面板里的轴映射表**只有表头、没有数据行**（截图），而卡其实是连着的
（状态栏显示"已执行 0 已拒绝 0 故障 0"、以及"需要回零后才能运动"）。

根因在 `MotionCardRowViewModel`：

```csharp
public int AxisCount => Device?.Capabilities.AxisCount ?? Descriptor.Axes.Count;

public void ReloadAxes() => Descriptor.EnsureAxes(Math.Max(AxisCount, Descriptor.Axes.Count));
```

- 面板**打开时**卡通常还没连 → `Device` 为 null → `AxisCount` 退到配置里的条数（新方案是 0）
  → `EnsureAxes(0)` → **一行都不铺**；
- 之后点「连接」成功，但 `ToggleConnect()` **没有重建轴表** → 表格一直空着。

用户此时完全无从下手：连"脉冲当量填在哪儿"都看不到。

修复两处：

1. **`ReloadAxes` 加下限** `MinimumAxisRows = 4`：未连卡时也铺 4 行可编辑的轴
   （`EnsureAxes` **只增不删**，连卡后按机型能力补齐，用户已填的值不会被清掉）；
2. **`ToggleConnect` 结束后 `row.ReloadAxes()`** —— 连接/断开都会改变机型能力
   （如 VPLC532R = 32 轴），必须重建，否则用户看到的仍是打开面板那一刻的表。

### 13.2 点「开始回零」再点「失能」→ 界面卡死

两个原因叠加，缺一个都不会卡死：

**① 命令排不进去**：`MotionDeviceBase` 的命令线程逐条执行，而回零是长命令
（仿真器没接原点开关时一直跑到 120 秒超时）。「失能」按 FIFO 排在它后面，得等它跑完。

**② UI 线程在同步等**：`SetEnable` 走 `SendAndWait`，里面是 `command.Completion.Wait(timeout)`
—— **在 UI 线程上阻塞**最长 `CommandTimeoutMs`（30 秒）。界面就冻住了。

修复三处：

| 位置 | 改动 |
| --- | --- |
| `MotionDeviceBase` | 新增「**打断性命令**」：`Stop` / `Disable` 入队时立即打断正在执行的那条（`_emergencyCts.Cancel()`），但**不清队列** —— 与急停区分：急停是更重的路径（清队列 + 打断 + 停全部轴） |
| `MotionDebugViewModel.SetEnable` | 改为 `async`，`await Task.Run(() => SendAndWait(...))`，UI 不再被冻 |
| `MotionDebugViewModel` | 新增 `RunGuardedAsync` 兜底：这些命令处理器是 `async void`，**异常没有接收者、会直接崩进程**，必须包住 |

打断的 `Cancel()` 刻意放在**入队锁之外**：锁内取消会同步进入命令线程的取消回调，
与状态回填抢同一把锁 —— 等于自己等自己。

### 13.3 验证

```
通过: 844  失败: 15
```

新增 5 条断言（打断性命令登记 / 入队触发取消 / 取消在锁外 / 面板不同步等待 / 异常兜底）。

其中"取消在锁外"这条**第一版写错了**：用全文 `IndexOf` 拿到了别的方法里的同名判断，
报出 `取消@16878 / 拒绝处理@16133` 的假失败 —— 改为**限定在 `Enqueue` 方法体内**比较后正常。

### 14.3 "点击（上游节点）返回原有内容无响应"

现象：绑定弹窗里点上游节点 `Global`（高亮出现了），右侧"绑定上游输出端口"**列表空着**。

根因：`CanBindTo(object, double)` 判为不兼容 —— 而**全局变量的默认类型就是 `object`**。
用户选中一个 Double 输入端口后，所有全局变量都被类型过滤滤掉了。

`object` 的语义是"**运行期**才知道真实类型"（装箱值）。静态这层拦不住真正的错配
（真错了运行期会报），却会把"类型待定"的合法用法全部禁掉。改为**双向放行**：

- `object → 任意`：值可能装得下；
- `任意 → object`：装箱永远成立。

同时**反转**了 `PortBindChecks` 里那条旧断言（原为"object 不可绑"），并在注释里写明为什么反转 ——
否则下一个人会把它当回归改回去。

### 14.4 轴选择不直观

原来"轴""卡地址"是纯 string 参数（`[StepConfig]`）→ 属性面板渲染成**文本框**，
用户得先去别处翻配置、记住逻辑名、再回来敲，敲错要到运行期才报"没有名为 X 的轴"。

新增**动态候选下拉**（可复用机制，不是给运动插件特批的）：

| 件 | 位置 | 作用 |
| --- | --- | --- |
| `StepConfigOptionsAttribute` + `StepConfigOptionKind` | `Core.Interfaces` | 参数上标注"候选从哪来"（轴名 / 卡地址） |
| `StepConfigOptionSource` | UI 库 | 候选来源注册表：宿主注入 `kind → 候选列表` 的函数 |
| `OptionSourceGenerator` | UI 库 | 属性面板生成器：标了特性的 string 参数渲染成**可编辑 ComboBox** |
| 注册 | `CardPropertyGrid` / `FlatPropertyGrid` | 两个面板都要注册，漏一个就有一半场景仍是文本框 |
| 宿主注册 | `MotionModule.Initialize` | 从当前方案取，**只列已启用**的轴 |
| 插件标注 | 7 个运动插件 | `AxisName` / `CardKey` 各加一行特性 |

三个设计要点：

1. **候选运行期现取**（lambda 里解析方案），所以改了轴映射表、新加了卡，下次打开就是新的 ——
   不需要任何"刷新通知"机制；
2. **下拉可编辑**（`IsEditable = true`）：候选为空是常态（还没配卡、想试个名字），
   做成只读下拉会把用户堵死。下拉的价值是"把常见答案摆在眼前"，不是"禁止其它答案"；
3. **绑 `Text` 而不是 `SelectedValue`**：可编辑下拉只有 `Text` 会带上"用户手打的字"；
   绑 `SelectedValue` 时手动输入**不会写回**，等于把"允许手填"做成摆设。

顺带：`UI` 库加了 `Core.Interfaces` 的**直接**引用（原先只经 `VM.Core` 间接引用，
而传递引用不参与编译 —— 看不到那个特性类型）。

## 15. 修正：轴 / 卡必须同时是**输入端口**（否则流程里赋不了值）

用户看完代码指出：

> 你的轴控制插件有个问题，标注这个特性，在编辑流程的时候没有办法被赋值吧

**判断完全正确**，而且框架里写着答案：

```1:14:Shard/Core.Interfaces/StepConfigAttribute.cs
/// 标记插件的配置属性：参与 InputValues 持久化与实例灌值，
/// 但不暴露为端口（不进数据流、不可变量链接）
/// 适用于纯配置项（如采集模式、使能开关），与数据流端口（如图像路径）区分
```

再配合 `FlowCompiler.cs:L508` 的灌值顺序（"输入端口 + `[StepConfig]` 配置属性；**链接端口跳过、以链接为准**"），
结论很清楚：

| | `[StepConfig]` 属性 | `InputPort<T>` 端口 |
| --- | --- | --- |
| 属性面板填常量 | ✓ | ✓ |
| **被上游变量链接赋值** | **✗ 框架明确不支持** | **✓** |
| 绑定界面显示下拉 | 需要自己加生成器 | ✓ 原生（`IsFunctionalEnum` + `PresetOptions`） |

### 15.1 §14 那一步做偏了

§14 我做了 `[StepConfigOptions]` 特性 + 自定义生成器 + 候选提供器，
**解决的只是"在属性面板里把常量填得更方便"**，而用户的诉求是"**能赋值**" ——
两者不是一回事。而且框架**本来就有**对应机制：

```32:43:Shard/Core.Interfaces/DataPort/InputPort.cs
/// 是否为功能性枚举端口
/// 标记为 true 时，该端口会在变量绑定界面显示预设选项，不需要链接上游变量
public bool IsFunctionalEnum { get; set; } = typeof(T).IsEnum;
public List<string> PresetOptions { get; set; } = ...
```

**我另造了一套轮子**（并且新轮子还只能用在"常量"上）。§14 的产物保留（对"填常量"仍有价值），
但真正解决问题的是这一节。

### 15.2 修法：端口 + 常量，两者并存

给 7 个运动插件各加两个**可链接端口**（IO 插件只加卡）：

```csharp
/// <summary>（端口）逻辑轴名：可被上游变量链接；不链接时用手填值；都为空则回落到上面的常量</summary>
public InputPort<string> Axis { get; } = new InputPort<string>("Axis", "逻辑轴名（可链接；不链接则用轴名常量）")
{
    IsRequired = false,        // 老流程只填常量，不能因为没链接就判编译失败
    IsFunctionalEnum = true,   // 绑定界面显示为下拉（候选来自当前方案）
    PresetOptions = StepConfigOptionSource.GetOptions(StepConfigOptionKind.MotionAxisName).ToList(),
};
```

运行期统一"**端口优先、常量兜底**"：

```csharp
var cardKey = string.IsNullOrWhiteSpace(Card.ActualValue) ? CardKey : Card.ActualValue;
var axisName = string.IsNullOrWhiteSpace(Axis.ActualValue) ? AxisName : Axis.ActualValue;
```

三个要点：

1. **读 `ActualValue` 而不是 `Value`**：前者是"实际生效值"（取值优先级 **链接值 > 手填值**），
   后者只是"手动值"。读 `Value` 会让链接上去的值不生效 —— 那又白做了。
2. **`IsRequired = false`**：老流程只填常量、不连端口，若端口标成必填会在编译期被判失败 ——
   **已有流程必须一点不用改**。
3. **常量与端口共存**（而不是把常量改成端口）：端口是**新增**的，
   所以老流程的序列化配置、行为都不变；新流程想要动态轴就链端口。

顺带把 §14 的候选提供器从 UI 库移到契约层（`Core.Interfaces.StepConfigOptionSource`）——
插件的端口声明在契约层可见的代码里，要用它填 `PresetOptions`，而 UI 库对插件不可见。
