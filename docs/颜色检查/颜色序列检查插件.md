# 第 0 章 这是什么

**颜色序列检查 = "沿一条采样带扫出一串颜色，看看顺序对不对"。**

> 生活比喻：一排 10 根导线，颜色依次是「黑 白 灰 紫 蓝 绿 黄 红 玫红 棕」。质检要确认**顺序没错、根数没错**。人眼顺着数一遍就行；视觉里的做法是——沿**垂直于线束走向**的一条采样带扫过去，逐点取色 → 分段找出每根线 → 每根判成一个颜色词 → 拼成序列 → 与配方比对。

它在流程里的位置（归在 **「图像处理」** 分组）：

```
[图像采集] → [创建 ROI] → [图像预处理] → [颜色序列检查] → [C#脚本] / [CSV记录] / [结果上报]
                                        ↓
    Result(判定) / BadIndex(第几位不符) / Verdict(结论) / Expected(期望) / Count(根数)
    Sequence(序列) / Detail(逐根明细) / Rows(每根行号)
```

**一句话**：区域颜色检查解决"这块是什么颜色"，而 **颜色序列检查解决"这一串颜色的顺序对不对"**——典型场景：线序、排线、色带、色块标签。

## 0.1 抽象层级：插件不认识"线"这个词

本插件是从"线序检测"脚本抽象出来的，但抽象层级选的是**通用「颜色序列检查」**：沿一条采样带取一维颜色序列 → 与配方比对。

好处：**线序、色带、排线、色块标签都能用同一个节点**。

## 0.2 ⚠️ 采样区的几何约定（务必先读）

采样区是一个**矩形**（`RoiParams` = `[中心行, 中心列, 角度(弧度), 半长, 半宽]`）：

| 方向 | 是什么 |
|---|---|
| **长轴**（半长大的那条） | **线束走向**（沿着线排开的方向） |
| **短轴** | **采样剖面方向**（扫过每根线的方向） |

> 长轴自动判为线束走向：半长大的那条轴。**用户把框竖着画也能用**。
> 序列索引 0 是**坐标较小的那一端**；要反过来看就勾「序列反向」。

# 第 1 章 设计思想

## 1.1 核心原理：先抓可靠的，再按间距铺开

这是整个算法最关键的立意，务必理解：

> **白线（V≈240）与浅色背景（V≈235）只差几个灰阶，颜色上根本不可分。**
> 任何"找边界"的思路（阈值分割、边缘、变化点检测）到了白线这里都会断。
>
> 所以骨架必须是：**抓得到的先抓（暗 / 彩 / 极亮），由它们的间距估出线距，再把整条链按等间距铺开** —— 抓不到的那根就被补回来了。

```
采样带剖面（逐点亮度和彩度）
   ↓  ① 自适应算三个阈值（暗线 / 白线 / 彩度）
   ↓  ② 找"可靠像素"连续段（暗 / 彩 / 极亮）
   ↓  ③ 由段间距 + 自相关 估出"线距"
   ↓  ④ 最小二乘回归定锚点（相位 + 端点）
   ↓  ⑤ 按等间距铺满整束（补出看不见的线）
   ↓  ⑥ 逐根取色 → 颜色词
黑,白,灰,紫,蓝,绿,黄,红,玫红,棕
   ↓  ⑦ 与配方逐位比对
合格 / 第 N 根不符 / 根数不符
```

## 1.2 三处"自适应"替换掉了脚本版的写死阈值

| 脚本版（写死） | 本插件（自适应） | 为什么 |
|---|---|---|
| 暗线阈值写死 150 | **众数亮度 − DarkSpanRatio ×（众数 − 2% 分位）** | 换一盏灯就要重新试 |
| 端部靠"第一个可靠段"当起点 | **最小二乘回归定锚点** | 端部漏检会**整条序列错位一格** |
| 手动给线距 | **自相关 × 分段线距交叉验证** | 自相关单独用会给出 16 而真值是 21.5 |

> 暗线判据口径（最要紧的一条）：
> - 缝/背景的水平取剖面的**众数**（剖面里最常见的那个亮度，就是缝或背景）；
> - 最暗的线像素取 **2 号百分位**（不用最小值：一个坏点就能把尺度拉跑）；
> - 判定线放在两者之间往下 `DarkSpanRatio` 的位置。
>
> 实测两张样本图的安全窗口是 100~160，这个口径给出 **154 与 114**，都落在窗口里。而脚本版那个写死的 150 只是**碰巧**落在这个窗口里。

## 1.3 线距到底谁说了算（按实测数据定的，不是按直觉）

自相关与分段线距会打架，仲裁规则：

| 情况 | 听谁的 |
|---|---|
| 两者接近（差在 25% 以内） | **取平均**，互相消噪 |
| 分段线距正好是自相关的整数倍（≥1.6 倍） | **信自相关**——那正是"漏检一半致使中位间距变成两倍"的典型情形 |
| 其余不一致 | **信分段线距**（实测样本图上自相关会给出 16 而真值 21.5，这时候听它的反而错） |

## 1.4 判定口径：配方缺失 ≠ 产品不良

> 配方缺失（根数对不上任何一条）时**直接报错让流程停住**，不判成 NG：
> 配方没配是**工程配置问题**，不是产品不良——判成 NG 的话，一条配错的线会永远把良品报成 NG，而现场只会以为"这批产品有问题"。

这一点与脚本版（走 Else 判 NG）是**有意不同**的。

## 1.5 期望词先过词表再比对

> 比对是按字面做的，词表外的词（"深红"这种）永远匹配不上，只会默默地把那一位判 NG——现场看到的结论是"应为 深红、实测 红"，根本想不到是配方写错了。**配置问题就该按配置问题报**。

# 第 2 章 技术特点

## 2.1 元数据

| 特性 | 值 |
|---|---|
| `Name` | 颜色序列检查 |
| `GroupName` | 图像处理 |
| `Description` | 在采样区里取一维颜色序列（线序 / 色带 / 排线通用），后续与配方比对 |
| `ShortName` | 图标（FontAwesome `f53f`） |

## 2.2 端口完整清单（全部固定端口，无动态端口）

### 输入

| 端口 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `Image` | HImage | ✖ | 待检查图像 |
| `ExpectedSequence` | string | ✖ | 期望序列（可选）：**填了就以此为准，不再查配方表**——留给"配方从数据库/工单取"的场景 |

> `ExpectedSequence` 为什么用 string 而不是枚举：枚举端口经 `InputValues` 往返会抛 `InvalidCastException`。

### 输出（8 个）

| 端口 | 类型 | 说明 |
|---|---|---|
| `Result` | bool | 判定结论（true = 合格） |
| `BadIndex` | int | **第几位不符（1 起）；0 = 全对或根数不符** |
| `Verdict` | string | 结论全文 |
| `Expected` | string | 本次比对用的期望序列（回显，便于排查"到底比的哪条配方"） |
| `Count` | int | 根数 |
| `Sequence` | string | 颜色序列（逗号分隔），如 `黑,白,灰,紫,蓝,绿,黄,红,玫红,棕` |
| `Detail` | string | 逐根明细：`序号+颜色+来源（检/补）`，如 `1黑检,2白检,3灰补,…` |
| `Rows` | string | 每根线中心的图像行号（逗号分隔），结果投射时用来贴标签 |

另有基类隐式端口 `Success`、`ErrorMessage`。

## 2.3 配置项

### 采样几何与主旋钮（日常只用前两个）

| 配置 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `RoiParams` | `double[]` | 空 | 采样区：`[中心行, 中心列, 角度(弧度), 半长, 半宽]` |
| `ReverseSequence` | bool | `false` | 序列反向：首尾对调（线束摆放方向相反时用） |
| `WireCount` | int | `0` | 手动指定线数；**0 或负数 = 由算法自动反推** |
| `Regularize` | bool | `true` | **等间距规整化**：开 = 按估出的线距铺满整束（能补出看不见的白线）；关 = 只报看得见的线 |

### 高级参数（Expander 折叠）

| 配置 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `DarkSpanRatio` | double | `35` | 暗线判据幅度（占"众数亮度到最暗像素"这段跨度的百分比） |
| `BrightPercentile` | double | `92` | 白线百分位：亮度高于该百分位的算可靠线像素 |
| `MinRun` | int | `4` | 最小段长：连着这么多行都可靠才算一根线 |
| `MaxRunRatio` | double | `0.33` | 最大段长比例：长过剖面长度这个比例的可靠段按背景丢弃 |
| `RuleWindowRatio` | double | `0.30` | 规整补色时的窗口半宽（线距的比例） |
| `ExtendEnds` | bool | `true` | 端点外推：允许在检出范围两端各多探一根 |

> 这些参数都是**无量纲的比例或百分位**，不是绝对灰阶值——换灯、换工装改的是尺度，比例大体不变，**这正是"自适应"的意义所在**。

### 颜色判据阈值（13 项）

与区域颜色检查**完全相同的一套**（`ColorlessSaturation 0.45` / `BlackValue 80` / `WhiteSaturation 0.15` / `WhiteValue 195` / `BrownWarmth 12` / `BrownValue 175` / `RoseHueFrom 330` / `RedHueFrom 350` / `RedHueTo 20` / `OrangeHueTo 45` / `YellowHueTo 70` / `GreenHueTo 160` / `BlueHueTo 230`）。

> 为什么每个算子各存一份而不是全局一份：不同工位/产品的打光与材质不一样，"玫红从哪里算起"本来就可能不同；全局一份会变成束缚。

### 配方与投射

| 配置 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `RecipeText` | string | 空 | 配方表：一行一条「产品名 = 颜色1,颜色2,...」，`#` 开头是注释。运行时按**实测根数**匹配 |
| `DisplayViewIndex` | int | `1` | 结果投射到哪个视图窗口（1~9；**0 = 不投射**） |

## 2.4 HALCON 算子清单

**插件内部直接调用的只有两个 HImage 方法**：

| 调用 | 作用 |
|---|---|
| `image.CountChannels()` | 判通道数，`< 3` 直接报"颜色序列检查要彩色图" |
| `image.GetImageSize()` | 取图像尺寸（采样点越界检查、投射夹取） |

**真正的取色在内核**，走**元组版 `get_grayval`**（`Core.Halcon/Color/ColorSampler.cs`）：

```csharp
HOperatorSet.AccessChannel(image, out HObject channelObject, ci + 1);
HOperatorSet.GetGrayval(channelObject, rowsTuple, colsTuple, out HTuple values);
```

> **分工**：内核负责"给点取色"，算子负责"点怎么来"。颜色序列检查自己算采样线的点，区域颜色检查让内核把 ROI 变成区域再抽样，两者的取色走同一条路。
>
> 取色一律走元组版：一次调用拿回整批点，比逐点调用快两个数量级；也不必把通道包成 HImage 去管句柄（那条路上踩过 HALCON `#4056 object-ID is NULL`）。

**明确没有用到的算子**：`reduce_domain`、`decompose3`、`trans_from_rgb`、单点版 `get_grayval`、`gen_rectangle1`、`smallest_rectangle1`、`select_shape`、`sort_region`、`tuple_*`。

> 颜色空间也没有用 HALCON 转换——HSV 语义是纯 C# 算的：`mx = max(R,G,B)` 当明度 V，`chroma = mx − min` 当彩度，`s = d/mx` 当饱和度。

## 2.5 性能与独特实现

| 手段 / 设计 | 做法 | 收益 |
|---|---|---|
| **自适应阈值** | 众数 / 2% 分位 / 大津法 | ⭐⭐⭐ 换灯不用重调 |
| **回归定锚** | 最小二乘迭代拟合 | ⭐⭐⭐ 端部漏检不再整条错位一格 |
| **自相关 × 分段交叉验证** | 三条仲裁规则 | ⭐⭐⭐ 线距估得稳 |
| **5 条采样线取中位** | 偏移 ±4 px，不摊开 | ⭐⭐ 抗单点噪声；且不会把扇形散开的边界线洗掉 |
| **等间距规整 + 端点外推** | 补出看不见的白线 | ⭐⭐⭐ 白线与背景不可分也能检 |
| **中位色掐掉上下各 1/4** | `MedianRgb(trimmed)` | ⭐⭐ 避开线两侧的暗缝 |
| **高位深归一** | >255 等比压回 8 位 | ⭐⭐⭐ 12/16 位相机不会整段失效 |
| **配方缺失报错而非判 NG** | 工程配置问题按配置问题报 | ⭐⭐⭐ 不会永远把良品报成 NG |
| **推图失败不影响判定** | `catch {}` | ⭐⭐ 投递只是锦上添花 |

# 第 3 章 使用方式

## 3.1 安装与启用

1. **无需单独安装**：正常编译解决方案即产出 `Modules/Plugin.ColorCheck.dll`。
2. 依赖 HALCON 原生库。
3. 重开软件，工具箱里出现「颜色序列检查」（**图像处理** 分组）。

## 3.2 配置界面总览（两列）

```
┌──────────────────────────┬────────────────────────────┐
│ 左：参数（330px 可滚动）     │ 右：图像编辑器 ImageEdit     │
│  ① 图像输入（🔗链接上游）    │  ← 右键 → 新建矩形采样区      │
│  ② 采样区（+ 清空按钮）      │                            │
│  ③ 检查参数                 │                            │
│     序列反向 / 线数 / 规整化  │                            │
│     「试算一下」+ 结果框      │                            │
│     高级参数（Expander）     │                            │
│  ④ 配方（多行文本框）        │                            │
│     「把试算结果存成配方」     │                            │
│  ⑤ 怎么用                  │                            │
└──────────────────────────┴────────────────────────────┘
```

## 3.3 第一次检查（4 步）

**第 1 步｜接图**：左栏「图像输入」点 🔗 绑定上游（或画布拖线）。点「执行」试运行后上游图自动上屏。

**第 2 步｜画采样区**：右侧图上**右键 → 区域 → 新建矩形**，框住线束。

> 长轴自动判为线束走向（半长大的那条），**竖着画也能用**。
> 第一次点「执行」会报「尚未框选采样区」——那是对的。

**第 3 步｜试算**：点「试算一下」，结果框显示根数、线距、阈值、来源、期望、判定。

**第 4 步｜存配方**（**推荐一键**）：点「把试算结果存成配方」→ 自动生成 `10 芯 = 黑,白,灰,紫,蓝,绿,黄,红,玫红,棕`。

> 💡 手打颜色词必须**正好**落在词表里（写成"深红"永远匹配不上）。拿一张已知良品的图点一下试算、再点一下这个按钮，就不会犯这个错。

## 3.4 参数调节速查表

| 现象 | 调哪里 |
|---|---|
| 根数少了 | 勾上「等间距规整化」（`Regularize`）；开「端点外推」（`ExtendEnds`） |
| 根数多了（检到不该检的） | 关「规整化」做对照；调 `MinRun`（最小段长）调大 |
| 序列反了 | 勾「序列反向」 |
| 线数已知、想强制 | 填「线数」（`WireCount`），0 = 自动反推 |
| 白线检不到 | 调 `BrightPercentile`（默认 92，可降到 85 左右） |
| 暗线判据不对 | 调 `DarkSpanRatio`（默认 35；实测安全窗口对应阈值 100~160） |
| 长段被误当成线 | 调小 `MaxRunRatio`（默认 0.33） |
| 12/16 位相机整段失效 | 已自动等比归一（日志会留说明） |
| 只要顺序不要判定 | 配方里该位写 `*` |

## 3.5 FAQ

**Q1** 明明细上有 10 根，为什么只报 8 根？
白线与浅背景只差几个灰阶，颜色上不可分。本插件的做法是"先抓可靠的（暗/彩/极亮），估出线距后按等间距铺开补回"。确认勾上了「等间距规整化」。

**Q2** 关掉规整化会怎样？
只报看得见的线（每一段就是一根，不铺开不外推）——这是**调参时的对照组**。

**Q3** 配方没配会怎样？
**报错让流程停住**，不判 NG。配方没配是工程配置问题，不是产品不良。

**Q4** 同一节点能适配不同芯数吗？
能。运行时按**实测根数**匹配配方（期望序列的长度就是这条配方要求几根）。5 芯图换上去会自动换配方。

**Q5** `BadIndex = 0` 是什么意思？
要么**全对**，要么**根数不符**（长度对不上时无从谈"第几位"，所以给 0）。

**Q6** 明细里的「检 / 补」是什么？
`检` = 命中了可靠段（真正看到了）；`补` = 按等间距规整补出来的（没看到但按线距推出来的）。画面上补出来的那几根标**橙字**，让你一眼看出哪几根是算出来的。

**Q7** 为什么不能拿"连接器"当反例？
连接器上有一排金属触点，它们本身就是等间距的暗块，算法会理所当然地把它们当"线"报出来——**那不是 bug，是采样区画错了地方**。真正的反例是纯背景。

## 3.6 现场排障

| 报错 / 现象 | 排查 |
|---|---|
| "尚未框选采样区" | 没画矩形。右键 → 新建矩形 |
| "颜色序列检查要彩色图，当前图像只有 N 个通道" | 输入是灰度图 |
| "采样区超出图像范围" | 框画到图外了 |
| "采样区的短边只有 N 个像素，太窄了" | 短轴太小（点数 < 8） |
| "采样区里几乎没有明暗变化…多半框到空白背景上了" | 对比度下限闸（亮度极差 < 25 级）挡下了，框对位置 |
| "只找到 N 段可靠线，凑不出线距" | 段数 < 2，放宽 `DarkSpanRatio`/`BrightPercentile` 或检查框的位置 |
| "未知产品" / 配方缺失 | 根数对不上任何一条配方，补配方 |
| "期望里认不出的词" | 配方里写了词表外的词（如"深红"） |
| 根数/顺序不对 | 先看试算里的线距与阈值，再对照 3.4 表调 |

## 4.2 P0/P1 级详解

### ① 采样线不能沿长轴摊开（实测踩到）

**现象**：第 10 根棕线丢失，根数直接少两根。

**原因**：实测样本图里的线束是**扇形散开**的（连接器在一端，线向另一端散开），同一根线在不同列上的行号能差十几像素；把采样线按 10/30/50/70/90 百分比摊开后**按行号合并**，会把只在个别列上明显的边界线洗成背景。

**修法**：改成 **5 条采样线，长轴只偏移 ±4 像素**（`{-4,-2,0,2,4}`），同一短轴位置取**中位**合成一条剖面。抗单点噪声靠"几条邻近线取中位"已足够，不需要摊开。

### ② 端部漏检 → 整条序列错位一格

**现象**：端部那根线漏检后，**整条序列错位一格**（而不只是少一根）。

**原因**：脚本版拿"第一个可靠段"当起点。

**修法**：改成对可靠段中心做**最小二乘回归**定锚点（迭代 2~3 轮即稳定），再外推覆盖整束。端部漏检只会**少一根**，不会整体错位。

### ③ 自相关零延迟陷阱 + 倍频

**现象**：直接取自相关全局最大值会给出 **3 像素**这种荒唐线距；真周期 p 的整数倍也是峰。

**修法**：
- **先等它衰减过零，再取第一个显著峰**（过零之后的第一个峰才是主周期）。
- 拿分段线距当参照（hint），在峰候选里挑**最贴近它的那个**（防倍频）。
- 信号选**边缘强度**（亮度差 + 彩度差的绝对值）而不是亮度本身——每根线的上下两条边界都会冒一个尖，于是信号周期正好等于线距；而亮度本身会被"黑线 vs 白线"的颜色差异压住，周期反而看不出来。

### ④ 自相关单独信不得（仲裁规则）

**现象**：实测样本图上自相关给出 16，真值是 21.5（边缘信号容易被线宽变化和斜线干扰）。

**修法**：三条仲裁规则（见 1.3）——接近取平均；分段线距是自相关整数倍时信自相关；其余信分段线距。

### ⑤ 高位深相机整段失效

**现象**：12/16 位相机图上，暗线判据整段失效、黑白灰棕全错。

**原因**：判据（暗线判据的众数/百分位、大津法直方图、明度阈值黑80/白195）**全是按 8 位标定的**。

**修法**：实测最大灰度 > 255 时等比压回 0~255（`k = 255.0/max`），并把说明塞进 `Warnings`。等比缩放不动色相与饱和度（它们是比值），颜色词答案不变。

## 5.3 附录 C：实战案例（算法思路，可直接照此理解/复现）

### 案例 1｜为什么不能"找边界"——白线与浅背景不可分

```
实测：白线 V≈240，浅色背景 V≈235 —— 只差 5 个灰阶，颜色上根本不可分。
任何"找边界"的思路（阈值分割 / 边缘 / 变化点检测）到这里都会断。

正确骨架：
  ① 抓得到的先抓：暗（V < 暗线阈值）/ 彩（chroma > 大津阈值）/ 极亮（V > 白线百分位）
  ② 由这些可靠段的间距估出"线距"
  ③ 按等间距把整条链铺开 → 抓不到的那根（白线）就被补回来了
```

### 案例 2｜暗线阈值自适应（别写死 150）

```
众数亮度  = Mode(剖面亮度)          ← 缝/背景的水平
最暗像素  = Percentile(亮度, 2%)    ← 不用最小值：一个坏点就能把尺度拉跑
暗线阈值  = 众数 − DarkSpanRatio% × (众数 − 最暗)

实测两张样本图的安全窗口是 100~160：
  本口径给出 154 与 114（都落在窗口里）
  脚本版写死的 150 只是"碰巧"落在窗口里 —— 换一盏灯就要重新试
```

### 案例 3｜线距：自相关 × 分段线距交叉验证

```
自相关信号 = 边缘强度（|亮度差| + |彩度差|）
   ↑ 每根线的上下两条边界都会冒一个尖 → 信号周期 = 线距
   ↑ 若用亮度本身，会被"黑线 vs 白线"的颜色差异压住，周期看不出来

找峰：先等它衰减过零，再取第一个显著峰
   ↑ 直接取全局最大会给出 3 像素（零延迟附近自相关天然最高）
   ↑ 用分段线距当 hint，在候选峰里挑最贴近的（防倍频 p, 2p, 3p…）

仲裁：
   两者接近（差 <25%）→ 取平均
   分段线距 ≈ 自相关 × N（N≥1.6）→ 信自相关（那是"漏检一半致间距翻倍"）
   其余 → 信分段线距（实测自相关给 16，真值 21.5）
```

### 案例 4｜相位与端点：回归定锚（防整条错位）

```
✗ 脚本版：拿"第一个可靠段"当起点
     → 端部那根一旦漏检，整条序列错位一格
✓ 本插件：对可靠段中心做最小二乘回归，迭代 2~3 轮定出锚点与线距
     → 端部漏检只会少一根，不会整体错位

端点外推判据：这一格附近"有没有起伏"
     → 一根线必然带来"亮-暗"的局部起伏；线束外的平坦背景没有
     → 用"局部起伏 ≥ 全局起伏的 20%"当证据（不要求认出颜色，只要求"那里有东西"）
```

### 案例 5｜逐根取色：中位色要掐头去尾

```
取每根线区间内的中位 RGB 时，掐掉上下各 1/4（trimmed）
   → 避开线两侧的暗缝，否则取到的中位色会偏暗

再交给 ColorVocabulary.Classify 判成颜色词
   → 黑 白 灰 棕 红 玫红 橙 黄 绿 蓝 紫

来源标记：命中可靠段 = 「检」；按线距补出来的 = 「补」
   → 画面上补的那几根标橙色
```

### 案例 6｜配方比对与三类结论

```
配方格式（一行一条）：
    产品名 = 颜色1,颜色2,颜色3
    # 井号开头是注释；空行忽略
    不带等号的行 → 整行就是颜色序列，产品名自动取「N 芯」
    某一位写 * → 这一位不检

匹配：按【实测根数】匹配（期望序列长度 = 这条配方要求几根）
     同芯数多条 → 取第一条并 Warn
     ExpectedSequence 端口有值 → 端口优先，不查配方表

三类结论：
    合格        → 线序正确
    第 N 位不符 → 线序错误：第 N 根应为 X、实测 Y
    根数不符    → BadIndex = 0，结论含"根数不符"

配方缺失 → 【报错停流程】，不判 NG（工程配置问题 ≠ 产品不良）
期望词不在词表 → 【报错】（词表外的词永远匹配不上，会悄悄判 NG）
```

## 5.6 附录 F：术语表

| 术语 | 含义 |
|---|---|
| 采样剖面 / Profile | 沿短轴扫过去的一条"亮度 + 颜色"序列 |
| 长轴 / 短轴 | 长轴 = 线束走向（半长大的那条）；短轴 = 采样方向 |
| 可靠像素 | 暗 / 彩 / 极亮——三种"抓得到"的像素 |
| 线距（Pitch） | 相邻两根线的间距（由自相关 × 分段交叉验证估出） |
| 规整化（Regularize） | 按估出的线距把整条链等间距铺开（能补出看不见的线） |
| 「检」/「补」 | 命中可靠段 = 检；按线距推出来 = 补（画面上标橙字） |
| 众数亮度 | 剖面里最常见的亮度（代表缝/背景的水平） |
| 2 号百分位 | 最暗的线像素（不用最小值，防坏点拉跑尺度） |
| 大津法（Otsu） | 自动求"彩度"阈值的经典方法 |
| 自相关 | 用信号与自身的延迟相关性找周期（这里找线距） |
| 回归定锚 | 最小二乘拟合可靠段中心，定出相位与端点 |
| 配方 | 一行一条「产品名 = 颜色序列」，按**根数**匹配 |
| `*` 通配位 | 配方里该位不检 |
