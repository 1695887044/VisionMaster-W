## 一、R3 最终裁决

### 1. Web 写变量触发流程：**已封（2026-10-22 追加落地）**

- 红队给出的路径成立：`cmd.input` → `ScadaValueWriter.TryWriteText` → 变量 `ValueChanged` →
  `FlowVariableTriggerService.Evaluate`（`Engine/FlowVariableTriggerService.cs:156-169`）→
  `FlowAutoRunner.RunOnce` → 流程里的运动步骤。只排除 `StartFlow/RunFlowOnce/ResumeFlow`
  封不住这条路。
- **最终裁决**：按架构师方案追加落地流程触发闸——
  `IScadaFlowTriggerQuery`（`VM.Scada`）+ `ScadaFlowTriggerQuery`（宿主，判据逐字复刻
  `FlowVariableTriggerService` 的启用 + `InvokeType.Variable` + `TriggerVariable.Trim()` 相等）；
  路由在 `HandleInput` 写入前与 `HandleElement` 的 `WriteVariable` 动作派发前拒绝，
  新码 `E_FLOW_TRIGGER`；guard 未接线时 **fail closed**（`E_INTERNAL`）。
- **验证**：M2-13f（`cmd.element` 写触发变量 → `E_FLOW_TRIGGER`、分发 0）、
  M2-13g（`cmd.input` 写触发变量 → `E_FLOW_TRIGGER`、写入 0）；`ScadaWebChecks` **119/0**。
- **现场口径**：A 范围现在保证“Web 没有直接的运动/停止入口、不能启动流程、
  不能写流程触发变量”；若现场确实需要 Web 写触发变量，必须显式关闭 `AllowCommands` 或改流程触发配置。

### 2. `clientInstanceId`：**不进幂等键，只作审计/诊断**

- 键保持 `(sessionToken ?? sessionId) + \u001F + requestId`（`ScadaWebCommandRouter.cs:182/1248`）。
- 理由：requestId 是 `crypto.randomUUID()`（`app.js`），撞号不是现实风险；进键会破坏
  “断线重连后同 requestId 找回结果”；客户端没有一种存储能同时满足“每标签独立 + 刷新不变”。
- 第一批未实现审计字段；下一批如需要，放 `sessionStorage["scada.clientInstanceId"]`。

### 3. 结果查询：**设计冻结为 WS `cmd.result`，第一批未实现**

- 请求：`{"type":"cmd.result","id":"q1","targetRequestId":"c7"}`；响应用新 `type:"result"`，
  不带 `ok`，避免被前端当 `ack`；查询在 `HandleTextFrame` 直接答，不入泵、不过版本闸、不过审计 fail-closed。
- `Dedup` 增加只读 `TryPeek`（不得像 `Check` 那样删过期项）。
- 边界：撤销即关连接，**撤销后不可查**；查询只覆盖“ack 丢但连接还在”。
- 第一批未实现：客户端目前不自动重试同 requestId，没有消费者；留到下一批与客户端一起做。

### 4. 分片：**设计冻结为字符串切片，第一批未实现；先把 WS 上限放宽到 4MB**

- 形状：`{"type":"snapshot.chunk","snapshotId","index","total","data","bytes","pageId","pageVersion","runGeneration"}`；
  `data` 是整份 JSON 的片段，客户端在 `handleRawMessage` 拼接后 `JSON.parse`；
  分片期间暂停该会话 `frame`；5s 超时/乱序作废并 resync。
- **第一批的替代措施**：把 Watson `WebSockets.MaxMessageSize` 从 64KB 放宽到 4MB
  （出站快照 3000 图元约 1.5–1.8MB），并在 `HandleTextFrame` 增加 64KB 入站命令帧硬上限
  （`MaxInboundCommandBytes`）。这能让大页面先跑起来，但没有解决 1.5MB 单条消息的
  `JSON.parse` 阻塞与 HOL；分片仍是下一批。
- 红队指出的 UTF-16 代理对切断问题：分片实现时必须按 Rune 边界或 base64，不得逐片 UTF-8 编码。

### 5. 默认值一致性：**第一批不做**

- 23 个渲染器没有 `defaults` 声明，拿 `/api/catalog` 比对是假绿。
- 下一批入口：先给渲染器加 `factory.defaults`（或集中 `renderer-defaults.js`），
  再在 `ScadaChecks\RenderCatalogChecks` 做静态比对，例外清单只许变短。

## 二、红队终审的反对意见（保留）

红队结论是 **fail**，理由：
- 只排除流程启动封不住 `cmd.input` 的变量触发旁路（成立，已登记为残余 P0）；
- `clientInstanceId` 进键没有可靠存储方案（采纳：不进键）；
- WS 结果查询在被踢场景不可用，`Dedup.Check` 会删表（采纳：查询用 `TryPeek`、撤销后不可查；第一批未实现）；
- 只含 pageKey 会跨轮命中（采纳：键加 runGeneration）；
- 字符串分片按 UTF-16 码元切会破坏代理对（采纳：实现时必须按 Rune/base64；第一批未实现）。

**红队的“必须放弃”建议中，第一批采纳了**：`clientInstanceId` 不进键、默认值一致性闸不做、
结构分片不做、结果查询延后。**未采纳**的是“砍掉增量帧”：增量帧 + keyframe + baseline-on-success
已通过 117 条断言，且是 1000 绑定 10Hz 带宽目标的唯一出路；砍掉它等于把 128Mbps 留在原地。

## 三、架构师与宿主角色的分歧

- 架构师主张第一批做“安全 + 多基座 + 查询 + 45s + 覆盖度”，把缓存/增量/预算/分片全砍；

- **主会话裁决**：两条线的交集（多基座、A 范围、覆盖度）全做；数据面取“缓存 + 增量 + 预算”
