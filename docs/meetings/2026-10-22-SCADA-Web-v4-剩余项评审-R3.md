## 一、`cmd.result` 的最终状态机（R2 §四-1）

### 裁决

**不引入 `Reserved → Running → Done` 三态，直接用"条目在不在 + result 是否为 null"表达三态。**

### 理由（逐条引用代码）

1. `ScadaWebCommandRouter.Handle` 在真正执行前就调 `Dedup.Check`（`ScadaWebCommandRouter.cs:191`），
   而 `Check` 在条目不存在时会**先登记**（`FirstSeenUtc`），执行完再 `Complete` 写入结果（`:232`）。
   因此"条目存在 + `result == null`"天然就是 `running`，不需要额外的状态字段。
2. reviewer 在 R2 担心的"`Begin` 占位吞命令"因此**不存在**：本批没有新增 `Begin`，
   `Check` 的 `Cached` / `Expired` 分支一字未改，重复请求的语义与第一批完全一致。
3. `TryPeek` **只读不删**（`ScadaWebCommandRouter.cs` 新增方法）：这是"查询不能毁掉幂等证据"的硬要求。
   如果查询顺手删条目，随后同 `requestId` 的重试会变成"新命令"再执行一遍——正好毁掉幂等表。
4. 响应 `type:"result"`、`id`（查询自身）、`targetRequestId`、`state`，**不带 `ok`**：
   它不是 ack，客户端不能拿它当命令结算（`ScadaWebHost.HandleResultQuery`）。
5. reviewer 在 R2 的反对条件是"没有客户端持久化/在飞状态时，服务端先做就是死代码"。
   本批**客户端查询同批落地**（`app.js` 的 `queryCommandResult` / `sendResultQuery`），
   条件已满足，反对意见消解。

### 落地证据

- `M2-13h`：执行成功 → `TryPeek` 首查/复查都命中且 `Ok`；未知 id 返回 false；查询不删条目。
- `B54` / `B54b`：主宿主（`AllowCommands=false`）也能答；未知 id → `unknown`、无 `ok`；缺 `targetRequestId` → `E_BAD_REQUEST`。

### 明确不做

- **不做自动重发**。重发必须复用原 `requestId` 并等 `AckWindow` 内的原回执；
  换 id 重发会把已执行的命令再执行一遍（这是查询存在的全部意义）。
- **不做客户端 `localStorage` 持久化**。本批的查询只覆盖"连接还在、ack 丢了"；
  跨刷新/跨重连的在飞命令需要服务端按 `sessionToken` 查，属于下一批（与控制通道一起）。

## 二、24 槽准入（R2 §四-1 后半）

### 裁决

**做，但按 reviewer 的"防双减"要求实现为幂等闸，不用"同 token 接管"替代。**

### 理由

1. **只按活跃数判容量有一个真实窗口**：取票（HTTP）与 WS 入册是两次往返。
   16 个活跃时第 17 个客户端仍能取票成功（`HandleTicket` 只判 `MaxSessionTokens`），
   票被核销后却进不了 WS——它拿到的是一枚"已经死掉"的 8 小时令牌。
   预留槽让"在途握手"有独立预算，活跃仍严格 ≤ `MaxSessions`。
2. **reviewer 的"同 token 接管"不能替代**：接管改变的是"同一账号多标签页"的语义
   （旧连接被踢），而这里要解决的是"握手在途"的容量表达；两者混在一起会让
   重连风暴时正常标签页互相踢下线，风险更大。
3. **防双减**：`ScadaWebAdmissionGate.ReleaseActive` 减到 0 为止、`ReleaseHandshake` 对不存在
   的票是空操作；`TryPromote` 在锁内"先移除握手项、再判活跃"，失败时预留已被消耗
   （票已核销，留着也没有下一次机会）。
4. **5 秒 TTL**：握手失败/客户端中途放弃时 `HandleWebSocket` 根本不执行，没有机会显式释放；
   在线列表循环每拍先 `SweepExpired`（`RunPresenceLoopAsync`），再清 45 秒死连接。

### 落地证据

- `B55`：8 个握手槽满后第 9 个被拒；8 个晋升后活跃 8；第二批 8 个再晋升到 16；
  活跃满时仍可占握手槽，但第 17 个活跃转不过去；释放一个后立刻可晋升。
- `B55b`：5 秒 TTL 清掉 2 个预留；TTL 后晋升失败；`ReleaseActive` 连调三次只减一次。
- `B55c`：正常连接关闭后 `AdmittedCount` 与 `HandshakeCount` 都归零（集成反证）。
- `B56` / `B56b`：`MaxSessions=1` 时第二个客户端**能通过握手**（预留槽生效），
  但入册被 **WS 1013 + bye** 拒绝（不是 HTTP 503——503 会被前端渲染成"登录失败"）；
  第一个连接关闭后两本账归零。

### 边界

- 取票阶段**不**按活跃数拒绝（否则 16 活跃 + 1 在途会把正常重连挡在 HTTP 401）。
- 预留失败（8 个在途）仍回 401：Watson 7.2.0 的 `AuthResult` 没有 503 语义（既有注释已说明）。
  这种情况下回收"本次新签"的会话令牌，续期票沿用的令牌不回收（与既有容量拒绝同口径）。

## 三、分片 / `view.resync` / 控制通道（R2 §四-2）

### 裁决

**确认延后，作为一个不可拆的单位。**

### 理由

1. 字符串分片不降低 `JSON.parse` 成本（最终仍要拼回整串解析一次），只降低 HOL；
   没有 `view.resync` 时，分片丢失一半会让页面停在半结构状态，比不分片更糟。
2. 没有控制通道时，大快照的 ack 队头问题无法根治；单独做分片等于把风险从"一条大消息"
   变成"多条消息的组装状态机"，故障面更大。
3. 现有硬闸已经把单份快照限制在 3.5MB（`EffectiveSnapshotMaxBytes`），
   3000 图元实测 1.5–1.8MB，4MB WS 上限能承载；本轮不需要为容量做分片。

### 入口条件（下一批）

控制通道 → `view.resync` → 分片，三者一起设计；在此之前不接任何"半套分片"。

## 四、默认值一致性（R2 §四-3）

### 裁决

**采用"catalog 首帧归一化 + 读键静态扫描"，不建第二份默认值事实源。**

### 理由

1. `/api/catalog` 的 `Properties[].DefaultValue` 已经是描述符的唯一投影
   （`ScadaElementPropertyInfo.DefaultValue`，`IScadaRenderCatalog.cs:96`）；
   客户端再写一份 `factory.defaults` 就是两份事实源，必然漂移。
2. `DefaultValue == ""` 表示"描述符没给默认值"（同文件注释），归一化时**跳过空串**，
   不把"合法空串"误判成默认值。
3. 红队指出的"catalog 晚于首帧"用两条路径兜住：
   - `normalizeElement` 在渲染器读属性袋之前补键（主路径）；
   - `loadCatalog` 到达后对已渲染页补键并重放一次（`applyCatalogDefaultsToPage` + `renderSnapshot`），
     因为 `elements-process.js` 的 `rawProp` 不查目录，只重放不补键等于没做。
4. **闸只查"读键 ⊆ 声明键"**，不查"字面默认值等不等于描述符默认值"：
   补键之后字面回退对"模型没写"这一态不可达；真正会漂移的是读了一个描述符不认识的键
   （WPF 侧永远没有值，Web 只能靠字面值画）。

### 落地证据

- `B57`：`/api/catalog` 原样发出 `DefaultValue`（`HH:mm:ss` 与空串两种形态）。
- `B57b`：`applyCatalogDefaults(el.Properties, el.TypeKey)` 的位置在 `createRecord` 之前；
  `loadCatalog()` 真的被调用（静态位置判据，不钉行号）。
- `[WR5]`（`ScadaChecks`）：55 个读键全部在描述符里声明；3 个运行态/演示键显式豁免并写明理由。

### 顺带修掉的真缺陷

`[WR5]` 第一次跑就抓到 `UnacknowledgedCount`：它是 `AckButtonElement` 的**只读运行态 DP**
（`AckButtonElement.cs:61-68`），不在描述符里，也不在模型属性袋里。
Web 渲染器原来只从 `el.Properties` / 值帧取它，真实运行态**永远显示 0**。
已改为：`createContext` 增加 `getUnacknowledgedCount()`（读 `state.unacknowledgedCount`，
由 `alarms` 广播维护），AckButton 在字段与值帧都缺失时用它兜底。

## 五、压测与完成定义（R2 §四-4/5）

### 裁决

1. 两进程压测与 S1-10% / S1-100% / S3-慢消费者三组证据**仍然有效**：
   本批改动不碰值帧循环、预算、序列化（只新增准入闸与一次 HTTP 目录拉取）。
2. 报告必须继续写"未覆盖"：真实网卡/交换机/WiFi、浏览器 DOM/布局/绘制、1.5MB parse、
   分片、重连风暴、>60s 长稳、三端一致。这些**不因为本批而变成已覆盖**。
3. 完成定义（本轮收尾口径）：
   - `ScadaWebChecks` 全绿（134/0）；
   - `ScadaChecks` 除外部 `FlowListView.xaml` 外全绿（2438/1）；
   - `node --check` 三个 JS 文件通过；
   - Git 提交并推送。

### 未决 / 明确未做
