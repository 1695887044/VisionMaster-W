- 议题：在**方案（.vms）级别**新增「配方」功能：一台设备/一套程序，按产品切换不同的参数集合。

## 一、需求边界（先钉死，避免七轮跑偏）

1. **配方是方案内的东西**：同一份 `.vms`（同一套流程/画面/变量/设备映射）下，按产品切换参数值。
   不是「每个产品一份 .vms」的替代品，也不是跨方案共享的中央配方库（可作为后续能力）。
2. **切换必须可解释、可回退、可审计**：操作员要知道「现在跑的是哪个配方」，工程师要知道「这次切换改了哪些值」。
3. **不改变现有语义**：没有配方时，`.vms` 的行为必须与今天逐字一致；老文件打开不得报错、不得静默改值。
4. **不引入第二套参数模型**：配方的值必须落到现有持久化面（`StepModel.InputValues` / 变量快照 / 点位表），
   由现有 `ApplyConfigValues`、变量写入、点位读取链路消费。禁止另建一套「运行时参数覆盖层」。
5. **安全优先于方便**：涉及运动位置、PLC 写入、相机曝光的切换，宁可拒绝并说明原因，不许静默半应用。

## 四、每轮输出契约（所有角色统一）

1. **一句话结论**（先给判断，不铺垫）。
2. **立场表**：对 F1–F5 各一行「选哪个 + 一句理由」。
3. **方案要点**：只写你这一域真正会碰到的机制与坑，带文件/行号证据。
4. **风险与反对**：至少 3 条，必须包含「如果按别人最可能的方案做，会怎么坏」。
5. **MVP 边界**：v1 必须有的 / 明确不做的 / 可以后置的。
6. **需要别人回答的问题**：不超过 3 条，指名角色。

禁止：写代码、改文件、跑构建、给没有代码依据的断言。
