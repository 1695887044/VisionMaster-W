## 一、R2 收敛的结论

1. **A 范围必须硬排除流程启动类动作**：`BuildAllowedSet` 里与镜像页动作并列硬排除 `StartFlow`、`RunFlowOnce`、`ResumeFlow`；`StopFlow`/`PauseFlow` 可保留（安全方向），但文案必须写清“停流程不等于停轴”。只改 `DefaultAllowedActions` 不够，因为显式 `allowedActions` 参数能把它加回来。
2. **快照缓存只缓存 raw structure**：缓存键至少包含 `pageId@pageVersion@有序baseIds|versions@popupId@popupVersion@popupBaseIds|versions@pageScalarsHash@runGeneration`；caps/未确认报警数/在线列表/租约逐会话或逐拍重算，绝不入缓存。
3. **增量帧**：per-session last-values；baseline 只在 `TrySend` 成功时推进；`frameSeq` 每连接单调；`keyframe:true` 首帧/结构变更后/每 10s；`seq` 仅诊断，不作 delta 基准。
4. **预算**：`FrameBudgetBytes` 语义定为“每帧每会话 UTF-8 字节（含 envelope）”；默认按 70Mbps/16/10Hz 推导为 **45KiB**（46,080B），100Mbps 档上限 64KiB；`FrameBudgetBytes=120KiB` 必须夹取，不能原样生效（120KiB×10×16=157Mbps）。
5. **控制帧双通道**：`ScadaWebSession` 新增 control（64 槽）与 bulk（128/256 槽）；ack/error/pong/stopped/bye 走 control，值帧走 bulk；发送循环优先 control。单通道 256 槽下 ack 最坏等待 21.5s，远超客户端 5s 超时。
6. **分片**：`snapshot.chunk{snapshotId,index,total,data,bytes,runGeneration,pageId,pageVersion}`；64KiB/片；分片期间暂停该会话 frame；客户端在 `handleRawMessage` 重组；5s 超时/乱序/超限作废并 resync；硬上限 `SnapshotMaxBytes`。
7. **多基座先修**：`ScadaWebValueResolver.Resolve` 只遍历 `BasePage`，必须改遍历 `BasePages`；客户端 `renderSnapshot` 只渲染第一只基座，必须按数组序渲染全部基座层。该缺陷与规模无关，缓存会固化它。
8. **弹窗结构必须能推出去**：`OpenPopup` 不动 `CurrentPage.Version`，`PageKey` 不含弹窗；缓存键补 popup 身份/版本/弹窗基座，并在 `OpenPopup/ClosePopup` 后下一拍发 `page`。
9. **45 秒检测双条件**：`now-LastSeenUtc>45s && now-LastSendSucceededUtc>45s`；`LastSendSucceededUtc` 在 `SendTextAsync` 返回后更新；跳过 `IsRevoked`；命令在飞（pending/executing）豁免；关闭码 4408 + `bye{reason:"idle-timeout"}`。
10. **容量 24 = 16 活跃 + 8 握手**：在 ticket 核销处预留握手槽，WS 入册后转活跃，所有失败出口释放；5s TTL（受票剩余寿命约束）；第 17 个活跃回 WS 1013 + `bye{reason:"at-capacity"}`；不抢占活会话。
11. **渲染器覆盖度闸**：放在 `ScadaChecks`，先调 `ScadaChartElements.Register()`，扫描 `wwwroot/*.js` 的注册表与 `ElementRegistry.All`（`ShowInToolbox`）比对；当前已知缺 6 个（ImageView/AxisConsole/AxisPanel/AxisPointTable/DataGrid/ChartTrend），需要显式例外清单，且清单只许变短。

## 二、R2 仍存争议

### 争议 A：Web 写变量触发流程，是否构成 A 范围的旁路

- **红队**：构成。`cmd.input` / `WriteVariable` 写一个被 `FlowVariableTriggerService` 监视的变量，上升沿会启动流程（`FlowVariableTriggerService.cs:156-169`），流程里可以含「轴运动」，这条路不受流程白名单影响。只排除 `StartFlow` 不够。另外 `StopFlow` 只 `Cancel`，不跑后续「轴停止」步骤、不清设备队列（`FlowEngineService.cs:736-749`），所以“Web 能停流程”不等于“Web 能停轴”。
- **架构师**：承认这是 A 范围的残余风险；但跨层 origin 传播要穿过 runner → FlowSessionFactory → 引擎上下文 → Motion 插件，五层且流程线程模型未核实，今晚不可证明。建议 A 范围把“写变量”限制为“不触发流程的变量”，或明确写入运维约束。
- **comm**：建议在变量写入前增加一道“该变量是否流程触发器”的查询；是则拒绝并审计。这样不用改流程引擎，也能封住这条路。
- **待 R3 裁决**：今晚是否实现“Web 写变量拒绝流程触发变量”？如果不实现，A 范围能否宣称“Web 不能运动”？

### 争议 B：`clientInstanceId` 是否进幂等键

- **架构师**：不进。前端 requestId 是 UUID，撞号不是现实风险；加进去会破坏“断线重连后同 requestId 找回结果”（R1 的 token 键正是为此）。
- **comm**：进。同账号多标签共用 token，不带 instance 时两个标签页的 requestId 空间无法隔离；`clientInstanceId` 由客户端生成并持久化（sessionStorage），重连复用，不破坏找回。
- **红队**：如果客户端在重连时重新生成 instance id，就会把同一条命令当新命令再执行；必须证明“持久化 + 重连复用”。如果不证明，宁可只把 instance 用作审计字段，不进键。
- **待 R3 裁决**：进键（并要求客户端持久化）还是不進键（只作审计/诊断）？

### 争议 C：结果查询 WS 还是 HTTP

- **架构师/comm**：WS `cmd.result`，请求用 `targetRequestId`，在 `HandleTextFrame` 里直接答，不入泵、不过版本闸、不过审计 fail-closed；响应用新 `type:"result"`，不带 `ok`，避免被前端当 ack。
- **红队**：WS 查询在“被踢下线”后不可用（连接已关）；HTTP 可以在重连前查询。且 `Dedup.Check` 会写表（超期删除），查询必须用只读 `TryPeek`。
- **待 R3 裁决**：WS 还是 HTTP？是否接受“撤销后不可查”的边界？

### 争议 D：分片形状：字符串切片 vs 结构分片

- **comm/ui**：字符串切片 `snapshot.chunk{data}`，客户端拼接后 `JSON.parse`；实现简单、保真。
- **hmi**：结构分片 `page.part{part,parts,page}`，逐片施加 caps；避免超大字符串和重复解析。
- **待 R3 裁决**：今晚用哪种？字符串切片更稳，结构分片更省内存。

### 争议 E：默认值一致性闸今晚做到哪一档

- **ui**：客户端 `fetch('/api/catalog')` + 渲染器 `factory.defaults` 比对；但 23 个渲染器目前没有 `defaults` 声明。
- **红队**：没有 `defaults` 声明的比对是假绿；要么给每个渲染器补声明，要么不做。
- **待 R3 裁决**：今晚只做“渲染器覆盖度”，默认值一致性留到下一批并写清欠账；还是给 23 个渲染器补 `defaults`？
