## 一、零回归：用「基线差分」替代「逐字相等」

### 1.1 为什么逐字相等不成立

`SolutionService.LoadAsync` 在内存里做多项迁移：`SolutionId` 补齐、`IoMigrationHook`、`InvokeType` 迁移、
`MandatoryFlows.Ensure`、`Scada.EnsureIdentity`、旧轴控件迁移；`MotionAxisRegistry` 还会补 `AxisId`。
因此「Load→Serialize 与磁盘逐字相同」对多份真实方案本来就不成立。

### 1.2 最终方案

改造前先跑一次**基线**：对 `解决方案\*.vms` 全量记录每份文件「Load→Serialize 与磁盘是否逐字相等」的清单
（相等/不等 + 差异摘要），改造后逐项不变。已知基线（R6 实测口径）：
- `合成颜色验证.vms`、`演示方案.vms`：无 AxisId、`MotionCards: []`；
- `柔性装配线.vms`：已有 AxisId；
- `ActiveRecipeId: Guid.Empty` 读入归一为 null 会造成文本不等——进基线差分，不写成「逐字相等」。

断言：
- D1 基线差分逐项不变；★变异：给任一既有属性补 `[JsonProperty(Order)]` → 基线必红。
- D2 `Recipes:null` 不写键；`[]` 写回 `[]`；★变异：给 `Recipes` 加 `= new()` → 红。
- D3 新字段 `Order=100/101/102` 全仓唯一（已 grep 零命中）；★变异：插到 `Scada` 之前 → 红。

## 二、脏判定：从「与磁盘逐字比较」改为「与打开时基线哈希比较」

### 2.1 问题

`EnsureAxisIds` 在启动/注册表构建时把 `AxisId` 写进内存模型 → 序列化文本多出键 →
`SolutionDraftService` 判「有未保存改动」→ 每次退出多存一份 `Autosave` → 捕获（要求无未保存改动）永远被拒。

### 2.2 最终方案

- 打开方案后强制 `EnsureAxisIds` + `Reload`，记录 `AxisIdentityState = Complete | Backfilled`
  （本次补过，或原始 JSON 缺 `MotionCards[].Id`——`MotionDescriptor.Id` 有 `Guid.NewGuid()` 初始值，缺键则每次打开换 Id）。
- 同时记录**打开时基线哈希**（对加载完成后的内存序列化文本取 SHA-256）；保存成功后重置基线。
- 脏判定 = 当前序列化哈希 ≠ 基线哈希；不再直接与磁盘文本比较。
- `AxisIdentityState == Backfilled` 时：横幅「轴身份已自动建立（N 根）但未落盘，请先保存」，
  捕获与应用都禁用；保存后自动转 `Complete`，不必重新打开（R3 的「保存并重新打开」是过度约束）。
- 基线哈希/轴身份态挂宿主（`[JsonIgnore]` 或 `RecipeService` 私有字段），不落盘。

断言：
- 开老文件不编辑→退出：`Autosave\` 零新增；改一个值→必新增。
- 保存后重启：轴 `AxisId` 与卡 `Id` 逐字不变。
- ★变异：把脏判定改回「与磁盘文本比较」→ 老文件用例必红。

## 三、旧版覆盖：canary + 文件外备份

### 3.1 `Version` 2.0 的时机（定稿）

- 唯一时机：`Recipes` 由 null 变非 null（首次创建/首次捕获），不是应用、不是保存。
- 不变式：`Recipes != null ⇒ Version >= 2.0`，必须在序列化前成立。
- 只捕获未应用的文件也必须 2.0；否则被旧版保存后配方静默消失且无告警。
- ★断言：经 `RecipeService` 产生的任何含配方状态，`Serialize` 必含 `"Version": 2.0`；
  静态扫描确认 `Recipes` 只有一处写。

### 3.2 告警与恢复

- 判据：`Version >= 2.0 && Recipes == null` → 横幅：
  「本文件声明为配方格式（2.0），但配方数据缺失，通常是被旧版软件保存过。请不要直接保存。
  可恢复来源：程序目录 `Autosave\` 草稿（保留 10 份）。」
- 动作：打开 `Autosave\` 目录 / 定位最新草稿 / 本次忽略（会话内）。不阻断打开与保存、不自动还原、不自动选草稿。
- **文件外旁路备份（v1 就带）**：每次保存成功写 `Recipes\<SolutionId>\<yyyyMMdd-HHmmss>.recipes.json`（只写不自动还原，留 5 份）。
  canary 只能在丢失后告警，备份才能丢失后恢复。
- 保存 2.0 文件时保留 `.bak`（`File.Replace(tmp, filePath, backup)` 第三参非空）；R180 双 catch
  `IOException` + `UnauthorizedAccessException`。

### 3.3 是否阻断

不阻断打开与保存；只在「保存会覆盖 2.0 文件且配方缺失」时二次确认。
旧版二进制实测是**人工硬项**：用上一版 exe 打开新 `.vms`→保存→再用新版打开，结果写进 `docs/code-changes/`。

## 五、复杂对象兼容（视觉域定稿）

### 5.1 候选派生剔除六类

1. 无 setter（基类不过滤，`SetValue` 异常会被空 catch 吞掉）；
2. `[RuntimeState]`；
3. 类型图不封闭（但见 5.2 的枚举例外）；
4. `IsHidden` 端口（不列候选，已有条目照常应用）；
5. 名字/路径类：`DefaultTemplateName`、`TemplateLibraryJson`、`TemplateShape`、Matching 五个迁移字段、
   CreateRoi 的 `SmearDrawData`/`SmearEraseData`（RLE 可超 4KB）；
6. 捕获时为空且非必填。

### 5.2 类型键与枚举

- `DeclaredType` 规范化键示例：
  - `System.Collections.ObjectModel.ObservableCollection\`1[Plugin.CreateRoi.Models.RoiItem]`
  - `System.Double[]`
  - `System.Collections.Generic.List\`1[Plugin.CaliperMeasure.Models.CaliperRegion]`
  - `System.Nullable\`1[Plugin.CaliperMeasure.MeasureKind]`
- **枚举叶子例外**：允许任意已加载程序集的枚举作为叶子（枚举无构造攻击面），但必须：
  ① 捕获存**成员名**（`JToken.FromObject` 默认写整数，必须显式转成员名）；
  ② 应用前 `Enum.IsDefined`（`[Flags]` 查全位）；未定义数值 → 整单拒绝。
  这条解决 `RoiItem.ShapeType` 是 `Core.Halcon.DrawShapeType` 与 R3 封闭类型图的矛盾。
- `PluginTypeName` 不用 AQN（现 `.vms` 存 AQN，插件升版即全量孤儿）；用程序集无关的规范化类型键。

### 5.3 变更矩阵

| 情形 | 判定 |
| --- | --- |
| 新增属性 | 允许 + 警告（取默认） |
| 删除属性 | 拒绝整单（仅当条目引用了它；无人引用则放行） |
| 属性改名 / `[JsonProperty]` 改名 | 拒绝（除非显式 `PreviousNames` 别名） |
| 类型收窄（double→int、枚举换枚举） | 拒绝 |
| 集合种类变（`List`↔`ObservableCollection`↔`[]`） | **允许 + 警告**（JSON 形状相同；CreateRoi 已做过这次重构，判拒绝会作废全部存量 ROI 配方） |
| 数组长度变 | 值级警告 |
| 枚举成员删除/改名 | 拒绝；仅改 `[Display]` → 放行（值仍是成员名） |
| 枚举新增成员 | 允许 |

反证：把 `RoiList` 换成 `List<RoiItem>`，旧配方仍可应用；改 `RoiItem` 命名空间，条目必红；配别名后必绿。

### 5.4 Matching 边界（再钉）

| 字段 | v1 |
| --- | --- |
| `RecipeName`（端口） | 可进；值域=本步骤模板库条目名；已链接 → 拒绝 |
| `DefaultTemplateName` | 永不进 |
| `TemplateLibraryJson` | 永不进（含 base64 模型） |
| 五个迁移字段 | 永不进 |

预检只解析名字、跳过 `Model`/`Mask` 值（流式 reader），按步骤+JSON 指纹缓存；查不到报 `ResolveEntry` 同款文案，
并加一句「这是模板名不是配方名」。另查重名：`MatchingTemplateEntry.Name` 无唯一约束，`FirstOrDefault` 会静默取第一个。

## 六、`.vmrecipe` v1.1（格式现在定，实现后置）

- 字段：`formatVersion`（主版本不等即拒）/ `kind` / `exportedAtUtc` / `By` / `sourceSolutionId` / `sourceSolutionName` /
  `sourceAppVersion` / `recipe` / `mappingHints`（步骤名+插件名+轴名/卡名/物理号）/ `contentHash`。
- 序列化：`TypeNameHandling.None` + `NullValueHandling.Ignore`（靠 `ValueIsNull`）；正向白名单 DTO 属性名闭集；
  深扫拒 `$type`、拒 `Path.IsPathRooted`、拒设备字段（地址/卡型/驱动键/软限位/通讯/相机 Settings）。
- 上限：4 MiB / 单条 64 KiB / 条目 ≤5000；严格 UTF-8（容 BOM，UTF-16 明确报错）。
- 匹配：同 `sourceSolutionId` 才可按 Id，否则**名称路径优先**；唯一命中才收；0/多命中 → 整单拒并列候选。
  `AxisId` 一律重映射（卡名+轴名+物理号 → 目标 `AxisId`）；任一点无唯一映射 → 整单拒或显式「仅导入步骤参数」。
- 导入只建定义不应用：断言 `ActiveRecipeId`、全部 `InputValues`、`Points` 引用与值、`FlowModel.Version` 不变，
  会话 `IsStale` 仍 false；审计一行（文件名+hash+匹配数+新 Id）；审计不可用 → 警告放行（可删）。

## 七、性能与上限

- 500 条条目不会触发 500 次重编译：`FlowSessionFactory` 只在 `TryEnsureSession` 编译，`Version` 只比大小；
  下次运行恰编译 1 次。
- 真风险是扇出：每次 `SetInputValue` 发通知 → `FlowModel.Version++`；若偏离/画布刷新订阅每次都全量重算，
  500 次 = 25 万次比较。做法：应用期间冻结偏离与画布刷新，结束调一次，订阅端 300ms 防抖；
  不压 `Version++`（stale canary 需要）；写循环里不 `Serialize`。
- 估算（探针钉住，非承诺）：预检 10–40ms（反射表不缓存则 300–1500ms）；快照 5–25ms（2 MiB 复杂对象 80–300ms）；
  写入 5–20ms；终检 5–30ms；偏离 10–40ms；未保存闸 30–150ms 加磁盘读。
- 后台：磁盘读、整方案序列化比对、候选/schema 反射、审计写盘。UI：快照、写入、终检回读、`ActiveRecipeId`/`Version` 赋值。
- 封门窗口 >800ms 判设计不达标。
- 复杂对象单条份额 ≤20ms、整单 ≤100ms；ROI ≤128 项、卡尺 ≤32 项、单条 ≤64 KiB。
