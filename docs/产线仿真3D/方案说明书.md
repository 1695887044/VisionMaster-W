| C2 | **单一虚拟时钟** | 两套时钟必然漂移，"图像与位置对不上"这类 bug 会被仿真自己制造出来 | 断言 S2：`DateTime.Now`/`Stopwatch` 在 `LineSim/` 下零出现（静态扫描） |
| C3 | **协议自版本化** | 仿真器与上位机是两个可独立升级的交付物；协议漂移是这类项目最常见的死法 | 断言 S3：`hello` 握手版本不匹配时**双方都拒绝进入 Online** |

### 2.3 为什么是独立进程（四条理由 + 一条代价）

| 理由 | 说明 |
|---|---|
| ① 可信度 | 被测系统与测试系统同进程时，一次未捕获异常、一次静态状态污染就能让"测试通过"变成假象 |
| ② 生命周期 | 仿真器要能单独重启、单独留日志、单独给第三方；同进程做不到 |
| ③ 契约压力 | 走网络就**必须**用契约（`ICameraDevice`/`IMotionDevice`）能表达的信息，反过来验证契约是否够用 |
| ④ 性能隔离 | 5MB/帧的图像合成不能和 WPF 主线程抢；独立进程可以单独绑核、单独限流 |

**代价（诚实写明）**：调试链路变长（跨进程抓包）、仿真器要自己实现协议与序列化、CI 里要管两个进程的启停。→ 用 §12.2 的录制/回放与 §8 的协议日志把代价压回来。

### 2.4 为什么不复用 `HttpImageServer` 推图（F3 的既有路径）

| 维度 | 推图（既有） | 拉图（本方案） |
|---|---|---|
| 触发语义 | 客户端想推就推，与产线状态无关 → **无法保证"图像 = 触发时刻"** | 上位机触发 → 仿真器渲染当前 tick → 严格对应 |
| 元数据 | 只有 `X-Image-Name` | 帧头可带 tick/曝光/增益/相机ID |
| 结论 | 保留给"只想喂一张图"的场景 | 产线仿真必须拉图 |

## 4. 仿真内核

### 4.1 单一时钟

- tick = **1ms**，`long Tick` 单调递增，`SimTime = Tick * 1ms`。
- 所有子系统（运动积分、IO 采样、通讯投影、编码器计数）都在 tick 上推进；**没有任何线程用墙钟决定行为**。
- 渲染**不在 tick 上**：tick 只决定"世界在 t 时刻是什么样"，渲染按需（被触发时）取快照。
- 墙钟只用于三件事，且**唯一出口**是 `LineSim/Kernel/WallClock.cs`（其余文件出现 `DateTime.Now`/`Stopwatch`/`Environment.TickCount` 即 S2 判红）：① 3D 视图刷新节流；② 看门狗（tick 推进落后 > 500ms 报警"仿真算力不足"，因为此时**时序已经不保真**）；③ 事件日志的时间戳。**WallClock 只读不写**：不许改世界状态、不许写帧、不许参与任何判定（反向断言见 S2）。

### 4.2 tick 流水线（严格顺序，7 步）

```
for each tick t:
  1. 收集输入：把上一 tick 之后到达的所有外部请求（运控命令 / IO 写 / 相机触发）从队列取出
  2. 应用输入：按到达顺序（同 tick 内按序号）作用到世界
  3. 推进物理：各轴梯形加减速积分 → 位置/速度/限位/到位；编码器按带速累加
  4. 更新 IO：机构与轴的耦合（例：压装轴到位 → DI7=true）、定时器、光电
  5. 通讯投影：把世界状态写进 Modbus 寄存器镜像 / S7 DB 镜像
  6. 冻结渲染快照：本 tick 被请求的相机 → 把 **t 时刻世界状态** 拷成不可变快照，投给渲染线程后立即返回（**不在 tick 上合成**，见下方注）
  7. 记事件：命令状态变化 / 限位 / 故障 / 工件移动 / 判定结果 → 事件日志
```

**关键点**：第 6 步用的是**第 3~4 步之后**的世界状态，所以"命令生效的那一拍"与"图像看到的那一拍"是同一个 `t`。这就是 C2 的落地方式。

> **合成不在 tick 线程上（v1.2 修正）**：5MP 合成 ≤25ms，而 §4.5 的 tick 预算只有 200μs —— 若把合成塞进第 6 步，tick 会以 100 倍落后；而宿主侧所有超时都是墙钟（`CameraSettings.cs:54` 的 `FrameTimeoutMs=3000`、`ImageAcquisitionPlugin.cs:720`），于是"仿真算力不足"会被误诊成"真机等图超时"。**tick 只负责冻结快照**，合成/编码/HTTP 发送都在渲染线程；快照自带 `t`，出图顺序与 `t` 的对应关系不因异步而改变（S2b 钉这条偏差）。

### 4.3 输入锁存（tick 边界）

| 规则 | 说明 |
|---|---|
| 外部输入永不直接改世界 | 一律入 `ConcurrentQueue<SimInput>`，由 tick 线程消费 |
| 同 tick 多输入按 `Seq` 排序 | `Seq` 由接收线程用 `Interlocked.Increment` 分配，保证"先到的先应用" |
| 命令受理与执行分离 | `enqueue` 只回 `Accepted`（进队列），真正执行在后续 tick 的 `ExecuteCommandCore` 等价逻辑里 —— **和真机一致：受理 ≠ 到位** |

### 4.4 确定性

| 措施 | 说明 |
|---|---|
| 随机数 | 一律 `DetRandom(seed, tick, cameraId, partId)`，**禁止共享 `Random` 实例** |
| 遍历顺序 | 凡参与计算或写文件的集合，一律 `SortedList`/按 key 排序，不用 `Dictionary` 的枚举序 |
| 并行 | **tick 内禁止并行**（`Parallel.*`/`Task.WhenAll` 在 `Kernel/` 下静态扫描为 0） |
| 浮点 | 全 `double`，不做 `Math.Pow` 之类的平台差异运算；**承诺"同机同版本可复现"，不承诺跨架构逐位一致**（诚实边界） |
| 时间 | `DateTime.Now`/`Stopwatch`/`Environment.TickCount` 在 `LineSim/` 下**除 `Kernel/WallClock.cs` 外**零出现（S2）；WallClock 不参与任何世界状态计算 |

### 4.5 性能预算（单机、i7 级、无 GPU 依赖）

| 项 | 预算 | 依据 |
|---|---|---|
| tick 推进 | ≤ 500μs / tick（44 轴 + 192 IO + 13 工位） | 1kHz 下占用 ≤ 50% 单核；v2.0 从 200μs 上调（轴 ×2.2、IO ×3） |
| 单帧合成 5MP mono | ≤ 25ms | 解析投影 + 贴图，非光线追踪 |

| 稳态帧率 | CAM2 40fps + 其余按需 ≤ 2fps | 见 §5.1 带宽表 |

### 5.2 成像链（**解析合成，不用 3D 渲染器**）

> 这是本方案最重要的一个技术选择：**"给人看的 3D" 与 "给算法测的图" 是两套渲染**。

| 步骤 | 做什么 | 为什么这样做 |
|---|---|---|
| ① 世界快照 | 取 t 时刻：工件位姿、相机位姿、光照参数 | 保证"触发即此刻" |
| ② 几何投影 | 工件几何（矩形/圆/多边形/盒体）经外参 → 相机系 → 透视投影（含畸变 `k1,k2,p1,p2,k3`）→ 像素 | 解析投影**可反算真值**，这是标定与重投影断言的基石 |
| ③ 表面贴图 | 工件表面纹理（合成纹理或照片）按单应变换采样 | 让模板匹配/缺陷检测有真实纹理可抓 |
| ④ 光照 | Lambert 漫反射 + 环境光 + 简化 Phong 高光；支持**光照不均 / 暗角 / 背光** | 背光是尺寸测量的真实条件（CAM3） |
| ⑤ 运动模糊 | 曝光窗口内按工件速度沿运动方向做 box blur，长度 = v × tExp | 让"曝光时间选错"变成可测的测量偏差（S12） |
| ⑤b 光学 PSF | 离焦/衍射的二维高斯卷积（σ 由 F 数、波长、离焦量推；默认 σ=0.6px），边缘再叠 **2×2 像素面积积分** | 没有 PSF 的边缘是"数学阶跃"，卡尺重复性会假好（S17 的 σ 判据会被高估）；面积积分让亚像素边缘有真实灰度过渡 |
| ⑥ 噪声 | 散粒噪声 σ=√(I·g) + 读出噪声 + 增益放大 + 8bit 量化 + 可选伽马 | 让阈值/滤波参数的选择有意义 |
| ⑦ 缺陷叠加 | 按缺陷谱在图像域叠加（划伤=细线、脏污=低对比斑、崩边=边缘缺口） | 缺陷真值与图像严格对应 |
| ⑧ 传感器非理想 | 坏点、镜头脏污、行噪声（默认关，可开） | 压力测试鲁棒性 |

**为什么不用 WPF/GPU 渲染出图**：① 不可控（驱动/AA/色彩管理差异）；② 拿不到亚像素真值；③ 非确定性（浮点与驱动差异）；④ 无法反算。**3D 视图因此与相机图像完全解耦**——即使 3D 视图整块删掉，仿真核心与图像质量不受影响（S21）。

**亚像素能力**：2×2 超采样 + 解析边缘 → 卡尺边缘重复性可到 **0.1px**（= 3μm @ CAM3），足以验证"重复性 < 0.02mm"这类指标。

**闭环做法**：仿真器按上表渲染 **≥12 张带畸变的倾斜标定板图**（`SimCaltab` 等价路径生成，灰度极性按板型配对）→ 上位机内参标定插件算 `CamPar` → 与真值比对 `focus/sx` 组合、`cx/cy`、`kappa`。这既是**标定插件的端到端验收**，也是 S13 的数据来源。

> v1.1 写"渲染一张带畸变的标定板图"是错的——单张图连 `MinImageCount` 都过不了，且平面单姿态无法解算内参。

### 5.4 触发语义与延迟模型

```
上位机 TriggerSoftware()                        ← 无参数（ICameraDevice.cs:83），宿主不知道仿真 tick
  → [控制通道] trigger(camId)                   ← 仿真器**收到请求的那一刻**才确定 t
  → 仿真器：t = 收到 trigger 的 tick；记录曝光窗口 [t, t+tExp]
  → 曝光中点 t+tExp/2 的世界快照 → 渲染线程合成（不在 tick 上，见 §4.2）
  → t + tExp + tXfer 时帧可用（tExp 取 CameraSettings.ExposureTimeUs，tXfer 默认 3ms）
  → 帧头 {tick, cam, w, h, ch, bits, exposureUs, gain, seq, ts}
```

> **`t` 的定义（v1.2 修正）**：`t` = **仿真器收到 trigger 请求的 tick**，不是"上位机发出的时刻"——上位机侧根本没有 tick（`TriggerSoftware()` 无参），v1.1 写的 `tickRequested=now` 在上位机不存在。因此**控制通道延迟必须计入误差预算**：`--camera-latency <ms>` 可注入固定延迟（默认 1ms），S11 的容差里含它。

| 场景 | 行为 | 断言 |
|---|---|---|
| 软触发（CAM1/3/4/5/6） | 每次 `TriggerSoftware` 受理 → 恰好产生 1 帧 | S8：触发 N 次收 N 帧，**且 `OverflowCount==0 && DroppedFrameCount==0`**（前提见 S8） |
| 编码器触发（CAM2） | 编码器计数每跨 5mm 自动产生 1 帧 | S9：帧 `tick` 序列 == 由 `Motion.ST2.Enc.PositionMm` **独立算出**的"每跨 5mm"tick 序列 |
| 连续模式 | 按配置帧率产生 | 仅用于"不关心触发"的调试 |
| 触发超时 | 上位机 `FrameTimeoutMs=3000` 到点仍未收到 → 报错（这是真机行为，仿真要能复现） | S10：仿真器故意不响应时，步骤报"等图超时" |
| 编码器触发的契约边界 | `CameraTriggerMode` 只有 `Software/RisingEdge/FallingEdge/Continuous`（`CameraTypes.cs:12-25`），`TriggerSourceLine` 只 0~3 → **"每 5mm"不是契约字段** | CAM2 映射 `RisingEdge`，5mm 间隔写进 `scenario.json`（仿真器侧）；若要上位机可配，需给 `CameraSettings` 加字段 → 走契约变更评审（**不在本期**） |

> ⚠ **陷阱（已在契约里）**：`CameraSettings.TriggerSchemaVersion` 为 0 的旧 JSON 会被迁成 `Continuous`（F4）。新建仿真相机必须走 `CameraSettings.CreateNew()`，否则软触发路径根本不进（F2 的分支条件不成立），表现为"不触发也出图"的**假绿**。这条写进 S14。

## 6. 运控子系统

### 6.1 命令语义（对齐契约 9 种）

> **架构前提（v1.1 更正，推翻 v1 的 §6.1）**：`Enqueue` 的门禁在 `MotionDeviceBase.CheckGateLocked`（`Shard/Core.Interfaces/Motion/MotionDeviceBase.cs:786`），**不在驱动里**。被门禁拒掉的命令**根本进不到 `ExecuteCommandCore`**，驱动没有任何机会把它们变成 `Failed`。所以仿真卡只实现"物理"，不实现"判据"——判据由 `MotionDescriptor` 的配置正确性负责。

**A. 基类门禁（仿真器不实现，只保证配置正确）**

| 判据 | 出处 | 返回 | 触发条件 |
|---|---|---|---|
| 状态不允许 | `MotionDeviceBase.cs:796-827` | `Rejected_NotConnected` | 非 `Online` 一律拒；`ClearAlarm` 例外放行 `Alarm`/`SafeStopped`；`Stop`/`Disable` 在 `Alarm`/`SafeStopped` 下也放行 |
| 轴号越界 | `:830-848` | `Rejected_InvalidArgument` | `MoveAbsolute`/`MoveRelative`/`Home`/`Enable`/`Disable` 的 `PhysicalAxis ≥ AxisCount`；`Stop` 轴号 ≥ 0 时越界 |
| 回零方式不支持 | `:850-859` | `Rejected_NotSupported` | `HomeMode` 不在 `SupportedHomeModes`（文案会列出该卡支持哪些） |
| 输出点越界 | `:861-867` | `Rejected_InvalidArgument` | `SetOutput.IoPort ≥ DigitalOutputCount` |
| 软限位 | `:874-914` | `Rejected_InvalidArgument` | 绝对运动比 `TargetMm`；**相对运动先按轮询快照算目标点再比**（否则"相对 +50"能绕过行程）；取不到当前位置一律拒，NaN/±∞ 一律拒 |
| 未使能 / 未回零 / 正在运动 | `:940-1010`（返回点 `:968`/`:979`/`:985`/`:995`/`:1002`） | **`Rejected_NotConnected`**（v1.2 更正，v1.1 误写 `Rejected_InvalidArgument`） | 运动类命令。`Home` **只**挡"正在运动"（回零本身就是为了解决未回零） |
| 队列满 | `:646` | `Rejected_QueueFull` | `PendingCommandCount ≥ Params.MaxQueueDepth`（默认 256） |
| **计数口径** | `:641-651`、`:1299` | — | 被门禁拒 → **只** `RejectedCommandCount++`；`ExecutedCommandCount` **仅在 `Done` 时 +1**。驱动永远没机会把被拒命令变成 `Failed`——这就是 §3.2 `SPARE`/`ST2.Enc` 不能用 `Failed` 表达"未接线"的原因 |

四类业务拒绝（软限位 / 未使能 / 未回零 / 正在运动）按 `reason` 文案判为 `MotionFaultSeverity.Notice`（`:669-677`）→ **不会把卡打进报警态**。这是"仿真里天天撞限位也不至于把卡打红"的前提，也是回归能跑一万次的原因。

**B. 驱动执行语义（仿真卡 `ExecuteCommandCore` 真正要实现的部分）**

| 命令 | 仿真行为 | 完成态 |
|---|---|---|
| `Enable` | 置轴使能位 | `Done` |
| `Disable` | 清使能、清到位、`Moving=false` | `Done` |
| `MoveAbsolute` / `MoveRelative` | 起一条速度曲线逐 tick 积分（`Curve` 两档，见 §6.2） | `Done` **= 下发完成**，不是到位（`MotionCommand.WaitsForCompletion=false`，`MotionCommand.cs:77`） |
| `Home` | 按 `HomeMode` 走回零状态机，耗时 ≥ **固定常量 200ms**（不是 `MotionParams` 字段，见 §6.3），完成时 `MarkHomed(true)` | `Done`（`WaitsForCompletion=true`，命令线程等它） |
| `Stop` | 按 `StopMode` 减速停（2）或立即停（3）；`PhysicalAxis=-1` = 全部轴 | `Done` |
| `Jog` | **立即 `Done`**（`WaitsForCompletion=false`），目标 = 当前位置 ± 1e6 mm（与 `VirtualMotionCard` 同口径，`VirtualMotionCard.cs:306-309`）。**停止只由 `Stop`/`Disable` 完成**："反向 `Jog`"不是停止手段——`IsInterrupting` 只含 `Stop`/`Disable`（`:618-619`），而 Jog 又不受运动前置门禁（`:941`），反向 Jog 只会排到队尾死等；若真做成阻塞式，被 `Stop` 打断时基类把取消映射成 **`Canceled`** 而非 `Done`（`:1180-1195`），断言必红 | `Done`（下发即完成） |
| `SetOutput` | 写 DO + 触发机构耦合（§6.2） | `Done` |
| `ClearAlarm` | 清报警位；**增量编码器且未回零时基类复核会保持 `SafeStopped`**（`:504`），仿真卡不必自己判 | `Done` |

**命令对象要点**（`Shard/Core.Interfaces/Motion/MotionCommand.cs`）：`Timeout` 是 `TimeSpan`（`<=0` 用卡级 `Params.CommandTimeoutMs`=30000）——**超时必须由驱动自己判**（v1.2 更正，v1.1 写反了）：基类对 `ExecuteCommandCore` 的调用**没有任何超时包装**（`MotionDeviceBase.cs:1149-1272`），`MotionCommand.Timeout` 在基类里只被 `ClearAlarm` 自己用（`:428-430`）；`TimedOut` 全仓只由驱动 `return`（`VirtualMotionCard.cs:336-341`、`ZMotionCard.cs:464/:495`），基类只做 outcome→state 映射（`:1200`）。**驱动写法**：`timeout = cmd.Timeout > TimeSpan.Zero ? cmd.Timeout : TimeSpan.FromMilliseconds(Params.CommandTimeoutMs)`，到期 `return MotionCommandOutcome.TimedOut`；`VelocityMmPerS`/`AccelMmPerS2` `<=0` 时用 `Params.DefaultVelocityMmPerS`(50)/`DefaultAccelMmPerS2`(500)；`Retryable` 对 `Home`/`Stop` 必须为 `false`；`Completion`（`ManualResetEventSlim`）是"等命令做完"的统一原语。

**全局（v1.2 更正三处）**：`EmergencyStop()` **有状态门禁**——非 `Online`/`Alarm` 直接 `Rejected_NotConnected`（`MotionDeviceBase.cs:707-708`），不是"不进门禁"。受理后基类构造 `Stop` 命令（`PhysicalAxis=-1`、`StopMode=3` 立即停）并打断当前运动（`:694-701`），队列清空、当前命令以 **`Canceled`** 收尾（不算故障）。仿真卡只需保证 `StopMode=3` 时速度立刻归零。**`AxisStatus.EmergencyStop` 位不许点亮**：那是硬急停输入位，点亮会被 `DetectCriticalSignals` 升级成 `Alarm` + `RequiresReset` 故障（`:1384-1399`），与既有断言"急停是预期操作：不记成设备故障、也不进安全停机"（`MotionChecks` 急停段）直接打架。

### 6.2 轨迹与加减速（比虚拟卡多出来的部分）

| 项 | 虚拟卡（F7） | LineSim |
|---|---|---|
| 速度曲线 | 匀速，无加减速 | **梯形 + S 曲线两档**（跟 `MotionCommand.Curve` 走：`Trapezoid` 加速/匀速/减速三段，`SCurve` 用七段 S 型），`AccelMmPerS2` 可配 |
| 位置推进 | 每拍 `速度 × 拍长` | 每 tick 解析积分，`PositionMm` 连续、`VelocityMmPerS` 同步 |
| 到位判据 | 走完才 `InPosition` | `\|目标-实际\| ≤ 到位窗口(默认 5μm)` 且速度 ≤ 阈值 → `InPosition=true`、`Moving=false` |
| 超时 | 无 | **由驱动判**（v1.2 更正）：`timeout = cmd.Timeout > 0 ? cmd.Timeout : Params.CommandTimeoutMs`（30000），到期 `return TimedOut`（基类无包装，见 §6.1「命令对象要点」）。仿真卡的"卡死" = 速度归零、`InPosition=false`、`Moving` 保持 true；到期驱动返回 `TimedOut`，基类映射成 `MotionCommandState.TimedOut` 并记 `Recoverable` 级故障（`MotionDeviceBase.cs:214-218`） |
| 软限位 | 无 | 基类按 `AxisMapping.SoftLimitMinMm/MaxMm` 判并拒绝（§6.1 A）；仿真卡负责**硬限位信号**：走到行程端点置 `PositiveLimit/NegativeLimit` → `HasCriticalSignal=true`，且速度立即归零（模拟撞限位）。⚠ 要让硬限位可观测，软限位必须比机械端点**松 5mm**（否则基类先拒，硬限位永远触发不了，见 S24） |
| 机构耦合 | 无 | 压装轴到位 → DI7/DI8；真空 DO4 → DI3 延迟 30ms 到位；分度台 45° 步进 → 定位销 DI6 |

> **耦合的意义**：让上位机的"等 IO 再动作"这类握手逻辑有真实对象可等，而不是永远恒 true 的假 IO。

## 7. 通讯子系统

### 7.0 总览：18 台设备 / 6 种协议 / 端口规划（v2.0）

**为什么端口 = 设备身份**：单机回环下所有设备都是 `127.0.0.1`，无法用 IP 区分；而上位机侧"一台设备一个 `ConnectionWorker` 线程 + 一份 `DeviceConfig`"（F22），所以仿真器**一台设备一个监听端口**，端口内再用协议自带的从站标识区分逻辑设备。设备清单见 §3.5，本节只讲协议侧实现。

| 协议 | 台数 | 端点 | 仿真侧实现 | 上位机侧驱动 | 备注 |
|---|---|---|---|---|---|
| Modbus TCP | 6 | `19520`（unit 1..6） | HSL `ModbusTcpServer` | `ModbusTcpConnection` | 一台监听端口服务 6 个 unit（**同一端口多 unit**，验"上位机把 unit 配错"） |
| Siemens S7 | 3 | `19530` / `19531` / `19532` | HSL `SiemensS7Server` | `SiemensS7Connection` | 一台一端口（S7 协议无 unit 概念，靠 Rack/Slot） |
| Mitsubishi MC | 2 | `19540` / `19541` | HSL `MelsecMcServer(isBinary: true)` | `MitsubishiMcConnection` | 3E 帧二进制 |
| Omron FINS | 2 | `19550` / `19551` | HSL `OmronFinsServer` | `OmronFinsConnection` | node 号区分 |
| 自由协议 TCP | 2 | `19560` / `19561` | **自写**（文本行，< 200 行） | `FreeProtocolConnection` | 验"无扫描组、事件驱动"路径 |
| Modbus RTU | 3 | `COM20` / `COM21` | **自写 RTU 从站**（CRC16 + `0x03/0x04/0x10`，< 150 行） | `ModbusRtuConnection` | **默认关闭**，需 com0com；HSL 无 RTU 从站 |
| — | — | `19500` 相机流 / `19510` 运控 | 自写（§8） | `Plugin.Camera.Sim` / `Plugin.Motion.Sim` | 不在本节 |

**协议栈复用 HSL 从站的代价（K10 同库抵消）**：仿真器用 `DLL/HslCommunication` 起从站、上位机用同一个 DLL 做客户端 —— **同一个库的自测不算验证**（编解码错也一起错）。因此 §14 增加 **S31：每协议一条绕过 HSL 客户端的原始 socket 手写报文**（Modbus 6 字节头 + PDU、S7 用 `CommStress` 已验证的裸报文、MC 3E 帧、FINS UDP、自由协议文本），失败即判"协议层不可信"。这不是可选项。

**RTU 的诚实口径**：本机没有真实串口，`com0com` 是第三方内核驱动（需装驱动、改本机环境）。因此 ① 默认 `devices.json` 里 D16–D18 `enabled: false`；② 装了就设 `VM_IO_RTU_PAIR=COM20:COM21`（沿用 F25 的既有约定）；③ 没装时 S35 记 **SKIP 并写反证**（`Win32_SerialPort` 查不到 COM20/COM21），按 R38 不许写成"跳过：环境不支持"了事。

### 7.1 Modbus TCP 映射（端口 19520，unit id = 1..6）

> **地址口径按 R137**：`Address` 是**原始协议地址**，不是 `4xxxx` 编号。仿真器只认原始地址，这正好复现"上位机把 40001 当原始地址"的经典坑。

| 工位 | 区 | 原始地址 | 长度 | 内容 | 方向 |
|---|---|---|---|---|---|
| 1..6 | Holding (0x03/0x10) | 0 … 7 | 8 | 命令区：`[0]=启动`,`[1]=复位`,`[2]=配方号`,`[3..4]=工件ID`,`[5..7]=保留` | 上位机 → 仿真 |
| 1..6 | Input (0x04) | 0 … 15 | 16 | 状态区：`[0]=状态字`,`[1]=节拍计数`,`[2]=OK数`,`[3]=NG数`,`[4]=结果码`,`[5]=缺陷码`,`[6..11]=测量值×1000`,`[12..15]=保留` | 仿真 → 上位机 |
| 1..6 | Coil (0x01/0x05) | 0 … 7 | 8 | 握手位：`[0]=就绪`,`[1]=完成`,`[2]=允许`,`[3]=报警`,`[4..7]=保留` | 双向 |
| 1..6 | Discrete Input (0x02) | 0 … 15 | 16 | 直接投影 §3.3 的 DI | 仿真 → 上位机 |

**字节序**：每个工位独立可配（`ABCD`/`CDAB`/`BADC`/`DCBA`），默认 `ABCD`（与 `DeviceSimulator` 轮转分配不同 —— 这里固定，便于定位）。

### 7.2 S7-1200 映射（19530 / 19531 / 19532，三台）

### 7.4 世界投影：地址 → 信号（唯一映射规则）

所有协议的地址不是"另写一套假数据"，而是**世界模型的一次投影**：

1. 每个 `(deviceId, area, offset)` 在 `devices.json` 里登记为一条 `SignalBinding`：`{ signal: "ST3.resultCode" | "ST3.meas[0..7]" | "DI[6]" | "DO[9]" | "ST11.chTemp[0..63]" | "ST13.slot[0..99].palletCode" }`。
2. 每 tick 结束，内核把世界状态写进 `SignalTable`（`Dictionary<string, double>`，值带单位与量化位）。
3. 协议层按 `SignalBinding` 把 `SignalTable` 编码成各协议的寄存器 / DB / 位区 —— **编码只有一份**，`PollAddress.MaxSegmentUnits`（F20）决定一次能带多少。
4. 上位机写入反向：协议层解出 → 写 `SignalTable.writeQueue` → 下一 tick 边界统一应用（§4.3 输入锁存）。

> 这条规则的意义：**加一台设备只改 `devices.json`，不改内核、不改协议层**；而"地址错位 / 字序错 / 单位错"这类 bug 一定会在投影层暴露（S34 钉 `devices.json` == §3.5 == §7 == 上位机导出配置 四处一致）。

### 7.5 物理量投影（力 / 扭矩 / 温度，v2.0）

产线里有些"信号"不是开关也不是位置，而是随运动耦合的物理量。它们**不参与动力学求解**（用户已裁决保真度 = 几何 + 时序），只按**运动学结果**解析计算：

| 物理量 | 归属 | 计算式（简化模型） | 暴露为 |
|---|---|---|---|
| 压装力 | `ST4.Press1/2` | `F = k·depth + c·v`（`k=200N/mm`、`c=5N·s/mm`，`depth` 由轴位置积分得到） | Modbus Input `[6..11]` ×1000、S7 `DB1` Real |
| 封口温度 | `ST8.Seal` | 一阶惯性 `T' = (Tset − T)/τ`，`τ=2s`，加热输出 = `DO[44]` | MC `D10` ×10 |
| 螺丝扭矩 | `ST12.Screw` | 到设定圈数后 `T = Tset ± 3%` 抖动（用种子） | RTU `Input[0..3]`、FINS `DM40` |
| 老化柜温度 | `ST11` 64 通道 | 每通道一阶惯性 + 0.1℃ 噪声，`Tset` 可配 | S7 `DB10` Real ×64 |
| 负载惯量 | `ST10.PalletZ` | 加速度 × (空载 + 箱数 × 单箱质量) → 只影响**速度曲线饱和判定** | 内部，供 §6.2 曲线断言 |

> **诚实边界**：这些是"看起来像真的"的投影，不是物理仿真。判据只有一条 —— **上位机侧的判定逻辑（阈值 / 滤波 / 报警）能否被正确驱动**；算出来的力曲线与真实压装机不会一致，也不该一致。

## 8. 协议

### 8.1 版本化与握手

```
POST /v1/hello   {"proto":1,"client":"VisionMaster","role":"camera|motion"}
→ {"ok":true,"proto":1,"sim":"LineSim","build":"2.0.0","world":"line-3x13st-44ax"}
```

> **只有相机流与运控通道走本协议**；6 种工业协议（Modbus/S7/MC/FINS/自由/RTU）由各自的标准栈处理，**没有 `hello`**——它们的"版本协商"就是协议本身的帧格式与从站标识。v2.0 更正：v1.3 曾把 `role` 写成 `camera|motion|modbus|s7`，与"标准栈"事实不符。

**端口规划（唯一登记处，S34 与 §8.1 表对齐）**：

| 段 | 端口 | 用途 |
|---|---|---|
| 宿主自身（既有，R176） | `19000` 收图 / `19100` 相机服务 / `8080` SCADA Web | 仿真器**不许占用**；启动自检会拦 |
| 仿真器 | `19500` 相机流 | HTTP，本协议 |
| 仿真器 | `19510` 运控 | TCP JSON-lines，本协议 |
| 仿真器 | `19520` | Modbus TCP（unit 1..6） |
| 仿真器 | `19530` / `19531` / `19532` | S7 ×3 |
| 仿真器 | `19540` / `19541` | 三菱 MC ×2 |
| 仿真器 | `19550` / `19551` | 欧姆龙 FINS ×2 |
| 仿真器 | `19560` / `19561` | 自由协议 ×2 |
| 仿真器 | `COM20` / `COM21` | Modbus RTU ×3（默认关闭） |

> **12 个 TCP 监听端口**是本方案的第二大代价（§0 rev#38）：本机防火墙需放行 `19500–19561` 整段，且端口被占时的报错必须写清"哪个端口、哪台设备"（`--check-ports` 子命令，S34 的启动期部分）。

- 版本不匹配 → **双方都拒绝进入 Online**（S3）。
- 每条连接先 `hello` 再业务。**未握手就发业务的拒绝语义按传输分开写**（v1.3 更正：原稿只写 HTTP 412，但 19510 是 TCP JSON-lines，没有状态码）：
  - HTTP 通道（19500 相机）：`412 Precondition Failed` + JSON 错误体 `{"ok":false,"err":"no_hello"}`；
  - TCP 通道（19510 运控、19520/19530 由标准协议栈处理不适用）：回 `{"ok":false,"err":"no_hello"}` 后**关闭连接**。
- 所有消息带 `proto` 字段，未知字段**忽略不报错**（前向兼容）。

### 8.2 相机流协议（端口 19500）

| 通道 | 端点 | 说明 |
|---|---|---|
| 控制 | `POST /v1/camera/{id}/trigger` | 触发一次；body `{"tick":<可选>}`；回 `{"accepted":true,"tick":n}` |
| 控制 | `POST /v1/camera/{id}/config` | 设置曝光/增益/触发源（对应 `CameraSettings`） |
| 控制 | `GET /v1/camera/{id}/ping` | 心跳，1Hz |
| 数据 | `GET /v1/camera/{id}/stream` | **长连接**，服务器推帧 |

**帧格式**（`Content-Type: application/octet-stream`）：

```
[4B 大端 帧总长][4B 大端 头长][头 JSON(UTF-8)][像素数据]
头 = {"tick":12345,"cam":"CAM3","w":2448,"h":2048,"ch":1,"bits":8,
      "exposureUs":800,"gain":0.0,"seq":7,"ts":1697...}
```

- **头里只有成像参数，没有真值**（S15 静态扫描帧头字段白名单）。
- 像素：mono = 1 通道 8bit 行优先；color = BGR 3 通道。
- **背压与丢帧可观测性（v1.3 更正）**：发送队列满 → LineSim 丢最旧 + `seq` 跳号。**上位机侧的两个计数器含义不同，别混**：宿主环形队列溢出计 `OverflowCount`（`CameraDeviceBase.cs:87`、`:529` `TrimOverflow` 里 `Interlocked.Add(ref _overflow, dropped)`），入帧被拒才计 `DroppedFrameCount`（`:90`、`:454/:470/:477`）。LineSim 发送侧的丢帧**到不了上位机**——驱动没有上报丢帧的 API（`_dropped` 私有）。所以：插件侧按 `seq` 缺口自己计数（存 `SetDetail` 或日志），断言查 `OverflowCount` 而不是 `DroppedFrameCount`；若要上位机看见传输丢帧，得加契约方法（如 `protected void ReportDroppedFrames(int n)`）→ 走 R12 评审，**本期不做**。
- **数据面三条硬约束（v1.3 补）**：① 帧总长上限 **64MB**，超限即断连并记错（4B 大端可表达 4GB，直接 `new byte[n]` 会 OOM）；② 客户端读取必须用 `HttpCompletionOption.ResponseHeadersRead` + 循环读满（`ReadExactly`），否则 `HttpClient` 会缓冲整包、长连接永远不出帧；服务端逐帧 flush；③ 断流即**丢弃整条连接的缓冲**、不尝试续帧，重连从 `hello` 重来、`seq` 归零。

### 8.3 运控协议（端口 19510）

| 操作 | 请求 | 响应 |
|---|---|---|
| `hello` | `{"op":"hello","proto":1}` | `{"ok":true,"card":"SIM20","axes":20,"din":32,"dout":32,"caps":{...}}` |
| `enqueue` | `{"op":"enqueue","id":"c1","kind":"MoveAbsolute","axis":4,"pos":123.45,"speed":300,"acc":1000,"timeoutMs":5000}` | `{"ok":true,"accepted":true,"id":"c1"}` |
| `poll` | `{"op":"poll"}` | `{"tick":n,"state":"Online","axes":[{...20}],"din":"<32hex>","dout":"<32hex>"}` |
| `estop` | `{"op":"estop"}` | `{"ok":true}` |
| `io.write` | `{"op":"io.write","port":5,"value":true}` | `{"ok":true}` |
| `io.read` | `{"op":"io.read","port":3}` | `{"ok":true,"value":true}` |
| `home` | 走 `enqueue` + `kind:"Home"` + `homeMode` | 同上 |

- `poll` 由上位机驱动（对齐契约的"轮询缓存"模型，F5），**仿真器不主动推**。
- `poll` 频率默认 10ms（与 `VirtualMotionCard.PollIntervalMs` 同口径），可配 1–1000。
- 每轴快照字段 = `AxisStatus` 全部字段（`PhysicalIndex`/`PositionMm`/`VelocityMmPerS`/`InPosition`/`Moving`/`Enabled`/`PositiveLimit`/`NegativeLimit`/`Origin`/`EmergencyStop`/`Alarm`/`AlarmMessage`/`Timestamp`）。
- 单次 `poll` 报文 ≈ 5.5KB（44 轴 × 约 120B + 头部），100Hz ≈ 550KB/s，可接受（v2.0 从 3KB 上调）。

### 8.4 为什么不用 gRPC / 不引第三方

| 方案 | 否决理由 |
|---|---|
| gRPC | 需 `Grpc.Tools` + HTTP/2，仿真器要能单文件交付、零依赖；且契约信息量用 JSON 足够 |
| WebSocket | 相机帧本来就是定长块 + 长度前缀，WS 再加一层帧头无收益；且要额外依赖 |
| 现成 OPC UA 栈 | 重型依赖，且与"零引用"（C1）冲突 |

**取舍（v1.3 写死，消除 v1.2 的自相矛盾）**：控制走 HTTP/JSON（易调试、可 curl）；**相机数据面也走 HTTP 长连接**（`GET /v1/camera/{id}/stream` + 长度前缀帧），**不再提"裸 TCP"**——同一端口、同一套握手与错误语义，客户端代码只有一份，坑也只有一套（三条约束见 §8.2）。

### 8.5 错误与重连

| 情况 | 行为 |
|---|---|
| 连接断开 | 上位机插件侧指数退避重连（200ms → 3.2s，上限 5s），状态 `Connecting` |
| 3s 无心跳 | 视为掉线 → `NotifyDeviceLost`（运控）/ `NotifyAlive` 超时（相机） |
| 仿真器未启动 | 插件 `Connect()` 返回 false 并给出明确错误（"LineSim 未运行或端口 19500 不可达"），**不许静默成功** |
| 协议版本不符 | 拒绝 Online，错误文案带双方版本 |

## 10. 3D 视图

### 10.1 选型

| 方案 | 结论 | 理由 |
|---|---|---|
| **A. WPF `Viewport3D`（原生）** | **基线** | 零 NuGet 依赖（C1 精神一致）、与仓库 WPF 技术栈一致、`Model3DGroup` 冻结后 60k 三角形 30fps 足够；代价是缺少轨道相机/拾取等便利设施，需自写约 300 行 |

| C. three.js（嵌 WebView2） | 否决 | 仓库无 WebView2（F10），且 R126「Web 产物是设计媒介不是交付物」——把 3D 做成网页会把仿真器拖成第二套前端 |
| D. SharpDX / Vortice 直连 D3D | 否决 | 依赖重、调试难，收益与 A 相比不明确 |

### 10.2 场景结构

```

├─ Ground（地面网格 20m×10m，浅灰，1m 格）
```

## 11. 闭环用例

> **范围（v2.0）**：11.1–11.5 是 **A 线**的五个闭环（v1.3 定稿）；v2.0 增补 **11.6 B 线包装/码垛**、**11.7 C 线老化/返修/立库**——后两条复用同一套成像链与投影层，只是工位与设备不同，不再重复设计。

### 11.1 定位引导（ST1 → ST2）

```
CAM1 软触发 → Matching（模板：料仓工件）→ (row,col,angle)
  → PoseTransform（九点标定矩阵）→ 机械 (x,y,θ)
  → MotionMove（ST2.PickX/Y/R）→ DO5 夹爪 → DI3 真空到位 → 抓起
```

**真值闭环**：抓取点与工件真实中心的偏差 ≤ **0.2mm**（S16）。偏差来源可分解：标定残差、模板匹配亚像素、机械重复性。

### 11.2 尺寸检查（ST3 / CAM3）

```
分度到位（DI6）→ CAM3 软触发（曝光 800μs）→ 背光图
  → CaliperMeasure（4 条边）×2 + GeometryFinder（孔径/孔距）
  → 与真值比 → 偏差 / 重复性
```

**判据**：连续 100 件，孔径测量**重复性 σ ≤ 0.02mm**、**偏差 ≤ 0.01mm**（S17）。

### 11.3 缺陷检测（ST3 / CAM4）

```
同轴光 → CAM4 软触发 → BlobDetect（划伤/脏污）+ Yolo（复杂缺陷）
  → NG 判定 → 结果码写 Modbus 输入寄存器[4]
```

**判据**：缺陷谱全开时，**检出率 ≥ 95%**、**误检率 ≤ 5%**（S18，参数需调，数值为实现期目标而非承诺）。

### 11.4 读码与复检（ST5）

```
CAM6 → CodeReader（DMC）→ 字符串与真值比对 → 写入 DB2
CAM5 → Matching（装配特征）→ 压装深度真值比对 → OK/NG
```

**判据**：读码正确率 100%（仿真无污损时）；引入污损后正确率下降且**可复现**。

### 11.5 分拣（ST6）

按 ST3/ST5 判定 → 分拣道 1/2/3 → DO9/DO10 → 计数写 Modbus。**判据**：100 件分流计数与真值完全一致。

### 11.6 B 线：包装 + 贴标 + 码垛（v2.0）

```
CAM7 软触发 → Matching + CaliperMeasure → 复判尺寸（与 A 线结论一致率 ≥ 99%）
CAM8 → BlobDetect（袋内气泡/异物）+ ColorCheck（封口变色）→ 封口质量
CAM9 → CodeReader（新贴标签）+ Ocr → 与真值标签串比对
CAM10 → Matching（纸箱角点）→ 码垛位姿；CAM11 → BlobDetect（缺件/多件）
```

**判据**：① 复判与 A 线结论**一致率 ≥ 99%**（不一致即两套成像链有系统性偏差，这正是"多相机交叉验证"的价值）；② 贴标读码 100%；③ 码垛 12 个垛位各 3 次抓取定位误差 ≤ 0.5mm（真值可反算）；④ 封口温度投影（§7.5）在 `Tset ± 2℃` 内稳定。

### 11.7 C 线：老化 + 返修 + 立体库（v2.0）

```
CAM12（0.2fps）→ 老化柜夹具到位 + 指示灯状态（低频，验"长周期不丢帧"）
CAM13（显微）→ 焊点 BlobDetect + 尺寸测量 → 与返修真值比对
CAM14 → CodeReader（托盘码）→ 库位映射；D09(S7) 与 D15(自由协议) 双通道校验
```

**判据**：① 老化柜 64 通道温度全部经 `DB10` 被上位机读到（**必须拆成 3 个变量，验 R153**）；② 返修 30 件/小时不阻塞 A/B 线（三线并发）；③ 立体库 100 库位 × 50 次出入库，`DB20` 读到的库位状态与真值零差异；④ 同一托盘码在 S7（D09）与自由协议（D15）两条通道上读到的值**必须一致**（不一致即投影层 bug，S34 的运行时补充）。
