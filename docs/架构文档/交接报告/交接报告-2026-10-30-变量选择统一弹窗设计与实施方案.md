# 交接报告 — 变量选择统一弹窗：设计与实施方案（2026-10-30）

> 类型：**设计方案，未改任何产品源码、未构建、未跑闸门**。
> 触发：用户「系统中不少地方变量绑定和变量名获取都用下拉框，几十条没事，数据量大时页面假死。请设计一套方案：让这些地方改用现有的变量绑定弹窗，并同时考虑全局变量和运行时变量」。
> 前置参考：`交接报告-2026-10-29-变量选择统一弹窗可行性方案.md`（下称"参考文档"）。
> 本文与该参考文档的关系：**§5 的实测数据是新的**（已实跑 `VariablePickerProbe`，全部 PASS，有容器数硬数字）；**§2 的语义裁决沿用参考文档**；**§9 有一处与参考文档结论相反的建议，需要用户拍板**。

---

## 1. 结论先行

| 问题 | 结论 |
|---|---|
| 卡死是"用了下拉"造成的吗 | **不是下拉这个形态本身**，而是**列表工程**：不虚拟化 + 每次按键 `Clear()`+`Add()` + 按行复制候选。换弹窗只是把同一份 N 条列表换个宿主，**不修工程照样卡**（参考文档 §3、本轮 §5 实测确认） |
| 能不能直接复用 `VariableBindingView`（现有绑定弹窗） | **语义上不能**：它的产物是 `LinkReference`（"这个**值**从哪来"），而这里是"写到**哪个名字**"。直接复用要么拿端口名当变量名（R33 记过的静默故障），要么给弹窗加"名字模式"（一个弹窗两种返回值，两个既有消费方都要分支） |
| 推荐 | **"同一套弹窗、同一份列表工程，独立视图与独立返回值"**：新建 `VariablePickerView`，视觉/交互/虚拟化完全照搬绑定弹窗（用户看到的就是同一个变量选择弹窗），但产物是 `VariablePickResult{Name, VariableId, Scope}`，**不碰 `LinkedSources`** |
| 顺序 | ① 修列表工程（不修则一切白搭）→ ② 抽弹窗 + 事件通道 → ③ 插件逐个迁 → ④ 收口 `LinkableValueEditor` 封闭集合下拉（同族雷） |

**一句话**：弹窗不是"更高级的下拉"，它是"把候选列表从行内搬到宿主侧、只实例化一次"。真正治卡死的是**虚拟化 + 过滤 + 快照共享**，弹窗只是让这三件事只做一次。

## 2. 为什么不能"直接复用现有绑定弹窗"（沿用参考文档的裁决）

| # | 理由 | 代码依据 |
|---|---|---|
| 1 | **名字不是端口** | `AssignmentRow.VariableName` 是普通字符串（`Models\AssignmentRow.cs:33-38`）；只有"值"是端口（`ValuePortName`）。绑定弹窗单绑定模式的前提是有端口：`LinkPathEvent.InputPortName` → 回调 `stepData.SetLink(port.Name, link)` |
| 2 | **弹窗的产物是"值"不是"名字"** | `LinkReference` 四种 `LinkKind` 全在回答"值从哪来"；`TargetPortName` 在步骤端口场景下是**端口名**，当变量名用 = 给不存在的变量赋值 |
| 3 | **这条路做过一次并被退役** | v3 在 `OnConfirm` 里 `RemoveLegacyNameLink` 明确删掉旧名字连线，`LegacyNameLinkAddress` 只留提示 |
| 4 | **规则明令** | §10 R33（名字类字段不许挂绑定）、§43 R188（取值只有绑定弹窗一条通道）、§45 R190（端口取值只许 `LinkableValueEditor` 与"运行时变量名手输"两种形态） |

> **但用户要的"统一体验"是合理的**：现在六个插件各写一套，长得都不一样。解法是**统一到同一个"变量选择弹窗"外观与交互**，而不是统一到同一个返回值契约。

## 3. 适用场景（按"该不该迁"分类）

### 3.1 该迁（写名选择，且名字空间是闭集或半闭集）

| 位置 | 现状 | 候选规模 | 结论 |
|---|---|---|---|
| `Plugin.Utility\VariableAssignmentPlugin` 全局列 | 自定义 `Popup` + `ItemsControl`（**不虚拟化**） | 实测 2414 / 10000 全实例化 | **首要目标**（缺陷集中地） |
| 同插件 运行时列 | 可编辑 `ComboBox`（**Fluent 模板不虚拟化**，实测 2414 → realized=2414） | 上游「变量定义」声明数（几十~几百） | 迁（但必须保留手输出口） |
| `Plugin.DataRecord` 变量列 | 可编辑 `ComboBox` + 字符串候选 | 全局变量数 | 迁 |
| `Plugin.ResultUpload` 变量列 | 可编辑 `ComboBox`（批 4 刚改的） | 全局变量数 | 迁 |
| `Plugin.CSharpScript` 共享变量声明表 | `ComboBox` + `VariableOption` 对象 | 全局+系统变量数 | 迁（对象绑定已有，改入口即可） |
| `ConditionEditorView` 判定变量 / 报警变量 | `ObservableCollection<string>` 下拉 | 变量数 | 迁 |
| `FlowResultSourceDialogView` 变量下拉 | `ComboBox` + 手写 `FilteredVariables`（`Clear()`+`Add()`） | 变量数 | 迁（并入统一弹窗后这段手写过滤可删） |

### 3.2 不该迁（不是"变量名"，或规模天然小）

| 位置 | 原因 |
|---|---|
| 枚举/极性/算法/相机/轴名/卡地址等固定候选 | 规模几十条以内，是**封闭语义**而非"变量名"，走 `LinkableValueEditor` 的 `StepConfigOptionKind` 即可；R33 要求"名字类用手填 + 候选下拉" |
| `LinkableValueEditor.EnumOptions` 承载的 `CommunicationVariableName` | **同族雷**（实测 10000 → realized=10000），但它是**值端口**的封闭集合，不能走名字弹窗；单独批次做下拉虚拟化 + 搜索（§7.4） |
| `ScadaVariablePickerView` | 绑 SCADA 的 `ScadaVariableRow`、内联色值、属 R191 暂停域，**不复用**（参考文档 §8.2 第 4 条） |
| SCADA 属性面板的变量选择 | 属组态场景，语义与端口绑定一致（走 Id），已有独立选择器 |

### 3.3 不需要动的

- **取值绑定**（端口 ← 全局变量 / 上游输出）：**已经统一**走 `LinkableValueEditor` 🔗 → `DataBindView`（R188/R189 收口），且该弹窗**已具备**虚拟化 + 高度有界（`VariableBindingView.xaml:1539` 的 `ListBox` + `UpdateCandidateMaxHeight`，1501 条从 6.2 s 修到 25~40 ms）。

## 4. 改造思路（四步，每步可独立验收）

### Step 0（已完成，本文档的依据）

`tools\probes\_VariablePickerProbe`（已登记 `probes.json`）实跑结果 **RESULT: ALL_OK**：

| 场景 | 实测 |
|---|---|
| S1 赋值插件全局浮层 2414 条 | `buttons=2416 items=2415` → **全实例化** |
| S1 同上 10000 条 | `buttons=10002 items=10001` → **全实例化**（线性增长，无回收） |
| S2 运行时可编辑 ComboBox 2414 条 | `realized=2414` → **Fluent 模板不虚拟化** |
| S3 `LinkableValueEditor` 封闭集合 10000 项 | `realized=10000` → **不虚拟化** |
| **S4 目标形态**（虚拟化 + `ICollectionView.Filter` + 高度有界）5000 条 | **`realized=6`**，过滤 **21 ms** |

> **判据取"实例化容器数"不取耗时**（R65 口径）：5000 条只实例化 6 行是可判定、可反证的表征；耗时随机器浮动。

### Step 1（必做，不涉及任何公共契约）— 修列表工程

即使不迁弹窗，这三处也必须修，否则弹窗只是搬运问题：

| 文件 | 改动 |
|---|---|
| `AssignmentRowVm.cs` | `FilteredCandidates` 改 `ICollectionView` + `Filter`（不再 `Clear()`+`Add()`）；`Candidates` 按 scope **共享一份**只读快照（不再按行复制） |
| `VariableAssignmentView.xaml:501-560` | 浮层 `ItemsControl` → 虚拟化 `ListBox`（`VirtualizationMode=Recycling`、`CanContentScroll=True`）+ **高度按视口有界、3 屏门槛**（照绑定弹窗 `UpdateCandidateMaxHeight` 的手法，含"十几行以内不出现内层滚动条"） |
| `VariableAssignmentPlugin.cs` | `BuildCandidates` 不再每行全扫；`RefreshAllRows` 只在上下文变化时重建一次；`RefreshNameCandidates` 的 `Contains` 去重换 `HashSet`；`FindVariable` 的 `FirstOrDefault` 改 `Dictionary` 索引 |

### Step 2 — 抽公共弹窗 + 事件通道

**新增**（宿主侧，带完整主题令牌）：

- `VisionMaster\Views\DialogViews\VariablePickerView.xaml(.cs)`
- `VisionMaster\ViewModels\DialogViewModels\VariablePickerViewModel.cs`
- `ProcessViewModel` 新增一个订阅与处理函数（照 `OnLinkPathEvent` 的写法）

**列表工程直接复用绑定弹窗的已验证做法**：`ListBox` + `VirtualizingStackPanel`（`Recycling`）+ `UpdateCandidateMaxHeight` 的"视口剩余高度 + 3 屏门槛" + `ICollectionView.Filter`（不 `Clear()`+`Add()`）。**不复制代码，复制做法**——两处都调同一套 `CandidateListSizer` 辅助（见 §7.2）。

**通道**（必须走宿主，插件拿不到 `IDialogService`）：

```csharp
// Shard\Core.Interfaces\PickVariableNameEvent.cs（纯加性，不改既有签名）
public sealed class PickVariableNameEvent
{
    public string Scope { get; set; }          // "Global" / "Runtime"
    public string CurrentName { get; set; }
    public bool AllowFreeText { get; set; }    // 仅 Runtime 可为 true（R190 唯一例外）
    public bool AllowRuntime { get; set; }     // 弹窗左栏是否显示"运行时变量"分组
    public Action<VariablePickResult> OnPicked { get; set; }
}

public readonly record struct VariablePickResult(string Name, Guid VariableId, string Scope);
```

复用既有 `GlobalEventBus.Subscribe<PickVariableNameEvent>` → `ProcessViewModel` → `dialogService.ShowDialog("VariablePickerView", …)` → 回调 `OnPicked`。**与 `LinkPathEvent` 完全同构**，这条通道已在插件视图里跑通（赋值插件的值列 🔗 就是它）。

### Step 3 — 插件逐个迁（同批删旧实现，不许两套并存）

顺序：`VariableAssignment` → `DataRecord` → `ResultUpload` → `CSharpScript` → `ConditionEditor` → `FlowResultSourceDialog`。
每个插件只保留：**一行名字 + 类型徽标 + 失效/手填徽标 + 提示行，整块可点 → 开窗**。

### Step 4 — 收口 `LinkableValueEditor` 封闭集合下拉（同族雷，独立批次）

`LinkableValueEditor.xaml:213` 的 `EnumOptions` 下拉自带模板（`OverridesDefaultStyle="True"` + 裸 `ItemsPresenter`，**未声明 `ItemsPanel`、未设 `MaxDropDownHeight`**），实测 10000 项全实例化。修法与 Step 1 同源（虚拟化 + 有界 + 搜索），但影响**所有** `OptionKind` 端口，单独一批做。

## 5. 全局变量 vs 运行时变量（两个不同的名字空间）

这是本方案最需要区分的部分——参考文档 §4.1 已裁定，本轮沿用并补上批 1~3 的新能力：

| | 全局变量 | 运行时变量 |
|---|---|---|
| 名字空间 | **闭集**：必须先在变量管理里存在 | **开集**：`Context.SetVar(name, …)` 可造出新名字；`CreateIfNotExists` 允许写"现在还不存在"的名字 |
| 能否只给列表 | **能**（列表即全集） | **不能**（列不全） |
| 身份 | 有 `VariableId`（**批 3 起已落进配置模型**） | 无稳定身份（每轮由「变量定义」重建） |
| 弹窗行为 | 只允许从列表选；**选中即回填 `Name` + `VariableId`** | 列表给"上游已声明"的那些 + **必须有一个"使用这个名字"出口**（输入框 + 明确按钮），否则堵死 `SetVar` / `CreateIfNotExists` 的合法用法（R190） |
| 失效态 | 名字查不到 → 「已失效」只读项（不清空、不自动替换） | 手填且不在上游声明里 → 「手填」徽标 + 提示"运行期会报错 / 会新建" |
| 重名（多设备） | 候选带设备后缀 `Alarm1[48] · B_PLC`（批 4 已做），**按 Id 落库** | 不涉及（运行时变量无设备） |

**关键设计**：弹窗返回 `VariablePickResult{Name, VariableId, Scope}`。
- 全局：`VariableId` 非空 → 运行期 Id 优先（批 3 已在用 `SharedVariables.TryWrite(Id, Name)`）；
- 运行时：`VariableId` 恒为 `Guid.Empty` → 运行期按名解析（这是既有语义，不改）。

**一屏两栏**：左栏"全局变量 / 系统变量 / 上游运行时变量"三组（数据源 = `PluginConfigContext.Variables` 快照，与现在的候选同源），顶部统一搜索框；运行时模式下额外多一行"使用「XXX」（手填名）"。

## 6. 性能优化点（按收益排序，全部有实测依据）

| # | 优化 | 依据 | 预期 |
|---|---|---|---|
| 1 | **虚拟化 + 高度有界**（3 屏门槛） | S4：5000 条 `realized=6`；绑定弹窗 1501 条 6.2 s → 25~40 ms | 打开从"秒级卡死"到"<50 ms" |
| 2 | **`ICollectionView.Filter` 替代 `Clear()`+`Add()`** | S4：过滤 **21 ms**；现状是 1 次 Reset + N 次 `CollectionChanged` + 容器整批拆建 | 键入无卡顿 |
| 3 | **候选快照按 scope 共享一份**（不按行复制） | 现状 32 行 × 2414 = 7.7 万对象/次重建 | 行数增加不再线性恶化 |
| 4 | **索引化查找**（`FindVariable` 用 `Dictionary`） | 现状每次 `RefreshHint` 走 3~4 次 `FirstOrDefault` | 刷新成本 O(1) |
| 5 | **打开时零构建**：弹窗才建候选，关闭即弃 | 行内不再持有任何 `List<NameCandidate>` | 行 VM 常驻内存与 N 无关 |
| 6 | **脏检查**：文本未改不重解析（批 4 的 `IsTextDirty`） | 已落地 | 确认时不做无谓全扫 |
| 7 | **弹窗复用同一份 `ICollectionView` 缓存**（同一次打开内） | — | 二次打开无重建 |

**反面清单（不要做）**：
- ❌ 不要给行内下拉"加一个 `MaxDropDownHeight`"就以为修好了——`ItemsControl` 本身不虚拟化，封高只改观感不改实例化。
- ❌ 不要在 `Filter` 回调里 `new` 集合——`Predicate` 里只做 `Contains`，不物化。
- ❌ 不要按行 `Clone()` 候选快照——共享只读实例。

## 8. 风险

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| 1 | **语义混淆**：用户以为"在弹窗里选了 = 建立了连线" | **高** | 弹窗标题写死「选择变量名（不建立连线）」；插件行内只显示名字，不显示 🔗；`PickVariableNameEvent` 的注释与手册明确"不写 `LinkedSources`" |
| 2 | **运行时开集被堵**：只给列表 → `SetVar` 造的变量无法选中 | **高** | 必须有"使用这个名字"显式出口（§5）；断言覆盖"确认列表外名字" |
| 3 | **交互步数增加**（点开 + 选 + 关 vs 点开 + 选） | 中 | 弹窗内 ↑↓ + Enter 直接确认关闭；实测相当于"点开 + 回车" |
| 4 | **公共契约变更**（`Core.Interfaces` 加事件） | 中 | 纯加性、无签名改动；按 R12 走一次架构评审 |
| 5 | **`Core.Controls` 逃出 R140 颜色闸** | 中 | 扫描根不含 `Shard`，色值只能内联；文件头写理由（先例 `LinkableValueEditor.xaml:199-200`）。**但本方案把弹窗放在宿主侧（`VisionMaster\Views`），主题令牌可用，只有 `CandidateListSizer` 落在 `Shard`（无颜色，纯尺寸计算）**——这条风险因此大幅降低 |
| 6 | **断言改动面大**（6 个插件 + 2 个宿主） | 中 | 按 Step 3 逐个迁，每步独立验收 |
| 7 | **弹窗模态叠加**：插件配置窗开着再弹选择窗 | 低 | 与现在 `LinkPathEvent` 同一形态（已跑通）；关窗时机照 `OnDialogClosed` 收尾 |
| 8 | **未实测项**：`PluginVariableOptions.Build` 在几万变量下的单次成本 | 低 | 按代码是 O(N) 一次；Step 1 顺手量一次 |

## 9. 需用户拍板的一处（与参考文档结论相反）

参考文档 §5.2 把"给 `DataBindView` 加名字模式"判为 ❌（一个弹窗两种返回值）。**本轮我建议：仍然是新建 `VariablePickerView`，但把"长相与交互"做到与绑定弹窗完全一致**——用户看到的是同一个变量选择弹窗，只是返回的东西不同。

如果你要的是**字面意义上复用同一个 `VariableBindingView`**（同一个 View、同一个 VM、加一个 `IsNamePickMode` 开关），代价是：

1. `VariableBindingViewModel` 要维护两套返回值（`BoundLink` / `VariablePickResult`）；
2. 两个既有消费方（`ProcessViewModel`、`ConditionEditorViewModel`）都要分支；
3. 每次改绑定弹窗都要考虑"名字模式会不会被带坏"。

**我的建议**：不这么做，用 §4 方案（独立视图、共享做法与尺寸辅助件）。如果你坚持要同一个 View，我按你拍板执行，但上面三条要写进评审记录。

## 10. 最终方案总结

1. **治卡死靠列表工程，不靠换壳**：虚拟化 + 高度有界（3 屏门槛）+ `ICollectionView.Filter` + 候选共享 + 索引查找。实测目标形态 5000 条只实例化 **6 个容器、过滤 21 ms**。
2. **形态统一到"变量选择弹窗"**：新建 `VariablePickerView`，**视觉/交互/虚拟化完全照搬绑定弹窗**，产物是 `VariablePickResult{Name, VariableId, Scope}`；**不写 `LinkedSources`**，守住 R33/R188/R190。
3. **通道复用既有先例**：`GlobalEventBus` + `PickVariableNameEvent`（纯加性契约）→ `ProcessViewModel` → `dialogService`。插件仍然只引用 `Core.Interfaces` + `Core.Controls`。
4. **两个名字空间分开处理**：全局 = 闭集 + 可返回 `VariableId`（批 3 已落）；运行时 = 开集 + **必须留"使用这个名字"手输出口**。
5. **存量零迁移**：`.vms` 的 `VariableName` 与 `VariableId` 语义都不变；旧配置照常打开；两套 UI 并存期不超过一个批次。
6. **分四步落**：Step 1 修工程（不涉及契约，必做）→ Step 2 抽弹窗 + 通道 → Step 3 六插件逐个迁（同批删旧实现）→ Step 4 `LinkableValueEditor` 封闭集合下拉（同族雷，独立批次）。

**工作量估算**：Step 1 ≈ 1~2 天；Step 2 ≈ 1~2 天；Step 3 每插件 0.5~1 天（共 4~6 天）；Step 4 ≈ 1 天。合计 **7~11 天**（含断言与验收）。
