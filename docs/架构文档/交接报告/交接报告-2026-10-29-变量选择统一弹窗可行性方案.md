## 1. 当前状态（结论先行）

| 问题 | 结论 |
|---|---|
| 卡死是"选了下拉而不是弹窗"造成的吗 | **不是**。卡死来自列表工程（不虚拟化 + 每次按键全量重建 + 每行复制全量候选），换成弹窗只是把同一份 2414 条列表搬到另一个窗口 |
| 名字列能不能改成绑定弹窗 | **不能按现有语义改**。名字不是端口，绑定弹窗的产物是"值"（`LinkReference`），落不到 `AssignmentRow.VariableName` 上 |
| "所有绑定全局/上游变量统一走弹窗" | **要分两类**：**取值绑定**已经统一（`LinkableValueEditor` 🔗 → `DataBindView`）；**写名选择**没有统一，且不该复用绑定语义，应统一到一个"名字选择器"控件 |
| 推荐路线 | 先修列表工程（必做，1~2 天）→ 再抽公共 `VariableNamePicker`（可选，跨插件收口）→ `DataBindView` 加"名字模式"**不做** |

## 3. 卡死原因（按代码，不按推测）

按影响排序，四处叠加（量级按 3000 条推算，实测口径见 §5 的探针项）：

| # | 位置 | 机制 |
|---|---|---|
| A | `VariableAssignmentView.xaml:501-560` | 全局浮层 `ScrollViewer + ItemsControl`，`ItemsControl` **结构上不支持虚拟化**。打开浮层即把 N 条全部实例化：每项 = `Button` + `Grid` + `StackPanel` + 3×`TextBlock` + `Style` 触发器 |
| B | `Models\AssignmentRowVm.cs:46-54 → :163-177` | 打开浮层时 `IsGlobalNameOpen=true` 先把 `GlobalSearchText` 清空 → 立刻 `ApplyGlobalFilter()`；之后每敲一个字符再来一次。实现是 `FilteredCandidates.Clear()` + 逐条 `Add` = 1 次 Reset + N 次 `CollectionChanged`，绑在已实例化的 `ItemsControl` 上 → 容器整批拆建 |
| C | `VariableAssignmentPlugin.cs:428-452 / :551-559 / :908-930` | 候选**按行复制**：`BuildCandidates` 每行重扫全表；`RebuildRowVms` 在 `Rows.CollectionChanged`（增/删/移行）时对**所有行**重跑；`RefreshAllRows` 又在 `SetConfigContext`/`Initialize`/`ApplyConfigValues`/`OnConfirm` 各跑一遍。32 行 × 5 万 = 160 万对象/次重建 |
| D | `VariableAssignmentPlugin.cs:395-426` + `AssignmentRowVm.cs:108-109` | `FindVariable` 是 `FirstOrDefault` 线性扫；单次 `RefreshHint` 被调 3~4 次（`BuildHint` 两次 + `GetTypeText` + `IsInvalidGlobal`）。每次键入都走一遍 |

**关键叠加**：全局行选中一个名字 → `Row.VariableName` 变更 → `OnRowPropertyChanged`（`:538-541`）→ `RefreshCandidates()` 整表重建 → 又把正开着的浮层列表重建一次。所以"打开卡、选一个更卡"。

**同形态缺陷已被实测过一次**：`docs\code-changes\2026-10-29-变量绑定候选列表卡顿（虚拟化失效）.md` —— 绑定弹窗 1501 条候选全量实例化 **6157 ms**，改成"高度有界 + 虚拟化"后每次重建 **25~40 ms**、只实例化 9~10 个容器。赋值插件的浮层比它更差：那边是 `VirtualizingStackPanel` 被无限高度架空，这边是**面板根本不支持虚拟化**。

**同族风险（影响"统一"方案）**：`Shard\Core.Controls\LinkableValueEditor.xaml:202-312` 的封闭集合下拉自带模板（`OverridesDefaultStyle="True"` + 裸 `ItemsPresenter`，未声明 `ItemsPanel`、未设 `MaxDropDownHeight`），且 `EnumOptions` 是全量 `ObservableCollection`（`LinkableValueEditor.xaml.cs:401-419` 每个端口实例都全量填）。今天"轴名/卡地址"只有几十条看不出来；`StepConfigOptionKind.CommunicationVariableName`（设备变量表可上万条）已经是同一颗雷。**这一条要在探针里实测，未实测前不得当成已确认。**

## 4. 为什么不能改成"链接变量弹窗"

四条，前两条是语义，后两条是本仓库的既有裁决：

1. **名字在 v3 行模型里不是端口。** `AssignmentRow.VariableName` 是普通字符串配置（`Models\AssignmentRow.cs:33-38`），只有"值"是端口（`ValuePortName`，`:69-79`）。绑定弹窗单绑定模式的前提是有端口：`LinkPathEvent.InputPortName` → `ProcessViewModel.cs:562-588` → 回调里 `stepData.SetLink(port.Name, link)`。名字行**没有端口可写**。
2. **弹窗的产物是"值"，不是"名字"。** `LinkReference` 的四种 Kind（`LinkReference.cs:14-29`）全部在回答"这个值从哪来"，编译器据此把值灌进端口；而名字行要的是"往哪个变量写"，运行期由 `TryAssign` 用 `row.VariableName` 去 `context.GlobalVariables.TryWrite(name, value)`（`VariableAssignmentPlugin.cs:1069-1141`）。若把 `link.TargetPortName` 当名字用：用户选"上游步骤.某端口"时 `TargetPortName` 是**端口名**，写进去等于给一个不存在的变量赋值 —— 正是 R33 记的"拿值当名字"。
3. **这条路 v2 走过，v3 主动退役了。** 旧 `InputPort<string>("Name")` 可以被连线（`VariableAssignmentPlugin.cs:43`），v3 在 `OnConfirm` 里 `RemoveLegacyNameLink`（`:902-906`）明确删掉旧名字连线，`LegacyNameLinkAddress` 只留一行提示（`AssignmentRow.cs:97-102`）。也就是说"名字挂连线"在本仓库已经做过一次并被判定为缺陷。
4. **规则明令。** AGENTS.md §10 R33（名字类字段不许挂绑定）、§43 R188（取值只有绑定弹窗一条通道，画布连线不作为取值入口）、§45 R190（端口取值只许 `LinkableValueEditor` 与"运行时变量名手输"两种形态）。`LinkableValueEditor` 的 `IsClosedValuePort`（`.xaml.cs:211-233 / 597-641`）就是这条规则的实现。

> 一句话：**弹窗不是"更高级的下拉"，它是另一种语义（值 vs 名字）。** 把名字塞进去不是升级，是把已修好的静默故障装回去。

### 4.1 运行时变量是不是原因？（2026-10-29 补，回答用户追问）

**是第二个独立原因，但只解释"运行时那一列"，不解释"名字列整体"。**

| 作用域 | 名字空间 | 能否用封闭选择器 | 代码依据 |
|---|---|---|---|
| 全局 | **闭集**（必须先在变量管理里存在），且**可按 Id 寻址** | 能 | `GlobalVariableWriter.TryWrite(name)` 找不到就明确报错、不新建（`Core\Binding\GlobalVariableWriter.cs:59-72`）；另有 `TryWrite(Guid variableId, fallbackName, …)` 重载（`:96`） |
| 运行时 | **开集** | 不能 | ① 候选只能静态扫到上游「变量定义」节点：`FlowQueryHelper.TryGetDefinedVariable` 只认 `PluginTypeName.Contains("VariableDefinitionPlugin")`（`Engine\FlowQueryHelper.cs:244`）；② 运行期还能被 `Context.SetVar(name, value)` 造出新名字（`Plugins\Plugin.CSharpScript\ScriptContext.cs:132`），静态不可见；③ `CreateIfNotExists` 允许写一个"现在还不存在"的名字（`VariableAssignmentPlugin.cs:1133-1137`） |

所以 R190 把"运行时变量名手输"留作唯一合法例外，正是因为这个名字空间列不全。

但要注意两点，别把因果搞反：

1. **"绑定弹窗"对两个作用域都不成立**，与运行时变量无关——拦住它的是"名字不是值"（§4 前四条）。
2. **运行时变量不是"不能枚举"那么简单**：绑定弹窗**确实**列得出运行时变量（`FlowQueryHelper.GetAvailableVariablesTree:91-108` 的上游声明那一批），它列不出的是"运行期才会被 SetVar 造出来的名字"。也就是说，限制发生在**写名方向**，不在**读值方向**。

结论：如果真要统一成"名字选择弹窗"，**全局列可行（闭集 + 有 Id）、运行时列不可行（开集，必须留手输）**；而"绑定弹窗"两列都不可行。

## 5. 统一走弹窗的可行性

### 5.1 先分清两类操作

| 类别 | 现状 | 是否需要改造 |
|---|---|---|
| **取值绑定**（端口 ← 全局变量 / 上游输出） | **已经统一**：`LinkableValueEditor` 🔗 → `DataBindView`（R188/R189 收口） | 不需要改入口；只需保证候选列表在几万条下可用（今天的 2026-10-29 修复就是这块） |
| **写名选择**（这一步写到哪个变量） | **没有统一**，五处各写一套 | 需要统一，但**不是**统一到 `DataBindView` |

写名选择的现状（各自一套）：

| 位置 | 形态 |
|---|---|
| `Plugin.Utility\VariableAssignmentPlugin` | 全局 = 自定义浮层；运行时 = 可编辑 ComboBox（`VariableAssignmentView.xaml:402-621`） |
| `Plugin.DataRecord` | `VariableNameCandidates` + 可编辑 ComboBox（`DataRecordPlugin.cs:190-253`） |
| `Plugin.ResultUpload` | `UploadFieldDef.VariableName` 手输列 |
| `Plugin.CSharpScript` | 共享变量声明表（`CSharpScriptPlugin.cs:828-830`） |
| `Plugin.Comm`（读/写立即） | `InputPort<string>` + `OptionKind=CommunicationVariableName` → `LinkableValueEditor` 下拉（**已有统一的"名字端口"机制**） |
| `Plugin.ImageAssign` | `TargetVariableName` 纯手输 `InputPort<string>`（`ImageAssignPlugin.cs:38`） |

### 5.2 三条路线与代价

| 路线 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **A：抽公共名字选择器**（推荐） | 新建 `VariableNamePicker`（`Core.Controls`，插件唯一可见的 UI 契约层），内部 = 搜索 + `ICollectionView.Filter` + 虚拟化列表 + 有界高度；输出 `{Name, VariableId, Scope, TypeName}`。赋值插件先切过去，再迁 `DataRecord` / `ResultUpload` / `CSharpScript` | 1 个新控件 + 每个插件删掉自己的实现；**不改任何公共契约**（`PluginConfigContext.Variables` 快照已够用） | ✅ 做 |
| **B：把名字变成封闭集合端口** | `StepConfigOptionKind` 加 `GlobalVariableName` / `RuntimeVariableName`，名字字段变 `IsFunctionalEnum` 端口 → `LinkableValueEditor` 自动渲染成"只能选、无 🔗" | 要动契约层枚举 + 宿主注册；**且**会把 2414+ 条塞进每个端口实例的 `EnumOptions`，而该下拉模板不虚拟化（§3 同族风险）→ 必须先修 `LinkableValueEditor` 下拉；另外候选会有两个来源（配置窗快照 vs 全局注册表）需要同步 | ⚠️ 只在"名字字段本来就该是端口"的新插件上考虑，存量不迁 |
| **C：给 `DataBindView` 加名字模式**（用户问的方案） | 新增 `IsNamePickMode`：隐藏左栏端口表，候选列表复用（已搜索+已虚拟化），返回名字而非 `BoundLink` | 改 `VariableBindingViewModel`（新模式 + 结果契约）、`ProcessViewModel`（新回调）、插件侧开窗与接收；`DataBindView` 从"产出连线"变成"有时产出连线、有时产出名字"，两个既有消费方（`ProcessViewModel`、`ConditionEditorViewModel`）都要分支；32 行逐行开模态窗的交互也差 | ❌ 不做（除非出现"整屏浏览 + 类型过滤"的真实需求） |

**C 不能治卡死的理由（要点）**：弹窗今天能跑 2702 条，是因为 2026-10-29 专门给它做了"高度有界 + 虚拟化"；把同样的列表换个宿主不会自动变快。而 A 路线是**把那次修复的做法下沉成可复用件**，一次解决所有名字字段。

## 7. 踩过的坑

- **别把"名字列没有 🔗"当成漏做**：那是 R33 的判据；补上等于把静默故障装回去。
- **别把"换弹窗"当成性能方案**：弹窗今天不卡，是因为 2026-10-29 专门修过它的虚拟化；同样的列表换宿主不会自动变快。
- **`ItemsControl` 不虚拟化**：判据看 `ItemsPanel` 是不是 `VirtualizingStackPanel`，不是看有没有 `ScrollViewer`。赋值浮层是"面板不支持"，绑定弹窗那次是"面板支持但高度无界"——**两种病因，同一种症状**。
- **虚拟化会改观感**：无条件封顶会把十几行压出内层滚动条（绑定弹窗那次踩过），必须带"3 屏门槛"。
- **可编辑 ComboBox 清 `ItemsSource` 会推空串**：改"一次性赋值"时必须保留 `AssignmentRowVm.cs:148-151` 的回填保护。
- **插件只能引用 `Core.Interfaces` + `Core.Controls`**（`Plugins\Plugin.Utility\Plugin.Util.csproj`）：任何"统一控件"必须落在 `Core.Controls`，而它解析不到 UI 主题令牌、且不在 R140 颜色闸的扫描范围内 —— 色值只能内联，需在文件头写明理由（先例：`LinkableValueEditor.xaml`）。
- **候选有两个来源**：`PluginConfigContext.Variables`（配置窗快照，含上游运行时变量）与 `StepConfigOptionSource`（宿主注册表，按 `OptionKind`）。路线 B 会把两者混在一个下拉里，先想清楚谁赢。

## 8. 决策建议（2026-10-29 用户确认方向：要"名字选择弹窗"）

**结论：赞成，且建议做成唯一入口（dialog-only）** —— 不保留行内浮层、也不保留可编辑 ComboBox。理由与代价如下。

### 8.1 为什么 dialog-only 反而更省

| 收益 | 依据 |
|---|---|
| **缺陷 A/B/C 直接消失**（不是被优化，是被删掉） | 行里不再实例化任何候选、不再按行复制 `List<NameCandidate>`、不再每次按键过滤。§3 表里 A（不虚拟化）、B（Clear+Add）、C（按行复制）三条的宿主代码全部移除 |
| 删掉一批已记录在案的坑 | `AssignmentRowVm.cs:79-100`（可编辑 ComboBox 清 `ItemsSource` 推空串、绑 `SelectedItem` 而非 `SelectedValue`）、`AssignmentRowVm.cs:46-54`（打开浮层清搜索词）、`VariableAssignmentView.xaml.cs:29-35`（R35 那套 6 个输入事件钩子）、`2026-10-27` 报告踩坑 1/2（作用域 setter 被推 null、派生投影不通知）—— 这些复杂度都源于"行内编辑控件" |
| 一处实现，五个插件受益 | 名字字段现状见 §5.1；弹窗落在宿主，天然带令牌（R140）、带虚拟化、带类型过滤 |
| 全局名可升级成按 Id 存 | 弹窗侧候选已带 `PortDefinition.VariableId`（`Engine\FlowQueryHelper.cs:74`），`PluginConfigContext.Variables` 也有 `VariableOption.VariableId` —— 改名不再断（R95 的同一思路）。**建议放到第二批**，别和性能修复混做 |

代价：改一行名字从"点开浮层 + 选"（2 次交互）变成"点开弹窗 + 选 + 关"（3 次）。缓解：弹窗内 ↑↓ 选、Enter 直接确认并关闭，实际是"点开 + 回车"。

### 8.2 四个硬条件（缺一条就不能落地）

1. **弹窗列表必须虚拟化 + `ICollectionView.Filter`**：照 `2026-10-29-变量绑定候选列表卡顿（虚拟化失效）` 的做法（高度按视口有界 + 3 屏门槛 + `Recycling`）。否则只是把卡死从插件搬到弹窗。
2. **运行时列必须允许"列表里没有的名字"**：名字空间是开集（§4.1），弹窗要有一个"使用这个名字（运行期由 SetVar 创建/不存在时自动创建）"的显式出口，否则堵死 `Context.SetVar` 与 `CreateIfNotExists` 的合法用法（R190）。
3. **通道走宿主事件，插件不自己开窗**：插件只引用 `Core.Interfaces` + `Core.Controls`，拿不到 `IDialogService`。照 `LinkPathEvent` 的既有先例（`LinkableValueEditor.xaml.cs:686-704` → `ProcessViewModel.cs:562-588`），新增 `PickVariableNameEvent{ Scope, CurrentName, AllowFreeText, OnPicked }`，由 `ProcessViewModel` 呼出弹窗并回调。**这条通道已在插件视图里跑通**（赋值插件的值列 🔗 就是它）。
4. **不复用 `ScadaVariablePickerView`**：它绑 SCADA 的 `ScadaVariableRow`、内联 `#FFFFFF` 等色值，且属 R191 暂停域；新建通用弹窗。

### 8.3 删除清单 / 新增清单

**删（`Plugin.Utility`）**：`VariableAssignmentView.xaml:402-577`（`GlobalNameToggle` + `Popup` + 搜索 + `ItemsControl`）、`:580-621`（可编辑 ComboBox）、`AssignmentRowVm.cs:38-100`（`Candidates`/`FilteredCandidates`/`IsGlobalNameOpen`/`GlobalSearchText`/`SelectedGlobalCandidate`/`SelectGlobalCandidateCommand`/`ApplyGlobalFilter`）、`VariableAssignmentPlugin.cs:428-452`（`BuildCandidates`）、`VariableAssignmentView.xaml.cs:29-35`（输入事件钩子）。行内只留：名字 + 类型徽标 + 失效/手填徽标 + 提示行，整块可点 → 开窗。

**留（必须改）**：`FindVariable` 换 `Dictionary`（缺陷 D，`:418-426`）；`RefreshNameCandidates` 的 `Contains` 去重换 `HashSet`（`:326`）。

**增**：`Core.Interfaces\PickVariableNameEvent.cs`（+ `VariablePickResult`）、`VisionMaster\Views\DialogViews\VariablePickerView.xaml(.cs)`、`ViewModels\DialogViewModels\VariablePickerViewModel.cs`、`ProcessViewModel` 一个订阅与处理函数。
