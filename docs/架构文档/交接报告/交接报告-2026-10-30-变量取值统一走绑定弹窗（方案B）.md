# 交接报告 — 变量取值统一走绑定弹窗（方案 B：合并「变量」档）

> 类型：**设计方案，未改产品源码**（本文档之外本批没有代码改动）。
> 触发：用户「不少地方变量绑定和变量名获取都用下拉框，数据量大时页面假死；改用现有的变量绑定弹窗，同时考虑全局和运行时变量」。
> 前置：`交接报告-2026-10-29-变量选择统一弹窗可行性方案.md`（下称"参考文档"）、`交接报告-2026-10-30-变量选择统一弹窗设计与实施方案.md`（下称"前版"）。
> **本版推翻了前版的核心判断**，理由见 §2（前版把「取值」误判成「写名」）。

---

## 1. 结论

**`FieldSource.Variable` / `ColumnSource.Variable` 这一档是「取值」（读），不是「写名」（写）。既然都是取值，就该和「端口」档走同一条通道：`LinkableValueEditor` 🔗 → `DataBindView` 绑定弹窗 → `LinkedSources`。**

方案 B = **删掉「变量」这一档，只留「端口」和「内置」两档**，把"从某个变量取值"统一表达为"绑定到那个变量"。

绑定弹窗左栏本来就同时列三类候选（`Engine\FlowQueryHelper.cs:51-148`）：
- 全局变量（含系统变量）—— `LinkKind.GlobalVariable`，带 `TargetVariableId`
- 运行时变量 —— `LinkKind.RuntimeVariable`，`RuntimeVariableProxyPort` 按名从 `LocalVariables` 取
- 上游步骤输出端口 —— `LinkKind.StepPort`，`LinkedSource` 直接引用

**一条通道覆盖三种来源，全部能取值，且绑定后自动显示路径（`DisplayAddress`）。**

## 2. 上一版错在哪（必须写清，否则方案会被误读）

| 上一版的说法 | 代码事实 | 结论 |
|---|---|---|
| "变量名列要的是**写目标**，不能用绑定弹窗" | `UploadFieldDef.cs:31` 注释原文："字段的**取值**来源"；`ResultUploadPlugin.cs:690` 是 `TryResolveVariable(...)` **读**值；`RecordColumnDef.cs:12` 注释"从 context.LocalVariables **按名取值**" | **错**。这两处是读，不是写 |
| "上游算子 OutputPort 没有名字语义，进不了候选" | 对**写名**成立；对**取值**不成立——绑定弹窗本来就把上游端口列为候选（`FlowQueryHelper.cs:110-145`，`LinkKind.StepPort`） | **只对一半** |
| "名字模式要从"变量来源"里筛候选" | 取值场景不需要"名字模式"，直接复用现有的完整候选树 | **多余** |

**唯一真的是「写名」的，只有「变量赋值」插件的「变量名」列**（`VariableAssignmentPlugin.cs:1071` 起是 `TryAssign` 往变量里写）。它不在方案 B 的改造范围内（见 §7）。

## 3. 现状（代码测绘）

### 3.1 两个插件、两档来源

| 插件 | 枚举 | 档位 | 取值实现 |
|---|---|---|---|
| 数据记录 | `ColumnSource`（`RecordColumnDef.cs:7-15`） | `Port` / **`Variable`** / `BuiltIn` | `Port` → `Inputs[col.Name].GetActualValue()`；`Variable` → `TryResolveVariable(ctx, id, name)`（`DataRecordPlugin.cs:658`） |
| 结果上报 | `FieldSource`（`UploadFieldDef.cs:32-43`） | `Port` / **`Variable`** / `BuiltIn` | 同上（`ResultUploadPlugin.cs:751`） |

### 3.2 「端口」档已经是绑定弹窗（这是关键前提）

`DataRecordView.xaml:38-51`：

```xml
<DataTemplate x:Key="ColumnPortEditorTemplate">
    <cv:LinkableValueEditor ... StepData="{Binding DataContext.StepData, ...}">
        <cv:LinkableValueEditor.Port>
            <MultiBinding Converter="{StaticResource InputPortConv}">
                <Binding Path="Name" />                              <!-- 列名 = 动态端口名 -->
                <Binding Path="DataContext" ... />                    <!-- 宿主插件 -->
                <Binding Path="DataContext.PortsVersion" />           <!-- 端口重建锚 -->
```

端口由 `DataRecordPlugin.cs:340` 的 `AddDynamicInput(new InputPort<object>(col.Name, ...))` 按列重建。`LinkableValueEditor` 的 🔗 → `LinkPathEvent` → `ProcessViewModel.cs:562-588` → `DataBindView` 单绑定模式 → `stepData.SetLink(port.Name, link)`。

**所以：`Port` 档早就是"绑定弹窗 + 显示路径"，`Variable` 档才是那个异类。**

### 3.3 运行期取值链（三种 LinkKind 都能取到值）

| LinkKind | 编译/运行期怎么取值 | 代码 |
|---|---|---|
| `GlobalVariable` | `VariableRegistry.ResolveGlobalLink` → 变量对象（Id 优先、名字兜底） | `Engine\FlowCompiler.cs:1046-1057`、`VariableRegistry.cs:145-161` |
| `RuntimeVariable` | `RuntimeVariableProxyPort`，`BindContext` 后按名从 `context.LocalVariables` 现取 | `Core\Models\Variable\RuntimeVariableProxyPort.cs:81-110` |
| `StepPort` | 直接引用上游 `IOutputPort`（含 `ArrayIndexProxyPort` 处理下标） | `FlowCompiler.cs:1059+` |

**三种都能读值**，这是方案 B 成立的技术基础。

### 3.4 存量落盘形态

- 插件配置存在 `StepModel.InputValues` 里（`.vms` 的 `"InputValues": { "$type": ..., "Columns"/"Fields": [...] }`）。
- 实测抽样 `artifacts\logs\20261027\backup-vms\视觉样例对拍.vms`（550 KB）：**不含** `VariableName` / `Source` / `ResultUpload` / `DataRecord`（该方案没用到这两个插件）。
- 全仓 81 个 `.vms` 里 `"Source": 1`（= `Variable` 档）**零命中** → **现有方案样本中没有一个用到「变量」档**。
  > 注意：这只说明**仓库内样本**没有；用户现场的方案可能有，迁移逻辑仍必须实现（§6）。

## 4. 方案 B 的设计

### 4.1 枚举与 UI 收缩

| 插件 | 改前 | 改后 |
|---|---|---|
| 数据记录 | `Port` / `Variable` / `BuiltIn` | **`Port`（改显示名「取值（绑定）」）/ `BuiltIn`** |
| 结果上报 | `Port` / `Variable` / `BuiltIn` | 同上 |

「端口」这个显示名要改：它现在的语义已经从"接上游端口"扩成"绑任意来源（全局/系统/运行时/上游端口）"，再叫「端口」会误导用户以为只能接上游。

> `Source=Port` 时列名/字段名同时是动态端口名（`DataRecordPlugin.cs:340`、`ResultUploadPlugin.cs:349` 附近）——**这条不变**，因为 `SetLink` 的键就是端口名。

### 4.2 删掉的东西

| 文件 | 删除内容 |
|---|---|
| `RecordColumnDef.cs` | `VariableName` / `VariableId` / `IsTextDirty` / `MarkTextClean` |
| `UploadFieldDef.cs` | 同上 |
| `DataRecordPlugin.cs` | `VariableNameCandidates` / `RefreshVariableCandidates` / `RefreshVariableHint` / `CaptureVariableIds` / `TryResolveVariable` / `FillMissingVariable` 分支 |
| `ResultUploadPlugin.cs` | `VariableNameOptions` / `RefreshVariableNameOptions` / `CaptureVariableIds` / `TryResolveVariable` |
| `DataRecordView.xaml` | `:804-819` 的变量名 ComboBox、`SourceVis` 的 `Variable` 分支 |
| `ResultUploadView.xaml` | `:898-915` 的变量名 ComboBox、`EnumInVis` 的 `Variable` 分支 |
| `DataRecordView.xaml.cs` / `ResultUploadView.xaml.cs` | 枚举显示名表里的 `Variable` 项 |

### 4.3 新增的东西

**只有迁移**，没有新控件、没有新契约、没有新 View——这就是方案 B 最大的好处。

### 4.4 运行时变量这一档的特殊性（必须保留手输的位置）

`FieldSource.Variable` 删掉后，"读一个运行时变量"变成"绑定到运行时变量"。但运行时变量有一个限制：

- 绑定弹窗的运行时候选只列**上游「变量定义」节点静态声明**的那些（`FlowQueryHelper.cs:190-221`，判据 `PluginTypeName.Contains("VariableDefinitionPlugin")`）。
- 而 `CSharpScript.SetVar`（`ScriptContext.cs:132-137`）造的名字、`JudgeTablePlugin.WriteRuntimeVariable`（`:949-960`）写的名字，**在静态图上看不到**。

**这是方案 B 唯一的真实功能退化**：删掉 `Variable` 档后，用户不能再"手填一个只在运行期存在的运行时变量名"。

两种补法（必须选一个，否则不能落 B）：

| 补法 | 做法 | 代价 |
|---|---|---|
| **B1** | 绑定弹窗底部加一行「手填运行时变量名」输入框（仅 `AllowGlobals` 场景显示），确认时产出 `LinkReference{Kind=RuntimeVariable, TargetPortName=手填名}` | 改 `VariableBindingViewModel` 一个分支 + 视图一行输入框；契约不变（`RuntimeVariable` 本来就按名解析） |
| **B2** | 在「变量定义」节点之外，让 `CSharpScript` / `JudgeTable` 的写入目标也进候选（扫描它们的配置） | 要改 `FlowQueryHelper` 的扫描面，且脚本变量名仍是自由文本、扫不全 |

**推荐 B1**：手填只产出一个 `RuntimeVariable` 连线，不改任何运行期语义（`RuntimeVariableProxyPort` 本来就按名取），也不引入新的候选来源。

## 5. 迁移方案

### 5.1 反序列化期迁移（推荐，用户无感）

在 `DataRecordPlugin.ApplyConfigValues` / `ResultUploadPlugin.ApplyConfigValues` 里，把 `Source=Variable` 就地翻译：

```
Source=Variable, VariableName="OKCount", VariableId=guid?
  ↓
Source=Port, 列/字段名不变（端口名不变）
+ 生成一条 LinkReference 写进该端口的 LinkedSources
```

`LinkReference` 怎么造（三档判定，与 `VariableOptionResolver.ResolveTarget` 同序）：

| 条件 | 产出 |
|---|---|
| `VariableId != Guid.Empty` 且能在 `VariableRegistry.FindById` 命中 | `Kind=GlobalVariable, TargetVariableId=id, TargetPortName=<当前名>, DisplayAddress="全局变量 (Global).<设备>.<名>"` |
| 名字能在 `GlobalVariables` 唯一命中 | 同上，补 `TargetVariableId` |
| 名字能在上游「变量定义」里命中 | `Kind=RuntimeVariable, TargetPortName=<名>, DisplayAddress="Runtime.<名>"` |
| 都不命中（脚本 SetVar 造的名字） | `Kind=RuntimeVariable, TargetPortName=<名>`（运行期按名取，与改造前行为一致） |

**关键点**：全局变量那档一定要补 `TargetVariableId`——这是批 3 已建立的"Id 优先"口径，迁移时顺手完成自愈。

### 5.2 迁移写在哪个时机

| 时机 | 可行性 |
|---|---|
| **`ApplyConfigValues`（推荐）** | 每次加载方案都会走（`DataRecordPlugin.cs:176`、`ResultUploadPlugin.cs:220`），且此时 `PluginConfigContext` 还没到、但**工作区可用**（`StepData` 在 `VisionPluginBase` 上）→ 能查 `VariableRegistry` |
| `OnConfirm` | 只在用户点确定时走，打开只看不改的旧方案永远不会迁移 |
| 反序列化回调 | 没有工作区上下文，查不到变量对象 |

**注意**：`ApplyConfigValues` 在无工作区的断言宿主里也会跑，所以迁移必须**容错**——拿不到注册表就只做"按名转 `RuntimeVariable`"，不抛异常。

### 5.3 落盘与回读

- 迁移后 `Source=Port` + `LinkedSources[列名] = LinkReference`，随 `.vms` 正常保存。
- 回读：`Port` 档走 `LinkableValueEditor` 的 `existingLink?.DisplayAddress`（`DataRecordView.xaml:44` 已支持），**路径自动回显**。
- **重复迁移安全**：再加一条判据——`Source=Variable` 才迁移，迁完置 `Port`；旧数据再打开时 `Source` 已是 `Port`，不会二次迁移。

### 5.4 需要同批改的断言

| 宿主 | 位置 | 内容 |
|---|---|---|
| `FlowCanvasChecks` | `DataRecordChecks.cs:113,165-167,204` | 5 处 `Col(..., ColumnSource.Variable, variable: "v")` 必须改成"建 Port 档 + 造 LinkReference" |
| `FlowCanvasChecks` | `ResultUploadChecks.cs:105-107,172` | 4 处 `Source = FieldSource.Variable` 同上 |
| `DataPipelineChecks` | 若有变量档用例 | 需全量搜索（本轮未逐个核，实施时以编译报错为准） |
| `VarScopeAudit`（本次新增的探针） | `C24_RecordUploadTarget` 整组 | 该组断言针对 `VariableName`/`ResolveTarget`，方案 B 后**整组要被替换**为"Port 档绑定"的断言 |

> 这是方案 B 最实的成本：**4 处既有断言 + 1 组新增探针要重写**。

## 6. 风险

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| 1 | **现场方案里 `Source=Variable` 的存量未知**（仓库样本 0 命中，但用户现场可能有） | **高** | 迁移必须实现且容错；上线前请用户在真实方案上跑一次"打开→保存→只读校验"；建议迁移时记一条 Info 日志（`"[迁移] 列 X 的变量来源已转为绑定：OKCount"`），便于事后核对 |
| 2 | **删档后无法手填运行时变量名**（静态扫不到的 SetVar 名） | **高** | 用 **B1**：绑定弹窗加"手填运行时变量名"出口（§4.4） |
| 3 | `Source=Port` 的语义被扩宽（不再只是"接上游"），旧显示名「端口」误导 | 中 | 显示名改「取值（绑定）」；ToolTip 写明可绑全局/系统/运行时/上游 |
| 4 | 列名/字段名同时是端口名——**改名会重注册端口**，已有 `UpdatePortNames`/`RebuildDynamicInputs` 逻辑 | 中 | 迁移不列名，只加连线；改名路径不变（`DataRecordPlugin.cs:325` 起） |
| 5 | 断言改动面大（4 处 + 1 组探针） | 中 | 按插件分批，每批独立验收 |
| 6 | `Source` 枚举数值变化（删掉中间项会让 `BuiltIn` 从 2 变 1） | **高** | **不要删枚举成员、不要改数值**——`Source=Variable` 的成员保留但标 `[Obsolete]`，UI 不显示；这样旧 JSON 反序列化照常（值仍解析成 `Variable`），迁移逻辑才接得住。**这一条是方案 B 能不能安全落地的关键** |
| 7 | 运行时变量绑定后 `DisplayAddress` 是 `Runtime.<名>`，与全局变量的 `全局变量 (Global).<名>` 格式不同 | 低 | 既有行为（`VariableBindingViewModel.cs:775-778`），一致 |

### 6.1 风险 6 的展开（必须看懂）

如果直接删 `ColumnSource.Variable` 这个枚举成员：

- `ColumnSource` 变成 `Port=0, BuiltIn=1`（原来 `BuiltIn=2`）；
- 旧 `.vms` 里 `"Source": 2` 会**反序列化成 `BuiltIn`** → 原来"取变量值"的列静默变成"记时间戳"；
- 这种错**不会报错**，只会让用户的记录列内容全错。

所以：**枚举成员必须保留、数值必须不动**，只是 UI 不再提供这一档，并在加载时迁移掉。这与"删掉这一档"在用户界面上等价，但数据安全。

## 10. 总结

**方案 B = 把「变量」这一档删掉（UI 层面），让"取值"只剩一条通道：绑定。**

- **技术基础**：绑定弹窗左栏本来就列全局/系统/运行时/上游端口四类候选，三种 `LinkKind` 运行期都能取到值（§3.3）。
- **最大好处**：不新增任何控件/契约/View；「取值」类字段的交互彻底统一，且绑定后自动显示路径。
- **最大风险**：旧方案 `Source=Variable` 的迁移——必须**保留枚举成员与数值**，只做 UI 隐藏 + 加载期迁移（§6.1）。
- **唯一功能退化**：手填运行时变量名，用 B1 补回。
- **不在范围**：变量赋值的写名列（它真的是写名）、`LinkableValueEditor` 下拉虚拟化。
