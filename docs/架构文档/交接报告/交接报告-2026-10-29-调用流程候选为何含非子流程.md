# 交接报告-2026-10-29-调用流程候选为何含「非子流程」

## 1. 当前状态

只读诊断，未改任何产品代码。

结论：**「调用流程」步骤的下拉没有 bug**。用户截图里那些"看起来不是子流程"的流程
（Blob缺陷检测_标签字符 / 二维码读取_QR / 几何计算_关系 / 前置质量门 / 差分_基准比对 / 形变匹配_局部非刚性），
**每一条都勾了「子程序」位**（`InvokeType = 160 = 整线 128 + 子程序 32`）。
之所以看起来"不像子流程"，是因为左侧流程树的徽标是**互斥单选**，只有"仅子程序"才显示「子」，
同时勾了整线的工位流程显示「循环」，把子程序位藏在了同一个字的背后。

> ⚠ **但"列表口径正确"不等于"这个配置对"**：整线与子程序同时勾是**自相矛盾的配置**，
> 运行期不会崩，但会稳定失败 / 静默跳过。见 §6（2026-10-29 用户质疑后复核追加）。

### 2.4 为什么"看起来不像子流程"

`Core\Models\FlowModel.cs`：

- `:326-329` `IsSubroutineOnly` = 勾子程序 **且** 无外部触发 **且** 非整线成员 —— 刻意严格，
  注释里写明理由："工位流程通常同时勾「子程序」与「随整线启动」，漏判会让它被标成只能被调用，用户就不敢按整线启动了"。
- `:333-342` `CallBadgeText` 是**互斥单选**：循环 > 外部 > 子 > 空。
- `VisionMaster\Views\FlowListView.xaml:338/346/354` 只渲染这**一个**徽标。

于是"整线 + 子程序"的工位流程只显示「循环」，子程序位在列表里不可见；
真正显示「子」的只有"仅子程序"那一种。用户把「子」当成"是子流程"的判据，就得到"下拉里混进了非子流程"的观感。

流程管理对话框里五位是**独立多选**（`VisionMaster\Views\DialogViews\FlowManagerView.xaml:306-366`，
注释原文"工位流程常同时勾「子程序」+「整线」"），那里的「子程序」胶囊对这批流程是亮的 —— 可用来现场核对。

## 5. 踩过的坑

- **`IsSubroutineOnly` ≠ "有子程序位"**：前者是"只能被调用"的展示判据（还要求非整线、无外部触发），
  后者是 `InvokeType & Subroutine`。本次困惑的根源就是这两者被当成同一个东西。
- **徽标是单选投影，不是状态全集**：`CallBadgeText` 四选一，任何"同时具备两种身份"的流程都会隐藏次要身份；
  排查"为什么它出现在 X 列表里"时不要以徽标为准，要看 `InvokeType` 位集。
- **`findstr` 搜中文在 936 代码页下会漏**（本次 `findstr /c:"Blob缺陷检测_标签字符" *.vms` 退出码 1 是假阴性）。
  可靠办法：搜 ASCII 键名（`FlowName` / `InvokeType`）取行号，再按行号配对读原文。

## 6. 追加（用户质疑后复核）：整线 + 子程序同时勾，运行期会不会"崩"

用户原话："主流程循环一套 子流程循环一套不就崩了吗"。
复核结论：**不会崩（不会双跑、不会句柄打架），但会稳定失败；而且这确实是矛盾配置，仓库自己记录过。**

### 6.1 为什么不会双跑

- **一个流程名 = 一个会话**：`Engine\IRuntimeManager.cs:206-213` 按名取（`FirstOrDefault`），
  `:150-159` `RegisterSession` 同名先停旧的再替换。
- **执行权是按会话的互斥锁**：`Engine\FlowEngineService.cs:264-278` `TryOccupySession` →
  `TryAcquireLock(StartLockKey(session))`，抢不到直接放弃。注释 `:247-253` 写明原因：
  "连点两次启动按钮时两个线程能双双穿过判断……第二次 `new CancellationTokenSource()` 会把第一次的覆盖掉，
  那个循环线程的令牌从此没人拿得到，变成点停止也停不掉的僵尸循环；同一批插件实例（Halcon 句柄、相机连接）
  还会被两个线程同时驱动。"
- 所以"两套循环"在数据模型里根本不存在 —— 两个入口抢的是同一把锁。

### 6.2 实际表现：谁先跑，另一个必然失败

| 场景 | 结果 | 代码位置 |
|---|---|---|
| 整线在跑 → Main 的「调用流程」调该工位 | 直接失败"正在运行中，本次子程序调用未执行"（Main 这一轮判 Faulted） | `Engine\FlowInvoker.cs:77-78` |
| Main 正在调该工位（那一轮没结束）→ 点「启动整线」 | **静默跳过**：`if (session != null && !session.IsRunning)` 没有 else，最后只报"已启动 N 个"，不说少了谁、为什么 | `VisionMaster\ShellViewModel.cs:2325-2339`（单次）、`:2420-2443`（连续） |
| 整线在跑 → 手动点该工位"运行" | 引擎 Warn 一条"已在运行中，忽略重复的启动请求"，界面无感 | `Engine\FlowEngineService.cs:485-490` |

即：这个组合不是"两套循环各跑各的"，而是"两个入口抢一个会话，后到的那个静默出局"。

### 6.3 仓库自己记录过这个危险

`Core\FlowBatchSelector.cs:26-28` 原文：
"工位/子程序流程为了能被「调用流程」拉起必须是启用的，如果批量运行把它们全当顶层启动，
就会和整线成员并发跑 —— **7 GB 内存事故就是这么来的**。所以"哪些算整线"必须是用户逐个勾出来的"。

也就是说设计上**假定**"工位要么整线、要么子程序"，但没有任何一处强制：
- `FlowManagerViewModel.SetFlag`（`:514-519`）只是位或，勾「整线」不清「子程序」，也不提示；
- `SubroutineFlowOptions.Describe`（`:73-79`）只标"当前流程/已禁用/步序已加密"，**不标"这是整线成员"**。

### 6.4 样例方案正好踩在矛盾形态上

`视觉样例对拍.vms`：11 条工位 = 160（整线 + 子程序），Main = 0（手动），且 Main 里用「调用流程」
串行调其中 7 条工位 —— 即"工位各自随整线跑"与"Main 编排工位"两种形态同时存在。
而 `Core\FlowBatchSelector.cs:19-24` 记录的 2026-10-28 裁决恰恰是
"工位必须与主任务**平级**：各自一条流程、各自一个会话"，按那条裁决，
Main 编排工位属于**已退役的旧形态**；样例方案是生成器在裁决前写的
（`tools\vms-generator\Program.SamplePair.cs:13` 的注释还在要求"工位流程 InvokeType 置 32"）。

### 6.5 自洽的两种形态（二选一，不能同时）

- **形态 A（2026-10-28 裁决）**：工位 = 整线，方案里没有 Main 编排；「调用流程」只用于真正的公共子程序（如回零工具流程）。
- **形态 B（Main 编排整线）**：Main = 整线，工位 = 只勾子程序、不勾整线。

样例方案现在是"A 的位 + B 的编排"，所以两条路都走不顺。
