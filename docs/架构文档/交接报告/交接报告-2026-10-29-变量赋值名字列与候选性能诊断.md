## 2. 已做（代码走读，逐条落到行号）

### 2.1 名字列不挂绑定弹窗是设计约束

**先纠正一处口径（2026-10-29 用户指出）**：本项目**不存在端口级的画布连线**，取值通道只有变量绑定弹窗一条（R188）。
本文初稿沿用插件手册 `04-名字与值口径.md` 的旧措辞（"落一条连线""画布上原来那根线"），属过时描述，已改。
正确形态：

| 层 | 实际是什么 | 位置 |
|---|---|---|
| 取值 | 变量绑定弹窗（`LinkPathEvent` → `StepData.SetLink(portName, link)`），落在**端口上的一条链接** | `Shard/Core.Controls/LinkableValueEditor.xaml.cs:693-701` |
| 画布 | 只画**模块级聚合线**：一对 producer/consumer 一根，含该对之间全部端口绑定 | `VisionMaster/ViewModels/FlowCanvasViewModel.cs:1907-1965` |
| 锚点 | 每个节点只有 `Inputs[0]` / `Outputs[0]` 一个输入一个输出，没有按端口拆开的锚点 | `VisionMaster/Views/FlowCanvasView.xaml:710,986` |

**为什么名字列仍然不能挂 🔗**（这一条不依赖画布，是纯语义）：

- v3 的行模型里**名字根本不是端口**：`AssignmentRow.VariableName` 是普通字符串配置（`Models/AssignmentRow.cs:34`），
  只有"值"是端口（`ValuePortName`，`Models/AssignmentRow.cs:75`）。所以"给名字挂绑定"在当前模型里语义不成立。
- 名字列的语义是**要写哪个变量**，是"名字"；绑定弹窗的语义是**这个端口的取值由上游/变量提供**，是"值"。
  两者不是同一件事 —— R33 把"名字类"（变量名、步骤名、卡地址、端口名）单列，只允许"手填 + 候选下拉"。
- 历史遗留：插件仍保留旧单行端口 `InputPort<string>("Name", …)`（`VariableAssignmentPlugin.cs:43`），
  老方案里可能还挂着链接，迁移时统一 `RemoveLink("Name")`（`:277-279` / `:296-300` / `:905`）。
  这也是"名字端口一旦可绑定，就会拿上游的值当名字"的实证 —— 运行期数值型变量的名字会变成 `"0"`，
  步骤照常绿、值写去别处。**该旧端口不提供给新视图使用**。
- 值列**已经有**绑定入口：`VariableAssignmentView.xaml:674-680` 的 `ValueCellTemplate` → `cv:LinkableValueEditor`
  （截图里值框右侧的 🔗 / ✕ / 🔒 就是它）。所以"要连上游"这件事在值列是通的。
- 名字列的两条合法形态：全局行 = `ToggleButton + Popup` 搜索候选（`VariableAssignmentView.xaml:402-577`，
  只能选、不可手填）；运行时行 = 可编辑 `ComboBox`（`VariableAssignmentView.xaml:580-621`，候选可填，
  因为 C# 脚本 `SetVar` 造的名字不在宿主快照里 —— R190 唯一允许手输的场景）。

**附带发现的文档欠账**：`Plugins/Plugin.Utility/Help/VariableAssignmentPlugin/04-名字与值口径.md`
第 32-45 行仍写"落一条…的连线"，第 129-131 行 FAQ 仍写"画布上原来那根线怎么没了"，与 R188 口径冲突；
同文引用的编译期报错文案 `[连线类型不匹配] … 期望 String` 在全仓已不存在（grep 0 命中）。
改它要重建插件并核 `Help` 内嵌资源数（R42 / 红线③），未做。

### 2.2 3000 变量的卡顿来源（四处叠加，按影响排序）

| # | 位置 | 机制 | 量级（3000 候选） |
|---|---|---|---|
| A | `VariableAssignmentView.xaml:501-507` | 全局候选浮层是 `ScrollViewer + ItemsControl`，`ItemsControl` 默认 `ItemsPanel` 是 `StackPanel` —— **不虚拟化**，全部实例化 | 3000 项 × 每项一个自定义模板 `Button` + `Grid` + `StackPanel` + 3 个 `TextBlock` + DataTrigger（`:510-556`）≈ 2 万+ 元素。首次打开浮层即秒级冻结 |
| B | `Models/AssignmentRowVm.cs:56-65 → :163-177` | `GlobalSearchText` setter 直接 `ApplyGlobalFilter()`，里面 `FilteredCandidates.Clear()` 再逐项 `Add` | 每次按键 3001 次 `CollectionChanged`；绑在已实例化的 `ItemsControl` 上 → 容器全部拆掉重建 + `StackPanel` 在 `ScrollViewer` 里无限高测量，每轮重量 3000 个子元素。打 5 个字 = 5 轮 |
| C | `VariableAssignmentPlugin.cs:428-452` + `:551-559` | `BuildCandidates` 按行重造全量 `List<NameCandidate>`；`Initialize`/`SetConfigContext` → `RefreshAllRows()` 对**每一行**都跑一遍 | 行上限 32 → 32 × 3000 = 9.6 万对象 + 每行 3000+3000 集合事件 |
| D | `VariableAssignmentPlugin.cs:418-426` | `FindVariable` 是 `FirstOrDefault` 线性扫全表；一次 `RefreshHint` 里被调 3~4 次（`BuildHint` 两次 + `GetTypeText` + `IsInvalidGlobal`） | 单行单次刷新 ≈ 1.2 万次字符串比较，× 行数 × 每次改动的行数 |

另有一条独立的 O(n²)：`VariableAssignmentPlugin.cs:326` 用 `NameCandidates.Contains(option.Name)` 去重，
3000 项 ≈ 450 万次比较，`Initialize` 与每次 `Scope.ValueChanged` 都走一遍。

**关键叠加**：全局行选中一个名字 → `Row.VariableName` 变更 → `OnRowPropertyChanged`（`:538-541`）→
`RefreshCandidates()` 整表重建（C 路径）→ 又把**正打开着的**那个浮层列表重建一次（B 路径）。
所以"打开浮层卡 → 选一个更卡"。

## 4. 下一步（若用户要求修）

不动语义，只改渲染与缓存：

1. 浮层列表换 `ListBox`（或 `ItemsControl` + `VirtualizingStackPanel`），
   `VirtualizingPanel.IsVirtualizing=True` + `VirtualizationMode=Recycling` + `ScrollViewer.CanContentScroll=True`。
   视觉零变化（同一 `ItemTemplate`），因此不触发 R125/R132 的设计基线变更流程。
2. `FilteredCandidates` 由 `ObservableCollection` 改「一次性赋值 + `PropertyChanged`」（`List<T>` 快照），
   去掉 `Clear()`+`Add()` 的 3000 次事件。
3. 候选按作用域缓存一份只读列表（global / runtime 两份），行只持引用；`BuildCandidates` 不再每行重扫。
4. 候选改为「浮层打开时才造」，`Initialize` 不给所有行预造。
5. `FindVariable` 换 `Dictionary<(name, scope), VariableOption>`（`OrdinalIgnoreCase`）。
6. `RefreshNameCandidates` 的 `Contains` 去重换 `HashSet`。

预期：打开浮层从秒级降到几十毫秒，按键与选名不再整表重建。

## 5. 踩过的坑

- **别把"名字列没有 🔗"当成漏做**：这正是 R33 的判据，补上等于把静默故障装回去。
- **别用"画布连线"描述取值**（本文初稿踩了）：R188 之后取值只有绑定弹窗一条通道，绑定落在**端口上的链接**；
  画布只画模块级聚合线，默认还不显示。用旧措辞会让"为什么不能给名字列挂绑定"这个论证直接站不住 ——
  因为读者会反问"画布上根本没有那根线"。正确论证是：**名字在 v3 行模型里不是端口**（`AssignmentRow.cs:34`），
  只有"值"是端口（`:75`）。
- **引用帮助手册前先核它与现行规则是否一致**：`04-名字与值口径.md` 仍带 R188 之前的措辞与已不存在的报错文案，
  照抄会把过时结论带进新文档。
- **`ItemsControl` 不虚拟化**：`ScrollViewer` 里套 `ItemsControl` 是最常见的"几百项就卡"形态；
  判据看 `ItemsPanel` 是不是 `VirtualizingStackPanel`，不是看有没有 `ScrollViewer`。
- **可编辑 `ComboBox` 清 `ItemsSource` 会推空串**（`AssignmentRowVm.cs:148-151` 已处理）：重建候选集合时
  必须先把行名记住、重建后顶回，否则名字被静默清空 —— 改造成"一次性赋值"时要保留这条保护。
- 本报告只做走读，**"卡"的结论来自代码路径推算**，真机计时仍需实测（R175 分层：断言宿主 → 真 exe）。
