# 交接报告 — 启动期 NullReferenceException 诊断与修复（2026-10-30）

## 当前状态

**已修复并构建通过**（DLL mtime 17:02:52 ≥ 源码 mtime 17:02:08，`0 个错误`）。

用户报：VS 启动解决方案时抛 `System.NullReferenceException`，栈顶
`Prism.Ioc.IContainerProviderExtensions.Resolve[T]` → `VisionMaster.App.<OnStartup>b__12_0()`（`App.xaml.cs:146`）。

结论：这是**设计内的 first-chance 异常**（被相邻 `catch` 吃掉、运行结果正确），
但调试器会按默认设置停在那一行，看起来像崩溃。现已改为**正常路径不产生异常**。

## 已做

### 1. 根因链路（已还原）

1. `App.OnStartup` 在 `base.OnStartup(e)`（原 :159）**之前**就装配 `SqliteSoftwareOperationLog`
   并 `SafeRecord` 写一条「启动」记录（原 :151）。
2. 首条记录触发 `SqliteSoftwareOperationLog.EnsureInitialized()` 建库，
   建库成功后**立刻调一次 `PruneExpired()`**（`Services\Core.Database\SqliteSoftwareOperationLog.cs:371`）。
3. `PruneExpired` 调 `_retentionDays()`（同文件 :309）→ 回调体
   `Container.Resolve<AppSettingsService>().Current?.AuditRetentionDays ?? 90`。
4. 此刻 Prism 容器尚未创建（`Container` 为 null）。`Resolve<T>()` 是
   **扩展方法**，provider 为 null 时先在扩展方法内部解引用 → NRE → 被外层 `catch { return 90; }` 接住。

即：行为正确（回落默认 90 天保留期），但调试器停在 first-chance 异常上。

### 2. 代码修改（`VisionMaster\App.xaml.cs`）

| 位置 | 改动 |
|---|---|
| `OnStartup` 的 `retentionDays` 回调（:143-153） | 改走已有的 `TryResolveService<AppSettingsService>()?.Current.AuditRetentionDays ?? 90`——先判空再解析，**正常路径不抛异常**；注释写明为什么不能直接 `Container.Resolve<T>()` |
| `RegisterTypes` 的 `LogService.SolutionRootProvider`（:343-358） | 同一类隐患的顺手加固：`ContainerLocator.Container` 先判空再 `Resolve<WorkspaceContext>()`（原写法 `ContainerLocator.Container.Resolve(...)` 在容器未建时会 NRE，同样被 catch 吞） |

两处都只把「靠异常当控制流」换成「先判空」；业务语义（90 天兜底 / 无方案返回 null）一字未变。

## 踩过的坑

- **把 `catch` 当控制流，代价是调试体验**：功能上完全正确（fail-open 兜底），
  但 first-chance 异常在 VS 里默认就断，用户看到栈顶在 `App.xaml.cs` 只会认为"启动崩了"。
  判据：**在启动关键路径上，凡是"预期内的失败分支"要判空/判状态，不许靠抛异常回到正常路径。**
- 本机 `git` 不在 PATH（`'git' 不是内部或外部命令`），`Program Files` 下也找不到 `git.exe`，
  所以无法用 `git diff` 取回原文——改文件前只能靠 Read 留档。
- `dotnet build` 的锁定错误里会点名锁持有者（`Microsoft Visual Studio 2022 (89524), VisionMaster (92976)`），
  看到 `MSB3027 + 进程名` 先查 `tasklist`，别当编译错误去改代码。
