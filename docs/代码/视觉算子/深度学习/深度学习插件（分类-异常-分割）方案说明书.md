# 深度学习插件（分类 / 异常 / 分割）方案说明书

> **状态**：分类已实现并跑绿；异常与分割为**待实现方案**（现行设计文档，按 R8 持续维护，不进归档）。
> **定位**：本文件是「深度学习」能力族的统一设计文档，记录缺口背景、三件套总览、已实现部分的设计与边界、待实现部分的契约与门槛。
> **相关代码**：`Plugins/Plugin.DlClassify/`（已实现）、`FlowCanvasChecks/ClassifyChecks.cs`（断言）。
> **同族既有插件**：`Plugins/Plugin.Yolo/`（目标检测，唯一既有 AI 插件）。

## 0. 缺口背景（为什么要做这一族）

盘点全仓现有 28 个插件，AI 维度**只有 `Plugin.Yolo` 一个，且只做目标检测**：

| AI 任务 | 现状 | 工业用量 |
| --- | --- | --- |
| 目标检测（detect） | ✅ `Plugin.Yolo`（YOLOv8/v11 ONNX） | 中 |
| **图像分类（classify，OK/NG）** | ❌ 缺（Yolo 的 `task` 守卫明确拒绝 classify） | **大** |
| **异常检测（无监督）** | ❌ 缺 | **大** |
| 分割（语义 / 实例） | ❌ 缺（Yolo 明确拒绝 segment/semantic） | 中 |

`Plugin.Yolo` 的 `task` 守卫（`YoloPostProcess.IsSupportedTask`）本身就把非 detect 模型"明确拒绝"了——
所以缺口 C 的落法是**新建插件**，而不是改 Yolo。

## 1. 三件套总览与分期

| 期 | 插件 | 中文名 | 分组 | 输入 → 输出 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 一 | `Plugin.DlClassify` | 深度学习分类 | 图像处理 | 整图 → 类别 + 置信度 | **已实现** |
| 二 | `Plugin.DlAnomaly` | 异常检测 | 图像处理 | 整图 → 异常分数 +（可选）热力图 | 方案（契约待真实模型验证） |
| 三 | `Plugin.DlSegment` | 分割 | 图像处理 | 整图 → 类别图 / 实例掩膜 | 方案 |

**为什么拆成多个插件，而不是一个"深度学习"总插件 + 任务下拉**

1. **预处理与输出格式完全不同**：分类是"整图 → 标量分数"；异常是"整图 → 分数 + 像素级热力图"；实例分割是"检测头 + 32 个掩膜系数 × 原型掩膜"。塞进一个插件会让"任务选择"成为贯穿预处理/后处理/端口/视图的巨型分支。
2. **仓库既有风格**：`Plugin.Yolo` 就是"一插件一任务 + task 守卫"；同族延续。
3. **task 守卫的可组合性**：每个插件只接受自己任务的模型，选错模型立即报错——这比"总插件里选错任务"更难出错。

**为什么都归「图像处理」分组**：与 `Plugin.Yolo` 保持一致（它就在「图像处理」）。将来若要单列「深度学习」分组，需连同 Yolo 一起迁移——属显示层改动，可另行评估。

## 2. 已实现：深度学习分类（Plugin.DlClassify）

### 2.1 它是什么

把一张图（或上游裁好的 ROI）送进 ONNX 分类模型，输出"最可能是什么类 + 把握多大"。
工业主用途是 **OK/NG 二分类**（划痕/脏污/色差/装配到位与否——"说不清规则、人一眼却认得"的外观判定）。

### 2.2 边界（沿用 Yolo 立的三条规矩）

1. **模型是客户资产，不内置**：模型以外部路径配置，找不到时明确报错，不静默退回默认模型。
2. **只做分类**：`task` 不是 `classify` 的模型（detect/segment/pose/obb/…）会被明确拒绝——
   不同任务的输出格式不同，按分类解读会得到错误结果却不报错。
3. **不做 OK/NG 判定**：只输出"最可能是哪一类、把握多大"，判定交下游（如比较节点 `PredictedClassName == "OK"`）。

### 2.3 端口契约（固定端口，无动态端口）

| 端口 | 方向 | 类型 | 说明 |
| --- | --- | --- | --- |
| `Image` | 入 | HImage | 待分类图像（`IsRequired = false`） |
| `PredictedClassId` | 出 | int | 最可能的类别索引（0 基） |
| `PredictedClassName` | 出 | string | 最可能的类别名（元数据没带时 `class_N`） |
| `Confidence` | 出 | double | 最高类别置信度 0~1 |
| `Scores` | 出 | `double[]` | 全部类别概率（与 `ClassNames` 同序） |
| `ClassNames` | 出 | `string[]` | 类别名数组 |
| `TopKText` | 出 | string | 前 K 类文本摘要（供记录/上传等标量下游用） |

另有基类隐式端口 `Success`、`ErrorMessage`。

> `TopKText` 为什么在数组之外还要给：画布上数组端口只能整体连给 object 输入口，
> 而记录/上传/比较这些既有下游节点都是按**标量**写的——没有它接不上（与 Yolo 的 `BoxesText` 同一理由）。

### 2.4 配置项

| 配置 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `ModelPath` | string | 空 | ONNX 分类模型路径（支持相对宿主目录） |
| `ResizeMode` | enum | `Letterbox` | `Letterbox`（等比补边）/ `Stretch`（拉伸） |
| `InputSize` | int | 0 | 0 = 用模型元数据静态尺寸；动态形状模型才手填（常见 224） |
| `TopK` | int | 3 | 结果里保留前 K 类（夹到 [1, 类别数]） |

> **`ResizeMode` 为什么显式暴露**：分类模型的训练预处理两种主流做法（letterbox / 拉伸）在非方形图上结果不同，
> 选错的表现是**精度静默下降**（不报错、不崩溃）。默认 Letterbox（不破坏几何的那一档），把选择权交给用户而不是替它猜。

### 2.5 推理链路

```
① 取原图尺寸
② 算缩放几何（ResizePlan：Letterbox 等比+居中补 114 灰 / Stretch 直接拉）
③ 构造输入画布（非 byte 图先转 byte；单通道 compose3 补 3 通道）
④ 转 NCHW float（get_image_pointer1 + Marshal.Copy，/255 归一化）
⑤ ONNX Runtime 推理
⑥ 后处理：布局嗅探 → 概率归一化 → TopK
```

**三个"必须做对否则静默出错"的点**：

- **补边灰度用 114**（不是 0）：黑边是模型没见过的强边缘，会让结果系统性偏移（与 Yolo 同款坑）。
- **归一化 /255**：少除或多除模型照样跑、不报错，只是精度静默劣化。
- **概率归一化判据**（`NormalizeToProbabilities`）：Ultralytics 导出的分类模型输出是**原始 logits**
  （softmax 在预测器里做，不在图里），但也有部分导出把 softmax 做进了图里。对已 softmax 过的输出**再做一次**
  会把分布压平（0.9 → 0.5），表现是"能跑但置信度没区分度"。判据：全在 [0,1] 且和≈1 → 视为概率原样用；否则 softmax。

### 2.6 会话生命周期

**进程级共享 + 引用计数**（`ClassifySession`，与 `YoloSession` 策略同源）：
同模型被多个流程引用只加载 1 份；路径没变复用、变了先放旧的再拿新的（避免"改了配置不生效"）。

### 2.7 配置界面

两列（980×620）：左参数（图像输入 / 分类模型 / 分类参数 / 高级 / 试算），右只读图像（`ImageReadOnly`，不吃 ROI）。
界面上刻意显示两处排障信息：**模型摘要**（输入输出形状 / task / 类别名）与**试算 TopK 概率**。

### 2.8 回归断言（`FlowCanvasChecks/ClassifyChecks.cs`）

三段，各自独立可跑：

| 段 | 需要模型 | 覆盖 |
| --- | --- | --- |
| ① 后处理（受控数据） | ❌ | letterbox 宽/高图几何、stretch、布局嗅探（[1,3]/[1000]/[1,1,5] 接受；[1,84,8400]/[1,2,224,224]/[1,1] 拒绝）、task 守卫、概率归一化（已是概率原样 / logits softmax / 全负 / 大 logits 稳定）、TopK（排序/占位/夹取） |
| ② ONNX Runtime 链路 | ✅（否则跳过） | 入参守卫、真模型加载、进程级缓存命中、引用计数释放 |
| ③ 插件壳 | ❌ | `[Display]` 分组、输出端口契约、默认值、partial 属性往返、未选模型/路径不存在 → 明确失败不抛异常 |

**实测**：`[深度学习分类]` 全段 33 条断言通过；全量 **2145 通过 / 0 失败**。

> 审查（reviewer）抓到的 P1 已修并补断言：`ClassNames` 端口曾用 TopK（只含前 K 条）回填全量名字，
> 在"模型带名字且 TopK < 类别数"时给出错名/占位混杂，违反与 `Scores` 同序的契约。
> 修法：`ClassifyResult` 携带**全量** `ClassNames`（来自模型元数据），由 `ClassifyPostProcess.ResolveClassNames`
> 统一生成；断言 `[核心] ClassNames 与 Scores 同序且全为真实名` 守门。

### 2.9 已知边界（诚实清单）

- ⚠️ **解码/归一化尚未用真实分类模型端到端验证**（最需要知道的一条）。受控数据只能证明公式自洽，
  不能证明对具体导出（logits vs softmax）的判据在真实模型上不出错——拿到真实 `.onnx` 后必须补验。
- 归一化的"已是概率"判据有**极小概率误判**（logits 恰好全在 [0,1] 且和≈1）；这是可接受的风险，已在断言中显式记录行为。
- 只带 CPU 版 ONNX Runtime（接 GPU = 换 ExecutionProvider + 多带原生库，不改端口契约）。
- `System.Numerics.Tensors` 必须随插件带（不在 .NET 9 共享框架里，漏带 = 运行期 `FileNotFoundException`）。
- 类别名依赖模型元数据 `names`，读不到用 `class_N`，**不编造**。
- 动态形状模型必须手填 `InputSize`（留 0 明确报错，不猜）。
- **不做判定、不做结果投射**（不给"标了类别的图"）。

## 3. 待实现：异常检测（Plugin.DlAnomaly）

### 3.1 它是什么

无监督缺陷检测：只用**良品**样本训练，推理时给出"这张图偏离良品有多远"的异常分数（可带像素级热力图）。
工业价值：NG 样本稀少/无法穷举时的外观检测（PatchCore / PaDiM / DRAEM 一族）。

### 3.2 为什么先不盲做（门槛）

与分类不同，**异常检测的 ONNX 输出没有统一标准**：不同框架（Anomalib 各算法、自研）导出的输出
数量、名字、形状（标量分数 / `[1,1]` / `[1,1,H,W]` 热力图 / 多个输出）各不相同。

盲写一套解码 = **臆造未给定的行为**，极可能对用户的真实模型无效。所以本插件**开工前必须先定契约并用真实模型验证**：

**拟定的输出契约（待真实模型验证后定稿）**：

| 张量 | 形状 | 含义 |
| --- | --- | --- |
| 图像级异常分数 | `[1]` 或 `[1,1]`（秩 ≤ 2） | 越大越异常；按 `[阈值]` 判 OK/NG |
| 像素级异常热力图（可选） | `[1,1,H,W]` 或 `[1,H,W]`（秩 4/3） | 定位异常区域；可输出为 HImage |

插件应：按秩识别哪个输出是分数、哪个是热力图；形状不认识就**明确拒绝**（不猜），并在配置界面显示读到的输出形状。

**开工门槛**：拿到至少 1 个真实异常模型的 `.onnx` + 对应良品/不良图，确认输出契约后再实现（否则就是盲写）。

## 4. 待实现：分割（Plugin.DlSegment）

### 4.1 两个子任务，格式都很明确

| 子任务 | 模型 | 输出 | 解码 |
| --- | --- | --- | --- |
| 语义分割 | 通用 ONNX | `[1, C, H, W]` | 逐像素 argmax → 类别图（`HImage` 单通道） |
| 实例分割 | YOLOv8/v11-seg | `[1, 4+C+32, N]` + `[1, 32, 160, 160]` 原型 | 检测头（复用 Yolo 解码）→ 32 系数 × 原型 → 掩膜 → 掩膜级 NMS |

- **语义分割**实现较直接（argmax + 类别图），风险低。
- **实例分割**是"检测 + 掩膜"两段，最复杂：要复用 `Plugin.Yolo` 的解码/NMS，再叠加掩膜系数 × 原型的矩阵乘与裁剪、
  以及掩膜级 NMS。工作量约等于再做一个半 Yolo。

**结论**：分割可做，但排在异常之后（工业用量低于分类/异常），且实例分割要单独评估工作量。

## 5. 复用与架构

### 5.1 当前做法（已落地）

- 每个深度学习插件**各自持有**一份"进程级共享会话 + 引用计数"实现（`YoloSession` / `ClassifySession`）。
- 这是**刻意的重复**：不改动已验证的 `Plugin.Yolo`，也避免插件间互相引用（跨插件依赖是坏味道）。

### 5.2 何时抽共享库（未决）

当**第三个**深度学习插件（异常或分割）落地时，会出现三份同构的会话实现——这正是仓库反复踩过的
"三份副本变一份"反模式（参见数值校验规则 `NumberValidationRule` 的教训）。届时建议：

- 抽出 `Services/Core.Onnx`（仿 `Services/Core.Halcon` 的公共库定位），承载：通用 ONNX 会话（共享+引用计数）、
  letterbox/NCHW 预处理、元数据解析（names/task）。
- 三个插件引用它；`Plugin.Yolo` 是否迁移可另行评估（最小改动原则：能不动就不动已验证件）。
- **这是公共契约/多模块级改动**，按 R12 需 architect 评审后再动。
