## 1. 构建能力：被沙箱阻断（阻塞项，需上层处理）

### 1.1 现象与证据

| 命令 | 退出码 | 关键输出原文 |
|---|---|---|
| `dotnet build FlowCanvasChecks\FlowCanvasChecks.csproj -c Debug -m:1 -nodeReuse:false` | 1 | `error MSB3491: 未能向文件"obj\Debug\net9.0\VM.Scada.AssemblyInfoInputs.cache"写入行。Access to the path 'D:\C#\VM\Scada\obj\Debug\net9.0\VM.Scada.AssemblyInfoInputs.cache' is denied.`（另有 Core.Interfaces / VM.Charts / Core.PluginGenerators 共 **4 个错误**） |
| `dotnet restore FlowCanvasChecks\FlowCanvasChecks.csproj`（默认多进程） | 1 | `已完成生成项目"...FlowCanvasChecks.csproj"(Restore 个目标)的操作 - 失败`，**0 个警告 0 个错误**（错误被吞） |
| `dotnet msbuild <proj> -t:_GenerateRestoreProjectPathWalk`（叶子工程 Core.Interfaces / HslCommunication / VM.Scada / Core.Halcon） | 0 | 成功 |
| 同上（有 ProjectReference 的工程：VM.Core / VM.Communication / VM.FlowEngine / UI / VisionMaster …） | 1 | **无任何错误文本**，只报"生成失败 / 0 个错误" |

### 1.2 根因（两层，均可复现）

1. **沙箱只给"仓库根目录"发了写权限**：`D:\C#\VM` 的 ACL 有一条
   `S-1-4-382083760-400130500 → DeleteSubdirectoriesAndFiles, Write, Delete, Synchronize (Allow)`；
   **所有子目录都没有这条**（且子目录 `IsInherited=False`，根的授权不向下继承）。
   实测写探针：根 = 可写；`FlowCanvasChecks\`、`FlowCanvasChecks\bin`、`FlowCanvasChecks\obj`、
   `VisionMaster\obj`、`Modules\`、`tools\`、`docs\`、`artifacts\logs\`、`_Retired\` = **全部 Access denied**。
   新建的根级目录（如 `_gate_tmp\`）= 可写（继承到根的授权）。
   → 这是"沙箱授权未下发到子树"，**不是** MSBuild/NuGet 的问题（在 `_gate_tmp` 里 `dotnet new`+`build`+`run` 全通）。
2. **MSBuild 默认多进程在受限会话里静默失败**：`dotnet build/restore` 默认 `-maxcpucount`，
   子节点靠命名管道通信，被拦后**内层工程失败、外层只报"0 个错误"**。
   加 `-m:1 -nodeReuse:false` 后该层恢复正常（restore 变 0 退出）——**这条要写进命令模板**，
   否则以后有人在这个环境里跑构建，会得到"0 错误但退出码 1"的假象。

### 1.3 影响与出路

- 影响：**"改断言 → build → run"这条 R65 闭环在本会话内不可执行**；也无法验证 `--no-incremental`、`pack.ps1`。
- 出路（任一）：① 把本会话切到 **full access（完全权限）**，或修复该目录树的文件权限（子目录缺沙箱授权，
  形态与 DSH 工作区授权未下发一致）；② 由**有完整权限的会话**执行 §3 的命令表并把日志交回；
  ③ 明确接受"用 12:45 二进制 + 明确标注陈旧"作为本轮 gate 口径（本报告即此口径）。
- 附带发现（与本环境相关、与产品无关）：**`File.Replace` 在沙箱内一律被拒**（`Access to the path is denied`），
  而 `File.Move` / `File.Copy(overwrite)` / `File.Delete` 都正常。`AppSettingsService.WriteReplacing` 只 `catch (IOException)`，
  `UnauthorizedAccessException` 会**直接把宿主进程带下去**（ScadaChecks/FlowCanvasChecks 各崩一次）。
  产品侧"Replace 失败退回覆盖写"的兜底在这种情况下不生效——**建议把 `catch (IOException)` 扩到
  `catch (Exception) when (ex is IOException or UnauthorizedAccessException)`**（属产品缺陷/健壮性，报给实现方，我不改）。

## 6. 变异反证（方法与仓内最近证据）

**操作法（四步，缺一不可）**
1. 选一条**新增或改过**的闸，明确它"应该拦什么"；
2. **改坏被测物**（不是改断言）：把判据针对的代码/配置改成错误形态；
3. `build`（禁用 `--no-build`）→ `run` → **必须准确变红，且红在该条上**（记下条数与失败原文）；
4. **还原** → 再 `build` → `run` → **必须变绿且条数回到基线**。
   若"改坏后仍然绿"，这条闸等于没跑过；若"改坏后整片红"，判据粒度不够。
