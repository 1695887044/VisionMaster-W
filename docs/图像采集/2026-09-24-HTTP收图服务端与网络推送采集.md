# HTTP 收图 → 视觉处理 → HTTP 反馈（服务端 + 网络推送采集 + 端到端冒烟）

承接 `2026-09-24-HTTP收图服务端依赖接入.md`（该篇只解决「用哪个服务端库、能不能在普通权限下跑」）。
本篇是**业务落地篇**：把这条链路真正接起来，并用真起服务端、真发 HTTP 图片的冒烟证明它通。

链路全貌：

```
上游系统 ──HTTP POST 图片字节──▶ HttpImageServer ──▶ ImageHub(按流程名分槽)
                                      │                      │
                                      │ 触发单次执行          │ 采集步骤取图
                                      ▼                      ▼
                                 FlowEngineService ──▶ ImageAcquisitionPlugin(Mode=Hub)
                                      │
                                      ▼
                                 FlowOutputCollector ──▶ JSON 回包
```

## 一、需求与决策

### 1. 五项已拍板决策

| # | 决策点 | 选择 | 为什么 |
|---|---|---|---|
| 1 | HTTP 触发流程的**会话来源** | **复用现有会话**：`GetSessionByName` 优先，没有（或图纸 Version 涨过）才在 HTTP 侧补编译并注册 | 界面上跑过的流程已有编译产物与运行状态，另起一套会话会出现「界面看到的状态」与「HTTP 跑的状态」两套，且会话锁各管各的 |
| 2 | body 里图像的**形态** | **编码图字节 + 宿主内存解码**（灰度 → `GenImage1`，彩色 → `GenImageInterleaved`），**零落盘** | 落盘会引入临时文件清理、并发写同名文件、磁盘 IO 拖慢节拍三类问题，而本链路只要求「把这一帧送进流程」 |
| 3 | HTTP **请求契约** | `POST /flow/{流程名}?outputs=步骤名.端口名`，`Authorization: Bearer {token}`，body = 图片字节 | 流程名放路径（一个 URL 对应一个流程，便于网关按路径分流）；输出用 query 指定（同一流程按需取不同端口，不必改流程） |
| 4 | 多流程并发的**图像路由** | `IExecutionContext` 加 `string CurrentFlowName`，`ImageHub` 按流程名分槽 | 插件只知道自己被哪个会话调用，**只有执行上下文能回答「我从哪个槽取图」**；不分槽则 A 流程的图会被 B 流程取走 |
| 5 | 监听地址/端口/Token 的**配置位置** | 写进 `AppConfig.json` 的 `HttpImageServer` 节；本期不做配置 UI | 与既有 `AppSettingsService` 的配置范式一致；现场改端口/令牌只需改文件，不必等界面 |

### 2. 关键设计取舍

**为什么用「静态 ImageHub」而不是把图塞进流程输入端口。**
图像是**每次请求都不同**的运行期数据，而 `StepModel.InputValues` 是**配置期**数据（改它会让 `FlowModel.Version` 递增、触发重编译）。
把图写进配置等于每来一张图就作废一次编译产物。`ImageHub` 是纯运行期的静态队列，与配置层完全解耦。

**为什么「槽里没有图」是阻塞等待，而不是报失败、也不是回退上一次的图。**

先说清楚这条链路里「槽空」到底意味着什么：`Mode=Hub` 的语义是「处理刚推过来的那一帧」。
上游是**先 Push 再触发流程**（`HttpImageServer` 里 `ImageHub.Push(item)` 紧挨着 `RunSessionOnceAsync(session)`），
所以正常路径下 `TryPop` 必然立刻命中、零等待。真正会走到「槽空」的只有一种情形：
**流程被别的入口（界面「运行流程」、定时器、另一路触发）拉起来跑，而这一刻还没有帧推过来。**

早期实现把这种情形报成失败，现场表现就是用户截图里那样：采集步骤红着报失败，
下游步骤连锁报「输入图像为空或未初始化」，**一条根因被两条噪音盖住**。
更糟的是它跑得飞快 —— 没有图也一路跑过去了，调用方以为流程「跑完了」。

改成阻塞等待，是把「等图」这件事**归回它本来的性质**：
对采集步骤来说，**等图就是它的正常工作状态**，等不到图不是错误。
插件在这里只做一件事：卡住不动，直到有新图推来，或者被「停止流程」的取消令牌打断。

为什么**不做旧图回退**：回退会让调用方拿到一个与本次触发无关的结果，
而且它**长得和成功一模一样** —— 现场表现为「结果偶尔不对但查不出来」。
阻塞等待则天然消除了这个歧义：要么拿到的是这一轮的新图，要么这轮压根没往下走。

**为什么「等待被打断」不算业务失败、插件也不能决定流程去向。**
「停止流程」是**用户的操作意图**，不是算法出错。若采集插件在这里返回失败并让流程中止，
就等于把「用户点了停止」翻译成了「这一步出错了」——语义错位，而且插件会获得一个它不该有的能力：
**终止整轮流程**。所以这里严格对齐既有 `DelayPlugin` 的停止行为：
`Success` 保持 `false`、插件打一条 Warn（不写 Error）、不碰 `FlowControlState`。
流程最终是否中止由引擎的取消令牌决定，**插件只负责如实汇报「我没产出」**。

**为什么 HTTP 侧要自己判一次 `session.IsRunning`。**
`FlowEngineService.TryOccupySession` 抢不到锁时**只记 Warn 然后 return**（静默吞单）。
若不复用这条判据，客户端会收到一个「success=true 但 outputs 全是上一次的值」的假成功。所以在 Push 之前先判，直接回 409。

**为什么超时不打断流程。**
单次执行的取消归引擎自己的 CTS 管，HTTP 侧去抢它的令牌会污染会话状态（把一次正常执行变成 Cancelled）。
超时只回 504 并挂 `ObserveFault` 观察者吃掉后续异常，流程在后台继续跑完。

### 3. 本轮排障：一次典型的「产物陈旧」事故

首轮冒烟 **294 通过 / 9 失败**，失败集中在「插件输出端口全是复位默认值、Hub 4 帧一帧没被取走」。

排查过程与结论：

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | 查 `ExecutionContext.CurrentFlowName` 是否漏赋值 | 是 `=> CurrentSession?.FlowName`，没问题 |
| 2 | 查 `ApplyConfigValues` / `ValueConverter` 灌值链 | 逻辑正确（同类型 `ChangeType` 直接返回） |
| 3 | 在冒烟里把 `Success` / `ErrorMessage` 一起取回打印 | **`ErrorMessage = 未知的采集模式: 2`** |
| 4 | 查 `AcquisitionMode` 定义 | `SingleFile=0, Folder=1, Hub=2` —— **2 就应该是 Hub** |
| 5 | **比对时间戳** | `Modules\Plugin.ImageAcquisition.dll` = **9:38**，`Enum.cs` = **10:35**，`ImageAcquisitionPlugin.cs` = **11:09** |

**根因：`Modules\Plugin.ImageAcquisition.dll` 是加 `Hub` 之前编出来的陈旧产物。**
运行期枚举里根本没有值为 2 的成员，`Enum.ToObject(modeType, 2)` 造出一个非法值，
`switch` 落进 `default` → 报「未知的采集模式: 2」；插件没走 Hub 分支，自然不取图、输出端口停在复位默认值。

**决定性证据是 `{mode}` 打印出的是数字 `2` 而不是 `Hub`** —— 枚举 `ToString()` 对非法值会回退成数字，
这一条就排除了「值没灌进去」，直接指向「加载的枚举里没有这个成员」。

重建插件（`Plugins\Directory.Build.targets` 的 `CopyPluginToModules` 会自动投递到 `Modules\`）后：
**304 通过 / 0 失败**。

> **教训**：`Modules\` 是插件的运行时装载目录，但它**不是**由 `VisionMaster.csproj` 构建带出来的
> （宿主工程不 ProjectReference 任何 `Plugin.*`）。改了插件源码却只重建宿主，跑的仍是旧插件。

### 5. 本轮追加：槽空改为阻塞等待（推翻早期「报失败」决策）

**触发**：现场日志截图显示，`Mode=Hub` 的采集步骤在槽里没图时报失败，
下游步骤连锁报「输入图像为空或未初始化」—— 一条根因被两条噪音盖住。

**早期实现的错在哪**：它把「等图」当成了错误。对采集步骤来说，
**等图就是它的正常工作状态**，等不到图不是失败；报失败还会让流程「没有图也一路跑过去」。

**改动**（`ImageHub.cs` + `ImageAcquisitionPlugin.cs` 两个文件）：

| 层 | 改动 |
|---|---|
| `ImageHub` | 每槽加一个 `SemaphoreSlim(0,1)`；`Push` 入队后 `Release`（吞 `SemaphoreFullException`）；新增 `WaitPop(flowName, token, out)`：先走 `TryPop` 快路径（HTTP 链路必然命中、零等待），否则 `signal.Wait(token)` 挂起，醒来一律回队列重试，取消时 `return false` |
| `ImageAcquisitionPlugin` | `AcquireFromHub` 槽空时改调 `WaitPop`；进等待时打一条 Info；被取消则返回 `Cancelled`。`RunAlgorithm` 见 `Cancelled` → `ErrorMessage="已停止等待网络图像"`、`Success` 保持 `false`、**插件打 Warn 而非 Error**，不碰 `FlowControlState` |

**为什么用「信号量 + 回队列重试」而不是 `ManualResetEventSlim` 或轮询**：
`Push` 可能发生在「`TryPop` 落空」与「挂起」之间，`SemaphoreSlim` 的计数会把这次唤醒存住，
不会丢通知（`AutoResetEvent` 同样能存一次，但 `SemaphoreSlim` 自带 `Wait(token)` 取消重载，
不必自己拼 `WaitHandle.WaitAny`）；醒来后一律回 `TryPop` 而不是直接把唤醒当成「有图」，
是为了对「被取消」和「假唤醒」都天然安全。

**为什么不需要改引擎**：等待的打断完全走既有取消令牌（`StopSession` → `CancellationTokenSource.Cancel()`），
`CompiledNode.RunSequence` 的取消检查、`FlowEngineService` 的 `OperationCanceledException` 处理都是现成的 ——
本次**零引擎改动**，行为与既有 `DelayPlugin` 的停止路径完全一致。

### 6. 本轮追加：调试试运行接入取消令牌（修「点执行后窗口假死」）

**触发**：调试阶段打开插件配置窗口，选「图像采集 + 网络采集」，点「执行」——
若槽里没有帧，窗口**假死**：状态栏停在「执行中...」，「取消」按钮点了没反应，只能强杀进程。

**根因是两条叠加，缺一不成立**：

| # | 根因 | 证据 |
|---|---|---|
| 1 | 试运行被**同步跑在 UI 线程**上 | `ExecutePlugin` 是同步 `void`；`ExecuteCommand` 是 Prism 的 `DelegateCommand`（文件头 `using Prism.Commands`），对同步委托是**就地执行**——即 UI 线程 |
| 2 | 传给插件的令牌**永不可取消** | `PluginTestRunner.Run` 里写死 `new ExecutionContext(..., CancellationToken.None)` |

叠加后的死结：插件在 UI 线程上 `WaitPop(None)` 永久挂起 → 消息泵停转 → 「取消」按钮的点击**根本派发不到** → 即便有 CTS 也永远等不到 `Cancel()`。
所以**只加令牌救不了场，必须同时把试运行挪到后台线程**。

**改动（2 个文件）**：

| 文件 | 改动 |
|---|---|
| `Engine\PluginTestRunner.cs` | `Run(...)` 参数表加 `CancellationToken cancellationToken`，替换写死的 `CancellationToken.None`。**插件侧、`ImageHub`、引擎零改动**——取消语义（`WaitPop` 返回 false → `Cancelled` → Warn）上一轮已就位 |
| `VisionMaster\ViewModels\DialogViewModels\PluginConfigShellViewModel.cs` | 见下四条 |

ViewModel 的四处改动：

1. **试运行挪后台**：`Task.Run` 包住 `PluginTestRunner.Run`，结果用 `Dispatcher.InvokeAsync` 回投 UI 线程刷状态。
   用 `InvokeAsync` 而非 `Invoke` —— 关窗流程会阻塞等这个任务收尾，`Invoke` 会和它互相死等。
2. **令牌生命周期**：每次「执行」换发新 `CancellationTokenSource`；配 `_execRunId` 轮次号丢弃上一轮迟到的回调，防止旧结果覆盖新一轮界面。
3. **「取消」= 先取消 → 等收尾 → 再关窗**：正在跑时只 `Cancel()` 令牌并把状态栏置为「⏹ 正在停止...」，**不立刻关窗**
   （关窗会释放掉后台线程正在用的会话与插件实例）；收尾回调里再 `RequestClose`。
4. **关窗兜底**：`OnDialogClosed` 先 `Cancel()`，再 `pending.Wait(2 秒)`；已停下就地释放，
   仍未停下（某插件不理会令牌）则 `ContinueWith` 把释放移交后台线程——宁可有短暂资源滞留，也不让窗口假死。

**为什么「已取消」由 ViewModel 判定，而不是给 `PluginExecuteResult` 加 `Cancel` 变体**：
取消**永远是配置窗口自己发起的**，窗口自己最清楚；在 ViewModel 里判 `token.IsCancellationRequested` 就能区分，
不必给公共类 `PluginExecuteResult`（`Shard\Core.Interfaces`）扩接口面。
于是状态栏有四态：`✅ 成功` / `❌ 失败` / `❌ 异常` / `⏹ 已取消 - 已停止等待网络图像`，
最后一种不再把「用户主动停止」误报成故障。

**后台线程安全性核查（结论：无需额外改造）**：

| 触碰点 | 结论 | 依据 |

## 四、已知边界

1. **仅 HTTP，未启用 HTTPS。** `WebserverSettings` 的 `ssl` 参数默认 `false`，按内网部署口径暂不启用。
   跨网段/不可信网络使用前必须补 TLS，否则令牌是明文传输的。
2. **默认令牌只 Warn 不拦启动。** `Token == "visionmaster"` 时打一条 Warn 就继续跑。
   这是「开箱即用」与「安全默认」的折中，**投用前必须改 `AppConfig.json`**。
3. **本期不做配置 UI。** 改端口/令牌/超时只能改 `AppConfig.json` 后重启。
4. **`ImageHub` 是单进程内存态。** 进程重启即丢；多实例部署时各实例的槽互相不可见（不做分布式分发）。
5. **每流程槽上限 8 帧，超限丢最旧。** 上游突发推送快于流程消费时会静默丢帧，不回压上游。
6. **超时不打断流程。** 默认 30s（`RequestTimeoutMs`），超时回 504，流程在后台继续跑完。
   上游重试需自行处理「上一帧仍在跑」的 409。
7. **未做并发压测与长稳。** 冒烟是串行单请求，多路并发收图 + 大图（数 MB）下的内存与吞吐未测。
8. **插件改动后必须重建插件工程**（见上文「三、3」），只重建宿主不会刷新 `Modules\` 里的 DLL。
9. **`Mode=Hub` 槽空即阻塞等图，不报失败、不回退旧图。** 语义见「一、2」。
   影响面：若某条流程**长期没有帧推来**，该次执行会一直卡在采集步骤（不是错误，是设计如此）；
   停止方式就是界面上的「停止流程」，此时本步按「未成功 + Warn」收尾。
10. **并发抢图时可能出现「等不到的图」。** 两个请求几乎同时推同一流程的帧时，
    A 的帧可能被 B 取走，A 会一路等到 HTTP 侧 30s 超时才回 504。
    本期按「上游串行投递」的口径先不处理（配合 #6 的 409 重试即可规避）。
11. **调试试运行与正式运行共用同一个 `ImageHub` 槽（会抢生产待处理帧）。**
    `ExecutionContext.CurrentFlowName` 在调试时取的是**真实流程名**，所以配置窗口点「执行」会去取
    **正式运行待处理的那一帧**——调试期间恰好有生产帧推来，可能被调试吃掉，
    导致正式那次执行一路等到超时（配合 #6 的 504/409）。
    本期不处理（`Mode=Hub` 调试的语义就是「真取一帧」），**调试请在无生产流量时进行**。
12. **调试执行的取消是「软取消」，上限 2 秒。** 取消令牌只能叫停**理会它**的插件
    （如网络采集等图，毫秒级退出）。若某插件在算法内部长阻塞且不检查令牌，
    关窗会等满 2 秒后强制关掉，其清理移交后台线程（资源短暂滞留，不会泄漏）。
