# 缩略图快路径：先在 HALCON 侧等比缩小再转位图（A2）

- 类型：性能优化（消除每帧×每端口的全尺寸托管分配与随之而来的 GC 压力）
- 前置：[A1（`ToHImage` 去 HGlobal 中转）](2026-10-04-图像采集原始像素转HImage去掉HGlobal中转（A1）.md)
- 涉及工程：`Core`（`HalconImageHelper`）、`VisionMaster`（`ImageCollectionService`）、`FlowCanvasChecks`（新增断言）
- 日期：2026-10-04

---

## 1. 改了什么

### 问题

`ImageCollectionService.MakeThumbnail` 原先的顺序是**先转换、后缩放**：

```
整张图 → HalconImageHelper.ToBitmapSource()（全尺寸位图，500万像素彩图约15MB）
       → TransformedBitmap(full, scale)（缩到最长边 160px）
```

而它在**每帧 × 每输出端口**上被调用（`BuildFrame` 是 `Harvest` 与 `Capture` 的共同出口）。
为一张 160px 的缩略图把整张图搬进托管堆，随即被 GC 回收——旧注释里其实已承认这笔代价。

### 改法

把顺序倒过来：**先在 HALCON 侧等比缩小，再转位图**。

| | 改造前 | 改造后 |
| --- | --- | --- |
| 转换量 | 全尺寸（如 1920×1080 = 200 万像素） | 缩略图尺寸（160×90 ≈ 1.4 万像素） |
| 托管分配 | 全尺寸位图（灰度2MB / 彩色6MB） | 缩略图位图（约 14KB） |
| 缩放位置 | WPF 侧 `TransformedBitmap` | HALCON 侧 `ZoomImageSize` |

新增 `HalconImageHelper.ToThumbnailSource(HImage?, int maxSize)`：

1. 读通道数与像素类型，做守卫（宽高非法 / 指针为空 → 返回 null）；
2. **只对 `byte` / `int2` / `uint2` 走快路径**（理由见 §2）；
3. 按最长边等比算目标尺寸；原图本就小于上限时直接转（不放大）；
4. `ZoomImageSize(targetW, targetH, "bilinear")` 缩小 → 走既有 `ToBitmapSource` → **Dispose 缩小图**。

`MakeThumbnail` 改为：先试快路径，返回 null 时回落原有全尺寸路径（行为与历史逐字一致）。

## 2. 三个关键决策

### 2.1 插值必须是 `bilinear`，不能用默认值

HALCON `ZoomImageSize` 的 `interpolation` 默认是 `"constant"`（最近邻）：缩十几倍以上时，细线条会**整条消失**、出现摩尔纹——那不是"缩小"，是失真。`"bilinear"` 取邻域加权，才是缩略图该有的样子。

**这条有判别性测试守着**（见 §3 第④组）：64×64 图每 4 行一条 1 像素白线，缩到 32×32 后白线仍可见（最大灰度 255）；若用最近邻会接近 0。

### 2.2 `int4` / `real` 刻意不走快路径

`HalconImageHelper.StretchToGray8` 对 `int4` / `real` 是**按本图自身 min/max 线性拉伸到 0~255** 再显示。先缩小会让量程取自缩小后的图，缩略图对比度与全图不一致。

这类图（视差图 / 深度图 / 浮点结果图）本就少见，为省一点开销引入"缩略图和大图看起来不一样"的困惑不值得。故这两类返回 null，回落全尺寸路径。

### 2.3 缩略图不参与任何视觉算法（本改造的前提）

已逐点核实：

| 证据 | 位置 |
| --- | --- |
| `Thumbnail` 的**唯一消费点**是图像集网格的渲染 | `ImageGallery.xaml`：`<Image Source="{Binding Thumbnail}" Stretch="Uniform" />` |
| 类型注释明确"仅供缩略图网格渲染" | `ImageFrame.cs` |
| 大图 / 导出 / 标注 / 取色走的是**全尺寸原图** `frame.Image` | `ImageExporter.cs` 用 `WriteImage(frame.Image, ...)`；XAML 大图绑 `SelectedFrame.Image` |

因此这条路径与算法结果没有任何交集。**§3 第⑦组用逐字节比对证明了这一点**。

## 4. 性能实测（2026-10-04，Release，`FlowCanvasChecks.exe --perf`）

改造前/改造后两套实现**同进程交替测量**，"改造后"直调生产代码 `ToThumbnailSource`，"改造前"按原实现复刻（全尺寸转位图 + `TransformedBitmap`）。每组 200 轮，取中位数：

| 场景 | 改造前 | 改造后 | 每帧省 | 托管分配/帧 | 30fps 折算 |
| --- | --- | --- | --- | --- | --- |
| 灰度 1920×1080 (2MB) | 0.856 ms | 0.070 ms | **0.786 ms（91.8%）** | 1.98 MB → 17.5 KB（省 99.1%） | 23.6 ms/s，59 MB/s |
| 彩色 1920×1080×3 (6MB) | 5.126 ms | 0.180 ms | **4.946 ms（96.5%）** | 11.87 MB → 89.1 KB（省 99.3%） | 148.4 ms/s，354 MB/s |
| 彩色 2448×2048×3 (5MP, 15MB) | 14.079 ms | 0.266 ms | **13.814 ms（98.1%）** | 28.69 MB → 130.3 KB（省 99.6%） | 414.4 ms/s，857 MB/s |

**两点解读**：

- **A2 是两项改造里收益更大的一项，且同时省时间与托管分配。**彩色 5MP 图每帧省 13.8 ms、28.69 MB——注意 `MakeThumbnail` 在**每帧 × 每输出端口**上被调用：30fps × 5 端口 = 每秒 150 次调用，即**每秒约 2.1 GB 的托管分配被消除**。这正是 GC 压力（节拍抖动）的主要来源。
- **改造前彩色 5.1 ms 的大头是三平面→交错的逐像素托管循环**（`HalconImageHelper.FromThreeChannels` 对 200 万像素跑 `for` 重排），缩小后这个循环从 200 万次降到 1.4 万次。

数字与独立验证工程的三次运行高度一致（灰度 0.836/0.887/0.856 ms），可复现。

基准已固化为 `FlowCanvasChecks\PerfChecks.cs`（`--perf` 选择性运行，含回归护栏断言与托管分配对比）。**必须 Release 构建**。

### 5.1 A3 为什么不做（决定记录）

**做法**：图集采集加"面板不可见就不拷贝"的门控（判据拟用 `LayoutDocument.IsSelected` + 主窗口未最小化，含滞回宽限期）。

**决定：不做。** 三条理由：

1. **报警留存会静默变空（决定性）**。`ScadaRuntimeHost` 在报警时调 `ImageCollectionService.SaveSnapshot` 落盘图集，而 SCADA 运行时操作员必然不在「视觉图像」标签上（从组态画面启动运行窗口，主窗口常停在组态画面甚至最小化）——恰好命中"没在看"的判据。结果是**最需要留证据的现场，复盘时没有图**，且不报错、不告警。
2. **与既有教训直接冲突**。本仓库为"循环运行图不进画布"查过一轮（见 `ImagePreviewCapture` 与 `ImageCollectionService.Capture` 的注释），结论是"**静默缺图是最难查的一类故障**"。A3 是有意制造静默缺图，会让"图有时候没有"重新变成不可归因的问题。
3. **收益场景与危害场景重叠**。省拷贝主要发生在"连续运行 + 人不在图页"，而那个组合正是**调试期**——最需要看清图对不对的时候。

**收益边界**：A3 不影响视觉算法精度（图集是只读旁路，图不进流程、不回流），危害全在证据链与可诊断性。

**替代方案（若将来确有内存压力）**：做"**不可见时降级为每轮只保留 1 张**"而非"完全不采"——省的是保留内存（N 帧 → 1 帧），不省拷贝，因此不触发上述任何危害：报警留存仍有 1 张、切回来立刻有当前帧、单次运行也有图。注意这与现有 `KeepFrameHistory=false`（同槽位覆盖）是**两条不同的轴**，前者按"面板可见性"降级，后者按"槽位"覆盖。
