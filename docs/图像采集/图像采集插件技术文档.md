## 一、总览

### 1.1 插件身份

| 项 | 值 |
| --- | --- |
| 工程 / 类型 | `Plugins\Plugin.ImageAcquisition` / `Plugin.ImageAcquisition.ImageAcquisitionPlugin` |
| 显示名 | 图像采集（`GroupName=常用工具`，图标 `\uf1c5`） |
| 依赖 | `Core.Interfaces`（契约）、`Core.Halcon`（HImage/预览控件）、`Core.Controls`（可链接参数编辑器/预览扩展）、`UI`（样式库）、`halcondotnet` |
| 不依赖 | 宿主工程（`VisionMaster`/`VM.Core`）——插件只认契约，宿主能力全部经执行上下文与配置上下文递送 |
| 一句话职责 | 把"图"从**文件 / 文件夹 / 网络推送 / 相机**四种来源变成 HImage 进入流程，并把最新图按需投到主界面视图窗口 |

### 1.2 四种采集模式一览

| 模式 | 枚举 | 数据源 | 典型场景 | 关键语义 |
| --- | --- | --- | --- | --- |
| 指定图像 | `SingleFile=0` | 单个图像文件路径 | 调试、单图复现、脚本化验证 | 读图失败=业务失败；`TotalFiles=1` |
| 文件目录 | `Folder=1` | 文件夹内按**自然序**排序的图像 | 离线批处理、序列图回放 | 每轮重新枚举（不缓存）；索引越界**夹取并在结果里留痕** |
| 网络推送 | `Hub=2` | 外部程序经 HTTP 推入本流程的图像槽 | 相机/PLC/上位机"推一张跑一次" | 槽空**阻塞等待**（不是失败）；停止流程可打断；取消≠业务失败 |
| 相机采集 | `Camera=3` | 方案里已配置相机的帧队列 | 产线连续采图（推模式） | 每帧只被消费一次；**超时永远有限**；掉线/未采流/超时三类失败分开报 |

> 历史沿革：相机模式曾在 2026-09-15 因"只生成占位图却报成功"被**整体删除**，2026-09-25 随相机契约层一期落地后**重新实现**——这条曲线本身是一条设计原则（宁可没有，不可假成功）。

## 二、技术文档

### 2.1 端口与配置面

插件的公开面严格分四类，界面绑定与持久化口径各不相同：

| 类别 | 成员 | 可变量链接 | 持久化 | 说明 |
| --- | --- | --- | --- | --- |
| 输入端口 | `FilePath`(string)、`FolderPath`(string)、`FileIndex`(int)、`FrameTimeoutMs`(int) | ✅ | InputValues（键=端口名） | 全部 `IsRequired=false`：四种模式各用各的，用不到的口留空是合法状态 |
| 输出端口 | `Image`(`OutputPort<HImage?>`)（重载语义见下） | — | 运行期 | 由基类 `AutoDisposeRoundOutputs` 负责轮首回收 |
| | `CurrentPath`(string)、`CurrentIndex`(int)、`TotalFiles`(int) | — | 运行期 | 文件模式=路径/索引/总数 |
| | `FrameId`(long)、`ReceivedCount`(long) | — | 运行期 | **相机模式精确帧号**；非相机模式为 0 |
| 纯配置项 | `Mode`、`DisplayViewIndex`、`CameraSerial`（均带 `[StepConfig]`） | ❌ | InputValues（键=属性名） | 永不参与连线；`DisplayViewIndex` 写入即夹取 0~9 |
| 纯界面状态 | `PreviewImage`、`PreviewImagePath`、`StatusMessage/StatusLevel`、`FileCount`、`CurrentFileName`、`CameraOptions/SelectedCameraOption/CameraStateText`、`Push*` 系列 | — | 不持久化 | 只在配置窗口存活 |

要点：

- **索引/总数在相机模式下是重载语义**（`CurrentIndex`=第几帧、`TotalFiles`=累计收帧数）：这是为了不让既有下游接线全部重连的兼容做法；2026-10-03 新增 `FrameId`/`ReceivedCount` 两个**无重载**的精确口，新接线一律用新口。
- **相机寻址用序列号**（`CameraSerial`）：序列号是相机对外寻址键（收图 URL 里的那段）且不随显示名变化；存 Id 无法人工核对，存名字改名即断链。
- `FrameTimeoutMs` 是**端口**而不是配置项：不同产品的等图节拍不同，要能被上游变量控制；填 0 = 用相机自身配置（`CameraSettings.FrameTimeoutMs`，基类保证 ≥1）。

### 2.2 执行核心（`ExecuteCore`，唯一一份）

`RunAlgorithm` 只做三件事：**开轮清零 → 调 `ExecuteCore` → 按结果写端口与日志**。四条链路都在 `ExecuteCore` 里，互不干扰：

| 结果形态 | 处理 | 为什么 |
| --- | --- | --- |
| `Success` | 写全部输出口 + `PublishPreview`（`DisplayViewIndex>0` 时）+ Info 日志 | 成功文案也被复用为"做了什么"的说明 |
| 业务失败 | `ErrorMessage` + Error 日志；输出口保持开轮清零值 | 下游不会读到上一轮残留（`CurrentIndex/TotalFiles/FrameId/ReceivedCount` 手动归零，基类只清 IDisposable 值） |
| 取消（等图被打断） | `Success=false` + `ErrorMessage=人话说明`（"已停止等待图像"），**不算业务失败** | 流程去向由引擎的取消语义决定，插件绝不触碰流程控制状态 |
| 异常 | 基类 `Execute` 统一转失败并落日志（`RethrowOnException=false`） | 插件不必到处写 try/catch，同时不吞异常信息 |

各模式的收尾边界（最要紧的三处）：

1. **文件模式**：`ReadImage` 抛异常时**先 Dispose 已创建的 HImage 再上抛**（HALCON 对象失败路径不释放会持续吃非托管内存）。
2. **Hub 模式**：槽空→`WaitPop`（先探快路径，正常 HTTP 链路零等待）；被打断→Cancelled；**绝不回退旧图**（回退会产出"长得像成功"的错结果）。
3. **相机模式**：`Closed`（用户没连）/ 找不到序列号 / `Online` 未采流 / 超时四类分开报；超时文案必须带 `相机状态 + 待消费帧数 + 累计收帧 + 溢出丢帧`——现场"没有图"要先分清是掉线、没触发、还是流程太慢没消费完。**不做"重试等下一帧"**：这一帧没等到就是没等到，继续等只会让流程越来越滞后。

### 2.3 原始像素 → HImage 的唯一转换核心（`ToHImage`）

Hub 与相机两条链路的像素**逐字节同约定**，因此只允许一个转换核心（各写一份早晚出现"相机彩色图反色、网络推送正常"，而灰度图上完全看不出来）：

- **约定**：灰度=1 字节/像素走 `GenImage1`；彩色=BGR 交错 3 字节/像素走 `GenImageInterleaved("bgr")`；HALCON 侧通道 1/2/3 = **R/G/B**（与仓库 `ColorSampler` 同一口径）。
- **≥4 通道（BGRA/RGBA）先抽掉 alpha 压成紧凑 BGR**：直接交给 `GenImageInterleaved` 不报错但整帧错位花屏。
- **入口三守卫**（2026-10-03 补全）：
  1. `宽×高×通道` 用 **long** 计算并拒绝 `> int.MaxValue`（int 溢出成负数会让"长度不足"校验**反面放行**，最后以 `AllocHGlobal(负数)` 抛难懂的错）；
  2. 长度不足直接拒（不足时 HALCON 会越界读 HGlobal 缓冲，轻则错乱重则进程崩）；
  3. `channels==2` 明确拒绝（没有约定好的解释方式，静默按灰度读会读错半张）。
- 走非托管中转的原因：`gen_image1`/`gen_image_interleaved` 只认裸指针且**复制**数据（区别于 `gen_image1_extern` 的引用+归还回调），所以 Copy 后立即 `FreeHGlobal` 是安全的。

### 2.4 显示链路（PublishPreview → 图像集 → 画布）

三个环节，各自对应一个"只在循环运行下现形"的时序缺陷（2026-10-03 全部修复，详见 §5.8）：

| 环节 | 机制 | 已固化的纪律 |
| --- | --- | --- |
| ① 发布 | `PublishPreview(image, 窗口号)`；**窗口号就是 1~9，直传不要 +1**（消费端按"ViewIndex == 窗口号"等值筛选） | 推图是锦上添花：投递失败只记 Warn，绝不把一次成功采集判成失败（`TryPublishPreview`） |
| ② 捕获 | 宿主实现 `IImagePreviewCapture`，`PublishPreview` 在**发布线程**上先同步 `CopyImage` | 这张图**活不过发布方的下一轮**（基类轮首释放端口值）；异步到 UI 线程再拷就是死图 |
| ③ 收录/显示 | `ImageCollectionService` 收到帧副本 → 与本轮的"待清空"**同一 UI 批次**完成替换 → 画廊刷新（`DispatcherPriority.Normal`） | 界面只能看到"旧图 → 新图"，绝不出现"旧图 → 空 → 新图"；清空/插入同批、刷新不被插帧洪水饿死 |

配套语义（2026-10-03 与用户确认的"方案 A"）：

- `RunStartMode=覆盖本流程`（默认）与 `清空整张画布` 两种口径**都不在轮首清**，改为"本轮第一张新图到达时"清+插同批；
- **本轮没有任何新图 ⇒ 不清空**，画布保持上一轮（监视器语义：有图才有替换）；故障由步骤状态/日志暴露；
- 用户手动「清空画布」仍立即生效；
- 诊断：日志首帧 + 每 200 帧一条 `[图像集] 已收录 N 帧（最近 流程·发布方 WxH → 窗口 N）`，发布时图已失效则告警——"图不进画布"从此可一眼区分"没收录"还是"收录了没刷新"。

### 2.5 配置界面（`ImageAcquisitionView`）

- **布局**：左表单（`1*`，MinWidth 300 / MaxWidth 430）+ 右预览与信息栏（`1.6*`，MinWidth 240）；根 `MinWidth=560 MinHeight=280`（按宿主对话框最小内容区 624×304 反推），TabControl 分「基本参数 / 图像参数」。
- **采集模式**用 `WrapPanel` 排四个单选项（模式从 3 涨到 4 后，窄窗口横排会把最后一个挤出可视区）。
- **信息栏**（右侧常驻）：左边显示来源路径（`PreviewImagePath`），右边显示状态消息，颜色由 `StatusLevel` 驱动（`Info 绿 / Warning 橙 / Error 红`），色值只在 XAML 的 DataTrigger 里。
- **相机页**：下拉同时显示"名字 + 当前状态"（`CameraOption.StateText`）；**刻意没有"预览相机图像"按钮**——预览需要设备对象，而配置态只拿得到快照，硬要预览就得让插件持有宿主对象；相机预览归于「系统 → 相机设置」（那里的 Live 预览走 `TryGetLatest`，不消费生产帧）。要验证本步骤能否取图，用配置窗口的「执行」试运行（与正式运行同一段代码）。
- **推送测试页**：宿主经 `PluginConfigContext` 透传流程名/HTTP 参数/令牌/超时；"选本地图片并推送"真发一次 `POST /flow/{流程名}`，验的就是外部客户端走的那条路（鉴权、URL 转义、流程触发、回包）。服务是否在听由 `PushServiceHint` + 分级色提示；信息栏是否显示这条状态**由当前模式决定**（只有 Hub 模式显示，不覆盖其他模式的路径/相机提示）。
- **链接感知**：`FilePath/FolderPath/FileIndex` 被变量链接时，配置态不做路径校验、不报"请先选择"（路径要运行时才由上游产出）；文件夹路径被链接时预览直接给中性说明并跳过，文件索引被链接时预览文案注明"运行期以链接值为准"。
- **预览**：异步读图（后台 `ReadImage` → 回 UI 线程赋值）+ 轮次号 `_previewLoadId` 丢弃过期结果 + `_disposed` 拒绝往已关闭窗口写图；载体 `ImageReadOnly`。

### 2.6 生命周期与资源所有权

| 资源 | 所有者 | 释放时机 | 纪律 |
| --- | --- | --- | --- |
| 输出口 HImage（`Image`） | 插件实例（经端口） | 基类在**下一轮开始**统一回收（`AutoDisposeRoundOutputs`）；透传场景自动跳过 | 插件开轮不再手动 Dispose 旧输出，避免与新输出口打架 |
| 预览图（配置态） | 插件实例 | `PreviewImage` setter 换图弃旧；对话框关闭 `Dispose()` 置 null | 绑定在 UI 线程同步刷新，释放的是"已不被 UI 引用"的旧图 |
| 相机帧 / Hub 帧（byte[]） | 设备侧队列 / ImageHub | 全部托管数组，无需 Dispose | 队列有上限；丢帧必计数（相机）或丢最旧（Hub） |
| 图像集副本（显示用） | `ImageCollectionService` | 淘汰/覆盖/清空时由采集服务释放 | 显示端只读不释放；副本在**发布线程**拷出 |
| 相机设备 | `CameraProvider` | 方案切换/设备删除时统一 `SyncFromSolution` | 界面只改配置+标脏，绝不自己 new/Dispose 设备 |

`Dispose()` 顺序：先立 `_disposed` 标记（在途读图回来只释放不赋值）→ `_previewLoadId++` 作废在途 → 置空预览（由 setter 释放）→ `base.Dispose()`（回收输出口非托管值）。

## 三、设计原则

> 每条都是踩过坑后的结论；括注"落点"指这条原则体现在哪段代码/断言上。

**A. 数据与状态**

1. **一份实例一份数据，四类成员各归其位**——数据流参数=输入端口、永不链接的配置=`[StepConfig]`、纯界面状态=普通属性。（落点：类头注释 + `VisionPluginBase` 默认灌值/回写）
2. **一个事实源**：扩展名白名单只有一处常量，执行核心/文件夹列表/浏览 filter 全部由它派生；`DisplayViewIndex` 三处语义统一为"真实窗口号 1~9"。（落点：`ImageExtensions`；2026-09-15 整改）
3. **状态消息与级别必须成对更新**——唯一写入口 `SetStatus(message, level)`，否则典型症状是"失败变红之后再成功，颜色还停在红"。（落点：`SetStatus`；配置视图优化）
4. **插件只管语义，视图只管颜色**——`StatusLevel` 是纯语义枚举，色值只在 XAML DataTrigger，插件不引用任何 Brush。
5. **重载必须留下退路**：相机模式 `CurrentIndex/TotalFiles` 的口语义重载保留（不打断已有接线），但新增 `FrameId/ReceivedCount` 无重载口供新接线使用。

**B. 失败与边界**

6. **绝不静默**：能报的错一定要报出来，且报"下一步怎么办"（"请到系统→相机设置添加该相机"）；写值失败不许被宽容 catch 吞掉（枚举持久化缺陷的根因）。（落点：四类失败文案、`ValueConverter` 枚举分支、图像集收录诊断）
7. **宁可没有，不可假成功**：占位实现（旧相机模式）整体删除胜过返回 `Success=true`；`Success=false` 的取消不算业务失败，也不写 Error。
8. **取消 ≠ 失败 ≠ 超时**，三者分开处置：取消只 Warn、不碰 `FlowControlState`；超时是业务失败且必须带诊断上下文（状态/队列/计数）。
9. **等图必须有超时且响应取消**：无超时等图=现场只能杀进程（参考工程的原罪）。（落点：`FrameTimeoutMs` 端口 + `CameraSettings` 兜底 ≥1 + `WaitPop(token)`）
10. **链接端口不做配置态校验**：路径要运行时才由上游产出，配置态判"不存在"是假告警；反过来，被链接时预览要给中性说明而不是报错。
11. **不确定性优先暴露成"可见的失败"，而不是"猜一个默认"**（相机模式宁报"未选择相机"也不自动挑一台）。

**C. 所有权与时序**

12. **图像引用活不过发布方的下一轮**——需要留存必须在发布线程同步拷贝（`IImagePreviewCapture`）；事件订阅者拿到的是"可能将死"的引用。（落点：捕获钩子 + `Captured` 标志）
13. **每轮更新必须原子**：清空与插入同一 UI 批次，界面只能看到"旧图→新图"；本轮无图则不动（监视器语义）。（落点：`ApplyPendingClearFor` + 方案 A 断言）
14. **刷新不能被生产洪水饿死**：与插帧同优先级（`Normal`）才能 FIFO 公平；低优先级刷新在循环下会被永久饿死。（落点：`QueueRecompute`；有反证断言）
15. **异步必须带身份与生命周期守卫**：轮次号丢弃过期结果、`_disposed` 拒绝写已关闭窗口。（落点：`_previewLoadId` / `_disposed`）
16. **进过非托管世界的对象，失败路径要自己收拾**（`ReadImage`/`GenImage*` 失败先 Dispose 再上抛，否则失败次数会累积成内存泄漏）。

**D. 硬件与外部链路**

17. **推模式 + 消费语义**：设备持续入队、流程按节奏消费，每帧只被取一次；预览只读 Peek（防"一开监视窗口就偶发漏检"）。
18. **帧队列有上限、丢帧必计数**：`OverflowCount`（处理不过来丢最旧）与 `DroppedFrameCount`（掉线/停止丢弃）**原因与处置不同，绝不合并**。
19. **"在线未触发"与"掉线"必须分开**：心跳+帧超时双判据，否则会把正常暂停渲染成故障，把运维引到不存在的故障上。
20. **配对键必须稳定且可人工核对**：用序列号而不是显示名/内部 Id；改名不失联。
21. **新链路独立端口，不回归既有链路**：相机收图 19100 与网络推送 19000 分开。
22. **监听地址 ≠ 可连接地址**：`0.0.0.0`/`[::]` 展示成"本机 IP"，否则客户端填了连不上还查不出原因。
23. **契约层零 Helcon / 零第三方**：帧以 `byte[]` 传递，避免换一家相机把全部插件绑死同一 HALCON 版本。

**E. 工程纪律**

24. **编译 0 错误不代表界面可用**：XAML 绑定模式/资源键是运行时校验——新增/改动对话框必须真打开一次（TwoWay 绑只读属性=打开即抛）。
25. **改了插件源码必须重建插件工程**：`Modules\` 不由宿主工程带出，只重建宿主跑的仍是旧 DLL（曾致冒烟 294/9 的"产物陈旧"事故）。
26. **验证以历史基线为准并甄别环境性失败**：警告数/通过数对基线；拷贝失败先查是否有人在跑 VisionMaster 占用 `Modules\`。
27. **动手前读源码核实假设**：多个"自我误判"（如以为 `Value`/`TypedValue` 不同源）都是靠读契约源码推翻的。
28. **用户明确排除的范围不得擅自恢复**，需用户重新提出（网络推送测试曾被搁置，同日用户重启后才实施）。

## 四、使用说明

### 4.1 快速上手（配置窗口）

1. 流程里拖入「图像采集」→ 双击/右键打开配置窗口（左表单、右预览与信息栏、底部状态）。
2. 在「基本参数 → 采集模式」选四种模式之一，按 §4.2 完成对应配置。
3. 需要投到主界面时，到「图像参数」页选「显示窗体」（`图像窗口1~9` / `不显示`，默认窗口 1）。
4. 用窗口底部「执行」试运行（跑的就是正式运行同一段代码），确认信息栏状态与右侧预览。
5. 「确定」写回步骤（只写内存，方案保存另算）。

### 4.2 四种模式怎么配

**① 指定图像**
- 「图像路径」：双击下划线区域浏览选图（支持 `.bmp .jpg .jpeg .png .tif .tiff`），或点 🔗 链接上游变量。
- 信息栏即时校验：空→橙"请选择图像文件"；文件不存在→红。已链接变量时不做校验（运行期才产出）。

**② 文件目录**
- 「文件夹路径」：浏览选择；「文件索引」：0 基，可手填或链接变量。
- `◀ ▶` 翻页、`刷新预览` 重扫目录；"当前文件：xxx（共 N 张）"随索引更新。
- **排序是自然序**（`img2` 在 `img10` 前），与资源管理器一致——文件索引直接对应工件顺序，排序错=顺序错。
- 运行期每轮重新枚举（新增/删除的文件当轮可见）；索引越界自动夹取到有效区间，并在结果文案里注明"索引 X 超出 0~N，已夹取"。

**③ 网络推送（Hub）**
- 页面显示宿主收图服务状态（绿=正在监听 / 橙=未在听，附原因）与四行接口说明。
- 表单：流程名（预填当前流程，可改成不存在的名字验 404）、主机、端口、令牌（填错验 401）；「选择本地图片并推送测试」= 真发一次 `POST /flow/{流程名}`，结果区显示状态码/耗时/图像尺寸/输出摘要/错误原因。
- 流程侧语义：本步骤从**本流程的图像槽**取一帧；槽空会阻塞等新图（日志："槽内暂无图像，开始等待网络推送"），点「停止流程」可打断。

**④ 相机采集**
- 先在「系统 → 相机设置」添加相机（选驱动类型 + 填序列号，网络相机是"填序列号"，不是"搜设备"）并连接/开始采流。
- 回到本页：下拉选相机（同时显示名字与当前状态）；`当前状态：` 行说明"现在能不能跑"（未连接=红 / 已连接但未采流=橙 / 采流中=空）。
- 「取图超时(ms)」：默认 0=用相机自身配置；可填/链接变量。
- 运行失败时的三类文案即排查指引：找不到序列号（去相机设置添加）、未连接（去连接）、等图超时（附状态/待消费/累计/溢出计数）。

### 4.3 显示窗口号与视觉图像页

- 「图像参数 → 显示窗体」= 目标窗口号（0~9；0=不显示）。采集成功后图会投到该窗口，**编号直传**（选"图像窗口1"就进第 1 格）。
- 视觉图像页每格只收"显示窗口号=自己"的图；页面上每轮的更新语义见 §2.4。
- 若格子一直空：先看「系统参数设置 → 画布」的**启用画布采集**与**收录插件注入的图像**两个开关是否开；再看日志里有没有 `[图像集] 已收录 N 帧`（有=收录成功，问题在显示侧）。
- 相机图像的实时预览在「系统 → 相机设置」（Live），**不在**采集步骤的配置窗口。

### 4.4 对外接口速查（给集成方）

**A. 网络推送（Hub）—— 推一张跑一次**

| 项 | 值 |
| --- | --- |
| 地址 | `POST http://{Host}:{Port}/flow/{流程名}?outputs=步骤名.端口名`（`outputs` 可省略=回全部端口） |
| 鉴权 | `Authorization: Bearer {Token}`（默认占位值 `visionmaster`，投用前必须改） |
| 请求体 | 图片原始字节（非 multipart）；可选头 `X-Image-Name`（回传为 `CurrentPath`，缺省为 `hub://{流程名}`） |
| 回包 | JSON：`success / requestId / flow / elapsedMs / image{width,height,channels} / outputs`；失败 `{success:false, message}`（错误在 **message** 字段） |
| 错误码 | 401 无/错令牌；404 未知流程；400 空 body；409 流程正在运行；504 等待结果超时（不打断流程，后台继续跑完） |
| 约束 | 同一流程串行：一次 POST = Push 一帧 + 单次执行；槽只留最新；每槽上限 8 帧（丢最旧） |
| 配置 | `AppConfig.json → HttpImageServer`（Enabled/Host/Port/Token/RequestTimeoutMs），本期无配置 UI |

**B. 相机推帧/心跳 —— 一期网络相机**

| 项 | 值 |
| --- | --- |
| 推帧 | `POST http://{Host}:19100/camera/{序列号}/frame`，头 `X-Image-Name`，body=图片字节；回 `{success,serial,frameId,received,pending,overflow,bytes}` |
| 心跳 | `POST /camera/{序列号}/heartbeat`（无 body，**每秒一次，与推图节拍无关**——暂停推图也必须继续发，否则 3 秒判掉线） |
| 鉴权 | 同上 Bearer；端口 19100 独立于 19000 |
| 工具 | `Tools\VirtualCameraClient`（独立 WPF"假相机"：选图片文件夹按 IntervalMs 连续推图 / 手动推单张；心跳独立循环） |

### 4.5 相机设置里哪些参数真的生效

| 参数 | 是否生效 | 说明 |
| --- | --- | --- |
| `FrameTimeoutMs` | ✅ | `WaitNextFrame` 等图超时（采集步骤端口可覆盖） |
| `BufferCapacity` | ✅ | 环形队列容量，默认 8；满则丢最旧并计 `OverflowCount` |
| `HeartbeatTimeoutMs` | ✅ | 判活阈值，默认 3000ms；超时判掉线并清空陈旧帧 |
| 曝光 / 增益 / 触发模式 | ❌（网络相机一期） | 由客户端决定，软件侧无下发通道；界面已显式标注 |

状态语义（四态）：`Closed`（未打开）→ `Connecting`（等待客户端接入/重连中）→ `Online`（**在线但没出图**：没触发/暂停——正常）→ `Streaming`（正在收帧）。

### 4.6 常见故障排查

| 现象 | 多半是 | 处置 |
| --- | --- | --- |
| 步骤失败"尚未选择相机" | 没在下拉里选 | 本页选一台；方案里没有相机则先去相机设置添加 |
| 失败"找不到序列号为 X 的相机" | 相机被删/序列号改过 | 「系统 → 相机设置」确认，或本页重选 |
| 失败"未连接（…）" | 相机 `Closed` | 相机设置里点连接 |
| 失败"等图超时（N ms）；相机状态：已连接·未采流…" | 在线未触发/没开始采流 | 相机设置点「开始采流」；网络相机确认客户端在推 |
| 失败文案里 `溢出丢帧` 持续增长 | 处理速度跟不上相机节拍 | 缩短处理链或降帧率；**每帧=一个工件，丢帧必须查** |
| Hub 模式日志"槽内暂无图像，开始等待网络推送"长期不动 | 客户端没推 / 流程名不一致 / 令牌错 | 核对 `POST /flow/{流程名}` 的流程名与令牌；停止流程可退出等待 |
| HTTP 回 409 | 上一帧还在跑 | 上游需串行重试（同流程同时只允许一次执行） |
| 视觉图像页空白，流程明明成功 | 画布开关关着 / 显示窗口号=0 / 帧没进图像集 | 看 §4.3；日志有"已收录 N 帧"=显示侧问题，没有=收录侧问题（先看插件 DLL 是否重建） |
| 循环运行时画面黑↔图频闪 | 2026-10-03 之前的版本（轮首预清） | 升级到含"每轮原子替换"的版本 |
| 文件夹里新增的图读不到 | 扩展名不在白名单（`.bmp/.jpg/.jpeg/.png/.tif/.tiff`）或不在同一目录 | 改名/换目录；运行期无目录缓存，当轮即可见 |
| 彩色图颜色不对（反色） | 链路像素约定被破坏 | `ToHImage` 是唯一转换核心（BGR 入、HALCON R/G/B 通道）；查有没有绕过它的新路径 |

### 4.7 参数与默认值速查

| 项 | 默认 | 备注 |
| --- | --- | --- |
| `Mode` | SingleFile | 枚举落盘为数字，坏档会被踢回默认（见 §5.7） |
| `DisplayViewIndex` | 1 | 写入即夹取 0~9；0=不显示 |
| `FrameTimeoutMs` | 0（用相机配置） | 相机模式；相机的 `FrameTimeoutMs` 默认 3000ms |
| `BufferCapacity` / `HeartbeatTimeoutMs` | 8 / 3000ms | 相机设置里可改 |
| 图像集上限 | 单流程 50 / 总 300 | 「系统参数设置 → 画布」；0/负=不限 |
| 收图服务默认 Token | `visionmaster`（占位） | 只告警不拦启动，投用前必改 |

## 七、关联组件实现要点（面向新手）

> 本章写给第一次接触这个项目的人：不要求你读得懂全部代码，只求**建立一张心智地图**——图从哪来、到哪去、谁负责什么，以及几个"反直觉但很重要、踩了会很痛"的点。已有基础的读者可直接跳过。
> 遇到不认识的词，先翻 [7.10 术语小抄](#710-术语小抄)。

### 7.0 先把整条链路想成一个快递站

```
寄件人（外部程序 / 相机客户端）
   ├─ 走"网络推送"通道 ──► HttpImageServer（19000）──► ImageHub（按流程分格的收件箱）
   └─ 走"相机"通道     ──► NetworkCameraServer（19100）──► 每台相机一条传送带（帧队列）
                                                        │
                       图像采集插件（流水线上的"取件工"）◄─┘
                                                        │
   取到的图 → 交给后续算法步骤 →（可选）投到主界面视图窗口 → 图像集 → 画布格子
```

只要记住"图可能在**两个不同的地方排队**"（ImageHub / 相机帧队列），排查"为什么没有图"时就不会像无头苍蝇。

### 7.1 插件怎么跟宿主"对上暗号"（三条通道）

新手最常见的困惑：插件是个独立 DLL，凭什么能用宿主的能力？答案是三条**用途不同**的通道：

| 通道 | 形态 | 什么时候用 | 例子 |
| --- | --- | --- | --- |
| ① 契约程序集 | 插件与宿主都引用同一份 `Core.Interfaces` / `Core.Controls` | 编译期定"接口" | `ICameraDevice`、`ImageHub`、`InputPort` |
| ② 执行上下文（运行期递送） | 引擎执行插件时把 `IExecutionContext` 递进去 | 运行期拿"能力" | `Logger`、`CancellationToken`、`Cameras`、`GlobalVariables` |
| ③ 配置上下文（配置期快照） | 宿主打开配置窗口时把 `PluginConfigContext` 推给插件 | 配置期拿"环境信息" | 当前流程名、HTTP 地址/令牌、相机候选列表 |

**为什么"静态类"能跨程序集共享**（这段很多人第一遍看不懂，值得多读两遍）：
`ImageHub`、`GlobalEventBus`、`ImagePreviewCaptureHub` 都是**静态类**——"整个进程里只有一份"。
插件是用 `Assembly.LoadFrom` 从 `Modules\` 目录加载的，而 `Modules\` 里放的是 `Plugin.*.dll` 与第三方依赖（如 `hdevenginedotnet.dll`、`Microsoft.CodeAnalysis.*`），**没有** `Core.Interfaces.dll` / `Core.Controls.dll` 这类公共契约程序集。
所以插件引用公共程序集时，只能"命中"宿主已经加载的那一份 → 两边看到的是**同一个** `ImageHub`、**同一个**事件总线，图投进去才能取出来。

> ⚠ **一条不能碰的红线**：如果有人把 `Core.Interfaces.dll`（或 `Core.Controls.dll`）拷进了 `Modules\`，这套"暗号"就会失效——进程里会出现**两份**静态状态，投进去的图取不出来，而且现象诡异（比如预览永远不显示）。改动部署目录前先想清楚这件事。

**新手易踩的坑**：以为"插件拿不到宿主的东西"就去加参数、加引用。正确做法是先在契约里找现成的递送口（`IExecutionContext` / `IPluginConfigContextProvider`）。

### 7.2 ImageHub：按流程分格的收件箱 + 门铃

**它是什么**：一个静态类，内部是"流程名 → 一个队列"的字典。`Push` 投一帧，`TryPop` / `WaitPop` 取一帧。

**为什么要有**：HTTP 收图是"推一张 → 跑一次流程"。这些图是**运行期数据**，绝不能写进步骤配置（写配置会让流程版本号变化、触发重新编译，每帧都编译一次）。

**关键实现点**：
1. **按流程名分槽**：多条流程可能同时被 HTTP 触发；若共用一个队列，A 流程的图会被 B 流程取走——现场表现是"图串了"，且只在并发时偶发，是最难查的一类问题。
2. **每槽最多 8 帧，满了丢最旧**：有的客户端一直推，而流程里偏偏没有取图步骤，队列不设上限就会把内存吃干；丢最旧是因为对"实时检测"来说旧帧已无价值，丢新帧反而让延迟越积越大。
3. **用"门铃"而不是轮询**：`Push` 之后敲一下门铃（`SemaphoreSlim.Release`）唤醒正在等图的取图方；没人等时门铃已经响着，多敲的那下会抛异常——那正是"不需要唤醒"，吞掉即可。
4. **`TryPop` 取的是最新一帧**（把队列排空，只留最后一个）：投递方是"发一张、等结果、再发下一张"的同步节奏，正常队列里最多一帧。
5. **`WaitPop` 只会被两件事唤醒**：新图到达，或取消令牌被置位（用户点了"停止流程"）。它自己**绝不**改变流程状态。

**新手易踩的坑**：把"槽里没图"当成故障。它只是"还没图"——正常情况下就该等；只有"等到被取消"才算结束。

**读代码从哪看起**：`Shard\Core.Interfaces\ImageHub\ImageHub.cs`——类注释把"为什么静态 / 为什么分槽 / 为什么设上限"写得非常全，是学习本仓库注释风格的好样本。

### 7.3 HttpImageServer（19000）：前台接待员

**它是什么**：宿主里的一个 HTTP 服务，对外只有一条路由：`POST /flow/{流程名}`。

**一次请求的生命周期（按顺序）**：
1. **验令牌**（`Authorization: Bearer xxx`）——不对直接 401；
2. **找流程会话**：优先复用界面上已编译的那一份（图纸版本涨过才重新编译），保证"HTTP 看到的"与"界面上看到的"是同一套运行状态；
3. **先判"是不是已经在跑"**：正在跑就回 409，不排队、不覆盖。这一步很关键——引擎抢会话锁失败时只会静默记一条警告，不判 409 就会让调用方拿到"success=true，但 outputs 是上一次的值"的**假成功**；
4. **解码**：图片字节在内存里解成原始像素（灰度 Gray8 / 彩色 Bgr24），**零落盘**——避开临时文件、同名写、磁盘 IO 一堆麻烦（解码核心 `ImageBytesCodec` 被两条收图链路共用）；
5. **投递 + 触发**：把这一帧 `Push` 进 `ImageHub`，然后**单次执行**这条流程（推一张跑一次）；
6. **等结果、组回包**：按 `?outputs=步骤名.端口名` 从编译产物里反查端口值组装 JSON；超时（默认 30 秒）回 504——**不打断流程**（流程在后台继续跑完，上游自己决定要不要重试）；
7. **错误信息在 `message` 字段**（不是 `error`），中文内容在 JSON 里默认会被转义成 `\uXXXX`。

**新手易踩的坑**：① 把 504 当"流程失败了"——它只是"这次没等到"；② 改完插件忘记**重建插件工程**，跑的仍是 `Modules\` 里的旧 DLL（曾导致冒烟从 304/0 掉到 294/9）。

**读代码从哪看起**：`VisionMaster\Services\HttpImageServer.cs`。服务端库为什么选 Watson 7.2（普通用户权限就能监听，不需要管理员/http.sys）见 `2026-09-24-HTTP收图服务端依赖接入.md`。

### 7.4 NetworkCameraServer（19100）：相机的传送带

**它是什么**：另一个 HTTP 服务，但它**不是**"推一张跑一次"，而是替每台相机持续收帧：`POST /camera/{序列号}/frame`（推帧）+ `POST /camera/{序列号}/heartbeat`（心跳）。

**和 19000 的区别（新手最容易混）**：

| | 19000 HttpImageServer | 19100 NetworkCameraServer |
| --- | --- | --- |
| 语义 | 一张图 → 跑一次流程 → 回结果 | 相机持续出图 → 进帧队列 → 流程按自己节奏取 |
| 路由键 | **流程名** | **相机序列号** |
| 队列 | ImageHub（每流程 8 帧，取最新） | 每台相机一条队列（容量可配，丢最旧并计数） |
| 心跳 | 无 | 有（每秒一次，与推图节拍**无关**） |

**关键实现点**：
1. 收到帧 → 内存解码 → 调设备的 `PushFrame`（设备把它塞进自己的帧队列）；
2. 收到心跳 → 调 `NotifyAlive()`（"设备还活着"的证据）。**暂停推图时心跳照发**——否则 3 秒后会被判掉线；
3. 心跳停 3 秒 → 判掉线并清空陈旧帧；心跳恢复 → 自动回到在线。正是靠它，"在线但没推图（用户暂停）"才不会被误报成"掉线（故障）"。

### 7.5 CameraProvider + CameraDeviceBase：相机仓库与"驱动骨架"

**CameraProvider（仓库）**："配置"与"运行态"的唯一对接处：
- **配置**（有哪些相机、序列号、参数）随方案保存（`SolutionModel.CameraConfigs`，纯数据、可存盘）；
- **设备**（句柄、队列、状态）是运行态对象，随进程生死，并且**只在 `CameraProvider` 一处** new / 重建 / 释放（方案变了调 `SyncFromSolution` 对齐）；
- 插件通过 `IExecutionContext.Cameras.TryGetDeviceBySerial(序列号)` 拿设备。

**CameraDeviceBase（骨架）**：每个厂商的驱动只继承它、**只写差异点**（`OpenCore` / `CloseCore` / `ApplySettingsCore`，真机再加"SDK 回调里 `PushFrame`"），队列 / 状态机 / 超时全部由基类提供：

| 基类提供 | 说明 |
| --- | --- |
| 帧队列 | 容量可配（默认 8）；满了丢最旧，`OverflowCount` 计数**必须暴露给界面** |
| 状态机 | `Closed → Connecting → Online → Streaming` 四态（`Online` = 在线但没出图，"没触发 / 暂停"是正常态） |
| 心跳看门狗 | `RequiresHeartbeat=true` 的设备（网络相机）超时判掉线；真机可以关 |
| `WaitNextFrame(超时, 取消)` | **生产取图**：消费一帧，取不到就等到超时或被取消；超时**永远是有限值** |
| `TryGetLatest()` | **预览取图**：只读最新一帧，**不消费**（否则"一开监视窗口就偶发漏检"） |

**两条硬纪律**（写在基类注释里，新人必须知道）：
1. **SDK 收图回调里绝不阻塞**——回调只做"拷一份 + 入队"；一阻塞，SDK 内部队列就会溢出、丢帧甚至掉线；
2. **帧队列必须有上限、丢帧必须计数**——"丢帧 = 漏检工件"；可以丢（否则雪崩），但必须让现场看得见。

**新手易踩的坑**：把 `OverflowCount`（处理不过来丢最旧）与 `DroppedFrameCount`（掉线/停止清队列丢弃）合成一个数——两者原因与处置完全不同。

**读代码从哪看起**：`Shard\Core.Interfaces\Camera\ICameraDevice.cs`（契约与注释）、`VisionMaster\Services\Camera\CameraProvider.cs`。

### 7.6 ImageCollectionService：画布的照片墙

**它是什么**：把"流程运行期间产生的图"收成一份列表，供「视觉图像页」显示（也供报警留存 / 导出）。

**关键实现点**（这块踩过三个大坑，值得慢慢读）：
1. **收到的是"影印件"而不是原图**：`CopyImage()` 出一份独立副本，之后原图怎么变、怎么被释放都与它无关；
2. **拷贝必须在"发布线程"上完成**：插件发布的图**活不过它的下一轮**（基类在下一轮开始时释放上一轮的输出）。若等事件派发到 UI 线程再拷，循环运行下 UI 一落后就拷到死图——帧会**静默消失**（日志里连一句提示都没有）。所以宿主实现了 `IImagePreviewCapture` 钩子：`PublishPreview` 在**发布调用返回之前**就把图拷走；
3. **每一轮的"清空"和"插入"必须同一批做完**：先清后画会让界面看到"旧图 → 空 → 新图"，循环运行时就是**黑屏↔图片频闪**。现在轮首只登记"待清空"，等本轮第一张新图到达时才清 + 插，而且这一批中间**没有让出调度的机会**——界面只看到一次替换；
4. **本轮没有新图就什么都不做**：画布保持上一轮的图（"监视器"语义：有图才有替换）；
5. **集合只在 UI 线程改**：`ObservableCollection` 不是线程安全的；所有写入都封送到 UI 线程（拷贝则留在发布线程做）；
6. **有上限、要淘汰**：单流程 50 张、总 300 张（可配，0 = 不限），超出按最旧优先淘汰并释放副本；提示只发一次，避免日志刷屏；
7. **有诊断**：首帧 + 每 200 帧一条 `[图像集] 已收录 N 帧…`。遇到"图不进画布"，先看这条日志——有=收录成功（问题在显示侧），没有=收录侧（先查插件 DLL 是否重建）。

**新手易踩的坑**：在 UI 线程之外的任何地方读/改这个集合。

### 7.7 ImageGallery / ImageView：格子画布，以及"刷新不能被饿死"

**ImageView（页面）**：负责"摆格子"——第 N 格 ↔ 插件里的"显示窗口号 N"；每格是一张完整画布（大图 + 下方缩略图条），布局（单画面 / 1×2 / 四宫格 / 九宫格…）可切换。
**ImageGallery（控件）**：只管数据——按 `ViewIndexFilter` 过滤出"属于自己这一格"的帧，重建可见列表 `FilteredFrames`。

**关键实现点：为什么刷新要用 `DispatcherPriority.Normal`**：
- WPF 的 UI 线程按**优先级**取活干：高优先级的活没干完，低优先级的永远排不上；
- 触发重算的正是"采集往集合里插帧"，它走 `Normal`；如果重算挂在更低的 `Background`，循环运行时的连续插帧就是一场洪水 → **重算被永久饿死**：帧明明已经在集合里，界面却一直停在"本格暂无图像"；
- 所以重算必须与插帧**同优先级**——按 FIFO 交替执行，最坏只是跟着排队，不会被饿死；
- 另外：多次变更要**合并**（一次插 N 帧只重算一次），避免 O(N²)。

**新手易踩的坑**：看到"界面不刷新"就去改数据源。先问自己："这个刷新动作的优先级 / 调度时机对不对？"

### 7.8 VirtualCameraClient：一台"假相机"

**它是什么**：一个独立的 WPF 小工具（`Tools\VirtualCameraClient`，不进主解决方案）：选一个图片文件夹，按间隔不停把图 POST 给 19100 端口，就像一台真相机在推图；另有一条**独立的心跳循环**（窗口一开就跑，与推图开关解耦）。

**为什么要有**：没有真实相机时也能把"相机模式"整条链路（配对、队列、溢出、掉线、恢复）验证出来；而且它能**故意**制造丢帧、暂停、掉线这些真机不好复现的场景。

**新手易踩的坑**：以为"暂停推图"时心跳也可以停——停 3 秒主程序就判掉线，之后恢复推图会因"相机未打开"全部失败。

### 7.9 小结：出问题先查哪

| 症状 | 先看哪个组件 | 看什么 |
| --- | --- | --- |
| HTTP 推送没人接 | HttpImageServer | 服务是否在听（端口 / Enabled）；回包是 401 还是 404 |
| 相机没有图 | NetworkCameraServer + 设备状态 | 客户端在推吗？心跳在发吗？状态是 `Online`（没触发）还是 `Connecting`（没接入）？ |
| 步骤报"等图超时" | CameraDeviceBase 的计数 | `待消费 / 累计收帧 / 溢出丢帧` 三个数就能分清"掉线 / 没触发 / 处理不过来" |
| 视觉图像页空白 | ImageCollectionService | 日志有没有"已收录 N 帧"：没有=收录侧，有=显示侧 |
| 画面闪黑 / 停在旧图 | ImageCollectionService + ImageGallery | 每轮原子替换与刷新优先级（见 §2.4、§5.9） |
| 改了代码没效果 | 构建产物 | 插件改的是 `Modules\Plugin.ImageAcquisition.dll`——必须**重建插件工程** |

### 7.10 术语小抄

| 词 | 一句话解释 |
| --- | --- |
| 插件 / 宿主 | 插件是独立的算子 DLL（`Modules\Plugin.*.dll`）；宿主是主程序 VisionMaster |
| 契约 | 插件与宿主之间的"公共语言"（`Core.Interfaces` 里的接口与数据类） |
| 端口 | 算子的输入/输出"插口"；输入端口可以固定填值，也可以连到上游变量 |
| 上游 / 下游 | 数据流的方向：生产数据的是上游，消费数据的是下游 |
| 流程会话（Session） | 一条流程的一次"编译产物 + 运行状态"，HTTP 与界面共用同一份 |
| 帧队列 | 相机持续出图时的缓冲队列；满了丢最旧并计数（防雪崩） |
| 心跳 | 客户端每秒发一次的"我还活着"，与推图节拍无关 |
| 序列号 | 相机的"身份证号"（寻址键）；改显示名不影响引用 |
| 取消令牌（CancellationToken） | 一个"叫停信号"；等图这类阻塞操作必须能被它打断 |
| 派发器优先级 | WPF UI 线程按优先级干活；低优先级活在高优先级洪水下会被饿死 |
| 非托管 / 托管 | HALCON 的图（`HImage`）占用非托管内存，必须 `Dispose`；`byte[]` 是托管内存，GC 自动回收 |
| 影印件（副本） | `CopyImage()` 出来的独立图：与原图互不影响，谁持有谁负责释放 |
