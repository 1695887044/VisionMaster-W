# 通讯设置 UI 三缺陷修复（A1 异步连通测试 / A2 删连接二次确认 / A3 孤儿变量口径）

> 来源：对「通讯设置」弹窗的一次工程审查。审查结论为 3 个真缺陷（A1/A2/A3）+ 6 个工程缺口（B1-B6）+ 3 个优化点（C1-C3）。
> 本文只覆盖用户选定先行修复的 **A1 + A2 + A3**，并附上为该修复服务的断言（C6）排障结论。

## 1. 需求与决策

### 1.1 三个缺陷的原始现象

| 编号 | 现象 | 根因 |
| --- | --- | --- |
| **A1** | 点「连通测试」后界面白屏、被系统判定「无响应」 | `AdvancedCommunicationManager.TestConnection` 内部 `GetAwaiter().GetResult()` 在 **UI 线程**上硬等一个 `TimeoutMs`（默认 3000ms）；而「连不上」时必然等满，恰恰是用户最需要按这个按钮的场景 |
| **A2** | 删连接**没有任何确认**，点一下就没了 | `ExecuteDelete` 直接 `RemoveConnection` + `Configs.Remove`，无二次确认，无影响面告知 |
| **A3** | 删连接后，该连接下的网络变量变成「孤儿」—— 界面上还在，但永远采不到值，且**无任何提示** | `RemoveConnection` 只清 Manager 侧注册；变量仍留在方案的全局变量表里，`VariablePersistenceService` 对「连接名不存在」的变量按**离线定义**落盘 |

### 1.2 决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| A1 怎么修 | **`TestConnection` 拆成「同步薄包装 + `TestConnectionAsync`」，UI 改走异步版** | 保留同步签名（`CommunicationCheck` 在 `Task.Run` 内仍在用，且它自带 `PerTestTimeoutMs` 限时），不破坏既有调用点；UI 侧 await 后界面照常可操作 |
| A1 并发保护 | **同一条连接的测试按钮置灰（`_testingConnection`）** | 「连通测试」的实现是「连一次再关掉」，同一条连接并发测两次会互踩 socket |
| A2 确认框内容 | 连接名 + **不可撤销** + **变量数影响面** + **流程运行中额外警告** | 删除是破坏性且不可撤销的操作；运行中删连接会让正在读该变量的算子**立即报错**，必须显式警告 |
| **A3 口径** | **只删连接，不删变量**；变量保留为「离线定义」，但从删除那一刻起**停止采集**，并在确认框与结果提示中明确告知 | 变量被算子/连线/监视项**按名字引用**，删变量会级联到流程语义，通讯模块不该拥有流程语义。用户已确认此口径 |
| 确认框实现 | `EasyDialog.ShowSync("删除连接确认", message)` | 项目既有模态确认入口；注意参数顺序是 **(title, message)** |

### 1.3 关键设计：`async void` 的 `finally` 是硬要求

`ExecuteTestConnection` 改为 `async void`（`DelegateCommand` 的执行体只能是 `void`）。**`finally` 里必须恢复 `_testingConnection = null` 并 `RaiseCanExecuteChanged()`**：

- 漏掉这一步，这条连接的「连通测试」按钮会**永久置灰**（canExecute 只认 `_testingConnection`）；
- canExecute **不会自动重评估**，必须手动 `RaiseCanExecuteChanged()`（项目既有约定：置灰状态写在命令上，不绑界面 `IsEnabled`）。

### 1.4 措辞陷阱：删掉再加同名连接**不会**自动恢复轮询

`RebindAll`（把变量的 `ScanGroup`/连接关系重新灌进 Manager）**只在方案加载时调用**（[ShellViewModel.cs](file:///e:/VM/VisionMaster-W-master/VisionMaster/ViewModels/ShellViewModel.cs) 手动打开方案 / 自动加载方案两处）。

因此「删连接 → 再建一条同名连接」这条路径上，**变量不会被重新注册**，采集不会自动恢复。确认框文案据此规避，**不承诺「自动恢复」**。

## 4. 附：C6-4 排障结论（HSL `ConnectServer()` 的真实语义）

**首版 C6-4 失败**：靶子用 `192.0.2.1:502`（TEST-NET-1 保留段，理论上不可达），断言「探测结果应为 false」，实测却返回 **True**。

### 4.1 三层证据链

给 `CommChecks` 加临时诊断（读 `PipeTcpNet.socket` 私有字段、直连 HSL `ConnectServer()`、对照真实读取），得到：

```
[诊断] 探测耗时=16ms 返回=True 目标=192.0.2.1:502 TimeoutMs=300
[诊断] pipe=HslCommunication.Core.Pipe.PipeTcpNet IsConnectError=True pipe.ConnectTimeOut=300 pipe.Ip=192.0.2.1:502
[诊断] pipe.socket=<null>
[诊断] HSL直连 ConnectServer: IsSuccess=True 耗时=0ms Msg=成功
[诊断] ConnectServer 之后 pipe.socket=非null
[诊断] 真实读取 ReadCoil: IsSuccess=False 耗时=628ms Msg=Socket Exception -> 远程关闭了连接
```

### 4.2 源码定位

顺 HSL 源码链（本项目 `HslCommunication` 是**本地源码工程**引用，可直接读实现）：

| 层 | 位置 | 关键行为 |
| --- | --- | --- |
| `DeviceTcpNet.ConnectServer()` | `DLL\HslCommunication\Core\Device\DeviceTcpNet.cs` | `CommunicationPipe.OpenCommunication()` 成功即返回其 `Content`（无协议层握手） |
| `PipeTcpNet.OpenCommunication()` | `DLL\HslCommunication\Core\Pipe\PipeTcpNet.cs` | `if (IsConnectError())` → `CreateSocketAndConnect(...)`（**唯一真正建 TCP 的动作**）；否则（socket 已活）直接 `Success(value: false)` |
| `CommunicationPipe.IsConnectError()` | `DLL\HslCommunication\Core\Pipe\CommunicationPipe.cs` | 基类 = `connectErrorCount > 0`；`PipeTcpNet` 覆写为 `socket == null`（故**首次**必走真实建连，**第二次**直接秒回成功） |

**结论**：`ConnectServer()` 只证明「TCP 连接建立」，**不证明对面是活的 Modbus 设备**。在装了本地代理 / TUN 的机器上，到 `192.0.2.1:502` 的 TCP 会被代理**秒接**（0ms）→ `IsSuccess=true`；只有真实读取才暴露（628ms 后 `远程关闭了连接`）。

### 4.3 处置

| 项 | 处置 |
| --- | --- |
| **断言靶子** | 换成 **`127.0.0.1:1`**（本机回环、必然无人监听的端口）：由内核直接 `ECONNREFUSED`，**不依赖网络环境、不受代理影响**，是唯一确定性的「连不上」靶子。原 `192.0.2.1` **不是**环境无关的 |
| **C6-3 断言强度** | 原 `callMs < 150` 只量到 async 的同步前导段（实测 1ms），证明不了「不阻塞」。改为**先用 `worker.Invoke(_ => { Thread.Sleep(600); return true; })` 占住 Worker 线程，再断言 `callMs < 150 && !probe.IsCompleted`** —— 若 `TestConnectionAsync` 退化成同步硬等，必然陪等 600ms 以上 |
| 临时诊断代码 | 全部删除，只保留终版断言 |

### 4.4 顺带发现（本次未修，供后续决策）

1. **`ModbusTcpConnection` 未映射 `config.TimeoutMs` → `_device.ConnectTimeOut`**：ctor 只赋 `IpAddress`/`Port`，所以连接页里配的「超时」对 HSL 建连**无效果**。
2. **「连通测试」当前语义只是「TCP 可达」**：`TestConnectionAsync` 返回的是 `ConnectServer()` 的结果，不验证设备活性。若要真验设备活性，应由**一次轻量读**（读一个寄存器/线圈）来判定。

## 5. 已知边界

1. **A1/A2/A3 的界面行为无法被断言覆盖**：这是 WPF VM + XAML 交互，`CommChecks` / `ScadaChecks` 都是无 UI 的控制台宿主，跑不到。**必须实机点验**两条：
   - 删连接 → 应弹确认框；文案含「N 个变量…变为离线定义并停止采集」；流程运行中额外出现警告。
   - 连通测试 → 点不可达 IP，界面不应白屏/无响应，按钮应置灰直至返回。
2. **同步版 `TestConnection` 仍会阻塞**：它的契约就是「硬等」，**只能由非 UI 线程调用**。UI 一律走 `TestConnectionAsync`（已在 XML 注释中写死该约定）。
3. **A3 的「停止采集」是立即生效、不可逆的**：变量保留在方案里但采不到值，用户若想恢复必须重建同名连接**并重新注册**（`RebindAll` 只在方案加载时跑，见 1.4）。
4. **删连接不级联删变量，意味着方案里会积累「离线定义」**：这是有意的（保护流程引用），但没有任何「离线变量一览」入口 —— 属于 B 类工程缺口，未在本轮范围内。
5. **C6 是唯一会真发起 TCP 连接的断言段**：靶子为本机未监听端口（内核秒拒），故整段耗时可忽略；放在断言链**最后**执行。
