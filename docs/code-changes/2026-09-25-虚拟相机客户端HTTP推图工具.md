# 虚拟相机客户端小工具 Tools\VirtualCameraClient

主软件侧的"网络相机（虚拟）"需要一台**假装是相机**的客户端来推图。本工具就是这个"假相机"：
用户选一个图片文件夹，它按节拍把图片通过 HTTP 推给主软件，并持续发心跳让主软件知道"我还在"。

本工具是**完全独立的 WPF 工程**：不进 `VisionMaster.sln`、不引用主解决方案任何工程、不引任何 NuGet 包，
只依赖 BCL + WPF，通过 HTTP 与主软件通信。

---

## 一、需求与决策

| 分支 | 结论 | 理由 |
|---|---|---|
| 工程归属 | 新建 `Tools\VirtualCameraClient\`，**不进** `VisionMaster.sln` | 独立小工具，单独 `dotnet build` 即可；进 sln 会拖慢主仓整体构建 |
| 依赖 | 仅 BCL + WPF（`System.Text.Json` / `HttpClient` / `PeriodicTimer`） | 硬约束：零 NuGet、零主仓引用，避免版本耦合 |
| 框架 | `net9.0-windows` + `UseWPF` + `ImplicitUsings=enable` + `Nullable=disable` | 按任务约定 |
| MVVM | 手写 `ObservableObject` / `RelayCommand`，不引 CommunityToolkit/Prism | 零 NuGet 约束下，一个 `SetProperty` 足矣 |
| 推送技术 | 后台 `Task` + `PeriodicTimer` | 绝不用 `Thread.Sleep` 卡 UI；`PeriodicTimer.WaitForNextTickAsync` 支持取消，关窗即退 |
| `HttpClient` | 全局**单实例**复用，超时 5s | 每次 new 会耗尽本地端口(TIME_WAIT)；它本就是设计给长期复用的类型 |
| 心跳 | **独立循环**，窗口一开就转，与推图开关解耦 | 主软件 `HeartbeatTimeoutMs=3000`，靠"多久没心跳"判掉线 |
| 图像预览 | `BitmapImage` + `OnLoad` + `Freeze` | 立即释放文件句柄，冻结后可跨线程安全交给 UI |
| 线程模型 | 后台循环改界面属性统一 `Dispatcher.BeginInvoke`；推图线程读"快照数组"而非 `ObservableCollection` | 集合有线程亲和性，跨线程枚举会偶发崩溃 |

**心跳为什么不能跟着推图开关停**：主软件判"在不在线"只看心跳，谁都不看推图。
一旦暂停推图时把心跳也停了，3 秒后主软件就把相机判为掉线；用户再点"开始推图"，
服务端已是"相机未打开"状态，推帧会全失败。所以：**暂停推图，心跳照发**。

## 三、协议契约（客户端实现口径）

基础地址 `http://{host}:{port}`；默认 host=`127.0.0.1`、port=`19100`；头 `Authorization: Bearer {token}`，默认 token=`visionmaster`。

```
推一帧  POST /camera/{serial}/frame
        X-Image-Name: {文件名}
        Content-Type: application/octet-stream，body = 图片原始字节
        → 200 { success, serial, frameId, received, pending, overflow, bytes }
        → 4xx/5xx { success:false, message }

心跳    POST /camera/{serial}/heartbeat（无 body，每 1 秒一次）
        → { success, serial, state, received, pending, overflow, dropped }
```

容错：非 JSON 响应（如 `404 not found`）不崩溃，`Summary` 里带 HTTP 码；单帧业务失败不抛异常、不中断推图循环；
只有"用户取消"才抛 `OperationCanceledException` 让循环安静退出。

## 四、验证结果

```
dotnet build "Tools\VirtualCameraClient\VirtualCameraClient.csproj" -nologo

  VirtualCameraClient -> E:\VM\VisionMaster-W-master\Tools\VirtualCameraClient\bin\Debug\net9.0-windows\VirtualCameraClient.dll

已成功生成。
    0 个警告
    0 个错误
```

首轮编译暴露一个真实坑：`UseWPF` 的隐式 using 集合**不含 `System.IO`**，也不含 `System.Windows.Shapes.Path`
（后者若被隐式引入会与 `System.IO.Path` 二义）。修法：显式 `using System.IO;`，并对 `Path` 使用
`using Path = System.IO.Path;` 别名双保险。

## 五、已知边界

1. **服务端尚未实现该协议**。当前主软件只有 `POST /flow/{流程名}`（见 `HttpImageServer.cs`），
   `/camera/{serial}/frame` 与 `/camera/{serial}/heartbeat` 属"客户端先行"，需服务端 `NetworkCameraServer` 落地后
   才能真正跑通端到端。本工具按任务给定协议实现，未自行改动协议。
2. **默认端口差异**：主软件现有 `HttpImageServerSettings` 的默认是 `0.0.0.0:19000`，本工具按任务约定默认 `127.0.0.1:19100`。
   联调时以界面实际填写的端口为准。
3. **未做端到端冒烟**：仅验证编译（0 错 0 警），未连服务端实跑推图/心跳。
4. **统计仅当前会话内存计数**，关窗即清零；未做持久化（工具定位为调试用假相机）。
5. `IntervalMs` 绑定到 `TextBox`，非法输入（清空/字母）会被 WPF 默认转换器拦下、保留旧值，不弹校验提示。
