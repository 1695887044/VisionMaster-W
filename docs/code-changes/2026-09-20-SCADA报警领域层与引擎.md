## 一、需求与决策

### 1. 需求

组态软件真正的价值出口不是"把画面画出来"，而是**出问题的时候能喊人**。S10 之前，SCADA 这一摊只做到"变量值能显示、按钮能写值"——值越限了、通信断了，画面上什么都不会发生。这一阶段补上报警。

三条报警源（路线图 S11 原文）：

1. **变量越限**：高限 / 高高限 / 低限 / 低低限（四限）；
2. **布尔跳变**：置位报警（`BoolOn`）/ 复位报警（`BoolOff`）；
3. **通信断线**：变量一段时间没收到新值。

报警必须能回答现场那四个问题：**什么时候报的、报的是哪一条、当时值是多少、谁确认的**。

### 2. 决策清单 —— 分层与线程（A-1 ~ A-3、A-16、A-17）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| A-1 | 态机归属层 | **独立类 `ScadaAlarmEngine`**（`Scada\Models\`），不塞进 `ScadaRuntime` | `ScadaRuntime` 管的是"画面怎么动"（订阅/释放/切页），报警管的是"值意味着什么"。两件事的变更频率与测试方式完全不同：引擎全部逻辑可以用假时钟在控制台里一口气推过去，塞进 `ScadaRuntime` 就得连 WPF 一起拉起来 |
| A-2 | 线程模型 | 引擎**自带上锁**（`_gate`）；**事件一律在锁外抛** | 见下 §4.1 |
| A-3 | 定义 vs 记录 | `ScadaAlarmDefinition`（配置，落 `.vms`，走 `ScadaModelBase` 吃撤销栈）+ `ScadaAlarmRecord`（运行态，不落 `.vms`，走 `BindableBase`） | 见下 §4.2 |
| A-16 | 引擎职责边界 | 不落盘、不做动作、不读文档以外的数据、解析不到变量**静默跳过** | 引擎是纯判定器。落盘归宿主、动作归 S8 的动作表。解析不到就报"配置错误"报警，会在用户还没接完线的组态阶段刷屏 |
| A-17 | 节拍归属 | 引擎**不起定时器**；宿主用 `DispatcherTimer` 驱动 `Tick()`，建议 100~500ms | 起定时器 = 引擎拥有线程 = 引擎得管生命周期。`Tick()` 由外面推，控制台里就能把 10 分钟压进 1 毫秒跑完 |

### 3. 决策清单 —— 判定语义（A-5 ~ A-12）

| # | 决策点 | 选择 | 依据 |

| A-5 | 寻址口径 | 与 `ScadaBinding` **逐字一致**：`Id` 优先、名字兜底 | 同一个变量在绑定里怎么找，在报警里就该怎么找。两套口径迟早出现"画面上显示 85、报警说没越限" |

| A-7 | "范围内报警" | **没有**这个种类 | 要"值落在区间内就报"就配低限 + 高限两条，语义更清楚，也免了"区间边界算不算"的歧义 |

| A-12 | 初判 | `Attach` 后**对每条定义立即判一次** | 挂上画面时值可能**已经**越限了。等下一次值变化才报，意味着"一直越限、值没再变"的工况永远不报——这恰是最该报的那种 |

### 6. 本轮修掉的两处旧债（S11-a4 / S11-a5）

**s11-a4 —— 新建报警没有身份。** `ScadaAlarmDefinition.AlarmId` 原本是自动属性，`AddAlarm` → `new ScadaAlarmDefinition()` 之后 `AlarmId == Guid.Empty`。而引擎的 `Acknowledge` 明确拒 `Guid.Empty`（它是"空身份"的哨兵值）。症状是**运行中点确认毫无反应，也不报错**——因为 `Acknowledge(Guid.Empty)` 直接返回 0。修复：字段初始化 `private Guid _alarmId = Guid.NewGuid();`。

**s11-a5 —— 变量改名级联漏到报警。** `ScadaDocument.RefreshVariableReferences` 原本只遍历 `_pages`，报警定义里的 `VariableName` 不在其中。在 `ScadaWriteGuard.Strict` 下，这个支路既会抛 `InvalidOperationException`（没套 `Suspend`），又会留下"画面绑定改了、报警没改"的半成品。修复：报警遍历整段套 `using (ScadaWriteGuard.Suspend())`——因为这是**数据自愈**（把过期的引用修回来），不是用户发起的一次画面编辑，不该产撤销记录、也不该被严格守卫拦。

## 二、为什么这么设计（逐条展开）

### 1. 为什么事件必须在锁外抛（A-2）

订阅者会干什么？落盘、刷 UI、写数据库。这些动作可能：

- 慢（磁盘 IO）；
- 回调回来再读引擎（`ActiveAlarms`）——而 `ActiveAlarms` 自己也要拿 `_gate`。

如果事件在锁内抛，第二种情况就是**自锁**（同一个线程重复进 `lock` 在 C# 里是允许的，但一旦订阅者换线程去读，就是死锁）。所以 `Evaluate` / `Raise` / `Recover` / `AcknowledgeCore` 全都接一个 `List<Action> pending`，把"要发的通知"攒起来，出锁之后 `Flush(pending)` 统一执行。

这是"先收集、后广播"的经典写法，代价是每个内部方法多一个参数；收益是**引擎永远不会在持锁状态下调用外部代码**——一条能让将来所有人放心的不变量。

### 2. 为什么定义和记录要分成两个类（A-3）

| | `ScadaAlarmDefinition` | `ScadaAlarmRecord` |
|---|---|---|
| 生命周期 | 跟方案走，用户增删改 | 跟一次"激活 → 清除"走 |
| 落 `.vms` | 是 | 否 |
| 基类 | `ScadaModelBase`（吃撤销栈 + 写守卫） | `BindableBase`（纯通知） |
| 内容 | 阈值、回差、延时、文本、变量寻址 | 激活时刻、触发值、确认时刻、恢复时刻、清除时刻 |

合在一个类里的后果：`ActivatedAtUtc` 这种字段会跟着方案落盘，下次打开方案时读到一个**上次运行的**激活时间——历史被伪造了。分开之后从类型上就不可能。

注意 `ScadaAlarmRecord` 的构造是**快照式**的：`Name` / `Message` / `Severity` / `Kind` / `VariableName` / `ConditionText` 全部在构造时从定义拷贝一份。这样事后改配置，不会把三个月前那条历史记录的文案也改掉。

### 3. 为什么消抖要两道闸门（A-8）

`Deadband`（回差）与 `DelaySeconds`（延时）解决的是两个不同方向的抖动：

- **回差管退出**：值在阈值附近来回蹭（80.1 / 79.9 / 80.2），没有回差就会"报 → 恢复 → 报 → 恢复"刷屏。回差要求退出时必须**多让开一个带宽**（`IsStillTriggered`：`High` 用 `> Threshold - band`）。
- **延时管进入**：值瞬间冲过阈值又立刻回落（尖峰干扰），没有延时就会产生一条实际不存在的报警。延时要求条件**连续成立**够久才报。

两者的方向性很关键：**进入按裸阈值判，退出才多让开一个回差**。反过来（进入就要超过 `阈值+回差`）会让本该报的值差一点点报不出来。

延时计时用的是 `ConditionSinceUtc`：条件第一次成立时记下时刻，`Tick` 时算 `now - ConditionSinceUtc >= DelaySeconds`。中途条件断掉就**清空**这个时刻——所以"断一次要重新计时"，而不是累计。

### 4. 为什么断线不吃延时（A-9）

`Stale` 的触发条件是 `(now - LastValueAtUtc) >= StaleSeconds`。这个条件**本身就是"已经等够了"的结论**——用户配 `StaleSeconds = 10` 说的就是"10 秒没值就算断"。再叠一层 `DelaySeconds = 30` 等于把超时悄悄变成 40 秒，用户在界面上看到的是 10，实际生效的是 40。这种"配置写了不生效"是最难查的一类现场问题。

所以 `Evaluate` 里对 `Stale` 明确跳过延时叠层。

### 5. 四态机为什么这么分岔（A-10、A-11）

```
                    ┌──────────── 条件成立 ────────────┐
                    ▼                                  │
   ┌────────┐   条件成立   ┌────────┐  确认   ┌──────────────┐
   │ Normal │ ───────────▶ │ Active │ ──────▶ │ Acknowledged │
   └────────┘              └────────┘         └──────────────┘
       ▲                      │                      │
       │                   条件恢复                条件恢复
       │                      ▼                      ▼
       │               ┌────────────┐           （直接了结）
       └─────确认──────│ Recovered  │
                      └────────────┘
                           │ 条件又成立
                           └──▶ 退回 Active（清 RecoveredAtUtc）
```

三个分岔的理由：

- **未确认恢复 → `Recovered` 而不是 `Normal`**：报警自己消失了不等于操作员知道过。如果直接回 `Normal`，一条"半夜闪了一下"的报警会静默消失，而它恰恰是需要第二天复盘的那条。
- **已确认后恢复 → 直接 `Normal`**：操作员已经看过并处理完了，再拦他一次确认是重复劳动。
- **`Recovered` 时条件又成立 → 退回 `Active`**：这是同一个物理事件的延续（值又冲上去了），不是新事件。**不清 `RecoveredAtUtc` 会让时长算错**（恢复时刻停在中间，时长显示成一个毫无意义的值）；清掉之后时长从最初激活时刻连续累计——"这条报警一共闹了多久"才读得对。

### 6. 配置热更新为什么要"自动跟随"（A-18）

组态软件的一个基本操作习惯：**运行中改一个阈值，希望能立刻看到效果**。如果引擎只在 `Attach` 时读一次配置，用户改完阈值必须停画面再启动——现场调试时这个来回极其烦人。

做法是订阅 + 标脏：

- `Attach` 时挂 `Alarms.CollectionChanged`（增删定义）；
- 对**每一条**定义挂 `PropertyChanged`（改阈值、改回差、停用）；
- 任何一处变化 → `_dirty = true`；
- 下一次 `Tick` 检查 `_dirty`，是则**在锁外**调 `Reload()`。

两个细节：

- **标脏而不是立刻 `Reload`**：`PropertyChanged` 可能在任意线程、任意时机来（比如批量导入方案时连改 200 条），立刻重挂就是 200 次重建。攒到下一拍只做一次。
- **`Reload` 必须在锁外**：`Reload` 要退订旧定义、订阅新定义，而订阅/退订本身会触发对方的 `CollectionChanged`/`PropertyChanged`——在锁内做容易和"自动跟随"的回调打结。

### 7. 为什么时钟要注入（A-19）

引擎的核心逻辑全部是"时间到了没有"：延时、超时、时长。用 `DateTime.UtcNow` 直读，意味着测一条 `DelaySeconds = 30` 的报警要**真的等 30 秒**；测 `StaleSeconds = 600` 要等 10 分钟。整个断言段会被时间拖垮，然后所有人开始"少测几条"。

注入 `Func<DateTime> clock` 之后，断言里写：

```csharp
DateTime now = new DateTime(2026, 9, 20, 8, 0, 0, DateTimeKind.Utc);
Func<DateTime> clock = () => now;
// ... now = now.AddSeconds(11); engine.Tick();
```

——十分钟在控制台里推完，而且**确定性的**（不依赖机器快慢，不会偶发红）。生产代码不传（`null` → `DateTime.UtcNow`），零成本。

`Attach()` / `Reload()` / `Tick()` / `Acknowledge()` / `AcknowledgeAll()` / `OnValueChanged()` 全部走 `_clock()`，一个都不能漏——漏一处就会出现"注入的时钟推不动某条支路"。

### 8. 一个容易忽略的初始化（`Slot.LastValueAtUtc`）

`Attach` 建槽时把 `LastValueAtUtc` 初始化成 `nowUtc`，含义是"**刚收到过值**"。

如果不初始化（默认 `DateTime.MinValue`），`Attach` 的第一次 `Tick` 会算出 `(now - MinValue).TotalSeconds` 是个天文数字 → **刚挂上画面就报一片断线**，然后用户收到值之后又全部恢复。这个"开机虚报"会严重损害报警系统的可信度（现场口头语："这软件的报警不准，一开就报"）。

### 2. 设计上的刻意取舍

- **`Stale` 依赖 `Tick` 而非事件**：断线判定的本质是"时间在走、值没来"，只能靠 `Tick` 推。宿主若不推 `Tick`，断线报警不会响（其余种类靠事件仍能工作）。这是 A-17"节拍归宿主"的直接代价，S11-b 必须落实。
- **`_slots` 线性扫描**（A-13）：报警条数上千时 `Tick` 会变慢。当前量级（几十条）无影响，S13 性能基线时若报警数上到千级需重新评估。
- **报警与画面的引用关系是单向的**：报警只认变量，不认画面。同一变量在多张画面上显示时，一条报警会同时影响所有画面——这是对的（报警是设备属性不是画面属性），但 S11-c 的报警条图元要明确"这张画面上显示哪些报警"的过滤口径。
- **引擎不认识"报警组 / 报警抑制"**：现场常见的"检修期间屏蔽某类报警"还没有。路线图未列，暂不做。

### 3. 与 S10 遗留项的关系

S10 的两项真机待核（锁角标与诊断角标是否重叠、单击整组/框选单个的不对称是否困惑）仍未做真机复核——这两项与 S11 无关，但按路线图验收口径 3 仍是 S10 的挂账。

## 六、真机复核清单（S11-c 交付后一并执行；S11-b 已交付）

1. 组态一个越限报警 → 启动运行 → 手动改值越限 → 报警条出现、状态栏计数变红。
2. 点"确认" → 记录转"已确认"、红点数字减一。
3. 值恢复 → 记录消失（`Acknowledged` 路径）。
4. 未确认时值恢复 → 停在"已恢复未确认"等一次确认。
5. 运行中改阈值 → 无需重启即生效。
6. 断线报警：拔掉通信 → `StaleSeconds` 后报警，且**不是** `StaleSeconds + DelaySeconds` 才报。
7. 报警历史面板按时间倒序查询、CSV 导出内容与面板一致。
8. 关闭再打开方案 → 报警配置在；重启运行 → 历史记录仍可查（落盘通路）。
