## 二、显示上限（本次新增的核心机制）

**已定**：不做"适配全图"。长链流程（227 步约 25 000 px 高）适配到全图 = 每个节点 0.6 px，等于一片空白。

**待定：上限怎么实现。** 三种做法，性能与交互差别很大：

### 方案 A：视口窗口化（滚动）

- 画布保持可缩放，**只绘制视口内的节点**（现有视口裁剪已在做），另加单帧绘制上限 N。
- 上下拖动/滚轮 = 滚动看后续节点，和现在 Nodify 的操作习惯一致。
- 画面永远只显示 N 个节点，**文字始终可读**（不再有 0.25 缩放问题）。
- **代价**：VM 层仍为全量节点建 `CanvasNodeViewModel`，省不掉 `装填` 那 412~631 ms。
- 工作量：**2 天**（含滚动条/滚动位置保持）。

### 方案 B：真分页（PLC 风格）

- 流程按 N 步切页，画布只显示当前页；页码 + 上一页/下一页。
- **只有这个方案能继续降 VM 成本**：只为当前页建节点 VM。
- **代价**：跨页拖动改序要特殊处理（拖到页边界 = 触发翻页）；"看整体"要靠小地图/大纲；
  需要改 `FlowCanvasViewModel` 的 `Nodes` 语义（从"全量集合"变成"窗口视图"），
  连带影响流程树选中、属性面板、撤销栈。**风险最高**。
- 工作量：**4~6 天**（含 VM 窗口化与回归）。

### 方案 C：超限折叠（分段折叠条）

- 一页最多 N 个节点，超出的连续步骤收成一条"…还有 137 步"的折叠条，点开展开下一段。
- 视觉上仍是"一条完整流程"，不需要页码 UI。
- 折叠条是**新的图元类型**（要进基线、要能被框选/拖动/展开）。
- 不降低 VM 成本（同方案 A）。
- 工作量：**3 天**。

> **我的建议：先做 A。** 它解决"看得清"和"一屏节点数可控"，工作量最小、风险最低；
> 若验收后你仍觉得 0.9 s 不够快，再单独立项做 B 的 VM 窗口化（那是另一笔账，和渲染无关）。
> C 只在"你希望画面像一条连续流程而不是滚动窗口"时才值得。

**待定：一页节点数 N**。建议 **60**（约 4 屏，滚动 1~2 下能看完一屏）；可选 40 / 60 / 100。

- 运行中（`IsRunning`）要按现有规则上锁；
- 编辑失败必须写状态栏/回执，不许静默空跑（R172）。
