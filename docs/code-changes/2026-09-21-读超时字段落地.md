# 新增「读超时(ms)」字段并真正下发到 HSL 设备（config.ReadTimeoutMs → device.ReceiveTimeOut）

> 来源：上一篇《连接超时真正下发到 HSL 设备》的**已知边界 1 / 2 / 3** ——
> 「串口 `TimeoutMs` 无人消费」「S7 的 COTP 握手读不受本值约束」「读/写超时整体未映射」三件事，根因是同一个：**项目里根本没有「读超时」这个配置概念**。
> 用户确认后执行：**新增独立字段 `ReadTimeoutMs`（默认 5000）**，TCP 与串口统一下发到 HSL `ReceiveTimeOut`。

## 1. 需求与决策

### 1.1 问题：一条超时字段，两种完全不同的语义被混在一起

上一篇修完「连接超时」后，通讯链路上的超时只剩一处没管：**每一次读写帧等对端回包**的时长。此前它是 HSL 自己的默认值，用户无从配置：

| 量 | HSL 属性 | HSL 默认值 | 约束什么 | 改造前能否配置 |
| --- | --- | --- | --- | --- |
| 连接超时 | `DeviceTcpNet.ConnectTimeOut` → `PipeTcpNet.connectTimeOut` | **10000ms** | 只约束 socket 建连 | ✅ 已由上一篇修好 |
| **读超时** | `BinaryCommunication.ReceiveTimeOut` → `CommunicationPipe.receiveTimeOut` | **5000ms** | 每一帧读写等待对端回包 | ❌ **完全没入口** |

由此衍生出三个具体症状：

| # | 症状 | 说明 |
| --- | --- | --- |
| 1 | **串口的 `TimeoutMs` 是死配置** | `ModbusRtu.Open()` 打开端口是本地动作，没有「建连超时」可言。界面给串口显示了一个超时输入框，用户填了却对任何行为都没有影响。串口真正需要的是读超时 |
| 2 | **S7 建连封不住** | `SiemensS7Net.InitializationOnConnect()` 在建连时会做一次 COTP 协议握手**读**（`ReadFromCoreServer`），它吃的是 `ReceiveTimeOut`。所以 S7 实际建连上限 ≈ `ConnectTimeOut` + `ReceiveTimeOut`，只修前一个等于只封了一半 |
| 3 | **掉线设备暴露太慢** | 设备在运行中掉线时，一帧读写要等满 5000ms 才报失败。对 100ms 的快组而言，这是 50 个节拍的浪费，且用户无法调小 |

### 1.2 决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 字段放哪 | **`ConnectionConfigBase` 新增 `ReadTimeoutMs`** | 读超时对每种连接都成立（TCP 与串口共用 `BinaryCommunication.ReceiveTimeOut` 这一个入口），放基类与 `TimeoutMs` 并列最自然 |
| 默认值 | **5000ms** | **刻意与 HSL 自身默认值同值** → 「老方案不填这个字段」= 「行为与改造前一字不差」，零兼容风险（见 1.3） |
| 范围校验 | `[RangeValidation(100, 60000)]` + `Validate` 里 `<= 0` 拦截 | 与 `TimeoutMs` 保持完全一致的双保险（属性面板声明式 + 代码路径显式） |
| 界面名 | 「**读超时(ms)**」，`高级参数` 组，`Order = 13` | 紧接在 `超时时间(10)` / `重试次数(11)` / `重试间隔(12)` 之后。**不需要改任何 XAML** —— `SuperDisplay` 属性驱动属性面板自动呈现 |
| 是否复用 `TimeoutMs` 一个值通吃 | **不复用，新增独立字段** | 「建连有耐心」与「读帧要快失败」是两个相反的诉求：跨网段建连可能想等 10 秒，但读一帧超过 1 秒就该判掉线。一值通吃会把这两件事绑死 |
| 映射到哪个 HSL 属性 | **`_device.ReceiveTimeOut`** | 这是 `BinaryCommunication` 上的 public 属性，TCP（`ModbusTcpNet` / `SiemensS7Net`）与串口（`ModbusRtu`）**共用同一入口**，一处映射三处生效 |
| 串口要不要一起改 | **要** | 顺带解掉「串口 `TimeoutMs` 是死配置」：串口唯一能真正用上的超时就是读超时。串口原来的 `TimeoutMs` 保留在基类不动（见已知边界 1） |
| 是否加断言 | **加 C8** | 同 C7 手法：纯对象状态、不真建连、离线可跑，防止被重构悄悄带回去 |

### 1.3 兼容性与行为变化

**兼容性：无风险。** 新字段默认值 5000ms 与 HSL 自身默认值**完全相同**，因此：

- 老方案文件里没有 `ReadTimeoutMs` 字段 → 反序列化后走属性初始化器默认值 5000 → 下发到设备的值与改造前 HSL 的默认值一致；
- 反过来说，C8-1 那条断言（默认值路径）**只能证明「默认行为没被改坏」**，真正证明「配置真的下发了」的是 C8-2 / C8-3 / C8-4 三条非默认值用例。这一点在断言注释里已写明，避免后来人误读断言强度。

**行为变化：仅当用户主动改这个值时才发生。** 用户把它调小（如 800ms）后，掉线设备会更快报失败——这正是这个字段存在的意义。

**注意**：`ReceiveTimeOut` 同时被 HSL 用于「等回包」和「判断消息是否收完」（见 `PipeSerialPort.ReceiveMessage` / `PipeUdpNet` 里的计时判断）。所以调得过小（如 100ms）在**慢速串口**上可能把「正常但慢的回帧」判成超时。现场若用低波特率（2400/4800）串口，建议不要低于 1000ms。

**为什么 6 个配置类都要补 `Clone()`**：`Clone()` 是**逐字段手抄**的（不是反射拷贝），任何新增基类字段都必须在**全部 6 个**具体配置类里补一行，漏一个就会出现「复制连接后读超时被重置成默认值」的隐蔽缺陷。这是本项目配置类的一个已知脆弱点，本次按现有风格逐处补齐（见已知边界 3）。

反射探针（重构后）：

```csharp
/// <summary>取连接实现里私有的 HSL 设备实例（_device）</summary>
private static object GetDevice(ICommunicationConnection connection)
    => connection.GetType()
        .GetField("_device", BindingFlags.Instance | BindingFlags.NonPublic)!
        .GetValue(connection)!;

/// <summary>读设备上的一个 int 属性（C7 用 ConnectTimeOut、C8 用 ReceiveTimeOut）</summary>
private static int DeviceIntProperty(ICommunicationConnection connection, string propertyName)
{
    var device = GetDevice(connection);
    return (int)device.GetType().GetProperty(propertyName)!.GetValue(device)!;
}

private static int DeviceConnectTimeOut(ICommunicationConnection connection)
    => DeviceIntProperty(connection, "ConnectTimeOut");

private static int DeviceReceiveTimeOut(ICommunicationConnection connection)
    => DeviceIntProperty(connection, "ReceiveTimeOut");
```

**未改动**：`AdvancedCommunicationManager`（它只消费 `TimeoutMs` 作为等待预算，与读超时无关）、`ConnectionWorker`、`ICommunicationConnection` 接口（读超时是**构造期**一次性下发的设备属性，不需要接口方法）、任何 XAML（属性面板由 `SuperDisplay` 驱动自动呈现）。

## 4. 已知边界

> **后续进展（同日）**：边界 1 已收口，见 [2026-09-21-串口隐藏无效连接超时.md](./2026-09-21-串口隐藏无效连接超时.md) —— 给 `SuperDisplayAttribute` 加了 `Visible` 开关（默认 `true`），`TimeoutMs` 改 `virtual` 并由 `SerialConfig` `override` 重贴 `[SuperDisplay(Visible = false)]`，串口弹窗不再显示该框（模型字段仍保留，老方案兼容）。CommChecks 由 72 增至 77。

1. ~~**串口的 `TimeoutMs` 仍然留在界面上、仍然不被消费**：本次按用户口径「新增独立字段」执行，**没有**把 `TimeoutMs` 从串口的属性面板隐藏，也没有把串口的 `TimeoutMs` 改成映射读超时。因此串口连接设置里现在会同时看到「超时时间(ms)」（无效）和「读超时(ms)」（有效）两个框。**这是本次刻意保留的现状**，如需收口（例如给 `SerialConfig` 加 `[SuperDisplay]` 覆盖以隐藏基类字段）需另行确认。~~
   **已解决（同日）**：串口的「超时时间(ms)」框已从属性面板隐藏；串口的 `TimeoutMs` 仍不被消费（这是设计事实，不是缺陷），模型字段保留以保证老方案兼容。
2. **写超时（`SendTimeOut`）未映射**：本次只映射了读超时。HSL 的发送超时对 Modbus/S7 这类请求-响应协议影响很小（发送阻塞通常由 socket 缓冲区决定），暂不引入第三个字段。
3. **`Clone()` 是逐字段手抄，属结构性脆弱点**：本次 6 处都补齐了，但下次再加基类字段仍会重复这个风险。若后续还要继续加字段，值得考虑把 `Clone()` 改成「基类字段统一在基类拷贝 + 子类只拷自有字段」的形式（例如基类提供 `protected void CopyBaseTo(ConnectionConfigBase target)`）。**本次不做**，避免超出授权范围。
4. **断言只证明「值到了设备对象上」**：不证明「超时真的按这个值生效」——那需要真设备（黑洞地址 + 计时）才测得出，属实机项。
5. **调得过小的副作用**：见 1.3 末段。低波特率串口上把读超时压到 100~200ms 可能把正常慢回帧判成超时。`RangeValidation` 的下限是 100ms（与 `TimeoutMs` 对齐），**没有**按串口波特率做动态下限保护。
6. **`ReceiveTimeOut` 也参与「消息收完没」的判断**：HSL 侧它不只用于「等第一帧」，还用于「帧未收全时的累计计时」（见 `PipeSerialPort.ReceiveMessage` / `PipeMqttClient`）。调小会影响「分片到达」的容忍度，这层耦合不在本项目控制范围内。
