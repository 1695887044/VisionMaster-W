## 一、语义定案（三位的触发语义）

| 位 | 触发条件 | 执行方式 | 不触发的边界 |
| --- | --- | --- | --- |
| **Timer** | `now - 上次触发 ≥ TimerIntervalMs`（下限 100ms） | 单次执行（非调试） | 未启用 / 未勾定时 / 间隔 ≤0（未配置）/ 步骤已加密 |
| **Variable** | `TriggerVariable` 指定的变量**由假变真**（上升沿） | 单次执行（非调试） | 非上升沿（真→真、真→假都不触发）；变量名不匹配 |
| **Subroutine** | 被别的流程的「调用流程」步骤调用 | 同调用方等待（父流程阻塞等它跑完） | 未勾子程序 / 禁用 / 加密 / 目标正在运行 |

三处共同点（一条纪律）：**自动触发不抢占**——目标正在运行就跳过（定时/变量）或直接失败（子程序调用），
不排队、不补跑。排队会把"流程互等"变成挂死现场，补跑会让"一小时错过 200 拍"在一瞬间连跑 200 次。

## 二、契约：`IFlowInvoker`（插件怎么够到"调用流程"的能力）

沿用仓库既有的能力递送范式（与 `IGlobalVariableWriter` / `ICameraProvider` / `IMotionProvider` 一致）：

- `IFlowInvoker` / `FlowInvokeResult`（成败 + 中文原因 + 耗时）/ `NullFlowInvoker`（调用即失败并说明原因）
  定义在 `Shard\Core.Interfaces`；
- 挂在 `IExecutionContext.FlowInvoker` 上，**默认 NullFlowInvoker**（容器注册的简化上下文、单元测试夹具走默认路径，
  插件只判 `Success`，不必判空）；
- 真实现 `Engine\FlowInvoker.cs` 由 `FlowEngineModule` 在装配时**属性注入**进引擎
  （`FlowEngineService.FlowInvoker`）——调用器自己要用引擎跑子流程，两者互为引用、构造期解不开环；
- 引擎在构造 `ExecutionContext` 时把它递进上下文（两处：连续运行 / 单次运行）。

**门禁全在宿主侧一处判定**（插件不做二次判定，避免"两处各判一半"）：存在 / 启用 / 未加密 /
**勾了「子程序」** → 缺一不可；目标在跑直接失败。自身递归与成环由"正在运行"这一条天然拦住
（父流程持有自己的会话锁）。

**超时不打断目标**（与 HTTP 收图的超时口径逐字一致）：取消归引擎自己的 CTS 管，
这里抢它的令牌会污染会话状态；只把"没等到"如实报给父流程。等待期间**响应父流程的急停令牌**（轮询式等待）。

## 三、定时调度（`FlowTimerScheduler`）

> ⏫ **节拍源已升级**：本批的 100ms 托管计时器已换成"高精度节拍源"（默认 kernel32 高精度等待计时器，
> 备选 winmm 多媒体时钟，兜底托管计时器；拍 5ms、定时间隔下限 100ms → 20ms）。
> 见 `docs/code-changes/2026-10-05-定时器高精度节拍源（高精度等待计时器与多媒体时钟）.md`。
> 下面这段描述的是本批当时的实现，保留作背景。

- **单计时器 + 每拍扫一遍**（拍长 100ms），不是"每条流程一个计时器"：
  退出链一次 Dispose 全停，不会漏掉匿名计时器把进程钉住；100ms 与 10 分钟的间隔用同一套机制表达；
- **间隔下限 100ms**：低于它就不是"定时"而是"死循环"；`0` 的语义是"没配间隔"，**不触发**（不是"每 100ms"）；
- 每拍重入保护（上一拍可能正卡在编译）；异常就地隔离并记 Warn，不逃逸出计时器线程；
- 触发时刻**先记再跑**：一轮要几百毫秒到几秒，不先记会在下一拍被当成"从没跑过"重复触发；
- `TickOnce(utcNow)` 是公开的——检查工程用手动时钟驱动做确定性断言（真实现走 `DateTime.UtcNow`）。

## 四、变量触发（`FlowVariableTriggerService`）

- 订阅面：工作区全局变量集合 `CollectionChanged` + 每个变量的 `ValueChanged`；
  集合变化（方案切换是 Reset/Replace，不带明细）**统一全量重挂**——变量量级小，
  而"漏挂一个变量"的代价是整条触发链路静默失效；
- **只在上升沿触发一次**：任何变化都触发的话，一个每秒刷新的计数变量会把流程刷爆（现场最典型踩法）；
- "真值"判定：bool 取自身 / 数值非 0 / 字符串非空白 / 其它非空对象算真（HImage 这类"有值即发生了一件事"）；
- `Evaluate(variable)` 公开，检查工程直接喂变量驱动（真实现由事件调进来）。

## 五、共用执行段（`FlowAutoRunner`）

定时与变量触发共用同一段"该跑一次 → 真的跑一次"：目标在跑 → 跳过；没会话或图纸改过 → 编译并注册；
单次执行（非调试：自动触发不允许被遗留断点卡住产线）；任务异常消化并留带触发来源的 Warn。
口径只写一份，避免"定时跑的流程不带调试豁免"这类隐蔽差异。

## 六、「调用流程」插件（`Plugin.RunFlow`）

- **无自定义视图**：参数面全由端口表达（`FlowName` / `TimeoutMs` / `Invoked` / `ElapsedMs` / `Message`），
  宿主自动包一层参数面板（`AutoPortConfigView`）——所以本工程不需要 WPF、也不需要 `Core.Controls`；
- 不写 `[StepConfig]`（配置走端口），因此不触及源生成器约定（R16–R18）；
- 「等待」是默认且唯一模式：引擎按节点顺序执行，父流程等子流程时本来就没法往下走；
  不做"不等待"分支，避免"子流程还在写全局变量、父流程已经往下跑"的竞态；
- 产物按 `Plugins\Directory.Build.targets` 约定投递到仓库根 `Modules\Plugin.RunFlow.dll`（红线①）。

## 九、未决问题

1. **变量触发的"通知面"有一处缺口**（审查 P2-7 更正）：`LocalVariableModel.Value` 变化发 `ValueChanged`；
   `NetworkVariableModel` 在**轮询镜像更新**（`UpdateMirrorValue`）与**显式写成功**两条路上也发，
   因此网络点位做触发源是可用的——**只有"直接给 `Value` setter 赋值"这一条路不发事件**
   （该 setter 的职责是"镜像 + 下发设备"，不是"报告变化"）。
   副作用：变量触发的回调可能落在**通信轮询线程**上，服务内部已按"加锁 + 集合快照 + 异常隔离"处理（同批修订）；
   现场若用网络点位触发，建议先用监视栏确认值确实在变（值不变时 `SetProperty` 会短路，不会触发，这是刻意语义）；
2. **定时/变量的实时性是 100ms 拍粒度**：对产线节拍够用；若将来要 <100ms 的触发精度，得改成专用计时器；
3. 「调用流程」的目标流程**靠手填/端口传名字**，还没有"从方案流程列表里选"的候选下拉；
   传参/回收目前只能经全局变量（子流程与父流程之间没有直接端口映射）；
4. **GUI 实机冒烟未做**：流程管理勾选、定时/变量触发的真机观察、插件拖入流程后的参数面板待验收
   （面板「执行」按钮的调用器注入已补齐，见第八节 P2-3）。
