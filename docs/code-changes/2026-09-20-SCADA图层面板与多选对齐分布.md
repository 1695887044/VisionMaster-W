## 一、需求与决策

### 1. 需求

两条口子来自用户原话：

> 图元要有图层的概念
> 图层的功能应该是选中控件后点击右键功能栏显示图层功能,不需要放到属性栏

前一轮（2026-09-19）已经落地了"图元 → 图层归属"（右键菜单里的「图层」子菜单）与「叠放次序」，但**图层自己没有界面**——新建/重命名/删除/显隐/锁定全都只能在代码里调。本轮把这一半补齐。

同时按"动作进菜单"那条口径（见上一轮的 §1.4），对齐/分布/批量删除这类**动词**必须进右键菜单，而不是属性栏。

### 2. 两处入口的分工（刻意不重叠）

| 入口 | 回答的问题 | 作用域 |
|---|---|---|
| 画布右键菜单 →「图层」子菜单 | **选中的这个图元**归在哪一层 | 主选中那一个 |
| 右侧「图层」面板 | **这张画面一共有哪几层**、各自开没开、锁没锁、谁在谁前面 | 整张画面 |

同一件事不留两个入口。属性栏里的「图层」组在上一轮已整体撤掉，本轮**没有把它加回来**——面板是独立停靠面板，不是属性栏里的一行。

### 3. 决策清单 —— S10-a 图层面板

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| A-1 | 行的形态 | **不可变快照 `ScadaLayerItem`**，不是直接把 `ScadaLayer` 绑到行上 | 行上要显示的东西比图层自己多：`ElementCount` / `CanRemove` / `CanMoveUp` / `CanMoveDown` / `ContainsSelection` 全是**画面级**算出来的量，图层对象上根本没有。硬塞给它就是把编辑器知识写进领域模型。而且快照能被断言直接读（`Items[0].CanRemove` 一句布尔判断），不必靠离屏渲染去数像素 |
| A-2 | 刷新信号 | **只订阅 `ScadaPage.Version` 一条** | `Version` 的递增规则已经把"图层增删改名 / 显隐 / 锁定"与"图元增删 / 改归属"全覆盖了（`OnLayersChanged` / `OnLayerPropertyChanged` / `OnElementsChanged` / `OnElementPropertyChanged`）。比分别盯两个集合 + 每个对象少一大截漏挂漏摘的机会 |
| A-3 | 值不变挡刷 | `ItemsEqual` **逐字段值比较**，不相等才 raise `Items` | 拖动图元会**逐帧**抬 `Version`。不挡一下就是每秒几十次重建列表 → `ItemsControl` 反复重建行容器 → 拖动肉眼可见地发涩。**注意**：挡的只有 `Items` 的通知，命令可用性仍然每次都重算（`RaiseAllCanExecute`），否则会出现"行没重建、按钮却停在旧的灰态" |
| A-4 | 显隐/锁定的写入口 | `using (layer.BeginEdit("隐藏图层 [名]")) { layer.IsVisible = next; }` | `ScadaLayer.IsVisible` / `IsLocked` **没有 `TrySet*`，是设计如此**：那两个属性就是图层对象上的唯一写入口，外面套一层作用域即可。一次点按 = **一条**撤销位，`Label` 直接就是撤销按钮的提示文案 |
| A-5 | 端点判灰 | `CanMoveUp = i > 0` / `CanMoveDown = i < Count - 1`，与 `ScadaPage.TryMoveLayer` 的越界钳制同源 | 两处各判一次就会出现"按钮亮着、按下去没反应"。另外行上按钮额外绑 `IsEnabled="{Binding CanMoveUp}"`——**双保险**：`DelegateCommand` 不跟随 `CommandManager`，只靠 `CanExecute` 会在重建空档里显示旧态 |
| A-6 | 删除的门槛 | `_page?.CanRemoveLayer(item?.Layer) == true`（空层 + 画面还剩别的层） | 判据只有领域层那一份。所以"灰着的垃圾桶"本身就在告诉用户"先把这层的图元挪走或删掉" |
| A-7 | 空态两句话 | 无画面 → `"打开方案并选中画面后，这里会显示该画面的图层。"`；有画面无图层 → `"当前画面还没有图层。点下方「新建图层」即可添加。"` | 两种空的原因不同，给同一句话会让用户以为"面板坏了"。`HasPage` 为真而 `Items.Count == 0` 时仍要能点「新建图层」（`AddLayerCommand` 只看有没有画面） |
| A-8 | 未分层提醒 | `UnassignedCount` 数 `page.ResolveLayer(element) == null` 者，**两条来源**：`LayerId == Guid.Empty`、以及**指向已删图层的幽灵归属** | 幽灵图元在画布上照常显示、照常能编辑，只是不属于任何一层。不说一声会显得面板"漏了东西" |
| A-9 | 防误判文案 | 面板底部固定一句「图层顺序不改变图元叠放」，`ToolTip` 指向画布右键菜单的「叠放次序」 | **图层次序不参与叠放计算**，谁盖住谁只由 `ScadaElement.ZIndex` 决定。不写出来的话，用户点几次上移发现画面前后关系没变，会判定成"这个按钮坏了"——解释成本最低、收益最高的一句 |
| A-10 | 图标字体写法 | 视图里写 **pack 绝对串**，不用 `{StaticResource Icon}` | 与上一轮踩的同一个坑：`App.xaml` 那份要靠 `Application` 资源查找，`ScadaChecks` 的离屏断言宿主**没有 `Application`**，取不到就静默回落 Arial（图标变豆腐块） |
| A-11 | 挂摘 | 视图 code-behind 只做"**可逆挂摘**"：`Loaded → Activate()` / `Unloaded → Deactivate()` / `DataContextChanged` 时若已入树补挂 | 面板的 `Version` 订阅必须跟着视图入树/离树，否则离了树的面板还被旧画面钉着（等于订阅泄漏）。`Activate` / `Deactivate` 都**幂等**，重复调不重复订阅 |
| A-12 | 实例注册 | `RegisterForNavigation<ScadaLayerView, ScadaLayerViewModel>()`（**非单例**），与属性面板共用同一个 `ScadaEditorViewModel` 单例 | 面板跟着视图入树/离树挂摘，一份 VM 实例只服务一个视图实例最省心。当前画面从 `editor.SelectedPage` 取 |

### 4. 决策清单 —— S10-b 多选 / 对齐分布 / 批量删除

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| B-1 | 对齐与分布是否拆两个枚举 | **不拆**，同一个 `ScadaAlign`（6 对齐 + 2 分布） | 对用户来说这是同一件事——"把选中的这一堆摆整齐"，同一个子菜单里的八项、撤销栈里同一句"对齐 [3 个图元]：水平分布"。拆开就得在每处调用点再分一次流，而分出来的两条路除了算式不同，前置校验、作用域、写入口完全一样 |
| B-2 | 对齐基准 | **整组包围盒**，不是"贴到某一个图元的边" | 后者用户得先猜"谁是基准"；包围盒是选完之后看一眼就知道的东西。也是商业组态软件的通行口径 |
| B-3 | 分布口径 | **等间隙**（相邻图元空隙一样大），不是等中心距 | 图元宽度不一时，等中心距看上去仍是乱的（宽的挤在一起、窄的之间空一大片）。等间隙是肉眼唯一能验证"排匀了"的口径，Illustrator / PowerPoint 都是这么做的 |
| B-4 | 分布的两端 | **两端原地不动**，只重排中间几个 | 排匀不该把整组挪走 |
| B-5 | 门槛数字放哪 | `ScadaAlignExtensions.MinimumCount()`（对齐 2、分布 3），菜单判灰与领域层前置校验**读同一个数** | 各写一遍就会出现"菜单亮着、点了却返回 false"。分布至少要三个：两个图元"分布"的结果就是原地不动，判成可用只会让用户点了没反应 |
| B-6 | 锁定图元怎么办 | **既不参与、也不作为基准**，直接跳过；一个都排不了才返回 false | 拿一个动不了的图元当基准，结果就是"其余都挪了、就它没动"，看着像对齐失败。与拖动/删除口径一致（`IsElementEditable` 是唯一的编辑资格判定） |
| B-7 | 撤销粒度 | 一次排列 = **一条** `BeginEdit($"对齐 [{n} 个图元]：{DisplayName}")` | 批量挪 10 个图元若各记一条，用户要按 10 次 Ctrl+Z 才能回到对齐前（S9 的验收硬指标） |
| B-8 | 批量删除的失败语义 | 锁定项**跳过**而不是整批失败；全锁死才返回 false | 多选里混进一个锁住的底图是常态（设备底图往往整层锁住）。为此让整批删除失败，Delete 键看起来就是"时灵时不灵" |
| B-9 | 选中集合的不变式 | **主选中 == 集合首项**；写入口只有 `ScadaCanvas.SetSelection` 一处 | 宿主那边（`ScadaEditorViewModel`）与画布那边各维持一遍，迟早劈叉。集合的 DP 声明 `BindsTwoWayByDefault`，双向绑定直接可用 |
| B-10 | 空选中的归一 | 落在集合之外（含 `null`）→ 走 `ApplySelection`；落在集合之内 → 只 `SetMainSelection` + 刷新命令 | `SelectedElements` 设成"集合没变、但主选中要换"时也要写主选中；而 `SetMainSelection` 直写字段、**刻意不走 `SelectedElement` setter**（否则死循环） |
| B-11 | 框选的命中口径 | 橡皮筋矩形与图元**包围盒相交**即入选；**看不见的不入选** | 看不见的紧接着就会被 `PruneSelection` 剔掉，先选上等于白闪一下 |
| B-12 | 框选的结果与现状相同 | **一个字都不写**（`SameSelection` 值比较挡一下） | `SetSelection` 会连着改两个依赖属性，白写一次就白刷一轮选中视觉 |
| B-13 | 多选拖动 | 整组一起挪（`SelectedElements.Count > 1` 时按主选中算位移量，其余跟同一个 delta） | 与方向键微调同口径：选中三个标签按一下方向键，用户要的是"这一组整体微调"，只挪主选中那一个会让人以为键卡了 |
| B-14 | 批量改图层归属 | **不支持整批**，只有主选中 | 菜单上的打勾状态只能表达"一个归属"。多选若跨了层，会渲染出"一项都没打勾"的空档，用户看不出这批图元算哪一层——那比少一个批量功能更难解释 |
| B-15 | 八个动作的图标 | 水平三兄弟 `F036/F037/F038`，垂直三兄弟 `F341/F034/F33D`（同族转 90°），分布另用 `F337/F338` | 水平组和垂直组必须同一套画法转 90°，否则"顶对齐"和"左对齐"看起来像两个软件里的东西。分布不是"贴到某条边"，图标跟着不一样，用户才不会把它当成第七种对齐 |
| B-16 | 分组图标缺省 | `IconOf` 的 `default` 分支退化成分组图标 `F039` | 将来枚举加了新动作而忘了配图标，是"图标不好看"，不是"菜单空白" |
| B-17 | 删除项在菜单里的位置 | **放最后** | 它是四栏里唯一"不可见地改变画面内容"的一项（另外三栏都只是换个摆法），排在末尾才不会被误点 |

### 5. 口径沉淀

- **快照挡刷 ≠ 命令不刷**：值没变只挡列表重建，可用性每次都要重算。这两件事分开，才能既"拖动不卡"又"按钮不僵"。
- **判据只留一份，同源读**：`MinimumCount` / `CanRemoveLayer` / `IsElementEditable` / `IndexInZOrder` 的稳定排序口径，全都是"菜单判灰"与"领域层前置校验"共读同一处。任何"两处各判一次"都是"按钮亮着但按下去没反应"的温床。
- **"解释成本最低、收益最高的一句文案"值得写**：「图层顺序不改变图元叠放」这句就是为了防"按钮坏了"的误判。
- **构造 ≠ 编辑**：`AddLayer` 造对象走 `ScadaChangeScope.Detached`（见 S9 记录 §4），否则"新建图层"会先冒出几条 `Name: "" → "图层_1"` 的垃圾记录。

### 1. 构建

## 四、已知边界

1. **图层面板尚未真机验证**：`ScadaChecks` 的离屏宿主**没有 `Application`**、`IsLoaded` 恒 false，量不到真实渲染（行高、图标字形、悬停色）。本轮的断言全部打在**视图模型层的快照**上（`Items[0].VisibilityIcon == EyeGlyph` 等），视图层的视觉正确性只能靠静态审图 + 人眼在真机上复核。**这是本轮唯一没有自动化兜底的一环。**
2. **本轮刻意未给图层面板产离屏证据图**（与属性面板 / 右键菜单不同）。原因不是偷懒，是这条路走不通：上一轮 §3.3 的修法是 `new FontFamily(new Uri("pack://application:,,,/UI;component/Asserts/FontFamilys/"), "./....otf#...")` 这种"**包基址 + 相对路径**"的两参构造，而 XAML 里的 `FontFamily` **只能写成一个字符串**，字符串就是那条绝对 URI——表达不出"基址单独给"这层信息。所以 `ScadaLayerView.xaml` 里的 `IconFont` 只能写 pack 绝对串，在无 `Application` 的宿主里必然回落 Arial。
   更麻烦的是**外部注入也救不了**：那份 `IconFont` 定义在视图自己的 `Grid.Resources` 里，比 `UserControl.Resources` 更靠内；而行模板里 `{StaticResource IconFont}` 是**静态**引用，在 `Grid.Resources` 解析时就已经求值进 Style 的 setter，事后改写资源字典不会回溯生效。
   硬凑一张"图标全是豆腐块"的图给人眼复核，只会误导判断——不如不产。**结论：图层面板的视觉只能真机复核。**
3. **图层顺序不参与叠放计算**：谁盖住谁只由 `ScadaElement.ZIndex` 决定。已在面板底部写明文案（A-9），但用户仍可能直觉以为"归到上层图层就会盖住下层"。这条口径需要在真机上再看用户反应。
4. **无拖拽调序**：图层排序只有行内的上移/下移两个按钮，没有"列表里拖一下"。领域层 `TryMoveLayer(layer, targetIndex, out error)` 已支持任意目标位次，将来加拖拽不用改领域层。
5. **删除仅限空层**：`CanRemoveLayer` 要求"空层 + 画面还剩别的层"。要删非空层得先把里面的图元挪走或删掉——这是刻意的（防误删），但"灰着的垃圾桶"对新手仍是一次解释成本。
6. **批量改图层归属不支持**：多选时「图层」子菜单只有主选中那一个会变（B-14）。跨层多选时菜单会渲染成"一项都没打勾"。
7. **对齐/分布只作用于可编辑图元**：锁定项跳过。全部锁死时返回 false 且**不产撤销记录**（`TryAlignElements` 在进 `BeginEdit` 之前就返回了）。
8. **分布允许负间隙**：图元本身重叠时"排匀"的结果就是均匀地重叠，不做额外处理——强行推开等于替用户决定"不该重叠"，那不是排列该管的事。
9. **`ScadaAlign` 不落盘**：它是一次操作、不是一个状态，`.vms` 里没有它。所以枚举数值不承担兼容负担。
10. **SCADA 新文件仍未纳入版本控制**：`Scada/Models/ScadaAlign.cs`、`Scada/Models/ScadaEditHistory.cs`、`Scada/Models/ScadaChangeScope.cs`、`Scada/Models/ScadaWriteGuard.cs`、`Scada/Models/ScadaChange.cs`、`Scada/Models/ScadaModelBase.cs`、`Scada/Models/ScadaZMove.cs`、`VisionMaster/ViewModels/ScadaLayerViewModel.cs`、`VisionMaster/ViewModels/ScadaMenuItem.cs`、`VisionMaster/Views/ScadaLayerView.xaml(.cs)` 等仍是 `??`（未跟踪）状态。**提交需用户明确授权。**
11. **`UI/Controls/obj` 陈旧产物会引发 `RG1000`**：见 §3.3，属环境性，删 `obj` 即恢复。若再遇到同类"重复键"报错，先怀疑 `wpftmp` 临时工程，不要先怀疑代码。
