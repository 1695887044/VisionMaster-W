# 多流程并发：帧归属与清空范围（批 1 实施，2026-10-27）

## 一、当前状态

批 1（正确性）已落地并通过断言：**多流程并排循环时，A 的一轮不再清掉 B 的窗口**。

- 根因两条（见同日诊断记录 `2026-10-27-多流程并发显示互相清屏与界面卡顿（诊断）.md`）：
  ① 帧归属靠单例全局 `_currentFlowName`（"最后开轮的那条流程"）；
  ② 自动清空口径 `ClearAll` 是**画布级**（任一流程开一轮 → 下一条任意流程的帧清掉所有窗口）。
- 修法：流程身份随**发布事件**走（`PreviewScope` 注入）；自动清空只允许**窗口级 / 流程级**，
  且每条流程每轮各清一次；`ClearAll` 存量值在加载时迁移为 `ClearView`。
- 验证：`FlowCanvasChecks` 全套 **3969 通过 / 0 失败**；`UIThemeSmokeTest --gallery` 全 PASS；
  新断言做了两组变异反证（见第四节）。

### 新断言（[MC] 组）

- MC1 两条流程各占一个窗口：帧归属各是各的。
- MC2 **A 开一轮不得清掉 B 在另一个窗口的图**（现场回归）。
- MC3 A 的帧仍归 A，且同一窗口只留本轮一张（按"窗口1 恰好一张"判，避免旧帧在时假绿）。
- MC4 窗口级口径只清目标窗口。
- MC5 窗口级口径确实清掉目标窗口里别的流程的旧帧。
- MC6 流程级口径每轮只清一次：同一轮两个窗口的新帧都在。
- MC7 无流程作用域 → 落伪流程桶（绝不猜最后开轮的流程）。

## 六、踩过的坑

- **另一会话正在同仓库施工**（R9）：`ScadaLoginViewModel.cs`、`AppSettingsService.cs`、
  `SolutionSessionCoordinator.cs` 在我编辑期间被连续改写；我第一次构建的 `CS0103` 是**两边同时构建**
  撞出来的假象（符号其实已在 `Core.Interfaces.dll` 里）。判据：看 mtime + 二进制里搜符号，
  不要只看一次编译错误就改别人的文件。
- **宿主在跑 = 无法构建**：`VisionMaster.exe` 锁住 `VisionMaster\bin\*.dll` 与 `Modules\Plugin*.dll`，
  `-p:UseAppHost=false` 只能省掉 exe 拷贝，省不掉 DLL 拷贝。绕法：`-p:OutDir` + `-p:ModulesDir`
  + `-p:HostBinDir` 全指到 `artifacts\build\<批次>\`。
- **隔离目录跑全套会假红**：`ParallelExecutionChecks` 按 `AppContext.BaseDirectory` 上溯仓库根，
  隔离目录少一层 → 去 `D:\C#\Modules\` 找 `Plugin.RunFlow.dll` 直接崩；
  `ProcessViewTemplateChecks` 也找不到源文件。要跑全套必须把隔离产物**回填**到
  `FlowCanvasChecks\bin\Debug\net9.0-windows` 再运行（宿主进程锁的是 `VisionMaster\bin`，不是这里）。
- **断言写"取第一张看名字"会假绿**：归属错时旧帧仍在同窗口，`FirstOrDefault` 取到的是旧帧。
  改成"该窗口恰好一张 + 名字对"才咬得住（MC3 就是这么加强的）。
- **`ClearAll` 的语义迁移必须落盘**：只在运行时按窗口级处理还不够——磁盘上的老值会让设置界面
  继续显示旧口径。迁移放进 `NormalizeLoadedCollections` 并返回 `true`，借启动自检的回写自愈。
