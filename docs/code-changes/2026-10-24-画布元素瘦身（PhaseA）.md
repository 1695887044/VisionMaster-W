> 前置：`docs\performance\2026-10-23-流程切换卡顿基线.md`（含 §9 P1 复测，结论是 P1 减分配不解决问题）

## 一、根因（元素数量，不是分配）

按 Nodify 7.3 默认主题展开后逐个计数（详见 `docs\performance\2026-10-23-画布虚拟化（P3）前置调研.md`）：

| 实例 | 可视树元素 | 附带的菜单对象（从没打开过） |
| --- | ---: | ---: |
| 步骤节点 | **45** | **14** |
| 容器框 | 42 | 13 |
| 泳道 | 19 | 0 |
| 一根连线 | 2 | 5 |
| 小地图项（打开小地图时） | 7 | 0 |

3542 步 + 7083 根线 → **约 20 万个可视元素、8.5 万个菜单对象**。
单次重建实测（用户机器配置 `ShowDataLinks=true`）：**40.9 秒**；数据线关时 18 秒。
其中 VM 侧只有 2.1 秒（4%）——所以 P1 那类"减分配"打不到点上。

**PLC 梯形图能扛上万行，是因为它不建"每行 N 个 UI 元素"**，只把可视区画在一个绘制表面上。
本批先做"把元素数量砍下来 + 大流程默认折叠"，把打开从"假死"降到"能忍"；
要"全展开也不卡"必须换渲染结构（Phase C）。

## 二、改了什么

### A1 右键菜单改为全画布共享单实例（`FlowCanvasView.xaml`）

- 原来三处 `ContextMenu` 都写在 `DataTemplate` 里 = **每个节点/每根线各造一份**：
  节点 14 个对象 × 3542 + 容器 13 × 990 + 连线 5 × 7083 ≈ **8.5 万个未打开对象**。
- 改成 `UserControl.Resources` 里的三个共享实例：`StepNodeContextMenu` / `ContainerNodeContextMenu` / `ModuleLinkContextMenu`，
  由 `Grid.ContextMenu="{StaticResource ...}"` 挂上去。
- **绑定一行没改**：WPF 弹出时把 `ContextMenu.DataContext` 设成 `PlacementTarget.DataContext`（节点/连线 VM），
  `{Binding XxxCommand}` 与内联时等价；同一份菜单复用到不同类型节点也安全（可见性按 DataContext 求值）。
- 资源必须定义在 `DataTemplate` **之前**（R173：模板延迟物化）。
- 连线菜单的 `ContextMenuOpening`（顺序链整体拦掉）保持不变。

### A2 连接点模板瘦身（`FlowConnectorStyle`）

- Nodify 默认 `NodeInput/NodeOutput` 模板每个 7 个元素（Grid + 带 `OpacityMask` 的隐藏 Border +
  StackPanel + Control + Ellipse + ContentPresenter…），每节点 2 个 = 14 个元素，常态 `Opacity=0`。
- 换成自定义 `Template` = **单个 `Ellipse`**（`Fill="Transparent"` 保证可命中，描边走 `TemplateBinding`）。
- 每节点从 45 → 约 33 个元素，3542 步方案下省约 4 万个。

### A3 大流程首次挂接自动折叠（`FlowCanvasViewModel`）

- 新增 `BigFlowAutoCollapseThreshold = 600`：步骤数超过就**把该流程所有容器记为会话折叠**，
  首帧只画顶层。状态栏提示"大流程（N 步）：已自动折叠 M 个容器…"。
- **不写 `.vms`**：折叠记在 `_sessionCollapsed`（`HashSet<Guid>`），换方案时清空。
- 用户手动展开某容器 → 从集合移除（否则下一次渲染又被折回去，点开没反应）。
  用户点「展开全部 / 折叠全部」→ 整个会话折叠集合清空（显式意图优先）。
- `TryGetLayout` 合并口径：`collapsed = 落盘值 || 会话折叠`。

### A4 流程树虚拟化 —— **未做**（实测收益太小，风险太大）

量过：3542 步时把流程栏也显示出来，只比画布单独多 **约 540 ms**（`open` 9567 vs `canvas` 9025），
而 `tree` 侧的可视元素只有约 2 万个（每行约 5.6 个）。
要让 TreeView 真虚拟化必须替换它的默认模板（默认 `ScrollViewer.CanContentScroll="False"`，
只加 attached property 无效），并且会打断 `TreeViewBehavior.TrySelectDescendant`
（依赖 `ContainerFromIndex`，虚拟化后屏幕外返回 null）——那是"失败自动跳转"的定位路径。
**结论：不值。** 记在这里避免下一轮重复评估。

### A5 超大流程数据线降级（`BuildLinks`）

- `ShowDataLinks=true` 且当帧聚合根数 > **1500** 时，只保留非法线；工具条出现「已精简连线」提示。
- 不改任何数据；根数回落到阈值内自动恢复。353 步流程约 350 根（正常），3542 步约 3500 根（卡死）。
- 新增只读属性 `DataLinksReduced` 供视图显示。

### A6 方案反序列化移出 UI 线程（`Core\SolutionService.cs`）

- 原实现 `await File.ReadAllTextAsync(...)` 没有 `ConfigureAwait(false)`，续体回到 UI 线程做
  `JsonConvert.DeserializeObject`（3.9 MB / 3542 步 → 1~2 秒白卡）。
- 改为 `await Task.Run(() => JsonConvert.DeserializeObject<...>)`：
  只把**纯 CPU 解析**挪走，后续迁移钩子仍在原上下文（它们经 DI 拿插件表，不保证线程安全）。

### 顺带修掉的构建阻塞

`UI\Controls\Themes\Dialog\Dialog.Input.xaml:265` 的 XML 注释里写了 `--r-sm`，
XML 不允许注释内出现 `--` → **整个解决方案编译不过**（MC3000）。改为 `r-sm`。
该文件 1 分钟前被另一个进程改过（mtime 1:23:41），本处只做最小语法修复，未动内容意图。

## 三、实测（`--switch-perf`，Debug，屏幕外真窗口，数据线开、树可见）

| 场景 | 改前 | 改后 |
| --- | ---: | ---: |
| **3542 步单流程**（`压测-3000节点-单流程.vms`，`open` 相位） | **40.9 s**（`datalinks`）/ 18.0 s（数据线关） | **9.5 s** |
| 同上，`canvas` 相位（流程栏收起） | 18.0 s | **9.0 s** |
| 同上，`datalinks` 相位 | 40.9 s | **9.2 s**（降级生效，数据线不再计入） |
| **353 步 × 13 流程**（`压测-3000节点.vms`，`open` 相位） | 1.38 s | **1.27 s** |

关键变化：
- **数据线开/关的差距消失了**（41 s → 9 s 与 9 s）：A5 降级把 3500 根线挡在 VM 构造之前。
- VM 侧从 2099 ms 降到 461 ms（A1/A2/A3 共同作用）。
- 剩下的约 9 秒全在 WPF：885 个顶层节点 × 约 33 个元素 ≈ 3 万个元素 + 布局 + GC。
  **每元素约 0.1 ms，这是 WPF"每项一个元素"结构的成本下限。**

## 四、为什么还没到「几千点不卡」

因为**结构**没变：仍然是"一个节点 = 一个 `ItemContainer` + 一套模板"。
A1~A3 把常数从 45 降到约 33、把节点数从 4532 降到 885，所以是 4.3 倍；
但要把 9 秒压到 0.3 秒，需要的是 **30 倍**，只能靠"不再为每个节点建元素"。

两条可选路线见 `docs\performance\2026-10-23-画布虚拟化（P3）前置调研.md` §6：
- **C1 复制并改写 Nodify 编辑器模板**（1~2 周，伪虚拟化：视口外不实现，视口内仍全实现）
- **C2 自写画布渲染层**（2~4 周，彻底 O(可见)，但要重写全部交互，19 条断言改写）

**建议**：先做 1 天的决策实验——临时把 `Nodes` 裁到"视口 + 缓冲"量一次；
如果 `heavy_layout` 掉到 1 秒内，投 C1；否则直接上 C2。

## 七、真机证据与新增埋点（2026-10-24 追加）

### 7.1 用户真机日志（`VisionMaster\bin\Debug\net9.0-windows\Logs\2026-10-24.log`）

```
08:16:22.452 [INFO] [系统变量] 通讯设备拓扑变化：当前 0 条
          …… 73 秒无任何日志 ……
08:17:35.119 [INFO] [退出链] 开始执行（触发：应用退出）
08:17:35.548 [WARN] [退出链] 方案有未保存改动，已转存草稿：…\压测-3000节点-20261024-081735.vms
```

结论：
- 打开的就是 `压测-3000节点.vms`（13 条流程，最大 353 步）。
- 方案**加载本身不慢**：探针测同一文件 `load_ms = 672`（反序列化 + 迁移）。
- 因此那 73 秒发生在「方案切换完成之后」——候选只剩画布重建与**呈现（光栅化）**。
- 用户反馈"227 算子约 6 秒"，而探针同一量级只需要 1 秒左右 → **探针环境与真机有系统性差距**，
  不能再靠探针数字调参。

### 7.2 新增埋点（`FlowCanvasViewModel.PerfLog`）

`App.xaml.cs` 把 `FlowCanvasViewModel.PerfLog` 挂到 `ILogService.Info`；只对 ≥80 步的流程打两行：

```
[画布] 流程「X」步骤=227 可见节点=227 连线=200 重建+布局=…ms
[画布] 流程「X」呈现=…ms
```

- 第一行：`RebuildCore` 开始 → Background 优先级回调（容器生成 + measure/arrange 完成）。
- 第二行：同上 → 下一帧 `CompositionTarget.Rendering`（渲染线程把这一帧交给合成器）。
- **两行的差就是"UI 算得快、但画不出来"的证据**；若第一行本身就大，才是 UI 线程的问题。
- 走 `ILogService` 而不是弹泡（R78）；静态挂点避免给构造器加依赖（本 VM 在十余处断言宿主被 `new`）。

用新构建打开 `解决方案\压测-3000节点.vms`，点一条流程，然后把日志里那两行发出来。
