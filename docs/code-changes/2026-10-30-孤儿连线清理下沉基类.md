# 孤儿连线缺陷下沉 VisionPluginBase.PruneOrphanLinks

日期：2026-10-30
类型：既有缺陷修复 + 公共基类能力下沉（R12 级：动契约程序集，但纯加性、零接口变化）

---

## 1. 问题（既有缺陷，不是本批引入）

动态端口插件的输入端口名来自**配置**（列名 / 字段名 / 参数名 / 变量名）。配置一改
——改名、切换来源、删除行、换语句、换过程——旧端口被 `RemoveDynamicInput` 摘掉，
但 `StepModel.LinkedSources` 里挂在旧端口名上的那条连线**没有人删**。

它成了界面上够不到的悬空键（没有同名端口 → 行内 ✕ 删不到；画布不给它长输出脚），
而 `FlowCompiler` 对它是**硬错误**：

```
[连线错误] '数据记录_1' 没有名为 '温度' 的输入端口，这条连线不会生效。
```

`CompilationResult.Success = Errors.Count == 0`（`Engine\FlowCompiler.cs:263`），
所以**一条孤儿键足以让整条流程编译失败、跑不起来**，而用户在界面上找不到原因。

`Core\Models\ProcessStep\StepModel.cs:432-439` 的 `GetLinkedPortNames()` 注释原文就是为这件事写的：
"对不上的那条在 FlowCompiler 里是**错误**……足以让整条流程编译失败，而它没有同名端口、
行内与画布都够不到。"

## 3. 落地方案：下沉基类 + 各插件显式调用

### 3.1 新增 `VisionPluginBase.PruneOrphanLinks`

`Shard\Core.Interfaces\VisionPluginBase.cs`（`OnCancel` 之后、`#endregion` 之前）：

```csharp
protected int PruneOrphanLinks(IStepConfigData stepData, IEnumerable<string>? extraKeep = null)
```

- `stepData == null` → 返回 0（编译期实例 `StepData` 为空，`FlowCompiler.cs:883` 不调 `Initialize`）
- `stepData is not IStepLinkInventory` → 返回 0（12 个断言夹具都不实现这个接口，与 JudgeTable 同口径）
- 有效键 = `Inputs.Keys`（静态端口 + 动态端口）+ `extraKeep`
- 遍历 `GetLinkedPortNames()` 快照，不在有效键里的 `RemoveLink`，返回删除条数

**为什么是 `protected` 方法而不是往 `IStepConfigData` 加成员**：
`IStepLinkInventory.cs:8-13` 明确写过教训——那个接口有 8 个实现者，加非默认成员会
"把所有夹具一起拽进来改"。这次正是靠 `IStepLinkInventory` 这个能力接口才做到零夹具改动。

### 3.2 三条硬约束（都在 XML 注释里写明）

| 约束 | 依据 |
|---|---|
| **只在 `OnConfirm` 调用，绝不在 `RebuildDynamicInputs` 里自动清** | 重建在用户输入过程中反复触发（列名清空、改名撞名、类型切换）。那一刻"名字暂时为空但行还活着"的端口名不在 `Inputs` 里，自动清理会把有效绑定当孤儿删掉。`CSharpScriptPlugin.cs:410-419` 的 `_linkKeys` 锚点字典就是为这件事存在的 |
| **必须在 `base.OnConfirm` 之后** | 基类 `OnConfirm`（`VisionPluginBase.cs:383-391`）会给"未链接的端口"写 `InputValues` 固定值。先清 → 被删的键被当成未链接 → 留下一条脏常量在运行期覆盖连线 |
| **`extraKeep` 是给"配置态暂时没有端口但必须留住"的锚点** | 与上一条同源 |

### 3.3 五个插件的接入点

| 文件 | 位置 | 调用 |
|---|---|---|
| `Plugins\Plugin.DataRecord\DataRecordPlugin.cs` | `OnConfirm`（:185） | `PruneOrphanLinks(stepData);` |
| `Plugins\Plugin.ResultUpload\ResultUploadPlugin.cs` | `OnConfirm`（:235），`MigrateLinksOnRename` 与 `base` 之后、`SnapshotPortNames` 之前 | `PruneOrphanLinks(stepData);` |
| `Plugins\Plugin.Database\DatabasePluginBase.cs` | `OnConfirm`（:422），`base` 之后 | `PruneOrphanLinks(stepData);` |
| `Plugins\Plugin.ImageScript\ImageScriptPlugin.cs` | 新增 `OnConfirm` 覆盖（原来没有） | `base.OnConfirm(stepData); PruneOrphanLinks(stepData);` |
| `Plugins\Plugin.ResultDisplay\ResultDisplayPlugin.cs` | `OnConfirm`（:322），`base` 之后、常量清理之前 | `PruneOrphanLinks(stepData);` |

**三个已有自己实现（CSharpScript / JudgeTable / VariableAssignment）刻意不动**：
它们的清理带各自的锚点/快照回滚逻辑，强行合并会把差异抹掉。

### 3.4 「禁用」的口径（本次明确的取舍）

**端口消失 → 连线必须删**，没有第三种选择。理由：端口确实不存在了，留着就是编译错误。
代价与"删掉这一行"相同——重新启用要重新绑定。这一点在 `DataRecordPlugin.OnConfirm`
的注释里写明了，与改造前行为一致（改造前禁用列照样报编译错，只是报得晚、且找不到线）。

### 5.4 未覆盖（如实说明）

- **ImageScript 没有端到端断言**：它的端口名来自 `EProcedure` 过程接口，headless 造不出过程
  上下文（`ScriptTemplates` 的默认过程绑定在 HDevelop 引擎侧）。该插件的接入点只有一行
  `base.OnConfirm` + `PruneOrphanLinks`，靠代码评审钉住。
- **Database 的 `OnConfirm` 全路径没跑通**：`ValidateForConfirm` 要求"已选数据库 + 已选命名语句"，
  headless 建不出来（会抛"还没有数据库配置"）。所以 C30.18/C30.19 验的是
  "参数端口随 `Parameters` 重建" + "直接调 `PruneOrphanLinks` 会清旧键"，
  `OnConfirm` 里的调用位置由代码评审钉住。
- **视觉验收**：只做到字符串级与集合级断言，没有真跑界面看"清理后状态栏是否给出回执"
  （本次**没有加**状态栏回执，见 §6）。

## 6. 未做

1. **没有加"已清理 N 条失效连线"的状态栏回执**。`PruneOrphanLinks` 已经返回条数，
   但 `DataRecord` 没有可写状态栏字段，`ResultUpload.StatusMessage` 语义是"改名迁移"。
   要加得先统一各插件的提示出口（另一个批次）。
2. **`VariableAssignmentPlugin.DropOrphanLinks` 仍用反射取键列表**（`:951-971`）。
   基类现在有更好的能力接口，但它的 `extraKeep` 语义与基类不同（按 `Value_` 前缀过滤），
   合并属于独立清理项（交接报告 §3.4「死代码待清」同批）。
3. **`DataRecord` 改名仍然"删连线"而不是"迁移连线"**（`ResultUpload` 是迁移）。
   两种口径不一致，但都合法：迁移更好用，删除更保守。统一属于体验优化，另议。
