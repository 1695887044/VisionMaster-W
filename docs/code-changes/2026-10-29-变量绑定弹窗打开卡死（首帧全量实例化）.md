# 2026-10-29 变量绑定弹窗打开卡死（首帧全量实例化候选行）

> 现象：现场全局变量 **9000** 个，一打开「变量绑定」弹窗就卡死——十几秒到两分钟无响应，
> 看起来像死机（点哪都没反应，任务管理器显示 CPU 单核跑满）。
> 与同日《变量绑定候选列表卡顿（虚拟化失效）》是**同一个视图、同一类症状**，但那次只治好了
> 「改搜索词 / 换端口」的重建路径；**打开弹窗这一条仍然是全量实例化**。
> 根因不是"虚拟化没打开"，而是**高度上限在首帧之前被放宽成了无穷**。

## 一、当前状态

已修复并实测（`UIThemeSmokeTest.exe --variable-binding`，1180×760 宿主，**9001 条候选**）：

| 阶段 | 改前 | 改后 |
|---|---|---|
| Fixture（9000 变量 + `BuildTree` + 候选表重算） | — | 28 ms |
| 视图构造（含首帧高度预置） | — | 16 ms |
| **首次布局 `UpdateLayout()`** | **122 781 ms**（realized=9001） | **61 ms**（realized=5） |
| 布局后收敛 `Pump` | 1 675 ms | 4 ms |
| **打开总耗时** | **≈ 124 s** | **≈ 110 ms** |

`run_gates.ps1` 全量闸门结果见第四节。

## 二、根因（两层，缺一不可）

**第一层：`LayoutUpdated` 救不了首帧。**
`CandidateList` 整块嵌在右栏 `BindingBodyScroll`（外层 `ScrollViewer` + `StackPanel`）里，
外层量它时可用高度是无穷；`MaxHeight` 默认也是 `Infinity`。
上一轮的修法是把高度上限挂在 `LayoutUpdated` 上算——但 `LayoutUpdated` 是**这一轮布局跑完之后**
才发的，它只能让第二轮收敛回十来行，**首帧已经付掉的代价收不回来**。

**第二层（更致命）："短列表不封顶"的判据把"还没绑定上"当成了"列表很短"。**
`UpdateCandidateMaxHeight` 用 `CandidateList.Items.Count * 50` 判断内容是否超过 3 屏。
而 `ItemsSource` 是**布局期间**才落到 `ListBox` 上的，于是第一次 `LayoutUpdated` 看到的
`Items.Count == 0` → 判成短列表 → `MaxHeight = Infinity` → 紧接着的下一轮布局正好拿到全部候选 →
**逐行实例化，一行都不回收**。实测顺序（加临时诊断量出来的）：

```
[DIAG] Measure      =      8 ms  realized=0        ← ItemsSource 还没落地
[DIAG] Arrange      =      2 ms  realized=0
[DIAG] UpdateLayout = 122781 ms  realized=9001     ← 这一轮把全部候选建了出来
[DIAG] Pump         =   1675 ms  realized=6        ← 收敛回十来行（所以旧断言看不出来）
```

行成本实测 **≈13 ms/行**（9000 条 ≈122 s；1500 条 ≈20 s）。比同日上一篇记的 4 ms/行更高——
首帧含行模板首次实例化 / JIT 预热，且行模板本身仍是重模板（4 个 `AncestorType=UserControl` 绑定）。

## 三、已做

| 文件 | 改动 |
|---|---|
| `VisionMaster\Views\DialogViews\VariableBindingView.xaml.cs` | 构造器里 `CandidateList.MaxHeight = CandidateMinHeight`：**首帧之前**就有界，后续由 `UpdateCandidateMaxHeight` 放宽（短列表恢复 `Infinity` = 基线自然高度，长列表封在视口剩余高度） |
| 同上 | `UpdateCandidateMaxHeight` 增加 `Items.Count == 0 → return`：**条数未知时保持现状**，不许按"0 条"判成短列表。空列表本身高度为 0，不会被这条兜底压出观感差异 |
| `VisionMaster\ViewModels\DialogViewModels\VariableBindingViewModel.cs` | `RefreshDisplayPorts` 按"本次重算"缓存 `类型名 → Type`（9000 条变量只有几种类型，原来每条走一次 `Type.GetType`，解析不出来还要遍历全部已加载程序集）；只在真要上屏时才 `CloneForCandidate`（默认视图里被类型隐藏的项不再造对象） |
| `UIThemeSmokeTest\VariableBindingViewSmoke.cs` | 新增两条断言（见第四节）；批量夹具仍用 1500 条保持冒烟速度 |

## 六、踩过的坑

- **`LayoutUpdated` 不是"首帧之前"，是"这一轮布局之后"**：把"必须有界"的责任全压在它身上，
  等于让首帧裸奔。凡是"高度/宽度必须有界才能虚拟化"的列表，初始值就必须是有界的。
- **`Items.Count == 0` 不能当"列表很短"**：0 条最常见的原因是 **ItemsSource 还没绑定上**
  （绑定在布局期间才落地）。拿它做阈值判断，会在"恰好还没数据"的那一轮把上限放开。
- **"收敛后的终态"会掩盖首帧代价**：上一轮的断言（`realized <= 25`）在缺陷存在时照样绿，
  因为全量实例化之后会收敛回 6 个容器。判据必须取**首轮布局刚结束、`Pump` 之前**那一刻。
- **不要用耗时做闸**（沿用上一篇口径）：耗时随机器浮动；这里用"首帧实例化了几个容器"作为判据，
  耗时只作诊断打印，不进断言。
- 诊断打印要**先取时间再遍历可视化树**：`Descendants<ListBoxItem>()` 在 9001 个容器上本身就要几秒，
  顺序写反会把测量结果污染成"下一步很慢"。
