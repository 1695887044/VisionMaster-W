## 一、需求与决策

### 病根：循环头守卫把「上限」当成了「退出原因」

旧实现 [CompiledWhileNode.cs](file:///e:/VM/VisionMaster-W-master/Core/Models/Compileds/CompiledWhileNode.cs#L82) 用 `while (iter < MaxIterations)` 当循环头守卫，退出后再做一次事后判断：

```csharp
while (iter < MaxIterations) { ... if (!isTrue) break; ... }
// 退出后
if (iter >= MaxIterations && MaxIterations > 0 && !cancelled) throw new InvalidOperationException("疑似死循环");
```

**问题**：退出 loop 时 `iter == MaxIterations` 有两种完全不同的原因，事后无法区分——

| 退出原因 | `iter` | 该不该抛 |
|---|---|---|
| (a) 条件自然转假，循环正常跑完 | 恰好 `== MaxIterations`（边界巧合） | **不该抛** |
| (b) 条件恒为真，被守卫掐断 | `== MaxIterations` | 该抛 |

于是 `Counter < 9999` 配默认上限 9999、`i < N` 配 `MaxIterations = N` 这类**完全合法**的写法会被误报成死循环，**整条流程 Faulted**。默认上限就是 9999，工业连续场景真会撞上——不是纸面问题。

### 决策：调换判断顺序，而非"补一次求值"

对比过两种改法：

| 方案 | 做法 | 评价 |
|---|---|---|
| **选定** | 循环改 `while (true)`，**先求条件再判上限** | 两种退出原因天然分流：自然结束走 `return`、被掐断走 `throw` |
| 否决 | 保留守卫，退出后拿循环外的 `args` 再求值一次 | `args` 是**上一圈开始时**的快照，循环体可能已改过上游值 → 判断依据可能过期，不如方案正确 |

### 求值次数核算（改动的代价量化）

| 场景 | 旧实现求值次数 | 新实现求值次数 |
|---|---|---|
| 条件自然转假（第 3 圈后结束，上限 9999） | 3 | 3（**不变**） |
| 条件恰到上限那圈转假（`Counter < 5`，上限 5） | 5（且误抛） | 6（不抛 ✓） |
| 条件恒真（上限 5） | 5（抛） | 6（抛 ✓） |

结论：**只有"本来会被守卫掐断"的那一种场景多求值一次**，自然结束路径的求值次数与旧实现完全一致。`ConditionLambda` 是纯表达式、无副作用，多一次求值无语义风险。

### 一处顺带收敛

把 `MaxIterations <= 0` 的判断提到[循环外](file:///e:/VM/VisionMaster-W-master/Core/Models/Compileds/CompiledWhileNode.cs#L77)。旧实现把这个条件夹在事后判断里（`&& MaxIterations > 0`），提到循环外之后：一是循环体里不必再夹一个条件，二是"上限配 0 圈 = 正常不执行"这个语义有了单一落点。

### 新旧循环体对照

```csharp
// 旧：上限是"守卫"，退出后靠事后推断原因
while (iter < MaxIterations)
{
    if (cancelled) break;
    eval cond; if (!isTrue) break;
    body; iter++;
}
if (iter >= MaxIterations && MaxIterations > 0 && !cancelled) throw ...;   // ← 分不清 (a)/(b)

// 新：上限是"判定依据"，条件求值在前，两种退出原因各有出口
if (MaxIterations <= 0) return;
while (true)
{
    if (cancelled) return;
    eval cond;
    if (!isTrue) return;                      // (a) 自然跑完
    if (iter >= MaxIterations) throw ...;     // (b) 被掐断
    body; iter++;
}
```

构建说明：`HslCommunication` 是 net48 老式工程（显式 `<Compile Include>` 列表），其增量状态陈旧时会伪装成 `VM.Communication` 的编译错误（详见 A 组记录「已知边界」第 4 条）。本组统一用**全图重建**规避：

上一基线 343 → **347**，净增 4 条（`[E8]` ④b）且全通过；`[E1]`~`[E9]` 与 HTTP 冒烟段无回归。

### ④ / ④b 成对实跑（关键：两条能区分两种退出原因）

```
  [√通过] 恒真 While 图纸编译通过
  [√通过] 撞上限会抛穿流程  →  InvalidOperationException          ← ④ 被掐断：该抛
  [√通过] 恰好跑满上限 5 圈（不多不少）  →  实际 Runs=5
  [√通过] 刚好跑满上限的图纸编译通过
  [√通过] 条件恰好在上限那一圈转假 → 不误报死循环（旧实现此处必抛）   ← ④b 自然结束：不该抛
  [√通过] While 节点落 Success（不是 Failed）  →  State=Success
  [√通过] 恰好跑 5 圈（不多不少）  →  实际 Runs=5
```

④ 与 ④b 的**图纸形状完全相同**（都是"跑满 5 圈"），唯一差别是退出原因。旧实现无法区分 → 会同时抛；新实现按原因分流 → ④ 抛、④b 不抛。

### 断言的灵敏度实测

把上限判断**临时挪到条件判断之前**（即旧行为的等价物），其余不动：

```
[√通过] 撞上限会抛穿流程  →  InvalidOperationException
[√通过] 恰好跑满上限 5 圈（不多不少）  →  实际 Runs=5
[×失败] 条件恰好在上限那一圈转假 → 不误报死循环（旧实现此处必抛）
        →  InvalidOperationException: While节点 '刚好跑满While' 达到最大迭代次数 5，循环被强制中断（疑似死循环，请检查循环条件与变量刷新）
[×失败] While 节点落 Success（不是 Failed）  →  State=Failed
通过: 345  失败: 2
```

这正是 #5 报告的**假阳性现场完整复现**：合法的"正好跑满 5 圈后条件转假"被判成死循环、节点落 Failed。且 ④ 在同一次运行中仍绿——证明两条断言确实在测不同的东西。验完已立即还原。

## 四、已知边界

| # | 项 | 说明 |
|---|---|---|
| 1 | **"上限"从硬闸门变成判定依据，死循环场景会多求值一次条件** | 见「求值次数核算」。`ConditionLambda` 当前是纯表达式（DynamicExpresso 编译后的委托），无副作用，故无语义风险。**但若将来允许条件里内联副作用操作，这条要多想一步** |
| 2 | **上限判定仍依赖"循环体每圈都会推进状态"** | 若循环体的 Continue/Break 控制流把上进的路径绕开（旧注释提到"每圈都 Continue 的死循环"），`iter++` 仍在 Continue 分支后执行，计数不丢。这一点由 [E2] 与 ④ 覆盖 |
| 3 | **`[E8]` ④/④b 都用反射改 `MaxIterations = 5`** | 避免真跑 9999 圈；依赖 `NodeLookup` 为 public（已确认），不构成产品能力，与 A 组记录同一口径 |
| 4 | **未验证 9999 这个默认值本身是否合适** | 本组只修"判定方式"，未动默认上限大小。清单也未提出该项。若现场需要更细粒度控制（或需要区分"上限掐断"与"业务主动 break"的可配置策略），需产品侧另行设计 |
| 5 | **`MaxIterations <= 0` 的语义：静默不执行** | 沿用旧语义（上限配 0 圈 = 正常不执行、不报错）。这是**刻意的**：若改成报错，会把"条件初值即为假的循环"与"上限配错"混为一谈。但代价是上限误配成 0 时无人告警 |
