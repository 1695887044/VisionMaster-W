# 2026-09-18 SCADA 事件与动作骨架（S5）—— 从"能跑起来"走到"点一下有反应"

## 一、需求与决策

### 这一阶段要交付什么

S4 让画面**跑起来**了，但运行态是一张"死"的画：点按钮毫无反应，因为
`ElementDescriptor.Events` 只是把事件词表**立住了**，一条都没真触发（S4 边界清单第 2 条）。

S5 补的是商用组态软件的第二条闭环：

> 设计期勾一个事件 → 运行时点一下 → 动作真的执行（本阶段动作 = 记一行日志）。

### 用户在本阶段定下的硬契约

| # | 契约 | 落地位置 |
|---|---|---|
| 1 | **事件钩子是必备能力**（对标商用组态），不是可选装饰 | `ScadaElement.EventHooks` / `ScadaPage.EventHooks` |
| 2 | 钩子**声明在描述符上**，属性面板按「描述符 ∪ 已有钩子」渲染 | `ElementDescriptor.Events` + `ScadaPropertyViewModel` 事件组 |
| 3 | 本版事件钩子**不与流程引擎关联**，只做界面级动作 | `ScadaActionType` 仅 Log / WriteVariable / Navigate |
| 4 | **设计期不触发事件**——"我设计完直接运行一下不就能看出来了吗" | `ScadaRuntime.RaiseElementEvent` 第一道闸门 `!_running → 0` |
| 5 | 所有按钮、所有能绑定变量的图元都**应当有事件钩子**（含值变化） | `BuiltInElements` 逐个描述符声明 |

### 四条关键决策与理由

**决策一：动作模型放领域层，分发器放 WPF 层。**

`ScadaAction` / `ScadaEventHook` / `ScadaActionType` 在 `VM.Scada`（零 WPF 引用），
`IScadaActionDispatcher` 接口也在领域层，实现 `ScadaActionDispatcher` 在 `VisionMaster/Services`。
理由：**"点一下该干什么"是数据**（要写进 `.vms`、要跨版本读回来），
而**"怎么干"才依赖运行环境**（记日志要用 `ILogService`）。分开之后，
断言工程可以拿一个假的 `ILogService` 跑完全部动作分支，不需要开窗口。

**决策二：三道闸门全放在会话里，宿主一条规则都不判。**

```
① !_running                                    → 0 条
② CurrentPage == null || FindElement 引用比对不等 → 0 条
③ 钩子事件不匹配 或 Actions.Count == 0           → 跳过该条
```

宿主 `OnScadaEvent` 只做"从控件反查模型 → 交给会话"，连"这是不是当前画面上的图元"都不问。
理由：这三条规则图元级和画面级**是同一套**，写在两处就是两份副本，
将来 bug 也会分布在两处。S5 新增 `RaisePageEvent` 时只换了第②道的问法
（"这还是不是当前那一页"），其余原样复用 `RaiseHooks`。

**决策三：`ScadaActionType` 刻意没有 `None`，默认值是 `Log`。**

一条动作记录**必然**表达一件要干的事，"没有动作"由 `Actions` 集合为空表达。
副作用正好是想要的：属性面板点"添加动作"先长出一条"记录日志"，改内容就能用，
不必先做一次无意义的类型选择。

**决策四：属性面板勾选**只改数据，不执行、不预览。**

"勾上『按下』"= 往 `EventHooks` 里补一条带默认动作的钩子（**只补缺，不覆盖**）；
"取消勾选"= 整条摘掉（连同它下面的动作）。两个方向都标脏画面（`Version` 变大），
否则编辑器不会提示保存，配好的钩子会被悄悄吞掉。
重复勾一次**不加钩子、也不空转版本号**——否则"点开面板再关掉"就成了"有改动"。

**决策五：动作编辑内联在属性面板里，本版只做"增删 + 选类型 + 改文案 + 调序"。**

勾上事件后，事件行**原地**长出一张动作表（`动作（自上而下依次执行）：` + 若干行 + `+ 添加动作`），
**不新增弹窗**。理由：动作是钩子的从属数据，弹窗会让"我在配哪条钩子"这个上下文丢失，
而组态软件里用户要连着配十几个钩子，每次弹窗就是一次上下文切换。
本版只做最小闭环（增 / 删 / 选类型 / 改文案 / ↑↓ 调序），
`WriteVariable` 的变量选择与 `Navigate` 的目标画面选择**明确留到 S6 / S8**——
那两处的参数编辑器（变量选择器、画面选择器）属于各自阶段的地基，先做就是凭空造两套。

**决策六：顺序有语义，所以 ↑↓ 本版一起做。**

执行侧严格按 `Actions` 集合次序跑（`ScadaActionDispatcher` 顺序遍历），
所以"先写变量再记日志"和"先记日志再写变量"是两件事。
只给增删不给调序，用户就只剩"删掉重加"这一条路——那等于把顺序语义藏起来了。

**决策七：动作表直接双向绑到模型对象本身，不做拷贝。**

`ScadaEventRow.Actions` 返回的就是 `Element.FindEventHook(EventType)?.Actions`
（模型里那张 `ObservableCollection<ScadaAction>` 本身）。理由：`ScadaAction` 本就是
带变更通知的模型对象，**没有"文本形态"**——不存在"用户打的字模型接不接得住"这种歧义。
其余属性行之所以要走 `Read()` / `Commit(text)`，是因为它们背后是 `double` / `Color` / `bool`
这类无通知的值类型；动作行不欠这一层。

**决策八："还没接通"的提示语只写一份。**

`ScadaActionTypeExtensions.PendingReason()`（领域层）同时供给两处：
属性面板的橙色提示文字、以及运行时分发器留的那行日志。
面板上写"要等 S6"、日志里写另一句，用户就没法把"我配的那条"和"日志里那条"对上号。
这与 `DisplayName()` 只写一份是同一个理由。哪一段补齐了就删对应的一项，全接上了整个方法一起删。

**决策九：面板换模板的判据是"行的自述"，不是"行的类型"。**

XAML 里 `PropertyRow` 外层用 `ContentControl` + DataTrigger 判 `IsCompositeEditor`（基类上的可绑标志）
来决定是否整份换成事件行模板。理由：XAML 不该认得 `ScadaEventRow` 这个自定义类型——
将来再加一种复合行（比如"报警联动"），只需在 VM 里把标志置 `true`，XAML 一行都不用改。

## 三、根因分析：图元事件"发得出去、收不到"

这是本阶段最值得写下来的一条，因为它**在日志里看起来像"事件根本没触发"**。

### 现象

运行态点按钮：日志**一行都没有**。既没有"按下"，也没有任何报错——
像是鼠标根本没点中，或者事件压根没发。

### 排查过程（三段插桩法）

窗口侧没有 logger（`Scada.Controls` 不依赖 Core，窗口也没注入 `ILogService`），
所以诊断写独立文件 `_diag_runtime.log`，在三个位置各挂一座临时桥：

| 段 | 挂在哪 | 回答什么问题 |
|---|---|---|
| ① 输入段 | 画布 `PreviewMouseDown/Up`（`handledEventsToo=true`） | 鼠标到底有没有点到画布上？ |
| ② raise 段 | 画布 `ScadaEventEvent`（`handledEventsToo=true`） | 图元控件 `RaiseEvent` 之后，事件有没有冒到画布？ |
| ③ 窗口根段 | 窗口根 `ScadaEventEvent`（`handledEventsToo=true`） | 有没有冒到窗口根？被标 Handled 了吗？ |

### 诊断实测（同一次点击）

```
②raise 冒泡到画布 src=ScadaCanvas evt=Pressed
③冒泡到窗口根 src=ScadaCanvas orig=ButtonElement handled=False evt=Pressed
①输入 PreviewMouseDown src=TextBlock 画布坐标=560,444
②raise 冒泡到画布 src=ScadaCanvas evt=Released
③冒泡到窗口根 src=ScadaCanvas orig=ButtonElement handled=False evt=Released
```

三行同时到位，说明：**输入到了、命中到了、事件发了、冒到窗口根了、没被标 Handled**。
可主日志里宿主桥的 `[诊断]` 行**零出现**——断点锁死在**画布之上、窗口根之下**的最后一跳。

### 结论：WPF 把 `Source` 重定目标了

图元控件是**代码创建**的，挂在 `PART_ElementLayer` 这层 `Canvas` 下。
WPF 路由事件冒泡时，会把 `Source` **重定目标（retarget）到最近一个有逻辑连接的祖先**——
本案例里就是画布 `ScadaCanvas`。而 `OriginalSource` 永远锁定在 `RaiseEvent` 的那个控件本尊上，
不受重定目标影响。

宿主原来的入口第一行是：

```csharp
if (args.Source is not ScadaElementBase control) return;   // Source 已是 ScadaCanvas → 静默返回
```

于是**每一条事件都在日志之前被静默丢弃**——现象就是"点了没反应、也没有任何线索"。

### 修复

```csharp
// 必须用 OriginalSource 而不是 Source：图元控件挂在代码创建的图层下（无逻辑父级），
// 冒泡途中 WPF 会把 Source 重定目标到最近有逻辑连接的祖先（画布），
// 而 OriginalSource 永远锁定在 RaiseEvent 的那个控件本尊上，不受重定目标影响。
if (args.OriginalSource is not ScadaElementBase control) return;
```

### 顺带修掉的第二个真 bug：双桥重复执行

`ScadaRuntimeWindow` 构造时曾在画布上也挂了一座 `AddHandler(ScadaEventEvent, ...)`，
宿主又在窗口根上挂了一座。**路由事件按委托逐个回调**，
两座桥会让同一钩子的动作**被执行两遍**（日志里同一动作出现两行）。
修复 = 删掉窗口侧那一座，全程序只留宿主一处订阅（`AddHandler`/`RemoveHandler` 成对）。

### 方法论收获（写给下一个人）

- **"事件没触发"要先分成四段查**：输入到没到 → 命中没命中 → 事件发没发 → 冒到没冒到。
  四段各挂一座桥，一次点击就能定位，比读代码猜快一个数量级。
- **`e.Source` 在路由事件里不可信，`e.OriginalSource` 才可信。**
  凡是"从事件反查触发者"的代码，一律用 `OriginalSource`；用 `Source` 的都要复查一遍。
- **诊断桥一律 `handledEventsToo=true`**：否则"被标 Handled"和"没冒上来"看起来一模一样。
- **改完即删探针**：三段桥、宿主 `[诊断]` 行、`_diag_runtime.log` 全部清除，已 grep 确认零残留。

## 五、已知边界（欠债清单，按优先级）

1. **`Unloaded` 不触发。** `ScadaRuntime.Stop()` 里刻意不发（发了也没人接），与 S4 边界一致。
2. **动作只有 `Log` 真能执行。** `WriteVariable` 等 S6 数据泵、`Navigate` 等 S8 画面导航；
   现在**配置允许存**（这是有意的：让用户先把逻辑配出来），但运行时会走"本版本未实现"分支留一行日志。
3. **动作的「参数」还编不了，但动作本身已经能编了。** 面板已支持**增 / 删 / 选类型 / 改文案 / ↑↓ 调序**；
   欠的是 `WriteVariable` 的变量选择器（等 S6）与 `Navigate` 的目标画面选择器（等 S8）。
   在那之前，这两类动作只显示一行橙色 `PendingReason` 说明——配置允许存，运行时不执行。
4. **删光最后一条动作不会顺手摘钩子。** 空动作表在执行侧本来就等同没配，
   面板用提示说明比替用户做决定诚实（要摘钩子请取消勾选，那条路会连表一起收走）。
5. **事件钩子未与流程引擎关联**（用户明确定的本阶段边界）。
6. **图元级 `ValueChanged` 词表立住了但发不出来。** 需要 S6 数据泵把变量值写回图元才有"值变化"可言。
7. **`ScadaBinding` 只有模型，没有数据泵**（承接 S4 边界第 1 条，仍是最大差距）。
8. **图层面板没有 UI**；`ScadaPage` 的 `Try*` 家族除断言外无入口。
9. **重命名方案不改 `.vms` 文件名**（产品决策项，非 bug）。
10. **`Hmi.Text` 空文本不可见**（待决：默认文字=图元名，或空文本画虚线占位框）。
11. **SCADA 新代码全部未纳入版本控制**（`Scada/`、`Scada.Controls/`、`ScadaChecks/` 等）。

### 操作纪律（踩过两次以上，写死在这里）

- **启动 GUI 做真机验证，必须用 `Invoke-CimMethod -ClassName Win32_Process -MethodName Create`
  脱离终端启动。** `Start-Process` 起的进程会随终端作业对象回收被一起收掉，
  表现为"启动后自行退出"，而日志里**一点异常都没有**——非常误导。
- **强杀旧实例后不要立刻重启**：0.5 秒内起新进程，新进程会在约 7 秒后**静默退出**，
  事件查看器里**无任何崩溃记录**（不是异常崩溃）。错开几秒启动即正常，
  已连续两次复现、一次干净启动对照确认。
- **`click` 与 `get_app_state` 必须用同一个 `max_depths`**，否则元素 id 对不上。
- **`get_app_state` 必须显式传 `pid`**，否则报 `pid is not running`。
- **本仓库的 `click` 用坐标时 `element_id` 也是必填**（传目标窗口根，写 `"0"`）：
  只传 `x`/`y` 会报 `Input validation error: element_id: Invalid input: expected string`。
- **属性面板太长时先折叠无关分组，别硬点被裁掉的元素。**
  本阶段点「+ 添加动作」时按钮被面板底部裁出可视区，点不动也不报错；
  折叠上方「外观」组把它顶进可视区后一次就中。
  另有一次用坐标补点**误命中了旁边的类型下拉框**（歪打正着验证了下拉，但不是可控操作）——
  **能拿 element_id 就别用坐标**。
- **本仓库有单实例检查**（`VisionMaster/App.xaml.cs` 的 `SingleInstanceCheck`）：
  已有实例在跑时，新起的实例会**自己退出**。真机验证前先确认旧实例已停。
- **多窗口应用要按 `windowId` 定向查询**，否则 tooltip 窗口会抢走"当前截图目标"，
  导致 UI 树被截断成 `(... elements hidden)`。
