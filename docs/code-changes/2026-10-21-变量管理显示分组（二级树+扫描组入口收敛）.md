# 变量管理显示分组（二级树 + 扫描组入口收敛）

- 日期：2026-10-21
- 涉及：
  - `Core\Models\Variable\VariableGroupDescriptor.cs`（新增）
  - `Core\Models\SolutionModel.cs`、`Core\Models\Variable\NetworkVariableModel.cs`、`Core\Models\Variable\VariableDto.cs`、`Core\Models\VariableNode.cs`
  - `VisionMaster\Services\VariablePersistenceService.cs`
  - `VisionMaster\ViewModels\DialogViewModels\GlobalVariableManagerViewModel.cs`、`VariableGroupEditorViewModel.cs`（新增）
  - `VisionMaster\Views\DialogViews\GlobalVariableView.xaml`、`GlobalVariableView.xaml.cs`、`GlobalVariableViewConverters.cs`
  - `FlowCanvasChecks\GlobalVariableChecks.cs`、`UIThemeSmokeTest\GlobalVariableViewSmoke.cs`
- 触发：用户要求变量管理左栏在「来源」之下再做一级分类——**设备下的变量按用途分组（如监控 / 控制），分组可新增、可改名、不能重名**；并明确「只做显示归类与筛选，不影响采集 / 轮询 / 写入」。

---

## 1. 起因

改造前左栏只有一级「来源」：本地变量、系统变量、每条通信连接平铺（`VariableSourceNode` 只有 `Key` / `DisplayName` / `Count` / `IsOnline`）。一条连接下挂几十个点时，监控点与控制点混在一张表里，只能靠搜索或地址猜。

用户的需求有三条硬约束：

1. **二级分类挂在设备（连接）下面**，不是把变量按全局标签重排；
2. **分组可维护**：新增、改名、删除，且**名称不能重复**；
3. **纯显示语义**：分组不能进入采集 / 轮询 / 写入链路——这一点必须与既有的「扫描组」严格区分开（扫描组是连接级调度资源，见 §2.6）。

## 2. 口径与决策

### 2.1 分组表放方案级 `SolutionModel.VariableGroups`

```csharp
// Core\Models\SolutionModel.cs:202-219
private List<VariableGroupDescriptor> variableGroups = new();
[JsonProperty(ObjectCreationHandling = ObjectCreationHandling.Replace)]
public List<VariableGroupDescriptor> VariableGroups
{
    get => variableGroups;
    set => variableGroups = value ?? new();   // .vms 可人工编辑，"VariableGroups": null 不该让变量管理崩
}
```

`VariableGroupDescriptor` 只有两个字段（`Core\Models\Variable\VariableGroupDescriptor.cs:20`）：

| 字段 | 语义 |
| --- | --- |
| `Guid Id` | 稳定身份，创建时生成，改名不变 |
| `string Name` | 显示名（方案内唯一，不区分大小写；「未分组」为内置保留名） |

**为什么不放在每条连接（`CommunicationConfig`）里**：用户要的是"这条设备下的变量怎么归类"，但分组本身是**方案级**的展示资源——同一条连接在不同方案里可以有不同归类；放进连接配置会让"改方案"与"改通讯配置"耦合，也会把纯展示字段写进 `communications.json`。放方案级后，它随 `.vms` 一起走，与 `VariableSnapshots` 同生命周期。

### 2.2 变量按 Guid 引用：改名不级联

- `NetworkVariableModel.GroupId`（`Core\Models\Variable\NetworkVariableModel.cs:79`）
- `VariableDto.GroupId`（`Core\Models\Variable\VariableDto.cs:88`，`FromNetwork` 在 `:202` 拷贝）
- 展示节点 `VariableNode.GroupId` / `GroupOptions` / `SelectedGroup` / `GroupChanged` / `ShowGroup`（`Core\Models\VariableNode.cs:100/:105/:112/:126/:131`），候选项 `VariableGroupOption { Id, Name }`（`:571`）

**为什么不用名字做键**：扫描组是按名字登记进 `PollScheduler` 的，改名必须同步轮询侧与模型两处；显示分组若照抄这套，改名就要遍历所有变量改写字符串。用 Guid 之后，`RenameGroupCore` 只改 `Name` 一个字段（`VariableGroupEditorViewModel.cs:365-372`），变量侧零改动。

**旧方案零迁移**：`.vms` 没有 `VariableGroups` → 反序列化为空表；`VariableDto.GroupId` 缺字段 → `Guid.Empty` → 归入「未分组」。`SolutionModel.VariableGroups` 的 setter 另有 null 兜底（§2.1），避免人工编辑出的 `null` 在打开弹窗时 NRE。

### 2.3 名称唯一：trim + `OrdinalIgnoreCase`，新增与改名共用一份校验

`VariableGroupEditorViewModel.ValidateGroupName`（`:322-339`）是唯一实现：

| 规则 | 实现 | 上屏文案 |
| --- | --- | --- |
| 空名 | `Trim()` 后长度为 0 | 请输入分组名称 |
| 超长 | `MaxNameLength = 20`（`:34`） | 分组名称最多 20 个字符 |
| 保留名 | 与 `UngroupedName = "未分组"`（`:31`）按 `Ordinal` 比较 | 「未分组」是系统内置分组，不能作为分组名 |
| 重名 | 与其它组的 `Name.Trim()` 按 `OrdinalIgnoreCase` 比较 | 已存在同名分组「…」 |
| 改名排除自身 | `exceptId` 命中即跳过 | — |

**为什么必须共用**：新增走 `AddGroup`（`:169-194`）、改名走 `CommitRename`（`:249-274`），两条路径各写一份校验，最常见的漏就是"新增拦住了重名、改名绕过去"。断言 `[G]` 第 2 条专门钉住"改名时拿别人的名字才算重名"。

### 2.4 删组：变量回落到 `Guid.Empty`，变量不删

```csharp
// VariableGroupEditorViewModel.cs:345-362
public static int DeleteGroupCore(List<VariableGroupDescriptor> groups,
    IEnumerable<NetworkVariableModel> variables, Guid groupId)
{
    if (groupId == Guid.Empty) return 0;        // 内置「未分组」不可删
    foreach (var variable in variables)
        if (variable.GroupId == groupId) { variable.GroupId = Guid.Empty; affected++; }
    groups.RemoveAll(g => g.Id == groupId);
    return affected;
}
```

三条口径：

1. **先回落、后删组**：任何时刻变量的 `GroupId` 要么指向存在的组、要么是 `Guid.Empty`，不存在"指向已删组"的中间态。
2. **变量本身不删**：分组是展示分类，删分类不该带走数据。
3. **确认条报影响面**：`VariableGroupRow.DeleteConfirmText`（`:444-445`）逐字为「删除「X」？N 个变量将归入「未分组」，变量本身不会被删除。」——`N` 是该组的实时计数。

另有两条兜底：编辑器的 `Reload` 与变量管理的 `CountVariables` 都把"分组表里没有的 Id"按 `Guid.Empty` 统计（`VariableGroupEditorViewModel.cs:132-138`、`GlobalVariableManagerViewModel.cs:359-360`）；持久化恢复时同样归一（§2.5 末尾）。

### 2.5 左栏二级树 + 分组筛选；搜索跨分组

**树结构**（`GlobalVariableManagerViewModel.RebuildSourceTree`，`:268-333`）：

```
本地变量
系统变量
PLC_Modbus            [▾]        ← 连接行可折叠（ShowExpand 只给连接行）
  全部                 (N)
  监控分组             (n)        ← 方案分组按定义顺序
  控制分组             (m)
  未分组               (k)
PLC_S7_1              [▸]
```

- **连接默认展开**（首次建树时把全部连接记入 `_expandedConnections`），之后按用户折叠状态保留（`:275-280`、`:363-369`）。
- **空分组也显示**（计数 0）：分组表是方案级资源，用户刚建完就要能在树上看到；0 计数的行在视图里降低不透明度但仍可点（`GlobalVariableView.xaml:328-331`）。
- **选中语义**（`ApplySelection`，`:195-232`）：来源行 → `SelectedGroupId = null`（全部）；分组行 → `_selectedSourceKey = ParentKey`、`_selectedGroupId = node.GroupId`。`SelectedSource` 保留为派生属性（分组行返回父连接），让"按来源建变量 / 收放三列"的既有代码不必区分层级（`:136-144`）。

**筛选**（`FilterDisplayNodes`，`:526-572`）：来源 + 分组 + 搜索三者取交集，数组子行跟随父级（2026-10-11 的既有契约）。

**搜索必须跨分组**（`:549-552`）：

```csharp
bool matchGroup = searching
    || groupId == null
    || !node.IsNetwork
    || node.GroupId == groupId.Value;
```

在「监控分组」里搜一个属于「控制分组」的点，必须能搜到——否则用户第一反应是"明明有这个变量却搜不到"。界面用 `SearchScopeLabel = "搜索范围：全部分组"` 明示口径（`:153`，视图 `GlobalVariableView.xaml:655-661`）。

### 2.6 扫描组入口收敛：变量管理只保留"给变量选组"

- **保留**：明细表的「扫描组」下拉（`ScanGroupOptions` / `ScanGroupText` / `ShowScanGroup` / `ScanGroupChanged` 不变）。
- **移除**：变量管理里打开扫描组编辑器的入口（原 `ManageScanGroupsCommand` / `ManageGroupsButton`）。

**为什么移除**（代码注释逐字保留了理由，`GlobalVariableManagerViewModel.cs:649-653`）：

> 组表是连接级调度资源（周期 / 请求配额 / 段合并），改它的影响面是整条连接；且它需要 `IHardwareEditGate` 的"管理员 + 流程未运行"门禁与通讯配置置脏——这两样都不在变量管理的职责里。

即：变量管理的这条入口原本**既没传门禁、也没传置脏回调**，等于绕过扫描组的调度语义与权限语义。收敛后，扫描组编辑器只在「通讯设置 → 连接 → 操作 → 扫描组」开，变量管理只做"这个点属于哪个组"的选择（`OnScanGroupChanged` 仍会 `ReRegister`，语义未变，`:1004`）。

断言 `[G]` 里有一条**静态扫描**钉住这条：`vm` 与 `xaml` 中都不许再出现 `ScanGroupEditorViewModel` / `ManageScanGroupsCommand` / `ManageGroupsButton`（`GlobalVariableChecks.cs:1297-1300`）。

### 2.7 表格用「分组」列替换原「来源」列

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 第 3 列 | 来源（badge，120 宽） | **分组（ComboBox，120 宽）**，列名 `GroupColumn` |
| 来源信息 | 行内 badge | 卡片头 tag（`SelectedSource.DisplayName`，`GlobalVariableView.xaml:642-647`）+ 左栏导航 |
| 扫描组 / 地址列 | 不变 | 不变 |

**为什么敢换**：左栏选中来源后，右栏整张表已经只显示该来源的变量（筛选在 VM 里），来源列每行都是同一个值；而"分组"是每行都可能不同、且用户需要就地改的那一列。宽度契约不变——**分组列仍取 120（MinWidth 120）**，网络来源固定列合计仍是 `220 + 104 + 120 + 104 + 88 + 100 = 736`，1200 窄档视口 924 下 `736 + 160 = 896` 仍成立（`GlobalVariableChecks.cs:629-646` 逐列快照）。

### 2.8 在当前分组作用域里新建变量 → 直接归入该组

```csharp
// GlobalVariableManagerViewModel.cs:1476-1480
netVar.GroupId = _selectedGroupId is { } selectedGroupId && selectedGroupId != Guid.Empty
    ? selectedGroupId
    : Guid.Empty;
```

- 在「监控分组」下点「添加变量」→ 新变量直接进该组；
- 在「全部」或「未分组」下新建 → `Guid.Empty`（未分组）。

这条只在**创建那一刻**生效一次，之后归类由下拉决定；不改变"添加变量"弹窗的属性网格契约（C9）。

### 2.9 本地 / 系统变量不参与显示分组（v1 口径）

- 左栏二级分组只挂在网络连接下；
- 表格「分组」列的 ComboBox 由 `ShowGroup => IsRootNode && IsNetwork`（`VariableNode.cs:131`）控制可见性；
- 筛选里 `matchGroup` 对 `!node.IsNetwork` 恒为真（`:551`）。

理由：本地变量没有"设备归属"这一层，系统变量由宿主维护；给它们造分组只会多一套"看起来能改、实际不影响任何东西"的空维度。v1 明确不做，留待需要时再议（§5）。

### 2.10 分组编辑器是弹窗内的覆盖层，不是独立 Prism 弹窗

`VariableGroupEditorViewModel`（新增）+ `GlobalVariableView.xaml` 的 `GroupEditorOverlay`（`:1931-1935`）。

- **即时生效**：与变量管理的其它动作（写值 / 删变量）同一事务模型，没有"确定/取消"；行内改名、行内删除确认（`IsEditing` / `IsConfirmingDelete`），提交即写方案表。
- **改完必须重建节点**：每个 `VariableNode.GroupOptions` 是建节点那一刻的快照，只刷新左栏会让明细表的下拉继续显示旧组名 → `OnVariableGroupsChanged` 里 `RebuildSourceTree() + RefreshTree()`（`:990-997`），重建按 `VariableId` 保留数组展开态。
- **当前选中的组被删 → 回落到「未分组」**（`:992-993`），因为分组表即时生效、没有撤销可找回。
- **无方案时明确提示并禁用「添加」**：`RefreshNewGroupState` 在 `CurrentSolution == null` 时把 `NewGroupError` 设成"当前没有打开的方案，无法保存分组"且 `CanAddGroup = false`（`:196-217`）；`AddGroup` 首行再兜一次（`:171-175`）。**改前这里会静默失效**——`Groups` 在无方案时返回临时 `new List<>()`，加进去即丢，用户输完名字点一下什么都不发生。

## 5. 未决 / 边界

1. **本地 / 系统变量不参与显示分组（v1）**：`ShowGroup` 只对网络根节点为真，筛选对非网络节点不生效。若将来要给本地变量也分类，需要先回答"分组表是否还叫方案级"与"系统变量由宿主维护、归类存在哪"。
2. **无方案时「添加分组」明确提示并禁用**：这是有意的行为收敛（改前静默失效）。真实运行期 `CurrentSolution` 一定有值，这条只在启动早期 / 异常路径可见。
3. **WPF 重入未做视图级断言**：在「监控分组」作用域里把某行的下拉改到「控制分组」，该行会被筛掉（集合重建 + 行容器回收）。当前用 `ApplyGroupSelection` 纯函数 + 冒烟（选中/筛选/覆盖层）覆盖核心路径，**没有**在真实 `DataGrid` 上断言"改完分组后行被移除、焦点不丢"。这是已知的断言缺口，不是已修复项。
4. **`design.html` 早于本次改动**：设计基线里的 Web 设计稿（v1/v2/v3）没有"左栏二级分组 / 分组列 / 管理分组覆盖层"这三块。本次只同步 `docs\UI设计基线\global-variables\README.md` 与证据 PNG；**`design.html` 需要时再重绘**，在此之前以 README 与 `evidence\after-render-v1-*.png` 为准。
5. **表格「来源」列被「分组」列替换**是有意取舍：来源信息仍在卡片头 tag 与左栏导航；若将来需要"跨来源查看全部变量"，需要新增一个真正的「全部来源」作用域，而不是把来源列加回来（加回来会破 1200 窄档的 736 固定列预算）。
6. **分组只按定义顺序显示**：`VariableGroups` 是 `List`，左栏与覆盖层都按表内顺序；没有排序/拖拽。改名不改变顺序（Id 不变）。
