## 一、需求与决策

### 需求

第一批把"数值 + 指示"补齐了，但工艺流程图上**还是画不出设备**：一台泵、一台电机、一段带流向的管子，
是任何一张产线画面都躲不开的三样东西。本批就是补这三个**流程符号**。

| 图元 | 依赖 | 本批 |
|---|---|---|
| `Hmi.Pump`（泵） | 无 | ✅ |
| `Hmi.Motor`（电机） | 无 | ✅ |
| `Hmi.Pipe`（管道，带流向） | 无 | ✅ |

三者**共用同一套状态语汇**，这是本批最要紧的一条设计决定。

### 决策一：三图元共用 `DeviceState`，单开一个枚举文件

泵、电机、管道都要表达"停机 / 运行 / 故障"，配色也必须是同一套（灰 / 绿 / 红），
否则同屏一台泵绿着、一台电机红着，现场看一眼就以为坏了。

于是把枚举抽出来单开 [DeviceState.cs](file:///e:/VM/VisionMaster-W-master/Scada.Controls/Elements/DeviceState.cs)：

```
Stopped（灰 #FF7A7A7A） / Running（绿 #FF34C759） / Fault（红 #FFE03A2B）
```

**放置判据是"有几个使用者"**：`DeviceState` 有泵 / 电机 / 管道三家共用 → 单开文件；
而 `PipeFlowDirection` 只有管道一个使用者 → 就住在 `PipeElement.cs` 里，不为它单开文件。
"够用就好，不预先抽象"——只有第二个使用者出现时才搬家。

### 决策二：状态色是"输入"，不是"外观直设"

三图元的 `State` 都声明为**可绑变量**（`IsBindable = true`），且都带一个 `StateBrush` 只读推导属性：

- 用户只设三个颜色（`StoppedColor` / `RunningColor` / `FaultColor`）；
- 模板只绑 `StateBrush`；
- `State` 一变，控件内部把 `StateBrush` 重算成对应颜色。

好处与第一批「决策二」完全一致：**换算只有一处**、断言可直接读控件属性、换皮肤只改模板。

`State` 的取值口径三处统一：**整数 0=停机 1=运行 2=故障**，写枚举名（`Running` / `Fault`）也认；
**认不出的值按停机收敛**，不让坏数据把整页渲染打断（沿用第一批「决策三：坏输入一律收敛」）。

### 决策三：位号带——泵与电机底部四分之一让给位号标签

泵和电机在工艺图上**通常要带位号**（`P-101` / `M-201`），而位号由外层文本图元叠上去。
所以两者的**符号本体都不许占满整个控件**：

| 图元 | 常量 | 含义 |
|---|---|---|
| `Hmi.Pump` | `LabelRatio = 0.25` | 底部 25% 让给位号，泵壳只在**上方 75% 里内接正圆** |
| `Hmi.Motor` | `LabelRatio = 0.25` | 底部 25% 让给位号 |
| `Hmi.Motor` | `BoxRatio = 0.18` | **顶部 18% 再切一条**给接线盒 |

于是电机机身的内接圆被上下两条线夹住：`regionTop = H × 0.18`、`regionBottom = H × (1 − 0.25)`，
直径取 `min(宽, 区高)`。这条"内接正圆、短边定直径"的账与第一批的泵壳、表盘同源。

**管道没有位号带**——管子本身就是一段细长条，位号压在管身上会把流向箭头盖掉。

### 决策四：管道箭头数量**现算**，不写死

管子的可见部分是**管身描边 + 一组人字箭头**。箭头个数写死会在管子拉长时稀稀拉拉、缩短时挤成一团。
所以个数由"管身排得下几个"现算：

```
step   = 短边 × ArrowStepRatio(1.8)
count  = Clamp(Round(管身长 / step, AwayFromZero), 1, 6)
中心 x = inset + 管身长 × (i + 1) / (count + 1)      // 两端各留一份空档
```

上限 6 是**防止超长管子画成一排蚂蚁**；下限 1 是**保证再短的管子也看得见流向**。

### 决策五：人字的"尖 vs 端头"命名纪律（本批踩过的坑）

一个箭头人字只有三个点：两个**端头**（上、下）和一个**尖**（中间那个折点）。
尖落在前进方向那一侧、端头留在另一侧——**两个方向就是把这一对 x 对调**。

第一版把端头命名成了 `tipX`，起笔点走端头位置，结果 `LeftToRight` 画出来是**朝左**的
（契约与实现整体相反，详见第四节）。

**命名纪律**：`Segments[0]` 的**终点**是尖，**起笔点 / 收笔点**是端头；
朝向断言比这两者的 x 大小，**不写死数值**。

## 三、本批修掉的两个问题

两个都不是"编译不过"这类硬报错，而是**跑起来才露头**的东西。

### ① 管道箭头采样伪失败：决定描边线宽的是**短边**

- **症状**：`dotnet run` → 726 通过 / 1 失败，
  `管道：运行态箭头被真的画上…` 采到 `#FF35C158`，期望 `#FF34C759`。
- **根因**：管道可见部分是**描边**不是填充。第一版 `[X]` 装配把管道设成 320 × 64，
  **只把宽度翻倍、短边仍是 64** → 箭头线宽 `64 × 0.10 = 6.4` 设计像素 → 乘 `Zoom = 0.4`
  后只剩 **2.44 设备像素**，采样点踩在抗锯齿边上，混进约 4% 管身灰 `#3A3A3A`
  → `Distance` 正好 = 8，卡在 `SameColor` 阈值（`< 8`）上，红绿全看运气。
- **修**：`[X]` 装配把管道改为 **640 × 128**——**宽高一起给**，短边也翻倍，线宽回到 5 设备像素。
  采样公式全部由 `pipe.Width / pipe.Height` 反推，自动跟上。

> **账要记住**：缩放后的线宽 = `短边 × 比例 × Zoom`。放大一个"描边型"图元时，
> 只放大长边是没用的——短边才决定线宽。采样点必须落在**笔画正中心**，
> 离两侧边缘至少一个多像素，才不会被抗锯齿混色骗过去。

### ② 管道箭头朝向整体反向（**真缺陷**，靠离屏证据图抓出来）

- **症状**：727 全绿之后**读离屏证据图** `artifacts/scada-canvas-render.png` 发现——
  `Direction` 默认 `LeftToRight`，但箭头画成**朝左**（`<`）。
  **断言全绿却没拦住它**：原来那两条朝向断言把"端头"当成了"尖"，断言语义本身是反的。
- **根因**：`BuildArrows` 里名为 `tipX` 的其实是两个**端头**，真正的尖角落在 `centerX`。
  起笔点走了端头位置，于是两个方向整体对调 → 契约与实现相反。
- **修**（[PipeElement.cs](file:///e:/VM/VisionMaster-W-master/Scada.Controls/Elements/PipeElement.cs) `BuildArrows`）：
  新增 `tailX`（端头），`StartPoint` / 收笔点用 `tailX`，`Segments[0]` 的尖角用 `tipX`。
- **同步修断言**：
  - `[S]` 两条朝向断言语义修正——改用 `Segments[0].Point.X` 与 `StartPoint.X` 比大小；
  - `[X]` 采样点公式修正——"上端头 → 尖"斜边中点即 `(箭头中心 x, 管中心 y − 半高/2)`，
    箭头序号位置也改按控件同一条公式现算，不写死 1/4。
- **影响面**：`Grep RightToLeft|PipeFlowDirection` 确认仅 `PipeElement.cs` 本体 + 断言 +
  `BuiltInElements.cs:1109-1110`（`Choices` / `Description` 文字，与新行为一致），**无其他依赖**。

> **方法学教训**：**证据图不参与判定，但它是发现"断言钉不住的真缺陷"的唯一途径。**
> 本批的朝向 bug 正是靠"727 全绿后仍去读证据图"才抓出来的。
> 断言能证明"你想到的都对"，证明不了"你没想到的"。

## 四、`.vms` 往返断言（s7-12 / s7-13）

### 需求

路线图行 188-190 有一条硬要求：每个图元必须**一次交付完整**（描述符 + 控件 + 模板 + 默认值 + **`.vms` 往返断言** + 工具箱分类），
**不许出现"先画出来，属性以后补"**。

第一批的已知边界 7 明说欠着：`.vms` 往返断言未含 `Hmi.Gauge` / `Hmi.Valve`。
本批先连同三个新图元一起补上——**五个图元、60 条属性**（s7-12）；
收尾时自我识别出"这套做法本就是通用的"，于是**再往前一步扩到全部 14 个内置图元、141 条属性**（s7-13）。

### 做法：探针值逐键对账，而不是挑一两条手工钉

属性袋是纯字符串字典，**序列化层不认识任何业务键**（它只负责搬运），
所以"漏没漏"不能靠"我记得写过了"，只能靠**穷举**：

1. 遍历 `ElementRegistry.All` 里**每一个已注册图元**的描述符，
   对**每一条非几何属性**按 `Kind` 生成一个可辨认的探针值：

   | Kind | 探针 |
   |---|---|
   | `Color` | 固定 `#FF1A2B3C` |
   | `Number` | 量程内 37.5% 处（与默认值重合就换 62.5% 处）——**越界值会被控件夹取，就测不出"存的是我写的那个"** |
   | `Bool` | 默认值的反面 |
   | `Choice` | 第一个不等于默认值的候选 |
   | `Text` / `MultilineText` | 固定 `往返探针` |

2. 写进模型 → 保存 `.vms` → 加载 → 逐键 `ElementValueAccess.Read` 对账。
3. 顺带钉**属性袋键数 = 描述符声明的非几何属性数**：
   少一条说明"声明了却写不进去"，多一条说明有两条属性共用了同一个键。

**名单从注册表全量取，不写死数组**（s7-13 的改动就一行）：

```csharp
string[] probeTypes = ElementRegistry.All.Select(d => d.TypeKey).ToArray();
```

这样新增图元时这条断言自动覆盖它，不必记得回来补一行数组——
"靠记得"正是这类覆盖型断言最常漏的地方。

### 关键一条：探针有效性自检

**探针必须与描述符默认值不同**。否则"整条属性被漏掉"也会读到默认值，
逐键往返那条断言就退化成一个**永远绿的摆设**——这类"断言自己失效了却还是绿的"比断言红掉更难发现。

所以单钉一条元断言：遍历全部 14 个描述符的 141 条属性，逐条确认探针 ≠ 默认值。
将来谁加了一条默认值恰好撞上探针的属性，这条会先红，而不是悄悄削弱往返覆盖。

### 第二条元断言：探针覆盖面

还有一类"测不到"比"测不准"更隐蔽：某个图元**一条属性袋键都没有**（描述符只剩几何属性），
它在上面几条里会一路绿着走过去，却什么也没证明。所以另钉一条：
**每个已注册图元都至少有一条可探的属性袋键**。

### 新增断言（`[O]` 段 6 条）

| 断言 | 钉住什么 |
|---|---|
| 探针有效性 | 141 条属性的探针全部与默认值不同（元断言） |
| 探针覆盖面 | 14 个图元每个都至少有一条可探属性袋键（元断言） |
| 带全属性探针的方案保存成功 | 落盘这一步不抛 |
| 带全属性探针的方案加载成功 | `$type` 白名单未挡下 |
| 逐键往返：每一条声明出来的属性都原样回来 | **主断言**（含流向 / 状态 / 三个状态色 / 全部基础件属性） |
| 往返后类型键不变 | 14 个类型键各回一条，没被改名或合并 |
