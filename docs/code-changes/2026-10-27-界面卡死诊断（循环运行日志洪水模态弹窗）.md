## 2. 已做

### 2.1 排除了三类常见误判

| 假设 | 反证 |
|---|---|
| 死锁（线程全在 Wait） | 3 秒 CPU 涨 24.6s、10 秒涨 90.6s，**有 8~9 个线程在 Running/Ready**，不是等锁 |
| 内存爆炸 / OOM | 工作集 831→834MB 稳态；`_pendingFrames` 按 (流程,窗口) 合并，长度被 7×窗口数封顶 |
| UI 线程被硬阻塞 | `WM_NULL` 往返 11~15ms，消息泵正常 |

### 2.2 定位到三条叠加成因

**成因 ①（直接原因，主界面「点什么都没反应」）：一个模态弹窗把主窗口置灰。**
`读取PCB散焦图像` 是步骤参数弹窗，`ShowDialog` 期间主窗口 `IsWindowEnabled = False`。
此状态下点击主界面**不会产生任何反馈**（不是慢，是根本不进消息处理），用户感知就是"卡死"。
弹窗本身是活的（ping 15ms），只是没人去点它的「取消」。

**成因 ②（把 UI 线程压满）：约 1000 条日志/秒，每条都往 UI 线程投一个 Normal 优先级动作。**
`VisionMaster\ViewModels\LogViewModel.cs:164`：

```csharp
logService.OnLogReceived += (log) => SafeDispatch.BeginInvoke(() => AppendWithCap(log));
```

`AppendWithCap`（同文件 189-197）对**每条**日志做 `ObservableCollection.Add` + `while (Count > max) RemoveAt(0)`，
上限 `DefaultLogPanelMaxRows = 5000`（`Core\Models\AppConfigModel.cs:832`）。即：
**1000 次/秒的集合增删 + 1000 次 CollectionChanged + ListView 逐条位移**，
且走的是 **Normal 优先级（高于 Render/Input）**——正是 `ImageCollectionService` 注释里点名的
"Normal 洪水饿死重绘与输入"那个坑（`ImageCollectionService.cs:118-121`），日志面板这一侧还没做同样的合并。

**成因 ③（持续压着 UI 线程）：图像集按「来帧速率」往 UI 提交，没有提交速率上限。**
`ImageCollectionService` 的合并队列只把**队列长度**封顶到 (流程,窗口) 数，**没有封顶提交速率**：
`DrainPendingFramesCore`（505-561）每轮取走整批并逐帧 `CommitFrame`，只要来帧快于 UI 提交速度，
排空动作就会一直重排（`ScheduleUiDrain`），UI 线程永远不空闲。
7 条流程合计约 860 帧/秒 → UI 线程被这一项吃掉大半（实测总占用 73%）。

**触发源**：22:53:32 用户对 7 条样例流程同时发起「循环运行」（`MainRunState.RunningContinuous`），
无节拍间隔、无轮次上限，跑到现在（23:03）已 10 分钟、每流程数千圈。

### 2.3 已确认可用的恢复动作（未代替用户执行）

- 关掉模态弹窗（点「取消」）→ 主窗口立即恢复可点（23:02 实测已恢复 `Enabled=True`）。
- 点工具栏「停止」→ `ShellViewModel.StopAll`（`ShellViewModel.cs:2255-2268`，StopAll 语义：界面运行/单流程/HTTP 触发一起停）→ 日志洪水与 CPU 占用同时归零。

## 4. 下一步（按性价比排序）

1. **日志面板合并投递**（对应成因 ②，改动最小、收益最大）：
   把 `LogViewModel.cs:164` 的"每条一个 `BeginInvoke`"改成"进一个待刷队列 + 定时器（~10Hz）批量 Append"，
   或给 `OnLogReceived` 加节流；追加仍走 `AppendWithCap` 的纯函数形态（断言已钉住它）。
2. **图像集提交限速**（对应成因 ③）：排空时若"上一轮刚提交完 < N ms"，直接丢掉中间帧只留最新，
   用时间片而不是"能提交多少提交多少"。
3. **循环运行加节拍上限/轮次上限**（对应触发源）：`循环运行` 至少给个"最小轮间隔"，
   避免 7 条流程空转把机器吃满；对拍场景应走"运行一次"或带间隔的循环。
4. 给本机装 `dotnet-dump`，下次这类现场直接 `dotnet-stack` 抓栈，不再靠推断。

## 5. 踩过的坑

1. **`Process.Responding == True` 不等于界面能用**。它只证明"UI 线程在泵消息"；
   模态弹窗把主窗 `IsWindowEnabled` 置 `False` 时，主界面照样"点什么都没反应"，而 `Responding` 仍是 `True`。
   → 判"主界面能不能点"要看**主窗口的 `IsWindowEnabled`**，并枚举进程可见窗口找模态子窗。
2. **运行中进程的日志文件读不了也测不准**：`[IO.File]::ReadAllLines` 抛 `IOException`（独占锁）；
   `Get-Item`/`Get-ChildItem` 拿到的 `Length`/`LastWriteTime` **是陈旧的**（实测 22:23 而文件已写到 22:58）。
   → 一律 `FileStream(..., FileShare.ReadWrite)` 打开，长度也从这个句柄取。
3. **WPF 窗口没有子 HWND**：`EnumChildWindows` 对 `HwndWrapper[...]` 返回 **0 个**，
   读不到任何按钮文本。→ 读 WPF 弹窗内容必须走 UI Automation（`AutomationElement.FromHandle` + `TreeWalker`）。
4. 本会话的 bash 工具实际是 `cmd.exe`：`;`、`head`、`echo` 串联全部失效（报"不是内部或外部命令"）。
   → 一条命令只做一件事，PowerShell 用 `powershell -NoProfile -Command "..."` 单条包起来。

## 7. 本轮实施（2026-10-27 23:14–23:33）

用户确认「开工」后按 §4 的顺序落地了三条改动，另加一条同源缺陷的修复。

### 7.1 日志面板：逐条投递 → 10Hz 批量投递

`VisionMaster\ViewModels\LogViewModel.cs`

| 项 | 改法 |
|---|---|
| 投递 | `OnLogReceived` 不再 `BeginInvoke(AppendWithCap)`，改为 `EnqueueLog`：进 `_pendingLogs`（锁保护，上限 20000，超了丢最旧并记账） |
| 起表 | `ScheduleFlush()` 用 `Interlocked.Exchange(ref _flushScheduled, 1)` 保证"洪峰 1000 条/秒只产生 1 次 Dispatcher 投递"；起表动作经 `SafeDispatch` 送回 UI 线程（`DispatcherTimer` 有线程亲和性） |
| 节拍 | `DispatcherTimer(Background, 100ms)`；队列排空即 `Stop()`，无日志时零开销 |
| 批量 | 每次最多取 500 条（`MaxBatchPerFlush`），走新加的 `AppendBatchWithCap`：先全部 `Add`，再**一次性**裁到上限 |
| 计数 | 批量期间 `_batchDepth > 0` → `OnSystemLogsChanged` 只做增量计数，收尾统一 `RaiseFilterCounters()` 一次（否则 500 条要重算 500 遍 O(n) 筛选） |
| 契约 | `AppendWithCap`（逐条）**一字未改**，仍是上限语义的单一事实源；批量版与它逐字等价 |
| 无宿主 | `Application.Current == null`（断言宿主/设计器）时直接同步排空，行为与改造前一致 |
| 丢条 | 只在队列排空时补一条汇总，且**直接写集合、不经 LogService**（否则"报告洪水"本身又制造一条洪水） |

### 7.2 图像集：提交速率限速

`VisionMaster\Services\ImageCollectionService.cs`

- `DrainPendingFramesCore` 从"连排最多 4 轮直到排空"改为**一次只提交一批**；提交完若仍有积压，
  记 `_nextCommitAllowedTick = now + 50ms`（`MinCommitIntervalMs`，20Hz）并交回调度。
- `ScheduleUiDrain` 在限速窗口内改走 `ScheduleDelayedDrain`（`Task.Delay` + `BeginInvoke(Background)`，
  `_delayedDrainScheduled` 保证同时只有一个），不再"每来一帧就立刻重排"。
- **headless 分支保持同步、不受限速影响**：断言宿主没有消息循环，`[UI3]` 判的是"恢复排空后立刻可读"。
- 语义不变：窗口内到达的帧仍由合并队列按 (流程,窗口) 顶掉，只留最新一张。

### 7.3 运行锁：入树时补种运行态（修「循环运行中双击算子仍弹参数窗」）

根因：`GlobalEventBus` 是纯转发、**不缓存最后一条消息**（`Shard\Core.Controls\Events\GlobalEventBus.cs`），
而 `EditGate` 的订阅随面板挂/摘反复 `Activate`/`Deactivate`（AvalonDock 隐藏面板、切标签、组态设计态收敛都会走
Unloaded）。离树期间发生的 `RunningContinuous` 就永远收不到，重新入树后 `_runState` 停在 `NotStarted`
→ `ModuleParameters` 放行 → 双击算子弹出 `PluginConfigShell` 模态窗 → 主窗口 `IsWindowEnabled=False`。

改法：
- `EditGate` 新增静态镜像 `LastPublishedRunState` + `PublishRunState(...)`；
  `Activate()` **先补种再订阅**（值有变化时补发 `RunStateChanged`，画布横幅等绑定面跟着刷新）。
- `ShellViewModel.RunState` 的 setter 在 `GlobalEventBus.Publish(value)` 旁边同步写镜像。
