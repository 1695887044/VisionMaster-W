# 启动链路收口：配置先加载 + AutoStart 生效 + 非阻塞建连（t7）

日期：2026-09-17
主线：通信流程重构 —— t7「启动链路上的加载/连接/自检时机修正」

## 一、需求与决策

### 需求
t6 把 Manager 的 I/O 全部改道到 `ConnectionWorker`（每连接一个专属线程），但**启动链路**仍是旧的：
配置在 `ShellViewModel` 构造函数里才异步加载、`AutoStart` 没有任何人消费、自检可能把软件"判死"、
启动会被离线设备串行冻结。t7 的目标是让"软件启动 → 通讯子系统就绪"这条链路自洽、可预期、不阻塞。

t7 定位出的 4 个真实缺陷：

| 编号 | 现象 | 根因 |
| --- | --- | --- |
| **B8** | 通讯自检永远报"无通讯配置" | 配置加载发生在 `ShellViewModel` 构造函数（`App` 里 **L86** `Container.Resolve<Shell>()`），而自检链在 **L75** 就跑完了 —— 自检看到的是空列表 |
| **B9** | 配了"自动启动"却从不连接 | `ConnectAll()` 全仓库只有 `StartAll()` 调用，而 `StartAll()` **没有任何人调用**，`AutoStart` 是个死配置项 |
| **B10** | 设备离线时软件卡启动，甚至直接退出 | `ConnectAll()` 逐条同步等 `Config.TimeoutMs`（默认约 3s），N 条离线 → 串行冻结 3N 秒；叠加自检链**单项硬超时 30 秒且判 Error 级会自动 `Environment.Exit(2)`** |
| **B11** | 启动时序不确定（间歇性自检误报） | 建连是异步的，自检立刻判"不可达"，没有给自动连接留追赶时间 |

### 关键决策
| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 配置加载时机 | **前移到 `CommunicationModule.Initialize`**（同步 `LoadConfig()`） | 模块初始化在自检注册/执行**之前**（`App` L52-53 vs L55-75），且早于 `Shell` 构造。此处只有几 KB 本地文件读取，同步完成反而消除了 UI 线程 `await` 带来的时序不确定；同时删掉 `ShellViewModel` 里的加载，避免"两处都能加载配置"的真相源分裂 |
| 自动连接入口 | `CommunicationModule.Initialize` 里调 `manager.StartAll()` | 模块初始化是"启动装配"的唯一责任点，模块自声明比在 App 里散落调用更好维护 |
| `StartAll` 建连方式 | **非阻塞发起**（用户拍板）：`_ = worker.Connect(0)` | `timeoutMs=0` 只登记"维持连接"意图（`_autoConnect=true` / `_reconnectAttempt=0` / `_nextConnectTick=0`）立即返回，真正 socket 建连由连接专属线程做，状态经 `StateChanged` 广播。调用方（启动链路）绝不会被离线设备阻塞 |
| `ConnectAll` 内是否仍逐条 `ConfigureWorker`+`RebuildPollPlan` | 保留 | 这两步是纯本地计算（灌参数、编译批量计划），不含 I/O，保留可让 Worker 一被唤醒就能用正确参数与轮询计划工作 |
| 连上时是否重编译轮询计划 | **新增**：`OnWorkerStateChanged` 中 `Connected` → `RebuildPollPlan` | `RegisterVariable` 只在 `IsConnected` 时立即编译，否则推迟到"建连时"；t7 把建连改成后台异步后，"建连时"的唯一可靠落点就是状态回调。否则在"已登记连接意图但尚未连上"期间注册的变量会**静默不参与轮询** |
| 自检等待策略 | 两段式：先 `SettleWindowMs = 3000` 追赶窗口，再逐条实测 | 给异步建连留出收敛时间，消除 B11 的间歇性误报 |
| 自检实测预算 | **总预算 `TestBudgetMs = 12000` + 单条 `PerTestTimeoutMs = 3000`** | 硬性保证自检耗时远离 30 秒硬超时，绝不触发 `Environment.Exit(2)`；超预算的连接记"未在检测预算内完成"而非"不可达" |
| 已连上的连接在自检里 | 直接计成功，**不再打设备** | `TestConnection` 对活连接本就短路返回 `true`，等价但省一次跨线程投递 |
| `IsRunning` | **保持 `StartAll/StopAll` 手工置位**（明确不改） | 真实连接实况由 `ConnectedCount` + `config.State` 表达；再引入"派生 IsRunning"属过度设计 |
| 主窗口构造与建连日志顺序 | `AdvancedCommunicationManager.LogSink` 挂接**提前到模块初始化之前** | 启动装配（加载配置 + 发起自动连接）产生的日志也必须进 UI 日志窗口，否则这段最容易出问题的时序是"黑洞" |

### 1. `AdvancedCommunicationManager`（5 处）

**(a) 同步 `LoadConfig()` + 私有 `ApplyConfigJson(json)`，`LoadConfigAsync` 退化为薄包装**

```csharp
public void LoadConfig()
{
    if (!File.Exists(ConfigFilePath)) { LogInfo($"配置文件不存在: {ConfigFilePath}"); return; }
    try
    {
        LogInfo($"正在加载配置: {ConfigFilePath}");
        ApplyConfigJson(File.ReadAllText(ConfigFilePath));
    }
    catch (Exception ex) { LogError("加载配置失败", ex); throw; }
}

public async Task LoadConfigAsync()
{
    await Task.Run(LoadConfig).ConfigureAwait(false);
}

private void ApplyConfigJson(string json)
{
    var configs = JsonConvert.DeserializeObject<List<CommunicationConfig>>(json, _configJsonSettings);
    if (configs == null) { LogInfo("配置加载完成: 文件内容为空"); return; }
    foreach (var config in configs)
    {
        try { AddConnection(config); }
        catch (Exception ex) { LogError($"加载连接配置失败: {config.ConnectionName}", ex); }
    }
    LogInfo($"配置加载完成: 共加载 {configs.Count} 个连接");
}
```
- 新增同步入口是 t7 的**核心前置条件**：启动链路是同步的（模块初始化 → 自检 → `Shell`），需要一个可同步调用的加载入口
- `ApplyConfigJson` 抽出的意义：单条配置损坏只记日志、不影响其余连接，两条加载路径行为完全一致

**(b) `StartAll` 补文档注释（行为未变）**：明确"建连不在此等待（见 `ConnectAll`），调用方不必担心被离线设备阻塞"。

**(c) `ConnectAll()` 改为非阻塞发起**

```csharp
public void ConnectAll()
{
    var enabledConfigs = new List<CommunicationConfig>();
    lock (_connectionsListLock)
        enabledConfigs = _connectionsList.Where(c => c.IsEnabled && c.AutoStart).ToList();

    if (enabledConfigs.Count > 0)
        LogInfo($"{enabledConfigs.Count} 条连接标记为自动启动，正在后台建立连接");

    foreach (var config in enabledConfigs)
    {
        if (!_workers.TryGetValue(config.ConnectionName, out var worker)) continue;
        try
        {
            ConfigureWorker(worker, config);
            RebuildPollPlan(config.ConnectionName);
            // timeoutMs = 0：只登记连接意图立即返回，不阻塞调用线程（结果由状态机与事件上报）
            _ = worker.Connect(0);
        }
        catch (Exception ex) { LogError($"启动连接失败: {config.ConnectionName}", ex); }
    }
}
```
- 旧实现逐条 `Connect()` 等 `Config.TimeoutMs` → 现场 8 台设备全离线时启动冻结 24 秒，且发生在 Splash 显示之前，用户只看到"点了没反应"
- 非阻塞后 `ConnectAll()` 是**纯内存操作**（快照列表 + 灌参数 + 编译计划 + 登记意图），耗时与设备数量无关

**(d) `OnWorkerStateChanged` 在 `Connected` 时补 `RebuildPollPlan`**

```csharp
// 连上即重编译轮询计划：变量可能在"已登记连接意图但尚未连上"期间注册
// （RegisterVariable 只在 IsConnected 时立即重编译，否则推迟到"建连时"），
// 这里是"建连时"的唯一可靠落点，否则那批变量会静默不参与轮询
if (newState == ConnectionState.Connected)
    RebuildPollPlan(connectionName);

OnConnectionStateChanged(connectionName, oldState, newState);
```
- 这是 (c) 的**配套修复**，二者必须同时存在；只改 (c) 会引入"启动期注册的变量永久不被轮询"的隐性 bug

**(e) 只读确认、未改**：`IsRunning { get; private set; } = false` 仍由 `StartAll/StopAll` 手工置位。

### 2. `CommunicationModule.Initialize`（启动装配唯一入口）

```csharp
var manager = container.Resolve<AdvancedCommunicationManager>();

// ===== 启动装配：必须在"自检链执行"与"Shell 构造"之前完成 =====
try
{
    manager.LoadConfig();      // 同步恢复 communications.json
    manager.StartAll();        // 按 AutoStart 非阻塞发起自动连接
}
catch (Exception ex)
{
    // 配置文件损坏不应阻断软件启动：记录后按"无通讯配置"继续，用户可在通讯设置里重建
    container.Resolve<ILogService>().Error($"[Comm] 启动装配失败，本次按无通讯配置运行：{ex.Message}");
}

lifetime.RegisterExitTask(ExitTask.Of("断开通讯连接", () =>
{
    manager.StopAll();
    manager.DisconnectAll();
}));
```
- 配置损坏**兜底不阻断启动**：通讯是可选子系统，不该让整个软件起不来

### 5. `CommunicationCheck`（时机 + 预算）

三个常量：`SettleWindowMs = 3000`、`TestBudgetMs = 12000`、`PerTestTimeoutMs = 3000`。

```csharp
// 放进线程池：TestConnection 可能阻塞，绝不能占住启动 UI 线程
return await Task.Run(async () =>
{
    var manager = _managerFactory();
    var configs = manager.ConnectionsList;
    if (configs.Count == 0) return CheckResult.Ok("无通讯配置");

    // 1) 追赶窗口：自动连接的建连是异步的，不等这一小段时间会把"正在连"误报成"不可达"
    if (configs.Any(c => c.State != ConnectionState.Connected))
        await WaitAllSettledAsync(configs, SettleWindowMs, ct);

    // 2) 仍未连上的逐条实测（TestConnection 对已连上的连接直接返回成功，不会打断活连接）
    long deadline = Environment.TickCount64 + TestBudgetMs;
    var problems = new List<string>();
    int ok = 0;

    foreach (var config in configs)
    {
        if (config.State == ConnectionState.Connected) { ok++; continue; }
        if (Environment.TickCount64 >= deadline)
        {
            problems.Add($"{config.ConnectionName}(未在检测预算内完成)");
            continue;
        }

        bool reachable;
        var task = Task.Run(() => manager.TestConnection(config.ConnectionName), ct);
        try { reachable = task.Wait(TimeSpan.FromMilliseconds(PerTestTimeoutMs)) && task.Result; }
        catch { reachable = false; } // 超时/异常均按不可达处理

        if (reachable) ok++; else problems.Add($"{config.ConnectionName}(不可达)");
    }

    int total = configs.Count;
    return problems.Count == 0
        ? CheckResult.Ok($"{ok}/{total} 条连接正常")
        : CheckResult.Fail(CheckLevel.Warning, $"{ok}/{total} 条连接正常，异常：{string.Join("、", problems)}");
}, ct);
```
- 结果仍为 `CheckLevel.Warning`：通讯不可达**不该**终止软件启动
- `WaitAllSettledAsync`：每 100ms 轮询，全部连上提前返回，`ct` 取消时静默返回

## 四、已知边界

1. **`IsRunning` 仍是手工置位**，未与 Worker 实际状态挂钩。真实连接实况请看 `ConnectedCount` 与 `config.State`。
2. **B5 协议选项不一致未修**（欧姆龙/三菱/OPC UA 选了点"添加"抛 `NotSupportedException`）—— 用户明确决定不改。
3. **`ConnectionSettingsViewModel.ExecuteTestConnection` 仍直连 `connection.Connect()/Disconnect()`**、
   **`NetworkVariableModel.TryWriteToValue` 仍直连 `connection.Write`**（绕过 Manager/Worker 队列），均在 t8 收口。
4. **自检时间上界**：最坏耗时 ≈ `SettleWindowMs`(3s) + `min(N × PerTestTimeoutMs, TestBudgetMs)`(≤12s) = **约 15 秒**，
   远离自检链单项 30 秒硬超时。但**总时长仍与"待实测连接数"线性相关**（预算内每条最多 3s），
   若现场配置了几十条不可达连接，自检会稳定停在 ~15 秒。
5. **非阻塞建连的"无返回值"语义**：`ConnectAll()` 与 `StartAll()` 不再告诉调用方"连上了没有"，
   需要结果只能订阅 `ConnectionStateChanged` 或轮询 `config.State`。启动自检是唯一的等待方。
6. **多线程可见性**：`config.State` 由 Worker 线程写、UI/自检读，标量属性绑定 WPF 会自动调度到 UI 线程；
   但**不要**在 Worker 线程上对 `ConnectionsList` 做集合变更（会崩），现有代码未这么做。
7. **未做运行期实测**：本次仅编译验证。"8 台离线设备启动是否秒开""启动后 3 秒内自检结果是否正确""连上后启动期注册的变量是否真的被轮询"需现场跑设备确认。
