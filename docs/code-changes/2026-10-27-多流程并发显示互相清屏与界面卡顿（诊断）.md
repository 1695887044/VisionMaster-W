# 多流程并发显示互相清屏与界面卡顿（诊断，2026-10-27）

## 一、当前状态

现场现象：流程 A 循环运行、结果显示投到图像窗口 1；过一段时间流程 B 也循环运行、投到图像窗口 2
→ **界面卡住**，且**窗口 2 的画面被 A 影响**（反复被清空 / 不跟随 B 的最新帧）。

本轮结论（**代码 + 磁盘配置取证，未启动 VisionMaster.exe 复验**；影响面为 grep/read 结论，非索引结论）：

1. **主因 1（窗口互相影响）**：本机 `AppConfig.json` 里 `ImageGallery.RunStartMode = 0`（= `ClearAll`，
   每轮开始「清空整张画布」）。这个口径是**画布级**的，不是"流程级 / 窗口级"：任一流程每开一轮都登记一次
   "清空全部"，下一条**来自任一流程**的帧到达时，把集合里**所有窗口**的帧连同图像副本一起清掉。
   A、B 同时循环 ⇒ 两个窗口轮流把对方清空。
2. **主因 2（界面卡住）**：清空与插帧都封送到 UI 线程，且用的是 `DispatcherPriority.Normal`（9）。
   每次选中帧变化要跑 **2 次整幅 `RenderAll`**（`HImage` 与 `Annotations` 两个 DP 各触发一次）；
   清空后旧图已被释放，还会多走一次 `SetFullImagePart` 全幅铺满。两条流程并发后 UI 线程的
   Normal 队列排不空 → Input(5) / Render(7) 被饿死（Normal 优先级高于它们）→ 界面表现为"卡住"。
3. **并发口径缺陷（即使改回 `ReplaceFlow` 也仍在）**：`ImageCollectionService._currentFlowName`
   是**单例全局**的"当前流程"，A/B 并发时按"最后开轮的那条流程"给帧归属 →
   `ReplaceFlow` 的"只清本流程"会清错流程的帧。

## 二、已做（证据链）

### 链路 1：为什么"图像 2 会被 A 影响"

1. 两条流程各自 `RunSessionAsync` 起一个 `Task.Run` 循环，**每轮**都广播一次 `FlowRunStarted`
   （`Engine\FlowEngineService.cs:439-475`，广播点 `:462`）。
2. `ImageCollectionService.OnFlowRunStarted`（`VisionMaster\Services\ImageCollectionService.cs:343-365`）：
   - `:347` 把 `_currentFlowName` 写成"刚开轮的这条流程"（**全局单值**，`:98` 声明为 `volatile`）；
   - `:354-364` 按 `RunStartMode` 登记待清空：`ClearAll` → `_pendingClearAll = true`；
     `ReplaceFlow` → `_pendingClearFlows.Add(flowName)`。
3. 任一流程发布一帧 → `Capture`（`:529-573`）在发布线程上先拷贝，再 `RunOnUi` 到 UI 线程；
   UI 线程里 `:568` 先 `ApplyPendingClearFor(frame.FlowName)` 再插帧。
4. `ApplyPendingClearFor`（`:371-398`）：
   - `clearAll == true` → `:390-394` 调 `Clear()`；
   - `Clear()`（`:140-149`）对**整个 `_frames`** 做 `Clear()`，不区分流程、不区分 `ViewIndex`。
   ⇒ 本机 `RunStartMode=0` 时，**A 的一轮开轮登记 + B 的第一帧到达 = 整张画布被清空**，
   窗口 2 里 B 的上一帧连同 HImage 副本一起被释放。A 每轮都登记，于是窗口 2 被 A 反复清空。
5. 即使把口径改回 `ReplaceFlow`，第 2 步的 `_currentFlowName` 仍是全局单值：
   A 开轮 → B 开轮 → A 发布时 `:547` 读到的是 `"B"`，帧被记成 B 的；
   随后 `ApplyPendingClearFor("B")` 把 **B 的帧（窗口 2）** 清掉（`RemoveFramesOfFlow`，`:762-770`）。
   同一个错误也会让"流程"归属标签、`PerFlowLimit` 分组（`:772-806`）一起错。
6. 触发这个口径的源头在 2026-10-26 的诊断记录里：
   `docs\code-changes\2026-10-26-图像窗口不跟随最新帧（诊断）.md:97-99` 把
   `RunStartMode=ClearAll` 当"临时规避"给出，并写明代价是"每跑一条流程就清掉其它流程的图"。
   本机配置正是这条规避（`VisionMaster\bin\Debug\net9.0-windows\AppConfig.json:36-48`，`RunStartMode: 0`）。

### 链路 2：为什么会"卡住"

1. 每发布一帧，`ImageCollectionService.RunOnUi`（`:838-847`）都用 `dispatcher.BeginInvoke(action)`，
   **默认优先级 = Normal(9)**。WPF 里 Normal(9) > DataBind(8) > Render(7) > Input(5)，
   所以 Normal 队列只要排不空，重绘和输入就永远排在后面。仓库自己已经记录过同类现象：
   `Core\Models\ProcessStep\StepModel.cs:240-243`（"每秒上万次跨线程通知…UI 光处理通知就排满了队"）。
2. 每帧的 UI 工作量（默认 `KeepInjectedHistory=false`，每格只留一张）：
   - 清空：`_frames.Clear()` → 每格 `ImageGallery` 收到 Reset → `QueueRecompute`
     （`Services\Core.Halcon\Controls\ImageGallery.cs:553-562`，同样是 Normal 优先级）→
     `Recompute` 里 `SetCurrentValue(SelectedFrameProperty, newest=null)`（`:606-622`）→
     `PART_Big.HImage` 绑定变 null → `HImageChangedCallBack` 走 `ClearWindow()`。
   - 插帧：再选最新帧 → `HImage` 变化 → `HalconBase.HImageChangedCallBack`
     （`Services\Core.Halcon\Base\HalconBase.cs:245-314`）→ `RenderAll()`；
     由于旧图已被 `Dispose`（`IsInitialized()==false`），`:265-301` 判成"尺寸变了" →
     `TryRestoreViewPart`/`SetFullImagePart` + 再 `RenderAll()`（两次整幅绘制）。
   - 同一帧的 `Annotations` 绑定也会变（`Themes\ImageGallery.xaml:74-79` 两个绑定都挂 `SelectedFrame`）
     → `Annotations` DP 回调再 `RenderAll()` 一次（`HalconBase.cs:1547-1549`）。
   ⇒ **每次选中帧变化 ≈ 2~3 次整幅 `ClearWindow + DispObj + InvalidateVisual`**。
3. 两条流程、每条每轮通常发 2 帧（采集 1 帧 + 结果显示 1 帧）：
   `Plugin.ImageAcquisition\ImageAcquisitionPlugin.cs:1128`、`Plugin.ResultDisplay\ResultDisplayPlugin.cs:729`。
   并发后清空次数翻倍，且**每次清空会让两个窗口都重画一遍**（一个清成空、一个画新帧）。
   一旦"每帧 UI 成本 > 帧间隔"，Normal 队列开始积压；积压的每个动作还各自钉着一张全幅 HImage 副本
   （500 万像素彩图约 15MB），内存与 GC 压力一起上涨 → 队列越积越长 → 界面彻底不响应。
4. 同一时刻两个窗口都活着：`Shell.xaml:1599-1601` 与 `RunCockpitView.xaml:225` 各挂一份 `ImageView`，
   每份 `ImageView` 建一套 `ImageGallery`，两份都绑同一个 `Frames` 集合 → 渲染工作量再乘一份。

### 链路 3：次要缺陷（不是本次主因，但会放大后果）

1. **泄漏**：`ImageView` 构造函数里 `GlobalEventBus.Subscribe<ImageCanvasChangeEvent>(e => ShowCanvas(...))`
   （`VisionMaster\Views\ImageView.xaml.cs:39`）**从不退订**；`ImageGallery` 对
   `Frames.CollectionChanged` 的订阅（`ImageGallery.cs:520-532`）也没有 `Unloaded` 退订。
   而 `LayoutHelper` 每次加载布局/切换方案都会 `new Views.ImageView()`
   （`Services\LayoutHelper.cs:136`、`:1588-1603`、`:1611-1639`）→ 旧实例被静态事件表钉住，
   其格子继续对每一帧跑 `Recompute`。加载几次布局就多几份幽灵格子。
2. **全局 HALCON 状态**：`RenderAll` 用 `HSystem.SetSystem("flush_graphic","false")`
   （`HalconBase.cs:1135`）再在末尾置回 `"true"`（`:1208`），这是**进程级**状态；
   中间任何一句抛异常都被 `:1213-1216` 的空 `catch` 吞掉，`flush_graphic` 会停在 `"false"`。
   同时 `OnControlUnloaded`（`:57-70`）没有把 `hWindow`/`hSmart` 置空，被泄漏的格子仍会拿失效窗口调
   `RenderAll` → 更容易走进"设了 false 却没置回 true"的分支。**是否真的导致其它窗口不刷新，
   需要运行期验证**（本轮未跑真机）。
3. **启动 B 时的一次性停顿**：`RunSingleFlowAsync`（`ViewModels\FlowListViewModel.cs:309-360`）在 UI 线程上
   同步走 `FlowSessionFactory.TryEnsureSession` → `FlowCompiler.Compile`。流程大时这一次编译就是一次
   明显卡顿；它只解释"点下循环运行那一下"，不解释持续卡住。

## 五、踩过的坑

- **`ClearAll` 是画布级语义**：`Clear()` 直接 `_frames.Clear()`，`ViewIndex` 只影响显示筛选，
  不影响清空范围。多流程并跑时它就是"互相清屏"。
- **2026-10-26 的临时规避变成了今天的现场**：那条记录把 `ClearAll` 当规避给出，代价原文写着
  "每跑一条流程就清掉其它流程的图"。诊断记录里的"临时规避"必须带失效条件，否则会被当成配置沿用。
- **`volatile` 不等于"每流程一份"**：`_currentFlowName` 保证的是可见性，不是归属正确性；
  并发场景下"最后写入者"就是错的。
- **Normal 优先级是 UI 假死的常见成因**：`Dispatcher.BeginInvoke(action)` 默认 Normal，
  比 Render/Input 都高。循环运行场景下必须考虑节流或降优先级。
- **两个 DP 绑同一个源会放大渲染**：`PART_Big` 上 `HImage` 与 `Annotations` 都绑 `SelectedFrame`，
  一次选帧变化触发两次 `RenderAll`，再叠加"旧图已释放 → 判成尺寸变化 → 第三次"。
