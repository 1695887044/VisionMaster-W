# 线序颜色检测流程（解决方案\线序检测.vms + C#脚本）

用户问「用已有的插件能不能做线序颜色检查」。查完结论是：**拼不出来，但能兜住**——
现有 20 个预处理算子全是「图进图出」，**没有任何一个能把像素变成颜色数值**，
链路上恰好断在「逐根取色」这一环。于是用一个 `C#脚本` 节点把取色、判色、比序列一次做完。

本轮交付一份可直接打开的 `.vms` 方案 + 一条端到端断言，把「能跑通」证明掉。

---

## 一、需求与决策

### 1. 需求

用户指令（逐字）：

> 「我给你个图片 你走本地采集 可以给我构建一个检测线序的完整流程吗 可以使用脚本」

样本图：`Image\颜色\cable1.png`（640 × 480，线束水平走向，右端一个 5 脚连接器）。

### 2. 现有节点的能力边界（调研结论）

| 环节 | 现有节点 | 能否覆盖 |
|---|---|---|
| 取图 | `图像采集` | 能 |
| 划检测区 | `ROI` | 能 |
| **逐根取色** | —— | **不能**（无任何算子输出颜色数值） |
| 判色 + 比序列 | `C#脚本` / `图像脚本` | 能（写代码） |
| 输出 / 记录 | `结果上报` `数据记录` `Excel导出` | 能 |

`图像预处理` 的输出端口只有 `Image` / `StepCount` / `ActiveCount` / `ActiveOperators`；
工具集里的 `数值比较` `数学计算` 只吃标量、喂不进图像。**缺口不在算法，在"像素 → 数值"这一步。**

### 3. 关键决策

| # | 决策点 | 结论 | 为什么 |
|---|---|---|---|
| 1 | 交付形态 | 直接给一份 `.vms` 方案文件 | 「完整流程」的字面含义；用户双击即可打开 |
| 2 | 采样方式 | **竖直扫一条线横切线束** | 线是弯的、会交叉遮挡，顺着线走极不可靠；垂直切一刀，切出来的顺序天然就是引脚顺序 |
| 3 | 分线依据 | **真实间隙**（不是颜色跳变） | 颜色分段会把相邻同色线并成一根；间隙是物理分隔，与颜色无关 |
| 4 | 单根取色 | **中位色**，且掐掉上下各 25% 边缘 | 平均值会被边缘混入的背景和高光啃掉一截 |
| 5 | 颜色判据 | HSV：先判「有没有颜色」，再按色相分色系 | 对打光强弱不敏感 |
| 6 | 红 / 玫红怎么分 | 色相 **+「蓝比绿大」双保险** | 两者实测色相只差 17°（344° vs 1°），单靠色相阈值太险 |
| 7 | 期望线序放哪 | 脚本顶部参数区常量 | 换产品改一行；也可以改成输入端口由上游喂 |
| 8 | 不合格怎么表达 | **不 `Fail`**，输出 `Result=false` + 日志 `Warn` | 保留下游步骤（上报 / 剔除）的执行权；想让它变红，脚本里留了一行注释说明改法 |
| 9 | 触发模式 | `TriggerMode = 0`（单次执行） | 样本图是静态的，连续运行只会空转刷日志 |


### 过程中真实踩到的 4 个坑（都已修）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 方案里 `ScriptText` 变成对象，脚本跑的是默认模板 | PowerShell 5.1 的 `ConvertTo-Json` 会把管道里的字符串包成 `{"value":...}` | 改用 `HttpUtility::JavaScriptStringEncode` 转义，再按 JSON 字符串字面量做定点替换 |
| 2 | `cannot convert from 'out HImage' to 'out HObject'` | `HOperatorSet.Decompose3` 的 out 参数是 **`HObject`**（Halcon 图形对象基类），不是 `HImage` | 声明 `HObject`，再 `new HImage(o)` 包一层（用完立刻 Dispose，避免 Halcon 句柄泄漏） |
| 3 | `Math.Round` 调用歧义（`decimal` vs `double`） | `HImage.GetGrayval(int,int)` 返回 **`HTuple`**，而 `HTuple` 同时能隐式转 `double` 和 `decimal` | 显式 `(double)` 落一次 |
| 4 | 只切出 3 根线（红、黄丢了） | 「洞 / 缝」阈值取 6 太大，而 **红\|黄 之间只有 4 行背景**，三根被并成一根 | 阈值降到 3；并给「线像素」判据补一条「极亮（V>240）算线」，兜住暗线上的镜面高光 |

## 四、已知边界

1. **采样线 X（`SampleX`）与产品/打光绑定**
   默认 430，是这张样本图上「线束最整齐、彼此分得最开」的那一列。换产品、换相机高度、换工装都要重新标定。
2. **`MinGap` 是「洞 / 缝」的分界，必须夹在两个数之间**
   要 **大于**线芯高光的最大宽度，**小于**线间的最小真实间隙。本样本上界是 4（红\|黄 的间隙），所以取 3。
   若某产品的线挨得更紧（间隙 ≤ 3 行），必须把 `MinGap` 再降。
3. **相邻同色线靠真实间隙分线**
   间隙够大就能分开；若两根同色线之间几乎无缝，会被并成一根——这是「按间隙分线」这一策略的固有代价。
4. **期望线序是脚本顶部的常量**
   当前写死 `黑,棕,玫红,红,黄`。要多产品切换，应改成输入端口（由上游或变量喂），本流程未做。
5. **只支持「线束被竖直一刀横切出一排」的形态**
   线有交叉、遮挡、或走向与采样线近乎平行时，这一刀切不出顺序。
6. **颜色只分到色系名，不分色号**
   输出是「黑/棕/玫红/红/橙/黄/绿/蓝/紫/白」这一级。同色系不同深浅（如深红 vs 浅红）区分不了。
7. **「白」和「灰」归为同一类**
   判据是「亮且不彩」→ 白；需要区分灰/白时得再加一档明度阈值。
8. **断言里钉死了黄金线序**
   `WireSequenceCheck` 把 `黑,棕,玫红,红,黄` 写成常量。换样本图（或改脚本阈值）后断言会红——
   这是刻意设计（当场发现分类漂移），但换图时要同步改断言。
9. **不合格不置红**
   脚本只输出 `Result=false` + 一条 `Warn` 日志。想让这一步直接变红，把脚本里
   `if (ok) Context.Success(detail); else Context.Warn(detail);` 换成 `if (!ok) Context.Fail(detail);`。
10. **灰度相机下退化**
    单通道图会把同一个值喂给 R/G/B，判色只剩「黑/白/棕」三档，色序检查失去意义——
    这条链路的前提是**彩色相机**。
