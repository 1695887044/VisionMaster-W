## 一、需求与决策

### 1. 需求

S11-b 交付后，报警在**引擎里**活了：变量越限会建记录、会排好序、会落盘。但现场打开画面**什么都看不见**——`ScadaAlarmEngine` 是宿主内部的一个字段，画布上的图元谁也够不着它。这一阶段要解决的是三件事：

1. **够得着**：运行态的那些"全局只有一份"的东西（引擎、节拍），怎么送到图元手里；
2. **看得见**：报警条长什么样、画什么、什么颜色、什么时候闪；
3. **不错位**：闪烁相位谁算、排序谁做、配色谁挑——三个"看着像模板该干"的活各自归位。

### 2. 决策清单（C-1 ~ C-4）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| C-1 | 工具箱分类 | 描述符 `Category = "报警"`，**新建一类** | 塞进"指示"那一组的话，找报警条要翻遍十几个同类项。报警是独立的一等工作，不是"一种指示" |
| C-2 | 装配位置 | `ScadaRuntimeHost.StartAlarms` 内、`Attach()`/`Start()` **之前** | 这两个调用一落地就可能抛事件，而订阅方是"装上上下文才订阅"的——先装包，订阅关系才赶得上第一条报警 |
| C-3 | 解装配位置 | `TeardownAlarms` **开头**、停节拍之前 | 订阅方比引擎先退场更符合因果；反过来的话，摘订阅就发生在引擎已经收场之后，读起来像对着尸体动手 |
| C-4 | 模板的职责边界 | 挑色 / 排序 / 闪烁相位**一概不做**：挑色归 `RebuildRows`、排序归引擎、相位归控件的只读属性 `BlinkOn` | 三件事都不属于"外观"：配色规则要跟整幅画面共用一套语汇（放模板里就得用转换器跨层取值，出错时静默显示成默认色）；排序是产品规则不是显示偏好；相位必须做成属性，因为**模板可被替换、控件拿不到模板内部元素** |

### 3. 关键设计：`ScadaRuntimeContext`（运行态上下文）

把"引擎 + 节拍"**打成一个包**，而不是给图元加两个属性：

| 理由 | 展开 |
|---|---|
| 引擎与节拍**同生共死** | 它们在 `StartAlarms` 里一起建、在 `TeardownAlarms` 里一起收。拆成两个属性注入，消费方就得处理"一个来了另一个还没来""一个走了另一个还挂着"这些组合状态；打包成一个对象之后，"有"就是都有、"没"就是都没，消费侧只剩一个分支 |
| 注入点**只开一次** | 今天只有报警条要它，明天趋势图、走马灯、状态栏都要（`ScadaBeatSource` 的类注释已经点了这几家的名）。每来一个消费者就改一次图元基类的接口，基类会变成杂物间 |
| 线程契约**有地方写** | `Beat` 跑宿主 UI 线程，但 `Alarms` 三个事件可能在变量轮询线程抛——这条契约写在类注释里，比散在每个消费方各自猜要好 |

注入链（宿主向下注入、控件**不反向抓画布**，与 `LayerVisibilityResolver` 同一范式）：

```
ScadaRuntimeHost.StartAlarms()
        │  window.CanvasHost.RuntimeContext = new ScadaRuntimeContext(engine, beat)
        ▼
ScadaCanvas.RuntimeContext  ──setter 遍历──▶  已存在的每个容器控件
        │                                      control.RuntimeContext = value
        │  CreateContainer() 新造容器时逐个补发
        ▼
ScadaElementBase.RuntimeContext ──setter──▶ OnRuntimeContextChanged(old, new)   ← 虚钩子
        │
        ▼
AlarmBannerElement：走人时退订阅，来人时挂订阅，末尾无条件补读一次
```

两处细节：

- **`ReferenceEquals` 短路**：`setter` 开头 `if (ReferenceEquals(_runtimeContext, value)) return;`。重复装同一个上下文不该挂出第二份订阅——一次事件触发两遍重读，行为上看不出来，代价是泄漏。
- **造完才装配那条路由**：`CreateContainer` 里逐个补发（宿主是在 `Show()` 之前装配的，那时容器一个都还没造）；`RuntimeContext` 的 `setter` 兜住"造完才装配/收场换人"这条。两条路都通，不需要额外的"补发一次"逻辑。

### 4. 本阶段修掉的缺陷

#### 断言自身缺陷：收场后订阅者没归零（**假红**）

- **症状**：`[AH3]` 段"收场后引擎与节拍的订阅者都回到零"失败，`beat=1 / engine=1`。
- **根因**：断言里造了两条报警条——`banner`（从头到尾挂在上下文上）与 `probe`（专测订阅成对）。收场时只摘了 `probe`，**`banner` 的上下文还挂着**，那 1 个节拍订阅 + 1 个引擎订阅正是它自己。
- **修复**：收场时按真实顺序补一句 `banner.RuntimeContext = null`（先摘上下文、再停节拍、再 `Detach` 引擎，与 `ScadaRuntimeHost.TeardownAlarms` 一致），并把引擎三个事件一并纳入断言。
- **性质**：这是**断言自己制造的泄漏**，不是产品缺陷——控件本身的订阅成对已经由 `probe` 那组断言钉住了。但这条假红值得留着，它反过来证明了断言确实在数订阅者。

## 二、为什么这么设计（逐条展开）

### 1. 为什么节拍相位必须由控件算、而不是模板动画

模板可以用 `Storyboard` 自己闪，代码更少。但那样有两个后果：

1. **每条报警条各闪各的**：`BeginTime` 取"模板加载那一刻"，一屏五条报警条的相位互不相同，看上去是"画面花了"而不是"报警在闪"；
2. **相位不可测**：断言里量不到 `Storyboard` 的当前值（无窗口环境下动画时钟不走），这条链就只能靠肉眼。

所以相位做成**只读依赖属性** `BlinkOn`，由控件从全画面共享节拍源的**累计时长**算：

```
bool on = (long)(elapsed.TotalMilliseconds / BlinkHalfPeriodMilliseconds) % 2 == 0;
```

发累计时长而不是"拍到了"信号（S11-b 的 B-2），是为了漏拍时只跳一下、不会永久错开。模板只把它翻译成 `Opacity`：

```xml
<MultiDataTrigger>
    <Condition Binding="{Binding IsFlashing, RelativeSource={RelativeSource TemplatedParent}}" Value="True" />
    <Condition Binding="{Binding BlinkOn,   RelativeSource={RelativeSource TemplatedParent}}" Value="False" />
    <Setter TargetName="AccentBar" Property="Opacity" Value="0.25" />
</MultiDataTrigger>
```

一个触发器就够，因为**不闪时 `BlinkOn` 恒为真**（`RebuildRows` 在不闪的分支里把 `_blinkOn` 归位为 `true`）。这条归位不是可选的：停在上一条的暗相位上，看着像"报警还在但变灰了"，比不闪更误导。

### 2. 为什么"只有严重且未确认"才闪

```
Critical + (Active | Recovered)  →  闪
Critical + Acknowledged          →  不闪（有人认领了）
Warning  + 任意状态              →  不闪
```

判据落在 `RebuildRows`：

```csharp
flashing = _active.Any(r => r.Severity == Critical && r.State.NeedsAcknowledge());
```

`NeedsAcknowledge()` 含 `Recovered`（"已恢复未确认"）——这时候不闪，等于告诉现场"没事了"，而实际上这条报警还挂在列表上等人认领。这条规则与 S11-a 的 `NeedsAcknowledge` 是同一个口径，没有第二份定义。

### 3. 为什么表头要同时报两个数

`"未确认 2 / 共 2"` 而不是只报总数。只给一个数，操作员判断不了**自己能不能走开**：

| 表头 | 操作员读到的 |
|---|---|
| `共 3 条` | "有 3 个问题"——但都是老问题还是刚冒出来的？ |
| `未确认 0 / 共 3` | "3 个都有人管了，可以走" |

实现上 `SummaryText` 由 `BuildSummary(count)` 算，`count == 0` 时返回**空串**（不是"共 0 条"）：一条都没有的时候表头右侧不该有任何字，那是空态的活（`EmptyText`）。

### 4. 为什么行是"快照 + 攥着来源记录"

`AlarmBannerRow` 是**不可变快照**（`Name`/`Detail`/`TimeText`/`StateText` 都是构造时算好的字符串），但保留 `Record` 引用：

- **快照**：行数据是"这一拍的样子"。直接绑 `ScadaAlarmRecord` 的话，`INotifyPropertyChanged` 会让每一行自己刷新——那意味着 N 行各刷各的，且刷新时机与整表重读不同步（排序会错乱）。
- **攥着 `Record`**：将来"点这一行去确认"要按它找回定义（`AlarmId`）。这条引用现在没用上，但**删掉就得改结构**，留着是零成本的。

行文本的换算规则（`BuildDetail` / `CompactStateText`）：

```
无触发值     →  "高高限 > 100（回差 5）"
有触发值     →  "高高限 > 100（回差 5）｜触发值 120"
状态短写法   →  激活 / 已确认 / 已恢复 / 正常
时刻         →  本地时刻 HH:mm:ss（等宽字体，一列对齐后"哪条先报的"一眼扫得出）
```

条件文案与 CSV 导出**共用同一份** `ScadaAlarmDefinition.ConditionText`——面板与文件各写一遍的话，现场会看到"界面上写 `>`、导出文件里写 `≥`"这种对不上的事。

### 5. 模板里两处刻意的写法

**① 文字属性设在外层 `Border` 上，靠继承往下传**

```xml
<Border TextElement.FontFamily="{TemplateBinding FontFamily}"
        TextElement.FontSize="{TemplateBinding FontSize}"
        TextElement.FontWeight="{TemplateBinding FontWeight}"
        TextElement.Foreground="{TemplateBinding Foreground}">
```

内部的 `TextBlock`（表头、行、空态提示）全都继承到。之所以不逐个 `TemplateBinding`：**`DataTemplate` 里没有 `TemplatedParent`**——嵌在 `ControlTemplate` 里的 `DataTemplate` 写 `TemplateBinding` 是取不到值的，这是 WPF 里最容易踩且**不报错**的坑之一。

**② 层级只靠"字重 + 透明度"区分，字号统一继承**

名字重、其余淡；字号不逐个写死。这样把 `FontSize` 调大给大屏用时，行高、徽标、时间会一起放大，不会出现"名字变大了、时间还停在 11px"的错位。

### 6. 严重度徽标用描边而不是实心

```xml
<Border BorderThickness="1" BorderBrush="{Binding ChipBrush}" Padding="5,0" CornerRadius="3">
    <TextBlock Text="{Binding SeverityText}" />
</Border>
```

实心徽标一旦把严重度色配浅了（现场常有人把"严重红"改成粉），白字就糊成一片；描边徽标配任何颜色都读得清。徽标底色由**每行自己**的严重度决定（`AlarmBannerRow.ChipBrush`），不是整表一个色。

| ④ 事件驱动 | 条件恢复 → 引擎发 `AlarmChanged` → 行还在、状态变"已恢复"；仍闪（已恢复未确认） |
| ⑤ 闪烁相位 | 起表时 `BlinkOn=true`；跑过半个周期 → `false`；再跑半个周期 → `true` |
| ⑥ 清空归位 | 确认两条 → 从实时列表清空；零行 / 空态 / 正常绿 / 计数清空；不闪且相位归位；重新越限 → 又出现一行 |
| ⑦ 订阅成对 | `probe` 装上挂 4 个（节拍 + 引擎三事件各一）；摘掉退 4 个；摘后回设计态；**重复装同一上下文不重复订阅**（`ReferenceEquals` 短路）；收场后订阅者归零 |

第 ⑦ 组用了一个新工具——反射数**字段式事件**的订阅者：

```csharp
private static int SubscriberCount(object owner, string eventName)
{
    var field = owner.GetType().GetField(eventName, BindingFlags.Instance | BindingFlags.NonPublic);

    return (field?.GetValue(owner) as Delegate)?.GetInvocationList().Length ?? 0;
}
```

为什么要反射：C# 的事件只对外开 `+=` / `-=`，读不到订阅表。而"装上挂订阅、摘掉退订阅"这件事在**行为上是看不出来的**——控件每次重读的都是"当前那个上下文"，留着一份旧订阅只是让重读多做一次。它的真实代价是**泄漏**（上一轮的引擎攥着这一轮的控件），所以只能数订阅者来钉。走的是编译器的后备字段（字段式事件的字段名就是事件名），是编译器保证的命名，不是实现细节。
