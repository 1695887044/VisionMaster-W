# 2026-10-03 循环运行显示链路修复（三处时序缺陷：丢帧 / 不刷新 / 闪黑）

- 日期：2026-10-03
- 范围：`Shard\Core.Controls\Events`（捕获钩子 + 发布辅助）、`VisionMaster\Services\ImageCollectionService.cs`（捕获时机 + 每轮清空语义）、`Services\Core.Halcon\Controls\ImageGallery.cs`（刷新优先级）
- 触发：现场反馈"**单次运行正常，循环运行一开，视觉图像页不显示图**"，修完后进一步暴露"**黑屏 ↔ 图片来回切换**"
- 三个缺陷是同一类问题（单次运行正常、只在循环高频下现形）的三个不同环节：帧的**拷贝时机**、界面的**刷新公平性**、每轮更新的**可见语义**

---

## 缺陷 1：预览帧拷贝时机太晚（发布方下一轮已释放源图）

### 现象与证据

流程日志一切正常（采集成功、下游算子出结果），运行日志里只有一条告警：

```
16:15:24.134 [WARN] [图像集] 拷贝图像失败（MainTask.MainTask.图像采集_0.）：
    HALCON error #4060: Image data management: access to deleted region in operator copy_image
```

658 次采集成功只有 1 条拷贝告警——其余是 **静默丢弃**（`IsInitialized()` 为 false 时无声 return）。

### 根因

`PublishPreview` 走 `GlobalEventBus.PublishOnUIThread`（`BeginInvoke` 到 UI 线程），
`CopyImage()` 发生在 **UI 线程回调**里；而插件发布的 HImage 就是它的输出端口值，
基类 `VisionPluginBase.DisposePreviousRoundOutputs` 在**下一轮开始时**释放它。
单次运行源图活到下次运行，来得及；循环（~30ms/轮、大图、每轮 2 帧）UI 一旦落后一轮，
此后每帧的回调执行时源图都已释放 → 全部丢弃。

### 修法

| 文件 | 改动 |
| --- | --- |
| `ImagePreviewCapture.cs`（新增） | `IImagePreviewCapture` + `ImagePreviewCaptureHub.Current`：**发布线程上的同步捕获时机** |
| `PluginPreviewExtensions.cs` | 4 个重载归一到完整版；派发事件前先调钩子（不吞事件，无钩子时行为不变） |
| `ImageDisplayEvent.cs` | 加 `Captured` 标志 + 补所有权文档（这个引用活不过发布方下一轮） |
| `ImageCollectionService.cs` | 实现钩子并在构造时注册：**拷贝+缩略图改在发布线程完成**，只有入集合封送 UI 线程；原回调作无钩子兜底，见 `Captured` 跳过（同一帧只收一次） |
| 同上（附带诊断） | 首帧 + 每 200 帧记一条"已收录 N 帧"；发布时图已失效则**告警**（不再静默）——这类"图不进画布"以后一眼可判"没收录"还是"收录了没刷新" |

## 缺陷 2：画廊重算被"插帧洪水"饿死（帧在集合里，界面永远空白）

### 根因

`ImageGallery.QueueRecompute()` 把重算挂在 **`DispatcherPriority.Background`**，
而触发重算的"采集插帧"本身走 **`Normal`**（`ImageCollectionService.RunOnUi` → `BeginInvoke` 默认优先级）。
WPF 调度器只在**高优先级队列空了**才处理低优先级：循环运行时插帧是连续洪水，
Background 的重算被**永久饿死** → `FilteredFrames` 一直是空 → 界面停在"本格暂无图像"。
单次运行插完就没流量，重算立刻补跑，完全正常——这个不对称正是缺陷潜伏的原因。

### 修法

`QueueRecompute` 改用 `DispatcherPriority.Normal`（与插帧同优先级 → FIFO 交替执行，不被饿死，最坏只是跟队排队），并写上"为什么不能用 Background"的注释。

## 缺陷 3：每轮"先清后画"被渲染看见 → 显示窗口在黑屏与图片之间来回切换

### 根因

连续运行的**每一轮**都广播 `FlowRunStarted`（[FlowEngineService.cs:299](../../Engine/FlowEngineService.cs)），
图像集订阅它并在轮首**立即清空**上一轮的图；而本轮第一张新图要等采集+处理跑完（循环节拍下几十毫秒）
才被收录——清完到出图之间是**空窗**：黑屏 + 空提示，随后图片出现，下一轮再清空。循环下就是频闪。
单次运行没有"上一轮"可清，所以完全正常（与前两个缺陷同一类"只在循环下现形"的时序问题）。

### 修法（方案 A：清空推迟到首帧，与插入同批原子完成）

| 位置 | 改动 |
| --- | --- |
| `ImageCollectionService.OnFlowRunStarted` | **不再**在轮首清空，只登记"待清空"（按流程名 / 整张画布两种模式） |
| 新增 `ApplyPendingClearFor(flowName)` | UI 线程消费待清空：`RemoveFramesOfFlow` / `Clear` 与随后的插入**同一批**（中间无调度点），界面只会看到"旧图 → 新图" |
| `Capture` / `ApplyHarvest` / `OnRealtimePreview`（兜底） | 三条插入路径都在插入前先 `ApplyPendingClearFor` —— 无论本轮的图来自插件注入还是兜底枚举，清空都不会单独先于图出现 |

语义保持不变（仍是"每轮只看最新一轮"）；**本轮没有任何新图 ⇒ 不清空，画布保持上一轮的图**
（监视器语义：有图才有替换）。用户手动「清空画布」仍是立即生效。

## 已知边界

1. **成本转移**：拷贝+缩略图从 UI 线程移到流程线程，总量不变，循环节拍会多这一次的时间（换来不丢帧、界面更跟手）。
2. **画布仍可能"落后若干帧"**（UI 显示节拍有限），但不再丢帧、不再闪黑。
3. **"本轮没有新图"的语义已定**（方案 A 的自然推论）：不清空、画布保持上一轮的图。
   若某轮采集失败，画布不会变空——故障由步骤状态/日志暴露（流程失败红光），画面作为"最后一次有效结果"保留。
4. **捕获钩子一个进程一个**（后注册覆盖）；将来多个留存方需改为集合/事件。
5. **其它事件订阅者**拿到的 `Image` 引用仍可能已释放（历史语义不变）；需要留存必须实现捕获钩子。
