## 2. P0：编辑连接保存必失败，且旧连接被摘掉

**根因链**

1. `SerialConfig` / `SiemensS7Config` / `MitsubishiMcConfig` / `OmronFinsConfig` 的 `Clone()` 都**没拷贝基类 `ConnectionConfigBase.Type`**，而它默认是 0（= `ModbusTcp`）。`FreeProtocolConfig.Clone()` 拷贝了，说明是漏写。
2. `CommunicationConfig.Clone()` → `Config = Config?.Clone()`；`CopyFrom` → `Config = other.Config?.Clone()`，把丢掉的 `Type` 带进活对象。
3. `CommunicationSettingsViewModel.ExecuteEdit` 正是"副本编辑、确定回写"：`config.Clone()` → 属性网格 → `CopyFrom(copy)` → `UpdateConnection`。
4. `UpdateConnection` **先 `RemoveConnection` 再 `AddConnection`**；`AddConnection` 调 `config.Validate`，`CommunicationConfig.Validate` 判 `Protocol != Config.Type` → 抛「协议类型不匹配」。
5. 此时旧连接已从 `_connections` / `_configCache` / `_workers` / `_connectionsList` 全部移除；UI 的 `Configs` 还留着对象 → 界面上有、管理器里没有。

**实测（修复前）**

```
--- ModbusRtu ---  clone: typeField=ModbusTcp valid=False err=协议类型不匹配
--- SiemensS7 ---  clone: typeField=ModbusTcp valid=False err=协议类型不匹配
--- MitsubishiMc --- clone: typeField=ModbusTcp valid=False err=协议类型不匹配
--- OmronFins ---  clone: typeField=ModbusTcp valid=False err=协议类型不匹配
--- ModbusTcp / FreeProtocol --- valid=True
```

**修法**：五个 `Clone()` 首行统一 `Type = Type,`（含 ModbusTcp，避免"恰好等于枚举默认值 0"的隐性依赖）。守门：`CommChecks` **C4-10**（六协议 Clone / CopyFrom 后 `Config.Type` 跟随协议且 `Validate` 通过）。

## 3. P1（数据正确性）：MC 的 W 区单读与批读打到不同设备

**根因**：`PollAddress.Start` 是解析后的**十进制**设备号，而 `PollBatchPlanner` 用 `SegmentPrefix + Start` 拼段地址。MC 的 X/Y/B/W 是十六进制编址（`MelsecMcDataType.FromBase = 16`）：

- 用户填 `W100`（= 0x100 = 256）→ `TryParse` 得 256 → 段地址拼成 `"W256"` → HSL 再按十六进制解析 = **598**。
- 单读走 `BuildAddress` 的 `"W100"`（256）；批读走 `"W256"`（598）。

**实测（修复前）**

```
W offset=100  addr='W100'  batch=YES seg='W256' start=256
W offset=10   addr='W10'   batch=YES seg='W16'  start=16
```

**修法**

- `PollAddress` 新增 `SegmentAddressOverride`，`SegmentAddress => SegmentAddressOverride ?? SegmentPrefix + Start`。
- `McAddress.TryCreatePollAddress` 用**该设备区的进制**生成覆盖串（`{Area}{Format(start)}`）。
- `McAddress` 新增 `Vendor`（默认三菱，存量 JSON 缺字段即按三菱）：ZR 的进制随厂商（三菱 10 / 基恩士 16）。
- `McAddress.BuildAddress` / `TryParseBaseStart` 统一按 `Radix` 解析与回写，**十六进制区允许 `1A` / `0x1A`**。

**实测（修复后）**

```
W offset=100  addr='W100'  seg='W100'  start=256
W offset=1A   addr='W1A'   seg='W1A'   start=26
ZR 三菱 off=100 start=100；ZR 基恩士 off=100 start=256
```

守门：`CommChecks` **B8-1 / B8-2 / B8-6**。

## 5. P1：存储区候选不按厂商收窄

**根因**：`GetAreaOptions` 只看 `Protocol`，不看 `(Config as MitsubishiMcConfig)?.Vendor`。同一份 `McArea` 枚举：

- 松下 `ParsePanasonicFrom` 只认 R/X/Y/L/D；
- 基恩士 `ParseKeyenceFrom` 的 F 只认 FM、S 只认 SM/SD、没有 V；
- 而 `McAddress.Validate` 固定用三菱解析器 → 12 个区全部放行，运行时才报错。

**修法**：`AllowedMcAreas(vendor)` 收窄候选；`McAddress.Validate` 按 `Vendor` 走对应解析器（`ParseMelsecFrom` / `ParseKeyenceFrom` / `ParsePanasonicFrom`）；`TryBuildAddress` 增加 `mcVendor` 参数，创建/预览/导入三处都传。

**实测（修复后）**：松下 M / 松下 W / 基恩士 F / 基恩士 S / 基恩士 V 在创建阶段即被拒，错误文案带厂商名。

守门：`CommChecks` B8-5、`FlowCanvasChecks`「存储区：基恩士收窄 / 松下只留 D/R/X/Y/L」。

## 6. P1：添加变量弹窗内切换连接后候选不刷新

**根因**：`NetworkVariableDraft.AreaOptions` 在构造时钉死；`ComboSourceGenerator` 只在建表时取一次候选；`PropertyGridBase` 只对 `RequireRefresh` 属性整表重建。后果：切换连接后仍列旧协议的区 —— 同名的 `"D"` 静默建错区，不同名则"预览报先选存储区、候选里却没有可选项"的死路。

**修法**：新增 `NetworkVariableDraftContext`（连接名 → 存储区候选 / 默认区 / 扫描组候选的回调）；`ConnectionName` 标 `RequireRefresh = true`，setter 里重置 `AreaName` 为新区默认值、`ScanGroupName` 尽量保留同名组。VM 的 `CreateDraft` 注入 context。

守门：`FlowCanvasChecks`「存储区：弹窗内切换连接后候选与默认区跟着新协议走」。

## 9. 未做 / 已知边界

1. **属性网格没有"按协议动态显隐"能力**：`SuperDisplay.Visible` 是静态的，`RequireRefresh` 只能整表重建、不能改可见性。本批用 `Description` 标注适用协议；要真正隐藏需要给属性网格加"可见性谓词"（框架级改动，回归面大）。
2. **`McAddress.Vendor` 是新序列化字段**：存量 JSON 缺字段按三菱解析（默认值），单读地址串不变；W 区的批读段地址会从错误的 `"W256"` 变为正确的 `"W100"`——这是修 bug，不是行为回退。
3. **全量 `dotnet build VisionMaster.sln` 当前被 `ScadaChecks` 的并发改动挡住**（`FakeNavigator` 未实现 `IScadaNavigator.GoBack(out string?)`，`ScadaChecks\Program.cs` mtime 13:08），与本批无关；本批按工程逐个构建验证。
4. **未跑 `UIThemeSmokeTest`**：本批只改了一处绑定名（`{Binding Protocol}` → `{Binding ProtocolText}`），视图数据源为 `CommunicationConfig`（`BindableBase`，属性存在且发通知）。
5. 未做真机验证：W/ZR 区的实际地址需上 PLC 复核（HSL 解析器已按随仓源码对齐）。
