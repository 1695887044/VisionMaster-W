## 一、需求与决策

### 1. 需求

路线图风险登记（2026-09-20 版）里两条，原文逐字：

> `| 审计文件无保留策略（按天滚动，不清理） | 现场跑一年磁盘会被审计 CSV 吃满 | S13 随打包/维护窗口一起做（与报警历史保留策略同一处） |`
>
> `| ScadaUserStore 改账号不写审计 | "谁改了谁的密码"无凭证，出事查不到 | S13；改密/建号/删号都应落审计 |`

拆成两件事：

- **需求 A（保留策略）**：S12 做的"按天滚动"只解决了**单个文件不会涨到打不开**，没解决**目录会一直涨**。这台机器要连跑几年：一天一份、一年三百多份、从不清理——最后不是"审计写不进去"（磁盘满），就是"备份要拷一整天"。
- **需求 B（账号审计）**：权限体系里唯一真正致命的一问是"**谁在什么时候把谁的密码/角色改成了什么**"。提权最省事的办法不是破解哈希（PBKDF2 + 随机盐 + 十万次迭代，逐个暴力试代价极高），而是**让人把某个账号的角色改一下**。而这一问必须三个月后还答得上来——运行日志会滚动、会被现场随手清掉，指望不上。

### 2. 决策清单

#### 2.1 保留策略（需求 A）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| A-1 | 清理**时机** | **跨天那一刻清一次**（`PurgeIfNewDay`），不是每次追加都清 | 每次追加都扫一遍目录 = 给"点一下按钮"叠上一次目录枚举。审计是低频事件，这个代价**换不来任何东西**：需要清的文件一天只多一份。进程刚起来 `_lastPurgedDay` 为空，当天第一次写入就会清一次——现场"攒了一年没开过机"也能在启动后第一次操作时收掉 |
| A-2 | `_lastPurgedDay` **何时记下** | **在清理之前记** | 某份文件删不掉时（多半 Excel 开着），不该每次追加都重扫目录、重报一句警告 |
| A-3 | 清理与写入的**顺序** | **清理放在写成功之后** | 反过来的话，写不成时（磁盘满）先删掉旧凭证，等于把"**唯一能作证的那一份**"赔进去 |
| A-4 | 清理失败怎么处置 | **绝不抛、也不碰 `IsFaulted`** | "旧文件删不掉"与"新记录写不进去"是**两件事**。混成一档，接下来的写入会被当成"审计坏了"，而它其实好着——产生误导性告警 |
| A-5 | 删哪些文件 | **三重确认只删本类自建**：前缀（`Audit-` / `AlarmHistory-`）+ 后缀（`.csv`）+ 中间段能按 `yyyy-MM-dd` 用 `DateTime.TryParseExact` 解析 | 解析不出来**当它不是本类文件**（宁可漏清一个，不能误删一个）。清理策略把用户的文件删掉，是这类功能最不能犯的错 |
| A-6 | 默认保留天数 | 审计 **90 天**、报警历史 **365 天** | 审计 90 天 = "够查一次季度复盘、又不至于让目录无限涨"；报警历史装着"当时什么状态"，现场偶尔翻**很久以前**的同类故障对比，故默认一年 |
| A-7 | `retentionDays <= 0` 的含义 | **永不清理**（留给"法规要求留档、磁盘也够"的现场） | **必须在算截止日之前先判**：否则截止日会算到"今天之后"，把**今天刚写的那份也删掉**——那是刚写进去的凭证 |
| A-8 | 截止日公式 | `nowLocal.Date.AddDays(1 - _retentionDays)` | 保留"最近 N 天**含今天**"，早于截止日才删。N=90 时截止日 = 今天 − 89 天 |
| A-9 | 单个文件删不掉 | `failed++` + `firstError ??=`，继续删其余；最后只报**一句** `Warning` | 不影响其余文件；一句警告说明"下次跨天写入时会再试一次"，不刷日志 |
| A-10 | 可测性 | `PurgeExpired(DateTime nowLocal)` 是 `public` | 断言传假日期即可测保留期，不必改系统时钟（与 `Append(entry, nowLocal)` 同一手法） |
| A-11 | 报警历史是否同构 | **同构实现**（两份 writer 逐条一致，仅前缀与默认天数不同） | 两者是同一类东西（按天滚动的流水账），保留策略没有理由分头演化 |

#### 2.2 账号审计（需求 B）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| B-1 | **落笔点**选在哪 | **`ScadaUserStore`**，不是两个弹窗的 ViewModel | 这五个方法是账号数据的**全部出口**，落在这里就不可能漏：将来多一条调用路径（运维命令行改密、恢复出厂管理员）也自动被记上。落在调用方则要求每个调用方都记得记一笔——而审计最怕的**不是记错，是漏记而无人知道**：文件看着完好，只是少了那几行 |
| B-2 | 署名（actor）从哪来 | 构造注入 `Func<string?>? actorProvider`，宿主接到"此刻登录着谁" | `ScadaUserStore` **不认识会话**（它连 `ScadaAccessPolicy` 都不引用，保持"验身份 → 记会话"的单向链）。取不到时由 `ScadaAuditEntry` 回落"未登录"——**"未登录就把账号改了"本身就是一条线索** |
| B-3 | 哪几个方法落审计 | 五个公开**写**方法：`TryChangePassword`（修改密码）/ `TryResetPassword`（重置密码）/ `TryAddUser`（创建账号）/ `TryRemoveUser`（删除账号）/ `TrySetRole`（修改角色） | `TryValidate` **不落**：它不改变任何数据，记进去只会让"账号管理"这一栏被登录动作刷满 |
| B-4 | 成功 / 失败都记吗 | **都记** | "谁试着改了谁的密码但没成"与"改成了"是**两条不同的线索**。只记成功的那一半，事后问"他到底动过没有"答案会是"没有" |
| B-5 | 失败那一格的说明写什么 | 直接用 `error` | 那是给操作员看的原因，与界面弹的那句话**同源**，审计与现场口述才对得上 |
| B-6 | "事件"列写什么 | 固定 `private const string AuditEventText = "账号管理";` | 与运行态越权那条（"权限校验"）同构：这一列是**类别名**，回答"从哪儿来的"，具体干了什么在"动作"列 |
| B-7 | "说明"列（detail）的语义 | 成功时写**净效果**：改密"密码已修改"、重置"密码已重置（管理员路径，未校验旧密码）"、建号"角色：{档}"、删号"原角色：{档}"、改角色"角色：{旧} → {新}" | 审计要回答"改成了什么"。删号那条**先记下角色再摘除**——摘掉之后"他原来是什么身份"就查不出来了，而这恰恰是删号审计里最该留下的一格 |
| B-8 | 值未变时（`TrySetRole` 同档） | 返回成功、**不写盘**，但 detail = `"角色未变（仍是{档}），未写盘"` | 不记的话，"他没动过"与"他动了但值没变"分不出来 |
| B-9 | 审计写不成怎么办 | `Audit` **绝不抛、绝不影响返回值**；`_audit == null` 时整件事不存在 | 与"审计写不成不能让操作失败"同一口径（见 `ScadaAuditWriter` 类注释）：磁盘故障时把异常抛回，表现是"点了按钮程序崩了"，比丢几行审计严重得多 |
| B-10 | 新密码会不会被写进审计 | **绝不** | 凭证不该成为第二份密码泄漏点。这条有断言钉住（见 §三.3） |
| B-11 | 重构手法 | 五个方法拆成 `public Try*`（只做**归一化** + 调私有核心 + `Audit`）+ `private` 核心（原逻辑，多带一个 `out string? detail`） | `public` 一律先过 `Normalize`（`(userName ?? "").Trim()`），审计的"对象"列才不会带着尾随空格。核心逻辑一行没改，只是把出口收成一处 |
| B-12 | 接线怎么写 | `App.xaml.cs` 用**工厂**注册，显式传 `audit:` 与 `actorProvider:` | `audit` / `actorProvider` 都是**可选参数（默认 null）**，交给容器去猜的结果是**编译能过、运行起来审计一直空着、而且不报任何错**——这正是审计最怕的失效方式。这是 `App.xaml.cs` L163 已经踩过的坑，注释里写着"接上审计这件事在注册处一眼可见" |

## 四、已知边界

1. **清理只在"跨天写入"时发生**。若这台机器一直开着、且连续几天没有任何操作（审计是低频事件，完全可能），过期文件会一直留着——直到下一次写入跨天。这不是缺陷（低频事件不清理不产生任何代价），但**不能承诺"保留期一到就删"**，只能说"保留期一到、下次跨天写入时删"。
2. **审计与报警历史各清各的目录**。`Audit/` 与 `Alarms/` 的保留期是两个独立参数（90 / 365），且**目前都在构造处用默认值**——还没有接到方案级配置。现场要改保留期，得改 `App.xaml.cs` 的注册（一行）。
3. **保留期只按文件名的日期判**，不看文件内容，也不看"这个日期是否真有记录"。手工把一份旧文件改名成今天的日期，它就会一直被留着（但绝不会误删——方向是安全的）。
4. **没有"清理了多少份"的日志**。只有删不掉时才报一句 `Warning`；成功清理是静默的。理由：清理是维护动作、不是事件，每天报一句"清了 1 份"只会变成噪音。真要审计清理行为，得再加一层。
5. **账号审计的署名是"此刻登录着谁"**，不是"这条命令是谁发起的"。单人操作同一台机器时两者等价；将来若有远程/多会话（一个进程里两个登录态），`Func<string?>` 这个口子需要重做。
6. **`ScadaUserStore` 构造是破坏性变更**（新增两个参数）。断言工程里那些 `new ScadaUserStore(path)` 因默认参数仍能编译，**它们跑的是"不记审计"这条路径**——这符合断言的本意（测 store 本身），但也意味着**断言全绿不能证明宿主接上了审计**。宿主接线由 §二 的 `App.xaml.cs` 改动 + 代码审查保证，`ScadaChecks` 里**没有**"宿主注册处真的传了 audit"的断言（那要起 WPF 容器）。
7. **保留策略未做真机验证**。断言用的是假日期 + 临时目录，证的是"逻辑对"；"真机上跑一年目录不涨"这件事按定义**要跑一年才知道**，本轮不具备条件。
8. **`--stress` 从 1216 涨到 1238**，一次跑仍要一分多钟；保留策略这 10 条断言在**常规**运行里也跑（属 `[AU]` 段），不必等 `--stress`。
