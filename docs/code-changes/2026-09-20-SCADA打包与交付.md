## 一、需求与决策

### 1. 需求

路线图（2026-09-20 版）S13 清单里最后一条，原文逐字：

> `- 打包：安装、升级、方案文件迁移、异常退出后的现场恢复。`

这一条在路线图上挂了最久，因为它**不是一个功能，是四件事**，而且四件事都不是"写代码"：

| 子项 | 真实含义 | 本阶段的做法 |
|---|---|---|
| 安装 | 现场机器上怎么把软件跑起来 | **目录式交付**：整个目录拷过去双击 exe，无安装器（D-1） |
| 升级 | 换了新版本怎么覆盖，且**不丢配置** | 结构上保证：用户数据不在程序文件里（D-2 / D-4） |
| 方案文件迁移 | 老版本写出的 `.vms` 能被新版本打开 | 加载路径补身份字段，**幂等**（D-15） |
| 异常退出后的现场恢复 | 崩了之后，用户的活还在不在 | 崩溃留档（D-16）+ **未保存草稿转存**（D-19）+ 启动提示（D-23） |

**"异常退出后的现场恢复"是这一条里唯一有产品分量的部分。** 一个视觉软件跑在现场机台上，操作员配了两小时的画面，程序崩了——如果那两小时没了，这是软件事故；如果有草稿能救回来，这就只是一条日志。所以本阶段的重点不是打包脚本，是**草稿**。

### 2. 决策清单

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| D-1 | 交付形态 | **目录式**（一个目录 + 双击 exe），不做 MSI/安装器 | 本工程没有安装器工程，也没有需要写注册表、注册服务、装驱动的动作——那三件事是安装器存在的理由，这里一件都没有。为一个不存在的需求引 WiX/InnoSetup，等于给自己加一条"打包失败时先怀疑安装器脚本"的排查分支 |
| D-2 | 升级怎么做 | **覆盖同名文件**；用户数据不在程序文件里，所以"升级不丢配置"是**结构上成立**的 | 靠安装器脚本"记得跳过某些文件"是**约定**，约定会被忘；靠"那些文件根本不在覆盖范围内"是**结构**，结构不会忘 |
| D-3 | 打包时程序正在跑怎么办 | **直接拒绝**，抛一句人话（列出 PID） | 程序文件被占用时覆盖会失败，现场看到的会是一串 `IOException` + 半个新旧混杂的目录。宁可让打包的人先关软件 |
| D-4 | 清理旧目录怎么清 | **只清程序文件**，`protected` 名单里的用户数据一个都不动 | 交付目录**可以**就是现场目录（`-OutputDir` 允许指过去）。那时 `Remove-Item` 整个目录 = 把配置、方案、草稿、崩溃留档一起删——**不可恢复**。所以开头承诺的"用户数据不在覆盖范围"，必须在这里也成立 |
| D-5 | `dotnet publish` 够不够 | **不够，补齐三处**：Halcon 原生库 / `Modules\` / `ScriptAssets\` | 三处都是实测确认过的缺口：publish 只带 `halcondotnet.dll`（托管封装），原生库不随行；插件是独立工程、投递到仓库根 `Modules\`；`ScriptAssets` 由 `xcopy` 投递到 `bin\`。漏了的现场表现分别是"一打开图像就崩"、"一个算子都没有"、"插入示例代码报 unresolved procedure call" |
| D-6 | 插件怎么补 | **整目录拷**（`Copy-Item "$src\*"`），不逐个列文件名 | 插件带自己的私有依赖（`Microsoft.CodeAnalysis.*` 等）。逐个列文件名的话，**加一个插件就要回来改打包脚本**，而"忘了改"的表现是"新插件在现场没有"——很难联想到打包脚本 |
| D-7 | 交付目录里要不要留说明 | **写一份 `用户数据说明.txt`**，含"怎么用 / 升级怎么做 / 受保护清单 / 兼容性承诺 / 出问题先看哪里" | 打包脚本里那套"哪些能删哪些不能删"的知识，只有写脚本的人知道。把它写成文件放进交付目录，现场维护的人才有依据——否则升级时"顺手清一下目录"就是一次数据事故 |
| D-8 | 自检验什么 | **17 项必需文件**逐个 `Test-Path` | 缺口要在**打包时**暴露，不要留到现场。列的都是"少了就一定有某个功能不可用"的文件 |
| D-9 | 自检够不够 | **不够，加 `-Smoke`**：从交付目录启动一次 exe，15 秒后看它是否还活着 | "文件在"≠"跑得起来"。目录式交付最常见的翻车点是 **Halcon 原生库没随行**——自检全绿、启动即崩。这是唯一能验出它的手段 |
| D-10 | 冒烟失败怎么报 | 退出码**翻译成人话**（`-1073741515`=缺 DLL `0xC0000135`、`-1073741819`=访问冲突 `0xC0000005`、`-532462766`=`.NET` 未处理异常 `0xE0434352`） | 光给一个负数退出码，看的人得去查表。这三个码是目录式交付最可能撞到的三种死法，直接写出来 |
| D-11 | `-SkipPublish` 有什么用 | 跳过 publish，直接对已有 `bin\<Configuration>` 做补齐 | "只改了补拷逻辑"时不必等一次完整 publish。**它同时是最快的"升级不丢配置"验证路径**（本阶段 §三.5 就是这么验的） |
| D-12 | 落盘方式 | **原子写**：先写同目录 `.tmp` → 目标已存在走 `File.Replace`、不存在走 `File.Move`；失败清 `.tmp` 再抛 | 写一半断电/崩溃不留半截 json。**临时文件必须与目标同目录**——跨盘 `File.Replace` 会失败。这个范式在本工程是**统一口径**（`ScadaUserStore` 同一手法） |
| D-13 | 草稿判据用什么 | **按落盘口径序列化一次 + 与磁盘文本逐字比较**，不用 `IsDirty` 脏标记 | 脏标记要在**每一个**写模型入口埋点（`Try*` / `Add*` / 属性 setter…），漏一处就是"改了但退出不存草稿"——而漏的那处**极难自证**。逐字比较不需要任何埋点，代价是每次退出多一次序列化（毫秒级）。所以先钉死前提：`SolutionService.Serialize` 与 `SaveAsync` 写出的文本**逐字一致**（有断言，D-13 的成败全押在这条上） |
| D-14 | `SolutionFilePath` 要不要落盘 | **不落盘**（`[JsonIgnore]`） | 它是运行期 UI 提示（状态栏/标题显示当前文件），不是方案内容。而且它**必须在落盘之后**才拿得到（保存成功才有路径）——若参与序列化，磁盘那份永远比内存少一个字段，D-13 的逐字比较会把**一次没改过的方案**判成"有未保存改动"，每次退出都多存一份草稿 |
| D-15 | 老 `.vms` 怎么迁移 | 加载路径补发稳定身份（`EnsureIdentity`），且**幂等** | 老文件里没有 `PageId` / `ElementId` / `LayerId`（这些是后来才引入的）。不补发，绑定/事件钩子就没有可引用的目标。幂等是硬要求：重复加载**不许换 Id**，否则"打开 → 保存 → 再打开"会把所有绑定打断 |
| D-16 | 崩溃留档走不走日志服务 | **不走**，`CrashReportWriter` 自己写文件 | 崩溃时日志服务**可能已经死了**（它自己就是被 dispose 的对象之一）；就算活着，日志按天滚动、当天文件里几百行，现场那一次崩溃会被淹掉。崩溃现场要的是"一份独立的、带时间戳的、不可能被淹没的文件" |
| D-17 | 崩溃报告留几份 | **最近 20 份**，超出裁掉最早的 | 与日志的"按天滚动"同一个取舍：留够复现，不留到把磁盘吃满 |
| D-18 | 崩溃提示怎么做到"只弹一次" | 取走时**把文件改名挂 `.acked` 后缀**（不是删除） | 用"文件是否存在"表达"还没提示过"。改名而不是删除：**现场不能毁**——万一提示弹窗本身失败，那份报告还得在 |
| D-19 | 草稿什么时候存 | **退出链**里存（正常关闭与严重异常退出**都走退出链**） | 见 D-22。不选"定时自动保存"：那会在用户正常编辑时反复写盘，且"存了哪一份"说不清 |
| D-20 | 没改动也要存吗 | **不存**（`NoChange`），一份文件都不写 | 每次退出都产生一份草稿，用户会以为软件在乱写文件，而且保留策略会把真正有价值的草稿挤掉。三种"不存"：`Skipped`（没打开方案 / 方案从未落过盘——**没有对照物**）/ `NoChange`（逐字一致）/ `Failed`（出错，记 `Warn` 不抛） |
| D-21 | 提示过的草稿怎么处理 | **归档到 `Autosave\recovered\`**（移动，不删除）；保留策略只动未提示区 | 那是用户**唯一一份**未保存内容。归档而不是删除，且归档区**不受 10 份保留策略影响**——用户成果归用户自己管 |
| D-22 | 退出任务的顺序 | 退出链**逆序**执行；"未保存草稿转存"注册在"日志落盘收尾"**之后** → 逆序时先跑，此刻日志服务还活着 | 转存结果（存了/失败）要能记进日志。注册顺序就是这个意图的唯一表达方式，所以两处都写了注释说明"为什么排在这里" |
| D-23 | 恢复提示怎么问 | 两件事分开说、**合在一处问**；**先讲草稿（用户的成果）再讲现场**（给开发者/售后的证据）；只给一个"打开目录"动作，Yes 时**优先开草稿目录** | 用户真正在意的是"我的活还在不在"。先讲崩溃现场，用户会以为软件坏了、慌了；先讲草稿，用户知道"东西还在"。只给一个动作是刻意的：两个"打开目录"按钮在现场会被点错 |
| D-24 | 基线数字怎么落档 | 新增 `baseline.ps1`：跑 → 抓 `[BL]`/`[ST]` 两块 → 写 `docs/code-changes/性能基线-YYYY-MM-DD.md`；**同一天重跑会覆盖** | S13-a 的原做法是"跑完人工粘贴"，于是"回归时看数字不看感觉"全靠人记得粘，漏一次就永远对不上。同一天覆盖的理由：同日多次跑通常是改代码试数字，留最早那次没有意义；跨天才有对比价值。**脚本不产出任何结论**——数字给人看，退出码只反映 `ScadaChecks` 自己的断言 |
| D-25 | 脚本跑失败了现场怎么办 | **全绿才清临时输出，有红条就留着并打印路径** | 失败时最需要原始日志，删掉等于把现场毁了——与"崩溃留档不删"（D-18）是同一个道理 |
| D-26 | PowerShell 脚本怎么存 | 一律 **UTF-8 with BOM** | Windows PowerShell 5.1 读**无 BOM** 的 `.ps1` 时按系统 ANSI 码页（中文机器 = GBK）解码，中文注释/字面量变乱码并引发一连串语法错误。`pack.ps1` 与 `baseline.ps1` 都因此崩过 |

### 4. 本阶段修掉的真缺陷（五处）

这一阶段的代码量不大，但**五个缺陷全是在"实跑"这一步才暴露的**，静态审查一个都没看出来。按性质分两类。

#### ① 产品缺陷：`SolutionFilePath` 落盘导致"打开就退也误判成有改动"

- **现象**：`Serialize` 与磁盘文本对不上，逐字比较永远为真 → 每次退出都多存一份草稿。
- **真因**：`SolutionFilePath` 是"保存成功**之后**"才赋值的，若参与序列化，磁盘那份永远比内存少一个字段。
- **修法**：`[JsonIgnore]`。同时新增两条断言把这个前提钉死（"Serialize 与落盘文本逐字一致"、"往返文本稳定"）——**这类"判据的前提"必须自己占一条断言**，否则它失效时的表现是"草稿功能看起来在乱写文件"，排查方向全错。

#### ② 打包缺陷：`Copy-Item <源目录> <目标目录> -Recurse` 会嵌套

- **现象**：`ScriptAssets` 文件数 34 → 68。
- **真因**：**目标目录已存在**时，PowerShell 会在目标里再套一层同名目录（`dist\ScriptAssets\ScriptAssets`）。
- **修法**：拷 `"$src\*"` 而不是 `$src`。`Modules\` 那一步同一手法，代码里都留了注释。

#### ③ 打包缺陷：`-SkipPublish` 会删掉用户数据

- **现象（代码审查发现）**：原实现无条件 `Remove-Item $OutputDir -Recurse`。
- **真因**：`-OutputDir` **可以**就是现场目录（这是文档里明写的用法）。那时整目录删 = 配置、方案、草稿、崩溃留档一起没。
- **修法**：`protected` 名单 + 只清名单外的程序文件（D-4）。

#### ④ 打包缺陷：只验"文件在"不验"能跑"

- **真因**：缺 Halcon 原生库时自检全绿、启动即崩（D-9）。
- **修法**：加 `-Smoke` + 退出码翻译（D-10）。

#### ⑤ 脚本缺陷：`Start-Process -Wait` 挂死（两轮）+ `ExitCode` 读成 `$null`（一轮）

**这是本阶段最值钱的一条经验，单独展开。**

`baseline.ps1` 的"跑 `--stress`"这一步，前后**改了三轮**才稳：

| 轮次 | 写法 | 结果 | 真因 |
|---|---|---|---|
| 一 | `Start-Process dotnet -ArgumentList ... -Wait` | **永久挂起**，日志里早就"全部断言通过" | `-Wait` 等的是**输出流 EOF**。`dotnet run` 会拉起 MSBuild 工作进程（`/nodeReuse:true`，常驻 15 分钟），它们**继承**了被重定向的那个句柄——句柄一直有人拿着，EOF 永远不来 |
| 二 | 去掉重定向，只 `-Wait` | **仍然挂起** | `-Wait` 同时等**整个进程树**。`dotnet build` 留下的 MSBuild 常驻节点让它挂着 |
| 三 | `& dotnet build`（编译）+ `Start-Process -PassThru` **不带 `-Wait`** + 自轮询 `HasExited` + 兜底超时 | 能跑了，但**末尾打出"有断言失败（退出码 ）"——括号里空着** | Windows PowerShell 5.1 的 `Start-Process -PassThru` 返回对象，**没调用过 `WaitForExit()`** 时 `ExitCode` 取回 `$null`。它把一次全绿的运行误判成失败 |

**终版**（三条一起上）：

```powershell
& dotnet build -c $Configuration $project --nologo          # 编译：只等被调进程本身
if ($LASTEXITCODE -ne 0) { throw "..." }

$proc = Start-Process -FilePath 'dotnet' -ArgumentList @($appDll, '--stress') `
    -WorkingDirectory $repoRoot -NoNewWindow -PassThru `
    -RedirectStandardOutput $outFile -RedirectStandardError $errFile   # 不带 -Wait

$deadline = (Get-Date).AddMinutes(20)
while (-not $proc.HasExited) {
    if ((Get-Date) -gt $deadline) { Stop-Process -Id $proc.Id -Force -ErrorAction SilentlyContinue; throw "..." }
    Start-Sleep -Milliseconds 500
}

$proc.WaitForExit()          # ← 必须先调它，否则下面读出来是 $null
$exitCode = $proc.ExitCode
if ($null -eq $exitCode) {   # 兜底：某些 PS 版本仍拿不到时，用 ScadaChecks 自己的结论行判
    $exitCode = if (($lines -join "`n") -match '>>> 全部断言通过 <<<') { 0 } else { 1 }
}
```

顺带三条同源修法：

- **`>` 不能用**：`>` 会先按 `[Console]::OutputEncoding` 解码再重编码，中文机器默认 GBK，会把 UTF-8 输出解成乱码。重定向到文件是**原始字节直通**。
- **`$md += $blocks` 不能用**：`$blocks` 是 `List[string]`，`+=` 会把整个 List 当成**一个元素**塞进去。必须 `$md += @($blocks)`。
- **`pack.ps1 -Smoke` 段有同一个 `ExitCode` 陷阱**（主动排查发现，非实跑暴露）：`HasExited` 为真时直接读 `$proc.ExitCode` 同样拿到 `$null`，`switch` 会落到 default 分支打出 `退出码 （0x00000000）`这种误导话。同样补了 `$proc.WaitForExit()`。

> **教训**：`Start-Process -Wait` 的失败方式是最坏的一种——**不报错，只是永远不返回**。看日志"全部通过"了，人还在等。任何"等一个可能带子进程的外部程序"的地方，都该用"自轮询 + 兜底超时"，不要用 `-Wait`。

## 四、已知边界

1. **草稿判据对"别的版本写过"的磁盘文件有已知偏差**。逐字比较的口径是"本版本的序列化输出"。若磁盘上那份 `.vms` 是**别的版本**写的（缩进/字段顺序不同），会被判成"有改动"而多存一份草稿。**方向是安全的**（宁可多存，不会漏存），所以**刻意不引入 JSON 规范化**——规范化会把"逐字"变成"语义"，而语义比较要维护一套字段级规则，反而更容易出"看起来一样其实不一样"的静默错。
2. **`Sanitize` 只处理非法文件名字符**（替换成 `_`）。方案名里的保留字（`CON` / `NUL` 等）与超长名未处理。极端情况下草稿写不出来 → `Failed` → 记 `Warn`，**不影响退出**。
3. **崩溃报告靠文件名里的毫秒时间戳区分**。同一毫秒内写两份会互相覆盖。实际路径上（一次崩溃只写一份）不会撞；断言里为此专门 `Sleep(30)`。
4. **`baseline.ps1` 的兜底判据依赖 `>>> 全部断言通过 <<<` 这一行文本**。若将来改了 `Finish()` 的输出文案，兜底会静默失效（但 `WaitForExit()` 那条主路径不受影响）。
5. **`baseline.ps1` 未在 CI 上跑过**。它写 `docs/`（有副作用），CI 上要不要写、写到哪，属于接入 CI 时再定的事。目前只有"人在本地跑"这一条路径。
6. **`pack.ps1` 的自检是"17 项必需文件"，不是"全部文件清单"**。多一个插件、多一份资源不会被发现——但少一份会被发现。这是刻意的方向选择：白名单会随插件增减而腐化，必需项不会。
7. **`-Smoke` 只验"启动 15 秒后还活着"**，不验功能。启动即崩能抓到，启动 3 分钟后崩抓不到。
8. **`Core\Toolkit\GlobalExceptionHandler.cs` 是死代码**。全工程唯一引用它的是它自己和 `docs/`。真正的接线是 `AppLifetimeService.RegisterGlobalExceptionHandlers()`（`App.xaml.cs:45`）。它自带"自动重启"逻辑，与本工程"崩溃留档 + 恢复提示、**不自动重启**"的产品决策冲突——留着会误导后来人。**本阶段未删**（改动面之外），列入 §五。
9. **恢复提示是模态 `MessageBox`**，启动后弹在 `ApplicationIdle`。若主窗口还没出来（受限桌面等）走的是无 owner 分支。提示本身失败只记一行日志，**绝不影响主界面**（`App.xaml.cs:353-357`）。
10. **SCADA 全部新代码（含本阶段新增的 `Core\Lifetime\*`、`SolutionDraftService`、两个 `.ps1`）仍未被 git 跟踪**。提交需明确授权，本阶段未做任何 git 写操作。
