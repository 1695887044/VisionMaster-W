# Manager 接线：专用线程 + 批量轮询落地（t6）

日期：2026-09-17
主线：通信流程重构 —— t6「`AdvancedCommunicationManager` 接线到 `ConnectionWorker`」

## 一、需求与决策

### 需求
t4 交付了 `ConnectionWorker`（连接专属线程 + 状态机），t5 交付了 `PollBatchPlanner`（批量轮询规划器），
但两者都还是"孤儿"：`AdvancedCommunicationManager` 仍用**三套 Timer**（重连 / 心跳 / 变量轮询）
并发驱动同一个设备对象。t6 的任务是把 Manager 全部 I/O 路径改道到 Worker，并让轮询走批量规划器。

旧实现的三个根因：
1. **B2 线程不安全**：HSL 设备对象不是线程安全的，Timer 回调 / UI 线程 / 重连线程会同时操作同一个 socket → 随机错包、半开连接；
2. **C1 假心跳**：心跳只读 `IsConnected` 属性，半开连接永远显示"正常"；
3. **C5 重连叠加**：固定间隔重连，多个 Timer 可同时发起，重连风暴无法收敛。

### 关键决策
| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 线程模型 | **每连接 1 个 Worker**，`Read`/`Write`/`TestConnection`/轮询/建连/断开全部经 `worker.Invoke(...)` 串行化 | 设备对象从此只有一个线程碰它，从根上消除竞态；不需要给每个连接实现粒度锁 |
| 状态真相源 | **Worker 状态机独家维护**，`StateChanged` 回调里同步到 `config.State` 并广播 | 旧实现"谁发起谁改状态"，重连线程改的状态没人通知 UI（界面长期停在"已断开"） |
| 三套 Timer | **整体删除** | 轮询节奏、重连退避、连接活性全部并入 Worker 主循环，不可能再叠加 |
| 心跳 | 改为**真实读写成功时刻**（`LastCommunicationSuccessTime`） | 只有真正收发过数据才算活，`IsConnected` 属性骗人的问题消失 |
| 重连节奏 | 指数退避 `base × 2^(n-1)`，封顶 `ReconnectMaxIntervalMs`(30s) | 对上位机友好；`MaxReconnectAttempts>0` 时超限停在 `Error` 终态 |
| 自动重连开关 | Manager 注入 `worker.AutoReconnect = AutoReconnectEnabled && config.AutoReconnect` | 管理器总开关与连接级开关取与；关掉即"失败不重试"（`CommTest` 依赖此语义） |
| 轮询计划编译时机 | **注册变量时不编译**，只在 `Connect` 与"已连接的连接收到注册/注销"时编译 | 批量注册 N 个变量若每个都重建，会做 N 次全量规划（N² 行为） |
| 通信故障日志 | 按 `commerr:{连接名}` 节流 5s | 退避重连期间同一条故障会按秒重复上报，日志窗口被刷满 |
| `TestConnection` 对活连接 | 直接返回 `true`，不打设备 | 各实现都是"连一次再关掉"，对活连接调用会关掉在用的 socket（自毁） |

## 二、修改文件清单

| 文件 | 改动 |
| --- | --- |
| `Communication/Communications/Manager/AdvancedCommunicationManager.cs` | 接线主体（13 处） |
| `Communication/Communications/Manager/ConnectionWorker.cs` | 新增 `AutoReconnect` 公共属性；`Connect` 重置重试预算；`ScheduleReconnect` 尊重开关 |

### 1. 字段与属性
- 删除：`_reconnectTimers`、`_reconnectAttempts`、`_heartbeatTimers`、`_variablePollingTimers`、`static _readMethodCache`
- 新增：`_workers`（`ConcurrentDictionary<string, ConnectionWorker>`）、`_throttleTicks` + `ThrottleMs = 5000`
- `ConnectedCount` 改为 `_workers.Count(w => w.Value.IsConnected)`；删除 `HeartbeatIntervalMs` 属性；
  `GlobalReconnectIntervalMs` 语义明确为"重连基准间隔（连接级 `RetryIntervalMs` 优先）"

### 2. 连接生命周期
- `AddConnection`：创建 Worker → 订阅 `StateChanged`/`CommunicationError` → 存入 `_workers` → `Start()`
- `RemoveConnection`：`_workers.TryRemove(...).Dispose()`（Worker.Dispose 内部会 Join 线程 → 断连 → 释放连接对象）；
  保留"无 Worker 的孤儿连接"兜底释放分支
- `UpdateConnection`（**B1 修复**）：先快照变量注册表 → `Remove + Add` → 重新 `RegisterVariable`。
  旧实现直接移除重建，而 `RemoveConnection` 会连变量注册一起清空 —— "改个超时时间"就把该连接所有变量轮询悄悄停掉
- `Connect`：`ConfigureWorker`（灌周期/重连参数/自动重连开关）→ `RebuildPollPlan` → 等首次建连（超时 `Config.TimeoutMs`）。
  返回 `false` ≠ 放弃：Worker 仍在后台按退避重连，状态变化经事件广播
- `Disconnect`：`worker.Disconnect()`
- `Dispose`：遍历 `_workers` 逐个 `Dispose()`，并清理 `_varForwardHandlers` / `_throttleTicks`

### 3. 数据读写
- `TestConnection`：活连接短路返回 `true`；否则 `worker.Invoke(c => c.TestConnection())`
- `Read<T>` / `Write`：`worker.Invoke(...)` 投递到连接线程取回结果（与轮询天然串行）
- `TriggerWrite`（**B7 真异步**）：`worker.EnqueueWrite(...)` 立即返回，`ContinueWith` 只做失败日志 + 上报，
  不再让调用方被网络阻塞（旧实现名异步实同步）

### 4. 变量注册与轮询
- `RegisterVariable` 末尾 / `UnregisterVariable` 内：`RequestPollPlanRebuild(connectionName)`
  （已连接才立刻重编译，未连接推迟到 `Connect`）
- `ConfigureWorker`：`PollIntervalMs = ReadCycleMs`、`ReconnectBaseIntervalMs = Config.RetryIntervalMs ?? GlobalReconnectIntervalMs`、
  `MaxReconnectAttempts`、`AutoReconnect`
- `RebuildPollPlan`：`PollBatchPlanner.Build(...)` → `worker.PollAction = planner.PollItemCount > 0 ? planner.Poll : null`；
  变量清空时置 `null`（不空转），并打印"N 个变量 → 每轮 X 次段读 + Y 次单读"
- 删除：`StartVariablePollingTimer` / `StopVariablePollingTimer` / `PollVariables` / `ReadValueByType`

### 5. 事件桥接（原「定时器管理」区整段替换）
- `OnWorkerStateChanged`：状态变化 → `config.UpdateLastConnectedTime()`（Connected 时）→ `config.State = newState` → `OnConnectionStateChanged` 广播
- `OnWorkerCommunicationError`：经 `IsThrottled` 节流后 `LogWarning` + `OnConnectionError`

### 6. ConnectionWorker 补充
- 新增 `private volatile bool _autoReconnect = true` 与公共属性 `AutoReconnect`（语义：是否维持自动重连）
- `ScheduleReconnect` 首行判断 `!_autoReconnect` → `_autoConnect = false` + `SetState(Error)` 直接收尾
- `Connect()` 增加 `_reconnectAttempt = 0`：否则 `Error` 终态后再 `Connect` 会立刻因"重试次数已用尽"再次放弃
- 清理 Manager 中已无用的 `using System.Reflection;` / `using System.Threading;`

## 三、验证结果

- `dotnet build Communication/VM.Communication.csproj` → **EXIT=0**，仅存量的 `Core.Controls` nullability 警告
- `dotnet build CommTest/CommTest.csproj` → **EXIT=0**（验证 `AutoReconnectEnabled` 等公共 API 未破坏）
- 全量 `VisionMaster.sln` 编译 **EXIT=0，0 错误**（`VisionMaster -> bin\Debug\net9.0-windows\VisionMaster.dll` 已产出）
- 构建工具链结论：**全量编译必须用 VS2022 的 `MSBuild.exe`**，不能用 `dotnet build`。
  - `dotnet build VisionMaster.sln` 会在 WPF 项目上生成临时工程 `VisionMaster_*_wpftmp.csproj`，
    该临时工程编译时拿不到 XAML 生成代码，抛 142 条 `CS0103 不存在名称 InitializeComponent` + `CS5001 无 Main`；
    这是 `dotnet build`（SDK 版 MSBuild）对 net48 旧式 WPF 工程的工具链差异，非代码问题。
  - 正确命令：
    ```
    & "D:\Program Files\Microsoft Visual Studio\2022\Community\MSBuild\Current\Bin\MSBuild.exe" `
      "e:\VM\VisionMaster-W-master\VisionMaster.sln" /t:Build /m /v:m /nologo
    ```

## 四、已知边界

1. **构建环境依赖一个软链接**：`DLL/HslCommunication/HslCommunication.csproj` 的 Newtonsoft 引用写的是
   `HintPath=..\packages\Newtonsoft.Json.13.0.4\lib\net45\Newtonsoft.Json.dll`，即 `DLL\packages\`，
   而 NuGet 实际还原到的是**解决方案级** `packages\`（仓库根）。已创建目录联接
   `DLL\packages` → `..\packages` 使该 HintPath 可解析（`packages` 已被 `.gitignore` 忽略，不污染仓库）。
   若该联接丢失，`HslCommunication` 会报约 60 条 `CS0246 未能找到类型或命名空间名"Newtonsoft"`。
   注意：不要删除 `HslCommunication` 的 `obj/bin`，否则会触发该工程的真正重编。
2. **`PreProcessingPlugin` 等并发编辑文件**：与 t6 无交集，但会让全量编译结果产生噪声，需以"报错文件归属"判断。
3. **`NetworkVariableModel.TryWriteToValue` 仍直连 `connection.Write`**（绕过 Manager/Worker 队列），
   `CommunicationSettingsViewModel.ExecuteTestConnection` 仍直连 `connection.Connect()/Disconnect()` —— 均在 t8 收口。
4. **`AutoStart` 尚未生效**：`StartAll()` 目前只在外部显式调用时才连，`AutoStart` 配置项没有人在启动链路里消费（t7）。
5. **轮询线程与 UI 线程**：`config.State` 的通知由 Worker 线程发出，WPF 对标量属性绑定会自动调度到 UI 线程；
   若后续把 `ConnectionsList` 内部元素改动放到 Worker 线程（集合变更），则会崩 —— 现有代码未这么做。
6. **`IsRunning` 仍由 `StartAll/StopAll` 手工置位**，未与 Worker 实际状态挂钩（t7 一并处理）。
7. **未做运行期实测**：本次仅编译验证；批量段数、值正确性、断线重连收敛速度需现场跑一台真实设备确认。
