## 一、需求与决策

### 1. 需求

给图像采集模块增加相机采集能力。参考工程（`WPF-Halcon-流程拖拉`）的做法是：抽象基类 `CameraBase` + 每家相机一个插件工程（大恒 / 海康 / 迈德威视 / Basler / OPT），`PluginService` 扫 `Plugins\Plugin.*.dll`，按 `[Category("相机")]` 归入 `PluginDic_Camera`，`Plugin.GrabImage` 里用 `eImageSource.相机采集` 分支取图。

要求：**标准化、符合设计模式、好扩展**。

### 2. 参考工程值得借鉴的与必须避开的

**借鉴结构**：厂商差异收敛在驱动插件里，使用方只认抽象基类。

**必须避开的三个坑**：

| 坑 | 后果 |
|---|---|
| `CameraBase` 一个类既 `[Serializable]` 做配置、又持 `Image`/`EventWait`/掉线回调做运行态，全靠 `[NonSerialized]` + `OnDeserializing` 手工补救 | 序列化边界脆弱，漏补一个字段就 NRE，且只在"打开旧方案文件"时暴露 |
| `EventWait.WaitOne()` **没有超时** | 相机不触发 → 流程线程**永久卡死**，现场只能杀进程 |
| 相机类型用 `Dictionary<string,...>` 的中文 DisplayName 当 key | 改个字就断链，无编译期约束 |

### 3. 决策清单（逐条与用户确认）

| # | 决策点 | 结论 | 依据 |
|---|---|---|---|
| 1 | 相机归属 | **跟随方案** —— 存 `SolutionModel.CameraConfigs`，随 `.vms` 落盘，入口 = 系统菜单→相机设置 | 与既有 `CommunicationConfigs` 同构；换方案=换产品=常同时换相机工位。"监听端口/令牌"那种"这台机器怎么对外"的才进 AppConfig.json |
| 2 | 采集语义 | **推模式** —— 设备持续出图进帧队列，流程按自己节奏取 | 硬触发产线的真实形态；拉模式每次都要等一次曝光+传输，高节拍下慢 |
| 3 | 取图语义 | **消费为主 + 只读 Peek** —— 生产走 `WaitNextFrame`（每帧只被取一次），预览走 `TryGetLatest`（不消费） | 防"流程跑得比相机快时重复检测同一张图"（同一工件判两次 NG）；防"一开预览窗口就吃掉生产帧导致偶发漏检" |
| 4 | 溢出策略 | **丢旧保新 + 溢出计数告警** —— 容量默认 8 可配；首次溢出立即 Warn，计数暴露到界面 | 处理不过来时继续吃旧帧只会越来越滞后（雪崩）；而"丢帧=漏检工件"，绝不允许静默吞掉 |
| 5 | 掉线处理 | **状态机 + 自动恢复**，流程侧**立即失败**（不阻塞等硬件） | 产线不该因一次抖动停机等人点按钮；流程的职责是"要么给结果、要么明确失败" |
| 6 | 一期范围 | **网络相机（虚拟）+ 独立客户端进程**，真机 SDK 留二期 | 虚拟相机是可测性基础设施：能注入丢帧/掉线/延迟，把上面 3、4、5 三条策略当场验出来；真机反而做不到 |
| 7 | 推图通道 | **HTTP 每帧一请求** —— `POST /camera/{序列号}/frame` | 客户端几十行 HttpClient 就能写完；断线/超时天然可观测。**明确代价**：本地回环 33 req/s 无压力，但这不是产线形态（真机走 GigE），属于"用真实性换可验证性"的有意取舍 |
| 8 | 服务归属 | **宿主新起 `NetworkCameraServer`，独立端口 19100** | `HttpImageServer`(19000) 承载已上线的"网络推送"，改它有回归风险；且两者语义完全不同（只留最新帧 vs 消费+环形缓冲+溢出计数） |
| 9 | 配对键 | **相机序列号 `SerialNo`**（内部引用仍用 Guid，序列号只做入口寻址） | 序列号是真实相机本身就有的概念，换真机时客户端配对方式一字不改；改名不失联（参考工程的中文名 key 就是反例） |
| 10 | 在线判定 | **心跳 + 帧超时双判据** | HTTP 无连接，只能靠"多久没消息"推断；而"客户端在但没推图"与"客户端没了"必须分开——前者是正常，后者是故障 |

### 4. 关键决策 10 的推演：为什么必须分开"在线未触发"与"掉线"

现场看到"没有图"时的第一句话必然是"相机到底在不在"。这两种情况的原因与处置完全不同：

- **在线但没送帧**（用户按了暂停 / 图片放完）→ 该去查触发链路，**不该报故障**；
- **掉线**（客户端进程挂了 / 网线松了）→ 该报故障。

只靠"多久没收到帧"来判，用户一按暂停界面就报"相机掉线，正在重连"，运维会去查一个根本不存在的故障；而真正该修的问题（流程太慢导致溢出）反而被这条噪声盖住。

**心跳的作用就是这个**：客户端每秒发一次 `POST /camera/{序列号}/heartbeat`，与推图节拍**无关**（暂停推图时心跳照发）。心跳停 3 秒 → 判掉线，清空陈旧帧；心跳恢复 → 自动回到在线/采流状态。

## 二、架构

```
① 契约层   Shard\Core.Interfaces\Camera\        纯接口 + DTO + 驱动基类，零第三方依赖，不引用 Halcon
              ICameraDevice / ICameraProvider / CameraDescriptor / CameraSettings / CameraFrame
              CameraDeviceBase（推模式骨架：环形队列 + 溢出计数 + 状态机 + 心跳看门狗）
              IExecutionContext.Cameras ← 插件与宿主之间唯一的能力通道

② 宿主服务  VisionMaster\Services\Camera\
              CameraProvider        方案级相机配置 ⇄ 运行态设备表的唯一对接处
              NetworkCameraServer   HTTP 收图 + 心跳，独立端口 19100
              CameraModule          自装配（注册/启动/退出收尾）

③ 驱动层    Plugins\Plugin.Camera.Network\
              NetworkCameraDevice   只写"网络相机与真机的差异点"，队列/状态机全由基类固化

④ 使用层    Plugins\Plugin.ImageAcquisition\
              AcquisitionMode.Camera + AcquireFromCamera：调 context.Cameras，从不碰任何相机 SDK

⑤ 独立工具  Tools\VirtualCameraClient\   选图片文件夹、按节拍/手动推帧、独立心跳
```

**加一家真机相机 = 加一个只实现 `OpenCore` / `CloseCore` / `ApplySettingsCore` 的插件工程**，使用层与宿主一行不改。

### 两条硬纪律（写在 `CameraDeviceBase` 的注释里）

1. **SDK 收图回调线程绝不阻塞**。大恒 / 海康 / HALCON 的 SDK 都一样，回调里一阻塞就会内部队列溢出、丢帧甚至掉线。回调只做"拷一份 + 入队"。
2. **帧队列有上限且溢出必须可见**。这是与"绝不漏检"之间唯一诚实的折中：丢是必须丢的（否则雪崩），但必须让现场看得见。

### 为什么 `CameraFrame` 装的是 `byte[]` 而不是 `HImage`

`Core.Interfaces` 是 `net9.0` 纯托管层，**刻意不引用 Halcon**（与既有 `HubImageItem` 同一约束）。硬塞 `HImage` 会把 halcondotnet 拖进契约层，进而要求每一个相机驱动插件都与宿主共用同一个 HALCON 版本——那正是"换一家相机就要把全部插件重编一遍"的来源。

分工：驱动负责「SDK 缓冲 → 原始像素」（唯一一次拷贝），消费者负责「原始像素 → HImage」。
**附带一个很实在的好处**：队列里全是托管 `byte[]`，所以帧的淘汰、清空、丢弃都不需要 `Dispose`，设备实现里不存在"忘了释放"这条泄漏路径。

## 五、已知边界

1. **HTTP 每帧一请求不是产线形态**。它验证不了真实相机的 GigE 带宽/丢包行为。这是决策 7 明确接受的取舍；二期接真机 SDK 时才是产线路径。

2. **虚拟相机没有"枚举设备"这一步**。参考工程是"选类型→搜设备→添加"三步，网络相机改成"选驱动类型 + 填序列号"。相机设置界面的流程因此按驱动类型分叉。

3. **网络相机的曝光/增益/触发模式由客户端决定，软件侧设了不生效**。这三项在界面上必须明确标注；而 `FrameTimeoutMs` / `BufferCapacity` / `HeartbeatTimeoutMs` 是**真实生效**的（由基类消费）。已在 `NetworkCameraDevice.ApplySettingsCore` 注释与相机设置界面说明里写明。

4. **相机模式的"索引/总数"输出口语义重载**。`CurrentIndex` 改为表达"第几帧"、`TotalFiles` 改为表达"累计收到多少帧"（端口描述文案仍是原文件夹模式的文字）。加一对新输出口会让下游接线全要重连，故沿用。若后续要严谨区分，应新增 `FrameId` / `ReceivedCount` 两个输出口。

5. **相机图像预览只在相机设置界面**。配置态插件只拿到 `CameraOption` 快照、拿不到设备对象，硬要预览就得让插件持有宿主对象（破坏"插件只认契约"）。采集步骤侧要验证能否取到图，走配置窗口的「执行」试运行即可。

6. **仓库里有外部并发改动**（不是本次工作引入）：
   - `VisionMaster.sln` 在 11:48 被外部改动，新增 `Plugin.ColorCheck` / `Plugin.BlobDetect` / `Plugin.Ocr` / `Plugin.CodeReader` 四个工程，但 `Plugin.CodeReader` 的声明 GUID（`C8F5D3A2…`）与它自己的 13 处配置/嵌套引用（`3F8C2A47…`）不一致，形成孤儿 GUID，**导致整个解决方案无法加载**（`MSB5023`）。已改声明侧一行使其自洽（SDK 风格工程无 `ProjectGuid`，两侧等价）。
   - `FlowCanvasChecks\ColorRegionCheck.cs` 同批新增，编译报 `CS0246: 未能找到类型或命名空间名"DrawShapeType"`，**未修**（不属于本次范围，且不清楚其意图）。
   - 构建中多次出现 `CS2012: 无法打开 … because it is being used by another process`，说明还有另一个进程在同时构建本仓库。

7. **方案"未保存"提示是既有设计缺口**。仓库刻意不用脏标记，改由 `SolutionDraftService` 退出时逐字比较内存与磁盘来决定是否转存草稿；Shell 没有实时"* 未保存"指示。相机配置改了会被逐字比较自然发现，但用户仍需手动保存。

8. **真机驱动未做**。`CameraDeviceBase` 已预留 `NotifyDeviceLost(reason)`（供 SDK 掉线回调）与 `RequiresHeartbeat`（真机 false）。真机的**后台退避自动重连**（1s→2s→5s→10s）尚未实现——网络相机的"重连"是等心跳回来（无需主动动作），所以一期不需要它。

9. **`DevicesChanged` 回声抑制依赖界面比对**（`CameraSettingsViewModel.RowsMatchProvider()`）。若后续调整 `DevicesChanged` 的语义，这里需同步检查。

## 六、缺陷修复记录

### 修复 1：打开相机设置抛 `XamlParseException`（TwoWay 绑到只读属性）

**现象**：点「系统 → 相机设置」直接抛

```
Message=“设置属性“System.Windows.Controls.TextBox.Text”时引发了异常。”，行号为“516”，行位置为“37”。
内部异常: InvalidOperationException: 无法对“…CameraSettingsViewModel”类型的只读属性“NetworkFrameUrl”
          进行 TwoWay 或 OneWayToSource 绑定。
```

**根因**：`TextBox.Text` 的绑定模式**默认是 TwoWay**，而 `NetworkFrameUrl` / `NetworkHeartbeatUrl` 的 setter 是 `private set`——从绑定引擎角度看就是**只读属性**。给它绑 TwoWay，WPF 在解析 XAML 时直接抛异常。

**修法**：这两个只用于展示（`IsReadOnly="True"`）的地址框显式声明 `Mode=OneWay`。

**为什么编译期发现不了**：XAML 的绑定模式与只读性冲突是**运行时**校验的，`dotnet build` 只做 BAML 编译，绑定路径/模式要到 `InitializeComponent()` 真正解析时才检查。所以"0 错误"完全不代表 XAML 绑定没问题——**新增对话框必须真打开一次**。

**同类风险的全量排查**（已做）：
- 该视图所有 `TextBox.Text` 绑定：只有上述两个是只读属性；`AutoConnect` / `ExposureTimeUs` / `Gain` / `FrameTimeoutMs` / `BufferCapacity` / `HeartbeatTimeoutMs` / `NewSerial` / `NewDisplayName` 的 setter 都是 public，TwoWay 正常。
- 读只读属性的绑定（`StateText` / `StateDetail` / `OverflowCount` / `DroppedFrameCount` / `ReceivedFrameCount` / `PendingFrameCount` / `OverflowWarning` / `NetworkTokenText` / `NetworkListeningText` / `HasPreviewImage`）**全部挂在 `TextBlock` / `Visibility` 上**，这些的默认模式是 OneWay，不受影响。
- 视图引用的 29 个 `{StaticResource}` 键**逐一核对**在 `UI\Controls\Themes\` 中均有定义（键不存在同样是运行时 `XamlParseException`）。
- `VirtualCameraClient\MainWindow.xaml` 同样排查：5 个 `TextBox.Text` TwoWay 绑定的 setter 均为 public；`LogText` 已显式 `Mode=OneWay`。

## 七、给后续开发者的三条纪律

1. **新建相机驱动**：只继承 `CameraDeviceBase`，只写 `OpenCore` / `CloseCore` / `ApplySettingsCore`（真机再加"SDK 回调里调 `PushFrame`"）。**不要自己写队列、状态机或超时逻辑** —— 基类里那三件事是全部相机共有的，各写一遍必然有的对有的错。
2. **等图必须有超时**，且要能响应 `CancellationToken`。无超时的等图 = 现场只能杀进程（参考工程的原罪）。
3. **丢帧必须计数并暴露给界面**。`OverflowCount` 与 `DroppedFrameCount` 分别表达"处理不过来"与"掉线/停止丢弃"，两者原因与处置完全不同，不要合并。
