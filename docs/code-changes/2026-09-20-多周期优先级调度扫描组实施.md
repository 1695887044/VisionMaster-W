# 多周期优先级调度（扫描组）实施记录

日期：2026-09-20
依据：`docs/code-changes/2026-09-20-多周期优先级调度扫描组详细设计.md`（§7 交互规格 / §13 十二步实施顺序）
目标：让一条连接下的变量按"扫描组"分组、各组独立周期采集（对标 KEPServerEX Scan Class），为对接几万点的商业 SCADA 采集铺路
状态：**第 1\~11 步已完成，`VM.Core`** **/** **`VM.Communication`** **/** **`VisionMaster`** **编译全部 EXIT=0；第 12 步（手工用例）待验证**

## 1. 需求与决策

用户指令："先详细设计多周期优先级调度方案" → 批准后"开始吧 把地基打牢 这个通信系统 是为了对接后面商业的Scada软件采集"。

### 关键决策（D1\~D13）

| 编号  | 决策                                           | 理由                                                      |
| --- | -------------------------------------------- | ------------------------------------------------------- |
| D1  | 命名"扫描组"                                      | 与 KEPServerEX Scan Class / Ignition Tag Group 对齐，用户一眼懂  |
| D2  | 组表挂在**连接**上（不是全局）                            | 周期是通信资源的属性：一条连接的波特率/请求能力决定它能跑几档节拍                       |
| D3  | 保留 `ReadCycleMs`，语义收敛为**默认组周期**              | 老方案零回归；避免"周期有两个真相源"                                     |
| D4  | 抽出独立 `PollScheduler`（不塞进 `ConnectionWorker`） | 调度策略与线程/连接生命周期解耦，可单测、可复用                                |
| D5  | 周期**升序**即优先级；一拍内跑完所有到期组                      | 优先级不是"抢占"，而是"谁先跑"；慢组不阻塞快组                               |
| D6  | 计划**全量重建**（不做增量）                             | 重建 O(N) 且只在"变量/组表变更 + 建连"时发生，几万点几十毫秒可接受；增量带来的状态一致性风险不值得 |
| D7  | 单连接扫描组上限 **8**                               | 超过 8 档节拍，段切碎导致的请求数上升会吃掉多周期的收益                           |
| D8  | 删组 → 变量回落默认组；改名 → 级联改变量                      | 安全侧设计：宁可采集慢一点，不可丢点                                      |
| D9  | 写命令**插队不做**                                  | 写是低频人工操作，当前"写后由下一拍读回"足够                                 |
| D10 | 组级死区**不做**                                   | 死区已按点实现（P0 第一批），组级再做会与点级冲突                              |
| D11 | **默认组不落盘**（虚拟组）                              | 老方案文件组表为空 → 全部变量走默认组 → 行为与改造前完全一致                       |
| D12 | 编辑器里拖动排序**仅影响显示顺序**                          | 优先级恒由周期决定，避免"顺序与周期不一致"的双真相源                             |
| D13 | 编辑器入口 = 连接设置操作列追加图标按钮                        | 不新开顶层菜单，入口贴着"这条连接"出现                                    |

### 两个正交维度（务必区分）

- `ScanGroupConfig`（连接级**组表**）：决定"这条连接有几档节拍"
- `PollAddress.GroupKey`（协议**存储区分组**）：决定"轮询请求怎么合并成块读"（DB7/M/FC3/FC1）
- 两者互不影响：同一扫描组内仍照常按存储区批量合并。

## 4. 已知边界

1. **第 12 步手工用例**：6 个用例中 5 个已固化为 `CommChecks` 离线断言（见第 5 节）；仅剩「诊断实测周期」必须实机（真 PLC）才能测。
2. **换连接后组名失效**：变量改了 `ConnectionName` 后，原组名在新连接不存在 → 下拉会显示"默认组"并把模型回落为空串（安全侧，不丢点），但**不会**弹提示。设计文档原计划的"黄点提示"未做，仅用 ToolTip 说明语义。
3. **组表复制到其他连接**：编辑器支持，但两条连接的存储区/协议不同时，地址段合并效果会不同（诊断区显示的段数是各自连接的真实口径）。
4. **在线改组的瞬时抖动**：`UpdateConnection` 会重建连接（`State` 回落到 `Disconnected`），编辑器内已用 `wasConnected → RequestConnect` 补偿，但会有一次断连-重连的可见抖动。
5. **组数上限 8** 是编译期过滤（`Resolve` 里 `break`），不是 UI 硬拦；UI 侧由编辑器限制，若手工改 JSON 超限则多余组被静默忽略（变量回落默认组并计入 `fallbackCount`，可在诊断区看到）。
6. **Core 不引用 Communication**：`VariableNode` 里不能写 `PollScheduler.DefaultGroupName`，默认组文案由 VM 侧注入——后续若有人想在 Core 里用该常量，需先解决工程依赖方向。

## 5. 第 12 步验证收口（2026-09-21）

### 5.1 期间发现并修复的缺陷：变量级扫描组不落盘

**现象**：在变量管理里给网络变量选了「快组」→ 保存方案 → 重开方案，扫描组静默退回「默认组」。

**根因**：`ScanGroup` 只活在内存对象图上，落盘链路的三个环节都把它丢了：

| 环节 | 文件 | 缺什么 |
| --- | --- | --- |
| 存盘快照 | `Core\Models\Variable\VariableDto.cs` | `VariableDto` **没有 `ScanGroup` 字段** |
| 网络变量 → DTO | `VariableDto.FromNetwork(nv, protocol)` | 没有把 `nv.ScanGroup` 抄进 DTO |
| DTO → 模型 | `VisionMaster\Services\VariablePersistenceService.cs` 的 `Restore` | 没有把 `dto.ScanGroup` 还原到 `NetworkVariableModel.ScanGroup` |

**为什么这个缺陷很隐蔽**：`NetworkVariableBridge.Register` 里的 `ScanGroup = nv.ScanGroup` 是**唯一**把组名灌进 `CommunicationVariable` 的通道。快照丢了字段 → 还原时模型是空串 → 桥接把空串抄进去 → 归桶走默认组。全程不报错、不打日志，只在节拍上看不出快慢。

**修复**（3 处，全部保留零回归语义）：

```csharp
// VariableDto.cs —— 新增字段
public string ScanGroup { get; set; } = string.Empty;

// VariableDto.FromNetwork —— 拷贝
ScanGroup = nv.ScanGroup ?? string.Empty,

// VariablePersistenceService.Restore —— 还原
ScanGroup = dto.ScanGroup ?? string.Empty,
```

`?? string.Empty` 是关键：**旧方案 JSON 里没有这个字段**，反序列化得到 null，回落空串 = 默认组，行为与改造前**逐字节一致**。

### 5.2 新增断言宿主 `CommChecks`

**为什么另起工程而不是复用 `CommTest`**：`CommTest` 是**实机联调**工程（要求 Modbus TCP 502 / S7 108 模拟器在线），且只引 `VM.Communication`、拿不到 `VisionMaster.Models` 的 `VariableDto` / `SolutionModel`，无法断言"扫描组随方案落盘"。两者目标相反。

`CommChecks` 照 `ScadaChecks` 骨架（`net9.0-windows` + `UseWPF` + 只引 `..\VisionMaster\VisionMaster.csproj`），已接入 `VisionMaster.sln`（不进 `NestedProjects`，与 `ScadaChecks` / `FlowCanvasChecks` 一致挂解决方案根）。

**5 段共 60 条断言**：

| 段 | 主题 | 条数 | 关键断言 |
| --- | --- | --- | --- |
| C1 | 组表过滤边界（`PollScheduler.ResolveGroupNames`） | 13 | 默认组恒首位；`ReadCycleMs=0/-5` 回落 1000；保留名/越界周期/空名被剔除；边界值闭区间接受；重名取首个；自定义组封顶 8（被剔除的不占额度） |
| C2 | 归桶 / 回落 / 不丢点（`PollScheduler.Create`） | 12 | 空集与全 `WriteOnly` → null；**变量数守恒**；组按周期升序；同组相邻地址合 1 段；不同组不合并；不存在组回落默认组且**回落汇总只出一条日志**；空组整组跳过 |
| C3 | 改名级联 / 删组回落（`ReassignScanGroup`） | 16 | 改的是注册表里**同一实例**（引用未换）；`newName=null`/纯空白 → 回落；幂等返回 0；空参数不抛；`GetScanGroupPreview` 支持 `configOverride` 且不要求连接在线 |
| C4 | 组表复制（`CommunicationConfig.Clone` / `CopyFrom`） | 9 | 深拷（容器与元素都非同一引用）；改副本不影响原件；`PollHint` 收到通知；组表为 null 不抛 NRE |
| C5 | 变量级扫描组落盘往返 | 9 | 序列化文本里**真的有** `"ScanGroup"` 字段；反序列化存活；`Restore` 还原；还原后组名能归进对应组（端到端闭环）；旧方案缺字段 → 空串 |

**C3 段的技巧**：`RegisterVariable` 只校验 4 项非空、**不查连接存在性**，所以整段可以 `new AdvancedCommunicationManager { AutoReconnectEnabled = false }` 后直接注册变量，**零后台线程、零设备依赖**——这是"离线可跑、可进 CI"的前提。

**C5 段的技巧**：C5-8 用 `JObject` / `JArray` 逐项 `Remove("ScanGroup")` 手工剥出"旧方案"，C5-9 断言缺字段回落空串——把"零回归"从口头承诺变成可执行断言。
