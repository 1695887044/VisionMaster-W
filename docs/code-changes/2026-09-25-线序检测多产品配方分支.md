# 线序检测：多产品配方 + 条件分支（2026-09-25）

## 一、需求与决策

**需求**：`Image\颜色\` 下新增 `cable2.png`（**10 芯**），要做一个"复杂一点的流程"，用上逻辑分支。
用户明确要求：**"你要做预处理什么的，用算法计算，而不是问我"** —— 芯数与线序必须自己算出来。

**逐条确认的决策**：

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| 1 | 复杂在哪 | **多产品配方 + 条件分支**（用户选项） | 正好用上新增的 cable2 |
| 2 | 流程骨架 | 采集 → 找线 → **选配方(If/ElseIf/Else)** → 比对 → **结果分流(If/Else)** | 5 步、2 个容器节点 |
| 3 | 芯数从哪来 | **算法反推**（等间距规整化），不做成配置项 | 用户要求"用算法计算" |
| 4 | 配方放哪 | 分支体里的**「变量赋值」**节点 | 分支才有事可做，条件与配方分开 |
| 5 | 节点间怎么交接 | **运行时变量**（脚本 `SetVar` / 条件表达式直接引用） | 不落全局变量、不写盘，跑完即弃 |
| 6 | 找线与比对 | **拆成两个脚本节点** | 换产品只动配方，算法一个字不碰 |
| 7 | 未知芯数 | 走 Else → 配方置空 → 比对明确报"未知产品" | 产线上宁可误停不可误放 |

## 二、算法：等间距规整化（本次的核心）

### 为什么"按间隙切分"在新图上必然失手

量 `cable2.png` 得到两条硬事实：

1. **线束在连接器附近是密排的** —— 线之间的缝是 V≈165 的**暗影**，不是亮背景；
   任何"亮度回落即缝隙"的规则会把整块都判成线（我第二个原型就栽在这，cable1 都算成了 7 根）。
2. **白线/浅灰线与浅色背景只差几个灰阶** —— 实测白线 `(218,218,223)` vs 背景 `(215,217,222)`，
   差 5 个灰阶。**任何按颜色判线的规则都抓不到它**。

### 破法：先抓能确定的，再按等间距把漏的补回来

```
① 逐行取采样带的中位色（±3 列取中位，抗噪）
② 判「可靠线像素」：暗(mx<150) 或 彩(delta>40) 或 极亮(mx>240)   ← 故意不指望抓到白线
③ 连续可靠行 ≥4 行才算一段 → 得到若干"线的中心"
④ 线距 = 相邻中心差的中位数        ← 取中位，漏检造成的 2 倍间距会被自动忽略
⑤ 线数 = round(跨度 / 线距) + 1    ← 芯数由算法反推，不配置
⑥ 按等间距铺开：能对上已检出段的用它干净的中位色（避开两侧暗缝），
   对不上的（就是白线/浅灰线）用规整位置附近的窗口色
⑦ 分类
```

**实测验证**：

| 图 | 粗检到 | 相邻中心差 | 中位线距 | 跨度 | **反推线数** | 结果 |
|---|---|---|---|---|---|---|
| cable1 | 5 段 | 21,21,21,18 | 21 | 81 | **5** ✓ | 黑,棕,玫红,红,黄 |
| cable2 | 9 段 | **43**,20,20,22,26,17,20,19 | 20 | 187 | **10** ✓ | 黑,**白**,灰,紫,蓝,绿,黄,红,玫红,棕 |

cable2 的 9 段里那个 **43 正好是 20 的两倍多** —— 漏了一根（白色那根），规整化把它补了回来，
线数 10 与用户所说一致。cable1 的结果与既有黄金参照**完全一致**，旧断言不作废。

### 分类表的三处修正（都是实测撞出来的）

| 现象 | 原因 | 修法 |
|---|---|---|
| cable1 的棕线被判成灰 | 灰/棕都是低饱和，只按明度分不开 | 棕 = 低饱和 **且偏暖**（R−G≥12 且 R−B≥12）**且偏暗**（V<175） |
| cable2 的紫线被判成蓝 | 色相分界 260° 落在紫(252°)与蓝(209°)之间偏外侧 | 分界挪到 **230°** |
| 红与玫红分不开 | 两者色相只差十几度，且都 B>G | 按色相分：**[330,350) 玫红；[350,360)∪[0,20) 红** |

## 四、顺带挖出的两个平台 bug

### bug 1：「变量赋值」节点只要手填参数就永远编译不过

编译期的必填检查是 `IsRequired && LinkedSource == null` —— **只看有没有连线，不看有没有填值**。
而 `InputPort.IsRequired` 默认就是 `true`，`VariableAssignmentPlugin` 把 `Name` 显式写成 true、
另两个没写 → 三个端口全成了"必须连线"。可这三个参数本来就是**界面上手填**的。

表现：分支里放一个「变量赋值」→ 编译报 9 条「必填参数 Name/Value/CreateIfNotExists 未配置」。
修法：三个端口显式 `IsRequired = false`。**这是全局修复**，该节点从此手填值可用。

### bug 2：C#脚本的动态端口依赖 InputVars 的运行时类型

`CSharpScriptPlugin.InputVars` 的声明类型是 `ObservableCollection<ScriptVarDef>`，
`ApplyConfigValues` 按声明类型做转换。用 `List<ScriptVarDef>` 塞进去**转换不过、集合静默变空** →
`RebuildDynamicInputs` 建不出动态端口 → 编译期报「'找线' 没有名为 'Image' 的输入端口」。
只影响程序化生成 `.vms` 的场景；主程序自己保存的文件天然是 ObservableCollection，无此问题。

## 五、脚本侧踩到的两个坑

1. **脚本上下文里没有 `InstanceName`** —— 它是插件属性，不是脚本变量。
   写 `Context.Info($"{InstanceName} ...")` 会在运行期报
   「The name 'InstanceName' does not exist in the current context」。引擎本来就给日志加了步骤前缀。
2. **`Decompose3` + `new HImage(...)` 这条路会报 `HALCON error #4056: object-ID is NULL`**。
   改成**元组版 `GetGrayval`**：一次调用取回整条采样带（整高 × 条带宽）的所有灰度，
   再按 `AccessChannel` 逐通道取。既不必包 `HImage`、不用管句柄，还比逐点调用快两个数量级
   （10080 次调用 → 3 次）。

## 七、补修：画布节点图标全没了（用户反馈）

**现象**：打开方案，画布上所有步骤都没有图标。

| 条件分支 | `\uf0e8` | `PluginService` 的 `BuiltIn_If` |

**教训**：用代码造节点时，凡是「工具箱里能看到的属性」（图标、描述）都要显式补齐 ——
界面上新建节点时框架会自动带，代码造的时候没人替你带，而这类缺失**不报错、只难看**，

## 八、补修：「变量绑定」窗口不回显当前值（用户反馈）

**现象**：双击分支里的「变量赋值」节点，弹出的「变量绑定」窗口里「常量值输入」是**空框**，
看不到已经填好的配方，只剩一行灰字提示。

**根因（第一版定位错了，这里记准确）**：手填的值存在 **`InputValues`** 里，**不是** `LinkedSources`。

`StepModel` 上"端口的值从哪来"有**两条**路，运行期 `ApplyConfigValues` 的取舍是
「**有连线就以连线为准**（`IsLinked` 就跳过 InputValues），没连线才用手填值」：

| 来源 | 存在哪 | 谁写的 |
|---|---|---|
| 手填常量 | `InputValues[端口名]` | 插件 `OnConfirm`（配置窗口确认时回写） |
| 常量 / 上游端口 / 变量 连线 | `LinkedSources[端口名]` | 变量绑定窗口 `Confirm` / `DoFinalBind`，或画布连线 |

而 `VariableBindingViewModel.BuildTree` 建左侧端口表时**只读了 `LinkedSources` 的显示地址**，
`SelectedInputPort` 的 setter 又只调 `UpdatePresetOptions()`（只管功能性枚举端口）——
于是**手填的值永远回显不出来**，常量框一直是空的。

**第一版为什么没修好**：我只查了 `LinkedSources`，没查 `InputValues`。
**断言为什么没拦住**：我造用例时把三个端口都造成「常量连线」，
绕开了"手填值"这条真实路径 —— 代码明明不对，用例却全绿。
修好夹具后补了一条**前提断言**（"Name 的值必须存在 InputValues 而不是 LinkedSources"），
把这个坑固化下来：以后谁改了夹具的建模方式，前提断言先红。

**顺带发现的更严重问题**：`Confirm()` 的规则是「常量框非空就写常量」，而**换端口不会清空这个框**。
所以「选中 A 端口填了值 → 再点 B 端口看看 → 点确定」会把 A 的值写到 B 上——
界面上毫无异常，被静默写坏的是另一个端口的绑定。

**修法**（`VariableBindingViewModel .cs`）：

| 改动 | 内容 |
|---|---|
| 新增 `LoadExistingConstant()` | 挂在 `SelectedInputPort` 的 setter 上，**每次换端口**都执行：先清空；有连线则按连线（只有常量连线才回显其值）；没连线则回显 `InputValues` 里的手填值 |
| 新增 `ResolveBindKey()` | 取键口径统一：条件节点用端口描述、其余用端口名，与 `DoFinalBind`/`Confirm` 三处一致 |
| 新增 `ExtractConstantText()` | 优先取 `TargetPortName`（`Confirm` 写入时放的就是原值），取不到再剥 `LinkProtocol.ConstantDisplayPrefix` 前缀 |
| 改 `UpdatePresetOptions()` | 原来无条件 `ConstantValue = PresetOptions.First()`，会把刚回显的值冲掉；改为**只在空着时**才退到第一个预设项 |

**两条设计红线**（都写进注释了）：

1. **换端口必须重置常量框** —— 要么回显该端口自己的值，要么清空，绝不能留上一个端口的残留。
2. **连线的文本不许进常量框** —— 只回显 `LinkKind.Constant`；上游端口/全局变量/运行时变量的
   来源由左栏以地址展示，塞进常量框会让"点确定"把连线改写成常量，等于悄悄把线拆了。

**新增断言**（`FlowCanvasChecks\VariableBindingCheck.cs`，5 条，直接驱动 ViewModel 不碰 WPF 控件）：
前提（值存在 InputValues）/ 打开即回显手填值 / 换到常量连线端口回显其常量 / 换到连线端口常量框清空 / 换回来值还在。

**验证**：整仓构建 0 错误；FlowCanvasChecks **421 通过 / 0 失败**；ScadaChecks 1691 通过 / 0 失败。

## 九、给「变量赋值」做专属配置界面（用户反馈：通用绑定窗口容易误解）

**用户的判断**：打开「变量赋值」看到的是通用「变量绑定」窗口，三栏并列、看不出先做哪步，容易误解。

**为什么通用窗口在这里别扭**：它是"给**任意端口**绑**任意数据源**"的通用工具，
而本节点只有"给一个变量赋一个值"这么简单的事。用通用工具表达简单意图，用户就得替工具消化概念差。

| # | 通用窗口的具体误导 | 根因 |
|---|---|---|
| 1 | 三栏并列，像三个平等选项 | 实际是两步：左选端口 → 右给值，界面没有引导 |
| 2 | 「选择上游算子」把整条流程都列出来 | 通用窗口不按类型过滤；对"给 Name 填常量"完全无关，还混着别的分支里的同名节点 |
| 3 | 右下角冒出 `Success` / `ErrorMessage` | 那是"你选中的上游节点"的输出口，但界面没写归属 |
| 4 | 概念层级多 | 输入端口 / 绑定 / 常量 / 上游输出 一整套，用户想的是"把 Expected 设成 xxx" |
| 5 | 常量框不提示该填什么类型 | 端口有 String / Bool / Object 之分，提示只有一句通用的话 |

**做法**：给插件实现 `IPluginCustomViewProvider`，用三行表单把语义摊平：

```

变量名   [Expected                    ]            🔗 ✕
值       [黑,棕,玫红,红,黄            ]            🔗 ✕
☑ 变量不存在时自动创建

「值」填常量文本；要引用上游步骤的结果，点该行尾部的链接图标。
```

| `Plugins\Plugin.Utility\VariableAssignmentView.xaml.cs` | **新增** | 纯壳，无业务逻辑 |
| `Plugins\Plugin.Utility\VariableAssignmentPlugin.cs` | 改 | 实现 `IPluginCustomViewProvider.GetConfigView`（`Initialize(stepData)` + `DataContext = this`，与其它插件同一约定） |

**顺带修的 bug**：`LinkableValueEditor.IsTextEditableType` 的白名单是

## 十、变量赋值支持「全局变量」作用域（用户反馈）

**用户诉求**：想用「变量赋值」把流程里的 HImage 写进**全局变量 `Img`**，从而把「变量定义」和「图像赋值」两个节点从流程里删掉。

**先说清他们那条报错的性质**（不是 bug）：

```
[连线类型不匹配] '变量赋值_5' 的输入端口 'Name' 期望 String，但上游 'Global' 提供的 'Img' 是 HImage
步骤[线序检测.变量赋值_5] 执行失败: 本地变量 全局变量 (Global).Img 不存在
```

`变量名` 端口要的是**变量名的文本**，而它在变量绑定里把 `Img` 这个**全局变量本身**连给了它 →
HImage 塞不进 String（类型守门正常拦下）→ 运行期又拿那串地址文本当名字查 → 找不到。
**正解是「变量名」那格直接打 `Img`。**

**先核实的三处底细**（决定了能不能做）：

| 环节 | 结论 |
|---|---|
| 变量管理能否建「图像 (HImage)」类型的变量 | ✓ 能（`GlobalVariableManagerViewModel:453`） |

### 踩到的真坑：枚举端口不能经 InputValues 往返

第一版把作用域写成 `InputPort<VariableScope>`（枚举），存盘后是 `"Scope": 1`，
再打开时 `ApplyConfigValues` 把它赋给端口 → **直接抛异常**：

```
InvalidCastException: Invalid cast from 'System.Int32' to 'VisionMaster.Plugins.Util.VariableScope'.
```

`InputPort<T>.Value` 的 setter 对枚举只做硬转换，不做"从数字/文本解析"。
（图像采集的 `Mode=0` 之所以一直没问题，是因为它是 `[StepConfig]` **属性**，走的是另一条带转换的路径。）
**改成 string 端口**（`"Runtime"` / `"Global"`），两端都能无损往返；
并且加**取值白名单校验** —— 认不出来就报错，绝不"不是 Global 就当 Runtime"，
否则拼错一个字母会把结果静默写到另一个变量池里。

**这个坑是离屏渲染探针抓出来的**：探针在 `Initialize(stepData)` 那一步就炸了，
而单看代码、单跑断言都不会暴露 —— 这也是为什么每轮改视图都要真渲染一遍看。

**新增断言**（`VariableAssignmentCheck.cs`，8 条）：

| # | 断言 | 结果 |
|---|---|---|
| 1 | 全局变量注册后按名可查（注册表订阅了集合变更） | ✓ |
| 2 | 【运行时】不存在 + 勾自动创建 → 建成并赋值 | ✓ |
| 3 | 【运行时】已存在 → 覆盖为新值 | ✓ |
| 4 | 【运行时】不存在 + 没勾 → 明确报「不存在」 | ✓ |
| 5 | 【全局】目标存在 + 值是 HImage → **写进全局变量** | ✓ 变量现值 = HImage |
| 6 | 【全局】目标不存在 → 明确报错、**且不新建变量** | ✓ 变量数 14 → 14 |
| 7 | 【全局】类型不匹配（int 变量写文本）→ 明确报错 | ✓ |
| 8 | 作用域取值拼错 → 明确报错，不静默当成运行时 | ✓ |

前 4 条是为了证明**既有行为没被碰坏** —— 这个节点在既有流程里到处都是。

### 已知边界

1. **「不存在就新建」没有做**，两条理由：
   - **SCADA 绑定是设计时动作**：变量不在变量管理里，右侧 `ƒx` 就选不出它，新建救不了设计时；
   - **跨线程**：`GlobalVariables` 是 UI 绑定的 `ObservableCollection`，而流程跑在后台线程上，
     从插件路径往里插会踩 WPF 跨线程；要做需要额外设计（如"待创建队列 + UI 线程消费"）。
   现在的行为是**明确报错并给出中文原因**，与「图像赋值」当初的决策一致。
2. **作用域是字符串参数**（`Runtime` / `Global`），不是枚举 —— 原因见上。
3. **「图像赋值」插件保留未删**：新路径跑通前先留着，避免出现"两个都不能用"的空窗。
4. 「变量定义」节点与本改动无关（它建的是**运行时**变量），删不删都不影响全局变量。

## 十一、修「保存方案失败：HALCON #4056 serialize_image」（用户反馈）

**现象**：保存方案弹红条

```
保存方案失败: HALCON error #4056: Image data management: object-ID is NULL (0) in operator serialize_image
```

**根因**：`VariablePersistenceService.Capture` 把全局变量的**值**原样塞进了快照：

```csharp
case LocalVariableModel local:
    snapshots.Add(new VariableDto {
        ...
        DefaultValue = local.DefaultValue,   // ← object
        Value = local.Value                  // ← object
    });
```

而 `VariableDto.DefaultValue` / `Value` 的注释写明约定是「**JSON 原生编码：数字/字符串/布尔/数组**」。
图像变量的值是个 `HImage` —— Newtonsoft 序列化它会走 Halcon 自己的序列化（`serialize_image`），
句柄为空（未初始化 / 已释放）就抛 #4056。**而这一抛发生在"保存方案"里，于是整个方案都存不下来。**
（就算句柄有效，把整幅像素写进 `.vms` 也是荒唐的。）

**修法**：`Capture` 增加 `PersistableValue` 白名单 —— 只有
数字 / 字符串 / 布尔 / 枚举 / `DateTime` / 由它们构成的数组才落盘，其余（`HObject`、自定义对象、位图类第三方对象）
一律落 `null`。**只存定义（名字/类型/描述/稳定身份），不存值。**

这不是"权宜之计"，而是与平台既有口径一致：
`VariableNode` 写着「图像的来源本就是流程，不是手填」，
`VariableValueConverter` 写着「位图不是一段文本，手填这条路根本不存在」——
图像变量的值本就是流程产物、重启即失效，本来就不该落盘。

| 文件 | 动作 |
|---|---|
| `VisionMaster\Services\VariablePersistenceService.cs` | 改：`Capture` 的两个值字段过 `PersistableValue` 白名单；新增 `PersistableValue` / `IsPersistable` |
| `FlowCanvasChecks\VariableAssignmentCheck.cs` | 改：新增 `[A3]` 段（4 条断言） |

**新增断言**（`[A3]`）：

| 断言 | 结果 |
|---|---|
| 含图像变量的方案能序列化（旧实现抛 HALCON #4056） | ✓ |
| 图像变量的定义照样落盘（名字 / 类型 / 稳定身份都在） | ✓ `DataTypeString=HalconDotNet.HImage…` |
| 图像变量的当前值与初始值都不落盘（落 null，不把像素写进 .vms） | ✓ `Value=null / DefaultValue=null` |
| 普通变量的值照旧往返（这次收紧没有误伤） | ✓ `Num.Value=42` |

用例里**故意放了两个图像变量**：一个有效句柄、一个 `new HImage()`（空句柄）——
空句柄那个就是用户踩到的情形，专门钉住它。

**已知边界**：
1. 这次只挡了"变量里的值"。若将来有别的路径把 `HImage` 塞进**步骤的 InputValues**（例如某插件把图像当常量存），
   同样会在保存时炸 —— 本次没有覆盖那条路。
2. 图像变量的值**不随方案保存**，重开方案后是空的（这正是期望行为：图的来源是流程，不是存盘）。

## 十二、颜色序列检查插件（第一刀：ROI 采样区）

**用户诉求**（原话）：
> 如果我想这个线序检查 可以做到插件化 不使用脚本 抽象成颜色检查插件 你有什么思路 提供下吗

### 12.1 为什么"线序检测"该抽成插件而不是继续堆脚本

线序检测现在是一条 **C# 脚本节点**（找线 + 比对）。它能跑，但对产线有三个硬伤：

| 硬伤 | 具体表现 |
|---|---|
| 参数埋在脚本正文里 | `SampleX=440`、判据阈值、颜色分类边界都写在脚本里，换工装要**改代码** |
| 无法示教 | 画框、选色、看结果都在脚本的"自说自话"里，操作工改不了 |
| 不可复用 | 同一套"沿一条采样带取颜色序列、与配方比对"的逻辑，换个产品/换个工位就得复制脚本 |

**抽象的关键一步**：把"线序"这个词从插件里彻底拿掉。
插件不认识"线"，它只认 **"沿一条带取一串颜色词，和期望序列比"** ——
线序检测只是它的一个用法（一维排列），PCB 色块顺序、排线端子、标签色序都是同一个东西。
这就是**「颜色序列检查」**。

### 12.2 设计树（七层，逐层问、逐层定，全部经用户确认）

| # | 层 | 要回答的问题 | 定案 |
|---|---|---|---|
| 1 | **抽象** | 插件到底检查什么？ | 通用「颜色序列检查」：沿一条采样带取**一维颜色序列**，与配方比对 |
| 2 | **几何** | 采样带怎么定义？ | **ROI 矩形 + 框内按比例 5 条采样线取中位**（抗单点噪声 / 抗脏点） |
| 3 | **算法** | 怎么从像素到颜色词？ | 搬脚本的「等间距规整化 + 颜色分类」，全部**参数化**（判据阈值 / 规整化开关 / 最小段长 / 线数自动或指定） |
| 4 | **颜色** | 颜色判据从哪来？ | 先做**内置色卡 + 阈值可调**；参考色示教留作下一步 |
| 5 | **配方** | 期望序列怎么给？ | **配方表进插件**，同时**保留「期望序列」输入端口**（两全：现场能在界面改，流程里也能连上游） |
| 6 | **输出** | 结果怎么往外给？ | `Result` / `Count` / `Sequence` / `Detail` / `BadIndex` 五个端口 + **投射内置**（投到哪个视图窗口可配） |
| 7 | **迁移** | 现有脚本方案怎么办？ | 现有脚本版 `.vms` **保留不动，新插件并行**（不做双写、不做自动转换） |

**为什么几何选"ROI 矩形 + 框内多条采样线取中位"**：
线束在图上是一条带，用**矩形**圈住最省事（不用拖多段线）；
带内单点取值容易被反光/脏点骗，所以框内按比例拉 5 条线、每条取该线颜色的中位色，
再对 5 个中位色投票 —— 这是"工业上够用、现场能画、代码不复杂"的折中点。

### 12.3 本轮只切第一刀：ROI 采样区

七层不可能一口气做完。第一刀选**最底、最不可变**的那层 —— 采样区：
它一旦定错（例如后来发现该用多段线），上面六层全得返工；而它做完之后，
剩下的算法/配方/投射都只是"在已定好的输入上做计算"，风险低得多。

**实现要点**（关键在**三方同步**：画布 → 配置 → 存盘）：

```
        ┌──────────── 拖拽 / 新建 框 ────────────┐
        ↓                                        │
  ImageEdit.DrawObjectList  ←──────────── CanvasRois（ObservableCollection）
        │  回写 HTuples（INPC）                   ↑ 回填
        ↓                                        │
   RoiParams（double[5]）──OnConfirm──→ InputValues ──→ .vms 落盘
```

- 与 「Plugin.CreateRoi」 的做法一致：`CanvasRois` 绑 `DrawObjectList`，
  `CollectionChanged` → 回写 `RoiParams`；`HTuples` 的 `PropertyChanged` → 回写（**拖拽句柄走的是这条通道**）；

- **预览图和运行图分家**：`PreviewImagePath` 只是配置期的示意图（`.vms` 里存路径，
  打开配置时读一下），运行期一律用上游图像 —— 否则插件就偷偷依赖磁盘上的图了。

### 13.2 三处自适应替换了什么

| 环节 | 脚本版（硬编码） | 插件版（从本幅图现算） |
|---|---|---|
| 判「可靠线像素」 | `mx<150 \|\| delta>40 \|\| mx>240` | 暗线 = 众数亮度 − 35% ×（众数亮度 − 2 号百分位）；彩度 = 大津法；白线 = 亮度 92 号百分位 |
| 估线距 | 相邻可靠段中心差的**中位数** | 中位数 + **自相关**交叉验证（见 13.3 的修正） |
| 定起点/线数 | 拿**第一个可靠段**当起点 + `round(跨度/线距)+1` | 对可靠段中心做**最小二乘回归** `y = y0 + k·pitch`，外推覆盖整束 |

第 ③ 条是相对脚本的实质改进：脚本拿"第一个可靠段"当锚，端部那根一旦漏检，
**整条序列会错位一格**（最致命的失效模式）；改成回归定锚后，端部漏检只会少一根，不会错位。

### 13.3 三个被实测推翻的设计（本轮最值钱的部分）

这一刀没有一次做对，是靠"把剖面逐点打出来看"改了三轮。三处教训都记在这里。

**（1）5 条采样线"摊开 + 按行号合并"会把边界线洗掉**

原设计是 5 条采样线沿长轴按 10/30/50/70/90 百分比铺开，再按行号逐点取中位合并。
实测结果：cable2 只报出 8 根（少了玫红与棕），cable1 报出 19 根。

把剖面打出来一看就明白了 —— 样本图的线束是**扇形散开**的（连接器在一端，线向另一端散开）：

```
采样区中心列 440 → 锚点行号 [147,190,210,231,252,279,295,315,334]   9 个，反推 10 根 ✓
采样区中心列 400 → 锚点行号 [154,190,195,212,229,249,273,291,308,324] 10 个，反推 11 根 ✗
采样区中心列 480 → 一个锚点都没有（那里已经是连接器了）
```

同一根线在不同列上的行号能差十几像素；摊开 96 像素后按行号合并，第 10 根棕线在多数列上
都落在背景里，取中位就被洗成背景了。

**改法**：采样线在长轴方向只偏移 ±4 像素（5 条），与脚本版「左右各取 3 列取中位」同源。
抗单点噪声的诉求靠"几条邻近采样线取中位"已经满足，不需要摊开。
改完立刻对上：cable2 得 10 根、锚点行号 `147…334` 与脚本版**完全一致**。

**（2）"不一致时信自相关"是错的**

原设计承诺"自相关与分段线距不一致时信自相关（它不依赖检出了几根）"。
实测：cable1 上自相关给出 **16.0**，而真值是 **21.5** —— 于是报出 6 根、序列多了一个"灰"。

自相关还踩过一个更蠢的坑：第一版直接取全局最大峰，而**相邻像素本来就相似**，
零延迟附近的自相关天然最高，结果给出 **3 像素**这种荒唐线距（cable2 报出 56 根）。
改成"先等它衰减过零，再取第一个显著峰"。

**改法**：以**分段线距为准**，自相关只在"分段线距正好是它的整数倍（≥1.6 倍）"时才接管 ——
那正是"漏检一半致使中位间距变成两倍"的典型情形，这才是自相关真正的用武之地；
两者接近（差 25% 以内）则取平均互相消噪。改完 cable1 得 5 根、序列逐位对上。

**（3）阈值用百分位是"看着自适应、其实不牢"**

第一版暗线阈值取亮度 P35。实测 cable1 给出 195、cable2 给出 169，而阈值扫描显示
**两张图同时正确的窗口是 100~160**（见下表）—— P35 落在窗口外，cable1 直接退化成 9 根。

```
cable1 暗线阈值扫描（需要 5 根）：  100~190 都对；90→6 根；200→10 根
cable2 暗线阈值扫描（需要 10 根）： 100~160 都对；80/90→9 根；170→11 根；180→15 根
```

**改法**：口径换成"**明显比线间缝还暗**"—— 缝/背景的水平取剖面的**众数**
（剖面里最常见的那个亮度就是缝或背景），最暗的线像素取 **2 号百分位**
（不用最小值：一个坏点就能把尺度拉跑），判定线放在两者之间往下 35% 的位置。
实测给出 154（cable1）与 114（cable2），都落在安全窗口里。

**顺带发现**：彩度（有没有颜色）这条用大津法，实测对结果**极不敏感**
（20~110 都给出同一个根数），所以交给算法自己求，人不用管。

### 14.1 逐条问出来的四个决定（外加一条行为差异）

| 问题 | 定案 |
|---|---|
| 配方从哪来 | **配方表进插件**（一行一条 `产品名 = 颜色1,颜色2,...`），运行时**按实测根数匹配**（期望序列的长度就是芯数）；另保留「期望序列」输入端口，**端口填了就以端口为准**（兼容配方从数据库/工单取的场景） |
| 比对规则 | **严格逐位**；期望里写 `*` 表示这一位不检；长度不符直接判不合格 |
| 投射画什么 | 采样线 + 逐根颜色标签 + 结论行；**合格绿 / 不合格红**；不符的那一根红字；**规整补出来的那几根橙字** |
| 配方怎么编辑 | 多行文本框 + **「把试算结果存成配方」**按钮（手打颜色词必须正好落在词表里，写成「深红」永远匹配不上，一键生成从根上避开这个坑） |
| **配方缺失怎么办** | **明确报错，让流程停在这一步**（不判成 NG） |

最后一条与脚本版**有意不同**，值得单独说：

```
脚本版：选配方 → Else（未知产品）→ Expected 清空 → 比对步骤判 Result=False + Warn → 分流记 NG
插件版：按根数查不到配方 → 步骤失败，日志写「未知产品：10 芯没有对应配方（配方表里有 5 芯排线（5 芯））」
```

理由：「配方没配」是**工程配置问题**，不是产品不良。判成 NG 的话，一条配错的线会**永远把良品报成 NG**，
而现场只会以为"这批产品有问题"，反而更难发现。

## 十六、颜色内核抽取（为"一族颜色算子"打底）

**起因**：用户提出目标是**通用工业视觉软件、要覆盖各种场景**，并问"这个是通用的颜色识别插件吗"。
答案是"不是" —— 它是**一维颜色序列检查**（只认顺序）。于是引出架构判断：

> **通用 ≠ 万能插件，而是「一族小算子 + 公共内核 + 流程编排」。**

不做"一个大而全的颜色插件"的理由（逐条写下来，免得以后有人再想合）：

| 做成一个大插件 | 拆成一族小算子 |
|---|---|
| 界面要塞下所有场景的参数，没人看得懂 | 每个算子只露自己那几个旋钮 |
| "配方"结构打架：序列 vs 区域表 vs 阈值表 | 每个算子有自己的配置结构 |
| 回归组合爆炸：改一处要验 N 个场景 | 每个算子独立断言、独立回归 |
| 一处改坏，所有场景一起坏 | 坏一个只影响一类场景 |
| 工具箱里只有一个名字，操作工不知道能干什么 | 工具箱一目了然：检顺序用序列，检单块用区域 |

**必须共享的只有一件事：颜色词与判据**。否则"玫红"在三个算子里会给出三种答案 —— 现场最恨这个。

### 16.1 逐条问出来的四个决定

| 问题 | 定案 |
|---|---|
| 内核放哪个工程 | **`Services\Core.Halcon\Color\`**（采样必须用 Halcon，而它已经是"Halcon 封装的公共家"；插件本来就引用它，零新增工程引用） |
| 一块区域的颜色怎么定 | **网格采样 → 逐点分类 → 投票取主色 + 报主色占比**（判定 = 主色在期望里 且 占比 ≥ 阈值）。抗反光脏点；顺手回答"红占多少"；两色混杂时直接报"不纯"而不是硬给一个词 |
| 色卡阈值怎么管 | **每个算子各带一份可调副本**（默认值来自内核同一处）。不同工位/产品的打光材质不一样，"玫红从哪里算起"本来就可能不同；全局一份会变成束缚 |
| 新算子支持哪些 ROI 形状 | **矩形 + 圆 + 椭圆**（用 Halcon 区域当掩膜）。理由很实际：**用方框去框圆形指示灯时四个角是背景**，不作掩膜的话背景会参与投票、主色可能直接变成"背景色"，而且因为占比高还"看起来很有把握" |

### 16.2 内核内容（4 个文件 + 1 个共用控件）

| 文件 | 说明 |
|---|---|
| `Services\Core.Halcon\Color\ColorThresholds.cs` | 13 个判据阈值 + 默认值 + `Clone()`。**内核里不藏魔数**（原 `ColorClassifier` 里那六个写死的常数全部搬到这里） |
| `Services\Core.Halcon\Color\ColorVocabulary.cs` | 颜色词表（黑/白/灰/棕/红/玫红/橙/黄/绿/蓝/紫）+ `Classify(r,g,b,thresholds)` + `Hue/Saturation` 工具 + `IsKnown` |
| `Services\Core.Halcon\Color\ColorSampler.cs` | **给点取色**（`TryReadPixels`，元组版 GetGrayval）+ **ROI→区域→抽样点**（`TryBuildRoiPoints`，矩形/圆/椭圆三种形状走同一条链，超出图像自动裁掉） |
| `Services\Core.Halcon\Color\ColorMarks.cs` | 画面语言：`Pass=green / Fail=red / Inferred=orange` + `Line/Text` 两个造标注的小工具 |
| `Shard\Core.Controls\ColorThresholdEditor.xaml` | **共用阈值编辑器**：13 行紧凑网格，靠 DataContext 继承 + 按属性名绑定。颜色算子以后会越来越多，不能让每个视图各写 13 行绑定（迟早写歪） |

**分工原则**：**内核负责"给点取色"，算子负责"点怎么来"** ——
序列算子自己算采样线的点（沿短轴逐点扫），区域算子让内核把 ROI 变成区域再抽样；两者的取色与投射走同一条路。

### 16.5 本轮遇到的环境问题：并行任务把整仓构建弄红了

构建时报：

```
Core\Models\SolutionModel.cs(126,42): error CS0234: 命名空间「VisionMaster.Core」中不存在类型或命名空间名「Interfaces」
```

**不是本次改动引入的**（这一轮没碰 `Core\Models`），而是**另一个并行任务**在同一工作区里新加了一行：

```csharp
public ObservableCollection<Core.Interfaces.CameraDescriptor> CameraConfigs { get; set; } = new();
```

`SolutionModel` 位于 `namespace VisionMaster.Core` 里，而 C# 会把这个作用域里的 `Core` 解析成 `VisionMaster.Core`
（**命名空间遮蔽**），于是 `Core.Interfaces` 找不到。正确写法是 `global::Core.Interfaces.CameraDescriptor`。
`CameraDescriptor` 本身是存在的（`Shard\Core.Interfaces\Camera\CameraDescriptor.cs`），所以纯粹是限定名写歪了。

**怎么绕过去把断言跑绿的**（记下来，以后再遇到同样情况照做）：

```
① 只编自己的工程：dotnet build <我的工程> -p:BuildProjectReferences=false
② 把新编出来的 Core.Halcon.dll / Core.Controls.dll 手工拷进 FlowCanvasChecks\bin\Debug\net9.0-windows\
   （否则运行期用的是旧版内核，插件会找不到 Core.Halcon.Color 里的类型）
③ 同样带 -p:BuildProjectReferences=false 编 FlowCanvasChecks，再 dotnet run --no-build
```

**这个仓库同时有并行任务在改文件**，所以「整仓构建」有时会被别人的半成品挡住。
判断责任的办法：看报错文件是不是自己碰过的 + 看该文件的修改时间。

### 16.6 已知边界（颜色内核）

1. **内核只提供默认值，改默认值不会回头改已存的方案** —— 这是"每个算子各带一份"的必然结果，也是对的
   （现场调过的参数不该被后来的一次发版悄悄改掉）。
2. **13 个阈值全在界面上**，但绝大多数情况只需要动「玫红起点 / 蓝止点 / 白明度」这几个。
3. **`ColorSampler.TryBuildRoiPoints` 对超出图像的 ROI 是"裁掉"而不是报错**（框得松一点是常事），
   而「颜色序列检查」那条路对超出图像是**报错**（它的采样线必须整条落在图内）。两处口径不同，是有意的。
4. **`ColorThresholdEditor` 靠属性名绑定**，所以任何颜色算子只要暴露同名属性就能嵌它；
   代价是属性名被"隐式契约"绑住了 —— 改名会让界面静默绑不上（WPF 绑定失败不报错）。
   所以这 13 个属性名不要随便改。
5. **`Plugin.ColorRegion`（区域颜色检查）还没做** —— 内核抽完了、但第二个消费者还没落地。
   按"只有一个消费者的内核是猜的"这条纪律，**内核的通用性还没被真正证明**，要等它。

## 十七、第二个颜色算子「区域颜色检查」（内核通用性被证明）

**目的**：上一节把颜色内核抽出来了，但那时只有「颜色序列检查」一个消费者 ——
按"只有一个消费者的内核是猜的"这条纪律，**内核到底通不通用还没被证明**。
本算子就是第二个消费者：它用内核的同一套颜色词、同一套采样（`TryReadPixels` / `TryBuildRoiPoints`）、
同一套投射语言（绿/红/橙）与同一个阈值编辑器，**但一行都没复用序列算子的东西**
（不找线、不比顺序、没有配方表）。

### 17.1 它认什么（与序列算子的分工）

| | 认什么 | 典型场景 |
|---|---|---|
| 颜色序列检查 | **顺序**：沿一条线取一串颜色词，逐位比 | 线序、排线、一排色带 |
| 区域颜色检查（本算子） | **一块区域**：逐点分类投票，取主色与占比 | 指示灯什么颜色、色标对不对、这块区域颜色纯不纯、某颜色占比够不够 |

### 17.2 四条定案的落地

| 定案 | 落地 |
|---|---|
| 网格采样 → 逐点分类 → **投票取主色 + 占比** | `RegionColorAnalyzer.Analyze`：区域内抽样 ≤400 点，逐点分类，票数降序（同票按词表序，保证每次结果一样）；主色占比 < 60% 时额外留一条"颜色不纯"的 Warn |
| ROI 支持**矩形 / 圆 / 椭圆** | 形状由用户右键画什么就是什么（写进 `RoiShape`）；采样交给内核 `TryBuildRoiPoints`，三种形状走同一条链，**用 Halcon 区域当掩膜** |
| 色卡阈值**每个算子各带一份** | 本算子也暴露那 13 个阈值，界面里嵌的是同一个 `ColorThresholdEditor` |
| 每个算子独立 | 自己的工程 `Plugin.ColorRegion`、自己的断言段 `[R6]`、自己的 `.vms` 配置 |

**分工一句话**：**内核负责"给点取色"，算子负责"点怎么来"与"怎么判定"。**

| 【画布】矩形 / 圆 / 椭圆 | 三种形状的回填与回写都对 |
| 【投射】 | 矩形轮廓 4 条线 + 标签 + 结论 = 6 条；圆形轮廓 **32 段折线**；合格绿字、不合格红字 |
| 参数落盘 | 形状 / 采样区 / 期望颜色 / 最小占比 / 采样点数 / 投射窗口 / 颜色阈值全对 |

### 17.5 本轮踩到的三件事（都值得记住）

**（1）线间缝会被归到「灰」—— 跨多根线的框，主色往往是灰**

实测：一个横跨两根线（蓝 230 / 绿 251）的框，主色是**灰 61%**，而不是蓝或绿。
原因是线之间的暗影（缝）本身就是无彩的中等亮度 → 按内核的判据就是"灰"。

这不是 bug，是诚实的反映："这块区域里混了多种颜色"。但它给了现场一个**很重要的操作提示**：
**框要框准一根线**，框大了主色会被缝与背景带跑。已写进算子的「怎么用」与下面的边界。

**（2）"回填"的守卫要分形状看**

打开配置回填画布时，我原本用"半长 > 0"判断"参数里真的画过一个框"。
但**圆的第 4 个参数本来就是占位 0**（5 个参数统一是为了让存取只有一条路径），
于是圆形框永远回填不出来 —— 断言立刻变红。改成"矩形/椭圆看半长、圆看半径"。

**（3）试算里带判定会造成顺序死锁**（这条最值钱）

第一版把"判定"放进了 `TryAnalyze`，于是**没填期望颜色时连试算都失败** ——
可现场的正常顺序恰恰是"先试算出主色 → 再一键把它填成期望颜色"，
试算一卡，那个一手入口就永远用不上。

改成：**试算只做颜色分析、不做判定**（结论行写「尚未配置期望颜色（点下面那个按钮即可把主色填进去）」）；
**判定只在运行期做，并且必须做**（没填、词写错，运行期一律报错停住）。

### 17.7 已知边界（区域颜色检查）

1. **框要框准**：跨多根线时，线间的暗影会被归到"灰"，主色可能变成灰而不是任何一根线的颜色。
   这是诚实的反映（区域里确实混了多种颜色），但现场看到的是"主色灰 61%" ——
   要么框小一点只框一根线，要么用「最小占比」把它挡成"不纯"。
2. **只支持"一块区域"**，不支持"一张图上多个散开色块各自的颜色"。后者请在一张流程里挂多个本算子
   （每个框一块），或等后续的"多区域"算子。
3. **要彩色图**（≥3 通道）。灰度图会给黑/白/灰三档，但本算子直接报错要求彩色图 ——
   因为认颜色是它的本职，用灰度图容易得出"看着对其实没检"的结论。
4. **`ColorThresholdEditor` 的 13 个属性名不能随便改**（WPF 按属性名绑定，改名是静默失效）。
5. **期望为空 = 报错**（与序列算子的"配方缺失"同一口径）；只有显式写 `*` 才是"只报不判"。
6. **轮廓绘制**：矩形画 4 条边，圆/椭圆按 32 段折线画。折线段数固定，放大到很大时能看出棱角
   （只影响画面观感，不影响判定）。

## 十八、修「配置界面显示不全 / 图像绑不上上游」（用户反馈）

**用户原话**：

（附截图：配置窗口里左栏被裁到「高级参数」一半，右栏图像区也短了一截；状态栏 `❌失败 - 上游没有图像`。）

### 18.1 问题一：显示不全 —— 视图写死的尺寸比宿主内容区还大

宿主配置窗口的尺寸在 `PluginConfigShellView.xaml` 里写着：**880 × 600**（可缩放）。
去掉顶部 50 + 底部 50 + `ContentPresenter` 的 8×2 边距，**内容区只有 864 × 484**。

而我两个视图写的是 `Width="1000" Height="620"` —— 比内容区还大，于是底部被硬裁掉。

**修法**：视图不再写死尺寸，改成 `MinWidth="700" MinHeight="360"` + 让内容自适应；
左栏本来就是 `ScrollViewer`，空间不够时它自己滚动，**信息一条都不会丢**。

### 18.2 问题二：图像绑不上上游 —— 配置界面里压根没有"用上游图"这条路

先查清了平台的机制（`Engine\PluginTestRunner.cs`）：配置窗口的「执行」是
**先执行上游依赖链，再把上游的输出值快照灌进配置实例的同名输入端口**
（`BridgeInputs`），最后才在配置实例上跑目标插件。也就是说**上游图本来就会进到端口里**。

问题在我的插件侧：配置界面只给了"填示意图路径 → 载入"这一条路，
端口里那张上游图**我根本没接**。用户看到右栏空着、执行又报"上游没有图像"，
体感自然就是"图像绑不上上游"。

**修法**（两个算子都改）：

| 改动 | 说明 |
|---|---|
| 订阅 `Image` 端口的 `PropertyChanged` | 端口一变就把上游图**拷一份**显示到画布上（`new HImage(上游)`，我们只持有自己的副本 —— 上游句柄归框架管，免得谁先 Dispose 把对方弄坏） |
| `OnViewLoaded` 优先上游图 | 有上游图就用它；没有才退回"读示意图路径" |
| 「怎么用」重写 | 写清两步：① 在流程里把 Image 连到上游（画布拖线，或右键 → 变量绑定选上游的 Image 输出）；② 点「执行」把上游图带进来 |
| 加一句预期说明 | "第一次点「执行」会报「尚未框选采样区」——那是对的，此时图已经上屏，框完再执行一次即可" |
| 「上游没有图像」提示改成能指路 | 原来只有六个字；现在写清怎么连、以及"点执行能把上游图带进来" |

### 18.4 ⚠ 事故记录：sln 的 GUID 撞车，以及我误删了 CodeReader 的配置

**必须记账。**

**（1）GUID 撞车**：我给 `Plugin.ColorRegion` 选的 GUID 是 `{3F8C2A47-…}`，
而**这个 GUID 早就被 `Plugin.CodeReader` 用了**。表现很隐蔽：

```
dotnet sln list            →  看不到 Plugin.ColorRegion
dotnet build VisionMaster.sln  →  0 错误（因为它压根没参与构建）
Modules\Plugin.ColorRegion.dll →  存在，但那是我手工编出来的
```

也就是说：**"登记了却不在解决方案里"，而且构建不报错**。这也解释了为什么整仓构建"成功"却没重建它。
换成未被占用的 `{C7D4E8A2-…}` 后正常（`dotnet sln list` 里出现、整仓构建里出现 `Plugin.ColorRegion ->`）。

**（2）误删 CodeReader 的配置映射**：清重复时，我看到 sln 里有两段**完全一样**的 12 行配置，
就去掉了一段 —— 但那两段其实分属两个工程（GUID 相同、文本自然完全相同），
于是把 **CodeReader 的配置映射一起删了**。已按旧 GUID 补回 12 行。
（少了这段，CodeReader 会**静默地不参与构建**，不会报错 —— 这种静默失效最危险。）

**教训（写进纪律）**：
- **往 sln 加工程之前，先 grep 一下那个 GUID 有没有被占用**；
- **sln 里出现两段完全相同的文本，先怀疑"GUID 撞了"，不要盲目去重** ——
  去重前必须确认每个 GUID 在 `Project(...)` 行里只对应一个工程；
- **加完工程要验三件事**：`dotnet sln list` 里有它、整仓构建输出里有它、`Modules\` 里那份的时间戳晚于源码。
  只看"构建 0 错误"是不够的。

## 十九、已知边界

1. **`SampleX` 是唯一与相机/工装绑定的参数**（当前 440）。
   换相机高度、换工装、换线束走向都要改它 —— 它是脚本参数区的第一行。
2. **线距估计取相邻中心差的中位数**，靠的是"漏检的线少于一半"。
   若一条线束里**大多数**线都是白/浅灰（例如全白排线），中位线距会失真，芯数就不准了。
3. **只支持 3 通道彩色图**。1 通道灰度图会直接 `Context.Fail` 并说明原因（不静默给错结果）。
4. **颜色分类是"颜色词"级别的**：红/玫红/棕/灰/白/黄/绿/蓝/紫/橙。
   同色号的深浅（深红 vs 浅红）不区分，也不区分色差很小的同色线。
5. **配方是"从样本图量出来的黄金参照"，不是从工单/数据库取的**。
   当前样本即标准；换产品要在界面上改分支里的 `Value`。
6. **`IsRequired` 那处修复是全局的**：该节点以后手填值都能编译通过，
   但填了**不存在的变量名**仍只会在运行期报错（不是编译期），这一点没有变。
7. **结果分流的两条分支目前只写 `Verdict` 变量**（OK / NG），没有接「结果上报」「数据记录」。
   接产线时把那两个节点拖进分支即可，分支骨架不用动。
8. **改插件必须走「关程序 → 构建 → 核对 `Modules\` 里 dll 真的变了 → 再启动」**（上轮踩过的坑）。
   本轮改了 `Plugin.Utility`，已确认 `Modules\Plugin.Util.dll` 重新投递。
9. **「颜色序列检查」目前只有采样区，还不能出结果**：取序列 / 颜色分类 / 配方比对 / 投射四层未做。
   所以现在把它拖进流程会**明确报"尚未框选采样区"或直接通过但不产生任何输出**，
   线序检测**请继续用现有脚本方案**，不要切到新插件（切了就拿不到 `Sequence`/`Result`）。
10. **一个节点只认一个采样区**（画了第二个，参数就跟着第二个走）。多条采样带（例如连接器两排端子）
    要等后续版本拆成"采样区列表"。
11. **示意图路径（`PreviewImagePath`）存在 `.vms` 里，是绝对/相对路径**。
    换机器后路径失效 → 打开配置只给一句中文提示，**不影响运行**（运行期用的是上游图像）。
12. **采样区参数是 `double[5]`**，按 Halcon 的 `GenRectangle2` 约定 `[中心行, 中心列, 角度, 半长, 半宽]`。
    单位是**像素**（不是毫米）—— 换相机分辨率就要重画。
