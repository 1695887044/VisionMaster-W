# 线序检测：多产品配方 + 条件分支（2026-09-25）

## 一、需求与决策

**需求**：`Image\颜色\` 下新增 `cable2.png`（**10 芯**），要做一个"复杂一点的流程"，用上逻辑分支。
用户明确要求：**"你要做预处理什么的，用算法计算，而不是问我"** —— 芯数与线序必须自己算出来。

**逐条确认的决策**：

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| 1 | 复杂在哪 | **多产品配方 + 条件分支**（用户选项） | 正好用上新增的 cable2 |
| 2 | 流程骨架 | 采集 → 找线 → **选配方(If/ElseIf/Else)** → 比对 → **结果分流(If/Else)** | 5 步、2 个容器节点 |
| 3 | 芯数从哪来 | **算法反推**（等间距规整化），不做成配置项 | 用户要求"用算法计算" |
| 4 | 配方放哪 | 分支体里的**「变量赋值」**节点 | 分支才有事可做，条件与配方分开 |
| 5 | 节点间怎么交接 | **运行时变量**（脚本 `SetVar` / 条件表达式直接引用） | 不落全局变量、不写盘，跑完即弃 |
| 6 | 找线与比对 | **拆成两个脚本节点** | 换产品只动配方，算法一个字不碰 |
| 7 | 未知芯数 | 走 Else → 配方置空 → 比对明确报"未知产品" | 产线上宁可误停不可误放 |

## 二、算法：等间距规整化（本次的核心）

### 为什么"按间隙切分"在新图上必然失手

量 `cable2.png` 得到两条硬事实：

1. **线束在连接器附近是密排的** —— 线之间的缝是 V≈165 的**暗影**，不是亮背景；
   任何"亮度回落即缝隙"的规则会把整块都判成线（我第二个原型就栽在这，cable1 都算成了 7 根）。
2. **白线/浅灰线与浅色背景只差几个灰阶** —— 实测白线 `(218,218,223)` vs 背景 `(215,217,222)`，
   差 5 个灰阶。**任何按颜色判线的规则都抓不到它**。

### 破法：先抓能确定的，再按等间距把漏的补回来

```
① 逐行取采样带的中位色（±3 列取中位，抗噪）
② 判「可靠线像素」：暗(mx<150) 或 彩(delta>40) 或 极亮(mx>240)   ← 故意不指望抓到白线
③ 连续可靠行 ≥4 行才算一段 → 得到若干"线的中心"
④ 线距 = 相邻中心差的中位数        ← 取中位，漏检造成的 2 倍间距会被自动忽略
⑤ 线数 = round(跨度 / 线距) + 1    ← 芯数由算法反推，不配置
⑥ 按等间距铺开：能对上已检出段的用它干净的中位色（避开两侧暗缝），
   对不上的（就是白线/浅灰线）用规整位置附近的窗口色
⑦ 分类
```

**实测验证**：

| 图 | 粗检到 | 相邻中心差 | 中位线距 | 跨度 | **反推线数** | 结果 |
|---|---|---|---|---|---|---|
| cable1 | 5 段 | 21,21,21,18 | 21 | 81 | **5** ✓ | 黑,棕,玫红,红,黄 |
| cable2 | 9 段 | **43**,20,20,22,26,17,20,19 | 20 | 187 | **10** ✓ | 黑,**白**,灰,紫,蓝,绿,黄,红,玫红,棕 |

cable2 的 9 段里那个 **43 正好是 20 的两倍多** —— 漏了一根（白色那根），规整化把它补了回来，
线数 10 与用户所说一致。cable1 的结果与既有黄金参照**完全一致**，旧断言不作废。

### 分类表的三处修正（都是实测撞出来的）

| 现象 | 原因 | 修法 |
|---|---|---|
| cable1 的棕线被判成灰 | 灰/棕都是低饱和，只按明度分不开 | 棕 = 低饱和 **且偏暖**（R−G≥12 且 R−B≥12）**且偏暗**（V<175） |
| cable2 的紫线被判成蓝 | 色相分界 260° 落在紫(252°)与蓝(209°)之间偏外侧 | 分界挪到 **230°** |
| 红与玫红分不开 | 两者色相只差十几度，且都 B>G | 按色相分：**[330,350) 玫红；[350,360)∪[0,20) 红** |

## 四、顺带挖出的两个平台 bug

### bug 1：「变量赋值」节点只要手填参数就永远编译不过

编译期的必填检查是 `IsRequired && LinkedSource == null` —— **只看有没有连线，不看有没有填值**。
而 `InputPort.IsRequired` 默认就是 `true`，`VariableAssignmentPlugin` 把 `Name` 显式写成 true、
另两个没写 → 三个端口全成了"必须连线"。可这三个参数本来就是**界面上手填**的。

表现：分支里放一个「变量赋值」→ 编译报 9 条「必填参数 Name/Value/CreateIfNotExists 未配置」。
修法：三个端口显式 `IsRequired = false`。**这是全局修复**，该节点从此手填值可用。

### bug 2：C#脚本的动态端口依赖 InputVars 的运行时类型

`CSharpScriptPlugin.InputVars` 的声明类型是 `ObservableCollection<ScriptVarDef>`，
`ApplyConfigValues` 按声明类型做转换。用 `List<ScriptVarDef>` 塞进去**转换不过、集合静默变空** →
`RebuildDynamicInputs` 建不出动态端口 → 编译期报「'找线' 没有名为 'Image' 的输入端口」。
只影响程序化生成 `.vms` 的场景；主程序自己保存的文件天然是 ObservableCollection，无此问题。

## 五、脚本侧踩到的两个坑

1. **脚本上下文里没有 `InstanceName`** —— 它是插件属性，不是脚本变量。
   写 `Context.Info($"{InstanceName} ...")` 会在运行期报
   「The name 'InstanceName' does not exist in the current context」。引擎本来就给日志加了步骤前缀。
2. **`Decompose3` + `new HImage(...)` 这条路会报 `HALCON error #4056: object-ID is NULL`**。
   改成**元组版 `GetGrayval`**：一次调用取回整条采样带（整高 × 条带宽）的所有灰度，
   再按 `AccessChannel` 逐通道取。既不必包 `HImage`、不用管句柄，还比逐点调用快两个数量级
   （10080 次调用 → 3 次）。

## 七、补修：画布节点图标全没了（用户反馈）

**现象**：打开方案，画布上所有步骤都没有图标。

**根因**：程序化生成 `.vms` 时，`new ActionStep("", "图像采集", ...)` 的**第一个参数就是图标**，

影响 10 个节点：采集 1 + 脚本 2 + 条件分支 2 + 变量赋值 5。

| 条件分支 | `\uf0e8` | `PluginService` 的 `BuiltIn_If` |
| 变量赋值 | `\uf044` | `VariableAssignmentPlugin` |

**教训**：用代码造节点时，凡是「工具箱里能看到的属性」（图标、描述）都要显式补齐 ——
界面上新建节点时框架会自动带，代码造的时候没人替你带，而这类缺失**不报错、只难看**，
测试也断言不到（`.vms` 照样能加载、能跑、断言全绿）。

## 八、补修：「变量绑定」窗口不回显当前值（用户反馈）

**现象**：双击分支里的「变量赋值」节点，弹出的「变量绑定」窗口里「常量值输入」是**空框**，
看不到已经填好的配方，只剩一行灰字提示。

**根因（第一版定位错了，这里记准确）**：手填的值存在 **`InputValues`** 里，**不是** `LinkedSources`。

`StepModel` 上"端口的值从哪来"有**两条**路，运行期 `ApplyConfigValues` 的取舍是
「**有连线就以连线为准**（`IsLinked` 就跳过 InputValues），没连线才用手填值」：

| 来源 | 存在哪 | 谁写的 |
|---|---|---|
| 手填常量 | `InputValues[端口名]` | 插件 `OnConfirm`（配置窗口确认时回写） |
| 常量 / 上游端口 / 变量 连线 | `LinkedSources[端口名]` | 变量绑定窗口 `Confirm` / `DoFinalBind`，或画布连线 |

而 `VariableBindingViewModel.BuildTree` 建左侧端口表时**只读了 `LinkedSources` 的显示地址**，
`SelectedInputPort` 的 setter 又只调 `UpdatePresetOptions()`（只管功能性枚举端口）——
于是**手填的值永远回显不出来**，常量框一直是空的。

**第一版为什么没修好**：我只查了 `LinkedSources`，没查 `InputValues`。
**断言为什么没拦住**：我造用例时把三个端口都造成「常量连线」，
绕开了"手填值"这条真实路径 —— 代码明明不对，用例却全绿。
修好夹具后补了一条**前提断言**（"Name 的值必须存在 InputValues 而不是 LinkedSources"），
把这个坑固化下来：以后谁改了夹具的建模方式，前提断言先红。

**顺带发现的更严重问题**：`Confirm()` 的规则是「常量框非空就写常量」，而**换端口不会清空这个框**。
所以「选中 A 端口填了值 → 再点 B 端口看看 → 点确定」会把 A 的值写到 B 上——
界面上毫无异常，被静默写坏的是另一个端口的绑定。

**修法**（`VariableBindingViewModel .cs`）：

| 改动 | 内容 |
|---|---|
| 新增 `LoadExistingConstant()` | 挂在 `SelectedInputPort` 的 setter 上，**每次换端口**都执行：先清空；有连线则按连线（只有常量连线才回显其值）；没连线则回显 `InputValues` 里的手填值 |
| 新增 `ResolveBindKey()` | 取键口径统一：条件节点用端口描述、其余用端口名，与 `DoFinalBind`/`Confirm` 三处一致 |
| 新增 `ExtractConstantText()` | 优先取 `TargetPortName`（`Confirm` 写入时放的就是原值），取不到再剥 `LinkProtocol.ConstantDisplayPrefix` 前缀 |
| 改 `UpdatePresetOptions()` | 原来无条件 `ConstantValue = PresetOptions.First()`，会把刚回显的值冲掉；改为**只在空着时**才退到第一个预设项 |

**两条设计红线**（都写进注释了）：

1. **换端口必须重置常量框** —— 要么回显该端口自己的值，要么清空，绝不能留上一个端口的残留。
2. **连线的文本不许进常量框** —— 只回显 `LinkKind.Constant`；上游端口/全局变量/运行时变量的
   来源由左栏以地址展示，塞进常量框会让"点确定"把连线改写成常量，等于悄悄把线拆了。

**新增断言**（`FlowCanvasChecks\VariableBindingCheck.cs`，5 条，直接驱动 ViewModel 不碰 WPF 控件）：
前提（值存在 InputValues）/ 打开即回显手填值 / 换到常量连线端口回显其常量 / 换到连线端口常量框清空 / 换回来值还在。

**验证**：整仓构建 0 错误；FlowCanvasChecks **421 通过 / 0 失败**；ScadaChecks 1691 通过 / 0 失败。

## 九、给「变量赋值」做专属配置界面（用户反馈：通用绑定窗口容易误解）

**用户的判断**：打开「变量赋值」看到的是通用「变量绑定」窗口，三栏并列、看不出先做哪步，容易误解。

**为什么通用窗口在这里别扭**：它是"给**任意端口**绑**任意数据源**"的通用工具，
而本节点只有"给一个变量赋一个值"这么简单的事。用通用工具表达简单意图，用户就得替工具消化概念差。

| # | 通用窗口的具体误导 | 根因 |
|---|---|---|
| 1 | 三栏并列，像三个平等选项 | 实际是两步：左选端口 → 右给值，界面没有引导 |
| 2 | 「选择上游算子」把整条流程都列出来 | 通用窗口不按类型过滤；对"给 Name 填常量"完全无关，还混着别的分支里的同名节点 |
| 3 | 右下角冒出 `Success` / `ErrorMessage` | 那是"你选中的上游节点"的输出口，但界面没写归属 |
| 4 | 概念层级多 | 输入端口 / 绑定 / 常量 / 上游输出 一整套，用户想的是"把 Expected 设成 xxx" |
| 5 | 常量框不提示该填什么类型 | 端口有 String / Bool / Object 之分，提示只有一句通用的话 |

**做法**：给插件实现 `IPluginCustomViewProvider`，用三行表单把语义摊平：

```
给一个运行时变量赋值
运行时变量只在本轮执行内有效、跑完即弃。要跨流程或需要随方案存盘，请改用全局变量。

变量名   [Expected                    ]            🔗 ✕
值       [黑,棕,玫红,红,黄            ]            🔗 ✕
☑ 变量不存在时自动创建

「值」填常量文本；要引用上游步骤的结果，点该行尾部的链接图标。
```

| `Plugins\Plugin.Utility\VariableAssignmentView.xaml` | **新增** | 三行表单；两行值编辑器用 `LinkableValueEditor`，布尔开关用 `CheckBox` |
| `Plugins\Plugin.Utility\VariableAssignmentView.xaml.cs` | **新增** | 纯壳，无业务逻辑 |
| `Plugins\Plugin.Utility\VariableAssignmentPlugin.cs` | 改 | 实现 `IPluginCustomViewProvider.GetConfigView`（`Initialize(stepData)` + `DataContext = this`，与其它插件同一约定） |

| `Shard\Core.Controls\LinkableValueEditor.xaml.cs` | **顺带修 bug** | `IsTextEditableType` 白名单里加 `object`，见下 |

**顺带修的 bug**：`LinkableValueEditor.IsTextEditableType` 的白名单是
`string / 基元类型 / enum / decimal` —— **不含 `object`**。而「变量赋值」的「值」端口正是 `InputPort<object>`

## 十、变量赋值支持「全局变量」作用域（用户反馈）

**用户诉求**：想用「变量赋值」把流程里的 HImage 写进**全局变量 `Img`**，从而把「变量定义」和「图像赋值」两个节点从流程里删掉。

**先说清他们那条报错的性质**（不是 bug）：

```
[连线类型不匹配] '变量赋值_5' 的输入端口 'Name' 期望 String，但上游 'Global' 提供的 'Img' 是 HImage
步骤[线序检测.变量赋值_5] 执行失败: 本地变量 全局变量 (Global).Img 不存在
```

`变量名` 端口要的是**变量名的文本**，而它在变量绑定里把 `Img` 这个**全局变量本身**连给了它 →
HImage 塞不进 String（类型守门正常拦下）→ 运行期又拿那串地址文本当名字查 → 找不到。
**正解是「变量名」那格直接打 `Img`。**

**先核实的三处底细**（决定了能不能做）：

| 环节 | 结论 |
|---|---|
| 变量管理能否建「图像 (HImage)」类型的变量 | ✓ 能（`GlobalVariableManagerViewModel:453`） |
| 插件能否把 HImage 写进全局变量 | ✓ 能（`IGlobalVariableWriter`，做「图像赋值」时加的） |
| SCADA 图元能否显示该变量 | ✓ 能（`ScadaValueSource:65` 把 HImage 转 BitmapSource；图元描述写着"绑一个图像变量（HImage）"） |
| 「变量赋值」接上全局写入 | ✗ 缺这一环 ← 本次补的就是它 |

**决策（用户选项）**：给「变量赋值」加一个**作用域**参数 —— `Runtime`（运行时变量，默认）/ `Global`（全局变量）。
不采用"先找运行时、再找全局"的自动路由：同名时两者是不同东西，自动路由要么歧义、要么用户看不出写去了哪。

**实现**：

| 文件 | 动作 | 说明 |
|---|---|---|
| `Plugins\Plugin.Utility\VariableAssignmentPlugin.cs` | 改 | 新增 `Scope` 端口 + 全局写入分支（走 `context.GlobalVariables`）+ 作用域取值白名单校验 |
| `Plugins\Plugin.Utility\VariableAssignmentView.xaml` | 改 | 顶部加「作用域」下拉；提示里写明全局变量须先在变量管理里建好 |
| `FlowCanvasChecks\VariableAssignmentCheck.cs` | **新增** | 8 条断言，见下 |

### 踩到的真坑：枚举端口不能经 InputValues 往返

第一版把作用域写成 `InputPort<VariableScope>`（枚举），存盘后是 `"Scope": 1`，
再打开时 `ApplyConfigValues` 把它赋给端口 → **直接抛异常**：

```
InvalidCastException: Invalid cast from 'System.Int32' to 'VisionMaster.Plugins.Util.VariableScope'.
```

`InputPort<T>.Value` 的 setter 对枚举只做硬转换，不做"从数字/文本解析"。
（图像采集的 `Mode=0` 之所以一直没问题，是因为它是 `[StepConfig]` **属性**，走的是另一条带转换的路径。）
**改成 string 端口**（`"Runtime"` / `"Global"`），两端都能无损往返；
并且加**取值白名单校验** —— 认不出来就报错，绝不"不是 Global 就当 Runtime"，
否则拼错一个字母会把结果静默写到另一个变量池里。

**这个坑是离屏渲染探针抓出来的**：探针在 `Initialize(stepData)` 那一步就炸了，
而单看代码、单跑断言都不会暴露 —— 这也是为什么每轮改视图都要真渲染一遍看。

**新增断言**（`VariableAssignmentCheck.cs`，8 条）：

| # | 断言 | 结果 |
|---|---|---|
| 1 | 全局变量注册后按名可查（注册表订阅了集合变更） | ✓ |
| 2 | 【运行时】不存在 + 勾自动创建 → 建成并赋值 | ✓ |
| 3 | 【运行时】已存在 → 覆盖为新值 | ✓ |
| 4 | 【运行时】不存在 + 没勾 → 明确报「不存在」 | ✓ |
| 5 | 【全局】目标存在 + 值是 HImage → **写进全局变量** | ✓ 变量现值 = HImage |
| 6 | 【全局】目标不存在 → 明确报错、**且不新建变量** | ✓ 变量数 14 → 14 |
| 7 | 【全局】类型不匹配（int 变量写文本）→ 明确报错 | ✓ |
| 8 | 作用域取值拼错 → 明确报错，不静默当成运行时 | ✓ |

前 4 条是为了证明**既有行为没被碰坏** —— 这个节点在既有流程里到处都是。

### 已知边界

1. **「不存在就新建」没有做**，两条理由：
   - **SCADA 绑定是设计时动作**：变量不在变量管理里，右侧 `ƒx` 就选不出它，新建救不了设计时；
   - **跨线程**：`GlobalVariables` 是 UI 绑定的 `ObservableCollection`，而流程跑在后台线程上，
     从插件路径往里插会踩 WPF 跨线程；要做需要额外设计（如"待创建队列 + UI 线程消费"）。
   现在的行为是**明确报错并给出中文原因**，与「图像赋值」当初的决策一致。
2. **作用域是字符串参数**（`Runtime` / `Global`），不是枚举 —— 原因见上。
3. **「图像赋值」插件保留未删**：新路径跑通前先留着，避免出现"两个都不能用"的空窗。
4. 「变量定义」节点与本改动无关（它建的是**运行时**变量），删不删都不影响全局变量。

## 十一、修「保存方案失败：HALCON #4056 serialize_image」（用户反馈）

**现象**：保存方案弹红条

```
保存方案失败: HALCON error #4056: Image data management: object-ID is NULL (0) in operator serialize_image
```

**根因**：`VariablePersistenceService.Capture` 把全局变量的**值**原样塞进了快照：

```csharp
case LocalVariableModel local:
    snapshots.Add(new VariableDto {
        ...
        DefaultValue = local.DefaultValue,   // ← object
        Value = local.Value                  // ← object
    });
```

而 `VariableDto.DefaultValue` / `Value` 的注释写明约定是「**JSON 原生编码：数字/字符串/布尔/数组**」。
图像变量的值是个 `HImage` —— Newtonsoft 序列化它会走 Halcon 自己的序列化（`serialize_image`），
句柄为空（未初始化 / 已释放）就抛 #4056。**而这一抛发生在"保存方案"里，于是整个方案都存不下来。**
（就算句柄有效，把整幅像素写进 `.vms` 也是荒唐的。）

**修法**：`Capture` 增加 `PersistableValue` 白名单 —— 只有
数字 / 字符串 / 布尔 / 枚举 / `DateTime` / 由它们构成的数组才落盘，其余（`HObject`、自定义对象、位图类第三方对象）
一律落 `null`。**只存定义（名字/类型/描述/稳定身份），不存值。**

这不是"权宜之计"，而是与平台既有口径一致：
`VariableNode` 写着「图像的来源本就是流程，不是手填」，
`VariableValueConverter` 写着「位图不是一段文本，手填这条路根本不存在」——
图像变量的值本就是流程产物、重启即失效，本来就不该落盘。

| 文件 | 动作 |
|---|---|
| `VisionMaster\Services\VariablePersistenceService.cs` | 改：`Capture` 的两个值字段过 `PersistableValue` 白名单；新增 `PersistableValue` / `IsPersistable` |
| `FlowCanvasChecks\VariableAssignmentCheck.cs` | 改：新增 `[A3]` 段（4 条断言） |

**新增断言**（`[A3]`）：

| 断言 | 结果 |
|---|---|
| 含图像变量的方案能序列化（旧实现抛 HALCON #4056） | ✓ |
| 图像变量的定义照样落盘（名字 / 类型 / 稳定身份都在） | ✓ `DataTypeString=HalconDotNet.HImage…` |
| 图像变量的当前值与初始值都不落盘（落 null，不把像素写进 .vms） | ✓ `Value=null / DefaultValue=null` |
| 普通变量的值照旧往返（这次收紧没有误伤） | ✓ `Num.Value=42` |

用例里**故意放了两个图像变量**：一个有效句柄、一个 `new HImage()`（空句柄）——
空句柄那个就是用户踩到的情形，专门钉住它。

**已知边界**：
1. 这次只挡了"变量里的值"。若将来有别的路径把 `HImage` 塞进**步骤的 InputValues**（例如某插件把图像当常量存），
   同样会在保存时炸 —— 本次没有覆盖那条路。
2. 图像变量的值**不随方案保存**，重开方案后是空的（这正是期望行为：图的来源是流程，不是存盘）。

## 十二、已知边界

1. **`SampleX` 是唯一与相机/工装绑定的参数**（当前 440）。
   换相机高度、换工装、换线束走向都要改它 —— 它是脚本参数区的第一行。
2. **线距估计取相邻中心差的中位数**，靠的是"漏检的线少于一半"。
   若一条线束里**大多数**线都是白/浅灰（例如全白排线），中位线距会失真，芯数就不准了。
3. **只支持 3 通道彩色图**。1 通道灰度图会直接 `Context.Fail` 并说明原因（不静默给错结果）。
4. **颜色分类是"颜色词"级别的**：红/玫红/棕/灰/白/黄/绿/蓝/紫/橙。
   同色号的深浅（深红 vs 浅红）不区分，也不区分色差很小的同色线。
5. **配方是"从样本图量出来的黄金参照"，不是从工单/数据库取的**。
   当前样本即标准；换产品要在界面上改分支里的 `Value`。
6. **`IsRequired` 那处修复是全局的**：该节点以后手填值都能编译通过，
   但填了**不存在的变量名**仍只会在运行期报错（不是编译期），这一点没有变。
7. **结果分流的两条分支目前只写 `Verdict` 变量**（OK / NG），没有接「结果上报」「数据记录」。
   接产线时把那两个节点拖进分支即可，分支骨架不用动。
8. **改插件必须走「关程序 → 构建 → 核对 `Modules\` 里 dll 真的变了 → 再启动」**（上轮踩过的坑）。
   本轮改了 `Plugin.Utility`，已确认 `Modules\Plugin.Util.dll` 重新投递。
