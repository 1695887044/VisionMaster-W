# code-changes — 代码改动记录

> 每次代码改动一篇，`yyyy-MM-dd-<主题>.md`。**只追加，不回改**：结论错了就写新的一篇更正，
> 旧篇保留原样（它是当时的事实）。
>
> 检索请用 [`INDEX.md`](INDEX.md)（按日期倒序、自动生成、勿手改）。

## 这个目录是什么

`code-changes/` 是**日志类**文档，回答"某天改了什么、怎么验的、坑在哪"。
它不是设计文档（去 [`../方案设计/`](../方案设计/)），不是使用手册（去各插件目录），
也不是架构说明（去 [`../架构文档/`](../架构文档/)）。

## 什么时候必须写

满足任一条就写：

1. 改了公共契约、多模块、或流程语义（`AGENTS.md` R12 的大改动闭环）；
2. 踩了坑并且有理由相信别人还会再踩（**这是最有价值的一类**）；
3. 有个结论改变了后续做法，而它不在任何现行文档里；
4. 一轮会话结束（`AGENTS.md` R177：没留落盘物 = 这轮结论等于没发生）。

**不用写**：纯格式化、改错别字、一句话级改动。

## 一篇的最小骨架

```markdown
# <主题>（yyyy-MM-dd）

## 结论先行
一句话说清改完是什么状态、验没验、还剩什么。

## 改了什么
文件路径 + 关键函数/字段，别贴大段代码。

## 怎么验的
命令、日志文件名、条数。**没跑的必须写"没跑"**，不许含糊成"已验证"。

## 踩过的坑
现象 → 根因 → 为什么以后不会再犯（或：怎么早点发现）。
```

第 4 节是这个目录存在的理由。只写"改了什么"的记录，三个月后没人会读。

## 约定

- **文件名日期 = 实际动手那天**，不是提交那天。
- 中文文件名允许，但不要用 `()（）` 之外的括号混排，`_` 分隔优于空格。
- 一篇记录只讲一件事；一个改动跨两天就写两篇并相互链接。
- 目录不设子目录：`INDEX.md` 按月分组已经够用，再分一层就会有人找不到。
