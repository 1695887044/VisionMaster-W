# 2026-10-29 字区位变量并段（第 1 批）

> 来源：通讯体系优化清单第 1 批（B 项）。目标：`D100.5` 这类"字区里的布尔"不再每点独占一次设备往返。
> 前置：`2026-10-29-EasyNet真机连通修复（回显0x02与段上限）.md`、`2026-10-29-通讯超时三处错接修复（第0批）.md`。

## 一、当前状态

已落地。字区布尔作为"1 个字的段成员"跟着所属字一起读回，`DecodeBit` 的位上限改为按**单元宽度**决定
（字节单元 0~7、字单元 0~15）。`CommChecks` **393 通过 / 0 失败**（新增 8 条）。

## 二、已做

### 2.1 缺陷

`EasyNetAddress.TryCreatePollAddress` 原来对字区布尔直接 `return false`：

```csharp
// 字区 D/R/W：位访问走单读（规划器的位切片只处理字节内 0~7 位，字内位会越界）
if (DataType == DataValueType.Boolean) return false;
```

后果：每个 `D100.5` 每轮都落进**兜底单读**，一次设备往返。EasyNet 是位寻址协议，读一个字的 16 位是免费的——
旧实现等于"明明一次能拿 16 个位，却每个位各发一次请求"。

根子在 `PollBatchPlanner.DecodeBit` 只支持位偏移 0~7（从单字节切片取位），字内 8~15 位会抛
`ArgumentOutOfRangeException`。于是地址层干脆把整类变量排除掉了。

### 2.2 改动

| 文件 | 改动 |
|---|---|
| `Communication\Communications\Address\EasyNetAddress.cs` | 字区布尔改为"字区段成员"：`GroupKey=Area`、`Start=字号`、`SpanUnits=1`、`IsBitAccess=true`、`BitOffset=位号`、**`SegmentAddressOverride` 保持 null** |
| `Communication\Communications\Manager\PollBatchPlanner.cs` | `DecodeBit` 增加 `byteLength` 参数：位上限 = `byteLength*8`，取位改为 `data[byteOffset + bitOffset/8] >> (bitOffset%8)`；调用点传本变量的字节跨度 |
| `Core\CommunicationContracts\PollAddress.cs` | `BitOffset` 注释由"0-7"改为"按单元宽度（字节 0~7 / 字 0~15）" |
| `CommChecks\Program.cs` | 旧的"D 布尔位访问 → 单读"断言改为 8 条新断言（见 2.3）；新增 `FixedBytesConnection` 桩与 `EasyWordVar` 助手 |
| 两份 EasyNet 文档 | 原文"位访问不批量 / D100.15 必须走单读"加"已作废"标注并指向本文 |

### 2.3 断言（8 条）

| 断言 | 钉住什么 |
|---|---|
| D 布尔位访问 → 字区段成员 | `Start=100`（字号）、`SpanUnits=1`、`BitOffset=5`、`SegmentAddressOverride == null` |
| 数值 + 同字四个位 → 1 段 0 兜底 | 旧实现是 4 次兜底单读 |
| 同段内数值按字序解码（`20 10` → 4128） | 位成员进段没有污染数值解码 |
| 低字节 bit4=False / bit5=True | 字节内位序 LSB-first |
| 高字节 bit11=False / bit12=True | 跨字节取位（旧实现直接抛异常） |
| 整段只发一次请求 | `ReadCalls == 1`——收益的硬证据 |
| `TryReadOne` 位偏移 12 | 立刻读路径共用同一份解码 |
| S7 `M10.3` 仍取字节 0 第 3 位 | **反向**：放宽 `DecodeBit` 没带歪字节单元的协议 |

## 五、踩过的坑

- **`SegmentAddressOverride` 必须是 null，这是正确性前提不是风格**：`MergeSegments` 按
  `OrderBy(Start).ThenBy(EndUnit)` 排序，`SpanUnits=1` 的位变量 `EndUnit` 比同起点的 Int32 小，
  会排成**段首**。覆盖串一旦带 `.bit`（如 `"D100.5"`），整段就从位地址起读，段内所有变量一起错且**无异常**。
- **放宽解码会拆掉最后一道报警器**：旧实现在"字区位被误塞进段"时靠 `DecodeBit` 抛异常暴露
  （`MarkUncertain` + 限流日志，是可见失败）；放宽后同样的坐标错误变成"读到隔壁位"，完全静默。
  所以改动必须同批交付正/反断言，不能只放宽。
- **`ValueByteLength=1` 不是问题**：解码偏移来自 `UnitOffset × BytesPerUnit`，而 `ValueByteLength`
  只在 `Build()` 那个被 `!poll.IsBitAccess` 跳过的守卫里被读——解码路径从不碰它。
- **`CommunicationVariable` 没有 `Value` 属性**，读当前值要用 `CurrentValue`（`UpdateValue` 写入）。
  写断言时按"直觉"用 `.Value` 会连报一串 CS1061。
- **收益边界要说清**：孤立的 `D100.5`（附近没有同区字变量）改动后仍是 1 次往返（只是不再走反射单读），
  只有"字区布尔 + 同区字变量"才真正减少请求数。验收口径不能写"全部消除单读"。
- **插助手时误删了 `#region 断言框架` 头**：`Edit` 的 `old_string` 跨了 region 边界，
  替换后 region 头消失。判据是"改完看一眼上下文"——编译不会报错，但结构塌了。
