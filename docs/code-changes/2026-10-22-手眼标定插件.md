# 手眼标定插件（Plugin.HandEye）

> 日期：2026-10-22 ｜ 范围：`Plugins/Plugin.HandEye`（新建）+ `Core.Interfaces` 标定契约（纯加法）+ `FlowCanvasChecks` 断言 ｜ 状态：插件与断言已落地并全绿；**视图未做**（设计基线先行，见 §5）

## 1. 背景

`Plugin.Calibration` 只有二维能力：像素当量、九点（6 元仿射）、透视（9 元射影），外加 `IntrinsicsCalibration` 的内参标定。全仓搜索"手眼"只在 `Plugin.ImageScript/ScriptTemplates.cs` 的脚本文本里出现过，没有实现。

现场只要涉及"相机看到目标 → 机器人去抓"，就需要像素到机器人坐标系的 **6-DOF 刚体变换**，二维仿射表达不了（它假设目标永远在同一个平面、且相机与机器人平面平行）。这是接实际工程时最先撞到的缺口。

用户原话（m01540）："帮我实现手眼标定,告诉我 新建UI前要干嘛"。

## 3. 关键决策

1. **自研 Park-Martin，不用 HALCON `calibrate_hand_eye`**。后者要求 camera setup model + 标定板在各姿态下的观测位姿，是一条完整链路；现场实际能拿到的是"机器人位姿 + 相机位姿"成对数据。自研路线只要成对数据，且能拿合成数据做反证。
2. **相对运动两侧必须同侧取逆**：`A_0⁻¹·A_i` 配 `B_0·B_i⁻¹`。写成 `B_i·B_0⁻¹` 会得到一个**自洽但错误**的方程——实测解出的 X 旋转差 1 rad，而残差只有 3.6e-8。所以验收必须是"已知 X 的合成往返"，**残差小不代表解对**。
3. **"旋转激励"判据用 Max 而不是 (Max − Min)**。绕 X / Y / Z 各 60° 取三点是最充分的激励，但三个相对旋转的角度一模一样，(Max − Min) = 0 → 会把完全可解的数据判死（现场对称取点 ±45° 同理）。转轴是否张开交给奇异值比；反过来"角度有差但都绕同一根轴"由奇异值比拦，不会被这条漏掉。
4. **不复用 9 元 `ProjectiveMatrix`**：那是平面到平面的射影映射，装不下 4×4。`HandEye` 下 `Matrix` 保持零是**故意的**——未升级的消费者必须明确失败，不许把 6-DOF 静默降成平面仿射。
5. **`Transform.Value = null!` 而不是改 `OutputPort.Value` 的可空性**：`OutputPort<T>.Value` 声明成 `public object Value`（非空），但 setter 内部已经把 null 折成 `default(T)`，全仓既有写法就是 `null!`（`PreProcessingPlugin.cs:1401`、`ResultDisplayPlugin.cs:439`）。
6. **不标 `[ParallelSafe]`**：读文件本身无副作用，但同一份 CSV 被多条分支同时标定没有意义，先不给并行安全承诺。

构建（R179：必须 `-m:1 -nodeReuse:false`）：

```
dotnet build VisionMaster.sln -m:1 -nodeReuse:false
  → exit 0 / 0 个错误 / 1219 个警告 / 44.47 秒
dotnet build FlowCanvasChecks/FlowCanvasChecks.csproj -m:1 -nodeReuse:false
  → 0 个错误
```

断言宿主（日志 `artifacts/logs/20261022/gate-flow-handeye3.log`）：

```
通过: 3327  失败: 0        exit 0
```

19 条手眼断言全部通过，其中带真实数字的：

| 断言 | 实测 |
|---|---|
| 数学① 8 组合成往返 | 旋转误差 `0e+0` rad、平移误差 `1.257e-13 mm` |
| 数学⑥ 机器人侧加 0.05 mm 抖动 | 平移误差 `0.0816 mm`、平移 RMS `0.0976 mm`（残差非零 ⇒ 质量指标真在算） |
| 欧拉③ 位姿→六个数→位姿 | 最大偏差 `1.11e-16` |
| 插件⑥ 成功产物 | `Kind=HandEye`、矩阵 16 元、组数 8、与数学层最大偏差 `8.527e-14` |

四条退化路径全部"明确失败 + 说清理由"（不是返回一个看起来合理的矩阵）：

- 姿态完全不变 → `旋转激励不足：相机侧最大旋转只有 0°（要求 ≥ 5°）。请让机器人以不同姿态取点…`
- 绕同一根轴 → `旋转求解失败：旋转信息矩阵奇异（最小奇异值为 0），所有样本的相对旋转共线`
- 只有 2 组 → `样本不足：至少需要 3 组（当前 2 组）`
- 4 组 + 默认从严 → `成对数据只有 4 组，少于建议的 6 组：3 组能解但不可靠…`
- 残差超上限 → `平移残差 0.098 mm 超过上限 0 mm：点位数据可能含错点，或机器人未回零`

变异反证（R65）：

- 把相对运动的取逆侧换回**错误写法**（`B_i·B_0⁻¹`）→ `通过: 3315  失败: 12`，其中 `[HE] 数学①` 报「旋转误差 `3.142e+0` rad」「平移误差 `3.313e+2` mm」，`[HE] 插件⑤` 报「旋转残差 `31.146°` 超过上限 0.5°」，`[HE] 插件⑥` 报「Transform 为 null」。还原后回到 3327/0。**这条证明断言抓的是"解错"而不是"残差大"**——错误写法下残差可以很小。
- 附带否证（记下来免得以后误判）：把 `MinSingularRatio` 从 `1e-3` 放宽到 `1e-9` **不会**让数学④ 转红。共线样本的奇异值比恰好是 `0`，`0 < 任何正阈值` 都成立，所以这条常量不是该断言的实际守门人。真正守门的是"奇异值比为 0 就失败"这个事实本身。

## 5. 边界与未做

- **没有视图**。本阶段只到"端口 + 配置 + 算法"。R127/R128 要求先有 `docs/UI设计基线/手眼标定/` 才能改 XAML，该目录尚未建。`Help/06-dev-extension-checklist.md` 第四节写了加 UI 前必须完成的六件事。
- **只支持 ZYX 欧拉角**输入。接新品牌机器人必须先核对三个符号（手册 `03-mounting-and-frames.md` 给了"只绕单轴转 90°"的核对方法）；符号错的表现是"残差正常、抓取点整体镜像"。
- **不做运行期坐标换算**。把像素点换算成机器人坐标属 `Plugin.PoseTransform`，本插件只负责标定出那个 4×4。
- **断言只跑合成数据，没接真机**（R175 分层：真实渲染/启动链才用真 exe）。真机验证待现场数据。
- **4 组样本在旋转激励不足时仍会失败**——这是数学事实（旋转求解下限 3 组，但 3~5 组没有冗余），不是缺陷。
- `RequireRecommendedPairs` 默认从严（≥6 组）；现场只有 4 组时要手动关掉并自担风险。
