## 一、需求与决策

### 1. 需求（用户原话）

> 「你的按钮 不能绑定一个bool量后 选择 按下ON 或者切换」

拆开就是三件事，缺一个都算不上商用：

| # | 能力 | 现场含义 |
|---|---|---|
| 1 | **绑一根 bool 变量** | 按钮不再是"纯动作入口"，它得认识现场的那根开关量 |
| 2 | **模式可选**（按下ON / 按下OFF / 置位 / 复位 / 取反） | 点动（手按着才动）与置位（点一下锁住）是两种完全不同的操作习惯 |
| 3 | **状态双色双文本** | 同一个按钮，ON 显示「运行」+ 蓝底、OFF 显示「停止」+ 灰底，不用另配一个指示灯 |

### 2. 决策清单 —— 与「按钮」的边界

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| A-1 | 塞进 `Hmi.Button` 还是新开一个图元 | **新开 `Hmi.BitButton`** | 手册把两者分成两个控件（7.3.3.5 按钮 / 7.3.3.7 位按钮）。硬把位逻辑塞进按钮，会让"只想记一条日志"的按钮也背上一个**必须绑的变量**——这是给大多数场景加负担 |
| A-2 | 两者的分工怎么说清 | 按钮 = **动作入口**（点下去干什么由属性面板「事件」里的动作表决定：记日志 / 写变量 / 切画面，自己不认变量）；位按钮 = **变量的化身**（绑一根开关量，点击直接对这根量做位操作） | 一句话能说清的分工，才是好边界。含糊的边界迟早会长成"按钮里什么都有" |
| A-3 | 位逻辑交给动作表行不行 | **不行，必须写在控件里** | 位操作要**先读回当前值**（取反）、要**区分按下与释放**（按下ON / 按下OFF），而"写变量"动作是无状态的单向写（给什么写什么），表达不了这两种语义 |
| A-4 | 那它怎么把值写回工程变量 | 复用 N-2 落下的 `IScadaValueWriter` | 数值域的输入框（`IOFieldElement.CommitEdit`）已开同一先例：图元在自己的交互回调里回写工程变量，再由数据泵读回来显示——"画面上显示的"与"变量里存的"永远是同一个值 |

### 3. 决策清单 —— 控件层（`BitButtonElement`）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| B-1 | 状态外观从哪来 | **只读 DP**：`DisplayText` / `DisplayFill` / `DisplayForeground` | 与指示灯（`IndicatorElement`）同一路子：外观由一组输入推导（`IsOn` + `OutputInvert` + 六条状态外观），结果放只读 DP 供模板绑定。**模板里一条 DataTrigger 都不写**——"状态怎么判"这件事不该复制进 XAML，断言也能直接读这三个串 |
| B-2 | 六个模式怎么摆 | 五条中文常量直接落描述符 `Choices`（`置位`/`复位`/`取反`/`按下ON`/`按下OFF`） | 下拉的值与代码里的常量是**同一份声明**，不会出现"面板改了、代码不认"的两处写法 |
| B-3 | 「切换窗口」模式呢 | **不给常量** | 切画面要动运行态导航，那是按钮动作表 `ScadaActionType.Navigate` 的活。理由写进了 `Mode` 的 `Description`，不留暗坑 |
| B-4 | 按下 / 释放走哪个事件 | **隧道事件** `OnPreviewMouseLeftButtonDown/Up` | 冒泡阶段会被 `ButtonBase` 之类吃掉（与数值域进编辑态同一坑） |
| B-5 | 门禁（能不能操作）放哪 | 收进 `BeginPress`，**不放事件处理器** | 少一处判断就少一处漏判。三条件：有写通道（`RuntimeContext.Writer`）+ 「读变量」真绑了变量且没被停用 + 图元没被禁用。**设计期（无运行上下文）点一下只是选中图元** |
| B-6 | 滑开（按下后移出）怎么算 | 与画布对「释放」的同对象校验同口径——**这一下作废**；但**瞬动模式（按下ON / 按下OFF）必须把值复位** | 否则留下"手已经移开、量还按着"的假象，现场就是**电机一直转**，不可接受 |
| B-7 | 写出去的字面量 | `"1"` / `"0"` | 交给 `IScadaValueWriter.TryWriteText`，由 `VariableValueConverter` 落到 bool 变量——**写 bool 不必新增动作类型** |
| B-8 | 取反写回的是什么 | `!State`（**显示的状态**取反） | 写回去之后数据泵把新值读回来，显示随之翻转。"取反"是读回当前值再写反向，不是无脑写一个固定值 |
| B-9 | 写完要不要自己改 `IsOn` | **不改** | 值由变量持有，数据泵马上会把新值读回来。自己改一遍会出现"两个来源"，迟早不一致 |
| B-10 | 写失败要不要弹提示 | **不弹** | 失败原因（没绑变量 / 绑定停用 / 变量不存在 / 写不进去）由写通道记进运行日志。图元够不着变量注册表，编不出更准的话 |

### 4. 决策清单 —— 描述符（唯一真相，**D2**）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| C-1 | 新属性怎么分组 | `Mode` 进既有**「常规」**组；`IsOn` / `OutputInvert` / 六条状态外观进**新增「状态」**组 | 面板上"状态"是一整块语义（一根变量 + 两种长相），塞进"文字"会让"文字"变成杂物抽屉 |
| C-2 | 「状态」组能不能绑 | **能**（`IsBindable = true`，`状态` 不在 `NonBindableGroups` 里） | 该集合是 `{ "位置与尺寸", "外观" }`。状态文本与颜色都可能跟着配方走 |
| C-3 | 唯独 `OutputInvert` 不给 ƒx | **刻意不给** | 它是**设计期定死的极性**（低有效信号对齐），不是现场变量。给了 ƒx 反而制造"运行中翻极性"的误用 |
| C-4 | 组序 | 声明首现即组序：`常规 / 位置与尺寸 / 状态 / 文字 / 外观 / 事件 / 权限` | `GeometryProperties.With(extras)` 把 `Standard`（名称/X/Y/宽/高/旋转）排在**前**，extras 排在后 |
| C-5 | Choice 默认值 | `按下ON`（∈ `Choices`） | 描述符注册的三类硬校验之一就是"Choice 默认值 ∉ Choices"，会直接让整个图元类型注册失败。选 `按下ON` 因为它是**最常用的瞬动** |

### 5. 关键决策 —— 为什么把「按下/释放」抽成 public

写断言时卡住：**怎么像真按一下那样驱动控件？** `MouseEventArgs` 连公开构造函数都没有，`Scada.Controls` 也没对 `ScadaChecks` 声明 `InternalsVisibleTo`（全仓确认过），伪造鼠标设备这条路走不通。

选择：**把交互抽成三个 public 方法** `BeginPress()` / `ReleasePress()` / `CancelPress()`，事件处理器改成对它们的委托。

```csharp
protected override void OnPreviewMouseLeftButtonDown(MouseButtonEventArgs e)
{
    base.OnPreviewMouseLeftButtonDown(e);
    if (e.Handled) return;   // 别的隧道处理器先抢了（如数值域进编辑态），那就别动
    BeginPress();
}

protected override void OnPreviewMouseLeftButtonUp(MouseButtonEventArgs e)
{
    base.OnPreviewMouseLeftButtonUp(e);
    ReleasePress();
}

protected override void OnMouseLeave(MouseEventArgs e)
{
    base.OnMouseLeave(e);
    CancelPress();
}
```

依据与收益：

1. **有先例**：`IOFieldElement.BeginEdit()` 就是 public，断言直接调它模拟"点一下进编辑态"。
2. **交互的"唯一真相"留在控件里**：鼠标事件与断言是**同一个入口的两个调用方**，不是两份实现。断言驱动的是真代码，不是复刻。
3. **门禁一并收进来**：`CanOperate` 从事件处理器挪进 `BeginPress`——少一处判断就少一处漏判。

## 三、六个模式的写出时点

| 模式 | 按下 | 释放 | 滑开（取消） | 典型用途 |
|---|---|---|---|---|
| **置位** | — | 写 `1` | 一条不写 | 锁住一个标志、置启动位 |
| **复位** | — | 写 `0` | 一条不写 | 清标志、急停复位 |
| **取反** | — | 写 `!State` | 一条不写 | 手/自动切换 |
| **按下ON** | 写 `1` | 写 `0` | **写 `0`（复位）** | 点动、夹紧（手按着才动） |
| **按下OFF** | 写 `0` | 写 `1` | **写 `1`（复位）** | 低有效那一侧的点动 |

三条纪律：

1. **置位/复位/取反在"释放"这一侧生效**——"这一下确认后才动现场量"，按下就动会让误触直接落到设备上。
2. **瞬动模式两侧都要复位**——只复位一侧是漏判。
3. **门禁不过就一条不写，连按下态都不亮**——"点了没反应"总好过"点完才在日志里说写不进去"。

## 六、下一件（"先深后广"主线）

**先深**三件已闭环：N-1 颜色取色板 → N-2 数值域可读可写 → **N-3 位按钮六模式**。

按用户拍板「先深后广（推荐）」的释义，**接下来横向扩图元数量**：

> 「做完这三件**再横向扩图元数量**。」

手册里还没落的图元（按商用必要性排序）：**字符IO域 / 符号IO域 / 文本开关 / 位指示灯 / 字指示灯 / 图形开关 / 功能键 / 字按钮**；以及画面级机制（软键盘 / 弹出画面 / 模板画面 / 画中画 / 画面复制 / 系统图库）。

其中**位指示灯 / 字指示灯**与本次位按钮**共用同一套"变量 → 状态 → 只读 DP"范式**（`IndicatorElement` 已有 `LampBrush` 先例），是横向扩展里成本最低、复用度最高的一批。
