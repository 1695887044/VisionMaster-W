# 2026-09-15 条件逻辑编辑器 P0/P2 逻辑漏洞修复（方案 A）

## 一、需求与决策

### 背景
条件逻辑配置中心（ConditionEditor）全链路审计发现 14 条疑似漏洞，按 P0(数据正确性)/P1(UI 说谎)/P2(运行时不一致)/P3(空壳) 分级。用户拍板**方案 A：只修 P0+P2，先止血**，P1 界面重构留待后续。

### 本次修复的漏洞清单与决策

| 编号 | 漏洞 | 决策 |
|---|---|---|
| P0-① | 改条件不触发重编译：`FlowModel.Version` 只订阅顶层 Steps 的 PropertyChanged，条件存在 `Children[i].Expression` / `LocalVariables` 里，引擎永远感知不到 → "试运行对、正式跑错" | 保存成功后手动 `Workspace.CurrentFlow.Version++`，逼出"需要重新编译"提示 |
| P0-② | 取消不回滚：AvalonEdit TextChanged 打字即直写活模型 `SelectedBranch.Expression`，点"取消"数据已污染 | **事务草稿模式**：打开时深拷贝分支表头（StepName/BranchType/Expression）为草稿，弹窗期间一切编辑落在草稿上；保存才写回，取消即丢弃 |
| P0-③ | 单绑弹窗越界写活模型：ConditionEditor 发起的单绑 DataBind 弹窗在 `DoFinalBind`/`Confirm` 中把 `LinkReference` 直写 `Workspace.CurrentStep.LinkedSources`，此时 CurrentStep 可能是条件节点、bindKey 是中文描述（"当前准备绑定的变量"），留下垃圾键 | 单绑模式下（`_isSingleBindMode`）跳过对活模型 LinkedSources 的写入，只回传 `BoundLink` 给出题人（两个调用方——ConditionEditor 与 LinkPathEvent——本来就都消费回传值，行为不丢） |
| P0-④ | 保存零校验：别名可撞名(`Var_{Count+1}`)、空别名静默丢弃、语法错误延迟到运行时编译才爆、FlowCompiler 里空表达式标"[编译警告]"实为阻断编译的硬错误 | ①OnSave 前完整校验：别名非空/合法标识符/不重复、类型安全白名单、每条表达式用与 FlowCompiler **同款**的 `DynamicExpresso.Interpreter().Reference(typeof(Math)).Parse(expr, typeof(bool), params)` 预检；②整行全空的变量行静默丢弃、"绑定了但没名字"的行报错；③`[编译警告]` 文案改为 `[编译错误]` 诚实化 |
| P2-⑧ | While 与 If 运行时不一致：未绑定变量 While 一律注 `0.0`（string/bool 会炸委托传参）、条件求值异常 `catch { break; }` 静默零日志、迭代上限 9999 强制退出无提示 | 三处全部对齐 `CompiledIfNode`：按 `VarTypes` 声明类型给默认值（string→""、bool→false、其余 0.0）；catch 记 `Logger.Error` 后再 break；达到 MaxIterations 记 `Logger.Warn`（取消导致的中途退出不误报） |
| P2-⑨ | NaN/Infinity 无声走 Else | 属于浮点比较语义本体（NaN 与任何数比较为 false），不在本次范围，已在代码评审中向用户说明 |

### 关键设计说明（为什么这么做）

1. **草稿只拷贝"分支表头"，不拷贝 `Steps`**：本弹窗的职责边界是"编辑条件表达式+变量引脚"，分支内的步骤列表不属于它管。深拷贝 Steps 既昂贵又会在写回时破坏对象标识（SelectedStep 引用会失效）。
2. **`Branch` 入参索引换算**：调用方若传入活模型分支对象作初始选中（当前无调用方传，但接口存在），需 `node.Children.IndexOf(liveBranch)` 换算成同索引草稿，否则 ListBox 选中的是活模型对象，TextChanged 会绕过草稿直写。
3. **校验参数表含 `RuntimeVariableRefs`**：弹窗不编辑运行时变量引用，但表达式里合法引用它们；预检参数表不带就会误报"未知标识符"。
4. **While 的"循环体"分支 `BranchType=Default`**：If 分支里 Default/Else 不要求表达式，但 While 的循环体恰是 Default 类型且**必须**有表达式——校验按 `_targetNode is WhileStep` 分流，照抄编译器自己的规则。

## 四、已知边界

1. **Version++ 只作用于 `Workspace.CurrentFlow`**：条件节点必然位于当前流程（弹窗从流程栏打开），但若未来支持跨流程编辑子程序，需改为沿父链找所属 FlowModel。
2. **正式运行的会话编译缓存**：Version++ 能触发"需要重新编译"提示，但已在跑的循环是否即时换编译产物取决于调度器；建议保存后手动停止再启动验证。
3. ~~**P1 未动**~~：**已于同日方案 B 批次全部落地**，见下方"六、P1 界面重构"。
4. **RuntimeVariableRefs 撞名**：若运行时变量与局部别名同名，编译器会给 DynamicExpresso 传重名 Parameter 可能抛异常——弹窗校验已按"别名优先"规避，但该场景本身无 UI 可造（两拨名字来源不同），风险极低未处理。
5. **取消按钮的"草稿丢弃"依赖 GC**：草稿是普通对象图，无泄漏风险；但 `Variables` 里的 `VariableItem` 订阅了 View 的 PropertyChanged（着色器），弹窗关闭后 View 先于 VM 销毁属正常 WPF 生命周期，无残留。

## 五、重启后回归清单

1. 打开 If 弹窗 → 改表达式 → 点**取消** → 流程栏分支名 `[ ]` 内容应不变；
2. 同样操作点**保存** → 流程栏分支名应更新，且主界面出现"需要重新编译"状态；
3. 表达式写 `Score > ` → 保存应弹"语法错误"且停留在弹窗；
4. 加两行变量都叫 `Var_1` → 保存应报"别名重复"；
5. 条件变量绑定上游 → 取消 → 该条件节点 LinkedSources 不应出现"当前准备绑定的变量"键；
6. While 循环条件写错类型（如 string 变量 `Name > 5`）→ 日志窗口应有"While节点…条件执行异常"而非无声退出；
7. While 死循环（条件恒真）→ 9999 次后日志应有"达到最大迭代次数…疑似死循环"。

# 六、P1 界面重构（方案 B 批次，同日追加）

## 需求与决策

用户拍板：**For 弹窗并入条件编辑器（方案 b）**，清单上 P1 五项全部执行。

### 病根诊断
⑤"Else 让写条件"、⑥"For 弹窗空白"、⑦"红灯红字标准不一"是同一病灶的三次发作：`BranchType.Default` 一个枚举值被赋予三种相反语义——ConditionStep 里"免条件"、While 循环体里"必须条件"、For 循环体里"免条件但要次数"。UI、校验、编译器各按自己的理解猜它的含义，于是各说各话。

### 决策：从源头治，新增 `BranchType.WhileLoop`
| 备选方案 | 取舍 |
|---|---|
| a. 各处继续特判（`is WhileStep` 式） | 判点越多越容易漏，本次 P0 校验就差点被 Default 误伤——拒绝 |
| b. StepCollection 加 `bool? RequiresCondition` 字段 | 三态字段易误用，且没解决"类型系统该表达却让人记"的问题——拒绝 |
| c. **新增 WhileLoop 枚举值 + 加载时归一化老数据（采纳）** | 一个字段表达一个语义；FlowCompiler 的 While 路径（A-1）本就不读 BranchType，零编译改动；If 编译路径的 Else/Default 强制 true 逻辑不受影响 |

⚠ 枚举值只追加在末尾：JSON 按 int 序列化，插入中间会错位老方案。

## P1 回归清单（并入重启后总测）

1. 双击 For 节点 → 弹窗显示"计次循环设置"，改次数保存 → 重开弹窗数值保留；填 0 或 999999 → 校验弹窗拒存；

3. While 循环条件清空 → 流程栏"循环体"卡变红、文字带"未绑定条件"（老方案需先加载触发归一化+保存一次）；

5. 变量别名输入 `1abc` 或两行同名 → 输入框即时红框、悬浮有原因，不用等保存；
6. 取消 For 弹窗 → 节点循环次数不变（事务语义与条件编辑一致）。

## P1 已知边界

1. **老方案的 While 归一化只发生在加载路径**（`SolutionService.LoadAsync`）：若方案经其他通道进入内存（如未来新增导入/复制粘贴整流程），需同样调 `NormalizeBranchTypes`。
