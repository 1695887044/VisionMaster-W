# 2026-09-24 弹窗尺寸自适应与「变量来源」选中布局修复

## 1. 需求与背景

用户在实机使用中反馈三个问题（附两张实机截图）：

> 变量管理的界面拉深后,会异常,不会自动缩放,变量来源的选中布局也有问题
> 通信设置也是这样的问题

拆成三条具体诉求：

| # | 诉求 | 现象 |
| --- | --- | --- |
| 1 | 变量管理窗口拉大/最大化后**内容不自适应** | 内容块整体居中缩在中间，四周一圈留白，永远不跟着窗口变宽 |
| 2 | 「变量来源」列表**选中布局不对** | 经 `AskUserQuestion` 确认，用户指的是「右侧计数徽标位置不对」 |
| 3 | 通讯设置**同样的问题** | 与 #1 同源 |

## 2. 根因

### 2.1 主因：`UserControl` 根节点写死了 `Width` / `Height`

| 文件 | 原写法 |
| --- | --- |
| `CommunicationSettingsView.xaml` | 根节点 `Width="1080" Height="620"` |
| `GlobalVariableView.xaml` | 根节点 `Width="1240" Height="700"` |

**原理**：`UserControl` 的 `HorizontalAlignment` 默认值是 `Stretch`（撑满父容器）。
但 WPF 的布局规则是「显式尺寸优先于对齐」——**一旦显式写了 `Width`，`Stretch` 就退化成「居中」**：
元素按固定尺寸摆放，父容器多出来的空间平均分到两侧。

这完美解释了两张截图「左右留白对称」的现象，也解释了「拉大窗口内容纹丝不动」。

值得注意的是：**两个视图内部的 `*` 行 / `*` 列定义本身是正确的**，
问题只在外层 —— 外层被固定尺寸锁死，内部的 `*` 就永远分不到多余空间。

### 2.2 次因：`ListBoxItem` 的 `HorizontalContentAlignment` 默认是 `Left`

`GlobalVariableView.xaml` 左栏的 `ListBox` 为了去掉系统默认外观（选中蓝底、焦点框），
在 `ItemContainerStyle` 里把 `ListBoxItem` 模板整个换成了裸 `<ContentPresenter />`：

```xml
<ControlTemplate TargetType="ListBoxItem">
    <ContentPresenter />
</ControlTemplate>
```

配合 `HorizontalContentAlignment` 的默认值 `Left`，后果是：

1. `DataTemplate` 根 `Border` 只按「内容宽度」排版，不铺满整行；
2. 节点模板 `Grid` 里第 1 列（名称，`*`）**塌缩成 0**；
3. 于是第 3 列（计数徽标，`Auto`）**紧贴在文字后面**，而不是右对齐到行尾；
4. 顺带地，浅蓝选中高亮底也不会铺满整行。

即：徽标位置完全由「第 1 列 `*` 是否展开」决定，而 `*` 展开的前提正是
`HorizontalContentAlignment="Stretch"`。

### 2.3 范式对照：仓库里早就有正确写法

`PluginConfigShellView.xaml` 是「可缩放弹窗」的既有范式 —— 把「初始尺寸 + 最小尺寸」挂到
`Window` 上，`UserControl` 不写尺寸。其原注释已经点明了关键：

> 不用 `SizeToContent`，否则手动放大后内容不会重新布局填满

## 3. 决策

### 3.1 尺寸搬家：`UserControl` 根节点 → `prism:Dialog.WindowStyle`

两个视图都删掉根节点的 `Width` / `Height`，改挂：

```xml
<prism:Dialog.WindowStyle>
    <Style TargetType="Window">
        <Setter Property="ResizeMode" Value="CanResizeWithGrip" />
        <Setter Property="SizeToContent" Value="Manual" />
        <Setter Property="Width"  Value="1080" />   <!-- 变量管理为 1240 -->
        <Setter Property="Height" Value="620"  />   <!-- 变量管理为 700  -->
        <Setter Property="MinWidth"  Value="960" /> <!-- 变量管理为 1120 -->
        <Setter Property="MinHeight" Value="520" /> <!-- 变量管理为 580  -->
    </Style>
</prism:Dialog.WindowStyle>
```

搬到 `Window` 后 `UserControl` 自然撑满，内部的 `*` 行 / `*` 列才能吸收多余空间。

与 `PluginConfigShellView` 的**唯一差别**：这里**刻意不设** `WindowStyle="None"`，
保留系统原生标题栏（最小化 / 最大化 / 关闭），因为这两个弹窗是管理类工具窗，
用户需要用到最大化按钮 —— 这也正是本次 Bug 被发现的场景。

**刻意不用 `SizeToContent`**：它会让窗口随内容自己改大小，且手动放大后内容不重排。

### 3.2 选中布局：补 `HorizontalContentAlignment="Stretch"`

在「变量来源」`ListBox.ItemContainerStyle` 里显式补一个 Setter：

```xml
<Setter Property="HorizontalContentAlignment" Value="Stretch" />
```

并把「为什么必须显式写」的原因写进注释（避免后人当作冗余代码删掉）。

### 3.3 明确不动的部分

| 项 | 为什么不动 |
| --- | --- |
| 变量管理三栏列宽 `216 / 12 / 296 / 12 / *` | 主从布局（来源列表 + 表单 + 明细），左中两栏是固定宽度的操作区，**不该被拉宽**；只有明细表该吸收多余宽度 |
| `ScanGroupEditorView` 等小表单弹窗 | 走的是另一套范式（`ResizeMode="NoResize"` + `SizeToContent="WidthAndHeight"`），本就是内容自适应，无此问题 |

## 6. 已知边界

1. **窗口位置 / 尺寸不做记忆**。每次打开都回到初始尺寸（通讯设置 `1080×620`、变量管理 `1240×700`），
   不持久化用户上次拖拽的大小。若后续要加，需在 `WindowStyle` 之外补一段「关闭时存 / 打开时读」的逻辑。
2. **`MinWidth` / `MinHeight` 是经验值**，按「工具栏 + 表格表头 + 一行数据 + 底栏」不挤坏来定的：
   通讯设置 `960×520`、变量管理 `1120×580`。屏幕更小的机器（如 1024×768）打开时窗口会超出屏幕，
   但可手动缩放 —— 未做「按屏幕分辨率自适应初始尺寸」。
3. **变量管理左中两栏固定 216 / 296 像素**，在高 DPI（如 150%）下文字可能显挤。
   这是刻意的固定宽度策略，本次未改成比例宽度。
4. **未做 DPI 变更时的动态重排**验证（跨显示器拖动场景）。
5. **双击启动撞日志文件**（`IOException: … Logs\YYYY-MM-DD.log … being used by another process`）
   仍是既有问题，本次未修；实机点验前先确认无残留进程来规避。
