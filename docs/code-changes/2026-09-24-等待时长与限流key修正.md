# 2026-09-24 等待时长按到期算（C1）+ 限流 key 含连接名（C5）

## 一、需求与决策

### 1.1 问题 C1：Worker 恒定 10ms → 100Hz 空转

`ConnectionWorker.ComputeWaitMs()` 旧实现：

```csharp
if (State == ConnectionState.Connected && _scheduler is { HasWork: true })
    return 10;                       // ← 只要"已连接 + 有轮询工作"就固定睡 10ms
if (_autoConnect && State != ConnectionState.Connected)
    return 100;
return 200;
```

后果：**与扫描组周期完全无关地每秒醒 100 次**。

设一个连接有 1 个 10 秒周期的统计组（现场很常见），旧实现每 10ms 醒一次、每次醒来只看一眼 `IsDue()` 就接着睡——**1000 次唤醒里有 999 次是白干**。连接数一多（几十条），线程数与唤醒频率线性放大，纯粹烧 CPU 与电源。而唯一"换来"的好处只是"命令能快 10ms 被执行"。

**为什么现在才敢改**：这 10ms 原先有一半理由是"好快点响应命令"。上一轮 N1（写命令优先级）引入了唤醒信号 `_commandSignal`——命令入队即 `Release()` 立刻叫醒 Worker，**响应命令已不由这里负责**。于是等待时长可以纯粹为轮询节拍服务。

### 1.2 问题 C5：限流 key 不含连接名 → 跨连接互吞告警

`PollBatchPlanner` 的限流表是 **`private static readonly ConcurrentDictionary<string, long> _logTicks`**（跨连接共享，全进程一份），而段读失败/短读的 key 原先**只有地址**：

```csharp
LogThrottled($"seg:{seg.Address}", …);                       // 段读失败
LogThrottled($"short:{seg.Address}#{变量名}", …);             // 段内字节/点数不足
```

于是：**两台设备都读 `x=3;100`** 时，共用同一个 5 秒窗口——A 连接先失败报了一条，B 连接紧接着失败就被判"5 秒内已报过"直接静默。

现场表现：**日志里只看得到第一台设备出问题**，第二台怎么查都"没有报错"。这是典型的"故障被日志系统自己吃掉"，比不报警更危险（会让人有理有据地误判）。

对照：同一个文件里 `var:` 与 `decode:` 两处 key **本来就带连接名**（`$"var:{单读项.Variable.ConnectionName}.{名称}"`），只有 `seg:` / `short:` 两处漏了——属遗漏，不是设计。

### 1.3 核心决策与依据

| 决策项 | 结论 | 依据 |
| --- | --- | --- |
| C1 等待时长 | `Math.Clamp(scheduler.MsUntilNextDue(), 1, MaxIdleWaitMs)` | 见 1.4 |
| C1 上限 | `MaxIdleWaitMs = 200` | 见 1.4 |
| C1 下限 | **1**（不是 0） | 见 1.4 |
| C5 修法 | 给 `ReadSegment` 加 `ConnectionName`，3 处 key 补连接名 | 见 1.5 |
| N3（一条连接一个专用线程） | **只记录，本次不改** | 与用户确认的改动范围一致 |

### 1.4 C1 的上下限为什么是 1 / 200

**为什么下限是 1**：`_commandSignal.Wait(0)` 会**立即返回**。若 `MsUntilNextDue()` 返回 0 就直接透传，万一出现"某组明明到期却没能跑"的边角场景（例如取消令牌/异常路径），循环就变成**死循环空转**——比原来 10ms 更糟。留 1ms 兜底，对轮询精度无可感影响。

**为什么上限是 200**：`MarkPollPlanDirty()` **只置标志、不唤醒 Worker**（见 `ConnectionWorker.cs` 的 H1 注释），脏标记要等 Worker 下次醒来才被消费。扫描组周期最长 1 小时，若真睡满就会让"改了轮询计划"最长 1 小时不生效。而**旧实现**在"已连接但无轮询工作"时本来就是睡 200ms——取 200 作上限，等于**保证最坏响应延迟不劣于改动前**，这是一个安全的锚点。

**为什么取"最小值"**：组间周期升序即优先级，**最短周期组决定下一次"最早需要醒来"的时刻**。睡过头会让联锁点错过周期。

**为什么 `MsUntilDue()` 与 `IsDue()` 不会打架**：二者用**同一个基准** `_lastSuccessTicks + IntervalMs`——

```csharp
public bool IsDue()       => Environment.TickCount64 >= Volatile.Read(ref _lastSuccessTicks) + IntervalMs;
public long MsUntilDue()  => Volatile.Read(ref _lastSuccessTicks) + IntervalMs - Environment.TickCount64;
```

`MsUntilDue() <= 0` **当且仅当** `IsDue() == true`（除 `TickCount64` 的 15.6ms 粒度抖动外）。

### 1.5 C5 的修法依据：planner 必然属于一条连接

改 key 的前提是"一个 planner 只服务一条连接"。证据链：

1. `PollBatchPlanner.Build(variables, log)` 的 XML 注释写明参数是「**某连接下的**全部已注册变量」；
2. 唯一调用点 `AdvancedCommunicationManager.RebuildPollPlan(connectionName)` 里 `variables` 来自 `_registeredVariables[connectionName]`；
3. `PollScheduler.Create(variables.Values, …)` **每个连接调一次**（见 `RebuildPollPlan`）。

故 `ReadSegment` 在编译期从**段内首个变量**取 `ConnectionName`，即全段连接名，安全。

### 1.6 备选方案与不采纳的理由

| 方案 | 不采纳理由 |
| --- | --- |
| C1：改成 `Wait(0)` + 忙等 | 100% CPU 占用，比 100Hz 空转更糟 |
| C1：按"最小周期"固定睡 | 长短周期混合时短周期组准了，但"计划脏标记"的响应仍可能被长周期拖住；按到期算才是本意 |
| C1：等待时长上限设成"最长周期" | 等于允许睡 1 小时，"改了变量列表 1 小时不生效" |
| C1：把 `MarkPollPlanDirty` 改成**也唤醒 Worker** | 能去掉上限约束，但改了 N1 的信号语义（信号变多源），且要重新论证"唤醒风暴"；本次不做，仅记录 |
| C5：把 `_logTicks` 改成非 static（每 planner 一份） | 治标：两条连接若共享同一个 planner 实例（未来若做"多连接共用轮询计划"），问题会以另一种形式回来。**key 带连接名才是语义正确的粒度** |
| C5：直接关掉限流 | 恒坏段会每轮刷日志，把日志淹掉 |

### 2.1 关键代码

**`PollGroup.MsUntilDue()`（C1 的地基）**：

```csharp
/// <summary>
/// 距本组下次到期还有多少毫秒（&lt;= 0 = 已到期）。
/// 与 <see cref="IsDue"/> 用同一个基准（<c>_lastSuccessTicks + IntervalMs</c>），故二者永不矛盾。
/// 注意 <see cref="MarkDueNow"/> 把基准写成 0，此处会得到一个大负数——调用方按"已到期"处理即可。
/// </summary>
public long MsUntilDue() => Volatile.Read(ref _lastSuccessTicks) + IntervalMs - Environment.TickCount64;
```

**`PollScheduler.MsUntilNextDue()`**：

```csharp
public int MsUntilNextDue()
{
    long min = long.MaxValue;
    for (int i = 0; i < _groups.Count; i++)
    {
        long d = _groups[i].MsUntilDue();
        if (d < min) min = d;
    }

    if (min == long.MaxValue) return int.MaxValue;   // 无组：调用方自行封顶
    return min <= 0 ? 0 : (int)Math.Min(min, int.MaxValue);
}
```

**`ConnectionWorker.ComputeWaitMs()`（C1 的落点）**：

```csharp
private int ComputeWaitMs()
{
    if (State == ConnectionState.Connected && _scheduler is { HasWork: true } scheduler)
        return Math.Clamp(scheduler.MsUntilNextDue(), 1, MaxIdleWaitMs);

    if (_autoConnect && State != ConnectionState.Connected)
        return 100; // 重连中：小步快跑检查退避时刻
    return 200;
}
```

**`PollBatchPlanner` 的 C5 改动**：


### 3.1 本组断言的两个测试设计要点

1. **C1 走反射白盒**（`ProbeWaitMs`）：`ComputeWaitMs` 是私有方法，而它的返回值正是要钉的量。改成"真起线程跑一拍照再测耗时"会把"睡得对不对"与"线程调度抖不抖"混在一起，断言不稳。
2. **探针用的 Worker 不 `Start()`，但正常 `using` 释放**（`C14-7` 就是钉这一条的）：
   探针不需要线程，起线程反而让状态机改写 `_state` 与探针赛跑；而未 `Start()` 的 Worker 不持有任何 OS 资源（无线程、无句柄）。
   但它的 `Dispose()` 会走到"`Join` 一个从未启动的线程"这条路径——**这正是本轮暴露并修掉的缺陷**（见"已知边界 1"），`C14-7` 把"能安全 Dispose"钉成断言，防止将来有人把 `catch (ThreadStateException)` 改回去。

## 四、已知边界

1. ~~**`ConnectionWorker.Dispose()` 在"从未 Start"时会抛 `ThreadStateException`**~~（本轮新发现，**已修**）。
   **症状**：C14 白盒探针（Worker 不 `Start()`）走 `using` 释放时，进程被异常干掉，`exit code 3762504530`，堆栈指到 `Dispose()` 的 `_thread.Join(3000)`。
   **根因**：`Dispose()` 里 `_thread.Join(3000)` 之后只 `catch (InvalidOperationException)`，但 .NET 对"未启动线程"抛的是 **`ThreadStateException`**——该 catch 与它上面的注释（"线程尚未 Start"）**意图明确，却抓错了类型**。生产路径上 Worker 都会先 `Start()`，故一直未暴露。
   **修法**：`catch (InvalidOperationException)` → **`catch (ThreadStateException)`**，注释同步说明。
   **验证**：`C14-7`（从未 Start 的 Worker 能安全 Dispose）已通过；CommChecks 118/0 且**进程正常退出**（此前崩溃点不再复现）。
   **⚠ 勿回退**：不要把它改回 `InvalidOperationException`，也不要"两者并列"——这里唯一要吞的就是 `ThreadStateException`；`InvalidOperationException` 若真出现，说明是别的 Bug，应该炸出来。

2. **`MarkPollPlanDirty()` 仍不唤醒 Worker**（N1 的既有语义，本次未改）。
   后果：改了变量/扫描组后，新计划最长要等 `MaxIdleWaitMs = 200ms` 才生效（旧实现同量级，故不算退化）。若将来想做到"改完即生效"，可让 `MarkPollPlanDirty` 也 `Release` 一次信号——但那会改变 N1 的信号语义，需重新论证"唤醒风暴"，**勿顺手改**。

3. **等待时长精度受 `Environment.TickCount64` 粒度限制**（约 **15.6ms**）。
   故 200ms 周期组的实际唤醒间隔会在 185–200ms 之间浮动。这与改动前完全一致（旧实现同样用该时钟），不是本次引入。

4. **`_commandSignal` 容量固定为 1 的约束仍然成立**（N1 已记录）：`DrainQueues()` 是"写一条、读一条"交替，**勿回退成"先抽干写队列再抽干读队列"**——那样一次抽干读队列的期间新到的写命令仍会排在后面，C13-2 会重新变红。

5. **`PollBatchPlanner._logTicks` 仍是 `static`**。只补了 key 的连接名，没改成"每 planner 一份"。两条连接若将来共享同一个 planner 实例，本修法仍然正确（key 粒度是连接名），而"每 planner 一份"方案会失效——这正是选 key 方案的理由。

6. **未覆盖实机验证**：C14 断言的是"等待时长怎么算"与"限流 key 的粒度"，不是真机上的实际 CPU 占用下降与多设备并发告警。真机点验（多连接同时读同一地址、观察日志）留待联调。

7. **N3（一条连接一个专用线程）仍未修**：属结构性设计（连接数 > 约 200 条需改为 IO 复用），已在 N1 记录中列出，本次只记录不改。
