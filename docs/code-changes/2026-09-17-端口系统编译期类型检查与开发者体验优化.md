# 2026-09-17 端口系统编译期类型检查与开发者体验优化（R0+R1+R2）

## 一、需求与决策

**用户诉求**：上游/下游端口在不同插件之间链接变量的使用方式还能否优化，两个目的——

1. 性能损耗最小化；
2. 开发新插件时不需要太注重接口重载和输入输出端口的使用。

**摸底结论**（先量化再决策，避免无根据的"优化"）：

| 环节 | 单节点开销 | 对比 |
|---|---|---|
| OutputPort 写值（SetProperty + 引用比较 + 事件分发） | ~百纳秒 | Halcon 单算子 |
| InputPort.RefreshLinkedCache（引用命中） | ~纳秒 | 0.1 ~ 100 毫秒 |

管线与算法开销差 5~7 个数量级 → **管线保持原样不动**（决策点 1）。

真正的两个问题：

- **问题 A**：`FlowCompiler.LinkPorts` 连线只按名字接、不查类型。类型不匹配要到运行时才在
  `InputPort.RefreshLinkedCache` 抛 `InvalidCastException`，且异常沿上游节点的执行路径穿透，日志归因错乱。
- **问题 B**：`TypedValue` 在输入端是"手动值"、在输出端是"真实值"——同名反义，新手必踩；
  动态端口场景还要 `((OutputPort<HImage>)port).Value = img` 强转样板。

**给出的优化阶梯**：R0（文档加固+速查页）/ R1（编译期连线类型检查）/ R2（免强转扩展）/ R3（源生成器）。
用户选择：**R0+R1+R2**，R3 不做。

### R1 检查规则（与运行时转换能力严格对齐）

放行：同类型/派生→基类（`IsAssignableFrom`）、数值族互转、string⇄数值/bool、string→枚举（`Enum.Parse`）、
任一方 `object` 或 `DataType` 为 null（如 `ArrayIndexProxyPort` 非数组父端口时）→ 放行交运行时兜底。
拒绝并报错（归因**下游**节点、跳过连线）：`bool↔数值`（`Convert.ChangeType` 两方向都抛）、无关引用类型互连。

报错样例：

```
[连线类型不匹配] 'Blob分析' 的输入端口 'SrcImage' 期望 HImage，但上游 '读码器' 提供的是 String。请在变量绑定处改选类型兼容的输出，或调整上游算子的输出类型。
```

设计要点：检查不过时**跳过连线赋值**而不是硬接——下游会转而命中已有的"[参数缺失] 必填参数未配置"兜底错误，两条错误都指向同一个根因，比运行时炸异常 + 归因错乱好排查得多。

## 四、已知边界

1. **检查口径 = 运行时转换能力**：`IsLinkable` 放行集合与 `ValueConverter.Convert` 严格对齐；将来给 `ValueConverter` 加新转换规则时，`IsLinkable` 要同步，否则会误杀合法连线（两边都有注释互指）。
2. **类型未知一律放行**：`RuntimeVariableProxyPort` 未定义时、`ArrayIndexProxyPort.DataType` 为 null、任一方 `object`——编译期放行走运行时兜底，宁可漏报不误杀。
3. **数值窄化不拦**（double→int 会截断）、**枚举名拼错不在编译期校验**（string→枚举放行，运行时 `Enum.Parse` 才报）：都属于"值合法性"而非"类型合法性"，超出本次范围。
4. **条件节点（If/While）连线检查依赖 `LocalVariables` 声明类型解析**，`TypeHelper.GetActualTypeFromLink` 抛异常时按未知放行。
5. `Plugin.CreateRoi.csproj` 的 `$(SolutionDir)` 无回退遗留坑仍在（单独构建需手动传参），属他人工程未擅自修改。
6. R3（源生成器自动声明端口）未做——现有"public 属性 + 一行声明"已足够短，收益不抵引入生成器工具链的成本。
