# 开发记录：条件分支三个 P0（静默走错分支 / 编译期放行运行期炸 / 兜底值类型不符）

- 日期：2026-09-24
- 类型：Bug 修复（引擎执行语义 + 编译期/运行期口径对齐）
- 触发场景：对「条件分支（If / ElseIf / Else / While）」链路做一次全面排查，发现三处缺陷其实**是同一条链上的三个环**，任何一个单独修都不成立，必须一起改。

## 一、需求与决策

### 排查方法

不靠读代码猜，先写独立探针工程（引用与仓库同版本 `DynamicExpresso.Core 2.19.3`）实测委托调用的类型转换边界，再拿实测结论回推代码。

### 实测证据（探针输出，探针工程已删除）

```
=== 1. 裸 Delegate.DynamicInvoke 的收窄转换 ===
[FAIL] Func<int,bool>.DynamicInvoke(0.0 double) -> ArgumentException: Object of type 'System.Double' cannot be converted to type 'System.Int32'.
[OK  ] Func<int,bool>.DynamicInvoke(0 int)
[OK  ] Func<double,bool>.DynamicInvoke(0.0 double)
[OK  ] Func<double,bool>.DynamicInvoke(0 int)      ← 拓宽可以
[FAIL] Func<long,bool>.DynamicInvoke(0.0 double) -> ArgumentException: Object of type 'System.Double' cannot be converted to type 'System.Int64'.
[OK  ] Func<decimal,bool>.DynamicInvoke(0.0 double)

=== 2. DynamicExpresso Lambda.Invoke（与引擎同款调用） ===
[FAIL] int 形参收到 double 值 | expr="count > 0" args=[0(Double)] -> ArgumentException: ...
[OK  ] double 形参收到 int 值        ← 拓宽可以
[OK  ] string 形参收到 null
[OK  ] bool 形参收到 false
[OK  ] int 形参收到 null

=== 4. 重复形参名 ===
[FAIL] Parse("true", bool, [count:int, count:int]) -> DuplicateParameterException
```

**结论**：`Delegate.DynamicInvoke` 的默认 binder **只允许拓宽、不允许收窄**。

### 三个 P0 是一条链

| 环 | 位置 | 病灶 |
|---|---|---|
| P0-2 | [FlowCompiler.cs](file:///e:/VM/VisionMaster-W-master/Engine/FlowCompiler.cs#L799-L833) `IsLinkable` ↔ 运行期取值 | 编译期按 `ValueConverter.Convert`（= `Convert.ChangeType`，**支持数值族互转**）放行连线；而 If / While **根本不走 `InputPort`**，把上游端口原封不动存进 `UpstreamLinks` 并裸调 `Lambda.Invoke` → 运行期 `DynamicInvoke` 不做收窄 → 炸 |
| P0-3 | `CompiledIfNode` / `CompiledWhileNode` 的兜底值 | 变量未连线时一律注 `0.0`。`0.0` 是 `double`，喂给声明为 `int/long/decimal` 的形参同样触发收窄异常 → 「变量没连线」这种图纸疏漏会以「条件求值异常」的面目炸出来，**归因错乱** |
| P0-1 | [CompiledIfNode.cs](file:///e:/VM/VisionMaster-W-master/Core/Models/Compileds/CompiledIfNode.cs#L48-L83) 的 catch | 条件求值抛异常时**只记一条日志就 `continue` 试下一个分支**。而 Else 分支的 `ConditionLambda` 是 `Parse("true")`（恒真兜底），于是「本该走 If，实际走了 Else」，且步骤状态还标 `Success` |

**为什么 P0-1 是三个里最危险的**：崩溃会停机报警，走错分支会**一路放行不良品**，而且现场看到的是满屏绿。对工业视觉而言「绿的但走了错分支」比「红的崩溃」危险得多。

### 两项已确认决策

| 决策点 | 选定方案 | 理由 |
|---|---|---|
| 修复范围 | **P0-1 + P0-2 + P0-3 一起改** | 三者互为前提：只堵 P0-1 会把「走错分支」变成「频繁停机」，而触发停机的根因（口径不一致）还在；只补 P0-2 则异常照样被吞 |
| 失败语义 | **标 `Failed` + 上抛，中断流程** | 条件求值抛异常 = 判断结果**未知**。继续试下一个分支等于用错误的判断结果做决策。口径与既有先例 `CompiledPluginNode` 一致（业务失败返回 false → 标 Failed **不抛**；程序异常 → 标 Failed + **throw**）。最终由 `FlowEngineService` 把会话置 `Faulted` 并上报 |

### 关键设计：运行期口径必须与编译期口径重新对齐

编译期「能连」的依据是 `ValueConverter.Convert`（其文档注释明确声明**本类的转换能力集合是编译期连线检查的口径来源**），那么运行期就必须走**同一个** `ValueConverter.Convert`。修复的落点是基类两个 `protected static` 助手，If 与 While 共用——**口径只有一份**，不各写各的。

## 二、修改文件清单

| [CompiledNode.cs](file:///e:/VM/VisionMaster-W-master/Core/Models/Compileds/CompiledNode.cs#L60-L125) | 新增两个助手 | ①`CoerceConditionArg(rawValue, expectedType)`：null → 走兜底；`Nullable` 拆到实类型；`object` 形参或类型本就相符则原样交出；否则走 `ValueConverter.Convert`，失败抛 `InvalidCastException`（带上实际类型与值，便于现场归因）。②`DefaultForConditionArg(expectedType)`：`Nullable` 拆实类型 → `object`/引用类型给 `null`、`string` 给空串、值类型给 `Activator.CreateInstance(expectedType)`（一行通杀 `int/long/decimal/bool/...`） |

| [CompiledWhileNode.cs](file:///e:/VM/VisionMaster-W-master/Core/Models/Compileds/CompiledWhileNode.cs#L77-L121) | 改 `RunLoop` | ①两处取值改走 `CoerceConditionArg` / `DefaultForConditionArg`（保留 `args` 数组「循环外分配一次、循环内重填」的复用结构）；②运行时变量补 `v != null` 判断（原来 `TryGetValue` 命中但值为 null 会直接把 null 塞进形参）；③内层 catch 由 **`break` 改为 `throw`**（保留 Error 日志并补上「第几圈」，`RunAndGetNext` 里已有的 `catch { 标 Failed; throw; }` 承接） |

**编译器、`ValueConverter`、`FlowEngineService` 零改动**——P0-2 是「两侧口径不一致」，修的是运行期这一侧，让编译期那侧（已被 `ValueConverter` 的文档注释定义为唯一口径源）保持不动。

### 一处轻微的语义扩展（需说明）

`CompiledWhileNode` 内层 catch 由 `break` 改 `throw`，严格说属于原清单里的 **P1-4**，不在「P0-1+P0-2+P0-3」三项之内。改它的理由：用户确认的失败语义是「标 Failed + 上抛，中断流程」，而保留 `break` 会让 While 的条件异常仍然**静默**（循环悄悄少跑几圈、步骤照样标绿）——与刚确立的语义直接矛盾。若不加这一改，同一份代码里 If 会抛、While 会吞，属于新的口径分裂。
