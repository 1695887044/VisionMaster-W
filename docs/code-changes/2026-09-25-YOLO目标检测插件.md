# 开发记录：YOLO 目标检测插件（Plugin.Yolo）

- 日期：2026-09-25
- 类型：新功能（新插件模块 + 引入首个原生依赖）
- 前置：无
- 触发：用户「可以先把 Yolo 做成插件吗 要考虑这是通用工业视觉软件」→ 经 6 轮问答确认设计树 → 「并行推进，不等模型」

## 一、需求与决策

### 摸底实测（决定了整个方案的技术路线）

设计之前先做了 5 轮探针，结论直接改变了方案：

| 实测项 | 结果 | 对方案的影响 |
|---|---|---|
| HALCON `read_dl_model` 读 .hdl | **成功**（type=classification） | HALCON 深度学习许可可用 |
| HALCON `apply_dl_model` 推理 | **成功**（返回 10 类 softmax，最高 0.589） | 推理能力可用，GPU 也在（RTX 4070） |
| HALCON 读 **HALCON 自己导出的 .onnx** | **失败 #7801** | ONNX 导入通道可疑 |
| HALCON 读 **真实 YOLO ONNX**（ONNX Zoo 的 tinyyolov2，60 MB） | **失败 #7801** | 两次独立失败 → 该通道不可依赖 |
| 错误码身份核对（反射读常量值） | `#7801 = H_ERR_DL_READ_ONNX`，**不是** `H_ERR_DL_ONNX_LOADER`（=7804） | 排除"缺 protobuf 组件"假设，确认是**图不支持**（能力边界，非环境问题） |
| ONNX Runtime CPU 版体积 | **16.36 MB**（原生 15.7 + 托管 0.23 + Tensors 0.39） | 自包含投递在"通用工业软件"里可以接受 |
| NuGet 默认源 `api/v2` | **稳定 502**（连试 2 次），V3 端点正常 | 不用 NuGet，改走仓库既有的 `DLL\` + HintPath 约定 |

> 其中"缺 protobuf 组件"这个假设是**我先提出、又被实测推翻**的：`libprotobuf.dll` 确实躺在不在搜索路径的 `thirdparty\openvino\` 下，但把它加进 PATH 后依旧失败，且错误码是 7801 而非 7804。把这条写进记录，是为了避免后人再走一遍这条弯路。

### 用户确认的 4 个决策点

| 决策点 | 结论 | 用户给出的关键理由 |
|---|---|---|
| 功能范围 | 第一期只做**目标检测**，端口契约预留扩展 | 先窄后宽；端口不可逆、功能可加 |
| 运行依赖 | **只带 CPU 版**（实测 16.36 MB），GPU 留作后续配置 | 保证不可控的客户机器开箱可用 |
| 输出契约 | 结构化数组 + 文本 + **最佳目标裁剪图** | 跨过"下游框算子只吃参数不吃端口"的断层 |
| 验证模型 | 由用户方导出真实 v8/v11 模型提供 | 反正最终要部署的就是它 |

### 我直接确定的项（附理由）

| 项 | 结论 | 理由 |
|---|---|---|
| 插件标识 | `Plugin.Yolo`，`GroupName = "图像处理"` | 宿主只扫 `Modules\Plugin*.dll` |
| 依赖投递 | 放 `DLL\OnnxRuntime\`，用 HintPath 引用；原生库 PostBuild 投到宿主 exe 目录 | 沿用 Halcon/HslCommunication 的既有约定；绕开 NuGet 源 502；构建离线可复现 |
| 会话管理 | **进程级共享 + 引用计数**，**不照搬** OCR/CodeReader 的实例字段做法 | 插件实例每会话一份 → 同模型 5 个流程会加载 5 份会话，GPU 下直接吃光显存 |
| 布局校验 | 嗅探输出形状（通道在前= v8）+ 元数据 `task` 守卫；**不认识就报错，不猜** | 读错布局的结果是"框全错但不报错" |
| 框格式 | **xyxy**（左上右下，像素） | YOLO 解码原生就是 xyxy；下游 `crop_part` 也是 |
| 模型路径 | 绝对路径 + 相对宿主目录两种解析，找不到明确报错 | 换机器部署不用改配置 |
| 判定 | 不做 OK/NG | 沿用 ColorCheck/Ocr 立的规矩 |
| 结果投射 | 不做（不往图上画框） | 该机制尚未立起来，不自己造 |
| 设备参数 | **不加** | CPU-only 阶段的"设备"开关是个什么都不做的旋钮 |

### 实施中被真实数据推翻的三处

| 原实现 | 实测结果 | 处置 |
|---|---|---|
| letterbox 画布按"原图通道数"补通道 | 测试图是**单通道灰度**，补成 3 通道后画布仍 1 通道 → HALCON #3122 | 判据改为"送进 overpaint 的源图**恒为 3 通道**"，画布**无条件**补 3 通道 |
| 形状校验即可拦住非检测模型 | 分割模型 `[1,116,8400]`（116 = 4+80类+32 mask系数）在形状上与检测**无法区分** → 被误读成 112 类检测模型 | 补元数据 `task` 守卫；元数据缺失时放行（否则误杀老模型） |
| ORT 默认日志级别 | 实测加载模型刷出十几条 `Initializer ... appears in graph inputs` | 压到 `ORT_LOGGING_LEVEL_ERROR`（生产环境同样致命） |

## 四、已知边界

| # | 边界 | 说明 |
|---|---|---|
| **1** | **解码逻辑尚未用真实 v8/v11 模型验证（最需要知道的一条）** | 受控张量能证明"解码公式自洽"，但**不能**证明"v8 输出张量的语义与我的理解一致"。真实模型可获得的公开渠道都试过（HuggingFace 需鉴权 401、GitHub assets 只放 `.pt`、ONNX Zoo 只有 yolov2/v4）。**等用户方导出模型后必须补这一步**：看框是否落在目标上、类别是否对得上、数量是否合理。 |
| 2 | YOLOv5 布局不支持 | 输出 `[1, N, 5+C]`（带 objectness）会被明确拒绝并提示改用 v8/v11 导出。不按 v8 硬解是刻意的。 |
| 3 | 分割/姿态模型依赖 `task` 元数据兜底 | 它们的输出**在形状上与检测无法区分**（`[1,116,8400]` 会被形状校验误读成 112 类）。若模型元数据缺失 `task`，则拦不住 —— 这是已知风险。 |
| 4 | 只带 CPU 版 | GPU 是"换个 ExecutionProvider + 多带原生库"的配置，不改端口契约，但要重新实测体积与兼容性。 |
| 5 | `System.Numerics.Tensors` 必须随插件带 | 实测**不在** .NET 9 共享框架里，漏带的表现是运行期 `FileNotFoundException`。已放进 `DLL\OnnxRuntime\`。 |
| 6 | 类别名依赖模型元数据 | 读不到时用 `class_N` 占位，**不编造名字**（硬套 COCO 顺序会让人误以为识别对了）。 |
| 7 | 动态形状模型必须手填输入尺寸 | 元数据里读不到静态边长时，`InputSize` 留 0 会明确报错要求填写，不猜。 |
| 8 | 不做判定、不做结果投射 | 沿用既有约定：OK/NG 交下游（用 `Count`/`ClassNames` 接比较节点）；不给"画了框的图"。 |
| 9 | **原生库"在真实宿主进程里加载"尚未端到端验证** | 已验证：文件落到宿主 exe 目录、断言工程里能加载。**未验证**：VisionMaster 真实启动后插件加载模型。等有真模型时一并验。 |
| 10 | letterbox 与训练预处理的一致性无运行时校验 | 若客户导出时用了不同预处理（如 `rect` 拉伸而非 letterbox），精度会**静默劣化**。当前只在文档里约定。 |
| 11 | `BestCrop` 只给置信度最高的一个 | 多目标同时要裁剪时，下游需自行处理。这是"跨断层解法"的第一期形态。 |
| 12 | NuGet V2 源 502 仍未处理 | 本仓库无 `nuget.config`，机器级配置指向 `api/v2`（实测稳定 502）。本插件走 `DLL\` 本地引用绕开了，但**将来任何新增 NuGet 包的改动都会撞这个坑**，且报错像"没网"极易误判。 |
| 13 | 项目文件里含 16 MB 二进制 | `DLL\OnnxRuntime\` 与 `DLL\Halcon`(80 MB)、`DLL\HslCommunication`(55 MB) 同一约定，但确实增大了仓库体积。 |
