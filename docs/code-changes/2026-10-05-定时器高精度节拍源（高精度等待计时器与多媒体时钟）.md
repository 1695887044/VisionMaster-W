- 起因：用户提问——**"定时器能不能用 Windows 的媒体时钟？"**

---

## 一、直接回答：能用，而且本机实测可行；但默认选了它的现代替代

**实测（本机 Windows 11 26200，检查工程真跑）**：三种时钟各起一次、10ms 拍跑 300ms 数跳拍数：

| 节拍源 | 跳拍数（期望 ≈30） | 说明 |
| --- | --- | --- |
| kernel32 高精度等待计时器（`CreateWaitableTimerEx` + `HIGH_RESOLUTION`） | **30** | 本期默认 |
| **winmm 多媒体时钟（`timeBeginPeriod(1)` + `timeSetEvent`）** | **30** | 用户问的那个，本机可用 |
| 托管计时器（`System.Threading.Timer`） | 20 | 系统时钟粒度 ~15.6ms，符合预期 |

**但默认仍选高精度等待计时器**，两条理由（不是"媒体时钟不好用"，而是选型纪律）：

1. 微软已把 Multimedia Timers 标为 **legacy**。官方原文（Multimedia Timers 概览页）：
   > [The feature associated with this page, Multimedia Timers, is a legacy feature. It has been superseded by
   > Multimedia Class Scheduler Service. … Microsoft strongly recommends that new code use **Multimedia Class
   > Scheduler Service** instead of **Multimedia Timers**, when possible.]
2. `timeBeginPeriod(1)` 改的是**系统级**时钟分辨率（不只是本进程）——工控机常年跑会多耗电。
   等待计时器的高精度标志没有这个全局副作用。

因此：**高精度等待计时器为默认，多媒体时钟为备选（老系统 Win10 1803 之前的唯一 1ms 路子），
托管计时器为最终兜底**；三者由 `FlowTickSourceFactory` 按优先级自动挑，挑不中在启动日志里写明降级原因
（"为什么节拍不准"是现场常见疑问，日志必须能回答）。

## 二、设计：节拍源从调度逻辑里独立出来

```
IFlowTickSource（契约：Name / IsHighPrecision / Start(periodMs, onTick)）
├─ WaitableTimerTickSource      kernel32 CreateWaitableTimerEx + CREATE_WAITABLE_TIMER_HIGH_RESOLUTION(0x2)
│                               相对到期时间(100ns) + 毫秒周期；后台线程 WaitForMultipleObjects(计时器, 停止事件)
├─ WinMmMediaClockTickSource    winmm timeBeginPeriod(1) + timeSetEvent(TIME_PERIODIC|TIME_CALLBACK_FUNCTION)
│                               回调委托存成字段防 GC；成对 timeEndPeriod；失败时回滚已抬的分辨率
└─ ManagedTickSource            System.Threading.Timer（永远可用的兜底）
```

- **为什么要把时钟抽出来**：精度是平台能力、不是调度逻辑——同一套"该不该触发"的判定，配 1ms 或配 15.6ms 的时钟
  现场表现天差地别；换时钟不该动触发语义一行。而且两件事可以分开证：
  触发判定用手动时钟做**确定性**断言，时钟准不准另用**真实短跑**断言。
- **调度器接入**（`FlowTimerScheduler`）：`Start()` 时取源（工厂或注入的固定源），
  高精度源拍间隔 **5ms**、托管兜底 **25ms**（再密也快不过系统粒度）；`TickOnce(utcNow)` 语义不变，
  仍可供检查工程手动驱动。`TickSource` 属性公开（启动日志与断言用："现在到底用的哪个时钟"）。
- **定时下限 100ms → 20ms**：高精度源下把下限压到 20ms（给最短的取流场景留出极限）。
  ⚠ 若降级为托管计时器，实际稳定可用的下限约 50ms（15.6ms 粒度带来的抖动），这属平台能力限制，
  启动日志会写明"建议 ≥50ms"。
- **回调异常与生命周期**：时钟线程一律被 try/catch 包住（异常由调度器的 `SafeTick` 隔离并记日志，
  不许把时钟线程打死）；`Dispose` 严格成对（等待计时器：Cancel + Close + 停止事件 + Join；
  多媒体时钟：timeKillEvent + timeEndPeriod），并在释放后拒绝再次 `Start`。

## 四、未决问题

1. **MMCSS（Multimedia Class Scheduler Service）未采用**：微软推荐它是为了"媒体类线程的优先级与调度"，
   本场景要的是"稳定的周期节拍"，高精度等待计时器已满足；若将来出现"节拍被系统抢 CPU 拉长"的现场，
   再评估把时钟线程注册进 MMCSS（`AvSetMmThreadCharacteristics`）；
2. **`timeSetEvent` 的未来风险**：微软已将其标为 legacy，将来版本可能移除——工厂会自动降级
   （本机实测可用，仍作为备选保留；断言会如实记录"本机可用/不可用"）；
3. **拍间隔 5ms 下每拍仍遍历全部流程**：流程数是"方案里几十条"的量级，代价可忽略；
   若将来上千条流程，可改成"下次触发时刻优先队列"；
4. **GUI 实机冒烟未做**：定时触发的真机观察（含 20ms 间隔的实际节拍表现）仍需现场用真流程验证。
