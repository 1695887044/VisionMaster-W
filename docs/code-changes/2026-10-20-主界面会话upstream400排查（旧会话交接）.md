## 1. 证据链

上游响应**没有给出字段级错误**；ZCode 的 `providerCode` 只是把最后一次 `mcp__node_repl__js` 工具输入的 browser bootstrap 代码原样回显，不能据此认定是 node_repl 代码本身非法。

### 1.2 同一会话此前的成功请求

`model_usage` 表显示同一会话在 turn 22 曾成功处理过 **985,202 input tokens / 992,274 total tokens** 的请求；turn 77 失败前最后一次成功是 715,493 input tokens / 715,754 total。因此**不是简单的“超过 1M 上下文窗口”**（配置里该模型 `contextWindow=1000000`）。

### 1.3 失败前的会话状态

  - `msg_mvgauhwn_c5ad7505-a320-4964-8821-49b9c95f7a6d`（seq 925）

- 这些消息没有可上屏内容，但会进入下一次请求的历史；失败请求的 1225 条消息中 assistant 612 条、user 613 条，角色严格交替，没有空数组（日志深度脱敏后只能看到 `[Redacted:DepthLimit]`，但消息条数与 part 表可以互相印证）。

### 1.4 高置信度结论

**最可能的根因是会话历史被“取消/失败 turn 产生的空 assistant 消息”污染**：上游对该类消息返回 400，而 ZCode 每次重试又把新的空 assistant 消息追加进历史，形成“越重试越坏”的闭环。`providerCode` 里的 browser 代码是历史中最后一次 node_repl 工具输入的回显，不是失败字段。

这不是仓库代码的编译/运行错误：主工程在当前工作区构建为 **0 错误**，UI 冒烟全绿；旧会话的请求体是 ZCode 客户端会话层生成的，仓库内没有对应源码可直接修。

## 2. 处理方式

1. **不原地重试旧会话**：旧会话的请求历史已经包含多条空 assistant 消息，继续“继续任务”只会重复 400。
2. **新会话接管**：本会话已用旧会话的 turn/todo/文件时间线还原进度，并在当前工作区继续；不再依赖旧会话的请求上下文。
3. **如需恢复旧会话**（可选，需先备份 `db.sqlite`）：删除 seq 923/925/927/929/931/933 六条 assistant 消息及其 part，再从最后一条完整成功消息后重新发用户指令。不要删除 `Layout.xml` 或方案文件；本问题与布局无关。
4. **避免复发**：出现 `Turn execution failed` 后不要连续点“继续”；先新开会话并带上进度摘要，或先清理失败 turn 的空 assistant 消息。
