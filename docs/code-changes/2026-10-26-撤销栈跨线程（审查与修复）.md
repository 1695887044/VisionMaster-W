## 2. 审查结论

### 2.1 链路（每一环都读过代码）

1. `ScadaEditHistory` 是**静态类 + 静态 `Changed` 事件**（`ScadaEditHistory.cs:64-89`）；`Push` 是 `internal`，
   谁改文档谁压栈，**模型层没有任何线程约束**。
2. `ScadaChangeScope.Dispose()` 在最外层收口时 `Push`（`ScadaChangeScope.cs:168`）；
   `ScadaDocument.AddAlarm` 用 `using (BeginEdit(...))`（`ScadaDocument.cs:880`）——"新建报警"天然是一次可撤销编辑。
3. `RaiseChanged()` 在**压栈那个线程**上同步调用订阅者（`ScadaEditHistory.cs:147`）。
4. `ScadaEditorViewModel` 在 `Activate()` 订阅（`:182`）、`Deactivate()` 退订（`:197`），
   `Deactivate` 由视图 `Unloaded` 触发（`ScadaEditorView.xaml.cs:99`）。
5. `OnHistoryChanged` 直接 `RaiseCanExecuteChanged()`，之后还会读 `BasePageIds` 并可能重建
   `BasePageOptions`——**全是 UI 绑定状态**；修复前整个 VM 里没有 `Dispatcher` 字样。

### 2.2 崩溃现场（修复前，06:53 那次）

```
InvalidOperationException: 调用线程无法访问此对象，因为另一个线程拥有该对象。
  ButtonBase.get_Command → ButtonBase.UpdateCanExecute → Prism DelegateCommandBase.OnCanExecuteChanged
  → ScadaEditorViewModel.OnHistoryChanged → ScadaEditHistory.RaiseChanged → Push
  → ScadaChangeScope.Dispose → ScadaDocument.AddAlarm → RunSoundAlarmChecks
```

### 2.3 为什么是偶发（**更正上一版归因**）

上一版写的是"Prism 弱事件 + GC 时机"。**不对。** 真正的原因是**异常路径跳过了退订**：

- `RunScadaEditorToolbarChecks` 确实在方法末尾调了 `vm.Deactivate()`（`Program.cs:3490` 附近，
  注释还写着"2026-10-18 实测，一次连红三段"）——正常路径是干净的。
- 但那次崩溃的同一次运行里，这条检查**先抛了 `IOException`**：
  `artifacts\scada-editor-toolbar.png` 被**另一个并发的 ScadaChecks 实例**锁住（`SavePng` 在 `Deactivate` 之前）。
- 线程包装器 `catch` 掉这个异常后，`Deactivate()` 永远走不到 → 那个 VM 连同它绑的按钮留在静态事件上 →
  之后主线程的 `RunSoundAlarmChecks` 一压栈，就跨线程摸到了死线程的按钮。

所以：**"并发跑两个 ScadaChecks"是因，"证据 PNG 被锁"是链，"跳过退订"是果，"下一次压栈崩"是爆点。**
弱事件与 GC 与此无关（上一版的猜测已作废）。

### 2.4 生产路径能不能走到

| 改文档入口 | 调用方 | 线程 |
|---|---|---|
| `Document.AddPage` ×3 | `ScadaEditorViewModel:1076/1100/1119` | UI |
| `Page.AddLayer` | `ScadaLayerViewModel:379` | UI |
| `AddElement` | `ScadaEditorView.xaml.cs:372` | UI |
| `ScadaDocument.AddAlarm` | **生产代码零调用方**（只有断言宿主在用） | — |

今天全在 UI 线程，撞不到；但这是"碰巧"，不是"保证"。同族的第二个隐患：
`ScadaTemplateStore.TemplateUpdated`（`ScadaTemplateStore.cs:324`）也是静态单例上的同步事件，
VM 的 `OnTemplateUpdated`（`:1761`）在里面**改文档 + 弹对话框**——哪天有人从后台线程存模板就是同一场事故。

### 2.5 关于"会退进程"的更正

`App.xaml.cs:78` **有** `DispatcherUnhandledException` 兜底（记日志 + 提示 + `Handled = true`），
但它**只兜 UI 线程**。本例的异常是在**压栈那个线程**上抛的，后台线程走 `AppDomain.UnhandledException`，
进程仍然终止。所以"会退进程"成立，理由不是"App 没有兜底"，而是"兜底盖不到这条线程"。

## 6. 同族第二处：`ScadaTemplateStore.TemplateUpdated`（已实测，结论有更正）

`ScadaTemplateStore.Shared` 同样是**静态单例 + 普通同步事件**（`ScadaTemplateStore.cs:121/171`），
`TemplateUpdated?.Invoke`（`:324`）与 `RaiseChanged`（`:526`）都在**调用写入口的那个线程**上同步跑完所有订阅者。

### 6.1 实测（临时探针，`net9.0-windows` 引已构建 DLL，用完即删）

| 判据 | 结果 |
|---|---|
| **V1** 事件在哪个线程回调 | ✅ `caller=4 / handler=4` —— `TemplateUpdated` 在**压栈线程**上同步回调，没有任何封送 |
| **V2** 订阅者抛异常时盘上写没写 | ✅ 调用方拿到 `InvalidOperationException`，而内存与磁盘的 revision 都已经 `2 → 3` —— **写盘在广播之前**，"报失败但已落盘"成立 |
| **V3** 别的线程广播 → 工具箱重读 → WPF 绑定 | ❌ **没有抛**（我上一版的判断错了，见下） |

V3 的细节值：`changedThread=2`（广播线程）、`templatesRaisedThread=2`（工具箱确实在广播线程上
`RaisePropertyChanged(Templates)`）、`itemsSourceIsToolboxTemplates=True`（绑定目标**确实更新了**）、**无异常**。

**更正**：我上一轮说"工具箱会抛'不允许从非 Dispatcher 线程修改 SourceCollection'"。**错。**
`ScadaToolboxViewModel.Templates` 是普通 `IReadOnlyList`（`ScadaToolboxViewModel.cs:95`），
属性通知型绑定**会被 WPF 封送回目标 Dispatcher**；只有 `INotifyCollectionChanged`（ObservableCollection）
的增量通知才不封送。所以工具箱这条订阅**实际是安全的**。

### 6.3 现状与建议

写入口今天全在 UI 命令里（`ScadaEditorViewModel:1650/1753`、`ScadaToolboxViewModel:206/218`），

## 7. 踩过的坑
- **静态事件 + 一次性 STA 线程 = 定时炸弹**：断言宿主"每条检查各起一个线程"是常见写法，
  任何在 `Activate` 里订阅静态事件的 VM 都会活过线程本身。判据：一次性线程退出前必须 `Deactivate`，
  而且**要放在 `finally`**——正常路径末尾那一句挡不住中途抛异常。
- **"假红"会连锁成"真崩"**：并发跑两个 ScadaChecks → 证据 PNG 被锁 → 一条检查提前抛 → 跳过退订 → 下一次压栈崩进程。
  看到 `IOException` 型红条，先想"它后面的清理代码是不是没跑"。
- **弱事件会让缺陷变成偶发**：`GC.KeepAlive` 不是保险，是**必要条件**——不加它，`[HX2]` 会时绿时红。
- **"App 有全局兜底"不等于"后台线程安全"**：`DispatcherUnhandledException` 只管 UI 线程。
- **撤销栈是静态全局的**：任何 `ScadaDocument`（包括断言里 new 出来的那份）压栈都会广播给**所有活着的编辑器 VM**。
