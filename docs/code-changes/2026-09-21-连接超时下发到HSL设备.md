# 连接超时真正下发到 HSL 设备（config.TimeoutMs → device.ConnectTimeOut）

> 来源：通讯设置 UI 审查的顺带发现第 1 条 —— 「`ModbusTcpConnection` 没把 `config.TimeoutMs` 映射给 `_device.ConnectTimeOut`，连接页里配的超时对 HSL 建连完全无效」。
> 用户确认后执行。

## 1. 需求与决策

### 1.1 问题：一个「用户配了但没生效」的静默失效

`ConnectionConfigBase.TimeoutMs`（界面上「高级参数 → 超时时间(ms)」，默认 **3000ms**，范围 100-60000）在**每一种**连接的属性面板里都可见。但排查后发现它只有**一个**消费点：

| 消费点 | 位置 | 拿它做什么 |
| --- | --- | --- |
| 上层等待预算 | [AdvancedCommunicationManager.Connect](file:///e:/VM/VisionMaster-W-master/Communication/Communications/Manager/AdvancedCommunicationManager.cs#L313) | `worker.Connect(timeoutMs)` —— **等待「首次建连」完成的上限**，超时返回 false（Worker 仍在后台按退避重连） |
| **设备层（缺失）** | [ConnectionWorker.TryConnect](file:///e:/VM/VisionMaster-W-master/Communication/Communications/Manager/ConnectionWorker.cs#L320-L339) → `_connection.Connect()` → HSL `ConnectServer()` | **完全没拿到配置值** |

而 HSL 侧真正约束 socket 建连的是 `PipeTcpNet.connectTimeOut`，其**默认值是 10000ms**（[PipeTcpNet.cs](file:///e:/VM/VisionMaster-W-master/DLL/HslCommunication/Core/Pipe/PipeTcpNet.cs#L28)），由 `CreateSocketAndConnect(endPoint, ConnectTimeOut, LocalBinding)` 使用。

于是「界面上的 3000」和「实际生效的 10000」是**两套数**，产生两个方向的错位：

| 场景 | 用户预期 | 实际发生 |
| --- | --- | --- |
| 把超时**调大**（如慢速 VPN / 跨网段，想等 20 秒） | 等 20 秒 | socket **10 秒**就放弃 → 无论怎么调大都没用 |
| 把超时**调小**（如想 500ms 快速失败） | 500ms 内失败 | 上层 500ms 就报「未在 500ms 内建立」，但**建连线程还占着 socket 磨到 10 秒** → 期间重连/删除连接都要与它抢 |

### 1.2 决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 修哪一侧 | **设备层（连接实现的构造函数）** | 上层预算已经是对的；缺的是「配置值没有下发到真正建连的那一层」 |
| 下发到哪个属性 | `_device.ConnectTimeOut` | 配置字段的语义就是**连接超时**（XML 注释：「连接超时时间（毫秒）」，属性面板名「超时时间(ms)」）。不顺手映射 `ReceiveTimeOut`，那是「读超时」，另一个语义 |
| 改哪几种连接 | **ModbusTcp + SiemensS7**（两种 TCP 连接） | `TimeoutMs` 在**基类**上、对每种连接都可见，S7 存在**完全相同**的静默失效。只修 Modbus 会留下「一半生效一半不生效」的诡异状态 |
| 串口 | **本次不动** | `ModbusRtu` 没有「TCP 建连超时」这个量（`Open()` 端口是本地动作，不受网络超时约束），映射目标不明确，属另一个待定问题（见已知边界 1） |
| 是否加断言 | **加 C7** | 「配置值是否真的落到设备上」是纯对象状态，**不需要真设备**，可以离线固化成断言；否则这个缺陷随时可能被重构悄悄带回来 |

### 1.3 语义变化（重要，必须知情）

修完之后，`TimeoutMs` 同时是「socket 建连超时」和「上层等待预算」。这带来一个**行为变化**：

> 在**慢速但可用**的链路上（TCP 握手耗时接近 `TimeoutMs`，例如配 3000ms、实测握手 2.9 秒）：
> - 修复前：HSL 有 10 秒余量 → 握手成功 → Worker 到达 Connected（上层可能已在 3 秒时报过 false，但状态事件随后会广播 Connected，界面自愈）；
> - 修复后：socket 在 3 秒时超时 → 建连**真的失败** → 进入退避重连。

这个变化是**用户配置意图的直接兑现**（「超时时间 3000ms」本就意味着「3 秒连不上就算失败」），不是副作用；但对「现场网络很慢、又懒得改默认值」的用户，表现会从「偶尔能连上」变成「一直重连」。**需实机确认默认值 3000ms 在现场是否够用**。

新增反射探针（`#region 反射探针` 内）：

```csharp
/// <summary>
/// 读连接实现里私有 HSL 设备（_device）的 ConnectTimeOut（C7 用）。
/// 走反射是为了让断言工程不必引用 HSL 命名空间；ConnectTimeOut 是
/// DeviceTcpNet 上的 public 属性，故直接按名取即可。
/// </summary>
private static int DeviceConnectTimeOut(ICommunicationConnection connection)
{
    var device = connection.GetType()
        .GetField("_device", BindingFlags.Instance | BindingFlags.NonPublic)!
        .GetValue(connection)!;
    return (int)device.GetType().GetProperty("ConnectTimeOut")!.GetValue(device)!;
}
```

**未改动**：`ConnectionWorker`（上层预算逻辑本就正确）、`ConnectionConfigBase`（字段语义与校验范围不变）、`SerialConnection`（见已知边界 1）。

## 3. 验证结果

| 验证项 | 结果 |
| --- | --- |
| `VisionMaster.sln` MSBuild（Debug） | **MSBUILD_EXIT=0** |
| `CommChecks.exe` 回归 | **通过 68 / 失败 0**（C7 新增 3 条，原 65 条全绿） |

| C7-1 | `设备实际值 3000ms`（默认值路径：证明 HSL 自己的 10000 被覆盖） |
| C7-2 | `设备实际值 60000ms`（非默认值路径：证明不是「恰好等于默认值」的假通过，也没被 HSL 上限截断） |
| C7-3 | `设备实际值 1234ms`（S7 同样下发） |

C7 不真建连（只构造连接对象 + 读设备属性），因此**离线可跑**，与 C6（唯一真发起 TCP 的段）性质不同。

## 4. 已知边界

> **后续进展（同日）**：边界 1 / 2 / 3 中的「读超时」部分已由《[读超时字段落地](file:///e:/VM/VisionMaster-W-master/docs/code-changes/2026-09-21-读超时字段落地.md)》解决 —— 新增 `ConnectionConfigBase.ReadTimeoutMs`（默认 5000，刻意与 HSL 默认同值）并统一下发到 `device.ReceiveTimeOut`，TCP 与串口共用同一入口。下面保留原始记录，已解决项加删除线并注明。

1. ~~**串口的 `TimeoutMs` 仍未被设备消费**~~ → **已由《读超时字段落地》部分解决**：串口现在有了真正生效的「读超时(ms)」字段并映射到 `ReceiveTimeOut`。但**串口界面上原来的「超时时间(ms)」仍然保留且仍然无效**（本次刻意不隐藏，见该文已知边界 1）。
2. ~~**S7 的 COTP 握手读取未纳入本值约束**~~ → **已解决**：`SiemensS7Net.InitializationOnConnect()` 的握手读现在受新增的 `ReadTimeoutMs` 约束，故 S7 真实建连上限 ≈ `TimeoutMs` + `ReadTimeoutMs`，两个值都可配、都可封。
3. ~~**读/写超时整体未映射**~~ → **读超时已解决，写超时仍未映射**：本次只映射了读超时（`ReceiveTimeOut`）；写超时（`SendTimeOut`）对 Modbus/S7 这类请求-响应协议影响很小，暂不引入第三个字段。
4. **行为变化需实机确认**：见 1.3。特别要确认现场默认 `3000ms` 是否够用（跨网段 / VPN 场景可能要调大）。
5. **断言只证明「值到了设备对象上」**：不证明「超时真的按这个值生效」——后者要真设备（黑hole 地址 + 计时）才测得出，属实机项。
6. **反射探针已重构（同日）**：第 2 节里的 `DeviceConnectTimeOut` 单函数版已改为 `GetDevice` + `DeviceIntProperty` + `DeviceConnectTimeOut` / `DeviceReceiveTimeOut` 两个具名探针（C7 与 C8 共用），行为不变。`CommChecks` 通过数亦由 68 增至 **72**（新增 C8 四条）。
