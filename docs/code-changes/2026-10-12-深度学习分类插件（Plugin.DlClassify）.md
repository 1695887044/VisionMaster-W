## 一、缺口背景：为什么要新建插件而不是改 Yolo

盘点全仓 28 个插件，AI 维度只有 `Plugin.Yolo` 一个，且只做目标检测。`Plugin.Yolo` 的 `task` 守卫（`YoloPostProcess.IsSupportedTask`）本身就把非 detect 模型**明确拒绝**了——分类模型的输出格式（整图 → 标量分数）与检测（`[1,84,8400]`）完全不同，按检测解读会得到错误结果却不报错。所以缺口 C 的落法是**新建插件**，而不是给 Yolo 加一个"任务下拉"。

分期：一期分类（本轮）、二期异常检测、三期分割。三件套都归「图像处理」分组（与 Yolo 一致）。

## 三、设计要点

### 3.1 端口契约（固定端口，无动态端口）

| 端口 | 方向 | 类型 | 说明 |
| --- | --- | --- | --- |
| `Image` | 入 | HImage | 待分类图像（`IsRequired = false`） |
| `PredictedClassId` | 出 | int | 最可能的类别索引（0 基） |
| `PredictedClassName` | 出 | string | 最可能的类别名（元数据没带时 `class_N`） |
| `Confidence` | 出 | double | 最高类别置信度 0~1 |
| `Scores` | 出 | `double[]` | 全部类别概率（与 `ClassNames` 同序） |
| `ClassNames` | 出 | `string[]` | 类别名数组（**全量**，与 `Scores` 同序） |
| `TopKText` | 出 | string | 前 K 类文本摘要（供记录/上传等**标量**下游用） |

`TopKText` 在数组之外再给一个的理由：画布上数组端口只能整体连给 object 输入口，而记录/上传/比较这些既有下游都是按标量写的——没有它接不上（与 Yolo 的 `BoxesText` 同一理由）。

### 3.2 配置项

| 配置 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `ModelPath` | string（partial） | 空 | ONNX 分类模型路径（支持相对宿主目录） |
| `ResizeMode` | enum `ClassifyResizeMode` | `Letterbox` | `Letterbox`（等比补边）/ `Stretch`（拉伸） |
| `InputSize` | int（partial） | 0 | 0 = 用模型元数据静态尺寸；动态形状模型才手填（常见 224） |
| `TopK` | int（partial） | 3 | 结果里保留前 K 类（夹到 `[1, 类别数]`） |

`ResizeMode` 为什么显式暴露：分类模型训练预处理的两种主流做法（letterbox / 拉伸）在非方形图上结果不同，选错的表现是**精度静默下降**（不报错、不崩溃）。默认 Letterbox（不破坏几何的那一档），把选择权交给用户而不是替它猜。

### 3.3 推理链路

```
① 取原图尺寸
② 算缩放几何（ResizePlan：Letterbox 等比+居中补 114 灰 / Stretch 直接拉）
③ 构造输入画布（非 byte 图先转 byte；单通道 compose3 补 3 通道）
④ 转 NCHW float（get_image_pointer1 + Marshal.Copy，/255 归一化）
⑤ ONNX Runtime 推理
⑥ 后处理：布局嗅探 → 概率归一化 → TopK
```

三个"必须做对否则静默出错"的点：**补边灰度用 114**（不是 0；黑边是模型没见过的强边缘）、**归一化 /255**（少除多除都照样跑、只静默劣化精度）、**概率归一化判据**（已 softmax 过的输出再做一次会把分布压平，0.9 → 0.5）。

### 3.4 会话生命周期

进程级共享 + 引用计数（`ClassifySession`，与 `YoloSession` 策略同源）：同模型被多个流程引用只加载 1 份；路径没变复用、变了先放旧的再拿新的（避免"改了配置不生效"）。

### 3.5 视图与运行期

- 视图两列（980×620）：左参数（图像输入 / 分类模型 / 分类参数 / 高级 / 试算），右只读图；界面上刻意显示**模型摘要**（输入输出形状 / task / 类别名）与**试算 TopK 概率**两处排障信息。
- 运行期：置信度 < 0.6 时写 **Warn**（只提醒、不判 `Failed`——判定归下游，与 OCR 的"认不准必须看得出来"同一机制）；`RunAlgorithm` 起手查协作取消令牌（`[ParallelSafe]` 要求长阻塞可分步检查）。

## 四、回归断言（`FlowCanvasChecks/ClassifyChecks.cs`，三段各自独立可跑）

| 段 | 需要模型 | 覆盖 |
| --- | --- | --- |
| ① 后处理（受控数据） | ❌ | letterbox 宽/高图几何、stretch、布局嗅探（`[1,3]`/`[1000]`/`[1,1,5]` 接受；`[1,84,8400]`/`[1,2,224,224]`/`[1,1]` 拒绝）、task 守卫、概率归一化（已是概率原样 / logits softmax / 全负 / 大 logits 稳定）、TopK（排序/占位/夹取）、全量类别名同序 |
| ② ONNX Runtime 链路 | ✅（否则跳过） | 入参守卫、真模型加载、进程级缓存命中、引用计数释放 |
| ③ 插件壳 | ❌ | `[Display]` 分组、输出端口契约、默认值、partial 属性往返、未选模型/路径不存在 → 明确失败不抛异常 |

为什么①是重点：归一化与 TopK 写错的后果是**结果全错但程序不报错**（把已 softmax 的输出再做一次 softmax 会把分布压平、类别名错位，运行一切正常）——这类错误只能靠"已知输入 → 已知期望输出"来钉，不能靠"跑起来没崩"发现。

注册：`FlowCanvasChecks/Program.cs:203` 的 `ClassifyChecks.Run();`，紧接 `:200` 的 `YoloChecks.Run();` 之后。

### 5.2 P1（已修）：`ClassNames` 端口用 TopK 回填全量名字

- **现象**：`ClassNames` 端口曾用 TopK（只含前 K 条）回填**全量**类别名，在"模型带名字且 `TopK < 类别数`"时给出**错名/占位混杂**，违反与 `Scores` 同序的契约。
- **修法**：`ClassifyResult` 增加**全量** `ClassNames` 字段（来自模型元数据），新增纯函数 `ClassifyPostProcess.ResolveClassNames` 统一生成；补断言 `[核心] ClassNames 与 Scores 同序且全为真实名`（`ClassifyChecks.cs:137`）守门。

### 5.3 P2（已修）

1. `ClassifySession.TryAcquire` 建会话成功、但读元数据/建 Entry 失败时会话未释放 → 加 try/catch **就地 Dispose**；
2. 输入尺寸按方形处理会忽略模型**非方形**输入 → 改为按 `InputWidth`/`InputHeight` 分别处理；
3. `TopKText` 端口文档格式与实现不一致 → 对齐；
4. `ModelSummary` getter 内触发属性通知（**自我重入**）→ 移出 getter（改由 `OnModelPathChanged`/`OnViewLoaded`/`Initialize` 显式驱动）；
5. `RunAlgorithm` 未协作取消 → 起手查令牌。

### 5.4 P2（记录，未改）

`NormalizeToProbabilities` 的"已是概率"判据（`min≥0 且 max≤1 且 |sum-1|<1e-3`）在"小正 logits 恰好和≈1"时存在**极小误判概率**。属设计权衡：无脑 softmax 会压平已归一化输出，风险更大。已在断言中显式记录行为，不修。

## 七、已知边界（诚实清单）

- ⚠️ **未用真实分类模型端到端验证**（**最高优先待办**）——受控数据只能证明公式自洽，不能证明对具体导出（logits vs 已 softmax）的判据在真实模型上不出错。`ClassifyChecks` 第②段需环境变量 `CLASSIFY_TEST_MODEL` 指向真实模型，否则跳过（不判红）。
- 只带 **CPU 版** ONNX Runtime（接 GPU = 换 ExecutionProvider + 多带原生库，不改端口契约）。
- `System.Numerics.Tensors` **必须随插件带**（不在 .NET 9 共享框架里，漏带 = 运行期 `FileNotFoundException`）。
- **动态形状模型必须手填 `InputSize`**（留 0 明确报错，不猜）。
- 类别名依赖模型元数据 `names`，读不到用 `class_N` 占位，**不编造**。
- **不做 OK/NG 判定、不做结果投射**（不给"标了类别的图"）——判定交下游（如比较节点 `PredictedClassName == "OK"`）。
- 会话实现与 `Plugin.Yolo` **各自独立（刻意重复）**：不改动已验证的 Yolo，也避免插件间互相引用。第三个深度学习插件落地时评估抽 `Services/Core.Onnx` 共享库（见方案说明书 §5.2，按 R12 需 architect 评审）。
