# 2026-10-29 变量管理批量导入卡顿（O(N²) 树重建）

> 现象：导入汇川 2357 点变量表，变量管理弹窗 **UI 线程卡约一分钟**。
> 用户提问：是不是明细表没做虚拟化？

## 一、当前状态

已修复并实测：2357 条变量批量加入 **Add 循环 4ms + 一次重建 213ms ≈ 0.2 秒**
（`UIThemeSmokeTest --global-variables` 新增断言，gate 16 步全绿）。

**结论先说：不是虚拟化问题。** 明细表是 `DataGrid`，默认行虚拟化（`EnableRowVirtualization=true`）
没有被 `DialogDataGrid` 样式关掉，也没有被套进外层 `ScrollViewer`（`GlobalVariableView.xaml` 里唯一的
ScrollViewer 在 2089 行的分组编辑器里）。卡顿来自**每条变量加入都触发一次全量树重建**。

## 二、根因（三处，主因是第 1 条）

1. **每条 Add 一次全量重建（O(N²)）**：`GlobalVariableViewModelBase.OnGlobalVariablesCollectionChanged`
   在每次集合变化后都 `SafeDispatch.BeginInvoke(() => RefreshTree())`。`RefreshTree` 会为**全部**
   变量重建 `VariableNode`、清空并重填 `DisplayNodes`、再走一遍 `UpdateFilteredList`。
   导入 2357 条 = 2357 次 × 2357 节点 ≈ **550 万次节点构造** + 同量级的集合变更通知。
2. **每条 Add 一次全源计数扫描**：`GlobalVariableManagerViewModel.OnVariablesChangedForCountsHandler`
   直接调 `RefreshSourceCounts()`，它对每个来源/分组全量扫 `GlobalVariables`（9 个作用域 × N）。
3. **Apply 里的撞名预检是 O(N²)**：`DeviceVariableImportService.Apply` 对每个新增行
   `allVariables.Any(...)` 扫全表，2357 × 2357 ≈ 550 万次 `OrdinalIgnoreCase` 比较（数秒级）。

## 三、已做

| 文件 | 改动 |
|---|---|
| `VisionMaster\ViewModels\DialogViewModels\GlobalVariableViewModelBase.cs` | 新增 `QueueTreeRefresh()`：同一轮调度只投递一次 `RefreshTree`，`_refreshPosted` 门闩；集合处理改调它 |
| `VisionMaster\ViewModels\DialogViewModels\GlobalVariableManagerViewModel.cs` | 新增 `QueueSourceCountsRefresh()`（同口径门闩），计数处理器改调它 |
| `VisionMaster\Services\DeviceVariableIoService.cs` | Apply 撞名预检改成 `HashSet<string>(OrdinalIgnoreCase)`，O(N) |
| `UIThemeSmokeTest\GlobalVariableViewSmoke.cs` | 新增批量回归：2357 条 FakeVariable 加入真实 VM，量 **Add 循环**与**泵消息后的那一次重建**，并断言列表最终到齐 |

为什么这样合并是安全的：导入事务 `Apply` 在 UI 线程同步执行，期间 Dispatcher 不泵消息，
所以所有 `BeginInvoke` 都排到 `Apply` 返回之后；合并后只跑一次，拿到的必然是最终集合状态。
单条增删的行为不变（一次投递一次重建）。

## 五、未做 / 残留

- **未在真 exe 上重导 2357 点复测**：断言用的是真实 VM + 假变量（不经过 NetworkVariableBridge 的
  逐条注册）。桥接器注册是 O(1)/条，理论上再增加几十毫秒；用户重导一次即可确认端到端体感。
- `MonitorViewModel.OnGlobalVariablesChanged` 仍是每条 Add 重建一次监视栏包装器（O(监视项数)/条）。
  监视项少时无感；若现场监视项很多且导入仍卡，用同样的门闩模式合并即可。
- 导入**预览**页是 DataGrid，行虚拟化正常；2357 行的预览构建本身是 O(N)。

## 六、踩过的坑

- **别用"Add 循环耗时"代表 UI 总成本**：合并后重建发生在泵消息时，只报 4ms 会掩盖 213ms 的真实开销；
  断言必须把泵消息那一段一起量。
- 判断"是不是没虚拟化"不能只看控件类型：要确认 ① 样式没把 `EnableRowVirtualization` 关掉、
  ② 控件没被套进外层 `ScrollViewer`/无限高度容器。本表两条都不成立，所以问题不在虚拟化。
- 批量写集合时的通病：**每个 CollectionChanged 订阅者都可能各做一次 O(N) 全量刷新**，
  新增订阅者前先问"这条路径会不会在批量导入里被调用 N 次"。
