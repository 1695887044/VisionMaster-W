# 整线启动：工位与主流程平级（2026-10-28）

## 1. 背景与裁决

现场工位是并行的，但软件只有"启动唯一主流程"一个入口，主流程里的「调用流程」又是同步等待
（`Engine/FlowInvoker.cs` 起完子流程会话就轮询等它跑完）。于是现场只能把工位写成
`调用流程(工位1) → 调用流程(工位2) → …`，串行跑。

三条候选路径与裁决：

| 方案 | 结论 |
|---|---|
| A 工位各自独立流程、各自触发 | **采纳**（本条记录实现的就是它） |
| B 主流程里用「并行组」扇出 | 否决：要求现场用户理解泳道/分支/汇合，徒增学习成本；且并行分支只放行 `[ParallelSafe]` 算子，采集/运动被编译门禁挡住 |
| C 给「调用流程」加"派发不等待"+ 汇合 | 否决：join 就是耦合点——某个工位卡死时父流程结束不了，下一拍起不来，整线跟着停 |

裁决口径（用户 2026-10-28）：**工位与主流程平级**。一条流程失败/卡死只收尾它自己，
其余照常循环；「调用流程」保持同步，只用于真正必须等结果的子程序（取配方、标定、判定）。

## 3. 语义

- 勾了「整线」的流程 = 整线成员。工具栏一个按钮把它们**各起各的会话**一起启动，谁也不等谁。
- 一条流程失败 / 卡在等待 / 被操作员停掉 → 只影响它自己；再点启动会被幂等拒绝（"已在运行"）。
- 「停止」按钮语义不变：`FlowEngineService.StopAll`，一次停干净。
- 没勾任何「整线」的旧方案：行为与 2026-10-22 完全一致（唯一 Role=Main），不做静默升级。
- 「调用流程」未改：仍是同步子程序调用，超时/急停口径原样。

## 5. 未做 / 已知边界

1. **没有并行度上限**：现在只有 `GlobalParallelConfig.ForceSequential`（全部退化顺序）这一个总闸，
   没有"最多 N 条并行"。勾多少条就起多少条——7 GB 内存事故的成因是"把全部启用流程当顶层启动"，
   现在改成了显式勾选，风险面收窄但没有硬上限。工位多到两位数时要补。
2. **共享硬件不做**（用户 2026-10-28 明确先不考虑）：两个工位抢同一台相机/同一块运动卡时没有设备锁，
   现象会随机且难复现。
3. **界面未肉眼验收**：`FlowManagerView` 第五个勾选框在 300px 列宽下会折成两排（该表 `RowHeight` 已是自动，
   `MinRowHeight=46` 兜底），编译通过但没在真机上点过。
4. **批量启动的编译在 UI 线程**：`RunAllEnabledOnce` 里逐条 `_flowCompiler.Compile`，工位多时启动会有顿挫
   （旧行为，本次未改）。
5. **`EditGate` 仍按整体运行态锁编辑**：整线跑着时不能改图纸（与旧行为一致）。不影响"运行"，只影响"编辑"。

## 6. 踩过的坑

1. **`artifacts\build\` 不是我一个人的**：我用 `-p:BaseOutputPath=artifacts\build\` 做隔离构建后顺手
   `rmdir /s /q artifacts\build`，把**别的会话**留在里面的 `avalon-fix2`、`batch1-verify` 一起删了
   （`avalon-fix` 成了空目录）。这些都是隔离构建产物（`docs/code-changes/2026-10-27-多流程并发帧归属…`
   里写的 `artifacts\build\batch1-verify\` 就是它），按文档里的命令重跑即可再生，但**清理前必须先看目录里
   有没有别人命名的子目录**——`artifacts\build\<批次>\` 是多会话共用的约定。
2. **运行中的 `VisionMaster.exe` 同时锁 `bin\` 与 `Modules\`**：常规构建报 `MSB3027/MSB3021`（DLL 被
   进程 16944 锁定），插件投递报 `MSB3073`。正解不是杀进程，而是隔离输出：
   `-p:BaseOutputPath=<隔离目录>\ -p:ModulesDir=<隔离目录>\`。**路径不要加引号**——结尾的 `\` 会吃掉
   收尾引号，两个 `-p:` 会被拼成一个非法路径（`GenerateDepsFile` 报"目录名语法不正确"）。
