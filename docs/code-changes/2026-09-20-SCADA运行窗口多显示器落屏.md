# SCADA 运行窗口指定落到哪块屏（S13-e）

- 日期：2026-09-20
- 范围：让现场能把组态运行窗口**指定摆到某一块显示器上**——"副屏只给操作员看画面，主屏留给工程师"

## 一、需求与决策

### 1. 需求

路线图（2026-09-20 版）S13 清单里一条，原文逐字：

> `- 多显示器：运行窗口能指定落到哪块屏（现场常见"副屏只给操作员看画面"）。`

S13-e 之前，运行窗口的**形态**可配（依附主窗口 / 独立窗口），但**落在哪块屏**是写死的：
独立形态永远落主屏右下角，依附形态永远在主屏最大化。现场一旦是双屏工位，操作员正对的那块副屏就永远用不上——
要么把主界面整体拖到副屏（连带视觉图像也过去，工程师没法看），要么忍受运行画面跟主界面挤在一屏上。

这不是"好不好看"的偏好，是**物理位置**问题：机台的操作员站位与工程师站位往往不在同一侧。

### 2. 决策清单

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| D-1 | 配置里**存什么**来指认一块屏 | **显示器设备名**（如 `\\.\DISPLAY2`） | 存"第几块屏"看着直观，但序号是"枚举出来的次序"：现场插拔一次显示器、换一个视频口，同一个序号就指到另一块屏上——表现为"昨天还好好的，今天运行画面跑错屏了"，而且改配置的人看不出哪里错了。设备名由系统按"适配器 + 输出口"分配，只要线还插在同一个口上就不变 |
| D-2 | 默认值 / "不指定"怎么表达 | **空串 = 跟随主屏**，且是默认值 | 升级后所有已经在跑的机器读到的都是空串，落屏行为与 S13-e 之前**逐字一致**。多屏现场要"副屏给操作员"时才手动指定 |
| D-3 | 配置落哪一层 | **软件级 `AppConfig.json`**（`AppConfigModel.RunWindowMonitor`） | 与 `RunWindowMode` 同口径：它是"这台机器怎么摆"，不是"这份画面怎么画"。同一份 `.vms` 在开发机（单屏）、现场机（双屏）上本就该落不同的屏 |
| D-4 | 怎么拿到显示器清单 | **自己 P/Invoke** `EnumDisplayMonitors` + `GetMonitorInfoW`（新增 `ScadaMonitors`） | 只为了拿一份清单就给 `VisionMaster` / `ScadaChecks` 两个工程打开 `UseWindowsForms`，等于为一个查询把整套 WinForms 运行时和它的消息循环拖进一个纯 WPF 程序。两个 user32 函数就够了 |
| D-5 | 矩形用什么单位 | **物理像素**（`GetMonitorInfo` 的原生口径），到用的时候再换算 | "枚举时就换算成 DIP"看着省事，但那样这个类型就悄悄绑死了"缩放因子是多少"，而缩放因子是随机器变的。单位转换放在**离使用点最近**的地方（`ScadaMonitor.WorkDip`），读的人才知道这里换算过 |
| D-6 | DPI 缩放因子怎么求 | 主屏**物理**工作区宽 ÷ WPF 认的工作区宽（`SystemParameters.WorkArea`） | 两者测的是**同一块屏**，商就是因子。不必再引 DPI API，也不会出现"两个来源各说各话"的口径冲突。前提：本进程是 System-DPI-aware（无 `app.manifest`、未设感知开关），全局只有一个因子 |
| D-7 | 因子离谱时怎么办 | 落在 `[0.5, 4.0]` 之外一律按 **1.0** | 超出区间说明两个来源说的不是同一块屏（例如将来把进程改成 Per-Monitor V2 而这里没跟上）。那时按 1.0 处理，最坏是窗口尺寸不合预期；按一个错因子算，会把窗口摆到**屏幕外面**去——那在现场就是"运行画面不见了" |
| D-8 | 认不出的设备名怎么办 | **回落主屏**，并 `fellBack=true` → 宿主记一条 `Warn` 日志 | 拔线 / 换口 / 在别的机器上打开同一份配置都会认不出。回落本身是对的（总比把画面摆到屏外强），但**必须让日志说得出原因**——否则现场"我明明配了副屏，怎么还跑在主屏上"只能靠猜。**刻意不做**"离配置那块屏最近的替代屏"这种智能回落：落屏没有"差不多对"，摆到一块没人看的屏上比回到主屏更难排查 |
| D-9 | 形态与落屏什么关系 | **两个独立维度**，依附形态也能指定副屏 | 现场触摸屏一体机常见"主屏给工程师、副屏给操作员"，那时要的正是依附形态铺满副屏。弹窗里用一条分隔线把两者分成两件事来问，免得看成"选了独立窗口才能选屏"的从属关系 |
| D-10 | 依附形态 + 指定副屏怎么落 | **先挪到副屏，再最大化** | WPF 的"最大化"落在窗口**当前所在**的那块屏上。不先挪就直接最大化，结果还是主屏 |
| D-11 | 依附形态 + 跟随主屏 | **一个字节都不设**（`Left/Top` 保持 `NaN`） | 那时 WPF 按 XAML 的 `CenterScreen` 定位到主屏再最大化，正是现场已经在跑的行为——升级不该动它 |
| D-12 | 独立形态的落点规则 | **与 S13-e 之前逐字一致**（工作区 62% / 72%、右下角、留 24 边、夹在 480×360 以上），只是把"哪块屏"从写死主屏变成**入参** | 换屏是本次唯一要改的事；顺带调尺寸会让"升级后运行窗口大小变了"变成一个说不清的副作用。**不居中**的理由保留：主界面通常最大化，居中的窗口会正好压在图像区上，等于换个方式复现本来要躲的那个问题 |
| D-13 | 下拉第一项放什么 | 固定「**跟随主屏（默认）**」，设备名为空串 | "跟随"不是"选主屏"的别名：跟随是"主屏换了我跟着换"，与"钉死在某块屏上"不是一回事。而且它就是默认值，放在第一项让现场一眼看到"不指定"这条路 |
| D-14 | 下拉绑什么 | **设备名字符串**（`SelectedValue` + `SelectedValuePath="DeviceName"`），不绑选项对象 | 配置存什么、界面绑什么、确定时写什么，始终是**同一个字符串**，不会出现"选中的对象换了但字段没跟着换"那一类只在特定点击顺序下才复现的错 |
| D-15 | 配置里那台屏不在线时，弹窗显示什么 | 读回来**归空串**，界面显示「跟随主屏」 | 与运行时真正的回落结果一致。否则会出现"看着选了副屏、实际跑在主屏"，而弹窗里一点异样都看不出来 |
| D-16 | 下拉里怎么区分两块同型号屏 | 拼一句**方位描述**（`DescribePosition`：在主屏右侧 / 左侧 / 下方 / 上方） | 现场两块屏型号往往一样，光看"显示器 1 / 显示器 2"分不清哪块是哪块。判定拿两块屏的中心点连线，横向差更大算左右，否则算上下 |
| D-17 | 显示器清单什么时候取 | VM **构造时取一次** | 它是"点开这一刻机器上接着什么"，不是配置。弹窗活着时插拔显示器属于极端操作，为它做实时刷新只会引入一个没人测过的刷新路径。每次点开都重新构造 VM，清单自然是新的 |
| D-18 | 清单次序 | **主屏第一**，其余按设备名（`StringComparer.Ordinal`）排序 | 下拉框里的次序必须每次一样，否则"第二项是副屏"这种肌肉记忆会漂 |
| D-19 | 落屏入口的签名 | `ApplyRunWindowMode(mode, monitor)` —— 由单参扩成**双参**，唯一调用点是 `ScadaRuntimeHost.Start` | 保持"落屏只有一个入口"这条纪律。`monitor` 为 `null` 时退回 `SystemParameters.WorkArea`（= 枚举不出显示器的受限桌面走的路），**这不是防御性编程**：它是默认配置之外的唯一兜底，没有它，"枚举失败"会变成"运行窗口不显示" |
| D-20 | 改完什么时候生效 | **每次 `Start` 现读** `AppSettingsService.Current` | 与 S13-d 同口径。改完不必重启，下一次点「运行」就是新形态、新落屏；已经开着的运行窗口不动（它已经在跑了） |
| D-21 | 形态属性在哪设 | 仍在 `Show()` **之前**（`ApplyRunWindowMode` 里一次设完） | `WindowStyle` / `WindowState` 这类属性在窗口显示之后再改，WPF 会重建非客户区，表现为闪一下、尺寸跳一格 |

### 4. 断言进程崩溃的真因定位与修复（本阶段最花时间的一件事）

**症状**：`ScadaChecks` 跑到中段**进程直接死掉**，退出码 `3762504530`（`0xE0434352`）——
既没有红条，也看不出是谁抛的，只剩一个退出码。`stderr` 尾部是：

```
System.InvalidOperationException: The DialogCloseCallback has not been properly initialized...
   at Prism.Dialogs.DialogCloseListener.Invoke(IDialogResult result)
   at System.Threading.Tasks.Task.<>c.<ThrowAsync>b__128_1
```

**为什么断言框架抓不住它**：`Check` 只捕得住"主线程**同步**抛出的异常"。而
`DialogCloseListener.Invoke` 是 `async void`，里面的异常经 `Task.ThrowAsync` 甩到**线程池**，
按"异步未处理异常"把进程打死——绕过 `Check`，所以表现为"进程没了"而不是"一条红的"。

**怎么定位的**：挂一个 `FirstChanceException` 处理器，把抛出瞬间的 `Environment.StackTrace` 落盘，
拿到**完整调用链**：

```
at Prism.Dialogs.DialogCloseListener.Invoke(IDialogResult result)          ← 实际抛点（async void）
at VisionMaster.ViewModels.DialogViewModels.ScadaRunWindowSettingsViewModel.OnConfirm()  ... line 199
at Prism.Commands.DelegateCommand.Execute()
at ScadaChecks.Program.RunWindowModeChecks()  ... Program.cs:line 7751    ← 罪魁
at ScadaChecks.Program.Main(String[] args)    ... Program.cs:line 131
```

**根因**：`Program.cs:7751` 的 `reopen.ConfirmCommand.Execute()` 之前**从未给 `reopen.RequestClose` 赋值**。
`RequestClose` 是 auto-property（默认 `null`），`OnConfirm()` 里 `RequestClose.Invoke(...)` 因此走
`DialogCloseListener` 的 default 分支抛异常。

**为什么它看起来像"节拍源坏了"**：那次异常被甩到线程池后，在 `RunBeatSourceChecks` 的
`PumpDispatcher`（内部 `Dispatcher.PushFrame`）推消息循环时被**泵出来**，于是崩点显示在 `[AH2]` 附近；
同一根因还顺带把 `DispatcherTimer 确实在跳`（`拍数>=3`）打红——泵被异常打断，`拍数`只剩 1。
**它是同源症状，不是独立 flaky。**

**修复**（一行）：

```csharp
reopen.SelectedMonitorDeviceName = "";
reopen.RequestClose = MakeCloseListener(_ => { });   // ← 新增
reopen.ConfirmCommand.Execute();
```

**顺带留下的永久防线**：`Main` 顶部挂一个 `AppDomain.UnhandledException` 兜底打印，
把"静默死掉"变成"看得见的现场"：

```csharp
AppDomain.CurrentDomain.UnhandledException += (_, e) =>
{
    Console.Error.WriteLine("========== 未处理异常（进程即将退出） ==========");
    Console.Error.WriteLine(e.ExceptionObject);
};
```

**已排除的伪因**：① 非 `--stress` 专属（加不加都崩）；② 非本阶段新增的 `[DS]` 代码
（把 `RunWindowMonitorChecks()` 注释掉后仍崩）；③ 非 `MakeCloseListener` 用法本身
（它的 `_callback` 类型是对的，其它 5 处赋值点都没事）。

修复后：`--stress` **1292 通过 / 0 失败**，`DispatcherTimer 确实在跳` 随之转绿（证实为同源症状）。

### 5. 真机验证（路线图验收口径第 3 条）

启动 `VisionMaster.exe`（Debug，按启动纪律用 `Invoke-CimMethod Win32_Process Create` 脱离终端启动），
用界面实际操作走了一遍：

## 四、已知边界

1. **真机验证只走通"单屏 + 默认值"这一半**。见 §三.5：UIA 改不了下拉选中项（"Unsupported Pattern"），
   本机又只有一块屏（`\\.\DISPLAY5`），所以"选副屏 → 落副屏"这条路径**没有在真机上被观察到**。
   落点规则由 `[DS]` 的假副屏断言钉住，但"真有两块屏时 WPF 是否真的把窗口摆过去"仍缺真机证据。
   这是本阶段最大的欠账。
2. **`System-DPI-aware` 是硬前提，且没有守卫**。`DpiScale()` 的推导（主屏物理宽 ÷ WPF 工作区宽 = 全局唯一因子）
   只在"进程是 System-DPI-aware"时成立。若将来给程序加了 `app.manifest` 改成 Per-Monitor V2，
   这个推导会静默失效——护栏（`[0.5, 4.0]` 之外按 1.0）只能兜住"离谱"，兜不住"每块屏因子不同"。
   **改动 DPI 感知设置时必须回来重看这里。**
3. **换视频口会认不出设备名**。设备名的稳定性来自"线插在同一个口上"，换口就变。
   行为是回落主屏 + 日志 Warn（D-8），现场照着日志改一下即可——**不会把画面摆到屏幕外**，但也不会自动跟上。
4. **显示器清单是"弹窗打开那一刻"的**（D-17）。弹窗开着时插拔显示器，下拉不会刷新。极端操作，未做实时刷新。
5. **`RunWindowMonitor` 存的是设备名，没有"友好名"**。现场在 Windows「显示设置」里看到的是"显示器 1 / 2"，
   而配置里是 `\\.\DISPLAY2`。下拉项的 `ToolTip` 放了设备名方便对号，但**改配置文件的人得自己知道这层对应**。
6. **"改完立刻生效"的真机证据止于文件层**。`AppConfig.json` 确实写进去了、读得回来（§三.5 第 4 条），
   但"下一次点运行真的换了屏"**没有在真机上观察过**——原因同第 1 条（单屏 + 改不了下拉）。
   这条链路的证据靠断言（`[AB]` 的"再次打开现读"）+ 代码审查（宿主每次 `Start` 现读）。
7. **`[DS]` 的窗口半在 MTA 的 `Main` 上跑不了，单开 STA 线程**。
   `ScadaRuntimeWindow` 是 `Window`（`DispatcherObject` 血统），在 MTA 线程上构造会直接抛
   "The calling thread must be STA"，表现为**整个断言进程崩掉**而不是一条红的。
   样板与 `[AB]` 的 `RunWindowModeWindowChecks` 一致（`thread.SetApartmentState(ApartmentState.STA)` + `Join()`）。
8. **`MONITORINFOEX.szDevice` 的 32 是硬编码的**（Win32 头文件里的 `CCHDEVICENAME`），不能改小——
   缓冲区不够时 `GetMonitorInfo` 会直接失败，表现为"一块屏都枚举不出来"。
9. **`--stress` 从 1261 涨到 1292**（+31）。`[DS]` 与 `[AB]` 都属常规断言，普通运行也会跑。
10. **`AppConfig.json` 被本次真机测试写过**（`RunWindowMonitor: ""`，等于默认值，行为无变化）。
11. **SCADA 全部新代码仍未被 git 跟踪**（承前风险登记头号）。本阶段**未做任何 git 写操作**。
