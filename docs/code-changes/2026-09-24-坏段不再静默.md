# 2026-09-24 坏段不再静默（A2：段级连续失败计数 + 旁路健康通道）

## 一、需求与决策

### 1.1 问题（A2，严重）

`PollBatchPlanner.Poll` 的**单个布尔返回值**同时承担了两个职责：

1. **链路是否还活着** —— 消费者是 `ConnectionWorker.RunPollCycle`，返回 false 就断线重连；
2. **采集是否健康** —— 原先**没有消费者**。

判定式把二者混成了一个值：

```csharp
if (attempted == 0) return true;   // 无读项：不算故障
return failed < attempted;         // ← 只要有一条段读成功就返回 true
```

后果：**只要有一个地址恒坏（配置错、越界、存储区不存在），它每轮都失败、却永远不报警**——
返回值照样是 true（因为别的段读成功了），于是：

| 后果 | 说明 |
| --- | --- |
| 变量永久停在黄点 | 段内变量每轮被 `MarkUncertain()`，值保留旧值、UI 显示黄点 |
| 不重连、不报错 | 判定式认为"通信正常"，重连逻辑永不触发 |
| 只有一条 5 秒限流日志 | `LogThrottled($"seg:{地址}", …)`，被 5 秒窗口吞掉后基本看不见 |

**这是一个"藏得住的错"**：一个坏地址混在几百个好地址里，现场表现只是"某几个点一直黄"，没人知道是配置问题。

### 1.2 核心矛盾：为什么不能简单把判定改成"全成功才算成功"

这是本任务**最关键的设计约束**，必须写清楚，防止后人回退：

> **不能**把判定改成 `failed == 0` 才算成功。

因为那会让**一个坏地址把整条连接打进无限重连循环**：

```
连上 → 轮询 → 有一项失败 → 判链路死 → 断开 → 重连 → 连上 → 轮询 → 有一项失败 → …
```

结果是把"一批点偶发黄"升级成"**所有点全灰**"——**比原问题更糟**。

所以解法只能是：**主判定语义一个字不改，另开一条旁路**。

### 1.3 决策（4 项，已逐条与用户确认）

| 决策项 | 结论 |
| --- | --- |
| 范围 | **只做「可见 + 上报」**——不熔断、不降频、不改返回值语义 |
| 粒度 | **组级汇总**（诊断面板按扫描组显示"异常段数 / 总段数"） |
| 阈值 | **连续 3 轮**失败才算异常段（单轮抖动不报警） |
| 质量戳 | **保持 `Uncertain`**（`VariableQuality` 枚举与所有 UI 绑定点零改动） |

**旁路健康通道设计**：

- 每个 `ReadSegment` 自带 `ConsecutiveFailures`（连续失败轮数，**成功一轮即归零**）与 `LastError`；
- 连续失败达 `FaultedSegmentThreshold = 3` 即计为**异常段**；
- 跨阈值那一刻发一条**不节流**告警（`_log?.Invoke(...)` 直调，**不走 `LogThrottled`**）；
- `GetHealthSnapshot()` 把"异常段数 + 首个坏段摘要"上到诊断面板。

### 1.4 备选方案与不采纳的理由

| 方案 | 不采纳理由 |
| --- | --- |
| 判定改 `failed == 0` | **一个坏地址 → 无限重连循环**，把"几个点黄"升级成"全部点灰" |
| 坏段**熔断/降频**（连续失败后跳过该段若干轮） | "何时恢复"需额外状态机；摘段会让变量**彻底不更新**（连黄点都没了），比黄点更糟 |
| 坏段直接把变量标 `Bad` | `Bad` 在 UI 语义上是"没有值"；这里旧值仍然有效，标 `Uncertain` 才是"值可能过期"的准确表达 |
| 靠已有的限流日志上报 | `LogThrottled` 的 5 秒窗口会吞掉告警（且 `_logTicks` 是 static），靠它上报等于没报 |

> ⚠ **本节代码示例里的限流 key 已随后续变更调整**：`seg:{地址}` → `seg:{连接名}.{地址}`
> （原因：`_logTicks` 是 static、跨连接共享，原 key 会让两条连接读同一地址时互吞告警）。
> 详见 `docs/code-changes/2026-09-24-等待时长与限流key修正.md`（C5）。**勿照抄本文旧 key**。

### 1.5 为什么告警必须"不节流"

`LogThrottled` 的 5 秒窗口对"每轮都发生的同一件事"是必要的（防刷屏），但对**状态跃变**（第一次跨阈值）是致命的——它可能整条都被吞掉。

故实现上分两条：

```csharp
// 跨阈值那一刻：直调，不节流，保证"从看得见升级为被通知"
if (failures == FaultedSegmentThreshold)
    _log?.Invoke($"[轮询] 段连续 {failures} 轮读失败，已计为异常段：{seg.Address}（{seg.SpanUnits} 单元）: {ex.Message}");

// 之后每轮：回落限流，避免恒坏段每轮刷一条
LogThrottled($"seg:{seg.Address}", $"段读失败 {seg.Address}（{seg.SpanUnits} 单元）: {ex.Message}");
```

只发一次（`failures == 阈值`），**不是 `>=`**——否则恒坏段会每轮刷一条。

### 2.1 关键代码

**段循环（`PollBatchPlanner.Poll`）**：

```csharp
try
{
    if (seg.IsBitArea)
        ApplyBits(seg, connection.ReadBits(seg.Address, (ushort)seg.SpanUnits));
    else
        ApplyBytes(seg, connection.ReadBytes(seg.Address, (ushort)seg.SpanUnits), byteOrder);

    // 读成功即归零：地址修好后诊断面板的"异常段"自然消失，不需要人工复位
    Volatile.Write(ref seg.ConsecutiveFailures, 0);
    seg.LastError = null;
}
catch (Exception ex)
{
    failed++;
    // 段内所有变量降级 Uncertain：值保留旧值，UI 黄点提示"最近一次读取失败"
    foreach (var item in seg.Items)
        item.Variable.MarkUncertain();

    int failures = Volatile.Read(ref seg.ConsecutiveFailures) + 1;
    Volatile.Write(ref seg.ConsecutiveFailures, failures);
    seg.LastError = ex.Message;

    // 跨阈值那一刻发一条"不节流"的告警（只在这一刻发，之后回落限流）
    if (failures == FaultedSegmentThreshold)
        _log?.Invoke($"[轮询] 段连续 {failures} 轮读失败，已计为异常段：{seg.Address}（{seg.SpanUnits} 单元）: {ex.Message}");

    LogThrottled($"seg:{seg.Address}", $"段读失败 {seg.Address}（{seg.SpanUnits} 单元）: {ex.Message}");
}
```

**健康快照（`GetHealthSnapshot`）**：

```csharp
public (int FaultedCount, string? FirstDetail) GetHealthSnapshot()
{
    int faulted = 0;
    string? first = null;

    foreach (var seg in _segments)
    {
        int failures = Volatile.Read(ref seg.ConsecutiveFailures);
        if (failures < FaultedSegmentThreshold) continue;

        faulted++;
        first ??= $"{seg.Address}（连续失败 {failures} 轮）：{seg.LastError}";
    }

    return (faulted, first);
}
```

**线程约定**：段状态仅 Worker 线程写；`GetHealthSnapshot()` 可由 UI 线程（`DispatcherTimer` 每秒）调用，故读写都走 `Volatile`。读到的最多是"上一拍"的值，诊断够用。

### 2.2 面板显示口径

- **「异常段」列**显示 `1/12` 形式（分子 = 异常段数，分母 = 本组总段数），无异常时显示 `—`。
  为什么用 `x/y` 而不是只报一个数：12 段坏 1 个只是局部，2 段坏 1 个就是半瘫——只有分子看不出严重程度。
- **ToolTip** 显示首个坏段摘要（地址 + 连续失败轮数 + 错误原因）。
  ⚠ `FaultTooltip` 类型是 `string?`，无异常时返回 `null`——**不能返回 `string.Empty`**，否则 WPF 会弹出一个空提示框。
- 它与「达成率」是**两件事**：达成率看周期快慢，异常段看"有没有地址读不到"。

### 2.3 断言（C12 组，13 条，全部离线可跑）

用测试桩 `FaultyConnection` 按地址注入失败，不接硬件。

| 断言 | 内容 | 意图 |
| --- | --- | --- |
| C12-0 | 两个相隔 100 寄存器的地址拆成 2 段 | 前提：必须能分别注入失败（间隙容忍 Modbus 寄存器 = 8，99 > 8） |
| C12-1 | 1 段成功 + 1 段失败 → `Poll` 仍返回 **true** | **核心**：不误判为链路故障 → 不会无限重连 |
| C12-2 | 坏段变量质量 = `Uncertain` | 不是 `Bad`：值保留旧值，黄点提示"最近一次读失败" |
| C12-2 | 好段变量质量 = `Good` | 同一轮里互不牵连 |
| C12-2 | 连续失败 1 轮 < 阈值 3 → 不算异常段 | 单轮抖动不该报警 |
| C12-3 | 连续失败按轮累计：2 轮仍 < 阈值 | 计数确实在涨 |
| C12-4 | 连续失败达阈值 3 → 计为 1 个异常段 | 跨阈值判定 |
| C12-4 | 摘要含地址与"连续失败 3 轮" | 面板 ToolTip 直接可读 |
| C12-4 | 跨阈值那一刻恰好 1 条告警 | **不节流**：走 `LogThrottled` 会被 5 秒窗口吞掉 |
| C12-4 | 持续坏 → 计数涨到 4 轮，告警**不重复**刷 | 只发一次（`==` 而非 `>=`） |
| C12-3 | 地址恢复 → 异常段归零 | 成功一轮即归零，不需人工复位 |
| C12-3 | 归零后再坏 2 轮仍 < 阈值 | 证明归零真的生效（未归零的话此刻早已 ≥ 阈值） |
| C12-5 | **全段失败** → `Poll` 返回 **false** | 通信级故障语义**未被改坏**，仍触发重连 |

**测试桩 `FaultyConnection` 的两个注意点**：

1. `ReadBytes` 必须返回 `new byte[length * 2]`——Modbus 寄存器区 1 单元 = 2 字节，若只给 `length` 字节，`ApplyBytes` 会走「设备返回字节不足」分支再记一次失败，干扰本组要验的"段读异常"路径；
2. 用桩而非真 `ModbusTcpConnection`：本组要验的是"规划器怎么消化失败"，不是"设备怎么失败"；且需要"同一地址按需坏/好"中途翻转，真连接做不到（且会依赖外部模拟器进程）。

## 四、已知边界

1. **兜底单读项不参与异常计数**：`_fallbacks`（无法合并成段的单读项）没有"段地址"概念，故不累计 `ConsecutiveFailures`。其失败时变量已标 `Uncertain`、且已有 `LogThrottled` 日志，属既有可见性范围，本次不扩。
2. **不做段熔断 / 降频**：异常段仍然每轮被读（只是失败），不跳过、不降频。"何时恢复"需额外状态机；摘段会让变量彻底不更新，比黄点更糟。
3. **质量戳仍为 `Uncertain`**：`VariableQuality` 枚举、所有质量戳 UI 绑定点、`ConnectionWorker` 的 `false = 通信级故障` 契约均**零改动**——本任务只加"可见性"，不改任何既有语义。
4. **未覆盖实机验证**：C12 断言的是"规划器如何消化段读失败"，不是"S7/Modbus 真机上坏地址的报文行为"。真机点验需模拟器在线，留待联调。
