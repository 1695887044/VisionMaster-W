## 二、已做

### 2.1 标定（Plugin.Calibration）

**CAL-1 打开方案推进标定时间戳（P1，建议先修）**

`Initialize` 的顺序是：

1. `base.Initialize(stepData)`（`CalibrationPlugin.cs:859`）→ 内部 `ApplyConfigValues` 按 `InputValues`
   顺序逐个 set 配置属性；
2. 迁移旧空行（`:868-870`）；
3. `_lastInputSignature = BuildInputSignature()`（`:873`）；
4. `RefreshStatus()`（`:881`）。

每个带 `OnXxxChanged → RefreshStatus → ComputeCalibration` 的属性在 set 时都会跑一次求解：
第一次 `known=false` 只记签名；第二次起签名变了就 `CalibrationStampUtc = DateTime.UtcNow`
（`:1122-1130`）。`CalibrationStampUtc` 在声明顺序上位于 `Intrinsics`、`CaltabDescrFile`、
`IntrinsicsModel`、`IntrinsicsPixelSizeMeters`、`IntrinsicsImageFolder/List`、`UndistortBeforeCalibration`
**之前**（`:357-505`），后面这些属性任一非默认值都会在 stamp 写入之后再触发一次 → 把方案里存的时间刷成"刚刚"。
`NormalizeLegacyAllZero` 迁移也在签名对齐之前，同样会触发。

断言 `CalibrationChecks.cs:463-496` 只模拟"运行实例直接设属性"的路径（先填点、再设 stamp、再 `RunAlgorithm`），
**没有走 `Initialize(stepData)`**，所以这条是绿的。建议补一条"打开方案"路径的断言，并让 `Initialize` 在灌配置期间
抑制 `ComputeCalibration`（或把签名对齐提前到 `base.Initialize` 之前 + 用 `_initializing` 标志跳过刷新）。

**CAL-2 导出/导入不含内参（P1）**

`CalibrationExportFile`（`Models/CalibrationFile.cs:16-74`）只有模式、网格、A/B、标定表、序列号、
阈值/护栏、尺寸、来源标签、时间戳与质量快照；`BuildCalibrationExportJson`（`:3133-3181`）没有写
`Intrinsics`，也没有写 `UndistortBeforeCalibration`。`ImportCalibrationJson`（`:3189-3277`）自然也不会恢复它们。

后果是"换机台/备份/第二台设备复用"这条用途在**带内参去畸变**的标定上不成立：

- 导入端开关是关的 → 用原始像素重算，和源机的去畸变域标定**不是同一份**，且没有提示；
- 导入端开关是开的 → 本机没有内参，运行期明确失败。

Help `03-ports-and-parameters.md:76-77` 与 `04-calibration-criteria.md:123-130` 的字段清单也没有提到内参，
所以文档与实现一致，但**功能缺口本身**需要在导出时补上（DTO 已经是白名单内的 `Plugin.*` 类型，直接加字段即可），
或至少在导出/导入时对"开关打开但内参未导出"给出明确警告。

**CAL-3 像素当量模式下的去畸变开关被静默忽略（P1）**

`ComputeCalibration` 的判定是：

```csharp
bool undistorting = UndistortBeforeCalibration
                    && Mode is CalibrationMode.NinePoint or CalibrationMode.Perspective or CalibrationMode.Mesh;
```

`CalibrationPlugin.cs:1152-1154`。像素当量模式不进这个集合，所以开关不生效；但 `UndistortHintText`
（`:1470-1496`）在内参良构时无条件返回"已启用（当前内参：…）：取点先经内参去畸变再求解，产出的标定 Kind 为
`*Undistorted`"。用户看到的是"已生效"，实际 `MmPerPixel` 仍是原始畸变像素域算出来的。

契约里确实没有 `PixelScaleUndistorted`，所以**不能**靠"把 Kind 改成去畸变"来修。建议二选一：
① 在 `UndistortHintText` 里按 `Mode` 分支，像素当量模式明确写"本模式不适用，开关被忽略"；
② 或在 `ComputeCalibration` 里对"PixelScale + 开关打开"直接判 `BlockingError`（更响，但会打断已有配置）。
另外 `OnModeChanged`（`:152-157`）目前只通知 `ShowPointTable`，没有通知 `UndistortHintText`；
按 `Mode` 分支后必须补上，否则切换模式时提示文字不刷新。内参卡片是"默认折叠"的 `Expander`
（`CalibrationView.xaml:758-777`），不是按模式隐藏——展开后在像素当量模式下同样会看到这条错误提示。

**CAL-4 运行期 `SourceImage` 的跨线程 UI 访问（P1，条件触发）**

`CalibrationPlugin` 构造函数订阅 `SourceImage.ValueChanged`（`:842-843`）；`InputPort.ValueChanged`
在 setter 线程同步触发（`InputPort.cs:256-265`），而 `RefreshOnlineImage`（`:2363-2384`）直接调用
`RefreshCanvasImageState`（`:2390-2403`），后者执行 `CanvasMarkers.Clear()`。`CanvasMarkers` 绑定到
`HalconBase.DrawObjectList`（`CalibrationView.xaml:1307`），`HalconBase` 在集合变更时同步 `RenderAll()`
（`HalconBase.cs:430-456`），内部直接操作 HALCON 窗口。

只要 `SourceImage` 在运行期被链接（上游每轮产生新 `HImage` → 引用变化 → `ValueChanged`），这段就在
**流程线程**上跑。配置窗关闭时 `CanvasMarkers` 可能没有活动绑定，不一定立刻炸；对话框开着跑流程时风险最高。
建议：`RefreshOnlineImage` / `RefreshCanvasImageState` 统一走 `PostToUI`（这里用 `BeginInvoke` 更合适，
避免流程线程等 UI），或者运行期只更新尺寸元信息、把"清标记"留给 UI 线程。

**CAL-5 参考模式不校验图像尺寸（P2）**

`LoadSavedCalibration`（`:997-1044`）只校验资产存在、`MmPerPixel > 0`、相机序列号；没有比对
`transform.SourceImageWidth/Height` 与当前 `SourceImage`。类注释说"失配（相机序列号/资产不存在）会明确失败"，
这里确实只承诺了两项；但契约要求消费方做尺寸自证，而 `SourceImage` 端口就在手边，补一条成本很低。
下游 `PoseTransform` 只在接了 `SrcImage` 时才查尺寸，没接就放行——参考模式是尺寸自证的最后一道口子。

**CAL-6 网格基线不可用时不清旧残差（P3）**

`ApplyRowResiduals`（`:1955-2018`）在 `_meshAffineBaseline` 为 null 或 `TryToMatrixFrame` 失败时直接
`return`/`continue`，不把 `ResidualPx` 归零。切换模式或点集退化后，表格里可能留着上一轮的残差数字，
而质量区已按新状态显示——纯 UI 误导，不影响输出。

**CAL-7 粘贴解析的区域性/非有限数（P3）**

`TryParseRows`（`:2529-2588`）用 `double.TryParse(cell, out var v)`（CurrentCulture）：
逗号小数区域会把 `"1,5"` 按分隔符切成两列（该方法的分隔符包含 `,`），且 `"NaN"`/`"Infinity"`
会解析成功（后者由 `CollectPoints` 的 `IsFinite` 兜住，不会算错，但错误会晚一步、且不带"第几列"）。
建议改 `NumberStyles.Float, InvariantCulture`，并在解析处直接拒绝非有限数。

**CAL-8 步骤锁与资产锁耦合（P3）**

`TrySaveCalibrationAsset` 把 `IsLocked = IsCalibrationLocked` 写进资产（`:1066`）。如果某次运行时步骤是锁定的，
资产会被写成锁定；之后解锁步骤再运行，`SolutionCalibrationCatalog.Save` 会因 `existing.IsLocked` 拒绝覆盖
（`SolutionCalibrationCatalog.cs:73-77`），只记一条 Warn，资产静默停在旧版。是否要把两个锁绑在一起，
建议在 Help 里写明；或让资产锁只由资产自己的管理入口控制。

**CAL-9 五列粘贴的首列静默丢弃（P3）**

`TryParseRows` 对 5 列输入固定把第一列当序号丢掉（`:2560-2561`），不校验它是不是数字。
用户如果从 Excel 复制了 5 列真实数据，第一列会无声消失。文案里已写"5 列（带序号）"，
但建议首列不是整数时明确报错，而不是继续。

### 2.2 手眼标定（Plugin.HandEye）

**HE-1 万向锁欧拉角符号错（P1）**

`TryMat3ToEulerZyxDeg` 的万向锁分支（`HandEyeMath.cs:594-599`）：

```csharp
rx = 0.0;
rz = Math.Atan2(r[0, 1], r[1, 1]);
```

按同文件的正解 `R = Rz·Ry·Rx`，`ry=+90°` 且 `rx=0` 时 `r[0,1] = -sin(rz)`、`r[1,1] = cos(rz)`，
所以 `Atan2` 得到的是 **−rz**。数值验证（PowerShell 复算同一组公式）：实际 `rz=30°` 提取为 `−30°`；
把符号改成负号后恢复 `30°`。`ry=−90°` 同理。注释宣称"往返矩阵仍然一致"不成立。

影响面：`Mat4ToXyzEulerZyxDeg` 目前只在断言宿主里用于造样本（`HandEyeChecks.cs:257/270/405/408`），
插件本身的 CSV 导出写的是原始 12 个数（`HandEyeCsv.Format(plugin.Samples)`），所以**当前主路径不经过它**；
但它是 public helper，注释明确说"标定出来的 4×4 要能被写回 CSV"，任何后续"把结果写成 12 个数"的功能
都会静默写错。修法：`rz = -Math.Atan2(r[0,1], r[1,1])`。

**已于 2026-10-26 修复**：断言改为 `rz=30°` 并补 `ry=-90°`，先红（`最大元素偏差 1e+0`）后绿
（`0e+0`）；详见 `2026-10-26-手眼万向锁欧拉角符号修复.md` 与 `artifacts\logs\20261026\he-euler-{before,after}.log`。

**HE-1b 断言在万向锁这一点上是盲的（P1 同族，R38）**

`HandEyeChecks.cs:268-279` 的「欧拉④」用 `PoseFromXyzEulerZyxDeg(10,20,30, 0, 90, 0)`——`rz=0`。
`rz=0` 时 `Atan2(0,1)=0`，符号错正好不可见，所以这条断言恒真。建议改成 `rz=30°`（并补 `ry=−90°`），
先用当前代码确认它会红，再修代码转绿——否则就是"改坏→红→还原→绿"缺了反证（R65）。

**HE-2 采集进度条永不显示（P1）**

`HandEyeView.xaml:63-91` 的模板是：

```xml
<Border x:Name="Track" ...>
    <Border x:Name="PART_Indicator" ... />
</Border>
```

WPF `ProgressBar` 的模板契约是 **外层 `PART_Track`（量宽度）+ 内层 `PART_Indicator`（被设置 Width）**。
缺 `PART_Track` 时 `Track` 字段为 null，`SetProgressBarIndicatorLength` 直接不执行，`PART_Indicator`
的 `Width` 保持 `Auto`；它又没有内容、`HorizontalAlignment=Left`，实际宽度为 0。
所以 `01-quickstart.md:74` 承诺的"进度条满了会由蓝转绿"永远看不到。

修法：把**外层** `Border x:Name="Track"` 改名为 `PART_Track`，内层保持 `PART_Indicator`。
**不要**照抄仓库里的 `FluentProgressBarStyle`（`UI/Controls/Themes/Fluent/FluentControls.xaml:762-781`）——
它把**填充**命名为 `PART_Track`、没有 `PART_Indicator`，是同一族的错（该样式当前未进合并链，所以没暴露）。

**已于 2026-10-26 修复**：`UIThemeSmokeTest --plugin-views Plugin.HandEye` 的渲染断言
修复前 `PART_Track=null / PART_Indicator=0`（红），修复后 `PART_Track=88 / PART_Indicator=44`（绿）；
详见 `2026-10-26-手眼采集进度条PART_Track修复.md` 与 `artifacts\logs\20261026\handeye-view-{before,after}.log`。

断言 `HandEyeChecks.cs:739-783` 的「进度①~⑥」只检查 VM 的 `SampleProgress`/`HasSample` 数值，
不渲染控件，所以拦不住"值对但条不显示"（R38：跳过型/间接断言必须能被反证）。

**HE-3 非有限数入表 → 求解抛异常（P1）**

- `HandEyePaste.TryParseRows`（`:149`）与 `HandEyeCsv.TryParse`（`:73`）都用
  `double.TryParse(..., NumberStyles.Float, InvariantCulture, ...)`。实测（PowerShell）：
  `"NaN"` 返回 **true**，值为 `NaN`；`"1e400"` 返回 false。
- `HandEyeSample.IsBlank` 判的是"12 个值全为 0"（`Models/HandEyeSample.cs:98-102`），`NaN != 0`，
  所以 NaN 行不会被当成"还没填"。
- `TryBuildSamples`（`HandEyePlugin.cs:955-988`）只查空行/全 0 行，不查有限性。
- 求解进入 `TryRotationLog`（`HandEyeMath.cs:636-678`）：`angle = Acos(NaN) = NaN`，
  `angle < 1e-12` 与 `angle < π-1e-6` 都为 false，落入 π 分支，`Math.Sign(NaN)` 抛
  `ArithmeticException`（.NET 行为，已用 PowerShell 复核）。
- 配置界面 `SolveForPreview`（`:409-437`）没有 try/catch；`RelayCommand.Execute` 直接调用委托
  （`Shard/Core.Controls/Commands/RelayCommand.cs:36`），异常落到 `App.OnDispatcherUnhandledException`
  （`VisionMaster/App.xaml.cs:78`），用户看到的是英文异常名而不是"第 N 行数据非法"。

修法（三层，建议都做）：
① `HandEyePaste`/`HandEyeCsv` 在入表处拒绝非有限数（带行号/列号）；
② `TryBuildSamples` 统一扫一遍 `double.IsFinite`，点名"成对数据第 N 行含非法数值"；
③ `TryRotationLog` / `JacobiEigenSymmetric` 入口判 `IsFinite` 返回 false（防御性，避免别的入口再踩）。

**已于 2026-10-26 修复**：三层守卫 + `SolveForPreview` try/catch 都已落地；
`HandEyeChecks` 新增 6 条「非有限」断言，先红后绿（全量宿主退出码 0）。核对时补充了一个细节：
只把**平移**设 NaN 不会抛异常，而是落成误导性的"平移堆叠矩阵奇异"；所以 `TryBuildSamples`
必须覆盖 12 个分量，不能只查旋转。详见 `2026-10-26-手眼非有限数防线修复.md`。

**HE-4 结果持久化从显示串反解 + Culture 混用（P2）**

`FormatCells`（`:593-600`）用 `v[i].ToString("0.000")`（CurrentCulture）生成 16 个显示串；
`SerializeSavedResult`（`:652-684`）再从这 16 个串用 `InvariantCulture` 反解成 `double[]`。
两个问题：

1. **精度**：保存的是 3 位小数后的矩阵，不是解出来的 `Mat4`；每次"打开→确定"再舍入一次，
   旋转矩阵不再正交。当前这份数据只用于重开方案的"上次结论"展示（执行时从 `Samples` 重算），
   所以不影响生产输出，但"方案里存着标定结果"这句话就名不副实。
2. **Culture**：显示串走 CurrentCulture、解析走 InvariantCulture。在逗号小数区域（如 de-DE），
   `"0,021"` 解析失败 → `NaN` → `TryParseSavedPayload` 判无效 → 重开方案从"完成"退回"未求解"。

### 2.3 坐标变换（Plugin.PoseTransform）

**PT-1 `RefreshConfigState` 不受 `_viewAttached` 约束（P2）**

**PT-3 4 通道图叠加会抛（P3；原结论已修正）**

**PT-5 叠加预览的轮廓静默不上色（P2，逐条核对时新发现）**

## 五、踩过的坑

- **万向锁断言为什么一直是绿的**：`HandEyeChecks` 的「欧拉④」用 `rz=0`，而符号错在 `rz=0` 时
  恰好不可见（`Atan2(0,1)=0`）。这类"参数取了让缺陷不可见的特殊值"的断言，比没有断言更危险——
  它给人一种"这一点已经测过"的错觉（R38 的反证要求）。
- **WPF ProgressBar 的 part 名字**：`PART_Track` 是**轨道**、`PART_Indicator` 是**填充**；
  进度宽度按 `PART_Track.ActualWidth` 算。仓库 `FluentControls.xaml:762-781` 把填充叫 `PART_Track`，
  是反的；不要拿它当范式。修 HandEye 时只改外层 Border 的名字，内层保持 `PART_Indicator`。
- **`double.TryParse("NaN", NumberStyles.Float, InvariantCulture)` 返回 true**：`NumberStyles.Float`
  不拦特殊值；`"1e400"` 反而返回 false。所以"解析成功"不等于"有限数"，入表处必须显式 `IsFinite`。
- **`Math.Sign(double.NaN)` 抛 `ArithmeticException`**：手眼求解的 π 分支在 NaN 输入下会走到这里，
  而 `RelayCommand` 不捕获异常——症状是英文全局弹窗，不是业务失败文案。
- **HALCON 23.05 的 `paint_xld` 不吃 3 通道 + 3 元组**：探针实测轮廓点仍是 `(0,0,0)`，静默不上色；
  1 通道 + 单值正常。仓库 `docs\代码\视觉算子\模板匹配\模板匹配插件.md:838` 早有记录，但坐标变换的
  叠加预览仍用了 3 通道 + 3 元组——**这条不是"可能"，是实测**。同一探针还纠正了一个误判：
