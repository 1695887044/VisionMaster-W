# 手眼标定：成对数据表为主、CSV 为扩展；设计基线升 v2

> 日期：2026-10-22 ｜ 范围：`Plugin.HandEye` 数据入口 + 设计基线 v2 ｜ 状态：已落地（断言 3329/0，gate 见 §4）

## 1. 背景

`Plugin.HandEye` 首版（提交 `3a1d41ed`）把成对数据锁在**一个 CSV 文件路径**上：`InputPort<string> SamplesPath` 端口 + `[StepConfig] SamplesFilePath` 配置，`RunAlgorithm` 只认磁盘文件。当时的设计基线 v1（提交 `118b3a28`）照此画了「CSV 路径 + 浏览…」的界面。

用户评审 v1 时否掉了这条决策，原话：

> 为什么非要导入 不能做成 列表吗 也可以手填写，csv作为扩展功能 可以导入导出

这条推翻了 Q1。原决策的理由「现场数据来自机器人控制器导出、手打 12 列 × N 行不现实」回答的是**数据从哪来**，而用户问的是**数据放哪、怎么改**。手填真正救的场景是"改一个打错的数字 / 删一行离群 / 补一组"——而这三件事原本都要回去开 Excel，Excel 会锁文件、会改编码、会把 `45.600` 存成 `45.6`。采集时逐组加行本身也构成台账。

## 3. 关键决策

1. **表格是数据的主存放位置，CSV 是导入导出。** 判据不是"数据从哪来"，是"数据要改的时候在哪里改"。只给文件路径意味着每次改一个数都要离开应用。
2. **空白行判据 = 12 个值全为 0，且必须单独报错。** 加了行没填若照常进求解，报出来的是「旋转残差 15.155° 超过上限 0.5°，姿态数据可能含错点/角度单位不对/欧拉约定不符」——用户会一路去怀疑机器人姿态和欧拉约定，真正的原因只是忘了填一行。所以 `IsBlank` 单独拦，文案点名"第 N 行还没填（12 个值全为 0）"。
3. **`ToMathSample()` 是全仓唯一的"一行→数学样本"入口。** CSV 导入、表格直跑都走它；否则两处各写一遍欧拉→矩阵换算，迟早分叉（分叉的症状是"导入的数据对，手填的数据不对"）。
4. **`TryBuildSamples` 先 `ToArray()` 快照再遍历。** 界面线程可能在求解过程中删行，直接遍历 `ObservableCollection` 抛 `InvalidOperationException`。
5. **`HandEyeCsv` 不碰文件。** 编码、覆盖确认、异常提示都是视图的事；纯函数单元才测得住（5 条 CSV 断言不需要临时目录）。
6. **`[JsonIgnore]` 只能标属性，不能标方法。** 标在 `ToMathSample`/`ToRow` 上报 `CSB0592 特性"JsonIgnore"对此声明类型无效`。
7. **状态隔离全部用语义类 `body:not([data-state=…])`，不用 inline style、不用 `only-default` 组合类。** v1 的两个渲染 bug 正是这两类写法造成的：inline 覆盖状态选择器、组合类被另一状态的规则误伤。

## 5. 边界与未做

1. **界面本身没做。** 本轮只做数据层与设计基线；`HandEyeView.xaml` 仍不存在，插件仍是"无视图、靠配置面板跑"。按 R127/R128，视图必须照 v2 基线复刻。
2. **表格没有粘贴能力。** 从 Excel 粘一片区域进来（Q6）未做，需要 `DataGrid` 剪贴板处理 + 列映射，属独立批次。
3. **没有"采集"按钮。** 逐组加行是手填；从相机/机器人自动读一组进来（Q2 的实时进度）未做，需要设备层回调。
4. **眼在手外（AX=ZB）只有契约没有求解器**（§11 D3），选了眼在手外目前会得到与眼在手上相同的结果语义但方程不同——**基线 v2 与插件都还没拦这个**，只在帮助手册 `03-mounting-and-frames.md` 写明限制。
5. **CSV 编码只按 UTF-8 读**，带 BOM 能处理，GBK 导出会乱码；视图层选文件时需明确提示，本轮未做。
6. **没接真机数据。** 全部断言走合成数据；欧拉约定的三个符号只经过"只绕单轴转 90°"的数学反证，**没有用现场机械臂核对过**。
