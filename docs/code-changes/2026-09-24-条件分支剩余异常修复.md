## 一、需求与决策

### 范围（7 项）

| # | 项 | 病灶 | 改法 |
|---|---|---|---|
| 1 | Else 的 `Parse("true")` 外套空 `catch { }` | 编译期零提示；`ConditionLambda` 留 null → 运行期被 `continue` 跳过 → Else 永不执行 | 空 catch → `errors.Add("[语法错误] ... 兜底分支 ... 条件编译失败")` |
| 2 | Switch/Case 是半成品 | 模型/ViewModel 各有一份 `Contains("Switch")` 建 Case 分支，但全仓无 Switch 算子注册 → 死代码 | 删模型 Switch 分支、`IsSwitchNodeSelected`、`AddCase` 命令与 XAML 按钮；两个枚举值保留 |
| 3 | ElseIf 可达性无校验 | `AddElseIf` 会插到 Else 前，但反序列化/手工排序后 ElseIf 落到 Else 之后即永不可达，编译期零报错 | 编译 If 分支时按顺序校验，Else/Default 之后还有分支 → `errors.Add("... 不可达分支 ...")` |
| 4 | 容器判定口径漂移 | 模型侧 `pluginTypeName.Contains("If")`、ViewModel 侧 `PluginName.Contains("If")`，两处各写一份 | 收敛为 `ConditionStep.IsIfLike` 单一公开属性，构造与 UI 同调 |
| 5 | 类型解析空 `catch { }`（2 处） | 解析失败却继续按 `double` 建 `Parameter` → 把「未知类型」伪装成 double，运行期归一类型与声明不符 | 空 catch → `errors.Add("[类型错误] ... 解析失败")` + `continue` |
| 6 | While `MaxIterations` 硬编码 9999，达上限只 `Warn` | 循环被掐断却把步骤标 `Success`，现场误以为「循环正常跑完」 | 提为具名常量 `DefaultMaxIterations`；达上限标 `Failed` + 上抛 |
| 7 | 补 `[E8]` 断言 | 三个 P0 与 P1-4 都改在运行期取值/异常路径上，只有「无回归」证据，没有「新行为」证据 | 新增 `[E8]` 段（6 组共 15 条断言） |

### 两项已确认决策

| 决策点 | 选定方案 | 理由 |
|---|---|---|
| Switch/Case 处置 | **删死代码，保留枚举**（推荐） | 无算子、无 UI 入口即死代码；但删枚举值会打乱既有序号，可能波及已存盘引用，故只删引用点、枚举值保留并加注释 |
| While 达 `MaxIterations` 语义 | **标 Failed + 上抛（推荐）** | 迭代上限被触发 = 循环没跑完就被强行掐断，结果不可信。与既有先例 `CompiledPluginNode` 对齐：程序级异常 → 标 Failed + `throw`，最终由 `FlowEngineService` 把会话置 `Faulted` |

### 关键设计：修「静默」而非修「功能」

这 7 项有一个共同特征——**都不影响正常图纸，只在异常/边缘路径上把问题藏起来**。所以本轮的统一准则是：

> 凡是「解析失败 / 编译失败 / 被强行掐断」这类**结果不可信**的分支，一律从「静默降级」改成「显式报错或抛异常」，让现场第一时间看见，而不是拿到一个看似成功的结果。

同时严守一条底线：**不改变存量合法图纸的行为**。为此在类型解析两处都加了 `IsNullOrWhiteSpace` 守卫——空类型名沿用历史兜底（按 `double`），只对真正的解析失败报错（详见「已知边界」）。

### 两处值得说明的改动

**① While 达上限判断为什么要带 `MaxIterations > 0`**

循环头守卫 `while (iter < MaxIterations)` 在 `MaxIterations = 0` 时一圈都不跑就退出，此时 `iter(0) >= MaxIterations(0)` 为真——若不加这个条件会把「上限配成 0 圈」这种正常的不执行误报成死循环。判断还排除了「取消请求」这个出口（取消是用户主动停止，不是死循环）。

**② `DefaultMaxIterations` 常量化的实际收益**

除了消除魔法数字，更重要的是把「默认值」与「判断依据」显式绑在一起：断言 `[E8]` ④ 里就是先 `Compiled` 再改 `MaxIterations = 5` 来避免真跑 9999 圈——**引擎语义与上限大小无关**这一点被这条断言钉住了。

## 四、已知边界

| # | 项 | 说明 |
|---|---|---|
| 1 | **Else 空 catch 的修复无断言覆盖**（#1） | 唯一能触发该路径的 `DuplicateParameterException` 会被同函数里 If/ElseIf 的 `errors.Add` 先阻断编译，现实中无触发路径。**属「修了但无法验证」**——修复意义在于把哑弹拆掉，而非消除已发生故障 |
| 2 | **类型解析空 catch 的修复无断言覆盖**（#5） | 同上：`TypeHelper.GetActualTypeFromLink` 本身**永不抛异常**，外层 `try` 实际抓不到东西。真正的解析失败早已由 `Type.GetType(...) ?? typeof(double)` 吞掉，故这条修复同样是「消除隐患」性质 |
| 3 | **`BranchType.Case` / `ModuleCommandAction.AddCase` 枚举值保留未删** | 用户决策：删引用点、留枚举值，避免打乱既有序号波及可能已存盘的引用（已核实 `ModuleCommandAction` 全仓从未序列化）。若后续确认无历史数据依赖，可再清理 |
| 4 | **`ConditionStep` 的非 If 兜底分支保留** | 删 Switch 分支后 `else` 兜底仍在（建一个 `BranchType.If` 的「默认分支」）。这是为「非 If 型条件算子」预留的入口，当前无算子命中，但与「保留枚举」的处置口径一致 |
| 5 | **`MaxIterations` 不可从 UI 配置** | 本轮只做了「常量具名化 + 达上限报错」，未把上限暴露成图纸/算子参数。默认 9999 对绝大多数场景足够；若现场需要更细粒度控制，需产品侧另行设计 |
| 6 | **`[E8]` ④ 用反射改 `MaxIterations` 而非图纸配置** | 断言里直接 `((CompiledWhileNode)NodeLookup[...]).MaxIterations = 5`，是为了避免真跑 9999 圈。这依赖 `NodeLookup` 为 public（已确认），不构成产品能力 |
