# 修复：方案重开后枚举配置静默丢失（平台级）

## 问题

用户要求生成「卡尺测量测试」方案（`.vms`）时，端到端验证暴露：**所有插件的 `[StepConfig]`
枚举配置，方案保存后重开会静默还原为默认值**。

影响面（不止卡尺）：图像采集的「模式」、预处理的各选项、卡尺测量的「极性/选择/插值/拟合算法」……
凡是非默认枚举，重开方案后全部悄悄变化——产线上表现为"方案 behaves 不对但看不出原因"。

## 证据链（实测）

```
生成方案 JSON：「MeasureKind": 3」 序列化正确
LoadAsync 回读：InputValues["MeasureKind"] = 3 (System.Int64)   ← 拆包成裸值
编译后插件实例：MeasureKind=Width（默认 0）                      ← 还原失败
端到端运行：5 种测量类型中 4 种按"宽度"跑，全部误判
```

## 根因

枚举以 JSON 数字落盘。`SolutionService.LoadAsync` 拆包后是**裸 `Int64`**（不是 JToken），
而 `ValueConverter.Convert` 只在 **JToken 分支**处理了枚举（`Enum.Parse`）；
裸值分支直接走 `Convert.ChangeType(Int64, 枚举)` → 抛 `InvalidCastException`
→ 被 `VisionPluginBase.ApplyConfigValues` 的宽容 `catch` **静默吞掉** → 属性保持默认值。

## 修复

`Shard\Core.Interfaces\ValueConverter.cs` 非 JToken 分支补枚举处理（一处，向下兼容）：

```csharp
if (targetType.IsEnum)
{
    if (rawValue is string strValue)
        return System.Enum.Parse(targetType, strValue);
    return System.Enum.ToObject(targetType,
        System.Convert.ChangeType(rawValue, System.Enum.GetUnderlyingType(targetType)));
}
```

- 字符串形式（手工配置/旧数据）→ 按名解析（行为不变）；
- 数值形式（JSON 回读）→ 按底层类型转换后 `Enum.ToObject` 还原；
- 其余类型仍走 `ChangeType`，行为不变；JToken 分支不动。

## 验证

```
重建宿主链 → 0 错误
生成的「卡尺测量测试.vms」端到端：LoadAsync → 编译 → 单次运行 → 采集输出
  [3.5] 5 个实例 MeasureKind 全部正确还原（PointToPoint/PointToLineDistance/CircleDiameter/Angle）
  [5]   宽度 40.0 / 两点距 240.0 / 点线距 200.0 / 圆直径 200.053 / 角度 90.0 —— 5 PASS / 0 FAIL，IsOk 全 True
冒烟回归：641 通过 / 14 失败，与基线一致（14 条均为并行任务线）
```

## 已知边界

1. **旧方案的损失已不可逆**：修复前保存的方案，非默认枚举在文件里就是正确数字，修复后重开
   即可正确还原——无需迁移数据。
2. `ApplyConfigValues` 的宽容 `catch` 保留（旧数据类型不匹配时仍跳过而非崩溃）；
   本次修复让"数字→枚举"这条**合法路径**不再落入该 catch。
3. `ValueConverter.Convert` 的口径注释要求与 `FlowCompiler.IsLinkable` 同步——本次恢复的是
   JToken 分支已有的枚举能力（灌值路径），连线检查口径未变。
