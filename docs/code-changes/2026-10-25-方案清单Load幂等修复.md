# 2026-10-25 方案清单「32768 项」事故：AppSettingsService.Load 幂等修复

## 1. 当前状态

**已闭环**：代码已修、断言已绿、被污染的配置已清、宿主已重建（`VM.Core.dll` 已带修复）、
`tools\run_gates.ps1` **14 步全绿**。宿主当前处于关闭状态（清理配置时优雅关闭，未自动重启）。

事故现象：启动自检日志逐次打印「方案清单 2048 → 4096 → 8192 → 16384 → 32768 → 65536 项」，
`VisionMaster\bin\Debug\net9.0-windows\AppConfig.json` 涨到 27.4 MB，里面 65536 条方案
（只有 2 个不同路径）与 2,097,152 条工具箱收藏（只有 1 个不同 id）。

## 2. 已做

### 2.1 根因

`Core\AppSettingsService.cs` 的 `Load()` 用 `JsonConvert.PopulateObject(json, Current, ...)` 原地填充，
目的是保住 `Current` 与 `ScadaWeb` 等嵌套对象的引用身份（模块在 `Initialize` 里拿的是这些引用）。
但 Newtonsoft 对**已存在的 `List<T>` 是追加，不是替换**——用仓里的 `Newtonsoft.Json.13.0.4` 实测：
初始 1 项，Populate 一次变 3 项，再一次变 5 项。

启动链上 `Load()` 至少跑两次（`AppSettingsService` 构造器 + `ConfigCheck.ExecuteAsync`），
于是每次启动内存里的清单翻一倍；随后任意一次 `Save()`（工具箱收藏、帮助开发章节、画布开关、
方案清单确认、系统设置保存都会存）把翻倍结果写回磁盘。

### 2.2 修法

`Core\AppSettingsService.cs`：

- 新增 `ReplaceCollectionsContractResolver`（`DefaultContractResolver` 子类）：
  对**集合属性**（实现 `IEnumerable`、排除 `string`）设 `ObjectCreationHandling.Replace`。
- `JsonOptions.ContractResolver` 接线该解析器。
- 对象属性仍走 Populate，`ScadaWeb` 等引用身份不变（新增断言钉住）。

为什么不用全局 `ObjectCreationHandling.Replace`：那会连嵌套对象一起换掉，正好破坏
`Load()` 里刻意保留的引用身份。为什么不清空两个列表了事：将来新增集合属性会静默复发；
解析器只写一次，新集合属性自动继承。

### 2.3 断言

`ScadaChecks\Program.cs` 新增 `AppSettingsLoadIdempotencyChecks()`（4 条，挂在
`SolutionListAuditChecks()` 之后）：

1. 同一实例连续 `Load()` 两次，方案清单仍是 1 项（追加会变 3 项）；
2. 同一实例连续 `Load()` 两次，工具箱收藏仍是 1 项；
3. `Load()` 不替换 `ScadaWeb` 引用（`ReferenceEquals`）；
4. `Load()` 后默认启动方案按磁盘值还原。

**为什么必须同一实例**：`new` 两个实例时每次都从空表开始，追加一次恰好等于文件内容，永远绿——
这正是缺陷能活到现在的原因。

## 5. 踩过的坑

| 现象 | 根因 | 修法 |
|---|---|---|
| 清单每次启动翻倍、配置文件涨到 27 MB | `PopulateObject` 对 `List<T>` 追加而非替换 | 集合属性走 `ObjectCreationHandling.Replace` 的 ContractResolver |
| 用 `new AppSettingsService()` 测不出来 | 新实例从空表开始，追加一次恰好等于文件内容 | 断言必须在同一实例上连续 `Load()` 两次 |
| `dotnet build ScadaChecks` 失败，报 `VisionMaster` 复制被锁 | 项目引用把宿主一起构建 | 只验 Core+Checks 时加 `--no-dependencies`（Core 先单独构建） |
| 清理完配置后几分钟又涨回去 | 有人/某脚本把 `AppConfig.json.bak-smartline` 原样拷回（SHA-256 相同） | 先确认没有外部还原，再清理；清理前备份原文件 |
| 收尾闸第一次 `audit_root` 红：`FILE  $null` | 根目录出现一个名字为空/`$null` 的瞬时条目（会话开始时 `dir /b` 也见过），随后消失 | 复跑 `audit_root.ps1` 即绿；与本次改动无关 |
| `taskkill /PID` 后新实例立刻出现 | 用户/现场重新启动了宿主 | 不要在宿主运行时反复尝试构建；重建要等它真正退出 |
