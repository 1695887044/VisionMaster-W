### #8：`PluginProvider` 的三个分类注册口——核实后改变了处置方式

清单的描述是"全是 NotImplementedException"。但核实出两条**清单没提到**的事实：

**事实 1：`CameraPlugins/LaserPlugins/MotionPlugins` 有真实消费者。**
[PluginScanCheck.cs:36](file:///e:/VM/VisionMaster-W-master/VisionMaster/Lifetime/Checks/PluginScanCheck.cs#L36) 把四个视图的 `Count` 相加作为插件总数。所以**不能直接删掉分类成员**。

**事实 2：这是文档里写明的"预留挂接点"，不是半成品疏忽。**
[设计思想.md:195](file:///e:/VM/VisionMaster-W-master/docs/设计思想.md#L195)：*"`PluginProvider` 已预留 `_motions` 仓库与 `RegisterMotion`（目前未实现），是后续接入 EtherCAT/脉冲的挂接点。"*

于是问题从"该删还是该实现"变成更精确的一问：**外部 DLL 用「相机/激光/轴卡」组名时，怎样才算行为正确？**

| 选项 | 后果 |
|---|---|
| **选定：转交模块注册表** | 算子正常出现在列表里、能拖能用，只是不带分类；另外给一条 Warn 说明分类未生效 |
| 否决：真正写进 `_cameras` | 工具面板与画布**只读 `ModulePlugins`**（[ToolViewModel.cs:100](file:///e:/VM/VisionMaster-W-master/VisionMaster/ViewModels/ToolViewModel.cs#L100)），插件会从算子列表里**消失** —— "加载成功却拖不出来"，比抛异常更难排查 |
| 否决：删掉分类概念 | 与 `PluginScanCheck` 的消费和文档里的设计意图冲突 |

**关键认识**：只"实现分类"反而是错的 —— 分类启用必须**连同消费端一起设计**（算子列表、画布端口都要认分类），只改注册端会造成插件静默不可见。所以本轮只拆掉"抛异常"这颗雷，把"分类未启用"这个事实**显式说出来**，并在注释里写清将来启用分类时必须同时改消费端。

同时修掉 `Get*` 的口径错位：注册落在模块表、而 `GetCamera` 查恒空的 `_cameras`，会变成"注册进去了却查不到"。现在两边查同一份表。

### #9：`Blueprints` 的递归填充——三份实现收敛成一份

核实发现是**三份实现**（清单只点了 `PluginTestRunner`）：

| 位置 | 口径 |
|---|---|
| [ShellViewModel](file:///e:/VM/VisionMaster-W-master/VisionMaster/ShellViewModel.cs) | 递归 ✓ |
| [HttpImageServer](file:///e:/VM/VisionMaster-W-master/VisionMaster/Services/HttpImageServer.cs) | 递归 ✓（注释里还专门写了"与 ShellViewModel 同语义"） |
| [PluginTestRunner](file:///e:/VM/VisionMaster-W-master/Engine/PluginTestRunner.cs) | **浅填（只填顶层）** ✗ |

三份口径并存必然漂移。修法不是"把第三份也改成递归"，而是**把不变量收到数据自己身上**：在 `FlowSession` 上加 `AddBlueprintsDeep`，让"Blueprints 必须含嵌套步骤"跟着 `Blueprints` 走，三份实现全删。

放在 `FlowSession` 而不是新建 helper 类，理由：① 它是 `Blueprints` 的属主；② 调用点全都是 `session.AddBlueprintsDeep(flow.Steps)` 这一种形状，读起来就是"把这个图纸装进这个会话"；③ 不新增文件。

**顺带修了断言宿主的浅填**：[ExecutionHarness.cs:48](file:///e:/VM/VisionMaster-W-master/FlowCanvasChecks/ExecutionHarness.cs#L48) 也是 `foreach` 浅填 —— 断言宿主与生产口径不一致，等于在用一个比生产更弱的语义验证生产。已改成同一份实现（实测无断言因此翻转）。

### #13：`PortBindingService` 恒为 null —— 明确删除

核对结果：`Core/ExecutionContext.cs` 声明了 `{ get; init; }` 属性，**两个构造函数都没赋值、全仓无任何赋值点** → 恒为 null。而它在 `Shard/Core.Interfaces`（插件面向的契约程序集）里暴露给插件，`RequestBinding` 是"呼出主界面绑定弹窗"这类 UI 交互能力 —— 插件一用就 NRE。

契约里没有实现方（`: IPortBindingService` 零匹配）、没有消费方。且架构上"插件弹窗选上游变量"这条路已被画布 + `VariableBindingViewModel` 取代（绑定走 `LinkReference`/`LinkedSources`）。

按用户对死契约的口径「**要么接上要么删掉**」选**删掉**：删契约成员、删实现属性、删接口文件本身。

**没有选"接上"的理由**：接上意味着让引擎反向调用 UI 弹窗，那是把 UI 依赖倒灌进执行层，与 `IUserNotifier` 注释里写的"禁止直接依赖 UI 库"直接冲突。

### #16：代码卫生

| 项 | 处置 |
|---|---|
| `FlowCompiler.cs` 的 `using System.Reflection.Metadata;` | 删（未使用） |
| `FlowCompiler.cs` 的 `using static System.Windows.Forms.LinkLabel;` | 删 —— 把 WinForms 静态成员拖进引擎，纯误引入 |
| `FlowQueryHelper.cs` 的同类未使用 using | 一并删 |
| `FlowQueryHelper` 的静态可变字段 `pluginProvider` | 改私有属性 + `Interlocked.CompareExchange` 原子发布 |

**为什么不用 `Lazy<T>`**：`Lazy` 会**缓存首次 `Resolve` 抛出的异常** —— 万一第一次调用发生在容器注册完成之前，之后每次调用都会重抛同一个异常，而本类没有任何"容器已就绪"的信号可等。`CompareExchange` 只让其中一个赢，输的一方下次调用重新尝试，行为与原来的懒解析一致，但发布是原子的（原来的 `if (x == null) x = …` 是非原子检查-赋值）。

### #11 / #14：只记录，不动（用户确认）

| 项 | 为什么不动 |
|---|---|
| #11（HTTP 会话置换 vs 请求生命周期缝） | 窗口极窄（需 UI 重编译正好落在 HTTP 请求执行期间），且改动要引入"会话引用计数"这种新机制，收益不成比例 |
| #14（`ResourceLockService._locks` 条目永不移除） | **在 `ReleaseLock` 里 `TryRemove` 会和 `GetOrAdd` 竞态**：两个线程可能各拿到一个 `ResourceLock` 实例 → 同一个资源上有两把独立信号量 → **互斥直接失效**。要安全就得加引用计数，而收益只是"每会话一个条目的内存"。风险大于收益，明确不改 |
