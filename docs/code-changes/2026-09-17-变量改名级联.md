# 2026-09-17 变量改名级联（TryRename 单一入口 + 引用侧自愈）—— SCADA S0-b

## 一、需求与决策

### 背景

S0-a 给变量发了稳定身份 `VariableId`，S0-c 建起了解析器 `IVariableRegistry`（Id 优先 / Name 兜底 / 旧连线自愈回填）。
但 S0-c 结尾留了一条明确的**已知边界**：

> 改名入口尚未统一。`IVariable` 继承自 `IOutputPort`，那里的 `Name` 是**只读**的；真正可写的 `Name` 落在
> `LocalVariableModel` / `NetworkVariableModel` 上。散落的 `model.Name = ...` 一旦漏调 `NotifyRenamed`，
> 索引就会留死键。

换句话说：**解析器已经能"按 Id 找到变量"，但没有任何一条路径能把"变量被改名了"这件事告诉那张索引和那些引用。**

这留下三个具体的坑：

| 坑 | 症状 | 不报错？ |
|---|---|---|
| 索引死键 | 直接写 `model.Name` 绕过注册表 → 索引里旧名还指着变量，新名查不到 | 是，静默 |
| 连线断链 | 老连线（`TargetVariableId == Guid.Empty`，名字即地址）改名后编译期解析不到 | 是，静默 |
| 幽灵轮询 | 网络变量轮询注册键是 `(连接名, 变量名)`，改名后旧键仍在 → 旧名继续读数、旧实例被闭包钉住不回收 | 是，静默 |

三个坑的共同特征就是**静默**——这是本阶段最想消灭的东西。

### 决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 可写变量名放哪 | 新增 `IRenameableVariable { string Name { get; set; } }`，由具体模型实现 | `IVariable : IOutputPort` 里的 `Name` 对端口而言是**定义期常量**（编译器按端口名寻址），不该被运行期改写；而变量名是"给人看的标签"，必须能改。两个诉求冲突 → 把可写 Name 单独提成接口 |
| 改名入口 | `IVariableRegistry.TryRename(variable, newName, out error)` **单一入口**：写模型 + 修索引 + 广播一次做完 | 三件事必须原子。拆成两步（写模型 → 手动 `NotifyRenamed`）就一定会有人漏第二步，而漏的后果是静默死键 |
| 入口如何认领 | 只认接口、**不 switch 模型类型** | 将来新增变量源（SCADA 外部标签、OPC 节点）只需实现 `IRenameableVariable`，改名级联一行不改——这是为 S1~S5 留的扩展点 |
| 判定顺序 | null → Trim 后空 → 与旧名 Ordinal 相同（幂等成功）→ 非 `IRenameableVariable` → `_byName` 查重（OrdinalIgnoreCase，`ReferenceEquals` 放行自命中） | 幂等必须在查重**之前**：否则"把 A 改名成 A"会因为 `_byName` 里已有 A 而被判重名拒绝 |
| 幂等是否广播 | **不广播** | 事件订阅方要做连线遍历 + 监视项重建 + 轮询重注册；没真改动还广播等于每次误触都白跑一遍全方案遍历 |
| 谁做级联 | `WorkspaceContext` 订阅**注册表实例事件** `VariableRenamed`（不是 `GlobalEventBus`） | 改名不是"公告给所有关心的人"，而是"索引改了必须通知依赖它的引用"。事件源即索引本身，订阅者与事件源同生共死（本类是单例、注册表字段只读）→ 无需退订，不引入生命周期问题 |
| 老连线怎么办 | 级联时对老连线（`TargetVariableId == Guid.Empty` 且名字≈旧名）做**一次性自愈**：改 `TargetPortName` + 补 `TargetVariableId` | 迁移不能要求用户重新连一次线。自愈后下次保存即落盘，迁移只发生一次 |
| 新连线怎么办 | 只刷新 `DisplayAddress`（纯展示串） | 新连线按 Id 寻址，改名后天然不断链 |
| 监视项判重 | `IsWatchingGlobalVariable(id, name)`：Id 优先、Id 为空退回按名 | 改名后仍认得出是同一个变量；旧数据（Id 为空）行为与从前一致 |
| 通信轮询重注册 | 用 `e.OldName` **注销旧键**，再按新名重注册（**新建实例**） | 不能用现成的 `Unregister(nv)`——它读的是 `nv.Name`（此时已是新名），拿新名去注销旧键等于没注销 |
| 树展开态 | `GlobalVariableViewModelBase.RefreshTree` 展开态改按 **VariableId** 记忆，Id 为空退回按名 | 按名字记的话，改名后新树节点与旧键对不上，展开中的数组变量会莫名自动折叠 |

### 一个关键论证：运行期（Running）改名安全，无需运行互锁

这是设计时最需要先想清楚的一点——**要不要给改名加一把"运行中禁止改名"的锁？** 结论是**不需要**，论证如下：

1. 编译产物持有的是 `IVariable` **对象引用**，不是名字。`InputPort` 取值链路是 `_linkedSource.Value`
   （见 [InputPort.cs](file:///e:/VM/VisionMaster-W-master/Shard/Core.Interfaces/DataPort/InputPort.cs#L235-L238)），`Name` **全程不在取值链上**。
2. `DisplayAddress` 是**纯展示字段**，编译器不得读取（这是 S0-c 就定下的纯度契约）。
3. `TryRename` 内部在 `_gate` 锁内完成索引改写，**锁外**才抛事件 → 取值线程不会撞上未完成的索引状态。
4. 轮询重注册走 `RegisterVariable` 的"摘旧 handler → 挂新 handler → `RequestPollPlanRebuild`"，
   旧变量实例在注销时被解绑，新实例接上；期间最坏情况是一次多余/一次缺失的轮询周期，不会读到错误地址。

因此**改名只在"索引 + 展示 + 注册键"这一层动**，运行中的数据面不受影响。加一把运行互锁反而制造了
"用户想改个显示名还得停机"的伪约束。

## 四、已知边界

1. **级联只对"方案树里的引用"负责**。没挂进任何流程、也没进监视列表的孤立 `LinkReference`，改名后按旧名落空——
   这是刻意的：级联遍历的是方案树（`CurrentSolution.Flows` + `WatchItems`），而不是全内存对象图。
   真正在用的连线都挂在流程里（见 `[K]`）。
2. **老连线的自愈是"用一次才落盘"**：改名级联会把 `TargetVariableId` 补上，但**保存方案**才真正写进文件。
   改名后不保存直接关软件，下次打开仍是老连线（仍能工作，只是继续走名字兜底）。
3. **`GlobalVariableName` 字段保留**：仍是旧数据的唯一可读键，`VariableId` 为 `Guid.Empty` 时全部退回按名路径。
   两条路径的判重口径必须一致（级联与 `IsWatchingGlobalVariable` 都按 `OrdinalIgnoreCase`）。
4. **`MonitorViewModel` 新增了一条 `VariableRenamed` 订阅，但它没有 `IDisposable` / `Activate` / `Deactivate`**，
   与其它面板 VM 的同类订阅泄漏问题归为一类（旧遗留 P3）。当前 `VariableRenamed` 事件源（`WorkspaceContext` 单例）
   与订阅者同生命周期，暂不构成实际泄漏；一旦面板 VM 改为可多次创建，必须一并收编。
5. **`DisplayAddress` 是纯展示字段，编译器不得读取**。级联只改这一个字段（加老连线的寻址键），
   若将来有人在编译器里读它，改名又会长出新的坑。
6. **`TryRename` 不做方案级联的"回滚"**：级联过程中若某个引用侧抛异常，索引已经改成新名（模型也已写入），
   不会退回旧名。当前级联实现全为纯内存字段赋值、无 IO，实际触发不了；将来若级联里加 IO，需要重新审视。
7. **网络变量轮询重注册是"注销 + 新建"，不是原地改键**：一次改名会让该变量的轮询实例换一个对象。
   这是为了不把旧实例的闭包/事件处理器带过来（见 `[L]` 的"重注册登记的是新实例"）；代价是极短暂的空窗。
8. **`ScadaChecks` 里两处白盒探针依赖 `AdvancedCommunicationManager._registeredVariables` 私有字段名**，
   字段改名会让断言静默失效（`IsRegistered` 返回 false → 断言反而"通过"）。管理器目前没有"查询已注册变量"的公开 API，
   若后续开放，应改用公开 API。
