# 2026-09-24 Blob 缺陷检测插件（Plugin.BlobDetect）

## 1. 需求与决策

### 1.1 需求来源

这是「补齐视觉核心工具链」的一步：仓库已有图像采集、图像预处理、ROI、脚本、C# 脚本、数据记录、导出、上报等能力，
但**缺少最基础也最常用的缺陷检测算子**。用户选定「缺陷检测」方向，规格在开工前已逐条确认完毕，
本次任务只负责按规格实现，不改变设计。

### 1.2 六项已确认设计决策（照录规格，不得更改）

| # | 决策项 | 结论 |
| --- | --- | --- |
| 1 | **形态** | 工程名 `Plugin.BlobDetect`，插件名 `Blob 缺陷检测`，分组 `缺陷检测` |
| 2 | **二值化** | 三方式：固定阈值（MinGray/MaxGray）、自动阈值（`binary_threshold` + `max_separability`）、动态阈值（`var_threshold`）；统一用「检测目标：亮缺陷/暗缺陷」映射到各方式自己的极性参数 |
| 3 | **判定规则** | `IsOk = !(DefectCount > MaxDefectCount \|\| MaxArea > MaxSingleArea)`；NG 时把原因写进基类 `ErrorMessage`，但**不判 Fail**（NG 是正常结果） |
| 4 | **检测区** | 本插件处理**整幅输入图**，不做 ROI；检测区依赖上游 ROI 插件（如 `Plugin.CreateRoi`）先裁好 |
| 5 | **输出端口** | 固定 7 个：`DefectImage(HImage)`、`Defects(HRegion)`、`DefectCount(int)`、`MaxArea(double)`、`IsOk(bool)`、`CenterRows(HTuple)`、`CenterCols(HTuple)` |
| 6 | **形态学** | 开运算半径 `OpenRadius`、闭运算半径 `CloseRadius`，**填 0 表示跳过该步** |

算法流程（Halcon 算子序列，与规格一致）：

```
count_channels → 彩色 rgb1_to_gray / 灰度 copy_image
→ 按 ThresholdMode + DetectTarget 二值化，得到 Region
→ OpenRadius>0 则 opening_circle；CloseRadius>0 则 closing_circle
→ connection 拆连通域
→ select_shape 按 'area' 筛选 [MinArea, 1e7]
→ count_obj 取个数；area_center 取面积与中心坐标（行/列用 _ 丢弃）
→ tuple_max 取最大面积
→ 判定
→ 画标注图：dev_display 底图 + 缺陷描边红圈 + dev_disp_text 左上角写结果
```

参数四区：① 二值化 ② 噪声清理（`MinArea`）③ 形态学（`OpenRadius`/`CloseRadius`）④ 判定规格（`MaxDefectCount`/`MaxSingleArea`）。

### 1.3 规格里两处表述不一致 / 歧义，及本次处理

规格本身是自洽的，但有两处细节在文字上互相牵动，这里记录**处理方式与理由**，便于复核：

**（a）标注图的底图是「原图」还是「灰度图」？**

- 输出端口表写的是「标注图（**原图**上把缺陷圈红 + 左上角写判定结果与个数）」；
- 算法流程写的是「dev_display **灰度图** + 缺陷描边红圈 + …」。

两者仅在「输入是彩色图」时才有差别（灰度输入时原图==灰度图）。
本次选择**显示原图（彩色输入保留彩色）**，理由：标注图是给人看的，彩色信息更利于现场判断；
且端口表正是「输出端口的定义」，权威性更高。已记入「已知边界」。

**（b）「检测目标」在固定阈值下要不要显示？**

规格把 `DetectTarget` 列在「二值化」区，同时又要求「切换时界面上**只显示该方式自己的参数**」。
固定阈值方式的极性是**由灰度区间本身表达**的（取哪一段就是找什么），此时 `DetectTarget` 是死控件。
本次选择：**固定阈值下隐藏「检测目标」**（`ShowDetectTarget = ThresholdMode != Fixed`），
在自动/动态阈值下显示（这两个方式才有 `'light'/'dark'` 极性参数）。
这是一处对歧义的取舍，若要改成「始终显示」只需改一行 Visibility 绑定。

### 1.4 关键实现决策（Why，均为仓库既有范式）

1. **端口与参数全部编译期存在**：7 个输出端口 + 1 个输入端口都是静态属性，`[StepConfig]` 参数由基类随
   `InputValues` 存盘，不写任何注册代码（`Directory.Build.targets` 自动投递 `Modules\`，宿主扫描加载）。
2. **算法核心与界面解耦**：`ExecuteBlobCore(src, logger)` 一份实现，配置预览与流程运行共用，保证「所见即所得」。
3. **资源所有权**：
   - 自建的中间 HALCON 对象登记进 `temp` 列表，`finally` 统一释放；
   - 交出去的 `AnnotatedImage`/`Defects` 用 `new HImage(obj)`/`new HRegion(obj)` 生成**独立句柄**后再移交端口，
     已实测「包装后释放原对象」不影响被包装结果（见 3.5）；
   - 输入图 `src` 全程只读借用，绝不释放。
4. **标注图渲染走离屏 `buffer` 窗口**：HALCON 写文字（`disp_text`）必须依附窗口字库，没有纯算子路径。
   照搬仓库 `Plugin.ImageScript/HDevDisplayBackend` 已验证的做法：`open_window('buffer')` 离屏渲染 →
   `dump_window_image` 回读成 `HImage`。窗口按「图像尺寸」缓存复用（HALCON 反复 open/close 有 #9302 死锁风险），
   每实例一把锁，`Dispose` 时关闭；渲染失败**只降级丢 `DefectImage`**，绝不把成功的检测判成失败。
5. **参数归一化（静默夹取）**：算子上传前把界面参数夹进安全区间（`NormalizedParameters()`），
   固定阈值上下限填反了自动排序。方案文件可能来自老版本或被人手工改过，这一步保证「配置坏了最多结果不对，不会炸流程」。
6. **开轮重置所有非 `IDisposable` 端口**：基类 `AutoDisposeRoundOutputs` 只回收 `HImage/HRegion`，
   `int/bool/double/HTuple` 端口需显式清零，否则本轮失败时下游读到上一轮脏数据（已实测，见 3.5 `[EMPTY]`）。
7. **NG 不写 `Fail`**：NG 是正常业务结果，`Success` 保持 true，只把中文原因写进 `ErrorMessage`。

```csharp
// 坑 1：rgb1_to_gray 对单通道图会报错，必须先 count_channels 判断
HOperatorSet.CountChannels(src, out HTuple channels);
if (channels.I == 1)      HOperatorSet.CopyImage(src, out gray);
else if (channels.I == 3) HOperatorSet.Rgb1ToGray(src, out gray);
else { result.Failed = true; result.FailMessage = $"不支持的图像通道数：{channels.I}…"; return result; }

// 二值化：三种方式各自的极性参数，统一由 DetectTarget 映射
case ThresholdMode.Auto:
    HOperatorSet.BinaryThreshold(gray, out region, "max_separability", p.Polarity, out _);
case ThresholdMode.Dynamic:
    HOperatorSet.VarThreshold(gray, out region, p.VarMaskWidth, p.VarMaskHeight,
        p.VarStdDevScale, p.VarAbsThreshold, p.Polarity);

// 坑 2：select_shape 面积上限必须写，否则整块背景会被当成一个超大缺陷
HOperatorSet.SelectShape(connected, out HObject defectsObj, "area", "and", p.MinArea, 1e7);

// 坑 3：23.05 没有 area 算子，取面积用 area_center + _ 丢弃圆心；空元组不能 tuple_max
HOperatorSet.AreaCenter(defectsObj, out HTuple area, out HTuple rows, out HTuple cols);
result.MaxArea = (result.DefectCount > 0 && area.Length > 0) ? area.TupleMax().D : 0;
```

## 6. 通用性三项优化

### 6.1 需求与决策

承接第 5 节自认的三条短板，本轮一次性解决：

| 优化 | 要解决的问题 | 做法 |
| --- | --- | --- |
| ① 灰度直方图 | 固定阈值默认值只能"猜" | 配置视图画当前预览图像的灰度直方图（矢量、随窗口缩放），并标出固定阈值上下限 |
| ② 阈值自适应 | `MinGray/MaxGray` 隐含 8 位假设，uint2 图差 16 倍 | 用 `min_max_gray` 取**实际灰度范围**换算阈值（不按像素类型硬编码） |
| ③ 面积自适应 | `MinArea/MaxSingleArea` 有分辨率依赖 | 以 640×480 为基准，按当前图像**面积比例**缩放 |

**触发规则（硬约束，不得更改）**：

- **自动触发**：加载/刷新预览图像时，**仅当全部参数仍等于出厂默认值**才自动适配一次，并在信息栏写明发生了什么；
- **绝不覆盖用户改过的值**：任一参数一旦不等于出厂默认值，自动适配完全跳过，一个字节都不动；
- **手动触发**：参数面板提供「按当前图像重新适配」按钮，任何时候都能重来一次。

**为什么"只在出厂默认值时自动触发"是关键取舍**：工业现场把参数当作"我调好的结果"，软件若在换图/重开方案时
静默改掉它，操作员会认为"参数自己变了 = 软件故障"，比"参数不理想"严重得多。所以自动适配只在
"用户根本没动过（全是出厂默认）"时才敢做——此时改动不会覆盖任何人的劳动成果；用户一旦调过，
就只由他主动按按钮来适配。这也是把"出厂默认值"抽成一处常量、并用容差比较的原因：
判定基准写歪了就会出现"没改过却判成改过 / 改过却判成没改过"。

### 6.3 关键代码片段

**（a）直方图分档与归一化**（`GrayHistogram.TryCompute` 节选）：

```csharp
// 实际灰度范围用 min_max_gray 度量，不按像素类型猜：12 位相机常只用 0~4095，
// 而 uint2 存储范围是 0~65535，两者差 16 倍，硬编码必错
HOperatorSet.MinMaxGray(domain, gray, 0, out HTuple minTuple, out HTuple maxTuple, out HTuple _);

// 分档 = 覆盖实际灰度范围所需档数，夹在 [8,256]：
// byte 整幅恰好 256 档；uint2 的 4096/65536 档被压到 ≤256（控件只有几百像素宽，再多也画不出）
int buckets = (int)Math.Clamp(Math.Ceiling(gMax - gMin + 1), 8, MaxDisplayBuckets);

// byte/uint2 走 gray_histo（按规格）→ 再按实际范围重新聚合；其它类型走 gray_histo_range
HOperatorSet.GrayHisto(domain, gray, out HTuple absHisto, out HTuple _);
bins = Rebucket(absHisto.ToDArr(), gMin, gMax, buckets);

// 归一化到 [0,1]：控件只关心分布形状，最高档画到满高
double peak = bins.Length > 0 ? bins.Max() : 0;
if (peak > 0) for (int i = 0; i < bins.Length; i++) bins[i] /= peak;
```

**（c）阈值/面积自适应换算公式**（`TryAdaptCore` 节选）：

```csharp
// 阈值：暗缺陷取灰度范围靠暗侧的一段，亮缺陷对称地取靠亮侧的一段（分位 0.25，依据见常量注释）
double range = Math.Max(grayMax - grayMin, 1);              // 均匀图防"零段"
if (DetectTarget == DetectTarget.Dark) {
    newMinGray = grayMin;
    newMaxGray = grayMin + DarkSideFraction * range;        // 最暗的 25%
} else {
    newMinGray = grayMax - BrightSideFraction * range;      // 最亮的 25%
    newMaxGray = grayMax;
}

// 面积：以 640×480 为基准，按面积比例缩放，保持"滤噪点 / 判定规格"语义
double scale = width * (double)height / (BaselineWidth * BaselineHeight);
newMinArea = DefaultMinArea * scale;                        // 30 * scale
newMaxArea = DefaultMaxSingleArea * scale;                  // 100 * scale
```

### 6.5 已知边界

1. **直方图的横轴是"实际灰度范围"而非固定 0~255**：窄分布图（如 102~206）会被横向拉伸到整宽，
   看得更清；代价是阈值若设在范围之外，标记会夹在两端（不画到控件外）。这是有意的取舍。
2. **直方图线性归一化会被"占绝对多数的背景峰"压扁**：当背景像素远多于缺陷像素时，缺陷那一段在图上很矮。
   这忠实反映分布，但小缺陷段的细节需要靠阈值标记位置推断，本轮未做对数/截断显示。
3. **自适应分位 25% 是"可用起点"，不是"正确值"**：见常量注释的依据。它在自带样图上恰好得到
   第 5 节人工调出的 128，属巧合而非目标——现场仍需按直方图与预览微调。**这是本轮最需要人工复核的一点。**
4. **用户改过值后不再自动适配是故意设计**（见 6.1）。副作用：换产品换图后必须手动点一次「重新适配」，
   或把参数改回出厂默认值才会恢复自动。这是"安全优先"的取舍。
5. **自动适配会作用于"参数恰好仍是出厂默认值"的方案**：若某个已保存方案的参数从未被改动过，
   打开它并加载图像时会被自动适配改写。按规格这是允许的（"加载/刷新预览图像时"），但值得现场确认是否符合预期。
6. **直方图计算只在 `RefreshPreview` 里做**：与既有预览共用 `SchedulePreview` 的 200ms 防抖 + UI 线程投递，
   `RunAlgorithm` 零新增开销。但既有代码有 `SrcImage.ValueChanged → SchedulePreview` 订阅，
   运行实例若也收到图像的赋值，理论上也会触发一次配置态刷新（连带直方图计算）——这是**上一轮既有行为**，
   本次未改动其触发路径，仅在记录中标注。
7. **非整数图走 `gray_histo_range` 兜底**：`byte/uint2` 用规格点名的 `gray_histo`；`real/int4` 等
   改用 `gray_histo_range`，以免 `gray_histo` 生成天文数字长度的数组。若两种算子都失败，
   退化为"不显示直方图 + 信息栏说明原因"，检测本身不受影响。
8. **直方图起点与算法灰度路径一致**：使用与 `ExecuteBlobCore` 同一份 `TryToGrayImage`（1 通道复用、
   3 通道 `rgb1_to_gray`、其它通道判失败），不会出现"检测能跑、直方图不能算"的不一致。
9. **未纳入自动冒烟**：与上一轮相同，`FlowCanvasChecks` 不覆盖本插件；本轮算法验证仍靠
   "仓库外临时控制台真跑 + 渲染差分"，该控制台已删除、不可复现。后续若要长期守护，
   建议把「surface_scratch 直方图 range=102~206 / 自适应 102~128 / 面积 31.5」固化成正式断言。

## 7. 修复：标注渲染的 HALCON 源对象泄漏（跨插件发现）

### 7.1 怎么发现的

在开发「卡尺测量」插件（`Plugin.CaliperMeasure`，见另一份记录 `2026-09-25-卡尺测量插件第一批.md`）
时，作者为遵守本项目"HALCON .NET 是引用计数语义"的既有教训做了一组内存观测实验，结论是：

> `new HImage(obj)` 生成的是**独立句柄**，但 `obj` 本身是**源对象**；
> **只释放一边会泄漏**（实测 500 次不释放源对象约漏 160MB）。

随后它比对同仓库写法时发现：`Plugin.BlobDetect\AnnotationRenderer.cs` 的 `DumpWindowImage`
回读处**只做了包装、没有释放源对象**。按当时"不修改其他插件"的任务约束，它没有直接改这个文件，
而是在自己的开发记录里把问题上报了出来。

### 7.2 复核与影响判断

本次修复前**独立复核确认该问题真实存在**（对照两处代码）：

| 插件 | `DumpWindowImage` 之后 | 结论 |
| --- | --- | --- |
| `Plugin.CaliperMeasure\AnnotationRenderer.cs` | `var result = new HImage(shot); shot.Dispose();` | ✓ 已规避 |
| `Plugin.BlobDetect\AnnotationRenderer.cs` | `return new HImage(shot);` | ✗ 源对象 `shot` 未释放 |

**影响范围不止"配置态预览"**：本插件的 `AnnotationRenderer` 在**流程运行时每轮也要渲染标注图**
（即 `DefectImage` 端口的值）。因此在长期运行的产线上，这条引用会随运行轮数持续累积。

另经全目录检索确认：`DumpWindowImage` 在本插件中**仅此一处**，不存在第二个同类漏点。

### 7.3 改动

`Plugins\Plugin.BlobDetect\AnnotationRenderer.cs`（唯一改动文件，1 处）：

```csharp
// 改前
HOperatorSet.DumpWindowImage(out HObject shot, win);
return new HImage(shot);

// 改后
HOperatorSet.DumpWindowImage(out HObject shot, win);
var result = new HImage(shot);
// HALCON .NET 是引用计数语义：new HImage(shot) 生成的是独立句柄，但 shot 本身是"源对象"，
// 不释放会留下一个引用计数（同期在卡尺插件上实测：500 次不释放源对象约漏 160MB）。
// 本插件的标注渲染在配置预览与流程运行都会走到，长期运行会持续累积，故包装后立刻释放。
shot.Dispose();
return result;
```

### 7.4 验证结果

```
dotnet build Plugins\Plugin.BlobDetect\Plugin.BlobDetect.csproj -v m -clp:ErrorsOnly
→ 已成功生成。 0 个警告 0 个错误

dotnet run --project FlowCanvasChecks\FlowCanvasChecks.csproj -c Debug --no-build
→ 通过: 610  失败: 14          （与修复前完全一致，无回退）
→ 全文 Blob 匹配条数: 0        （冒烟不覆盖本插件）
```

那 14 条失败全部来自**并行任务线**（相机插件 1 条 + 线序检测 13 条），与本次改动无关。

### 7.5 已知边界（本次修复后仍存在）

1. **本次只修了这一处，未做全插件的 HALCON 释放路径审计**：修复范围严格限定为 CaliperMeasure
   作者已实测确认的那一处（用户本轮选择的是"先修泄漏"，不是"全面排查"）。若要系统性审计
   （`temp` 列表、端口包装对象、控件缓存等），应作为独立任务进行。
2. **"泄漏"的准确表述**：严格说是"**依赖 GC/finalizer 延迟释放、峰值内存偏高**"，而非永久不可回收。
   但配置预览会随参数拖动频繁刷新、流程运行是持续性行为，延迟释放足以在生产环境累积成可观测的
   内存增长，因此按缺陷处理。
3. **该修复未经"长跑内存观测"复验**：改动本质是把已有的释放语义补齐（与 CaliperMeasure 同构），
   编译与冒烟均通过；但本次**没有重跑"连续 N 轮观察 WorkingSet"的实证实验**。如需硬证据，
   建议把该实验固化成正式断言（与 6.5 第 9 条同一诉求）。
