# 流程引擎优化：A1 循环内 If 失效 / A2 可观测 / A3 会话互斥 / B1 零查找 / B2 通知风暴 / B3 停止卡顿

日期：2026-09-22

## 一、需求与决策

背景：对流程引擎（`FlowCompiler` 编译期 + `Compiled*` 运行期栈式 DFS）做架构评审，识别出 A/B/C/D 四组问题。用户拍板本轮只做六项，验证方式选定「补进 FlowCanvasChecks 断言」——即**先造出能复现问题的红灯，改完再变绿灯**，不留口头结论。

明确排除在本轮之外：C2 增量编译与插件实例池、D1 FlowCompiler 拆分、DAG 依赖图并行、B4 可配置节拍。

### A1：循环体内的 If 分支静默失效（正确性 P0）

- **根因**：`CompiledWhileNode` / `CompiledForNode` 旧实现用 `foreach (var child in body) child.RunAndGetNext(context);` 逐个跑循环体，**把返回值丢掉了**。而 `CompiledIfNode` 唯一的交接口就是这个返回值——它把选中分支的第一个节点返回出去，自己不做任何"我选了谁"的副作用记账。于是循环体里的 If：条件照算、不报错、不写日志，分支里的算子**一个都不执行**。
- **修法**：抽公共静态执行器 `CompiledNode.RunSequence(nodes, context, yieldToControlFlow)`，内部用 `Stack<IEnumerator<CompiledNode>>` 承接每个节点的返回值并压栈续跑，While/For 一律改用它。`yieldToControlFlow=true` 给循环体（遇 Break/Continue/Return 立即让出并把状态带回上层），`false` 给顶层（就地清零 + `Logger.Warn`，防止顶层散落一个没人接的 Break）。
- **为什么统一而不各写一份**：控制流的语义必须只有一处定义。以前 If 走返回值、循环走 foreach，两套模型交界的地方就是这种"看起来跑了一半"的坑。

### B1：运行时反查图纸 O(N²) → 零查找

- **根因**：`Compiled*` 节点每上报一次运行状态，都要拿 `StepID` 去 `session.Blueprints` 里线性扫一遍找对应 `StepModel`。100 步流程一轮 ≈ 2 万次比较，且这个开销按节点数乘步骤数放大。
- **修法**：编译期在 `CompiledNode` 上挂 `Blueprint`（`StepModel` 反向指针），`FlowCompiler` 六条装配分支全部写入；运行期直接 `node.Blueprint.XXX`，查找次数归零。
- **代价**：编译产物持有图纸引用，生命周期与 `CompiledFlow` 一致——本来就是同生共死，无额外泄漏面。

### A2：容器节点不报错、不亮、不计耗时

- **根因**：只有 `CompiledPluginNode` 调 `UpdateStepRuntimeState`，If/While/For 容器跑完状态还是 `Ready`，画布上不高亮、耗时徽章空白，出了故障无从下手。
- **修法**：容器节点同样走 `UpdateStepRuntimeState`（Running → 移交 `session.FocusedStep` + `BeginTiming()`；Success/Failed → `EndTiming()`；Skipped 且是自己 → 释放焦点）。前置判断 `context is ExecutionContext { CurrentSession: not null }`，保证无会话的裸执行上下文不炸。

### A3：会话级启动互斥（用户中途改定的落点）

原提案是"给步骤加资源声明字段 + 属性面板配置"，用户否掉，改为**只做会话级互斥 + 修锁服务自身隐患，不新增字段、不做 UI**。

- **互斥**：`FlowEngineService` 启动前以 `StartLockKey(session) => $"FlowSession:{session.SessionID}"` 向 `ResourceLockService` 抢锁；抢不到就 `Logger.Warn("流程 X 已在运行中，忽略重复的启动请求")` 并直接返回——连点启动不再叠两套循环互写同一批 `StepModel`。单次执行同理会吼"忽略重复的单次执行请求"。
- **放锁顺序**：`finally` 的**最后一行**才 `ReleaseSession`，且必须晚于循环线程真正退出，否则"锁已放、线程还在"的窗口期内重复启动照样能挤进来。
- **锁服务自身隐患**：`ResourceLockService` 原先存在 Semaphore 释放溢出（`Release()` 超过 `AvailableWaitHandle` 计数会抛 `SemaphoreFullException`）与重复登记路径，本轮一并修掉。

### B2：运行状态通知风暴 → 记名 + 批量补发

- **根因**：运行状态 setter 里发 `RaisePropertyChanged(string.Empty)`。空串在 WPF 里等价于"我所有属性都变了"，而 `FlowModel.OnStepPropertyChanged` 正是靠"收到步骤通知"判定语义变更 → `Version++` → **整个流程重新编译**。跑一轮流程 = 每步至少一次全量重编译。
- **修法**：`StepModel.BatchRuntimeNotify()`（深度计数 + `RuntimeNotifyScope`），内层只记名不发，最外层退出时按真实属性名补发一次；`BeginTiming/EndTiming/ResetState` 各自包 `using (BatchRuntimeNotify())`。`ResetState` 再加"本来就是干净的直接 return"闸门，避免复位空转。
- **纪律**：运行状态字段一律 `[RuntimeState]` 名单化，通知只许带真名。

### B3：停止卡顿——把三秒等待挪出绑定锁

- **根因**：`StopSessionGracefully` 要等执行循环退出（最长 3 秒），而它原先被 `_lock` 抱着；`_lock` 同时是 `EnableCollectionSynchronization` 交给 WPF 的绑定同步锁。结果 UI 等循环退，循环等 UI 手里的锁，只能干等到超时。
- **修法**：拆成两把锁。`_registryLock` 串行化"等旧循环退出 → 摘旧 → 挂新"整段（可以长时间持有）；`_lock` 只包 `Add/Remove/Clear/Snapshot` 这几微秒。

### 本轮额外发现并修掉的越界问题

1. **`GetSessionById/GetSessionByName` 裸枚举**（E6 红灯抓出）：这两个查询方法不带锁直接 LINQ 扫 `ActiveSessions`，而增删都在 `_lock` 内。`EnableCollectionSynchronization` 只替 WPF 的 `CollectionView` 兜底，**不替我们自己代码里的 LINQ 兜底**——后台线程一 `Add`，UI 线程这次枚举就可能抛 `Collection was modified`。修法：查询也进 `_lock`（只做一次线性查找，几微秒，符合"锁里绝不等待"的纪律）。
2. **`UI/Controls/Behaviors/DataGridSelectionBehavior.cs:83` CS1061**：与本次范围无关的存量编译错误，卡住整个解决方案，经用户批准就地做最小修复。

## 四、已知边界

1. **A3 只做到"同一会话不许重入"**。"两个不同会话抢同一台相机/同一张图"仍需步骤级资源声明（本轮按用户决定不做），所以 `ResourceLockService` 目前只用 `FlowSession:{id}` 这一类键。
2. ~~**ForStep 的 `LoopCount` 引脚未接**~~ **已闭环（同日）**：见 `2026-09-22-补ForStep_LoopCount画布连线.md`——画布上变量定义节点长出「值输出脚」可直接拖出 `LinkKind.RuntimeVariable` 线，For 参数弹窗新增「选择数据源」入口，异层降级为隐形线，`[R]` 22 + `[E7]` 12 条断言固化。
3. **`yieldToControlFlow=false` 的顶层散落 Break 只 Warn 不报错**。图纸校验（`CheckLinkOrder` 那条线）里没有"控制流节点必须在容器内"这一项，需要时再补，不在本轮。
4. **E4/E6 是真实并发时序断言**，靠事件闸门而非 `Thread.Sleep` 构造窗口，但若机器被严重抢占，"未卡死"的 5 秒上限理论上仍可被拖穿（当前实测毫秒级）。
5. **桩插件不声明任何输入端口**。`InputPort<T>.IsRequired` 默认 `true`，且 `VisionPluginBase.EnsurePortsDiscovered()` 只反射 public **属性**——断言桩为了避开 `[参数缺失]`/`[端口声明错误]` 两条编译期检查而刻意无输入口，别把它当算子开发范例抄。
6. **A2 的状态上报依赖 `ExecutionContext.CurrentSession`**。任何绕过 `FlowEngineService` 直接 `CompiledFlow.Run(ctx)` 的用法（例如脚本试跑）不会有点亮与耗时——这是有意的降级，不是 bug。
