# 2026-09-17 变量稳定身份（VariableId）落地 —— SCADA S0-a

## 一、需求与决策

### 背景
SCADA/HMI 画布组态与"变量改名"是**互相依赖**的两件事：

- 画布图元要把自己绑到某个变量上，这个绑定要随方案落盘、要能在软件重启后恢复；
- 而变量名是用户随时可改的标签。

现状是**一切引用都按变量名寻址**（`LinkReference.TargetPortName`、`WatchItemModel.GlobalVariableName`、监视栏 `Global.xxx` 输入串）。于是改名即断链，级联又永远补不齐——这正是《变量管理系统-设计说明与交接文档》里列为 M4 前置的那条。

### 决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 身份载体 | `Guid VariableId` | 32 字节、跨方案唯一、不受改名/换连接/改类型影响；整数自增 Id 在"方案合并/复制粘贴"场景下会撞号 |
| 放在哪一层 | `IVariable` 接口上的只读 `Guid VariableId { get; }` | 连线、监视项、SCADA 绑定三类消费者拿到的都是 `IVariable`，接口上可见才不用到处转型 |
| 实现类可写 | `LocalVariableModel` / `NetworkVariableModel` 上是 `{ get; set; }` | 反序列化与旧方案迁移必须能写；接口只暴露 getter，防止业务代码随意改身份 |
| 旧方案兼容 | DTO 缺字段 → `Guid.Empty` → 持久化层补发新 Id | 不能让老 `.vms` 加载失败；补发的 Id 在**下一次保存**时随 DTO 回写，迁移只发生一次 |
| 引用侧是否同步改 | **本次不改** | 引用侧（`LinkReference` / `WatchItemModel`）改存 Id 涉及编译器取数路径与旧工程兼容，属 S0-b/S0-c 的范围。本次只把"身份的真相源"建起来，先保证它稳定、可往返 |

### 一个容易被忽略的点：为什么 Id 要随 `VariableDto` 走，而不是"加载时按名字现算"
若按名字现算（哈希），改名就会换 Id，等于没做；若加载时新生成，那每次打开方案的 Id 都不同，SCADA 里已存盘的绑定就永远匹配不上。所以 Id **必须**是持久化字段。

## 四、已知边界

1. **Id 目前尚无消费者**：连线、监视项、SCADA 绑定仍按变量名寻址，改名仍会断链。Id 的落地只是把地基铺好——S0-b（改名级联）与 S0-c（绑定解析器）才让引用侧受益。
2. **压力测试测的是内存搬运**，不含 JSON 落盘/读盘。真正的磁盘往返要等 S1 的画面文档序列化一起压（届时把 `SolutionModel` 的 JsonConvert 往返纳入断言）。
3. **无 Id 去重**：若脏数据里出现两个相同 Id 的变量，`Restore` 不会报错也不会合并。等到 S0-c 的解析器建立 Id→变量索引时再补唯一性校验（届时才真正需要"按 Id 找变量"）。
4. **`VariableNode.Name` 仍非 INPC**：变量管理树里改名不通知 UI（现状如此，本次未动）。属于 S0-b 一起处理的范围。
