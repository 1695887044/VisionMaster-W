## 一、需求与决策

### 1. 需求

`Shell.xaml` 里"开发者"是**写死的字面量**，全软件没有任何用户系统——谁都能改配方、改权限本身。本阶段要回答四件事：

1. **谁能登录、登录后是几档**（身份从哪来、怎么存）；
2. **"这个按钮不是谁都能按的"怎么声明、在哪判**（这是权限体系的全部价值所在）；
3. **空闲多久自动登出、登出后界面怎么退**（现场人走了不锁屏，等于没有权限）；
4. **谁在什么时候按了哪个按钮、值从多少改到多少**（事后追责要拿得出的凭证）。

### 2. 决策清单

#### R：角色模型与判定（领域层）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| R-1 | 角色档位 | **固定三档**：`Operator(1) < Engineer(2) < Administrator(3)` | 角色表（"新建角色、勾权限点"）是 MES / 数据库类软件的模型，要一套权限点清单 + 一套角色-权限映射 + 一套管理界面；组态画面的权限需求只有一句话——"这个按钮不是谁都能按的"。Operator / Engineer / Administrator 是工业 HMI 几十年的事实标准，现场一看就懂 |
| R-2 | `Undefined(0)` | **非法值**，不是"比操作员更低的一档" | 它是 `default(ScadaRole)` 的落点，存在的唯一理由是让"文件里存了个不认识的数值"（高版本存、低版本读）能被识别出来。判定侧遇到它**一律拒绝**（fail-safe）——放行等于把"一个不认识的数字"解释成"谁都能按"，那是**静默的权限放大** |
| R-3 | 未登录 | = `Operator`，**不是零权限** | 现场大量"开机自动运行、无人值守"的画面：没人登录，若未登录=零权限，那些画面上的加载钩子（初始化变量、切首页）会被全部挡掉，**软件等于开不起来**。密码保护的是高权限操作，不是"在场" |
| R-4 | 不限制 | `RequiredRole == null` | 绝大多数图元的常态（没配过就是 null）。它同时是**"旧 .vms 文件不用迁移"**的实现基础 |
| R-5 | 比较口径 | 高角色**包含**低角色（`Satisfies` = `>=`） | 管理员去按一个"工程师按钮"还要先降级，是纯添堵。这条口径也决定了判定只需**一次整数比较**，不必维护"角色 → 权限点集合"那张表 |
| R-6 | 判定实现 | **只有一份**：`ScadaRoleExtensions.Allows` | 两个实现方（领域层兜底 `DefaultScadaAccessPolicy` + WPF 侧 `ScadaAccessPolicy`）各写一遍的后果不是"多敲几行"，而是**两条判定分头演化**：加一档角色改了一处忘了另一处，表现是"预览里能按、运行起来不能按"。**规则的副本数就是将来 bug 的分布数** |
| R-7 | 判定顺序 | ① 要不要管（`null`）→ ② 配得对不对（非法值）→ ③ 够不够格 | 顺序是刻意的：反过来先比大小的话，`Undefined` 的数值 0 会因"0 比谁都小"被判成"需要管理员"，报出来的原因**完全指错方向**（现场会去改图元，越改越乱） |
| R-8 | 拒绝原因 | 一句话，**能念给操作员听、也能直接写进日志** | `"需要「工程师」权限，当前是「操作员」"` 比 `"权限不足"` 多出的那两句，正是现场要知道的；且属性面板、运行日志、审计文件三处同源 |

#### G：闸门（动作执行出口）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| G-1 | 闸门位置 | **`ScadaRuntime.RaiseElementEvent`**（领域层，动作分发之前） | 界面上把按钮画灰、把面板藏起来，挡住的只是鼠标，挡不住任何一条**直接调接口**的路径（脚本、外部接口、将来的无人值守任务）。这条口径 S8 定 `ScadaRuntime` 时就逐字写死，S12 只是兑现 |
| G-2 | 拦下之后 | **不发动作**，抛 `ElementAccessDenied(element, reason)` 事件 | 不弹"没权限"对话框——那只会让人以为**事件配错了**。理由由宿主接住：写运行日志 + 落一条 `Denied` 审计 |
| G-3 | 声明载体 | 实例级强类型字段 `ScadaElement.RequiredRole`；写回走 `ScadaPage.TrySetRequiredRole`（D3） | 见 §二.5 |
| G-4 | 未接线时 | `ScadaRuntime` 的 `accessPolicy` 参数缺省 → `DefaultScadaAccessPolicy.Instance`（永远"未登录=操作员"） | 设计态预览、断言工程里没挂会话时照常跑，且**判定规则仍是同一份** |

#### U：账号与登录

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| U-1 | 账号存储 | `ScadaUserStore`，落 `<程序目录>\ScadaUsers.json`，结构 `[{ Name, Salt, Hash, Iterations, Role }]`；口令 **PBKDF2-SHA256**（16 字节随机盐 / 10 万次迭代 / 32 字节输出） | 明文或快哈希（MD5、单次 SHA）在工业现场等于没保护。参数只有一份实现（`Derive`），改算法时不可能漏改某一处 |
| U-2 | 出厂账号 | 文件不存在 / 读坏 → 种下 `admin / admin123`（`MinPasswordLength = 4`）；登录后用 `IsUsingDefaultPassword` 提示改密 | 首装总得进得去；同时给这条"众所周知的口令"一个尽快关掉的窗口 |
| U-3 | 管理员不可清零 | `TryRemoveUser` / `TrySetRole` 拒掉"最后一个管理员"的删除与降级 | 否则一条误操作（把唯一的 admin 删掉或降级）**把软件永久锁死**，现场只能手改 json |
| U-4 | 名字比对 | 一律**忽略大小写** | 现场没人记得住当初建的是 `Admin` 还是 `admin` |
| U-5 | 单向链 | `ScadaUserStore（验身份） → ScadaAccessPolicy（记会话）`；**存储不碰会话** | 登录弹窗只做两件事：问 store 要一个"已通过验证的角色"，交给 policy 装进会话。将来权限口径要改，改的是这两处，不是弹窗 |
| U-6 | 落盘方式 | 先写 `<file>.tmp` 再 `File.Replace` / `File.Move`（**原子写**） | 写一半断电/崩溃不留半截 json——那会让下次启动读坏文件、回落成出厂账号 |
| U-7 | 无"刷新"按钮 | 用户管理弹窗只在打开时读一次账号文件 | 刷新会走 `Load()`，而它**读坏文件时回落成出厂账号**。一个手滑的刷新能把内存里全部账号换成 admin 一个，再保存一下就覆盖了文件 |

#### S：会话与超时（WPF 侧）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| S-1 | 会话归属 | `ScadaAccessPolicy`（`VisionMaster\Services\`，`BindableBase` 实现 `IScadaAccessPolicy`） | 登录/登出/计时器全是界面能力；接口在领域层只回答"够不够格" |
| S-2 | 接口**只读** | `Login` / `Logout` / `Touch` **刻意不在** `IScadaAccessPolicy` 上（契约③） | 把"问一句"和"改状态"混在一起，领域层就得认识**密码框**与**超时计时器**。宿主按接口取（只问够不够格），界面按具体类型取（要能 Login/Logout） |
| S-3 | 空闲登出 | `DefaultIdleTimeout = 10 分钟`；`DispatcherTimer` 15 秒一拍（`Background` 优先级）；`Login` 起表、`Logout` 停表；到点登出并广播 `AutoLoggedOut(userName)` | 15 秒是"最多晚 15 秒登出"的精度，10 分钟是"人走开一会儿又回来"与"人走了必须锁"之间的现场折中 |
| S-4 | 活动输入源 | `InputManager.Current.PreProcessInput` **一个总口**，认 Mouse / Keyboard / Touch / Stylus 四类 | 这是 WPF 在"输入分发到任何元素之前"的唯一一道总口，一次订阅覆盖主窗口、运行窗口和每个弹窗。反过来逐窗口挂事件，**每加一个窗口就要记得加一次**，漏一个的表现是"在那个窗口里操作也会被踢下线"——只在超时那一刻复现，极难往"少挂了一个事件"上想 |
| S-5 | 超时提示归谁 | 主窗口（`ShellViewModel` 订阅 `AutoLoggedOut`） | 超时那一刻登录弹窗多半是关着的（没人开着登录框干活）；主窗口一直开着，正是该说话的地方 |
| S-6 | 状态栏读数 | `ShellViewModel` 暴露 `public ScadaAccessPolicy AccessPolicy => _accessPolicy;`，XAML 直绑 `{Binding AccessPolicy.LoginStateText}` | **不转发**：转发一次就要同步一次，多一处漏改的机会。运行窗口更省——`DataContext` 就是 `ScadaRuntime`，直接 `{Binding AccessPolicy.LoginStateText}` |
| S-7 | 登录弹窗不订阅 `AutoLoggedOut` | 改订阅 `ScadaAccessPolicy` 的**属性变更**（`OnDialogOpened` 挂、`OnDialogClosed` 摘） | 为一个几乎不会命中的场景（开着登录框时正好超时）多背一份"关窗必须记得解订阅"的生命周期债不值；但"状态行跟着变"这个便宜要占 |
| S-8 | 登录按钮**不禁用** | 用户名/密码为空时放行点击，由 `ScadaUserStore.TryValidate` 报出「请输入用户名」/「请输入密码」 | 禁用只会让人对着一个灰按钮猜原因；界面上有字可读才是便捷 |
| S-9 | 登录成功即关窗 | 关窗前清掉明文密码 | 按「登录」的人要的是"进去"，不是"看到一句成功提示" |

#### P：属性面板声明（组态侧）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| P-1 | 权限行来源 | 面板自带一行 `ScadaRoleSpec`（`Key = "RequiredRole"`），**不是**属性袋里的键 | 属性袋是"描述符声明的可配项"；`RequiredRole` 是每个图元都有的**结构字段**，不该靠每个描述符各自记得声明一遍（漏一个 = 那个图元永远设不了权限） |
| P-2 | 下拉档位 | 只有三档合法角色，**不含** `Undefined` | 它是"文件里存了个不认识的数字"的标记，不是一种能授予的角色 |
| P-3 | 写回路径 | 一律 `ScadaPage.TrySetRequiredRole`（D3） | 裸写字段虽然也会落一条记录，但**那条记录没有操作名**，撤销栈里会出现一行说不清是什么的改动 |
| P-4 | 非法值显示 | 下拉选不中时回落成"操作员"并在提示里说清（`账号「x」的角色值非法(N)` 同款口径） | 直接绑非法值会选不中任何项、显示成一片空白，用户看不出问题在哪 |

#### A：操作审计落盘

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| A-1 | 审计 ≠ 运行日志 | **分开存**：`Logs` / `Alarms` / `Audit` 三目录独立 | 运行日志是**过程记录**（按大小滚动、会被现场随手清掉、混着通讯/流程噪音）；审计是**凭证**。两者记同一件事也必须分开——与"报警历史不并进 Logs"同一理由 |
| A-2 | 谁落盘 | 分发器只交纯数据 `ScadaAuditEntry`，**落盘细节一概不知**（归宿主/落盘器） | 与报警"引擎发事实、宿主记文件"完全同分工 |
| A-3 | 结果四档 | `Success`（成功）/ `Skipped`（未执行）/ `Failed`（跑了没成）/ **`Denied`（被权限拦下）** | `Denied` 单独一档的理由：权限不足**不是故障**，是产品设计如此。它回答的是"这个人有没有碰过这个按钮"——只记成功的那一半，事后查"他到底按过没有"，答案会是"没有" |
| A-4 | 时间戳由谁盖 | `ScadaAuditEntry` **刻意不带时间戳**；`Append(entry, nowLocal)` 在真正落笔那一刻盖 | 记录是"发生了什么"的纯数据，时间属于"写在哪一天的文件里"。副产物：断言传假日期即可测按天滚动 |
| A-5 | 精度 | `yyyy-MM-dd HH:mm:ss.fff`（**毫秒**） | 审计是"人的操作"，同一秒里连点两下也得分得出先后（秒精度一经排序就丢次序） |
| A-6 | 粒度 | **一次动作一行**（不是一次点击一行） | 按"时间 + 操作者 + 对象"分组即可还原那次点击的全貌 |
| A-7 | 说明列 | 写变量时写**净效果**「旧值 → 新值」（执行侧先快照 `before`） | 这是审计独有的那一问（日志只写了目标值），而它**只有执行侧拿得到** |
| A-8 | 文件格式 | `Audit-yyyy-MM-dd.csv`，UTF-8 **带 BOM**、7 列表头、RFC 4180 转义、`leaveOpen: true` | 与报警历史同款口径（Excel 双击不乱码、逗号不劈列）；`leaveOpen` 不是可选项——S11-b 踩过一次（表头 writer 一出作用域就把底层流关掉，之后写行必抛 `ObjectDisposedException`） |
| A-9 | 线程 | **不锁线程**（调用方只有两处，都在 UI 线程） | 未证实的并发需求不加锁：加了锁就得回答"锁谁、锁多久"，而答案是"没有人会同时写" |
| A-10 | 写不成 | **不抛**：`catch` 收住所有 IO 异常返回 `false`，进故障态；只在"成功 ↔ 失败"**翻转那一次**报一次诊断 | 审计写不成反过来让操作失败，现场看到的就是"点按钮程序崩了"。故障每行都报会把日志刷满，真正的原因反而被埋掉 |
| A-11 | 空值口径 | 空署名回落「未登录」、空对象回落「未命名对象」、`null` 记录不写不抛也**不进故障态** | 一条没有署名/没有对象的记录等于白记；调用方的空引用不该被记成磁盘故障 |

### 3. 接线上的两个关键手法（`App.xaml.cs`）

```csharp
// ① 可选构造参数 → 必须用工厂注册显式注入
//    ScadaActionDispatcher 的 audit 是可选参数（默认 null）。若用类型映射
//    RegisterSingleton<IScadaActionDispatcher, ScadaActionDispatcher>()，
//    容器可能不注入它 —— 结果是"编译能过、运行起来审计文件一直空着、也不报错"。
containerRegistry.RegisterSingleton<IScadaActionDispatcher>(c => new ScadaActionDispatcher(
    c.Resolve<ILogService>(), c.Resolve<IScadaValueSource>(),
    c.Resolve<IScadaNavigator>(), c.Resolve<ScadaAuditWriter>()));

// ② 必填构造参数 → 依赖必须先注册
//    ScadaRuntimeHost 的 audit 是必填参数，解析它时要求 ScadaAuditWriter 已在容器里，
//    所以审计端的注册必须排在宿主注册之前。
```

## 二、为什么这么设计（逐条展开）

### 1. 权限为什么必须卡在"动作执行出口"（G-1）

```
   只靠界面隐藏                        闸门放在执行出口
   ┌─────────────┐                     ┌─────────────┐
   │ 按钮画灰/藏 │ ──▶ 挡得住鼠标        │ 按钮画灰/藏 │ ──▶ 挡得住鼠标
   └─────────────┘                     └─────────────┘
          ✗                                    ✓
   ┌─────────────┐                     ┌─────────────┐
   │ 脚本调接口  │ ──▶ 直接进，没人管    │ RaiseElementEvent │
   │ 外部接口    │                     │   └─ Allows? ─▶ 拒绝 + Denied 审计
   │ 无人值守任务│                     └─────────────┘
   └─────────────┘                            ✓
```

界面这一层只是"界面门"（`IsAdmin`、面板灰掉），真正的拒绝在 `ScadaRuntime.RaiseElementEvent`。
`ScadaUserManagerViewModel` 的每个写命令第一句都是 `EnsureAdmin()`，也是同一条口径。

### 2. 为什么"未登录 = 操作员"而不是"零权限"（R-3）

现场大量画面是**开机自动运行、无人值守**：没有人在场，也就没人登录。若未登录 = 零权限，那些画面上
"加载时初始化变量、切到首页"的钩子会**全部被挡**，软件等于开不起来。

于是口径拆成两条互不干扰的表达：

- **权限判定**只看 `CurrentRole`（未登录 = `Operator`）；
- **"此刻是谁"** 单独由 `IsLoggedIn` + `CurrentUserName` 表达（审计要的正是这个区别）。

合成一个值的代价是再也说不清"现在到底是没人登录，还是张三以操作员身份登录着"。

### 3. 为什么判定规则只留一份实现（R-6、R-7）

```
   规则写两遍                         规则写一遍
   ┌──────────────────┐               ┌──────────────────┐
   │ DefaultScadaAccess│              │ ScadaRoleExtensions│
   │   Policy（兜底）  │              │   .Allows          │
   ├──────────────────┤               └────────┬─────────┘
   │ ScadaAccessPolicy │                       │
   │  （WPF 侧）       │              ┌────────┴────────┐
   └──────────────────┘               ▼                 ▼
    加一档角色 → 改了一处忘了另一处    DefaultScada…   ScadaAccessPolicy
    表现：预览能按、运行不能按        （两个实现方都只是"转发"）
```

`Allows` 内部的三步顺序也写死在注释里：**先答"要不要管"，再答"配得对不对"，最后才答"够不够格"**。

### 4. 超时链路：输入总口 → 会话 → 谁说话

```
   鼠标/键盘/触摸/触笔
        │  InputManager.Current.PreProcessInput（全局唯一一道总口，S-4）
        ▼
   ScadaAccessPolicy.Touch()            ← 只写一个 DateTime 字段
        │  （DispatcherTimer 15 秒一拍，Background 优先级）
        ▼
   空闲 ≥ 10 分钟 → Logout() + AutoLoggedOut(userName)
        │
        ├─▶ ShellViewModel：主窗口提示"已因空闲自动登出"
        └─▶ 属性变更 → 状态栏 {Binding AccessPolicy.LoginStateText} 立刻变"未登录（操作员）"
            运行窗口底条同理（DataContext = ScadaRuntime → AccessPolicy.LoginStateText）
```

`Touch()` 未登录时调用**无害**，所以这里刻意不做"登录了才上报"的分支——那会引入"登录前动鼠标不算活动"
这类只在特定时序下出现的偏差。

### 5. `RequiredRole` 为什么不是描述符声明的属性（路线图偏差说明）

路线图原文是"图元级 `RequiredRole`（**描述符声明**，面板渲染，分发器执行）"。实现时改成了**实例级强类型字段**，
理由有三条：

| 维度 | 描述符声明的属性（属性袋键） | 实例级强类型字段（**采用**） |
|---|---|---|
| 默认值 | 靠每个描述符各自记得声明，**漏一个 = 那个图元永远设不了权限** | 字段在基类上，**所有图元自动都有**，缺省 `null` = 不限制 |
| 类型安全 | 属性袋里是字符串，非法值要等运行时才发现 | `ScadaRole?` 枚举，写错编译不过 |
| 序列化 | 要进属性袋的序列化/反序列化，多一层转义与解析 | 与 `Guid Id`、`Name` 同级的结构字段，随 `.vms` 一起走 |

"面板渲染、分发器执行"这两半**照原话做了**（P-1 的 `ScadaRoleSpec` 行 + G-1 的闸门），
只有"声明载体"这一处换了更稳的形式。旧 `.vms` 文件因此**不需要迁移**：没有这个字段就是 `null` = 不限制（R-4）。

### 6. 审计为什么要"记拒绝"（A-3）

审计要回答的问题不是"系统跑得顺不顺"（那是日志），而是**"谁动过什么"**。一次被权限拦下的点击：

- 只记成功 → 事后查"他到底按过没有"，答案是"没有"——**这个答案是错的**；
- 记成 `Failed` → 把"产品设计如此"混进"出故障了"，报警与故障统计会被污染；
- 记成 `Denied` → 单独一档，且带上原因（`"需要工程师权限，当前是操作员"`）。

被拦下的那一条，**动作列写「（未执行）」而不是留空**：空着分不清"没记"和"没有动作"。

### 7. 审计文件长什么样

```csv
时间,操作者,对象,事件,动作,结果,说明
2026-09-20 19:17:53.900,张三,启动按钮,按下,写变量 启动 := 1,成功,启动：0 → 1
2026-09-20 19:17:54.120,未登录,未命名对象,按下,切换画面 → 主界面,未执行,
2026-09-20 19:17:55.007,张三,启动按钮,权限校验,（未执行）,被拒绝,需要工程师权限，当前是操作员
```

列序就是现场阅读顺序：**谁 → 对谁 → 什么事件 → 干了什么 → 成没成 → 说明**。

### 3. 真机验证（S12-e）：登录弹窗"点不出来"的根因与修复

按 §六 清单第 1 条启动软件后，**菜单「系统(S) → 用户登录」点了没反应**——没有弹窗，界面也无任何提示。
这是本阶段真机验证抓出的**头号缺陷**，定位过程与结论如下。

#### 3.1 现象为什么"什么都不说"

菜单项的 `invoke` 返回成功，界面却毫无动静，只在
`Logs\<当天>.log` 里多出一行：

```
[WARN] [UI] An unexpected error occurred while resolving 'System.Object', with the service name 'ScadaLoginView'
```

- `[UI]` 不是 Prism 的内部标记，而是本项目
  [AppLifetimeService.cs](file:///e:/VM/VisionMaster-W-master/Core/Lifetime/AppLifetimeService.cs#L60)
  的 **Dispatcher 未处理异常处理器**打的前缀；它顺手 `e.Handled = true`，于是**异常被吞掉、程序不崩、界面不响**。
- 那行日志只有最外层的 `ex.Message`。Prism 9 + Unity 抛的是**嵌套容器异常**，根因在最里层，
  只看外层等于什么也没看到。

#### 3.2 先补诊断能力，再看根因

`ExceptionGrading.Handle` 的 `Notice` / `Warning` 两档原先只记 `ex.Message`，**内层异常全丢**。
补上 `Describe(ex)` 后重编译、重启，同一处再点一次，日志立刻给出完整链条（逐字）：

```
[WARN] [UI] An unexpected error occurred while resolving 'System.Object', with the service name 'ScadaLoginView'
  ← ResolutionFailedException: Resolution failed with error: Exception has been thrown by the target of an invocation.
  ← TargetInvocationException: Exception has been thrown by the target of an invocation.
  ← XamlParseException: "设置属性"System.Windows.Documents.Run.Text"时引发了异常。"，行号为"94"，行位置为"37"。
  ← InvalidOperationException: 无法对"…ScadaLoginViewModel"类型的只读属性"LoginStateText"进行 TwoWay 或 OneWayToSource 绑定。
```

这一处改动是**产品级**的，不只服务本次排查：此后任何依赖注入 / XAML 解析错误都能在日志里一眼看到根因。

#### 3.3 根因：`Run.Text` 默认 TwoWay × 只读属性

```
   ScadaLoginView.xaml L94（修复前）
   <Run Text="{Binding LoginStateText}" />        ← 没写 Mode
                     │
                     ▼
   Run.Text 是 BindsTwoWayByDefault = true 的依赖属性
                     │
                     ▼
   LoginStateText 是只读表达式属性（=> _accessPolicy.LoginStateText）
                     │
                     ▼
   XAML 解析期即抛 InvalidOperationException
                     │
                     ▼
   容器解析 ScadaLoginView 失败 → 弹窗构造不出来 → 界面毫无反应
```

**正确写法是显式 `Mode=OneWay`**。同库 [ScadaUserManagerView.xaml](file:///e:/VM/VisionMaster-W-master/VisionMaster/Views/DialogViews/ScadaUserManagerView.xaml#L238)
（`<Run Text="{Binding StoreFileName, Mode=OneWay}" />`）本来就有正确范例——唯独登录弹窗漏了。
已按同一写法修好，并在该行上方留了 XAML 注释说明"`Run.Text` 默认 TwoWay、只读属性必须显式 `Mode=OneWay`"。

全库 `Grep` `<Run Text="{Binding` 复核：本应用内只有这两处，另一处（用户管理）本来就是对的；
其余命中都在独立插件工程 `WPF-Halcon-流程拖拉\02Plugins\...`，不属于本应用。

### 2. 设计上的刻意取舍

- **`ScadaAccessPolicy` 属 WPF 侧**：它引 `System.Windows.Threading`，所以落在 `VisionMaster\Services\`
  而**不是** `Scada` 领域层。将来若有非 WPF 宿主（控制台服务），需另写一个等价实现——这是 D1 依赖单向换来的确定性。
- **`DefaultScadaAccessPolicy` 是单例且永不抛**：设计态预览、断言工程没挂会话时都读它。它的存在保证了
  "判定规则只有一份"在**没有会话**的场合也成立。
- **`RequiredRole` 不迁移旧文件**（R-4）：字段缺失 = `null` = 不限制，与"旧图元本来就没配权限"语义一致。
- **审计不锁线程**（A-9）：调用方只有两处（分发器、宿主 `OnElementAccessDenied`），都在 UI 线程。
  将来若从后台线程落审计，必须重新评估。
- **`ScadaAuditWriter` 每次 `Append` 都开/关文件**：换来"不长期持有文件句柄"（现场能用 Excel 直接打开审计文件）。
  当前量级（人的操作，一天几百行）无影响。
- **用户管理弹窗没有"刷新"按钮**（U-7）：这是**刻意**的，不是漏做。
