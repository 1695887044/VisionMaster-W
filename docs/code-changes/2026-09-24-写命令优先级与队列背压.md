# 2026-09-24 写命令优先级与队列背压（N1 + N2）

## 一、需求与决策

### 1.1 问题来源

在"通信库还有什么可以优化"的复盘中，新发现 3 条与 `ConnectionWorker`（单连接单线程 Actor）相关的问题：

| 编号 | 问题 | 严重度 |
| --- | --- | --- |
| **N1** | **写命令没有优先级**：读命令与写命令挤同一条 FIFO 队列，UI 点一次"写值"要排在**所有待处理读命令 + 当前这一轮轮询**之后 | 中高（现场手感："点了没反应"） |
| **N2** | **队列满直接失败**：`BlockingCollection` 容量固定 256，投递时 `TryAdd` 不带超时 → 一满就立刻抛"队列已满"，**瞬时排队被误报成通信故障** | 中 |
| **N3** | **一条连接一个专用线程**：每条连接一个 `Thread` | 低（只记录，不改） |

本轮用户批准范围：**N1 + N2 一起改**，N3 只记录。

### 1.2 N1：为什么写命令会"卡"

`Loop()` 每轮迭代的顺序是：

```
① 状态机（自动重连）
② 等命令 → DrainQueues()          ← 读/写命令都从这里出队
③ 轮询计划重建（若脏）
④ RunPollCycle()                  ← 一次跑完所有到期扫描组
```

在旧实现里 ② 只有一条 `_queue`，读命令与写命令**同队同权**。于是写命令最坏要等：

- 排在前面的所有待处理读命令；**再加上**
- 如果命令队列恰好空着、Worker 正卡在 ④ 里，那还要等**整整一轮 `RunPollCycle()` 跑完**。

对操作员来说，就是"我点了一下写值，界面/PLC 过了好一会儿才动"。

### 1.3 N1 的核心设计：双队列 + 信号唤醒

**做法**：把 `_queue` 拆成 `_readQueue` + `_writeQueue`，Worker 每轮**先清空写队列、再清空读队列**。

**这里有一个必须解决的难点（否则改完比不改更差）**：

Worker 空闲时是**阻塞**在队列上的。旧实现阻塞在 `_queue.TryTake(waitMs)`；一旦拆成两条队列，Worker 只能阻塞在其中一条上——

> 如果它阻塞在 `_readQueue`，此时写命令投进 `_writeQueue`，**没人叫醒它**，写命令要等到超时才被发现 → 延迟反而更大。

**解法**：引入独立的唤醒信号 `SemaphoreSlim _commandSignal = new(0, 1)`：

- 任一条队列**入队成功**后 `Release()`（吞 `SemaphoreFullException`）；
- `Loop()` 第 ② 步改为 `_commandSignal.Wait(ComputeWaitMs(), token); DrainQueues();`
- **`Wait` 的返回值不参与判定**——无论因超时醒来还是因 `Release` 醒来，都**无条件**排空两条队列。这样彻底避免"漏命令"。
- 信号量容量固定为 `1`：它只表达"有活干了"这一件事，多余信号被吞掉即可（最坏多一次空转，无害）。

### 1.4 N1 的关键修正：写优先曾被自己写成"形同虚设"

**初版 `DrainQueues()` 是错的**：

```csharp
// ✗ 错误写法
while (true)
{
    bool any = false;
    while (_writeQueue.TryTake(out var w, 0)) { ExecuteItem(w); any = true; }
    while (_readQueue.TryTake(out var r, 0)) { ExecuteItem(r); any = true; }  // ← 这里会把读队列一次抽干
    if (!any) break;
}
```

**为什么错**：外层循环第一次进来时，读队列里可能已有命令。内层那个 `while` 会**一次性把读队列抽干**；期间新到的写命令只能排在读队列"之后"被处理——**写优先形同虚设**。

这个缺陷是被断言 **C13-2** 抓出来的（实测顺序 `读:D0 → 写:D100`，而期望是 `写:D100 → 读:D0`）。

**正确写法**——"写一条、读一条"的交替形式：

```csharp
private void DrainQueues()
{
    while (true)
    {
        if (_writeQueue.TryTake(out var w, 0)) { ExecuteItem(w); continue; }  // 每取一条前先看写队列
        if (_readQueue.TryTake(out var r, 0)) { ExecuteItem(r); continue; }   // 写队列空才取读命令
        break;
    }
}
```

既保证**写优先**（写队列有货就先执行写），又保证**读命令不被饿死**（写命令持续涌入时，每执行一条写就轮到一条读）。

### 1.5 N1 的正确性红线

> **同一个 socket 上不能并发两个事务。**

写命令只能在「命令与命令之间」「轮询段与段之间」插队，**绝不能打断正在进行的 `ReadBytes`**——否则半包读会导致协议解析错位。本设计是**单 Worker 线程串行执行**，天然满足这条红线（写命令只是"排队位置"提前，不是"并发执行"）。

### 1.6 N1 的收益边界（必须明说）

- ✅ 写命令**不再排在所有待处理读命令之后**；
- ❌ 写命令**仍然无法打断一整轮 `RunPollCycle()`**（该方法内部一次跑完所有到期组）。

若要进一步缩短，需要"组间让路"（每跑完一个扫描组就检查一次写队列）或"拆细粒度轮询"，属 N1 的后续增强，本轮**不做**。

### 1.7 N2：队列背压

**问题**：`TryAdd(item)` 不带超时，容量 256 一满就**立刻**失败，抛"队列已满"。而"队列满"通常只是**瞬时排队**（UI 连点写、脚本批量写），并不是真故障。

**做法（两条一起上）**：

| 措施 | 内容 |
| --- | --- |
| 带超时等待 | `TryAdd(item, CommandEnqueueTimeoutMs)`，`CommandEnqueueTimeoutMs = 2000`（ms） |
| 放宽容量 | `CommandQueueCapacity = 4096`（原固定 256） |

超时后抛：`InvalidOperationException($"连接 {ConnectionName} 命令队列已满（等待 {CommandEnqueueTimeoutMs}ms 仍未消化）")`。

**为什么"先等 2 秒"是可接受的**：调用方 `Read`/`Write` 本来就使用 `.GetAwaiter().GetResult()`（**同步阻塞**语义），所以最长多等 2 秒符合原有语义，不引入新的行为突变。

**Dispose 竞态**：`CompleteAdding` 之后 `TryAdd` 会抛 `InvalidOperationException`，与"队列满"是同一个异常类型；现有 `catch (InvalidOperationException)` 已覆盖，统一转 `ObjectDisposedException`。

### 1.8 N3：为什么只记录不改

| 理由 | 说明 |
| --- | --- |
| 改 async 不真的提升吞吐 | HSL 库本身是**同步 API**，改 async 只是把阻塞挪到线程池，并没有减少阻塞本身 |
| 每连接一个线程正是最直白的实现 | "每连接串行事务"用专用线程是最简单、最不易出错的实现；改 async 要动整个 `ICommunicationConnection` 契约 |
| 当前规模不需要 | 单机视觉上位机，几百条连接基本不会出现 |

**文档中记下上限**：**连接数 > 约 200 条时需重新设计为 IO 复用**（如 `SocketAsyncEventArgs` / `Channel<T>` + 少量 IO 线程）。

### 2.1 关键代码

**双队列 + 信号（字段）**：

```csharp
/// <summary>N2：命令队列容量（UI 连点写 / 脚本批量写不再轻易打满）</summary>
private const int CommandQueueCapacity = 4096;

/// <summary>N2：投递命令时等待 Worker 消化的上限（ms），超时才判"队列已满"失败</summary>
private const int CommandEnqueueTimeoutMs = 2000;

private readonly BlockingCollection<WorkItem> _readQueue = new(boundedCapacity: CommandQueueCapacity);
private readonly BlockingCollection<WorkItem> _writeQueue = new(boundedCapacity: CommandQueueCapacity);

/// <summary>N1：唤醒信号——容量固定为 1，只表达"有活干了"；醒来后无条件排空两队列，不会漏命令</summary>
private readonly SemaphoreSlim _commandSignal = new(0, 1);
```

**投递核心（N2 带超时 + N1 唤醒）**：

```csharp
public Task<TResult> Invoke<TResult>(Func<ICommunicationConnection, TResult> func)
    => EnqueueCommand(_readQueue, func);

public Task<TResult> InvokeWrite<TResult>(Func<ICommunicationConnection, TResult> func)
    => EnqueueCommand(_writeQueue, func);

private Task<TResult> EnqueueCommand<TResult>(BlockingCollection<WorkItem> queue, Func<ICommunicationConnection, TResult> func)
{
    ThrowIfDisposed();
    var tcs = new TaskCompletionSource<TResult>(TaskCreationOptions.RunContinuationsAsynchronously);
    try
    {
        if (!queue.TryAdd(new WorkItem { /* … */ }, CommandEnqueueTimeoutMs))
        {
            tcs.TrySetException(new InvalidOperationException(
                $"连接 {ConnectionName} 命令队列已满（等待 {CommandEnqueueTimeoutMs}ms 仍未消化）"));
            return tcs.Task;
        }
    }
    catch (InvalidOperationException)
    {
        // Dispose 竞态：CompleteAdding 之后 TryAdd 会抛
        tcs.TrySetException(new ObjectDisposedException(nameof(ConnectionWorker)));
        return tcs.Task;
    }

    try { _commandSignal.Release(); }
    catch (SemaphoreFullException) { /* 已有信号待消费，无需重复通知 */ }

    return tcs.Task;
}
```

**Loop 第 ② 步**：

```csharp
// 返回值不参与判定——无论因超时还是因新命令 Release 醒来，都无条件排空两队列，避免漏命令
_commandSignal.Wait(ComputeWaitMs(), token);
DrainQueues();
```

**排空（写优先且不饿死读）**：

```csharp
private void DrainQueues()
{
    while (true)
    {
        if (_writeQueue.TryTake(out var w, 0)) { ExecuteItem(w); continue; }
        if (_readQueue.TryTake(out var r, 0)) { ExecuteItem(r); continue; }
        break;
    }
}

private void ReleasePendingItems()
{
    while (_writeQueue.TryTake(out var w, 0)) w.OnAbandon?.Invoke();
    while (_readQueue.TryTake(out var r, 0)) r.OnAbandon?.Invoke();
}
```

### 2.2 断言（C13 组，6 条，全部离线可跑）

| 断言 | 内容 | 意图 |
| --- | --- | --- |
| C13-1 | 队列容量 > 256 | 证明容量已放宽（旧实现固定 256） |
| **C13-2** | 读先入队、写后入队 → 执行顺序仍是「**写 → 读**」 | **核心**：写插队真的生效（旧实现是「读 → 写」）。**这条曾抓出初版排空逻辑的缺陷** |
| C13-3 | `InvokeWrite` 能取回结果 | 与 `Invoke` 语义一致 |
| C13-4 | `InvokeWrite` 把委托异常回抛 | 走写队列 ≠ 吞异常 |
| C13-5 | 空闲时投递命令**立刻**被唤醒（< 150ms，不等满 200ms 空闲等待） | 证明 `_commandSignal` 有效；否则双队列反而更慢 |
| C13-6 | 队列满 → **先等 ~2000ms** 让 Worker 消化，超时才失败 | N2 核心：把"瞬时排队"与"真故障"分开 |

**测试桩 `OrderRecordingConnection`**：只记录"谁被执行了、按什么顺序"。**为什么不复用 `FaultyConnection`**：那个桩的语义是"按地址注入读失败"，本组要的是"记录执行顺序"，混在一起会让两个断言的意图互相污染。

**两个常量用反射读**：`CommandQueueCapacity()` / `CommandEnqueueTimeoutMs()` 从 `ConnectionWorker` 的私有静态常量读——断言按"实现自己的口径"验，而不是在测试里再抄一份数字。

**C13-2 的时序前提**：先用 `ManualResetEventSlim` 闸门让 Worker 卡住（`blocker`），`Thread.Sleep(300)` 确保 `blocker` 已被取走、两条新命令必然都还留在各自队列里，顺序才可比。

### 3.1 关于 ScadaChecks 的那 1 条失败

失败项：`Choice 候选里凡是英文的都有中文译名` → `Fill、Uniform、UniformToFill`。

**根因**：`Scada.Controls/Elements/ImageViewElement.cs`（HTTP 收图功能新增的图元）声明了一个复用 WPF `Stretch` 枚举的 `Choice` 属性，候选值 `Fill` / `Uniform` / `UniformToFill` 在 `Scada/Models/ScadaChoiceNames.cs` 词汇表里**没有中文译名**。

**为什么与本改动无关**：本次改动只涉及 `ConnectionWorker` / `AdvancedCommunicationManager` / `CommChecks`，全部在通信层；`ScadaChecks` 的这条断言扫描的是 HMI 图元描述符，两条链路零交集。该失败由 HTTP 收图那次改动引入（A2 验证时 ScadaChecks 还是 1691/0），**留待独立处理**。

## 四、已知边界

1. **N3 不改**：每条连接仍是一个专用线程。**连接数 > 约 200 条时需重新设计为 IO 复用**（`SocketAsyncEventArgs` / `Channel<T>` + 少量 IO 线程）。
2. **写命令仍无法打断一整轮 `RunPollCycle()`**：N1 的收益是"不再排在所有待处理读命令之后"，不是"随时抢占轮询"。要缩短到"组间可让路"需另做增强。
3. **写优先 ≠ 并发写**：红线是"同一 socket 不能并发两个事务"。单 Worker 线程串行执行保证写命令只是**排队位置提前**，绝不打断进行中的 `ReadBytes`。
4. **`DrainQueues` 的写法勿回退**：不能改回"内层 `while` 先抽干写队列、再内层 `while` 抽干读队列"——那样写优先会失效（C13-2 就是为守这条而存在的断言）。
5. **`_commandSignal` 容量固定为 1 勿改大**：它只表达"有活干了"。容量 > 1 会让计数与实际待处理命令数脱钩，可能出现"空转若干次"；容量 1 最坏只多一次空转，且永不漏命令。
6. **C13-6 的等待时长断言有 ±300ms 容差**：CI 机器负载高时 `Stopwatch` 实测可能略小于 2000ms，故判据为 `>= 2000 - 300`。
7. **未覆盖实机验证**：C13 验的是"Worker 的排队与背压行为"，不是"真 PLC 上写命令的到达时序"。实机手感点验（UI 点写值 → 设备响应延迟）留待联调。
