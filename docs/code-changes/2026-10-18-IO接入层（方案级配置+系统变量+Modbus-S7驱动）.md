# IO 接入层（方案级配置 + 系统变量 + Modbus/S7 驱动）

日期：2026-10-18
状态：第一版可运行实现（P1 纵向切片）

## 1. 目标

- 支持数字量/模拟量 IO（DI/DO/AI/AO），后续可扩展到更多厂家/协议；
- 新增厂家不改核心逻辑；
- IO 点位与状态投影成系统变量，流程/SCADA/监视通过变量读写；
- 配置随方案（`.vms`）走，属性编辑优先使用反射属性窗口；
- P1 协议范围：Modbus TCP、Modbus RTU、Siemens S7。

## 2. 分层与文件

### 契约层（Core.Interfaces）

- `Shard/Core.Interfaces/Io/IoTypes.cs`：点位类型/质量/状态/传输类型/`IoPointValue`/`IoWriteResult` 等；
- `Shard/Core.Interfaces/Io/IoDescriptors.cs`：总线/设备/点位描述符、TCP/串口/重连/轮询组配置、`IIoRuntimeContext`；
- `Shard/Core.Interfaces/Io/IIoDevice.cs`：运行态设备契约（缓存读、即时读、写、写等待、状态/事件）；
- `Shard/Core.Interfaces/Io/IIoProvider.cs`：设备仓库 + `NullIoProvider`；
- `Shard/Core.Interfaces/Io/IIoTransport.cs`：字节传输 + 协议编解码契约；
- `Shard/Core.Interfaces/Io/IIoDriverFactory.cs`：`[IoDriver]` 稳定 `driverId` + 工厂；
- `Shard/Core.Interfaces/Io/IoDeviceBase.cs`：单 Worker、轮询、写优先、重连、快照、质量、死区/防抖、写超时语义。

### 宿主运行层（VisionMaster）

- `VisionMaster/Services/Io/IoDriverRegistry.cs`：内置驱动注册（simulated / modbus.tcp / modbus.rtu / siemens.s7）；
- `VisionMaster/Services/Io/IoProvider.cs`：按方案配置创建/重建/启停设备；
- `VisionMaster/Services/Io/SimulatedIoDevice.cs`：内存模拟设备（无硬件测试）；
- `VisionMaster/Services/Io/HslIoDeviceBase.cs`：基于 HSL 的原始值读写、链路/协议错误分类；
- `VisionMaster/Services/Io/ModbusIoDevice.cs`：Modbus TCP/RTU；
- `VisionMaster/Services/Io/S7IoDevice.cs`：Siemens S7；
- `VisionMaster/Services/Io/IoModule.cs`：`IAppModule` 装配、方案切换重建、退出释放。

### 变量层（VM.Core）

### UI

## 3. 关键行为

- 设备/点位配置随方案走；切换方案时按 `IoProvider.Apply` 重建，变量目录重建；
- 变量命名：输入/输出均投影；输入只读、输出实现 `IWritableVariable`；
- 读：轮询缓存；`ReadNow` 绕过缓存发真实请求；
- 写：`WriteAndWait` 入队并等待；超时区分“未执行/可能已执行”；不自动重试；
- 质量：链路故障 → Bad；单点失败 → Uncertain；禁用 → Disabled；
- 缩放/偏移/死区在 `IoDeviceBase` 统一处理，驱动只读写原始值；
- Modbus 地址沿用字符串（40001/00001 等），S7 沿用 HSL 语法（DB1.DBX0.0 等）。

## 5. 已知限制与后续

### 本轮补上的设计条目（第二批）

- **系统变量统一宿主**：`Core/Binding/SystemVariableHost.cs` + `ISystemVariableProvider`。
  运动目录与 IO 目录都只产快照、通过 `Changed` 事件通知宿主，由宿主合并写集合；
  提供方清空/重建不会误删其它来源的变量（新增断言覆盖）。
- **坏点隔离**：`IoDeviceBase` 只轮询“可读”点；驱动返回 true 但某点没给值即记一次失败，
  连续 3 轮后移出正常轮询，改为 5s 低频探测；恢复读到值即自动解除。新增断言覆盖。
- **输出写租约**：`Core/Services/IoOutputLeaseRegistry.cs`。默认严格单写者，
  手动写用 `manual` owner；流程持有点位时手动写返回明确冲突（含当前 owner）。
  点位可显式开启 `AllowSharedWrite`；租约带超时回收。
- **站点状态系统变量**：`System.Io.{DeviceId}.Online / State / LastError`，
  IO 模块 200ms 刷新一次；实例复用，设备移除时同步摘除。
- **写超时取设备配置**：`IoOutputVariableModel` 使用设备 `Params.WriteTimeoutMs`（默认 500ms）。

### 本轮补上的设计条目（第三批）

- **流程侧写入作用域**：`Core/Services/IoWriteScope.cs`（`AsyncLocal`）。
  流程每次执行/每轮开始 `IoWriteScope.Begin("flow:{FlowName}/{SessionId}")`，
  变量写输出的 owner 自动取该值；作用域结束时 `ReleaseAll(owner)` 兜底释放，
  分支异常退出也不会漏。界面/SCADA/脚本在流程外写 = `manual` owner。
- **分支级 owner**：`CompiledParallelNode.ExecuteBranch` 为每个并行分支开子作用域
  `{flowOwner}/branch:{index}`；两个分支写同一个 DO 时后者被明确拒绝，
  分支结束只释放自己的租约，不影响兄弟分支。
- **租约注册表静态挂接**：`IoWriteScope.AttachLeaseRegistry`（`Initialize` 阶段调用）。
  执行引擎（`Core`）没有容器引用，用与 `MotionAxisResolution.Attach` 相同的手法注入，
  避免给执行上下文再增一个契约成员。
- **手动写审计**：`IoOutputVariableModel.RecordAudit` 走 `AuditLogger`，
  记录 owner（流程/分支/manual）、点位、旧值→新值、成功/失败原因。
  `AuditLogger` 新增内存环形队列 `RecentEntries`（最近 2000 条），
  供断言与诊断读取，不必等后台落盘线程。
- **变量订阅层**：`Core/Binding/VariableSubscription.cs`——
  独立发布周期、队列容量 1（只发最新）、丢更新计数、退订清理。
- **IO 健康快照**：`VisionMaster/Services/Io/IoHealthMonitor.cs`——
  总线/设备/点位三层不可变快照 + `Summary` / `ToDetailText()`；
  设备层含状态、最后成功、写/拒绝/故障计数、隔离点清单。
- **配置版本**：`IoBusDescriptor` / `IoDeviceDescriptor` 增加 `SchemaVersion`
  （`CurrentSchemaVersion = 1`）；高于当前软件支持时 `Validate` 明确拒绝并给出原因。

### 第五批：属性网格的多态切换修正（2026-10-18 真机反馈）

**问题**：IO 配置弹窗里"选 TCP 却同时显示串口参数、选 Modbus 却同时显示 S7 参数"。

**根因**：`IoBusEditModel` / `IoDeviceEditModel` 把两种链路的字段、两种驱动的字段
**平铺在同一个类上**。属性网格只渲染带 `[SuperDisplay]` 且 `Visible == true` 的成员，
平铺就意味着"全部一起出现"；而且这些属性是普通自动属性，没有 `PropertyChanged`，
即使标 `RequireRefresh` 也不会触发重建。

**修法**（复刻 `CommunicationConfig` 的三件套）：

| 要素 | 通讯设置（既有范式） | IO 配置（本次照搬） |
|---|---|---|
| 切换声明 | `Protocol` 标 `RequireRefresh = true` | `TransportKind` / `DriverId` 标 `RequireRefresh = true` |
| 换对象 | setter 里 `OnChanged` 把 `Config` 换成新的 `ConnectionConfigBase` 子类 | setter 里把 `Transport` 换成 `TcpLinkEditModel` / `SerialLinkEditModel`；`DriverConfig` 换成 `ModbusDriverEditModel` / `S7DriverEditModel` / `SimulatedDriverEditModel` |
| 嵌套渲染 | `Config` 标 `[PropertyItem(Type = typeof(Control))]` | `Transport` / `DriverConfig` 标 `[PropertyItem(Type = typeof(Control))]` |
| 通知 | `BindableBase.SetProperty` | 同样改成 `SetProperty` + 私有字段 |

配套：切换时保留另一种链路/驱动的**草稿实例**（来回切不丢已填参数）；
`ToDescriptor()` 把两种链路都写回（描述符本就并存两套，运行期只看 `TransportKind`），
驱动 JSON 按当前驱动类型生成。

**验证**：`IoChecks` 新增 18 条断言——TCP 链路的可见属性不含串口字段、串口链路的可见属性不含 TCP 字段、
切走再切回保留原值、Modbus 驱动只暴露站号/字序、S7 驱动只暴露系列/机架/槽位、
写回 JSON 只含当前驱动字段。

### 第六批：IO 健康面板 + 通讯配置方案级迁移

**1. IO 健康面板（`IoHealthView` / `IoHealthViewModel`）**

- 三个页签：设备 / 总线 / 点位，1s 自动刷新；
- 数据来自 `IoHealthMonitor.Capture()` 的不可变快照，UI 与 Worker 线程无共享；
- **原位更新行对象**（按 `DeviceId` / `BusId` / `DeviceId.PointId` 对齐），不清空重建——
  否则每秒刷新会把选中态与滚动位置重置；
- 刷新异常**停表**并把原因写进 `Hint`（不弹泡、不重复刷），与扫描组编辑器的诊断节拍同一处置；
- 状态/质量用状态点 + 文案双表达（颜色不是唯一信息载体）；
- 入口：主菜单「系统 → IO 健康」，紧挨「IO 设置」。

**UI 纪律**（R19~R22）：视图就地合并 `GridView.xaml`、`ListView` 挂 `GridListViewStyle`、
行容器自带 `GridViewRowPresenter`（内边距 4，列头 Padding 8）。

**2. 通讯配置方案级迁移（`CommunicationSolutionBinder`）**

- 连接配置的唯一事实源改为方案（`SolutionModel.CommunicationConfigs`）；
- `Apply(solution, autoStart)`：**先 StopAll → 再逐条 RemoveConnection → 再逐条 AddConnection**。
  先停后换是为了避免旧 Worker 仍占着 COM 口/TCP 端点（进程序内版的"两个进程抢串口"）；
- **逐条隔离**：某条配置非法只跳过并记日志，不让整份方案打不开；
- `Capture(solution)`：保存方案时把管理器当前连接写回方案；
- 接入三个切换点：打开方案、启动自动加载、新建方案（新建时清空，因为新方案没有连接配置）。

**机器级 `communications.json` 的定位**：仍保留启动读取，仅用于"没配启动方案时通讯自检有配置可测"；
一旦加载方案就被整体替换，不再出现两份配置各说各话。

### 第七批：配置版本迁移链 + 结构化测试用例

**1. IO 配置版本迁移（`Core/Services/IoConfigMigrator.cs`）**

- 挂在 `SolutionService.LoadAsync`：迁移的输入是"磁盘上的旧结构"，只有加载那一刻它还存在；
- **低于当前版本** → 跑迁移链（当前 1 无历史版本，入口已就位，加版本时只补一个步骤）；
- **高于当前版本** → **明确拒绝**并给出可读原因，不改动配置（静默丢字段比拒绝打开更糟）；
- **迁移失败保留原配置**并记日志（配置是现场资产，不做"丢掉重建"）；
- 无论是否迁移都跑一次防御性归一化：`Tcp`/`Serial`/`Reconnect`/`Params`/`Points` 补 null，
  `Scale == 0 → 1`，负死区/负防抖 → 0，空 `DriverConfigJson → {}`。
  这些是"旧文件缺字段"，不是配置错误，静默补齐即可。

**2. 测试用例结构化（`IoChecks/TestCase.cs`）**

- 每条断言 = **用例 ID + 名称 + 预期 + 实际 + 通过与否**；
- 用例 ID 按段落编号（`D.3` = 设备契约第 3 条、`AE.16` = 边界与异常第 16 条），报告能直接定位；
- 汇总按段落分组输出通过/失败计数。

### 第八批：HIL 联调（S7 真实帧 / RTU 编解码）+ 两个功能缺口（2026-10-19）

本批目标是把 IO 层从"代码路径跑通"推进到"真实链路跑通"，并清掉上一轮报告里点名的两个缺口。

#### 1. S7 真实帧联调 —— 抓到一个真缺陷：总线端口被忽略

**做法**：进程内起 HSL `SiemensS7Server`（不是 `tools\DeviceSimulator` 子进程）。
理由：子进程夹具失败时无法区分"环境没起来"和"驱动有问题"（R38）。

覆盖：读 I 区 / M 区 / DB 区（16 位整数）、缩放（55 × 0.1 = 5.5）、写 Q 区线圈、
写 DB 区寄存器、**从站侧确认真的收到了帧**（不是本地镜像）、写入回读、
后台轮询覆盖 4 个输入点、输出点不进轮询、断开后状态回落。

**发现的问题（产品缺陷）**：`SiemensS7IoDevice.Open` 用
`new SiemensS7Net(series, Bus.Tcp.Host)` 建客户端，**没有把 `Bus.Tcp.Port` 写进去**。
HSL 的构造函数把 `Port` 写死成 102，于是：

- 界面上改端口"改了没有任何反应"（配置与行为不符，R33 同类）；
- `tools\DeviceSimulator` 的 10000-10009 端口永远连不上；
- 现场走端口映射/防火墙转发时无法接入。

**修法**：`if (Bus.Tcp.Port > 0) client.Port = Bus.Tcp.Port;`（非法值保留 HSL 默认 102，
非法值由描述符校验拦）。断言 S7.1 的文案直接写成"总线端口来自配置，不是 HSL 写死的 102"，
将来若有人删掉这行，失败信息自己会说明原因。

#### 2. Modbus RTU —— 自写从站 + 三段式验证

**环境事实**：本机**没有 com0com**，`Win32_SerialPort` 只有蓝牙 COM5/COM6
（需要已配对的对端设备才能互通）。HSL 也只有 `ModbusTcpServer`，没有 RTU 从站。

于是把"能不能验证"拆成三段，只有最后一段依赖环境：

| 段 | 内容 | 依赖 | 结果 |
|---|---|---|---|
| ① 帧编解码 | `IoChecks/RtuSlave.cs` 的 `Handle(byte[])` 纯函数（01/02/03/04/05/06/0F/10） | 无 | 13 条全通过 |
| ② 链路负向 | 端口不存在时的连接失败、状态说明、读写失败与超时 | 无 | 7 条全通过 |
| ③ 真实帧 | 从站在 B 口、设备在 A 口，读写穿透 | **一对可互通串口** | 1 条跳过（见下） |

**为什么要写从站**：RTU 的"真实帧"必须两端都是串口，而编解码是最容易写错、
也最该被守住的一段（CRC、位打包、字节序、异常响应）。把它做成纯函数后，
**这部分现在就是真测过的**，未验证的只剩几十行串口收发。

**外部锚点**：CRC 用 Modbus 规范的经典示例帧 `01 03 00 00 00 0A` 断言算出 `0xCDC5`，
避免"实现与测试自洽但都错"。

**跳过项的口径（R38）**：RT.24 记 `[SKIP]` 而不是 PASS——
汇总表里单独列"跳过 1"，既不进通过数也不进失败数。原因写的是可反证的环境事实，
并给出反证方式：装 com0com 后设 `VM_IO_RTU_PAIR=COM20:COM21`（主站口:从站口）即可执行。

**过程中修正的 2 处测试预期错误（不是产品缺陷）**：

1. FC10 响应断言取错了下标（`writeRegs[6]` 是 CRC 低字节，数量在 `[5]`）；
2. "地址越界"用了 `0xFFF0 + 16`——那正好落在最后 16 个寄存器，是**合法**地址。
   改成 `0xFFF8 + 16 = 65544 > 65536` 才真越界。

#### 3. `AveragePollMs` 恒为 0

原实现里 `IoHealthMonitor.Capture()` 给总线实测周期直接填了常量 `0`，
而 UI 根本没有消费这个字段（等于"字段存在但永远是假的"）。

- `IoDeviceBase` 量 **`PollCore` 一次调用本身的耗时**（不含等待周期），
  指数滑动平均（新样本 0.2）抑制抖动，成功/失败都记（失败那次的耗时正是"超时前等了多久"）；
  新增 `AveragePollMs`（0 = 还没有样本），`ResetCounters()` 一并清零；
- `IoHealthMonitor` 取该总线上"有样本"的设备的平均；
- 健康面板总线页签新增「实测周期」列，**无样本显示「—」而不是 0ms**（0 会被读成"极快"）。

#### 4. IO 变量进全局变量管理器的只读系统变量分区

此前 IO / 系统变量与本地变量同住 `GlobalVariables`，而来源树只有"本地 + 各连接"，
于是它们以**可编辑、可删除**的样子混在「本地变量」里。

- 来源树新增「系统变量」节点（`SystemSourceKey = "System"`），计数 = `VariableType.System + VariableType.Io`；
- 筛选口径：`Local` **显式排除**系统/IO；`System` 只含它们；
- **删除 / 改名加守卫**（给中文原因，不静默空跑）：删掉不会"真的消失"
  （宿主下次 Rebuild 又加回来），而删的那一刻引用它的画面/流程已经断链；
  名字是派生量（含设备/点位标识），改它没有落点；
- `VariableNode.IsEditableNode` 排除系统/IO（`IsSystemOwned`）——
  初始值写了也不回灌设备，只能给"可编辑"的假象；
- 在「系统变量」分区点"新增"会先把来源切回本地，再走原有本地草稿流程
  （不静默什么都不做）。

**验证**：`FlowCanvasChecks` 新增 `RunSystemSourceContract()` 9 条，
其中「本地变量仍可编辑」是**反向对照**——防止把 `IsEditableNode` 一刀切成 false 也能全绿。
另外两处标量类型是刻意设的：`Root()` 默认造数组节点，不改成标量的话，
"系统变量不可编辑"会因为"数组本来就不可编辑"而**假通过**。

### 第十批：RTU 真实帧互通 + 地址基数 + 迁移链可测化（2026-10-19）

本批对应上一轮遗留清单里能落地的三项；第四项（订阅层接消费方）经核查**没有合适消费方**，
按"不静默跳过"的要求在末尾单独说明原因与替代。

#### 1. RTU 真实帧：用 RTU-over-TCP 替代 com0com

**阻塞**：本机没有 com0com，也没有可互通的物理串口，RTU 真实帧原本只能跳过。

**替代方案**：把自写从站挂到 TCP 上（`RtuOverTcpServer`，帧仍是**标准 RTU 帧**：站号 + 功能码 + CRC），
客户端用 HSL 真实的 `ModbusRtuOverTcp`。这样"我们的从站编解码能否与真实 Modbus 客户端互通"
不再依赖串口——**串口收发那几十行仍需硬件**，但帧层已经端到端跑通。

断言：连接成功 / 读保持寄存器 / 读线圈 / 写线圈穿透 / 写寄存器穿透 / 多帧交互且 CRC 全错为 0。

**过程中查清的一条 HSL 约定（重要）**：`AddressStartWithZero` 只影响**是否减 1**，
地址串里的 `4xxxx` **不会**被剥成寄存器偏移——`"40001"` 就是第 40001（0 基）或第 40000（1 基）号寄存器，
不是"第一个保持寄存器"。要用原始地址请写 `"0"` / `"1"`，或用 HSL 的 `x=3;0` 显式指定区域。
帧日志（`07-03-9C-40-00-01-AB-E8`，0x9C40 = 40000）是这条结论的直接证据。

#### 2. 地址基数开关（由上面的测试暴露的真缺陷）

`ModbusDeviceConfig` 原先没有暴露 `AddressStartWithZero`，而 HSL 默认 **true（0 基）**。
按 PLC 变量表（4xxxx，1 基）配置的用户会**静默读写到相邻寄存器**——不报错、值不对。

- `ModbusDeviceConfig` 增加 `AddressStartWithZero`（默认 `true`，保持既有行为不变）；
- `ModbusTcpIoDevice` / `ModbusRtuIoDevice` 都把它写到客户端；
- UI 的 `ModbusDriverEditModel` 增加同名字段并纳入 `ToJson` / `From` 往返；
- 描述写明两种口径的差别。

**断言**（M.6~M.10）：同一从站、同一地址串 `"40001"`，1 基设备读到 111（它自己写的），
0 基设备读到 123（另一台设备早先写的）——**两个设备必须落到不同寄存器**。
如果开关只加在 UI 上没接到驱动，两台会读到同一个值，这条立刻红。

#### 3. 迁移链可测化

- 抽出 `IoConfigMigrator.TryMigrate<T>(from, to, steps, item, out error)`：
  按版本顺序执行、一步失败即中止、步数不足明确失败、降级与负版本拒绝；
- `MigrateBus` / `MigrateDevice` 改为调用它，步骤表 `BusSteps` / `DeviceSteps` 目前为空；
- **修一个日志缺陷**：迁移消息原先在 `MigrateBus` 之后拼，`SchemaVersion` 已被改写，
  于是恒显示"从版本 1 迁移到 1"；改为先记 `from`；
- **版本 0 的语义**：0 = "写它的软件还没有版本字段"，结构与版本 1 相同，
  直接盖版本号、不占用迁移步骤（否则会误报"缺少迁移步骤"）。

断言 9 条（Q.16~Q.24），其中"某一步失败后不再执行后续步骤"是防止"继续跑把结构改坏"的关键一条。

#### 4. S7 边界与异常（替代真机）

真机 PLC 仍需要硬件，但失败路径与配置兜底不需要：

- 端口无人监听 → `Connect` 不抛、返回 false、计入 `FaultCount`、状态不是 Online；
- `DriverConfigJson` 损坏 → `JObject.Parse` 抛异常被兜住，回落默认值后**仍能连接并读写**；
- 未知 PLC 系列（`"S9999"`）→ `Enum.TryParse` 失败，保留默认 S1200，仍能连接。

**一处测试时序修正**：`Connect()` 等到 `ConnectTimeoutMs` 就返回，底层建连可能同时失败，
直接读 `FaultCount` 有竞态——改为最多轮询 2 秒等它落账（这是测试写法问题，不是产品缺陷）。

#### 5. 订阅层接消费方：核查后判定"无合适消费方"，未强行接线

`VariableSubscription` 目前**只在测试里被使用**。逐一看过潜在消费方：

| 候选 | 为什么不行 |
|---|---|
| 监视栏（`MonitorViewModel`） | 它订阅的是 `IOutputPort`（算子输入/输出），而 `VariableSubscription` 只接受 `IVariable`；混用会变成两条路径，更糟 |
| SCADA 图元 / 趋势 | 值由宿主数据泵 `TryApplyRuntimeValue` 推送，渲染侧已有 `ChartRenderScheduler` 合并，再套一层没有收益 |
| 历史 / 报警 | 这两个消费方还不存在 |

**结论**：保留该类（契约完整、有测试），但在下一次架构评审时要么接入真实消费方、要么删除。
强行接进监视栏属于"为用而用"，会把一个简单可靠的路径拆成两条——按"最小改动 + 不制造风险"的口径不做。
