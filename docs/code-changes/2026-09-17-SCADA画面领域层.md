# 2026-09-17 SCADA 画面领域层（S1）—— 从"变量身份"走到"画面文档"

## 一、需求与决策

### 背景：S1 在整条链上的位置

前三个阶段（S0-a / S0-b / S0-c）解决的都是**变量身份**这一件事：

| 阶段 | 产出 | 一句话 |
|---|---|---|
| S0-a | `VariableId`（Guid） | 变量有了稳定身份，名字退回"给人看的标签" |
| S0-c | `IVariableRegistry` | 解析器内核：**Id 优先、名字兜底**，旧数据命中即自愈回填 |
| S0-b | `TryRename` 单一入口 | 改名能级联：连线 → 监视项 → 网络变量轮询键 |

S0 结束时留了一条明确的待办：

> 第 3 条（SCADA 画面绑定不得沿用 `BindingKey` 做键，**S2 图元落盘应存 `VariableId`**）仍未关闭，属 S1 定案、S2 落地。

**S1 就是来关这一条的**：把"画面"这件事本身建模成领域对象——画面 → 图元 → 绑定，并且让绑定从第一天起就长成"按 `VariableId` 寻址"的形状，而不是先按名字存、以后再迁移。

用户长需求里对本阶段的四条硬约束：

1. **SCADA 系统**：商业级、可扩展控件、本地/网络变量、模块化；
2. **架构**：分层、关注点分离、设计模式、封装，**以长期可扩展性为最高优先级**；
3. **测试**：每个阶段都要"暴力测试"（压力/单元/集成/最大负载）；
4. **集成**：与既有数据源无缝对接、API 明确。

### 决策一：分层与依赖方向（本阶段最不能错的一件事）

```
Core（领域模型 + 序列化 .vms）  ──引用──▶  Scada（画面领域层，新）
        ▲                                        ▲
        │                                 （S2 才建）
  VisionMaster（WPF 应用）              Scada.Controls（图元控件库）
```

具体规则：

| 规则 | 理由 |
|---|---|
| `VM.Scada` 是 **`net9.0`（不带 `-windows`）、不引用 WPF** | 领域层不该知道"怎么画"。颜色用 `#AARRGGBB` 字符串承载，转 `System.Windows.Media.Color` 的活留给 S2。副作用是这一层能在无界面场景（网关/报表/离线校验）复用 |
| `VM.Scada` **不引用 `VM.Core`** | `SolutionModel` 要持有画面文档（`Core → Scada`），反向引用会成环 |
| `VM.Core` → `VM.Scada` 方向唯一 | 方案文件（.vms）里要装画面，这是"谁持有谁"的必然结果 |
| 图元类型用 **`TypeKey` 字符串 + 属性袋**，不用派生类 | 图元库要不断扩：派生类方案每加一个图元就改一次领域层；而且多态会往 .vms 写 `$type`，正好踩在 `SafeSerializationBinder` 白名单的校验路径上 |
| 属性袋值**一律 string**，不做类型化 | 领域层不该解释"`#FF0000` 怎么变成画刷"，转换规则归 S2 的描述符，一处解释、一处使用 |
| 模型里**不放编辑器态**（`IsSelected`、缩放比例、视图偏移） | `FlowModel` 的教训：把编辑器/运行态混进模型，就得维护一份"这些变更不算变更"的排除名单，名单漏项时鼠标划一下就把版本号刷爆 |

### 决策二：画面 → 图元 → 绑定，三层各管什么

| 类 | 职责 | 关键定案 |
|---|---|---|
| [ScadaDocument.cs](file:///e:/VM/VisionMaster-W-master/Scada/Models/ScadaDocument.cs) | 画面集合 + 结构版本号 | `SchemaVersion` 为将来的格式迁移留位；`AddPage()` 自动命名 `画面_N` 且**跳过已占用序号** |
| [ScadaPage.cs](file:///e:/VM/VisionMaster-W-master/Scada/Models/ScadaPage.cs) | 一块设计画布：尺寸/背景/网格 + 图元集合 | 尺寸语义是**设计像素**，运行态"适应窗口"的缩放是视图侧的事——存进模型就会出现"同一份画面在不同机器上落盘不同内容" |
| [ScadaElement.cs](file:///e:/VM/VisionMaster-W-master/Scada/Models/ScadaElement.cs) | 身份 + 几何（强类型）+ 类型键 + 属性袋 + 绑定集合 | 几何写成强类型字段而不是塞进属性袋：塞进去会让"拖一个矩形"退化成字符串解析 |
| [ScadaBinding.cs](file:///e:/VM/VisionMaster-W-master/Scada/Models/ScadaBinding.cs) | 图元属性 ← 工程变量 | 寻址口径与流程连线**完全一致**：`VariableId` 权威、`VariableName` 兜底 |

几个具体判断：

- **`ScadaBinding` 不存"显示地址串"**。流程连线有 `DisplayAddress` 是因为要显示 `全局变量 (Global).PLC_Ready[2]` 这种带前缀后缀的路径；画面绑定只有一个数据源，显示出来就是变量名本身——多一个字段就多一处改名后忘记同步的地方。
- **`IsEnabled = false` 的绑定照样落盘、照样被 `EnumerateBindings()` 枚举**。联调时"临时摘掉一条绑定看现象"比"删掉再配一遍"常用得多；停用只是运行态跳过。
- **`Num/Name` 分工**：`VariableId` 是机器寻址锚点，`VariableName` 是展示串 + 旧数据唯一可读键。两个都不删。

### 决策三：订阅保活三件套（照抄 `FlowModel.Steps` 的范式）

三个集合（文档.画面 / 画面.图元 / 图元.绑定）都必须满足：

```csharp
[JsonProperty(ObjectCreationHandling = ObjectCreationHandling.Replace)]  // ① 整体替换而非叠加
public ObservableCollection<T> Items { get; set; }                       // ② 带 setter 的摘/挂

[JsonConstructor]                                                        // ③ 兜底
public Ctor() { _items.CollectionChanged += OnItemsChanged; }
```

少任何一件，反序列化都会绕过 setter，集合变更通知就断了——**而且不报错**，表现为"打开方案后改图元属性，`Version` 不动"。

### 决策四：绑定变更必须往上冒两级

`Version`（画面变更计数）的语义是"文档内容真的变了"，递增规则：**图元增删 + 任一图元的任一属性变更**。

为此需要两条转译链：

| 链 | 做什么 | 为什么不能省 |
|---|---|---|
| `ScadaElement.OnBindingsChanged` → `RaisePropertyChanged(nameof(Bindings))` | 把"绑定集合内容变化"（`CollectionChanged`）转译成"`Bindings` 属性变更" | 上层只对每个图元挂了一个 `PropertyChanged` 处理器，没再往"每个图元的每个子集合"挂一层。要维护嵌套两级订阅，漏摘一次就是泄漏 |
| `ScadaElement.OnBindingPropertyChanged` → `RaisePropertyChanged(nameof(Bindings))` | 单条绑定的属性变更（换绑变量、改格式串、启停用）同样往上冒 | 少了它，`Version` 只能表达"绑定条数变了"，表达不了"绑定内容变了"——变量改名刷了一遍绑定、或用户换了绑定变量，**脏标记都不动**，于是"改了却没提示保存"、"运行态以为绑定表不用重建" |

### 决策五：`ScadaPage.FindElement` 走索引（本阶段压力测试逼出来的）

`FindElement` 的调用方全是"**高频 + 按 Id 单点取**"：S3 编辑器选中/命中测试、S4 运行态按绑定目标取图元。线性扫描在万级图元下单次就是一万次 Guid 比较（压力断言实测 **20 万次查询 10.9 秒**）。

处理方式与 `VariableRegistry` 完全一致：**加身份字典索引**（`_elementIndex`），重复身份时**保留集合中靠前者**，让解析结果不随插入顺序漂移。

## 四、压力测试暴露的两个真实缺陷（已修）

这一节是本阶段最有价值的部分——两个缺陷都**不报错**，只有压力测试才逼得出来。

### 缺陷 1：`FindElement` 是全表线性扫描

- **现象**：`[×失败] 按身份查找 200000 次全部命中且耗时 < 3000ms → hits=200000 / 10942ms`
- **根因**：`_elements.FirstOrDefault(e => e.ElementId == elementId)`，20 万次 × 1 万图元 = 20 亿次 Guid 比较。
- **为什么必须现在修而不是等 S3**：这个 API 的消费方（选中、命中测试、运行态取图元）全在鼠标/渲染热路径上。等 S3 上线才发现，症状会表现成"图元一多就卡"，且极难归因到领域层。
- **修复**：`Dictionary<Guid, ScadaElement> _elementIndex`，与 `VariableRegistry` 同一决定。三条配套规则：
  1. **重复身份保留靠前者**（口径与注册表一致），让结果不随插入顺序漂移；
  2. **图元身份被改写时同步索引**（旧数据补发 Id、将来粘贴副本重编 Id 都会走这条），否则 `FindElement(新Id)` 落空、`FindElement(旧Id)` 反而命中；
  3. **移除重复身份的靠前者时让靠后者顶上**，否则会对一个仍然存在的图元返回 null。

### 缺陷 2：`Clear()` 走 Reset 分支时订阅漏摘（两个类都有）

- **现象**：`ObservableCollection.Clear()` 触发 `NotifyCollectionChangedAction.Reset`，此时 **`e.OldItems == null`**——照着事件参数摘订阅，一个都摘不掉。
- **后果**（都是静默的）：
  - 旧图元/旧绑定被本对象**钉住不放**（泄漏）；
  - 清空后改旧图元，画面的 `Version` 照样被刷高 → **脏标记失真**（"改了就提示保存"、"运行态以为绑定表要重建"）。
- **修复**：维护 `_subscribedElements` / `_subscribedBindings` 订阅登记表，让挂/摘变成**幂等**操作；Reset 分支靠登记表全量补摘再按当前集合重挂。`Elements`/`Bindings` 的 setter 也改为"以登记表为准"摘旧订阅，避免任何历史路径留下的幽灵订阅被新集合继承。

### 附带修掉的一个 O(n²) 隐患

`EnsureIdentity` 给旧数据补 Id 时会**逐个改写 `ElementId`**，而每次改写都会触发索引维护。若每次都整表重建索引，万级画面打开会卡住数秒。处理：加 `_suspendIndexRebuild` 挂起标志，批量结束时重建一次。压力断言已守住这一条（补发 1 万条身份 **2ms**）。

> 挂起期间索引"短暂陈旧"是安全的：`EnsureIdentity` 是同步方法，期间不对外返回，没有并发读的机会。

## 五、已知边界

1. **画面领域层不参与运行态取值**。本阶段只把"画面长什么样、绑了哪些变量"建模并落盘；"怎么把变量值写进图元"是 S4 的事。
2. **绑定 Id 绝不会被凭空补发**。`EnsureIdentity` 只补画面与图元的 Id——绑定的 `Guid.Empty` 是**有含义的**（"只能按名字找"），靠加载期按名解析成功或改名级联时自愈回填，不能在这里编一个出来。
3. **自愈是"用一次才落盘"**：改名级联会把绑定补成按 Id 寻址，但**保存方案**才真正写进文件。改名后不保存直接关软件，下次打开仍是按名的旧绑定（仍能工作，只是继续走名字兜底）。
4. **`Version` 只增不减、不落盘**，且消费者尚未出现（S3 缩略图缓存/脏标记、S4 绑定表重建）。本阶段只负责如实递增，谁订阅谁解释。
5. **`TypeKey` 在领域层是纯字符串**，没有任何合法性校验——拼错的 `TypeKey` 不会在这一层报错，要等 S2 图元注册表查不到时才发现。若需要"打开方案时提示未知图元"，那是 S2/S3 的校验职责。
6. **`_elementIndex` 不落盘**（`readonly` 字段，序列化不参与），每次加载后由 setter / `EnsureIdentity` 重建。
7. **画面背景等颜色字段不做格式校验**：`Background` 存的是字符串，非法值会在 S2 转 `Color` 时才失败。
8. **重复身份（同一画面内两个图元同 Id）是"容忍"而非"禁止"**：索引保留靠前者，不抛异常。理由与 `VariableRegistry` 一致——脏数据不该让画面打不开。若将来要提示，应做成 S3 的校验警告而不是加载期异常。

## 七、下一阶段（S2）的接口约定

本阶段为 S2 预留、且已在断言中固化下来的契约：

| 约定 | 固化位置 |
|---|---|
| 图元控件由 `TypeKey` 查注册表得到，领域层不认识任何 `TypeKey` 取值 | `[M]` 断言只用 `"Basic.Rectangle"` / `"Hmi.Label"` 这类字符串，模型侧零分支 |
| 图元特有属性一律走 `GetProperty(key, fallback)` / `SetProperty(key, value)` | `[M]` 属性袋四条边 |
| 绑定的 `TargetProperty` 是属性描述符声明的名字，领域层不解释 | `[O]` 断言中往返保留但不校验合法性 |
| 颜色等 WPF 类型由 S2 从字符串转换，领域层不引入 `System.Windows.Media` | `VM.Scada.csproj` 的 `net9.0`（无 `-windows`）本身即是约束——一旦有人引了 WPF，工程就编不过 |
