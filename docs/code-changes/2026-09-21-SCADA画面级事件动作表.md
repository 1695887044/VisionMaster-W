## 一、需求与决策

### 1. 需求

路线图 §六 风险登记里挂着一条：

> **画面级事件钩子的动作表无法在界面编辑** | 画面级动作只能手改 `.vms`，易错且静默丢字段

症状很具体：`ScadaPage.EventHooks` 从 S5 起就是通用集合（`Loaded` 由运行态首帧画完后上报，S8 起 `Unloaded` 也在停止 / 切走这一页时真发），但**界面只给了它一个单勾选框**——勾上能建钩子，钩子下面的动作表却无处可编。用户想"打开这一页时读一遍变量"，只能拿文本编辑器去改 `.vms`；改错字段名不报错，运行时静默什么都不发生。

原处置写的是"把 `ScadaPagePropertyRow` 改成 `IsCompositeEditor`"。真正落地时换了个更彻底的做法：**不让面板认两个具体类型，而是让两种宿主共有一个抽象**。图元与画面本来就是"宿主 + 事件 + 一串动作"这同一件事，只是宿主不同；抽一个 `IScadaEventHost` 之后，事件行只需**一份**实现。

### 2. 决策清单 —— 领域层：抽 `IScadaEventHost`

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| H-1 | 抽什么 | **接口**（`EventHooks` / `FindEventHook` / `GetOrAddEventHook` / `AddEventHook` / `RemoveEventHook` / `BeginEdit`），不抽基类 | 两个类各自还继承着 `ScadaModelBase`；而"能挂钩子"并非每个模型都成立（图层就不能）。塞进基类等于给所有模型发一张它们用不上的能力票 |
| H-2 | 接口住哪一层 | **领域层**（`Scada/Models/`） | 六个成员全是领域概念（钩子、事件、变更作用域），一个 WPF 类型都没有。依赖方向不变（`Core → Scada → Scada.Controls → VisionMaster`），面板只是它的一个消费者 |
| H-3 | 为什么不是"面板认两个具体类型" | 认类型就要在**每一个**用到钩子的地方写分支（建钩子、增删动作、调序、选变量、选画面……），分支数随功能线性增长 | 抽象落在接口上，分支数恒为 0；`ScadaEventRow` 内部 9 处调用从 `Element.*` 改成 `Host.*`，行为逐字不变 |
| H-4 | 为什么不让 `ScadaPagePropertyRow` 加 `IsCompositeEditor` 分支 | 那会造出**第二种**事件行实现 | 事件行的全部复杂度（复合编辑区、动作表、三条命令、撤销位合并）只该有一份。`ScadaPagePropertyRow` 保持纯净——它是"读一个值 / 写一个值"的行 |
| H-5 | `BeginEdit` 为什么也放上接口 | 面板在两种宿主上做的是同一件事（**建钩子 + 塞首条动作**，用户眼里是一次操作，撤销栈里也只该有一条） | 若只能从具体类型拿到作用域，那份逻辑就又分叉了。两个实现类各自声明的方法天然满足接口成员 |

### 3. 决策清单 —— 清单归属：`ScadaPageEvents` 与 `ElementDescriptor.Events` 对位

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| L-1 | 画面事件清单放哪 | **单开 `ScadaPageEvents`**，不塞进 `ScadaPageProperties.All` | 事件不是属性。属性行是"读一个值、写一个值"，事件行是"勾上之后挂一串动作"——面板上长得就不一样。图元侧早就这么分过：事件住在 `ElementDescriptor.Events`，**不在** `descriptor.Properties` 里 |
| L-2 | 声明几条 | **只声明有人发得出来的**：`Loaded`（首帧画完后一次）、`Unloaded`（被切走 / 运行停止） | 与 `BuiltInElements` 声明图元事件同一口径。清单里出现发不出来的事件，用户配上的就是个永远不响的钩子——比"面板上没这个选项"糟得多 |
| L-3 | `ValueChanged` 为什么不在清单里 | 要等 S6 数据泵；而且它**不是画面级语义**（画面自己没有"绑定的值"） | 同上：还没接触发源的事件不许出现在任何清单里 |
| L-4 | `ScadaPageProperties` 里那条 `Loaded` 声明怎么办 | **删掉**（8 条 → 7 条） | 留着就与事件行重复：同一个"加载完成"在面板上出两行，一行是勾选框、一行是动作表，用户不知道改哪个才算数 |
| L-5 | 显示名统一成哪个 | 事件行的唯一显示名「**加载完成**」 | 原属性行显示名是"加载事件"，事件行是"加载完成"。改走事件行后自动统一；`ScadaChecks` 与 `ScadaPropertyViewModel` 里的交叉引用一并改掉 |
| L-6 | `ScadaPage.EnableLoadedEvent` 还留不留 | **留**，作为模型层便捷开关（脚本 / 模板用） | 它本来就是投影：`[JsonIgnore]`，getter = `FindEventHook(Loaded) != null`，不落盘。只是**属性面板不再经过它**，改走 `IScadaEventHost` 那套通用路径 |

### 4. 决策清单 —— 行泛化：宿主 + 分组

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| R-1 | 行依赖什么 | `IScadaEventHost Host`（不再是 `ScadaElement`） | 见 H-3。类注释里写清："下面每一个 `Host.*` 调用，在图元上和画面上走的是各自那份实现，而面板这一层一行分支都不需要" |
| R-2 | 分组写死还是给 | **构造参数**（`ScadaEventSpec(eventType, group)` 的 `Group` 也从常量改成构造参数） | 图元事件落在「事件」组（图元面板的最后一组），画面事件落在「运行」组（与「启动画面」同处——共同点是"这一页**跑起来**是什么样"）。分组是宿主的属性，不是行的属性 |
| R-3 | 两种宿主的常量放哪 | `ScadaEventRow.ElementGroup = "事件"`；`ScadaPageEvents.Group = "运行"` | 各自跟着自己的清单走，不集中到一个"分组常量表"里 |
| R-4 | 显示次序怎么定 | 组的**首现次序**决定显示次序 | 画面侧 `StartupPage` 先入行，事件行随后 → 「运行」组 = 启动画面 + 加载完成 + 卸载 |
| R-5 | 画面事件行的刷新链 | `ScadaPage.OnEventHooksChanged` → `Version++` → `RaisePropertyChanged(nameof(Version))` → 面板 `OnPagePropertyChanged` 全量 `RefreshValue()` | 与图元侧的 `RaisePropertyChanged(nameof(EventHooks))` 机制略不同，但都汇到"面板重算"这同一条路上。已验证：勾选后 `HasActions` 变真、动作表长出来 |
| R-6 | XAML 要不要改 | **零改动** | 行模板按 `IsCompositeEditor`（一个 bool）分流，不认具体类型。画面事件行白拿整套动作表 UI |

### 5. 口径沉淀

- **"事件"不是"属性"**：判定一个东西该进 `*Properties` 还是该单开 `*Events`，看的是**面板上怎么渲染**——一行输入框 vs 一块可增删排序的动作表。这不是分类癖，是渲染方式决定的。
- **宿主抽象的正确落点**：当两份实现"语义逐字一致、只差宿主类型"时，抽的是**接口**（能力），不是**基类**（身份）。基类会污染不相关类型，接口不会。
- **撤销位纪律照旧**：`ScadaEventRow.Commit` 用外层 `Host.BeginEdit("配置事件 [Event]")` 把"建钩子 + 首条动作"合成**一条**撤销位。画面侧实测标签 = `配置事件 [Loaded]`。

### 4. UI 自审（执行"UI 改动后自己审查下是否美观"这条纪律）

自审对象：画面模式「运行」组新增两行事件行之后的排版。

- **渲染路径无分叉**：`ScadaPropertyView.xaml` 的行模板分流只认一个 bool——`DataTrigger Binding="{Binding IsCompositeEditor}" Value="True"` → 换 `EventRowBody`。画面事件行是 `ScadaEventRow` 实例，`IsCompositeEditor` 为真，**渲染与图元事件行同源**。
- **模板绑的全是行自己的成员**：`EventRowBody` 只绑 `DisplayName` / `BoolValue` / `HasActions` / `Actions` / `AddActionCommand` / `Description`——没有一个成员与宿主有关，所以"画面事件行会不会长得不一样"这个问题在模板层就不存在。
- **排版一致性**：`EventRowBody` 刻意**独占整行宽度、不排标签列**（82px 标签列留给动作表就只剩一条缝）。「运行」组因此呈现为：`启动画面 [勾选框]`（普通行，标签 + 编辑器）→ `☐ 加载完成`（整行，勾上才展开动作表）→ `☐ 卸载`。这与图元面板「事件」组的观感逐字一致，不是新造的一种排法。
- **结论**：无需改 XAML，无需新增视觉断言。⑪ 段的离屏渲染截图（`scada-property-panel.png`）是**图元模式**的，画面模式新增两行不影响它——已核对确认，不跟着更新。

## 四、已知边界

1. **画面事件只有 `Loaded` / `Unloaded` 两条**：`ValueChanged` 等 S6 数据泵，且不是画面级语义；`Pressed` / `Released` 是图元级（画面没有"被点"这回事）。清单里没有的事件**不出行**——这是刻意的，见 L-2。
2. **画面级事件不支持变量绑定**：画面属性一律不给 `ƒx`（`ScadaPageProperties.All.All(s => !s.IsBindable)`），事件行同样只有勾选框 + 动作表。
3. **`EnableLoadedEvent` 成为"模型层便捷开关"**：界面不再经过它，但脚本 / 模板仍可用。它与 `FindEventHook(Loaded) != null` 恒等价（投影关系），不会不同步。
4. **画面事件行的刷新依赖 `ScadaPage.Version++`**：与图元侧机制不同（图元是 `RaisePropertyChanged(nameof(EventHooks))`）。两者都汇到"面板全量重算"，行为一致；但若将来给 `ScadaPage` 换刷新机制，**必须同时保住这条链**，否则动作表不刷新。
5. **动作表直接双向绑模型对象**（`ScadaAction`），没有中间影子状态——这是既有口径（见 `ScadaEventRow` 类注释），本轮未改。
6. **真机未验**：本轮只验到"数据通路 + 离屏渲染同源"，没有真机点一下画面事件看日志的采样。这与图元级事件的真机验收（S5 验收口径）**同一性质**，§七 收口核对表也没有为图元事件单列一行，故本轮不新增行。
7. **SCADA 新文件仍未纳入版本控制**：`Scada/Models/IScadaEventHost.cs`、`Scada.Controls/Descriptors/ScadaPageEvents.cs` 仍是未跟踪状态。**提交需用户明确授权。**
