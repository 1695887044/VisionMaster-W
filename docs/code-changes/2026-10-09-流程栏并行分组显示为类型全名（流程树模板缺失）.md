- 日期：2026-10-09
- 项目：VisionMaster（Views/ProcessView.xaml）+ FlowCanvasChecks（RenderProbe 场景 F、ProcessTreeTemplateChecks U1-U5）
- 类型：缺陷修复（类型全名上屏，与 AGENTS.md R19-R22 同类病）+ 顺带修复（分支胶囊表达式重复渲染）
- 起因：真机截图——左侧流程栏里并行分组那两行整行显示 `VisionMaster.Models.ParallelStep`，分支、图标、名字全丢

## 一、现象与根因

**现象**（用户截图）：流程栏树里普通算子（图像采集_0 / 胶路检测_0）是"图标色块 + 名称 + 副标题"卡片，If/While/For 是"色条 + 图标 + 类型名 + -[ 别名 ]"组头，唯独并行分组是**光秃秃一行类型全名**，且其下两条分支（分支 1/分支 2）与分支内算子一个都不显示。

**根因一句话**：`ProcessView.xaml` 的步骤树是**按模型类型挂隐式模板**的（`DataType="{x:Type models:...}"`），仓库为 ActionStep / ConditionStep / WhileStep / ForStep / StepCollection 都写了模板，**唯独漏了 ParallelStep**。WPF 找不到模板就回退默认模板，而默认模板就是 `ToString()` → 类型全名上屏；`HierarchicalDataTemplate` 缺失同时意味着没有 `ItemsSource`，所以分支整体不渲染。

- 现场：`VisionMaster\Views\ProcessView.xaml`（`TreeView` 绑 `Workspace.CurrentFlow.Steps`，资源区 5 个类型键模板）
- 为何"新加的容器类型"必踩：模板是**类型键隐式匹配**，不走 `DataTemplateSelector`，新增模型类型时没有任何编译期或运行期提示——与 R19-R22 的 GridView 事故同族（那次是隐式样式顶掉模板，这次干脆没有模板），都是"屏幕上是类型全名/布局失踪"这一族症状。

## 二、修复（VisionMaster\Views\ProcessView.xaml）

1. **补 `ParallelStep` 的 `HierarchicalDataTemplate`**（`ItemsSource="{Binding Children}"`）——与 If/While/For 三个组头同构：色条 + 图标 + 加粗类型名"并行分组" + `-[ 别名 ]`；身份色取**画布泳道同源的蓝 #3B82F6**（画布并行泳道 = `FlowCanvasLane*` 蓝家族），与灰(If)/橙(While)/绿(For) 三兄弟区分。分支、分支内算子由既有 `StepCollection`/`ActionStep` 模板接续渲染。
2. **并行分支胶囊的蓝身份（压掉循环绿）**：并行分支 `BranchType=Default`，与 For/While 循环体同型 → 默认会被 `Default` 触发器涂成"循环绿"。加两条 DataTrigger 绑定
   `{Binding DataContext.ExecutionMode, RelativeSource={RelativeSource AncestorType=TreeViewItem, AncestorLevel=2}}`（`AncestorLevel=2` = 胶囊所在分支卡片的**父容器项**；`ExecutionMode` 只有 ParallelStep 有，其它容器取不到值=触发器不生效）→ 蓝底/蓝点。放在 Default/WhileLoop 之后（后写者赢）、`IsConditionMissing` 红灯之前（红灯仍最高优先级）。零转换器实现，已在场景 F 出图中实测生效（胶囊是蓝不是绿）。
3. **顺带修复：分支胶囊表达式重复渲染**（同视图既有缺陷，出图时抓到）：胶囊原来同时绑 `DisplayName`（`StepCollection` 已把"分支名 + [ 表达式 ]"拼好）与独立的 `ExpressionText`（再拼一遍 `[ 表达式 ]`）→ 已绑定条件的 If 显示成 `If [ Score > 80 ] [ Score > 80 ]`（未绑定条件的现场只显示 `If [ 未绑定条件 ]`，所以此前没人发现）。**删除 `ExpressionText` 元素与其 3 处 Foreground 触发器**，胶囊文案统一由 `DisplayName` 一处提供。

## 四、守门（FlowCanvasChecks\ProcessTreeTemplateChecks.cs，U1-U5）

- 口径：**VM.Core 里所有非抽象 `StepModel` 子类都必须在 ProcessView.xaml 里有 `DataType` 模板**（静态扫描，进程内可跑，进常规 gate 基线）。
- 例外清单（显式声明 + 反向断言）：`BreakStep` / `ContinueStep` / `ReturnStep` **UI 永不实例化**——工具箱 `BuiltIn_Break/Continue/Return` 一律落 `ActionStep`（`ProcessViewModel` 拖入只按 `IsContainer` 分派：容器认 While/For/Parallel 三个 BuiltIn 名、其余容器兜 If、非容器全走 ActionStep），编译期按 `PluginTypeName` 特判（`FlowCompiler`）。U3 反向扫描 `ProcessViewModel.cs` 不得出现 `new BreakStep(` 等构造——一旦 UI 开始 new 它们，清单必须同步补模板，否则树里又裸奔类型全名。
- 已知边界：U1-U5 是 XAML 文本级扫描，不替代出图；"模板存在但视觉写错"仍要场景 F 这类渲染复核兜底。

## 五、第二起（同日追报）：双击"分支卡片"弹出空窗/上个算子的参数窗

**现象**（用户追问"为什么并行分支 点击单个分支 还会出弹窗?"）：双击并行分组下的"分支 1"，弹出一个**空白**的「条件逻辑配置中心」，或弹出**上一个选中算子**的插件参数窗。

**根因链（三处口径各说各话）**：
1. 树的双击链是 `TreeViewBehavior.TreeView_MouseDoubleClick`：先 `item.IsSelected = true` → 经 `BindableSelectedItem` 写回 VM → 再执行命令（命令按"当前选中项"取参）；
2. `ProcessViewModel.SelectStep` 的 setter **拒绝 StepCollection**（`if (value is StepCollection) return;`）→ 写回被静默吞掉 → 命令拿到的是**上一个选中算子**（错靶）；
3. `StepParameterDialog.Open` 对"非 ActionStep"**一律兜底**弹 `ConditionEditor`，而 `ConditionEditorViewModel.OnDialogOpened` 只认 `ConditionStep`/`ForStep`（`TryGetValue<StepModel>("Node")` 拿不到就 `return`）→ 并行分组/分支卡片进来就是一个空窗。

顺带发现：`Rename`/`EditComment` 两个分支对 `CurrentSelectedStepModel`（`SelectStep as StepModel`，分支卡片进来就是 null）**没有空值保护**，右键重命名一个分支会直接空引用。

**修法（三道闸，任何一道单独成立都能挡住症状）**：
- **视图侧**（`ProcessView.xaml.cs`）：预览鼠标事件拦掉分支卡片——左键不选中、不派发双击（WPF 里阻止 TreeViewItem 选中与其后双击派发的标准做法：处理隧道阶段的 Preview 事件即压制随后的冒泡配对事件），右键不出菜单（菜单动作全是算子级的，对分支没有意义，出了只会打在旧算子上）。判据 = 命中的 TreeViewItem 的数据项是 `StepCollection`（命中元素取 `OriginalSource`，取不到时退回 `Source`——手工 RaiseEvent 回放只有 Source）。
- **VM 侧**（`ProcessViewModel.SelectStep`）：收到 `StepCollection` 不再"保留旧值"，而是**清空选中**——不留旧算子当错靶（`Workspace.CurrentStep` 一并归 null，`SwitchStep(null)` 本就是显式容忍的）；`Rename`/`EditComment` 补空值保护。
- **对话框分派侧**（`StepParameterDialog.Open`）：返回值改为"是否真弹了窗"，只有 `ActionStep`（插件参数）与 `ConditionStep`/`ForStep`（条件编辑器）两条出口，其余**不弹窗**；调用方据此给非模态提示——双击并行分组当时提示「并行分组暂无参数面板：执行模式与失败聚合按默认（并行执行 + 继承全局），分支不做条件判断」。**2026-10-09 同日后续：该提示已随「并行分组参数面板」落地而删除**（`ProcessViewModel.ModuleParameters` 不再出提示；双击组头改走新增的第四条出口 `ParallelStep → ParallelGroupConfig` 打开面板，面板记录见 `docs\code-changes\2026-10-09-并行分组参数面板（草稿事务-白名单分派-分支卡片交互闭环）.md`）。

## 六、第二起验证

- **断言 V1-V5**（`ProcessTreeInteractionChecks`，IDialogService 形状桩只记录"弹了哪个窗"，不真开窗）：
  V1 并行分组 → `ParallelGroupConfig`（返回 true；面板落地前口径为「不弹窗（返回 false）」，2026-10-09 改判）；V2 分支卡片 → 不弹窗；V3 If 容器 → `ConditionEditor`（原路径不回归）；V4 For 容器 → `ConditionEditor`（For 模式并同一弹窗）；V5 选中分支卡片 → `SelectStep` 与 `Workspace.CurrentStep` 都清空（不留旧算子当错靶）。
- **出图自检**（渲染探针场景 F 内，stdout 证据行）：`[render][check] 分支卡片左键被拦截=True，分支项被选中=False` —— 向树入口回放一次 `PreviewMouseLeftButtonDown`（Source 指向被点的分支文字元素；该事件是 **Direct**，按钮专用事件按元素逐个 crack，合成事件只能投给挂处理器的那个元素，所以按"处理器实际看到的那份 args"回放），处理器判为分支卡片并置 Handled。**该自检证明的是处理器判据，不是完整鼠标链路**：2026-10-09 面板轮次已把场景 F 自检升级为三条**差异判据**——分支卡片必须被拦 / 分支箭头必须放行 / 普通算子卡片不得误拦（stdout 证据行 `分支卡片被拦截=True（期望 True）；分支箭头被拦截=False（期望 False）；算子卡片被拦截=False（期望 False）`）；「分支卡片不选中、不派发双击」的完整生产链路（`TreeViewBehavior` 选中写回与双击派发、分支箭头展开）属**真机核对项**——把当轮输出行 `分支项被选中=False` 读作「生产路径上已验证」会超出该自检能证明的范围，审查已指出并据此改准。
- **回归**：全量 gate 1732/4（其余断言零回归）。
