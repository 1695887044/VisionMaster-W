## 一、需求与决策

### 1. 需求

S11-b 之后报警引擎已经在真机上跑起来了：越限会激活、会落盘、报警条会闪。但**用户看不到"这次运行一共报过什么"**——报警条只显示当前还挂着的（`MaxRows` 行），一确认就消失，一恢复就消失。现场真正的用法是收班时坐下来翻一遍："这个班报了几条？哪几条我还没确认？严重的那几条导出来交给设备科。"

这一阶段交付三样：

1. **报警历史面板**：本次运行的全部记录，最新在前，能搜、能筛、能逐条确认、能一键确认当前列表；
2. **CSV 导出**：把**当前可见**的那些导成文件带走（与按天流水账同一套列）；
3. **`[AH4]` 断言段**：把上面两样的行为逐条钉住。

### 2. 决策清单（C-5 ~ C-18）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| C-5 | 面板形态 | 右侧 **640 宽覆盖层**抽屉，五段式：标题 / 筛选条 / 七列 `GridView` / 提示 / 底栏 | 历史面板是"偶尔翻开看一眼"，不是常驻视图。做成 `Grid` 的**独立列**会挤压画布 → 触发 `SizeChanged` → `FitToScreen` → 整个画面重新缩放，操作员一开面板画面就"跳一下"。覆盖层不动画布一寸 |
| C-6 | 入口 | 运行窗口**顶条一个 `ToggleButton`**（带未确认徽标），不进属性栏 | 用户明确要求。报警是运行态的事，入口就该在运行态顶条上；属性栏是组态态的东西 |
| C-7 | 数据来源 | 引擎 `RecentRecords(MaxRows = 2000)`，**整表重建**；面板自己不存历史 | 引擎的 `_history` 才是唯一真相（它同时喂着落盘端）。面板再存一份就必然出现"两份历史对不上" |

| C-9 | 时长刷新 | 挂**节拍**，每满 1 秒对每行调一次 `RefreshDuration()`（只动 `DurationText` 一个属性） | 整表里只有"还没恢复那条"的时长会随钟走。为一行数字整表重建，既会丢选中（行对象全换）又会闪一下 |
| C-10 | 行模型 | 独立类 `ScadaAlarmHistoryRow`：记录是**事实**（枚举 / UTC / 枚举），行上是**画法**（色 / 文案 / 能不能点） | 与 `AlarmBannerRow` 同一条理由：换算留在类里，一次构造就能断言。靠转换器 + 跨层 `RelativeSource` 去凑，在无窗口的断言环境里都不可靠，出错还是"静默显示成默认色" |
| C-11 | 筛选 | 一档 = **文本 + 谓词**（`ScadaAlarmHistoryFilter`），状态 5 档、严重度 4 档，首档都是"全部" | "未确认"跨 `Active` / `Recovered` **两态**，那不是任何单一字段的等值比较。用"枚举 + switch"则每加一档要同时改三处，漏一处就是"选了没反应" |
| C-12 | 选中项找回 | 整表重建后按 **`RecordId`** 找回 | 重建后行对象全是新的，按引用找必然丢选中 |
| C-13 | 单条确认 | 按 **`AlarmId`**（**定义**身份）交给引擎 | 引擎 `Acknowledge(Guid)` 就是按"哪条定义"找它**当前**那条记录的；而 `CanAcknowledge` 为真的行必定还是槽里的当前记录，所以找回去命中的正是操作员点的那一行 |
| C-14 | 已清除的旧记录 | **不给**确认按钮 | 否则会出现"点一条三个月前的记录，确认掉的是刚刚那条" |
| C-15 | 全部确认 | 先 `Rows.ToList()` **快照**再遍历；动手之前**二次确认**；确认口由视图层注入 `Func<string,bool>` | ① 确认会抛事件、事件会请求重建，依赖"恰好还没执行"是脆的；② 一次确认十几条**不可撤销**（确认时间戳一落就没有"撤销确认"这条路），而按钮就在"导出"旁边，手快的人会点错 |
| C-16 | 导出范围 | 导**当前可见列表**（`Rows`），不是全量 | 现场最常见的用法是"筛出这个班次的严重报警，导出交班"。导全量再让他在 Excel 里筛，等于把筛子推给了别人 |
| C-17 | 导出失败 | **不抛**，返回 `false` + `out string? error`，只在底栏留一句原因 | 异常从命令里漏出去会变成未处理异常弹框，而现场只需要一句提示 |
| C-18 | 导出格式 | 与按天流水账**逐字节同构**（同一 `ScadaAlarmHistoryWriter.Export`、同 13 列、同 BOM、同转义） | 两份文件拼起来看不能有一列对不上；命名也复用 `SuggestFileName`，放回 `Alarms` 目录不会与历史文件打架 |
| C-19 | 导出按钮 | 走 `Click` 而不是绑命令 | `SaveFileDialog` 是 WPF 的东西，**不该**出现在视图模型里（视图模型要能在无窗口的断言环境里跑，那里弹不出对话框）。于是"选路径"与"写文件"两件事各自可测 |
| C-20 | 换挂 / 退挂 | `Attach(null)` 清表并回到"本次运行还没有报警记录。"；重挂同一上下文 `ReferenceEquals` **短路** | 一次运行一套引擎+节拍（`ScadaRuntimeContext`），换挂必须整体换；短路防"一次报警触发两遍重建" |

### 3. 本阶段修掉的三个缺陷

#### ① XAML 编译期 `MC3024`：状态列的 `TextBlock` 同时写了 `Style` 属性与元素

- **症状**：`ScadaAlarmHistoryView.xaml` 编译报 `MC3024: "Style" 属性已设置`。
- **根因**：状态列既要套一个通用样式、又要给这一列单独覆盖前景色，于是写成了 `<TextBlock Style="..." ><TextBlock.Style>...</TextBlock.Style></TextBlock>`——**同一个属性被设了两遍**。
- **修复**：删掉属性形式的那一个，只留元素形式（样式内部再 `BasedOn` 通用样式）。

#### ② XAML 编译期 `MC3000`：注释里出现了 `---------`

- **症状**：`MC3000: "-------" 不是有效注释`。
- **根因**：XML 注释里不能出现 `--`。分隔线习惯性写成了长横线串。
- **修复**：注释内的分隔线改用 `========`。

> 两个都是**编译期**拦下的，代价只是改一行——但如果当初把面板写成"运行时才解析的字符串模板"，同样的问题会变成运行时静默失效。

#### ③ 断言自身缺陷：一条**测不到东西**的假断言（"节拍把持续时长推着走"）

- **症状**：`[AH4]` 首跑 `通过 1113 / 失败 1`，唯一失败是 `节拍把「持续时长」推着走 → 6小时22分 → 6小时22分`。
- **根因（两层）**：
  1. `DurationText` 在 **≥1 小时**那一档渲染为 `"{h}小时{m}分"`——**没有秒**。而假时钟把记录钉在 6 小时前，所以 1 秒的增量恰好落在被舍掉的那两位上；
  2. `ScadaAlarmRecord.Duration` 用的是**真实 `DateTime.UtcNow`**（`(_recoveredAtUtc ?? DateTime.UtcNow) - ActivatedAtUtc`），注入的假时钟管不到它——所以时长确实在走，只是**显示上看不见**。
- **修复**：这条断言不能删（"时长会不会自己走"是这格字段存在的唯一理由），要**换个能看见的位置**：换挂那一轮改用贴着真实此刻的时钟（`DateTime.UtcNow.AddSeconds(-90)`），使时长落在 `"X分Y秒"` 档——这一档每秒都变。修完读数为 `1分30秒 → 1分31秒`。

> 这条值得单独记一笔：**"测不到"和"没通过"长得一模一样**。若当时顺手把它删了，`RefreshDuration` 这条链就再也没人钉——而它一旦断，现场看到的正是最像"软件卡住了"的那种症状。

## 二、为什么这么设计（逐条展开）

### 1. 为什么是覆盖层抽屉，而不是分栏（C-5）

```
   分栏（会挤压画布）                        覆盖层（不动画布一寸）
   ┌────────────┬─────────┐                ┌─────────────────────────┐
   │            │         │                │      画布（宽度不变）    │
   │   画布     │ 历史面板 │                │   ┌───────────────┐     │
   │  （变窄）   │         │                │   │  历史面板 640 │     │
   │            │         │                │   │   （浮在上面） │     │
   └────────────┴─────────┘                └───┴───────────────┴─────┘
        ▼                                        ▼
   SizeChanged → FitToScreen                画布尺寸没变 → 不缩放
   打开面板时整个画面"跳一下"                打开面板时画面纹丝不动
```

关键在**不参与画布的测量**：把面板声明成 `Grid` 里与画布**同一格**的后声明子元素（同一格内后声明的画在上），而不是新加一列。加列或改 `Margin` 都会让画布 `SizeChanged` → `FitToScreen` → 整个画面重新缩放。

### 2. 为什么整表重建，而且必须合并（C-7、C-8）

```
   不合并：一条报警一次重建                合并：一轮消息循环只重建一次
   报警① ──▶ 重建 2000 行 ──▶ 集合变更    报警① ─┐
   报警② ──▶ 重建 2000 行 ──▶ 集合变更    报警② ─┼─▶ RequestRefresh()（只排一次）
   报警③ ──▶ 重建 2000 行 ──▶ 集合变更    报警③ ─┘        │
   ...                                    （十余次）      ▼
   报警⑫ ──▶ 重建 2000 行 ──▶ 集合变更           重建 2000 行（一次）
   = 12 次重建 + 12 次 CollectionChanged 风暴   = 成本与报警条数无关
```

`RequestRefresh()` 里那个 `_refreshPending` 标志是合并的全部机关：已经在排了就**直接返回**，排在 `DispatcherPriority.Background` 上（重建是"把数据摆上屏"，不该插到输入与渲染前面——操作员正在点按钮时列表晚 10ms 刷新没人看得出来，抢在输入前面却会让手感变涩）。

**为什么宁可重建也不增量维护**：增量要维护"哪一行对应哪条记录"，而配置热重载（引擎自动重挂、旧记录成批消失）时最容易留下幽灵行。重建之后不存在"行忘了跟着记录刷新"这种陈旧显示。

### 3. 为什么只有持续时长单独刷（C-9）

整张表里其余字段都是**定值**：激活时刻、报警名、严重度、条件描述——记录一旦生成就不再变。唯一会随钟走的是"还没恢复那条"的持续时长（`"1分3秒"` → `"1分4秒"`）。

为这一格整表重建的代价是**双份**的：行对象全换 → 选中丢了；集合清空再填 → 界面闪一下。所以挂节拍、每满一秒调一次 `RefreshDuration()`：

```csharp
// ScadaAlarmHistoryViewModel.OnBeat
if (elapsed - _lastDurationRefresh >= DurationRefreshInterval)   // 1 秒
{
    _lastDurationRefresh = elapsed;
    foreach (var row in _all)          // 注意是 _all 不是 Rows：
        row.RefreshDuration();         // 被筛掉的那些一会儿筛回来时也要是新的
}
```

而 `RefreshDuration()` 落到底只是一次 `SetProperty`——**值没变就不发通知**（已恢复的记录时长是定值，算出来一样，通知数为 0）。这条被断言钉住了：没变时零通知，变了只发 `DurationText` 一个属性名。

### 4. 为什么筛选要用谓词（C-11）

```
   状态筛选要表达的东西              等值比较能表达吗
   ────────────────────────         ──────────────
   「全部状态」  恒真                  ✗ 没有"全部"这个枚举值
   「未确认」    Active ∨ Recovered    ✗ 跨两态
   「报警中」    IsActive（含已确认）   ✗ 是派生量，不是字段
   「已恢复」    == Recovered          ✓
   「已清除」    == Normal             ✓
```

五档里只有两档能用等值比较表达。所以一档 = **一行**（文本 + 谓词），加档只加一行，不会出现"改了枚举忘了改判定"这种"选了没反应"。严重度三档则**按枚举判、不按显示文本判**——文本是可改的词汇表，改名不该把筛选改坏。

### 5. 为什么确认按 `AlarmId`、选中按 `RecordId`（C-12、C-13、C-14）

两个身份是不同的东西，用错一处就是数据事故：

| | 身份 | 用途 | 用错的后果 |
|---|---|---|---|
| `RecordId` | 一次**记录** | 整表重建后找回选中的那一行 | 按引用找 → 每次重建都丢选中 |
| `AlarmId` | 一条**定义** | 交给引擎确认 | 按 `RecordId` 找 → 引擎里根本没有这个概念 |

引擎的 `Acknowledge(Guid)` 契约就是"给哪条定义，找它**当前**那条记录"。而"已清除"的旧记录**不给确认按钮**——它的 `CanAcknowledge` 为 false。这一条正是为了不出现"点一条三个月前的记录，确认掉的是刚刚那条"。

### 6. 为什么"全部确认"要问一句，而且口子由视图层注入（C-15）

**为什么问**：一次确认掉十几条是**不可撤销**的动作（确认时间戳一落，就没有"撤销确认"这条路），而按钮就在"导出"旁边——手快的人会点错。问一句的成本远低于让操作员去解释"我没看过就确认了"。

**为什么口子要注入**：`MessageBox` 在断言宿主里**根本不存在**（那里没有 `Application`）。所以视图模型收一个 `Func<string,bool>? confirm`：

```
   视图层（ScadaAlarmHistoryView）        视图模型（ScadaAlarmHistoryViewModel）
   Confirm(message)                        _confirm = confirm ?? (_ => true)
     └─ MessageBox.Show(owner, ...)         └─ if (!_confirm("确认当前列表里的 N 条报警？…"))
        MessageBoxImage.Warning                    return;
        MessageBoxButton.OKCancel
```

断言里换成"记账 + 按开关回答"，于是"问了几次、问的是什么、说不是否真的一条都不动"全部可测。图标用 `Warning` 而不是 `Question`：这是**注意**，不是"随便问问"。

### 7. 为什么导出与落盘分家，却又逐字节同构（C-16 ~ C-19）

```
   按天流水账（Append）                导出（Export）
   引擎 AlarmRaised 触发               用户点按钮触发
   一行一行追加                        一次性写整份快照
   从不覆盖                            覆盖写（用户自己选的路径）
   ────────────────┬───────────────────┘
                   ▼
        同一份 BuildRow / 同一 13 列 / 同 BOM / 同 RFC 4180 转义
                   ▼
        两份文件拼起来看，不会有一列对不上
```

两者只在**触发时机**与**写入方式**上分家（流水账是持续的、追加的、不覆盖的；导出是一次性的、覆盖的），但**格式必须同构**——否则"把导出件和流水账放一起看"这件事就不成立。

导出范围是 `Rows`（当前可见）而不是 `_all`：

```csharp
// ScadaAlarmHistoryViewModel.Export
var records = Rows.Select(r => r.Record).ToList();   // Rows 是 _all 在筛选下的投影
```

导出失败不抛：

```csharp
if (ScadaAlarmHistoryWriter.Export(filePath, records, out var error))
{
    SetNotice($"已导出 {records.Count} 条 → {filePath}");   // 导完一片安静，人不知道自己导没导成
    return true;
}

SetNotice($"导出失败：{error}");     // 异常从命令里漏出去会变成未处理异常弹框
return false;
```

### 8. 为什么退出时表要清空，而"两种空态"要分开说（C-20）

面板有**两种**空：

| 场景 | `EmptyHint` | 用户该做的动作 |
|---|---|---|
| 本次运行还没有报警记录 | `"本次运行还没有报警记录。"` | 什么都不用做（系统正常） |
| 有记录但被筛没了 | `"没有符合当前筛选条件的报警。"` | 改筛选条件 |
| 有内容 | `""`（空串，模板把它收掉） | — |

两种空态指向**完全不同的处理动作**，混成一句"没有数据"就会让人去查一个根本不存在的问题。同理，`Attach(null)` 退挂时清表回到第一态——那是"这一轮运行结束了"，不是"筛没了"。

### 2. `[AH4]` 断言段覆盖的行为（51 条，8 组）

| 组 | 覆盖 |
|---|---|
| ① 行投影（10 条） | 严重度是**中文词汇**不是枚举名；时间带日期且格式钉死 `MM-dd HH:mm:ss`（长度 14、分隔符位置）；`Detail` 与 `Record.DetailText` **同一句**（与报警条一分叉，操作员就以为说的是两件事）；状态用完整词汇；变量名落在行上；色板与报警条同一套语汇；**未知严重度回落"提示"色**（宁可低估也不谎报严重）；`RefreshDuration` 单点刷新（没变零通知 / 变了只发一个属性名）；关键字命中四样；忽略大小写与首尾空格、空关键字恒真 |
| ② 筛选档位（7 条） | 状态 5 档 / 严重度 4 档、首档都是"全部"；"全部"恒真；"未确认"**跨两态**；"报警中"含已确认、不含已恢复/已清除；"已恢复"与"已清除"互不串门；严重度按枚举判不按文本判；档位缺文本或缺谓词**当场抛** |
| ③ 串链路（10 条） | 构造必须注入 `Dispatcher`（断言宿主里没有 `Application.Current`）；挂上**立刻**读一次引擎历史（不等下一次报警事件）；最新在前；底部计数三段式；顶条徽标与"未确认"判定同源；有内容时空态是空串；关键字命中报警名 / 变量名；筛不中时的空态与"一条都没报过"**分开说**；重置筛选三样一起回默认 |
| ④ 订阅账（1 条） | 挂上正好**四条**订阅（引擎三事件 + 节拍一）——多一条就是重挂时漏摘 |
| ⑤ 确认（7 条） | 单条确认立刻给回执；确认落在引擎上且**同表其余各条不受影响**；计数与底部文案跟着重算；"全部确认"先问一句且问的正是**当前列表里待确认的条数**；二次确认说"不" → **一条都不动**；说"是" → 确认掉当前列表里全部待确认的（所见即所确认）；没有待确认的之后命令**自己灰掉** |
| ⑥ 导出（6 条） | 导出与按天流水账**逐字节同构**（与 `ScadaAlarmHistoryWriter.Export` 的产物做 `SequenceEqual`）；表头 13 列；带 UTF-8 BOM；成功在底部留一句回执并说清导了几条；导的是**当前可见**而不是全量（筛出 1 条只导 1 条）；失败**不抛**、只在底部留一句原因 |
| ⑦ 换挂与收场（3 条） | 重挂**同一**上下文不重复订阅（短路）；换挂到新一轮上下文 → 上一轮那套**一条订阅都不留**、新一轮各就各位；换挂后表里是**新一轮**的记录；退挂 → 表清空回到"本次运行还没有报警记录。"；收场后引擎与节拍的订阅者**都回到零**（断言自己不留尾巴） |
| ⑦-b 节拍推时长（3 条） | 还没恢复那条的时长**自己会长**（`1分30秒 → 1分31秒`）；**单点刷新**——行对象还是原来那个、整表没重建（选中与滚动位置不会被冲掉）；节拍只碰时长，报警名/状态/计数一个都没被改动 |

**为什么要另起一条 STA 线程**：面板里包 `DispatcherTimer`（节拍）与 `ObservableCollection` 的变更通知，与图元控件同一房间要求。照 `ElementControlChecks` 的样板另起 STA 线程跑，异常存进 `failure` 后 `Join` 回主线程判定。`PumpDispatcher(int ms)` 把消息循环推起来，让 `DispatcherTimer` 真的跳够几拍、也让 `BeginInvoke(Background)` 的重建真的执行。

### 3. 本轮断言"抓到东西"的地方

`[AH4]` 首跑是 `通过 1113 / 失败 1`，唯一那条失败抓出的不是产品 Bug，而是**断言自己测不到东西**——见 §一.3.③。修正后 `1分30秒 → 1分31秒` 一次通过。

这条比抓到一个产品 Bug 更值得记：**"测不到"和"没通过"长得一模一样**，顺手删掉就等于给 `RefreshDuration` 这条链留了个永久盲区。

## 五、已知边界与欠债

| # | 边界 | 说明 |
|---|---|---|
| 1 | **真机视觉未复核** | 无窗口环境下量不到：抽屉滑出/收起的手感、七列在 640 宽里的实际观感、`GridView` 表头样式、未确认徽标与其它顶条元素是否挤。**s10c-4 的两项待核（锁角标 vs 诊断角标是否重叠、单击整组/框选单个的不对称）仍挂账** |
| 2 | **报警条点行确认未做** | `AlarmBannerRow.Record` 已留引用、`ScadaAlarmEngine.Acknowledge(Guid)` 已就绪，缺的是点击命中测试与 `DataContext` 回溯。历史面板已能确认（本阶段补上），报警条那一侧仍欠 |
| 3 | **面板不显示"上一次运行"的记录** | `Attach(null)` 退挂即清表——历史面板只覆盖**本次运行**。跨运行查询要靠落盘的 CSV（`Alarms\AlarmHistory-*.csv`），本阶段没有做"从文件回读"的入口 |
| 4 | **`MaxRows = 2000` 是硬上限** | 与引擎的内存历史上限对齐。一屏摆不下的那些不显示，也没有"翻页/加载更多"。当前量级（几十条）无影响 |
| 5 | **导出没有列选择** | 固定 13 列。现场若要"只要三列"的报表，得另做（或复用 Excel 报表插件的通路） |
| 6 | **提示语 8 秒自动收** | `NoticeLifetime = 8s` 挂在节拍上。若节拍停了（运行收场），提示语不会自己消失——但那时面板本来也退挂了 |
| 7 | **未确认徽标 `>99` 收成 `"99+"`** | 刻意：徽标是给"有没有"看的，让它跟着数字变宽会把顶条挤歪，三位数以上的精确值在面板里一眼就有 |

### 设计上的刻意取舍

- **面板不自己存历史**（C-7）：引擎的 `_history` 是唯一真相。代价是"面板显示什么"完全取决于引擎的历史保留策略（`MaxHistoryRecords = 2000`），好处是永远不会出现两份对不上的历史。
- **确认不可撤销**（C-15）：确认时间戳一落就没有回头路，所以"全部确认"必须二次确认。将来若要做"撤销确认"，得在引擎里加一条态迁移，那是新需求不是补丁。
- **导出与落盘共用一份格式代码**（C-18）：好处是永远同构；代价是将来若"导出件要加一列"而"流水账不能动"，就得先把 `BuildRow` 拆开。
