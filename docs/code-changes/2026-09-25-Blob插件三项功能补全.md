# Blob 缺陷检测插件功能补全：运行显示窗口 / 缺陷编号 / 4 通道支持

日期：2026-09-25
范围：`Plugins/Plugin.BlobDetect`（插件 + 视图）、`FlowCanvasChecks/BlobDetectChecks.cs`

## 一、背景：评审发现的三项功能缺口

对照仓库内其他出图插件（图像采集 / PreProcessing / ImageScript / CSharpScript / CreateRoi）
与产线常规用法，Blob 插件有三处功能缺口：

1. **正式运行时标注图不发布到主界面视图窗口** —— 其他出图插件都有 `DisplayViewIndex`
   并在运行末尾 `PublishPreview`，Blob 只有配置对话框里的预览，产线操作员在主界面看不到检测结果。
2. **标注图不画缺陷编号** —— 「输出排序」的文案承诺"便于人工核对编号"，但渲染器只画红色轮廓 +
   左上角汇总文字；报表说 3 号超标时操作员在图上找不到 3 号，排序链路断在最后一步。
3. **4 通道图（RGBA/BGRA，常见于相机 SDK 与带透明通道的解码）直接拒绝** ——
   报"不支持的图像通道数：4"，而 alpha 对亮度没有贡献，本不该让整次检测失败。

## 二、改动明细

### 1. 运行显示窗口（对齐图像采集插件同一口径）

- `BlobDetectPlugin.cs`：新增 `[StepConfig] DisplayViewIndex`（默认 1 = 1 号窗口，0 = 不发布）；
  `RunAlgorithm` 在端口赋值完成后，若 `DisplayViewIndex > 0` 且标注图非空，
  `this.PublishPreview(result.AnnotatedImage, DisplayViewIndex)`。
  **NG 也发布**——恰恰是判 NG 时操作员最需要立刻看到缺陷在哪。
  总线无订阅者 / 无 WPF 宿主时是 no-op（`GlobalEventBus.PublishOnUIThread` 已有降级），离线跑流程不受影响。
- `AreAllParametersAtFactoryDefault` 纳入 `DisplayViewIndex`：保持"任一参数改过就不再自动适配"的契约完整。
- `BlobDetectView.xaml`：⑤ 输出区新增「运行显示窗口」下拉（0~9，0 显示为"不显示"），
  控件形态与图像采集插件一致（int 数组保证 SelectedItem 回显匹配）。

### 2. 逐缺陷编号（AnnotationRenderer）

- 新增 `DrawDefectNumbers`：描边之后、汇总文字之前，对每个缺陷在其**外接矩形中心**
  （不是质心——细长/L 形区域的质心会漂出区域）写 1 基编号，红字、无白底框（白框会把小缺陷整个盖住）。
- **顺序即输出顺序**：传入的就是排序后的 `defectsObj`，图上编号与 `CenterRows / DefectAreas`
  等端口逐项对应，"报表 3 号"与"图上 3 号"是同一个。
- 贴边缺陷的锚点夹进图内；单个编号写失败只丢号不丢图（try 在循环体内）。
- **坐标系必须用 `"window"` 而不是 `"image"`**（本轮实测踩坑，见第三节）：
  窗口按底图尺寸 1:1 创建、底图原点在 (0,0)，两种坐标天然等价；
  但无显示会话环境里 buffer 窗口的 disp_obj 不生效、image part 不成立，
  `"image"` 坐标的 disp_text 会整段画不出来，`"window"` 则总是可靠（左上角汇总文字一直用的就是它）。

### 3. 4 通道图支持

- `TryToGrayImage`：`channels == 4` 时取前 3 通道（`access_channel` × 3）按彩色转灰度
  （`rgb3_to_gray`），alpha 忽略。注意 HALCON 只认通道序不认颜色语义，
  BGRA 输入时加权里 R/B 对调——得到的仍是对比度保留的有效灰度图，对 Blob 检测无实质影响。
- `BuildDisplayBase`：4 通道先经新增的 `DropAlphaChannel`（`append_channel` 两步拼出 3 通道）
  再走显示流程——`disp_obj` 只稳妥支持 1/3 通道，4 通道直接画会报"通道数不对"，
  整张标注图就没了。检测路径（TryToGrayImage）与显示路径（BuildDisplayBase）各修各的，互不影响。
- 错误提示更新为「仅支持 1 通道灰度、3 通道彩色或 4 通道 RGBA/BGRA」。

## 三、验证（冒烟 + 实测探针）

### 新增断言（`BlobDetectChecks.RunMultiChannelAndNumbering`）

- 【多通道】3 通道输入检出与 1 通道一致（同场景 R=G=B 复制，加权求和后数值不变）；
- 【多通道】4 通道输入检出与 1 通道一致（第 4 通道当 alpha，被忽略）；
- 【多通道】4 通道输入的标注图照样生成（渲染零告警——底图丢 alpha 这条路真的通了）；
- 【编号】缺陷 C（圆心 (150,150)、半径 8）的编号锚点开窗内红主导像素 ≥3
  （红字指纹：R − max(G,B) > 40；不写编号时该窗内只有均匀底色，为 0）。
  带环境闸门：离屏窗口若连文字都不渲染（整图均值 ≈0）则记跳过，不制造假失败。

### disp_text "image" 坐标不渲染的定位过程（对后续开发有用）

编号首版用 `"image"` 坐标系，断言红像素 = 0。忠实复现渲染序列的探针给出定案：

```
probe=image=0 window=17
```

同一 buffer 窗口、同一 disp_obj 铺底之后：`"image"` 坐标的文字画不出来，
`"window"` 坐标的文字正常渲染。原因是该环境 disp_obj 不生效、image part 不成立；
而本渲染器窗口尺寸 ≡ 底图尺寸，`"window"` 坐标即像素坐标，任何环境下都正确。
编号实现已改为 `"window"`（与左上角汇总文字同款），断言随之通过（红像素 = 7）。

### 全量冒烟

`FlowCanvasChecks` 全套：**644 通过 / 15 失败**；Blob 段（含 4 条新增）零失败。
15 条失败全部为既有问题，与本次改动无关：

- [E12] 相机插件转交模块注册表后可见（模块表 0 项）——相机模块注册，1 条；
- [W] 脚本版多产品线序方案（C# 脚本步骤产出为空：WireCount/Expected 全空、预览 0 帧）——14 条。
  流程组成是 采集 / C#脚本 / 条件分支 / 变量赋值，不经过 Plugin.BlobDetect；
  且与当前工作区未提交的全局变量重构（ExecutionContext.cs / IGlobalVariableWriter /
  Plugin.ImageAssign）高度相关，应在该工作流内排查。

## 四、已知边界

1. **编号恒开**，未做开关：新参数会牵动 `AreAllParametersAtFactoryDefault` 的默认值契约与界面分区，
   而编号与红描边同色、只占缺陷中心一小块，权衡后不加。将来若现场反馈干扰，再加
   `[StepConfig]` 开关并同步进默认值契约。
2. **发布的是标注图（DefectImage）而不是原图**：渲染失败时 DefectImage 为 null，
   此时跳过发布（端口保持空、日志已有 Warn），不会发黑图占窗口。
3. **本环境（无显示会话）离屏窗口的 disp_obj 不渲染**（底图黑、轮廓不可见），这是既有环境约束，
   位深断言同样受此闸门约束；带显示会话的环境上需目视复核一次标注图的最终观感（编号大小/位置）。
4. `DisplayViewIndex` 参与"出厂默认值"判定：改过显示窗口后自动适配不再触发（与"改过任何参数"同语义）。
   实际影响很小——配置实例打开视图时就会先触发一次自动适配，之后才轮到用户改窗口号。
