# 2026-09-24 协议清单合一（B3）+ 添加连接失败回滚（B4）

## 一、需求与决策

### 1.1 问题 B3：三份"哪些协议可用"的说法互相打架

三个事实单独看都正常，拼起来就是 Bug：

| # | 事实 | 位置 |
| --- | --- | --- |
| ① | `CommunicationType` 有 **7** 个值：`ModbusTcp / ModbusRtu / SiemensS7 / OmronFins / MitsubishiMc / FreeProtocol / OpcUa` | `Core/CommunicationContracts/CommunicationType.cs` |
| ② | 工厂只注册了 **3** 个（ModbusTcp / SiemensS7 / ModbusRtu），其余在 `GetFactory` 处抛 `NotSupportedException` | `ConnectionFactoryManager.RegisterDefaults()` |
| ③ | `CommunicationConfig` 里躺着**两份不一致的协议清单**：`OnChanged`（属性 setter 路径）认 6 个；`CreateConfig` 只认 3 个 | `Core/CommunicationContracts/CommunicationConfig.cs` |

后果分两档，都是"走到最后一步才炸"：

- **选中 OmronFins / MitsubishiMc / OpcUa**：配置类真实存在（`OmronFinsConfig` 等都在），参数能填，`Validate()` 也通过 —— 一路走到 `ConnectionFactoryManager.CreateConnection` 才抛 `NotSupportedException`。用户前面填的全白填，且错误信息完全没说是协议不支持。
- **选中 FreeProtocol**（最严重）：`OnChanged` 里落到 `_ =>` 分支，**在属性 setter 里直接抛 `ArgumentOutOfRangeException`**。而这个交互发生在"创建新通信"弹窗内部，调用方的 `try/catch` 拦不到 → **未处理异常把程序干掉**。

### 1.2 ★ 顺带挖出的真 Bug：构造器里那行重复赋值是有害的

读 `ConnectionConfigBase` 时发现：

```csharp
public CommunicationType Type { get; set; }   // 非 virtual、无默认值 → 默认值 0 = ModbusTcp
```

而 `ModbusTcpConfig` / `SerialConfig` / `SiemensS7Config` / `OmronFinsConfig` / `MitsubishiMcConfig` / `OpcUaConfig` **没有一个覆写 `Type`**。

于是旧的 `CommunicationConfig(CommunicationType protocol)` 构造器：

```csharp
Protocol = protocol;                  // setter 内部 OnChanged() 按协议建好 Config，Type 正确
Config = CreateConfig(protocol);      // ← 紧接着又覆盖一次
```

而 `CreateConfig` 造的配置**不赋 `Type`**，`Type` 落到默认值 `0`（= ModbusTcp）。净效果：

> `new CommunicationConfig(CommunicationType.ModbusRtu)` 造出来的对象，`Protocol = ModbusRtu` 而 `Config.Type = ModbusTcp` —— **自相矛盾**，一进 `Validate()` 就被判「协议类型不匹配」。

所以删掉这行**不是"去冗余"，是修 Bug**。B3-3 断言专门钉它。

### 1.3 问题 B4：`AddConnection` 中途失败留下隐形僵尸

`AddConnection` 的登记顺序：

```
_connections[name] → _configCache[name] → _workers[name] → worker.Start() → _connectionsList.Add(config) → config.State → OnConnectionStateChanged(...)
```

"登记之后还可能抛"的动作是有的（`worker.Start()`，以及**最后那次事件广播**——`OnConnectionStateChanged` 里没有任何 `try/catch`，任何 UI 订阅者抛一次就穿透回来）。此时前三个字典里已有它、而 `_connectionsList` 里还没有它。失败不回滚的后果**不是"加失败"这么简单**：

- **隐形僵尸连接**：UI 连接列表里看不见它，但它的工作线程已经在跑、已经在读设备；
- 开头那句 `if (_connections.ContainsKey(...)) throw` 预检**永远为真** → 用户改完参数重试，只会一直得到"已存在同名连接"，除了删连接无路可走（而它又不在列表里，删不掉）。

| B3 未实现协议怎么办 | **不在 setter 里抛异常**，安静地保留原 `Config`；由 `Validate()` 报人话 | 见 1.6 |
| B3 下拉框 | **照旧全列 7 个协议**，不隐藏 | 见 1.7 |

### 1.5 为什么清单放在 Core 层、靠断言兜一致性

`Core.csproj` **不引用** `VM.Communication`（方向也不允许反过来），所以 Core 层**取不到**工厂注册表 —— 不能写成 `CommunicationProtocols = ConnectionFactoryManager.Instance.SupportedTypes`。

只能手工双写 + 用回归钉住：

- Core 层声明 `CommunicationProtocols.Implemented`；
- CommChecks 用 **B3-1** 断言"两份清单必须完全一致"，谁加了一边忘了另一边，回归当场失败。

这是本次唯一可接受的双写，因为跨层依赖方向不能破。

### 1.6 为什么"安静保留原 Config"而不是抛异常 / 置 null

`OnChanged` 是**属性面板双向绑定的写入路径**，两条理由：

1. **不能抛**：setter 抛异常会穿透成未处理异常，而该交互在弹窗内部，调用方的 `try/catch` 拦不到（改造前选 `FreeProtocol` 就是这么把程序干掉的）。
2. **不能置 null**：`Config` 置 null 后，属性面板里"底层链路参数"那个嵌套分组就无处展开（框架对 null 嵌套对象的行为未验证）。保留原配置更稳——反正 `Validate()` 会拦住它。

错误话术交给 `Validate()`，且**必须前置判定**：

```csharp
// 必须在 Config 判空之前：未实现协议时 OnChanged 刻意保留原 Config（不为 null），
// 若不先判这一条，用户会一路走到「协议类型不匹配」——那句话根本没告诉他真正的问题。
if (!CommunicationProtocols.IsImplemented(Protocol))
{
    errorMessage = $"协议 {Protocol} 尚未实现，当前可用：{CommunicationProtocols.ImplementedText}";
    return false;
}
```

改前 vs 改后的用户感受：

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 选 FreeProtocol | **程序崩溃** | 弹气泡，点确定时报"协议 FreeProtocol 尚未实现，当前可用：ModbusTcp / ModbusRtu / SiemensS7" |
| 选 OpcUa | 填完所有参数、点确定 → 报一句底层 `NotSupportedException` | 上面同一句人话，且更早报出 |

### 1.7 为什么不把下拉框收窄成只列 3 个

属性下拉由公共组件 `EnumGenerator` 生成，它对 `Enum.GetValues` 的**每个值无条件全列**（`foreach (var value in Enum.GetValues(enumType))`），且**按类型做了 static 缓存**。要收窄就得：

1. 给 `SuperDisplayAttribute` 加"允许值"字段；
2. 改 `EnumGenerator` 的缓存键（否则同类型只生成一次，过滤参数进不去）。

动的是**全项目共用的属性网格组件**，回归面远大于收益。故选择"下拉照旧全列，选中未实现协议时给一句人话"，并在 `CommunicationProtocols` 的 XML 注释里写明这个取舍。

### 1.8 B4 回滚为什么不能按名字盲删

方法开头那句 `ContainsKey` 预检与后面的写入之间**没有锁**，不是原子的（**TOCTOU**）。并发下同一个名字可能已由另一路 `Add` 写入了它自己的对象 —— 若回滚按名字盲删，就会把别人的连接**连线程一起干掉**。

故每一步都是"先 `TryGetValue` 拿到当前值，再用 `ReferenceEquals` 确认'就是我放进去的那个'，才 `TryRemove`"。`_connectionsList` 用 `IndexOf` 按引用移除（`CommunicationConfig` 没覆写 `Equals`，`IndexOf` 就是引用比较，正好是想要的语义）。

释放归属：`ConnectionWorker.Dispose()` 内部会释放它持有的 connection，所以

- 有 worker → 只 `worker.Dispose()`（它连带释放 connection）；
- 没有 worker（失败在建 worker 之前）→ 自己 `connection.Disconnect(); connection.Dispose();`。

两边 `Dispose` 都有幂等保护，重复调用安全。两步各自 `try/catch` + `LogError`，避免"回滚本身抛异常"把原始异常盖掉。

### 1.9 备选方案与不采纳的理由

| 方案 | 不采纳理由 |
| --- | --- |
| B3：把 `CommunicationType` 枚举删到只剩 3 个 | 枚举是公共契约，删值会让已保存的方案文件反序列化失败；且 OmronFins 等将来要实现，留着枚举是合理的 |
| B3：给未实现协议也补上连接实现类 | 工作量大且本次目标不是"实现协议"，是"把话说清楚" |
| B3：`Validate()` 保持原样，只在 UI 层拦 | UI 层不是唯一入口（`AddConnection` 也会调 `Validate`），模型层的规则应该在模型层 |
| B3：下拉框收窄 | 见 1.7，要动公共组件 |
| B3：`OnChanged` 里 `Config = null` | 属性面板的嵌套分组无处展开，见 1.6 |
| B4：失败后按名字盲删 | TOCTOU 会误删别人的连接，见 1.8 |
| B4：失败后 `try { RemoveConnection(name) } catch {}` | 复用 `RemoveConnection` 会触发它自己的一整套事件/日志，语义上"假装加过又删了"，不如直接摘干净 |

### 3.1 本组断言的两个测试设计要点

1. **B4 的触发手段是"给 `ConnectionStateChanged` 挂一个抛异常的订阅者"**，不是去戳 `worker.Start()`。
   原因：`worker.Start()` 的实现是 `if (_thread.IsAlive) return; _thread.Start();`，正常路径**不会抛**，造不出失败。而 `OnConnectionStateChanged` 恰好满足两个条件：**在五个登记动作全做完之后**、**且广播本身没有 `try/catch`**。订阅者抛异常在生产里并不罕见（UI 订阅者的任何一句都可能抛）。
2. **"B4-1 前提"这条断言是必须的**：它先取证"抛异常那一刻，连接确实已在 `_connections` 里、也已在列表中"。只有确认了"失败点在全登记之后"，后面那几条"回滚干净"的断言才有意义 —— 否则测的可能只是"还没登记就失败了"，回滚断言空跑也照样绿。
3. **B4-3 用反射直接调私有 `RollbackFailedAdd`**：生产路径上该方法只在 catch 里被调，测试要构造"拿别人的对象来调"这个场景无处可调，只能反射。反射取不到时**直接抛**、不静默放过（否则护栏断言会变成空跑）。

## 四、已知边界

1. **`CommunicationConfig(string name, ConnectionConfigBase config)` 的既有隐患（本次未修）**
   该构造器里有 `Protocol = config.Type;`。调用方若像 `CommTest` 那样写 `new SiemensS7Config { ... }` 而**没赋 `Type`**，`Type` 就是默认值 `0`（ModbusTcp），于是 `Protocol` 被赋成 `ModbusTcp`。这是**已存在**的问题、超出本次范围（本次只修 `ctor(CommunicationType)` 那条路径）。
   影响面：凡"外部造好 Config 再套 `CommunicationConfig`"的调用点都可能踩到。**要修的话建议统一走 `new CommunicationConfig(CommunicationType.X)` 再填参数**。⚠ 想改 `ConnectionConfigBase.Type` 为 `virtual` 并在各子类覆写默认值，会波及所有配置子类与序列化，需单独评估。

2. **属性下拉框仍全列 7 个协议**（未实现协议不隐藏，只报错）。
   若将来要收窄，需给 `SuperDisplayAttribute` 加"允许值"字段 + 改 `EnumGenerator` 的 static 缓存键 —— 动的是全项目共用的属性网格组件，务必单独做并全量回归。

3. **`CommunicationProtocols.Implemented` 是 `public static readonly` 数组，元素可被外部改写**（`readonly` 只保证引用不变，不保证内容不变）。
   当前无外部写入方，未加只读包装。若要收紧可改为私有数组 + 暴露 `IReadOnlyList<CommunicationType>`（**未获确认，不要擅自改**）。

4. **⚠ 手工双写约束**：`CommunicationProtocols.Implemented` 与 `ConnectionFactoryManager.RegisterDefaults()` **必须同步**。B3-1 断言就是为此设的 —— **加/删工厂时务必同步改清单**，否则 CommChecks 变红。这是跨层依赖方向（Core 不能引用 Communication）导致的必要妥协，不是遗漏。

5. **⚠ 勿回退 `OnChanged` 的"安静保留原 Config"**：不要改成"抛异常"（弹窗内崩溃）或"置 null"（嵌套分组无处展开）。B3-2 的两条断言分别钉住这两点。

6. **⚠ 勿回退 `RollbackFailedAdd` 的 `ReferenceEquals` 比对**：不要简化成按名字盲删。虽然生产上"同名并发添加"极罕见，但盲删的后果是把别人的连接连线程一起干掉 —— 后果比"多留一个僵尸"严重得多。B4-3 就是钉这一条的护栏断言。

7. **B4-3 是反射护栏断言、非生产路径**：它验证的是"回滚方法的护栏逻辑"，不代表生产上真的发生过 TOCTOU 误删。方法名若被改过，反射会直接抛，提醒同步更新断言。

8. **未覆盖实机验证**：B3 断言的是"清单一致 / 不抛异常 / 错误话术"，B4 断言的是"登记痕迹摘干净 / 同名可重试"。真机点验（在 UI 里选一次 OmronFins 看气泡话术、在真连接上制造一次添加失败）留待联调。
