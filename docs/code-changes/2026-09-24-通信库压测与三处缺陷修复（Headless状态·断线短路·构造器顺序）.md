# 2026-09-24 通信库自建靶子压测与三处缺陷修复（Headless 状态 · 断线短路 · 构造器顺序）

## 一、需求与决策

### 1.1 需求

> 「你使用 Hsl 的 S7 服务器 和 Modbus 服务器功能 自己建连接设备 做压力测试 看下还有没有可以优化的地方」

仓库内已带有 HslCommunication 全量源码（含 `ModbusTcpServer`、`SiemensS7Server`），因此可以**在本机自建靶子服务器**，让产品的通信库去真实连接、真实收发、真实断线——比纯断言更能暴露"设计层面的延迟与语义缺陷"。

为此新建了独立压测台工程 `CommStress`（net9.0-windows，`OutputType=Exe`，引用 `..\VisionMaster\VisionMaster.csproj`），并按场景编号：

| 编号 | 场景 | 关注点 |
| --- | --- | --- |
| S1 | 连通性冒烟 | 能否连上自建靶子 |
| S2 | 单连接满速读 | 达成率、分配速率 |
| S3 | 稀疏点位 | 段规划是否退化 |
| S4 | 多连接并发 | 连接耗时、线程数 |
| S5 | 多周期扫描组 | 快慢组是否互相拖累 |
| S6 | 写队列 | 入队吞吐、积压后同步写延迟 |
| S7 | S7 大批量 | 段数 / 请求速率（对照 Modbus） |
| S8 | **断线场景** | 掐线 / 静默掉线 / 恢复耗时 |

### 1.2 S8 暴露出的三处缺陷

压测把三处**只有真实运行形态才暴露**的问题打了出来：

#### 缺陷 1（最高）：Headless 宿主下状态/错误全部失真

`AdvancedCommunicationManager.OnWorkerStateChanged` 的 `config.State = newState`、`OnWorkerCommunicationError` 的 `cfg.LastError = message` 都包在 `SafeDispatch.BeginInvoke(...)` 里。而 [SafeDispatch.cs](file:///e:/VM/VisionMaster-W-master/Core/Helpers/SafeDispatch.cs#L20-L39) 在 `Application.Current?.Dispatcher == null`（控制台程序 / Windows 服务 / 单元测试）时**直接 return 丢弃动作**。

后果：这类宿主里 `GetAllConnections()[i].State` **永久停在 Disconnected**、`LastError` 永远是 null——诊断信息全部丢失，而事件广播却照常。压测台的控制台里就是"明明连上了，状态却写着断线"。

#### 缺陷 2（高）：断线判定无 early-abort，延迟 = 段数 × ReadTimeoutMs

批量轮询是"一个段一次往返"。半开场景（拔网线 / 防火墙丢包 / 服务端进程假死）下 socket 不会立刻报错，只能等读超时：

```
掉线检测延迟 ≈ 段数 × ReadTimeoutMs
             =  5 段 × 3s = 15s        尚可忍
             = 167 段 × 3s ≈ 8 分钟     不可接受
```

段循环里每一段都各自烧掉一整个超时，而第 1 段失败时其实就已经能判定链路死了。

#### 缺陷 3（中）：`CommunicationConfig(name, config)` 2 参构造器静默丢弃传入配置

```csharp
// 修改前
public CommunicationConfig(string connectionName, ConnectionConfigBase config)
{
    ConnectionName = connectionName;
    Config = config;          // ← 先赋 Config
    Protocol = config.Type;   // ← 再赋 Protocol
}
```

`Protocol` 的 setter 内部会 `OnChanged()` **重建一份默认 Config**，于是刚传进来的那份被顶掉——端口、超时、字节序全部变回默认值，**连接打到错的地方去**。这与 `CopyFrom` 的同类缺陷同源（`CopyFrom` 里顺序是对的，可作对照样板）。

### 1.3 决策（3 项，已逐条与用户确认）

| 决策项 | 结论 |
| --- | --- |
| 缺陷 1 | **新增 `GetConnectionState(name)` / `GetConnectionError(name)`**（不经 Dispatcher 的可靠访问器），保留 `config.State` 作为 UI 绑定镜像 |
| 缺陷 2 | **加 early-abort，仅 socket 级异常中断**（协议错误码不算链路故障） |
| 缺陷 3 | **修构造器顺序**（`Protocol` 先、`Config` 后） |

### 1.4 关键设计推演

#### （a）为什么缺陷 1 用"加访问器"而不是"去掉 SafeDispatch"

`config.State` / `config.LastError` 是 `INotifyPropertyChanged` 属性，**存在的意义就是给 WPF 绑定用的**，其回写必须回到 UI 线程。去掉 `SafeDispatch` 会在 UI 宿主下引发跨线程异常。

所以正确做法是**读的两条路分开**：

- UI 读 `config.State`（镜像，必须走 Dispatcher）；
- **任何宿主**读 `GetConnectionState(name)`（直读 Worker，唯一真相源）。

真相源在 [ConnectionWorker.cs](file:///e:/VM/VisionMaster-W-master/Communication/Communications/Manager/ConnectionWorker.cs)：`State` 取自 `(ConnectionState)Volatile.Read(ref _state)`、`IsConnected => State == Connected && _connection.IsConnected`；错误消息新增 `private volatile string? _lastError` + `LastError => _lastError`（Worker 线程写、任意线程读，绕过 Dispatcher），连接成功后 `_lastError = null`。

#### （b）★ 缺陷 2 的核心难点：如何区分"链路死了"与"只是这个地址读不到"

这是本任务**最关键的设计约束**，必须写清楚，防止后人写宽了：

> **绝不能**用"异常类型 / 异常消息文本"判定链路故障。

因为产品的连接实现把所有 HSL 错误一律包成 `InvalidOperationException(result.Message)`，原始 `SocketException` 已经丢失；`result.Message` 还是本地化文本。靠它判定必然误伤。

> **更不能**用"读失败"判定链路故障。

否则**一个坏地址（配置错 / 越界 / 存储区不存在）会把整条好连接打进无限重连循环**——把"几个点黄"升级成"全部点灰"，比原问题更糟（此约束与 `docs/code-changes/2026-09-24-坏段不再静默.md` 一脉相承）。

**正确入口是 HSL 管道自身的链路错误状态位。** 这里踩过一个坑，记录下来：

> ⚠ **HSL 继承链坑**：`GetPipeSocket()` / `PipeSocket.IsSocketError` 属于**遗留支线**
> `NetworkDoubleBase : NetworkBase`（只被旧机器人类 `YRC1000TcpNet` / `YamahaRCX` 使用），
> **`ModbusTcpNet` / `SiemensS7Net` 拿不到**（编译会直接报 `CS1061`）。
>
> 真实继承链是：
> `ModbusTcpNet : DeviceTcpNet : DeviceCommunication : BinaryCommunication`（`BinaryCommunication` **无基类**）。
> 探针入口应取 [BinaryCommunication.CommunicationPipe](file:///e:/VM/VisionMaster-W-master/DLL/HslCommunication/Core/Net/BinaryCommunication.cs#L73-L83)（`public virtual`，Modbus/S7 均未覆写，返回内部 `PipeTcpNet`）。

`CommunicationPipe.IsConnectError()` 的语义恰好就是我们要的：

```csharp
private int connectErrorCount = 0;

public int ResetConnectErrorCount() => Interlocked.Exchange(ref connectErrorCount, 0);
protected int IncrConnectErrorCount() { ... Interlocked.Increment(ref connectErrorCount) ... }
public virtual bool IsConnectError() => connectErrorCount > 0;   // 上次传输 I/O 是否失败
```

- **传输层失败才置位**：`PipeTcpNet.Send` 遇 `SocketErrorCode` → `CloseCommunication()` + `-IncrConnectErrorCount()`；`Receive` 超时/异常 → `-IncrConnectErrorCount()`；`OpenCommunication` 建连失败 → `-IncrConnectErrorCount()`。
- **成功即清零**：`ReadFromCoreServer` 成功分支末尾 `ResetConnectErrorCount()`。
- **`PipeTcpNet` 覆写**：`socket == null ? true : base.IsConnectError()`（"socket 已关"也算故障）。
- **★ 坏地址不置位（铁证）**：[BinaryCommunication.ReadFromCoreServer(pipe, ...)](file:///e:/VM/VisionMaster-W-master/DLL/HslCommunication/Core/Net/BinaryCommunication.cs#L340-L371) —— 协议错误码（Modbus 非法地址异常 / S7 越界）是在**管道读成功之后**由 `UnpackResponseContent` 解析产生的，且失败结果直接返回、**不再 `Incr`**，故计数仍为 0。

于是探针一句话即可，且与异常类型、报错语言都无关：

```csharp
public bool HasLinkFault => _device.CommunicationPipe?.IsConnectError() ?? false;
```

#### （c）探针为什么做成"可选接口"而不是加到 `ICommunicationConnection` 上

```csharp
/// <summary>链路健康探针（可选能力）</summary>
public interface ILinkHealthProbe
{
    bool HasLinkFault { get; }
}
```

- 串口（`SerialConnection`）基于 `SerialPortBase`，无同源状态位，**不实现**该接口；
- 用 `is` 模式匹配消费，不实现的实现**行为与旧版完全一致**（零回归风险）；
- 若加到 `ICommunicationConnection` 上，会强迫串口等实现写一个假的 `HasLinkFault`，属于把可选能力做成强制契约。

#### （d）缺陷 2 落码时预先识别的两个误判坑

写代码前就把这两个坑堵了（都在 [PollBatchPlanner.cs](file:///e:/VM/VisionMaster-W-master/Communication/Communications/Manager/PollBatchPlanner.cs#L429-L463)）：

| 坑 | 现象 | 规避 |
| --- | --- | --- |
| **坑 A** | seg1 成功、seg2 报链路故障 → `attempted=2, failed=1` → `failed < attempted` 为 true → **误判"通信正常"**，Worker 不断线 | 显式 `if (linkFault) return false;` 写在 `return failed < attempted;` **之前** |
| **坑 B** | break 后仍跑 `_fallbacks` 单读，若单读大量成功 → 同样 `failed < attempted` 误判 | `if (!linkFault) { foreach ... }` **整段跳过**单读 |

核心代码：

```csharp
int attempted = 0;
int failed = 0;

// 链路级故障短路标志
bool linkFault = false;

var byteOrder = connection.ByteOrder;
```

```csharp
catch (Exception ex)
{
    failed++;
    foreach (var item in seg.Items) item.Variable.MarkUncertain();
    // ... 连续失败计数与跨阈值告警（见「坏段不再静默」）...
    LogThrottled($"seg:{seg.ConnectionName}.{seg.Address}", $"段读失败 {seg.Address}（{seg.SpanUnits} 单元）: {ex.Message}");

    // early-abort：段读失败后问一句"是链路死了，还是只是这个地址读不到"。
    // 探针读的是底层 socket 的错误标志（传输层 I/O 是否失败），不含"帧收到了但内容是错误码"
    // 的情况（Modbus 非法地址 / S7 越界），所以个别坏地址不会误触发短路。
    if (connection is ILinkHealthProbe probe && probe.HasLinkFault)
    {
        linkFault = true;
        _log?.Invoke($"[轮询] 段读失败且链路已判定断开，跳过剩余 {_segments.Count - attempted} 段并立即重连：{seg.Address}: {ex.Message}");
```

### 1.5 备选方案与不采纳的理由

| 方案 | 不采纳理由 |
| --- | --- |
| 去掉 `config.State` 的 Dispatcher 回写 | 该属性存在意义就是 WPF 绑定，回 UI 线程是必须的；去掉会引入跨线程异常 |
| 按异常类型 `SocketException` 判链路故障 | 连接实现已把 HSL 错误包成 `InvalidOperationException(result.Message)`，原始类型丢失，不可靠 |
| 按错误消息文本（如含 "Socket"）判链路故障 | 依赖本地化文本，同一错误换语言就失灵 |
| 只要读失败就短路线路 | 坏地址 → 无限重连循环，把"几个点黄"升级成"全部点灰" |
| 用 `GetPipeSocket()?.IsSocketError` | **编译不过**：属遗留支线 `NetworkDoubleBase`，Modbus/S7 继承链上不存在 |

### 2.1 `AdvancedCommunicationManager` 新增的两个访问器（逐字）

```csharp
/// <summary>
/// 读取连接当前状态（读 Worker 状态机，<b>不经 Dispatcher</b>，任何宿主下都正确）。
/// <para>为什么需要它：<c>GetAllConnections()[i].State</c> 那条回写被包在 SafeDispatch.BeginInvoke 里，
/// 而 SafeDispatch 在 Application.Current == null（控制台 / Windows 服务 / 单元测试）时直接丢弃动作——
/// 于是 config.State 会永久停在 Disconnected。本方法读 Worker（连接状态的唯一真相源）绕开该限制。</para>
/// <para>未登记的连接返回 <see cref="ConnectionState.Disconnected"/>。</para>
/// </summary>
public ConnectionState GetConnectionState(string connectionName)
{
    if (string.IsNullOrWhiteSpace(connectionName))
        return ConnectionState.Disconnected;

    if (_workers.TryGetValue(connectionName, out var worker))
        return worker.State;

    // 兜底：Worker 尚未建好等极少数情况，用连接实现自身的 IsConnected 推断
    if (_connections.TryGetValue(connectionName, out var conn))
        return conn.IsConnected ? ConnectionState.Connected : ConnectionState.Disconnected;

    return ConnectionState.Disconnected;
}

/// <summary>
/// 读取连接最近一次通信故障消息（读 Worker，<b>不经 Dispatcher</b>）；无故障或连接不存在时返回 null。
/// </summary>
public string? GetConnectionError(string connectionName)
{
    if (string.IsNullOrWhiteSpace(connectionName))
        return null;

    return _workers.TryGetValue(connectionName, out var worker) ? worker.LastError : null;
}
```

## 四、已知边界

1. **`config.State` / `config.LastError` 在 headless 宿主仍不可信**：本次**保留**该回写（它是 UI 绑定的镜像），只新增了可靠通道。任何非 WPF 宿主（控制台 / 服务 / 单测）必须改用 `GetConnectionState(name)` / `GetConnectionError(name)` / `ConnectionWorker.IsConnected` / `ConnectedCount` 读状态。
2. **串口未实现 `ILinkHealthProbe`**：`SerialConnection` 基于 `SerialPortBase`，链路故障判定**回落旧版**（无短路，仍是"段数 × 串口读超时"）。这是有意的——不做"假实现"。
3. **探针依赖 HSL 内部语义**：`HasLinkFault` 建立在 `CommunicationPipe.IsConnectError()`（`connectErrorCount > 0`）之上。**若将来升级 HSL 版本，必须复核该方法语义**（尤其"协议错误码是否会被计入"这一点，它决定了坏地址会不会被误判成链路故障）。
4. **探针是"上一次传输"的快照，非实时探测**：`IsConnectError()` 读的是上一次 I/O 的结果，不做额外 I/O（设计约定要求无副作用、可跨线程）。因此"从未读过数据的连接"探针恒为 false——但这不影响用途，因为短路只在"段读刚失败之后"才被查询。
5. **S8[D] 语义特殊**：`TcpRelay.Pause()` 期间客户端仍能完成 TCP 握手（半开的真实表现），故测出 0ms。**不能解读为"恢复快"**，它反映的是"TCP 层连上了但应用层还不通"。
6. **HSL 服务端 `ServerClose()` 缺陷与本产品无关**：`CommunicationTcpServer.ServerClose()` 后 `AsyncAcceptCallback` 连失 3 次即 `throw` → 进程被带走（exit code `0xE0434352`）。产品是**纯客户端**，不受影响；但**将来若内置服务端功能须注意：绝不在客户端连着时调用 `ServerClose()`**。压测台用独立的 `TcpRelay` 绕开了该缺陷。
7. **`TcpRelay` 仅存在于压测台**，不属于产品代码。
8. **压测台绕行代码已清理**（见 §3.5）：`NewModbusConfigCore` / `NewS7Config` 的 `{ Config = link, ... }` 与 `RunDiag` ⑤/⑥ 的二次赋值均已删除。仍保留 `WaitState()` 读 `GetConnection(name)?.IsConnected`（规避的是缺陷 1，而该缺陷有意保留），以及 S8 报告里的 `config.State` 对照行。

## 五、经验沉淀（供后人避坑）

1. **HSL 继承链**：`ModbusTcpNet : DeviceTcpNet : DeviceCommunication : BinaryCommunication`（**无基类**）。
   `NetworkDoubleBase` / `NetworkBase` / `PipeSocket` / `GetPipeSocket` 是**与 Modbus/S7 无关的遗留支线**，别照着它写代码。
2. **读 HSL 链路状态用 `device.CommunicationPipe.IsConnectError()`**，它能区分"传输层 I/O 失败"与"帧收到了但内容是协议错误码"。
3. **协议错误 ≠ 链路故障**：任何"把坏地址当链路故障"的写法，都会引发无限重连，比原问题更严重。
4. **改 `CommunicationConfig` 时**：`Protocol`（及其 `OnChanged()`）必须先于 `Config` 赋值，否则传入配置被默认值顶掉。`CommunicationConfig(protocol)` 与 `CopyFrom` 同理。
5. **非 WPF 宿主读连接状态**：一律用 `GetConnectionState(name)` / `GetConnectionError(name)`；`config.State` 只作 UI 镜像。
