# 启动提速第二批：插件清单缓存（层 3）——命中路径跳过反射与实例化

- 日期：2026-10-16 ~ 17
- 涉及：`Engine\PluginCache.cs`（新增）、`Engine\PluginService.cs`（缓存命中/失效两路径）、`Engine\VM.FlowEngine.csproj`（`InternalsVisibleTo FlowCanvasChecks`）、`FlowCanvasChecks\PluginCacheChecks.cs`（新增 PC1~PC8）
- 触发：用户裁定"按照这个落地"（层 3 设计——插件清单缓存）。

---

## 1. 设计前提（先查实，再动手）

层 3 的决定性问题是：**缓存命中时连 `Assembly.LoadFrom` 能不能省掉**。查实结果是不能全省——
下游三处都依赖"程序集已在内存里"：

| 下游 | 位置 | 依赖 |
| --- | --- | --- |
| 相机/运动卡**自动连接** | `CameraModule.Initialize` / `MotionModule.Initialize`（`CreateShell` 之前） | `Activator.CreateInstance(驱动类型)`，类型解析靠 `Type.GetType` + 逐已加载程序集找 |
| **流程编译** | `Engine\FlowCompiler.cs:748` | `Activator.CreateInstance(type)`，类型来自步骤的 `ModuleTypeName` |
| **帮助手册合并** | `HelpCatalogService` | 读插件程序集的**内嵌资源** |

所以缓存路径**仍 LoadFrom 全部插件**，但**省掉 `GetTypes()` 反射与 42 个 `Activator.CreateInstance`**——
插桩实测这两项合计约 2.5 秒（`Plugin.ImageScript.dll` 的注册段一项就 2449ms），正是大头。

## 2. 结构

```
Modules\PluginCache\manifest.json   ← 清单缓存（只存扫描产物：ToolItemModel 快照 + 指纹）
Modules\Plugin*.dll                  ← 插件本体（不变）
```

**指纹**（四道全满足才命中，任一不满足即全量重扫并重写缓存）：
① SchemaVersion 对得上；② 登记的每个 DLL 都在、大小+mtime 逐项对得上；
③ 磁盘上没有多出未登记的 `Plugin*.dll`（新增插件必须被看见）；
④ 宿主契约程序集版本没变（插件二进制对 `Core.Interfaces` 链接，契约变了清单里的类型名可能已失效）。

## 3. 守门断言（`FlowCanvasChecks\PluginCacheChecks.cs`，进常规 gate 基线）

| # | 判据 | 挡的是 |
| --- | --- | --- |
| PC1 | 刚写的缓存下次读得出来（基准） | 写/读通道本身 |
| PC2 | 插件 mtime 变了 → 缓存失效 | 产物陈旧族（R42/红线③ 同族） |
| PC3 | 插件大小变了 → 缓存失效 | 同上 |
| PC4 | 多出未登记的 `Plugin*.dll` → 缓存失效 | 新增插件被缓存"看不见" |
| PC5 | 契约版本变了 → 缓存失效 | 接口/基类签名改动后类型名失效 |
| PC6 | 缓存产物与全量扫描逐项一致（剔除内置节点） | 缓存路径丢插件 |
| PC7 | 端口表快照与全量扫描一致（Name/DataTypeName/OptionKind） | 缓存路径丢端口 |
| PC8 | 插件构造器无副作用（构造器体里不出现 进程/网络/程序集加载 调用） | **反向钉住前提**：缓存路径跳过实例化，前提一破就必须当场红 |

**PC8 的口径收窄过程**（断言被真机数据教育的一次）：初版全文件扫关键词，`ExcelExportPlugin` 的
`Process.Start`、`ImageAcquisitionPlugin` 的 `HttpClient` 误报——那两个调用在**运行期方法**里
（导出完打开文件夹、推送图像），不在构造器里。缓存路径只跳过"构造"这一步，运行期照样跑，
所以判据收窄到**构造器体**（按"类名(" 起头、括号配对到 `}`）。这是"断言先织网再动手"的又一例：
网先红了，才发现是网太粗，不是被测对象错了。

## 4. 验证证据（真机启动日志，2026-10-17）

| 路径 | 插件扫描段 | 关键行 |
| --- | --- | --- |
| 缓存命中（23:43） | 52.488 → 54.969 = **2.5 秒** | `命中缓存：31 个插件 DLL，跳过反射与实例化（2423ms）` |
| 缓存失效（23:58） | 55.877 → 59.13 ≈ **3.3 秒** | `缓存失效（mtime 变了 Plugin.BeadInspect.dll），全量重扫` |

- 命中路径把反射+实例化（约 2.5 秒）省掉了；剩下的 2.4 秒是 `Assembly.LoadFrom`（程序集必须在内存里，
  是设计决定，不是疏漏）。
- 失效原因日志工作正常（`mtime 变了 Plugin.BeadInspect.dll` 精确点名是哪个插件）。
- 下游闭环验证：命中路径上帮助合并照常（42 个插件、86 页开发章节全在），相机/运动/通讯照常——
  缓存只省反射与实例化，不省加载，下游类型解析/资源读取不受影响。

## 5. 验证（断言）

- `FlowCanvasChecks`：**2545 通过 / 0 失败**（PC1~PC8 全绿）。
- 构建注意：VisionMaster 在 VS 里开着会锁住 `VM.Core.dll` 等 DLL（MSB3021/3027），
  先关掉再构建——这与本次改动无关，是宿主进程占文件的常态。

## 6. 累计效果（层 0+2+3 合计）

| 阶段 | 改前 | 改后（缓存命中） |
| --- | --- | --- |
| 插件扫描段 | 2.8 ~ 7.9 秒（波动） | **~2.5 秒**（LoadFrom 不可避免）+ 反射/实例化已省 |
| 帮助手册合并 | 自检链上（1.2 秒） | 主界面显示后后台跑 |
| `软件加载成功` 时机 | 插件扫描+帮助合并都跑完之后 | 插件扫描完即出（帮助后台补） |

稳态热启动从"插件扫描 2.8 秒 + 帮助合并 1.2 秒"压到"插件扫描 ~2.5 秒（缓存命中）+ 帮助后台"——
用户看到主界面的时间提前了约 1.2 秒以上，且插件扫描本身又省了反射与实例化那 2.5 秒里的大头。
