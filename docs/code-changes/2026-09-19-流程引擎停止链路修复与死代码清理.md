# 流程引擎停止链路修复与死代码清理、性能优化

日期：2026-09-19

## 一、需求与决策

背景：对流程引擎（FlowCompiler / CompiledFlow / FlowEngineService）做系统性评审后识别出 7 项问题（P0/P1/P2 分级），用户拍板本轮只做三项：①单次执行停止失效修复、⑤FlowPriority 死代码处置、⑦性能优化。②失败策略、③暂停响应性、④超时 watchdog、⑥图像生命周期为后续候选，未在本轮范围内。

### D1：RunSessionOnceAsync 停止链路断裂的根因与修法

- 根因：Once 模式从不创建 `CancellationTokenSource`，ExecutionContext 拿到的是 `?? CancellationToken.None` 兜底的永不可取消令牌；而 `StopSession` 要求 `CTS != null` 才执行 Cancel——两个条件互斥，单次执行期间点停止完全无效。
- 修法：与连续模式（RunSessionAsync）对称——方法开头 `new CancellationTokenSource()`，finally 中 `Dispose()` + 置 null。
- 附带决策：补 `catch (OperationCanceledException)` 静默分支。否则停止时节点抛出的取消异常会落入通用 `catch (Exception)`，被误记为「流程单次执行异常」并把会话打成 Faulted——停止是用户主动的正常路径，不是故障。
- `Task.Run` 的第二参数也传入 token（与连续模式对齐），使取消能正确传导为任务取消而非普通异常。

### D2：FlowPriority 判定为纯死代码，直接删除

- 全仓库 grep `\.Priority|FlowPriority` 确认：除 FlowSession.cs 自身的枚举定义与 Priority 属性声明外，其余 .Priority 命中均属无关类型（SoftMail.Priority、ThreadPriority、PriorityBinding、PropertyGrid 描述符、AvalonEdit CompletionData）。
- 无任何调度消费方，保留只会误导后来者以为存在优先级调度。删除枚举 + 属性，共约 20 行。

### D3：性能优化两处

1. **Thread.Sleep → 令牌等待**：连续模式循环体尾部的 `Thread.Sleep(10)` 空转轮询，停止请求最长要再等一轮 Sleep 才被检查。改为 `token.WaitHandle.WaitOne(10)`——空闲节流语义不变（最多 10ms），但 Cancel 会立即唤醒，停止响应从「10ms + 一轮循环」缩短为即时。
2. **While args 数组移出循环**：CompiledWhileNode 每次迭代都 `new object[totalArgs]`，但数组大小（LocalVarIds.Count + RuntimeVarNames.Count）在整个循环期间固定。分配移到 while 外，循环体内只重填值，消除高频迭代下的分配压力。

## 四、已知边界

1. **上机验证项**：单次执行中点「停止」应使流程在当前节点检查点退出、会话状态归为 Stopped（而非 Faulted）；连续模式停止应即时生效。建议构造一个含长耗时节点的流程实测。
2. **停止粒度未变**：本次只打通取消令牌的传递，节点内部的取消检查密度（如视觉算法单步执行中不可中断）维持原状——属评审遗留项③的范畴。
3. **Once 模式无暂停语义**：PauseLock 仅在连续模式两轮之间生效，单次执行不支持暂停（与改动前一致）。
4. **FlowEngineService 的 CS8625 存量告警**：`session.CancellationTokenSource = null` 的赋值模式在连续模式本就存在同类告警，Once 模式补齐后对称出现一处；为保持代码一致性未加 `null!` 压制，可空性治理属全仓库后续专项。
5. **评审遗留候选**（用户未拍板，记录待议）：②节点异常→整线停机的失败策略、③暂停/停止的节点级响应性、④ExecutionStartTime 无超时 watchdog、⑥HImage 所有权协议、`$(SolutionDir)` 无回退的长期方案。
