## 二、已做

### 1. 四个端口（`Plugins\Plugin.Ocr\OcrPlugin.cs`）

| 端口 | 类型 | 语义 |
| --- | --- | --- |
| `Classes` | `OutputPort<string[]>` | 逐字符**原始**类别名，与 `Confidences` / `CharBoxes` 逐项对齐、按阅读顺序；拒识保留原始 U+001A（不替换成 `?`） |
| `Confidences` | `OutputPort<HTuple>` | 逐字符置信度 0~1，长度 = `Count` |
| `RejectedCount` | `OutputPort<int>` | 拒识字符数（= `Classes` 里 U+001A 的个数） |
| `CharBoxes` | `OutputPort<HTuple>` | 逐字符外接框，扁平 stride 4：`[row1,col1,width,height, …]`；`smallest_rectangle1` 轴对齐框，宽高按像素含端点（`col2-col1+1`），顺序与 `Classes` 一致 |

- `OcrOutcome` 增 `Classes` / `Confidences` / `CharBoxes`（都是托管数组；`RejectedCount` 原就有）。
- `TryRecognize` 里新增 `TryBuildCharBoxes(segment, count, …)`：**逐对象** `SelectObj(segment.Chars, i+1)`
  + `SmallestRectangle1`，`single` 在 `finally` 里 `Dispose`；0 字符输出空数组、不报错。
  之所以逐对象取而不是一次算整元组：把"第 i 个框 ↔ 第 i 个类别"写死在代码里，不依赖 HALCON 的输出顺序契约。
- `RunAlgorithm` 成功后赋四个端口（`new HTuple(double[])` 逐项转；空数组 = 空元组）。
- **识别语义未动**：`OcrEngine` / `CharSegmenter` 一行未改（`Recognition.Classes/Confidences/RejectedCount` 直接复用）。
- `Text` 语义未动：仍是 `Classes` 直接拼接，拒识位是 U+001A（帮助里已写清，要可显示文本用 `Detail`）。

### 2. 轮首清零（有意扩到八个端口）

`RunAlgorithm` 开头把 `Text` / `Count` / `Confidence` / `Detail` / `Classes` / `Confidences` /
`RejectedCount` / `CharBoxes` 全部置空。理由：基类 `AutoDisposeRoundOutputs` 只回收 `IDisposable`
（`HImage`/`HRegion`），`string`/`int`/`double`/`HTuple` 端口会原样留下上一轮的值；
只清四个新端口会出现"`Classes` 空但 `Count` 是上一轮的值"，逐项对齐的契约当场自相矛盾。
与 `BlobDetect.RunAlgorithm` 开轮注释同一套（那里把这条叫"极易漏的镜像 bug"）。

### 3. 断言（`FlowCanvasChecks\OcrChecks.cs`，新增 Section `[OCR] 结构化输出端口`，10 条）

1. `端口契约：Classes=string[] / Confidences=HTuple / RejectedCount=int / CharBoxes=HTuple`
2. `结构化端口与 Count 对齐：Classes/Confidences 长度 = Count，CharBoxes 长度 = Count×4`
3. `Classes 直接拼接 == Text（逐字符与整串同源，不是两份数据）`
4. `Confidences 逐项落在 0~1（长度由对齐那条钉住）`
5. `11240B 零拒识：RejectedCount = 0 且 Classes 里没有 U+001A`
6. `每个字符框宽高 > 0 且落在图像范围内（像素含端点，单像素宽的字也是 1）`
7. `字符框按阅读顺序排列（横排：框中心列严格递增）`
8. `【核心】拒识数 == Classes 里 U+001A 的个数（低对比点阵图确有拒识）`
9. `拒识位在 Detail 里是 '?'，非拒识位不是 '?'（逐位对照 Classes）`
10. `【反向】失败轮四个新端口全空、Count = 0（下游读不到上一轮残留）`

- 真图用例：`lot_number_01.png`（11240B，6 字，零拒识）跑长度/同源/置信度/零拒识/框几何/阅读顺序；
  `dot_print_01.png` + `dot_print_02.png`（低对比点阵，参数与既有用例逐字相同）跑拒识数与 `Detail` 对照。
  这两张**允许分割失败**（既有口径是"给出结果或可读原因"），所以一致性只核"跑出结果的那张"，
  "确有拒识"要求两张合计 > 0 —— 与既有第 12 条同口径，不额外收紧。
- 反向判据两条：第 9 条查"非拒识位不许是 `?`"（只查"拒识位是 ?"的话，把 `Detail` 全显示 `?` 也能过）；
  第 10 条同一实例先跑成功、再清掉 `RoiParams`（必然失败），四个新端口必须回到空。
- 端口契约那条**不依赖真图**：`imageDir == null` 时先跑契约再返回，不会跟着图库一起跳掉。

## 五、踩过的坑

1. **`%ERRORLEVEL%` 在 `cmd` 的复合行里是解析期展开**，`dotnet build ... && echo EXIT=%ERRORLEVEL%` 拿到的是上一行的值；
   而 `dotnet build | findstr "个错误"` 的退出码是 `findstr` 的（且中文经管道会按 936 解码，永远不命中）——
   正是 R183 记的那两条。最后用"裸跑 + 工具回报的退出码 + 单独看 `0 个错误`"两路互相印证。
2. **`HTuple` 不是 `IDisposable`**，所以基类轮首回收管不到它 —— 这也是"必须显式清零"的根据（见上）。
3. **`smallest_rectangle1` 是闭区间**：单像素宽的字 `col1 == col2`，直接相减得 0 宽；必须 `col2-col1+1`。
4. **PowerShell 5.1 读无 BOM 的 UTF-8 `.ps1` 会按 936 解码**：临时校验脚本里写中文路径 → 路径变乱码、`ReadAllBytes` 抛，
   且循环里沿用上一轮变量，输出看起来"这条也过了"。改为枚举 `Help` 目录（ASCII 路径）+ 只看文件名，才拿到真结果（R2 同款坑）。
5. **帮助页与代码对不上是静默的**：`11-dev-host-contracts.md` 原写 `Text` 拒识"显示为 `?`"（实际是 U+001A）、
   并断言"没有数组端口"。加端口时必须回读每个页面里"不输出/没有/显示为"这类否定句，否则手册会反向指导现场。
