## 二、已做

### 2.1 缺陷一：FreeProtocol 把「读超时」当写超时用

`FreeProtocolConnection.cs` 原来：

```csharp
_stream.ReadTimeout  = Math.Max(100, _config.ResponseTimeoutMs);   // 读：协议专属字段
_stream.WriteTimeout = Math.Max(100, _config.ReadTimeoutMs);       // 写：借用了通用读超时
```

后果：用户在属性面板上改「读超时(ms)」，对**读**毫无作用（读吃的是「响应超时」），实际只改了写超时——
一个看起来管读、实际管写的死配置。

**改法**：引入单一生效值 `EffectiveTimeoutMs = ResponseTimeoutMs > 0 ? ResponseTimeoutMs : ReadTimeoutMs`，
读、写、超时提示文案三处共用它。规则与 OmronFins 统一为「**专属字段优先、0 = 跟随通用读超时**」。

### 2.2 缺陷二：OmronFins 的「读超时」被自己的默认值永久遮蔽

`OmronFinsConnection.cs` 的取值规则本身是对的（`ResponseTimeoutMs > 0 ? 它 : ReadTimeoutMs`），
但 `OmronFinsConfig.ResponseTimeoutMs` 默认写死 **5000**，于是第一个分支恒真，通用「读超时」永远是死配置。

**改法**：默认值 `5000 → 0`（= 跟随通用读超时，默认 5000，**生效值不变**），补
`[RangeValidation(0, 60000)]` 与字段说明；连接侧加 `Math.Max(100, …)` 兜底。

已存盘的老方案里 `ResponseTimeoutMs` 是显式 5000，反序列化后行为逐字不变——只有新建连接才走"跟随"。

### 2.3 缺陷三：`TriggerWrite` 的文档承诺了不存在的合并

`ICommunicationManager.TriggerWrite` 的 remarks 写着"可以合并连续的写入请求 / 快速连续调用会被合并"，
实现只是逐条入队（每次调用一个队列条目 = 一帧）。下一个人会以为已经合并过而重复实现。

**改法**：删掉三条不成立的优点，明确写"本方法不会合并写入请求"，并指向"要合并必须走显式批量入口（规划中）"。

### 2.4 补断言：四种连接的超时下发此前一条都没有

`CommChecks.ReadTimeoutPropagation` 原来只覆盖 ModbusTcp / SiemensS7 / 串口，EasyNet / MC / FINS / FreeProtocol
**零断言**——这正是错接能活到今天的原因。

| 断言 | 覆盖点 |
|---|---|
| C8-5 | MitsubishiMc：`ReadTimeoutMs` 如实下发到 HSL `ReceiveTimeOut` |
| C8-6 | OmronFins：`ResponseTimeoutMs = 0` 时跟随通用读超时（旧默认会遮蔽） |
| C8-7 | OmronFins：显式填响应超时时以它为准（专属优先） |
| C8-8 | EasyNet：`ReadTimeoutMs` 落到 `NetworkStream.ReadTimeout` |
| C8-9 | FreeProtocol：响应超时留 0 时**读、写都**跟随通用读超时 |
| C8-10 | FreeProtocol：显式填响应超时时读写同一生效值（钉住"读 700 / 写 1600"的旧错配） |

EasyNet / FreeProtocol 的超时设在 `NetworkStream` 上，必须真建连才能核——用本机回环监听（`TcpListener` 绑 0 端口），
连上即断言，服务端不发任何数据，不碰任何真实设备。

## 五、踩过的坑

- **"错接"比"没接"更难发现**：FreeProtocol 不是没下发超时，而是把 A 字段接到了 B 用途上。
  只看"有没有赋值"会判成正常，必须看"赋的是哪个字段、管的是哪条路径"。
- **默认值会遮蔽同义字段**：FINS 的 `ResponseTimeoutMs = 5000` 让通用「读超时」永久失效。
  凡是"专属字段 > 0 优先"的取值规则，专属字段的默认值必须是 0（跟随），否则通用字段就是死配置。
- **文档里的"优点"要当断言看**：`TriggerWrite` 那条"可以合并"写得像已实现的能力，实际没有。
  改这类文档时顺手确认"实现真的做了吗"，否则下一个实现者会重复造。
- **`CommChecks` 的 C17-3 是时序敏感断言**（连 `127.0.0.1:1` 等 OS 层拒绝，本机约 2~3s，阈值 2900ms）：
  本轮首跑 3008ms 红了一次，重跑 2320ms 绿。与本次改动无关，属既有抖动（见台账 C-28 同族）。
- **给需要真建连的断言找"不碰设备"的靶子**：`TcpListener(Loopback, 0)` + 只 accept 不发送，
  对 EasyNet / FreeProtocol 这种"Connect 只做 TCP 握手"的连接足够，且不依赖任何外部服务。
