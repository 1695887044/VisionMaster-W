## 一、需求与决策

t1~t8 已经把通信链路重构成"结构化地址 → 连接层 → 连接专属线程（ConnectionWorker）→
批量轮询规划器（PollBatchPlanner）→ Manager 统一入口"的新模型。原来挂在
`AdvancedCommunicationManager` 旁的两套旧体系（`Data/`、`Monitor/`）随之失去所有调用方，
成为死代码。t9 的任务就是把它们清掉，避免后人误以为那是"现役扩展点"。

清理前先做**引用实证**（Grep 全仓，含 .cs/.xaml/.json）：

| 待删对象 | 外部引用数 | 结论 |
| --- | --- | --- |
| `Communications/Data/`（7 个文件） | 0（仅彼此互引） | 可删 |
| `Communications/Monitor/`（2 个文件） | 0 | 可删 |
| `Communications/Core/IConnectionHealthCheck.cs` | 0（唯一实现者是 `Monitor/ConnectionHealthCheck.cs`） | 删 Monitor 后才变孤儿，**已向用户确认后一并删除** |

用户拍板：**一并删除** `IConnectionHealthCheck.cs`。

## 四、重构主线回顾（t1~t10 知识索引）

| 阶段 | 主题 | 开发记录 |
| --- | --- | --- |
| t1~t4 | 基线梳理 / 结构化地址体系（`Address/`）/ 连接层拆分（`Connection/`）/ `ConnectionWorker`（每连接一条专属线程，I/O 全串行） | 无独立记录文件（进度见 todo 与后续记录的回顾部分） |

| t10 | 全量 `/t:Rebuild` 验证 | 本文 |

最终线程模型一句话总结：

> **一条连接 = 一个 `ConnectionWorker` + 一条专属后台线程**；
> 读（含批量轮询）、写、测试、建连、断开全部以 `WorkItem` 投递到这条线程串行执行；
> 调用方（UI / 变量模型）只通过 Manager 的统一入口说话，状态真相源是 Worker 状态机，
> 经 `ConnectionStateChanged` 单向广播出去。

## 五、已知边界（继承自各阶段，尚未消除）

1. **B5 协议选项不一致**：用户上轮明确决定保留现状（欧姆龙/三菱/OPC UA 选项点"添加"会抛 `NotSupportedException`）。
2. **`ExecuteTestConnection` 仍为阻塞调用**：`TestConnection` 内部 `worker.Invoke(...).GetAwaiter().GetResult()`，设备不可达时 UI 会等一个 socket 超时。
3. **`IsRunning` 仍是手工置位**，未接入 Worker 状态机。
4. **`UpdateConnection` 会重建 Worker**：改配置后连接状态丢失，需重新点"连接"。
5. **删除的 `Data/`、`Monitor/` 能力未做替代实现**：若后续确实需要"数据点历史/报警"这类功能，应按新模型重写（注册为变量 + 轮询），而不是恢复旧类。
6. **未做运行期实测**：t8/t9 只验证到编译通过，UI 实际观感与状态事件回报时序仍需运行确认。
