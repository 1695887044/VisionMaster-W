## 一、结论先说（不粉饰）

**P1 的四条改进都落地了，但在 3000 节点上几乎没有可测量的收益。**

| 场景 | 改前 | 改后 | 变化 |
| --- | --- | --- | --- |
| 3000 节点 / 10 流程 `heavy_layout` | 1327 ms | 1376 ms | **在噪声内（甚至略高）** |
| 3000 节点 / 单流程 `heavy_layout` | 18090 ms | 18002 ms | 持平 |
| 409 步真实方案 `heavy_layout` | 206 ms | 206 ms | 持平 |
| 其中 GC 暂停（3000 节点） | — | **≈ 900 ms** | 占 `layout` 的 **65%** |

原因见 §四：**大头是 GC 停顿，而 GC 停顿来自"一次性造出几千个对象"**。P1 减的是"白造的线 VM"，
但节点 VM、`ItemContainer`、模板元素、`CanvasLinkBinding` 仍然按全量造——
只有把"造对象"变成 O(可见) 才能根治，那是虚拟化（P3）的活。

四条改动本身仍然正确（少造对象、少做无用功），保留；但不能拿它当"几千点不卡"的答案。

## 二、改了什么

### P1-1 渲染期不再逐节点重算锚点（`FlowCanvasViewModel.cs`）

**问题**：`RefreshNodeState` 每建一个节点就写 `node.Location`（`:1013`），
`OnNodePropertyChanged` 立刻对**上一流程尚未清空的 `Links`** 跑整轮 `UpdateLinkAnchors()`。
复杂度 O(新节点数 × 旧线数)，每次还会发 4 条 `PropertyChanged`。

**改法**：新增 `_suppressAnchorUpdate`，`Render` 全程置位（`try/finally`），
`OnNodePropertyChanged` 判它直接 return。锚点由 `RenderCore` 自己在连线全部建好后算（`BuildLinks` 末尾 + 顺序链后各一次）。

**为什么不用 `_rebuilding` 代替**：`OnNodePropertyChanged` 故意不判 `_rebuilding`——
拖动时要实时跟随，而拖动期间 `_rebuilding` 是 false。

### P1-2 隐藏的数据线不再构造 VM（`FlowCanvasViewModel.BuildLinks`）

**问题**：`ShowDataLinks=false`（默认）时仍为每对端口建 `CanvasLinkViewModel` + 3 个命令 + N 个
`CanvasLinkBinding`，最后逐根 `UnhookModels` + `RemoveAt` 丢掉。

**改法**：两遍走。第一遍只聚合（新的私有类 `AggregatedLink` 记 producer/consumer/bindings/是否非法），
第二遍只为"会显示的线"造 VM。判据与旧的"建完再删"逐字一致：`!ShowDataLinks && !HasIllegal` 才跳过。

**语义未变**：过滤仍晚于聚合与合法性判定（否则后到的非法绑定会挂在一根从未渲染过的线上）。

### P1-3 节点池跨流程存活（`FlowCanvasViewModel`）

**问题**：换流程无条件 `_nodePool.Clear()`，A→B→A 时 A 的节点全重建。

**改法**：
- 不清池；`PrunePool` 的判据从"在不在**当前拓扑**"改成"在不在**当前方案的任何流程**里"。
  只有"步骤被删了"才回收。
- 方案级 StepID 集合**按方案缓存**（`_poolScopeSolution` / `_poolScopeIds`），换方案才失效——
  每帧重扫全方案在 3000 节点下是白交的钱。
- 硬上限 `NodePoolHardLimit = 4000`，超了整体清一次，防长期运行无限涨。

**为什么原来会清池**：注释写"StepID 在不同流程间可能重复"——但 `GetOrCreateNode` 的复用判据
已经是「StepID 命中**且** `ReferenceEquals(pooled.Model, step)`」，同 Id 不同实例照样重造。
清池只是白丢复用机会。

### P1-4 流程栏收起时停止工作（`ProcessView.xaml.cs`）

**问题**：只挂 `Loaded/Unloaded`。面板 `Collapsed` 不触发 `Unloaded`，`ProcessViewModel` 的
200ms 计时器继续每拍遍历整棵流程树并发统计通知。

**改法**：加 `IsVisibleChanged` → `Activate()/Deactivate()`（幂等共存）。

**画布没做同样处理，原因**：`FlowCanvasView` 的 `Deactivate` 会 `Detach()`（丢掉节点池订阅与图纸挂接），
重新 `Activate` 会 `Rebuild()` 全量重建——对"切到视觉图像标签页再切回来"这种高频操作，
反而比让它继续挂着更贵。**这是取舍，不是遗漏。**

### 顺带修的一个 bug

`FlowSwitchPerf` 默认读 `解决方案\综合测试台（1023）.vms`，该文件被"保存为文件夹式方案"取代后消失，
探针从此不带参数就报"方案不存在"。改成：显式参数优先，否则取 `解决方案\` 下（含一级子目录）**最大的** `.vms`。

## 三、压测方案（新增）

`tools\vms-generator` 新增 `Program.StressSolution.cs` + `--stress` 入口（无参 `dotnet run` 行为不变）：

```powershell
# 3000 节点摊在 10 条流程上（压"切换"）
GenSolution.exe --stress

# 3000 节点塞进一条流程（压"单帧重建"）
GenSolution.exe --stress --giant

# 其它：--nodes N / --flows N / --seed N / --layout none / --out <path>
```

设计决策：
- **全部步骤 `IsDisEnable = true`** → `FlowCompiler.CompileSteps` 直接 `continue`（`Engine\FlowCompiler.cs:303`），
  所以不需要图片/设备/通讯/变量定义就能打开。
- **预填 `Layout.Nodes`** → 不触发 `AutoLayout`，让"首次打开"与"热切换"同口径。
- **真实连线**：同层相邻叶子接成 `Delay.ET → Delay.Delay` 数据链。没有 `LinkedSources` 的图根本走不到
  `BuildLinks`，P1-2 的收益会被测成 0（本轮先踩过这个坑，第一版方案没有连线）。
- 结构混合 `If`（`Expression="1 > 0"`，避免"缺条件"红框）/ `For` / `While`（`BranchType=5`）/
  `Parallel`（`ExecutionMode=0`，避开 `[ParallelSafe]` 硬失败）。

产物（都在 `解决方案\`，**没使用** `MissingSolutionSamples` 那 5 个名字）：

| 文件 | 规模 |
| --- | --- |
| `压测-3000节点.vms` | 13 条流程 / 3561 步 / 561 容器 / 982 泳道 / 3.9 MB |
| `压测-3000节点-单流程.vms` | 4 条流程 / 3566 步（其中一条 3542 步、4532 个画布节点）/ 3.9 MB |

## 四、实测（`--switch-perf`，Debug，3 次中位数）

### 4.1 3000 节点 / 10 流程

| 段 | 改前 | 改后 |
| --- | --- | --- |
| `vm` | 51.7 | 48.6 |
| `layout` | **1327.4** | **1376.3** |
| `deferred` | 131.0 | 157.7 |
| `total` | 1510.2 | 1582.5 |

### 4.2 单条 3542 步流程（4532 个画布节点）

| 段 | 改前 | 改后 |
| --- | --- | --- |
| `vm` | 2076.7 | 1936.7 |
| `layout` | **18090.0** | **18002.4** |
| GC 暂停 | 9805.3 | 9816.7 |
| `total` | 21659.3 | 21522.7 |

`vm` 段掉了 7%，`layout` 几乎不动，GC 占 55%。

### 4.3 409 步真实方案（`综合测试台（测试员版）.vms`）

`heavy_vm=9.0 heavy_layout=206.4 heavy_settle=13.6 heavy_total=229.0`
——与基线报告里的 78 步方案（`heavy_layout ≈ 210`）同量级，**说明 409 步方案里最大单流程只有几十步**，
真正的重负载是压测方案。

### 4.4 归因（`diag` 相位，3000 节点 / 10 流程）

| 组 | 做法 | `layout` 中位数 |
| --- | --- | --- |
| A | 两栏可见但收起 | **~1500 ms**（GC 600~840） |
| B | 摘画布 DataContext | **~230 ms**（GC 75~205） |
| C | 再摘流程栏 DataContext | **0 ms** |

单次切换分配：**27 MB**（353 步流程，451 个节点 / 254 根线）。

> 注意 "两栏收起" 并不省时间（A 组仍是 1.5 s）——**收起面板 ≠ 不付钱**，
> 这与基线报告 §1 第 3 条一致，本轮再次确认。

## 五、目标未达成（如实登记）

立项时的验收口径是「3000 节点切换 `heavy_layout` 降到 1000 ms 以内」。**实际 1376 ms，未达标。**

按方案里写好的约定：「达不到就如实报数字，不进 P2/P3」。现在把判断权交回用户：

- 若要继续降，**只有 P3（虚拟化）这一条路**，因为 65% 是 GC 停顿，而 GC 停顿来自按全量造对象。
- P3 的前置调研与两条路线对比见 `docs\performance\2026-10-23-画布虚拟化（P3）前置调研.md`。
- 调研里给了个**1 天成本的决策实验**：临时把 `Nodes` 裁到"视口内 + 缓冲"量一次，
  看 `heavy_layout` 掉多少，再决定要不要投 1~2 周。
