### 3. 根因链（机制）

1. `Core\Lifetime\AppLifetimeService.cs` 的 `RunStartupChecksAsync` 给**每个**自检项 30 秒兜底超时（原为 `linked.CancelAfter(30_000)` 写死，现 `:107`）→ 超时判 `CheckLevel.Error`；
2. `Error` 级失败 → `VisionMaster\App.xaml.cs:122` `Environment.Exit(2)` —— **干净退出**（所以 Windows 事件日志无记录、`crash_reports\` 无留档）；
3. `VisionMaster\Lifetime\Checks\PluginScanCheck.cs` 要冷读 `Modules\`（**37 个 DLL / 12,848,216 B（12.25 MiB）**，含 6.25 MiB 的 `Microsoft.CodeAnalysis.CSharp.dll`）并逐个 `Assembly.LoadFrom` + 反射扫描（`Engine\PluginService.cs:39-45` 定位目录、`:51-61` 逐个加载、`:205-214` `Assembly.LoadFrom` + `GetTypes()`；其中 `Plugin.CSharpScript.dll` 的引用链会把 `Microsoft.CodeAnalysis` 全家桶 4 件 / 9.26 MiB 一并拉进来）——它就是那条波动带。

### 4. 三处叠加的设计问题（都在本轮修掉）

1. **30 秒超时对"冷读 12 MB + 反射扫描 37 个程序集"太紧**——历史最慢 28.83 s，等于每天在掷骰子；
2. **`PluginScanCheck` 自己的注释写着「失败仅警告不阻断」（`:11-12`），它内部 catch 抛异常时返回的确实是 `Warning`（`:65-69`）——只有"超时"这一条路径被外层升级成了 `Error`，两者口径自相矛盾**；
3. **`Environment.Exit(2)` 立刻退出反而让第二次启动必然命中热缓存**——症状因此稳定复现（"第一次退、第二次成功"）。

## 三、机制与逐项口径

### 1. `TimeoutMs` / `TimeoutLevel` 的契约语义

| 成员 | 默认 | 语义 | 谁该改 |
| --- | --- | --- | --- |
| `TimeoutMs` | `DefaultTimeoutMs` = 30_000 | 本项兜底超时（毫秒）。**超时不等于"检查失败"**——执行方抛异常时可自行决定级别；**超时**由宿主按 `TimeoutLevel` 处置 | 冷启动明显更慢的项自己调大（本仓目前只有 `PluginScanCheck` → 120_000） |
| `TimeoutLevel` | `CheckLevel.Error` | 本项"未在 `TimeoutMs` 内返回"时按什么级别处置 | 只有"该项缺失也不影响主界面可用"的项才放宽（本仓目前只有 `PluginScanCheck` → `Warning`） |

### 2. 超时判定的四种组合（旧 vs 新）

`winner = await Task.WhenAny(execTask, Task.Delay(Timeout.Infinite, linked.Token))`：

| 组合 | winner | `linked` 已取消 | `execTask.Status` | 旧判定（只看赢家） | 新判定（`AppLifetimeService.cs:115-117`） |
| --- | --- | --- | --- | --- | --- |
| 按时完成 | `execTask` | 否 | `RanToCompletion` | 取 `.Result` ✅ | 取 `.Result` ✅ |
| 真超时·**实现尊重 `ct`**（取消后以已取消状态收尾） | **`execTask`** | 是 | `Canceled` | 取 `.Result` → **`AggregateException`** → `catch (Exception)` → **`Error「检查异常」`**（`TimeoutLevel` 被架空）❌ | `timedOut=true` → 按 `TimeoutLevel` 处置 ✅ |
| 真超时·实现不响应取消 | `Delay` | 是 | `Running` | `timedOut=true` ✅ | `timedOut=true` ✅ |
| 外部取消（窗口关闭等） | 任意 | 是（`ct` 也取消） | 任意 | `catch (OperationCanceledException) when (ct.IsCancellationRequested)` → **rethrow** ✅ | 同左 ✅（新判据带 `!ct.IsCancellationRequested` 守卫，不会把外部取消误判成超时） |

### 3. `FormatTimeout`（`:158-159`）

`ms >= 1000 ? $"{ms / 1000} 秒" : $"{ms} 毫秒"`。断言夹具用 200ms 超时，旧写法（统一按秒）会把 200ms 显示成 `0 秒`——"检查超时（0 秒）"看不出是哪里配的。**整数除法向下取整**（1500ms 显示"1 秒"），纯文案问题，见 §七。

### 4. `PluginScanCheck`：120 秒 + Warning

- **120 秒**：历史最大 28.83 s 的 4 倍余量；
- **Warning**：本项缺失不影响主界面可用（插件列表为空，进界面后可重扫），把"磁盘慢"当成"软件坏了"代价过大。

## 四、关键技术决策（为什么）

### 1. 为什么超时级别要**逐项声明**，而不是全局放宽

自检链 6 项里有两项**必须**保持 `Error`：`SingleInstanceCheck`（拿不到互斥体 = 双开，`:25`）、`ConfigCheck`（`AppConfig.json` 读不出 = 工作目录坏了，`:35` / `:49`）；第三项 `HalconCheck` 的失败出口**本来就是全 `Warning`**（`:148`）且自带 10 秒内层封顶（`:37` / `:63`），根本走不到外层超时。**全局放宽 = 把单实例 / 配置校验也放过**——"任何自检超时都放行"的后果比误杀更严重。所以级别必须由**每一项自己声明**，默认口径**仍是 Error**（守门断言 ⑤ 反向钉死这一点）。

> 附带复核（评审逐项核过，6 个既有项**均无同类误杀**）：`ConfigCheck` 只读 1.3 KB JSON（`AppConfig.json` 实测 1305 B）；`HalconCheck` 自带 10s 内层封顶且失败出口全 Warning（`:148`）；`CommunicationCheck` 自带 12s 预算（`:26` `TestBudgetMs`）+ 3s 单项超时（`:29`）且全 Warning；`SingleInstanceCheck` 瞬时返回；`HelpCatalogCheck` 纯内存读内嵌资源。

### 2. 为什么超时判定**不能只看 `WhenAny` 的赢家**（本轮核心教训）

**完整推理链**：

1. 尊重 `ct` 的实现（典型：`await Task.Delay(..., ct)`）在超时取消后会**以已取消状态收尾**——但它**仍然赢下 `WhenAny`**（先于 `Task.Delay(Infinite, linked.Token)` 完成）；
2. 此时 `winner == execTask`，旧判定放行，照直取 `execTask.Result`；
3. .NET 9 上 `Task<T>.Result` 对 **Canceled** 任务抛的是 **`AggregateException`**（内层 `TaskCanceledException`）——**不是** `OperationCanceledException`（本记录作者用独立 .NET 9 探针实测确认）；
4. 于是下面这个过滤器**不匹配**：`catch (OperationCanceledException) when (ct.IsCancellationRequested)`（`:123`）——外部 `ct` 根本没取消；
5. 落进 `catch (Exception)`（`:127-130`）→ `result = CheckResult.Fail(CheckLevel.Error, "检查异常：" + ex.Message)` → **`TimeoutLevel` 声明的级别整个架空**。

**实测频率**（本记录作者独立探针，.NET 9 控制台，临时目录、未进仓库；检查项与断言 stub 同形——内联 async 方法 `await Task.Delay(30s, ct)`）：

- 旧逻辑 300 轮：**98~138 轮**落进 catch 记成 `Error「检查异常」`（三次重复：128 / 98 / 138，即 **33%~46%**）；
- 新逻辑 300 轮：**300/300** 正确判超时、按声明级别处置；
- 竞态胜率随机波动大（评审另测 26/40；探针形态不同胜率不同），但结论一致：**这是多数路径，不是理论边角**。

**修法**（`:115-117`）：

```csharp
bool timedOut = winner != execTask
    || (linked.IsCancellationRequested && !ct.IsCancellationRequested
        && execTask.Status != TaskStatus.RanToCompletion);
```

三个子条件的职责：`winner != execTask`（普通超时）；`linked.IsCancellationRequested && !ct.IsCancellationRequested`（是**本轮**超时取消、不是外部取消）；`Status != RanToCompletion`（赢家是 `execTask` 但**没跑完**——正是"已取消收尾"这一条）。

> **这条 bug 是实现方自己写的断言在自测时抓到的**（`StartupChainTimeoutIsNotFatal` 的 ① 在自测中先红后绿），不是预防性改动。

### 3. 为什么选 120 秒

- 历史最大 28.83 s（10-01 22:50:19），120 s = **4 倍余量**；
- `Modules\` 会继续长大（历史最慢那次是 38 个插件时测到的 28.8 s，现在已是 50 个插件），且慢盘 / 杀毒实时扫描（读 12 MB 会被逐文件检查）都是现场变量；
- 启动链**没有总看门狗**（退出链才有，`ExecuteExitChainAsync` 30 s），所以每一项的 `TimeoutMs` 就是最坏启动时长的组成部分：从 `6×30 s = 180 s` 升为 `5×30 s + 120 s = 270 s`（Splash 全程保持响应、帧泵在跑，无实际阻断；见 §七-2）。

### 4. 残留风险与口径（120 秒仍未跑完时才会发生）

- `PluginScanCheck.ExecuteAsync` 的 `Task.Run(..., ct)`（`:57-62`）**不响应取消**——`InitPlugins()` 一旦开始就继续跑完；
- 后台扫描继续，但 `PluginProvider` 四个插件字典返回的是**防御性副本**（`Engine\PluginProvider.cs:35/43/51/59` 的 `new Dictionary<>(...)`），**迟到完成的注册不会通知已绑定的界面**；
- 且紧随其后的 `HelpCatalogCheck`（`VisionMaster\Lifetime\Checks\HelpCatalogCheck.cs:38-41`）会**一次性**把帮助目录建成（`HelpCatalogService.Build()` 幂等、不会自动重跑，`:96-148`），超时场景下建出的是**缺插件页**的目录；
- 两种表现都是"**工具箱为空 + 帮助缺插件页**"，**重启一次即可恢复**，远好于"进程直接退出"。日志里会留下明确提示。

### 5. 为什么超时文案要单独一个 `FormatTimeout`

断言夹具用 200ms 超时。旧文案统一按秒 → `200 / 1000 = 0` → **"检查超时（0 秒）"**，日志里看不出是哪里配的、像程序算错；改为不足 1 秒显示毫秒后，"检查超时（200 毫秒）"直接指认配置来源。

## 五、守门断言（5 条）与变异反证

`FlowCanvasChecks\FlowEngineFixChecks.cs` 的 `StartupChainTimeoutIsNotFatal()`（`:154-193`），用 `AppLifetimeService` + 三个私有 stub 真跑启动链（无 GUI）：

| # | 断言 | 判据 | 行 |
