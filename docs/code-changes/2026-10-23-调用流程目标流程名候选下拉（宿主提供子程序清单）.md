# 调用流程：目标流程名改为宿主提供的子程序候选下拉（2026-10-23）

## 背景

「调用流程」(`Plugin.RunFlow`) 的 `FlowName` 端口一直是普通 `InputPort<string>`：
通用参数面板渲染成「文本框 + 🔗 链接 + ✕ 清除」，用户只能手打流程名，或者从上游文本输出绑一个值。
但"哪条流程允许被当子程序调用"只有宿主知道（判据是 `FlowModel.InvokeType` 的 `Subroutine` 位），
插件物理上看不到方案里的流程表。

后果是两类错误都只在运行期暴露，且日志里长得一样：

- 名字拼错 / 改名后失配 → `当前方案中没有名为「X」的流程`；
- 名字对但没勾「子程序」→ `流程「X」未开放「子程序调用」`。

同时，把流程名做成可绑定的"值"端口违反 R33（名字类端口不许挂通用绑定弹窗）：
上游给的值不是方案里的名字时，等于把编译期能发现的问题推到运行期。

## 口径（本次定稿）

| 项 | 决定 |
| --- | --- |
| 候选来源 | **宿主提供**：`StepConfigOptionKind.SubroutineFlowName` + `Engine\SubroutineFlowOptions.cs`，启动时经 `StepConfigOptionSource.RegisterAdditional` 注册；界面每次打开现取（不用 `PresetOptions` 快照——插件实例在方案打开前就被反射 new 出来，快照必然为空） |
| 过滤 | 只列 `(InvokeType & Subroutine) != 0` 的流程；同名流程按名去重（`FlowInvoker.FindFlow` 也是取第一条） |
| 值 | 流程名本体（`Ordinal` 精确匹配，与 HTTP 路由 / 运行状态镜像同口径）；显示文本只加状态后缀，不参与寻址 |
| 状态后缀 | `（已禁用）` / `（步序已加密）` / `（当前流程，不能调用自己）`。这些项**仍列出**：剔掉会让已配好的值在下拉里显示空白（值还在、只是选不到），用户会以为配置丢了；标注才看得出失败原因 |
| 链接 | 封闭集合端口，`LinkableValueEditor` 自动隐藏 🔗 / ✕（R33）。要按配方选流程，改用「分支匹配」/「条件判断」把不同的「调用流程」分到各分支 |
| 空候选 | 方案里一条子程序都没有时，控件退化成可手填文本框并提示"无候选，可手填"；手填能过界面，运行期仍会被门禁拦下 |

## 边界与已知取舍

- **改名连锁仍在**：被调流程改名后，已配步骤的存档值还是旧名，下拉会显示为空（值未被清掉）；重选一次即可。
  候选里没有"旧名占位项"，因为显示文本不能当值写回。
- **动态流程名下线**：原先文档里的"码读取.Text → FlowName"不再可用（R33）。
  按配方选流程改为分支画法；`TimeoutMs` 仍可由上游给。
- **老 `.vms` 的上游连线**：升级前已经连过的步骤，连线**仍生效**（不破坏既有工程）；但面板下拉照常显示，
  选一项即 `RemoveLink` 并写固定值，绑定弹窗也不再放开上游模式。新配置无法再产生这种连线。
- **仅大小写重名**：`Abc` / `abc` 两条流程都可被 `FindFlow` 按 Ordinal 命中，但全局候选表
  （`StepConfigOptionSource`）按 OrdinalIgnoreCase 去重，下拉只列第一条。这是既有全局口径
  （运动轴/通讯变量共用），这类名字本身极易误选，建议在流程管理里改名区分。
- **没有自定义视图**：仍是通用参数面板，只是这一行由 `LinkableValueEditor` 渲染成下拉。
  以后若要"下拉 + 手填 + 链接"三合一，需要新增 `IPluginCustomViewProvider`，并重新讨论 R33 的例外口径。
- **手册与代码同源**：候选类别、宿主来源、注册点、断言四处必须同口径（已写入 10-dev 第十节）。
