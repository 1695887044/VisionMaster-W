# 线序检测：结果投射到 1 号视图 + 脚本引用集修复 + 配置界面列宽

用户报了三件事：**界面显示不全**、**运行不通过**、**想把结果投射到 1 号画布**。

其中「运行不通过」是真 bug，根因不在流程本身，而在 **C#脚本引擎的 Roslyn 引用集依赖加载顺序**。

---

## 一、需求与决策

### 1. 用户原话

> 「界面显示不全 / 运行不通过 / 我想的是 你把结果投射到1号画布上」

### 2. 「运行不通过」的根因（本轮最有价值的发现）

主程序日志：

```
步骤[线序检测.C#脚本_0]执行失败：第 19 行 第 30 列:
The type or namespace name 'HImage' could not be found (are you missing a using directive or an assembly reference?)
```

而**同一份脚本、同一份插件**，在无界面断言宿主里编译通过、跑出正确线序。差异只可能在"引用集"。

逐层排查后定位到 `VisionMaster.deps.json`：

```json
"libraries": {
  "halcondotnet/23.5.0.0": { "type": "reference" },   ← 关键
  "Newtonsoft.Json/13.0.4": { "type": "package" },
  "VM.Core/1.0.0":          { "type": "project" }
}
```

`type: "reference"` 的库**不会被塞进运行期 TPA**（`TRUSTED_PLATFORM_ASSEMBLIES`）。
于是 `CSharpScriptEngine.GetOptions()` 里那两条来源——TPA + 「当前已加载程序集」——能不能拿到
`HalconDotNet`，就完全取决于**编译脚本那一刻它有没有恰好被加载过**：

| 环境 | 脚本编译时 HalconDotNet 是否已加载 | 结果 |
|---|---|---|
| 无界面断言宿主 | 是（先跑采集，碰过 HImage，顺带加载） | 编译通过 |
| 主程序 | 否（脚本先编译） | `HImage` 找不到 |

这是典型的"测试能过、现场不能过"——**引用集不该依赖加载顺序**。

### 3. 三项修改的决策

| # | 决策点 | 结论 | 为什么 |
|---|---|---|---|
| 1 | 引用集怎么修 | 在 TPA + 已加载程序集之外，**补扫宿主根目录的 `*.dll`** | 把"依赖加载顺序"这个不确定性从根上掐掉；原生 dll 不是托管程序集，`CreateFromFile` 抛异常会被就地丢弃，不影响其余引用 |
| 2 | 结果怎么投射 | 走**预览事件自带的标注层**（`MeasureAnnotation`：线/角度/文本），不往图像里画 | 主程序本来就有"图像 + 标注同帧覆盖渲染"的通道（`ImageView` → `HalconBase.RenderAnnotations`），复用它比在 Halcon 里往图上写字干净得多 |
| 3 | 脚本怎么写标注 | 给脚本门面加 `NewMarks()` / `MarkLine()` / `MarkText()`，脚本用 `var` 接住即可 | 脚本正文里**不出现任何标注类型名**，少一个类型就少一处可能解析失败的地方；调用点也短 |
| 4 | 投射内容 | 绿竖线 = 采样线位置；每根线右侧 = 判到的颜色（判对绿字、判错红字）；顶部 = 结论（合格绿、不合格红） | 现场要一眼看出"在哪量的、每根判成什么、这一单过没过" |
| 5 | 投射到哪个窗口 | 由脚本决定（参数区有 `ShowView` 常量，调用点也可直接写字面量），随方案走 | 用户指定；投射窗口是**产品配置**不是算法正确性，所以断言也不钉它（见第五节） |
| 6 | 界面怎么修 | 加宽变量表列宽 + 关键控件设 `MinWidth` + 「显示窗口」列改 `Auto`；左列横向滚动**保持 `Disabled`** | 见下文第四节"二次定位"——第一版把横向滚动改成 `Auto` 是错的，反而更糟 |

## 四、二次定位：「输入输出变量显示不全」的真正根因

用户回了一张更清楚的图，一看就明白上一版改错了方向。

**症状**：「每项生成一个动态输入端口；连线取上游值…」这句提示是**被硬切断的**，不是换行；
输出变量右边那几列（显示窗口 / 备注 / ✕）整列看不见。

**根因**：第一版把左列的 `HorizontalScrollBarVisibility` 从 `Disabled` 改成了 `Auto`，
本意是"宁可出滚动条也不让内容够不着"。但 WPF 的 `ScrollViewer` 在允许横向滚动时，
会用**无限宽度**去测量内容 —— 于是里面 `TextWrapping="Wrap"` 的提示文字**不再换行**，
变成一条几百像素的长线，把卡片顶宽；卡片超出视口后被裁掉，右边的控件就全被推到视口外。

**修法**：

| 改动 | 从 | 到 | 为什么 |
|---|---|---|---|
| 左列横向滚动 | `Auto` | `Disabled` | 锁死横向，`TextWrapping` 才会生效，内容才塞得进视口 |
| 输出行「显示窗口」列 | `Width="78"` | `Width="Auto"` | 这一列只有图形输出（HImage/HRegion…）才显示，非图形时控件是 `Collapsed`；改成 Auto 后连宽度一起收掉，省下的宽度留给「备注」 |

改完的宽度账（左列 460，减滚动条 8、卡片内边距 24，可用 428）：

| 行 | 定值部分 | 弹性列实得 |
|---|---|---|
| 输入 | 名称 120 + 类型 104 + 删除 30 + 外边距 16 = 270 | 连线编辑器 **158px** |
| 输出 | 名称 112 + 类型 100 + 删除 30 + 外边距 18 = 260 | 备注框 **168px** |

**教训**：`ScrollViewer` 的 `HorizontalScrollBarVisibility` 不是一个"要不要滚动条"的开关，
它会连带决定**内容是被约束测量还是被无限测量**——后者会让 `TextWrapping`、`*` 列宽一起失效。
"改滚动条比改列宽省事"这个直觉是错的。

## 五、追加：断言不再与用户可改参数耦合

用户在主程序里把脚本的投射调用点从 `ShowImage(image, ShowView, marks)` 改成了 `ShowImage(image, 2, marks)`，
结果两条断言当场变红——**这是断言写得太死**：

| 原来 | 现在 | 为什么 |
|---|---|---|
| 断言源码里含 `ShowImage(image, ShowView, marks)` 字面量 | 断言源码里含 `Context.ShowImage(` | 调用点写法是用户在界面上随手可改的参数 |
| 断言"带标注那帧落在第 1 号窗口" | 断言"带标注那帧恰好 1 帧，且窗口号在 1~9 之间" | 投射到第几号窗口是产品配置，不是算法正确性 |

算法正确性（线序、标注内容、标签位置）继续钉死；**可配置项不钉死**。这是断言该有的分寸。

## 六、三轮都没"生效"的真相：改动压根没投递到 `Modules\`

用户连着三轮反馈「重启后还是不行」。**不是改法不对，是改的东西从没到过他手上。**

对比同一时刻的两个文件：

| 文件 | 时间 | 含本轮改动（`VarRowInput`） |
|---|---|---|
| `Plugins\Plugin.CSharpScript\bin\Debug\...\Plugin.CSharpScript.dll` | 02:38:08 | **有** |
| `Modules\Plugin.CSharpScript.dll`（主程序实际加载的那份） | 02:32:48 | **没有** |

**为什么**：插件产物靠构建的 PostBuild 拷进 `Modules\`。构建时若主程序在跑，它占着
`hdevenginedotnet.dll` 与 `Microsoft.CodeAnalysis*.dll`，拷贝报 `MSB3073` → **整次构建判失败** →
投递没做完。于是用户"重启"之后加载的仍是旧插件，症状当然一模一样。

**怎么定死的（不再靠截图猜）**：写了个一次性探针，按主程序同样的路子建视图
（`GetConfigView` → `Initialize(stepData)`），在 STA 线程挂到屏幕外的透明窗口上逼出 `Loaded`，
再 `Measure/Arrange` → `RenderTargetBitmap` 出 PNG，**同时把可视树的真实宽高 dump 成文本**。
离屏渲染 + 数值 dump 实测：

```
外层 Grid w=1176 cols=[460,716]          ← 左列 460 生效
输入行   TextBox w=120 h=32 text='Image'
         ComboBox w=92 h=32 sel='HImage'  ← 92 = 列 104 − 外边距 12
         链接框   TextBox w=120 h=21 text='图像采集_0.Image'   ← 完整显示
输出行   TextBox w=112 h=32 text='WireCount'
         备注框   TextBox w=178 h=32 text='检测到的线数'
```

**结论：布局本身早就对了**（列宽、行高、文字换行全部正常）。用户看到的自始至终是 02:32 那版，
也就是"列宽已加宽、但行高还是 24、提示文字还不换行"的上一轮产物。

**两条教训**：

1. **改了插件必须走完这一串**：关掉程序 → 构建 → **确认 `Modules\` 里那份 dll 的改动真的变了** → 再启动。
   只看源码、或只看"构建成功"都不够 —— 构建可能整体判失败（本轮就是），投递在半路断掉。
2. **布局问题别靠截图猜**：截图会被查看器缩图，12px 的字糊成一条线，据此推断"文字被切成横线"完全是误判。
   离屏渲染 + dump 真实宽高，一次就能定位（探针用完即删，方法记在这里）。

## 七、已知边界

1. **改插件必须「关程序 → 构建 → 核对 Modules → 启动」四步走**
   插件 dll 是进程启动时 `Assembly.LoadFrom` 进来的，不重启跑的还是内存里那份；
   而构建时程序在跑，PostBuild 拷 `Modules\` 会失败（`MSB3073`）并让整次构建判失败、投递中断。
   所以要**先关程序再构建**，并且构建后核对 `Modules\` 里那份 dll 确实更新了（本轮踩的坑，见第六节）。
2. **界面已用离屏渲染核对过（不再只是"请看"）**
   左列 460、行内控件 120×32 / 112×32 / 备注 178×32、提示文字正常换行、链接框完整显示 —— 都量过了（第六节）。
   真机上若仍有差异，多半是宿主给的对话框宽度不同：窄于约 850px 时右列会先压到 MinWidth(360)。
3. **标注的实际绘制没被断言覆盖**
   断言只证到"带标注的预览帧确实发出去了、内容正确"。真正把文字画到窗口上的是
   `HalconBase.RenderAnnotations`（WPF/Halcon 窗口路径），无界面宿主里跑不到，只能肉眼验。
4. **投射会覆盖采集步骤那一帧**
   采集与脚本都往 1 号窗口发帧，后发的（脚本）胜出。若脚本失败，窗口里留的是采集的原图（没有标注）——
   这也是刻意的：宁可看到原图，也不要看到一张空窗口。
5. **引用集在进程内只构建一次**
   `GetOptions()` 结果缓存在静态字段里。本轮的修法让首次构建就已完整，不再依赖"当时谁被加载过"；
   但若将来又有新的 `type:reference` 库且不在宿主根目录，仍会踩同一个坑。
6. **投射窗口是产品配置，改它要认准调用点**
   脚本参数区留了 `ShowView` 常量，但调用点若被写成字面量（如 `ShowImage(image, 2, marks)`），
   改 `ShowView` 就不生效——两者只有一处是对的。建议统一走 `ShowView`。
