## 一、需求与决策

### 1. 需求（路线图 S9 原文）

> **目标**：把"改模型"收敛成一个入口，然后撤销只是这个入口的副产品。
> - `IScadaChangeScope`：所有编辑器写操作走 `using (page.BeginEdit("移动图元")) { ... }`，作用域结束时产出一条变更记录。
> - 命令栈（撤销/重做）+ 与 `page.Version` 脏标记打通；直接 setter 在 S9 后**只允许运行时（数据泵）使用**，编辑器路径一律禁止——这条要用断言钉住，不能只靠约定。
> - 批量操作（多选拖动、对齐、删除）必须是**一次撤销**，不能十步回退。
>
> **验收**：拖 10 个图元 → Ctrl+Z 一次全部回去；撤销后重做，版本号与磁盘内容一致。

这条是三条地基纪律里 **D3（写模型只有一个入口）** 的落地：S9 之前 D3 只是"约定"（大家自觉调 `ScadaPage.Try*`），S9 之后它变成**机制**——写守卫会在违规时报错，断言会在 CI 里报错。

### 2. 决策清单

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| 1 | 记录模型 | **值级 diff（反向命令），不是对象快照** | 快照（`CloneHelper.DeepCopy`）在本项目会踩三个坑：① **换对象**——全仓多处用 `ReferenceEquals` 认身份（`ScadaDocument.FindPage`、`ScadaCanvas.Contains`、`ScadaRuntime` 当前页判定），撤销后对象换了一批这些判定全落空；② `Version` 标了 `[JsonIgnore]`，快照回填会把它抹掉；③ `[JsonConstructor]` 会重挂一遍集合订阅，与登记表对不上。值级 diff 只改字段、不换对象，三个坑一个都不踩 |
| 2 | diff 采集点 | **三处既有汇聚点**：`ScadaModelBase.SetProperty` override（覆盖 8 个模型全部标量 setter）+ `ScadaElement.SetProperty(key, value)`（属性袋，不走 setter）+ 六个集合回调（`ScadaCollectionRecorder`） | 这三处本来就是"所有写的必经之路"。在这三处收口，等于**新加一个属性自动被记账**，不必在几十个 setter 里各写一遍——那样每加一个属性都是一次漏记的机会 |
| 3 | 作用域形态 | `BeginEdit(label)` → `IDisposable`；**嵌套合并进最外层**；**零改动不产记录** | 合并是"批量操作 = 一次撤销"的实现基础（外层包一次，内层 `Try*` 自开的作用域不各占一个撤销位）；零改动不产记录对齐"同值不刷 Version"的既有口径——拖回原位、把属性改成原值，不该占一次撤销位 |
| 4 | 守卫怎么钉 | `ScadaWriteGuard.Strict` **默认关**，只有断言段显式打开；`ScadaPage.Try*` 家族各自内部开作用域 | 默认开会把运行态数据泵、反序列化、测试夹具全炸掉（它们本就该裸写）。"编辑器路径必须走入口"是**编辑器**的纪律，不是**领域层**的纪律 |
| 5 | 撤销栈归属 | **静态 `ScadaEditHistory`**（容量 50，切文档清栈） | 撤销是"编辑器级"能力而非"页面级"：用户按 Ctrl+Z 想的是"撤掉我刚才那一下"，而一次操作可能跨页（改页名）、跨对象（删页面连带删里面的图层）。挂在 `ScadaPage` 上就必须回答"这条记录算谁的"，答案会很难看。容量对齐 Flow 侧 `MaxUndoStack`（50） |
| 6 | 与 `Version` 的关系 | **`Version` 不回滚（单调递增）**；验收口径改为"撤销后序列化 JSON == 操作前 JSON" | 见下节，这是本轮**唯一一处改动产品语义**的决策 |

### 3. 关键决策 6 的推演：为什么 `Version` 不能进撤销栈

路线图原话是"撤销后重做，**版本号与磁盘内容一致**"。落地时发现这句话按字面做不到，也不该做到：

- `Version` 标了 `[JsonIgnore]`——**它根本不落盘**，所以"版本号与磁盘内容一致"本身就不是一个可判定的命题。
- 更重要的：`Version` 的消费者是**缩略图缓存失效**与**运行态绑定表重建**，判据都是"版本号是否变大"。一旦版本号可回滚，"撤销后版本号变小"会让这两处以为"没变过"从而不重建——**画面不重绘、绑定不重算**，是用户看得见的错。

所以口径改成：`Version` **只增不减**；验收改用**序列化 JSON 逐字节比对**（`Formatting.Indented` / `NullValueHandling.Ignore` / `TypeNameHandling.Auto`，只序列化 `ScadaPage` 本身以避开 `SolutionModel.solutionName` 那类时间戳字段）。

### 4. "构造 ≠ 编辑"的分界线：`ScadaChangeScope.Detached<T>`

`new ScadaLayer { Name = "图层_1" }` 的 `Name` 走 setter，一样会经过 `ScadaModelBase.SetProperty`。但此刻这个对象**还没进文档**——给它填初始值既不是"编辑"（不该进撤销栈，否则撤销一次"新建图层"要先冒出几条 `Name: "" → "图层_1"` 的垃圾记录），也不是"越权写"（不该被 `Strict` 拦下）。

`Detached<T>` 就是这条分界线：

```csharp
public static T Detached<T>(Func<T> factory)
{
    using (ScadaWriteGuard.Suspend())
    using (SuspendRecording())
    {
        return factory();
    }
}
```

**已改造的构造点（9 处）**：`ElementDescriptor.CreateElement`、`ScadaElement.AddBinding` / `AddEventHook`、`ScadaPage.AddEventHook` / `AddLayer` / `EnableLoadedEvent` 动作、`ScadaPropertyViewModel` 两处动作。

**另补两处非编辑路径的 `Suspend`**：`ScadaPage.EnsureIdentity`（旧数据补发身份，用户 Ctrl+Z 不该把补发的身份撤掉）、`ScadaElement.RefreshVariableReferences`（改名级联自愈）。

### 5. 口径沉淀

- **"谁改模型"只能有一个答案**：编辑器一律 `page.BeginEdit(...)`；`Try*` 家族自己开作用域，调用方不必再包一层；运行时数据泵与反序列化走 `ScadaWriteGuard.Suspend()`。
- **记录单位是"用户视角的一次操作"，不是"一次属性写"**：`Label` 直接就是撤销按钮的提示文案（`撤销：移动图元（Ctrl+Z）`）。
- **撤销必须逆序回写**：一次操作内部的写有先后依赖（比如"先改 `LayerId` 再改 `ZIndex`"），正序回滚会让中间态短暂自相矛盾，而中间态会被集合订阅看见并触发索引重建。
- **回写走反射调 setter，不直写字段**：属性 setter 里挂着完整链路（变更通知 + `ScadaPage.Version++` + `ElementId` 索引修正）。反射慢一点，但撤销是人工低频操作，这点开销换来的正确性划算。

### 3. 本轮抓到的两个真缺陷（同一个根因）

首轮运行 `[AD]` 段：**1 条断言失败 + 1 次进程崩溃**，两者根因相同——**`Version` 借道 `SetProperty`**。

**现象 A**：断言"撤销不回滚 `Version`"失败，`撤销前=2 / 撤销后=1`。`Version` 被当成普通标量记进了变更记录，撤销时被一起拽回去了。

**现象 B**：进程崩溃，`System.InvalidOperationException: 直接写模型被拒：ScadaPage.Version`。崩点在 `strictPage.Elements.Add(guardElement)`——集合增删本身没有守卫，但集合变更回调里的 `Version++` 走了 setter，于是守卫拦下的是**一个根本没被写的属性**，真正的违规点（作用域外的集合增删）反而藏在异常消息之外。

**修法**：`ScadaPage.Version` 的 setter 改为直写字段 + `RaisePropertyChanged(nameof(Version))`，**不再经过 `ScadaModelBase.SetProperty`**：

```csharp
[JsonIgnore]
public int Version
{
    get => _version;
    set
    {
        if (_version == value)
            return;

        _version = value;
        RaisePropertyChanged(nameof(Version));
    }
}
```

这是全仓**唯一一处**绕开基类收口的标量属性。它是"写操作的回声"，不是文档数据本身——不该被守卫约束（否则报错指错地方），也不该被记账（否则版本号可回滚，缩略图缓存/绑定表会据此判断"没变过"从而不重建）。语义与改动前完全一致（同样同值短路、同样发 `PropertyChanged`），只是不再经过那两个钩子。

修后重跑：**821 通过 / 0 失败**。

## 四、已知边界

1. **守卫只覆盖"标量属性 setter"这一条路径**。集合增删（`Elements.Add` 之类）在 `CollectionChanged` 回调里落账，事件到达时集合**已经改完**，此处再抛异常只会留下"改了但报了错"的半改状态，所以集合路径**刻意不加守卫**。这意味着 `Strict=true` 挡不住"作用域外的裸 `Elements.Add`"——它只挡裸 setter。
2. **`Clear()` 不可撤销**。`ScadaCollectionRecorder` 只记 `Add`/`Remove`，`Reset` 分支不记（事件到达时集合已空，拿不到"被清掉的是什么"、更拿不到顺序）。当前编辑器没有"清空画面"入口；将来若加，应写成"逐条 `Remove`"而不是 `Clear()`。
3. **撤销栈是静态单栈**，同一进程内所有 `ScadaPage` 共用一个栈。切文档清栈靠 `ScadaEditorViewModel.OnDocumentChanged` 这一处调用，**不在领域层**——绕过编辑器直接 `SwitchSolution` 不会清栈。
4. **撤销时 `Version` 仍会递增**（回写走 setter，链路里的 `Version++` 照跑）。这是设计：单调递增。所以"撤销后版本号回到操作前"这个断言**不该写**，验收一律用 JSON 比对。
5. **`ScadaRuntime` 刻意不继承 `ScadaModelBase`**：它是运行态（当前页、页栈），不是要落盘的文档数据。运行态改了不进撤销栈，也不受写守卫约束。
6. **`ScadaElement.Properties` 的 setter 刻意不挂守卫**（直接给字段赋值）：它是 JSON 反序列化通道。该属性的编辑走 `SetProperty(key, value)` 方法，守卫与记账都在那里。
7. **`ScadaPage.RefreshVariableReferences` 自身未包 `Suspend`**：依赖内层 `element` 的 `RefreshVariableReferences` 已 `Suspend`。本条断言未直接覆盖。
8. **真机未验证**（见"三、4"）。
9. **SCADA 新代码尚未纳入版本控制**：`Scada/`、`Scada.Controls/`、`ScadaChecks/` 仍是未跟踪状态。这是当前头号风险。
