## 一、需求与决策

### 1. 需求

路线图 §六 风险登记里挂着一条：

> **参数被改（如超时改成 0）不落审计** | 有"参数变更也要留凭证"的现场会提 | **仍未做**——S13-d 只做了"把三个数字交给现场配"，**没做"改配置要留凭证"**（两者常被当成一件事，其实是两件）

"改配置要留凭证"这句话在工业现场的分量：把空闲自动登出改成 `0` 等于**关掉自动登出**；把审计保留改成 `1` 天等于**自己给自己缩短追责窗口**；把"默认启动方案"改成另一份 `.vms` 等于**改掉无人值守机台上电后跑哪一套程序**——改错了要到第二天开机才发现。这三件事的共同点：**改完现场看不出来、事后才想起来要问**。审计存在的唯一理由就是那一刻答得出"是谁改的、从什么改成什么"。

### 2. 勘察结论：路线图措辞要修正

原处置写的是"**唯一**写盘出口是 `ScadaSystemParametersViewModel.OnConfirm`，接一条审计即可"。逐处读代码后确认**不准确**，实际有 **3 处**软件级配置写盘出口：

| # | 出口 | 改的东西 | 落在 `AppConfig.json` 的字段 |
|---|---|---|---|
| 1 | `ScadaSystemParametersViewModel.OnConfirm` | 空闲超时 / 审计保留 / 报警历史保留 | `IdleTimeoutMinutes` / `AuditRetentionDays` / `AlarmHistoryRetentionDays` |
| 2 | `ScadaRunWindowSettingsViewModel.OnConfirm` | 运行窗口显示形态 / 落哪块屏 | `RunWindowMode` / `RunWindowMonitor` |
| 3 | `SolutionListViewModel.OnConfirm` | 方案清单 / 默认启动方案 | `Solutions` / `StartupSolutionPath` |

三处都在**同一个文件**（`AppConfig.json`）上写盘，改错任何一处都影响"这台机器怎么跑"。因此本任务按"三处一起做"落地，并把发现写回路线图。

### 3. 决策清单 —— 落笔点与署名

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| A-1 | 审计写在哪一行 | **紧挨 `Save()` 之后**（写盘成功那一刻），不是命令入口 | 沿用 B-1 纪律"落笔点选最靠近数据/界面的写盘出口"。写在入口会记下"用户点了确定"，但用户点了确定**不等于**配置变了 |
| A-2 | 署名从哪来 | **构造注入 `Func<string?>? actorProvider`**，由宿主接"此刻登录着谁" | 沿用 B-2 纪律。ViewModel 住 `VisionMaster` 层，但它**不该认识会话**——认识会话就得认识 `ScadaAccessPolicy` 的登录态与超时，那是宿主的事。ViewModel 只问"现在是谁"，不问"怎么知道是谁" |
| A-3 | 取不到署名怎么办 | 回落 `"未登录"`（`ScadaAuditEntry` 构造内已有该回落） | **不留空白**。"有人没登录就改了参数"本身就是一条线索，比一格空白有用 |
| A-4 | 参数可空还是必填 | **可选参数**（`ScadaAuditWriter? audit = null, Func<string?>? actorProvider = null`） | 三个 ViewModel 现有全部调用点（含单机调试直接 `new`）无需改动即可编译；审计不是"能不能改配置"的前提 |
| A-5 | 没接审计时行为 | **照常写盘**，一个字都不变 | 审计写不成（磁盘满、权限不足）不该让"配置改没改成"这件事变样。这条单独写了断言 |
| A-6 | 失败也记吗 | **记**（`Failed`，`detail` = 弹窗上那句中文原因） | 沿用 B-4 纪律。"谁试过把审计保留期改短但没改成"与"谁改成了"同样值得留痕 |

### 4. 决策清单 —— "说明"列写什么

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| D-1 | 成功时"说明"写什么 | 这次操作的**净效果**：只列**真变了**的项，形如 `空闲自动登出：45 → 0 分钟` | "旧值 → 新值"是现场最想要的一句话：既能追责，也能**照原样改回去**。只列真变的项——把没动的也列出来，等于让读的人自己挑 |
| D-2 | 多处同时改怎么拼 | `string.Join("；", changes)`（中文分号） | 一条审计行 = 一次操作。用户点一次确定改了三项，就是一条留痕，不是三条 |
| D-3 | 一处没动也落吗 | **落**，说明写 `……均未变（…），未写盘` | 事后问"他到底改过没有"，答案是"**点过，但没改**"——这与"没点过"是两件事。零变更分支也**不写盘**（内存对象被 `OnDialogOpened` 归正过，但归正结果与磁盘一致时 `Save()` 是无谓 IO） |
| D-4 | 取消落吗 | **不落** | 改到一半放弃不该留痕，与"未写盘"同一口径 |
| D-5 | 设备名怎么展示 | 原样写设备名（`\\.\DISPLAY9`），不换成"显示器 2" | 它才是与 Windows「显示设置」对得上的那个值。换成序号要多绕一层，且**序号会随插拔变**，设备名不会 |
| D-6 | 形态怎么展示 | 中文档位（`依附主窗口` / `独立窗口`） | 枚举名 `AttachedToMainWindow` 是给代码看的，"依附主窗口"是给现场看的。这一列是给人读的 |
| D-7 | 空路径怎么展示 | `（未设置）` | 与弹窗里那格显示一致；留空白在 CSV 里会被读成"这一列没值"，分不清"没配"和"没记" |

### 5. 决策清单 —— 宿主注入（本节最易踩坑的一处）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| H-1 | 怎么把 audit / actorProvider 送进 VM | `Prism.Mvvm.ViewModelLocationProvider.Register<TView>(() => new TVm(...))` | **`ViewModelLocationProvider.Register` 优先于 `AutoWireViewModel` 的容器解析**：注册了工厂，视图被造出来时走工厂，不再走容器 `Resolve<TVm>`。本仓现成先例 3 处 |
| H-2 | 为什么不在 `RegisterTypes` 里注册 VM | `RegisterTypes(IContainerRegistry registry)` 拿到的 `registry` **不是容器**，拿不到 `ScadaAuditWriter` 实例 | 而工厂闭包**在视图构造时才执行**——那时容器早已就绪，闭包里可以直接用 `App` 自己的 `Container` 属性（`App` 是 `PrismApplicationBase` 派生类，`Container` 随时可用） |
| H-3 | 为什么不用 `IContainerRegistry.GetContainer()` | 本仓 Prism 包里**不存在**这个方法（`PrismIocExtensions` 也没有） | 反射扫描确证。硬套会编译不过 |
| H-4 | 为什么不给三个 VM 加 `[DependencyInjection]` 之类的自动装配 | 那会要求 `audit` 与 `actorProvider` 都**可被容器解析**，而 `Func<string?>` 容器解析不出来（要么加包装类型，要么给 `ScadaAuditWriter` 加个可解析的接口） | 为一个可选参数造一个包装类型，是把"注入"这件事的复杂度推给别人。工厂闭包 3 行就够 |
| H-5 | 运行窗口弹窗的失败提示 | 从 `Notifier.ShowError(reason)` 改成**弹窗内红字区**（`ErrorMessage` / `HasError`） | ①**与另两处口径一致**（系统参数、方案清单弹窗本来就有红字区）；②`Notifier` 走的是 `Application.Current` 那条路，**断言环境里会 NRE**——不可测的失败分支等于没写 |

### 6. 口径沉淀

- **"配置"与"凭证"是两件事**：S13-d 做的是"把三个数字交给现场配"（可用性），本任务做的是"改配置要留凭证"（可追责）。**能配 ≠ 有记录**，现场审计时问的永远是后者。
- **同一个文件的多处写盘出口要一起盘**：`AppConfig.json` 被三个弹窗写，只给其中一个接审计，审计表上就会出现"有些改动有记录、有些没有"的**假完整**——比完全没有审计更危险，因为它会让人以为"表上没有就是没发生"。
- **"点过但没改"值得留痕**：这是审计语义里最容易被漏掉的一格。留了它，事后才能把"没人动过"和"有人试过"分开。
- **可选参数必须显式工厂注册**（D-4 纪律的复用）：`audit` / `actorProvider` 都是可选参数，容器"编译能过、运行时不生效、不报错"——**必须有断言证明宿主真接上了**。本任务在断言里显式 `new TVm(settings, auditWriter, () => actor)` 走的是"参数通路"，宿主那一侧的接线由编译 + 人工复核保证（见 §四.2）。

## 四、已知边界

### 1. `AppSettingsService.ConfigPath` 写死，失败分支造不出来

`ConfigPath` 是 `private static readonly`，写死 `Path.Combine(AppDomain.CurrentDomain.BaseDirectory, "AppConfig.json")`，**无法注入临时目录**。因此三处断言的"写盘失败"分支（`Failed` + 红字）**无法用临时目录造**；已覆盖的是成功分支与零变更分支。三处断言一律"存原值 → try → finally 恢复 + `Save()`"，不给下一次运行留脏配置。

### 2. 宿主三处接线的"真的接上了"仍靠编译 + 人工复核

断言里是显式 `new TVm(settings, auditWriter, () => actor)`，走的是**参数通路**；`App.xaml.cs` 里那三行工厂注册的**实际生效**（视图被造出来时真走了工厂、真拿到了 `ScadaAuditWriter`）目前**没有断言覆盖**——`ScadaChecks` 是控制台宿主，不起 Prism 容器。这与路线图 §六 另一条欠债（"配置改完生效只有代码审查保证"）是同一类问题。**真机验证项**：改一次系统参数，去审计目录看有没有那一行。

### 3. `SolutionListViewModel` 失败分支仍走 `Notifier.ShowError`

三处弹窗里只有这一处**没有** `ErrorMessage` / `HasError` 红字区，失败提示仍走 `Notifier.ShowError(reason)`（走 `Application.Current` 那条路）。**与另两处口径不一致**，且断言环境里该分支会 NRE（本次未覆盖该分支，故未触发）。

**为什么本轮不改**（留待决策，不是遗漏）：

1. **红字条不能照抄**。另两处弹窗是**浅色卡片**（内容区 `#F8F9FA`），红字条用 `#FEF0F0` 底 / `#FDE2E2` 边 / `#F56C6C` 字（Element 风格）恰好。而 `SolutionListView.xaml` 是**深色**弹窗（`#1E1E22` 底、`#6B6BEF` 按钮）——照抄会在这块深色面板上拍出一块**刺眼的亮粉**。要用深色版本（如 `#3A2224` 底 / `#5A3033` 边 / `#FF7875` 字），而这需要**肉眼看过才算数**。
2. **本机没有视觉验证手段**：屏幕采样纯黑（`CopyFromScreen` 400×400 网格 `distinctColors=1`），截不了图（见路线图 §七 #1）。配色改动**无断言可证**，属于"改了也不知道好不好看"的一类。
3. **一致性收益是部分的**：该 ViewModel 的 `Notifier` 还承担"方案文件不存在""加载成功"等**非弹窗内**提示（那些提示出现在主界面，走 `Notifier` 是对的）。只换失败这一处，VM 里仍会留着 `Notifier`。

**建议的收口方式**（下一轮认领时）：给 `SolutionListView` 定一套深色错误条配色，`OnConfirm` 失败分支换成 `ErrorMessage` / `HasError`，并在开发记录的 UI 自审里**留一行"待肉眼复核"**。

### 4. `SameList` 不比 `Index`，是刻意

`AppSolutionEntry.Index` 带 `[JsonIgnore]`，是显示序号。用户拖动重排一次，落盘内容其实没变——若把 `Index` 算进"改了清单"，每次重排都会留一条审计，审计表会被无意义的行淹掉。代价：**重排顺序本身不留痕**（顺序影响的是界面展示次序，不影响"上电跑哪一份"，风险可接受）。

### 5. 审计写不成时"配置改没改成"这件事不变样，是刻意

`ScadaAuditWriter.Append` 绝不抛（内部 catch 一切 IO 异常 → `ReportFault` → `return false`），而三处 `OnConfirm` 都**不看它的返回值**。即：磁盘满 / 审计目录无权限时，配置照样改得成、弹窗照样关、用户无感——只是审计目录里少一行，且 `ReportFault` 会在日志里留一条诊断。**这是刻意的**：审计是旁路，不该成为主流程的失败点。
