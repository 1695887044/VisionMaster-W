# 参数弹窗"先大后小"闪动（2026-10-25）

## 一、当前状态

已修并真机验证：双击算子打开参数弹窗时，不再出现"先弹一个大窗、再啪地缩成小窗"。

## 二、已做

### 2.1 先取证：到底变了几次

在 `AutoPortConfigView.OnLoaded` 里挂了 `window.SizeChanged` 逐次打日志（临时，验完已删）。
真机实测（打开「通讯与1」的参数面板）：

```
13:47:46.164  [弹窗] Loaded 起始 size=960x680 (W=960 H=680 STC=Manual)
13:47:46.168  [弹窗] SizeChanged 960x680 → 560x680   ← ① 改宽
13:47:46.169  [弹窗] SizeChanged 560x680 → 560x560   ← ② SizeToContent 生效，被旧 MinHeight=560 钳住
13:47:46.186  [弹窗] Loaded 设定后 size=560x560
13:47:46.188  [弹窗] SizeChanged 560x560 → 560x486   ← ③ MinHeight 放宽到 180，高度再掉一次
```

**是三次，不是两次**，全部落在 24ms 内的不同帧上。

### 2.2 根因

旧代码的顺序是"先开 `SizeToContent`、后改 `MinHeight`"：

```csharp
window.Width = 560;                          // ① 960 → 560
window.SizeToContent = SizeToContent.Height; // ② 高度被**旧的** MinHeight=560 挡住
window.MinHeight = 180;                      // ③ 下限放宽 → 高度再掉到内容高
```

`SizeToContent` 每次赋值都会自己触发一轮布局，所以必然多出一帧。

### 2.3 修法（一次算好，不用 SizeToContent）

```csharp
window.MinWidth = 560;  window.MinHeight = 180;  window.MaxHeight = 760;   // 先把上下限放好
window.SizeToContent = SizeToContent.Manual;
window.Width = 560;
window.UpdateLayout();                       // 在 560 宽下量一次内容
double chrome = window.ActualHeight - root.ActualHeight;   // 非客户区
window.Height = Math.Clamp(root.DesiredSize.Height + chrome, 180, 760);
```

修完实测：

```
13:52:56.904  [弹窗] Loaded 起始 size=960x680
13:52:56.907  [弹窗] SizeChanged 960x680 → 560x680   ← ① 改宽
13:52:56.911  [弹窗] SizeChanged 560x680 → 560x390   ← ② 设高
```

**三次 → 两次**，剩下的两次都在 `Opacity=0` 期间完成（见 2.4），肉眼不可见。
真机确认最终尺寸 560×486 / 560×390 都正确、内容贴合、底部无空白。

### 2.4 兜底：显形推迟到尺寸落定之后

窗口 Style 加 `Opacity = 0`，外壳（`PluginConfigShellView`）的 `Loaded` 里恢复 1。
WPF 的 `Loaded` **由内向外**触发（子元素先），所以 `AutoPortConfigView` 改尺寸一定先跑完。
即使以后又冒出第三次变化，也看不见。

## 三、真正的原因（2026-10-25 第二次取证）

前两版都没解决，是因为判断错了方向。加了 `Opacity` 诊断后拿到：

```
Loaded: opacity=0.00 visible=True size=960x680 STC=Manual **allowsTransparency=False**
SizeChanged 960x680 → 560x680 opacity=0.00
SizeChanged 560x680 → 560x486 opacity=0.00
```

`Opacity=0` 确实生效了，但 **`AllowsTransparency=False`**——这时 WPF 只把"内容"变透明，
**窗口那块由系统绘制的矩形照样不透明**。用户看到的不是内容在闪，是那块白色窗口底在变大小。

**修法**：窗口 Style 加

```xml
<Setter Property="AllowsTransparency" Value="True" />
<Setter Property="Background" Value="Transparent" />
```

改完实测 `allowsTransparency=True`，三次尺寸变化全在 `opacity=0.00` 下完成，肉眼不可见。
顺带：开了真透明之后，内容里的圆角与投影才真正生效（之前被窗口矩形切掉）。

## 四、未做

- **用户实测"exe 还是有闪动"**（DLL 已是最新）。因此把显形时机从 `Loaded` 改投递到
  `DispatcherPriority.ContextIdle`：`Loaded` 的触发顺序依赖可视树构建过程，外壳若先于
  `AutoPortConfigView` 触发，就会先显形成 960×680、再被缩一次。
  `ContextIdle` 排在本次布局与渲染队列之后，子视图的尺寸调整必定已完成。
  **这一版没能在真机确认**（GUI 绑定漂移），需要用户再试。
- 同一模式的其它弹窗（如 `SolutionListView` 在 `Loaded` 里设 960×640）没改——不是双击触发的。

## 四、下一步

如果还有别的弹窗闪，按同一套路：窗口 Style 先 `Opacity=0`，在**最外层**的 `Loaded` 里恢复。

## 五、踩过的坑

- **`Loaded` 的触发顺序是自下而上**：子视图先、外壳后。利用这一点才能"先改尺寸、后显形"。
  反过来（外壳先 Loaded）就得用 `ContentRendered` 或 `DispatcherPriority.Loaded` 再延后一拍。
- **`WindowStartupLocation` 不能写进 Style**（不是依赖属性，会抛 `ArgumentNullException`），
  居中走 `WindowCenteringBehavior`——这条是既有约定，本轮没动。
