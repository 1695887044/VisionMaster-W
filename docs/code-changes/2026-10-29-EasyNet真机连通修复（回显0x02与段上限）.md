### 2.1 定位（不是"连不上"，是"连上之后每段都失败"）

运行日志（`VisionMaster\bin\Debug\net9.0-windows\Logs\2026-10-29.log`，09:00–09:01）显示：

段读失败 U402BC0（60 单元）: 读响应命令与请求不一致（请求 0x01，响应 0x02）

设备是 **`h5u_daemon.exe`（汇川 AutoShop 自带 H5U 模拟器，`D:\INOVANCE\AutoShop\Simulator\`）**，
不是之前那台 12939 模拟器。用 `tools\oneoff\easynet_probe.ps1` 与新增的
`tools\oneoff\easynet_limit_probe.ps1` 直接发原始帧问设备，得到三条硬事实：

| 探测 | 设备实际行为 |
|---|---|
| 读成功应答的 `[8]` | **0x02**（请求是 0x01），地址/位数原样回显，数据从 `[22]` 起 |
| 字区单帧上限 | 501 字（8016 位）成功；512 字（8192 位）→ 错误码 **129** |
| 位区单帧上限 | 8000 位成功；8001 位 → 错误码 64；8192 位 → 129 |
| 写应答 | `09 00 01 03 01 00 00 00 06`（与我们的 `ValidateWriteAck` 完全一致） |
| U 区裸地址 `0x2100070` | 接受，不报错，返回数据 |

### 2.2 三个缺陷

1. **读回显校验要求 `response[8] == request[8]`**（`EasyNetCodec.ValidateReadEcho`）。
   真机对读请求回 0x02，于是**每一次成功读都被判失败**。
   HSL 原版客户端 `ParseDeviceReadResult` 只判 `content.Length > 22` 就切掉 22 字节取数据，
   **根本不校验这一字节**——这就是"HSL 能连、我们不能"的直接原因。
2. **字区段上限 2000 字**（`PollAddress.MaxSegmentUnits`）。真机 512 字就拒，2000 字的段必然全灭。
   旧数字"4000 字 / 16000 位"来自另一台宽松模拟器，在官方 H5U 模拟器上不成立。
3. **全段失败 ⇒ 判链路故障**（`PollBatchPlanner.Poll`）。第 1、2 条让每段都失败，第 3 条把它
   升级成"链路断开"，于是 TCP 明明连着、界面却一直重连——**放大器**，也是最误导人的一层。

### 2.3 改动

| 文件 | 改动 |
|---|---|
| `Communication\Communications\Protocol\EasyNetCodec.cs` | `ValidateReadEcho` 命令字节由"必须等于请求"改为"只接受 0x01/0x02"（0x0F 错误帧仍由 `IsErrorResponse` 先拦）；补实测依据注释 |
| `Core\CommunicationContracts\PollAddress.cs` | `PollProtocol.EasyNet` 字区 `MaxSegmentUnits` **2000 → 500**（= 8000 位，与位区同口径封顶） |
| `Communication\Communications\Manager\PollBatchPlanner.cs` | 全失败时再分一层：连接实现 `ILinkHealthProbe` 且 `HasLinkFault == false` → 判**地址级失败**返回 `Completed`；只有链路自证断开（传输层 I/O 失败）或不支持自证的连接才判 `LinkFault` |
| `CommChecks\Program.cs` | ① 断言由"0x02 必须被拒"改为"0x02 必须被接受"，并新增"0x06 写回执必须被拒"；② 段上限断言改 8000/500；③ 新增 `DeviceRejectConnection` 桩 + 正反两条："全段被设备拒绝但链路正常 → Completed" / "全段失败且链路自证断开 → 仍判 LinkFault" |
| `tools\oneoff\easynet_limit_probe.ps1` | 新增一次性探针：量字区/位区单帧上限与写应答格式（只读，写测试只回写原值） |

### 3.1 U 区映射实测（2026-10-29 补充）

现场给了点位 `Alarm3[91] Bool UB 210119B`。用 `tools\oneoff\easynet_u_routing_probe.ps1` 做三步：

1. 读 `UB 210119B`（裸地址 `0x0210119B` → 线路字节 `9B 11 10 02`）→ **False**
2. 写 1 → 应答 `09 00 01 03 01 00 00 00 06`（写成功）
3. 读回 → **True**

同时读**同一低 20 位、类型码为 M 区**的 `M2811`（线路字节 `9B 11 10 00`）→ **False（未受影响）**。

**结论（已闭环，2026-10-29 现场确认）**：
- U 地址写入后能读回 → **读写自洽**
- 与 M 区**不别名** → 落在独立内存，不是"误路由到 M 区"
- 我们的 U 编码（原始 32 位小端、不做类型码合并）在这台 H5U 上**工作正常**
- **PLC 侧确认**：写入后 AutoShop 监视表里 `Alarm3[91]` 变为 1 —— 说明这一位就是 PLC 程序用的那位，
  不是"独立但没人用"的空单元。**U 区映射验证完成**。

**顺带纠正一条旧推测**：前置记录里写"只有位地址 20~23 位全 1 才路由进 U 区"，
实测 `0x0210119B` 的 20~23 位是 `0x2`（不是 0xF）却依然进了真正的 U 区——**H5U 的路由规则比那更宽**，
参考服务器的行为不能直接当成真机结论。

## 五、踩过的坑

- **"能连"和"能读"是两件事**：状态列显示"重连中"不代表 TCP 连不上。判据是日志里有没有
  `Reconnecting -> Connected`——有就是链路通、问题在报文/地址层。
- **HSL 的宽容度是隐式兼容性**：`InovanceEasyNet` 不校验回显、不把单点错误升级成链路故障。
  我们加了严格校验却按"必须相等"实现，等于把 HSL 的兼容面收窄成"只认参考服务器"。
  加严格校验时必须先问"真机回的是什么"，不能拿参考实现当唯一真相。
- **参考服务器不是真机**：前置记录里的"模拟器接受 4000 字 / 16000 位"在官方 H5U 模拟器上不成立
  （512 字即拒）。凡"上限"类数字必须标注是在哪台设备上量的。
- **探针地址要先确认存在**：第一次量字区上限用了 `D20000`，全部回错误码 **64**（地址非法），
  差点被读成"长度限制"。换到日志里真实存在的 `D800` 才量到 501/512 的真实边界。
- **`[8]` 不是回显**：写应答 0x06、错误 0x0F、读成功 0x02——这一字节在真机上是"响应类型"，
  不是请求命令的回显。
- **PowerShell 直接打印日志里的中文会乱码**（控制台 936 vs 文件 UTF-8）：读日志一律
  `[IO.File]::ReadAllLines($p, UTF8)` 后写 UTF-8 文件再用编辑器看，别信终端回显。
