## 1. 要解决的问题

### 1.1 现状

今天每条连接只有**一个**轮询周期（`CommunicationConfig.ReadCycleMs`），该连接下**所有**变量共用它：

```
连接 PLC-A（ReadCycleMs = 1000）
   ├── 1000 个急停/联锁点   → 1s 刷新   ← 太慢，联锁要 100ms 级
   └── 19000 个统计/累计点  → 1s 刷新   ← 太浪费，统计量 10s 足够
```

两类需求被强行绑在同一个节拍上，结果两头不讨好：
- 想让联锁快 → 把 `ReadCycleMs` 调到 100ms → 19000 个统计点也被迫 100ms 刷一遍，请求数 ×10，PLC 直接被打爆；
- 想让统计省 → 把 `ReadCycleMs` 调到 10s → 联锁点 10s 才看一眼，安全上不可接受。

### 1.2 目标

一条连接内支持**多个扫描组（Scan Class）**，每组独立周期，组内照常批量合并：

```
连接 PLC-A
   ├── [联锁组]  100ms  →  50 个点，3 次段读/轮
   ├── [工艺组]  1s     →  4000 个点，200 次段读/轮
   └── [统计组]  10s    →  14950 个点，700 次段读/轮
```

**对标商业 SCADA**：
| 产品 | 概念 | 说明 |
|---|---|---|
| KEPServerEX | **Scan Class**（扫描类） | 每 Tag 挂一个 Scan Class，Class 上定义扫描速率 |
| Ignition | **Tag Group** | 每 Tag 挂一个 Tag Group，Group 上定义 Rate |
| WinCC | **Acquisition Cycle**（采集周期） | 每 Tag 选一个采集周期 |

三者本质是同一件事：**周期是"组"的属性，不是"点"的属性**。

### 1.3 必须记住的一条铁律（本方案的由来）

> **变量级周期与批量化天然互斥。**

历史教训：`CommunicationVariable` 上曾有一个 `PollIntervalMs` 字段，最终被**彻底删除**（见 `2026-09-17-删除变量级PollIntervalMs静默失效字段.md`）。原因是——批量规划器 `PollBatchPlanner` 把"地址相近的变量"合并成一次块读，一旦每个变量各带一个周期，就必须按周期把地址段切碎，**批量合并直接崩掉**，退化成"每变量一次请求"的旧世界。

**所以本方案绝不恢复变量级周期。** 正确做法是"分组"：周期挂在组上，**组内变量仍然整批合并**，批量化完好无损。

## 2. 一个必须澄清的技术前提：两个维度是正交的

设计前最大的技术风险是"分组会不会把批量合并搞坏"。结论：**不会，因为"扫描组"与"存储区段分组"是两个正交维度。**

`PollAddress.GroupKey` 是**协议存储区**的分组键（见 [PollAddress.cs](file:///e:/VM/VisionMaster-W-master/Core/CommunicationContracts/PollAddress.cs)、[PollAddressResolver.cs](file:///e:/VM/VisionMaster-W-master/Communication/Communications/Address/PollAddressResolver.cs)）：

| 协议 | GroupKey 取值 |
|---|---|
| S7 | `DB7` / `M` / `I` / `Q` |
| Modbus | `FC3`（保持寄存器）/ `FC1`（线圈）/ `FC4` / `FC2` |

`PollBatchPlanner.MergeSegments()` 的分组表达式是 `GroupBy(x => (x.Address.Protocol, x.Address.GroupKey))`。

扫描组切分发生在**更早一步**：先把"本连接全部变量"按 `ScanGroup` 名切成 N 个集合，**每个集合各自调用一次 `PollBatchPlanner.Build()`**。于是：

```
变量全集
  │  ① 按 ScanGroup 切分（本方案新增）
  ├──► 联锁组变量集 ──► PollBatchPlanner.Build() ──► 内部照旧按 GroupKey 合并段
  ├──► 工艺组变量集 ──► PollBatchPlanner.Build() ──► 内部照旧按 GroupKey 合并段
  └──► 统计组变量集 ──► PollBatchPlanner.Build() ──► 内部照旧按 GroupKey 合并段
```

两个维度互不干扰。**这是整个方案能落地的前提。**

```
│  变量全集 ──按 ScanGroup 名归组──► [默认组][联锁组][工艺组][统计组]                        │
│                                        │                                                │
│                          每组各调一次 PollBatchPlanner.Build()                          │
│                                        ▼                                                │
│                          产出 List<PollGroup>（已按周期升序排序）                         │
└───────────────────────────────────────────┬─────────────────────────────────────────────┘
                                            │ worker.PollScheduler = newScheduler
┌──────────────────────────── 执行层（ConnectionWorker + PollScheduler）──────────────────┐
│                                                                                         │
│   Worker 单线程 Loop（既有）                                                             │
│     ├── 状态机 / 命令队列（既有，不动）                                                   │
│     ├── 拍前消费脏标记 → RebuildPollPlan（既有 H1，不动）                                 │
│     └── if (Connected && scheduler.HasWork && scheduler.ShouldRun())                    │
│              scheduler.Run(connection)   ← 替换原 PollAction(_connection)                │
│                                                                                         │
│   PollScheduler.Run()：一拍内按【周期升序 = 优先级顺序】串行跑完所有到期组                  │
│     ① 联锁组(100ms) 到期？ → 跑 → 记成功时刻                                             │
│     ② 工艺组(1s)    到期？ → 跑 → 记成功时刻                                             │
│     ③ 统计组(10s)   到期？ → 跑 → 记成功时刻                                             │
│     任一组返回 false（通信级故障）→ 立即中止本拍剩余组，交给 Worker 断线重连               │
│                                                                                         │
│   全部 I/O 仍在这**一条线程、一个 socket** 上串行 —— 物理上限没变，变的是分配方式           │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

**一句话总结价值**：单个 socket 的请求吞吐是固定物理上限，扫描组不凭空变出带宽；它的价值是——**把宝贵的请求配额优先分给联锁点（100ms 级延迟），把统计点降频腾出配额（总请求数降一个数量级）**。

### 5.1 `RebuildPollPlan` 改造（[L689](file:///e:/VM/VisionMaster-W-master/Communication/Communications/Manager/AdvancedCommunicationManager.cs#L689-L708)）

```csharp
private void RebuildPollPlan(string connectionName)
{
    if (!_workers.TryGetValue(connectionName, out var worker))
        return;

    if (!_registeredVariables.TryGetValue(connectionName, out var variables) || variables.IsEmpty)
    {
        worker.PollScheduler = null;              // ← 原 worker.PollAction = null
        worker.ClearPollPlanDirty();
        LogDebug($"连接 {connectionName} 无已注册变量，已停止轮询");
        return;
    }

    // 组表从配置缓存取；取不到（极端时序）→ 传 null，全部走默认组（安全兜底）
    _configCache.TryGetValue(connectionName, out var config);

    var scheduler = PollScheduler.Create(variables.Values, config, LogWarning);
    worker.PollScheduler = scheduler;             // ← 替换 PollAction
    worker.ClearPollPlanDirty();

    // H2 精神：一次重建只出一条汇总日志（几万点下重建频繁，禁止逐组/逐变量刷屏）
    LogInfo(scheduler == null
        ? $"连接 {connectionName} 无可轮询项，已停止轮询"
        : $"轮询计划已更新: {connectionName} 变量 {variables.Count} 个 → {scheduler.GroupCount} 组，" +
          $"{scheduler.Describe()}，合计 {scheduler.TotalSegments} 段 + {scheduler.TotalFallbacks} 单读");
}
```

### 5.3 组表变更如何生效

组表存在 `CommunicationConfig` 上，用户在扫描组编辑器里改完 → 走既有 `UpdateConnection(config)` 链路：

```
UpdateConnection
  → RemoveConnection（清 worker / configCache）
  → AddConnection（写入新 config 到 _configCache，ConfigureWorker 重灌参数）
  → RestoreVariables（逐变量 RegisterVariable → RequestPollPlanRebuild → MarkPollPlanDirty）
  → Worker 下一拍前消费脏标记 → RebuildPollPlan 读到**新组表** → 新周期生效
```

**结论：不需要新增生效通路。** 唯一需要确认的点是——若该连接当前**一个变量都没注册**，`RestoreVariables` 不会调 `RegisterVariable`，脏标记不会被置位；但此时也没有轮询在跑，无影响。

### 5.4 H1 标脏机制在多组下的扩展

**完全不需要改。** 脏标记仍是"整连接一个布尔"，重建仍是"全量重切 + 全量重编译各组"。理由：

- 重建成本 = O(N)（N = 变量总数），H1 已把**触发次数**从 O(N) 压到 O(1)；
- 组切分本身只是几次 `GroupBy`，相对 `PollBatchPlanner.Build()` 的合并计算可忽略；
- 若做"只重建受影响的那一组"，需要维护"变量 → 组"的增量索引，复杂度上升但收益接近 0（重建不在热路径，且已标脏合并）。

> 这是刻意的取舍：**用"整连接全量重建"换掉"增量维护组索引"的复杂度**。几万点下每次重建一次 O(N)，H1 已保证不会高频发生。

## 6. 执行层详细设计：新增 `PollScheduler`

新文件：`Communication/Communications/Manager/PollScheduler.cs`（含三个内部类型，避免文件碎片化）

### 6.1 类型结构

```csharp
namespace VisionMaster.Communications
{
    /// <summary>一个扫描组的运行态：目标周期 + 该组的批量读计划 + 上次成功时刻 + 诊断计数</summary>
    internal sealed class PollGroup
    {
        public string Name { get; }
        public int IntervalMs { get; }
        public PollBatchPlanner Planner { get; }
        public int VariableCount { get; }

        private long _lastSuccessTicks;   // Volatile 访问：Worker 写、UI 诊断线程读
        private long _lastStartTicks;
        private int  _avgActualMs;        // 实测周期的指数滑动平均（EMA），诊断用

        public PollGroup(string name, int intervalMs, PollBatchPlanner planner, int variableCount) { ... }

        /// <summary>建连成功后立即允许首轮（对齐旧 TryConnect 里 `Now() - PollIntervalMs` 的语义）</summary>
        public void MarkDueNow() => Volatile.Write(ref _lastSuccessTicks, 0L);

        public bool IsDue() => Environment.TickCount64 >= Volatile.Read(ref _lastSuccessTicks) + IntervalMs;

        public void BeginRun()  { long now = Environment.TickCount64; Volatile.Write(ref _lastStartTicks, now); }

        public void MarkSuccess()
        {
            long now = Environment.TickCount64;
            long last = Volatile.Read(ref _lastStartTicks);
            if (last > 0)
            {
                long actual = now - last;
                // EMA：α=0.25，抗单次抖动，又能在 10 拍左右反映真实趋势
                int prev = Volatile.Read(ref _avgActualMs);
                Volatile.Write(ref _avgActualMs, prev == 0 ? (int)actual : (int)(prev * 0.75 + actual * 0.25));
            }
            Volatile.Write(ref _lastSuccessTicks, now);
        }

        public ScanGroupStats Snapshot() => new(Name, IntervalMs, VariableCount,
            Planner.SegmentCount, Planner.FallbackCount, Volatile.Read(ref _avgActualMs));
    }

    /// <summary>只读诊断快照（跨线程传给 UI，值语义，不共享引用）</summary>
    public readonly record struct ScanGroupStats(
        string GroupName, int TargetIntervalMs, int VariableCount,
        int SegmentCount, int FallbackCount, int AvgActualMs)
    {
        /// <summary>达成率 = 目标周期 / 实测周期，封顶 100%（实测比目标还快时按 100% 计）</summary>
        public double AchieveRate => AvgActualMs <= 0 ? 0
            : Math.Min(1.0, (double)TargetIntervalMs / AvgActualMs);
    }

    /// <summary>多组轮询调度器：持有 N 个扫描组，按"周期升序 = 优先级顺序"驱动</summary>
    public sealed class PollScheduler
    {
        private readonly List<PollGroup> _groups;   // 构造时已按 IntervalMs 升序排好

        public bool HasWork => _groups.Count > 0;
        public int GroupCount => _groups.Count;
        public int TotalSegments  => _groups.Sum(g => g.Planner.SegmentCount);
        public int TotalFallbacks => _groups.Sum(g => g.Planner.FallbackCount);

        public static PollScheduler? Create(
            IEnumerable<CommunicationVariable> variables,
            CommunicationConfig? config,
            Action<string>? log);

        public bool ShouldRun();
        public bool Run(ICommunicationConnection connection);
        public void ResetAllDue();
        public IReadOnlyList<ScanGroupStats> GetStats();
        public string Describe();
    }
}
```

### 6.2 `Create()`：切分 + 编译 + 排序

```csharp
public static PollScheduler? Create(IEnumerable<CommunicationVariable> variables,
                                    CommunicationConfig? config, Action<string>? log)
{
    var all = variables as IList<CommunicationVariable> ?? variables?.ToList()
              ?? new List<CommunicationVariable>();
    if (all.Count == 0) return null;

    // ① 解析组表：默认组（ReadCycleMs，永远存在）+ 自定义组（去重、过滤非法、封顶 8 个）
    var defs = ScanGroupTable.Resolve(config);

    // ② 按组名归组；未知组名 / 空 / 保留名 → 回落默认组（并汇总一条日志，不逐变量刷屏）
    var buckets = ScanGroupTable.Bucket(all, defs, log);

    // ③ 每组各编译一次批量计划；空组 / 无可轮询项 → 不建运行态（避免空转）
    var groups = new List<PollGroup>();
    foreach (var def in defs)
    {
        if (!buckets.TryGetValue(def.Name, out var vars) || vars.Count == 0) continue;

        var planner = PollBatchPlanner.Build(vars, log);
        if (planner.PollItemCount == 0) continue;   // 组内全是被跳过的变量

        groups.Add(new PollGroup(def.Name, def.IntervalMs, planner, vars.Count));
    }

    if (groups.Count == 0) return null;

    // ④ 周期升序 = 优先级顺序（短周期先跑），在构造期定序，热路径零排序
    groups.Sort((a, b) => a.IntervalMs.CompareTo(b.IntervalMs));
    return new PollScheduler(groups);
}
```

**`ScanGroupTable`**（同文件内的 `internal static` 小类）：

```csharp
internal static class ScanGroupTable
{
    public const string DefaultGroupName = "默认组";
    private const int MinIntervalMs = 50;
    private const int MaxIntervalMs = 3_600_000;

    /// <summary>组表解析：默认组恒在首位；自定义组按 (非空名 + 未重复 + 非保留名 + 周期合法) 过滤</summary>
    public static List<(string Name, int IntervalMs)> Resolve(CommunicationConfig? config)
    {
        var list = new List<(string, int)>
        {
            (DefaultGroupName, config?.ReadCycleMs is > 0 ? config.ReadCycleMs : 1000)
        };

        foreach (var g in config?.ScanGroups ?? Enumerable.Empty<ScanGroupConfig>())
        {
            if (string.IsNullOrWhiteSpace(g?.Name)) continue;
            var name = g.Name.Trim();
            if (name == DefaultGroupName) continue;                 // 保留名
            if (list.Any(x => x.Item1 == name)) continue;           // 重名（取首个）
            if (g.IntervalMs is < MinIntervalMs or > MaxIntervalMs) continue;
            list.Add((name, g.IntervalMs));
            if (list.Count > CommunicationConfig.MaxScanGroups + 1) break;  // +1 = 默认组
        }
        return list;
    }

    /// <summary>把变量按 ScanGroup 名归桶；无法归属的一律进默认组</summary>
    public static Dictionary<string, List<CommunicationVariable>> Bucket(
        IList<CommunicationVariable> variables, List<(string Name, int IntervalMs)> defs, Action<string>? log)
    {
        var valid = new HashSet<string>(defs.Select(d => d.Name));
        var buckets = defs.ToDictionary(d => d.Name, _ => new List<CommunicationVariable>());
        int fallbackCount = 0;

        foreach (var v in variables)
        {
            var key = v.ScanGroup?.Trim();
            if (string.IsNullOrEmpty(key) || !valid.Contains(key))
            {
                if (!string.IsNullOrEmpty(key)) fallbackCount++;   // 指向了不存在的组
                buckets[DefaultGroupName].Add(v);
                continue;
            }
            buckets[key].Add(v);
        }

        // H2 精神：汇总一条，不逐变量刷屏
        if (fallbackCount > 0)
            log?.Invoke($"有 {fallbackCount} 个变量的扫描组名不存在（可能组已被删除），已回落到默认组");

        return buckets;
    }
}
```

### 6.3 `Run()`：一拍内跑完所有到期组

```csharp
/// <summary>是否至少有一个组到期（Worker 用它决定要不要进本轮调度）</summary>
public bool ShouldRun()
{
    for (int i = 0; i < _groups.Count; i++)
        if (_groups[i].IsDue()) return true;
    return false;
}

/// <summary>
/// 执行本拍到期的所有扫描组，**严格按周期升序（= 优先级）串行执行**。
/// 返回 false = 通信级故障（交给 Worker 断线重连）。
/// </summary>
public bool Run(ICommunicationConnection connection)
{
    for (int i = 0; i < _groups.Count; i++)
    {
        var g = _groups[i];
        if (!g.IsDue()) continue;

        g.BeginRun();
        bool ok = g.Planner.Poll(connection);   // 契约不变：false = 本轮所有读都失败 = 通信级故障

        if (!ok)
        {
            // 链路已死：本拍剩余组不再空跑（省掉无谓的等待与日志噪音），
            // 不 MarkSuccess → 该组保持"到期"，重连成功后立即补读
            return false;
        }

        g.MarkSuccess();
    }
    return true;   // 含"本拍到期的组全部成功"；Worker 只在 ShouldRun()==true 时才调本方法，故不会假报活跃
}
```

**调度语义三条要点（答辩级）**：

1. **优先级 = 周期升序**。短周期组天然是"更急"的，同一拍内先跑它。因为 `_groups` 在构造期就排好序，热路径上只是顺序遍历，**零比较零排序**。
2. **拍内跑完所有到期组，不做预算截断**。理由：截断会引入"长周期组被短周期组饿死"的风险，而工业采集里"统计点永远不更新"比"统计点晚几十毫秒"严重得多。代价（短周期组的实际周期被拖长）**用诊断面板如实暴露**（见 §8），而不是偷偷丢掉工作。
3. **失败即中止本拍**。任一组 `Poll` 返回 `false` 意味着"该组所有读都失败"——`PollBatchPlanner` 的判定规则是 `failed < attempted`，只有全失败才是通信级故障。链路已死时继续跑剩余组只会浪费时间与刷日志。

**线程安全**：`PollGroup` 的 `long`/`int` 字段全部 `Volatile` 读写；快照是值拷贝，UI 拿到后与 Worker 再无共享。**重建时** `worker.PollScheduler` 被整体替换——UI 最多读到"上一个实例的快照"一个刷新周期（1s），不崩不错。

## 9. 量化收益（几万点场景）

设某连接 1.9 万点，段读平均覆盖 20 点。每秒请求数 = `Σ(组内段数 / 组周期秒)`。

| 方案 | 联锁点延迟 | 每秒请求数 | 说明 |
|---|---|---|---|
| 现状：全部 1s | 1000 ms | ≈ 950/s | 单 socket 与 PLC 双双过载 |
| 现状：全部 100ms | 100 ms | ≈ 9500/s | 完全不可行 |
| **扫描组**：联锁 50 点/100ms、工艺 4000 点/1s、统计 14950 点/10s | **100 ms** | ≈ **300/s** | 吞吐降 68%，联锁延迟降 90% |

**必须如实说明的代价**：分组会让组内点变稀疏，合并率略降（经验值 5~15%），即总段数比单组略多。上表已按此计入。收益主要来自**周期拉长**，不是来自"更聪明的合并"。
