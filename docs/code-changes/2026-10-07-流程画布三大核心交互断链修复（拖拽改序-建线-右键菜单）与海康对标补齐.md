## 一、起因

用户要求对 `VisionMaster\Views\FlowCanvasView.xaml`（712 行，Nodify 7.3.0）做多方交叉审查并向海康 VisionMaster 画布看齐。三方审查交叉质证后确认：**画布三大核心交互——拖动改序、拖线建线、连线右键编辑绑定——在真机上全部不可用**。此前 2026-09-16 的 207 条画布断言全绿是因为 headless 直调伪造参数（`Tuple<object,object>` / 伪造 List），绕过了 Nodify 真实事件链——本波修复的核心教训是"**断言必须用库实际会传的参数驱动**"。

## 二、三大 P0 的根因（Nodify 7.3.0 IL 取证）

### P0-1 拖拽改序 / 跨分支移动从不提交

- `NodifyEditor::OnItemsDragStarted/Completed` 的 IL 是 `Execute(get_DataContext)`——**实参 = 编辑器自身的 DataContext（即 FlowCanvasViewModel）**，不是被拖容器列表。
- 旧实现 `ExtractDraggedNodes`（`FlowCanvasViewModel.cs:1448`）首行 `if (parameter is not IEnumerable) return` → 永远空 → 快照 null → `ReorderCommand` / `MoveBranchCommand` 的提交代码永不可达。
- 真机表现：节点拖过去位置变了，执行顺序、分支归属纹丝不动。

### P0-2 建线闭环真机断链（两层叠加，第二层在首轮修复后仍被 reviewer 复核抓出）

1. **先清后读**：旧 `OnCompleteConnection` 第一行置 `PendingConnection.IsVisible = false` → 属性通知回调同步把 Source/Target 置 null → 再读必是 null → 提前 return；`Tuple<object,object>` 恢复分支是死代码（那是编辑器级 `ConnectionCompletedCommand` 的实参形态，本项目没用它）。
2. **Nodify 内部时序**（首轮修复后 reviewer 反汇编补刀）：`PendingConnection::OnPendingConnectionCompleted` 里 **`set_IsVisible(false)` 发生在 `Execute(get_Target)` 之前**，且 `IsVisibleProperty` 元数据默认 **TwoWay** → 控件置 false 会回流 VM，把 `PendingConnection.Source/Target` 清空——所以"把读取挪到置 false 之前"的修复在真机时序下依然读到 null。**源端必须取自拖线开始时的快照字段**。

### P0-3 连线右键菜单整体失灵

- `FlowCanvasView.xaml` 连线上属性元素内联 `<nodify:LineConnection.ContextMenu>` 是依赖属性**本地值**，同时压掉 Style setter（`DataLinkMenu`，沦为死资源）与 IsOrderLink 触发器的 `{x:Null}`。
- 内联菜单 `ItemsSource={Binding Bindings}` 无 ItemTemplate，`CanvasLinkBinding` 未重写 `ToString()` → 数据线右键弹出一行行 `VisionMaster.ViewModels.CanvasLinkBinding` **类型全名**（AGENTS.md R20 同款病的菜单版），点击无任何命令；顺序链（Bindings 空）弹空菜单，与代码注释"顺序链不挂菜单"矛盾。
- 同行还绑定了**不存在的属性** `ContextMenuVisibility`（必然失败的死绑定）+ `Converter={x:Null}` 调试残留。

## 三、修法

### 3.1 拖拽（P0-1）——`FlowCanvasViewModel.cs`

- `OnItemsDragStarted`：参数提取保留（兼容测试直喂），空则**回退选中集** `_nodeMap.Values.Where(n => n.IsSelected && n.IsDraggable)`。核心假设"Nodify 拖动手势开始前被拖容器已选中"经 reviewer 反汇编 `ItemContainer::BeginDragging` IL 证实（`if(!IsSelected) Select(Replace)` 先于 `Editor.BeginDragging`）。
- `OnItemsDragCompleted`：命令写回包进 `_internalWriteback++/finally--`，配合 `OnFlowStepsChanged` 判定"这是画布自己刚压栈的命令写的集合"，不清撤销栈。
- **多选取舍（刻意，注释声明）**：语义提交只认 `snapshot[0]`，其余被拖节点只挪坐标——整批换 owner 的插入顺序有歧义，留待后续。

### 3.2 建线（P0-2）——`FlowCanvasViewModel.cs`

- 新增 `_pendingSourceConnector` 快照字段：`OnStartConnection` 存入；`OnCompleteConnection` 取 `source = _pendingSourceConnector ?? PendingConnection.Source`，**在 null-guard 之前清字段**（正常完成与落空取消两条路都清）；`OnPendingConnectionChanged` 只清 PendingConnection.Source/Target 并复位端口反馈，**绝不碰快照字段**（那里在 Execute 前就会跑）。
- 删除 Tuple 死分支；方向归一、`CanLinkSteps` 拓扑校验、拒绝文案、`ModuleLinkRequested` 事件链恢复可达。

### 3.3 右键菜单（P0-3）——`FlowCanvasView.xaml` + `CanvasLinkViewModel/CanvasNodeViewModel`

- 菜单**内联在 `ModuleLinkTemplate` 里**（DataTemplate 内每连线一份实例，DataContext 即连线 VM，无共享实例串线）；菜单项命令走**注入的闭包命令**（弹层够不到主 VM 资源树）：`CanvasLinkViewModel.OpenBindingCommand / UnbindCommand / UnbindAllCommand`，主 VM 在 `BuildLinks` 注入。
- 顺序链拦截：`LineConnection.ContextMenuOpening`（code-behind `OnConnectionContextMenuOpening`，IsOrderLink 时 `e.Handled=true`）——ContextMenu 类没有 Opening 事件（首版误写，MC3072 编译报错纠正）。
- 逐条解绑子菜单改用 `MenuItem.ItemsSource + ItemContainerStyle` 标准写法（替换原来嵌 ItemsControl 的键盘导航死角）；`CanvasLinkBinding` 补 `ToString()` 兜底。
- **守门**：UIThemeSmokeTest 静态扫描钉住"连线**样式侧**不得再出现 ContextMenu 的 Setter/触发器"（本地值永远压掉样式值，样式侧再挂就是事故回潮；注意守门目标不是属性元素语法本身——修复方案就是内联属性元素）。

### 3.4 撤销栈与外部结构变化同步（新防线）

- `OnFlowStepsChanged`：`_internalWriteback>0 || _suppressUndoRedo` 豁免；外部变化只在 **Remove/Replace/Reset**（塌陷下标）时 `ClearUndoStacks()`，Add/Move 不清——保留"先写回、后压栈"的既有模式，代价是外部 Add/Move 后撤销可能回滚到略偏顺序（不崩溃不丢步骤，注释声明）。
- 删除命令 `DeleteSelectionCommand`（Delete 键 + 节点右键菜单共用）：`DeleteSelectedNodesCore` 在 `_rebuilding=true` 包裹内批量 `RemoveAt`（容器连子树一起走，`IndexOf` 按引用现查防同批挤动），结束后清撤销栈；回执按实际移除数计数。
- 整批解绑：`UnbindAllBindings` 把一根聚合线承载的全部解绑打包成 **MultiUndoCommand**（`CanvasUndoCommands.cs` 新增，Undo 逆序 / Redo 正序），Ctrl+Z 一次整批回滚。

## 五、踩坑记录（给后来者）

1. **Nodify 7.x 命令实参形态**：`ItemsDragStarted/Completed` = 编辑器 DataContext；`PendingConnection.Completed` = 单个目标连接器（编辑器级 `ConnectionCompleted` = ValueTuple，且 `is Tuple<,>` 匹配不上 ValueTuple）。升级 Nodify 版本先反汇编这三个方法。
2. **`PendingConnection.IsVisible` 默认 TwoWay**：控件置 false 的回流先于 CompletedCommand.Execute——任何"从 PendingConnection 状态读拖线上下文"的写法都会被这个时序击穿，上下文要在手势开始时快照。
3. **ContextMenu 本地值 vs 样式**：连线菜单只能"模板内联每实例一份"或"逐实例赋值"，绝不能样式侧挂（本地值压掉）也不能资源共享（DataContext 串线）。
4. **断言必须用库实际传参驱动**：`RequestLink` 喂 Tuple 的 207 条绿掩盖了三条 P0；这次 Harness 一度少复刻 IsVisible 回流，又被 reviewer 抓出来。headless 断言的仿真层每次都要对照 IL 核。
5. **ContextMenu 没有 Opening 事件**（只有 Opened/Closing）；拦截要挂外层元素的 `ContextMenuOpening`。
6. **`PendingConnection` 不继承 Shape**（无 Fill 属性）；`BaseConnection` 也**没有** IsSelected/IsSelectable（连线选中机制未取证前别盲绑——本轮连线删除改走右键菜单通道）。
7. Nodify 默认主题是暗色演示风格（ItemContainer 蓝框 / 小地图 #121212 / 连接点 DodgerBlue / 橡皮筋蓝虚线），浅色调画布必须逐项覆盖，且 `BasedOn {x:Type}` 对主题字典里的默认样式在编译期查不到（MC4005/MC3072），只能显式全量自绘。

## 六、续做：连线形态视觉整改 + 渲染探针出图（同日晚，用户真机反馈）

用户真机截图反馈：「太丑了」「这种连线意义不明」。渲染取证（`FlowCanvasChecks --render` 渲染探针，见下）确认两个视觉根因：

1. **连线控件选型**：`LineConnection` 是纯直线——节点错位布局时斜线斜穿整张画布；Nodify 默认 offset 模式还在两端锚点外各画一段"横杆"。先后试过 `CircuitConnection`（中段是 45° 斜线，两端接近同列时斜线拉得很长，`Angle` 属性管不了它），最终定型 **`StepConnection`（台阶式纯直角走线）**：`SourcePosition/TargetPosition` 四边枚举定义进出方向（数据线 Right→Left、顺序链 Bottom→Top），配 `SourceOffsetMode/TargetOffsetMode=None` 让端点贴锚点。走线在 Nodify 内部自带圆角直角，观感与海康一致。
2. **连接点过重**：14×14 且统一亮蓝。收敛为 12×12 + 分态——未连线=淡灰空心（`FlowCanvasNodeSubTextBrush`），已有连线=亮蓝实心（IsConnected 触发器换 `BorderBrush`），拖线中不可达端口压灰 0.3 不变。

**渲染探针**（`FlowCanvasChecks\RenderProbe.cs`，`dotnet run -- --render [输出目录]`）：STA 线程真实实例化 `FlowCanvasView`（Prism 的 `AutoWireViewModel` 在构造期触发，经 `ViewModelLocationProvider.SetDefaultViewModelFactory` 返回预建 VM；App 级资源以 Colors.xaml 文本直载 + Segoe MDL2 兜底 Icon 字体），渲染两个典型图式（纵向两步+双线、If 容器双分支）出 PNG。**视觉整改必须有图**：逻辑断言绿 ≠ 观感过关，本轮 `LineConnection→CircuitConnection→StepConnection` 三轮换型每轮出图对比才定型。

**排障教训**：改 XAML 后只重建 VisionMaster、`dotnet run --no-build` 跑的是断言工程 bin 里的**旧 dll**——两轮渲染图一模一样一度像"控件没用"，先查产物新鲜度再怀疑代码。

**守门升级**：UIThemeSmokeTest 的连线断言正则从写死 `LineConnection` 改为 `nodify:\w+Connection` 反向引用（换控件类型守门不失效）。

**回归**：逻辑断言 1525/4（既有）不变；烟测 FlowCanvas 守门 4 条 PASS。运行中的 VisionMaster.exe 为重建而关闭，需重启查看。

## 七、续做：算子注释上画布（同日，用户要求）

用户指出"每个算子都可以加注释"但画布节点没显示。实现：

- `CanvasNodeViewModel` 新增 `Comment`（读 `StepModel.Description`）/ `CommentVisibility` / `CardTooltip`（名称/插件名/注释拼合悬停）；`OnModelPropertyChanged` 补 `Description` 监听（配置界面写注释，画布即时跟随，不等重建）。
- 节点模板（Step/Container）改两行结构：Row0 = 卡片/框体（锚点几何基准不变），Row1 = **注释行**（卡片下缘外的灰色小字，海康式；`TextTrimming` 截断、悬停看全文）。泳道不参与。
- **语义坑**：`StepModel` 构造把 `Description` 默认置为**插件名**（StepModel.cs:347）——"用户真写了注释"的判据是**非空且 ≠ 插件名**，否则每个节点下方都会平白多出一行与副标题重复的字。断言钉死这个判据（[T] T3b：默认态不显示、写入自定义注释即时显示、悬停含注释）。
- 探针场景 C 补注释数据出图验证；回归 1528/4（画布 0 失败）、烟测 exit=0。

## 八、续做：多算子布局问题与端口/连线显隐（2026-10-07~08，用户真机反馈第二轮）

用户反馈「多算子后不对」（容器框巨大空白、泳道停在框外、端口飘在远离头带处）与「只有绑定的数据才显露端口/连线」的想法。逐项：

1. **拖动后容器框/泳道不贴合**（主诉）：拖动只更新坐标、容器几何要等下次结构变化才重算——拖走内容后框还撑在旧位置。修法：`OnItemsDragCompleted` 收尾统一 `RebuildInPlace()`（提交路径本已触发，幂等）。断言 [T] T8 钉住（拖 40px 框高 234→274；拖出泳道会触发跨分支移动提交——那是另一条已验证路径）。
2. **容器连接点锚头带**：`EdgeMidpoint` 对容器的左右脚改锚 `Location.Y + 头带高度/2`（折叠态用折叠框中心）；模板连接点顶部对齐 + `SideConnectorMarginLeft/Right`（与锚点同一点、左右分别骑边）——框体再高端口都贴着"质量分档/深度检测"徽标那一行。
3. **端口显隐**（用户想法）：`FlowConnectorStyle` 三态——已连线=亮蓝实心常显；未连线=默认隐藏、**悬停节点浮现**淡灰空心（拖线入口不丢）；拖线手势中全部现形（`IsDragInProgress` 由主 VM 统一置位，不可达端口 0.25 压灰）。渲染探针验证：A 图每个节点只剩 1 个实心蓝点。
4. **顺序链开关**：工具条新增「顺序链」勾选（`ShowOrderLinks`，默认开）——关掉后只画真实绑定的数据线，正是"只有绑定的数据才露线"的字面实现。断言 T6。
5. **连线进出边动态选向**：数据线按**节点中心差**选（明显错开到左侧 > 半模块宽 → 左出右入绕就近侧；垂直对齐/略偏 → 右出左入）。判据踩坑实录：第一版用锚点差——Right/Left 锚点天然差一个模块宽，竖排同列被误判成"消费方在左侧"，线从左缘出被节点盖住（OnTop=False）**整条数据线消失**；断言 T7 用真实拖动路径钉住两个方向的语义。
6. **层次**：`DisplayConnectionsOnTop=False`——线从节点后面绕行（穿越段被节点遮住），海康式层次；泳道 tint 的轻微罩色可接受。
7. 顺带取证：`LineConnection.Spacing` 默认 0、`SourceOffsetMode` 默认 `Static(14,0)`——绕行量不由 Spacing 控制，StepConnection 的路径是"缓冲段 + 中点分割"。

回归：逻辑断言 **1535 / 4（既有环境失败）**；烟测 exit=0（FlowCanvas 守门 4 条 PASS）；渲染探针 A/B/C 图复核。

## 八·补2 超深自动折叠与布局排序口径（2026-10-08）

**布局排序口径（回答"按执行顺序排吗"）**：`AutoLayout` 的排序键是 `SortId`，但**全项目没有任何地方写 SortId**（`FlowTopology.cs:13-14` 注释早有警告）——`OrderBy` 稳定排序退化为**集合插入顺序 = 执行顺序**（FlowTopology 与编译器的同一真相源）。节点上的执行序号角标也直接来自 FlowTopology 的集合下标；拖拽改序（按几何 Y 算新下标 → Move 集合）改变的就是真实执行顺序。若将来有人开始维护 SortId，布局序会与执行序脱钩——届时必须同步改这里。

**超深自动折叠**（`FlowLayoutStore.AutoLayout`）：
- 新增 `AutoCollapseDepth = 3`：本次**新布局**的容器深度超过 3 层时默认带折叠标记。
- 只作用于"缺布局的步骤"（HasMissing 才进 AutoLayout）——已有全量布局的老流程不动；用户手动展开过的容器（折叠标记已翻掉、坐标已在库）不会折回去。

## 十、并行分组容器·第一期（2026-10-08）

**定位（立项评审）**：第一期做"布局与约束语义"——执行语义 = 顺序逐分支跑完汇合（与 For 同骨架），零运行时风险；真并行（Task.WhenAll）是第二期专项，前置条件是 LocalVariables 并发化、调试门/高亮指针多线程化、失败聚合语义、插件 IsThreadSafe 标记。

改动：
- **模型**：新增 `ParallelStep : StepModel, IContainerStep`（Core\Models\ProcessStep\ParallelStep.cs）——默认双 Default 分支（无条件语义）、`RecommendedMaxBranches=8`、Children 带 Replace 两件套（存盘往返不翻倍）。

- **拓扑**：零改动——IContainerStep 口径自动覆盖（深度/Branch/Classify 全对）；跨并行分支连线落 CrossBranch 兜底非法。画布 `Explain` 给并行专门文案（"时序不确定；共享数据请在并行分组之前定义"）。
