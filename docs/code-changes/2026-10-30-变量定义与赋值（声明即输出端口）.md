# 「变量赋值」→「变量定义与赋值」（声明即输出端口，v4）

日期：2026-10-30
类型：功能新增 + 插件改名（R12 级：动契约程序集 `Core.Interfaces`，纯加性）

---

## 1. 为什么做（不是改名好看）

`VariableAssignmentPlugin` 在 v3 是**只有输入、没有输出**的纯副作用节点：

```
IDynamicOutputProvider → 0 命中
AddDynamicOutput       → 0 命中
OutputPort<            → 0 命中
```

它只写三处：`LocalVariables[名]=值`（:1220/:1226）、`SharedVariables.TryWrite`（:1192）。

而 **方案 B（同日）把「变量」取值档下线了** → 下游"按名读"的通道没了：

| 下游消费方式 | 方案 B 之前 | 方案 B 之后 |
|---|---|---|
| 数据记录 / 结果上报的「变量」档 | ✅ 按名读 `LocalVariables` | ❌ **已删** |
| 绑定弹窗「运行时变量」组 | ⚠️ 只列 `VariableDefinitionPlugin`（**该类在本仓库不存在**） | ❌ 实际一直为空 |
| C# 脚本 `GetVar` | ✅ | ✅ 只有它能读 |

**结论：这个节点写出去的值，除了 C# 脚本没人拿得到。** 端口绑定是唯一跨插件取值通道，
所以必须给它补输出端口 —— 这就是 v4。

## 2. 落地口径（三条已定）

| 项 | 决定 |
|---|---|
| 哪些行生成端口 | **所有 `Scope=Runtime` 且变量名非空的行**；全局行不生成（它写的是既有变量，再开一个入口会配错） |
| 端口命名 | `Var_{变量名}`（加前缀避免和用户的输入端口重名） |
| 类型 | 新增 `AssignmentRow.Type`（`VariableValueType`）；枚举**下沉 `Core.Interfaces`**，与 `Plugin.CSharpScript.ScriptVarType` 分开（后者含 HALCON 图形类型） |

## 3. 改了什么

### 3.1 新增契约文件 `Shard\Core.Interfaces\VariableValueType.cs`

```
public enum VariableValueType { Object, Int, Double, Bool, String }   // 带 [Display(Name="中文")]
public static class VariableValueTypes
{
    Type ToClrType(this VariableValueType)          // 枚举 → CLR Type
    VariableValueType FromClrType(Type?)            // CLR Type → 枚举（不认识 → Object）
    bool TryCoerce(object?, VariableValueType, out object?, out string?)   // 运行期转换，失败给中文原因
}
```

为什么下沉：`Plugin.Util` 与 `Plugin.CSharpScript` 各有一套变量声明表，两边都要"类型 → CLR Type"映射。
放插件里就是两份要手工同步的表（以后加类型漏一处 = 静默不兼容）。

`TryCoerce` 的口径与仓库既有"宽进严出"一致：能转就转（文本按 InvariantCulture），
**数值文本拒绝千分位逗号**，转不动报清被拒原值。

### 3.2 `Plugins\Plugin.Utility\Models\AssignmentRow.cs`

新增 `public VariableValueType Type`（默认 `Object`）。
旧 `.vms` 没有这个字段 → 反序列化成 `Object` → 多出一个 `OutputPort<object>` 端口，
是**新增能力**不是行为回归（没人连它就没有任何影响）。

## 5. 未做 / 已知边界

| # | 项 | 原因 |
|---|---|---|
| 1 | **下游是指向"输出端口"的引用，改名后下游那条键会悬空** | 端口是**下游步骤**的输入名，出现在下游的 `LinkedSources` 里，不归本插件管。A2-v4-5 明确断言了这一边界。要根治需要"跨步骤连线级联"（改上游输出名 → 扫全流程下游并迁移），属于编译器/画布层能力，不在本批 |
| 2 | 类型下拉在**窄档（<640px）**没有单独列，放在第 2 行 | 布局取舍 |
| 3 | 没有做"类型从值来源自动推断" | 需要静态类型推导，跨插件；当前靠用户选（默认 `Object` = 不校验） |
| 4 | 没有真机视觉验收 | 只做字符串级与集合级断言；类型列的实际排版需要人眼确认 |
| 5 | 旧的 `DropOrphanLinks` 仍用反射取键列表 | 可以改用 `IStepLinkInventory`，属"死代码/小重构"批次 |
