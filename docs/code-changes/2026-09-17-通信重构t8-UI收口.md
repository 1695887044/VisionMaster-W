## 一、需求与决策

t6 把"裸连接 I/O"收口到了连接专属线程（ConnectionWorker），t7 修好了启动链路（配置先加载、
AutoStart 生效、非阻塞建连）。但**通讯设置对话框**仍停留在旧模型上，逐条排查出 4 个新缺陷（B1~B4），
另有 1 个"看起来能改、改了出事"的隐患（B5）。下表为缺陷与用户拍板的处置决策：

| 编号 | 缺陷描述 | 影响 | 治疗 |
| --- | --- | --- | --- |
| B1 | `ExecuteTestConnection` 先 `Disconnect()` → `Connect()` → 再 `Disconnect()`，直接拿 `GetConnection()` 裸连接操作；连接不存在时还会临时 `AddConnection` 再 `RemoveConnection` | ① 正在使用的连接被强行打断，且 Worker 状态机仍认为"已连接"，两边打架；② 测试动作绕过连接专属线程，重新引入 t6 已消除的并发操作同一 socket 风险 | 改走 `AdvancedCommunicationManager.TestConnection(name)`（用户拍板：**只探测，不改变连接状态**） |
| B2 | `NetworkVariableModel.TryWriteToValue` 与 `WriteToDevice` 都拿裸连接 `connection.Write(...)`，绕过 Manager/Worker；后者还 `catch { }` 一吞了之 | t6 消除的"两个线程同时操作一个 socket"竞态仍在变量写入路径上；写失败无任何痕迹，出现"赋值了却没进设备"永远查不出来 | 两条写路径都改走 `CommunicationManager.WriteVariable(...)`（用户拍板：**两条都收口，保留隐式写**） |
| B3 | `ExecuteEdit` 用 `EasyDialog.ShowPropertyGridSync(..., config)` **直接编辑活对象** | PropertyGrid 是即时写属性值的：点了"取消"对象也已经被改脏；叠加 `ShellViewModel` 关闭时**无条件** `SaveConfigAsync()`，脏数据会静默落盘到 `communications.json` | 改为**副本编辑**，确定后才 `CopyFrom` 回写（用户拍板：**副本编辑，确定才回写**） |
| B4 | `ExecuteToggleConnection` 走同步 `Connect`/`Disconnect`（内部 `.GetAwaiter().GetResult()`），最坏在 UI 线程上硬等一个 `Config.TimeoutMs`（默认 3000ms） | 设备离线时点一下"连接"界面就卡 3 秒；`Connect` 返回 false 时还会误报"建立失败"，而 Worker 其实仍在后台按退避重连 | 新增 `RequestConnect`/`RequestDisconnect` 非阻塞入口，UI 订阅状态事件回报结果（用户拍板：**非阻塞发起 + 状态事件回报**） |
| B5 | 编辑弹窗里能改 `ConnectionName`，而 `Manager.UpdateConnection` 是**按名称定位**旧连接的 | 改名 = "新增一条 + 旧连接无人更新"，旧连接被孤立、已注册变量静默失联 | **禁止改名**：提示用户并放弃本次修改（用户拍板：**禁止改名，提示用户**） |

用户明确**不修改**的历史项：B5 之外，"欧姆龙/三菱/OPC UA 选项抛 NotSupported"按上轮决定保持不动。

### 1. CommunicationConfig：新增 CopyFrom（"副本编辑、确定才回写"的落地手段）

```csharp
/// <summary>
/// 把 <paramref name="other"/> 的**可编辑字段**复制到本实例（"副本编辑、确定才回写" 的落地手段）。
/// 只覆盖用户在属性面板能改的项，State/CreatedTime/LastConnectedTime
/// 等运行时状态一律保留本实例的值——它们反映真实连接实况，不能被编辑弹窗清掉。
/// </summary>
public void CopyFrom(CommunicationConfig other)
{
    if (other == null)
        throw new ArgumentNullException(nameof(other));

    // 顺序不可颠倒：Protocol 的 setter 内部会 OnChanged() 重建一份默认 Config，
    // 先赋 Protocol 再赋 Config，最终落到 Config 上的才是副本里的那份配置
    Protocol = other.Protocol;
    Config = other.Config?.Clone(); // 再深拷一份：避免活对象与副本共享同一条链路配置子对象
    ConnectionName = other.ConnectionName;
    ReadCycleMs = other.ReadCycleMs;
    IsEnabled = other.IsEnabled;
    AutoReconnect = other.AutoReconnect;
    AutoStart = other.AutoStart;
    Description = other.Description;
    UpdateModifiedTime();
}
```

两个必须记住的点：

- **赋值顺序**：`Protocol` setter 内部会 `OnChanged(value)` 重建一份默认 `Config`。所以必须"先 Protocol、后 Config"，反了就会被默认配置覆盖回去。
- **只拷可编辑项**：`State`、`CreatedTime`、`LastConnectedTime` 是运行时真相，绝不能从编辑副本带回来。
- 现成的 `Clone()` 不能直接当"回写源"用：它把名字改成 `名称 + "_Copy"`，用于"复制一份新连接"场景，恰好不能用于原地编辑。

### 2. AdvancedCommunicationManager：非阻塞入口

```csharp
public void RequestConnect(string connectionName)
{
    if (string.IsNullOrWhiteSpace(connectionName)) return;
    if (!_configCache.TryGetValue(connectionName, out var config)) return;
    if (!_workers.TryGetValue(connectionName, out var worker)) return;

    // 灌参数 + 编译轮询计划都是本地计算，必须先做：Worker 一被唤醒就能用正确参数与计划工作
    ConfigureWorker(worker, config);
    RebuildPollPlan(connectionName);

    // timeoutMs = 0：登记意图立即返回（与 ConnectAll 同语义）
    _ = worker.Connect(0);
}

public void RequestDisconnect(string connectionName)
{
    if (string.IsNullOrWhiteSpace(connectionName)) return;
    if (!_workers.TryGetValue(connectionName, out var worker)) return;

    worker.Disconnect().ContinueWith(t =>
    {
        if (t.IsFaulted)
            LogWarning($"断开连接异常: {connectionName} - {t.Exception?.GetBaseException().Message}");
    }, TaskScheduler.Default);
}
```

`ConnectAll` 的循环体随之简化为复用 `RequestConnect(config.ConnectionName)`，消除重复代码。

**为什么 `timeoutMs = 0` 就等于"非阻塞"**：`Worker.Connect(timeoutMs)` 会把
`_autoConnect = true`、`_reconnectAttempt = 0`、`_nextConnectTick = 0` 登记好，
然后 `WaitStateAsync(Connected, 0)` 的 deadline 立刻到期 → 立即返回 false。
真正的 socket 建连由 Worker 循环下一圈执行，结果经 `StateChanged` 广播。
所以**返回 false 不代表失败**，只代表"我登记完就走了"。

### 3. NetworkVariableModel：变量写入不再绕过 Worker

```csharp
// TryWriteToValue 内（显式写命令）
// 经 Manager → 连接专属线程下发：与轮询、其他写命令在同一条线程上串行执行，
// 不再出现"两个线程同时操作一个 socket"（旧实现直接拿裸连接写，绕过了 Worker）
CommunicationManager.WriteVariable(ConnectionName, AddressConfig.Address, rawValue);

// WriteToDevice 内（Value setter 的隐式写）
catch (Exception ex)
{
    // setter 不是用户的显式命令，不弹窗打扰；但也不能像旧实现那样 catch {} 一吞了之——
    // 写失败必须留痕，否则"赋值了却没进设备"永远查不出来
    System.Diagnostics.Debug.WriteLine($"[NetworkVariable] 变量 {Name} 隐式写失败：{ex.Message}");
}
```

注意保留差异：**显式写**（`TryWriteToValue`）返回 `(bool, error)` 给调用方；
**隐式写**（`Value` setter）不弹窗、不抛异常，只记 Debug 日志——避免绑定的 setter 里抛异常把 UI 绑死。

### 4. CommunicationSettingsViewModel：状态事件回报 + 三个按钮改写

打开/关闭成对订阅（Manager 是单例，不退订会每次打开泄漏一份订阅）：

```csharp
public void OnDialogOpened(IDialogParameters parameters)
{
    // 非阻塞的连接/断开由状态事件回报结果，所以打开时订阅、关闭时退订
    _communicationManager.ConnectionStateChanged += OnConnectionStateChanged;
    LoadConfigs(_communicationManager.GetAllConnections());
}

public void OnDialogClosed()
    => _communicationManager.ConnectionStateChanged -= OnConnectionStateChanged;
```

事件由**连接专属线程**触发，而 `Notifier` 和 `ICollectionView` 只能碰 UI 线程，因此先封送：

```csharp
private void OnConnectionStateChanged(object? sender, ConnectionStateChangedEventArgs e)
    => VisionMaster.Helpers.SafeDispatch.BeginInvoke(() => HandleStateChanged(e));
```

`HandleStateChanged` 的核心是"只回报自己发起的那一次"，靠 `_pendingConnect`/`_pendingDisconnect` 标记：

- `Connected` → `ShowSuccess("已建立（轮询已启动）")`，清空标记
- `Reconnecting` → `ShowError("未建立，后台按退避重试中")`（**不报"失败"**：Worker 还会继续重连）
- `Connecting` 等中间态 → 直接 return，避免刷屏
- `Disconnected` 且命中 `_pendingDisconnect` → `ShowInfo("已断开")`
- 末尾 `_configsView.Refresh()`，让"在线/离线"筛选跟着变

三个按钮的改写要点：

| 方法 | 旧 | 新 |
| --- | --- | --- |
| `ExecuteTestConnection` | 裸连接 Disconnect→Connect→Disconnect，含临时 Add/Remove | 一句 `_communicationManager.TestConnection(name)` |
| `ExecuteEdit` | PropertyGrid 直接编辑活对象 | `Clone()` 出副本 → 弹窗编辑副本 → 取消直接 return（活对象从未被动过）→ 改名则 `ShowWarning` 并放弃 → 否则 `CopyFrom` + `UpdateConnection` |
| `ExecuteToggleConnection` | 同步 `Connect`/`Disconnect`，当场报成功/失败 | 先设 `_pendingXxx` 再 `RequestXxx`，提示"正在连接/断开 …"，结果交给事件回报 |

`ExecuteEdit` 里"禁止改名"的判据来源值得记一笔：

```csharp
var copy = config.Clone();          // Clone 会加 "_Copy" 后缀
copy.ConnectionName = config.ConnectionName; // 改回原名，只为弹窗显示正常
...
if (!string.Equals(copy.ConnectionName, config.ConnectionName, StringComparison.Ordinal))
{
    Notifier.ShowWarning($"不允许修改连接名称，[{config.ConnectionName}] 的本次修改已放弃。如需改名请删除后重新添加。");
    return;
}
```

副本名先归位成原名，用户**一旦在弹窗里改名**，副本名就会与原名不同 → 正好当判据，
既保证弹窗显示的是正常名称，又能检出改名动作。

`ExecuteToggleConnection` 的 `catch` 里必须把两个 pending 标记清空：
登记阶段就失败（连接不存在、命令队列已满）时若留着标记，
**后面一条无关的状态事件会被误当成"本次操作的结果"来提示**。

## 四、已知边界

1. **`ExecuteTestConnection` 仍是阻塞调用**：`TestConnection` 内部走
   `worker.Invoke(...).GetAwaiter().GetResult()`，设备不可达时 UI 会等一个 socket 超时。
   本次只按"只探测、不改变连接状态"收口语义，未做异步化——点测试时短暂卡顿属预期。
2. **测试用的是 Manager 里的配置，不是列表对象**：`TestConnection(name)` 只按名称取 Worker，
   所以必须先在编辑弹窗点"确定"（走 `UpdateConnection`）再测试，改了一半就测仍是旧参数。
3. **`UpdateConnection` 会重建 Worker**：`CopyFrom` + `UpdateConnection` 后连接会被重建，
   已连接状态随之丢失，需要重新点"连接"。参数变更在下次建连后生效。
4. **`RequestConnect` 无返回值**：调用方拿不到"这一次到底连上没有"，只能等状态事件。
   需要同步结果的场景请用 `Connect`（阻塞 ≤ `TimeoutMs`）。
5. **状态回报可能被后续动作覆盖**：`_pendingConnect` 是单槽位，
   同一对话框里连续点两次"连接"只有最后一次会收到提示。
6. **B5 协议选项不一致仍未修**：用户上轮明确决定保留现状。
7. **未做运行期实测**：本轮只验证到编译通过 + 静态语义对齐，UI 实际观感与事件回报时序需运行确认。
