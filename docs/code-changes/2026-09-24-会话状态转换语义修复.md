## 一、需求与决策

### #6：`OldState` 恒等于 `NewState`——没有设计选择，是纯粹的赋值点错位

病根在赋值与取值的顺序上：

```csharp
// 8 处调用点全都这么写：
session.State = SessionState.Stopped;            // ← 先赋新值
NotifyStateChanged(session, SessionState.Stopped);

// 而方法内部又读一次：
var oldState = session.State;                    // ← 读到的是刚写进去的新值
session.State = newState;
```

于是事件里的 `OldState` 永远等于 `NewState`，字段彻底失效。**唯一消费者是 `CommStress` 压测程序**（[Program.cs:881](file:///e:/VM/VisionMaster-W-master/CommStress/Program.cs#L881) 用 `e.OldState → e.NewState` 统计状态转换）——也就是说那个工具一直在统计空气。

修法：把赋值收进 `NotifyStateChanged` 内部，使它成为**全引擎唯一的 `session.State` 赋值点**，8 处调用点的直接赋值全部删除。它内部本来就是"先取旧值、再写新值"，只是调用点抢在它前面写了。

### #7：暂停对单次执行无效——两种语义澄清方案的选择

`PauseSession` 的判据是 `State == Running`，而**单次执行期间 `State` 同样是 Running**，所以判据通过 → 置 Paused、`PauseLock.Reset()`。但 `RunSessionOnceAsync` 从头到尾不碰 `PauseLock` → 流程照跑到底、结束直接落 Stopped。**UI 全程显示"已暂停"，而流程根本没停。**

本质区别：

| 执行模式 | 暂停的落点 |
|---|---|
| 连续执行 | 循环里每圈开头 `PauseLock.Wait(token)` —— **有落点** |
| 单次执行 | `ExecutionEngine.Run(context)` 一把跑完整图 —— **中间没有可插入等待的位置** |

三个候选：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **选定** | 语义澄清：明确"单次执行不可暂停"，`PauseSession` 显式拒绝并留痕 | 改动小、语义一致；代价是"试跑中想暂停"确实做不到 |
| 否决 | 功能补全：在引擎节点遍历处插 `PauseLock` 检查 | 功能更完整，但改动深入引擎热路径，需另评性能与重入 |
| 否决 | 最小改动：单次执行只在 `Run` 前等一次 `PauseLock` | 只修一半 —— 一旦进 `Run` 就不等了，UI 仍会出现"显示 Paused 却在跑" |

选定的实现：给 `FlowSession` 加一个运行期标记 `IsContinuousRun`（[:129](file:///e:/VM/VisionMaster-W-master/Core/Models/FlowSession.cs#L129)），连续执行置 `true`、单次执行置 `false`，`PauseSession` 按它分流。

**为什么不用别的方式判断**：`State` 区分不出来（两者都是 Running）；用 `FlowEngineService` 里的 `HashSet<sessionId>` 记"哪些是单次执行"会造出第二份账本 —— 而这正是 A 组 #4 刚删掉的反模式（`LockedResources`）。所以标记放在会话自己身上。

**赋值顺序上的保证**：`IsContinuousRun` 一律在 `IsRunning = true` **之前**写入（[:188](file:///e:/VM/VisionMaster-W-master/Engine/FlowEngineService.cs#L188) / [:309](file:///e:/VM/VisionMaster-W-master/Engine/FlowEngineService.cs#L309)），而 `PauseSession` 的守卫先读 `IsRunning` —— 能通过守卫的调用，必定看得到本轮的正确值。

### 清单外的第 3 处：`message` 参数被认真填、却从未送达

`NotifyStateChanged(session, SessionState.Faulted, ex.Message)` 在两个 Faulted 路径上煞有介事地传了失败原因，但 `SessionStateChangedEventArgs` **根本没有 `Message` 字段** —— 参数被吞掉了。

这是个陷阱：后人读到调用点会以为失败原因送达了订阅者。按用户对死契约的口径「**要么接上要么删掉**」，这里选**接上**——失败原因是状态变更事件语义的一部分（一个只说 Faulted 不说为什么的"半事件"用处有限），且新增字段是纯增量、零风险。

### 断言的灵敏度实测

还原两处旧写法（把 `State = Stopped` 挪回调用方、`PauseSession` 跳过 `IsContinuousRun` 判定）：

```
[×失败] 【核心】OldState 不再恒等于 NewState（Stopped 事件的旧状态是 Running）
        →  实际 2 次转换: Idle▶Running → Stopped▶Stopped     ← 恒等现场复现

```

两个症状都完整复现。验完已立即还原。

### 关于「触发两次 PropertyChanged」这条推测

[E11] 里有一条 `一次状态转换只触发一次 State 通知 → 实际 2 次`（Running 一次 + Stopped 一次）。

**必须诚实标注：这条断言新旧代码都会通过，灵敏度为 0。** 原因是我在核实阶段就判断清单该条推测不成立——Prism 的 `SetProperty` 在值相等时短路，调用方先赋一次、`NotifyStateChanged` 再赋一次是 no-op，不会重复触发。所以它的价值是**反证清单这一条**，不是防回归。

## 四、已知边界

| # | 项 | 说明 |
|---|---|---|
| 1 | **单次执行彻底不能暂停** | 用户选定方案的固有代价。若将来现场提出"试跑中要能暂停"，需要走被否决的"功能补全"路线：在引擎节点遍历处（`RunSequence` / `RunAndGetNext`）插 `PauseLock` 检查，让"当前节点跑完就挂起"生效。**届时 `IsContinuousRun` 这个标记可以删掉**（因为两种模式都能暂停了），但要重新评审引擎热路径的性能与重入 |
| 2 | **`IsContinuousRun` 是运行期标记，不落盘** | `FlowSession` 本身不参与序列化（落盘的是 `SolutionModel`/`FlowModel`），所以不需要 `[JsonIgnore]`。若将来有人把会话持久化，必须补上 |
| 3 | **`PauseSession` 的拒绝是"Warn + 无操作"，没有返回值** | `IFlowEngine.PauseSession` 的签名是 `void`。UI 若想据此禁用暂停按钮，需要改接口（返回 bool 或改用 `CanPause` 查询）。本轮只做到"有留痕"，没改契约 |
| 4 | **⚠ 本组验证受并行写入干扰，基线数字不可比** | 断言总数在验证期间随 `WireSequenceCheck` 频繁变动（371 → 377 → 380），所以本记录**不引用"通过 380 / 失败 6"这类绝对数字**，只以 `[E1]`~`[E11]` 段零失败为口径。另注意：并行写入会让同仓库的增量构建出现"读到半写文件"的假错误（实测到一次 `WireSequenceCheck.cs` 报 `StepState` 不存在，重跑即消失）——**遇到莫名其妙的编译错误，先重跑一次** |
| 5 | **`Message` 目前仍无消费者** | 接上字段是为让契约诚实（调用点确实在传失败原因），但当前没有任何订阅者读它。若将来仍无人用，可考虑与 `PortBindingService`（清单 #13，恒为 null）一起做一次"死契约清理" |
| 6 | **`SessionStateChanged` 事件无生产订阅者** | 全仓只有 `CommStress` 压测程序与断言在读它。这解释了为什么 `OldState` 恒等这么久没被发现——**没有真实消费者，缺陷就一直潜伏**。是否要把它接到 UI（状态栏/日志）属于产品决策，不在本组 |
