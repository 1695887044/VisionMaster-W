## 1. 当前状态

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| L1 有 `Alarm[90]`，导入 L2 的 `Alarm[90]` | 错误行（方案内唯一） | **允许新增**（不同设备） |
| L1 有 `Alarm[90]`，在 L1 再建/导入同名 | 错误行 | 仍拒绝（同设备） |
| 本地变量叫 `Alarm[90]`，任何设备导入同名 | 错误行 | 仍拒绝（本地无设备，全方案唯一） |
| 网络变量改名成**同设备**别人已用的名字 | 拒绝 | 仍拒绝（提示点名 `设备「L2」`） |
| 网络变量改名成**另一台设备**已用的名字 | 拒绝 | **允许** |
| 本地变量与网络变量互相改名成对方的名字 | 拒绝 | 仍拒绝（双向） |

**判据唯一入口** `Core/Binding/VariableNameScope.cs`：

- `Conflicts(scopeConnection, other)`：目标作用域 vs 既有变量。目标无设备（本地）→ 与任何变量冲突；对方无设备（本地/系统）→ 也冲突；双方都是网络变量 → 仅同连接冲突（`Ordinal`，与轮询注册表的键一致）。
- `Conflicts(target, other)`：两个既有变量之间，**必须对称**。
- `FindBlocker(variables, name, scope)`：新建/导入共用的"找撞名者"，名字大小写不敏感。
- `DescribeScope`：上屏文案（`设备「L1」` / `本地变量` / `系统变量`）。

## 5. 踩过的坑（暴力测试抓到的两个真问题）

1. **`Conflicts` 方向不对称**（已修）。第一版写成"目标在设备上 → 只有对方也是同设备网络变量才冲突"，于是 `Conflicts(网络变量, 本地变量)` 返回 **false**：网络变量可以改名成某个本地变量已用的名字，改完那一刻"成功"，之后按名解析永远歧义。
   - 抓到它的是 **C10.1 6×6 真值表**、**C10.3 对称性**、**C6.6 网络→本地改名**三条独立断言同时报错。
   - 修法：`Conflicts` 里补"对方没有设备 → 冲突"，并让两个重载共用同一套三分支逻辑。
2. **`Apply` 里有第二道独立复核**（已修）。`BuildPlan` 放行跨设备同名之后，`Apply` 仍用旧的扁平 `HashSet<string>`（方案内唯一）再查一遍，直接抛"变量名已被占用，请重新预览"。
   - 抓到它的是 **C12 端到端 Apply**（C12.1 计划是 New，C12.2 应用直接抛异常）。
   - 教训：**"计划"和"落地"两处各写一遍校验，就一定会漂移**。批 1 的教训是"四条写入路径要共用一对索引维护方法"，本批是"两处校验要共用一份判据"。
3. **探针夹具的假失败**：第一版 C4/C11/C12 全红，原因不是产品 bug 而是夹具把 `布尔 (bool)` 放进了 Modbus 保持寄存器区，被"存储区不支持该数据类型"先拦掉，把要验的"名字冲突"盖住了。夹具改用 `整数 (int)` 后正常。
   - 教训：**断言失败先看 `Note` 原文**，别急着改产品代码。
4. **C11 夹具的第二个坑**：`BuildPlan` 的 `existingDeviceVariables` 是"本连接下的既有变量"，我一开始传了空表、却把本设备的同名变量塞进了 `allVariables`，于是被正确判成"同设备冲突"。真实调用方 `DeviceVariableImportViewModel.DeviceVariables()` 是按连接过滤的——夹具必须照做。
