## 一、需求与决策

### 1. 需求

路线图 S6 唯一的未闭合项，原文逐字：

> 真机（**未做，S6 唯一未闭合项**）：1920×1080 画面挂 200 个绑定，接模拟变量以 20ms 周期跳变，跑 60s，UI 不卡、内存不涨、停止后句柄与订阅归零。

它要回答的是一个 `[BL]` 回答不了的问题：**同一份负载连着跑 60 秒，各项指标会不会随时长往上走？**

`[BL]`（S13-a）量的是**瞬时单位成本**——一次操作摊多少 µs。它是"快不快"。但组态软件现场是**连着跑几个月**的，真正难查的故障形态是**缓慢泄漏**：订阅漏摘一条、脏表漏清一格、角标数组每帧加一项，跑一分钟看不出来，跑八小时就卡死。这类问题**只有"持续负载 + 中途取样对比"才测得出来**。

### 2. 决策清单

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| T-1 | 与 `[BL]` 的分工 | **另开一段 `[ST]`，不塞进 `[BL]`** | `[BL]` 是"操作摊薄到单次"的**除法**；`[ST]` 是"同一份负载随时间的**曲线**"。一个量瞬时、一个量趋势，混在一段里两类数字会互相污染 |
| T-2 | 值从哪来 | **`System.Threading.Timer` 后台线程推值，UI 线程只消费** | 生产上 `ValueChanged` 来自后台轮询线程（`IScadaValueHandle` 注释写明"可能在非 UI 线程"）。**若让 UI 线程自己推值，这个测法就是循环论证**——UI 被自己写的值卡住，测出来的是"它自己卡自己"，不是"被数据压垮" |
| T-3 | 怎么把帧真的刷出来 | **复用现成的 `PumpDispatcher(ms)`**（`DispatcherFrame` + `DispatcherTimer(Send)` + `PushFrame`），不用连续 `FlushNow()` | `FlushNow()` 是**抄近路**——直接调刷帧函数，绕过 `Interlocked` 排队 + `BeginInvoke` 这条**真正要压的路径**。真推消息循环才能让 `BeginInvoke` 排进去的 `Flush` 真的跑，走生产路径 |
| T-4 | "UI 卡不卡"怎么量 | **UI 线程上的 `DispatcherTimer(Normal, 20ms)` 心跳探针**，记最长间隔 `maxGapMs` | 无窗口环境没有"体感"。探针的**间隔**就是 UI 线程的**可用性**：刷 200 个绑定若把 UI 线程占住，探针间隔立刻被拉长。断言 `< 1000ms`，精确数字进留档块 |
| T-5 | 为什么 60s = 预热 2s + 正式 58s | **前 2s 吞掉 JIT / 模板解析 / 首次刷帧** | 冷启动那几十毫秒的抖动会把"最长停顿"和"节拍"污染掉，让数字不可比。预热段同时被断言用来证"值真的落到控件上" |
| T-6 | 怎么防"最后一拍"偶发假红 | `PauseRaiser()` **三件事**：停表 → `SpinWait` 等 `inFlight == 0` → `PumpDispatcher(200)` 排空 | 不等 `inFlight` 归零，读控件与读 `lastRaised` 之间会夹进一拍 → 断言偶发红。**偶发红的断言最后一定会被当噪声忽略**，等于白写 |
| T-7 | 拍数断言怎么写 | 目标 3000 拍，断言 **`>= 2400`**（留 20% 余量） | 机器抖动、GC 停顿都会吃掉几拍。断言"没被拖垮"而不是"精确 3000"——字面值由留档块打印 |
| T-8 | 内存怎么量 | **`GC.GetTotalMemory(true)`**（强制 GC 后取），中途基线 vs 终了，阈值 **< 8MB** | 不强制 GC 的话量到的是"还没回收的垃圾"，不是泄漏。8MB 对 200 绑定 × 3000 拍是极宽的口子，只拦**真泄漏** |
| T-9 | 图元怎么摆 | **20 列 × 10 行铺开**，不堆在同一点 | 挤在同一个点上会被渲染层的**可见性裁剪**跳过一大片——那就压了个空，200 个绑定里真正刷的可能只有十几个 |
| T-10 | 取值断言怎么配对 | **按引用配对**（`ReferenceEquals(c.Element, probeElement)`） | `EnumerateControls()` 的**返回顺序不是契约**。按下标配对会在实现改顺序时假红 |
| T-11 | 断言的观测点 | **中途取样 + 终了取样两处**，不只看终了 | 只看终了的话，"中途涨到 500、终了回落 200"这种**抖动型**问题会被漏掉。中途那一次取样专门钉"订阅数/命中数/句柄订阅者都不随时长增长" |

### 3. 本段测的 10 件事

| # | 断言 | 拦什么 |
|---|---|---|
| 1 | 装配口径：1920×1080 + 200 图元 / 200 绑定 / 200 变量 | 装配本身就错了（尺寸、条数、变量唯一性） |
| 2 | 建表：200 命中 / 0 未命中 / 200 订阅 / 每句柄 1 订阅者 | 建表期就漏配或重复订阅 |
| 3 | 中途（约 100 拍）：订阅 200 / 命中 200 / 角标 0 / 句柄订阅者 200 | **订阅数随时长增长**（泄漏的头号形态） |
| 4 | 预热段的值已落到控件（走生产路径） | 管道**根本没通**（值卡在脏表里没刷出去），测法退化成空跑 |
| 5 | 60s 内跑出 ≥ 2400 拍 | 持续负载把节拍拖垮（每帧越刷越慢） |
| 6 | UI 线程最长停顿 < 1000ms | UI 被 200 个绑定刷帧占死（画面卡住） |
| 7 | 58s 后内存不涨 < 8MB | 内存随时长增长（脏表/角标/委托链泄漏） |
| 8 | 60s 后控件是最新值 | 负载跑满时长后，**最后一拍被丢掉** |
| 9 | 停止后订阅与句柄一起归零 | `Stop()` 漏摘订阅（变量注册表是长生命周期对象，漏一条就是永久泄漏） |
| 10 | 停止后 200 图元全部回设计值 | 运行值污染设计值（或需要一张"恢复现场"的备份表） |

  [√通过] 跑完 60s 后控件上是最新值（负载跑满整个时长，最后一拍的值也没被丢掉）  →  「1.0」 vs 期望「1.0」

### 4. 长稳数字（留档 —— 回归时与这一块对比）

跑于 2026-09-20，开发机（Windows / .NET 9 / Debug 构建）：

```
  ┌─ 长稳数字（留档：粘贴进 docs/code-changes）────────────────────
  │ 装配 | 1920×1080 | 200 图元 / 200 绑定 / 200 变量 | 建表命中 200、未命中 0、订阅 200
  │ 节拍 | 目标 20ms × 60s = 3000 拍 | 实跑 3001 拍 = 19.99ms/拍
  │ UI  | 最长停顿 73ms
  │ 内存 | 中途 28256KB → 终了 28103KB（+-153KB）
  │ 订阅 | 建表 200 → 中途 200 → 停止 0
  └────────────────────────────────────────────────────────────────
```

**怎么读这一块**（回归时先看这里）：

- **节拍 19.99ms/拍**：目标就是 20ms，实跑 3001 拍（比 3000 多 1 拍是计时器相位差，正常）。**关键看"节拍有没有随时间变慢"**——本测法量不到单拍曲线，只能看总数；若某次实跑掉到 2400 附近，说明刷帧开始跟不上推值。
- **UI 最长停顿 73ms**：这是**整整 60 秒里最坏的一帧**。73ms ≈ 3.6 个推值周期，属于 GC 停顿 + 一次刷 200 个绑定的正常叠加。**这条一旦跳到几百毫秒，说明 UI 线程被刷帧占住了**（先查是不是每次 Flush 都重算了整页）。
- **内存 28256KB → 28103KB（-153KB）**：**降了**。降是正常的——中途取样时预热刚结束、GC 还没来得及回收，终了那次强制 GC 更彻底。**要看的是"涨"，涨过 8MB 就是真泄漏**。
- **订阅 200 → 200 → 0**：**这是本段最值钱的一条数字**。中间那个 200 证明"跑了一分钟没多也没少"，最后那个 0 证明"停止时摘干净了"。组态软件现场连跑几个月，**订阅数不随时间增长**才是"跑得住"的定义。

## 四、已知边界

1. **这是"单进程内的等价负载"，不是真机 60s**。没有真窗口、没有 GPU 合成、没有真实渲染管线；`PumpDispatcher` 推的是消息循环不是画面合成。它证的是**领域层 + 绑定管道 + Dispatcher 排队**这条链跑得住，**证不了"真窗口下 200 个图元重绘不掉帧"**。
2. **更不是 8 小时**。路线图 S13"长稳：运行态 8 小时，句柄/内存/订阅数曲线必须平"这一条**仍挂账**——本段只覆盖 60s 等价负载。8 小时真机长稳需要现场机器 + 长时段独占，本轮不具备条件。
3. **量不到"单拍曲线"**。本测法只记总拍数和全程最长停顿，不记"第 1 分钟 vs 第 5 分钟的节拍"。若出现"前 30s 正常、后 30s 逐渐变慢"的形态，本段只能靠总拍数偏低**间接**察觉。做单拍曲线要落盘时序数据，属于 8 小时长稳那一摊。
4. **`maxGapMs` 是"最长停顿"不是"平均帧时间"**。一次 GC 停顿就能把它顶到几十毫秒，但它掩盖不了"平均 30ms/帧"这种持续偏慢。**两条口径互补，本段只钉了前者**。
5. **内存阈值 8MB 是极宽的口子**。它只拦"真泄漏"，拦不住"每拍多留 1KB"这种慢泄漏（60s 只有 60KB）。慢泄漏要靠 8 小时长稳的曲线看。
6. **`--stress` 才跑本段，且本段要真跑 60 秒**。所以它**只适合改动 SCADA 绑定/刷帧相关代码时跑**，不适合每次编译验证——一次 `--stress` 现在要一分多钟。
7. **Debug 构建下的数字**。与 S13-a 同一纪律：Release 会更快，**不要跨配置对比数字**。
8. **假时钟**：本段用真时钟（`Stopwatch` + `System.Threading.Timer`），因为它量的是**真实耗时**。这与 `[BL]` 报警组传定值时钟（避开 `Sleep` 抖动）是两种相反但各自正确的取舍。
