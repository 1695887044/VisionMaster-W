## 一、症状（一次构建失败牵出的僵尸进程）

2026-10-08 22:31 重建插件工程时构建失败：MSB3027「超出了重试计数 10，文件被 “VisionMaster” (7916) 锁定」+ MSB3021「文件正由另一进程使用」，涉及 `Modules\Plugin.*.dll`（红线③那一族：产物建不出来）。

排查发现 `VisionMaster.exe` **PID 7916 是个孤儿僵尸**：

- 启动于 22:18:12，**父进程 36344 已死**（孤儿）；当前 `devenv.exe` PID 37556 是 22:30:47 才启动的，比它晚约 12 分钟——排除“VS 调试宿主攥着进程”（用户当时并没有在 VS 里调试）。
- `MainWindowHandle = 0`；`EnumWindows` 枚举其名下 22 个窗口**全部不可见**，全是 `GDI+ Window` / `WPF MediaContextNotificationWindow` / `Default IME` 之类基础设施窗口，**无应用主窗口**——`VisionMaster\App.xaml:7` 是 `ShutdownMode="OnMainWindowClose"`，退出由关窗口触发，主窗口早已销毁。
- 58 条线程**全部 Wait 状态**；应用日志文件也被它独占着句柄。
- `Modules\` 下 33 个 DLL 里 29 个被占用（清单：`Plugin.*.dll` **27** 个 + `hdevenginedotnet.dll` + `Microsoft.CodeAnalysis.Scripting.dll`；未占用的 4 个是 Roslyn 三件 + `MiniExcel.dll`——“当前实例没懒加载到它们”本身也是旁证：被占的正是已加载进进程的那些）。
- 还攥着单实例互斥体 `Local\VisionMaster-W-SingleInstance`（`VisionMaster\Lifetime\Checks\SingleInstanceCheck.cs:13`、`:21`）——此后任何新启动都会被判“已在运行中”拒绝；以及 TCP **19000**。

## 三、根因（环形等待 / async 上下文死锁）

触发点在 `VisionMaster\App.xaml.cs:383-389`：

```csharp
protected override void OnExit(ExitEventArgs e)
{
    try { _lifetime?.ExecuteExitChainBlocking("应用退出"); }
```

`OnExit` 跑在 UI（Dispatcher）线程上；而（修复前）`Core\Lifetime\AppLifetimeService.cs` 里的阻塞版是

```csharp
public void ExecuteExitChainBlocking(string trigger)
    => ExecuteExitChainAsync(trigger).GetAwaiter().GetResult();
```

用 `GetAwaiter().GetResult()` 把这条线程同步占住；同时链内循环里

```csharp
var winner = await Task.WhenAny(exec, Task.Delay(Timeout.Infinite, per.Token));
```

没有 `ConfigureAwait(false)`——链从 UI 线程起步，`await` 捕获到的可捕获上下文就是 Dispatcher，续体要排回**同一条** Dispatcher 才继续。于是：**GetResult 等链完成 → 链的下半段等 UI 线程空下来 → UI 线程被 GetResult 占着**。互相等，永不恢复。

两个连带事实：

- 挂死在“第几项”取决于该时刻 action 是否已先于 `await` 完成（22:26 那次第 1 项如此，故只有它留了 ✓）；10-06 能走完而 10-07 起必挂的差异在这一点上，**具体原因本轮未查证**（见「六」7）。
- `App.xaml.cs:387` 的 `_singleInstance?.Dispose()` 排在阻塞调用之后，永远走不到 → 互斥体随僵尸锁死（证据见「一」）；退出链第 10、11 项（未保存草稿转存 / 日志落盘收尾）也永远轮不到——`App.xaml.cs:58-61` 的注释声称“正常关闭与严重异常退出都会走退出链，所以两条路都受这一项保护”，**实际上从 10-07 起正常关闭这条路一项都没跑到**（10-07/10-08 共 14 次挂死，草稿转存一次未执行）。

## 四、修复（`Core\Lifetime\AppLifetimeService.cs`，单文件 3 处）

1. **阻塞版本改为从线程池起步**（`:249-250`，注释 `:243-248`）：

```csharp
public void ExecuteExitChainBlocking(string trigger)
    => Task.Run(() => ExecuteExitChainAsync(trigger)).GetAwaiter().GetResult();
```

整条链从**线程池**起步，线程池上没有 SynchronizationContext，`await` 抓不到可捕获的上下文，续体不再需要 UI 线程——环断。

2. **链内 `await` 追加 `.ConfigureAwait(false)`**（`:224-225`，注释 `:222-223`）：兼顾“严重异常”路径——`OnCriticalAsync`（`:149`）是从 UI 线程 `dispatcher.BeginInvoke`（`:158`）起步调用 `ExecuteExitChainAsync("严重异常")`（`:162`）的，那里仍会捕获 Dispatcher，故方法本身也要做到与上下文无关。

3. **30 秒看门狗由“只取消 token”改为真兜底**（`:196-209`）：

```csharp
watchdog.Token.Register(
    () =>
    {
        if (_log is IDisposable logDisposable) { try { logDisposable.Dispose(); } catch { } }
        CrashReportWriter.Write(new TimeoutException($"退出链总看门狗超时（30s），触发：{trigger}"), "退出链看门狗", SafeScene());
        Environment.Exit(3);
    },
    useSynchronizationContext: false);
```

`useSynchronizationContext: false` **不可省**（默认会把回调投回 UI 线程，而那正是可能被占住的那条）；先 `ILogService.Dispose()`（`LogService.Dispose` 会 `Complete()` 队列并 `Join(3000)` 刷盘）→ `CrashReportWriter` 留档 → `Environment.Exit(3)`，硬停机时不再丢诊断日志。

与 2026-10-05 那批的关系：那批加的 `Task.Run(task.Execute)`（`:221`，注释 `:218-220`）让“单项 action 卡住”能超时；本批解决的是“**链整体从被占住的 UI 线程阻塞起步**”——前者在位时，链依然可以整体卡死（本次就是）。

## 六、未决与观察（如实记录，本轮未处理）

1. **死代码分支**：`catch (OperationCanceledException) when (watchdog.Token.IsCancellationRequested)`（`:230-234`）实为死代码——看门狗取消只让 `Task.Delay(Timeout.Infinite, per.Token)` 变成“已完成”，`Task.WhenAny` 不抛异常，故 `[退出链] 总看门狗超时（30s），剩余任务放弃`（`:232`）永远不会打印；实际表现是剩余项被逐项记为 `✗ … 超时（…ms），跳过`（`:228`），并且每项的 action 仍会被 `Task.Run`（`:221`）真的启动一次。
2. **误报成功**：某项 action 若抛 `OperationCanceledException`，其 `exec` 为 cancelled，`winner == exec`（`:226`）成立，会被记成 `✓`。
3. **预算不一致**：30 秒看门狗 vs 最坏总和 11 项 × 5 秒（草稿项 8 秒，`App.xaml.cs:71`）≈ **58 秒**——若多项真的逐项超时，链会在 30 秒处被硬停机，此时第 10 项“未保存草稿转存”可能还没轮到（与第 1 条叠加：硬停机先到，逐项 ✗ 的输出也同样戛然而止）。
4. **只验证了正常路径**（各项都不卡）；“某项真超时”与“看门狗硬停机”两条异常路径**未做运行时验证**。
5. **回归缺口**：既有断言 `[E17] ③ 退出链：卡住的退出任务可超时跳过`（`FlowCanvasChecks\FlowEngineFixChecks.cs:122-148`）是直接调 `ExecuteExitChainAsync("断言").GetAwaiter().GetResult()`（`:136`），**不经** `OnExit` / `ExecuteExitChainBlocking`，且那条线程上没有可捕获的 SynchronizationContext（它能通过本身就是佐证）——本缺陷的成立前提不在覆盖范围内，它当时是绿的、缺陷照样发生。建议后续补一条“**从带 SynchronizationContext 的线程上阻塞起步**”的用例（本轮未做）。
