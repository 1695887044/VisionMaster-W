# 2026-10-05 逻辑分支容器四项修复（For 上限 / 容器失败上浮 / Break 状态 / 循环体分支数）

- 日期：2026-10-05
- 范围：`Core\Models\Compileds\CompiledForNode.cs`（+MaxIterations 与超限闸）、`CompiledBreakNode.cs`（Break/Continue/Return 上报状态）、`Core\Models\FlowSession.cs`（+`EscalateContainerFailures`）、`Engine\FlowEngineService.cs`（两条执行路径收尾调用上浮）、`Engine\FlowCompiler.cs`（+`SelectLoopBody` 分支数校验）+ 检查 2 文件（新增 `FlowContainerChecks.cs`、`Program.cs` 注册）
- 类型：语义加固（不设防 → 设防）+ 状态如实化（绿着错 → 红着停），**不动控制流**
- 起因：用户提问"逻辑分支容器有没有问题"；核实后 While/For 语义上只有一个循环体（构造器只建一个、UI 没有加分支入口），因此第 4 项从"功能缺口"改判为"坏数据防御"

---

## 一、四项改动

| # | 问题 | 改动 | 依据 |
| --- | --- | --- | --- |
| 1 | **For 无运行期迭代上限**：`LoopCount` 可接运行时变量，`Convert.ToInt32` 后不夹取 → 写错量级就是不可中断的长循环 | `CompiledForNode.MaxIterations = 9999`（与 While 同口径）；超限**拒绝执行 + 记 Error + 抛 InvalidOperationException**（由既有的 catch 标 Failed、引擎置 Faulted）——刻意不夹到上限（夹取会静默少跑，比报错难查） | While 早有 9999；现场"计数变量"接错量纲是真实路径 |
| 2 | **容器状态不上浮**：子步骤业务失败而 If/For/While 仍报 Success（唯一聚合的只有子程序调用链） | `FlowSession.EscalateContainerFailures()`：回合收尾递归整棵蓝图树，子孙有 Failed → 容器标 Failed。放在**回合收尾**而不是容器节点内部——If 在"选出分支"即返回、分支体由上层序列执行器跑，容器自己没有"子步骤跑完"的时刻；收尾统一上浮覆盖三种容器且**零控制流风险**（只改状态报告；State 是 `[RuntimeState]`，不递增 Version、不落盘） | 上位机/HTTP 按容器状态判 OK 会放行不良品 |
| 3 | **Break/Continue/Return 不回报运行状态**：画布上这几步永远不亮、无耗时 | 三个节点补 `CurrentNodeId + Running → Success`（Return 标成功：它是"按指令终止"的正常出口，与"流程异常"区分） | 与 A2 口径（容器/算子都上报）对齐 |
| 4 | **循环体分支数不校验**：`Children.FirstOrDefault()` 静默丢弃多余分支，而 `FlowTopology` 会遍历全部分支（两处口径不一致） | 新增 `FlowCompiler.SelectLoopBody`：`Children.Count > 1` → `[容器分支数错误] … 多余的不会被编译——请删除多余分支`（控制流仍取第一个，交给既有空值检查） | 多余分支只能来自手改 .vms（UI 无入口）；坏数据防御 |
| 附带 | HTTP 不报"有步骤失败" | `HttpImageServer` 响应体新增 `failedSteps`，>0 时记 Error（保持 200，不改既有客户端契约） | 审查 P1-4 的最小修法 |

## 二、验证证据（本机实跑）

- 构建：`VisionMaster.csproj`、`FlowCanvasChecks.csproj` 均 **0 错误**；
- 断言：**1494 条 → 通过 1490 / 失败 4**；4 条失败全是既有"另案"（相机模块注册表、YOLO 类别过滤、Motion 属性面板 ×2）——**本批零新增失败**（较上批 5 → 4：并发会话的 BeadInspect 漂移已自愈）；
- **新增 [E19] 12 条全绿**：
  - For 上限：超限图纸编译通过（闸门在运行期）→ **循环体一圈没跑** → 容器标 **Failed** → Error 日志含实际次数与上限（实测 `10000 超过上限 9999`）；
  - 容器上浮：用「调用流程」插件（流程名指向不存在的流程）造**运行期真失败** → 子步骤 Failed → **If 容器如实 Failed** → 控制流未变（走 If 分支、Else 里的步骤没跑）；
  - Break 状态：含 Break 的 3 次循环只跑 1 圈 + **Break 步骤 State=Success**（此前永远 Idle）；
  - 分支数：往 For 手塞第二个分支 → 编译报 `[容器分支数错误] For 的循环体只能有一个分支（当前 2 个）`。

## 三、未决

1. `StepState.Warning` / `Cancel` 两个从未被赋值的死值：**已删除**（用户决策：项目尚未落地、无历史数据顾虑；全仓零引用，删后仅剩 Idle/Running/Success/Failed/Skipped 五个真实结局，枚举注释写明了"运行期语义、不承载业务结论、不需要数据迁移"）。附带说明：State 会被序列化进 .vms，删成员使 Failed/Skipped 的数值前移，但 `ResetState()` 每轮开场就把它清回 Idle，仓库里的旧文件首次运行即被抹平；
2. 容器状态上浮后，**子程序调用链的失败计数会同时包含容器与子步骤**（判定结果不变：只要有一个失败就报失败）；
3. 剩余 4 条基线（相机模块注册表 / YOLO 测试模型 / Motion 属性面板 ×2）属"另案"，需各自定性；
4. GUI 实机冒烟：容器红色状态、Break 步骤高亮、For 超限报错文案待现场验收。
