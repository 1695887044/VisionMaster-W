# 手眼标定：补齐眼在手外（AX = ZB）求解器

> 日期：2026-10-23 ｜ 范围：`Plugins/Plugin.HandEye`、`FlowCanvasChecks/HandEyeChecks.cs`、设计基线 README ｜ 状态：已落地，`FlowCanvasChecks` 3340 通过 / 0 失败

## 1. 背景

用户要求「眼在手外（AX=ZB）求解器一起做了」，并问为什么不用 HALCON 的 `calibrate_hand_eye`。

动手前先查了一遍现状，发现的问题比"缺功能"严重：

```csharp
// HandEyePlugin.TrySolve —— 改之前
bool solved = HandEyeMath.SolveAXEqualsXB(samples, out Mat4 x, ...);   // 完全不看 PoseKind
```

**`PoseKind` 只影响界面文案与输出标签，求解器不分装法**。用户选「眼在手外」会拿到一个眼在手上的解，还被界面标成 `X = T_base←camera`：残差漂亮、数字齐全，但整体是错的。这类"静默错解"比报错危险得多——报错会让人停下来查，错解直接进生产。

## 3. 关键决策

1. **两个装法的相对运动 B 侧不同，只差一个取逆位置。**
   - 眼在手上：`(A_0⁻¹·A_i)·X = X·(B_0·B_i⁻¹)`，解出的就是 X。
   - 眼在手外：`(A_0⁻¹·A_i)·Z = Z·(B_0⁻¹·B_i)`，解出 Z 后 `X = A_0·Z·B_0⁻¹`。
   我第一版照抄了眼在手上的 `B_0·B_i⁻¹`，合成数据实测旋转差 **2.747 rad**、平移差 **1484 mm**。**只有合成真值能抓到这个错**——它是另一个方程的正确答案，残差自洽。

2. **退化判据只写一份。** 抽出 `SolveRelative(relA, relB, …)`：旋转激励、共线、平移病态、det、残差统计都在这里。两种装法共享同一套"什么算解不出来"，避免两套判据慢慢漂移（本仓在别处踩过一次）。

3. **绝对式复算兜"换算式写错"的底。** 相对式残差接近 0 只说明 Z 解得对，不说明 `X = A_0·Z·B_0⁻¹` 写对。所以换算完再用 `E_i = (X·B_i)⁻¹·(A_i·Z)` 从 **i = 1** 起算一遍（i = 0 是换算基准，残差恒为 0，算进去会压低 RMS）。

4. **报错文案必须写清按哪种装法求解。** 残差超限的原文补上「（按「眼在手上」求解）…也可能是装法选错了——先核对「眼在手上 / 眼在手外」」。不写的话，用户看到"残差 31°"只会去翻姿态数据和欧拉约定，永远想不到是工具条上那个开关。

5. **不用 HALCON `calibrate_hand_eye`**：① 数据契约不匹配（它要 camera setup model + 标定板观测，现场给的是算好的成对 4×4，用它等于重新采一整天）；② 坐标约定风险（它输出自己 camera setup 坐标系下的位姿，与客户视觉软件的约定不同，混用得到"残差漂亮、抓取点整体镜像"）；③ **可反证性**——纯数学内核能用合成真值做 1e-13 往返、能逐条列举退化必须失败，HALCON 算子只给"一个结果 + 它自报的残差"，构造不出反例；④ 零依赖（`HandEyeMath.cs` 不引 HALCON / NuGet，可直接被断言宿主 `Compile Include`）；⑤ 诚实的代价：自研约 400 行，靠合成往返 + 退化反证 + 变异反证补，HALCON 交叉验证是可选项不是依赖。

## 5. 边界与未做

1. 只支持 ZYX 欧拉角给定位姿；其他控制器约定需先在 `EulerZyxDegToMat3` 改，并按 03 手册用"只绕单轴转 90°"核对三个符号。
2. 输出口径仍是「相机在基座」与「相机在法兰」两种；不做运行期坐标换算（那是 `PoseTransform` 的职责）。
3. 逐对残差（D2）仍未返回，`Quality` 只给 RMS 与最大值。
4. 真机数据未验：全部结论来自合成数据。欧拉符号错的表现是"残差正常、抓取点整体镜像"。
5. `SolveAXEqualsZB` 对 Z 不设物理约束（不检查靶标是否真装在法兰上），垃圾进垃圾出。
6. 已知既有间歇性红：`MotionChecks` ② `FakeAlarmCard` 的 `SafeStopped` 竞态（`CompleteCommand` 早于 `SetStateLocked`），与本批无关，单开一条改事件驱动等待。
