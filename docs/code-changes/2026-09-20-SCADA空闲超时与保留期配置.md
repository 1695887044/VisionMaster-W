## 一、需求与决策

### 1. 需求

路线图风险登记（2026-09-20 版）里一条，原文逐字：

> `| 空闲超时 `10 分钟` 写死不可配 | 现场有"半小时才走开"的场景，客户会提 | S13 做成方案级配置项 |`

S13-c 的开发记录 §四.2 也留了同一类欠债：

> 审计与报警历史各清各的目录。`Audit/` 与 `Alarms/` 的保留期是两个独立参数（90 / 365），且**目前都在构造处用默认值**——还没有接到方案级配置。现场要改保留期，得改 `App.xaml.cs` 的注册（一行）。

三件事的根因是同一个：**它们都是"换一个现场就该换一个值"的东西，却都写成了编译期常量**。

- 空闲超时 10 分钟：工业 HMI 的常见取值，但现场真有"走开半小时"的工位（去仓库取料、去看另一台设备）。一律按 10 分钟踢人只会让人反复重登，**最后干脆用管理员账号不登出**——那比放宽超时更不安全。反过来说，无人值守的机台也可以配 0（永不自动登出）。
- 审计留 90 天：有客户有留档要求（一天都不能删），也有机台磁盘紧张。
- 报警历史留 365 天：现场要翻很久以前的同类故障做对比，但也可能磁盘不够。

写死的结果是"**每换一个现场改一次源码、重编一次软件**"。

### 2. 决策清单

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| D-1 | 配置**落在哪一层** | **软件级 `AppConfig.json`**（`AppConfigModel`），不是方案级 `.vms` | 路线图原文写的是"方案级"，**这是本次唯一一处实现偏差**。理由：`Audit/` 与 `Alarms/` 目录是**全局共享**的（`AppContext.BaseDirectory` 下），与"当前打开的是哪份方案"无关；空闲超时描述的是"这台机器怎么用"，也不是"这份画面怎么画"。做成方案级会出现"切了方案，同一台机器的超时和保留期跟着变"——那是说不清的行为 |
| D-2 | 三个默认值从哪来 | 常量集中在 `AppConfigModel`：`DefaultIdleTimeoutMinutes = 10` / `DefaultAuditRetentionDays = 90` / `DefaultAlarmHistoryRetentionDays = 365` | `ScadaAccessPolicy.DefaultIdleTimeout`、两个 Writer 的 `DefaultRetentionDays` 全部**从它取**。两处各写一个 90，早晚改一处忘一处，表现是"新建的机器留 90 天、老机器升级后留 180 天" |
| D-3 | 默认值选多少 | **与历史行为逐字一致**（10 / 90 / 365） | 升级不能让现场已经在跑的机器忽然"不踢人了"（那等于把一台无人看管的设备一直留在管理员权限上），也不能忽然把攒了一年多的报警历史清掉 |
| D-4 | "改完立刻生效"**怎么实现** | **现读**，不是推送：三个使用方各注入一个 `Func<...>` 读取口，每次取用时现读 `AppSettingsService.Current` | "把新值推给谁"的写法漏一次就变成"界面改了、实际没改"，**而这种失效不报错、只在超时那一刻才看得出来**。现读之后"改完生效"是**结构上保证**的，不靠谁记得在某处同步一下 |
| D-5 | 空闲超时读取口返回什么类型 | `Func<TimeSpan>`（宿主直接给 `AppConfigModel.IdleTimeout`） | 让 `ScadaAccessPolicy` 不必认识"分钟"这个单位。它认的语义本来就是"`TimeSpan.Zero` 或负值 = 不自动登出" |
| D-6 | "分钟 → TimeSpan"与"0 表示永不"**写在哪** | **只写在 `AppConfigModel.IdleTimeout` 一处**（`[JsonIgnore]` 派生属性） | 这两条规则如果分散在宿主、弹窗、断言三处，早晚出现"界面显示 0 分钟、实际还是按 10 分钟踢人"——**这种不一致只在现场长时间无人操作时才暴露，最难查** |
| D-7 | 派生量进不进 JSON | **不进**（`[JsonIgnore]`） | 落盘的只有分钟数那个原始值。`IdleTimeout` 是派生量，写进去只会多一个**可能与真值矛盾**的数字 |
| D-8 | 保留期读取口返回什么 | `Func<int>`（天数） | 保留期的判定逻辑（`retention <= 0` 先判、再算截止日）本来就在 Writer 里，读取口只需给原始天数 |
| D-9 | 读取口为 `null` 时怎么办 | 回落到构造兜底值（`DefaultRetentionDays` / `DefaultIdleTimeout`） | 断言与单机调试会直接 `new`，这条路径必须能用；也是"没有配置时"的兜底 |
| D-10 | 注入了读取口之后，`ScadaAccessPolicy.IdleTimeout` 的 **setter** 还生效吗 | **不生效**（读取口一律优先） | 配置是唯一真相。两处都能改只会让"界面上明明改了"变成说不清的事 |
| D-11 | 枚举/整数怎么落盘 | 都是**整数**（`IdleTimeoutMinutes` / `AuditRetentionDays` / `AlarmHistoryRetentionDays`） | 与 `RunWindowMode` 同口径：整数更稳，拼错字符串会连带丢整份配置 |
| D-12 | 一致性读（同一次清理里读两次会不会"半新半旧"） | `PurgeExpired` 把 `RetentionDays` **读进局部变量 `retention`** 再判 0、再算截止日 | 保留期现在每次现读，同一次清理里两次读之间若有人正好在改配置，会出现"按 0 判不清理、却按 365 算截止日"这种半新半旧的组合 |
| D-13 | 弹窗输入框**接 `int` 还是接 `string`** | **接 `string`**，在点确定时统一解析 | 直接把 `int` 绑到 `TextBox.Text`，用户敲进 `3O`（字母 O）时 WPF 会**静默把绑定置无效、属性保持旧值**——界面上什么都看不出来，点了确定还写盘成功，而实际保存的是他上一次的值。**宁可不让他确定，也不能让他以为改成了** |
| D-14 | 校验口径 | 与配置模型**一致**（0 或负数 = 不自动登出 / 永不清理），不在 UI 层另立更严的规则 | 两处规则不一致时，界面上"填 0 就能不清理"的提示会变成假话 |
| D-15 | 留空怎么处理 | **当失败**，不当 0 | "留空"被猜成"永不清理"正好是最不该猜错的那个值 |
| D-16 | 三个字段校验的顺序 | **一起校验、一起报错**，短路求值保证 `ErrorMessage` 留下的是**第一条**出错的原因 | 逐条弹窗式的"错一个改一个"在设置页上很烦人 |
| D-17 | 写盘失败怎么办 | **不关弹窗**，且如实说清"没有写入 AppConfig.json" | 用户刚敲进去的三个值还在界面上，关掉就要重填。配置在内存里已被改过但没落盘，所以不能只说"失败" |
| D-18 | 弹窗打开时读几次配置 | 构造时读一次 + `OnDialogOpened` 再读一次，**共用同一个 `ReloadFromConfig()`** | 两处各写一遍，早晚出现"新加一个字段只在其中一处灌"（表现为：首次打开是对的，再打开就退回旧值）。不依赖"容器每次都新建一个 VM"这个假设 |
| D-19 | 菜单入口放哪 | 「系统 → 系统参数设置」，紧跟「运行窗口设置」 | 两者同口径（软件级配置，存 `AppConfig.json`，改完立即生效），放一起让现场一看就知道"这台机器的参数都在这两个地方" |
| D-20 | 新枚举成员加在哪 | `SystemAction` **末尾** | 整数值可能已落进 `Layout.xml`/旧配置，中间插成员会整体移位 |

### 4. 断言的四个层次（对应"做成配置项"真正要成立的四个环节）

1. **默认值**：三个数字只有一个来源（`AppConfigModel` 的常量），升级不改现场行为。
2. **派生量**：分钟 → `TimeSpan`、"0 表示永不"两条规则只写在 `IdleTimeout` 一处；派生量不进 JSON。
3. **读取口**：三个使用方（`ScadaAccessPolicy` / `ScadaAuditWriter` / `ScadaAlarmHistoryWriter`）都"每次现读"，改完立刻生效不靠谁记得同步。
4. **弹窗**：非法输入整体拒绝并说明原因、确定才落盘、再次打开现读。

其中 `ScadaAccessPolicy` 那一份断言**挂 STA 线程**跑（它的构造函数会建 `DispatcherTimer`），样板与 `[AB]` 段的窗口断言一致——单开一条 STA 线程，不把 `Main` 标成 `STAThread` 去改 S0/S1 那批断言的既有运行环境。

弹窗那一半用**真的** `AppSettingsService`（`ConfigPath` 是 `static readonly`、写死在程序目录，没法注入临时目录），所以 `finally` 里把三个原值写回——不给下一次运行留一份脏配置。

## 四、已知边界

1. **配置是软件级，不是方案级**（D-1，本次唯一一处与路线图原文的实现偏差）。路线图写的是"方案级配置项"，实际落在 `AppConfig.json`。理由见 D-1；**副作用**是：同一台机器上换方案不会换参数，现场若真有"这份方案要不同的超时"的诉求，需要另做一层。
2. **改完立刻生效只覆盖"读取口已接线"的三处**。宿主 `App.xaml.cs` / `ScadaRuntimeHost.cs` 里的三处接线由代码审查保证，`ScadaChecks` 里**没有**"宿主注册处真的传了读取口"的断言（那要起 WPF 容器）。断言证的是"读取口本身每次现读"，不是"宿主接上了"。这是与 S13-c §四.6 同一类欠债。
3. **真机验证做了功能，没做像素**。见 §三.5：菜单入口、弹窗初值、非法/留空拒绝、确定落盘、取消不落盘、再次打开现读、**回车与 Esc 的真实按键**都已在真机上走通（磁盘文件逐个核对）。**但没拿到截图**——`PrintWindow` 对 WPF 窗口返回空白位图，锁屏会话下像素采样不可用。所以"弹窗好不好看"这件事仍只有 XAML 层自审，**没有像素级证据**。路线图验收口径第 3 条"留截图"这一半仍欠。
4. **"改完立刻生效"没有在真机上被观察到**。真机验证证明了"值确实写进了 `AppConfig.json`、再次打开读得回来"，但**没有观察到行为变化**（比如把空闲超时改成 1 分钟、登录后干等 1 分钟看是否被踢）。原因是当时处于未登录状态，空闲计时器不跑；要观察得先用管理员账号登录。所以"现读"这条链路的真机证据止于**文件层**，行为层靠断言（§三.3 的"读取口的值一改，同一个实例的立刻跟着变"）。
5. **空闲超时的精度不变**。`ScadaAccessPolicy` 的检查节拍仍是 15 秒（`IdleCheckInterval`），所以"配 1 分钟"的实际表现是"最多晚 15 秒登出"。这是节拍本身的性质，不是本次改动引入的。
6. **没有"配置被改过"的审计**。谁在什么时候把空闲超时从 10 改成了 0，这件事**不落审计**。理由：本次落点是"读配置"，没有经过 `ScadaAuditWriter`。若现场有"参数变更也要留凭证"的要求（法规场景常见），需要另接一条审计——`ScadaSystemParametersViewModel.OnConfirm` 是唯一的写盘出口，接起来不难，但本轮没做。
7. **0 / 负数没有区分**。配置模型把"0"与"负数"都当"不限制"，弹窗也不拦负数。理由是负数没有现实语义（"留 -1 天"是什么意思？），当成同一个意思比另报一个错更省事。副作用是配置里可能出现 `-5` 这种值，界面上显示为 `-5`、行为是"不限制"——不影响正确性，但不美观。
8. **`--stress` 从 1238 涨到 1261**。`[SS]` 段属常规断言（不在 `--stress` 分支里），普通运行也会跑。
9. **弹窗尺寸写死 `Width="580"` + `SizeToContent="WidthAndHeight"`**。字段说明文字换行后高度会变，`Width` 固定是为了让两组卡片对齐。若将来加第四个字段，需要重看这个宽度。
10. **真机验证的驱动脚本是临时的**。UIA 驱动（含本次新加的 `key` 动作）写在 `%TEMP%\vm-uia2.ps1`，**没有进仓库**。仓库里现有的 [vm-uia.ps1](file:///e:/VM/VisionMaster-W-master/tools/vm-uia.ps1) 只有 `list / invoke / texts / click` 四个动作，**注入不了键盘**——下次要在真机上验证键位，得先把 `key` 动作补进它。
