## 4. 建议的“真数据快照”方案（先不接 UI）

### Phase 1：只读快照（推荐先做）

写一个**独立只读提取器**，读 `.vms` + 方案目录 `Image\`，输出 `asset-snapshot.json`，不碰 `ProjectAssetsViewModel`、不改 UI。

每条记录至少带：

```json
{
  "kind": "calibration",
  "assetId": "2aa0b611-342b-7f1b-ba74-11cbd48ddf26",
  "name": "LineCalib",
  "sourceType": "Core.Interfaces.CalibrationAsset",
  "sourcePath": "SolutionModel.Calibrations[0]",
  "status": "real-persisted",
  "version": 1,
  "fields": {
    "calibrationKind": "PixelScale",
    "mmPerPixel": 1.0,
    "cameraSerial": "NET-STATION-02",
    "residualRmsPx": 0.0
  },
  "warnings": ["BaselineOnly", "NoAudit", "NoReview"]
}
```

派生记录同样写清来源和缺口：

```json
{
  "kind": "image",
  "assetId": "file:Image/board_01.png",
  "name": "board_01.png",
  "sourceType": "File",
  "sourcePath": "ST2_Position/采集定位图/FilePath",
  "status": "derived",
  "fields": { "width": 1280, "height": 960, "sha256_8": "FF2F5B7C" },
  "warnings": ["NoAssetClass", "NoVersion"]
}
```

```json
{
  "kind": "recipe",
  "assetId": "step:ST5_Assembly/胶路检测/RecipeLibraryJson[0]",
  "name": "BeadA",
  "sourceType": "Plugin.BeadInspect.RecipeLibraryJson",
  "status": "derived",
  "fields": { "refImage": "Image/adhesive_bead_01.png", "points": 31 },
  "warnings": ["EmbeddedInStep", "NoRecipeDefinition", "NoAudit"]
}
```

三条纪律：

1. **有 Id 用真 Id**（`CalibrationId`、`CameraDescriptor.Id`、`FlowID`、`VariableId`、`PageId`）；
2. **没有 Id 不要现造 GUID**，用 `file:` / `step:` 这类可追溯键；
3. **没有值就写 `null` / `未配置` / `warnings`**，不要用看起来合理的假值填。

3. **模板/模型为空**：6 个模型槽位、1 个模板库都没有文件。
4. **顶层配方缺失**：`SolutionModel.Recipes` 为空；`BeadA` 是插件内嵌 JSON，不能直接当 `RecipeDefinition`。
5. **没有版本/复核/审计/引用索引**：除 `CalibrationAsset.Version/IsLocked` 外，其他数据都没有这些字段。

7. **页面会变稀**：真实五类只有 16 行；要 28 行只能扩类或补数据。

## 6. 建议

先做 **Phase 1 只读快照**，不接 UI。  
产出物只包含：`asset-snapshot.json` + 一份 provenance 说明（每条数据的类、路径、状态、缺口）。  
看完快照后再决定：接受稀疏真实页（A），还是扩设备/工程资产类型（B），还是先补真实模型/模板/配方（C）。

**不建议**为了保持 28 行去生成模板/模型/配方假记录；那只是把 UI 假数据换成了 JSON 假数据，问题没解决。

## 7. 方案级资产边界（2026-10-26 补充）

通讯、板卡、相机已经在设备视图里，**不要搬进项目资产页做第二套 CRUD**。建议把方案数据分三层：

| 层 | 内容 | 归属视图 | 是否进项目资产页 |
|---|---|---|---|
| 内容资产 | 标定、模板、模型、配方、标准图/参考图、报表模板、画面模板、子流程模板 | 项目资产 | 是；有生命周期、版本、引用、冻结/归档 |
| 设备配置 | 相机、运动卡、通讯、IO、数据库连接 | 设备视图 | 否；资产页只显示“关联设备/引用位置”，点链接跳到设备视图 |
| 工程对象 | 流程实例、变量、SCADA 页面、报警、报表实例、数据记录 | 各自编辑器 | 否；资产页只在“引用”页显示影响面 |

**判定一个对象该不该进资产页，问四个问题：**

1. 它是否随方案保存、并且可能跨方案复用？
2. 它是否有稳定 Id、内容版本/哈希，能按 Id 引用而不是复制内容？
3. 流程/画面是否按 Id 引用它，改它会影响多处？
4. 它是否需要冻结、归档、回滚、权限、引用影响面？

四条都成立 → 内容资产；只满足“随方案保存” → 配置或工程对象，留在原视图。

按这个口径，当前建议的资产清单是：

| 资产类型 | 现状 | 结论 |
|---|---|---|
| 标定资产 | `CalibrationAsset` 已有，1 条 | 保留；补版本/复核/有效期 |
| 模板资产 | `TemplateLibraryJson` 有槽位，0 条 | 保留类型；补模板资产类与真实模板文件 |
| 模型资产 | `ModelPath` 有槽位，0 条 | 保留类型；补模型资产类与真实模型文件 |
| 配方资产 | `RecipeDefinition` 有类，顶层 0 条；`BeadA` 内嵌 | 保留类型；把内嵌配方提升为顶层配方或做适配器 |
| 图像资产 | 文件有 14 条被引用，无资产类 | 保留类型；补文件资产 DTO/哈希/尺寸 |
| 报表模板 | `ExcelExport` 只有配置字符串 | 可选；做成独立文件资产后再进 |
| 画面模板 | SCADA 页面已有 15 页，但当前是方案内容 | 可选；只有“跨方案复用”时才做画面模板资产 |
| 子流程模板 | 流程已有 14 个，但当前是方案实例 | 可选；只有“跨方案复用”时才做流程模板资产 |
| 相机/运动卡/通讯 | 已有独立设备视图 | **不进资产页**；资产详情只显示关联设备与跳转 |
| 流程/变量/SCADA 页面 | 已有各自编辑器 | **不进资产页**；只在引用页显示使用位置 |
| 运行态/日志/审计 | 运行服务 | **不进资产页**；审计单独服务 |

**推荐的信息架构：**

- 项目资产页继续只做“内容资产”五个页签；
- 资产详情增加“关联设备”只读卡片：显示 `CameraDescriptor.Id/SerialNo`、`MotionDescriptor.Id/DisplayName`、`CommunicationConfig.ConnectionName`，点击跳设备视图；
- “引用”页签列出流程/步骤、SCADA 页面/图元、配方/工位；
- 设备视图仍是相机/板卡/通讯的唯一编辑入口；
- 如果以后要跨方案复用设备配置，再单独做“设备档案/设备配置快照”资产，引用设备视图对象，而不是复制一份设备配置。

这样不会出现“同一个相机在两处可编辑、改一处另一处不生效”的双源问题。

## 8. 五类内容资产“录入”的改动与影响

“录入”有两种口径，工作量差一个量级：

- **只读录入**：把 `.vms`/方案目录里已有的真数据读进资产页，不新建、不编辑、不落盘。
- **可写录入**：用户能在资产页新建/导入/编辑/冻结/升版，并随 `.vms` 保存。

建议先做只读录入，再决定是否做可写录入。

### 8.1 五类分别要做什么

| 资产 | 现有承载 | 只读录入要做的 | 可写录入还要做的 | 影响 |
|---|---|---|---|---|
| 标定 | `SolutionModel.Calibrations` / `CalibrationAsset` | 直接投影；显示“基线/待计算” | 版本历史、复核、有效期、默认资产、权限 | 低；现有 `ICalibrationCatalog` 不动 |
| 模板 | `MatchingPlugin.TemplateLibraryJson` | 解析模板库；当前 0 条，只能显示未配置 | 新 `TemplateAsset` 类、文件入库、哈希、预览图、引用 Id | 中高；插件配置要能按 Id 解析 |
| 模型 | OCR/YOLO/DL 的 `ModelPath` | 读路径；当前 6 个槽位全空 | 新 `ModelAsset` 类、模型文件入库、类型/输入尺寸/标签/精度 | 高；大文件、插件契约、版本 |
| 配方 | `SolutionModel.Recipes` + `BeadInspect.RecipeLibraryJson` | 顶层 0 条；内嵌 `BeadA` 做适配器 | 把内嵌配方提升为 `RecipeDefinition`，补版本/审计 | 中；不能直接改插件 JSON 语义 |
| 图像 | `ImageAcquisitionPlugin.FilePath` + 文件 | 解析 14 个引用文件，算尺寸/SHA | 新 `ImageAsset` 类、标准图/参考图/采集图分类、版本 | 中；路径相对方案目录，需文件存储 |

### 8.2 数据与存储改动

1. **不要把所有资产塞进一个多态基类**。  
   现有 `CalibrationAsset` / `RecipeDefinition` 已经是具体类；新增模板/模型/图像也用具体类 + 具体集合，避免 `SafeSerializationBinder` 白名单和 `$type` 迁移。
2. **`.vms` 只存元数据 + 相对路径 + 哈希，不存二进制**。  
   模板/模型/图像文件放方案目录 `Assets\`（或软件级资产库），`.vms` 保持可读、可 diff；否则模型一多，`.vms` 会膨胀到不可维护。
3. **新增集合要有默认值和迁移**。  
   `SolutionModel` 新增 `TemplateAssets` / `ModelAssets` / `ImageAssets` 时给空集合默认值；旧 `.vms` 没有这些键 → 空集合，不报错。`SolutionService.LoadAsync` 加一次迁移/补齐。
4. **旧版本兼容要明确**。  
   新程序读旧文件没问题；旧程序读新文件会忽略未知键，但**旧程序保存时可能把新资产段丢掉**。要么升方案 schema 并提示“需新版本打开”，要么用 `[JsonExtensionData]` 保留未知段；不能默认没事。
5. **资产 Id 稳定**。  
   新类用 `Guid AssetId`；文件资产再用 `ContentHash` 判断内容是否变化。版本只在内容变化时递增，不能每次保存都 +1。

### 8.3 引用与插件改动

这是最大的一块，也是“录入”能否真正有用的关键：

- 现在模板/模型/图像在步骤里是**路径/名字字符串**（`TemplateLibraryJson`、`ModelPath`、`FilePath`），不是资产 Id；
- 只读录入可以按路径/名字做**弱引用**，但改名/移动就断；
- 要按 Id 引用，必须给插件配置加可选 `AssetId` 字段，并让插件通过宿主解析器拿资产；
- 这会改插件契约 → 必须重建全部插件工程（红线③）→ 跑 `run_gates.ps1` 全量验证。

**建议**：第一期只做弱引用 + 引用影响面提示，不改插件契约；第二期再给模板/模型加 `AssetId`，图像可先保持路径。  
配方和标定已有 Id（`RecipeId` / `CalibrationId`），可以优先按 Id 引用。

### 8.4 UI 改动

- `ProjectAssetsViewModel.BuildMockAssets()` 删除，改为 `IProjectAssetCatalog` 查询；
- `ProjectAssetItem` 保留为 UI 投影模型，不直接当持久化模型；
- 新建弹窗按类型拆分：标定/模板/模型/配方/图像字段不同，不能继续用一个“名称+类型+工位+相机”表单；
- 增加导入文件选择、文件校验（扩展名/大小/哈希）、重复检测；
- 详情页“引用”从静态演示改成真实扫描结果；
- 设备相关只显示“关联设备”只读卡片，跳设备视图，不在资产页编辑。

### 8.5 对现有的影响

| 现有对象 | 影响 | 风险/注意 |
|---|---|---|
| `SolutionModel` / `.vms` | 新增资产集合；文件变大（元数据） | 旧版本保存丢新段；需 schema/兼容策略 |
| `CalibrationPlugin` / `ICalibrationCatalog` | 不改；资产页只读它 | 若做统一 Id 迁移，必须保留 `CalibrationId` |
| `RecipeDefinition` / 配方 UI | 不改类；资产页读 `Recipes` | 当前顶层为空；内嵌 `BeadA` 不能冒充顶层配方 |
| 模板/模型/图像插件配置 | 只读期不改；写期可能加 `AssetId` | 改插件要重建、跑全量 gate |
| `ProjectAssetsView` / ViewModel | 替换假数据；新建/导入 UI | 页面会从 28 行降到 16 行左右 |
| 权限/审计 | 现在资产动作是演示，无真实权限 | 可写录入必须接 `AccessPolicy` + 审计 |
| 撤销/草稿 | 资产元数据可进撤销；大文件不能进 | 文件复制/哈希放服务层，不进 undo |
| 解决方案大小/性能 | 模型/图像入库会变大；哈希扫描耗时 | 后台扫描 + 大小/mtime 缓存；导出包带文件 |
| 多方案复用 | 方案级复制会产生重复模型/图像 | 后续可做软件级资产库，方案只存引用 |
| 测试/闸门 | 新增 catalog/导入/引用断言 | 插件契约改动会触发全量重建与 gate |

### 8.6 推荐分期

| 阶段 | 内容 | 估算 | 对现有影响 |
|---|---|---:|---|
| Phase 1 | 只读 catalog：标定/配方/图像 + 模板/模型空态；UI 绑真实数据 | 1–2 天 | 只改 UI/服务，不动 `.vms`、不动插件 |
| Phase 2 | 模板/模型/图像可导入、落方案 `Assets\`、哈希/版本/重复检测 | 5–8 天 | 新增资产类/集合/迁移；不动插件契约 |
| Phase 3 | 按 Id 引用、冻结/回滚/权限/审计/引用影响面 | 1–2 周 | 可能改插件契约、全量重建、兼容策略 |

**结论**：前五个作为内容资产录入是对的；但先做只读录入，页面会变稀是正常的。  
真正的成本不在“显示”，而在**文件入库、Id 引用、版本/审计、旧版本兼容**这四件事。

## 9. 不考虑旧方案兼容后的修订

前提变化：项目未落地，旧 `.vms` 可以丢弃/重建；不做迁移、不保留旧字段、不支持旧程序打开新文件。

### 9.1 可以简化掉的

| 原来要做的 | 现在 |
|---|---|
| 旧 `.vms` 缺字段补齐、迁移服务 | 不做；升 `AssetSchemaVersion`，旧文件直接拒绝并提示重建 |
| 旧程序读新文件丢字段的兼容 | 不做；新格式只保证新程序 |
| 为兼容保留旧路径/旧名字段 | 可以重命名、删除、重排；`Recipes` 可以从 nullable 改为非空 |
| 双读/双写、灰度开关 | 不做；一次切换 |
| 为了不破坏旧数据而保留的弱引用 | 可以第一天就要求 `AssetId` |
| 保留现有 28 条假数据结构 | 可以整体重写 ViewModel/UI |

### 9.2 仍然不能简化的

- **真实模板/模型/配方文件仍然要外部提供**；没有文件，代码只能显示“未配置”。
- **`LineCalib` 仍是预置基线**；不是实测标定，需要真实标定图/已知长度跑一次。
- **相机/板卡/PLC 仍是虚拟/占位设备**；不是生产硬件。
- **版本、审计、权限、引用影响面仍要设计**；没有旧数据不等于这些自动有了。
- **改插件契约仍要重建插件、更新帮助、跑全量 gate**；不兼容旧方案不会减少这项成本。

### 9.3 修订后的推荐架构

- **具体类型集合 + 统一读模型**：`Calibrations`、`Recipes`、`TemplateAssets`、`ModelAssets`、`ImageAssets` 各自具体类；UI 用 `IAssetCatalog` 合并成统一 `AssetDescriptor`。  
  不建议做一个多态 `AssetBase` 集合——序列化 binder、校验、迁移都会变复杂。
- 五类统一公共元数据：`AssetId`、`Name`、`Scope`、`Version`、`Status`、`ContentHash`、`CreatedAt/By`、`UpdatedAt/By`、`IsFrozen`。
- `.vms` 存元数据 + 相对路径 + 哈希；文件放方案 `Assets\{templates,models,images}\<hash>\...`，不把二进制塞进 JSON。
- 模板/模型/图像插件配置改为按 `AssetId` 解析；路径/名字只作为导入来源，不再作为主键。  
  这是“干净设计”的最大成本，但既然不兼容旧方案，建议一次做对。
- 标定继续保留 `CalibrationAsset` + `ICalibrationCatalog`，资产页包一层读模型；不要为了统一而改 `CalibrationId`。
- 配方保留 `RecipeDefinition`；顶层 `Recipes` 改为非空列表；`BeadA` 从插件内嵌 JSON 一次性导入为配方资产。
- 引用按 `AssetId` 扫描流程/SCADA；资产详情显示引用位置，设备只显示只读关联。

### 9.4 修订后的影响

| 对象 | 影响 |
|---|---|
| `.vms` | 格式故意不兼容；旧文件拒绝；示例方案重建 |
| `CalibrationPlugin` / `ICalibrationCatalog` | 尽量不动；资产页适配，不改 `CalibrationId` |
| `RecipeDefinition` | 保留类；顶层列表非空；内嵌 `BeadA` 一次性导入 |
| 模板/模型/图像插件 | 加 `AssetId` 解析；重建全部受影响插件；更新帮助/测试 |
| `ProjectAssetsView` / ViewModel | 整体重写假数据层；新建/导入按类型拆分 |
| 权限/审计 | 必须新接；不能沿用演示按钮 |
| 测试/闸门 | 资产 schema/catalog/导入/引用断言；插件改动触发全量 gate |

### 9.5 修订后的估算

| 阶段 | 内容 | 估算 |
|---|---|---:|
| Phase 1 | 新资产 schema + 只读 catalog + 真实 UI（不改插件） | 2–3 天 |
| Phase 2 | 模板/模型/图像导入、文件入库、哈希/版本/重复检测 | 4–6 天 |
| Phase 3 | 插件按 `AssetId` 解析 + 引用扫描 | 3–5 天 |
| Phase 4 | 冻结/回滚/权限/审计/引用影响面 | 5–10 天 |

总计约 **2–3 周**（不含真实模型/模板/配方数据准备）。  
不兼容旧方案大约只省掉 **2–3 天**的迁移/兼容工作；真正的大头仍是**文件入库、插件按 Id 引用、版本/审计**。

### 9.6 建议

既然不兼容旧方案，建议**一次把 schema 和 Id 设计对**，但不要把所有类型强行塞进一个多态基类：

1. 先做 Phase 1，页面用真实数据，模板/模型显示空态；
2. 再做 Phase 2，让用户能导入文件并落方案 `Assets\`；
3. 最后做 Phase 3/4，把插件引用、权限、版本、审计补齐。

这样不会出现“先做一套路径引用、后面再全量改 Id”的二次返工。
