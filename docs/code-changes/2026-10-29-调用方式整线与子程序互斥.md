## 2. 为什么必须互斥（运行期口径）

一个流程名只有一个会话（`Engine\IRuntimeManager.cs:206-213` 按名取、`:150-159` 同名替换），
执行权是一把会话锁（`Engine\FlowEngineService.cs:264-278`）。两个入口同时勾时：

| 场景 | 结果 | 代码位置 |
| --- | --- | --- |
| 整线在跑 → 「调用流程」调它 | 直接失败"正在运行中，本次子程序调用未执行"，父流程这一轮判 Faulted | `Engine\FlowInvoker.cs:77-78` |
| 父流程正在调它 → 点「启动整线」 | **静默跳过**（`if (session != null && !session.IsRunning)` 没有 else） | `VisionMaster\ShellViewModel.cs:2325-2339` / `:2420-2443` |
| 整线在跑 → 手动点它"运行" | 引擎 Warn 一条"已在运行中，忽略重复的启动请求" | `Engine\FlowEngineService.cs:485-490` |

即"两条路都配上了，但任何时刻只有一条能用，另一条要么报错要么无声跳过"。
`Core\FlowBatchSelector.cs:26-28` 也记录过同源事故（"7 GB 内存事故就是这么来的"）。

## 6. 踩过的坑

- **运行中的 exe 锁 `VisionMaster\bin`**：`dotnet build` 会报 MSB3021/MSB3027，看起来像构建失败，
  实际 `error CS` 一条都没有——判"代码有没有错"必须 grep `error CS`，别把文件锁当编译错误。
- **断言宿主的 `..\..\..\..\Modules` 是"4 层"约定**（相对 `AppDomain.BaseDirectory`）：
  临时输出目录必须放在 `<仓库>\<a>\<b>\<c>\net9.0-windows\`。
  第一次放到 `artifacts\gatecheck\bin\`（5 层）→ 找不到 `Modules\` → 前提断言直接红。
- **`Plugins\Directory.Build.targets` 每次构建都投递插件 DLL 到 `Modules\`**：
  隔离构建必须同时重定向 `ModulesDir` / `HostBinDir`，否则会去覆盖运行中进程已加载的 DLL。
- **`Select-String -SimpleMatch` 的 pattern 是字面量**：写 `'\[FM4\]'` 永远匹配不到，白白以为"断言没跑"。

### 7.2 为什么留「Main 是整线入口」这一种

旧写法（工位 160 + Main 手动）是"两种模式都支持"：启动整线跑七工位各自的会话，
手动跑 Main 串行调它们。两种模式同时用就撞会话锁——`FlowInvoker` 回「正在运行中（被其它执行占用）」，
统计读到上一轮旧值（生成器 `PairRebuildMain` 的旧注释原文就是这么写的）。
互斥落地后只能留一种，按用户口径留「Main 是整线入口，工位只当子程序」。

### 7.5 两个必须知道的点

1. **运行中的应用会把旧位集写回来**：`VisionMaster.exe`（PID 21240，16:46 启动）内存里仍是 160。
   它再保存一次就把本次改动覆盖掉。改完数据后应先关掉它；若关闭时问是否保存，选**否**。
2. **`--pair` 会把 `VariableSnapshots` 写回生成器那份 57 条**，应用保存时再把数组展开成逐元素
   （实测备份里是 2414 条）。这是应用侧的正常归一化，不是数据丢失；重开方案即恢复。
