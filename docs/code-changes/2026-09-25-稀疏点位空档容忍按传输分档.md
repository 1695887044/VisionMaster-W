# 2026-09-25 稀疏点位空档容忍按传输分档（S3：1000 段 → 84 段）

## 一、需求与决策

### 1.1 问题（源自 CommStress 压测 S3）

压测 S3「1000 个点、步长 10 个寄存器」的实测结果：

```
默认组   1000 变量   1000 段   兜底 0   目标 1000ms   实测 1084ms   达成率 92%   点/段 1.0   923 请求/s
```

**每个点各占一次往返**，923 请求/s 几乎把 1000ms 周期占满——周期已经到顶，无法再提频。

### 1.2 根因：空档阈值只看协议、不看传输

[PollBatchPlanner.cs](file:///e:/VM/VisionMaster-W-master/Communication/Communications/Manager/PollBatchPlanner.cs) 里三个常数：

```csharp
private const int GapUnitsS7 = 16;              // S7
private const int GapUnitsModbusRegister = 8;   // Modbus 寄存器区
private const int GapUnitsModbusBit = 64;       // Modbus 位区
```

合并判据 `tooFar = poll.Start - current.EndUnit > GapOf(poll)`。步长 10 意味着相邻点间隔 **9**，比寄存器区的 8 大 1 —— **每次合并刚成立就被打断**，于是贪心算法只能每点自成一段。

### 1.3 关键事实：合并算法本身不用动

`ApplyBytes` 只在 `item.UnitOffset` 处解码，**段内空档的字节自动被忽略**：

```csharp
int byteOffset = item.UnitOffset * bytesPerUnit;
int byteLength = item.SpanUnits * bytesPerUnit;
if (byteOffset < 0 || byteOffset + byteLength > data.Length) { MarkUncertain(); continue; }
```

也就是说"整段读回 + 本地裁剪"这个能力**代码里早就有**，缺的只是"允许跨多大空档"这一个阈值。**不需要新算法。**

### 1.4 核心约束：为什么阈值不能一刀切

同一个改动，在两种传输上结论**完全相反**：

| 传输 | 多读 1 个寄存器的代价 | 结论 |
| --- | --- | --- |
| 以太网（Modbus TCP / S7） | ≈ 0（119 个寄存器 = 238 字节） | 多读几乎免费，**应放开** |
| 串口 RTU @9600 | **2.29 ms**（2 字节 × 11 位 ÷ 9600） | 多读 118 个 ≈ 270ms，**比一次往返还贵两个数量级** |

串口侧估算：同样 1000 点这一轮，**8.0s（每点一段）→ 23.6s（按 120 放开）**，慢 3 倍。

而 [GapOf()](file:///e:/VM/VisionMaster-W-master/Communication/Communications/Manager/PollBatchPlanner.cs) 原来只看协议。**协议与传输是正交的两个维度**——同一个 Modbus 协议就同时有 TCP 和 RTU 两种传输，用协议枚举反推不出传输。

### 1.5 决策（2 项，已逐条与用户确认）

| 决策项 | 结论 |
| --- | --- |
| 方案 | **方案 A：传输类型分档**——以太网档放开、串口档保留原常数（未采用"加密度闸门"或"只调大常数"） |
| 范围 | **三个区统一放开**（Modbus 寄存器区 / Modbus 位区 / S7），规则统一：以太网档取该区的单请求上限 |

统一规则后的阈值：

| 传输 | Modbus 寄存器区 | Modbus 位区 | S7 |
| --- | --- | --- | --- |
| 以太网 | 120 | 2000 | 110 |
| 串口 | 8 | 64 | 16（未改动） |

以太网档"阈值 = 单请求上限"等价于**不限空档**，段大小完全由 `MaxSegmentUnits` 决定。最坏白读 = 上限 − 1 个单元（寄存器区 119 个 = 238 字节 / S7 109 字节 / 位区 1999 点 = 250 字节），在 TCP 上都是零头。

### 1.6 备选方案与不采纳的理由

| 方案 | 不采纳理由 |
| --- | --- |
| **方案 B：A + 密度闸门**（段内有效点占比过低就不合） | 多一个要调的阈值参数；本例步长 10 的密度 12/120 = 10%，闸门拦不下来，收益与 A 相同 |
| **方案 C：只调大 `GapUnitsModbusRegister`**（一行、不区分传输） | 串口 @9600 上整轮从约 8s 劣化到约 24s；且规则变成"分区不同政策"，难解释 |
| 把 `MaxSegmentUnits` 从 120 提到 125 | 已贴协议上限（FC03 是 125）；只能把 84 段降到 77 段（−8%），却要冒"部分 PLC 只认 120"的兼容风险 |
| 空档阈值改成按波特率计算（`RTT ÷ 单元线时`） | 理论最优，但本次**无串口实测数据**支撑，属过度设计；`SerialConfig.BaudRate` 已可用，留作后续 |

### 1.7 ★ 一个刻意的接口选择：必填参数，不给默认值

`PollBatchPlanner.Build` 新增的 `transport` 参数**刻意不给默认值**：

```csharp
public static PollBatchPlanner Build(
    IEnumerable<CommunicationVariable> variables,
    PollTransportKind transport,   // ← 必填
    Action<string>? log = null)
```

若给默认值（比如默认串口档），调用方忘了传就会**静默退回旧行为、编译期毫无提示**——这正是本会话修掉的 `CommunicationConfig(name, config)` 构造器缺陷的同一类坑（默认值把传入配置悄悄顶掉）。必填能让编译器替我们盯住每个调用点。当前共 3 个调用点，全部已显式表态。

### 2.1 核心代码

**`PollTransportKind`（PollAddress.cs）**：

```csharp
/// <summary>
/// 轮询地址所在的传输家族。与 <see cref="PollProtocol"/> 是<b>正交</b>的两个维度：
/// 协议决定"怎么编址"，传输决定"多读一个单元要花多少代价"。
/// </summary>
public enum PollTransportKind
{
    /// <summary>以太网（TCP）：空档代价可忽略，按单请求上限放开合并</summary>
    Ethernet,

    /// <summary>串口（RTU/ASCII 等）：空档要花真实线时，按保守常数合并</summary>
    Serial
}
```

**`GapOf`（PollBatchPlanner.cs）**：

```csharp
private static int GapOf(PollAddress poll, PollTransportKind transport)
{
    if (transport == PollTransportKind.Ethernet) return poll.MaxSegmentUnits;

    if (poll.Protocol == PollProtocol.S7) return GapUnitsS7;
    return poll.IsBitArea ? GapUnitsModbusBit : GapUnitsModbusRegister;
}
```

**`ResolveTransport`（PollScheduler.cs）**：

```csharp
private static PollTransportKind ResolveTransport(CommunicationConfig? config)
    => config?.Config is EthernetConfigBase ? PollTransportKind.Ethernet : PollTransportKind.Serial;
```

判据取配置类的**继承关系**（`EthernetConfigBase` / `SerialConfig`），不用协议枚举——`ModbusTcp` 与 `ModbusRtu` 是同一协议、不同传输，协议名分不出来。配置缺失时取保守档 `Serial`（该路径本就是"安全兜底"，退保守档只是少合并、不会读错数据）。

### 2.2 ★ 连带影响：C12-0 断言地址必须改

[CommChecks/Program.cs](file:///e:/VM/VisionMaster-W-master/CommChecks/Program.cs#L919-L921) 的 C12-0 用"两个地址相隔 **100** 个寄存器"来保证"拆成 2 段、可分别注入失败"：

```csharp
var goodVar = MakeVar("GOOD", "", 0);
var badVar = MakeVar("BAD", "", 200);   // 原为 100
```

100 < 120，放开阈值后会被**并成 1 段**，C12 整组"可分别注入失败"的前提就塌了。改为 200（间隔 199 > 120）。

> 这说明**阈值不是一个可以随便调的局部常数**——它被测试依赖着，调它等于动契约。

## 四、已知边界

1. **收益窗口是"中等稀疏"，不是"所有稀疏"**：步长 ≤ 9 的点表**本来就已经合并**（旧阈值 8 即可覆盖），改了没变化；步长 ≥ 120 一段连 2 个点都装不下（需 `s ≤ 119`），改了也没用。**主战场是步长 10 ~ 119 个寄存器。**
2. **单请求上限是硬下限**：Modbus 寄存器区 120（协议上限 125）→ 任何点表每轮**至少** `ceil(跨度/120)` 次请求。1000 点 / 步长 10 的 84 段已是该点表的下限，不可能再低。
3. **★ 故障隔离粒度变粗**：段内任一地址非法 → PLC 拒绝整个请求 → **整段变量全部变 Uncertain**。原 1 点/段只影响 1 个变量，现 12 点/段会一起变黄（"我只配错一个点，怎么 12 个都黄了"）。已有的坏段告警（连续 3 轮 + 不节流通知）能帮助定位，但**不能阻止邻居变黄**。这是本次改动付出的主要代价。
4. **串口档一字未改**：`SerialConfig` 走的是原三个常数，行为与修复前完全一致（C15-2 已钉住）。**没有**按波特率细分——`SerialConfig.BaudRate` 已可用于将来做"阈值 = 往返代价 ÷ 单元线时"，本次未做（无串口实测数据支撑）。
5. **`MaxSegmentUnits` 未动**：Modbus 寄存器区仍 120、位区 2000、S7 110。
6. **位区 2000 点/请求 = 250 字节**：部分 PLC / 网关对大量线圈读有隐性限制，**本次未在真机验证**；S3 只覆盖了 Modbus 寄存器区，位区与 S7 的放开是"按同一规则推导"，缺真机数据。
7. **配置缺失时退保守档**：`ResolveTransport` 在 `config` 为 null 或 `Config` 未建时返回 `Serial`。这是安全侧选择（少合并），但意味着这种路径上拿不到 S3 的收益。
8. **全量构建未复验全绿**：2 个 `MSB3073` 由运行中的 VisionMaster.exe 锁文件引起，需关闭应用后重跑一次 `dotnet build VisionMaster.sln`。

## 五、经验沉淀（供后人避坑）

1. **协议与传输是正交维度**：批量合并的"空档代价"取决于**传输**，不是协议。判传输用配置类继承关系（`EthernetConfigBase` / `SerialConfig`），不能用协议枚举反推。
2. **改阈值等于改契约**：`GapUnitsModbusRegister` 看着是个局部常数，实际被 C12-0 断言依赖着。放宽前先搜断言。
3. **必填参数 > 带默认值的可选参数**：默认值会让"忘了传"静默退回旧行为，编译期毫无提示——这正是本会话修掉的构造器缺陷的同一类坑。
4. **放开之前先想清"代价在哪一侧"**：以太网放开是纯赚（字节免费），串口放开是纯亏（线时要钱）。同一行代码在两个场景下结论相反时，说明它缺一个维度。
5. **不要顺手动 `MaxSegmentUnits`**：它贴着协议上限，收益小（84→77 段）而兼容风险实。
