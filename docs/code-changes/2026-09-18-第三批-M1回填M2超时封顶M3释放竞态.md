目标：为对接商业 SCADA 的长期稳定运行消除"静默失联 / 线程永久挂起 / 释放竞态"三类隐患

## 1. 需求与决策

用户指令："开始吧 把地基打牢 这个通信系统 是为了对接后面商业的 Scada 软件采集" + "继续"。按排查文档第三批（防御加固）实施 M1/M2/M3。

| 项 | 问题 | 决策 |
|---|---|---|
| M1 | `UpdateConnection` = Remove + Add。Remove 已把变量注册记录连同连接对象一起销毁；若 Add 抛异常（配置非法/工厂创建失败），`keepVariables` 的恢复循环执行不到 → 这批变量**静默停止轮询且无任何提示**，直到下次 RebindAll 才恢复 | Add 失败（抛异常或返回 false）时**先回填注册记录再上抛/返回**；回填走 `RegisterVariable` 而非直接写字典 |
| M2 | `ConnectionWorker.Connect(int timeoutMs = -1)` → `WaitStateAsync` 的 `deadline = long.MaxValue`；设备永久离线 + 无限重连时 Task 永不完成，**同步 `.GetAwaiter().GetResult()` 的调用线程永久挂起** | 默认参数改 `DefaultConnectTimeoutMs = 30000`；负数（含 -1）一律按 `MaxConnectWaitMs = 300_000`（5 分钟）封顶 |
| M3 | Worker `Dispose` 的 `Join(3000)` 超时后仍继续 `_connection.Dispose()` / `_queue.Dispose()` / `_cts.Dispose()`——后台线程多因卡在建连长 IO 仍在跑，随后操作已释放对象（socket 层竞态、`TryTake` 抛 `ObjectDisposedException`） | Join 超时分支**一律不释放** `_connection/_queue/_cts`；置 `_disposeConnectionOnExit` 由 Worker 线程在 `Loop` 末尾"谁使用谁释放" |

### M1 关键设计

- **注册表与连接对象解耦**：`_registeredVariables` 只是"该连接应轮询哪些变量"的登记表。回填后即使当前无连接/无工作线程也安全——`RegisterVariable` 内的 `RequestPollPlanRebuild` 找不到 Worker 时静默跳过（H1 后是标脏，无 Worker 则无操作），待重新添加同名连接即可继续参与轮询。
- **回填走 `RegisterVariable` 而非直接写字典**：`RemoveConnection` 在 H3 修复后会退订转发 handler，直接写字典会留下"有变量、无 handler"的不一致状态；走 `RegisterVariable` 会重建 handler 并标脏，往返自洽。
- **异常传播保持原状**：改动前 `AddConnection` 失败同样是抛异常（其 `catch` 分支是 `throw;`，返回 false 实际不可达），因此"回填 + 上抛"不引入新的崩溃路径，只是补上了回填。

### M2 关键设计

- 只影响"本次调用能否拿到成功结果"，**不改变后台重连意图**：超时返回 false 后 Worker 仍按指数退避继续重连（`Connect` 调用方 `AdvancedCommunicationManager.Connect` 已有 `LogWarning("连接未在 Xms 内建立…后台按退避继续重连")` 分支，语义天然吻合）。
- 调用点核实：全工程 `worker.Connect` 仅 1 处（`AdvancedCommunicationManager.Connect`），且始终传有限超时（`config.Config.TimeoutMs` 或 3000），改默认值不影响既有行为。

### M3 关键设计

- **正常路径完全不变**：Join 成功 → 仍由主线程释放连接对象（既有稳定路径零改动）。
- **仅异常路径改变**：Join 超时 → 主线程跳过全部释放，由 Worker 线程在 `Loop` 退出前释放连接对象。此刻该线程已不再触碰连接对象，释放安全且不会与主线程重复释放。
- **队列/CTS 不释放是刻意的**：`_queue` 已 `CompleteAdding`、`_disposed` 已置位，`Invoke` 侧被 `ThrowIfDisposed` 拦截不会再有新命令；线程 `ReleasePendingItems` 会清空残留条目（`OnAbandon` → `tcs.TrySetCanceled()`），调用方 Task 不会悬挂。

## 2. 修改文件清单

### `Communication/Communications/Manager/ConnectionWorker.cs`
- 新增字段 `volatile bool _disposeConnectionOnExit`（M3）
- 新增常量 `public const int DefaultConnectTimeoutMs = 30000` / `private const int MaxConnectWaitMs = 300_000`（M2）
- `Connect`：默认参数 `-1` → `DefaultConnectTimeoutMs`（M2）
- `WaitStateAsync`：负数一律封顶为 `MaxConnectWaitMs`，不再产生 `long.MaxValue` 的 deadline（M2）
- `Loop`：退出前（`ReleasePendingItems` 之后）按 `_disposeConnectionOnExit` 释放连接对象（M3）
- `Dispose`：Join 超时分支提前返回，不释放 `_connection/_queue/_cts`，改为置 `_disposeConnectionOnExit`（M3）

### `Communication/Communications/Manager/AdvancedCommunicationManager.cs`
- `UpdateConnection`：Add 包 try/catch；异常路径回填后 rethrow；成功/失败路径统一走 `RestoreVariables` 回填；返回值改用 `AddConnection` 的真实结果
- 新增私有方法 `RestoreVariables(connectionName, variables)`：逐个 `RegisterVariable` 并 try 兜底（M1）

## 4. 已知边界

1. **M3 残留极窄竞态**：`Join(3000)` 超时返回后、主线程置 `_disposeConnectionOnExit = true` 之前的微秒级窗口内，Worker 线程若恰好退出，会读到 `false` 而跳过释放 → 连接对象改由 GC/终结器回收（socket 可能延迟关闭）。窗口极小、后果良性，未再加锁（加锁会把异常路径也串行化，得不偿失）。
2. **M3 超时分支不释放 `_queue`/`_cts`**：属刻意的资源让渡，无句柄泄漏（`BlockingCollection` 与 `CancellationTokenSource` 均无必须显式释放的非托管资源，终结器兜底）。
3. **M1 的异常最终仍会向上抛到 UI**：`CommunicationSettingsViewModel` L288 调用 `UpdateConnection` 时**未包 try/catch**，且工程内未注册 `DispatcherUnhandledException` 全局兜底 → 配置非法时可能以未处理异常形式中断。这是**改动前就存在的行为**（`AddConnection` 原本就 `throw`），本批只补齐回填、未扩大范围。建议后续单独一项：在 ViewModel 侧捕获并 `Notifier.ShowError` 提示。
4. **M1 回填后无连接时的可见性**：变量登记保留但 UI 连接列表已无该连接 → 变量管理界面可能显示"来源连接不存在"。属预期（登记表与连接解耦），重新添加同名连接即恢复。
5. **全量编译仍受外部阻塞**：`Shard/Core.Controls/Editing/`（另一任务）缺 AvalonEdit 引用；本批改动全部位于 VM.Communication 工程，已独立编译验证。
