# 2026-09-24 串口（Modbus RTU）字节序可配置化（读写两侧同源）

## 一、需求

> 用户原话：「先帮我修复串口读写不对称的问题」

这是 [2026-09-24-Modbus字节序可配置化.md](file:///e:/VM/VisionMaster-W-master/docs/code-changes/2026-09-24-Modbus字节序可配置化.md) 的**直接续作**——那份记录「已知边界 2」原文：

> `SerialConnection`（Modbus RTU）同样存在读写不对称，本次未修（其 HSL `ModbusRtu` 默认 `ByteTransform = CDAB`，读侧为 ABCD），待 `SerialConfig` 补字序字段后统一。

**不对称的精确机制**（与 Modbus TCP 修复前完全同类）：

- **写侧**：[SerialConnection.Write](file:///e:/VM/VisionMaster-W-master/Communication/Communications/Connection/SerialConnection.cs#L109) → `HslHelper.WriteTyped` → HSL `Write(addr, int/float/…)` → 设备 `ByteTransform.TransByte`。而 `ModbusRtu()` 构造函数里**写死** `base.ByteTransform = new RegularByteTransform(DataFormat.CDAB)`（[ModbusRtu.cs#L110](file:///e:/VM/VisionMaster-W-master/DLL/HslCommunication/ModBus/ModbusRtu.cs#L110)）。
- **读侧**：[SerialConnection.Read\<T\>](file:///e:/VM/VisionMaster-W-master/Communication/Communications/Connection/SerialConnection.cs#L98) → `_device.Read(address, RegisterCount<T>())` 拿原始 wire bytes → `HslHelper.ConvertTo<T>(content, ABCD)`（**硬编码 ABCD**）。

于是 32/64 位「写进去、读不回来」：写 `int 0x12345678` → 写侧 CDAB 上线 `56 78 12 34` → 读侧 ABCD 解出 `0x56781234` ✗。
16 位因 HSL `ByteTransDataFormat2` 把 ABCD/CDAB 归同一分支（退化等价）而无感，所以这个坑一直藏得住。

## 二、决策（逐条与用户确认，一次一问）

| # | 问题 | 用户决策 | 影响 |
|---|---|---|---|
| Q1 | 改动范围 | **方案 A：加 `ByteOrder` 字段** | `SerialConfig` 新增字序字段，读写两侧同源跟随 |
| Q2 | 默认值 | **默认 ABCD** | 与 TCP 的 CDAB 不同：串口读侧历史行为就是 ABCD，取它可让软件内可见读数**零变化**，只把写侧拉齐 |
| Q3 | 测试 | **方案 A：补一组断言** | CommChecks 新增 C10 组（5 条），离线可跑、不接硬件 |

### 为什么默认值取 ABCD（与 ModbusTcp 的 CDAB 不同）

- 串口**读侧**（用户实际看得到的那一侧）历史行为一直是 ABCD。默认取 ABCD ⇒ 存量连接的读数**一个都不变**，只把「写侧永远 CDAB」拉齐到 ABCD，扰动最小。
- 现场证据：`communications.json`（根目录与 `bin\Debug\net9.0-windows\` 两处）**均无 SerialConfig 条目**，即不存在会被默认值改变的存量串口连接——但即便有，取 ABCD 也仍是「可见读数不变」的保守选择。
- 16 位及以下 ABCD 与 CDAB 退化等价，故只有 32/64 位变量受这个下拉影响。

| 项 | 结果 |
|---|---|
| `VisionMaster.sln` 编译 | **exit code 0**（仅既有 CS86xx 可空性警告） |
| `CommTest.csproj` 编译 | **exit code 0** |
| CommChecks 回归 | **82 通过 / 0 失败**（新增 C10-1 ~ C10-5 全绿） |

| CommTest `[H]` 字节序断言 | **19 通过 / 2 失败**（2 条为 `Connect(Modbus 502)` / `Connect(S7 108)`「连接失败——检查模拟器」，环境问题，与本次改动无关） |

C10 断言明细：

| 断言 | 校验点 | 实测 |
|---|---|---|
| C10-1 | 默认值 ABCD（读侧历史行为，保存量读数不变） | 默认值 ABCD |
| C10-2 | `Clone()` 带上字序（漏拷 = 克隆一份配置就丢设置） | 克隆后 CDAB |
| C10-3 | 连接的字序跟随配置（写死常量 = 配置摆着看） | 连接读出 CDAB |
| C10-4 | 配 CDAB 时写侧 `DataFormat` 是 CDAB（HSL 默认值，证明没被改坏） | 设备实际 CDAB |
| C10-5 | **配 ABCD 时写侧确实改成 ABCD**（只测 CDAB 测不出「根本没下发」） | 设备实际 ABCD |

> C10-5 是关键一条：HSL 的 `ModbusRtu` 默认恰好就是 CDAB，所以只测 CDAB 无法区分「真的下发了」与「压根没下发」。只有配 ABCD 并断言设备变成 ABCD，才能证明下发真的生效。
>
> 实现细节：CommChecks **无 `InternalsVisibleTo`**，不能引用 `HslHelper`（internal）与 HSL 命名空间，故 C10 全程走**反射 + `ToString()` 比较**（`GetDevice` → `ByteTransform` 属性 → `DataFormat` 属性 → `ToString()`）；又因两套枚举（本项目 `ByteOrderFormat` 与 HSL `DataFormat`）成员顺序不同，比**名字**才安全。

## 五、已知边界

1. **串口 32/64 位读写不对称已消除**：写侧 `ByteTransform` 与读侧 `ConvertTo` 现在同源跟随 `SerialConfig.ByteOrder`。
2. **串口默认 ABCD，Modbus TCP 默认 CDAB——两者刻意不同**：串口取 ABCD 是为了让「读侧可见读数」零变化（读侧历史行为即 ABCD）；TCP 那份是用户在上一任务里按现场设备判断选的 CDAB。同一个软件里两个协议默认值不一致，是各自历史行为 + 现场判断的结果，不是笔误。
3. **16 位及以下不受影响**：ABCD 与 CDAB 在 HSL `ByteTransDataFormat2` 里退化等价，只有 32/64 位变量才受该下拉影响。
4. **改字序需重连才生效**：`ByteTransform` 在构造时下发，改配置后要重连该串口连接（与其他连接参数的既有行为一致）。
5. **`ReadBytes` / `WriteBytes` 不走字序**：原始字节接口本就按调用方自己的口径解析，字序只作用于 `Read<T>`（读链路）与 HSL 强类型 `Write`（写链路），符合「原始字节由调用方负责」的既有约定。
6. 未做「字节序变更时自动重连/重下发」。
