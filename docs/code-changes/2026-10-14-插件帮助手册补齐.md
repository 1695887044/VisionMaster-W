# 插件自带帮助手册补齐（2026-10-14）

> 一句话：把"插件有没有帮助手册"从**没人管**变成**闸门守**——42 个工具箱条目全部自带手册（77 页 / 10088 行），宿主按插件类型分册取页，`FlowCanvasChecks\HelpManualCheck.cs`（HM0~HM11）进 gate 基线，`dotnet run --project FlowCanvasChecks` = **2418 通过 / 0 失败**。

---

## 一、需求与普查口径

**用户原话**："阅读其它插件加载进主框架的帮助手册，看下他们怎么写的，把没有帮助手册的补齐，**要特别详细的**。"

"要特别详细"这句决定了后面两个取舍：① 闸门里那条"每册 ≥70 行"（HM8）不是拍脑袋的数字，是把"特别详细"变成可判据；② 首轮 HM8 把三份历史手册判红时，处理方向是**把旧页补厚**，而不是下调阈值。

### 普查怎么做的（可复算）

| 项 | 口径 |
| --- | --- |
| 什么算"一个需要手册的东西" | **工具箱条目 = 带 `[Display(GroupName = "…")]` 的插件类**。枚举上也挂 `[Display]`，但只有 `Name`、没有 `GroupName`，所以取 `GroupName` 当判据 |
| 条目从哪几张表来 | 宿主 `HelpCatalogService` 合并**四张表**成一棵树：`ModulePlugins`（流程算子）+ `CameraPlugins` + `LaserPlugins` + `MotionPlugins`。所以**相机驱动 / 运动卡也算工具箱条目**，它们没有流程步骤身份，但有配置界面、也进帮助树 |
| 什么算"有手册" | 工程 `Help\` 目录下存在 `.md`（并最终被 `<EmbeddedResource>` 打进 DLL） |
| 普查结果 | **31 个程序集 / 42 个插件类**；`Plugin.Utility` 一个程序集 6 个条目、`Plugin.Motion.Steps` 7 个，其余 29 个程序集各 1 个 |
| 补齐前 | 只有 **5 个程序集**自带手册 → **26 个程序集没有**，界面上走第三层兜底（`[Display]` 元数据 + 注册期端口表自动生成一页，页脚"自动生成"徽标），现场看到的就是一张干巴巴的端口清单 |
| 补齐后 | 42 个条目**全部**自带手册：**77 页 / 10088 行**，台账见 §十 |

台账本身用一份一次性脚本现算（按"插件类名 → `Help\{类名}\`，单插件程序集 → 扁平 `Help\`"这条与宿主一致的取页规则统计页数行数），数字与 `find Plugins/Plugin.*/Help -name '*.md' | wc -l` = 77、总行数 = 10088 双向对得上。

## 二、帮助手册是怎么加载进主框架的（三层契约）

代码在 `VisionMaster\Services\Help\HelpCatalogService.cs`。

| 层 | 来源 | 触发条件 | 本轮用了哪层 |
| --- | --- | --- | --- |
| ① | **程序集内嵌资源**，前缀 `{程序集名}.Help.` | 工程 `Help\` 下有 `.md` 且 csproj 挂 `<EmbeddedResource Include="Help\**\*" />` | **全部走这层**（零配置，加文件即可） |
| ② | `IPluginHelpProvider.GetHelpSections()` | 插件自己实现接口 | 一个都没用（理由见 §三） |
| ③ | 自动生成页（`[Display]` + 注册期端口表） | ①② 都没有 | 补齐后 42 个条目全部**不再**落到这层 |

第①层内部这几条规则，**每一条都是静默的**（写错不报错，只是效果不对）：

1. **发现**：`assembly.GetManifestResourceNames()` 里以 `{程序集名}.Help.` 开头、`.md` 结尾的资源各成一页（`CollectEmbeddedPages`，源码注释第 285-286 行就写着这条约定）。
2. **页序** = 资源名的 **Ordinal 排序**（`.OrderBy(n => n, StringComparer.Ordinal)`）→ 文件名必须 `NN-` 前缀；`1-` 和 `10-` 会排错，`01-`/`02-` 才对。
3. **页标题** = `ExtractTitle()` 取**正文第一个 `# ` 一级标题**：`Trim` 后以 `# ` 开头的行才算，开头允许空行与 `<!--` 注释，**但正文一旦开始就不再往下找**；一个都没找到就**回退用文件名**——于是界面上会出现一个叫 `01-overview` 的页（静默劣化）。
4. **图片**：非 `.md` 的 `Help.` 资源进图片解析表，键是去掉前缀后的相对路径（`{程序集名}.Help.images.xxx.png` ← 正文里写 `images/xxx.png`）。
5. **树的结构**：按 `[Display] GroupName` 分组建分类节点，**分类顺序由白名单 `CategoryOrder` 决定**（"常用工具、图像处理、缺陷检测、测量、定位、标定…"），表外的分类按中文排序排在后面；分类**内的条目按标题 `zh-CN` 排序**（`NameComparer`），与文件名无关。

> 顺带一条口径：兜底自动页**故意不生成参数表**（源码注释："参数以插件自己的配置界面为准，抄一份到手册里必然漂移"）。所以我们写的手册里那张"关键参数"表必须自带那句"界面为准"的免责行（见 §四）。

## 三、本轮唯一的机制改动：一个程序集里有多个插件时按类型分册

### 问题

①的前缀是**程序集级**的。`Plugin.Utility`（6 个条目）与 `Plugin.Motion.Steps`（7 个条目）挤在一个 DLL 里，如果各插件的手册都平铺在 `Help\`，宿主只能按程序集名收窄 → 这 **13 个条目在界面上显示同一批页面**（看"数学计算"的手册，里面挂着"变量赋值"的内容）。这不是假设：`Plugin.Utility` 里 6 个条目只要放扁平页就必然串页。

### 两条出路，选了哪条

| 方案 | 代价 | 结论 |
| --- | --- | --- |
| 让这 13 个类各自实现 `IPluginHelpProvider.GetHelpSections()`（②） | 13 处代码 + 手册内容从 md 文件搬进 C# 字符串（改手册=改代码=重编，且中文长串进源码） | 否 |
| **宿主按插件类型收窄**，手册仍放文件 | 宿主约 20 行、**向后兼容**（既有 5 份手册一个字不改） | **采用** |

### 改法

`CollectEmbeddedPages(Assembly assembly, string source, Type? owner = null)`（`CollectPluginPages` 调用处改成把 `type` 传进去），拿到资源名列表后先收窄：

```csharp
private static List<string> NarrowToPlugin(List<string> names, Assembly assembly, string prefix, Type owner)
{
    var ownPrefix = prefix + owner.Name + ".";
    var own = names.Where(n => n.StartsWith(ownPrefix, StringComparison.OrdinalIgnoreCase)).ToList();
    if (own.Count > 0) return own;                       // 有本插件的分册 → 只给自己的
    var typeNames = new HashSet<string>(
        assembly.GetTypes().Select(t => t.Name), StringComparer.OrdinalIgnoreCase);
    return names.Where(n => !typeNames.Contains(n.Substring(prefix.Length).Split('.')[0])).ToList();
}
```

由此得到**约定**（AGENTS.md R41 第②条）：

- 多插件程序集：各插件的页放 **`Help\{插件类名}\`**，目录名**逐字等于 C# 类名**。
  例：`Plugins\Plugin.Utility\Help\MathCalculationPlugin\01-overview.md`。
- 单插件程序集：继续放扁平 `Help\`（回退分支：排除掉"落在某个类型目录下"的页之后就是扁平页）。
- **为什么是类名而不是显示名**：显示名是给人看的、会改（本轮就遇到"创建ROI"的工具箱实名其实是「ROI」）；类名才是身份，且收窄是按 `Type.Name` 精确匹配的。
- 图片解析表仍按 `{asm}.Help.` **全树**建键，所以分册不影响取图。
- 同步把这条约定写进 `Shard\Core.Interfaces\IPluginHelpProvider.cs` 的三层列表文档注释（①那条）。⚠ 动 `Core.Interfaces` 会让全解决方案重编——本轮确实全量重编了。

实测产物（`Modules\Plugin.Util.dll` 里的资源名，正是收窄要吃的前缀）：

```
Plugin.Util.Help.MathCalculationPlugin.01-overview.md
Plugin.Util.Help.ComparisonPlugin.01-overview.md
Plugin.Util.Help.VariableAssignmentPlugin.01-overview.md
Plugin.Util.Help.VariableAssignmentPlugin.02-名字与值.md
…（共 7 个，与 6 个条目的 7 页对账相等）
```

## 四、房屋风格：一页手册长什么样

范式来源（本轮之前唯一的两份）：`Plugin.ResultDisplay\Help\01-overview.md`、`Plugin.BeadInspect\Help\01~02`。分节顺序**固定**：

1. `# 中文名` —— 与工具箱显示名逐字一致（从源码 `[Display(Name = …)]` 抄）。
2. `> 分类：X ｜ 来源：插件 Plugin.Y` —— 分类抄 `[Display]` 的 `GroupName`。
3. 一段话定位（做什么、**不做什么**）。
4. **为什么需要它 / 原理**（现场工程师要的是判据，不是术语）。
5. 输入端口表 `| 端口 | 必填 | 说明 |` / 输出端口表。
6. **关键参数**——表格前逐字一行：
   `> 完整参数与取值范围以流程中该步骤的「模块参数」界面为准，这里只解释含义。`
   然后每个参数写"默认值 + 调大/调小分别会怎样"。
7. **现场现象 → 先查什么**（症状表；本轮最长一张 14 行）。
8. 口径与失败策略（找不到算不算失败、坐标系、单位、角度归一化范围、轮首归零）。
9. 典型用法 / 接线（ASCII `──▶` 图，端口名用真名）。
10. 常见问题 Q&A。

### 三条内容纪律

1. **事实来源只有源码**。端口名、默认值、取值范围、夹取规则、错误文案逐条对着 `.cs` 抄；派工指令里写死"源码里没有的端口要删掉或改正，**不许改源码**"。
2. **厂商码必须写明是谁的码**。例：`HomeMode` 的 C# 值是 **0~7**，正运动 `homemode` 是 **1/2/17/18/19/23/27/37**（映射在 `Plugin.Motion.ZMotion\ZMotionModels.cs:72-79`）。手册那一列的表头写的是"正运动模式码"——写成"编码"就会被现场当成 C# 值去填。
3. **界面还没做到的事不许写成做到了**。R40 的 `[Display]` 欠账还在（`Plugin.Utility` 的运算枚举、`Plugin.PreProcessing\Models\OperatorEnums.cs` 等），下拉里就是英文成员名。这些插件的手册于是写成 Q&A「`Operation` 下拉里为什么是英文？」，**而不是**承诺"下拉是中文"。反过来，已经做到的要写实：「变量赋值」的作用域确实是中文下拉（`Plugin.Utility\VariableAssignmentView.xaml:66-67` 的 `ComboBoxItem Content="运行时变量" Tag="Runtime"`），手册就照这句写"界面用中文下拉，落盘是 `Runtime`/`Global` 两个英文串"。

## 八、抓到一条真隐患：增量构建会静默漏打包手册（→ AGENTS.md R42）

**现象**：`dotnet build VisionMaster.sln -m:1` 报 **0 错误**，csproj 里 `<EmbeddedResource Include="Help\**\*" />` 也在，但：

```
$ tr '\0' '\n' < Modules\Plugin.ImageAssign.dll | grep -a "Help"
（无输出）
```

对该工程单独 `--no-incremental` 之后，资源名 `Plugin.ImageAssign.Help.01-overview.md` 才出现。

**根因**：MSBuild 的增量判定没把"新挂上的内嵌资源项"当脏（与红线③"产物陈旧"、R16"改生成器必须重建插件"、R28"CodeGraph 不重建就静默少返回"是同一族坑）。**宿主加载不到手册不报错**，只会悄悄退回③自动生成页——所以"构建全绿"完全不等于"手册交付了"。

**判据（收尾必做，不能只看退出码）**：

```bash
tr '\0' '\n' < Modules\Plugin.X.dll | grep -a -c "\.Help\."   # 必须等于该工程 Help\ 下的 .md 数
```

**稳妥做法**：收尾那一次全量重建用 `--no-incremental`（或先 `dotnet clean`）。本轮已对 31 个插件工程逐个 `--no-incremental` 重建并全部对上账。

## 九、新增一页手册的操作清单（runbook）

1. 在插件工程 `Help\` 下加 `NN-名字.md`；**单插件程序集放扁平 `Help\`，多插件程序集必须放 `Help\{插件类名}\`**。
2. 文件**第一行内容**就是 `# 中文名`（= 工具箱显示名，去源码 `[Display(Name=…)]` 抄）；第二行 `> 分类：X ｜ 来源：插件 Plugin.Y`。
3. 按 §四 的分节顺序写；参数表前放那句"界面为准"的逐字行。
4. 端口名/默认值/取值范围/错误文案**逐条回源码**，别照抄旧稿。
5. csproj 确认有 `<EmbeddedResource Include="Help\**\*" />`（新工程要自己加，**没有全局 props 规则**）。
6. 重建该插件工程（红线③），并按 §八 的判据核对 DLL 真的带了资源。
7. `dotnet run --project FlowCanvasChecks` 跑 gate，HM0~HM11 必须全绿。
