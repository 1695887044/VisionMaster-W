# C1 + B3 修复：执行上下文能力面装配单点化

> 来源：`docs/code-changes/2026-10-24-流程引擎评审团交叉评审.md`（五路评审团报告）中的 C1 与 B3 两条 blocker。
> 实施日期：2026-10-24

## 一、问题（评审团指控 → 主会话复核结论）

| 编号 | 原文指控 | 复核结论 |
|---|---|---|
| C1 | 单次执行路径（`TryRunSessionOnceAsync`）漏注入 `Database`，插件在单次执行时永远拿到 `NullDatabaseAccess`，报"没有接入数据库服务" | 成立。`FlowEngineService` 里连续执行与单次执行各写一份对象初始化器，单次执行那份少五项里的 `Database` |
| B3 | 并行分支的 `ParallelBranchExecutionContext` 手写五项能力面赋值，全部回落空实现，分支内任何能力调用都报"未接入" | 成立。分支上下文构造器把五项都赋成 `NullXxxInstance`，与父上下文无关 |

两条同源：**能力面装配散落在三处（连续执行 / 单次执行 / 并行分支），各写一份清单，漏一项不报错。**

## 二、改法：一份清单 + 一个装配入口

### 1. `Core/ExecutionContext.cs`

新增三样东西（这是唯一的"清单事实源"）：

```csharp
public static readonly System.Reflection.PropertyInfo[] RuntimeCapabilities  // L144-151
public object?[] SnapshotCapabilities()                                      // L154-160
public static ExecutionContext Create(ILogService logService, FlowSession? session,
    IWorkspaceManager? workspace, CancellationToken token,
    ExecutionContextCapabilitySource source)                                 // L174-188
```

`RuntimeCapabilities` 恰好登记五项：`Cameras` / `Motions` / `FlowInvoker` / `Comms` / `Database`。

### 2. `Core/ExecutionContextCapabilitySource.cs`（新文件，89 行）

- `ExecutionContextCapabilitySource`：五个 `init` 属性，就是五项能力的来源。
- `internal object?[] ResolveCapabilities()`：按 `RuntimeCapabilities` 逐项 switch，**null 回落对应 `NullXxxInstance`，未知名字直接抛 `InvalidOperationException`**（文案写明"新增能力时必须同时改这两处"）。
- `internal static void CopyInto(ExecutionContext parent, ExecutionContext child)`：把父上下文五项逐项搬给子，父项为 null 直接抛。

### 3. `Engine/FlowEngineService.cs`

```csharp
private ExecutionContext CreateExecutionContext(FlowSession session, CancellationToken token)
    => ExecutionContext.Create(_logService, session, _workspaceManager, token,
        new ExecutionContextCapabilitySource { Cameras = _cameras, Motions = _motions,
            FlowInvoker = FlowInvoker, Comms = _comms, Database = _database });   // L215-224
```

连续执行与单次执行**两条路径共用这一个方法**，C1 的根因（两条路径各写一份）从结构上消失。

### 4. `Core/Models/Compileds/ParallelBranchExecutionContext.cs:133`

```csharp
: base(parent.Logger, parent.CurrentSession, parent.Workspace, branchToken)
{
    ExecutionContextCapabilitySource.CopyInto(parent, this);   // L133
}
```

删掉手写的五项赋值，B3 的根因（分支自己写一份清单）从结构上消失。

### 5. `Engine/PluginTestRunner.cs:100-112`

插件试运行同样改走 `ExecutionContext.Create` + `ExecutionContextCapabilitySource`。

## 三、新增断言：`FlowCanvasChecks/EngineContextWiringChecks.cs`（五段 W1~W5）

| 段 | 判据 | 结果 |
|---|---|---|
| W1 | 清单非空（≥5 项）/ 无重复 / 每项都是 `ExecutionContext` 上可写属性 / 每项默认值非空 / 恰好是五个名字 | 5 条全绿 |
| W2 | 第一方 727 个 `.cs` 里**没有手写能力面对象初始化器**；只有 `FlowEngineService.cs` 与 `PluginTestRunner.cs` 走 `ExecutionContext.Create` | 3 条全绿 |
| W3 | `PluginTestRunner.cs` 走 `Create` 且五项来源全传 | 3 条全绿 |
| W4 | **C1 反证**：单次执行跑完，插件体内拿到的 `Database` 就是宿主注入的那一份（`ReferenceEquals`），并按清单逐项比对其余四项；**反向对照**：不注入数据库时插件拿到 `NullDatabaseAccess` | 7 条全绿 |
| W5 | **B3 反证**：两条并行分支抓到的 `ParallelBranchExecutionContext` 五项能力面**全部与父上下文同一实例**；**反向对照**：分支号互不相同（确为逐分支派生） | 6 条全绿 |

W4/W5 用五个 `RecordingXxx` 桩（相机 / 运动 / 流程调用 / 通讯 / 数据库）做"宿主那份实例"，判据是**身份相等**而不是类型名——这样"回落成空实现"与"确实注入"才区分得开。

## 五、已知边界

1. **主工程 `VisionMaster.csproj` 未能重建**：用户当时开着 `VisionMaster.exe`（PID 38828，18:58 启动）与 VS（devenv PID 35964），`bin\Debug\net9.0-windows` 下 28 个 DLL 被锁，`MSB3021/MSB3027`。**库工程与断言宿主都已是最新**（`Core\bin\...\VM.Core.dll` 19:08:33 ≥ 源码 19:08:26），故 `Modules\` 产物未受影响、未触发红线③。等进程释放后重跑 `tools\run_gates.ps1` 即可收尾。
2. `VisionMaster.sln` 里有一条陈旧条目 `Demo\Demo.csproj`（该目录已删除），导致 `dotnet build VisionMaster.sln` 报 `MSB3202 未找到项目文件`。这与本次改动无关，属既有问题。
3. `RuntimeCapabilities` 用反射按名字寻址：**新增能力面属性必须同时登记进清单**，否则 `Create` 不会装它（漏装仍是"静默回落"）。这是有意留的唯一一处人工同步点，`ExecutionContextCapabilitySource.ResolveCapabilities` 的未知名字分支会抛异常兜住反方向。
