# 2026-09-22 扫描组诊断定时器异常兜底

> 上下文：承「弹窗 UI 青蓝风统一」的收尾排查。排查中发现「取消按钮未停表」的疑点，经查证**该疑点不成立**（停表已就位），
> 但顺着这条线查出了一个更危险的真问题：诊断定时器的 `Tick` 没有异常兜底。

---

## 1. 需求与决策

### 1.1 排查结论一：「取消」路径的停表**已经就位，无需修改**

排查起因：承前怀疑 `CancelCommand` 没有 `_statsTimer.Stop()`，取消后 1 秒节拍仍在空跑。

查证结果——两条退出路径都停了表：

| 路径 | 停表位置 | 说明 |
| --- | --- | --- |
| 点「确 定」 | [ScanGroupEditorViewModel.cs#L353](file:///e:/VM/VisionMaster-W-master/VisionMaster/ViewModels/DialogViewModels/ScanGroupEditorViewModel.cs#L350-L354) | 显式 `_statsTimer.Stop()` 后才 `RequestClose` |
| 点「取 消」 | [ScanGroupEditorViewModel.cs#L94-L97](file:///e:/VM/VisionMaster-W-master/VisionMaster/ViewModels/DialogViewModels/ScanGroupEditorViewModel.cs#L94-L97) | `OnDialogClosed()` 里 `_statsTimer.Stop()` |

**为什么「取消」写在 `OnDialogClosed` 而不是 `CancelCommand` 里**：`CancelCommand` 只做
`RequestClose.Invoke(ButtonResult.Cancel)`，而 Prism 的 `DialogService.ShowDialog`
（调用点见 [CommunicationSettingsViewModel.cs#L495](file:///e:/VM/VisionMaster-W-master/VisionMaster/ViewModels/DialogViewModels/CommunicationSettingsViewModel.cs#L495)）
在窗口 `Closed` 时统一回调 `OnDialogClosed`。所以写在 `OnDialogClosed` 能**一次覆盖三条路**：
取消 / 确定 / 「连接被别处删掉」时主动关窗；写进 `CancelCommand` 反而会漏掉后两条。
这也与同目录 `CommunicationSettingsViewModel.OnDialogClosed()` 退订 `ConnectionStateChanged` 的写法一致
（[CommunicationSettingsViewModel.cs#L241-L245](file:///e:/VM/VisionMaster-W-master/VisionMaster/ViewModels/DialogViewModels/CommunicationSettingsViewModel.cs#L241-L245)）。

**决策：不改。** 额外加一句 `_statsTimer.Stop()` 与现有逻辑完全等价，属冗余代码。

### 1.2 排查结论二（本次实际修改）：`Tick` 异常会把软件打崩

原实现把刷新方法直接挂给定时器：

```csharp
_statsTimer.Tick += (_, _) => RefreshStats();
```

`DispatcherTimer.Tick` 的异常**没有兜底**，会一路冒到 Dispatcher 上终止进程。也就是说：
「每秒瞄一眼诊断数据」这一件纯展示的事，一旦某次读取抛异常，代价是整个软件闪退。
这比「表没停」严重得多——表没停只是空跑，Tick 抛异常是直接崩。

**决策：给 Tick 加异常兜底。** 处置策略：

1. **停表** —— 避免每秒重复抛异常，也避免「错误提示 / 正常数据」每秒来回翻转导致界面闪烁；
2. **把原因写进 `StatsHint`** —— 该属性就是诊断区空态文案（[ScanGroupEditorViewModel.cs#L180](file:///e:/VM/VisionMaster-W-master/VisionMaster/ViewModels/DialogViewModels/ScanGroupEditorViewModel.cs#L180-L191)），用户看得见，不用去翻日志；
3. **不弹气泡** —— 若不停表、每秒失败一次还弹一次气泡，就是标准的日志风暴（承前 H2 已踩过同类坑）。

代价：失败后诊断区停在失败原因上，需关掉弹窗重开才能重试。这是有意的——异常本身说明存在真 bug，明确停下比每秒重试更容易被发现。

## 4. 已知边界

1. **兜底策略是「停表」而非「重试」**：瞬时异常（例如 `GetStats()` 恰逢调度器整体替换的那一拍）也会导致诊断停止刷新，需关掉弹窗重开。若实测发现瞬时异常偏多，可改为「不弹气泡 + 不 停表 + 只在文案变化时通知」的自愈策略。
2. **`RefreshStats` 内部的异常仍可能留下半更新状态**：若异常发生在 `Stats` 列表原位更新的中途（[L622-L632](file:///e:/VM/VisionMaster-W-master/VisionMaster/ViewModels/DialogViewModels/ScanGroupEditorViewModel.cs#L621-L632)），部分行是新值、部分是旧值。本次不处理——`HasLiveStats` 已被置 `false`，界面切到空态，不会让用户看着半截数据做判断。
3. **该兜底不覆盖其它弹窗**：`CommunicationSettingsViewModel` 等没有 1 秒节拍，无需同类处理；若后续新增定时刷新，应复用同一套「try/catch + 停表 + 写可见文案」范式。
4. **UI 行为无断言宿主**：`StatsHint` 文案是否真的显示在诊断区空态上，仍属 XAML 视觉行为，需实机点验。
