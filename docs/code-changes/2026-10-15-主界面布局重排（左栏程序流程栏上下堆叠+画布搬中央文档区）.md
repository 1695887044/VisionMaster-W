## 三、结构与停靠语义逐项

### 1. 左栏：并排两列 → 一列上下堆叠

旧结构（两列并排，各占一个 `LayoutAnchorablePane`）：

```
LayoutPanel(Horizontal)
├─ LayoutAnchorablePane DockWidth="13*"   ← 程序
│   └─ LayoutAnchorable "程序" (Panel_FlowListView)
└─ LayoutAnchorablePane DockWidth="17*"   ← 流程栏 + 画布（同 pane = 互斥标签页）
    ├─ LayoutAnchorable "流程栏" (Panel_ProcessView)
    └─ LayoutAnchorable "流程画布" (Panel_FlowCanvasView, CanHide=False)
```

新结构（一列竖向，两层 pane）：

```
LayoutPanel(Horizontal)
└─ LayoutPanel(Vertical, DockWidth="20*")          ← 左侧一列
    ├─ LayoutAnchorablePane DockHeight="180"       ← 程序（固定高度）
    │   └─ LayoutAnchorable "程序" (Panel_FlowListView)
    └─ LayoutAnchorablePane                        ← 流程栏（吃剩余高度）
        └─ LayoutAnchorable "流程栏" (Panel_ProcessView)
```

**为什么上下堆叠而不是各占一列**：程序列表只有几条流程、天然矮；流程栏是长树、天然高。并排两列会让"矮的那个"白占一整列高度；上下堆叠后两者共享同一列宽度，程序固定高度（够放几条流程 + 折叠按钮），流程栏吃掉剩余全部高度。

**为什么必须拆两个 `LayoutAnchorablePane` 再套竖向 `LayoutPanel`**：同一个 pane 里的多个 anchorable 是**互斥标签页**（同一时刻只见一个）——那是"二选一"；要"同时可见、上下分"必须拆 pane 再套竖向 `LayoutPanel`。这也是 §五断言 ⑤/⑥ 直接钉的结构。

### 2. 画布：左侧栏标签页 → 中央文档区文档

画布从「流程栏 pane 里的第二个 anchorable」改为「中央 `LayoutDocumentPane` 里的第三个 `LayoutDocument`」：

```
LayoutPanel(Vertical, DockWidth="70*")            ← 中央工作区
└─ LayoutDocumentPane
    ├─ LayoutDocument "视觉图像"   (Panel_ImageView,       IsSelected="True")
    ├─ LayoutDocument "流程画布"   (Panel_FlowCanvasView)          ← 搬来此处
    └─ LayoutDocument "组态画面"   (Panel_ScadaEditorView)
```

**为什么画布从左侧栏搬到这里**：它是节点编辑器的主工作区，面积需求与视觉图像同级；而原来跟流程栏挤在 `17*` 宽的同一列里做标签页——同一时刻只能看见一个，等于"要么看树、要么看画布"，两件事本来是要对照着做的。搬进文档区后可拖出成分屏对照着调。

**`IsSelected` 的落点**：视觉图像保留 `IsSelected="True"`（`:868`），**画布身上刻意不写 `IsSelected`**（防抢启动视角）——一个 pane 里有多个文档时，默认激活哪一个不保证是第一个；不写视觉图像那一行就可能让"组态画面"抢走启动时的前台标签。

### 3. 宽度与活动栏

- 左栏 `20*`（原两列合计 `30*`）；中央 `70*` 不变；右侧定宽 260 / 240 / 300 不变。
- 活动栏 5 个 `Toggle` 对应程序 / 流程栏 / 工具箱 / 图元工具箱 / 图层——**本来就没有画布按钮**（画布历来不是活动栏项），本轮无需增删。
- 菜单项「流程画布」仍在（`Shell.xaml:302-310`）。

## 四、关键技术决策（为什么）

### 1. 为什么拆两个 pane（而不是同 pane 两个 anchorable）

见 §三-1。这是本轮结构里**唯一"不拆就实现不了"**的点：同 pane 的 anchorable 互斥显示，要"同时可见、上下分"必须拆 pane + 套竖向 `LayoutPanel`。

### 2. 为什么画布进中央文档区（而不是留在左栏）

见 §三-2。画布与视觉图像是**要对照着用**的两个主工作区，同 pane 标签页 = 只能二选一。

### 3. 为什么必须升 `CurrentLayoutSchemaVersion`（本轮的核心机制点）

`LayoutHelper` 加载布局前走 `IsLayoutXmlUsable`（`:258-288`）两道闸：

1. **结构版本闸门**：`version < CurrentLayoutSchemaVersion` → 返回 false（`:266-272`）；
2. **覆盖度校验** `LayoutXmlCoversAllPanels`（`:240-249`）：逐个 `ContentFactories` 的 `ContentId` 做 `Contains` 检查。

**为什么这次覆盖度校验完全拦不住**：本轮三个面板（`Panel_FlowListView` / `Panel_ProcessView` / `Panel_FlowCanvasView`）的 **ContentId 一个没改**——只是"谁和谁同 pane / 谁在哪个 pane / anchorable 还是 document"变了。磁盘上那份 **v2** 的 `Layout.xml`（实测 `LayoutRoot LayoutSchemaVersion="2"`）里这三个 ContentId **全都在**，覆盖度校验照常放行 → `LoadFromString` 会把"画布还在左栏标签页里"的老排法**原样恢复回来** → 改造在老用户机器上**等于没发生**。

**闸门动作链**：

- `IsLayoutXmlUsable` 对 `version < 3` 返回 false → `LoadFromString`（`:201-205`）打印拒绝原因、**放弃本次恢复**（`return false`）→ `Shell.xaml` 声明的默认布局生效；
- 版本不符**只跳过恢复、不删用户的 `Layout.xml`**（`:200` 注释原文："那是旧结构下的现场记录，删了才是真丢数据"）；
- `Reset()`（`:293-327`）：过期出厂快照 `DefaultLayout.xml` 不可用 → `IsLayoutXmlUsable(snapshot)` 返回 false → 作废删除（`:314-318`）→ 下次启动 `CaptureDefaultLayoutSnapshot`（`:138-151`）按新布局重新捕获。

> **口径**：`CurrentLayoutSchemaVersion` 是 **ContentId 之外的结构指纹**——"面板归属 / 停靠语义一变就递增"，见 `LayoutHelper.cs:33-44` 注释。

### 4. 升级后老布局静默作废（用户可见后果，升级必读）

**所有已有安装的 `Layout.xml` / `DefaultLayout.xml`（实测磁盘上都是 `LayoutSchemaVersion="2"`）在升级后首次启动会被 v3 闸拒绝** → 用户自己拖出来的布局（属性 / 图层位置、浮动窗口、面板显隐）**静默作废**，退出时被新布局覆盖。

**这是机制的本意**（否则重排在老机器上等于没发生），但属"升级必读"级信息：用户会感觉"我的布局被重置了"，且 `Layout.xml` 并未被删（只是没被恢复）。UI 侧的「加载布局 / 恢复默认布局」菜单文案对此无提示（见 §七-6）。

### 5. `CriticalPanelContentIds` 对画布已成空转（注释改成真话）

`CriticalPanelContentIds`（`:395-399`）仍含 `Panel_FlowCanvasView` + `Panel_ProcessView`。但画布搬成 `LayoutDocument` 后：`CanHide` 恒 false（document 无"收起"语义）+ `CanClose="False"` → 结构上进不了 `Hidden`；而 `EnsureCriticalPanelsVisible`（`:405-416`）的判据是 `content is LayoutAnchorable anchorable && !anchorable.IsVisible`——对 document 型画布**恒不命中**（空转）。**条目保留**（覆盖"万一被用户拖成 anchorable 后又隐藏"的廉价双保险），注释已改写成真话（`:387-394`）。此条与 §七-4 的"画布能否被拖成 anchorable"互为前提：只有"能拖"时这条兜底才有实际意义。

## 五、守门断言（6 条）与变异反证

`UIThemeSmokeTest\Program.cs` 的 `RunShellLayoutChecks()`（`:1252-1325`），用 `XDocument` 静态判 `VisionMaster\Shell.xaml`（`:1263`），**判据只认"元素类型 + 谁是谁的父/兄弟"，不写死行号与空白**（改缩进 / 改注释不误伤）：

| # | 断言名 | 判据 |
| --- | --- | --- |
| ① | 流程画布是中央文档区的文档标签（不是左侧栏的标签页） | `canvas.Name.LocalName == "LayoutDocument"` 且其父 `== "LayoutDocumentPane"`（`:1283-1288`） |
| ② | 流程画布与视觉图像同处一个文档窗格 | `canvas.Parent` 与 `image.Parent` 是同一引用（`:1290-1292`） |
| ③ | 默认选中仍是视觉图像 | `image` 的 `IsSelected` 等于 `"True"`（`OrdinalIgnoreCase`，`:1294-1297`） |
| ④ | 默认选中唯一：画布身上不得有 `IsSelected` | `canvas.Attribute("IsSelected") == null`（`:1299-1301`） |
| ⑤ | 程序与流程栏是两个独立窗格（上下同时可见，不是二选一标签页） | 二者父引用不同，且两个父都是 `LayoutAnchorablePane`（`:1303-1308`） |
| ⑥ | 程序与流程栏同处左侧一列（竖向 `LayoutPanel` 上下堆叠） | 二者父的父是同一引用、类型 `LayoutPanel`、`Orientation == "Vertical"`（`:1310-1314`） |

**变异反证（已做）**：

- **①直接反证**：把左栏 `LayoutPanel Orientation="Vertical" DockWidth="20*"` 临时改成 `Horizontal` → 输出
  `[FAIL] 程序与流程栏同处左侧一列（竖向 LayoutPanel 上下堆叠）  共同祖先=LayoutPanel，Orientation=Horizontal` + `### Shell 布局结构：1 项失败`；已还原并复绿。
- **9 份变体逐条实测（评审）**：D1 画布改回 anchorable → ①红；D2 画布放另一个 `LayoutDocumentPane` → ②红；D3 去 `IsSelected` → ③红；D4 两栏合并回同一 pane → ⑤红；D5 `Vertical`→`Horizontal` → ⑥红；**D8 改缩进 / 插注释 → 不误伤**（判据不依赖空白）。

> **刻意未钉的东西**：左栏宽度 `20*` / 中央 `70*` / 程序 `DockHeight="180"` 这些**像素值没有断言保护**——避免正常调参被误判为回归（见 §七-1）。
