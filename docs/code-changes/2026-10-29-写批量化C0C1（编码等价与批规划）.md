## 二、已做

### 2.1 编码器：`HslHelper.EncodeForWire`（C0 的核心）

合并写走 `WriteBytes` 会绕过 HSL 的 `ByteTransform` 与窄类型提升，所以必须自己把值编成**线路字节**。
推导：`GetValueArray` 产出"逻辑大端序"V；解码侧 `V = T(wire)`，四种变换都是对合，故 `wire = T(V)`。

窄类型口径照抄 `WriteTyped`：

| 族 | `byte` / `sbyte` | 依据 |
|---|---|---|
| Modbus / 字编址（MC/FINS） | 提升为 1 个 16 位寄存器（2 字节） | 与 `WriteTyped` 的 `(ushort)` 提升一致 |
| S7 / EasyNet | 保持 1 字节 | 提升会多覆盖相邻字节 |

字符串与 `byte[]` 无端序语义，原样下发、绝不重排。

### 2.2 顺带修掉一个既有缺陷：`GetValueArray` 的 `ulong` 溢出

`GetValueArray` 原先没有 `long`/`ulong` 分支，兜底走 `Convert.ToInt64(value)`；
`0x99AABBCCDDEEFF11` 这类 `ulong > long.MaxValue` 的值会抛 `OverflowException`。

**这是 C0 断言当场抓出来的**（第一次跑 C33 直接崩宿主）。`WriteTyped` 有显式 `case ulong` 所以旧路径没暴露；
任何走兜底分支的调用都会中招。已补 `long`/`ulong` 两个分支。

### 2.3 批规划器：`WriteBatchPlanner`

纯计算（不碰 socket、不碰队列）：N 个写请求 → M 个段。

**只合并严格连续的同一区地址**（`prev.End == next.Start`）。空隙一律断开、绝不用本地镜像填充——
对方源码复核确认它填的是未初始化堆内存，等于往 PLC 写垃圾。

**四种情况不合并**（各自成段、走单值写，行为与今天逐字一致）：

| 情况 | 原因 |
|---|---|
| 没有结构化地址 | 无从判断连续性与槽位 |
| 位区 | 位写语义不同，走 `Write(addr, bool[])` |
| `SegmentAddressOverride` 非空 | U 区十六进制 / MC 八进制区，`Prefix+Start` 会打到别的地址 |
| 编码字节数 ≠ 地址跨度 | 窄类型提升口径不一致（如 EasyNet 的 `byte`：槽位 2 字节、编码 1 字节） |

### 2.4 批执行器：`AdvancedCommunicationManager.TryWriteBatch`

批 = **一个队列条目**（`InvokeWrite`），在连接专属线程上逐段执行：

| 行为 | 说明 |
|---|---|
| 失败即停 | 段失败后不再发后续段（已发出去的收不回），后续段标 `Attempted=false` |
| 链路短路 | 段失败后查 `ILinkHealthProbe.HasLinkFault`，为真则在结果里标 `StoppedByLinkFault` |
| 不抛异常 | 逐段 try/catch；队列层异常（队列满/已释放）落到逐项结果里 |
| 段粒度结果 | 设备只回"这一帧成功/失败"，故结果按段扇出到项 |
| 阻塞语义 | 等整批执行完（一次阻塞换掉 N 次阻塞） |

结果模型把 `Attempted` 与 `Success` 分开："没发出去"与"发了但失败"必须能区分。

## 三、C2/C7 接线：写批会话 + 步骤边界冲刷

### 3.1 为什么冲刷点是"步骤边界"

插件只写变量、不该关心什么时候发（无感要求），所以由执行器在步骤边界开/关会话。
按步骤切批而不是按轮询周期，是因为**步骤是流程里的顺序单位**：
步骤 1 写 D100、步骤 2 写 D101，各自在步骤末尾冲刷 → 两帧、两个 PLC 扫描，顺序与今天一致。
按周期攒批会把两步合进同一帧，PLC 同一扫描看到两者，步骤边界被抹平。

### 3.2 组件

| 组件 | 位置 | 职责 |
|---|---|---|
| `WriteBatchSession` | `Core\Binding\WriteBatchSession.cs` | `AsyncLocal` 作用域；记账；按连接分组冲刷；成功项才回填镜像 |
| `NetworkVariableModel` | `Core\Models\Variable\NetworkVariableModel.cs` | 会话内改"记账 + 返回 true（已受理）"，不再立即下发 |
| `CompiledPluginNode` | `Core\Models\Compileds\CompiledPluginNode.cs` | 包住 `ExternalPlugin.Execute(context)`：执行完冲刷，失败数进日志 |
| `ICommunicationManager.TryWriteBatch` | `Core\CommunicationContracts\ICommunicationManager.cs` | 契约层暴露批量入口 |

### 3.3 三条语义

1. **返回 true = 已受理，不是已到 PLC**。镜像（界面显示值）等冲刷成功才更新——
   否则界面会显示一个设备上并不存在的值。
2. **失败项不更新镜像**。镜像 = 设备真值；写失败就保持旧值 + 由步骤边界汇总报"N 笔未确认"。
3. **并行分支各自成批**。`AsyncLocal` 保证两条分支的写不串进同一帧。

## 四、C3/C5 与 RecipeService（本轮补齐）

### 4.1 C5 段间让路

`WriteBatchExecutor` 从 `TryWriteBatch` 里抽出来，只为**可测**：让路判据 `shouldYield` 与执行委托
`SegmentWriter` 都可注入。`ConnectionWorker` 新增 `HasUrgentPendingWork`（只读、无副作用），
执行器在**每段之前**问一次：

- 命中 → 停止，剩余段与其中项标 `Attempted=false`（"没发出去"与"发了失败"分开）
- 让路**不是故障**：`StoppedByLinkFault` 保持 false
- 段失败即停；若连接自证链路断开，剩余项原因是"链路已断开，本段未下发"

### 4.2 C3 "等待完成"勾选

`VariableAssignmentPlugin` 新增 `WaitForCompletion`（默认 **false**）：

| 勾选 | 行为 |
|---|---|
| 不勾（默认） | 会话由执行器在步骤边界冲刷；本步骤只保证"已受理"，失败由边界汇总 |
| 勾上 | 会话升级为**插队车道**（`InvokeUrgentWrite`），本步骤内等回执，未确认笔数直接判本步失败 |

**勾上仍然合并**（1 帧写 N 个值），只是排队位置提前——这是它跟"逐行单发"的关键区别。

`WriteBatchSession.Begin(urgent)` 支持嵌套升级：外层已开会话时，内层传 true 会把**同一实例**升级为插队。

### 4.3 写后读前冲刷

`WriteBatchSession.FlushCurrent()`，在 `GlobalVariableWriter.TryRead` 入口调用。
理由：会话内写完立刻读，读到的是旧镜像（对方源码复核也确认它没有屏蔽机制）——不补就是静默错值。

### 4.4 RecipeService

配方下发整批走会话（插队车道），**终检前显式冲刷**：终检读的是变量镜像，批没落地就永远是旧值。
未确认笔数 > 0 直接抛，配方按未完整下发处理（原有回滚链照旧）。

## 五、踩过的坑

- **`InternalsVisibleTo` 不重建依赖就不生效**：先用 `-p:BuildProjectReferences=false` 编 CommChecks，
  得到一串 `CS0122 WriteProtocolFamily 不可访问`——因为被引用的 `VM.Communication.dll` 还是旧版本，
  没带上新加的 `InternalsVisibleTo` 特性。**判据**：报"internal 类型不可访问"但源码里已经加了
  `InternalsVisibleTo` → 先重建被引用工程，再编宿主。
- **`ulong` 走 `Convert.ToInt64` 会溢出**：`GetValueArray` 的兜底分支对 `ulong > long.MaxValue` 抛
  `OverflowException`，整条写入路径崩掉。这类"兜底分支没覆盖全类型"的缺陷平时不显形，
  一上边界值就炸；断言里必须放极值（`0x99AABBCCDDEEFF11`）。
- **断言段号会撞车**：CommChecks 已有 C1~C32（中间还有重复段号的历史包袱）。新增段落前先
  `findstr /c:"Section(\"C"` 列一遍，别按"我以为是下一个号"拍脑袋。本轮连撞两次（C20/C21、C31/C32）。
- **`Assert` 型检查要放在"能跑得到"的位置**：C33 第一次跑崩在 `GetValueArray`，
  宿主直接退出、后面 300 多条断言一条没跑——**崩溃点之前的绿灯没有意义**。
  新增断言段要优先验证"它自己能跑完"。
