- 日期：2026-10-10

- 起因：用户提问"检查逻辑分支与引擎，添加 Case 分支化怎么加合适" → 逐条取证后由用户拍板：**B 方案（判据 + 匹配值）／独立内置算子／兜底用 Else／支持值类型**

## 一、设计决策（口径定死，后续改动先读这里）

| # | 决策 | 理由 |
| --- | --- | --- |
| 1 | **复用 `CompiledIfNode`，不新建编译节点** | Case 的运行语义（按序求值、**首个命中即选中**、不穿透、无命中则整容器空过、求值异常上抛）与 If 逐条同构。另起一套只会把 If 已修过的坑（异常上抛、状态上报、断桥注入、容器失败上浮）重踩一遍 |
| 2 | **判据（容器级）+ 匹配值（分支级）** | 判据 `CaseStep.JudgeExpression` 只写一次；每条 Case 分支的 `StepCollection.Expression` **存的是匹配值文本，不是布尔表达式**（`RequiresExpression` / `IsConditionMissing` / `DisplayName` 三处既有判定天然复用：空值照样红灯、胶囊照样显示 `Case 1 [ 100 ]`） |
| 3 | **编译器合成「判据 == 常量」** | 常量以**追加参数**（`new Parameter(caseParamName, judgeType)`）承载，不拼字面量文本——字符串转义/数值类型陷阱都不经过文本层；运行期由 `CompiledBranch.ConstantArgument` → `BuildBranchArgs` 末尾追加（顺序 = LocalVarIds → RuntimeVarNames → 常量） |
| 4 | **值转换口径单一来源**：`CaseValueHelper.TryConvert`（编译期与编辑器共用） | 编辑器放行的、编译器必然也放行；底层走 `ValueConverter.Convert`（与端口灌值同一转换链路） |
| 5 | **支持范围 = 值类型 + 字符串**（`TypeHelper.IsSafeExpressionType` 白名单，`object` 与引用类型拒绝） | 与条件变量白名单同一口径；引用类型比较结果不可预期，宁可编译期说清楚 |
| 6 | **兜底分支用 `BranchType.Else`**（构造器预建"默认"） | 编译器"恒真"语义现成、灰色身份色现成；`Default` 已被 For 循环体占用（绿色身份，语义混淆） |
| 7 | **硬约束（全部编译期报错）**：判据为空 / 判据未声明 / 匹配值为空 / 值不能转成判据类型 / 重复匹配值（不可达） / 默认分支之后还有 Case（不可达，沿用 `elseSeen`） / 一条可用 Case 分支都没有 / **同一个容器里混用 If/ElseIf（双向都拦）** | "这个分支的 Expression 到底当表达式还是当匹配值"必须只有一个口径；混装会让编辑器、编译器、显示名各说各话 |
| 8 | **判据是语义属性**（走 `SetProperty`，`[RuntimeState]` 排除名单之外） | 改判据 → `FlowModel.Version++` → 触发重编译；用自动属性会静默不发通知，改了判据跑的还是旧编译产物（与 `ParallelStep.ExecutionMode` 同一坑） |
| 9 | **常量参数名防撞**：`__caseValue` 若与已声明变量重名则追加下划线 | 用户别名允许下划线开头，重名会让 Parse 把常量绑到用户的变量上（静默错值） |
| 10 | **判据名重名时取先出现者**（`TryResolveParamType`，顺序 = 局部变量别名 → 运行时变量名） | 与表达式实际解析顺序一致（先加入 delegateParams 的先绑定），判据值与运行期取值必须同一个源 |

历史注：Switch/Case 半成品曾于 2026-09-24 下线（`docs\code-changes\2026-09-24-条件分支剩余异常修复.md`），当时点名的两个病根正是"Case 被当普通布尔表达式解析"与"没有判据值来源"；本批是把这两个缺口补全的正式实现，`BranchType.Case`（值=4）与 `ModuleCommandAction.AddCase` 两个占位枚举值原样启用。

## 二、运行期与链路（未改动，说明为什么不用改）

- **执行**：`CompiledIfNode.RunAndGetNext` 分支循环不变；`CompiledNode.RunSequence`（唯一执行器）不变；容器失败由轮末 `FlowSession.EscalateContainerFailures` 上浮，不变；
- **连线**：`FlowTopology`（只认 `IContainerStep`）、`LinkPorts` 的 If 分支 Guid 键挂接、`ResolveConditionVarType`、`CheckLinkOrder` 全部自动覆盖 CaseStep（它是 `ConditionStep` 子类）；
- **存盘**：`TypeNameHandling.Auto` 按 `$type` 重建 `CaseStep`；`BranchType` 按 int 落盘（Case=4 位置未动）；`SolutionService.NormalizeBranchTypes` 无需新增分支。

## 三、UI 落点

- 工具箱：`BuiltIn_Case` →「逻辑控制 / 分支匹配」，`IsContainer=true` → `StepFactory` 显式造 `CaseStep`（**不能靠 default 兜底**，兜底会造出普通 If 容器）；
- 流程栏：`CaseStep` 的 `HierarchicalDataTemplate`（紫 `#8B5CF6` 身份色；U2 守门自动要求）+ Case 分支胶囊紫色触发器（后写者赢、`IsConditionMissing` 红灯仍最高）+ 组头右键「添加 Case 分支」（插在兜底分支之前，命名取第一个未占用的 `Case N`，运行锁由 `ModuleActionAsync` 顶部统一拦截）；
- 画布：`CanvasNodeViewModel.TypeBadge` 加 `CaseStep => "分支匹配"`（**必须先于 `ConditionStep` 判断**，子类优先）；
- 条件编辑器：`IsCaseMode`（照 `IsForMode` 先例）——顶部"判据"输入 + 分支区把布尔表达式编辑器换成"匹配值"框（AvalonEdit 与快捷插入面板在 Case 模式隐藏：让用户在表达式框里写 `1` 只会换来一句看不懂的类型错）；兜底分支灰条文案随模式切换；写回仍走"草稿 → 校验 → 一次性写回 → 手动 Version++"事务管线。

## 五、未决 / 已知限制

1. **GUI 实机冒烟未做**：工具箱拖入"分支匹配"、右键「添加 Case 分支」、弹窗判据/匹配值交互、紫色身份色与胶囊配色，需现场验收（渲染探针场景 F 未加 CaseStep 样例——`RenderProbe.cs` 当时正被并发会话编辑，未动它）；
2. 匹配值统一 **Trim 后**转换（首尾空格被裁掉），需要匹配含空格字符串的场景暂不支持（弹窗内是单行框）；
3. Case 分支**没有专属删除入口**（与 If 的 ElseIf 同款现状：只能删容器或改值），如需"删除本条 Case 分支"照并行分组的胶囊右键先例加（R25/R26/R27 三条纪律要一起过）；
4. 判据与变量重名（局部别名 vs 运行时变量名）取先出现者，编译期不做同名去重（与既有 `CompileLocalVarParams` 的现状一致）；
5. `StepCollection.Expression` 的语义随 `BranchType` 分叉（Case=匹配值、其余=布尔表达式）——本文件与 `CaseStep` 注释已写明，后续给 StepCollection 加属性的改动必须同步这条口径；
6. `docs\软件手册.md` 的内置节点清单（If/While/For/Break/Continue/Return）未含本次新增的"分支匹配"，也未含 10-09 的"并行分组"——**既有遗漏**，本批未动该手册（随包手册 `VisionMaster\Help\*.md` 不含节点清单，无缺口）。
