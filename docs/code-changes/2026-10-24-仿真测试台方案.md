## 3. 方案

### 3.1 总架构（四层，仿真器仍在最底层）

```
┌──────────────── VM（被测系统，不改业务代码） ────────────────┐
│  流程 / SCADA / 算法                                          │
│    ├─ Plugin.Motion.Sim   → TCP 19510                        │
│    ├─ Plugin.Camera.Sim   → HTTP 19500                       │
│    └─ VM.Communication 真驱动 → Modbus/S7/MC/FINS 19520+     │
└───────────────┬──────────────────┬──────────────────┬────────┘
                │                  │                  │
┌───────────────┴──────────────────┴──────────────────┴────────┐
│ LineSim（独立进程，世界内核，零程序集引用）                    │
│ 45 轴 · 14 相机 · 18 设备/6 协议 · 1ms tick · 故障注入 · 回放  │
└───────────────────────────┬──────────────────────────────────┘
                            │ 新增管理通道（HTTP JSON，19580，默认关）
┌───────────────────────────┴──────────────────────────────────┐
│ SimBench（本仓 tools\SimBench，薄 CLI）                       │
│ 环境启停 / 配置导出 / 冒烟用例 / 报告                          │
└──────────────────────────────────────────────────────────────┘
```

**为什么不新造仿真器**：LineSim 已经有 222 条自检、三条通道、故障注入与回放；重造等于把已经踩过的 17 个坑（见 LineSim `docs/status.md`）再踩一遍。本仓要补的是"使用面"，不是"世界"。

### 3.2 三条通道保持不动，只加一条管理通道

| 通道 | 端口 | 用途 | 现状 |
|---|---|---|---|
| 运控 | 19510 | `hello` / `enqueue` / `poll` / `cancel` / `estop` | 已有 |
| 相机 | 19500 | `/health` `/trigger` `/config` `/stream` | 已有 |
| 设备 | 19520-19561 | 6 种标准工业协议从站 | 已有 |
| **管理** | **19580** | 轴点动/使能/回零/定位、IO 读写、寄存器读写、相机触发、故障注入开关、场景加载、录像控制 | **新增（建议）** |

管理通道三条纪律：
1. **只监听 `127.0.0.1`，且默认关闭**，必须显式 `--console` 才开；
2. 只做"测试口"，不做鉴权、不做远程部署（与 LineSim 现有"明文、无鉴权、只监听回环"口径一致）；
3. 协议单独版本号，不复用运控通道的 `proto`。

### 3.3 三个需要拍板的决策

#### D1 操作台放哪

| 方案 | 内容 | 代价 | 结论 |
|---|---|---|---|
| **A. LineSim 网页测试台（推荐）** | 在 `--web` 的 three.js 大屏加一个「测试台」页，调管理通道 | 改外仓；浏览器零安装 | **推荐** |
| B. VM 侧 WPF 单窗口 | `tools\SimBench` 做桌面 App | 触发 R111-R132（设计基线、令牌、五态），成本远高于收益 | 备选 |
| C. 纯 CLI | 只做命令与脚本 | 手动排查不友好 | 作为 A 的补充 |

推荐 A 的理由：操作面跟"世界"放在一起，避免第二个前端；VM 侧只留一个不碰 UI 纪律的薄 CLI。

#### D2 ZMotion 要不要仿真"驱动本身"

现状：`ZMotionCard` 通过 `ZAux_*` P/Invoke 调 `zauxdll.dll`（约 20 个函数），连接方式是 `ZAux_OpenEth(ip)`；没有卡就一定失败。现有 `SimMotionCard` 只在**语义层**对齐正运动（8 种回零、单位、限位、报警门禁、下发≠到位），不覆盖 `ZMotionCard` 的代码路径。

| 方案 | 内容 | 风险 | 结论 |
|---|---|---|---|
| A. 假 `zauxdll.dll` | 做一个 native 桩，按导出名转发到 LineSim | stdcall 导出/签名多、易被误拷到现场、维护两份 SDK 行为 | **否决** |
| **B. 语义对齐（现状）** | 测试同事用「产线仿真运动卡」 | ZMotion 驱动本身未覆盖 | **默认，先做** |
| C. 驱动内 API 抽象 + 仿真后端 | 抽 `IZMotionApi`，真实实现仍走 P/Invoke，仿真实现走 LineSim 19510；新增 `ZMotionSimCard` | 动生产驱动，需 R12 评审 | **P3 可选** |

C 的判据（若做）：现有 `MotionZMotionChecks` 6 条必须仍绿；新增"同一命令序列在两个实现上产出同一 `MotionCommandOutcome`"的对照断言；真实路径默认实现不得改变任何行为。

#### D3 通讯端口

| 方案 | 内容 | 结论 |
|---|---|---|
| **A. 保持 19520+（推荐）** | 避开真设备与系统端口；配置生成器自动填 | **推荐** |
| B. 对齐 502 / 108 | 用 `--comm-port-shift`（加法偏移）或改 `devices.json` 每台端口 | 仅当测试脚本硬编码标准端口时使用 |

注意：`--comm-port-shift` 是**全设备统一加法**，把 Modbus 对齐到 502 需要 `-19018`，S7 会落到 512 而不是 108；要精确对齐只能改 `devices.json` 的逐台端口。不要用偏移去凑标准端口。

`SimBench preset export` 输出到 `artifacts\sim\<yyyyMMdd>\`：

## 7. 附：3D 场景现状目视评估（2026-10-24 实测）

**实测方式**：`LineSim.exe --serve --web --demo --no-comm`，浏览器 1600×900，实测 60 FPS、tick 约 11.7 万、在线 69 件、良品率 93.4%。

**当前有两套 3D，定位不同：**

| 渲染器 | 入口 | 观感 | 定位 |
|---|---|---|---|
| Web 数字孪生（three.js） | `--web` → `http://127.0.0.1:19600/` | 浅灰厂房地面、三条平行输送线、13 台白色机身 + 黑色机架 + 黄黑警示条、蓝色料箱、木色/黄色工件；带 KPI 卡、工位状态、互锁/凸轮/CNC 详情、缺陷图例、视角按钮 | 主场景，演示 + 观察 |
| WPF 调试视图 / 快照 | `--view` / `--snapshot` | 深色背景、低多边形白色龙门架 + 半透明蓝罩 + 彩色状态块 | 结构示意，可整块删除 |

**优点（保留）**
- 三线/13 工位的空间关系一眼可读；设备造型统一（白机身 + 黑机架 + 警示条），不像玩具。
- KPI、逐工位状态、缺陷分类、互锁红绿、当前 G 代码行、凸轮表都在同一屏，信息密度够。
- 60 FPS 稳定，无明显渲染错误；视角按钮与 A/B/C 线过滤直接可用。

**问题（按对"测试"的影响排序）**
1. **视角预设不自动取景**：实测「正视」「俯视」都切到线内，设备上下/左右被裁切；默认等轴测下方约 40% 是空地板，产线只占画面中间一条。
2. **左侧「怎么编写」帮助面板常驻**，占约 1/4 宽度并遮挡场景，还带横竖滚动条；应改成可折叠抽屉或独立帮助页。
3. **3D 里看不到测试真正要看的量**：没有轴位置/IO 点位/相机视锥/工件 ID/缺陷标签的叠加层；右侧工位状态只有"空闲 / #135 良品"这类文字。
4. **工件稀疏且小**：在线 69 件，画面里只看到零星几件；没有轨迹、编号或高亮，难以定位某一件。
5. **ST1 不在「工位状态」列表**：13 工位只列 ST2–ST13（ST1 是上料/搬运位，状态在详情区里另列）。
6. **厂房环境不完整**：等轴测与正视视角没有墙/顶，像一张悬空布局图；只有部分视角能看到屋顶桁架。
7. **缺陷图例颜色接近**（良品黄 / 划伤浅黄 / 压伤橙 / 缺料红），在 3D 里很难把颜色对应到具体工件。

**结论**：作为"演示大屏"已经够用，性能也好；作为"测试台"还缺**可观测性**。下一步优先补 3D 叠加层（轴/IO/相机/工件标签）与视角自动取景，而不是继续加美术细节。这条与 §3.4 P2 的「操作台」是同一件事的两面：操作面板负责"发命令"，叠加层负责"看见结果"。

## 9. 第二批实施：空跑 / 速度精度 / 相机实拍（2026-10-25）

> 落点仍在外仓 `D:\C#\LineSim`。本仓只改文档。

### 9.1 三种运行场景

| 场景 | 启动 | 有料 | 判据 |
|---|---|---|---|
| 空跑 | `--mode dry` | 否 | 只判链路不断：通信/运动受理/相机出图/空工位判无件/不出现 Fault |
| 虚拟调试 | `--mode sim`（默认） | 由上位机叫料 | 动作与上位机预期一致 |
| 验收 | `--mode accept` | 由上位机叫料 | 逐条判据 + `report.json/.md` |

`RunMode` 新增 `Dry = 3`，`RunModes` 支持 `dry` / `dryrun` / `empty` 三种写法；`DemoDriver.Prime(feedParts:false)` 不上料且跳过抓取动作。

### 9.2 速度 → 精度

新增 `src/World/SpeedAccuracy.cs`：

- 三条退化：模糊 `v×T_exp÷像元`、视觉滞后 `v×T_v`、跟随滞后 `v²/(10a)`。
- **停走式 vs 连续式**：停走式拍照时工件速度 = 0，三条全 0，任何线速免补偿；连续式三条全中。
- `MotionOfStation(station)` 是唯一事实源：ST2（飞剪）、ST6（分选）连续，其余停走。
- 判据阈值：模糊 >1px / 滞后 >0.5mm / 跟随 >0.1mm 任一超限即需补偿；补偿只补滞后与跟随，模糊只能降速或缩曝光。

`/api/state` 的 `speedAccuracy[]` 每台相机一条，含 `motion`、`blurPx`、`lagMm`、`needsCompensation`、`compensationMm`、`residualErrorMm`、`maxSpeedMmPerS`、`note`。

### 9.3 相机视场与实拍

| 接口 | 行为 |
|---|---|
| `GET /api/camera/{serial}` | 返回该相机此刻的 PNG；**不进帧队列、不增加 triggers** |
| `GET /api/camera/{serial}?w=320` | 服务端降采样：2527KB → 42KB |
| `GET /camera/{serial}/snapshot`（相机服务 19500） | 同上，挂在产品服务上 |

大屏新增 `视场` 按钮（3D 画 FOV 框，抬到设备顶面之上 + 四角竖线）与 `取图` 按钮（2Hz 实拍 + 补偿结论）。

### 9.4 本轮踩的坑

1. **`/api/camera` 的 `?w=` 静默失效**：WebServer 在路由前已按 `?` 剥过查询串，传给 handler 的是 `route`；必须传原始 `path`。症状是"降采样写了但 2.5MB 一点没小"。
2. **取图只拍到背景**：渲染器成像位置 = 首轴位置 + `皮带里程×0.1`，皮带里程单调增长到几十万毫米，叠加后工件早飞出画面。大屏取图固定传 `beltMm = 0`（看"本工位这件"），产品口径仍走 `/trigger`。
3. **停走式工位被算成"需补偿"**：所有站一律按线速算退化，导致 13 个站全显示"补偿 3.33mm"。加 `MotionKind` 后停走站归零，只有 ST2/ST6 需补偿。
4. **`using var server = new CameraServer(...)` 编译失败**：该类型只实现 `IAsyncDisposable`，必须 `DisposeAsync().GetAwaiter().GetResult()`。
5. **自检断言前提写错**：我先写"200mm/s 免补偿"，实测 10ms 视觉延迟在 200mm/s 下就是 2mm 滞后，早就超限。判据的"慢"门槛必须由延迟推出来，不能拍脑袋。
