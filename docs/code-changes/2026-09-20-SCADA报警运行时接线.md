## 一、需求与决策

### 1. 需求

S11-a 交付后，报警引擎在断言里跑得起来，但**真机上一条报警都不会产生**：没人 `new ScadaAlarmEngine`、没人推 `Tick()`、`AlarmRaised` 没人接。这一阶段把这条链接通，并把三件一并欠着的地基做掉：

1. **引擎归属**：谁在什么时候建它、什么时候挂载、什么时候拆；
2. **节拍归属**：引擎自己不起定时器（A-17），那"推 `Tick`"这件事落到谁头上；
3. **落盘归属**：报警记录往哪写、写不成怎么办。

### 2. 决策清单（B-1 ~ B-11）

| # | 决策点 | 选择 | 依据 |
|---|---|---|---|
| B-1 | 节拍源归属 | 新建独立类 `ScadaBeatSource`（`Scada.Controls\Runtime\`），一次运行只养**一个** `DispatcherTimer` | 一屏十几个报警灯各养一个定时器：① 起表时刻不同 → 闪烁相位不同 → 看上去是"画面花了"而非"报警在闪"；② 定时器数随图元数线性增长，每个都往 UI 队列塞消息，把渲染挤掉 |
| B-2 | 节拍发什么 | 发**累计时长**（`TimeSpan`），而不是"拍到了"信号 | 消费者各自累加"我收了几拍"，只要漏一拍（UI 忙、窗口最小化后恢复）相位就**永久错开**，表现又是"画面花了"。发绝对时长则任何消费者都能自算此刻该亮该灭，漏拍只跳一下 |
| B-3 | 节拍优先级 | `DispatcherPriority.Normal`（**不用** `Background`） | 时钟图元晚几毫秒没人看得出来，但报警延时与断线判定以节拍周期为分辨率。`Background` 下操作员按住鼠标拖图元时输入消息一直排前面，报警会跟着卡——而这是最不能卡的一条链。`Normal` 仍低于输入优先级，不抢手感 |
| B-4 | 节拍周期 | `DefaultIntervalMilliseconds = 200`；下限 10ms（`Normalize` 钳住） | 与引擎建议的 100~500ms 取中间值。再密就是拿 UI 线程烧 CPU，而报警的延时分辨率不会因此更准 |
| B-5 | 订阅者抛异常 | 逐个 `try/catch` + **必须上报** | `DispatcherTimer.Tick` 里漏出异常会冒到调度循环 → **进程级崩溃**；但也不能静默吞掉（报警系统悄悄不工作了比崩掉更危险）。上报口没给时仍收住 |
| B-6 | 起表位置 | `Start()` 里 **`window.Show()` 之前**（`StartAlarms`） | 引擎 `Attach` 会对每条定义**立即初判**，而"启动那一刻变量早就越限了"是现场常态。挂在 `Show()` 之后，这段窗口期发生的报警没人判；更要紧的是初判属于"一启动就该报"的事实，不该取决于操作员看不看那个窗口 |
| B-7 | 落盘端 | `ScadaAlarmHistoryWriter`；诊断口**复用** `OnBindingDiagnostic` | 日志里"落盘失败"和"绑定没接上"应长得一样，现场排查时才不用先想"这条是哪个子系统报的" |
| B-8 | `OnAlarmRaised` 线程 | 落盘与写日志**不碰 UI**，在哪个线程都安全；将来弹窗/刷面板**必须自己切 `Dispatcher`** | 条件类报警的值变化来自变量轮询线程，断线报警由节拍（UI 线程）发现——引擎承诺事件在锁外抛，但**不**承诺在 UI 线程抛 |
| B-9 | `OnAlarmRaised` 日志级别 | `Severity >= Critical` → `_log.Error`，否则 `_log.Warn` | 把"严重"降级成 Warn，复盘时会看不出当时有多急 |
| B-10 | 收场顺序 | 节拍最先停 → 摘 `AlarmRaised` → `_alarms.Detach()` → 清 `_alarmWriter`；**排在 `session.Stop()` 之前** | ① 节拍先停，否则一次迟到的 `Tick` 会落到正在收场的引擎上（引擎内部判 `_attached` 兜得住，但"先断线后关灯"读起来不必靠对方兜）；② 摘槽在 `session.Stop()` 之前——引擎攥着变量订阅，而变量注册表比窗口活得久得多 |
| B-11 | 起表顺序 | 先赋值 `_alarmWriter` / `_alarms`，**再** `Attach()` | `Attach()` 里就会初判并可能立刻抛 `AlarmRaised`，那一刻两个字段必须已经是活的，否则**第一条报警会被吞掉** |

### 3. 本阶段修掉的两个 Bug

#### ① `ScadaAlarmHistoryWriter` 写不进任何数据行（**真实产品 Bug**）

- **症状**：`Append` 返回 `false`，目录与文件都建出来了（BOM + 表头在），但**一行数据行都没有**。表现是"报警历史功能看起来正常，实际永久不记任何东西"。
- **根因**：`new StreamWriter(stream, Utf8NoBom)` 默认 `leaveOpen: false`。写表头那个 writer 一出 `using` 作用域就**把底层 `FileStream` 一起关掉**；紧接着写行的 writer 对已关闭的流操作 → 抛 `ObjectDisposedException` → 被 `catch` 收成"落盘失败"。
- **修复**：两处 writer 构造改为 `new StreamWriter(stream, Utf8NoBom, 1024, leaveOpen: true)`，并把原因写进注释。

```csharp
// leaveOpen: true 不是可选项：StreamWriter 默认会连底层流一起关掉，
// 表头那个 writer 一出作用域就把 stream 关了，下面写行时必然抛 ObjectDisposedException——
// 表现是"报警历史一行都写不进去，但目录和空文件建出来了"。
```

#### ② 断言自身 Bug：`StartsWith("\uFEFF")` 恒真（**永远绿的假断言**）

- **症状**：断言"追加不重写表头、也不重复插 BOM"失败，但诊断显示实际数据**完全正确**（行首字符分别是 `'2'` 与 `'激'`，无任何 BOM 混入）。
- **根因**：`StartsWith` 默认走**文化相关比较**，而 U+FEFF（BOM）在 .NET 里是"可忽略字符"（ignorable）→ **任何字符串** `.StartsWith("\uFEFF")` 都返回 `true` → `!true = false`。**若不修，这条断言从没校验过任何东西。**
- **修复**：改为字符级比较 `lines2[1][0] != '\uFEFF' && lines2[2][0] != '\uFEFF'`；时间前缀比较一律显式加 `StringComparison.Ordinal`。

## 二、为什么这么设计（逐条展开）

### 1. 为什么节拍必须"全画面统一"（B-1、B-2）

```
   各养一个定时器                        统一节拍源
   ┌──────┐ 起表 t=0ms  ┌──────┐        ┌──────────────┐
   │ 灯 A │────────────▶│ 亮   │        │ ScadaBeatSource│  200ms 一拍
   └──────┘             └──────┘        └───────┬──────┘
   ┌──────┐ 起表 t=37ms ┌──────┐                │ Beat(累计时长)
   │ 灯 B │────────────▶│ 灭   │        ┌───────┴───────┐
   └──────┘             └──────┘        ▼       ▼       ▼
   ┌──────┐ 起表 t=91ms ┌──────┐       灯 A    灯 B    灯 C
   │ 灯 C │────────────▶│ 亮   │       （都读同一份 Elapsed → 相位天然对齐）
   └──────┘             └──────┘
   相位互不相同 → "画面花了"          相位一致 → "报警在闪"
```

关键在**发绝对时长而非"拍到了"**：漏拍（UI 忙、窗口最小化后恢复）在"各自累加计数"的方案里会让相位永久错开；发累计时长则任何消费者都能自算此刻该亮该灭，漏拍只跳一下。

### 2. 为什么引擎和节拍要分家（B-6、B-10）

`ScadaAlarmEngine` 的注释把这条边界写死了：**领域层不自己起定时器**（A-17）。否则"节拍多快""跑在哪个线程"这两条宿主决策就写进模型里，断言里也没法一口气把十分钟推过去。

代价是"宿主不推 `Tick()`，断线报警不会响"——这正是本阶段要落实的硬性交付项。落到 `ScadaRuntimeHost` 上就是一条最短的链：

```
   Start()
     └─ StartAlarms(document, window)        ← Show() 之前（B-6）
          ├─ new ScadaAlarmHistoryWriter(...)     先赋值（B-11）
          ├─ new ScadaAlarmEngine(...)            先赋值（B-11）
          ├─ new ScadaBeatSource(window.Dispatcher, 200ms, OnBindingDiagnostic)
          ├─ engine.Attach()      ← 立即初判，可能当场抛 AlarmRaised
          └─ beat.Start()
     └─ window.Show()
```

收场是它的镜像，且顺序不可换（B-10）：

```
   OnWindowClosed() → TeardownAlarms()
     ├─ _beat.Stop(); _beat.Beat -= OnBeat;      ← 节拍最先停
     ├─ _alarms.AlarmRaised -= OnAlarmRaised;
     ├─ _alarms.Detach();                        ← 退订阅、丢槽（历史保留在引擎里）
     └─ _alarmWriter = null;
   → 之后才 session.Stop()
```

### 3. 为什么 `TeardownAlarms` 在 `Stop()` 里还要再兜一次

`Stop()` 的正常路径是 `window.Close()` → `OnWindowClosed` → `TeardownAlarms`。但存在一种最难复现的脏状态：**会话活着而窗口没了**（窗口被外部关掉、构造中途失败）。这时若只靠 `OnWindowClosed`，引擎与节拍就成了没有主人的孤儿——它们攥着变量订阅，而变量注册表比窗口活得久得多。

所以 `Stop()` 在"窗口不在"的分支里**再调一次** `TeardownAlarms()`。`TeardownAlarms` 自身对 `null` 字段全判空，重复调用是空操作。

### 4. 落盘为什么"失败不抛、只报诊断"（B-7）

报警系统因为写不了历史文件而崩掉，比丢几行历史严重得多。所以 `Append` 的契约是：

- 写不成 → 返回 `false` + 进故障态（`IsFaulted` / `LastError`）；
- **只在故障态翻转时**上报一次诊断（磁盘故障时每行都报会把日志刷满，真正的原因反而被埋掉）；
- 恢复正常 → 补报一次 Warning（不再刷日志，但要让现场知道"又能写了"）；
- 传 `null` 记录 → 不写、不抛、**不进故障态**（调用方的空引用不该被记成磁盘故障）。

### 5. 落盘文件格式为什么这么定

| 决策 | 理由 |
|---|---|
| 文件名 `AlarmHistory-yyyy-MM-dd.csv`（按**本地**日期滚动） | 现场是按本地时间查"昨天那次报警"的；单份文件也不会涨到打不开 |
| 目录 `<软件目录>\Alarms`（与 `Logs` 刻意分开） | 报警历史是**资产**，运行日志是可随时清掉的过程记录 |
| UTF-8 **带 BOM** | 不带 BOM 的 CSV 用 Excel 打开中文必乱码——而现场第一反应就是双击用 Excel 看 |
| RFC 4180 转义（含 `,` `"` CR LF 的字段加双引号、内部引号翻倍） | 不转义会把一行劈成两列，在 Excel 里表现为"数据莫名其妙对不上" |
| 13 列，列序 = 现场阅读顺序 | 先说是什么（激活时间/名称/文本/严重度/类型）→ 再说为什么（变量名/条件/触发值）→ 最后是时间线（状态/确认/恢复/清除/持续） |
| **持续时长只在已恢复时写** | 把"到此刻为止"写进文件，过一天再翻就是一句假话；且时长**算到恢复而非清除**（清除时刻里含"人多久才来确认"，那是人慢不是报警持续） |
| 每次**态迁移追加一行** | 文件本身可重放：按激活时间分组就能还原从生到死的全过程 |
| 表头只在文件为空时补一次 | 追加不重写表头、不重复插 BOM |

### 2. `[AH2]` 断言段覆盖的行为

**A. writer（`CheckAlarmCsvWriter`，16 条，纯 .NET 主线程）**

| 组 | 钉住的行为 |
|---|---|
| 目录与滚动 | 默认目录落在软件目录下的 `Alarms`；按本地日期滚动出文件名；跨日期落到另一份文件且新文件自带表头 |
| 编码与格式 | 首三字节是 UTF-8 BOM；表头 13 列且列序就是现场阅读顺序；RFC 4180 转义（含逗号被双引号包住、内部引号翻倍） |
| 内容 | 行内事实来自记录**快照**（激活时间用本地时间、严重度/类型/条件都是人话）；未恢复记录持续时长列留空 |
| 态迁移 | 每次态迁移追加一行（文件可重放）；恢复后才写时长且**算到恢复而非清除** |
| 追加语义 | 追加不重写表头、不重复插 BOM |
| 故障路径 | `null` 记录不写不抛**不进故障态**；写不成返回 `false` 并进故障态；故障**只上报一次**；故障恢复后回正常态并**补报一次**；成功 writer 全程零诊断 |

**B. beat（`RunBeatSourceChecks`，9 条，STA 线程）**

| 组 | 钉住的行为 |
|---|---|
| 周期 | 缺省 200ms；下限钳在 10ms |
| 起停 | 起表前不在跳；`Stop` 可重复；`Start` 幂等（重复 Start 不重置相位） |
| 真在跳 | `DispatcherTimer` 确实在跳，且每拍都带着**累计时长**而不是"拍到了" |
| 健壮性 | 全部正常时零诊断；一个订阅者抛异常**不连带打死其余**订阅者；订阅者异常**必须上报**（且文案含"节拍"） |
| 停表 | 停表后可重复 `Stop`；累计时长保留最后一次的值**不归零** |

**STA 线程的必要性**：`ScadaBeatSource` 内包 `DispatcherTimer`，必须在 STA 线程上建（与图元控件同一房间要求）。主线程不是 STA，所以照 `ElementControlChecks` 的样板另起一条 STA 线程跑，异常存进 `failure` 后 `Join` 回主线程判定。新增 `PumpDispatcher(int ms)` 辅助（`DispatcherFrame` + `DispatcherPriority.Send` 的 stopper 定时器）把消息循环推起来，让 `DispatcherTimer` 真的跳够几拍。

### 3. 本轮断言的两处"抓到东西"

两条断言在**首跑就抓出问题**，这正是断言存在的意义：

1. "按本地日期滚动出文件名" 失败 → 暴露 `StreamWriter` 抢占底层流的**真实产品 Bug**（修 Bug①）；
2. "追加不重写表头、也不重复插 BOM" 失败，但诊断显示数据完全正确 → 暴露 `StartsWith("\uFEFF")` 恒真的**假断言**（修 Bug②）。

若没有这两条断言，第一个 Bug 会以"报警历史功能看起来正常、实际永久不记"的形态上线，第二个 Bug 会让"BOM 检测"从交付起就是空操作。

| **报警条图元的"显示哪些报警"过滤口径未定** | 报警是设备属性不是画面属性，同一变量在多张画面上显示时一条报警会同时影响所有画面（这是对的）；但报警条要明确"这张画面上显示哪些" | **S11-c** |
| **无报警组 / 报警抑制** | 现场常见的"检修期间屏蔽某类报警"还没有。路线图未列，暂不做 | — |

### 2. 设计上的刻意取舍

- **`Tick` 归宿主**（A-17 / B-6）：宿主不推 `Tick()` 则断线报警与延时判定不工作。这是"领域层不起定时器"的直接代价，已由 `ScadaRuntimeHost.StartAlarms` 落实。
- **`ScadaBeatSource` 属宿主侧（WPF）**：它引 `System.Windows.Threading`，所以落在 `Scada.Controls` 而**不是** `Scada` 领域层。将来若有非 WPF 宿主（如控制台服务），需要另写一个等价节拍源——这是 D1 依赖单向换来的确定性。
- **`_slots` 线性扫描**（A-13，承 S11-a）：报警条数上千时 `Tick` 会变慢。当前量级（几十条）无影响，S13 性能基线时若报警数上到千级需重新评估。
- **落盘按天滚动但不清理旧文件**：现场要能查三个月前，所以不能自动删。磁盘占满的风险由 S13 的运维文档承担（或将来加保留策略）。
- **`OnAlarmRaised` 不切线程**（B-8）：当前只落盘 + 写日志，都不碰 UI。**将来在这里弹窗或刷面板，必须自己切回 `Dispatcher`**——这一点写进了方法注释，防止后来者顺手加一行 UI 代码就埋下跨线程异常。

### 3. 与 S10 / S11-a 遗留项的关系

- **S11-a 归 S11-b 的三项欠债已全部清掉**：运行时接线、报警记录落盘、全画面统一节拍源（见 [S11-a 记录 §五](2026-09-20-SCADA报警领域层与引擎.md)）。
- **S10 的两项真机待核**（锁角标与诊断角标是否重叠、单击整组/框选单个的不对称是否困惑）仍未做——与 S11 无关，但按路线图验收口径 3 仍是 S10 的挂账。

## 六、真机复核清单（S11-c 交付后一并执行）

1. 组态一个越限报警 → 启动运行 → 手动改值越限 → 报警条出现、状态栏计数变红。
2. 点"确认" → 记录转"已确认"、红点数字减一。
3. 值恢复 → 记录消失（`Acknowledged` 路径）。
4. 未确认时值恢复 → 停在"已恢复未确认"等一次确认。
5. 运行中改阈值 → 无需重启即生效。
6. 断线报警：拔掉通信 → `StaleSeconds` 后报警，且**不是** `StaleSeconds + DelaySeconds` 才报。
7. 报警历史面板按时间倒序查询、CSV 导出内容与面板一致。
8. 关闭再打开方案 → 报警配置在；重启运行 → 历史记录仍可查（落盘通路）。
9. **（S11-b 专项）** 启动运行后到软件目录 `Alarms\` 下确认当天 `AlarmHistory-*.csv` 已生成，表头齐全；触发一条报警后用 Excel 双击打开，**中文不乱码、列不串位**。
10. **（S11-b 专项）** 一条报警从激活 → 确认 → 恢复走完，CSV 里应出现三行、按时间可重放，且"持续时长"只在恢复那行有值。
