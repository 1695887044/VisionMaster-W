## 一、需求与决策

### 核实中改变优先级判断的一条事实

清单把 #10「连线静默丢弃」列为**高优先级**，读起来像"用户正常操作会静默失效"。核实后发现：

[GetOutputPorts](file:///e:/VM/VisionMaster-W-master/VisionMaster/ViewModels/FlowCanvasViewModel.cs#L1104-L1140) 只给四类东西长输出脚 —— ① 已注册插件的 `OutputDefinitions`；② 动态端口快照 `OutputPortDefinitions`；③ `ForStep` 的 `Index`；④ 变量定义节点的值脚。

**`ConditionStep`（If/While）不在其中，也不是插件 → 零输出脚 → 画布上根本没有可以拖出连线的起点。**

所以 #10 的三处静默路径**只能由手改 `.vm` 或遗留文件触发，UI 画不出来**。这条事实把 C 组的性质从「正常操作会静默丢线」改成「**手改文件出错时极难定位**」：

- **好处**：改成硬报错，破坏存量正常流程的风险极低
- **代价**：含此类遗留脏线的旧文件，会从"静默打开"变成"报错打不开"

用户确认按「全部升级为编译错误」执行——与阶段一确立的准绳一致：**凡是"结果不可信"的分支，一律从"静默降级"改成"显式报错"**。

### 两条统一点评

C 组所有条目的共同特征：**"取到了数据源却无处安放"时什么都不做**。

```
sourcePort 拿到了数据
        ↓ 但目标端口/名字对不上
        ↓ 旧实现：无 else，什么都不做
sourcePort 保持 null 或直接被丢弃
        ↓
if (sourcePort != null) { 公共赋值段 }   ← 整段被跳过
        ↓
用户拿到"编译成功"，但那条线永远不生效
```

现场表现是"变量没值 / 圈数不对"，却找不到任何错误提示，只能通读图纸猜。

### 实际改了 8 处（清单列了 6 处）

清单的 #10 列了 3 处、#12 列了 3 处。动手时在同一条链路上又找出 **2 处同性质出口**，一并修了 —— 理由：只修枚举出来的行号、却在同一个函数里留下两个一模一样的静默出口，"本链路再没有静默丢线"这个结论就无法自证。

| 来源 | 处 |
|---|---|
| 清单 #10 | 上游是容器节点、RuntimeVariable 输入名不存在、For 的 LoopCount 名字不匹配 |
| 清单 #12 | `int.Parse` 溢出、重复 StepId、While 无循环分支 |
| **核实新增** | 端口名正则整体失配（`Port[abc]`）、If/While 条件键不是 Guid |

### 一处值得说明的设计：⑦ 的 `else` 为什么不会误伤正常图纸

⑦ 所在的公共赋值段是**所有 linkKind 共用**的，不只在 RuntimeVariable 分支下。所以"给 For 加 else 报错"看起来有误伤风险。

但整段被包在 `if (sourcePort != null) { … }` 里 —— 能走到这里，说明**数据源已经解析出来了，只是没地方放**。正常图纸里每条连线都必然有合法的目标端口，所以不会命中。这条注释也写进了代码，免得后人误删。

### 断言的灵敏度实测（关键）

C 组有**两种截然不同的旧症状**，所以各还原一处做对照：把 ③ 的 `int.TryParse` 还原成 `int.Parse`、把 ⑦ 的 `else` 删掉：

```
[×失败] For 的连线键不是 LoopCount → 连线报错
        ← 旧行为：编译"成功"（断言因 !Compiled 为假而红）—— 连线被静默丢弃
[×失败] 端口下标超出整数范围 → 定位错误（不再炸成'系统崩溃级错误'）
        → 系统崩溃级错误: Value was either too large or too small for an Int32.
[×失败] 下标溢出的错误带上了出错节点名（可定位）
        → 系统崩溃级错误: Value was either too large or too small for an Int32.
```

两个症状都完整复现：

| 旧症状 | 现场表现 |
|---|---|
| **静默丢线** | 编译通过、无任何提示，那条线永远不生效 |
| **无定位崩溃** | 一句 `系统崩溃级错误: Value was either too large or too small for an Int32.`，不知道是哪个节点写错了 |

验完已立即还原。

## 四、已知边界

| # | 项 | 说明 |
|---|---|---|
| 1 | **硬报错会让含遗留脏线的旧文件打不开** | 这是用户已确认接受的代价。依据：这类连线**只能由手改 `.vm` 触发**（画布不给容器节点长输出脚），正常编辑流程画不出来。若将来收到现场反馈"某旧文件突然打不开"，正确的处置是让用户删掉那条无效线，而不是回退成静默 |
| 2 | **`[E10]` 全部是"构造图纸 → 断言编译报错"的静态断言** | 这些路径都不依赖运行时行为，所以不需要真执行；也因此没有覆盖"报错之后流程还能不能继续用"——那属于错误恢复，不在本组范围 |
| 3 | **重复 StepId 的判重口径与 `FlowTopology` 不一致** | `FlowTopology` 对重复 Id 是**容忍**的（只做拓扑分类，不判重），而编译器现在**报错**。本组把编译器的口径收紧成"报错"（因为静默容忍会让图纸行为不确定），但**没有同步改 `FlowTopology`** —— 两处口径仍不一致，只是不一致的方向从"一个容忍一个崩"变成"一个容忍一个报错"。要彻底统一需另行决策 |
| 4 | **While 无分支报错后，`RunLoop` 里的 `LoopBranch?.ConditionLambda == null` 守卫保留** | 编译期已拦住"无分支"与"条件为空"两种情况，这条守卫现在是纯防御性的（例如将来新增别的装配路径）。没有删，因为它成本为零而能兜住未知路径 |
| 5 | **未改画布侧的 `CanConnect`** | 本组只动编译器。`CanConnect` 走的是 `FlowTopology`，理论上可能放行一条编译器会拒的线（画布上出现红框 + 错误列表，这正是既定设计：**建线期不做类型校验，类型/结构问题交给编译错误红框**）。是否要把新增的这几条判定前移到画布，需另行决策 |
| 6 | **端口名正则未放宽** | 现有正则 `^(?<port>[^\[]+)(\[(?<idx>\d+)\])?$` 只支持"一层数组下标"，`Out[0][1]` 这类多维写法会被判为"格式非法"而不是解析成二维。本组只把它从"静默"改成"报错"，**没有扩展语法** |
