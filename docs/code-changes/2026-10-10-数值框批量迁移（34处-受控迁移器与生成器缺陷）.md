## 一、侦察：37 处、三种形状、两个陷阱

上一轮定了"逐个接"的做法，本轮先把 37 处全部扫出来（扫描器见「二」），发现三类陷阱 —— **样式名叫 `PluginNumericBox` 不代表绑的一定是数值**：

| 处 | 绑定 | 结论 |
| --- | --- | --- |
| `Plugin.PoseTransform\PoseTransformView.xaml:241` | `PreviewImagePath` | **图片路径** ✗ 不迁（只是借了同一个样式当文本输入用） |
| `Plugin.Calibration\CalibrationView.xaml:425` | `CameraSerial` | **设备序列号**（字符串）✗ 不迁 |
| `Plugin.CaliperMeasure\CaliperMeasureView.xaml:196` | `Value`（结果列表里的可编辑值） | 语义不明，**保守排除** ✗ |

另外三种块形状都要处理：**带规则的**（Matching 用 `cv:NumberValidationRule`（Core.Controls 共享）、CaliperMeasure 用自带副本）、**不带规则的**（Calibration 那 12 处是裸 `Text="{Binding X}"`）。

## 二、迁移器（`_LogViewProbe\NumericBoxMigrator.cs`）

```
LogViewProbe.exe --scan-numeric    列出每一处：文件 / 行号 / 绑定路径 / 规则区间   （不动文件）
LogViewProbe.exe --apply-numeric   按允许清单迁移（清单：_LogViewProbe\numeric-migration-allowlist.txt）
```

设计要点（都是为了"不重演上一轮的全红事故"）：

- **不用 PowerShell 正则**：仓库纪律 R3 禁止用 PowerShell 往返编辑源文件（无 BOM UTF-8 会被按 ANSI 读、按另一编码写回 → 静默损坏）。这里严格 UTF-8 解码读、写回时保留原 BOM，且**只改匹配到的块**；任何一处形状不认识就整篇不写并打印。
- **允许清单**：`文件|绑定路径[|int]` 一行一处（`int` → 生成 `DecimalPlaces="0"`）。哪些是数值、哪个是整数类型，都是逐个核对过**属性声明**才写进去的（`MaxMatches`/`NumLevels`/`CaliperCount`/`FitMinPoints` 是 int；`EdgeThreshold` 名字像 int 其实是 double）。
- 幂等：扫描只认 `<TextBox>`，已迁移的块不会再匹配 —— 所以"漏跑/重跑"不会二次改写。

**执行前后各留备份**（`%TEMP%\vm_migrate_backup\`）—— 仓库没有版本控制，这是唯一的回滚绳。

## 四、共享校验规则：第三份副本也必须修

Matching 用的是 **Core.Controls 里的共享 `NumberValidationRule`**（`cv:` 前缀），而上一轮只修了 BlobDetect / CaliperMeasure 两份**插件自带**副本 —— 不修共享那份，Matching 迁完必然重演"全字段变红"。
本轮把 `Shard\Core.Controls\NumberValidationRule.cs` 也改成"字符串与已转换数值都认"。

> **三份副本是根因**：同一个规则在三个地方各写了一遍，修一处漏两处。建议后续收敛成 Core.Controls 那一份（插件里那两份删掉、视图改前缀）—— 已记入「六」。

## 五、过程中踩到的两个生成器缺陷（都被构建当场抓住）

| 缺陷 | 症状 | 修法 |
| --- | --- | --- |
| 元素形式生成时用正则"去重复 Style"，`(?m)^.*Style=…` **把开头整行吃掉了** | 生成的 XAML 丢了 `<ui:NumericBox` 元素名与原有属性，构建报 `MC3015: 附加属性 NumericBox.Value 在 Grid 上未定义` | 改成朴素写法：**只替换元素名 + 在结尾 `>` 之前补属性**，不裁剪/重建整行 |
| 整数位插入用 `Replace("<ui:NumericBox", …)`，**命中了 `<ui:NumericBox.Value>`** | 生成 `<ui:NumericBox DecimalPlaces="0".Value>`，构建报 `MC3000: 名称不能以 '.' 开头` | 用 lookahead：`<ui:NumericBox(?=[\s>])` |

两次都是**先改坏了、构建立刻报错**（没进真机），按备份回滚两个文件、修生成器、重跑 —— 幂等设计让重跑干净。教训一句话：**能"只替换元素名 + 在 '>' 前插属性"做到的，就别去裁剪/重建整行。**

**构建绕锁**：`Modules\Plugin.*.dll` 被 VS 2022 与运行中的 VisionMaster 占用（投递目标被锁，`MSB3027`），本轮所有构建都用 `-p:ModulesDir="%TEMP%\vm_modules_skip\"` 把投递改到临时目录完成；**真机生效仍需关掉 VS 与实例后正常重建一次。**

## 七、未决与观察

- **真机验证待做**：本轮结论全部来自离屏渲染 + 数据通路断言；上下键/滚轮手感、钳制时值跳变是否被现场接受，仍要上真机（且需先按「五」重建）。

- **下一个落点（A 项的自然延伸）**：SCADA 属性面板（`ScadaPropertyView.xaml`）的编辑器族目前只有 `EditText`，数值属性走的是裸文本框 —— 加一个走 NumericBox 的数值编辑器即可覆盖 SCADA 那批元素属性（消费方现成）。
- `CaliperMeasure` 的 `Value`（结果列表里可编辑的那个）语义没确认，**留着没迁**；确认是数值的话按允许清单补一行即可（工具幂等，重跑安全）。
