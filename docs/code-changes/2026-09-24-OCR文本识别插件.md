### 用户确认的 5 个决策点

| 决策点 | 结论 | 关键理由 |
|---|---|---|
| 识别后端 | MLP + 内置模型 | 零外部依赖、与现场脚本方案口径一致 |
| ROI 形态 | 单个矩形，一节点认一处 | 输出单值而非数组，**下游更好接**（数组要"取第 3 个"才能用） |
| 分割参数 | 分层暴露（常用可见 / 高级折叠）+ 试算 | 默认值管标准场景，难例必须能看见中间结果再调 |
| 判定与投射 | 都不做 | 沿用 `ColorCheckPlugin` 立的规矩：判定交下游；投射机制尚未立起来 |
| 开工范围 | 全套一次做完 | — |

### 我直接定的 6 项

| 项 | 结论 |
|---|---|
| 插件标识 | `Plugin.Ocr`，`GroupName = "图像处理"`（DLL 名须匹配宿主 `Plugin*.dll` 扫描） |
| 端口 | 入 `Image`；出 `Text` / `Count` / `Confidence` / `Detail` |
| 模型句柄 | 缓存在插件实例，`Dispose()` 里 `ClearOcrClassMlp` |
| 模型投递 | 自带 `Assets/ocr/`；两条投递路径（见下） |
| 分割路线 | 手搓（阈值→形态学→连通域→筛选→排序），**不用 `SegmentCharacters`** |
| 算法分层 | `CharSegmenter` / `OcrEngine` 各自成类，插件类只做端口/配置/UI 通道 |

**关于"不用 `SegmentCharacters`"**：我最初倾向用它（Halcon 自带的投影法切字），实施时改走手搓。理由是它的控制参数（`ThresholdOffset`/`CharWidth`/`Inhibition`）是它自己的内部概念，现场调参时看不懂；而手搓路线的参数是"阈值、字符尺寸、形态学"，与脚本原型同构、现场已有使用经验。

### 实施中被实测推翻的两个设计

| 原设计 | 实测结果 | 处置 |
|---|---|---|
| 点阵字用**膨胀**焊合 | 膨胀只扩不缩 → 笔画变粗、字形失真 → 分类器**系统性错认**（0→A、3→T、5→Q） | 改为**闭运算**（先扩后缩，连上了但尺寸还原），`ClosingRadius` 成为独立旋钮 |
| 加"对比度归一化"旋钮（`scale_image_max`） | 对低对比点阵图**没有任何改善** | **删掉**。留一个没被证实的旋钮，比没有更糟 —— 它看起来有用 |

### 本轮明确不做

期望格式校验（属下游）、字符集约束纠正（0/O、1/I 混淆，需受约束重打分，是独立课题）、Deep OCR 后端、多 ROI、结果投射。

### 定位过程（不是猜出来的）

前两轮全错，靠两步诊断定位：

1. **把识别区裁出来看** → 发现 `lot_04` 字符**顶部被切掉**（字形残缺 → 认成 `II1V4WUA` 乱码）、`dot_print_01` 整块是**空白纸面**（框在 y 310，真值在 y≈200）、`dot_print_02` 首个字符被左边缘切掉。
2. **把切出的字符区域涂在图上** → `dot_print_02` 的 9 个块与字形**一一对应**，分割完全正确。这一步把"分割问题"与"识别问题"彻底分开，才找到真因是低对比导致的特征偏移。

### 断言不只覆盖"对的情况"

`[OCR]` 里有 4 条 `【核心】` 断言专门覆盖**失败面**：

```
[√通过] 【核心】低对比点阵图认不准时给出低置信度（现场据此判不可信）  →  dot02 置信=0.72，dot01 置信=0.83
[√通过] 【核心】低对比点阵图必须出现拒识，而不是清一色'认出来了'  →  dot02 拒识=3，dot01 拒识=16
[√通过] 【核心】出现拒识字时写 Warn（否则错字符串会被当成功结果放行）
        →  Warn:OCR 有 3 个字符被拒识（不在分类器字符集内或字形不可辨），识别结果不完整：1:A(0.39) 2:?(0.98) …
[√通过] 【核心】均值置信度偏低时写 Warn 提示结果不可信
        →  Warn:OCR 均值置信度偏低（0.72 < 0.90），本次识别结果不可信，请勿直接用于放行：…
```

**为什么这几条最重要**：OCR 最危险的失败不是"认错"，而是"给出一串看似正常的错字符却没有任何提示" —— 那种结果会被下游当成成功识别直接放行。插件里两条 Warn 就是防这个，断言把"注释里的承诺"变成了可验证行为。

## 四、已知边界

| # | 项 | 说明 |
|---|---|---|
| 1 | **`dot_print_*` 两张图认不准（最需要知道的一条）** | 瓶盖曲面 + 细纹理纸面、字符仅 25~28px、对比度极低（字≈90 / 底≈150）。**分割是对的**（`dot_print_02` 9 个块与字形一一对应），是分类器在这类字形上大面积拒识 + 错认。当前行为是"认不准但看得出来"（置信 0.72/0.83、拒识 3/16 + 两条 Warn）。**要真认准需另开课题**：局部对比度增强（`emphasize`/`dyn_threshold`）、按字符投影精修分割、或换 Deep OCR 后端。**没有把它调成"看起来通过"** —— 那等于把缺陷藏进断言 |
| 2 | **`ErosionRadius` / `DilationRadius` 本轮无实测用例** | 现有图集不需要它们（该用闭运算）。保留的依据是脚本原型注释里明确记录了这两个相反方向的需求（字符粘连要腐蚀断开、笔画过细要膨胀加粗），属"已知需求"而非臆测。**但要诚实说明：它们没有实测证据支撑**，第一次用到时应先补断言 |
| 3 | **分类器字符集只含 0-9 与 A-Z** | `:` `/` 空格等一律拒识。实测发现：拒识表现为**一个"看不见但不是空串也不是空格"的字符**（明细里是 `2:(0.98)` 这种），所以拒识判据改成"**输出里没有字母也没有数字**"，而不是判空 —— 后者会把拒识当成"认出了一个字符"漏过去 |
| 4 | **`LowConfidenceThreshold = 0.9` 是常量，不是配置项** | 它只影响"要不要提醒"，不参与判定（判定归下游）。取常量是为了让现场少一处要调的东西。若将来要按工艺调，需改成 `[StepConfig]` |
| 5 | **未做结果投射** | 只输出文本与逐字符置信度，不画字符框。`SegmentResult` 已带 `Chars`/`Rows`/`Cols`，投射机制一旦立起来可直接用；本轮不自己造 |
| 6 | **未做期望格式校验** | 如"料号应为 8 位"。属下游比较节点的职责（沿用 `ColorCheckPlugin` 立的规矩） |
| 7 | **0/O、1/I 混淆未处理** | 属"字符集约束重打分"，需自己实现评分约束，是独立课题，不是"顺手加个参数" |
| 8 | **`Assets` 目录名是通用的** | 当前宿主目录下无同名目录（已核实），但若将来别的插件也用 `Assets`，会共用同一目录。真要隔离需改成 `PluginOcrAssets` 之类 |
| 9 | **模型文件在仓库里有两份** | `Plugin.ImageScript/ScriptAssets/ocr/` 与 `Plugin.Ocr/Assets/ocr/`。选两份是为了插件自包含（0.2 MB，代价可忽略），代价是**将来换模型要记得改两处**。`ModelPath` 配置项可绕开内置模型 |
