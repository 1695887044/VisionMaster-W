## 约定（先读）

| 项 | 约定 |
| --- | --- |
| 命名 | 插件内**对外文案**统一叫「胶路」，算法层与文档中「线形特征」同义——本插件的模型能力不限于涂胶（见第十章通用性） |

## 一、背景与目标

### 1.1 现状

HALCON 23.05 提供 `create_bead_inspection_model` / `apply_bead_inspection_model` / `create_planar_uncalib_deformable_model` / `find_planar_uncalib_deformable_model` / `projective_trans_image` 等算子，本机 HALCON（`C:\Users\16958\AppData\Local\Programs\MVTec\HALCON-23.05-Progress`，工程引用 `DLL\Halcon\halcondotnet.dll`，FileVersion 23.5.0.0）**已确认全部存在**。

但仓库**没有任何插件封装它们**：

- 现有插件全部是「在固定搜索区里量一个数」或「对整图做区域分析」的范式；
- **没有任何插件能接受一条轮廓曲线作为输入**（全仓库只有图像脚本 / C# 脚本插件有 `InputPort<HObject>`）；
- 形状匹配插件只提供**刚性 + 缩放**对齐（`create_shape_model` / `find_scaled_shape_model` + `vector_angle_to_rigid`），无法吸收透视形变。

因此用现有插件拼不出胶路检测：`Image\bead\` 的 7 张样图姿态差异明显（01 明显倾斜、03/05 接近正对），刚性对齐吸收不了透视变化；即使对齐了，卡尺插件也只能在**手工摆放的少数几个位置**测胶宽，两个卡尺之间的断胶/缺胶**根本检测不到**，也给不出「缺胶 / 太细 / 太粗 / 位置偏移」的分段分类。

### 1.2 范例在做什么（三段）

1. **平面可变形（投影）对齐**：4 组手工点 `vector_to_proj_hom_mat2d` → 矫正参考图 → `binary_threshold` + `opening_circle` + `connection` + 按面积取最大平面区 → `fill_up` + `dilation_circle` → `create_planar_uncalib_deformable_model` 建平面可变形模型。检测时 `find_planar_uncalib_deformable_model` 求 `HomMat2D` → `hom_mat2d_invert` + `hom_mat2d_translate(RowT, ColumnT)` → `projective_trans_image` 把图搬回参考位姿。
2. **建胶路模型**：`gen_contour_nurbs_xld` 生成参考胶路曲线（范例里是**硬编码**的 14 个控制点）；`create_bead_inspection_model(ContourRef, 14, 7, 30, 'dark', [], [], Model)`。
3. **检测与分类**：`apply_bead_inspection_model` 输出左右轮廓、错误段与 `ErrorType` 字符串数组（取值 `no bead` / `too thin` / `too thick` / `incorrect position`，OK 时长度为 0）；再用 `gen_parallel_contour_xld` + 自写过程 `close_parallels` + `intersection_closed_contours_xld` 把错误段画成可视化区域。

### 1.3 目标

1. 把上述能力做成**平台通用插件**：对齐策略可选、参考路径来源多样、多产品配方、输出平台口径的 OK/NG 与可消费结果；
2. 下游能**直接接** `ResultUpload` / `DataRecord` / `ExcelExport`，无需再补插件；
3. 算法层与界面层分离，为「平面配准」「线形特征检测」后续复用留出接口。

## 二、关键设计决策

| # | 决策点 | 结论 | 理由 / 代价 |
| --- | --- | --- | --- |
| 1 | **插件拆分** | **单插件** `Plugin.BeadInspect`，对齐作为内部模式 | 对齐模型与参考图、参考路径**同源**——拆成两个节点会强制用户在两处维护同一份参考数据，是稳定的错误来源。代价：平面配准暂不能被别的插件直接复用；缓解：算法收进独立的 `BeadInspectHalcon` 静态类，未来抽 `Plugin.PlanarAlign` 时直接搬 |
| 2 | **配置传递** | `[StepConfig]` 属性 + 配方库 JSON（仿 Matching），**不新增 `InputPort<BeadInspectionConfig>`** | 仓库唯一的复杂 DTO 输入端口（`PoseTransform.Transform`）是**跨插件契约**才需要；本插件配置自包含，走 `[StepConfig]` 才能随 .vms 落盘、才能被配置界面直接绑定。若做成必填端口，用户不连线就用不了插件 |
| 3 | **参考路径来源** | **三种入口并存**：① **画布逐点拾取**（主入口，用户点胶路中心线）；② **从良品图自动提取中心线**（一期实现，见 §6.4）；③ 点列**文件导入**（CAD/示教数据） | 点列是所有来源的**统一中间表示**（与 Matching 的「条目」地位相同），下游算法只认点列。范例的 14 个硬编码控制点不可用，必须换掉 |
| 4 | **对齐策略** | 三模式：`None`（固定相机/治具）、`PoseFromMatching`（接匹配位姿）、`PlanarDeformable`（内置投影对齐） | 真实产线大量是固定相机或治具定位，强制投影对齐会把简单场景做复杂。三模式覆盖「固定→刚性→透视」全谱 |
| 5 | **多配方** | 仿 `MatchingTemplateEntry`：每个配方存参考图路径、矫正四点、参考路径点列、胶宽/容差/极性、学习指纹 | 与平台一致（用户已熟悉 Matching 的配方列表交互），多产品换型不改流程 |
| 6 | **模型持久化** | **存输入、运行期重建**：bead 模型与 planar 模型**都没有 write/read/serialize 算子**（反射确认），因此落盘的是「参考图 + 矫正四点 + 路径点列 + 参数」，模型在运行期按**参数指纹**惰性重建 | 这是 HALCON 的硬约束，不是设计取舍。planar 模型重建较贵 → 缓存 + 指纹失效；bead 模型重建很便宜 → 可每轮重建 |
| 7 | **画布交互** | **不改共享控件**：在插件视图里给 `ImageEdit` 叠加鼠标事件，用其公开的 `HWindow` 取图像坐标实现「**逐点拾取**」 | `ImageEdit` 的右键菜单只有矩形/圆形/椭圆，`DrawShapeType` 也无折线类型（`Rectangle, Ellipse, Circle, Region, Mask`）——**扩展共享控件会影响所有插件**。叠加式实现零侵入，一期即可用。逐点拾取同时天然产出「可编辑的点列」，与自动提取/导入两条入口共用同一数据结构 |
| 8 | **判定语义** | 沿用 BlobDetect 口径：**NG 是正常结果**（`Success` 保持 true），只有「执行失败」才 `Fail(...)` | 平台既有约定，NG 时下游仍要拿到结果与标注图，不能当异常处理 |
| 9 | **可视化** | 复用 BlobDetect 的离屏渲染法（`open_window` → `set_part` → `disp_obj` → `dump_window_image`）把参考路径、左右轮廓、错误段画进标注图 | 范例的 `gen_parallel_contour_xld` + `intersection_closed_contours_xld` 只是为了让「太细」段看起来更直观，属**可选美化**，不作为算法依赖 |

## 三、契约与端口

### 3.1 输入端口

| 端口名 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `SrcImage` | `HImage` | ✅ | 待检测图像（接图像采集） |
| `RecipeName` | `string` | ❌ | 配方名/产品型号；未连接或为空时用「默认配方」。**照抄 Matching 的选配方机制** |
| `AlignedImage` | `HImage` | ❌ | 仅 `PoseFromMatching` 模式使用：接匹配插件的 `AlignedImage` |
| `RoiRegion` | `HRegion` | ❌ | 可选检测范围（`reduce_domain` 提速）；未连接 = 整图 |
| `Transform` | `CalibrationTransform?` | ❌ | **mm 换算的首选来源**（接标定插件的 `Transform` 输出）。未连接时才回退到手填 `PixelSizeMm`（见 §5.4） |

> `RoiRegion` 只缩小计算域，**不改变坐标**（`reduce_domain` 保持原坐标系），下游拿到的坐标仍是整图坐标。

### 3.2 输出端口

| 端口名 | 类型 | 说明 |
| --- | --- | --- |
| `IsOk` | `bool` | 判定结果（true = 合格） |
| `NgReason` | `string` | NG 原因（如「缺胶 2 段、过薄 1 段」）；OK 时为空串 |
| `AnnotatedImage` | `HImage` | 标注图（原图 + 参考路径 + 左右轮廓 + 错误段红标 + 判定文字） |
| `ErrorCount` | `int` | 错误段总数（已按 `MinErrorLength` 过滤） |
| `ErrorTypes` | `HTuple` | 各错误段类型字符串数组，与下面三个逐项对齐 |
| `ErrorLengths` | `HTuple` | 各错误段长度（像素） |
| `ErrorRows` | `HTuple` | 各错误段中心 Row |
| `ErrorCols` | `HTuple` | 各错误段中心 Col |
| `TotalErrorLength` | `double` | 错误段总长度（像素，或 mm——按 `UnitOutput`） |
| `NoBeadCount` | `int` | 「缺胶」段数 |
| `TooThinCount` | `int` | 「太细」段数 |
| `TooThickCount` | `int` | 「太粗」段数 |
| `MispositionCount` | `int` | 「位置偏移」段数 |
| `ErrorSegments` | `HXLD` | 错误段轮廓集合（可直接给下游/存图） |
| `BeadContours` | `HXLD` | 检出的左右胶路轮廓（2 个对象；OK 时也可用于复检） |
| `AlignedImage` | `HImage` | 对齐后的图（供下游复用；由 `OutputAlignedImage` 开关控制，关闭时输出空） |

> 端口名一经发布即是对外契约（改名 = 断链），实现时**不要**顺手重命名。

### 3.3 落盘 DTO（插件内部，不进 `Core.Interfaces`）

配方条目与结果都**只在本插件内使用**，因此**放在插件工程内**，不进公共契约程序集——避免 `Core.Interfaces.dll` 被拷进 `Modules\` 的红线风险（AGENTS.md 红线 2）。

```csharp
// Plugins\Plugin.BeadInspect\Models\BeadRecipeEntry.cs
public class BeadRecipeEntry : INotifyPropertyChanged
{
    public string Name { get; set; } = "";              // 配方名（RecipeName 端口按它匹配）
    public string RefImagePath { get; set; } = "";      // 参考图路径（学习/重学时载入）
    public string RefPointsJson { get; set; } = "[]";   // 参考路径点列 [[row,col],...]（统一中间表示）
    public string RectifyQuadJson { get; set; } = "";   // 矫正四边形四点 [[row,col]x4]，空 = 不矫正
    public double TargetWidth { get; set; } = 15;       // 目标胶宽（像素）—— P3 实测 15.26
    public double WidthTolerance { get; set; } = 8;     // 胶宽容差（像素）—— P12：须 ≥ 提取偏差 8.39
    public double PositionTolerance { get; set; } = 30; // 位置容差（像素）—— P9：待现场标定
    public string Polarity { get; set; } = "dark";      // dark / light
    public string LearnedSignature { get; set; } = "";  // 学习指纹（点列+参数+参考图哈希）

    [JsonIgnore] public HTuple? RuntimeBeadModel;        // 运行期句柄（不落盘）
    [JsonIgnore] public HTuple? RuntimePlanarModel;      // 同上
    [JsonIgnore] public string? RuntimeModelSource;      // 当前句柄对应的指纹
    [JsonIgnore] public HObject? RuntimeContour;         // 参考路径 XLD（显示用）
}
```

**为什么 `LearnedSignature` 是必要的**：模型不能落盘，只能重建。指纹把「重建所需的全部输入」压成一个字符串；运行期发现指纹不符即重建。这与 Matching 的 `LearnedSignature`（参数改了 → 提示「需重新学习」）是同一套范式。

## 五、运行语义

### 5.1 执行流程

```
RunAlgorithm
├─ 1. 取图（SrcImage.ActualValue 为空/未初始化 → Fail）
├─ 2. 选配方：RecipeName 端口 → 默认配方 → 库首条（都无 → Fail）
├─ 3. 对齐（按 AlignMode 分支）
│     ├─ None              : aligned = src
│     ├─ PoseFromMatching  : aligned = AlignedImage.ActualValue（未连线 → Fail）
│     └─ PlanarDeformable  : 惰性重建 planar 模型 → find → hom_mat2d_invert
│                            → hom_mat2d_translate(RowT, ColT) → projective_trans_image
├─ 4. 取/建 bead 模型（指纹校验；不符则重建）
├─ 5. apply_bead_inspection_model(aligned, model) → left/right/errorSegment/errorType
├─ 6. 过滤（按 MinErrorLength 丢碎段）→ 统计四类计数 → IsOk = (ErrorCount == 0)
├─ 7. 渲染标注图（离屏窗口）→ 赋输出端口
└─ 8. DisplayViewIndex > 0 时 PublishPreview
```

关键调用（照抄签名，勿猜）：

```csharp
// 建模型（每配方一次；参数或点列变化则重建）
// ✅ P1 实测：一期用折线（gen_contour_polygon_xld）——用户给的是「经过点」，
//    折线语义最直接；NURBS（gen_contour_nurbs_xld，需控制点+权重+阶数）留作二期可选平滑
HOperatorSet.GenContourPolygonXld(out HObject contour, rows, cols);
HOperatorSet.CreateBeadInspectionModel(contour, targetWidth, widthTolerance,
    positionTolerance, polarity, new HTuple(), new HTuple(), out HTuple beadModel);

// 检测
HOperatorSet.ApplyBeadInspectionModel(aligned, out HObject left, out HObject right,
    out HObject errorSeg, beadModel, out HTuple errorType);
```

> 两种口径（折线 / NURBS）**已由探针 P1 实测裁决**：都能建模型，折线长度 1015.68px、NURBS 1006.23px（同一点列）。
> 选折线的理由见 §7.1 P1。`GenContourNurbsXld` 的签名保留在附录速查里备用。

### 5.2 失配的强制失败（中文提示必须给「下一步」）

| 条件 | 结果 |
| --- | --- |
| `SrcImage` 为空/未初始化 | `Fail("输入图像为空或未初始化")` |
| 无可用配方（库空且 `RecipeName` 未命中） | `Fail("未找到可用配方：请在配置界面新建配方并学习参考路径")` |
| `AlignMode=PoseFromMatching` 但 `AlignedImage` 未连线 | `Fail("对齐模式为「匹配位姿」但未连接 AlignedImage：请连接匹配插件的对齐图输出，或改用其它对齐模式")` |
| 平面匹配未命中（`score < MinScore`） | `Fail($"图像对齐失败：平面匹配分数 {score:0.00} 低于阈值 {MinScore:0.00}，请检查参考图与当前图是否为同一平面")` |
| 参考路径点列不足 2 点 | `Fail("参考路径至少需要 2 个点：请在配置界面拾取或导入胶路中心线")` |
| 点列近似重合/退化 | `Fail("参考路径退化（各点几乎重合）：无法生成有效曲线")` |
| 未学习（无模型且无法重建） | `Fail("配方未学习：请先在配置界面载入参考图并点击「学习」")` |
| 单位输出为 mm 但无当量来源 | `Fail("输出单位设为毫米，但既未连接标定变换也未填写像素当量：请补其一")` |
| 算子抛异常 | 基类兜底转本节点失败；如需中断当轮 `override bool RethrowOnException => true;` |

> **NG 不走 `Fail`**：检出缺胶/太细/太粗/偏移时 `Success` 保持 true，结果照常输出，仅在 `NgReason` 留痕。

### 5.3 模型生命周期（本设计最需要说清的一点）

```
配置态「学习」按钮
  → 载入参考图 → 建 planar 模型（贵，一次）
  → 由点列建参考路径 XLD → 建 bead 模型（便宜）
  → 写 LearnedSignature

运行期每轮
  → 指纹不符（换配方/改参数）→ 重建对应模型
  → 指纹相符 → 直接复用缓存句柄
```

- **planar 模型**：`create_planar_uncalib_deformable_model` 是训练型算子，耗时明显 → 必须缓存，且**只在配置态与换配方时重建**；
- **bead 模型**：`create_bead_inspection_model` 是几何模型，开销小 → 允许每轮重建，实现上仍走同一缓存路径；
- 两个句柄都是 `HTuple` 非托管资源，**换配方/释放插件时必须 `clear_bead_inspection_model` 并释放旧句柄**，否则泄漏（对标 Matching 的 `RuntimeModelId` 生命周期管理）。

### 5.4 mm 换算（`UnitOutput = Mm`）

**首选来源是标定插件的 `Transform` 端口**，`PixelSizeMm` 仅作未接标定时的兜底。口径与「坐标变换」插件（`PoseTransform`）**严格对齐**——那里已经踩过一遍，本插件照抄结论，不重新发明：

| 情形 | 处理 |
| --- | --- |
| 接了 `Transform` | 用 `CalibrationTransform.MmPerPixel` 换算长度/面积；面积按当量**平方**缩放 |
| 未接 `Transform`，但填了 `PixelSizeMm > 0` | 用 `PixelSizeMm` 换算 |
| 未接 `Transform` 且 `PixelSizeMm <= 0`，但 `UnitOutput = Mm` | **`Fail`**（不静默按像素输出）——「输出单位设为毫米，但既未连接标定变换也未填写像素当量：请补其一」 |
| 接了 `Transform` 但**图像尺寸不符**（`SourceImageWidth/Height` 与当前图不一致） | **`Fail`**（换分辨率/换相机 → 旧标定失效）——「标定失配：当前图 W×H ≠ 标定图 W×H，换分辨率/换相机后需重新标定」 |
| 接了 `Transform` 且 `Kind = PixelScale` | 只取 `MmPerPixel` 做长度换算；**不**使用其矩阵（该模式矩阵除对角线外为 0，无机械坐标含义） |
| `Transform` 为 `null` 但端口已连线（上游未产出） | 同「未接」处理并回退 `PixelSizeMm`；两者都无则 `Fail` |

> 纪律来源：`PoseTransform` 的「失配必须明确失败，绝不静默用旧标定」（见 `PoseTransformPlugin.cs:25` 与 `:447`）。本插件的失配检查**同样必须报出「下一步」**。

### 5.5 失败与 NG 的边界（复述，最易写错）

- **执行失败** → `Fail("…")`，`Success = false`：图像为空、无配方、对齐未命中、路径退化、未学习、单位换算缺来源。
- **判定 NG** → `Success` 保持 **true**，结果与标注图照常输出，`NgReason` 留痕（检出缺胶/太细/太粗/偏移）。

### 6.2 画布交互（不改共享控件的实现要点）

| 操作 | 行为 |
| --- | --- |
| 左键点击 | 在点击处**追加**一个点（自动插到离点击处最近的线段之间，而非一律追加到末尾——避免补点时把路径画成来回折返） |

### 6.3 矫正四边形（`PlanarDeformable` 模式）

范例硬编码了 4 个参考点与矫正目标尺寸（`W=5.4, H=3.4`）。通用化后：

### 6.4 自动提取中心线（一期，决策 D3）

**目的**：用户不必逐点描一条几十点长的胶路，而是**载入一张良品图 → 点「自动提取」→ 得到点列**，再在画布上微调。这是换产品效率的关键。

**前提**：用于提取的图必须是**良品图**（有完整胶路）且**已对齐**（或本来就是参考位姿）——提取的是「胶路中心线」，姿态错了整条路径就错了。

**算法链**（✅ = 已实测跑通，见 §7.1 的 P6/P7/P8/P12）：

```
良品图（已对齐）
 └─ ① 缩域到平面区：ReduceDomain(good, plane)          ← 排除投影变换留下的大片黑边
 └─ ② 取胶区：**与无胶参考图做 AbsDiffImage** ✅
      AbsDiffImage(good, refAligned) → BinaryThreshold('smooth_histo','light')
      无参考图时回退 black-hat：GrayClosingRect(15,15) − 原图 → BinaryThreshold('light')
      ⚠ 绝不能用 BinaryThreshold(...,'dark')：平面区里含大块暗区（拱形开口 65323px），
        会整块被当成胶（实测），细胶线反而漏掉
 └─ ③ 去噪取主胶条：ClosingCircle(3.5) → Connection → 按面积取最大连通域 ✅
 └─ ④ 骨架化：Skeleton(region, out skeleton) ✅
 └─ ⑤ 骨架转轮廓：GenContoursSkeletonXld(skeleton, out contours, 5, 'filter') ✅
      mode 只有 'filter' 合法（其余报 #1302，实测）；length=5 丢短枝
 └─ ⑥ **树直径合并**（关键，非可选）✅
      骨架是"树"（实测 3 段交汇于一点）：只取最长一条只覆盖 68.9%，
      未覆盖的 341px 会被误判「缺胶」；树直径（两次 DFS）覆盖 98.2%，短枝自动排除
 └─ ⑦ 平滑：SmoothContoursXld(merged, out smoothed, 11) ✅
 └─ ⑧ **托管侧等距抽稀**到 40~80 点 ✅
      不用 GenPolygonsXld（实测所有 type 报 #1301，本版本不可用）；
      按累计弧长等距取点，保端点与走向
 └─ ⑨ 取点列：GetContourXld(…) → 存入 RefPointsJson ✅
```

> 上表每一步都在 `tools\BeadProbe` 实测通过；`mode`/`type` 等参数值集**已实测裁决**（P7/P8），不再是推断。
> 唯一的**硬性算法要求**是 ⑥ 树直径——这是本次探针最重要的发现。

**关键取舍**

| 项 | 结论 | 理由 |
| --- | --- | --- |
| 提取结果是「点列」而非 XLD | 直接落进 `RefPointsJson`，与逐点拾取/导入**共用同一数据结构** | 三条入口一个出口；用户提取后还能继续手工增删点 |
| **分叉处理** | **必须用「树直径」合并**，不是"取最长一条" | 实测只取最长覆盖 68.9%（丢 31%），未覆盖处**误判缺胶**；树直径覆盖 98.2% |
| 是否保序 | 树直径法**天然产出有序路径**（按节点父子关系还原并逐段定向） | bead 模型对曲线方向敏感；端点顺序决定 `PositionTolerance` 的符号方向 |
| 点数控制 | **托管侧等距抽稀**到 40~80 点 | `GenPolygonsXld` 本版本不可用（P7）；实测抽稀到 40 点不增大偏离（P12） |
| 分割口径 | **参考图差分优先**，black-hat 回退 | 差分实测 σ=0.96px（最紧）、覆盖最全；black-hat 只覆盖部分 |
| 失败语义 | 提取不到（差分后无主胶条 / 骨架为空）→ 界面红字提示，**不自动写入空点列** | 空点列会覆盖用户已拾取的点，是破坏性操作 |

**与逐点拾取的关系**：两者**不互斥**——推荐工作流是「自动提取 → 画布微调 → 保存」，这也是 §8.2 步骤 6 的验收内容。

### 7.1 探针实测结论（2026-10-04 已跑完）

> 探针工程：`tools\BeadProbe\`（临时脚手架，**结论已回写本节，工程用完即删**）。
> 原始输出：`tools\BeadProbe\probe_result.txt`。**以下全部为实测值，不是推断**。

**环境**：HALCON 23.05 Progress；样图 8 张均 1280×1024、单通道 byte；`HALCONROOT` 正常。

#### P1 点列 → 曲线口径：**两者都可用，取折线**

| 口径 | 结果 |
| --- | --- |
| `gen_contour_nurbs_xld`（范例口径，14 控制点 + 权重15 + 阶3） | 成功，长 1006.23px |
| `gen_contour_polygon_xld`（折线） | 成功，长 1015.68px |

两者建模型都成功，模型内省参数一致（`target_thickness=14 / thickness_tolerance=7 / position_tolerance=30`）。
**结论：一期用折线**——用户给的是"经过点"，折线语义最直接、无权重/阶数等额外概念；NURBS 作为可选平滑留二期。

#### P2 矫正四边形：**做矫正更稳，但非必需**

| 口径 | 7 图平均 score | 失败数 |
| --- | --- | --- |
| 按范例做投影矫正 | **0.9248** | 0 |
| 不做矫正 | 0.9145 | 0 |

矫正略优（+0.010），但**两种都不失败**。**结论：`RectifyQuadJson` 保持可选**——不填时跳过矫正，对接近正对的相机足够；填了更稳。默认留空，界面给"可选"标注。

#### P3 胶宽像素口径：**实测 15.26px（不是范例的 14）**

`adhesive_bead_01` 实测：平均半宽 7.63px（σ=0.96）→ **平均胶宽 15.26px**，最粗处 18px。
`TargetWidth ≈ 15`。`WidthTolerance` 的 3σ 部分（≈3）只覆盖胶宽自然波动，
**还要叠加提取路径的偏差（P11：最大 8.39px）→ 终值取 8，见 P12**。

**关键交叉验证**：本坐标系胶路全长 1096.45px ÷ 范例坐标系 1006.23px = 尺度因子 1.090；
范例 `TargetWidth=14 × 1.090 = 15.26px` —— **与实测 15.26px 完全一致（比值 1.00）**。
两条独立路径得到同一数字，互为印证。

#### P4 真值表（7 张样图，范例控制点 + 范例参数）

| 图号 | 对齐 score | 错误段 | 类型 |
| --- | --- | --- | --- |
| 01 | 0.8984 | 0 | **OK** |
| 02 | 0.9818 | 0 | **OK** |
| 03 | 0.8937 | 2 | too thin ×1, incorrect position ×1 |
| 04 | 0.8788 | 0 | **OK** |

| 07 | 0.9887 | 4 | incorrect position ×3, no bead ×1 |

**7 张全部对齐成功（score 0.868~0.989）**。此表即断言真值表。

#### P5 planar 模型重建耗时：**284~360ms → 必须缓存**

两次实测 302ms / 284ms / 360ms。**结论：planar 模型必须缓存 + 指纹失效**，每轮重建会在产线节拍上明显拖慢。

#### P6 自动提取中心线：**可行，但必须用「树直径」合并分支**

提取链路（全部实测通过）：亮平面区内 `reduce_domain` → **与无胶参考图做 `abs_diff_image`** → `binary_threshold('smooth_histo','light')` → `closing_circle(3.5)` → 取最大连通域 → `skeleton` → `gen_contours_skeleton_xld(…,5,'filter')`。

**三个必须写进实现的实测事实**：

1. **分割必须用「参考图差分」，不能用「取暗」**。胶是亮面上的一条细暗线，平面区里还含大块暗区（拱形开口）：
   - 直接 `binary_threshold(...,'dark')` → 取到 65323px 的拱形开口（663×419），**根本不是胶**；
   - black-hat（`gray_closing_rect(15,15)` − 原图）→ 2864px，仍只覆盖部分；
   - **参考图差分 → 16019px，平均半宽 σ=0.96px（最紧）**。
   本仓库恰好有 `adhesive_bead_ref.png`（无胶参考图），故一期主推差分口径；无参考图时回退 black-hat。

2. **骨架是「树」，只取最长一条会丢 31% 路径**。实测骨架 3 段，全部交汇于 (435,804)：
   `755.22px` + `321.09px` + `20.14px`（短枝），合计 1096.45px。
   - 「取最长一条」→ 755px，覆盖 **68.9%** → 未覆盖的 341px 会被**误判「缺胶」**；
   - **「树直径」（两次 DFS 求最长路径）→ 1076.31px，覆盖 98.2%**，短枝自动排除，无需另写"去毛刺"规则。
   **结论：实现必须用树直径法**（算法已在本探针 `LongestPathThroughTree` 中验证）。

3. **抽稀点数对结果几乎无影响**（见下 J），但会影响人工微调手感。

#### P7 `gen_polygons_xld`：**本版本不可用，改托管侧抽稀**

实测**所有候选 type 全部报 #1301**：`lines` / `lines_color` / `lines_circles` / `lines_ellipses` / `max_deviation` / `max_distance`（整数 0~3 报 #1201）。
**结论：一期不用 `gen_polygons_xld`**，改为**托管侧等距抽稀**（按累计弧长等距取点，保端点与走向，见探针 `Downsample`）。
实测抽稀到 40 点**未增大偏离**（最大偏离 8.39px 不变，平均 1.98→2.18px）→ **40~80 点足够**。

#### P8 `gen_contours_skeleton_xld` 的 `mode`：**只有 `'filter'` 可用**

实测：`filter` 可用；`nurbs` / `polygon` / `original` / `lines` / `smooth` / `filter_smooth` 全部报 #1302。
**结论：固定用 `'filter'`**，`length` 参数用 5（丢短枝）。

#### P9 位置偏移分布：**本批样图不足以定 `PositionTolerance`**

基准取图01中心线，其余图最大偏移 555~630px —— 但**这些图本身含 NG**，且基准图01未经范例验证为良品。
**结论：`PositionTolerance` 默认值待定**，需在有「确认良品」样本后重测；一期给保守默认并标注"需现场标定"。

#### P10 `target_thickness` 有下界：**< 6 报 #3716**（重要）

实测扫值：1/2/4 **失败**（#3716），6/8/10/14/20/40 可用。
**结论：插件必须对 `TargetWidth` 做下限保护**（`<6` 时给中文提示或夹到 6），不能直接把用户填的值丢给算子——否则现场会看到一句英文 HALCON 错误。
（本项目实测胶宽 15.26px 高于该下界，不冲突；但换产品后可能低于。）

#### P11 坐标系一致性（决定性对照）：**同一坐标系，平均偏离 1.98px**

提取中心线 vs 范例 `ContourRef`：
- 提取线→范例线：有向 Hausdorff（最大偏离）**8.39px**，平均偏离 **1.98px**
- 范例线→提取线：有向 Hausdorff **3.98px**
- 长度比 1.070（骨架链码对数字化曲线的固有高估上限约 8%，**在范围内**）

**结论：对齐后的图与范例 `ContourRef` 是同一坐标系**，范例参数可直接换算使用。
最大偏离 8.39px 出现在局部（分叉/端点处），这正是下一条要解决的。

> ⚠ 踩坑记录：`distance_cc` 的 **max 是"全体点对的全局最大距离"**（实测 619.8px ≈ 拱形自身尺度），
> 不是"提取线偏离参考线多远"。用它判读会得出完全相反的结论——本探针改在托管侧算**有向 Hausdorff**才得到正确值。

#### P12 容差口径（收尾的关键发现）：**`tolerance` 主导误报，点数几乎无关**

用提取点列，扫「点数 × tolerance」，与 P4 真值表比错误段数偏差：

| 点数 | tol=1 | tol=2 | tol=4 | **tol=8** |
| --- | --- | --- | --- | --- |
| 905（全点） | +15,+3,0,+20,+17,+34,+5 | +6,+11,+9,+10,+6,+4,+9 | +1,+6,+2,+2,+3,+20,+10 | **+1,0,+1,0,+1,0,+3** |
| 40 | +13,+5,0,+17,+15,+29,+3 | +6,+10,+8,+9,+6,+3,+5 | +1,+3,+1,+2,+3,+18,+6 | **+1,0,0,0,+1,0,0** |
| 150 | +11,+3,0,+16,+15,+31,+3 | +5,+11,+6,+9,+6,+3,+5 | +1,+3,+3,+3,+6,+19,+10 | **+1,0,+1,0,+1,0,+1** |

**两个结论**：
1. **点数无关**（40 与 905 结果几乎相同）→ 抽稀到 40~80 点安全，可放心做人工可编辑的点列；
2. **`tolerance` 主导**：`tol=1` 严重过报（提取路径的 2~8px 偏差被判"太细/太粗"），`tol=8` 才回到真值附近。
   范例的 `WidthTolerance=7` 是它自己坐标系下的值；本坐标系实测胶宽 15.26px、提取偏差平均 1.98px/最大 8.39px，
   故**容差应 ≥ 提取偏差上界**，一期默认取 **8**（而非机械照搬 7）。

> 这条直接修正了本方案 §4.1 的默认值：`WidthTolerance` 默认 **8**（不是 7），并在界面注明"自动提取的路径含 2~8px 偏差，容差需大于该偏差"。

#### 探针阶段小结（对方案的影响）

| 影响 | 改动 |
| --- | --- |

4. 本插件**不修改** `Shard\Core.PluginGenerators`，因此不触发「重建全部插件」的连锁要求；若实现中确实要改生成器，必须重建**全部**插件工程。

## 十、通用性分析

### 10.1 本设计刻意留出的通用性

| 维度 | 覆盖方式 |
| --- | --- |
| **对齐条件差异大** | 三模式覆盖：固定相机（`None`）→ 治具/刚性命中（`PoseFromMatching`）→ 透视倾斜（`PlanarDeformable`） |
| **路径来源差异大** | 点列统一中间表示，**画布逐点拾取 / 良品图自动提取 / 文件导入**三条入口一期并存（§6.4），多入口一出口 |
| **多产品换型** | 配方库 + `RecipeName` 端口，运行期可被上位机/变量切换；换型时「自动提取 + 微调」可在分钟内完成 |
| **明暗两种工艺** | `Polarity` 暗胶/亮胶可配（这是 HALCON 模型的硬约束，只能二选一，见 10.2） |
| **单位口径** | 像素为主、mm 可选；**mm 优先接标定插件 `Transform`**（失配即失败，见 §5.4） |
| **不锁死在「涂胶」** | 算法只依赖「一条已知曲线 + 沿线宽度的明暗带」——密封胶、焊缝、点胶、涂布边缘、线缆外皮同构 |

### 10.2 HALCON bead 模型的硬约束（✅ 全部实测确认，不要试图绕过）

1. **输入图必须已对齐**到参考位姿——否则「位置偏移」类错误失去基准；
2. **只能一条参考路径**——多条胶条要么合并、要么建多个模型（二期扩展）；
3. **极性只能二选一**（`'dark'` 或 `'light'`）——同一视场里既有暗胶又有亮胶无法用一个模型覆盖；
4. **宽度以像素计**——mm 口径必须外部给当量；
5. **模型不可序列化**——必须存输入并重建（本设计第 5.3 节）；
6. **`target_thickness` 有隐藏下界 6**（P10 实测：1/2/4 报 #3716，6 起可用）——必须做下限保护，
   否则现场会看到一句英文 HALCON 错误（已写进 §4.2 的钩子与断言 14）；
7. **`gen_polygons_xld` 在本 HALCON 23.05 上不可用**（P7 实测：所有候选 type 报 #1301）——
   点列简化必须在托管侧做（等距抽稀），**不要**把这个算子写进实现；
8. **`gen_contours_skeleton_xld` 只有 `mode='filter'` 合法**（P8 实测，其余报 #1302）——固定写死；
9. **骨架必须按「树直径」合并**（P6 实测：只取最长一条覆盖仅 68.9%，未覆盖处误判缺胶）——
   这是提取算法的硬要求，不是优化项；
10. **`WidthTolerance` 必须大于提取路径的偏差上界**（P11/P12 实测：提取中心线对范例参考线
    平均偏离 1.98px、最大 8.39px；tol=7 过报、tol=8 回到真值）——自动提取的路径不是"完美的"
    范例线，容差要把这笔偏差算进去。

## 十一、风险与边界

| 风险 | 后果 | 缓解 |
| --- | --- | --- |
| planar 模型重建耗时 | 换配方/改参数时有明显卡顿 | **已量化（P5）：284~360ms** → 指纹缓存；仅配置态与换配方时重建 |
| 参考路径质量决定成败 | 点列太稀 → 曲线偏离真实胶路 → 大面积误报 | **已量化（P12）：tol=1 时最多 +34 段误报，tol=8 归零** → 默认容差 8、界面注明原因；画布叠加显示路径与实测轮廓 |
| 提取路径在分叉/端点处偏差大 | 局部偏离可达 8.4px（P11），逼近容差边界 | 树直径合并已消除 98.2% 的分叉问题；剩余偏差靠容差吸收；用户可在画布上微调那几个点 |
| 自动提取依赖「无胶参考图」 | 现场可能没有无胶图 | 一期主推差分口径（有参考图时），black-hat 回退（无参考图时）；两种都已实测 |
| `PositionTolerance` 无现场依据（P9） | 默认值 30 可能偏大/偏小 | 界面标注"需现场标定"；有良品样本后按 P9 方法重测 |
| 画布交互体验受限 | 逐点拾取比拖拽画线繁琐 | 一期可接受（点列本就要能微调）；二期再评估扩展共享控件 |
| 非托管句柄泄漏 | 换配方频繁时内存增长 | 换配方/释放插件时 `clear_bead_inspection_model` + 释放旧句柄；断言 9 覆盖缓存路径 |
