## 根因（实测，不是推测）

| 事实 | 数字 |
|---|---|
| 每步骤节点 | **45 个可视元素 + 14 个右键菜单对象**（`FlowCanvasView.xaml:161-528`，菜单在 `:174-219` 每实例一份） |
| 每根连线 | 2 个可视元素 + 5 个菜单对象（`:1144-1226`） |
| 3542 步流程总量 | 4532 节点 + 7083 线 → **约 20 万可视元素、8.5 万菜单对象** |
| 单次重建（你机器配置：数据线开） | **40.9 s**（数据线关时 18 s） |
| 其中 VM 侧 | 2.1 s（4%）→ P1 那类优化打不到点上 |

**为什么 PLC 梯形图不卡**：它不建「每行 N 个 UI 元素」，而是画在一个绘制表面上、只保留视口内对象。我们是每项一个 WPF 元素，元素数随节点数线性增长，WPF 逐个走模板/绑定/布局。

## Phase A —— 让 3000 节点能打开（本轮做，1~2 天）

### A1 右键菜单从「每实例一份」改成「共享单实例」（最大单笔，风险最低）

- 现状：`StepNodeTemplate` 内联 `ContextMenu` 14 个对象 × 3542；容器 13 × 990；`ModuleLinkTemplate` 5 × 7083 ≈ **8.5 万对象**，绝大多数用户从没打开过。
- 改法：三处各抽成 UserControl 资源里的**一个** `ContextMenu`，`MenuItem.Command` 用 `{Binding PlacementTarget.DataContext.XxxCommand, RelativeSource={RelativeSource Self}}`；子菜单 `ItemsSource="{Binding PlacementTarget.DataContext.Bindings, ...}"`。
- 断言影响：`RenderProbe.ProbeCanvasEditingEntries`（`:1912-1942`）现在遍历每个节点的 `ContextMenu`，改为查共享菜单 + 用 `PlacementTarget` 模拟右键。
- 预期：-8.5 万对象。

### A2 连接点瘦身

- 现状：`NodeInput`/`NodeOutput` 走 Nodify 默认模板，每个 7 元素、常态 `Opacity=0` 仍参与命中；每节点 14 个。
- 改法：给 `FlowConnectorStyle`（`:120-158`）写自定义 `Template`，只留「透明可命中 Border + 1 个 Ellipse」。
- 预期：-4 万元素。

### A3 大流程自动折叠（会话态，不污染落盘）

- `FlowCanvasViewModel.RebuildCore` 挂接流程时：若步骤数 > 600，把该流程所有容器置为折叠，记在 VM 内的会话集合里（不写 `FlowLayoutStore`）；状态栏提示「大流程已自动折叠，点击 ∇ 展开」。
- 用户手动折叠/展开时写回会话集合并同步 `Layout`（用户意图优先）。
- 效果：3542 步 → 只画顶层约 150 个节点，`Nodes` 直接小一个数量级。

### A4 流程树虚拟化

- `ProcessView.xaml:491` 的 `TreeView` 现在无虚拟化：3542 个根项全实现，是流程栏自己的卡顿源。
- 改法：自定义 `TreeView` 模板（`ScrollViewer.CanContentScroll="True"`）+ `ItemsPanel` 换 `VirtualizingStackPanel`（`VirtualizationMode=Recycling`）。必须改模板——默认模板是 `CanContentScroll="False"`，只加 attached property 无效。
- 连带修：`TreeViewBehavior.TrySelectDescendant`（`:102-111`）依赖 `ContainerFromIndex`，虚拟化后屏幕外返回 null → 改成「先展开祖先 → `BringIntoView` → 重试一次」，失败时退回滚动定位。

### A5 数据线在超大流程下降级

- `ShowDataLinks=true`（你的配置）且**当帧根数 > 1500** 时，只画非法线 + 与当前选中节点相关的线；工具栏开关旁显示「大流程已精简连线」。
- 用户手动切开关则不降级（尊重显式选择）。

### A6 方案加载反序列化移出 UI 线程

- `SolutionService.LoadAsync:140` 的 `await File.ReadAllTextAsync` 没有 `ConfigureAwait(false)`，续体回到 UI 线程做反序列化 + 迁移（3.9 MB JSON）。加 `ConfigureAwait(false)`，只在最后切回调用方上下文。
- 预期：打开时 UI 少阻塞 1~2 s。

### A 验收（缺一条不算完成）

1. `--switch-perf open`（新相位，数据线开 + 树可见，量首次挂接）：3542 步从 **40.9 s** 降到 **< 2 s**。
2. `--switch-perf datalinks`（热切换，数据线全开）：从 40.9 s 降到 < 6 s（不开折叠时）。
3. 真机打开两份 `解决方案\压测-3000节点*.vms`：可交互、不冻结。
4. `FlowCanvasChecks` 全量仍 3501/0；`audit_root` 通过。

## Phase B —— 决策实验（0.5~1 天，A 完成后做）

临时把 `Nodes` 裁到「视口 + 缓冲」量一次 `--switch-perf datalinks`，看 `layout` 还能掉多少。**这只是实验，不进产品**——因为它会破坏 Nodify 的 `ItemsExtent`/框选假设。

产出：一个数字，决定要不要投 Phase C。

## Phase C —— 整块自绘（2~4 周，需单独批准）

只有 A+B 的数字证明「元素数量仍是瓶颈」时才做：

- 节点/泳道/连线全部画进一个 `FrameworkElement`，每节点预生成可冻结的 `DrawingGroup`，`OnRender` 只画视口内的项；平移缩放只改变换矩阵。
- 自己实现：命中测试（VM 的 `_frameRects`/`Location` 已够）、点选、框选、节点拖动、拖线、右键菜单、`FitToScreen`、缩放、参考线、小地图。
- 需重写 **19 条断言**（FLC-8/9/10/16/17/21×4/22/23 + `RenderProbe` 两组自检 + 6 条静态模板断言），并新增 3 条守门（框选不抛、多选拖动顺序正确、FitToScreen 覆盖全量）。
- 风险：交互全面重写，回归面最大；必须走架构评审 + `docs/code-changes/`。
